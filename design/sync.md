# 앱과 WIKI의 작업 연계

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

두 저장소의 작업 식별, PR, 승인, 복원과 부분 실패를 다룬다. [ADR 0017](../decisions/integration/0017-work-sync.md)의 연계 방향은 채택됐으며 원격 자동화는 미구현이다. 문서의 저장, 편집 수단은 [WIKI 저장](../discussions/knowledge/storage.md)이 소유한다.

11/08 문서 정리: 기존 주제 본문을 분리했다. 판단 날짜, 채택 상태는 원문과 연결된 ADR을 따른다.

## 두 저장소를 사용할 때

비공개 문서 저장소를 선택하면 코드와 WIKI의 Git 저장소는 두 개가 된다. 독립 배포 모듈의 소스 저장소는 기존 ADR 0009의 다른 역할이며, 코드 작업마다 세 저장소를 모두 수정한다는 뜻은 아니다. 하나의 Codex 세션에서 두 작업 경로를 다루는 구조는 가능하지만 허용 경로와 각 저장소 상태를 구분해야 한다.

11/04 보정: 앞선 설명은 변경된 저장소마다 PR을 준비하는 방식을 기본으로 적어 부담을 크게 제시했다. **별도 Git 저장소를 사용하는 것과 모든 변경에 PR을 강제하는 것은 다르다.** branch, PR 적용은 팀 정책이며, 저장소 정책이 허용하면 commit, push로 직접 공유할 수 있다. 앱 커밋 하나와 문서 커밋 하나를 항상 짝지을 필요도 없다. [GitHub push 안내](https://docs.github.com/en/get-started/using-git/pushing-commits-to-a-remote-repository).

11/05 사용자는 같은 작업의 앱, WIKI 커밋과 롤백을 함께 처리할 필요를 지적했다. 저장 시점만 나누고 버전의 대응 관계를 남기지 않으면 이 요구를 충족하지 못한다. 아래 B의 작업별 버전 연결과 후속 PR 자동화 2안 방향은 [ADR 0017](../decisions/integration/0017-work-sync.md)에 채택했다. 기록 커밋 형식, 명령 등의 상세는 후보이며 실제 Git 자동화나 롤백을 실행한 결과가 아니다.

### 여러 저장소를 하나의 프로젝트로 관리할 때

11/08 사용자는 모듈 코드와 공개 WIKI, 이후 적용 프로젝트의 backend, frontend, infra, private WIKI를 하나의 프로젝트로 관리하길 제안했다. 여기서 프로젝트는 다음을 구분해야 한다.

| 의미 | 제공하는 것 | 제공하지 않는 것 |
| --- | --- | --- |
| 로컬의 공통 작업 공간 | 관련 저장소와 문서를 한곳에서 탐색 | Git 이력, 원격, 권한, 동시 커밋의 통합 |
| GitHub Projects | 여러 저장소 Issue/PR의 진행을 모아 보는 보드 | 저장소를 담는 Git 루트, 접근 권한 상속, 교차 저장소 병합 트랜잭션 |
| 같은 계정/Organization의 저장소들 | 소유와 팀/저장소 권한을 정리할 기반 | 모든 저장소에 자동 통하는 기본 CI 토큰 |

추천은 독립 저장소를 유지하고 필요할 때 공통 보드로 추적하는 방식이다. Projects는 여러 저장소를 다룰 수 있지만 workflow는 저장소별이며 보드 접근 권한도 별도다. [GitHub Projects 자동화](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions).

같은 소유자 아래에서는 fine-grained PAT의 대상 저장소를 선택하거나 GitHub App을 필요한 저장소에 설치할 수 있다. 이는 소유, 권한 범위 덕분이며 공통 폴더나 Projects 보드에 묶었다는 이유가 아니다. 기본 GITHUB_TOKEN은 실행된 저장소 범위이므로 다른 WIKI의 PR 조작에는 필요한 별도 권한이 남는다. 실제 소유자, 계정 종류, 기능에 맞춰 자격 수단을 정하고 토큰 하나로 모든 프로젝트를 무제한 연결하지 않는다.

[PAT 범위](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [교차 저장소 인증](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow).

기존 코드/WIKI 두 버전 기록은 여러 코드 저장소를 쓰는 경우 관련 저장소별 기준 버전, 변경, 검증의 목록으로 확장할 필요가 있다. 그 작업에 바뀐 저장소만 PR/커밋을 만들며 변경 없는 frontend나 infra에 빈 커밋을 강요하지 않는다. 저장소 묶음이 원자성을 제공하지 않으므로 아래 부분 실패, 재개 조건을 그대로 적용한다. 다중 코드 루트의 분석 범위, 권한, 완료 조건은 후속 명세 대상이며 현재 연결 도구의 단일 코드 루트 지원을 확장 완료로 보지 않는다.

모듈 자체의 공개 WIKI와 소비 프로젝트의 private WIKI는 같은 연결 절차를 사용하되 공개할 수 있는 정보가 다르다. 11/08 채택한 C 배치와 자체 적용 순서, 비밀값 비기록 조건은 [모듈 자체 WIKI — 「모듈 자체의 WIKI」](module.md)에 통합한다. 여기서 WIKI 저장소는 PR과 CI를 적용할 일반 Markdown Git 저장소를 뜻한다. 새 Git, Projects, Organization, 토큰, CI를 생성하지 않았다.

### 원자성과 작업 단위

Git의 `push --atomic`은 한 원격에 대한 ref 갱신을 묶는다. 서로 다른 원격 두 개의 commit, push, PR 병합을 하나의 트랜잭션으로 만드는 기능은 아니다. 한 명령에서 순서대로 호출해도 중간 실패는 남는다. [Git push](https://git-scm.com/docs/git-push).

따라서 추천 목표는 **검증한 코드와 문서 버전을 하나의 작업으로 연결하고, 일부만 반영됐으면 감지, 재개하는 것**이다. 코드, 문서가 모두 바뀌는 작업은 같은 완료 단위로 다룬다. 코드만 바뀌고 문서가 여전히 유효하면 기존 문서 버전을 연결하고 빈 커밋은 만들지 않는다. 문서 정정만 있으면 반대로 같은 코드 버전을 유지한다.

프로젝트 터미널에서 `git -C <wiki-path> ...`로 WIKI 저장소를 지정할 수 있다. 앱의 remote를 바꾸는 것이 아니라 각 경로의 독립 Git을 사용한다. [Git의 -C 옵션](https://git-scm.com/docs/git). 저장, 검증, 공유, 배포 완료를 같은 상태로 취급하지 않는다.

### 연계 대안

| 안 | 방식 | 장점 | 부담, 한계 |
| --- | --- | --- | --- |
| A | 작업 식별과 두 저장소의 커밋, 검증 결과를 수동으로 기록 | 도구 개발 없이 시작, 기존 Git, PR 유지 | 누락, 오타, 부분 반영 확인을 사람이 반복 |
| B — 방향 채택 | 같은 기록을 쓰고 작은 공통 절차로 두 상태를 점검. commit, 공유, 복구 조작은 선택 보조 기능으로 묶음 | 앱 Git과 WIKI를 분리하면서 작업별 조회, 재개를 통일 | 중간 실패, 동시 변경, 권한 시험과 보조 구현 필요. 원자성은 제공하지 않음 |
| C | 앱 저장소가 WIKI를 submodule로 연결하고 특정 커밋을 고정 | Git 기본 기능으로 코드에 대응하는 WIKI 버전 표현 | 앱에 gitlink, 경로/원격 정보가 남고 별도 인증, 업데이트 필요. 두 원격 push는 여전히 별개 |

C에서도 private WIKI 본문 자체가 공개 앱 이력에 복사되는 것은 아니지만 연결 정보와 gitlink는 추적된다. 별도 private 상위 저장소로 둘을 감싸면 공개 연결은 피할 수 있으나 관리 저장소가 하나 더 생긴다. 현재 외부 vault, 낮은 관리 부담에는 B가 더 맞는다는 판단이다. [Git submodules](https://git-scm.com/docs/gitsubmodules).

B의 첫 범위는 기존 Git 명령, 작업 기록, 현재 상태 확인을 연결하는 수준이다. 별도 서버, 분산 잠금, 자동 PR 병합은 제안하지 않는다. 수동 A도 같은 기록을 만들 수 있어야 하며 **버전 조합 확인은 기본 일관성 조건, 커밋, 롤백 실행 보조는 선택 기능**으로 구분한다. 기존 커밋 보조 선택 원칙을 뒤집지 않는다.

### 저장과 공유 흐름

아래 A0, A1, W0, W1은 설명용 버전 기호다. 실제 기록은 저장소 식별과 정확한 Git object ID, 작업 범위, 검증 결과를 사용한다.

```text
작업 시작: 앱 A0 + WIKI W0
같은 작업의 변경, 검증
저장된 내용: 앱 A1 + WIKI W1
작업 기록: 이전 조합, 이후 조합, 변경 범위, 실제 검사와 미완료 상태
공유 확인: 두 원격의 대상 내용, 참조가 확인된 조합만 공유 완료
```

1. 두 저장소의 루트, 작업 범위, 기준 버전을 확인한다. 기존 미커밋, 미추적 자료를 별도로 보존하고 작업 외 변경을 자동 stage, stash, 삭제하지 않는다. 같은 브랜치 이름은 편의일 뿐 같은 작업의 증거가 아니다.
2. 관련 변경만 저장하고 정확한 코드, 문서 조합으로 검증한다. 커밋 전에 검사했다면 검사한 내용과 커밋된 내용이 같은지 대조한다. 내용, 설정, 필요 환경이 바뀌면 영향받은 검증을 다시 한다.
3. 비공개 WIKI에 작업별 기준/결과 버전, 검사 근거를 연결한다. 구현 후보는 본문 커밋 W1 뒤의 작은 기록 커밋 R이 A1, W1을 가리키는 방식이다. R 자신의 SHA를 R 본문에 넣지 않아 자기 참조 문제를 피한다. 이 때문에 문서 커밋이 하나 늘 수 있으며 정확한 파일 형식, 경로는 후속 명세다.
4. 변경된 저장소만 각 정책에 맞게 공유한다. 기록은 검증한 조합을 표현하며 아직 일어나지 않은 push 성공을 주장하지 않는다. 원격 공유 여부는 실제 대상 ref/내용을 확인해 판정한다. 한쪽만 성공하면 실패한 단계와 조합을 남기고 재개하며, 성공한 이력을 자동 강제 삭제하지 않는다.
5. PR squash, rebase, merge로 커밋이나 결과 트리가 바뀌면 최종 조합을 다시 확인한다. 새 clone, 이전 코드 조회, 오프라인에서도 최신 HEAD 두 개를 임의 조합하지 않는다. 도구를 우회한 직접 push, 수동 배포까지 이 보조 절차가 막는다고 보장하지 않는다.

기록과 private 원격, 로컬 경로는 비공개 측에 둔다. 앱 Git에는 내부 WIKI 본문이나 민감한 연결 정보를 넣을 필요가 없다. 작업별 commit, 검증 묶음을 공유 가능한 상태로 만들되 저장소 정책이 요구하는 PR을 생략하지 않는다. 두 PR이 있어도 리뷰 연결을 돕는 수준이며 자동 동시 병합은 첫 범위에 넣지 않는다.

### 롤백의 세 의미

| 목적 | 처리 후보 | 보존, 확인할 것 |
| --- | --- | --- |
| 과거 작업 상태 재현 | 기록된 앱, WIKI 커밋을 별도 작업 공간에서 함께 조회 | 현재 작업본을 바꾸지 않고 당시 문서, 코드 조합을 확인. 실행 재현에는 의존성, 환경, 데이터도 필요 |
| 공유한 작업 취소 | 해당 작업의 변경을 되돌리는 새 커밋과 현재 WIKI 정정으로 새 조합 작성 | 이후 다른 사람 변경 보존, 영향 범위, 충돌 검토, 새 결과 검증 |
| 미커밋 또는 한쪽만 반영된 작업 복구 | 저장해 둔 범위, 기준, 중단 상태를 보고 재개 또는 선택 복원 | 미추적 파일은 커밋 SHA만으로 복원 불가. 전체 폴더 reset, 덮어쓰기 금지 |

Git `revert`는 이전 변경을 상쇄하는 새 커밋을 만들고, 특정 시점 재현은 별도 worktree 등으로 분리할 수 있다. 이 Git 기능을 두 저장소의 연계 절차로 사용하는 부분은 본 설계의 제안이다. [Git revert](https://git-scm.com/docs/git-revert), [Git worktree](https://git-scm.com/docs/git-worktree).

WIKI 전체를 과거로 되돌리는 것을 기본값으로 두지 않는다. 현재 기능, 요구, 운영 설명은 되돌린 코드와 맞추되, 당시 ADR, 실패 원인, 검증 근거는 남기고 철회/대체, 복구 이유를 연결한다. 이는 사용자 기술 검토 근거 보존 목표와도 맞는다. [ADR 원문](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)은 뒤집힌 결정도 보존하고 대체 상태로 표시하는 방식을 설명한다.

코드/WIKI의 Git 복구와 배포, DB 데이터, 마이그레이션, Kafka 메시지의 복구는 다른 범위다. 두 SHA가 있어도 외부 실행 효과의 되돌리기를 보장하지 않는다. 적용 프로젝트의 실제 실행 상태에는 별도 복구 조건이 필요하다.

### 확인할 사례

채택 뒤에는 양쪽 정상 완료, 한쪽 공유 실패 후 재개, 검증 뒤 내용 변경, 코드만/문서만 변경, PR 결과 변경, 동시 편집, 미추적 자료 보존, 과거 조합 재현, 공유 변경 취소 후 ADR 보존을 확인한다. 상태 표시만 아니라 파일 내용, 연결된 검사, 실제 원격 상태를 대조한다. 현재는 문서상 비교만 했고 Git 실행, 새 저장소, 복구 시험은 하지 않았다.

### PR과 CI 연결

11/05 후속 질문은 앱 PR 생성, 승인, 반려를 WIKI PR에도 자동 반영할 수 있는지, 미커밋 문서는 어떻게 전달하는지다. GitHub 기준으로 조사했으며 후속 요청에서 아래 PR 2안의 방향을 채택했다. 실제 두 저장소의 공개 범위, 요금제, 보호 규칙, 리뷰어, 토큰 권한을 확인하거나 workflow, PR을 생성하지 않았다.

**로컬 변경을 원격에 준비하는 단계는 CI 연결로 없어지지 않는다.** 일반 GitHub-hosted 실행기는 GitHub가 준비한 별도 VM/컨테이너에서 동작하므로 사용자 PC의 Windows vault 작업본을 자동으로 읽지 못한다. 앱만 commit, push하면 WIKI의 미커밋 또는 로컬에만 있는 커밋은 원격 실행기의 입력이 아니다. [GitHub 실행기](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

앱 터미널에서도 경로를 지정해 각 저장소를 commit, push할 수 있다. 미커밋 여부는 각 저장소의 HEAD/index/작업본 관계이고, origin과 차이가 있다는 사실만으로 미커밋이라고 확정하지 않는다. 앱 PR이 먼저 생겨도 WIKI branch가 아직 없다면 관련 검사를 미완료로 둘 수 있을 뿐, CI가 없는 로컬 변경을 가져올 수는 없다. 개인 PC에 self-hosted runner를 두는 방식은 별도의 접근, 운영 설계이며 첫 추천에 넣지 않는다. CI가 코드 diff에서 WIKI를 새로 생성하는 것도 가능하지만 로컬의 판단 기록을 복원하는 것과 다르고 AI 생성 비용, 검토를 추가한다.

추천하는 개념 흐름은 다음과 같다. 명령 이름과 파일 형식은 아직 정하지 않았다.

```text
로컬 작업 준비
  ├─ 앱 변경 선택 → 앱 branch에 commit 후 push
  └─ WIKI 변경 선택 → private WIKI branch에 commit 후 push
작업 식별 + 두 branch/commit 연결
  → 앱 PR + WIKI draft PR 생성/재사용
  → CI가 두 현재 버전, 검사, 검토 상태 확인
  → 각 저장소 정책에 따른 검토, 병합
  → 실제 병합 결과 버전과 부분 완료 기록
```

앱 PR 생성 이벤트로 WIKI draft PR을 여는 것은 WIKI의 원격 branch와 신뢰할 작업 매핑이 준비돼 있을 때 가능하다. PR API는 head/base branch를 입력받는다. 이벤트가 재전송돼도 같은 작업에 PR을 중복 생성하지 않도록 해야 한다. [PR API](https://docs.github.com/en/rest/pulls/pulls).

| 신호 | 자동화 가능한 처리 | 지켜야 할 의미 |
| --- | --- | --- |
| 앱 PR 열림, 갱신 | 연결된 WIKI branch의 draft PR 생성/재사용, 작업 관계, 검사 갱신 | 원격 WIKI 변경이 먼저 필요. 승인 시점까지 생성을 미루면 검토 대상이 뒤늦게 생김 |
| 앱 review `APPROVED` | 권한, 정책에 따라 WIKI review API 호출 또는 공동 검토 상태 갱신 | 승인과 병합은 별개. 앱 코드만 본 승인을 WIKI 검토 완료로 간주하지 않음 |
| `CHANGES_REQUESTED`, 승인 철회 | 작업 상태를 수정 필요/미완료로 바꾸고 연계 완료 조건 해제 | 수정 요청은 PR 닫기, 변경 삭제가 아님 |
| 앱 PR 미병합 종료 | WIKI가 전용, 미병합 PR이고 합의한 취소 정책이면 함께 닫기 | 다른 작업이 공유하거나 이미 병합됐으면 자동 취소하지 않음 |
| 앱 PR 병합 | 조건을 다시 확인해 WIKI 후속 병합을 요청하고 결과 추적 | 두 저장소의 동시 원자적 병합을 보장하지 않음 |
| 새 코드/WIKI 커밋, base 변경 | 이전 버전 조합의 검사, 공동 승인 유효성 재판정 | 같은 PR 번호라도 내용은 달라짐. 과거 승인 상태를 맹목적으로 복제하지 않음 |

GitHub는 `pull_request_review`의 제출, 편집, 철회 이벤트와 review API의 `APPROVE`, `REQUEST_CHANGES`를 제공한다. `Reject`라는 단일 처리를 가정하지 않고 위 상태를 구분한다. 앱, WIKI 각각의 최신 상태를 다시 조회하고 두 버전과 승인 주체를 대조해야 한다. 한 명의 승인 이벤트가 다른 필수 리뷰, 검사, CODEOWNERS 조건까지 만족했다는 뜻은 아니다.

[이벤트](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [리뷰 API](https://docs.github.com/en/rest/pulls/reviews), [리뷰 규칙](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request).

PR 작성자는 자신의 PR을 승인할 수 없다. 같은 봇이 WIKI PR을 만들고 그 PR의 필수 승인까지 처리한다고 가정하지 않는다. 사람이 두 저장소의 고정된 diff를 실제로 검토했고 해당 권한도 있다는 전제에서 승인 전달을 설계할 수 있지만, 봇의 API 승인을 독립된 사람의 추가 리뷰로 계산하지 않는다. 개발 작업이면 실제 리뷰어 확보 여부부터 확인해야 한다. 새 커밋에 대한 승인 철회는 저장소 설정과 별개로 작업 연계 검사에서도 확인할 후보다. [승인, 작성자 제한](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request).

### PR 자동화의 세 범위

아래 1~3은 ADR 0017 B의 자동화 수준이다. 처음에는 비교안이었고, 11/05 사용자가 2안의 방향을 채택했다. 실제 적용, 실패, 복구 검증 결과로 보완하며, 문제가 확인되면 영향과 대안을 제시해 범위 변경을 협의한다.

| 안 | 범위 | 장점 | 부담, 추천 |
| --- | --- | --- | --- |
| 1 | 로컬에서 두 변경, PR을 준비하고 링크, 사람은 각각 검토, 병합 | 가장 단순, 승인 의미가 분명 | 두 PR 상태 확인을 사람이 수행. CI 권한, 예산이 맞지 않을 때 대안 |
| 2 — 방향 채택 | 로컬 준비 + CI의 PR 연결, 버전/검사 상태 확인. 승인은 사람이 각 PR에서 수행 | 중복 입력, 누락을 줄이고 검토 책임 보존 | 교차 저장소 권한, 상태 검사 구현 필요. 첫 범위에는 자동 승인, 연쇄 병합 제외 |
| 3 | 두 diff에 대한 한 번의 공동 검토를 근거로 승인 전달, 순차 병합/취소까지 자동화 | 사용자의 조작을 더 줄일 수 있음 | 승인 권한, 새 커밋, 다른 리뷰, 재전송, 부분 병합, 복구 설계가 큼. 현재 기한에서는 후속 후보 |

2안의 방향은 11/05 채택됐으며 최소 원격 연계의 첫 제공 범위는 11/11 채택했고 저장소 정책, 실제 리뷰어, 비용, 상세 구현은 별도 확인한다. 사용자 제안의 생성, 연결, 상태 검사부터 활용하고 승인/병합을 분리하는 판단이다. 두 diff를 보지 않은 앱 승인만으로 WIKI를 자동 승인하는 단순 복사는 추천하지 않는다. 위 신호 표의 승인 전달, 후속 병합 등은 3안까지 포함한 가능성 비교이며 채택한 첫 구현 목록이 아니다.

### 첫 배포의 PR 연계 후보

11/11의 첫 범위 비교와 선정은 [ADR 0007 — 「첫 PR 연계 범위」](../decisions/architecture/0007-release-scope.md)이 소유한다. **최소 원격 연계의 첫 제공을 채택했으며 제품은 구현과 검증 모두 미완료다.** 아래 절차는 이를 구체화할 명세의 입력이다. GitHub의 코드 저장소 하나와 WIKI 저장소 하나를 기준으로 준비하며 더 많은 저장소, 다른 서비스의 지원 완료를 주장하지 않는다.

1. 사용자가 승인한 공유 작업에서 두 원격 branch와 실제 commit을 확인한다. 미커밋 자료, 원격에 없는 branch는 CI 입력으로 취급하지 않는다. WIKI 변경이 불필요하면 근거와 기존 문서 버전을 연결하며 빈 커밋/PR을 만들지 않는다.
2. 같은 작업의 PR을 생성하거나 기존 것을 재사용하고 연결한다. 중복 실행, 한쪽 PR 생성 실패에도 이미 만든 PR과 작업 관계를 잃지 않는다. 정확한 명령/API, 인증 수단은 후속 명세에서 정한다.
3. 준비 검사와 CI에서 현재 코드/WIKI 버전, 필수 검사, 검토/미완료 상태를 대조한다. 새 커밋, base 변경, 권한 회수, 늦은 이벤트가 있으면 현재 상태로 다시 판단한다. 로컬 변경 준비나 실제 의미 검토를 CI가 대신했다고 표시하지 않는다.
4. 각 저장소의 사람이 검토, 승인/병합한다. 모듈은 승인을 다른 저장소로 복제하거나 자동 연쇄 병합하지 않는다. 작성자 자신의 검토와 GitHub의 필수 승인 충족을 구분하며 정책상 필요한 리뷰어가 없으면 충족했다고 꾸미지 않는다.
5. 두 실제 결과 버전을 확인해 작업 완료를 기록한다. 한쪽만 병합됐으면 즉시 부분 완료를 보고하고 사용자와 해결 범위를 정한다. 이미 공유된 커밋은 설치 파일의 자동 복원 대상으로 삼지 않으며 [롤백의 의미 — 「롤백의 세 의미」](sync.md#%EB%A1%A4%EB%B0%B1%EC%9D%98%20%EC%84%B8%20%EC%9D%98%EB%AF%B8)를 따른다.

공개 코드와 private WIKI의 매핑은 접근이 제한된 쪽에 두고, 공개 PR, 로그, 검사 출력에는 내부 문서 내용, 민감한 저장소명/경로, 비밀값을 내보내지 않는다. 원격 제어 작업은 허용된 저장소/주체, 버전만 다루며 신뢰하지 않는 PR 코드를 자격증명이 있는 작업에서 실행하지 않는다. 기본 토큰의 저장소 제한과 실제 workflow 발동, 플랜별 강제 가능 범위는 아래 [권한 조건 — 「필요한 권한과 비용, 실패 시 처리」](sync.md#%ED%95%84%EC%9A%94%ED%95%9C%20%EA%B6%8C%ED%95%9C%EA%B3%BC%20%EB%B9%84%EC%9A%A9%2C%20%EC%8B%A4%ED%8C%A8%20%EC%8B%9C%20%EC%B2%98%EB%A6%AC)을 따른다. [GitHub의 비신뢰 코드 실행 지침](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

CI 연결이 없는 사용자는 기본 하네스와 로컬 작업을 계속 사용할 수 있으나 원격 연계 완료를 주장할 수는 없다. 채택한 첫 범위에 따라 아래 실패 사례를 실제 시험 저장소/계정에서 검증해야 하며, 지금의 설계 문서 작성이나 모의 상태로 통과 처리하지 않는다. 계정 접근, PR 생성, 비용이 드는 실행은 아직 하지 않았다.

### 필요한 권한과 비용, 실패 시 처리

- workflow의 기본 `GITHUB_TOKEN`은 해당 저장소에 한정된다. 다른 private WIKI를 읽고 PR을 다루려면 두 저장소에 필요한 범위만 허용한 GitHub App 또는 적절한 토큰이 필요하다. 기본 토큰의 PR 생성, 승인 허용 설정과 별도 토큰의 권한을 혼동하지 않는다. [토큰 범위](https://docs.github.com/en/actions/concepts/security/github_token), [Actions 설정](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).
- 기본 토큰이 만든 이벤트가 후속 CI를 모두 자동 실행하는 것은 아니다. 11/05 공식 문서는 일부 PR 이벤트를 실행 승인 대기 상태로 만들며 나머지 자동 이벤트 제한도 설명한다. 선택한 토큰, 이벤트에서 실제 후속 검사가 실행됐는지 확인해야 한다. 다른 토큰으로 바꿨다고 저장소 정책을 우회하도록 만들지 않는다. [후속 실행 조건](https://docs.github.com/en/actions/concepts/security/github_token).
- 공개 앱 PR에는 private WIKI 본문, 내부 경로, 민감한 저장소명을 노출하지 않는다. 필요한 연결은 비공개 측이 소유하고 공개 측에는 비민감 작업 식별, 검사 결과만 표시하는 방식을 비교한다. 교차 저장소 권한을 가진 제어 작업은 임의 PR 코드를 실행하지 않고 허용한 저장소, 매핑, 실행 주체, SHA만 처리하도록 분리해야 한다. 이는 본 제안의 권한 경계다.
- GitHub Free의 private 저장소에 서버 측 필수 승인, status check 강제가 당연히 제공된다고 가정하면 안 된다. 보호 브랜치는 공식 안내상 private 저장소에서 Pro/Team 등 지원 플랜이 필요하다. PR 생성, 리뷰 자체와 병합 강제 조건을 구분한다. 현재 사용자 플랜은 미확인이고 Codex Plus/Pro와는 별개다. [보호 브랜치 제공 범위](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
- private 저장소 Actions는 포함 실행량과 초과 비용을 확인해야 한다. Git/API만 쓰는 연결은 모델 호출이 필수가 아니지만 CI 시간, 유지보수, 사람의 검토 비용은 남는다. 실제 비용, 토큰 절감은 미측정이다. [실행기 과금 경계](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
- Issue 링크는 추적 관계와 조건부 자동 닫기를 제공하며 두 PR의 승인, 병합 트랜잭션을 만들지는 않는다. 공통 Issue를 쓰더라도 한쪽 PR의 `Closes`만으로 전체 작업 완료를 표시하지 않는다. 두 작업의 실제 완료를 확인해 닫고, PR끼리 closing keyword를 잘못 연결해 미병합 PR이 닫히지 않도록 한다. [Issue 연결](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).
- 두 PR이 서로의 병합 완료를 선행 조건으로 기다리게 만들면 진행이 막힌다. 먼저 같은 버전 조합의 준비, 검토 상태를 확인하고, 합의한 순서로 처리하되 하나만 병합된 상태를 별도로 복구한다. 승인 뒤 변경, 취소와 늦게 도착한 이벤트는 최신 상태를 재조회하며, 이미 병합된 변경은 PR을 닫아도 되돌아가지 않는다.

추가 시험 후보는 WIKI branch 없음, 미push 상태, 중복 생성 이벤트, 앱 승인 뒤 WIKI 수정, 다른 리뷰어의 수정 요청, 권한 회수, CI 미실행, PR 종료/재개, 한쪽 병합 실패, 공개 로그 유출 방지와 공통 Issue의 조기 닫힘이다. 실제 YAML, GitHub App, PR, CI 실행을 만들지 않고 다음 명세의 입력으로 남긴다.
