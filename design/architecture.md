# 구조와 책임

작성 근거: 2026-10-22~28 설계, 감사, ADR. 2026-10-29에 중복을 통합했다. 후속 협의에서 **최소 역할, 프로젝트별 연결 원칙을 채택했으며 상세 실행 구조는 제안, 미구현 상태다.** 실제 구현은 [구조 감사](../discussions/architecture/baseline-audit.md), 수행 순서는 [진행표](../development/roadmap.md)가 소유한다.

## 목표와 추천

핵심 제품은 **요청, 변경, 위험에 따라 필요한 지식과 절차를 선택하고 검증, 실패 처리, 재개까지 연결하는 조건부 하네스**다. 원하는 품질, 검증, 복구를 유지하면서 전체 클라우드 사용량과 재작업을 줄이고, 프로젝트 전용 정보를 분리해 다른 프로젝트에도 적용한다. 코드, 기록에서 근거를 찾아 WIKI를 복원하는 기능은 이 하네스의 필수 제공 보조 기능이며 로컬 AI 채택과 독립된 목표다. 모든 도입과 작업을 역공학 분석부터 시작하지 않는다.

현재 추천은 **Codex가 의미 판단을 맡고, 작은 공통 코드가 실행 사실과 재개 근거를 관리하며, 프로젝트 설정, 지식은 각 프로젝트가 소유하는 구조**다. 로컬 AI는 이 기본 경로에 선택적으로 연결한다. 기존 도구가 충족하는 책임까지 새로 구현하지 않는다.

11/09 전체 조건을 대조하고 사용자가 수용한 기본값은 **Codex 메인 하나가 단위별로 순차 복원하고 검토하며, 후보를 원문과 분리해 단일 경로로 반영하는 방식**다. 상세 WIKI, 근거, 관계, 범위별 완료 기준은 줄이지 않는다. 독립 조사/복원의 제한 병렬과 로컬 검토는 효과를 비교하는 선택 분기이며 첫 배포의 필수 다중 실행 체계로 묶지 않는다. 단일 반영은 AI 한 명만 쓰라는 지시가 아니라 같은 WIKI에 대한 허용된 변경 적용을 직렬화하는 책임이다. 외부 편집, 입력 변경, 부분 실패는 [동시 편집과 반영](runtime/install.md)에서 다룬다. 기본 경계의 채택이며 구체 호출, 권한, 잠금/복구 수단과 구현, 효과 검증은 남아 있다.

첫 배포의 보존, 검증과 재개를 닫기 전에 다중 작성자, 다른 모델, 별도 판정자와 분산 잠금을 동시에 구현하면 검증 범위가 커진다. 기존 순차 경로에서 시간, 문맥과 품질의 병목이 확인된 역할만 확장한다.

공통 규칙, 데이터와 AI 도구별 연결을 구분하고 첫 구현, 검증은 Codex에 집중한다([ADR 0015](../decisions/integration/0015-agent-support.md)). 도구 호환성은 [추가 검토](../discussions/integration/ai-tools.md), 저장, 편집은 [WIKI 저장](../discussions/knowledge/storage.md), 앱/WIKI의 버전, PR 연결은 [작업 연계](sync.md)가 상세를 소유한다. 채택 상태의 원본은 ADR이며 전체 진행 상태는 [진행표](../development/roadmap.md)에서 확인한다.

최초 설치의 기능 선택과 이후 사용자 요청에 따른 기능 추가는 확정된 요구다. [ADR 0014](../decisions/knowledge/0014-features.md)의 최초 B에서 WIKI를 선택으로 둔 분류는 철회했다. 핵심 WIKI, 활용, 초기화를 기본에 포함하고 설명/학습 문서, 커밋 보조는 선택 확장으로 구분한다. 문서 확장의 의미와 커밋 보조의 선택 분류는 후속 요청에서 확인했다. 11/09 WIKI의 공통 색인/기능별 상세 구성, 분할 상세 복원, 완료 기준과 위임의 기본 경계를 채택했으며, 구체 호출, 설치 상세는 계속 협의한다. [모듈의 선택 확장과 실행 방식](module.md)은 문서 설치와 작업 위임을 구분한다. 최초 표는 비교용이며 로컬 도입, 모든 환경 지원을 확정한 것은 아니다.

- 기본 경로는 로컬 추론 서버 없이 동작한다.
- 첫 배포는 Windows 11, PowerShell, Windows용 Codex/Git/Python, Windows 로컬 프로젝트를 대상으로 한다(11/11 [ADR 0020](../decisions/runtime/0020-windows.md) 채택). WSL/Linux는 후속이며 공통 정책과 환경별 실행 책임은 분리한다. 정확한 지원 버전과 Java/Gradle 연결, 두 프로젝트 호환은 실제 검증 대상이다.
- 첫 범위에서 자체 전체 agent loop, 상시 역할별 agent, 동시 다중 writer는 보류한다. 범위 합의 없는 전체 WIKI 재생성, 근거 없는 ADR 자동 채택은 허용하지 않는다. 사용자가 요청한 전체 범위의 단위별 상세 복원은 기존 필수 목표다.
- 설치와 갱신 도구의 Git 릴리스 + Python 제공과 프로젝트 내 실행 구성을 채택했다. 정확한 패키지명, 명령, 지원 버전, 설치 자산별 언어와 개발 착수는 별도다. 새 서버를 전제하지 않는다.

WIKI 분석은 [ADR 0018](../decisions/knowledge/0018-reconstruction.md)의 **설치한 명령 → 일반 코드로 모델, 범위 선택 → Codex 비대화형 분석 → 후보 검토, 적용** 방향을 채택했다. 이는 아래의 일반 개발 흐름에 추가되는 기능이다. 전체 에이전트 실행기를 새로 만드는 안과 구분하며, 명령, 분할, 복구의 상세와 제품 구현은 남아 있다.

배포 책임은 네 부분으로 읽으면 된다.

| 위치, 책임 | 담을 것 | 상세 |
| --- | --- | --- |
| 공통 모듈 | 실행 절차, 도구 연결, 템플릿, 자체 테스트 | [모듈 구성 — 「원본과 적용본」](module.md) |
| 적용 프로젝트 | 기존 코드, 빌드 설정, 검사 정책과 확인한 연결 | [소유 경계 — 「무엇을 누가 소유하는가」](architecture.md#%EB%AC%B4%EC%97%87%EC%9D%84%20%EB%88%84%EA%B0%80%20%EC%86%8C%EC%9C%A0%ED%95%98%EB%8A%94%EA%B0%80) |
| 프로젝트 WIKI | 요구, 구조, 결정, 재사용할 실패 지식. 내부 또는 외부 폴더 | [정보 역할 — 「최소 WIKI」](knowledge/wiki.md) |
| 프로젝트 로컬 상태 | 진행, 검증, 재개, 캐시, 임시 출력. .harness 전체 Git 제외 | [상태 경계 — 「작업 상태와 Git 제외」](workflow/recovery.md) |

개발자의 기존 작업 환경이나 다른 프로젝트의 문서는 제품의 필수 입력이 아니다. 예비 연결 시험과 제품 이식, 문서 복원 성공을 구분한다.

### 제품의 중심과 도입 경로

11/09 사용자 재확인이다. 신규, 기존 프로젝트 모두 같은 조건부 하네스를 사용한다. 역공학은 필요한 지식을 확보하는 도입, 후속 보강 경로이며 제품 전체의 실행 흐름이 아니다.

| 도입 상태 | 처음 할 일 | 이후 공통 사용 |
| --- | --- | --- |
| 코드, 이력도 없는 신규 프로젝트 | 하네스 연결, 기본 규칙을 준비하고 확인한 목적, 초기 요구, 현재 결정을 기록 | 관련 WIKI 탐색 → 필요한 절차/검사 선택 → 개발, 검증 → 지식/상태 갱신, 재개 |
| 코드, 기존 WIKI가 있는 프로젝트 | 기존 규칙, 문서를 보존해 연결하고 부족하거나 충돌하는 범위만 확인 | 위와 같은 하네스 사용. 충분한 문서를 다시 역공학하지 않음 |
| 코드는 있으나 WIKI가 부족한 프로젝트 | 사용자가 정한 범위를 코드, 테스트, 이력 근거로 상세 복원, 보강 | 확보한 지식을 같은 하네스에서 사용하고 개발과 함께 갱신 |

신규 도입은 없는 과거 코드, 결정, 검증 결과를 채우는 작업이 아니다. 아직 정하지 않은 요구는 미정으로 두고 중요한 선택을 실제로 합의한 시점부터 기록한다. WIKI 기능은 필요하지만 모든 문서를 먼저 완성하거나 빈 파일을 미리 생성할 필요는 없다. 세부 사례는 [기존 자료와 신규 시작 — 「기존 문서 채택과 새 문서 복원」](knowledge/wiki.md)에 둔다.

ADR 0018의 비대화형 분석 B는 WIKI 복원 기능의 진입이다. 일반 개발 요청 전체를 그 명령으로 다시 실행하거나 매번 저장소 전체를 재분석하는 계약이 아니다. 위임 기본 경계와 별도로, 복원 기능을 실행하지 않는 일반 개발에서도 조건부 탐색, 검증, 실패/재개가 동작해야 한다. 수용 평가는 복원 품질과 하네스의 일상 동작을 각각 확인한다.

### 사용자 조작을 줄이는 실행 원칙

11/23 사용자 지정이다. **사용자는 목적에 맞는 진입을 실행하고 필요한 대상과 선택을 알려주면 된다.** 도구가 확인하거나 안전하게 재사용할 수 있는 값, 처리 순서와 내부 기록의 관리를 사용자에게 떠넘기지 않는다. 이는 Facade(복잡한 내부 처리를 간단한 진입으로 제공하는 방식)의 사용성 원칙이며, 이름만 같은 클래스나 중간 계층을 추가하라는 요구가 아니다.

| 사용자가 관여할 부분 | 도구가 처리할 부분 |
| --- | --- |
| 프로젝트와 WIKI가 불명확하거나 여러 후보일 때 대상 선택, 경로 변경 의사 | 확인된 경로 발견과 저장값 재사용. 이미 아는 경로를 다시 입력받거나 내부 설정 파일 편집을 요구하지 않음 |
| 기능, 분석 범위와 모델, 새로운 권한/비용 또는 변경 계획의 중요한 선택 | 선택하지 않은 기능의 준비물을 빼고 필요한 조건을 함께 점검. 같은 범위의 유효한 입력과 허용은 재사용 |
| 충돌 해결, 되돌리기 어려운 변경과 삭제의 확인 | 파일 배치, 연결, 검증과 기록을 정해진 순서로 수행. 내부 단계나 파일마다 같은 질문을 반복하지 않음 |
| 준비물 설치, 재실행 또는 복원처럼 실제 조치가 필요한 실패 | 현재 결과와 사용 가능 범위, 필요한 다음 행동을 가까이 안내. 저장 위치, DB나 가상환경 구조를 배워야 재개할 수 있는 흐름을 피함 |

기본 출력은 현재 대상, 진행 상태, 결과와 다음 행동을 먼저 보여주고 내부 구조/상세 로그는 필요할 때 찾아갈 수 있게 한다. 중요한 권한, 비용, 실패나 미확인을 짧게 만들겠다는 이유로 숨기지 않는다. AI 내부 진입과 일반 CLI도 같은 계획/결과를 사용하며, 이미 전달된 같은 선택을 중첩 질문으로 되풀이하지 않는다.

자동화는 사용자가 맡긴 목적 안에서 수행한다. 정상 시작을 자동 설치/업데이트/전체 WIKI 분석으로 확대하거나, 여러 대상 중 하나를 임의로 고르거나, OS/호스트의 권한을 우회하지 않는다. 입력을 받을 수 없는 환경에서는 필요한 항목과 재개 방법을 반환하고 무응답을 동의로 해석하지 않는다. 상세 권한 재사용은 [진입 명세 — 「승인의 재사용과 한계」](runtime/entry.md), 안내 배치는 [설치 안내 — 「README에 담을 순서」](runtime/install.md)가 소유한다.

사용성 검증에서는 정상 사용과 중단 후 복귀를 처음 쓰는 사람의 순서로 실행하고 불필요한 재입력, 중복 확인, 수동 파일 조작과 이해하기 어려운 안내를 찾는다. 질문 수를 무조건 0으로 만드는 목표나 실제 검증 전의 시간/토큰 절감률은 두지 않는다. [CLI Guidelines](https://clig.dev/#human-first-design)의 사람 중심 설계와 필요한 만큼의 안내를 참고하되, 업계 표준 인증이나 우리 제품의 사용성 입증으로 취급하지 않는다.

## 현재와 변경 후보

기준 구현은 HEAD `f6e33dd56baa2a651a70d7d0b2cc3ebde6575153`의 감사 기록이다. 이번 통합에서 제품 코드를 다시 실행한 결과가 아니다.

```text
현재
요청 → Codex 메인: 작업 수준, gate, 문서, 완료 판단
         ├─ 필요한 지침, 프로젝트 지식 선택
         ├─ shell: scope → 계획/검증/state/retry
         │          공통 처리와 프로젝트 이름, 선택 정책 혼재
         └─ 필요한 경우 선택적 subagent
세션/compact → hook → active, scope, 공유 marker, snapshot

추천
요청 → Codex 메인: 의미 판단, 조건부 컨텍스트, 최종 검토
         ├─ 프로젝트 원본 + 명시 정책 → 확인한 실행/문서 연결 정보
         ├─ 공통 코드: 계획 → 실행 → 결과, 미완료 보존 → 재시도/재개
         └─ 선택 보조: 허용한 작업과 입력 → 결과 후보와 근거 → 메인 검토
세션 연결 → 해당 작업의 짧은 인계 → 미확인 실행이 있으면 그 기록 대조
프로젝트 WIKI → 기존 자료 우선, 필요한 부족분만 근거와 함께 제안
```

공통 코드는 두 번째 planner나 전체 작업 스케줄러가 아니다. 메인이 판단한 요청을 검사하고 도구를 실행해 사실을 기록한다. Markdown matrix를 추가한다고 실행 정책이 자동으로 연결되는 것도 아니다.

11/11 사용자 재확인: 현재 AGENTS와 Direct/Scoped/Harness, gate ON/OFF의 이름, 개수, 구현은 고정된 제품 계약이 아니다. 필요한 절차, 문서를 선택하고 불필요한 읽기를 줄이는 목적을 유지하되, 설계, 실제 검증에서 더 나은 방식이나 문제가 확인되면 영향, 대안을 검토해 변경한다. 의미 판단을 반복하는 계층을 늘리거나, 지침만으로 호출, 완료를 강제할 수 있다고 가정하지 않는다. 채택한 테스트 작성 skill도 이 선택 흐름 안에 연결하며 구체 연결, 미확정 처리, 검증 조건은 [조건부 실행과 완료 판단](workflow/verification.md)이 소유한다.

| 책임 | 현재 | 변경 후보 | 이유, 근거 |
| --- | --- | --- | --- |
| 조건부 읽기, gate | 메인의 판단 | 목적 유지, 규칙 중복, 불필요한 의무 축소 | 필요한 확인 누락과 기본 비용을 함께 평가 |
| scope | script/hook별 해석 | 경계 검사 일관화, 변경 scope와 복구 감시 목록 구분 | E-006의 상대 경로, symlink 비대칭 |
| 검증 재시도 | 새 scope로 검사 재계산 가능 | 원래 실패 계획과 수정 후 실행을 구분 | E-012의 API FAIL→core PASS |
| 검사 선택 | 내장 모듈명, selector, floor | 프로젝트별 관련 검사, 확대 조건, 로컬/CI 완료 범위 명시 | 선택 누락과 예외 범위를 따로 확인. [ADR 0005](../decisions/workflow/0005-verification-selection.md)의 원칙 채택, 구현 상세는 후속 |
| PASS 재사용 | 일부 파일, pattern 비교 | 초기 자체 캐시 보류, 검증된 도구 재사용/새 실행 | E-005, 전체 의존 추적의 유지 비용 |
| 결과 표현 | 계획, 비활성에도 PASS | 계획, 미실행, 제외, 실패, 실제 결과 구분 | E-007, 과거 보고서로 현재 성공 대체 금지 |
| 복구 | 메인의 작업 경계 active 갱신, hook, 일부 검사 상태 기록 | 기존 흐름에 실행 미확인, 저장 내구성, 조건부 재개 대조 보강 | E-011, E-013, 종료/compact hook만으로 저장을 보장하지 않음 |
| 이식, 문서 | 공통 절차와 제품 지식 혼재 | 공통 원본, 프로젝트 정책/지식, 호스트, 작업 상태 분리 | ADR 0004, 0008~0011 |
| 로컬 보조 | 조사 범위에서 미구현 | 기본 경로 안의 선택 분기 | 단독 코드 개선과 별도로 효과 확인 |

boot 제외는 비공개 BOM 자원 접근 제한에 따른 확정된 프로젝트 예외다. 제외 해제를 선행 조건으로 삼지 않으며 실제 include 목록의 정확성은 별도 검토한다.

## 비교한 구조

| 안 | 방식 | 장점 | 단점, 현재 판단 |
| --- | --- | --- | --- |
| A. 코드 개선만 | 기존 Codex와 결정적 도구 처리 정리 | 새 모델 의존이 없고 검증하기 쉬움 | 언어 작업 비용이 크면 절감 한계. 기본 구성과 대조군 |
| B. A + 선택 보조 | 좁은 언어 작업만 로컬 등에 위임 | 기존 검증, 복구를 공유하며 분업 시험 가능 | 요청, 검토, 실패 복귀 비용 추가. 확장 경계로 추천, 실제 도입은 보류 |
| C. 외부 조정 계층 | 외부 코드가 상태, 일부 gate를 소유하고 모델 호출 | 실행기와 독립된 통제, 재개 가능성 | Codex와 계획, 상태 이중 소유. 기존 실행기로 해결할 수 없는 요구가 있을 때 재검토 |
| D. 상시 다중 agent | 역할별 작업자, 공유 상태, 자동 분업 | 독립 대형 작업의 병렬화 가능성 | 문맥 중복, 동시 수정, 통합, 실패 비용. 첫 범위 제외 |
| E. 로컬 메인 전환 | 전체 작업자를 로컬로 바꾸고 클라우드와 인계 | 로컬에서 끝나는 작업의 외부 호출 감소 가능 | 전체 도구 loop, 권한, 품질, 복구 재검증. 부분 위임과 별도 후속 기능 |

추천은 A를 먼저 신뢰 가능한 기본 경로로 만들고 B를 필요할 때 검증하는 것이다. A/B를 복제 파이프라인으로 만들지 않는다. C가 필요한 실제 통제 요구가 생기면 기존 추천을 지키기 위해 억지 우회를 늘리지 않는다. 첫 배포 규모의 세 대안과 축소 판단은 [ADR 0007](../decisions/architecture/0007-release-scope.md), B의 세부 도입 대안은 [ADR 0006](../decisions/integration/0006-local-assist.md)이 소유한다.

## 무엇을 누가 소유하는가

| 경계 | 소유할 내용 | 넣지 않을 내용 |
| --- | --- | --- |
| 공통 모듈 | 경로, 계획/실행, 결과, 재개 확인, 도구 연결, 최소 템플릿 | 특정 적용 프로젝트의 모듈명, 테스트 클래스와 제품 정책 |
| 프로젝트 원본 | 빌드/테스트 선언, 코드, 기존 공식 문서 | 다른 제품의 값 |
| 프로젝트 정책, 보정 | 검사 의무/예외, 문서 역할 매핑, 확인한 보정 | 원본 빌드 설정 전체의 수동 복제 |
| 파생 연결 정보 | 원본+보정에서 얻은 명령/경로, 출처, 식별 | 별도로 사람이 갱신해야 하는 두 번째 원본 |
| 호스트 | endpoint, 인증 참조, 설치 모델, 자원, 신뢰 설정 | 배포할 비밀값, 개인 절대 경로 |
| 작업 기록 | 작업/실행 식별, 입력, 로그, 미완료, 재개 | 설치 템플릿에 넣을 실제 진행 상태 |

실행 코드와 README, matrix가 같은 모듈 목록을 각각 수동 관리하지 않는다. 원본이 바뀌면 파생 정보를 다시 확인하고 계획, 증거의 유효성을 판단한다. 명령은 argv, cwd로 구분하고 프로젝트 빌드의 메타데이터 조회도 코드 실행을 동반할 수 있음을 고려한다. 상세 분석, 보정 계약은 [ADR 0004](../decisions/architecture/0004-portability.md)에 있다.

메인은 요청, gate, 검증 충분성, 중요 설계, 최종 통합을 맡고, 코드는 입력/형식 검사, 명령 실행, 실행 사실 저장을 맡는다. 보조는 범위 안의 후보를 반환한다. 보조의 처리 완료나 유효한 JSON을 테스트 PASS로 쓰지 않는다. 자연어 packet의 허용 경로도 실제 sandbox와 구분한다.

### 확장을 위한 경계

11/09 사용자 재확인: 기한 내 첫 필수 배포와 이후 확장성을 함께 지킨다. 첫 구현은 Codex, 합의한 실행 환경에 집중하되 공통 정책이 해당 도구, 모델, 프로젝트 구조를 전제로 굳어지지 않게 한다. [ADR 0015](../decisions/integration/0015-agent-support.md)의 채택된 분리 원칙을 구체화한 기준이며 다중 플랫폼 구현이 완료됐다는 뜻은 아니다.

책임은 다음과 같이 나눈다.

| 책임 | 다루는 정보와 동작 |
| --- | --- |
| 공통 흐름 | 작업 범위와 필요한 검사를 정하고, 근거에 따라 완료 여부를 판단한다. 문서 보존과 재개 조건도 관리한다. |
| 도구별 연결부 | 모델 목록을 조회하고 실행을 호출한다. 응답과 오류를 해석하며 지침 발견 방식, hook 이벤트와 권한 차이를 처리한다. |
| 프로젝트 및 호스트 연결 | 해당 문서와 검사 명령, 경로를 제공한다. |

공통 흐름이 특정 CLI의 원시 이벤트나 모델 이름별 조건문을 직접 처리하지 않도록 의존 방향을 정한다. 실제 함수/파일 수, 등록 형식, 구현 언어는 파일별 명세에서 필요한 만큼 정한다.

WIKI를 예로 들면, 재사용할 코드는 **허용 경로 확인, 원문 읽기와 검색, 원문 버전/실제 범위/오류 반환**이다. MCP 연결부는 이 기능을 도구 목록과 호출 응답으로 제공한다. 후속 로컬 연결 프로그램은 필요한 자료를 읽어 Ollama에 전달한다. 두 연결에서 같은 문서 처리 코드를 사용할 수 있다는 뜻이며, AI끼리 대화나 메모리를 공유한다는 뜻은 아니다. 현재 후보의 `files.py`와 `reader.py`는 문서 처리를, `server.py`는 MCP 연결을 담당한다. 배포 파일명이나 별도 라이브러리 분리를 확정한 것은 아니다.

같은 원문 보호 기능은 일반 CLI나 로컬 연결 프로그램에서도 사용할 수 있으므로 MCP만의 장점으로 계산하지 않는다. MCP의 이점은 여러 지원 클라이언트에 같은 도구 계약을 제공하는 데 있다. 클라이언트마다 필요한 STDIO 프로세스가 실행될 수 있으며 중앙 상시 서버를 새로 운영한다는 설계가 아니다. 직접 파일 접근에 임의의 MCP 왕복을 추가하거나, 아직 없는 여러 AI 연결을 미리 구현하지 않는다. 실제 사람/프로그램/모델의 동작 순서는 [코드와 WIKI 접근](integration/local-ai.md)이 소유한다.

| SOLID 기준 | 이 구조에서 확인할 것 |
| --- | --- |
| 단일 책임 | 실행기 호출을 바꾸는 수정이 WIKI 보존, 완료 판정 로직까지 퍼지지 않는가 |
| 개방, 폐쇄 | 새 도구/기능 연결을 추가할 때 공통 흐름 곳곳에 조건문을 덧붙이지 않고 해당 연결과 등록을 중심으로 확장할 수 있는가 |
| 리스코프 치환 | 같은 기능을 지원한다고 선언한 연결부가 결과, 실패, 중단 후 재개 계약을 지키는가. 기능 부재나 품질 차이를 성공으로 위장하지 않는가 |
| 인터페이스 분리 | 목록 조회, 실행, 이벤트 연결 등 필요한 기능만 요구하며 지원하지 않는 기능을 빈 구현으로 강제하지 않는가 |
| 의존성 역전 | 공통 흐름이 정한 작은 입출력 계약에 도구별 연결부가 맞추는가. 공통 코드가 특정 SDK, Codex plugin 자료형에 직접 의존하지 않는가 |

예를 들어 다른 AI 도구를 추가할 때는 새 연결부와 등록/지원 정보, 해당 계약 검사를 추가하는 범위를 목표로 한다. 모델 교체도 지원 기능, 선택 정보로 다루며 이름마다 별도 업무 흐름을 복제하지 않는다. 같은 형식의 출력을 받는 것만으로 의미 품질, 복구 동등성을 인정하지 않으며 공통 계약 검사와 도구별 실제 실행, 품질 검증이 필요하다. 새 요구가 공통 계약을 바꾸면 영향과 호환성을 검토해 수정할 수 있고, 앞으로 공통 코드가 절대 바뀌지 않는다고 약속하지 않는다.

첫 구현에는 실제 필요한 계약과 Codex 연결만 만들고, 미사용 provider, 거대한 공통 인터페이스, 동적 plugin 프레임워크를 미리 만들지 않는다. Codex plugin을 배포 수단으로 채택하더라도 핵심 정책은 plugin의 전용 경로/이벤트에서 분리해 호출한다. 아키텍처의 연결부 분리와 Codex의 plugin 상품 기능은 다른 개념이다. 변경 이유별 의존 경계를 유지하되 예상 기능을 모두 선행 구현하지 않는 기준은 [Robert C. Martin의 OCP 설명](https://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html)과 [Martin Fowler의 YAGNI 설명](https://martinfowler.com/bliki/Yagni.html)을 참고한 이 설계의 적용 판단이다.

## 검증과 복구, 이식의 책임 경계

검증의 채택 원칙과 후속 명세는 [검증 계약](workflow/verification.md)이 소유한다. 최초 계획을 보존하되 수정된 현재 코드를 검사하며, 검사 선택과 실행 재사용은 다른 책임이다. 기존 결함을 before와 동작이 같아야 한다는 이유로 유지하지 않는다.

복구는 [적용 경계 — 「복구의 대상과 경계」](workflow/recovery.md)에 따라 세션 문맥 복구, 개별 기능 재개, 설치/갱신 복구로 구분한다. 정상 문맥의 확인된 실패는 기존 수정, 재검증으로 이어가고, 미확인 실행이 있을 때 그 기록과 실제 효과를 대조한다. 기존 active, hook을 보강하는 B 방향과 기계 기록의 SQLite 저장은 채택됐으며, 공유 저장, 조회 코드가 모든 작업을 새 실행 관리기에 넣는다는 뜻은 아니다.

[복구 성공 기준](../verification/acceptance.md)은 저장, 읽기, 실제 행동을 대조한다. DB 내부 일관성, 실제 파일 복원, AI 문맥 복구는 각각 확인하며 마지막 미기록 판단의 복원을 보장하지 않는다. 정확한 수단, 제품 구현, Windows 복구 실증은 후속이다.

설치는 기존 문서가 있는 프로젝트와 없는 프로젝트를 모두 다룬다. 기존 시험 프로젝트의 WIKI를 자동 역공학의 성공 결과로 계산하지 않는다. 코드의 현재 동작, 사용자 요구, 기록으로 확인한 과거 결정, 추정을 나누며 기록 없는 설계 이유를 만들지 않는다. 배포 구성, WIKI, 상태, 설치/보존은 [모듈 안내 — 「주제별 읽기」](README.md)에서 각 소유 문서로 이어진다.

## 선택형 협업

문서 확장 설치, Codex 내부 서브에이전트, 로컬 AI 보조를 구분한다. 최초 표의 '협업'은 native 분업만 뜻했으며 로컬 보조를 없앤 결정이 아니다. 기본은 클라우드 메인의 직접 처리다. 기본 메인의 순차 처리, 별도 후보, 단일 반영, 선택 보조 경계는 채택했다. 구체 역할, 권한, 호출/복구 수단과 효과는 후속 검토 대상이다.

기본 Codex와 선택 보조는 같은 검증, 복구 계약을 사용한다. `/model`과 비슷한 간단한 선택 경험은 희망 사항이며 임의의 `/mode`가 현재 구현됐다고 설명하지 않는다. 전체 provider 전환, 부분 작업 위임, 필요한 문맥 분배는 서로 관련되지만 하나로 자동 완성되지 않는다.

로컬을 채택하면 단독/보조 전환과 동일 WIKI, 검증, 복구는 그 기능의 필수 계약이다. 이를 선택 실행이라는 이유로 부차적인 책임으로 취급하지 않는다. 기본 모드에 로컬 서버를 요구하지 않으며, 설치되지 않거나 허용하지 않은 보조를 묵시적으로 호출하지 않는다. 모드별 파이프라인을 복제하지 않는 경계와 대안은 ADR 0014에서 비교한다.

기존 로컬 후보는 로그 근거 추출(R-05)과 문서 근거 추출(R-09)이며, Codex 보조의 조사/복원/독립 검토 후보와 구분한다. 이 역할표는 agent 수가 아니다. 모드, 권한, 요청/결과, 실패 복귀, 측정은 [보조 역할](integration/local-ai.md)에서만 상세 관리한다. 실제 비용 비중이 작거나 원문을 메인이 전부 재독해야 하면 비용 절감용 위임으로 채택하지 않는다. 품질 검토나 지연 개선은 그 목적의 효과와 추가 비용을 별도로 비교한다.

## 판단 근거와 한계

아래는 기존 조사(10/22~28)의 출처다. 이번 문서 통합에서 새 버전, 기능, 성능을 재확인한 것은 아니다. 구현 전에 채택할 버전의 동작을 확인한다.

원본 Q&A의 비용 0, 100% 이관, 항상 작은 문맥, 완벽한 ADR 복원, 주소만 바꾼 동일 동작은 채택 전제가 아니다. 장비, 모델 context는 유한하고 클라우드 저장 여부가 능력을 보장하지 않는다. 첫 초안의 구체 CLI 버전은 당시 관찰이며 현재 지원 버전 확정을 대신하지 않는다.

평가와 추천 철회 조건은 [수용 기준](../verification/acceptance.md)에 둔다. 지원 범위의 고정 반례 통과로 모든 미래 작업의 무오류, 무회귀를 주장하지 않으며, 기본 도구와 비교한 추가 가치가 없으면 범위를 줄인다.
