# 진입과 프로젝트 연결

작성일: 2026-11-13. 4단계에서 [현행 자산 대응](../../development/migration.md)을 구체화한 연결 명세다. **기존 규칙을 재사용한 AGENTS 최소 연결 A와 제품 시작 명령을 통한 외부 WIKI 권한 자동 연결을 채택했다.** 11/15 일반 Codex 지원은 열린 세션 안의 트리거로 경로 등록/변경, 연결과 기능 사용을 진행하는 흐름이다. 처음 명세가 확인/안내에 치우친 부분을 사용자 의도에 맞게 보정했다. 11/18 ADR 0022로 전용 시작 명령 기본과 선택 MCP 비교를 채택했고, 11/22 실제 비교 후 첫 배포는 직접 접근에 집중하며 MCP는 후속으로 전환했다. 프로젝트별 연결과 모듈의 Codex 전역 설정 비변경은 유지한다. 연결 결과를 검증/복구에 넘기는 책임까지 아래에 명세했다. 최초 명세 작성 당시에는 제품 파일을 생성하거나 변경하지 않았다. 현재 구현 범위는 아래 연결 문서에서 구분한다. 템플릿의 근거와 한글 작성은 [문서 구성 — 「양식을 정하는 근거」](../knowledge/documents.md)을 따른다.

채택한 진입은 「AGENTS 연결 방식」과 「기존 규칙과의 통합」에서 확인한다. 11/18 사용자 실행 순서는 「설치부터 관리까지의 호출 순서」 → 「명령 입력과 결과 안내」에서 본다. 세부 소비 연결은 「연결의 입력과 실패 반환」 → 「결과를 받는 절차」 → 「실패 뒤 돌아갈 위치」 순서다. 설치의 소유/공유 정책은 [설치 결과 — 「설치 결과의 소유와 공유」](install.md), 문서 조회 형식은 [위치표](../knowledge/map.md), 복구 발동은 [작업 상태 — 「복구의 대상과 경계」](../workflow/recovery.md)가 소유한다.

11/18 최종 일반 사용 기준은 [설치 후 일반 Codex 사용](entry.md#%EC%84%A4%EC%B9%98%20%ED%9B%84%20%EC%9D%BC%EB%B0%98%20Codex%20%EC%82%AC%EC%9A%A9)이 소유한다. ADR 0022의 전용 시작 명령을 기본으로 하고, 충분한 권한이 있는 일반 Codex도 유지한다. [WIKI 연결의 저장과 변경](entry.md#WIKI%20%EC%97%B0%EA%B2%B0%EC%9D%98%20%EC%A0%80%EC%9E%A5%EA%B3%BC%20%EB%B3%80%EA%B2%BD)에 한 번 등록한 경로의 재사용과 권한 전달의 차이를 뒀다.

## 사용 흐름

설치 담당자가 코드 프로젝트와 WIKI를 선택하면 설치기는 기존 지침과 발견 위치, 충돌을 확인하고 변경 후보를 만든다. 확인한 후보를 적용한 뒤에는 프로젝트 안의 지침과 skill이 같은 프로젝트의 실행 코드와 설정을 사용한다. 설치가 완료된 실행 구성은 임시 설치 도구를 정리한 뒤에도 사용할 수 있어야 한다.

일반 작업의 흐름은 `프로젝트 지침 → 요청에 필요한 절차 → 프로젝트 설정과 필요한 원문 → 작업과 검증`이다. 간단한 답변에 설정, 전체 WIKI, DB를 먼저 읽는 절차를 넣지 않는다. 문서 작업이면 필요한 역할과 범위를 조회하고, 코드/계약 변경이면 해당 검증으로 연결한다. 복구는 실제 중단/문맥 유실 등 기존 조건에서만 연결한다. 상세 WIKI 복원 트리거는 별도의 설치된 실행 기능이며 일반 대화 요청이나 암묵적 skill 선택에만 의존하도록 바꾸지 않는다.

이 흐름은 AI가 지침을 따르는 절차와 일반 코드의 경로/형식/쓰기 검사를 함께 요구한다. 지침 문구가 있다는 사실만으로 필요한 읽기나 실행이 완료됐다고 판단하지 않는다.

## 도구가 정하는 연결 조건

11/13 OpenAI 공식 문서를 확인했다. 현재 WSL 설치 패키지는 `0.167.2`지만 이는 Windows 지원 버전이나 제품 동작 검증 결과가 아니다. 패키지에 포함된 안내만으로 아래 발견 규칙을 확인할 수 없어 공식 문서로 대조했다.

| 대상 | 공식 동작에서 확인한 조건 | 명세에 미치는 영향 |
| --- | --- | --- |
| 지침 | 시작 시 전역 지침과 프로젝트 루트부터 현재 위치까지의 지침을 구성. 같은 디렉토리에서는 override, AGENTS, 설정한 대체 이름 순서로 최대 하나 사용 | 파일 이름만 보고 수정할 대상을 정하지 않음. 실제 적용될 지침과 상하위 규칙, 용량 한계를 확인. [공식 지침 탐색](https://learn.chatgpt.com/docs/agent-configuration/agents-md) |
| skill | 프로젝트에서는 현재 위치부터 저장소 루트 사이의 `.agents/skills`를 탐색. 같은 이름을 자동 병합하지 않으며 본문은 선택할 때 읽음 | 모듈 전용 이름과 발견되는 설치 위치를 연결. 전역/기존 skill과의 충돌을 확인하고 본문/참조를 모두 선행 주입하지 않음. [공식 skills](https://learn.chatgpt.com/docs/build-skills) |
| hook | 프로젝트 JSON 또는 TOML 설정을 사용하며 여러 출처의 일치 항목이 함께 실행될 수 있음. 프로젝트와 개별 hook 신뢰가 필요 | 기존 표현을 보존하고 중복 등록, 병렬 실행, 사용자 검토를 처리. 파일 추가만으로 활성화 완료를 표시하지 않음. [공식 hooks](https://learn.chatgpt.com/docs/hooks) |
| 외부 경로 | 문서 위치를 설정하는 것과 샌드박스의 쓰기 허용은 별도 | WIKI 등록과 도구 권한을 각각 확인. 호스트 설정/시작 인자 자동 연결 수단은 아래 후속 명세에서 정함. [설정 참조](https://learn.chatgpt.com/docs/config-file/config-reference) |

첫 대상은 Windows의 로컬 Codex CLI 실행이다. 클라우드가 작업을 조정하는 실행에서의 hook 지원을 같은 것으로 확대하지 않는다. 이는 모델이 클라우드에 있는 일반 Codex 사용을 배제한다는 뜻이 아니라 작업 조정과 도구 실행의 위치를 구별하는 것이다. 공식 hook 문서도 두 실행 경로의 지원을 구분한다.

## 파일과 소비자

`전용 영역`은 이미 채택한 프로젝트 안의 실행 폴더를 뜻한다. 신규 설치의 기본값은 [프로젝트 루트의 `oneploom/` — 「프로젝트 설치 위치 후보」](install.md)이며 기존 사용자 배치는 보존한다. 아래에서 후보로 표시한 파일 이름과 정확한 필드는 후속 명세다.

| 연결 대상 | 위치와 소유 | 입력, 출력과 실제 소비자 |
| --- | --- | --- |
| 작업 진입 규칙 | 실제 발견되는 기존 프로젝트 지침. 없으면 루트 `AGENTS.md` 후보 | 요청과 현재 범위로 필요한 절차를 고르는 최소 규칙. 기존 규칙 재사용 후 부족한 연결에 A를 적용하는 원칙 채택 |
| 선택 절차 | 지원되는 `.agents/skills/<모듈 전용 이름>/SKILL.md` | 명확한 발동 설명과 필요한 실행/자료의 위치. 메인 AI가 선택해서 읽음. 기존 `.codex/skills`를 자동 이동하거나 이중 복제하지 않음 |
| 공통 실행과 사용 안내 | 프로젝트 전용 영역의 실행 파일과 `README.md` | 설치된 skill, hook, 명시적 기능 트리거가 호출. 실행 입력을 받으며 임시 다운로드 경로나 고정 상위 폴더 수에 의존하지 않음 |
| 프로젝트 연결 설정 | 전용 영역의 공유 설정 파일 후보 | 프로젝트 식별, 설치된 기능/진입 연결, 공개 가능한 WIKI 연결 참조. 실행기/조회기가 소비하며 도메인 목록이나 WIKI 본문을 복제하지 않음 |
| 기기별 WIKI 연결 | `.harness/` 아래 로컬 설정 파일 후보 | 외부 WIKI의 실제 절대 경로와 로컬 연결. 공유 설정의 식별과 대조해 같은 프로젝트의 위치를 해결. 실제 인증 값은 저장하지 않음 |
| WIKI 역할 위치표 | 선택한 WIKI의 기존/등록된 `map.json`과 필요한 하위 파일 | 요청한 역할과 범위를 받아 원문 경로와 확인 상태를 반환. 자세한 필드는 기존 위치표 명세를 따름. 공개 코드 쪽에 비공개 문서 목록을 자동 복제하지 않음 |
| 도구 설정과 hook 등록 | 프로젝트의 기존 `.codex/hooks.json` 또는 TOML 항목 | 이벤트와 cwd 등의 실제 입력에서 프로젝트 실행 코드로 연결. 소유가 확인된 항목만 관리하고 사용자 승인/관리자 제한을 우회하지 않음 |
| 설치 기준과 로컬 상태 | 공유 가능한 설치 기준은 전용 영역, 진행/복구 자료는 `.harness/` | 갱신 도구는 원래 기준과 사용자 편집을 비교. 상태 소비자는 해당 작업의 조건에서만 기록/조회. active를 WIKI 위치표에 섞지 않음 |

현재 프로젝트 루트는 명시된 대상과 Git 경계, 설치 기록을 대조해 확인한다. 하위 디렉토리에서 실행하거나 여러 checkout이 있으면 같은 파일명만으로 대상을 확정하지 않는다. 내부 WIKI는 프로젝트 상대 위치, 외부 WIKI는 기기별 매핑으로 해결하며 공유 지침에 개인 절대 경로를 넣지 않는다. 해당 설정을 읽어 실제 경로로 바꾸는 소비자가 필요하고 JSON이나 Markdown 변수가 자동 치환된다고 가정하지 않는다.

## AGENTS 연결 방식

기존 지침 보존과 최소 변경을 전제로 **부족한 진입 규칙을 어디에 두고 갱신할지**를 11/13 합의했다. 배치 전에 [기존 규칙과의 통합](entry.md#%EA%B8%B0%EC%A1%B4%20%EA%B7%9C%EC%B9%99%EA%B3%BC%EC%9D%98%20%ED%86%B5%ED%95%A9)을 거쳐 재사용할 부분과 추가할 부분을 나눈다. 배치 방식만으로 의미 충돌이 해결되지는 않으며 문장이나 파일이 남아 있다는 사실만으로 기존 동작이 보존됐다고 하지 않는다.

| 안 | 구체 동작 | 이점 | 부담과 한계 |
| --- | --- | --- | --- |
| A — 짧은 관리 구역, 11/13 채택 | 기존 유효 지침에 시작/끝 표시로 구분한 짧은 한글 규칙과 설치된 절차의 연결을 추가. 기존 규칙과 같은 내용은 제외. 지침이 없으면 짧은 AGENTS 생성 후보 | 처음 읽는 지침에서 필요한 작업을 분기. 모듈이 넣은 범위와 사용자 원문을 구별하기 쉬움 | 기존 파일 안에 구역이 생김. 표시 훼손과 사용자 수정 보호가 필요하며 구역 표시로 의미 충돌을 해결할 수 없음 |
| B — 별도 진입 문서 | 기존 지침에 발동 조건과 전용 영역의 진입 문서 참조를 추가 | 상세 진입 규칙을 독립 파일로 관리. 조건을 충족하지 않는 Direct는 추가 읽기를 생략할 수 있음 | 조건이 맞는 작업에는 별도 문서 읽기가 필요. 링크만으로 자동 포함되지는 않으며 읽기 누락 검증 필요 |
| C — 기존 본문에 통합 | 기존 지침의 적절한 절마다 규칙과 연결을 합쳐 하나의 문서로 정리 | 사람이 볼 때 별도 관리 표시가 없음 | 기존 문장과 모듈 규칙이 섞여 공식 갱신, 사용자 수정과 제거의 경계를 확인하기 어려움 |

A는 **기존 규칙을 재사용한 뒤에도 필요한 연결이 남는 경우의 기본 방식**으로 11/13 채택했다. 짧은 진입과 상세 절차를 나누면서 갱신 범위를 구별하기 쉽기 때문이다. 이미 필요한 분기와 연결이 있으면 그대로 사용하며 관리 구역을 넣기 위해 중복 규칙을 만들지 않는다. 기존 여러 절의 의미를 함께 고쳐야만 통합할 수 있다면 C의 국소 수정안을 비교하고 확인한다. 별도 규칙이 길어지는 경우에는 B의 장점도 있다. 모든 프로젝트에 A가 우월하거나 B/C 전환까지 자동 허용된다는 뜻은 아니다. 정확한 표시 형식과 제품 구현/검증은 후속이다.

A의 모양을 설명하는 예시다. 기존 프로젝트에 아래 「검증」 절이 있고 조건부 진입은 없다고 가정한다. 기존 명령과 상세 절차는 그대로 연결하며 전체 게이트를 확정한 배포 템플릿은 아니다.

```markdown
## 검증

- 코드 변경 시 변경 범위에 필요한 테스트를 실행한다.

<!-- 모듈 진입 시작: 실제 식별자는 후속 명세 -->
## 조건부 하네스

- 현재 문맥만으로 답할 수 있는 요청은 Direct로 처리하고 추가 문서를 읽지 않는다.
- 코드 검증은 위 「검증」 절의 실행 결과를 사용한다. 같은 입력과 변경 상태에서 동일 검사를 별도로 반복하지 않는다.
- 문서 작업은 등록한 WIKI의 필요한 역할만 찾는다.
- 검증 실패나 문맥 유실 신호가 있으면 해당 재시도 또는 재개 절차를 읽는다.
<!-- 모듈 진입 끝 -->
```

기존 「검증」과 별도의 테스트 실행 지시를 두 개 만드는 예시가 아니다. 설치 명세에서는 필요한 절차의 실제 위치까지 연결한다. 기존 실행 결과가 [검증 계약](../workflow/verification.md)의 입력, 범위, 완료 근거를 충족하는지 확인하며, 근거가 부족하면 보완할 부분을 남긴다. 이미 실행했다는 말만으로 PASS를 만들거나 필요한 재검사를 막지 않는다.

표시는 설치/갱신 도구가 수정 범위를 찾는 수단이며 Codex의 별도 문법이나 권한 경계가 아니다. 관리 구역 안의 문장도 사용자 편집으로 보호한다. 이전 기준과 달라진 구역을 무조건 교체하지 않고 [갱신 비교 — 「변경분과 충돌의 판정」](update.md)에 넘긴다. 표시가 없거나 중복되거나 의미가 충돌하면 다시 붙여 중복시키지 않는다.

같은 디렉토리에 `AGENTS.override.md`가 있거나 대체 이름이 사용되면 무시될 AGENTS에 구역을 쓰지 않는다. 실제 유효 지침을 찾아 변경 후보를 확인한다. 원래 지침을 가리기 위해 새 override를 생성하지 않고, 하위 지침과 충돌하는 규칙도 말없이 무효화하지 않는다.

### 기존 규칙과의 통합

설치와 갱신에서 해당 기능의 기존 유효 지침과 직접 연결된 절차를 대조한다. 같은 이름인지보다 적용 대상, 발동 조건, 수행 책임, 완료 기준이 같은지 확인한다. 모든 작업 요청마다 설치 시의 비교를 처음부터 반복하는 절차는 아니다.

| 기존 구성과의 관계 | 연결 후보의 처리 |
| --- | --- |
| 같은 책임과 조건을 이미 충족 | 기존 규칙과 실행 경로를 재사용. 같은 규칙이나 두 번째 실행 경로를 추가하지 않음 |
| 일부가 부족하지만 함께 사용할 수 있음 | 기존 부분을 재사용하고 부족한 연결이나 결과 기록만 보완. 테스트 작성과 실행의 역할, 원래 실패와 재시도 연결을 보존 |
| 같은 조건에 서로 다른 행동을 요구 | 충돌과 영향을 보여주고 사용자가 결정한 범위만 변경. 예를 들어 기존의 매 요청 전체 문서 읽기를 Direct 생략으로 말없이 덮지 않음 |
| 표현이 다르거나 다른 파일의 규칙과 관계가 불명확 | 이름 비교만으로 동일하거나 무관하다고 판정하지 않음. 관련 원문을 확인해 통합 후보를 만들고 정책 선택이 필요한 부분은 확인 대기 |

일반 코드는 파일 발견, 소유 구역, 변경 차이, 참조와 입력 형식을 검사한다. 기존 자연어 규칙의 의미를 완벽하게 통합하는 일은 문자열 검사만으로 보장하지 않는다. 허용된 AI 분석은 대응 후보와 근거를 만들 수 있지만 의미 검토를 대체하지 않으며, 중요한 정책 변경은 사용자 확인 뒤 반영한다. 같은 이름의 skill이나 다른 출처의 hook을 도구가 알아서 하나로 합친다고 가정하지 않는다.

통합한 진입은 기존 기준의 소유 위치를 참조한다. 해당 기준이나 실행 연결이 갱신되면 의미와 실행의 대응도 다시 확인한다. 관리 표시가 그대로라는 이유만으로 정책 호환성까지 통과 처리하지 않는다.

### Direct와 읽기 비용

Direct는 하네스가 정한 작업 수준이며 Codex가 문서 읽기를 자동 차단하는 설정이 아니다. 현재 요청과 문맥으로 충분하고 다른 적용 규칙이 추가 작업을 요구하지 않을 때 메인이 추가 읽기를 생략한다. 필요한 정보나 위험 신호가 나오면 범위와 게이트를 올리며 토큰 절감을 이유로 필수 검사를 생략하지 않는다.

- 시작 시 들어온 유효 AGENTS의 본문은 Direct라고 제거되지 않는다. [공식 지침 구성](https://learn.chatgpt.com/docs/agent-configuration/agents-md)에 따른 초기 컨텍스트와 이후의 파일 읽기를 구분한다.
- skill 이름, 설명, 경로는 초기 목록에 들어갈 수 있고 본문은 선택할 때 읽는다. [공식 skills](https://learn.chatgpt.com/docs/build-skills)의 점진적 읽기와 같은 원리로 상세 절차를 필요한 경우에 연결한다.
- Direct 판정을 위해 매번 별도 진입 문서, WIKI, 설정, DB 또는 판정 스크립트를 선행 실행하지 않는다. 파일 검토가 필요한 요청은 해당 범위를 읽으며 Direct로 고정하지 않는다.
- B도 발동 조건을 첫 지침에 두면 Direct에서 별도 문서를 건너뛸 수 있다. 따라서 A만 추가 읽기를 줄일 수 있다는 비교는 성립하지 않는다. A의 본문이 길어지면 초기 부담이 커질 수 있다.

토큰 차이는 미측정이다. 초기 지침/메타데이터, 실제 읽은 본문, 도구 출력과 중복 실행을 나눠 관측하고 절감량이 유의미한지 판단한다. A의 기본 추천 근거는 짧은 진입과 변경 소유의 가시성이며, 토큰 절감이나 실제 AI의 규칙 준수를 이미 검증한 결과가 아니다.

## 공유 설정과 로컬 연결

기존의 공유 설정/로컬 상태 분리를 파일과 입력에 대응한 초안이다. 제품명/명령은 [OnepLoom/oneploom — 「제품 이름과 변경 기준」](../module.md), 신규 기본 위치는 [프로젝트 루트의 `oneploom/` — 「프로젝트 설치 위치 후보」](install.md)으로 정했다. `project.json`, `.harness/local.json`은 후보 이름이며 브랜드 채택으로 변경하지 않는다. 11/22 아래 「연결 설정의 필드와 읽기 규칙」에서 필드의 형식과 소비를 구체화했다. 제품 구현과 배포 계약 확정은 아직이다. 설치 이력, 기능 목록, 복구 상태를 이 파일에 중복하지 않는다.

| 위치 후보 | 최소 입력 | 소비와 보존 |
| --- | --- | --- |
| `<전용 영역>/project.json` | `project_id`, `wiki.path`, `wiki.map` | 실행기가 대상과 WIKI 연결 방식을 확인. 공유 가능한 설정이며 기기별 절대 경로와 인증 값은 제외 |
| `.harness/local.json` | 같은 `project_id`, `project_root`, 외부 사용 시 `wiki_path`. 사용자 지정 설치에 `module_path`, 명시적 실행 선택에 `codex_path`, `launch` | 이 작업 사본의 설치본/WIKI/실행 선택을 해결. 기존 `/.harness/` 제외 정책을 따름 |
| WIKI의 위치표 | 기존 `entries`, `maps` 등 | 필요한 역할/범위의 원문 조회. 사용자별 경로, 세션 상태, 권한 설정을 넣지 않음 |

외부 WIKI를 쓰는 공유 설정 예시다. 아래 식별값은 가상이며 실제 생성 형식은 후속 명세다.

```json
{
  "project_id": "example-project",
  "wiki": {"path": null, "map": "map.json"}
}
```

같은 프로젝트의 기기별 설정 예시다.

```json
{
  "project_id": "example-project",
  "project_root": "C:/Work/project",
  "wiki_path": "C:/Work/project-wiki"
}
```

내부 WIKI는 공유 설정의 `wiki.path`를 `docs` 같은 프로젝트 기준 상대 경로로 두며 `wiki_path`를 요구하지 않는 후보다. `null`은 로컬 등록이 필요한 외부 WIKI를 뜻하고 필드 누락, 빈 문자열과 구별한다. 내부/외부 설정이 함께 남아 다르게 가리키면 한쪽을 조용히 우선하지 않고 정리를 안내한다. `wiki.map`은 WIKI 기준 상대 위치이며 기존 위치표가 다른 이름이면 그 위치를 등록한다. `map.json`을 무조건 새로 생성하지 않는다.

프로젝트 식별값은 같은 프로젝트의 clone에서 유지하지만 인증 수단이나 작업 사본 구분을 대신하지 않는다. 현재 루트, Git 경계, 실제 설치 설정과 로컬 기록의 연결을 함께 대조하며 이름이 같다는 이유만으로 다른 checkout의 상태를 이어받지 않는다. `.harness/local.json`이 없는 새 clone에서는 필요한 로컬 경로와 실행 조건을 준비하고 공유 설치나 문서 분석을 반복하지 않는다.

시작할 때 반복 적용할 사용자 선택도 이 로컬 연결의 책임으로 둔다. WIKI 경로와 권한의 유효성을 같은 값으로 취급하지 않으며, [최초 실행 선택과 재사용](entry.md#%EC%B5%9C%EC%B4%88%20%EC%8B%A4%ED%96%89%20%EC%84%A0%ED%83%9D%EA%B3%BC%20%EC%9E%AC%EC%82%AC%EC%9A%A9)에 따라 필요한 정보만 기록한다. 실제 Codex 권한이나 공유 config 전체를 복사하는 파일, 별도 승인 DB를 추가하지 않는다. 위 JSON은 경로 연결 예시이고 시작 선택의 최종 필드까지 구현한 형식은 아니다.

경로 처리는 모델 호출 없이 일반 코드가 맡는다. Windows 입력을 정규화해 로컬에는 절대 경로로 저장하는 후보다. 상대 입력은 화면에 표시한 대상 코드 루트를 기준으로 해석하고 결과를 확인한다. 실제 접근 대상이 등록한 범위인지 검사하며 임의의 상위 폴더, 다른 프로젝트나 삭제된 위치를 기본값으로 대체하지 않는다. WIKI 위치를 바꿀 때는 새 경로/위치표/권한을 확인한 뒤 연결을 바꾸며 실패하면 이전 설정을 보존한다. 파일 이동, Git clone/pull, Obsidian 열기는 경로 등록만으로 실행하지 않는다.

위치표의 `root: code`는 확인한 코드 루트, `root: wiki`는 위 절차로 해결한 WIKI 루트에 연결한다. 역할 목록이나 기능별 문서 목록을 공유/로컬 설정에 다시 복제하지 않는다. 임의의 추가 원본 이름은 [위치표 계약 — 「입력의 경계」](../knowledge/map.md)에 따라 등록 여부를 검사한다.

### 연결 설정의 필드와 읽기 규칙

11/22 구현 후보의 범위는 연결 정보다. 같은 구조를 `connect`, `check`, `start`, `resume`과 열린 Codex의 연결 절차가 사용한다. 공유 설정은 담당자가 설치할 때 만들고, 팀원은 기기별 연결만 준비한다. 이름을 바꾸거나 필드를 늘리기 위해 기존 사용자 설정을 자동 변환하지 않는다.

| 파일과 필드 | 형식과 조건 | 생성 또는 소비 |
| --- | --- | --- |
| 공유 `project_id` | 비어 있지 않은 문자열 | 설치가 부여하고 clone에서 유지. 인증이나 작업 사본 식별을 대신하지 않음 |
| 공유 `wiki.path` | 프로젝트 기준 상대 폴더 문자열 또는 `null`. 필수 | 문자열이면 내부 WIKI, `null`이면 외부 로컬 등록을 조회. 누락/빈 문자열을 외부 연결로 추정하지 않음 |
| 공유 `wiki.map` | WIKI 기준 상대 파일 문자열. 필수 | 등록된 위치표를 찾음. WIKI 밖으로 벗어나거나 없는 위치를 다른 파일로 대체하지 않음 |
| 로컬 `project_id` | 공유 값과 같은 문자열. 로컬 파일이 있으면 필수 | 다른 프로젝트의 설정 복사 탐지 |
| 로컬 `project_root` | 등록한 코드 루트의 Windows 절대 경로. 로컬 파일이 있으면 필수 | 다른 clone으로 복사된 설정을 구별. 현재 실제 루트/Git 경계/설치 연결과 함께 검사 |
| 로컬 `module_path` | 사용자 지정 설치 디렉토리의 프로젝트 기준 상대 경로. 기본 위치는 생략 | [설치본 발견 — 「설치 위치의 저장과 발견」](project-entry.md)에만 사용. WIKI/실행 명령/다른 프로젝트의 절대 경로를 넣지 않음 |
| 로컬 `wiki_path` | 외부 WIKI의 Windows 절대 경로. 외부 연결일 때만 필수 | 코드 저장소에 공개하지 않고 재사용. 내부 WIKI와 함께 남으면 연결 변경 절차에서 정리 |
| 로컬 `codex_path` | 사용자가 명시적으로 선택한 진입 경로. 선택 때만 저장 | 자동 발견이 모호하거나 별도 설치를 선택한 경우 사용. 버전별 내부 바이너리 경로를 자동 저장하지 않음 |
| 로컬 `launch.args` | 반복 적용에 동의한 옵션의 문자열 배열. `launch`가 있으면 필수 | 확인한 권한 선택만 저장. 모델/인증/프롬프트나 이번 요청의 임의 인자를 자동 저장하지 않음 |
| 로컬 `launch.context` | 아래 비교 입력의 SHA-256, 소문자 64자리. `launch`가 있으면 필수 | 과거 선택을 현재 대상/관련 조건에 적용해도 되는지 비교. Codex의 허가를 대신하지 않음 |

내부 WIKI를 쓰고 기본 설치 위치이며 별도 실행 선택도 없으면 로컬 파일을 만들 이유가 없다. 외부 WIKI 또는 사용자 지정 설치/명시적 실행 선택이 있을 때만 필요한 필드를 저장한다. 기본값 상속을 `launch: {}`로 표현하지 않고 `launch`를 생략한다.

`launch.context`는 경로를 두 벌 보관하는 대신 선택의 적용 조건을 대조하는 값이다. **저장할 옵션을 덧붙이기 전의 설정**과 그 선택에 필요한 대상/정책을 [재사용 조건의 비교 형식](entry.md#%EC%9E%AC%EC%82%AC%EC%9A%A9%20%EC%A1%B0%EA%B1%B4%EC%9D%98%20%EB%B9%84%EA%B5%90%20%ED%98%95%EC%8B%9D)에 맞춰 계산한다. 저장 당시와 현재의 조회가 같은 조건에 대응하고 필요한 값이 모두 확인됐을 때만 비교한다. 모델/화면 값, 무관한 프로젝트 신뢰와 전역 설정 파일 전체는 포함하지 않는다. 이 해시는 권한 증명이나 비밀값 보관 수단이 아니며, 해시가 같아도 현재 관리 제한과 실제 실행 권한을 대신하지 않는다.

첫 구현에서 반복 저장을 허용할 옵션은 지원되는 Codex 연결 코드가 의미를 확인한 권한 선택으로 제한한다. 알 수 없는 `-c` 값이나 sandbox 해제 옵션을 통째로 보관하는 기능이 아니다. 사용자 `--profile` 등 현재 사전 조회와 대응하지 못한 선택은 이번 호출의 명시적 입력 보존과 자동 재사용을 구별한다. 필요한 조회를 지원하지 않으면 기존 「호스트 조회와 실행 인계」의 미확인 처리를 따른다. 이 필드 명세만으로 모든 권한 프로필의 재사용이 구현된 것은 아니다.

설정은 UTF-8 JSON으로 읽고 같은 객체의 중복 키, 잘못된 형식과 인식하지 못하는 필드는 조용히 버리지 않는다. 읽지 못한 파일을 빈 설정으로 덮지 않으며 필요한 명령만 중단해 이유를 알린다. 기기 명령은 발견에 필요한 부분을 읽기 전용으로 확인하고 프로젝트 코드가 자기 연결 설정을 검사한다. 이 책임 구분을 알 수 없는 값을 삭제/자동 보정하거나 전체 설정을 정상 판정하는 근거로 쓰지 않는다. 공유 설정에는 기기별 절대 경로나 자격증명을 넣지 않는다. 상대 경로는 CWD가 아니라 해당 표의 기준 루트로 해결하고, Windows의 드라이브 상대 경로, URI, 범위 밖 경로를 일반 폴더로 오인하지 않는다. 경로 문자열의 대소문자 변환만으로 같은 파일인지 판단하지 않는다.

읽기 전용 확인은 설정을 다시 저장하지 않는다. `connect`의 저장은 기존 [파일 반영 보호 — 「파일 반영과 핸들 수명」](update.md)를 사용해 원래 내용을 대조한 뒤 수행하며 중간 종료/동시 편집이면 이전 설정 또는 복구 근거를 보존한다. 권한 부족으로 새 연결을 실제 사용할 수 없다면 이전 연결을 정상값으로 유지하고 부족한 조건을 안내한다. 파일 형식 검사와 실제 저장/권한 검증은 [진입 설정과 반환의 검증 입력](../../verification/acceptance.md)으로 나눠 확인한다.

## 외부 WIKI 권한과 시작 방식

경로를 안다고 Codex의 쓰기 권한까지 생기지는 않는다. 공식 CLI는 [추가 디렉토리 인자](https://learn.chatgpt.com/docs/cli/reference)의 `--add-dir`를 제공하고, [설정 참조](https://learn.chatgpt.com/docs/config-file/config-reference)는 `sandbox_workspace_write.writable_roots`를 설명한다. 두 수단 모두 실제 실행의 sandbox/관리 정책과 대조해야 하며 경로 등록 성공을 권한 확인으로 대신하지 않는다.

| 후보 | 사용자 흐름 | 이점 | 부담과 조건 |
| --- | --- | --- | --- |
| 연결된 시작 명령, ADR 0022의 기본 진입 | 프로젝트 진입 명령이 저장 WIKI 경로를 현재 설치된 Codex의 시작/재개 인자로 전달 | 긴 경로 반복 입력, 공유 config의 개인 경로 저장을 줄임 | 새 짧은 명령을 익혀야 하며 실제 Windows 입력/출력, 옵션, 재개 보존 검증 필요 |
| 일반 codex의 지속 연결, 선택 호환 경로 | 기존 충분한 권한 또는 별도 연결 도구로 같은 WIKI 사용 | 익숙한 명령 유지 | 전역 설정 비변경과 사용자 config 보존. MCP는 11/22 결정에 따라 첫 제공 후 검토 |

사용자는 11/13 **제품 시작 명령으로 자동 연결**을 선택했다. 임의의 Windows WIKI 위치와 기존 공유 설정을 함께 보존하기 쉬운 점이 채택 근거다. 정확한 제품 명령과 Windows 동작은 아직 구현/검증하지 않았다. 두 번째를 불가능하다고 판단한 것은 아니지만 모든 사용자의 기존 설정에 자동 적용할 수 있다고 보장하지 않는다. 이미 허용된 WIKI 경로는 확인 후 재사용하며 같은 권한을 중복 등록하지 않는다.

설정에 대한 공식 제약도 확인했다. [설정 계층](https://learn.chatgpt.com/docs/config-file/config-basic)은 사용자 설정과 신뢰된 프로젝트 설정을 구분한다. `--profile`로 선택하는 [설정 프로필](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles)과 `/permissions`에서 선택하는 권한 프로필은 별개다. 전자는 별도의 설정 파일을 겹쳐 읽으며 top-level `profile` 자동 선택을 지원하지 않는다. 후자는 아래와 같이 세션의 허용 범위를 선택하는 수단이다. 모듈은 사용자 전역의 권한 목록을 포함한 전역 설정을 변경하지 않는다.

설치된 도구를 찾아 실행하고 사용자 모델, 인증, 승인 정책을 임의로 바꾸거나 안내 프롬프트를 자동 전송하지 않는다. 새 세션과 재개는 구분하며 같은 세션 선택을 보존해야 한다. 일반 `codex`로 이미 시작한 세션의 권한을 skill이나 hook이 조용히 바꾸었다고 처리하지 않는다.

[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)와 [권한 profile](https://learn.chatgpt.com/docs/permissions)의 지원/혼합 제약은 실제 대상 버전에서 확인한다. 별도 권한 방식이 필요한 환경을 기존 sandbox로 임의 전환하거나 관리자 제한을 우회하지 않는다. 등록, 실제 읽기/쓰기, 시작/재개, 경로 변경 뒤의 권한 보존은 Windows 제품 시험에서 각각 확인해야 한다.

### 설치 후 일반 Codex 사용

11/18 후속 합의로 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)를 채택했다. 기본은 전용 시작/재개 명령이며, 일반 codex는 기존 권한과 프로젝트 기능을 그대로 사용하는 호환 경로다. MCP는 실제 비교 뒤 11/22에 후속 제공으로 전환했다. 사용자 비용은 [진입 방식 비교 — 「전용 시작 명령과 MCP의 비교」](entry.md#%EC%A0%84%EC%9A%A9%20%EC%8B%9C%EC%9E%91%20%EB%AA%85%EB%A0%B9%EA%B3%BC%20MCP%EC%9D%98%20%EB%B9%84%EA%B5%90), 제공 순서는 [두 방식의 선택 제공](entry.md#%EB%91%90%20%EB%B0%A9%EC%8B%9D%EC%9D%98%20%EC%84%A0%ED%83%9D%20%EC%A0%9C%EA%B3%B5)을 따른다.

앞선 11/18에는 명령 이름까지 일반 codex인 사용을 기본으로 요구했으나, 현재 설치된 Codex 기능 보존과 유지 부담을 비교한 뒤 위 결정으로 변경했다. 저장 WIKI의 재사용과 변경 트리거, 평소 요청에 따른 조건부 동작은 유지한다. 긴 추가 경로 입력이나 매 작업의 활성화 절차를 요구하지 않는다.

설치된 지침과 발견 가능한 skill, 필요한 hook 연결을 통해 요청의 수준과 게이트를 판단한다. 예를 들어 “이 API를 수정해줘”라는 요청은 관련 규칙/코드 → 필요한 구현/검증 → 영향받는 WIKI 반영으로 이어져야 한다. 사용자가 매번 테스트 skill이나 WIKI 연결을 따로 선택하도록 요구하지 않는다. Direct의 추가 읽기 생략과 조건부 복구는 유지하고, 모든 요청에서 전체 WIKI/DB/검사를 실행하는 방식으로 확대하지 않는다. 상세 복원, 공식 업데이트나 자료 정리처럼 별도 의도가 필요한 작업까지 진입만으로 자동 실행하지 않는다.

일반 codex에서 외부 WIKI 권한이 부족하면 관련 기능만 안내하고 필요한 같은 세션 재개를 연결한다. 기존 권한이 충분한 사용자는 추가 진입을 요구받지 않는다. 모듈의 로컬 경로 저장을 호스트 권한 확보로 대신하지 않으며, 전용 명령 성공을 일반 codex의 외부 접근 성공으로 바꾸지 않는다.

공식 [설정 계층](https://learn.chatgpt.com/docs/config-file/config-basic)과 [권한 프로필](https://learn.chatgpt.com/docs/permissions)에 따른 지속 연결은 선택 호환 대안이다. [기존 배치 비교 — 「지속 권한 설정의 배치」](entry.md#%EC%A7%80%EC%86%8D%20%EA%B6%8C%ED%95%9C%20%EC%84%A4%EC%A0%95%EC%9D%98%20%EB%B0%B0%EC%B9%98)와 부분 관측을 보존하되 기본 설치가 config 전체를 생성/제외하도록 바꾸지 않는다.

첫 지원 환경에서는 선택한 진입에서 새 세션/기존 세션 재개, 실제 WIKI 접근과 조건부 절차를 검증한다. 일반 codex와 MCP 지원은 각 경로의 결과를 따로 표시한다. 관리 정책이나 기존 설정을 우회하지 않으며 실제 제품이 구현/검증됐다는 뜻은 아니다.

### WIKI 연결의 저장과 변경

한 번 확인한 WIKI 경로는 이 작업 사본의 로컬 설정으로 보존하고 명시적으로 바꾸기 전까지 재사용한다. 매 요청이나 매 세션에 같은 입력을 다시 요구하지 않는다. 필요한 문서를 사용할 때 현재 경로/원본과 접근이 유효한지 확인하는 것은 유지하며, 실패를 다른 폴더 탐색/자동 재연결이나 빈 WIKI 생성으로 해결하지 않는다.

연결 명령의 같은 구현을 외부 CLI와 Codex 안의 연결 skill/트리거가 사용한다. 제품 명령 접두어는 `oneploom`으로 채택했고 `connect`는 아직 하위 명령의 후보 이름이다. 새 경로를 받으면 해당 프로젝트의 원본인지, 위치표와 실제 접근 및 지속 권한이 맞는지 확인한 뒤 변경한다. 실패하면 이전 유효 연결과 문서를 보존한다. 저장 연결의 변경, 호스트 권한 준비와 현재 세션 반영은 구별하고 재진입이 필요하면 그 사실을 안내한다. 일반 재시작마다의 필수 단계로 만들지 않는다.

| 방식 | 판단과 트레이드오프 |
| --- | --- |
| 최초 기기 준비 때 경로 등록, 변경 명령으로 재설정 | 공통 원칙. 저장 위치를 매번 입력하지 않음. 등록된 위치와 현재 Codex의 실제 권한은 별도로 확인 |
| 제품 시작/재개 명령이 저장 경로를 전달 | ADR 0022의 기본. 전역 설정 편집 없이 현재 Codex를 열며 사용자 권한과 설치 형식의 호환 검증이 필요 |
| 일반 codex에서 기존 충분한 권한 또는 선택 연결 사용 | 유지할 호환 경로. MCP는 후속 제공이며 권한/호출 검증 없이 기본 진입과 동등하다고 하지 않음 |
| 매 세션마다 연결 skill을 먼저 호출 | 초기 미등록이나 경로 변경에는 유용하지만 정상 사용에 강제하면 반복 절차가 됨. 저장 연결을 매번 새로 만드는 기본안으로 비추천 |

설정 저장/조회는 일반 코드로 처리할 수 있으며 매번 경로를 추론하는 모델 호출이 필요하지 않다. 이 사실만으로 전체 토큰 절감량을 확정하지는 않는다. 해당 프로젝트의 기본 선택에 필요한 권한만 연결하고 기기 경로를 공유 WIKI나 팀 Git에 넣지 않는다. 과거 경로 권한을 제거할 때도 모듈 소유와 다른 사용처를 확인하며 사용자/다른 프로젝트의 허가를 함께 지우지 않는다. 모든 기기의 영구 권한이나 관리자 정책 우회를 보장하는 안은 아니다.

### 실행 조건의 확인과 미확인 처리

11/19 [설치된 타입과 보존 스키마의 대조](../../evidence/experiments/wiki-access/2026-11-19_15-17-25-mcp-capabilities.md)에서는 MCP의 표준 요청과 Codex 모델 목록에서 **현재 대화의 유효 도구 출력 한도를 알려주는 전용 필드**를 확인하지 못했다. 전날 관측한 모델 캐시도 현재 대화의 적용값을 증명하지 않는다. 유효 한도를 항상 자동으로 얻을 수 있다고 가정하지 않는다. 아래는 기존 범위 보존 요구를 위한 설계 보완이며 자동 조회나 제품 지원을 구현한 결과가 아니다.

후속 [설치본 파싱 확인](../../evidence/experiments/wiki-access/2026-11-20_00-33-30-mcp-read-contract.md)에서는 기존 시험 위치의 Windows Codex 0.170.0이 `mcp_servers.<name>.tools.<tool>.output_token_limit`의 문자열을 거부하고 양수 설정을 받아들였다. 일회성 인자의 mcp get 조회만 사용했고 설정 저장, 서버/모델 호출은 없었다. 조회 결과에는 해당 값이 노출되지 않아 현재 대화의 적용 한도 확인으로 확대하지 않는다. prompt-input 도움말도 과거 도구 수신을 그대로 조회하는 수단으로 확정하지 않았다. 공식 안내에 설정 키가 있다는 사실, 설치본의 파싱 지원, 실제 대화 적용값을 구별하며 전역 설정을 변경하거나 제품 기본값으로 자동 주입하지 않는다.

| 정보의 출처 | 확인할 수 있는 것 | 대신 판단하면 안 되는 것 |
| --- | --- | --- |
| MCP의 프로토콜과 capabilities | 상대가 선언한 지원 기능과 통신 형식 | 현재 Codex 모델, 남은 문맥, 합산 도구 출력의 유효 한도 |
| 현재 설치본의 설정 조회와 모델 목록 | 조회가 지원하는 설정/선택 후보. 추가 설정 키의 존재 가능성도 보존 | 디스크 선언값이나 모델 목록을 실행 중 대화의 최종 적용값으로 확정 |
| 저장된 대화의 메타데이터 | 기록된 프로젝트/모델 등의 제한된 정보 | `thread/read`를 모든 실제 턴의 실행 계측으로 취급하거나 새 시작에도 조회 강제 |
| 도구의 실제 반환과 호스트 수신 기록 | 보낸 구간, 실제 받은 본문과 잘림 등 관측 가능한 결과 | 서버 전송 성공이나 시작/끝 숫자만으로 원문 전체 수신을 증명 |

[2025-11-25 규격](https://modelcontextprotocol.io/specification/2025-11-25/schema)의 초기화와 [2026-07-28 규격](https://modelcontextprotocol.io/specification/2026-07-28/schema)의 요청 메타데이터는 형식이 다르다. 각 규격과 실제 SDK/호스트가 지원하는 기능을 사용하며 새 규격을 강제로 적용하지 않는다. 후자의 clientInfo는 진단용 자기 신고 정보이므로 이름/버전에서 기능이나 한도를 추정하지 않는다. 선택 확장 필드는 가능하지만 현재 Codex가 유효 한도를 제공하는 확장은 확인되지 않았다.

조회 가능한 항목은 필요한 연결/설정 변경 경계에서 사용한다. 한도를 찾기 위해 매 문서 읽기마다 전체 설정/캐시를 조회하거나, 별도 App Server로 현재 TUI를 제어하거나, 모델 추론을 요청하지 않는다. MCP의 sampling은 모델 생성을 요청하는 기능이므로 한도 조회 수단으로 사용하지 않는다. 관련 값이 없거나 출처를 현재 실행에 대응시킬 수 없으면 **미확인**으로 남긴다. 선택적 한도 정보의 부재만으로 모든 기본 읽기를 막지 않으며, 필요한 프로토콜/도구 기능 자체가 없는 경우는 별도 미지원으로 처리한다.

한도 확인 여부와 관계없이 요청 범위, 같은 원문인지 나타내는 revision, 실제 받은 본문과 남은 구간을 대조한다. 잘린 흔적이나 필수 정보 부재가 있으면 같은 원문에서 부족한 구간만 다시 요청한다. 메타데이터만 남고 본문이 잘린 경우도 완료가 아니다. 호스트가 표시 없이 내용을 자르는 경우를 서버 혼자 알아낼 수 있다고 보장하지 않으며, 판별할 수 없는 범위는 미확인으로 남기고 실제 사용 검증의 미해결 항목으로 보고한다.

**호스트의 한도와 모듈의 자원 정책은 별개**다. 전자는 사용자 실행 조건이며, 후자는 우리 연결 코드가 메모리/탐색/한 번의 반환을 관리하는 정책이다. 구체 후보와 SDK 크기 진단은 앞 절 「MCP 읽기의 남은 보완」의 「반환 정책과 크기의 기준」, 「SDK 전송과 호스트 수신의 대조」에서 관리한다. 호스트 한도가 미확인이라는 이유로 무제한 처리나 임의의 작은 상한을 대신 넣지 않는다. 숫자와 실제 사용 검증이 남은 현재 상태를 배포 조건 확정으로 표시하지 않는다.

### 환경 변경을 확인할 경계

[환경 변경 원칙 — 「사용자 환경의 변경과 호환성」](../workflow/verification.md)을 실제 확인 시점에 연결한다. 버전별 한도표를 만들거나 매 읽기마다 설정 전체를 조회하는 방식은 채택하지 않는다. 11/20 [확인 근거](../../evidence/experiments/wiki-access/2026-11-21_00-23-11-mcp-delivery-review.md)는 정적 소스와 기존 기록의 대조이며 자동 감지 구현이나 갱신 호환성 시험 완료가 아니다.

| 달라진 것 | 확인할 시점과 범위 |
| --- | --- |
| 사용자가 Codex를 업데이트함 | 다음 실행에서 선택된 실행 파일과 실제 호스트 관측을 대조. 디스크 패키지 버전만으로 이미 열린 세션도 바뀌었다고 단정하지 않음 |
| 사용자가 모델/관련 설정을 바꿈 | 변경 후 해당 요청에 적용되는 선택과 확인 가능한 도구 계약을 대조. 조회할 수 없는 유효 한도는 미확인으로 유지 |
| WIKI 경로/연결 설정이 바뀜 | 기존 연결 변경 절차에서 대상과 권한/원문을 확인. 다른 연결의 cursor나 이전 경로의 성공을 재사용하지 않음 |
| 모듈의 SDK/도구 선언이 바뀜 | 설치/갱신의 영향 검사에서 도구 발견, 인자와 반환 해석을 확인. 사용자 Codex를 자동 갱신하거나 옛 버전으로 되돌리지 않음 |
| 선택적 한도 정보만 조회되지 않음 | 확인 가능한 기본 읽기까지 막지 않음. 실제 수신/범위 대조를 유지하고 누락을 확인할 수 없는 경우에 해당 작업을 미완료로 알림 |

Codex가 모델/설정을 선택하는 책임과 MCP 서버가 연결/요청/원문을 확인하는 책임을 구분한다. 표준 MCP 초기화 정보만으로 모델 변경을 감지했다고 판단하지 않는다. 현재 호스트에서 선택/변경 사실을 전달받을 수 있는 방법과 자동 확인 코드는 미구현이다. 사용자에게 모델을 바꿀 때마다 수동 검사 명령을 요구하는 방향으로 확정한 것도 아니다.

이전 결과는 바뀐 입력과 직접 의존하는 범위만 다시 확인하며 변경 없는 검사까지 전부 반복하지 않는다. 서로 다른 날짜에 0.170.0과 0.171.0에서 일부 읽기가 성공한 사실은 각 표본의 관측이다. 같은 설치를 갱신하고 이전 작업/문서/설정을 보존했는지 대조한 갱신 시험으로 합산하지 않는다. 한도 관련 값은 [공식 설정 설명](https://learn.chatgpt.com/docs/config-file/config-reference)과 실제 적용을 구별하며 전역 설정에 자동 기록하지 않는다.

### 갱신 비용과 실패의 크기

생성 방식은 **공통 원본이 바뀐 시점과 Codex가 읽는 생성본이 갱신된 시점이 다를 수 있다**는 비용을 만든다. 아래는 이해를 위한 가상 예시이며 현재 사용자 설정이나 실제 장애의 관측이 아니다.

| 순서 | Git 공통 원본 | 이 기기의 생성본과 실제 사용 |
| --- | --- | --- |
| 최초 연결 완료 | 현재 팀 설정 | 같은 설정에 자신의 WIKI 경로를 합쳐 사용 |
| 팀이 새 접근 제한을 추가하고 커밋 | 새 제한 포함 | 다른 기기의 생성본은 아직 예전 설정 |
| 팀원이 Git pull | 이 기기도 새 공통 원본을 받음 | Git에서 제외된 생성본은 그대로. 일반 Codex가 새 원본을 직접 읽는 것은 아님 |
| 연결 갱신 후 적용 확인 | 새 공통 원본 | 새 제한과 기존 개인 WIKI 경로를 함께 반영. 열린 세션은 실제 적용/재진입 필요 여부 별도 확인 |

따라서 ‘Git pull이 성공했다’와 ‘새 팀 설정으로 Codex가 동작한다’는 같은 결과가 아니다. 공통 원본을 바꾸지 않은 평소 작업에는 재생성이 필요하지 않으며, 단순 앱 코드/WIKI 본문 변경마다 설정을 갱신한다는 뜻도 아니다.

| 문제 | 영향 판단 | 처리 방향과 남는 한계 |
| --- | --- | --- |
| 공통 원본 변경을 생성본에 반영하지 않음 | 내용에 따라 낮음부터 높음. 표시/선호 차이, 도구 실행 실패, 새 접근 제한 누락의 영향은 서로 다름 | 원본/생성 기준의 불일치를 확인하고 갱신 후 실제 적용 검사. 의도한 권한 제한이 적용됐다고 오인하는 경우는 출시 차단 조건 |
| 재생성으로 사용자의 직접 편집을 덮음 | 높음. 정책 완화나 설정 유실 가능 | 이전 기준/현재 편집/새 원본을 대조하고 충돌은 보존한 채 확인. 기존 갱신/복원 계약 재사용. 임의의 TOML 편집을 항상 자동 통합한다고 약속하지 않음 |
| 기존 공유 config의 관리 방식 전환 | 초기 전환과 장기 호환의 비용. 기존 자동화가 정확한 파일명을 기대하면 함께 영향받음 | 설치 전 공유/소비 경로를 확인하고 전환은 선택. 동의 없으면 기존 파일 유지. 설명만으로 해소되는 기술 문제가 아님 |
| 제외된 생성본의 삭제/브랜치 덮어쓰기 | 입력이 남으면 재생성 가능하나 실제 연결은 끊길 수 있음 | 원본/개인 입력/사용자 편집의 보존 상태를 구별. 입력까지 잃으면 재입력/복구 필요. Git 제외는 백업이 아님 |

자동화 후보의 우선순위는 다음과 같다. 아직 이 절차를 채택하거나 구현한 것은 아니다.

1. **모듈이 수행하는 설치/연결/업데이트에서는** 공통 원본과 생성본의 대조, 필요 시 생성, 형식/소유/실제 적용 확인을 같은 완료 조건으로 연결한다. 생성만 끝났다고 연결 완료로 표시하지 않는다.
2. **모듈 밖에서 받은 변경에는** 원본 내용 해시와 이전 생성 기준을 좁게 대조하는 감지 경로가 필요하다. 최초 진입/재개와 관련 변경 경계의 후보를 검증하며 매 요청의 전체 Git/DB/문서 읽기를 추가하지 않는다. 활성 세션 도중 변경도 별도 입력이다.
3. [Git의 post-merge/post-checkout](https://git-scm.com/docs/githooks)은 일부 갱신 뒤 실행할 수 있지만 실패한 merge, 다른 Git 작업, 수동 편집까지 모두 포괄하지 않는다. 기존 사용자 Git hook을 교체하거나 이것을 유일한 동기화 보장으로 삼지 않는다. 전역 hook 설정은 변경하지 않는다.
4. [Codex 시작 hook](https://learn.chatgpt.com/docs/hooks#sessionstart)은 감지/안내 후보지만 신뢰/활성화가 필요하고, 공통 설정을 반영하기 전의 시작을 전부 통제하는 장치는 아니다. hook 비활성/실패, 설정 파싱 실패로 hook까지 도달하지 못하는 경우와 세션 권한 재적용을 따로 검증한다. 모듈의 작업 중단을 Codex 전체의 권한 철회로 설명하지 않는다.

영향을 줄이려면 생성 책임을 최소화해야 한다. AGENTS, skill, script와 별도로 읽히는 [프로젝트 hooks.json](https://learn.chatgpt.com/docs/hooks#where-codex-looks-for-hooks)은 기존 공유 경로를 우선하며, 모든 하네스 구성을 config 템플릿에 몰아넣지 않는다. 기존 팀의 config 공유 충돌 자체가 이 분리만으로 없어지는 것은 아니다.

내용 해시 비교와 설정 생성은 AI 없이 구현할 수 있어 그 계산 자체에 모델 토큰이 필요하지 않는다. 실행 시간과 정상/오류 출력에 따른 전체 토큰 차이는 미측정이다. 주된 비용은 모델 사용량보다 동기화 경계, 사용자 편집 보존과 도구 버전/팀 환경의 호환 검증이다. 프로젝트/브랜치/기기와 기존 설정 관리 도구가 늘수록 검증 조합이 늘지만 현재 발생률이나 공수를 수치로 추정하지 않는다.

판단은 **통제 가능한 설계 후보이지만 가벼운 편의 보완으로 보기는 어렵다**는 것이다. 한 번 준비한 뒤 변경 없는 평소 사용은 단순하게 유지할 수 있다. 반면 변경된 권한이 조용히 누락되거나 설정 변경마다 사용자가 원인을 추적해야 한다면 현재의 신뢰성/사용성 요구를 충족하지 못한다. 기존 관리 방식 전환의 선택과 일반 진입에서의 감지/갱신/적용 검증 전에는 최선이나 지원 완료로 확정하지 않는다.

### 현재 검증과 남은 확인

[프로젝트 로컬 설정 시험](../../evidence/experiments/runtime/2026-11-18_11-03-32-project-permissions.md)은 Windows Codex 0.169.1에서 10개 설정 조회를 확인했다. A/B/A와 A 하위 폴더는 자기 설정을 읽었고 C의 전후 설정은 같았다. D는 연결 전과 자기 정의를 받은 뒤 모두 조회됐다. 기존 sandbox 입력도 E의 루트만 추가한 프로젝트 설정에서 기존 허용 루트/네트워크 값이 보존됐다.

이어 명시적 프로필과 일회성 MXC 선택의 native sandbox에서 A는 WIKI-A, B는 WIKI-B에 파일을 쓰고 다시 읽었다. 상대 WIKI에 대한 쓰기와 C의 외부 WIKI 쓰기는 거부됐다. **이는 실제 파일 권한의 부분 검사이며 일반 TUI/세션 재개, 모든 기존 정책과 제품 설치기의 성공은 아니다.** 모듈이 기본으로 MXC를 강제하거나 사용자 전역 설정에 쓰는 안도 아니다. 모든 시험에서 실제 사용자 config는 유지했다.

전용 시작 명령 기본은 ADR 0022로 채택했다. [Windows 인자 비교](../../evidence/experiments/runtime/2026-11-18_13-54-14-launch-arguments.md)에서 .cmd 경유의 환경변수 확장과 셸 없는 실행의 원문 보존을 관측했다. 이어 [터미널 시험](../../evidence/experiments/runtime/2026-11-18_14-23-43-terminal-start.md)용 시작 파일의 경로/명령 검사를 통과했지만, 사용자 첫 실행은 추가 쓰기 루트를 허용하지 않는 권한 때문에 종료됐다. 기본 권한 상속에서의 최초 실패와 명시적 선택 뒤 결과를 구분한다.

시험 파일에 사용자가 이번 실행의 workspace-write를 명시할 선택 인자를 추가했다. 후속 인증을 마친 뒤 [시험 WIKI 읽기와 수정](../../evidence/experiments/runtime/2026-11-18_14-49-24-terminal-io.md)의 사용자 출력이 실제 파일과 일치했고 요청한 상태 한 줄 외에는 원본 바이트가 보존됐다. 이어 같은 세션 ID로 재개해 프로젝트/WIKI 권한, 직전 변경 설명과 파일 보존을 확인했다. 사용자는 재개 대화 선택 외 추가 요청이 없었다고 보고했다. 다른 설정의 호환성은 남아 있다. 기본 상속을 자동 변경하지 않는다. 제품의 최초 준비에서는 현재 권한이 허용하는지와 사용자 선택을 먼저 확인하고, 외부 WIKI 연결을 위해 무관한 권한을 덮거나 전역 설정을 고치지 않는다. 이번 시험은 시작과 재개에 workspace-write를 명시했으므로, 제품의 최초 선택 저장/재사용까지 완료한 것은 아니다. 전체 옵션, 작업 중 취소/비정상 종료와 다른 프로젝트 대화의 잘못된 선택은 별도로 검증한다. 선택 MCP의 [후속 부분 결과](../../evidence/experiments/wiki-access/2026-11-18_15-50-14-mcp-projects.md)는 A/B 실제 읽기, A 재개와 하위 경로 보정까지이며 기본 진입 전체의 수용과 구분한다.

근거: [프로젝트 설정 계층](https://learn.chatgpt.com/docs/config-file/config-basic), [권한 설정과 기존 sandbox](https://learn.chatgpt.com/docs/permissions), [프로젝트 설정과 프로필 제한](https://learn.chatgpt.com/docs/config-file/config-advanced#project-config-files-codexconfigtoml), [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox), [Git 제외의 범위](https://git-scm.com/docs/gitignore). 실제로 채택할 연결 방식과 그에 필요한 변경/제외 절차는 우리 모듈의 구현과 검증이 남아 있다.

### 일반 Codex에서 연결하기

아래 트리거는 최초 기기 연결이 부족하거나 경로를 바꿀 때의 설정 기능이다. 준비가 끝난 평소 작업마다 먼저 호출하는 활성화 단계가 아니다. 일반 사용의 완료 기준은 [설치 후 일반 Codex 사용](entry.md#%EC%84%A4%EC%B9%98%20%ED%9B%84%20%EC%9D%BC%EB%B0%98%20Codex%20%EC%82%AC%EC%9A%A9)을 따른다.

11/15 사용자 의도는 **이미 열린 Codex 안에서 설치된 모듈의 트리거로 WIKI 경로 등록/변경과 연결을 진행하고 같은 세션에서 기능을 사용하는 것**이다. 직전의 확인/안내만으로 좁힌 설명은 이 사용 흐름을 충분히 반영하지 못했다. 외부 터미널의 제품 시작 명령과 Codex 안의 진입은 같은 프로젝트 설정과 공통 연결 코드를 사용한다. 별도 WIKI 처리 로직이나 두 번째 설치본을 만들지 않는다.

흐름은 `일반 codex → 설치된 연결 트리거 → 저장 경로 재사용 또는 사용자 입력 → 공통 connect/check 처리 → 권한이 준비된 현재 세션에서 작업`이다. 구체적인 트리거 이름은 미정이다. 구현 후보는 사용자가 명시적으로 호출하는 skill이 필요한 입력을 받고 프로젝트의 연결 코드를 호출하는 방식이다. [공식 skill 안내](https://learn.chatgpt.com/docs/build-skills)는 CLI에서 `/skills` 또는 `$`로 skill을 선택하고 지침과 보조 script를 사용하는 구성을 설명한다. 이 기능의 Windows 실제 동작은 구현 뒤 검증한다.

1. 연결이 이미 있으면 같은 프로젝트/작업 사본인지 확인해 재사용한다. 경로를 바꾸라는 요청이 없으면 입력을 다시 요구하지 않는다.
2. 연결이 없거나 변경 요청이 있으면 사용자에게 WIKI 경로를 받는다. Codex 안에서는 대화로 필요한 값을 모으고 공통 코드에 명시적 인자로 전달하는 후보로 둔다. 외부 콘솔에서 질문받는 방식과 같은 검사/저장 로직을 사용하며, 에이전트 도구 안에 별도 대화형 콘솔을 열어 입력을 기다리게 하지 않는다.
3. 공통 코드가 대상, 경로, 위치표와 필요한 접근을 검사하고 [로컬 연결 — 「공유 설정과 로컬 연결」](entry.md#%EA%B3%B5%EC%9C%A0%20%EC%84%A4%EC%A0%95%EA%B3%BC%20%EB%A1%9C%EC%BB%AC%20%EC%97%B0%EA%B2%B0)을 저장한다. 실패하면 기존 연결과 사용자 파일을 보존한다. 경로 입력과 저장은 모듈의 책임이며 Codex 호스트 권한 설정을 편집하는 것과 구분한다.
4. 현재 세션의 실제 권한이 충족되면 등록한 WIKI를 이용해 원래 작업을 이어간다. 연결 자체를 위해 새 모델/대화 세션을 만들거나 사용자를 외부 터미널로 보내지 않는다. 연결 성공이 요청하지 않은 상세 복원이나 설치/갱신의 실행 허가가 되지는 않는다.

공식 문서의 [`/permissions`](https://learn.chatgpt.com/docs/developer-commands?surface=cli#update-permissions-with-permissions)는 이미 구성된 권한 프로필을 세션에서 선택할 수 있다고 설명한다. [권한 프로필](https://learn.chatgpt.com/docs/permissions)은 외부 경로를 포함할 수 있고 Windows도 지원 대상으로 안내한다. 따라서 기기의 비공유 설정에 한정한 프로필을 준비하고 사용자가 선택하는 경로는 가능하다. 이는 `.harness/local.json`을 Codex가 직접 읽거나 skill이 자신의 권한을 늘릴 수 있다는 뜻은 아니다. 새로 저장한 프로필의 즉시 재로딩, 다음 세션의 자동 선택까지 이 근거로 보장하지 않는다.

경로 설정과 현재 Codex 세션의 권한 변경은 별개다. 연결 트리거는 기존 `connect`와 `check` 책임을 재사용하며 매 요청의 선행 절차로 넣지 않는다. skill은 필요한 코드를 실행하고 사용자가 선택할 권한 절차를 안내할 수 있으나 자체 스크립트나 자식 프로세스로 부모 Codex의 권한을 바꾸었다고 처리하지 않는다.

| 현재 상태 | 최소 보완안의 처리 |
| --- | --- |
| 모듈은 설치됐으나 WIKI 연결이 없거나 변경 요청이 있음 | Codex 안에서 입력을 받아 같은 연결 코드로 검사/저장. 필요한 권한이 충족되면 현재 세션에서 계속 사용 |
| 설치와 필요한 권한이 이미 준비됨 | 같은 지침/실행 파일/설정으로 계속 사용. 연결용 두 번째 모델이나 별도 작업 세션을 만들지 않음 |
| 필요한 경로를 포함하는 권한 프로필이 이미 로드됨 | 사용자가 `/permissions <프로필 식별자>`로 선택하도록 안내. 적용한 뒤 실제 범위 확인. 승인 정책과 모델을 함께 바꾸지 않음 |
| 현재 권한이 부족하고 세션 안에서 적용할 수단도 없음 | 그 제한을 확인한 경우에만 같은 세션의 제품 명령 재개를 대안으로 안내. 재개를 내부 연결의 정상 완료로 세지 않으며 두 번째 대화형 Codex를 중첩 실행하지 않음 |
| 설치/권한 설정이 없거나 지원 여부가 불명확 | 필요한 준비와 제한 원인을 알리고 해당 기능만 대기. 내부 WIKI 복사나 전역 권한 확대로 조용히 대체하지 않음 |

첫 배포의 일반 진입 보완에는 위의 모듈 연결 설정과 재사용을 포함한다. 11/15에는 **Codex 호스트의 권한 설정 자동 생성/병합**을 후속으로 뒀다. 11/18 일반 진입 요구에 따라 첫 지원 환경의 지속 연결 준비는 먼저 해결해야 한다. 모든 기존 호스트 설정을 자동 병합하는 범용 기능까지 선행 구현한다는 뜻은 아니며, 구체 저장/연결 수단을 비교해 지원 범위를 검증한다. 권한 설정 자동화에는 기존 deny/네트워크 정책의 보존, 설정 병합/복원, 로딩 시점과 Windows 조합의 추가 검증이 필요하다. 추가 설계나 구현 검증에서 문제가 드러나거나 더 나은 대안이 확인되면 근거와 영향을 정리해 재검토한다. 모든 sandbox에서 무재시작 연결을 보장하지 않으며 실제 구현 공수도 아직 측정하지 않았다.

기본 `--add-dir`도 파일 접근 권한만 보완하며 프로젝트/hook 신뢰, `.git`이나 `.codex` 등의 보호, 원격 서비스 인증을 모두 해결하지는 않는다. 일반 진입 지원과 승인 재사용은 다음 절의 범위 안에서 판단한다. 11/15 로컬 WSL 패키지 `0.169.0`과 `codex --help`를 읽어 `--add-dir` 제공을 확인했지만 이는 Windows의 실제 연결 시험이 아니다.

### 승인의 재사용과 한계

사용자 요구는 설치, 실행, 조건부 작업과 WIKI 접근 전반에서 필요한 권한을 명시하고 한 번 허용한 범위의 반복 승인을 없애는 것이다. **모듈이 관리하는 같은 범위의 중복 확인을 줄이는 것과 OS, Codex, 원격 서비스의 모든 승인을 영구 통합하는 것은 구별한다.** 후자는 모듈이 보장할 수 없다. 아래 경계를 적용하며, 방향 채택을 현재 호스트의 설정 변경 허가로 확대하지 않는다.

| 승인 또는 접근 | 재사용 수단과 적용 경계 |
| --- | --- |
| 모듈의 작업 범위 확인 | 선택 기능, 대상과 작업을 보여주고 승인된 범위 안에서는 재질문하지 않음. 설치 도구를 직접 실행한 경우와 AI가 도구를 호출하는 경우의 실제 권한은 구별 |
| 코드와 WIKI 파일 접근 | 로컬 경로 등록과 도구의 실제 쓰기 허용을 연결. 지속 설정 또는 시작 인자로 반복 사용. 다른 위치나 기기까지 과거 승인을 자동 확대하지 않음 |
| 명령 실행 | Codex가 지원하는 좁은 명령 허용 규칙은 사용자 동의로 재사용. 일회성 승인을 영구 허가로 해석하거나 `python`/셸 전체를 허용하지 않음 |
| 프로젝트와 hook 신뢰 | 도구가 저장한 신뢰를 재사용. 새 hook이나 변경된 정의 등 도구가 재검토를 요구하면 차이와 이유 안내 |
| Git 원격/API 인증과 Windows 권한 | 제공자의 인증 저장, 권한 범위와 OS 정책을 따름. 만료, 철회, 다른 저장소, UAC를 모듈의 승인 기록으로 대신하지 않음 |

최초 준비 화면에는 선택한 기능에 필요한 대상 경로, 읽기/쓰기 또는 원격 작업, 저장 위치, 지속 범위와 해제 방법을 모아 보여준다. 한 번에 안내하는 것과 여러 권한 주체의 확인창을 하나로 합치는 것은 다르다. 외부 도구의 확인이 남으면 이유와 횟수/범위를 알 수 있게 하되 확인하지 않은 횟수를 약속하지 않는다. 선택하지 않은 후속 기능의 권한을 미리 수집하지 않는다.

재실행과 재개에서는 같은 기기/프로젝트/대상/행위에 대한 유효 설정을 재사용한다. 모듈 로컬 기록은 연결/확인 근거이며 권한의 원본이 아니다. 실제 도구/OS가 거부하면 과거의 `approved` 같은 표식으로 진행하지 않는다. 범위 확대, 권한 철회/만료, 대상 교체와 도구가 요구하는 변경 신뢰는 다시 처리하고 이유를 표시한다. 새로운 승인 요구가 없는 단순 재시작/동일 범위 작업에 모듈 자체의 확인을 반복하지 않는 것이 수용 목표다. 상세 저장 필드는 기존 로컬 연결과 복구 명세에서 필요한 만큼 정하며 별도 승인 DB부터 만들지 않는다.

파일 쓰기 권한은 같은 위치의 모든 작업을 승인했다는 뜻이 아니다. PR 승인/병합을 사람이 수행하는 기존 정책, 사용자 편집 보존과 삭제/공개 범위는 유지한다. 영구 무질문을 만들기 위해 sandbox를 해제하거나 hook의 신뢰를 우회하지 않는다. `approval_policy = "never"`도 부족한 권한을 추가하는 수단이 아니다.

근거: [Codex 승인과 sandbox](https://learn.chatgpt.com/docs/agent-approvals-security)는 실행 권한과 확인 정책을 구분한다. [명령 규칙](https://learn.chatgpt.com/docs/agent-configuration/rules)은 TUI의 허용 목록을 사용자 설정에 저장해 이후 호출에 재사용하지만 더 제한적인 정책을 우선한다. [hook 신뢰](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)는 현재 정의의 해시를 기준으로 하므로 변경 시 재검토가 필요하다. 허용 경로 하나로 이들 통제를 대체하지 않는다.

### 최초 실행 선택과 재사용

11/18 실제 시험에서는 사용자가 workspace-write를 명시한 뒤 외부 WIKI를 읽고 수정했지만, 다음 실행의 선택 저장까지 검증한 것은 아니다. 이 절은 기존의 한 번 연결/동일 범위 승인 재사용 요구를 시작 명령에 연결하는 상세 초안이다.

| 상황 | 시작 명령의 처리 |
| --- | --- |
| 현재 설정이 등록 WIKI 접근을 충족 | 기존 권한을 상속하고 필요한 경로만 전달. 별도 권한 선택을 만들거나 더 넓은 모드로 바꾸지 않음 |
| 최초 연결에 필요한 권한이 부족 | 프로젝트/WIKI와 달라질 접근 범위를 보여주고 현재 실행 또는 이 작업 사본에서의 재사용을 구별해 입력받음. 한 번 허용한 범위에 모듈 자체의 확인을 반복하지 않음 |
| 같은 기기/작업 사본의 유효한 선택이 있음 | 현재 관련 설정과 대상이 선택 당시 조건에 맞으면 재사용. 재개에도 같은 연결 절차 사용 |
| 대상 교체, 관련 정책 변경, 선택 철회 또는 확인 불가 | 예전 선택을 자동 적용하지 않고 영향을 받는 연결만 보류. 현재 설정만으로 충분하면 상속 경로 사용. 부족하거나 범위가 달라질 때만 원인과 필요한 선택 안내 |
| 새 팀원, 새 clone 또는 worktree | 현재 작업 사본에서 로컬 준비. 다른 사람/작업 사본의 선택을 같은 project_id라는 이유로 복사하지 않음 |

저장 대상은 사용자가 반복 적용하겠다고 고른 실행 방식/권한 선택, 적용할 프로젝트와 WIKI의 연결, 그 선택을 다시 사용할 수 있는 관련 설정의 확인 근거다. 코드 루트와 WIKI 경로 등 이미 가진 정보를 중복 저장하지 않는다. 이름이 같은 권한 프로필의 내용이 바뀐 경우도 구별해야 한다. 필드 후보는 「연결 설정의 필드와 읽기 규칙」을 따르고, 비교 순서는 아래 「권한 선택 재사용의 판단 순서」를 따른다. 해당 조회와 실제 Windows 실행이 같은 조건을 해석하는지는 구현 검증으로 남긴다.

선택을 저장한 것과 실제 적용을 확인한 것은 다르다. 시작 실패나 중단이 나도 선택 의도는 보존할 수 있지만 접근 확인을 성공으로 표시하지 않는다. `check`의 파일 읽기, CLI 시작 성공, 실제 세션의 허용 범위를 구별하고 기존 문서를 바꾸는 권한 시험을 자동 실행하지 않는다.

자동 재사용에는 다음 조건을 적용한다.

1. **기본값 상속을 우선한다.** 모듈이 WIKI를 연결한다는 이유로 sandbox, 승인 정책, 승인 검토자, 네트워크를 묶어서 바꾸지 않는다. 사용자가 이번 실행에 명시한 설정은 저장된 과거 선택과 충돌하는지 먼저 대조한다.
2. **선택을 확인한 조건을 비교한다.** 관련된 권한 정의와 실제 대상의 변경을 확인하며, 전역 config 전체의 수정 시각/해시만으로 재승인을 요구하지 않는다. 모델/화면 설정이나 다른 프로젝트의 신뢰 등록만 바뀌었다고 같은 WIKI 선택을 무효화하지 않는다. 관련 조건을 신뢰할 수 있게 조회하지 못하면 동등하다고 추정하지 않는다.
3. **권한 체계를 섞지 않는다.** 기존 권한 프로필을 보존해야 하는 환경에 저장된 `--sandbox workspace-write`를 자동 덧붙이지 않는다. 기존 권한 정의의 세부 제한을 삭제하거나 관리 정책을 우회해서 해결하지 않는다.
4. **선택 해제와 경로 변경을 연결한다.** 사용자는 로컬 연결 절차에서 반복 적용 선택을 해제하거나 변경할 수 있다. 열린 Codex의 권한이 즉시 바뀐 것으로 표시하지 않으며 필요한 재개/재진입과 실제 적용을 확인한다. 모듈은 Codex 전역 config나 자격증명을 쓰지 않는다.

근거: [공식 설정 우선순위](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence)는 CLI 옵션이 일반 config보다 우선한다고 설명한다. [권한 프로필 문서](https://learn.chatgpt.com/docs/permissions)는 기존 sandbox 설정과 새 프로필을 합성하지 않으며 `--sandbox`가 프로필 대신 기존 체계를 선택할 수 있음을 명시한다. 그래서 시험에서 동작한 옵션을 모든 사용자에게 고정 저장하는 방식은 채택하지 않는다. 현재 Windows 설치본에서 관련 조건을 조회하고 선택을 재사용하는 실제 검증은 남아 있다.

### 직접 접근의 저장 항목과 실행 판단

11/22 직접 접근 우선 선택 뒤, 기존 경로 등록과 권한 선택의 책임을 첫 실행기 단위에 대응한다. 새 연결 방식이나 별도 승인 DB를 추가하는 변경이 아니다. 파일 후보는 위 「공유 설정과 로컬 연결」을 유지하며 아래는 저장할 의미와 소비자다. 최종 필드명/직렬화 형식은 구현 전에 이 표와 맞춰 확정한다.

| 정보 | 보관 위치와 갱신 시점 | 사용하는 곳과 유효성 판단 |
| --- | --- | --- |
| 프로젝트 식별과 내부 WIKI 상대 위치, 위치표의 상대 위치 | 공유 설정. 최초 설치 또는 명시한 연결 변경 때 | `connect/check/start/resume`가 같은 경로 해결 절차를 사용. 현재 코드 루트와 실제 설치 설정을 함께 대조 |
| 외부 WIKI의 이 작업 사본 위치 | 제외된 로컬 설정. 경로 등록/변경이 검사를 통과한 뒤 | 다른 clone/기기의 로컬 등록을 자동 재사용하지 않음. 변경 실패 시 이전 연결 보존 |
| 사용자가 반복 적용하기로 선택한 실행 옵션/값 | 같은 로컬 설정. 명시적 반복 선택 또는 해제 때만 | 선택한 범위에서만 시작/재개에 적용. 기본값 상속이면 별도의 허용 기록을 만들지 않음. 매번 준 모델/화면/세션 옵션을 자동 저장하지 않음 |
| 반복 선택을 확인한 대상과 관련 조건의 비교 근거 | 기존 프로젝트/WIKI 정보는 참조하고 필요한 관련 근거만 보관 | 현재 지원되는 조회로 해당 조건이 유지됐는지 확인. 전역 설정 전체 해시의 변화나 다른 프로젝트의 변경을 재승인 사유로 쓰지 않음. 확인 불가를 허용으로 추정하지 않음 |
| 이번 실행의 대상, 프로그램/인자와 준비 판단 | 해당 호출의 결과. 정상 시작마다 DB/active에 누적하지 않음 | 시작기는 준비 결과로 Codex에 인계. 사용자/호출자는 부족한 조건과 다음 행동을 확인. 시작 결과를 실제 WIKI 읽기/쓰기 성공으로 바꾸지 않음 |

경로를 저장했다는 사실은 Codex 접근 허가가 아니다. 예를 들어 WIKI를 한 번 등록한 뒤 다음 날 다른 작업을 새 대화로 시작해도 같은 경로를 해결한다. 현재 권한이 충분하면 기존 설정을 상속한다. 반복 적용을 허용한 선택이 있으면 관련 조건을 대조해 사용한다. 관련 정책이 바뀌어 적용할 수 없다면 그 연결의 준비만 멈추고 이유를 알린다. 같은 WIKI 경로를 다시 입력시키거나 무관한 모델/인증 설정까지 바꾸는 해결책은 사용하지 않는다.

이번 호출의 결과는 다음 사실을 나누어 안내한다. 이를 위해 각각 별도 파일, 상태 DB나 실행기를 만들지는 않는다.

- **등록 확인:** 저장한 코드/WIKI 대상과 필요한 위치표를 확인했다. 원문 읽기 가능 여부도 실제 관측 범위만 알린다.
- **실행 준비:** 현재 설치본에 전달할 대상과 인자, 필요한 선택을 확인했다. 유효 권한을 확인하지 못한 부분은 이유와 함께 미확인으로 남긴다.
- **실제 사용:** Codex가 해당 WIKI를 읽거나 수정한 결과다. CLI 창이 열리거나 준비 검사가 통과했다는 사실로 대신하지 않는다.

권한 부족/정책 거부, 지원되지 않는 조회, 사용자가 선택을 취소한 경우와 CLI 자체 실패를 구별한다. 재사용 가능한 선택은 보존하되 새 실패를 성공으로 덮지 않는다. 일반 Codex 안의 연결 트리거도 같은 저장/확인 코드를 사용하고 현재 세션의 권한을 소급 변경했다고 표시하지 않는다. 비밀값, 자격증명과 대화 본문을 로컬 연결 정보에 넣지 않는다.

저장 필드는 「연결 설정의 필드와 읽기 규칙」, 결과 필드/종료 코드는 「명령 결과의 형식」으로 구체화했다. 지원 옵션의 실제 의미 확인은 아직 구현 조건이다. 이 책임 대응은 [개발 준비 인계 — 「직접 접근 실행기의 개발 준비」](../../development/migration.md)와 [전용 시작 명령 검증 — 「전용 시작 명령의 검증 입력」](../../verification/acceptance.md)에 연결한다. 조회 수단의 한계는 다음 절을 그대로 적용한다.

### 호스트 조회와 실행 인계

11/18 [Windows Codex 0.170.0 조회 시험](../../evidence/experiments/wiki-access/2026-11-18_17-52-34-host-query.md)에서 다음 수단을 확인했다. 공식 App Server는 Codex와 프로그램이 JSON 메시지를 주고받는 통로이며 WIKI용 MCP와는 다른 기능이다. 이번 시험은 격리된 합성 설정/세션을 사용한 부분 조회다. 제품이 매번 별도 서버를 실행하는 구조나 상시 서비스를 채택한 것은 아니다.

| 필요한 정보 | 조회 후보와 사용할 범위 |
| --- | --- |
| 프로젝트별 디스크 설정 | `config/read`의 cwd 지정. A/B와 하위 폴더의 계층을 확인했지만 실제 TUI의 최종 접근 판정은 별도 |
| 관리자가 허용한 조건 | `configRequirements/read`. null을 실제 쓰기 허용으로 해석하지 않으며 이번에는 관리 제한이 있는 환경을 시험하지 않음 |
| 선택 가능한 권한 프로필 | `permissionProfile/list`의 페이지 처리. 이름/설명/allowed는 선택 후보이며 특정 파일에 적용된 권한이 아님. 실험적 인터페이스의 지원 여부 확인 필요 |
| 명시적으로 재개할 기록의 위치 | `thread/read`에 ID와 `includeTurns: false`. 합성 기록의 cwd/notLoaded를 읽었으며 대화 재개는 하지 않음. 새 세션 시작에서는 호출하지 않음 |
| 재개 목록이 필요한 경우 | 기존 선택 화면을 우선. `thread/list`의 cwd는 정확 일치 필터이고 제목 검색은 고유 ID 판별이 아님. `useStateDbOnly`는 원시 기록 보정 스캔을 피하지만 미색인 기록을 빠뜨릴 수 있어 빈 목록을 전체 부재로 보지 않음 |

**조회 결과와 실제 실행 조건을 동일하다고 가정하지 않는다.** 시험에서는 read-only 옵션을 주어도 쓰기 프로필의 후보 목록이 그대로 남았다. 또한 `--profile`을 붙인 app-server는 도움말은 출력했지만 실제 조회 시작은 거부했다. 이 옵션은 사용자의 실행 설정 묶음 선택이며 위의 권한 프로필 목록과 다른 개념이다. `config/read`에도 해당 선택을 지정하는 입력은 없었다. 이를 임의의 config 값으로 바꾸거나 프로필 옵션을 제거해 조회 성공으로 만들지 않는다.

첫 실행기 단위는 **등록한 대상과 사용자 입력을 보존해 현재 Codex에 인계하는 것**이다. 조회는 그 판단에 필요한 곳에서만 사용하며 실제 기동의 옵션/환경과 대응이 확인된 결과만 재사용 근거로 삼는다. 기본값은 상속하고, 확인되지 않은 과거 권한 선택의 자동 적용은 보류한다. 조회할 수 없다는 이유로 무관한 설정을 덮거나 사용자의 정상 실행 옵션을 없애지 않는다. 상속한 옵션을 그대로 인계하는 경로와 자동 권한 선택을 적용하는 경로의 완료 조건을 구별한다.

| 첫 단위의 입력/산출 | 완료 조건 |
| --- | --- |
| 프로젝트와 등록 WIKI, 현재 설치본 | 작업 사본과 경로, 실제 프로그램/버전을 확인. 개발자 경로나 시험 npm 내부 경로를 배포 고정값으로 쓰지 않음 |
| 새 시작 또는 선택적 재개, 사용자가 넘긴 인자 | 새 시작에 세션 ID/목록 조회를 요구하지 않음. 인자는 배열로 보존하고 경로/권한 충돌을 순서로 덮지 않음. 명시적 재개에만 대상 확인 |
| 저장한 반복 선택과 현재 관련 조건 | 필요한 조회의 지원/한계를 판정하고 유효한 범위만 재사용. 조회 실패/미지원과 정책 거부를 구분하며 미확인 접근을 허용 완료로 표시하지 않음 |
| 실행 준비 결과 또는 준비 불가 사유 | 실행할 프로그램, 대상, 인자와 바뀔 범위를 확인할 수 있음. 추가 선택이 필요하면 그 차이를 안내. 프롬프트 자동 전송, 전역 config 쓰기와 모델 요청 없음 |
| 실제 Windows 시작/종료 관측 | 사용자 인증/모델/인자와 터미널 입력을 보존하며 취소/오류를 전달. 준비 결과만으로 WIKI 접근이나 문맥 복구 성공을 판정하지 않음 |

조회 응답 전체, 권한 정의 전체와 대화 preview/본문을 로컬 연결이나 공개 근거에 복제하지 않는다. 관련 항목만 소비하고, 저장하는 비교 근거는 그 출처와 적용 조건을 구분한다. App Server가 만드는 내부 로그/캐시와 모듈의 전역 설정 수정도 구별한다. 이번 격리 시험은 실제 사용자 config 비변경을 확인했지만 전체 사용자 환경의 무부작용 증명은 아니다.

로컬 저장 필드는 앞 절의 후보를 사용한다. 실제 사용자 `--profile`의 기동과 사전 조회 대응, 관리 정책/인증/성능과 Windows 취소는 구현 검증 조건으로 남긴다. 조회 지원을 확인한 것으로 이 조건을 삭제하지 않는다. [공식 App Server](https://learn.chatgpt.com/docs/app-server)의 설정/세션 API와 설치본에서 생성한 스키마를 함께 대조하며 버전이 다르면 지원 범위를 다시 확인한다.

### 권한 선택 재사용의 판단 순서

11/22 보완은 기존의 한 번 선택/동일 범위 재사용을 구현하기 위한 비교 명세다. 새 권한 저장소나 Codex 설정 병합기를 만들지 않는다. [기존 조회 응답의 재검토](../../evidence/experiments/runtime/2026-11-22_23-28-43-permission-reuse.md)는 설정 값과 실행 권한의 구별을 뒷받침하며, 아래 절차의 실제 Windows 성공 근거는 아니다.

1. **대상과 이번 입력을 먼저 정한다.** 현재 작업 사본, 등록 WIKI, 선택한 Codex 설치와 실제 실행 디렉토리를 확인한다. 이번에 사용자가 명시한 권한 옵션과 과거 선택이 충돌하면 과거 옵션을 덧붙이지 않는다. 이번 입력을 보존한 경로와 과거 선택의 자동 재사용을 구분해 안내하고, 저장 기록은 임의 변경하지 않는다.
2. **기본 상속에는 재사용 검사를 강제하지 않는다.** 저장 선택을 적용하지 않는 호출은 현재 Codex 설정과 사용자 인자를 인계한다. WIKI 경로를 등록한 것과 접근이 허용된 것은 다르므로 준비 결과만으로 접근 성공을 표시하지 않는다. 조회 기능의 부재를 정상적인 인자 인계까지 일괄 차단하는 이유로 삼지 않는다.
3. **저장 선택이 필요한 때 적용 전 조건을 조회한다.** 같은 Codex, 설정 원본, 실행 디렉토리와 관련 실행 인자에 대응하는 설정/관리 조건을 읽는다. 최초 저장 때도 반복 적용하기로 고른 옵션은 이 기준 조회에서 제외한다. 이전 쓰기 허용 옵션을 먼저 적용한 결과만 비교하면, 사용자가 새로 설정한 읽기 전용 조건을 가릴 수 있다.
4. **관련 값의 완전성과 비교 결과를 확인한다.** 아래 형식으로 대상, 적용 전 권한과 선택할 프로필의 정의/상속 관계, 관리 제한을 비교한다. `config/read`의 값 부재, `requirements: null`, 목록의 `allowed: true`는 각각 다른 사실이다. 조회 실패나 필수 값 부재를 제한 없음으로 바꾸지 않는다. 알려진 형식에 없는 권한 관련 값은 무시하지 않고 자동 재사용을 보류한다.
5. **현재 조건에서도 선택이 허용되는지 확인한다.** 비교가 같다는 이유만으로 현재 관리 제한을 생략하지 않는다. 선택을 적용한 준비 조건이 기존 권한 체계와 충돌하지 않고 조회/실행의 대응을 확인할 수 있을 때만 저장한 옵션을 넣는다. 프로필 이름만 같거나 그 이름이 목록에 있다는 사실로 충분하다고 판단하지 않는다.
6. **확인한 입력으로 한 번 인계한다.** 조회 후 대상이나 관련 설정이 바뀐 것이 발견되면 준비 결과를 폐기한다. 최종 권한 강제는 Codex가 맡으며 모듈의 확인이 설정 변경과 실행을 원자적으로 묶는다고 주장하지 않는다. 같은 인자를 재시도하더라도 권한 부족을 해결하려고 자동으로 더 넓은 모드로 바꾸지 않는다.

예를 들어 어제 허용한 외부 WIKI를 오늘 다른 모델로 열면 모델 변경만으로 다시 허용을 묻지 않는다. 반면 사용자가 같은 프로필의 쓰기 범위를 줄였다면 저장된 옵션을 먼저 적용해 그 변경을 가리지 않는다. 현재 설정만으로 정상 사용이 가능한 경우는 상속하고, 부족하거나 달라진 범위에 대해서만 필요한 선택을 안내한다.

조회 응답 전체는 프로그램 내부에서 처리하고 모델의 프롬프트, active나 상태 DB로 보내지 않는다. 이 절차에서 모델 생성 요청을 보내지 않으며, 조회 프로세스의 시작 비용/내부 로그/관리 설정 조회는 별도의 실제 검증 대상이다. 정상 시작마다 새 승인 기록이나 장기 조회 서버를 만들지 않는다.

### 재사용 조건의 비교 형식

비교용 값은 메모리에서 정리한 뒤 기존 `launch.context`에 해시만 저장한다. 다음 표의 구분은 계산 입력이며 로컬 설정에 새 파일이나 같은 경로의 사본을 추가하는 뜻이 아니다. 비교 값이 달라졌더라도 과거 원문을 보관하지 않았다면 어떤 설정 줄이 달라졌는지 추정해서 안내하지 않는다.

| 계산 입력 | 포함할 내용 | 제외하거나 별도 확인할 내용 |
| --- | --- | --- |
| 대상 | `project_id`, 실제 코드 작업 사본과 WIKI 폴더의 확인된 위치/식별 | WIKI 본문, 일반 파일 수정 시각, 앱/WIKI의 매 커밋 해시. 문서 편집 자체는 권한 재승인 이유가 아님 |
| 반복 선택 | 저장할 `launch.args`의 정확한 문자열 배열과 그 옵션이 선택하는 권한 체계 | 임의의 이번 요청 인자, 모델/프롬프트/인증. `--add-dir`의 대상은 등록 경로에서 계산하며 다른 폴더를 몰래 더하지 않음 |
| 설정 출처와 호출 조건 | 실제 설정 원본의 식별, 적용되는 프로젝트 계층/신뢰와 관련 명시 옵션, 지원하는 경우 선택된 실행 프로필 | 전역 설정 파일 전체 해시, 무관한 프로젝트 신뢰, 계층 전체의 version 값. 같은 파일의 모델 변경 때문에 재승인하지 않음 |
| 적용 전 권한과 선택의 정의 | 관련 `sandbox_mode`/`sandbox_workspace_write` 또는 선택된 `default_permissions`와 필요한 `permissions` 정의/부모 관계, 승인 정책과 검토자, 관련 Windows/네트워크 설정 | 다른 프로필 전체와 설명 문구만의 변화. 프로필과 기존 sandbox 체계를 모듈이 자체 합성하지 않음 |
| 관리 조건 | 해당 선택에 영향을 주는 sandbox/프로필/승인/Windows 허용 조건과 관련 강제 기능/네트워크 정책 | 무관한 서비스 설정/속도 선택. 조회가 완전한 경우의 null과 응답 자체의 누락을 구별 |

설정 필드는 현재 호스트가 해석한 결과와 지원되는 출처 정보에서 취한다. `config/read`의 추가 필드도 필요한 권한 항목이면 읽어야 하며, 정적 스키마의 명시 필드만 남겨 `default_permissions`나 `permissions`를 빠뜨리지 않는다. 관리된 프로필 정의, 기본값 또는 선택된 `--profile`의 적용 결과를 충분히 얻지 못하면 일부 값만으로 해시를 만들지 않는다. 현재 조회 수단에서 `--profile`을 거부했던 관측은 이 미확인 경로에 해당한다. TUI 인자를 빼거나 별도 TOML 병합으로 성공처럼 바꾸지 않는다.

정규화는 같은 의미의 입력을 일관된 바이트로 만드는 처리다. 비교할 객체의 키는 재귀적으로 정렬하고 UTF-8 JSON을 공백 없이 직렬화해 SHA-256을 계산한다. 배열 순서는 기본적으로 보존하며, 인터페이스가 순서 없는 집합이라고 보장한 항목만 중복 제거/정렬한다. 누락, null, 빈 배열과 false를 하나로 합치지 않는다. 알려진 기본값만 해당 호스트 계약에 맞춰 해석하고, 불명확한 값은 추정하지 않는다. 경로의 대소문자만 바꾸거나 심볼릭 링크 문자열을 비교해 같은 폴더라고 판단하지 않는다.

Codex 버전과 실제 실행 파일은 지원 기능 확인과 진단에 사용한다. 버전 문자열만 달라졌다고 사용자에게 같은 권한을 다시 허용하라고 요구하지 않으며, 새 설치에서 같은 조회/적용 의미를 확인할 수 있어야 재사용한다. 확인하지 못하면 지원 미확인으로 안내한다. 모듈 갱신으로 비교 규칙 자체가 달라졌을 때도 이전 해시와 임의 비교하거나 새 값으로 조용히 덮지 않는다.

| 확인 결과 | 이번 호출과 저장 기록 |
| --- | --- |
| 필요한 값이 완전하고 비교가 같으며 현재도 허용 | 같은 범위의 모듈 확인을 반복하지 않고 재사용 |
| 모델/화면 값이나 문서 내용만 변경 | 비교 입력에 넣지 않음. 다른 조건이 유효하면 재사용 |
| 경로/권한 정의/관리 조건이 달라짐 | 과거 선택 자동 적용 중단. 현재 상속으로 충분한지 판단하고 필요할 때 변경 범위 확인 |
| 조회 미지원/중단, 일부 필드/페이지 누락, 적용 결과 불명확 | 기존 선택 보존, 자동 적용만 보류. 명시 입력을 보존한 실행과 필요한 준비 방법을 안내. 같은 실패 조회를 무한 반복하지 않음 |
| 현재 관리 정책이 선택을 거부 | 그 선택을 적용하지 않음. 사용자의 재확인으로 관리 정책을 우회하지 않음 |

현재 명세는 [설정 우선순위](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence), [권한 체계](https://learn.chatgpt.com/docs/permissions)와 기존 저장 응답을 기준으로 한 설계다. 정확한 조회 호출/옵션 대응, 실제 권한 적용과 지연은 [재사용 수용 입력 — 「권한 선택 재사용의 검증 입력」](../../verification/acceptance.md)에서 확인한다. 어떤 Codex 업데이트에도 자동 호환되거나 모든 승인창이 사라진다는 보장은 아니다.

### 설치기와 시작 명령의 대상 확인

11/23 사용자가 설치기 실행에 관한 질문임을 정정하고 시작 명령도 함께 보완하도록 확인했다. **대상을 확인하는 기준은 함께 사용하되, 설치와 시작을 같은 동작으로 만들지 않는다.** 설치기는 변경 계획/보존/반영으로, 시작 명령은 정상 설치본의 실행으로 이어진다. 설치 상태별 처리는 [설치기 위치와 재실행 판단](install.md)이 소유한다. 이 절은 입력과 보호 명세이며 구현 결과가 아니다.

| 확인 순서 | 두 진입에서 지킬 기준 |
| --- | --- |
| 명령/옵션 | 도움/버전 조회는 프로젝트 없이 처리. 알 수 없는 동작이나 잘못된 옵션을 기본 시작/설치로 바꾸지 않음. OnepLoom 옵션과 하위 프로그램에 넘길 인자는 구분 |
| 대상 입력 | 명시한 프로젝트가 있으면 그 위치를 사용. 대상 입력의 상대 경로는 최초 호출 작업 폴더 기준으로 해석. 대상 입력이 없을 때만 현재 작업 폴더에서 후보를 확인. 시작 명령의 목록 선택은 아래 채택 흐름으로 구분. 명시 경로가 잘못됐다고 현재 폴더나 마지막 프로젝트로 대체하지 않음 |
| 위치 확인 | 입력 경로의 존재와 디렉토리 여부, 실제 위치와 접근 조건 확인. 없는 경로를 자동 생성하지 않음. 설치기 보관 폴더/시작 프로그램 폴더를 대상 프로젝트로 대신 사용하지 않음 |
| 저장소 경계 | Git 작업 폴더의 실제 루트를 확인. 하위 폴더 실행은 같은 루트에 연결하되 중첩 저장소, submodule과 worktree의 경계를 넘어 상위 설치본으로 대체하지 않음 |
| 의도/등록 대조 | 확인한 대상과 설치 기준/프로젝트 설정이 같은 작업 사본인지 대조. 동명 폴더, `.git` 존재나 이전 대화만으로 확인을 대신하지 않음. 잘못 복사된 설정/허용되지 않은 링크는 반영/실행 전에 중단 |
| 목적별 인계 | 설치기는 확인한 범위의 설치 상태를 판단. 시작 명령은 준비된 설치본에 인계하며 없거나 불완전하면 준비/복구 안내. 어느 쪽도 상대 동작을 자동 수행하지 않음 |

Git의 [작업 폴더와 루트 조회](https://git-scm.com/docs/git-rev-parse)는 저장소 경계를 확인하는 수단이다. 프로젝트의 업무 의미나 설치 허가를 증명하지 않는다. 단순히 `.git` 디렉토리를 찾는 코드로 정상 worktree의 `.git` 파일을 놓치거나, 상속된 `GIT_DIR`/`GIT_WORK_TREE`가 다른 저장소를 가리키는 것을 무시하지 않는다.

대상 지정 없이 홈/드라이브 최상위나 여러 프로젝트를 모은 폴더에서 실행했을 때는 하위 프로젝트를 찾아 임의로 선택하지 않는다. 설치기는 구체적인 설치 대상을 안내하고 멈춘다. 시작 명령은 아래 [여러 프로젝트의 선택과 실행](entry.md#%EC%97%AC%EB%9F%AC%20%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%EC%9D%98%20%EC%84%A0%ED%83%9D%EA%B3%BC%20%EC%8B%A4%ED%96%89)에 따라 등록 목록에서 사용자의 선택을 받을 수 있다. 하위 폴더나 등록 항목이 하나뿐이라는 이유도 자동 선택 근거가 아니다. 반대로 정상 저장소 안에 하위 디렉토리가 많다는 이유만으로 여러 프로젝트라고 단정하지 않는다. 명시 경로와 목록 선택에도 같은 대상 검사를 적용하며, 넓은 루트를 설치 대상으로 허용하는 예외는 별도 지원 조건 없이 추가하지 않는다.

새 프로젝트에는 아직 OnepLoom 설치 정보가 없을 수 있다. 설치기는 사용자가 의도한 구체적인 대상과 변경 계획을 확인해 새 설치로 진행하고, 시작 명령은 미설치 안내로 끝낸다. Git 부재 상태의 지원/초기 준비는 설치 명세에서 구체화하며 경로 탐지가 실패했다는 이유로 자동 `git init`을 실행하지 않는다.

현재 위치 입력, 명시 대상과 목록 선택은 같은 검사를 통과해야 한다. 시작/재개의 `--project PATH`, `--select`와 인자 구분은 [프로젝트 선택 명령 — 「시작 대상과 명령 문법」](project-selection.md), 사용자 지정 설치 위치와 실행 인계는 [프로젝트 설치본](project-entry.md)이 소유한다. 설치기의 상태별 관리 명령 상세는 후속이다. PC 전체의 활성 프로젝트나 디스크 자동 탐색 엔진을 만들지 않고 오타를 추정해 실행하지 않는다.

정상 등록을 같은 조건으로 재사용할 때 모듈이 대상 확인 질문을 반복하지 않는다. 최초 설치, 바뀐 대상 또는 충돌로 허용 범위가 달라질 때 필요한 확인을 한다. 경로/설치 상태 확인은 일반 코드가 수행하고 AI에게 프로젝트를 추측하도록 요청하지 않는다. 이 설계 보완으로 CMD/Git Bash를 지원 완료하거나 PowerShell 우선 범위를 변경하지 않으며, 셸별 입력/경로 전달은 [실행 환경 — 「터미널 창과 셸, 프로젝트 위치」](install.md)의 실제 검증 대상이다.

### 여러 프로젝트의 선택과 실행

11/23 [ADR 0024](../../decisions/runtime/0024-project-selection.md)로 현재 프로젝트 우선, 밖에서는 등록 목록 선택, 명시적 선택도 제공하는 흐름을 채택했다. 정확한 옵션과 입력 우선순위는 [프로젝트 선택 명령 — 「시작 대상과 명령 문법」](project-selection.md), 화면/취소/자동 실행은 [목록 화면과 입력 종료](project-selection.md)가 소유한다. 이 명세를 실제 제품 실행 결과로 해석하지 않는다.

**선택은 이번 실행에만 적용한다.** A 창을 유지한 채 B를 선택해도 A의 프로젝트/WIKI/권한은 바뀌지 않는다. 전역 활성 프로젝트나 기본 WIKI를 저장하지 않으며, 미설치/손상된 현재 대상이나 잘못된 명시 경로를 다른 프로젝트로 대체하지 않는다. 한 호출에서 여러 프로젝트를 일괄 실행하는 기능은 아니다. 같은 WIKI를 지정한 별개 프로젝트에는 기존 [동시 편집 보호 — 「동시 편집과 반영」](install.md)가 계속 적용된다.

#### 사용자별 프로젝트 목록

목록은 루트 경로를 찾는 사용자별 보조 자료이며 프로젝트의 실행 허가/설치 상태를 증명하지 않는다. [저장 위치와 형식 — 「목록의 저장 위치와 형식」](project-selection.md), [등록과 제거 — 「등록과 이동, 목록 제거」](project-selection.md), [중단/동시 갱신 — 「기록 중단과 동시 갱신」](project-selection.md)을 별도 명세로 분리했다. WIKI/권한/DB/세션은 목록에 복제하지 않고 선택한 프로젝트에서 확인한다. 기기 명령의 `registration.json`과도 구별한다.

목록 제거는 프로젝트/WIKI 삭제가 아니며 목록 오류로 설치를 초기화하지 않는다. 현재 위치/명시 경로 시작은 목록 없이도 동작해야 한다. 목록 조회와 선택은 일반 코드로 처리하고 모델에 판별을 맡기지 않는다. 설치기는 기존 신규/중단/갱신 판단을 유지하며 시작 대상 선택으로 설치나 WIKI 복원을 자동 실행하지 않는다. 실제 저장/선택/시간과 Windows 동작은 [검증 입력 — 「프로젝트 목록 형식과 명령 검증」](../../verification/acceptance.md)으로 확인한다.

### 짧은 명령의 등록과 프로젝트 선택

11/23 사용자가 **격리된 Python 환경과 표준 명령 등록**을 채택했다([ADR 0023](../../decisions/runtime/0023-command-registration.md)). 목표는 사용자가 `oneploom` 또는 `oneploom start`를 입력하면 현재 위치 또는 [명시적으로 선택한 프로젝트 — 「여러 프로젝트의 선택과 실행」](entry.md#%EC%97%AC%EB%9F%AC%20%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%EC%9D%98%20%EC%84%A0%ED%83%9D%EA%B3%BC%20%EC%8B%A4%ED%96%89)의 설치본과 등록 WIKI를 사용하는 것이다. [무인자 시작 — 「시작과 재개의 명령 흐름」](entry.md#%EC%8B%9C%EC%9E%91%EA%B3%BC%20%EC%9E%AC%EA%B0%9C%EC%9D%98%20%EB%AA%85%EB%A0%B9%20%ED%9D%90%EB%A6%84)과 함께 적용하되 하네스 기능은 프로젝트 안에 유지한다. 아래는 채택한 설계이며 실제 기기 등록, PATH 변경과 실행 파일 생성은 아직 하지 않았다.

PowerShell은 프로젝트에 파일이 있다는 이유만으로 그 파일 이름을 명령으로 찾지 않는다. [명령 탐색 규칙](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence)에 따라 명시 경로 또는 PATH에 등록된 실행 위치 등이 필요하다. PATH는 셸이 명령을 찾는 폴더 목록이며 Codex의 전역 설정과는 다른 사용자 환경이다.

| 방식 | 사용 예와 이득 | 비용과 판단 |
| --- | --- | --- |
| **사용자 기기에 작은 시작 파일을 등록** | 한 번 준비한 뒤 프로젝트 A와 B에서 같은 `oneploom start`를 사용. 시작 파일은 대상 설치본을 찾아 실행만 인계 | 11/23 채택. 사용자 전용 실행 폴더와 PATH 항목, 등록/제거와 호환 검사가 필요. 하네스 본체와 WIKI 처리 코드를 외부로 옮기지 않음 |
| 프로젝트 파일의 경로로 실행 | 루트에서 `py -3 .\oneploom\cli.py start`. 프로젝트 밖의 영구 등록이 없음 | 항상 제공할 직접 경로. 하위 폴더에서는 위치에 맞는 경로를 입력해야 해 평소 사용 편의가 낮음 |
| PowerShell 프로필에 함수 등록 | 함수를 통해 현재 프로젝트의 실행 파일을 찾을 수 있음 | 셸 프로필, 실행 정책과 기존 함수의 영향을 받음. 다른 셸의 동작도 같지 않으므로 첫 기본안으로 추천하지 않음 |

사용자 전용 위치 예시는 `%LOCALAPPDATA%\Programs\OnepLoom\bin`이다. [Windows 표준 폴더](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)의 사용자별 프로그램 위치를 참고하며 C 드라이브나 실제 계정 경로를 고정하지 않는다. 프로그램 전체를 `Program Files`에 설치하거나 상시 서버를 띄우는 안이 아니다. 표준 등록으로 생성한 콘솔 실행 파일을 사용하고, 아래 인자 보존과 복사 실행 조건은 실제 Windows에서 검증한다.

#### 등록 파일 형식의 비교

11/22 대안을 비교한 뒤 11/23 사용자가 **Python 패키지의 표준 명령 등록으로 `oneploom.exe`를 만드는 안**을 채택했다. 아래 대안은 선택 근거로 보존한다. 실제 패키지 생성/설치와 Windows 실행은 미완료이며, 설계 채택을 현재 사용자 기기의 변경 허가로 확대하지 않는다.

| 방식 | 이점 | 비용과 판단 |
| --- | --- | --- |
| **격리된 Python 환경에 표준 명령 등록** | [PyPA console_scripts](https://packaging.python.org/en/latest/specifications/entry-points/#use-for-scripts)가 Windows 콘솔 실행 파일과 표준 입출력을 연결. 별도 배치 파일의 인자 재해석 단계를 줄이고 널리 쓰이는 설치 규격을 활용 | 11/23 채택. `venv`와 그 환경의 `pip`, 배포본에 포함할 작은 wheel(Python 설치용 패키지 파일), 기기 등록/복구 관리가 필요. 용량과 초기 준비 시간은 미측정 |
| `.cmd` 시작 파일 | 텍스트 파일 중심이라 배포가 작고 내용을 읽기 쉬움 | [Python subprocess](https://docs.python.org/3/library/subprocess.html#security-considerations)의 Windows 배치 파일 해석 조건과 기존 특수문자 관측을 해결해야 함. 단순 `%*` 전달을 첫 기본안으로 채택하지 않음 |
| 자체 제작한 Windows 실행 파일 | Python 명령 등록 도구에 의존하지 않는 시작 파일을 만들 수 있음 | 빌드 도구, CPU 대상, 바이너리 배포와 인자/종료 처리의 유지보수 범위가 커짐. 현재 마감과 Python 준비 전제를 고려하면 우선순위가 낮음 |

명시 경로의 `py -3 .\oneploom\cli.py start`는 기기 등록을 하지 않거나 문제가 있을 때의 대안으로 유지한다. 어떤 실행 파일도 PowerShell의 최초 인자 해석, 기업의 실행 정책과 Codex까지의 전달을 자동 해결하지는 않는다. [PowerShell 인자 해석](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing)에 맞는 실제 입력부터 검증하며, `.exe`라는 이유만으로 오류가 없어졌다고 판단하지 않는다.

#### 표준 명령 등록 후보의 흐름

11/23 채택한 이 후보에서도 **배포 채널은 Git Release + Python**, 하네스 본체는 프로젝트의 `oneploom/`이다. Git Release에 작은 명령 연결용 wheel을 포함하고 외부 관리 도구가 로컬 파일로 설치한다. 적용 프로젝트 Git에는 wheel을 기본 포함하지 않으며 [팀원 최초 준비 — 「팀원 첫 준비의 배포 자료」](install.md)와 [명령만 등록 — 「시작 명령만 처음 준비하기」](management.md)을 구분한다. PyPI 공개, uv/npm/pipx 설치를 추가하는 안이나 PC 전체에서 하나의 하네스 본체를 공유하는 안과 구별한다. wheel의 공식 버전도 같은 OnepLoom 원본/릴리스에서 관리하며 사용자 프로젝트 편집에 새 버전을 부여하지 않는다.

1. 기존 등록/동명 명령과 선택한 Python을 확인하고, 만들 파일과 사용자 PATH의 한 항목을 안내한다. `venv`/`pip`가 없거나 정책상 쓸 수 없으면 필요한 준비를 안내하고 멈춘다. 같은 유효 등록은 재사용한다.
2. 사용자 프로그램 위치의 OnepLoom 전용 영역에 [가상환경](https://docs.python.org/3/library/venv.html)을 만든다. 이는 명령 연결 프로그램의 Python 패키지만 격리하는 폴더다. 프로젝트/WIKI/작업 DB를 이곳으로 옮기지 않으며 사용자나 프로젝트의 기존 가상환경을 재사용해 변경하지 않는다.
3. 해당 환경의 pip로 릴리스에 포함된 정확한 wheel을 설치한다. [로컬 파일 설치와 no-index](https://pip.pypa.io/en/stable/cli/pip_install/)를 이용하고, 외부 패키지 검색/의존성 자동 다운로드/최신 버전 조회를 하지 않는 입력으로 고정한다. 전역 pip 설정이나 환경변수가 저장 위치/다운로드를 바꾸지 않도록 해당 자식 실행의 조건을 검증한다. 전역 설정 파일은 수정하지 않는다.
4. 생성된 **OnepLoom 명령만** 사용자 PATH에 노출할 전용 `bin`에 둔다. 가상환경의 `Scripts` 전체를 PATH에 넣거나 매번 활성화하면 `python`/`pip`의 선택도 바뀔 수 있으므로 그렇게 안내하지 않는다. Windows의 링크 권한을 요구하지 않는 실행 파일 복사를 우선 검토하되 복사 후 실행, 인터프리터 연결과 제거 소유를 실제 확인한다.
5. 새 터미널에서 `oneploom`이 의도한 연결 프로그램을 선택하는지 확인한다. 이 프로그램은 아래 프로젝트 발견 절차로 대상의 실행 파일에 인계한다. 가상환경의 Python/설치된 명령은 명시 경로로 실행할 수 있으므로 사용자가 매번 `Activate.ps1`을 실행할 필요는 없다. 설치용 다운로드를 정리해도 필요한 등록 환경은 남긴다.

예를 들어 A에서 `oneploom`을 실행하면 A의 프로젝트 실행 파일이 WIKI-A를 연결한다. B에서 같은 명령을 쓰면 B의 실행 파일이 WIKI-B를 연결한다. 기기 프로그램은 이 두 WIKI 목록이나 내용을 전역에 저장하지 않는다.

[pipx의 공개 구현](https://github.com/pypa/pipx/blob/main/src/pipx/commands/common.py)은 환경 안의 앱을 별도 위치에 노출하고 링크 가능 여부에 따라 복사도 다루는 참고 사례다. 그 코드나 전체 관리 기능을 가져오지 않으며 OnepLoom이 만든 한 명령의 등록만 다룬다. 표준 패키지 설치가 사용자 PATH까지 자동 구성해 준다고 가정하지 않는다.

채택안의 비용은 전용 환경의 디스크 용량, 최초 준비 시간과 Python 교체/삭제 후 재구성이다. Python 문서는 가상환경을 이동 가능한 배포본으로 취급하지 않으므로, 준비한 폴더를 단순 이동/이름 변경해 갱신을 끝내지 않는다. 실제 적용할 위치에서 다시 준비하고 명령 연결을 확인한다. 등록 갱신/실패는 기존 설치 보존과 [복구 경계 — 「복구의 대상과 경계」](../workflow/recovery.md)에 연결하며, 연결 프로그램을 복구하는 중 프로젝트 하네스를 자동 갱신하지 않는다. 아래는 11/23에 구체화한 반영/복구 순서와 등록 정보 명세다. 프로젝트 인계 형식과 실제 기기 효과의 구현/검증은 남아 있다.

라이선스는 [pip의 원문](https://github.com/pypa/pip/blob/main/LICENSE.txt)과 [distlib의 원문](https://github.com/pypa/distlib/blob/master/LICENSE.txt)을 확인했다. 현재는 원리를 조사했으며 코드를 복사하거나 배포 파일을 생성하지 않았다. 실제 선택한 설치 도구와 생성/동봉 파일의 출처, 버전, 고지 대상은 [기존 기준 — 「라이선스와 저작권」](../module.md)으로 다시 확인한다. 이번 조회를 최종 배포물의 권리 검증 완료로 표시하지 않는다.

#### 등록과 갱신의 중단 복구

기기 명령 등록은 설치/관리 작업에만 속한다. 평소 `oneploom` 시작마다 환경을 재설치하거나 전체 설치 이력을 조회하지 않는다. 기존 등록이 유효하면 재사용하며, 새 프로젝트 준비 때문에 이미 사용 중인 연결 프로그램을 무조건 최신화하지 않는다.

**새 환경 준비와 사용 명령의 전환을 분리한다.** 예를 들어 기존 명령이 정상일 때 새 wheel 설치가 실패하면 기존 명령으로 계속 사용한다. 반면 명령 교체 직후 기록 저장이 끊겼다면 성공/실패를 추측하지 않고 실제 파일과 환경을 확인한다. 아래는 이 동작을 구현할 순서이며 무중단/무손실을 검증했다는 뜻은 아니다.

| 단계 | 처리와 완료 기준 | 중단 후 처리 |
| --- | --- | --- |
| 대상과 소유 확인 | 같은 사용자 등록을 변경하는 다른 설치/복구가 없는지 확인. 기존 실행 파일, 환경, Python, PATH의 현재 값과 소유를 대조하고 허용한 변경만 보존 | 소유 불명, 사용자 편집 또는 다른 등록 작업이 있으면 쓰기를 보류. 프로젝트의 평소 개발이나 다른 Codex 전체를 잠그지 않음 |
| 새 환경 준비 | 기존 환경을 보존한 채 새 환경을 **앞으로 사용할 최종 위치**에 생성. 확인한 릴리스의 로컬 wheel만 설치하고 출처/내용/설치 결과를 검사 | 실패한 준비물과 원인을 남기며 기존 명령 유지. 준비된 폴더를 이동해 활성화하지 않음. 재실행은 완료 근거가 유효한 단계만 재사용 |
| 전환 전 확인 | 새 환경의 명령을 절대 경로로 실행해 로드/버전/인자 처리를 확인하고 프로젝트 실행본과의 호환 조건을 대조. 검사 때문에 AI나 Codex 대화를 자동 시작하지 않음 | 호환이 불명확하거나 필수 확인이 실패하면 명령/PATH를 바꾸지 않음. 도움말 성공만으로 실제 WIKI/Codex 사용까지 통과 처리하지 않음 |
| 명령 반영 | 전용 bin의 후보와 기존 파일 보존을 확인하고 적용 직전 기준을 재대조. 생성 파일과 의도한 환경의 대응을 실제로 다시 읽어 확인 | 사용 중인 파일의 교체 거부나 결과 불명은 실제 남은 파일/사본을 확인해 복구. 기존 파일이 무조건 그대로라고 가정하거나 사용자 프로세스를 강제 종료하지 않음 |
| PATH 연결 | 처음 등록할 때만 필요한 사용자 PATH 항목을 추가. 기존 항목/순서를 보존하고 적용 직전 값과 저장 결과를 대조 | 다른 설정 변경이 확인되면 이전 PATH 전체로 덮어 복원하지 않음. 명령 파일이 준비돼도 PATH 반영이 미완료면 그 사실과 명시 경로를 안내 |
| 완료와 정리 | 등록 기록, 실제 실행 파일/환경과 새 셸에서의 명령 선택을 대조. 현재 사용할 수 있는 범위와 남은 조건을 구별 | 필수 확인이 남으면 전체 완료 아님. 이전 환경/사본은 실행 중 사용과 복구 의존이 해소됐는지 확인하고 기존 명시적 정리 절차로 처리 |

[venv 문서](https://docs.python.org/3/library/venv.html)는 환경의 이동 대신 대상 위치에서 재생성을 안내한다. 따라서 잠깐 두 환경을 유지하는 디스크 비용을 준비 검사에 포함한다. 새 환경 생성 자체를 기존 연결의 전환으로 기록하지 않는다.

[Windows 파일 교체 문서](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)는 실패별로 파일이 남는 상태가 다를 수 있음을 설명한다. 사용할 교체 API와 복원 절차는 실제 Windows에서 검증하며, 파일/환경/PATH/기록이 하나의 SQLite 트랜잭션으로 함께 commit된다고 가정하지 않는다. **반영 전 의도와 기준 보존 → 실제 변경 → 결과 재조회 → 완료 기록** 순서로, 완료 기록 누락만을 이유로 변경을 반복하지 않는다. 현재 파일이 후보와 같다는 사실 하나로 해당 작업의 쓰기 소유를 단정하지 않는다.

[환경변수의 사용자/프로세스 범위](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables)를 구별한다. 이미 열린 터미널이나 IDE가 옛 PATH를 유지하면 새 환경을 상속하는 창 또는 명시 경로 사용을 안내한다. PATH 전체 교체에는 다른 프로그램과의 동시 쓰기 위험이 남으므로 전후 대조만으로 모든 경쟁을 제거했다고 주장하지 않는다. 동일 등록 작업의 중복 적용 방지와 외부 편집 감지의 구현/시험은 필수다.

등록 복구에 필요한 정보는 **이 기기의 연결 프로그램 소유와 현재 연결**이다. 아래 [기기 등록 정보 — 「기기 등록 정보와 소유」](entry.md#%EA%B8%B0%EA%B8%B0%20%EB%93%B1%EB%A1%9D%20%EC%A0%95%EB%B3%B4%EC%99%80%20%EC%86%8C%EC%9C%A0)에 마지막 확인 결과를 남기고, [기존 DB 연결 — 「등록 작업과 기존 DB의 연결」](entry.md#%EB%93%B1%EB%A1%9D%20%EC%9E%91%EC%97%85%EA%B3%BC%20%EA%B8%B0%EC%A1%B4%20DB%EC%9D%98%20%EC%97%B0%EA%B2%B0)로 중단된 등록 작업을 찾는다. 프로젝트별 WIKI 목록이나 개발 이력을 복제하지 않으며 진행 원본은 해당 작업의 DB 하나다. 기기 등록 소유 정보는 첫 프로젝트를 삭제해도 남고, 상시 기기 DB나 JSON 진행 엔진은 추가하지 않는다.

Python 삭제/교체로 기기 명령 자체가 실행되지 않으면, 외부 배포 설치기의 복구 경로로 필요한 준비를 안내하고 등록 환경을 다시 구성한다. 임의 Python으로 조용히 바꾸거나 프로젝트 하네스를 함께 갱신하지 않는다. 복구 진입은 [외부 관리 도구의 command repair — 「시작 명령의 복구」](management.md)로 연결하며, 대응 안내는 [실행 전 안내와 중단 시 도움](install.md)에 연결한다.

#### 기기 등록 정보와 소유

11/23 표준 등록안의 후속 파일 명세다. **`registration.json`은 기기 명령의 마지막 확인 정보이며 설치 진행표가 아니다.** 예를 들어 A 프로젝트에서 처음 등록했더라도 A의 삭제로 이 파일과 기기 명령이 없어지지 않는다. 프로젝트를 찾는 규칙과 WIKI 설정은 아래 프로젝트 인계 절차를 그대로 따른다.

Windows의 실제 [사용자 프로그램 폴더](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)인 `FOLDERID_UserProgramFiles` 아래 `OnepLoom`을 등록 루트로 사용한다. 다음은 기본 위치의 예시이며 사용자 이름이나 C 드라이브를 코드에 고정하지 않는다.

```text
사용자 프로그램 폴더/OnepLoom/
  registration.json          마지막 확인한 등록과 미완료 작업의 참조
  bin/oneploom.exe            사용자에게 노출하는 명령 하나
  envs/<id>/                 실제 사용할 최종 위치에 만든 전용 Python 환경
```

환경의 `<id>`는 이름 충돌을 피하는 식별자다. 사용자가 고치는 코드에 임의 버전을 붙이거나 공식 릴리스와 다른 버전 체계를 만드는 값이 아니다. 이 위치는 OnepLoom 소유 자료에 한정하며 Codex 전역 설정을 변경하지 않는다.

| 값 | 저장할 최소 내용과 의미 |
| --- | --- |
| `current.environment` | 등록 루트 기준 `envs/<id>` 상대 경로. `bin/oneploom.exe`와 연결이 실제 확인된 환경 |
| `current.command_sha256` | 마지막 확인한 노출 실행 파일의 SHA-256. 내용 비교에 쓰며 파일 안전성이나 삭제 권한의 증명으로 취급하지 않음 |
| `current.path.entry` | 확인한 사용자 PATH의 해당 항목. 실제 등록 루트의 `bin`과 대응해야 하며 임의 명령 경로를 받지 않음 |
| `current.path.added` | 이번 등록 계보에서 도구가 그 항목을 추가했는지 나타내는 boolean. 원래 있던 항목은 `false`로 보존. 갱신 때 새로 추가하지 않았다는 이유로 기존 `true`를 잃지 않음 |
| 선택적 `pending` | `{state_root, db_id, task_id}`. 미완료 등록 작업의 기존 상태 루트, DB 식별과 작업 ID만 연결. 단계, 재시도 횟수, 현재 시도, 결과를 복제하지 않음 |

`current`는 필수다. 확인된 등록이 아직 없는 최초 준비에서만 `null`을 허용하며 소유가 불명확한 기존 설치를 `null`로 바꿔 덮지 않는다. `pending`은 작업이 없으면 생략하고 `null`, 빈 객체나 빈 문자열을 정상 상태로 바꾸지 않는다. `state_root`는 해당 기기에서 확인한 상태 폴더의 절대 경로이며 DB 이름은 기존 `state.db`를 사용한다. 연결된 DB에서 `db_id`, `task_id`, 대상 등록 루트와 허용 범위를 대조한 뒤에만 현재 시도를 찾는다.

패키지 이름/버전/설치 파일은 [표준 `.dist-info` 정보](https://packaging.python.org/en/latest/specifications/recording-installed-packages/)를, 환경의 기반 Python 정보는 [venv의 `pyvenv.cfg`](https://docs.python.org/3/library/venv.html)를 우선 참조한다. 같은 값을 등록 파일에 다시 저장하지 않는다. 선택한 Python의 실제 실행 파일과 릴리스 출처를 검증한 상세 근거는 등록 작업에 남긴다. 이후 별도로 복사한 bin 실행 파일과 사용자 PATH의 변경은 pip의 최초 `RECORD`에 자동 기록된다고 가정하지 않는다.

이 JSON 이름과 필드는 **OnepLoom의 설계 계약**이며 Python의 표준 파일 형식은 아니다. [pipx의 메타데이터](https://github.com/pypa/pipx/blob/main/src/pipx/pipx_metadata_file.py)와 [uv의 설치 receipt](https://github.com/astral-sh/uv/blob/main/crates/uv-tool/src/receipt.rs)는 설치 위치와 관리 정보를 별도로 보존하는 공개 구현의 참고다. 둘을 설치하거나 그 코드를 복사하지 않았다. JSON은 기존 설정/기록의 형식과 맞추기 위한 선택이며 별도 TOML 파서를 추가할 근거는 없다.

읽기 오류, 중복 키, 지원하지 않는 필드/형식, 루트 밖 경로와 허용하지 않은 링크는 신규 등록으로 해석하지 않는다. `added: true`도 영구적인 PATH 삭제 권한은 아니다. 현재 값과 사용자 변경을 다시 확인하고 도구가 추가한 항목만 제거 대상으로 삼는다. 환경 정리 역시 표준 설치 목록과 실제 파일을 대조하며, 알 수 없는 파일이 있으면 폴더 전체를 소유했다고 간주해 지우지 않는다.

평소 명령은 현재 프로젝트의 실행본으로 인계한다. 등록 관리가 필요하지 않은 시작에서 설치 DB 전체를 읽거나 `pending`이 있다는 이유만으로 아직 정상인 기존 명령을 막지 않는다. 다만 전환 후 실제 명령 자체가 손상된 경우에는 정상 사용을 보장할 수 없으므로 외부 설치기의 복구 경로 또는 프로젝트 실행 파일의 명시 경로를 안내한다.

#### 등록 작업과 기존 DB의 연결

등록 파일은 실행 파일을 전환하는 스위치가 아니다. 실제 전환은 bin의 명령을 반영하는 작업이며 `current`는 **마지막으로 확인한 결과**다. 파일, PATH, 등록 JSON과 SQLite 저장은 한 번에 확정되지 않으므로 중단 뒤 어느 하나만 읽어 완료를 추측하지 않는다.

| 실행 상황 | 진행 원본과 수명 |
| --- | --- |
| 프로젝트 설치/기기 준비 중 등록 | 그 실행에서 이미 사용하는 최초 보존 또는 프로젝트 DB에 등록 작업을 별도 `task_id`로 기록. 프로젝트 파일 변경과 복원 범위를 구분하며 DB를 하나 더 복제하지 않음 |
| 프로젝트 없이 기기 명령만 복구 | 외부 설치기의 기존 [최초 보존 절차 — 「최초 보존 자료의 형식」](../workflow/records.md)로 해당 등록 작업의 DB와 사본을 생성. 가짜 프로젝트/WIKI를 만들지 않음. 이 경우 인계할 프로젝트가 없으므로 외부 기록으로 보존하고 기존 명시적 정리를 적용 |
| 완료된 등록으로 평소 사용 | `pending` 참조 없음. 첫 프로젝트나 정리된 설치 이력을 요구하지 않고 현재 프로젝트로 인계. 작업 기록 정리와 현용 환경 제거를 구별 |

두 번째 행은 항상 켜져 있는 기기 DB의 도입이 아니다. 프로젝트가 없는 복구 작업에도 **하나의 작업 기록과 동일한 보존/재개 코드**를 쓰는 것이다. 완료 기록은 자동 삭제하지 않으며 정리 후 잃는 상세 복원 범위를 안내한다. `registration.json`만 남았다고 과거 임의 버전으로 되돌릴 수 있는 것은 아니다.

저장과 전환은 다음 순서로 연결한다.

1. 허용된 등록 루트와 현재 파일/PATH, 기존 등록 정보를 확인한다. 같은 사용자 등록을 수정하는 두 관리 작업은 함께 반영하지 못하게 조정하며 프로젝트의 일반 작업은 잠그지 않는다. 준비 계획과 보존 근거를 기존 DB에 저장한다.
2. 확인한 DB의 작업을 `pending`으로 연결하고 저장 후 다시 읽는다. 최초 등록 폴더 생성도 DB의 준비 범위에 포함한다. 그 직후 끊겨 등록 파일이 없더라도 남은 폴더/파일을 소유 없는 빈 공간이라고 단정하지 않는다.
3. 새 환경 준비와 검증, 명령 반영, 필요한 PATH 연결을 위 [중단 복구 표 — 「등록과 갱신의 중단 복구」](entry.md#%EB%93%B1%EB%A1%9D%EA%B3%BC%20%EA%B0%B1%EC%8B%A0%EC%9D%98%20%EC%A4%91%EB%8B%A8%20%EB%B3%B5%EA%B5%AC)대로 수행한다. 상세 의도/관측과 각 실패는 DB에만 기록한다. 전환 후보 준비 중에는 기존 `current`를 유지한다.
4. 실제 결과와 필수 사용 확인을 대조한 뒤 새 `current`를 저장한다. 이때도 `pending`을 유지하고, 등록 정보의 저장 결과까지 확인해 DB의 등록 작업 완료 근거를 남긴다. 마지막으로 해당 작업의 `pending`만 지우고 재조회한다. 사용자에게 전체 완료를 알리는 것은 이 확인 뒤다. 다른 관리 작업의 참조를 덮지 않는다.
5. DB 완료 뒤 `pending` 해제 전에 중단되면 실제 등록과 완료 근거를 대조한 후 참조 해제만 마친다. 완료 전 중단이면 기존 시도와 실제 상태를 대조해 관측 수집, 재시도 또는 복원을 결정한다. 기록이 없거나 다른 DB면 쓰기를 보류하며 새 DB로 미완료 사실을 숨기지 않는다.

등록 파일도 같은 디렉토리에 후보를 쓰고 검증한 뒤 기대한 이전 내용과 대조하여 교체한다. 파일 교체와 DB/PATH 사이의 중단 구간은 위 순서로 처리하며, 이것만으로 전원 장애나 외부 프로그램의 동시 변경을 모두 해결했다고 주장하지 않는다. 실제 Windows 저장/교체/사용 중 파일 검증은 남아 있다.

최초 DB를 프로젝트로 인계하기 전에는 그 DB를 가리키는 기기 등록 작업과 `pending` 해제를 먼저 끝낸다. 진행 중 참조가 가리키는 DB/사본을 정리하거나 이동하지 않는다. 프로젝트 설치의 실패/이전 구성 선택이 별도 등록 작업까지 자동으로 되돌리지는 않으며, 기기 명령 제거는 기존의 명시적 관리 범위로 처리한다.

기기 파일과 사용자 PATH를 현행 SQL이 이미 다룬다고 가정하지 않는다. 현재 `attempt_files`는 프로젝트/WIKI/state 파일용이므로 [등록 효과의 저장 경계 — 「기기 등록 효과의 저장 경계」](../workflow/storage.md)에 필요한 확장을 명시했다. **이번 완료 범위는 등록 정보와 기록 연결의 문서 명세**다. 그 효과의 DDL/저장 코드, Windows 반영과 실제 복구는 구현 완료 조건으로 남긴다.

#### 프로젝트를 찾고 실행하는 순서

시작 명령은 [설치기와 시작 명령의 대상 확인](entry.md#%EC%84%A4%EC%B9%98%EA%B8%B0%EC%99%80%20%EC%8B%9C%EC%9E%91%20%EB%AA%85%EB%A0%B9%EC%9D%98%20%EB%8C%80%EC%83%81%20%ED%99%95%EC%9D%B8)과 [실행별 선택](project-selection.md)을 먼저 적용한다. 대상이 확정되면 [설치 위치의 저장과 발견](project-entry.md)에 따라 기존 로컬 연결의 module_path 또는 기본 oneploom/을 확인한다. 목록 파일은 실행 파일 경로를 중복 저장하지 않는다.

[프로젝트 실행본으로 넘기는 입력](project-entry.md)이 Python/진입 파일, 절대 대상, 원래 호출 폴더와 인자, 입출력/종료의 상세를 소유한다. 기기 명령은 WIKI/권한을 직접 처리하거나 모델 요청을 만들지 않는다. 프로젝트 코드의 준비가 끝나기 전 Codex를 열지 않고 미설치/불일치/미지원은 [실패 대응 — 「호환성, 실패와 제거」](project-entry.md)으로 연결한다.

A의 하위 폴더에서 시작하면 A의 설치본과 WIKI-A를 사용하고, B를 명시 선택하면 B의 설치본과 WIKI-B를 사용한다. 다른 프로젝트를 대신 실행하거나 설치하지 않은 C를 자동 초기화하지 않는다. 사용자 지정 위치의 새 clone은 [첫 기기 준비 — 「처음 준비와 위치 변경」](project-entry.md)를 하며 공유 하네스/문서 분석을 반복하지 않는다. 실제 Windows 실행과 버전 조합의 호환은 아직 미검증이다.

#### 등록과 제거에서 보존할 것

- 최초 등록 계획에 만들 파일, 사용자 PATH에 추가할 정확한 항목, 재사용/제거 조건을 보여준다. 같은 등록이 유효하면 프로젝트마다 추가 등록하거나 확인을 반복하지 않는다. 시스템 PATH, PowerShell 실행 정책/프로필, Codex 전역 설정/모델/인증은 이 후보의 변경 대상이 아니다.
- 기존 `oneploom` alias/function/실행 파일과 동명 폴더의 소유를 확인한다. 충돌을 해결하려고 기존 명령을 삭제하거나 PATH 앞에 끼워 가리지 않는다. 충돌 또는 기기 등록 거절 시 명시 경로 실행을 안내한다. 등록을 확인하려고 출처 불명 실행 파일을 호출하지 않는다.
- 기존 PATH 값, 순서와 다른 도구 항목을 보존하고 이 제품의 항목만 중복 없이 추가한다. [Windows 환경변수의 범위와 상속](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables)을 고려해 이미 열린 터미널에는 새 등록이 반영되지 않을 수 있음을 안내한다. 새 터미널 또는 명시 경로로 첫 사용을 확인하며 전체 PATH를 덮지 않는다.
- 설치용 다운로드와 작은 시작 파일의 수명을 구분한다. 다운로드를 정리해도 짧은 명령은 유지돼야 한다. 프로젝트 하나를 제거한다고 다른 프로젝트가 쓰는 기기 등록까지 없애지 않는다. 기기 등록의 명시적 제거는 소유가 확인된 파일과 자신이 추가한 PATH 항목만 대상으로 하며, 사용자 수정이나 기존 항목이면 보존한다. 제거 후에도 프로젝트 파일과 WIKI는 유지한다.
- 서로 다른 공식 버전을 적용한 A/B가 같은 시작 파일을 쓰는 경우 실행 인계 형식의 호환성을 확인한다. 기기 시작 파일의 갱신은 프로젝트 하네스의 자동 업데이트가 아니다. 호환되지 않으면 조용히 실행하거나 전체 프로젝트를 갱신하지 않고 해당 프로젝트의 명시 경로를 안내한다.

Windows 인자 전달은 [등록 파일 형식 비교 — 「등록 파일 형식의 비교」](entry.md#%EB%93%B1%EB%A1%9D%20%ED%8C%8C%EC%9D%BC%20%ED%98%95%EC%8B%9D%EC%9D%98%20%EB%B9%84%EA%B5%90)의 핵심 검증 조건이다. 명시 경로와 짧은 명령에 같은 입력을 주어 Codex까지의 인자, 실제 TUI, 종료/취소를 확인해야 한다. 채택한 표준 등록의 추가 준비, 복구와 라이선스 조건도 위 흐름과 함께 검증한다. 11/23 설계 채택과 실제 실행 파일 생성/등록, 제품 검증 완료를 구분한다.

### 시작과 재개의 명령 흐름

평소 기본 진입은 ADR 0022의 제품 시작 명령이며 저장 경로를 현재 Codex에 전달한다. **새 작업은 새 세션으로 시작할 수 있고, `resume`은 사용자가 기존 대화를 이어가려 할 때 선택한다.** 같은 프로젝트의 모든 작업을 한 세션에 묶거나 특정 세션 ID에 연결을 고정하지 않는다. 일반 `codex`와 기존 충분한 권한은 계속 사용할 수 있다. 프로젝트 진입 파일의 후보는 [기본 배치 — 「프로젝트 설치 위치 후보」](install.md)의 `oneploom/cli.py`다. 아래 명령 이름은 명세 초안이며 지금 실행할 제품은 없다. 설치/갱신 관리 도구와 상세 WIKI 복원 트리거를 세션 시작으로 대신하지 않는다. 한 파일로 전 기능을 계속 늘리겠다는 구현 구조 확정도 아니다.

11/22 사용자는 **인자가 없는 `oneploom`을 `oneploom start`와 같은 시작 처리에 연결**하는 방향을 채택했다. 두 형태는 같은 프로젝트 선택, WIKI 연결, 권한 확인과 인계 코드를 사용한다. 최초 설치나 자동 세션 재개를 뜻하지 않는다. 도움/버전 조회를 제외하고 실행 옵션이나 Codex 인자를 전달할 때는 `oneploom start ...`처럼 하위 명령을 명시한다. `oneploom strt` 같은 미지원 명령, 빈 문자열 인자와 잘못된 옵션은 무인자 실행으로 취급하지 않는다. 준비되지 않은 프로젝트에서는 필요한 준비를 안내하며 다른 프로젝트나 마지막 WIKI로 연결하지 않는다.

| 동작 후보 | 입력과 처리 | 결과와 멈출 조건 |
| --- | --- | --- |
| `connect` | 대상 프로젝트와 WIKI 경로. 외부 콘솔의 질문 또는 Codex 안 트리거가 모은 명시적 입력을 같은 처리에 전달 | 새 경로/기준을 확인한 뒤 로컬 설정 저장. 제외 규칙 미준비, 다른 대상, 충돌이면 기존 연결을 보존하고 확인 |
| `check` | 등록된 설정, 경로, 설치 도구와 연결 조건을 읽기 확인 | 준비 상태와 미확인을 구분해 보고. 파일 읽기만으로 Codex의 실제 쓰기 권한까지 성공 처리하지 않음 |
| `start`, 또는 인자 없는 `oneploom` | 같은 시작 처리로 등록된 프로젝트/WIKI를 확인하고 현재 설치된 Codex에 대상과 필요한 경로를 전달 | 빈 입력 상태의 새 CLI 세션. 프롬프트를 자동 전송하거나 역공학/모델 작업을 시작하지 않음 |
| `resume [세션]` | 같은 경로 해결을 사용하고 명시한 세션 또는 사용자의 세션 선택으로 연결 | 선택한 기존 세션 재개. ID를 고정하거나 임의의 최근 세션/새 세션으로 대체하지 않음 |

재사용하는 WIKI 연결과 설치된 조건부 규칙은 프로젝트/작업 사본에 속하고, 대화의 컨텍스트는 세션에 속한다. 예를 들어 같은 프로젝트에서 오늘은 로그인 기능을 새 대화로, 다음에는 검색 기능을 또 다른 새 대화로 작업해도 같은 등록 WIKI를 사용할 수 있어야 한다. 새 시작은 과거 대화 목록/본문 조회나 세션 선택을 선행 조건으로 요구하지 않는다. 필요한 문서 읽기는 각 요청의 조건부 라우팅을 따른다.

기존 작업을 새 세션으로 이어가겠다는 요청에는 [문맥 복구 — 「복구의 대상과 경계」](../workflow/recovery.md)를 적용할 수 있다. 이것도 기존 대화의 `resume`과는 별개다. 새 세션을 열었다는 이유만으로 이전 active/DB의 작업을 자동 실행하거나 지우지 않으며, 작업 전환과 기존 상태 보존은 복구 계약을 따른다.

프로젝트 루트에서의 예시 호출은 `py -3 .\oneploom\cli.py start`다. 실제 제품 구현과 Windows 검증 뒤 README에 복사해서 실행할 명령을 제공한다. 짧은 명령은 [명령 이름과 충돌 방지](../module.md)의 기준으로 별도 등록하며 `start` 같은 일반 단어를 전역 별칭으로 만들지 않는다. Codex 경로와 버전을 개발자의 값으로 고정하지 않고 사용자 환경에서 찾되 지원 여부를 확인한다. PowerShell의 실행 정책과 `codex.cmd` 같은 진입 차이는 대상 환경에서 처리하며 전역 실행 정책을 자동 변경하지 않는다.

`.cmd`는 Codex나 MCP의 필수 확장자가 아니다. 이번 npm 설치에는 `codex.ps1`과 `codex.cmd`가 있고 두 파일 모두 같은 패키지의 `bin/codex.js`를 호출한다. 앞선 Windows 관측에서는 PowerShell의 `codex`가 ps1을 선택해 Restricted 정책에서 차단됐으므로 시험 명령에 cmd를 명시했다. [실행 정책](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)과 [확장자를 통한 명령 구분](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence?view=powershell-5.1)을 따르며 모든 사용자의 실행 정책이 같다고 가정하지 않는다. 일반 codex가 이미 동작하는 환경은 유지한다. 같은 환경의 npm 갱신 안내도 ps1이 차단되면 `npm.cmd`를 명시해야 한다. 사용자에게 짧은 명령을 안내하는 문제와 프로그램이 임의 인자를 안전하게 전달하는 문제는 구별하며, 앞서 관측한 cmd의 변수 확장 문제까지 해결됐다는 뜻은 아니다.

경로 선택과 준비 확인은 일반 코드의 일이며 AI에게 목록이나 경로 변환을 질문하는 요청을 만들지 않는다. 시작/재개에서 설정을 확인하는 것과 매 사용자 요청마다 WIKI/DB를 읽는 것은 다르다. 세션 진입 후에는 채택한 Direct/조건부 읽기를 따른다. 등록 위치를 바꿨거나 다른 작업 경로의 세션을 재개하면 대상과 권한을 다시 대조하며, 재개한 대화 기록만으로 현재 파일 상태를 확정하지 않는다.

### Codex 설치 형태와 실행 파일 선택

11/22 사용자가 **npm 설치와 공식 Windows 독립 설치를 첫 지원 범위로 채택**했다([ADR 0022 — 「Codex 설치 지원 범위」](../../decisions/runtime/0022-wiki-entry.md)). [공식 설치 안내](https://learn.chatgpt.com/docs/codex/cli.md)의 두 방식 중 사용자가 이미 설치한 Codex를 이용한다. 우리 모듈의 Git 릴리스 + Python 배포는 유지하며, 두 종류의 Codex를 모두 설치하도록 요구하지 않는다. 지원 범위의 채택과 제품 구현, 실제 Windows 검증은 구별한다.

| 지원안 | 동작과 이점 | 비용과 한계 |
| --- | --- | --- |
| 두 공식 설치 형태 지원, 채택 | npm 설치 또는 공식 Windows 설치본 중 사용자가 선택한 것을 찾아 실행. 정상 설치를 바꾸라는 요구를 줄임 | 두 경로의 발견/갱신/종료를 검증해야 함. 독립 설치본의 실제 관측은 아직 없음 |
| npm 설치부터 지원 | 현재 부분 실증이 있는 경로를 먼저 제품화 | 구현/시험 범위가 작지만 독립 설치 사용자는 설치 방식을 맞추거나 지원을 기다려야 함 |
| 발견한 명령을 형식 구별 없이 실행 | 별칭이나 다양한 설치를 그대로 호출할 가능성 | 현재 셸과 하위 프로세스의 탐색 차이, batch 인자 변형과 임의 wrapper의 의미를 보장하기 어려워 첫 기본안으로 추천하지 않음 |

선택할 실행 경로는 다음 두 형태로 구별한다. 설치 형태에 따라 달라지는 부분은 프로그램의 위치와 진입점을 확인하고 실행하는 처리다. 프로젝트/WIKI 설정, 권한 선택, 시작/재개 인자 검증과 결과 안내는 같은 흐름을 사용한다. 설치별로 전체 실행기를 따로 만들거나 여러 패키지 관리자를 자동 지원한다고 확대하지 않는다.

- **npm:** 선택한 설치의 `package.json`에 등록된 `bin.codex`를 확인하고 해당 Node로 인자를 배열로 전달하는 후보다. 현재 디스크의 0.171.0 패키지에서도 공식 JS 진입점이 플랫폼 바이너리, 관리 환경과 입출력/종료 전달을 처리한다. 그 내부 바이너리만 찾아 직접 호출하지 않는다. Windows npm의 prefix와 `bin`은 [npm 폴더 규칙](https://docs.npmjs.com/cli/v11/configuring-npm/folders/)과 [실행 진입점 규칙](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#bin)을 따른다. 개발자 기기의 경로/버전은 고정값이 아니다.
- **공식 Windows 설치본:** 설치된 공개 진입 `codex.exe`를 배열 인자로 실행하는 후보다. [공식 설치기 원문](https://releases.openai.com/codex/install.ps1)은 실행 파일과 함께 자원을 배치하고 버전별 위치와 공개 진입을 연결한다. 실행 파일 한 개를 우리 프로젝트로 복사하거나 내부 release 폴더를 영구 고정하지 않는다. 설치기 실행, 다운로드나 사용자 설치 변경은 이번 조사에 포함하지 않았다.

이번 호출의 명시적 경로, 유효한 로컬 `codex_path`, 현재 PATH의 명확한 선택 순서로 대상을 정한다. PATH 후보가 여럿 있다는 이유만으로 매번 묻지는 않지만, 서로 다른 선택이 충돌하거나 형식을 확인할 수 없으면 다른 설치로 조용히 대체하지 않는다. 별칭/함수는 Python 프로세스의 PATH와 같지 않으므로 해석할 수 없는 셸 사용자 정의는 실행 경로 지정으로 구분한다. `.cmd`/`.ps1`이 같은 npm 설치를 가리키는 경우는 서로 다른 Codex 두 개로 세지 않는다. 현재 폴더의 임의 실행 파일을 우선하도록 검색 경로를 늘리지 않는다.

자동 발견의 결과는 이번 실행에서만 사용한다. `codex_path`를 저장하는 경우도 사용자가 선택한 안정적인 진입 경로이며, 다음 시작 때 다시 실제 대상/지원 기능을 확인한다. npm 갱신이나 독립 설치의 current 전환 뒤 예전 내부 경로를 계속 사용하지 않는다. 명시한 경로가 없어졌거나 미지원이면 이유와 준비 방법을 알리고 다른 설치로 바꾸려는 선택을 확인한다. 자동 설치/업데이트, 전역 PATH/PowerShell 정책 변경으로 해결하지 않는다. 관련 권한 조건의 유효성은 [직접 접근의 저장 항목과 실행 판단](entry.md#%EC%A7%81%EC%A0%91%20%EC%A0%91%EA%B7%BC%EC%9D%98%20%EC%A0%80%EC%9E%A5%20%ED%95%AD%EB%AA%A9%EA%B3%BC%20%EC%8B%A4%ED%96%89%20%ED%8C%90%EB%8B%A8)에 따라 별도로 확인하며 설치 형태의 지원만으로 권한까지 보장하지 않는다.

예를 들어 npm 설치만 사용 중인 사람은 Windows 독립 설치를 추가하지 않고 평소 프로젝트 시작 명령을 사용한다. 두 설치가 함께 있어도 유효한 저장 선택이 있으면 매번 다시 고르지 않는다. 공식 Windows 독립 설치만 사용하는 사람에게 npm 경로에 필요한 Node/npm을 요구하지 않는다.

인자는 [Python subprocess의 Windows batch 주의사항](https://docs.python.org/3/library/subprocess.html#security-considerations)과 기존 인자 비교 근거에 따라 셸 문자열로 합치지 않는다. 두 후보 모두 실제 TUI 입력, 특수문자, Node를 거치는 경우의 자식 종료, Ctrl+C와 현재 설치 갱신 후 동작을 Windows에서 검증해야 한다. `.exe` 또는 배열 사용 자체가 검증 완료를 의미하지 않는다.

근거의 날짜/해시와 한계는 [이번 조사 기록](../../evidence/experiments/runtime/2026-11-22_22-58-36-entry-contract.md)에 보존한다. 공식 문서와 설치기를 참고하고 기존 사용자 프로그램을 호출하는 설계이며 외부 소스/실행 파일을 배포물에 복제한 것은 아니다. 현재 Codex 패키지의 Apache-2.0 표기와 [상위 LICENSE](https://raw.githubusercontent.com/openai/codex/main/LICENSE)를 확인했으며, 향후 실제 편입 자산의 라이선스 검토를 대신하지 않는다.

### 재개 대상과 인자 확인

사용자가 `resume`으로 기존 대화를 선택했을 때 적용하는 조건이다. 같은 대화를 편하게 이어가는 사용성을 유지하면서 다른 프로젝트의 연결이 섞이지 않게 한다. 재개 시 프로젝트를 결정하고 관련 설정을 해결한 뒤 Codex에 인계한다. 준비된 인자에 현재 작업 폴더를 무조건 덧붙이는 것으로 대상 일치를 대신하지 않는다. 세션 위치 조회/선택은 새 세션 시작의 필수 단계가 아니며 아래 인자 전달과 종료 처리는 해당 시작 경로에도 적용한다.

| 입력 또는 상황 | 처리 기준 |
| --- | --- |
| 세션을 지정하지 않은 재개 | 해당 프로젝트 기준의 Codex 선택 화면을 기본으로 사용. 임의 `--last`/`--all`이나 새 대화로 대체하지 않음 |
| 명시한 ID/이름의 재개 | 선택한 대화의 작업 위치와 현재 프로젝트/작업 사본을 대조. 이름이 모호하거나 위치가 다르면 시작 전에 확인하며 WIKI와 경로를 조용히 바꾸지 않음 |
| 프로젝트 이동 또는 다른 작업 사본으로 이어가기 | 기존 승인 범위와 다른 변경으로 구분. 사용자 의도와 새 로컬 연결을 확인하고 과거 active/DB를 현재 상태로 간주하지 않음 |
| Codex의 모델/추론/화면 옵션 | 사용자가 준 값을 인자 배열 그대로 전달하고 평소 기본값은 상속. 시작기가 임의 모델/프롬프트를 추가하지 않음 |
| 코드 경로, 추가 WIKI 경로, 권한/profile/config 옵션 | 저장된 연결과 겹치는 값을 먼저 대조. 같은 값은 중복 전달하지 않으며 상충 값을 인자 순서로 조용히 덮지 않음. 이번 실행의 명시적 변경과 영구 저장은 구별 |
| 조회 불가, 미지원 옵션/설치 형식, CLI 오류 | 해당 원인과 가능한 다음 행동 반환. 모르는 설정을 임의 해석하거나 다른 실행 파일/새 세션으로 재시도하지 않음 |

공식 [resume 안내](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-resume)는 현재 폴더에 따른 선택 범위와 `--cd`의 우선 적용을 설명한다. `--cd`가 프로젝트 일치 검사를 해 주는 것은 아니다. 기존 시험 시작 파일은 합성 프로젝트와 시험 UUID를 외부에서 확인한 조건의 코드이며, 임의 세션을 검증하는 제품 구현으로 그대로 가져오지 않는다.

세션 위치는 지원되는 호스트 메타데이터 조회로 확인하는 것을 우선한다. 대화 본문 전체를 읽거나 별도 AI에게 프로젝트를 추측시키지 않는다. 조회 API/버전과 네이티브 선택 화면에서 확인할 수 있는 범위, 정확한 옵션의 충돌 처리는 첫 실행기 구현의 검증 대상이다. 확인할 수 없는 명시적 세션에 경로를 강제로 적용한 뒤 사용자에게 알아서 점검하라고 넘기는 안은 완료 기준이 아니다.

자식 Codex가 입력을 받는 동안 시작기는 고정 시간 제한으로 정상 작업을 종료하지 않는다. 취소/정상 종료/비정상 종료를 구별하고 중복 자식 실행이나 세션 잠금을 해결하려고 사용자의 전체 Codex 서버를 종료하지 않는다. 창이 열렸다는 사실을 문맥 복구나 WIKI 작업 성공으로 기록하지 않는다. 이 부분의 실제 Windows Ctrl+C, 오류/종료 코드와 잔류 프로세스 검사는 구현 후 수행한다.

### 설치부터 관리까지의 호출 순서

11/23 [설치와 명령 관리](management.md)에 최초 실행, 명령 복구/제거와 미리보기 반환을 분리 명세했다. [사용자 조작 최소화 — 「사용자 조작을 줄이는 실행 원칙」](../architecture.md)를 적용하되 설치기와 평소 시작의 목적은 유지한다. 이 표는 단계 연결이고 구체 관리 입력/처리는 연결 문서가 소유한다.

11/18에는 기존 설치, 연결과 복구 결정을 사용자 행동에 대응했다. 아래는 **명령 책임의 명세이며 최종 명령 이름이나 구현 완료를 뜻하지 않는다.** 외부 관리 도구와 프로젝트 실행 파일은 같은 제품의 서로 다른 수명에 맞춘 진입점이다. 설치된 기능이 다운로드 폴더의 코드를 계속 참조하는 구조로 바꾸지 않는다.

| 사용자 행동 | 실행할 진입과 필요한 입력 | 결과와 다시 실행할 때의 기준 |
| --- | --- | --- |
| 최초 도입 | 고정 배포본의 `oneploom.py install`. 코드 루트, 내부/외부 WIKI, 선택 기능과 변경 허용 범위 | 변경 계획을 확인한 뒤 설치/인계/연결 검사. 중단하면 같은 배포본과 작업을 확인해 유효한 완료 이후부터 진행. 단순 재실행을 새 설치로 처리하지 않음 |
| 설치된 프로젝트를 받은 팀원의 첫 사용 | 프로젝트 연결 실행. 공유 결과와 자기 기기의 도구/계정, 필요한 WIKI 로컬 경로 | 로컬 연결과 필요한 신뢰 확인. 공유 skill이나 WIKI를 재생성하지 않고 담당자의 DB를 복사하지 않음 |
| 평소 새 세션 시작 또는 선택적 기존 세션 재개 | `oneploom` 또는 `oneploom start`로 새 대화를 열거나, 이어갈 때만 `resume`으로 기존 세션 선택. 일반 `codex`의 충분한 권한도 재사용 | 어느 쪽도 저장된 프로젝트/WIKI 연결 사용. 새 시작에 세션 선택을 강제하지 않음. 필요한 조건부 절차로 연결하며 세션 열기를 설치/업데이트 미완료의 자동 재실행으로 사용하지 않음 |
| WIKI 위치 변경 | 프로젝트의 `connect` 후보 또는 열린 Codex의 연결 트리거. 같은 원본인지 확인할 새 경로 | 유효하면 연결 변경, 실패하면 기존 연결 보존. 파일 이동, Git 동기화와 호스트 권한 변경은 별도 책임 |
| 상세 WIKI 복원/보충 | 설치된 분석 기능의 명시적 진입. 코드/WIKI, 선택 범위, 플랫폼/모델과 실행 계획 | 분할 분석과 후보/검토/반영. 중단 뒤 해당 분석 작업을 식별해 재개하며 세션 열기만으로 분석을 시작하지 않음. [분석 실행](../../discussions/knowledge/reconstruction.md) 기준 적용 |
| 기능 추가 또는 공식 업데이트 | 외부 관리 도구. 이전 설치 기준, 현재 편집과 선택한 공식 배포본 | 차이와 필요한 검사를 제시한 뒤 적용. 실패 시 [재시도 또는 이전 구성 사용 — 「업데이트 실패 후 선택」](update.md)으로 연결. 다른 팀원은 검토된 공유 결과를 받음 |
| 시작 명령만 최초 준비 | 외부 관리 도구의 `command install`. 현재 Windows 사용자 계정의 등록 | 최초 프로젝트 담당자는 install 안에서 같은 처리를 사용. 새 팀원은 명령 한 번 준비 후 프로젝트 connect |
| 시작 명령 복구 또는 제거 | 외부 관리 도구의 `command repair` 또는 `command remove`. 현재 Windows 사용자 계정의 등록 | [관리 명세](management.md)의 소유/보존/재개 적용. 프로젝트 하네스/WIKI/목록 제거와 구별하고 정상 프로젝트의 재설치를 요구하지 않음 |
| 보관 자료 조회와 명시적 정리 | 설치 후에는 프로젝트 실행에서 해당 상태의 자료를 조회/정리할 진입을 제공하는 후보. 설치 종료에서는 관리 도구가 같은 정리 계약 사용 | 현재 의존과 확인한 삭제 범위를 대조. 미완료/미확인 자료 보호, 이력 보존. 설치물이 없어도 나중 정리할 수 있어야 하며 정확한 하위 명령/코드 배치는 구현 명세에서 결정 |

예를 들어 설치 중 필요한 도구가 없어 멈췄다면 도구 준비 뒤 **설치 작업을 다시 실행**한다. 반면 개발 대화를 계속하려면 **선택한 Codex 세션을 재개**한다. 같은 ‘이어가기’라도 전자는 파일 반영의 진행을, 후자는 대화 연결을 다룬다. 전자의 재개는 초기 기록 또는 프로젝트로 인계된 현재 기록을 찾아 사용하며, 사용자가 DB 경로를 외우게 만들지 않는다. 중단 안내에는 재개할 작업과 실제 명령을 남기고, 후보가 여러 개거나 다른 clone이면 선택 없이 이어가지 않는다.

임시 관리 도구를 지웠거나 프로젝트 실행 파일이 갱신 중 사용 불가한 경우에는 **해당 기록/기준을 읽을 수 있는 공식 고정 배포본을 다시 준비**하도록 안내한다. 무조건 최신 도구로 바꾸거나 새 빈 DB를 만들지 않는다. 정상 사용은 원래 설치물 없이 가능해야 하고, 관리 도구 재확보의 필요 여부와 지원 형식은 [갱신 도구 — 「버전 확인과 실행 도구」](update.md)가 소유한다.

### 명령과 설정의 표준 적용

11/22 [작성 기준](../../development/standards.md)을 현재 진입 설계에 적용한 것이다. **공식 규격, 널리 쓰이는 관례와 OnepLoom의 선택을 구분한다.** 모든 CLI가 같은 기본 동작이나 설정 형식을 사용하는 것은 아니므로, 무인자 시작은 이 제품의 사용성 선택으로 기록한다. 아래는 설계 기준이며 제품 구현이나 Windows 검증 완료를 뜻하지 않는다.

| 대상 | 근거와 적용 |
| --- | --- |
| 명령 사용법 | [GNU 명령 인터페이스](https://www.gnu.org/prep/standards/standards.html#Command_002dLine-Interfaces)의 `--help`, `--version`과 옵션 구분 관례를 참고한다. `oneploom --help`, `oneploom start --help`에서 해당 범위의 사용법/옵션/짧은 예시를 안내하고, `oneploom --version`은 어느 OnepLoom 실행본의 버전인지 표시한다. 이 조회는 Codex나 모델을 실행하지 않는다. GNU 전체 규칙을 Windows 제품의 의무 규격으로 선언하지 않음 |
| 인자 해석 | [Python argparse](https://docs.python.org/3/library/argparse.html#subcommands)처럼 도움 생성과 하위 명령을 지원하는 기존 파서를 우선 검토한다. 명령/옵션을 임의 문자열 분할로 직접 해석하지 않고, 뜻밖의 실행을 막기 위해 오타를 자동 실행으로 보정하지 않는다. argparse 채택 시 긴 옵션 자동 축약도 끄는 방향. `--` 뒤 Codex 인자는 기존 전달 계약을 따름 |
| Python 실행 진입점 | [Python 공식 실행 방식](https://docs.python.org/3/library/__main__.html)은 스크립트 실행과 `python -m`에서의 패키지 `__main__.py`를 구별한다. 현재 `oneploom/cli.py`는 Git Release + Python 배포의 후보 이름이며 Python이 강제하는 표준 파일명이 아니다. 최종 배치에 맞는 진입 방식 하나를 정하고 시작 처리를 공유한다. 패키지 탐색 위치 확인 없이 `-m`만으로 임의 하위 폴더 실행까지 해결됐다고 보지 않음 |
| 패키지의 명령 등록 | [PyPA의 entry point](https://packaging.python.org/en/latest/specifications/entry-points/)와 [pyproject.toml의 scripts](https://packaging.python.org/en/latest/specifications/pyproject-toml/#entry-points)는 패키지 설치 도구가 명령을 연결하는 규격이다. 11/23 기기의 작은 연결 프로그램에 적용하기로 채택. Git Release의 로컬 wheel과 전용 환경의 pip를 사용하며 PyPI 공개, uv/npm 배포나 전역 패키지 설치를 추가하지 않음. 명령 생성과 사용자 PATH 등록은 별도 처리 |
| 설정 파일의 역할 | 다른 도구가 읽는 파일은 그 도구의 이름/위치/문법을 따른다. 자체 설정은 사람이 편집하는지, 코드가 생성/갱신하는지에 따라 형식을 정한다. `config/`는 디렉토리 이름이고 `.conf`만으로 문법이 정해지지 않으므로 소비하는 파서와 규칙을 함께 명시한다. 같은 값을 TOML/JSON/CONF에 중복 저장하지 않음 |

[TOML](https://toml.io/en/v1.0.0)은 사람이 읽는 설정의 후보지만 현재 연결 JSON을 그대로 대체하지 않는다. 현재 계약은 `null`, 누락, `false`를 구분하며 TOML의 값 형식에는 `null`이 없다. 변환하려면 외부 WIKI 선택을 표현하는 방식과 모든 소비자의 판단을 함께 설계해야 한다. [Python tomllib](https://docs.python.org/3/library/tomllib.html)은 읽기용이며 쓰기를 제공하지 않으므로, 자동 갱신이 필요하면 주석/사용자 편집 보존, 쓰기 도구의 의존성과 지원 Python의 TOML 문법 범위도 검토한다.

따라서 현재 `project.json`, `.harness/local.json`과 JSON 위치표의 역할/값 계약은 유지하고, 형식 변경은 실제 이점과 전환 검증을 확인한 뒤 별도 결정한다. `pyproject.toml`의 빌드/패키지 메타데이터, 도구별 설정 영역과 적용 프로젝트의 연결 설정을 같은 역할로 취급하지 않는다. 준비물이나 공개 계약을 바꾸는 선택은 기존 합의 순서로 다룬다. 규약 확인을 위해 외부 코드나 문서 템플릿을 복사한 것은 아니며, 실제 재사용 시 [라이선스 기준 — 「라이선스와 저작권」](../module.md)을 적용한다.

11/23 사용자의 간결한 명령 기준을 적용한다. 하나의 명령 정의에서 긴 옵션과 필요한 짧은 별칭을 같은 값으로 해석하며, 도움말과 예시는 그 정의를 따른다. 기존 `-h`/`--help`를 유지하고 다른 짧은 별칭은 반복 사용의 편의와 같은 범위의 충돌을 확인한 경우만 추가한다. 문서에서 명시하지 않은 접두어를 임의 축약 옵션으로 실행하지 않는다.

OnepLoom 자체 옵션과 `--` 뒤 Codex 인자는 다른 범위다. 예를 들어 프로젝트 선택은 `oneploom start --project "C:\work\app"`처럼 표현하고, 사용자가 뒤에 전달한 Codex 옵션은 기존 계약대로 보존한다. 짧은 옵션을 추가하면서 전달받은 Codex의 의미를 바꾸거나 오타를 추정 실행하지 않는다. 파서의 기본 동작을 그대로 안전성 근거로 삼지 않고 [명령 검증 — 「사용 단계별 명령 검증」](../../verification/acceptance.md)에서 확인한다.

사용 안내 README와 `--help`는 같은 명령 정의와 검증된 예시를 기준으로 맞춘다. 빠른 시작에는 필요한 준비, 실제 실행 명령과 다음 행동을 두고 내부 설계는 별도 문서로 연결한다. 구현 때 [사용 단계별 검증 — 「사용 단계별 명령 검증」](../../verification/acceptance.md)에서 기본 시작, 도움, 오류와 형식 보존을 확인한다.

### 명령 입력과 결과 안내

외부 PowerShell에서는 필요한 값을 순서대로 질문할 수 있다. Codex 안의 트리거는 사용자 대화에서 받은 값을 같은 처리 코드에 명시적으로 전달한다. AI 도구 안에 또 다른 대화형 입력 대기를 만들지 않는다. 경로 등록, 준비 확인, 버전 메타데이터 조회는 일반 코드가 수행하고 분석 모델 호출은 해당 기능의 범위/모델 선택 후에만 진행한다.

| 구분 | 공통 처리 기준 |
| --- | --- |
| 프로젝트 선택 | 명시한 코드 루트를 우선 대조. 생략 시 현재 작업 위치에서 확인한 프로젝트를 제시하고, 복수/불명확한 대상은 선택 요청. 도구의 압축 해제 폴더를 코드 루트로 간주하지 않음 |
| 경로와 범위 | 경로를 개별 인자로 받아 한글/공백과 특수문자를 보존. WIKI 연결의 Enter는 기존 유효값의 재사용과 최초 입력 누락을 구분. 분석 범위의 기본값과 확인은 분석 계약을 따름 |
| 도움과 입력 오류 | `-h`/`--help`, 하위 명령의 `--help`와 `--version` 조회에는 WIKI 연결, DB 생성/변환이나 모델 인증을 선행하지 않음. 잘못된 인자는 변경 전에 거부하고 관련 사용법만 안내. 무인자 시작과 구분 |
| 확인이 필요한 입력 | 원래 허용한 같은 범위는 재사용. 입력 채널이 없거나 EOF이면 새 확인을 추정하지 않고 필요한 입력과 현재 상태 반환. 정리의 Enter 의미는 [해당 확인 화면 — 「설치 완료 뒤 정리」](install.md)을 따름 |
| 결과와 다음 행동 | 수행한 동작, 확인한 대상, 완료/미완료/미확인, 보존한 변경과 다음 명령을 짧게 안내. 준비 확인, 세션 인계와 실제 작업 완료를 한 PASS로 합치지 않음 |
| 종료와 자동 처리 | 호출자가 성공, 사용자 취소, 준비/입력 필요와 실패를 구분할 수 있어야 함. 정확한 종료 코드/반환 형식은 구현 명세로 고정하고 본문/로그에서 추측하지 않음. 자식 프로세스 미종료를 성공 코드로 바꾸지 않음 |

사람용 안내와 AI/자동화용 결과는 같은 판단에서 만든다. 정상 출력은 짧게 유지하고 긴 원문은 관련 기록으로 연결하되, 실패 이유와 다음 행동을 로그 링크에만 숨기지 않는다. 조회/연결을 실행할 때마다 active를 다시 쓰거나 전체 DB를 모델에 전달하는 절차를 추가하지 않는다. 일반 코드 실행도 AI가 명령과 출력을 읽는 비용은 남으므로 토큰 효과는 별도로 측정한다.

구현 참고로 [Python argparse](https://docs.python.org/3/library/argparse.html#subcommands)는 하위 명령, 인자 선택과 도움 생성을 제공한다. [GitHub CLI의 종료 코드](https://cli.github.com/manual/gh_help_exit-codes)는 성공, 취소와 인증 필요를 구별하는 공개 사례다. 두 자료는 입력/결과를 분명하게 나누는 근거이며 해당 코드 번호, Python 최신 버전 또는 특정 라이브러리 구성을 그대로 채택하는 뜻은 아니다. Windows 실행 준비와 실제 지원 판단은 [지원 조건의 확인 순서](install.md), 미실행 시험은 [사용 단계별 명령 검증](../../verification/acceptance.md)에 연결한다.

### 연결 준비의 입력과 확인 전달

팀원의 첫 준비와 WIKI 위치 변경도 [같은 계획의 준비/적용 — 「CLI와 AI에서 같은 계획 확인하기」](management.md)을 사용한다. 현재 연결을 확인만 하거나 유효한 연결/기기 등록을 그대로 재사용하는 경우에는 새 계획/DB/확인을 만들지 않는다. 실제 설정 저장이나 기기 등록 효과가 필요할 때만 해당 변경 범위를 보존한다.

```text
cli.py connect [--project PATH] [--input FILE|-] [--preview|--prepare] [--json]
cli.py connect --apply --input FILE|- [--project PATH] [--json]
```

위는 구현 명세다. 최초 등록 전에는 팀 README의 실제 cli.py 경로로 실행하고, 등록 뒤에는 `oneploom connect`가 같은 처리로 인계한다. JSON 초기 입력은 관리 명세 중 project_root, wiki_root, register_command를 사용한다. features는 설치 기능 선택이므로 connect가 받지 않는다. module_path는 실행 중인 설치본과 대상에서 계산하고 사용자가 내부 경로를 다시 입력하게 하지 않는다.

대화형 호출은 필요한 질문과 계획 확인/적용을 한 번의 실행에서 이어간다. AI 경로는 일반 코드가 만든 plan_ref를 실제 사용자 선택과 함께 전달한다. 미리보기에는 plan_ref가 없으며, `--prepare`는 변경 대상 파일을 반영하지 않고 기존 상태 위치에 계획만 준비한다. `--apply`의 --project는 기기 시작기가 전달한 대상 또는 사용자가 확인할 대상을 기존 계획과 대조하는 용도다. 그 값으로 대상을 변경하거나 새 WIKI 경로/설정 입력을 섞지 않는다. 두 경로 모두 다른 계획으로 바뀐 범위에 예전 허용을 재사용하지 않는다.

`--json`은 사용자를 대신해 동의하거나 숨은 질문을 띄우지 않는다. 입력/확인이 필요하면 해당 조건과 필요한 항목을 반환한다. 준비/적용의 stage는 plan/apply이고, 변경 없는 연결 확인은 기존 connection을 유지한다. 같은 계획의 유효한 확인은 재사용하되 OS/호스트 권한의 허용을 뜻하지 않는다. 필요한 등록용 자료와 보관 책임은 [팀원 첫 준비의 배포 자료](install.md)가 소유한다.

### 명령 결과의 형식

11/22 결과 후보는 **등록 완료, 실행 준비와 실제 Codex 실행을 구별하는 최소 반환**이다. `connect`/`check`의 `--json`, `start`/`resume`의 `--preview --json`에서 같은 판단을 사람용 설명 또는 JSON으로 내보낸다. 옵션 이름과 아래 종료 코드는 구현 전 명세이며 현재 실행 가능한 제품 명령은 아니다. `--json`은 대화형 질문을 숨겨 띄우지 않고 필요한 입력을 결과로 반환한다.

11/23 목록 명령도 이 반환 형식을 사용한다. `projects` 명령과 선택/저장 오류의 대응은 [결과와 오류의 연결](project-selection.md)이 소유하며 별도 종료 코드 체계를 만들지 않는다.

시작기 옵션과 Codex에 전달할 옵션은 `--`로 구분한다. 예시 형식은 `start --preview --json -- <Codex 인자들>`이다. 구분자 뒤의 모델/화면 옵션 등을 시작기의 옵션으로 다시 소비하지 않는다. 경로/권한에 직접 영향을 주는 인자는 기존 충돌 검사를 거치고, 사용자 프롬프트를 시작기가 새로 만들지 않는다.

| 필드 | 형식과 의미 |
| --- | --- |
| `operation` | `connect`, `check`, `start`, `resume`, `projects.list`, `projects.add`, `projects.remove`. 외부 관리에는 `install`, `command.install`, `command.repair`, `command.remove`를 사용 |
| `stage` | `connection`, `prepare`, `catalog`. 변경이 있는 connect와 외부 관리에는 `plan`, `apply`를 사용해 계획 준비와 실제 적용 결과를 구별 |
| `status` | `ready`, `needs_input`, `unsupported`, `cancelled`, `error`. 해당 stage의 결과. `plan/ready`는 적용 허가/완료가 아니며 시작 준비의 ready도 실제 WIKI 사용 성공이 아님 |
| `reason` | `ready` 외에는 필수인 원인 코드. 예: `invalid_input`, `invalid_config`, `project_mismatch`, `permission_unknown`, `unsupported_installation`, `launch_failed` |
| `message` | 필수 한글 설명. 확인한 사실과 실패/미확인 원인을 짧게 안내 |
| `next_action` | 다음 행동이 있을 때 한글로 안내. 자동 실행할 셸 문자열이나 포괄적 재시도 지시가 아님 |
| `project_root`, `wiki_root` | 실제 해결한 대상만 포함. 알 수 없으면 누락하고 임의 기본값/빈 경로를 채우지 않음 |
| `launch` | 준비된 실행을 보여줄 때만 `program` 문자열, 개별 `args` 문자열 배열과 실제 작업 폴더 `cwd`를 포함. 비밀값/사용자 프롬프트는 가리고 원래 인자는 실행 코드의 메모리에서만 보존 |
| `projects` | 성공한 `projects.list --json`에서만 등록 루트의 문자열 배열. 각 프로젝트의 실행 가능 판정이나 WIKI 설정이 아님 |
| `plan_ref` | 실제 보존된 변경 계획을 확인/적용할 때만 포함. 구성과 재사용은 [관리 명세 — 「계획 참조와 확인의 재사용」](management.md)가 소유. 읽기 전용 미리보기와 평소 시작에는 없음 |
| `required_inputs` | needs_input에서 추가 입력/선택을 받는 경우만 항목 배열. 아래 입력 안내 형식을 사용하며 이미 해결한 값을 다시 묻지 않음 |

외부 관리의 stage별 완료, 미리보기와 JSON 범위는 [관리 반환 — 「미리보기, 반환과 안내」](management.md)이 소유한다. 별도의 출력 체계를 만들지 않으며 복구/제거 결과에 프로젝트와 WIKI를 임의로 채우지 않는다.

required_inputs의 각 항목은 `name`, 한글 `message`, 값 형식을 뜻하는 `type`을 갖는다. type은 path, boolean, choice, multi_choice, confirmation으로 제한하고 choice/multi_choice에만 실제 허용 값 value와 표시 이름 label을 가진 choices 목록을 붙인다. 예를 들어 외부 WIKI 위치가 없으면 wiki_root/path, 제시한 계획의 동의가 없으면 decision/confirmation이다. 표시한 기본값이 있을 때만 default를 포함하고, 출력했다고 선택됐다고 처리하지 않는다. 비밀번호/토큰 입력을 이 형식이나 로컬 계획에 담지 않는다. 호스트 자체의 권한 창을 이 목록으로 대신했다고 판단하지 않는다.

저장 선택의 적용이 필요한데 조건이 달라져 사용자의 선택이 필요한 경우는 `needs_input`이다. 필요한 조회 자체가 미지원이면 `unsupported`, 조회 처리 실패는 `error`로 구별한다. 저장 선택 없이 사용자 인자/설정을 상속해 인계할 준비가 끝난 경우는 `ready`일 수 있지만 실제 WIKI 접근을 확인했다는 뜻은 아니다. 어떤 경로를 준비했는지 설명하고 과거 선택을 적용하지 않은 사실을 숨기지 않는다.

예를 들어 경로는 확인했지만 자동 적용할 권한 선택을 판단할 수 없어 사용자 입력이 필요할 때는 다음처럼 반환한다. 이미 저장된 연결은 보존하고 실제 Codex를 성공적으로 열었다고 표시하지 않는다.

```json
{
  "operation": "start",
  "stage": "prepare",
  "status": "needs_input",
  "reason": "permission_unknown",
  "message": "WIKI 경로는 확인했지만 현재 실행의 접근 권한은 확인하지 못했습니다.",
  "next_action": "현재 권한과 적용할 실행 옵션을 확인해 주세요.",
  "project_root": "C:/Work/project",
  "wiki_root": "C:/Work/project-wiki"
}
```

준비 단계의 프로세스 종료 코드는 `0` 준비/등록 완료, `1` 처리 실패, `2` 잘못된 명령 입력, `3` 필요한 입력/확인 미충족, `4` 사용자 취소, `5` 미지원으로 대응한다. 이 숫자는 우리 도구의 후보 계약이며 업계 공통값이 아니다. `reason`으로 원인을 분기하고 자연어 문구를 분석해 자동 재시도하지 않는다. 도움 요청은 의존 도구/설정/DB 없이 끝나며 정상 종료만 표시한다. 해석 가능한 요청의 JSON 출력에는 로그/배너를 섞지 않고 진단은 stderr로 보낸다.

실제 `start`/`resume`은 터미널을 Codex에 넘기므로 JSON 결과 스트림을 TUI와 섞지 않는다. JSON 확인은 실행 전 `--preview`로 하고, 인계 후에는 자식 Codex의 실제 종료 코드를 보존한다. 따라서 **실행 전의 코드 3과 실행된 Codex의 코드 3을 같은 원인으로 해석하지 않는다.** 필요하면 연결 코드가 보유한 실행 단계와 종료 원인을 함께 소비한다. 준비는 성공했으나 프로세스를 만들지 못한 실패도 구별한다. 코드 0으로 끝난 대화도 WIKI 읽기/수정이나 모델 작업 완료의 증거가 아니다.

취소와 종료 전 확인은 제품 Windows 검증으로 닫는다. 준비 결과를 확인한 뒤 실제 실행까지 설정/대상이 바뀌면 다시 필요한 범위를 검사하며, 미리보기 결과를 실행 허가나 영구 캐시로 사용하지 않는다. 매 시작마다 DB/active에 이 객체를 추가하거나 전체 설정을 AI에 보내지 않는다. [GitHub CLI의 종료 코드](https://cli.github.com/manual/gh_help_exit-codes)는 완료/취소/인증을 구분하는 참고 사례이며, 우리 번호를 그 도구와 같게 맞추는 요구는 아니다.

## 연결의 입력과 실패 반환

| 단계 | 필요한 입력 | 반환할 내용과 중단 조건 |
| --- | --- | --- |
| 대상 확인 | 코드 루트, 설치 기준, 호출 위치, 사용 도구 | 확인한 프로젝트와 유효 지침. 대상이 모호하면 선택을 요청하며 가장 가까운 임의 설정을 사용하지 않음 |
| 필요한 자료 찾기 | 작업 범위, 정보 역할, WIKI 연결 | 요청 범위의 원문 위치, 미등록/접근 실패/깨진 연결의 구분. 없는 역할을 자동으로 빈 문서로 대체하지 않음 |
| 실행 연결 | 선택 절차, 프로젝트 설정, 허용된 파일/명령 | 실제 호출 대상과 실행 위치. 기존 동일 이름, 지원되지 않는 경로, 신뢰 미완료이면 해당 기능을 완료 처리하지 않음 |
| 반영/갱신 | 이전 소유/기준, 현재 파일, 새 후보, 검토한 범위 | 생성/수정/보존/충돌의 차이. 반영 직전 사용자 편집이 바뀌었으면 재대조. 무관한 사용자 자산은 자동 정리하지 않음 |

공통 검사 결과와 WIKI 조회 결과를 하나의 PASS로 합치지 않는다. 파일 접근, 도구 발견, 실제 사용, 의미 검토는 각각 필요한 근거를 확인한다. hook이 여러 출처에서 실행돼도 순차 실행을 전제하지 않으며 모듈 상태의 중복 처리는 [로컬 실행 보호 — 「소유 확인과 인계」](../workflow/recovery.md)에 연결한다.

### 결과를 받는 절차

연결 결과에는 확인한 코드 작업 트리, 사용한 설정의 출처, 요청한 역할/작업 범위와 그 범위에서 확인한 사실을 대응시킨다. 외부 WIKI는 필요한 기능에서만 해결한다. 읽기 확인, 현재 실행 환경의 권한 확인, 실제 명령의 실행 결과를 구별하고, 확인하지 않은 항목과 이유를 남긴다. 이는 반환 정보의 의미 명세이며 새 JSON 필드나 별도 승인 저장소를 확정한 것이 아니다.

`check`를 일반 터미널에서 실행한 결과는 그 실행 환경의 관측이다. Codex 안에서 같은 접근이 허용된다는 증거로 대신 쓰지 않는다. 읽기 확인을 위해 기존 문서를 수정하지 않으며 쓰기 검증은 정한 시험 범위에서 수행한다. 이전 허용 기록이 있어도 실제 작업에서 거부되면 해당 접근 실패를 처리한다.

| 결과를 만드는 곳 | 결과를 받는 곳 | 사용할 근거와 다음 행동 |
| --- | --- | --- |
| 외부 콘솔 또는 Codex 안 연결 트리거 | 같은 `connect` 처리 | 기존 연결 재사용 또는 사용자가 제공한 대상/경로와 변경 의도. 입력을 받는 방식만 구분하고 검사/저장 책임은 공유 |
| 공유 설정과 로컬 연결을 읽는 절차 | `check`, 시작/재개 진입, 필요한 기능의 실행기 | 확인한 작업 트리와 관련 설정, 해결된 위치를 사용. 대상/설정 충돌은 의존하는 실행 전에 반환. 같은 이름의 다른 clone 상태를 가져오지 않음 |
| `check` 또는 일반 Codex의 연결 확인 | 호출한 사용자/메인, 해당 기능의 준비 판단 | 준비됨, 부족한 조건, 미확인을 구별해 다음 행동 안내. 검사 PASS나 설치/작업 완료로 저장하지 않음 |
| `start` 또는 `resume`의 대상/인자 준비와 CLI 인계 | 선택한 Codex 세션 | 실제 지침과 필요한 권한을 갖춘 세션으로 연결. 런처 종료 코드나 세션 열림을 WIKI 작업, 검증, 문맥 복구 성공으로 소비하지 않음 |
| WIKI 위치표 조회 | 문서 작업 절차 또는 검증 계획을 정하는 메인 | 해당 역할의 원문 위치와 확인 범위. 원문 읽기/의미 판단은 필요한 절차가 맡으며 경로 반환만으로 정책 확인을 마쳤다고 처리하지 않음 |
| 프로젝트 명령/설정을 해결한 검증 계획 | [검증 실행과 완료 대조 — 「계획과 결과의 연결」](../workflow/verification.md) | 실제 argv, cwd, 선택 조건을 해당 계획/시도에 연결. 실행 전 준비 실패와 실행 후 FAIL, 종료 미확인을 구별하고 미완료 의무 유지 |
| 이어갈 작업을 확인한 세션 또는 중단된 기능 | [조건부 복구 — 「재개 판단 순서」](../workflow/recovery.md) | 문맥만 부족하면 해당 active와 필요한 참조, 실행 사실도 불명확하면 해당 시도와 실제 효과를 조회. CLI 진입만으로 설치/갱신을 재개하지 않음 |
| 설치/갱신의 연결 확인 | [설치 단계 — 「설치 기록과 단계 연결」](install.md)와 해당 적용 단위의 완료 판단 | 계획한 파일 반영과 연결 확인을 구별. 외부 권한 등 필요한 조건이 남으면 그 단위의 미완료를 표시하고 유효한 독립 완료는 보존 |

준비 결과를 받은 절차가 전체 상태를 다시 조사하는 구조로 만들지 않는다. 같은 호출에서 확인한 대상/설정은 다음 절차에 전달하고, 입력 변경, 권한 거부, 반영 직전 대조처럼 필요한 지점에서만 관련 사실을 다시 확인한다. 검증 결과 재사용의 범위는 [기존 계약 — 「PASS 재사용의 구체적 의미」](../workflow/verification.md)을 따르며 연결 확인을 테스트 캐시로 사용하지 않는다.

### 실패 뒤 돌아갈 위치

| 발견한 상황 | 멈추는 범위와 다음 단계 | 보존할 것 |
| --- | --- | --- |
| 설정 누락/대상 불일치, 역할 경로 오류, 필요한 도구 부재 | 그 입력에 의존하는 기능을 실행 전에 멈추고 원인과 준비 방법 안내. 보완 뒤 해당 연결부터 확인 | 이전 연결과 사용자 파일. 기존 작업의 미완료 의무를 제외나 PASS로 바꾸지 않음 |
| 경로는 맞지만 권한/신뢰가 부족 | 부족한 범위를 표시하고 위의 일반 진입 안내 또는 제품 시작/재개로 연결. 현재 세션의 실제 권한을 확인한 뒤 해당 기능 재개 | 선택한 프로젝트/작업/세션. 유효한 승인을 다시 요구하거나 전체 설정을 덮지 않음 |
| 분류/명령 선택의 의미가 불명확하거나 정책 충돌 | 메인의 범위 판단으로 돌아가 필요한 근거/사용자 선택 확인. 자동 실행이나 검사 면제로 해소하지 않음 | 원래 요구, 계획과 미확정 이유 |
| 검사 실행과 FAIL이 명확함 | [원래 실패의 수정/재검증 — 「재시도를 읽는 예시」](../workflow/verification.md)으로 연결. 같은 문맥에서 전체 복구 절차를 먼저 실행하지 않음 | 실패한 검사와 시도, 후속 수정의 관계. 영향받지 않은 유효 결과 |
| 실행/반영은 시작됐을 수 있으나 종료나 결과가 불명확함 | [재개 대조 — 「재개 판단 순서」](../workflow/recovery.md)에서 해당 프로세스/결과/실제 대상을 확인한 뒤 재시도 여부 결정 | 기존 시도와 미확인 상태. 연결 재확인 성공으로 실패/불명을 덮지 않음 |
| 설정 변경 또는 재접속 뒤 작업을 이어감 | 대상과 바뀐 입력을 대조하고 해당 근거만 재검토. 사용자 취소 뒤에는 재개 요청 없이 다시 시작하지 않음 | 관련 없는 완료 결과, 사용자 편집, 아직 남은 의무 |

예를 들어 검사에 필요한 WIKI를 읽지 못했다면, 연결을 고친 뒤 그 자료를 읽고 원래 검사를 이어간다. `check` 성공만으로 검사를 완료하지 않는다. 반대로 실제 검사가 이미 종료됐고 결과 저장만 끊겼다면, 같은 검사를 먼저 돌리지 않고 해당 결과의 대응부터 확인한다. 기존 [저장 시점](../workflow/recovery.md)에 따라 필요한 기록을 남기며 모든 연결 확인에 active/SQLite 작성을 추가하지 않는다.

## 확인할 시험과 남은 명세

이번 연결의 실제 행동 검사는 [진입과 연결의 검증 입력 — 「진입과 프로젝트 연결의 검증 입력」](../../verification/acceptance.md)이 소유한다. 새 clone, 하위 경로, 기존 지침/skill/hook, 외부 WIKI와 사용자 편집을 포함한다. 문서 검사만으로 Windows 설치나 AI의 실제 읽기를 통과 처리하지 않는다.

AGENTS 연결, 제품 시작 명령과 일반 진입의 최소 보완 범위는 합의했다. 위의 결과 소비와 실패 복귀는 기존 검증/복구 계약의 연결 명세이며 구현/시험 결과가 아니다. 검증 계획/시도/결과와 active의 필드, 파일, 저장/조회는 [기록 명세](../workflow/records.md), 설치/갱신과 기능 추가의 소비는 [설치 단계 연결 — 「설치 기록과 단계 연결」](install.md)에 뒀다. Windows 저장/실행 보호, 설정/명령의 최종 형식과 도구별 권한 전달은 남아 있다. 실제 순서는 [진행표](../../development/roadmap.md)를 따른다.

## 후속 연결 대안과 조사 이력

아래는 일반 codex 진입, 프로젝트 권한 설정과 MCP를 검토한 11/18 이후의 상세다. **현재 첫 배포는 ADR 0022의 전용 시작 명령/직접 접근 우선**이다. 아래 대안의 설정 생성/분리, Git 제외와 MCP 등록을 기본 설치의 필수 절차로 적용하지 않는다. 다른 기능에서도 필요한 소유 보호, 미확인 처리와 원문 보존은 유지하며 현재 흐름은 앞의 연결/실행 명세를 따른다.

### 지속 권한 설정의 배치

11/18 사용자 필수 조건: **배포 모듈은 Codex 전역 설정을 생성, 수정, 삭제하지 않는다.** 설치, 연결, 경로 변경, 갱신, 해제와 정상 실행에 동일하게 적용한다. 실제 `CODEX_HOME`의 사용자 config, 전역 기본값/권한 프로필, 전역 지침/hook과 셸의 공통 실행 설정을 이 모듈의 변경 대상으로 삼지 않는다. 기존 설정과 관리 정책은 호환 조건을 확인하는 입력이다. 충돌을 전역 설정 변경으로 해결하지 않는다.

프로젝트 로컬 설정에 WIKI 권한을 저장하는 연결은 부분 시험한 선택 호환 후보다. ADR 0022의 기본 진입은 전용 명령이며 아래 config 배치/전환은 기본 설치의 필수 절차가 아니다. **파일 전체 자동 제외나 공통 원본에서 전체 config를 생성하는 방식은 범용 기본안으로 추천하지 않는다.** 기존 충분한 권한과 사용자 설정 소유를 보존한다.

| 위치 | 현재 책임 |
| --- | --- |
| 프로젝트 `.codex/config.toml` | 사용자/팀 소유의 호스트 설정. 기존 권한을 먼저 재사용하고, 필요하고 합의된 모듈 연결 항목에 한해 보완 후보 검토. 파일 전체 소유/제외/생성을 전제하지 않음 |
| 프로젝트 `.harness/local.json` | WIKI 위치와 시작 시 재사용할 사용자 선택의 로컬 원본. 역할 목록이나 Codex 권한 정의를 복제하지 않으며 호스트 권한 파일을 대신하지 않음 |
| Codex 사용자/시스템 설정 | 읽어서 기존 정책과 지원 조건을 확인. 모듈이 쓰거나 전역 등록을 추가하지 않음 |

두 소비자는 같은 사용자 입력을 사용하되 책임이 다르다. 모듈은 조회 위치를 기록하고 Codex의 실제 접근 권한을 대조한다. 권한이 충분하면 호스트 설정/제외 규칙을 추가하지 않는다. 부족하면 지원되는 연결 후보의 변경 범위와 공유 영향을 먼저 확인한다. 경로를 두 번 입력시키거나 `.harness/local.json`만 저장하고 호스트 권한까지 연결됐다고 처리하지 않는다.

#### 연결 전후의 처리

1. 실제 프로젝트/작업 사본과 WIKI를 확인한다. 기존 Codex 설정의 소유, Git 추적, 실제 적용되는 권한과 관리자 제약을 먼저 읽는다. 신뢰가 필요하면 Codex의 사용자 절차를 안내하며 모듈이 전역 trust 값을 쓰지 않는다. 실제 쓰기 대상도 확인해 프로젝트 설정이 링크를 통해 전역 파일을 가리키면 수정하지 않는다.
2. 연결 전에는 존재하지 않는 권한 이름을 공유 파일에 미리 넣지 않는다. 새 팀원/기기는 일반 Codex의 기존 상태로 시작하고 필요한 연결을 준비한다. 최초 연결이 완료되기 전의 외부 WIKI 접근을 성공으로 표시하지 않는다.
3. 한 번 받은 WIKI 경로로 모듈 연결과 실제 권한을 대조한다. 필요한 경우에만 합의한 호스트 변경 후보를 준비한다. 권한 이름을 쓰는 후보는 이름/정의를 함께 완성하되 모델, 승인/네트워크 정책, 기존 허가/제한과 사용자 항목을 보존한다. 키 몇 개만 바꿨더라도 다른 동작이 달라지지 않는지 확인한다.
4. 로컬 전용 운영을 선택한 경우에만 아래 자동 제외 절차를 적용한다. 제외가 확인된 뒤 허용된 변경을 반영하고 실제 적용을 검사한다. 이미 추적 중인 config에 ignore 한 줄을 추가해 경로가 숨겨졌다고 판단하지 않는다. 파일 반영과 부분 실패는 기존 보존/복구 계약을 따른다.
5. 이후 그 프로젝트의 일반 `codex`가 저장 설정을 읽는다. 연결 변경/해제는 현재 작업 사본의 모듈 소유 항목만 대상으로 하며, 다른 프로젝트나 전역 설정을 수정하지 않는다. 현재 열린/재개한 세션의 반영은 별도로 확인한다.

예를 들어 프로젝트 A의 새 로컬 설정 후보는 아래와 같다. 기존 사용자 지정 정책이 없는 시험 입력의 예시이며 모든 사용자의 정책을 `:workspace`로 교체하는 양식이 아니다. 실제 이름은 충돌을 검사하고 프로젝트/제품 식별 규칙에 맞춰 정한다.

```toml
# 프로젝트 .codex/config.toml, 기기별 경로를 포함하므로 로컬 전용 후보
default_permissions = "example-wiki"

[permissions.example-wiki]
extends = ":workspace"

[permissions.example-wiki.workspace_roots]
"C:/Work/example-wiki" = true
```

A/B는 각자의 로컬 파일과 WIKI 경로를 사용하고, 모듈 미사용 C에는 아무 설정도 만들지 않는다. 연결 전 D에도 미정의 프로필 선택을 쓰지 않으므로 이전 후보의 시작 오류를 유발하지 않는다. 같은 프로젝트의 다른 clone/worktree도 각 로컬 연결을 사용한다. 다만 상위/하위 config의 실제 상속, 이름 충돌과 기존 사용자 권한의 누적까지 자동 해결된 것으로 보지 않는다.

#### 기존 정책과 Git 공유

| 기존 상태 | 처리 기준 |
| --- | --- |
| 별도 권한 정책 없는 신뢰된 프로젝트 | 로컬 권한 이름과 정의를 함께 준비하는 후보. 추가 허용 범위와 효과를 확인 |
| 기존 `sandbox_mode` / `sandbox_workspace_write` 사용 | 새 권한 프로필을 덧붙여 적용됐다고 가정하지 않음. 같은 체계에서 필요한 WIKI 루트 추가 후보를 만들고 기존 루트, 네트워크와 제한 보존을 검사 |
| 기존 사용자 지정 권한/관리 정책 | 현재 정책의 제한을 보존할 수 있는지 먼저 확인. 전역 프로필 변경이나 관리자 제한 우회 금지. 호환을 입증하지 못하면 적용 보류 |
| 새 config 또는 원래 로컬 전용인 config | 미추적/무시 상태만으로 모듈 소유나 비공유 의도를 확정하지 않음. 필요한 설정과 사용자가 선택한 관리 범위를 확인한 경우에만 로컬 제외 후보 적용 |
| 이미 Git으로 공유 중인 config | 자동 추적 해제, 무단 파일 이동, 기기 경로 삽입 금지. 기존 팀 설정 보존과 로컬 경로 연결을 함께 만족시키는 방식을 해당 프로젝트에서 협의 |

`.codex/` 전체를 가리지 않는다. 공유할 skill, hook, script와 로컬 파일을 구분하고, 파일이 새것이라는 이유만으로 장래 공유 정책을 정하지 않는다. 사용자는 프로젝트 로컬 방향과 자동화 검토를 수용했으나 후속 질문으로 무관한 설정의 관리와 미래 추적 전환의 영향을 지적했다. 아래 자동 제외는 **로컬 전용 운영을 명시적으로 선택한 경우의 제한된 수단**으로 보정한다. 제품 연결기는 아직 구현하지 않았다.

현재 공식 문서에서 프로젝트 `config.local.toml` 자동 덧씌우기나 임의 include를 확인하지 못했다. 별도 설정 프로필도 `--profile` 선택이 필요하고 프로젝트 `profile` 자동 선택은 지원하지 않는다. 이런 미지원 연결을 가정해 공유 config와 로컬 경로가 자동 병합된다고 설명하지 않는다. 기본 진입은 ADR 0022의 제품 시작 명령이며 일반 codex의 지속 연결은 별도 호환 경로다. 한 경로의 성공을 다른 경로의 완료로 표시하지 않는다.

#### 설정 소유와 공유 상태의 전환

11/18 검토 보정: `.codex/config.toml`은 호스트와 사용자/팀의 설정 파일이다. 모듈을 설치했다는 사실로 전체 파일의 소유권을 얻지 않는다. **관측한 Git 상태, 실제 편집 소유, 사용자가 원하는 공유 방식**을 구분한다. 미추적은 로컬 전용의 동의가 아니며, 무시 중인 파일도 나중에 공유할 수 있다. Git 추적은 공개 인터넷 게시와도 다르다. private 저장소의 추적 파일에도 기기 경로를 임의로 넣지 않는다.

| 관측한 상태 또는 전환 | 모듈의 처리 기준 |
| --- | --- |
| config 없음 | 실제 권한이 충분하면 생성/제외 불필요. 필요한 설정이 있으면 범위와 관리 방식을 제시. 빈 파일이나 장래 공유를 막는 제외를 미리 만들지 않음 |
| 사용자 config 존재, 미추적 | 사용자의 신규/준비 중 파일로 취급. 파일/주석/권한을 보존하고 자동 제외/템플릿 전환 금지 |
| 사용자 규칙으로 이미 무시 중 | 기존 규칙 재사용 가능 여부만 확인. 모듈 규칙을 중복 추가하거나 제거 때 사용자 규칙을 지우지 않음. 파일 내용 수정 권한까지 얻은 것은 아님 |
| HEAD 또는 index에 config 있음, 최초 stage 포함 | 공유 중이거나 공유 변경 중인 파일로 보존. 자동 untrack/unstage/제외 등록이나 개인 경로 삽입 금지. 기존 설정 재사용 또는 별도 연결 선택 필요 |
| 삭제를 stage했거나 merge 충돌 중 | 단순 파일 부재/미추적으로 오인하지 않음. index/HEAD와 작업 트리의 차이를 확인하고 관련 파일 반영 보류. 사용자의 삭제/충돌 해결을 되돌리지 않음 |
| 모듈 연결 뒤 사용자가 config를 stage/공유하려 함 | 이전 로컬 전용 동의를 자동 연장하지 않음. 모듈이 수행하는 stage/공유는 로컬 연결값을 확인하고 전환 후보부터 제시. 모듈 밖의 강제 add/push를 항상 막을 수 있다는 보장은 없음 |
| 공유 파일이 나중에 미추적/무시로 바뀜 | 모듈이 파일을 인수했다고 판단하지 않음. 새 관리 의도/현재 내용과 소유를 확인하고, 이전 개인 경로를 조용히 복원하지 않음 |
| 처음 모듈이 만든 파일에 사용자 설정이 추가됨 | 혼합 소유로 취급. 업데이트/연결 해제 때 전체 삭제나 옛 파일 덮기 금지. 현재도 식별 가능한 자기 변경만 대조/정리 |

Git의 [ignore 규칙](https://git-scm.com/docs/gitignore)은 이미 추적한 파일에 적용되지 않는다. 따라서 커밋 유무만 확인하지 않고 [index의 staged/unmerged 상태](https://git-scm.com/docs/git-ls-files)와 HEAD, 작업 트리, 유효한 제외 규칙을 함께 확인한다. Git이 사용자 의도까지 판별해 주는 것은 아니다. [Git FAQ](https://git-scm.com/docs/gitfaq)는 템플릿 + 무시된 개인 설정을 안내하지만 `skip-worktree`/`assume-unchanged`를 개인 변경 숨김 수단으로 쓰지 말라고 설명한다. 템플릿 방식의 일반적인 유효성과 이 모듈이 사용자 호스트 설정 전체를 관리해도 되는지는 별개다.

설치/연결/갱신/해제와 **모듈이 수행하는 관련 Git 반영 직전**에 필요한 상태를 다시 대조한다. 처음 설치 때 확인한 추적 상태를 영구 사실로 캐시하지 않는다. 읽기 뒤 실제 반영 사이의 사용자 변경은 기존 [파일 보호 — 「파일 반영과 핸들 수명」](update.md)와 재대조 조건으로 처리한다. 매 대화마다 전체 Git/DB 검사를 붙이거나 모든 외부 Git 행동을 가로채는 감시 기능을 새로 추가하지 않는다.

exclude를 쓰는 선택안도 규칙 소유를 보존해야 한다. 기존 규칙은 사용자 소유로 유지하고 모듈이 추가한 범위/당시 상태만 기존 설치/복원 기록에 연결한다. 현재 항목을 사용자가 수정했거나 출처/사용처가 불명확하면 제거하지 않는다. [Git 공통 info 디렉토리](https://git-scm.com/docs/gitrepository-layout) 때문에 같은 저장소의 linked worktree에 영향이 갈 수 있으므로, 저장소 로컬이라는 이유로 현재 작업 사본 하나에만 효과가 있다고 설명하지 않는다.

**상태에 따른 분기는 가능하지만 모든 상태에서 무승인 전환이 가능한 것은 아니다.** 일반 Codex의 기존 권한이 충분한 경우는 그대로 연결할 수 있다. 기존 공유 config를 보존해야 하고 직접 파일 접근 권한도 부족한 경우에는 아직 검증된 범용 연결 수단이 없다. 이를 별도 도구의 명시적 접근으로 풀 수 있는지는 아래 [로컬 WIKI 도구 후보 — 「로컬 WIKI 도구의 연결 후보」](entry.md#%EB%A1%9C%EC%BB%AC%20WIKI%20%EB%8F%84%EA%B5%AC%EC%9D%98%20%EC%97%B0%EA%B2%B0%20%ED%9B%84%EB%B3%B4)에서 검토하며, 일반 shell 권한이 추가된 것으로 보지 않는다. `.harness/local.json`을 권한 파일로 간주하거나, private 경로를 공유 파일에 넣거나, 제품 시작 명령을 강제해 이 미해결 조건을 숨기지 않는다. 해당 연결의 지원 범위/대안을 협의하며 무관한 프로젝트 설정을 관리 대상으로 넓히지 않는다.

따라서 앞서 제시한 전체 config 생성안의 채택 질문은 우선 보류하고 **모듈에 필요한 설정과 기존 호스트 설정의 경계를 먼저 확정하는 순서**로 보정한다. 생성/로컬 전용 운영은 사용자가 명시적으로 원하는 프로젝트의 선택안으로 남기며, 소유/공유 상태 전환을 부분 검사나 구현 완료로 보고하지 않는다.

#### 로컬 제외의 자동 처리

아래는 [소유와 공유 상태 — 「설정 소유와 공유 상태의 전환」](entry.md#%EC%84%A4%EC%A0%95%20%EC%86%8C%EC%9C%A0%EC%99%80%20%EA%B3%B5%EC%9C%A0%20%EC%83%81%ED%83%9C%EC%9D%98%20%EC%A0%84%ED%99%98)를 확인하고 사용자가 config의 로컬 전용 운영을 선택한 경우에만 적용하는 후보 절차다. 최초 연결 또는 경로 재설정에서 공통 연결 코드가 **해당 저장소의 `info/exclude`를 자동 처리**하므로 사용자가 별도 Git 설정 명령을 외울 필요는 없다. 자동 실행의 편의와 제외 정책을 임의 결정하는 것은 다르다. 이 파일은 Git 메타데이터여서 커밋/PR로 공유되지 않지만 여러 worktree에 효과가 갈 수 있다.

1. 코드 루트와 실제 Git 경로, config의 HEAD/index/작업 트리와 소유, 유효한 제외를 확인한다. `git rev-parse --path-format=absolute --git-path info/exclude`로 위치를 얻고 `.git/`이 디렉토리라고 가정하지 않는다. 추적/공유 변경 중이면 개인 경로를 넣기 전에 멈추고 관리 방식을 확인한다.
2. 선택한 로컬 config에 제외가 필요하고 기존 규칙이 충분하지 않을 때만 `/.codex/config.toml`을 등록한다. 기존 항목/사용자 편집/소유 기록을 보존하고 재실행 때 같은 항목을 추가하지 않는다. 공유 `.gitignore`, 전역 `core.excludesFile`과 Codex 전역 설정은 수정하지 않는다. Codex 안에서 실행할 때 보호 경로 쓰기 승인이 필요하면 호스트의 절차를 따른다. 자동 처리를 무승인 권한 확대와 혼동하지 않는다.
3. `git check-ignore`와 추적 상태로 실제 제외를 확인한 뒤 개인 경로를 저장한다. 상위/하위 `.gitignore`의 재포함 규칙 등으로 제외가 무효이면 연결을 완료 처리하지 않고 기존 상태를 보존한다. 파일 반영 도중 변경/중단의 처리는 기존 [보존 계약 — 「갱신과 복원」](update.md)을 따른다.
4. 같은 연결의 재사용에는 사용자 입력을 반복하지 않는다. 다른 팀원이나 새 clone은 자신의 최초 연결에서 같은 처리를 자동 수행한다. 작업 사본별 경로와 Git의 공유 메타데이터 범위를 구별하며, worktree의 exclude가 공통일 수 있으므로 해제 시 다른 작업 사본이 사용하는 항목을 지우지 않는다.

이 자동 제외는 경로 파일 하나에 대한 후보이며 기존 `/.harness/`의 [공유 제외 정책 — 「제외 규칙의 자동 설정」](../workflow/recovery.md)을 바꾸지 않는다. 이미 추적된 config의 자동 untrack, `skip-worktree`나 `assume-unchanged`로 숨기기는 사용하지 않는다. 사용자의 강제 stage까지 차단하는 보안 경계가 아니므로 모듈의 Git 작업은 개인 설정을 stage하지 않고 현재 추적 상태도 확인해야 한다.

Windows 합성 저장소에서 새 파일의 제외, 재실행 중복 방지, 일반 `git add .`의 공유 skill 보존, 기존 추적 파일의 보존, 재포함 규칙 충돌 시 개인 config 생성 중단을 확인했다. 상세는 [자동 제외 결과](../../evidence/experiments/runtime/2026-11-18_11-03-32-project-permissions.md)에 있다. 제품의 동시 편집/중단 복원과 실제 worktree는 별도 검증 대상이다.

#### 다른 도구의 사례와 적용 조건

11/18 공식 자료 대조다. 프로젝트별 개인 설정을 로컬에 보관하고 Git 공유에서 제외하는 원칙은 다른 개발 도구에도 있다. 아래 사례의 저장/제외 수단이 우리 조합과 같거나 우리 제품의 호환성을 입증하는 것은 아니다.

| 사례 | 공식 동작과 우리 설계에 주는 근거 |
| --- | --- |
| [Git 로컬 제외](https://git-scm.com/docs/gitignore) | 특정 저장소의 개발 작업 파일을 공유하지 않을 때 `info/exclude`를 사용하도록 안내. 우리가 쓰려는 제외 수단의 직접 근거 |
| [IntelliJ 프로젝트 설정](https://www.jetbrains.com/help/idea/configure-project-settings.html) | `.idea`에서 팀 설정과 개인 `workspace.xml`을 구분하고 개인 파일을 자동 제외. 공식 설명은 `.gitignore` 사용이며 우리 `info/exclude` 자동 처리와 동일하지 않음 |
| [Claude Code 설정](https://code.claude.com/docs/en/settings) | 공용 `.claude/settings.json`과 개인 `.claude/settings.local.json`을 별도 지원. 공식 문서상 도구가 개인 파일을 처음 쓸 때 전역 Git 제외에 등록하므로, 그 등록 범위를 프로젝트 한정인 우리 안에 그대로 옮기지 않음 |

**로컬 config만 제외하는 후보는 공유할 설정이 없고 사용자가 로컬 전용 운영을 선택한 경우에 한정한다.** Git은 TOML의 특정 키만 제외하지 않으므로 `.codex/config.toml` 전체를 제외하면 그 안의 공용 모델/권한/hook 설정도 함께 공유되지 않는다. 공용 설정이 필요한 경우의 새 후보와 공개 범위는 [공유 설정과 개인 경로의 충돌 해결](entry.md#%EA%B3%B5%EC%9C%A0%20%EC%84%A4%EC%A0%95%EA%B3%BC%20%EA%B0%9C%EC%9D%B8%20%EA%B2%BD%EB%A1%9C%EC%9D%98%20%EC%B6%A9%EB%8F%8C%20%ED%95%B4%EA%B2%B0)에 비교했다. 아직 채택하거나 구현하지 않았으며 사용자의 기존 공유 방식을 임의로 바꾸지 않는다.

| 발생 조건 | 영향과 대응 기준 |
| --- | --- |
| 새 clone/기기, Git 저장소 재생성 | 제외와 기기 경로가 자동 전달되지 않음. 현재 파일과 공유 의도를 확인하고 선택한 관리 범위만 기기 준비/연결에서 설정. 공유 설치 결과를 재생성하지 않음 |
| 다른 브랜치가 같은 config를 추적 | 브랜치 전환으로 무시된 로컬 파일이 덮어써질 수 있음. 모듈이 수행하는 전환은 대상의 추적 상태와 보호 옵션을 확인. 외부 IDE/Git 전환까지 설치 때의 제외가 보호한다고 보장하지 않음 |
| `git clean`의 무시 파일 포함 정리, 로컬 폴더 삭제 | 제외된 config도 삭제 대상. 유효한 로컬 연결 입력이 남으면 검사 후 자기 소유 설정만 재구성하고, 입력도 없으면 경로를 다시 받음. DB/원문까지 잃은 상황을 새 빈 상태로 정상 복구했다고 처리하지 않음 |
| 강제 stage, 나중 추적 전환, 제외 규칙 충돌 | 제외는 비밀정보 보호나 접근 제어가 아님. 비밀번호/토큰을 기록하지 않고 모듈의 반영/연결 변경에서 실제 추적 상태를 확인. 이미 공유된 파일은 자동 해제하지 않음 |
| linked worktree의 공통 Git 메타데이터 | [Git의 info 경로](https://git-scm.com/docs/gitrepository-layout)는 공통 디렉토리를 사용할 수 있음. 등록이 다른 사본의 미추적 config에도 영향을 주는지 확인. 해제 때 다른 사본이 쓰는 제외를 제거하지 않음 |
| config 상속/우선순위, 신뢰, 기존 정책 | 파일 저장/ignore 성공과 실제 Codex의 적용은 다름. [공식 설정 계층](https://learn.chatgpt.com/docs/config-file/config-basic)에 따라 실제 적용 범위와 일반 진입/재개를 검사 |

[Git checkout](https://git-scm.com/docs/git-checkout)의 기본 동작에는 무시된 파일의 덮어쓰기가 포함되고, [Git clean](https://git-scm.com/docs/git-clean)의 `-x`는 무시된 파일도 대상으로 한다. [Git add](https://git-scm.com/docs/git-add)의 강제 추가도 가능하다. 이는 공식 동작에 근거한 위험이며 이번 환경에서 새로 실행해 재현한 결과가 아니다. exclude를 `.gitignore`로 바꾸는 것만으로 덮어쓰기/삭제 위험이 사라지지 않는다.

설치/연결/변경/해제와 실제 WIKI 접근에 필요한 확인만 연결하고, 위험을 이유로 모든 요청에 전체 Git 검사나 DB 조회를 추가하지 않는다. 최소 안내는 [실행 안내 — 「실행 전 안내와 중단 시 도움」](install.md)에, 아직 실행하지 않은 사례는 [수용 입력 — 「지속 권한 설정의 검증 입력」](../../verification/acceptance.md)에 둔다. 일반 진입 전 자동 차단이 불가능한 구간을 사후 검사로 완전히 보호했다고 주장하지 않는다.

#### 공유 설정과 개인 경로의 충돌 해결

11/18 추가 질문의 검토안이다. **config 공개 자체를 문제로 보지 않고, 공유할 설정과 기기별 입력의 소유를 분리한다.** 공개 저장소에 추적하는 것, 비공개 팀 저장소에 공유하는 것, 실행 서버나 이미지에 포함하는 것은 서로 다른 결정이다. 개발 도구 설정이라고 모든 내용을 공개해도 되는 것은 아니다.

| 근거 | 확인 범위 |
| --- | --- |
| [Codex 프로젝트 설정](https://learn.chatgpt.com/docs/config-file/config-basic) | 프로젝트 `.codex/config.toml`을 지원하며 신뢰된 프로젝트에서 적용. 파일이 존재한다는 사실만으로 공개/비공개를 정하지 않음 |
| [공개된 팀 설정 예제](https://github.com/shanraisshan/codex-cli-best-practice/blob/main/.codex/config.toml) | 저장소가 해당 파일을 팀 공통 기본값으로 공개. 개인 경로까지 공유하거나 대기업 서비스가 보편적으로 같은 방식을 쓴다는 근거는 아님 |
| [Trail of Bits 설정 템플릿](https://github.com/trailofbits/codex-config/blob/main/config.toml) | 보안 업체가 Codex 설정 양식을 공개. 사용자 config로 복사/병합하는 템플릿이며 실제 서비스의 프로젝트 설정 공개 사례와 구별 |

공유 후보는 팀 지침의 상대 경로, 공통 도구 연결과 합의한 정책이다. 비밀번호/토큰/API 키는 이 설계의 설정이나 문서에 저장하지 않는다. 개인 WIKI 절대 경로와 공개가 허용되지 않은 내부 주소도 공유 원본에서 제외한다. 공용 모델/권한값 역시 사용자 정책을 확인한 뒤 필요한 항목만 다루며 모듈이 임의로 고정하지 않는다.

[공식 설정 계층](https://learn.chatgpt.com/docs/config-file/config-advanced#project-config-files-codexconfigtoml)과 [프로젝트 설정 로더](https://github.com/openai/codex/blob/main/codex-rs/config/src/loader/mod.rs)를 대조했다. 별도의 `config.local.toml` 자동 덧씌우기나 일반적인 include는 확인되지 않았다. [같은 기능의 공개 요청 #24961](https://github.com/openai/codex/issues/24961)도 조회 시 열려 있다. 이슈는 사용자 요구의 근거이며 지원 약속이나 구현 완료가 아니다. 현재 확인한 네이티브 로딩만으로 ‘공유 config 그대로 유지 + 임의의 비공개 외부 경로 + 전역 비변경 + 일반 codex 자동 진입’을 모두 해결했다고 할 수 없다.

| 방안 | 얻는 점 | 비용과 추천 조건 |
| --- | --- | --- |
| 로컬 config 전체 제외 | 최초 연결 뒤 일반 Codex가 기기 경로를 읽음. 기존 부분 시험 사용 가능 | 팀 설정 공유가 필요 없는 경우에만 충분. 이것만으로 전체 배포 환경을 지원하지 않음 |
| 공통 설정 원본 공유 + 로컬 config 생성 | 팀 설정은 공유하고 개인 경로는 로컬에 보관. 생성 후 일반 Codex가 공식 위치를 읽으며 전역 비변경 | 공통 원본 변경 시 생성본 갱신 필요. 사용자 호스트 설정 전체 관리로 넓어질 위험 때문에 기본 추천 철회. 해당 운영을 명시적으로 원하는 프로젝트의 선택안, 미채택 |
| 공유 config 유지 + 제품 시작 도구의 인자 | 기존 파일을 그대로 공유하고 기기 경로를 시작 인자로 전달. 별도 설정 동기화 감소 | ADR 0022의 기본 진입. 짧은 새 명령을 익혀야 하며 일반 codex의 외부 접근과는 별도로 검증 |
| 공유 config에 로컬 WIKI 도구 연결 | 공통 실행 등록만 공유하고 기기별 경로는 도구가 로컬 설정에서 조회. 일반 Codex와 전역 비변경을 함께 유지할 후보 | 명령 이름까지 일반 codex를 유지할 때의 미채택 대안. 사용자 비용을 포함한 [진입 방식 재비교 — 「전용 시작 명령과 MCP의 비교」](entry.md#%EC%A0%84%EC%9A%A9%20%EC%8B%9C%EC%9E%91%20%EB%AA%85%EB%A0%B9%EA%B3%BC%20MCP%EC%9D%98%20%EB%B9%84%EA%B5%90) 뒤 시험 여부 결정 |

앞서 추천했던 생성 후보의 개념은 다음과 같다. 소유/추적 전환 검토 뒤 범용 기본 추천은 철회했으며 비교 근거로 보존한다. 이름은 설명용이고 `config.template.toml`은 Codex가 자동으로 읽는 파일이 아니다. 이 선택안을 구현한다면 우리 연결 코드가 소비할 공통 원본이다.

```text
Git 공유: .codex/config.template.toml   팀 공통 설정 원본
로컬 입력: .harness/local.json         이 기기의 WIKI 연결
                   ↓ 설치/연결 코드에서 후보 생성과 대조
Git 제외: .codex/config.toml            Codex가 실제 읽는 생성 결과
```

1. 최초 담당자가 공유할 설정 원본을 정한다. 기존 추적 config가 있으면 이동/추적 변경과 경로 해석 차이를 미리 보여주고 동의받는다. 설정 관리 방식을 바꾸지 않겠다는 프로젝트를 자동 전환하지 않는다. 필요한 공통 설정이 없으면 빈 템플릿을 의무 생성하지 않는다.
2. 각 팀원의 최초 기기 준비가 같은 공통 원본과 자신의 WIKI 입력을 사용해 실행 설정을 만든다. private 경로를 공통 원본에 역반영하지 않으며, [로컬 제외의 자동 처리](entry.md#%EB%A1%9C%EC%BB%AC%20%EC%A0%9C%EC%99%B8%EC%9D%98%20%EC%9E%90%EB%8F%99%20%EC%B2%98%EB%A6%AC)로 실제 제외를 확인한 뒤 저장한다. 단순 문자열 치환이나 파일 전체 덮기로 기존 모델/승인/deny/네트워크와 사용자 항목을 잃지 않는다.
3. 준비 이후에는 일반 `codex`가 생성된 파일을 직접 읽는다. 매 요청의 AI 설정 생성, 새 모델 호출이나 전역 파일 편집은 필요하지 않은 설계다. 실제 TUI/재개의 검증은 여전히 남아 있다.
4. WIKI 경로 변경이나 공통 설정 갱신 때 기존 연결/갱신 코드로 재생성한다. 이전 생성 기준, 현재 사용자 편집, 새 공통 원본을 대조하고 충돌이면 자동 덮지 않는다. 기존 [갱신과 복원](update.md) 계약을 재사용하며 두 번째 범용 업데이트 엔진을 별도로 만들지 않는다.

**단점은 생성본이 저절로 최신화되지 않는다는 점이다.** 팀원이 Git pull로 공통 원본의 변경을 받았어도 기존 생성본은 그대로다. 따라서 이 후보에는 원본 변경 후 연결 갱신 절차가 필요하다. 변경을 받는 흐름과 최초 연결의 안내에 그 절차를 포함하고, 해시 대조 같은 좁은 검사로 불일치를 찾는 방안을 검증한다. 모든 대화마다 전체 설정/DB를 검사하지 않는다. 시작 hook이 권한 로딩 전에 실행되거나 이미 열린 세션의 권한을 자동으로 바꾼다고 가정하지 않으며, 재진입이 필요한 변경은 명시한다. 사용자가 모듈 밖에서 Git/설정을 변경한 모든 경우까지 무조건 자동 동기화된다고 보장하지 않는다.

생성 방식은 **기존 `.codex/config.toml`을 그대로 추적해야 하는 팀까지 투명하게 지원하는 해결책이 아니다.** 현재 우선순위는 [설정 소유와 공유 상태의 전환](entry.md#%EC%84%A4%EC%A0%95%20%EC%86%8C%EC%9C%A0%EC%99%80%20%EA%B3%B5%EC%9C%A0%20%EC%83%81%ED%83%9C%EC%9D%98%20%EC%A0%84%ED%99%98)에 따라 필요한 모듈 연결 범위부터 좁히는 것이다. 별도 공통 원본 운영을 원하는 프로젝트에서는 선택안을 다시 비교할 수 있다. 실제 설정 이동, untrack, 제품 구현이나 Windows 실행은 진행하지 않았으며 이 질문을 운영 방식 전환 동의로 해석하지 않는다. 소유/상태 전환과 실제 적용의 [수용 입력 — 「지속 권한 설정의 검증 입력」](../../verification/acceptance.md)은 미실행이다.

#### 전용 시작 명령과 MCP의 비교

11/18 검토 뒤 사용자가 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 전용 시작 명령 기본과 선택 MCP의 단계적 검증을 채택했다. 아래는 채택 근거와 구현 조건이다. 일반 codex만을 기본으로 둘 때 검토했던 MCP는 11/22 비교 뒤 후속 제공으로 전환했다. 두 방식의 동등한 첫 배포 지원을 요구하지 않는다.

전용 시작 명령은 새 AI 프로그램이나 별도 Codex 설치본이 아니다. `프로젝트 명령 → 해당 프로젝트의 로컬 경로 확인 → 현재 설치된 Codex에 필요한 인자 전달 → 원래 대화형 Codex`의 흐름이다. 예를 들어 제품의 `start`/`resume`이 저장된 WIKI 위치를 `--add-dir`로 전달하는 후보이며, [공식 CLI](https://learn.chatgpt.com/docs/cli/reference)는 이 추가 경로와 작업 위치, 세션 재개를 지원한다. 실제 사용자의 권한 방식에서 그 인자가 유효한지는 따로 확인한다.

별칭은 이 시작 코드를 짧게 부르는 선택 수단이다. 프로젝트 로컬 실행 파일을 명시적으로 호출하는 방식도 가능하며, 셸 프로필/PATH나 Codex 전역 설정을 자동 수정하는 해법으로 바꾸지 않는다. 고유 이름/등록은 [명령 기준 — 「명령 이름과 충돌 방지」](../module.md)에 따른다.

| 사용자 관점 | 일반 codex + 로컬 WIKI MCP 후보 | 전용 시작 명령 후보 |
| --- | --- | --- |
| 평소 진입 | 익숙한 codex 그대로. 프로젝트 도구 연결이 추가됨 | 짧은 제품 명령 하나로 Codex에 진입. 명령을 기억해야 함 |
| 최초 기기 준비 | 기존 준비 외 SDK/도구 등록과 시작/호출 권한 확인 | 기존 Python/Codex와 기기별 WIKI 등록, 실행 연결. 별도 MCP 의존성 불필요 |
| 사용 중 실행/시간 | 연결 유지 중 Python 도구 프로세스와 초기화, 요청/응답 비용. 웹 서버 운영은 불필요 | 시작 때 로컬 경로 확인과 프로세스 인계. 이후 기존 Codex 파일 도구를 사용. Windows에서는 시작 프로세스가 자식을 기다릴 수 있으나 별도 WIKI 서비스는 없음 |
| 토큰 | 도구 설명과 호출/반환 때문에 달라질 수 있음. 줄거나 늘어날 폭은 같은 작업으로 측정 | 경로 조회/인자 구성 자체는 모델 비호출. 자동 프롬프트나 매 요청의 경로 조회를 넣지 않음. 전체 토큰이 수학적으로 동일하다는 보장은 하지 않음 |
| 문제 해결 | 도구 시작/중단, 의존성, 도구별 승인과 읽기/쓰기 경로를 추가로 확인 | 실행 파일 탐색, 인자 전달, TUI/재개/권한을 확인. 원래 Codex 진입과 혼용하면 외부 접근 조건이 달라질 수 있음 |
| 기본 기능 | WIKI는 전용 도구를 이용하도록 지침/호환 확인 필요 | 실제 Codex를 실행하므로 기존 기능 유지가 목표. 잘못된 래핑으로 입력/옵션/재개가 깨질 수 있어 실증 필요 |

11/18 이 비교를 작성할 때 시간/토큰/메모리는 미측정이었다. 이후 시간/토큰의 단건 실측과 11/22 첫 제공 선택은 [MCP 비교 결과 — 「세 방식 비교와 첫 제공 판단」](../integration/mcp.md)에 연결한다. 메모리와 일반적인 비용 차이는 여전히 미확인이다. 작은 로컬 설정 조회는 매번 AI로 판단할 일이 아니며 MCP가 모든 환경에서 과도한 비용을 만든다고 단정하지 않는다. 다만 현재 범위에서는 **명령 하나를 익히는 부담보다 추가 의존성과 WIKI 접근 경로의 오류/지원 부담을 줄이는 이익이 더 클 것**으로 판단한다. 이는 공식 성능 결과가 아니라 첫 지원 환경과 기한, 요구사항을 대조한 추천이다. IDE/다른 호스트에도 같은 WIKI 도구를 제공할 필요가 생기면 MCP의 가치가 커질 수 있지만 이번에 지원을 확대하지 않는다.

채택한 전용 명령은 다음을 지킨다.

1. 사용자 환경의 Codex 실행 파일을 실행 때 찾고 실제 경로/버전의 지원 여부를 확인한다. 개발자의 절대 경로나 오래된 버전으로 고정하지 않으며 자동 업/다운그레이드하지 않는다. 사용자 설치 업데이트 뒤 새 진입에서 반영되는지 검사한다.
2. 기존 환경, 인증/세션 저장 위치, 모델과 옵션을 유지한다. 별도 CODEX_HOME, 다른 모델, 자동 요청문을 숨겨 넣지 않는다. 사용자 인자는 원래 인자 경계를 보존해 전달하고 제품 옵션과의 충돌을 명확히 알린다. 모든 미래 Codex 옵션/호스트 호환을 무조건 보장하지 않는다.
3. 시작은 빈 입력의 새 세션, 재개는 지정한 세션 또는 Codex의 선택 흐름을 사용한다. 기존 기록을 새 세션으로 바꾸거나 특정 UUID/최근 세션을 몰래 고정하지 않는다. 다른 프로젝트의 세션을 골랐을 때 현재 WIKI를 잘못 연결하지 않도록 확인한다.
4. 대화형 터미널 입력/출력, 종료 코드와 Ctrl+C를 보존하며 일반 사용을 짧은 시험 timeout으로 끊지 않는다. [Python subprocess](https://docs.python.org/3/library/subprocess.html#security-considerations)의 Windows batch/셸 인자 주의를 반영해 공백/한글/메타문자, `.cmd`/`.ps1`과 프로세스 종료를 실제 Windows에서 검증한다.
5. 추가 경로는 현재 작업 사본의 등록값만 전달한다. 관리/신뢰/보호 경로 제한을 무조건 우회하거나 sandbox/승인 정책을 강제로 완화하지 않는다. 승인 재사용의 기존 경계를 유지한다.
6. 기존 `codex`도 그대로 실행 가능해야 한다. 프로젝트 안 지침/skill은 해당 호스트 규칙대로 사용하고, 외부 WIKI 접근이 부족할 때는 필요한 기능만 안내한다. 일반 codex로 켠 것을 이유로 설치 전체를 망가뜨리거나 WIKI 검사를 조용히 생략하지 않는다. 권한이 이미 충분하면 추가 진입을 요구하지 않는다.

CLI 호출과 라이선스/재배포의 구분은 [라이선스와 저작권](../module.md)을 따른다. 초기 조사에서는 WSL Codex 0.169.1의 시작/재개 도움말과 패키지 메타데이터를 읽었다. 후속 Windows 사용자 시험의 모델 실행과 읽기/쓰기/재개 관측은 아래 실행 조건에 연결하며 제품 명령 구현과 구분한다. 동등한 사용 흐름의 수용 입력은 [전용 시작 명령 검증 — 「전용 시작 명령의 검증 입력」](../../verification/acceptance.md)에 둔다.

Windows npm 설치본은 `.cmd` 중계 파일의 호출만으로 임의 인자의 보존을 보장하지 않는다. 11/18 [인자 비교](../../evidence/experiments/runtime/2026-11-18_13-54-14-launch-arguments.md)에서 `%이름%` 형태가 환경변수 값으로 바뀌었다. 현재 설치본의 `package.json`에 등록된 공식 진입 파일을 해당 Node 실행 파일로 호출하는 후보는 셸을 거치지 않으며 같은 버전/도움말을 확인했다. 제품은 설치 형식을 확인해 지원하는 실행 경로를 선택하고, 모르는 중계 파일을 임의 해석하거나 문자열 인자를 이어붙여 실행하지 않는다. npm 내부 경로나 native 실행 파일의 위치를 사용자 전체의 고정 계약으로 복사하지 않는다. 후속 시험에서 현재 설치본의 대화형 읽기/쓰기와 같은 세션 재개를 확인했다. 다른 설치 형식, 실행 중 취소와 비정상 종료는 아직 검증하지 않았다.

#### 두 방식의 선택 제공

11/18 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 기본 진입을 유지하고, 11/22 실제 비교 뒤 **첫 배포는 전용 시작 명령/직접 접근에 집중하며 MCP 제공은 후속 검토로 둔다**고 사용자가 선택했다. 첫 설치가 MCP 등록/의존성/프로세스를 만들 필요는 없으며, 기존 사용자 MCP 설정을 제거하지 않는다. 향후 제공 시점과 지원 기능은 새 근거로 판단한다.

두 방식은 역할이 다르다. 시작 명령은 Codex를 어떤 경로/권한 인자로 열지 준비한다. MCP는 실행 중인 AI가 WIKI 작업을 요청할 통로다. 기술적으로 공존할 수 있지만 사용자가 둘을 동시에 켜야 한다는 뜻은 아니다.

| 제공 범위 | 얻는 것 | 부담과 판단 |
| --- | --- | --- |
| 전용 시작 명령/직접 접근 우선 — 11/22 채택 | 현재 Codex의 직접 파일 접근 활용, 초기 지원 범위가 작음 | 외부 WIKI 작업에 다른 시작 명령을 기억해야 함 |
| 두 방식 모두 첫 배포에서 동등 지원 | 진입 취향에 따른 선택과 대체 연결 | 설치/권한/갱신/장애 처리와 같은 작업의 두 경로를 검증해야 함. 현시점 우선 추천 아님 |
| 기본 경로와 선택 MCP를 단계적으로 검증 — 11/18 채택 이력 | 핵심 기능을 우선 완성하면서 MCP의 실제 효용 확인 | 실제 비교 후 11/22 직접 접근 우선으로 범위를 정함. 추가 MCP 보완은 후속 |

선택 MCP를 만들 경우 프로젝트 식별, WIKI 위치와 모듈이 수행하는 작업 규칙을 따로 복제하지 않는다. 기존 연결/보호 로직을 이용하고 MCP 연결부는 요청/응답 형식의 변환을 맡긴다. 다만 **Codex의 일반 shell/apply_patch 편집이 우리 코드의 검사를 반드시 거치는 것은 아니다.** 모듈이 소유한 작업과 직접/수동 편집을 구분하고 실제 호출 경로를 확인해야 한다. MCP 도입만으로 모든 편집의 보호가 통일됐다고 주장하지 않는다.

한 작업의 WIKI 접근 경로를 명확히 선택하고, 결과가 불명확한 쓰기를 다른 경로로 자동 재실행하지 않는다. MCP 미선택 사용자는 그 의존성 설치, 도구 등록, 프로세스 실행을 요구받지 않아야 한다. 활성화/비활성화와 갱신/제거는 기존 사용자 config, WIKI, 기본 사용 흐름을 보존해야 하며 전역 Codex 설정은 수정하지 않는다. 다른 AI 호스트의 연결 가능성은 확장 이점 후보일 뿐 첫 지원 환경을 넓히는 결정이 아니다.

검증은 필요한 읽기/검색과 프로젝트 구분부터 좁게 시작하고, 사용자 이점이 확인되면 쓰기/편집 충돌/중단 처리로 확장하는 순서를 제안한다. 읽기 전용 시험은 쓰기나 상세 복원 기능의 완료가 아니다. 기존 필수 WIKI 기능을 없애거나 읽기 기능만으로 첫 배포를 완료 처리하지 않는다. 같은 작업의 정확성, 사용자 입력/승인 횟수, 시작/처리 시간, 전체 토큰과 문제 해결 부담을 비교하고 이득이 작으면 MCP 확대를 보류한다. 수용 입력은 [두 방식의 비교 검증](../../verification/acceptance.md)에 둔다.

공개 병행 사례와 개인 기술 검토 판단은 [로컬 MCP의 추가 가치](../../discussions/architecture/alternatives.md)에 연결한다. 학습/기술 검토 목적만으로 제품 의존성이나 필수 기능을 늘리지 않는다.

#### 로컬 WIKI 도구의 연결 후보

MCP의 구체 구현은 제품에 추가된 연결이 아니며, 아래는 11/22에 첫 제공을 후속으로 미룬 후보/검증 기록이다. 재검토 전까지 기본 직접 접근 개발의 선행 조건으로 두지 않는다. 로컬 STDIO로 합성 Windows SDK 검사와 A 프로젝트의 실제 Codex 읽기/검색 표본을 확인했다. [시험 근거](../../evidence/experiments/wiki-access/2026-11-18_15-21-34-mcp-read.md)에 최초 출력 형식/실행 경로 실패와 보완을 보존한다. [후속 프로젝트/하위 경로 시험](../../evidence/experiments/wiki-access/2026-11-18_15-50-14-mcp-projects.md)에서는 B의 실제 검색/읽기와 A 재개를 확인했다. 하위 폴더의 경로 없음 실패는 Git 루트를 찾는 시험 시작 코드로 보정해 SDK 5곳과 실제 A/nested 읽기를 확인했다. 후속으로 [실제 문서 사본의 동일 코드 비교](../../evidence/experiments/wiki-access/2026-11-18_16-32-09-wiki-compare.md)를 실행해 Windows 파일 검사와 직접/MCP 반환 일치, 통신 시간을 확인했다. 이 선행 시험은 원본을 보존한 모델 없는 검사다. 이어 [실제 Codex 비교](../../evidence/experiments/wiki-access/2026-11-18_16-50-18-codex-wiki-usage.md)를 각 새 대화 한 요청씩 수행했다. 두 방식의 읽기는 추가 승인 없이 완료됐으나 필수 조건 누락이 있었고 이번 MCP 표본은 시간/토큰 절감 이점을 보이지 않았다. 쓰기와 제품 설치는 아직이다. 기존 권한으로 충분한 환경은 그대로 재사용한다.

MCP는 일반 Codex에서 등록 WIKI에 접근하는 사용성 이점이 있지만, 통신 연결이 탐색 품질이나 토큰 절감을 보장하지 않는다. [읽기 보완 — 「MCP 읽기의 남은 보완」](entry.md#MCP%20%EC%9D%BD%EA%B8%B0%EC%9D%98%20%EB%82%A8%EC%9D%80%20%EB%B3%B4%EC%99%84)의 명세/후속 후보/실측과 미검증은 유지한다. 11/22 첫 제공 보류 이후에는 재검토할 때 필요한 조건이며 기본 직접 접근 개발의 선행 작업으로 두지 않는다. 상세 수치와 표본 한계는 위 실행 근거가 소유한다.

공식 Codex 문서는 [프로젝트 config의 MCP 등록, STDIO와 실행 입력](https://learn.chatgpt.com/docs/extend/mcp#stdio-servers)을 지원한다. [설정 계층](https://learn.chatgpt.com/docs/config-file/config-advanced#project-config-files-codexconfigtoml)은 신뢰된 프로젝트의 설정을 읽는다. 아래는 그 기능을 이용한 **우리 모듈의 설계 후보**다. 현재 시험은 작은 읽기/검색 연결만 확인했으며 제품의 설치/설정 병합과 전체 연결 완료가 아니다.

| 위치 | 후보에 담을 내용 | 공유 여부 |
| --- | --- | --- |
| `.codex/config.toml` | 제품 전용 `mcp_servers` 항목의 실행 명령/인자/작업 위치와 필요한 도구 정책. 개인 WIKI 경로나 모델/일반 sandbox 변경은 넣지 않음 | 기존 사용자 공유 방식 유지. 이 항목은 공유 가능한 내용만 준비 |
| 프로젝트의 모듈 설치 영역 | WIKI 작업 코드와 MCP 연결부. 저장/검증/복구의 공통 처리를 재사용 | 기존 설치 결과와 같은 기준으로 공유 |
| `.harness/local.json` | 이 작업 사본의 프로젝트 식별과 실제 WIKI 위치 | 기존 로컬 제외 정책 유지 |

예를 들어 A는 `C:/Work/team-wiki`, B는 `D:/Notes/team-wiki`를 등록해도 공통 실행 등록은 같다. 공통 코드가 자기 작업 사본의 로컬 설정을 읽기 때문이다. 공유 config가 비공개 파일을 자동 include하는 기능이 생기는 것은 아니다. 기존 파일에 필요한 제품 항목만 후보로 추가하고 사용자 항목과 Git 추적 상태를 유지한다. 기존 충분한 등록이 있으면 중복하지 않으며 이름/의미 충돌은 먼저 확인한다.

여기서 서버는 별도 컴퓨터가 아니라 요청을 처리하는 프로그램의 역할을 뜻한다. [STDIO 규격](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports#stdio)은 클라이언트가 로컬 자식 프로세스를 실행하는 방식이다. 도구 사용 중 PC와 해당 프로세스는 실행 중이어야 하지만 24시간 켜둘 서버, Docker/클라우드 배포나 외부 포트가 필수는 아니다. [수명 주기](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle#shutdown)에 따라 연결 종료 때 프로세스를 정리해야 한다. Codex의 백그라운드 실행 구조 때문에 터미널 하나를 닫는 순간 항상 종료된다고 단정하지 않으며 실제 종료/재개를 확인한다. WIKI 원본은 기존 로컬 Markdown/Git 그대로이고 서버로 업로드하거나 이동하는 안이 아니다.

실행 흐름은 다음과 같다.

1. 담당자는 프로젝트에 모듈과 WIKI 도구의 실행 등록을 준비한다. 기기별 Python 실행 위치가 공유 파일에 들어가지 않도록 공통 진입을 정하고, 프로젝트 루트/하위 폴더/worktree에서 같은 설치본을 찾는지 검사한다. `command`, `args`, `cwd`의 실제 해석은 Windows 검증 대상이다.
2. 각 팀원은 최초 연결에서 자기 WIKI 위치와 허용할 작업을 등록한다. 필요한 준비물이 없으면 기존 설치/재개 흐름으로 안내한다. 연결하지 않은 기기는 다른 팀원의 경로를 빌리지 않고 준비 필요를 반환한다.
3. 일반 `codex`로 시작하면 해당 프로젝트의 WIKI 도구를 연결한다. MCP는 Codex가 실행하는 로컬 프로세스다. 시작 자체가 WIKI 전체 읽기나 AI 요청을 뜻하지 않는다. 경로 미등록/도구 실패는 관련 작업에 알리고 성공으로 건너뛰지 않되, 무관한 일반 작업까지 새로 차단하는 정책을 넣지 않는다.
4. 문서가 필요할 때 AI가 목록/검색/원문 읽기/변경 반영 같은 좁은 기능을 호출한다. 이름과 개수는 후속 명세다. 도구는 등록 범위와 현재 파일을 확인한 뒤 기존 WIKI 처리 코드로 실행한다. 모델이 만든 변경 후보의 검토와 최종 반영 책임은 유지한다.
5. 경로 변경은 기존 연결 기능에서 로컬 입력을 바꾼다. 열린 프로세스의 경로 재확인과 진행 중 작업을 연결해, 변경 전 요청이 뒤늦게 새/옛 WIKI에 잘못 쓰지 않도록 검증한다. 사용자가 매 세션마다 도구를 직접 실행하거나 경로를 다시 입력하는 기본 흐름은 아니다.

**권한 경계가 달라진다.** [Codex 권한 문서](https://learn.chatgpt.com/docs/permissions#scope-and-enforcement)는 로컬 shell sandbox와 MCP의 통제를 구분한다. 이 후보는 일반 shell/apply_patch의 외부 쓰기 권한을 추가하지 않는다. 명시적으로 허용한 WIKI 도구가 자기 접근 범위를 제한해야 한다. 등록 루트 밖 경로, 심볼릭 링크/Windows junction을 통한 범위 이탈, 임의 shell 명령, Git/호스트 설정 파일의 일반 편집을 허용하는 범용 우회 통로로 만들지 않는다. 호스트/관리자 정책이 이 도구를 허용하지 않으면 사용 불가를 알리고 다른 통로로 제한을 피하지 않는다.

기존 [파일 보호 — 「파일 반영과 핸들 수명」](update.md)와 [중단 처리 — 「복구의 대상과 경계」](../workflow/recovery.md)를 재사용한다. 요청 전후 파일 변경과 결과 유실을 확인하고 동일 반영을 무조건 재실행하지 않는다. MCP가 기록과 복원 로직을 하나 더 소유하지 않으며 단순 조회마다 DB 트랜잭션/active 갱신을 추가하지 않는다. 설치된 지침/skill은 필요한 WIKI 접근을 이 도구에 연결해야 하므로 도구 설치만으로 AI의 올바른 사용을 통과 처리하지 않는다.

[도구별 승인 설정](https://learn.chatgpt.com/docs/extend/mcp#other-configuration-options)으로 허용 범위 안의 반복 요청을 줄일 수 있는지 검증한다. 최초 연결의 범위 동의와 Codex의 프로젝트 신뢰, 도구/관리자 정책을 구분하며 기존 제한보다 넓은 자동 승인을 임의 적용하지 않는다. 같은 범위의 허용은 재사용하고 실제 정책이 추가 확인을 요구하면 그 원인을 안내한다. 모든 환경에서 최초 한 번의 승인만 남는다고 보장하지 않는다.

| 비용 또는 영향 | 검토 기준 |
| --- | --- |
| 실행/배포 | [STDIO 표준](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports#stdio)은 자식 프로세스의 stdin/stdout 통신이다. 웹 서버 배포/HTTP 포트를 필수로 만들 필요는 없지만 Python 프로세스의 시작/종료/오류 처리가 추가됨 |
| 의존성 | [공식 Python SDK](https://github.com/modelcontextprotocol/python-sdk) 사용 후보. 조회한 main 문서는 Python 3.11+지만 실제 시험한 2.3.0 배포 메타데이터는 3.10+다. Windows Python 3.13.9의 격리 환경에 SDK와 의존성 29개를 설치해 확인했다. 채택 시 지원 버전/의존성을 고정 확인하고 준비/설치 안내 필요. 프로토콜을 직접 재구현해 표준 라이브러리만으로 된다고 약속하지 않음 |
| 토큰 | 로컬 프로세스 실행 자체에 별도 모델 요청이 필요하지 않음. 도구 설명/입출력, 검색/재시도로 AI 토큰은 달라질 수 있음. 같은 원문/작업으로 직접 접근과 비교하고 차이와 완성도를 함께 판단. 수치는 미측정 |
| 읽기 범위 | 필요한 원문만 범위를 나눠 반환하고 누락/잘림을 표시. 원문을 임의 요약해 비용을 낮추지 않음. 로컬에서 읽어도 Codex에 반환한 본문은 기존 모델 입력이 됨 |
| 긴 작업 | 호스트의 시작/도구 호출 timeout과 제품 작업 완료를 구별. 대량 복원/긴 Git 작업을 동기 호출 하나에 묶지 않고 기존 단위/중단/결과 조회를 사용. timeout을 미실행으로 단정하지 않음 |
| 전체 기능 | 파일 읽기/변경 성공이 WIKI Git/PR, 비대화형 복원, hook/검증 연계까지 입증하지 않음. 필요한 작업별 공통 실행 연결과 허용 범위도 확인. 임의 shell 실행 도구 하나로 해결하지 않음 |

첫 시험은 합성 두 프로젝트의 서로 다른 WIKI, 공통 config 보존, 일반 Codex의 시작/재개, 경로 변경, 사용자 편집 충돌과 중단을 다룬다. 상세 입력은 [로컬 WIKI 도구 검증 — 「로컬 WIKI 도구의 검증 입력」](../../verification/acceptance.md)이 소유한다. 모델 없는 연결 확인과 실제 AI 도구 사용은 구분하며 후자의 입력/권한/비용은 실행 전에 정한다. 앞선 권한 프로필/합성 Git 검사를 이 후보의 성공 근거로 재사용하지 않는다.

현재는 전용 시작 명령 기본을 채택했고, MCP는 [선택 제공 — 「두 방식의 선택 제공」](entry.md#%EB%91%90%20%EB%B0%A9%EC%8B%9D%EC%9D%98%20%EC%84%A0%ED%83%9D%20%EC%A0%9C%EA%B3%B5)의 단계로 검증한다. 예비 WSL 도구/세션과 현재 위키의 접근 방식은 이번 제품 선택의 변경 대상이 아니다.

#### MCP 읽기의 남은 보완

선택 MCP의 읽기/검색 계약은 [MCP 읽기 명세](../integration/mcp.md)가 소유한다. 이 절은 기존 링크의 진입점으로 유지하고, 권한/설정 발견과 일반 Codex 연결은 이 문서에서 계속 다룬다. MCP의 첫 제공 여부나 쓰기 지원을 확정한 것은 아니다.

1. [동등성의 목표와 경계](../integration/mcp.md): 같은 입력 의미와 원문/결과, 달라도 되는 호출/전송 표현을 구별한다.
2. [읽기와 이어 받기 — 「읽기 입력과 이어 받기」](../integration/mcp.md), [검색과 계속 찾기 — 「검색 범위와 계속 찾기」](../integration/mcp.md): 요청 범위를 보존하고 다음 요청 인자를 도구가 반환한다.
3. [반환 정책 — 「반환 정책과 크기의 기준」](../integration/mcp.md), [전송/수신 대조 — 「SDK 전송과 호스트 수신의 대조」](../integration/mcp.md): 배포 후보의 기본값과 실제 호스트의 적용값을 구별한다.

[R-01~14 수용 입력 — 「MCP 읽기 보완의 검증 입력」](../../verification/acceptance.md)으로 같은 배포 후보/설정과 실제 사용 경로를 검증한다. SDK 부분 확인이나 원문이 같은 두 출력만으로 전체 수신/답변의 완전성을 보장하지 않는다. 아래의 실행 조건 조회도 현재 대화의 모든 한도를 자동 제공한다는 뜻이 아니다.

[축소 재시도 조건 — 「축소 재시도의 범위와 종료 조건」](../integration/mcp.md)은 11/20 B안으로 채택했고 별도 후보의 서버 instructions와 오류 안내에 반영했다. 코드/SDK 부분 검사와 실제 AI 동작은 구분한다. 기존 Windows 연결을 보존한 새 위치의 [실제 읽기와 검색](../../evidence/experiments/wiki-access/2026-11-21_04-19-04-mcp-retry-run.md)에서 지침 노출, 원문 전체 수신과 검색 결과 일치를 확인했다. 자동 축소는 아직 관측하지 못했다. 모듈의 page_bytes를 아는 것과 Codex의 유효 출력 한도를 아는 것은 별개다. 현재 후보는 첫 기본값 요청이 잘렸을 때 적용 크기를 항상 제공하지 못한다. 입력에 크기가 없으면 옛 숫자로 자동 재시도하지 않으며 미완료 이유와 확인할 연결 정보를 알린다. 이 보완을 위해 새 조회 도구, 전역 설정 변경이나 매 읽기의 설정 파일 탐색을 채택한 것은 아니다. 적용 크기 확보와 AI의 최대 횟수 준수는 미해결/미검증 항목으로 유지하고, 실제 첫 응답 유실을 포함한 자동 복구 범위는 수용 기준에서 따로 확인한다.
