# 갱신과 복원

11/09부터 협의한 사용자 편집 보존을 11/11의 프로젝트 내 설치에 맞췄다. 프로젝트 내 배치와 ADR 0011의 원문 보호, 독립 완료 유지, 실패 보고/조건부 복원, 합의 후 재개는 채택됐다. 11/16에는 [실패 뒤 재시도 또는 이전 구성 사용 — 「업데이트 실패 후 선택」](update.md#%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8%20%EC%8B%A4%ED%8C%A8%20%ED%9B%84%20%EC%84%A0%ED%83%9D)을 선택하는 흐름과 사전 안내를 추가했다. **파일 반영/실행 보호와 기록은 명세 후보이며 제품은 미구현**이다. SQL 저장 관계의 DDL 후보는 작성했고, 상세 병합, 단위 목록, 명령과 실제 Windows 검증은 남아 있다. 여기서 갱신은 프로젝트에 설치된 하네스를 새 배포 버전으로 바꾸는 작업이고, 복원은 갱신 중 문제가 생겼을 때 그 작업이 바꾼 파일, 설정을 이전 상태로 되돌리는 작업이다. WIKI 역공학이나 AI 세션 복구와는 대상이 다르다. 설치 수단 선택과 아래 갱신 계약의 채택은 구분한다.

아래 용어는 공통 파일의 보관 위치와 무관하게 역할을 구분한다. ‘공통’은 여러 프로젝트가 사용하는 하네스 기능이라는 뜻이며, 각 프로젝트의 업무 코드나 WIKI 본문을 가리키지 않는다.

| 용어 | 뜻과 예시 | 수정하는 곳 |
| --- | --- | --- |
| 모듈 원본 | 하네스 개발 저장소의 코드, 배포 자료. 예: WIKI 탐색, 검증, 실패 기록 기능 | 모듈 개발자가 이 저장소에서 개선하고 시험, 배포 |
| 프로젝트 설치본 — 앞서 쓴 ‘적용본’ | 그 프로젝트에 설치한 실행 파일, 연결, 설정과 공식 배포 기준 | 사용자가 프로젝트에 맞게 수정하고 필요할 때 공식 업데이트 적용. 사용자 변경은 갱신 전에 감지, 보존 |
| 프로젝트별 설정, WIKI | 그 프로젝트의 검사 명령, 문서 위치, 요구사항, ADR 등 | 해당 프로젝트 또는 연결된 WIKI에서 관리 |

**공식 버전을 발행하는 주체는 모듈 개발자/유지보수자다.** 설치 도구나 AI가 사용자 수정마다 공식 버전 번호를 만들거나 원본 저장소에 태그, 릴리스를 발행하지 않는다. 사용자 프로젝트의 변경 이력은 그 프로젝트 정책에 따라 관리하고, 우리 모듈 전용 버저닝을 추가로 요구하지 않는다.

설치 기록에 제안한 버전은 **‘어느 공식 배포본에서 시작했는가’라는 출처**다. 예를 들어 공식 1.0.0으로 설치한 뒤 사용자가 skill을 수정해도 설치 기준은 1.0.0이며 사용자 편집이 추가된 상태다. 이를 공식 1.0.1로 승격하거나 현재 파일이 공식 1.0.0과 동일하다고 표시하지 않는다. 번호를 각 파일, 폴더, 문서명에 붙이지 않고 필요한 설치 기준 한 곳에서 관리하는 후보다. 정확한 필드/형식은 미확정이다.

이 기록은 앞서 요청한 신버전 조회, 사용자 편집 보존, 업데이트/복원에서 이전 기준과 현재 파일을 구별하기 위한 것이다. 설치 후 공식 업데이트 기능을 사용하지 않고 독립적으로 관리하는 사용자에게 별도 릴리스 관리 절차를 요구하지 않는다. 자동 갱신을 지원할 때는 기존 배포 기준, 생성 입력과 현재 변경을 식별할 근거가 필요하고, 버전 문자열 하나만으로 안전한 병합/복구가 보장되지는 않는다. [Copier의 공식 갱신 설명](https://copier.readthedocs.io/en/stable/updating/)도 이전 템플릿, 생성 입력과 사용자 변경을 비교한다. 이는 설치 출처 기록의 근거이며 Copier 채택은 아니다.

앞서 쓴 **‘공통 수정’은 하네스 자체의 기능 개선, 버그 수정**을 뜻한다. 예를 들어 ‘실패 결과를 잘못 기록하는 하네스 버그’를 고친다면 모듈 개발자가 원본에서 수정, 시험해 새 버전을 배포하고, 사용하는 프로젝트는 갱신을 요청할 때 그 수정을 받아온다. 반면 해당 프로젝트의 검사 명령이나 요구사항이 바뀐 경우에는 그 프로젝트의 설정, WIKI를 수정한다.

**‘적용본의 공통 코드를 임시 수정’은 사용자가 설치된 하네스 파일을 직접 고친 경우를 가리킨 이전 표현**이다. 사용자 커스터마이징은 계속 유지할 수 있으며 ‘임시’로만 허용하거나 공식 원본 반영을 의무로 두지 않는다. 유지보수자가 공식 개선으로 받아들이기로 한 변경만 원본에서 별도 검토, 시험, 배포한다. 그 여부와 관계없이 사용자 편집은 보존하고, 새 배포와 함께 바뀌었다면 아래 충돌 절차로 처리한다.


## skill과 hook의 업데이트

우리 배포물의 공통 기능에는 실행 프로그램뿐 아니라 기본 skill의 절차, hook 처리 코드와 필요한 연결 템플릿도 포함된다. **실행 프로그램만 갱신하고 프로젝트에 복사된 옛 skill 절차를 방치하면 기능 개선이 일부만 반영될 수 있다.** 선택 기능의 script, skill, hook, 설정을 하나의 의존 관계로 검사해야 한다. 아래는 채택한 프로젝트 소유 경계의 갱신 후보이며 상세 자동화는 미채택, 미구현이다.

일반적인 프로젝트 차이는 검사 명령, 경로, 정책 입력으로 분리해 공통 절차를 그대로 사용하도록 추천한다. AI용 skill은 필요한 프로젝트 입력을 실제로 읽도록 연결한다. 프로젝트에서 절차를 바꾸면 설치된 skill, 처리 코드를 직접 수정할 수 있다. 설정으로 표현되는 값은 분리해 변경 지점을 줄이되 모든 수정을 설정만으로 제한하지 않는다. 임의 수정도 보존하지만 그 경우 모든 새 배포를 무인 적용할 수 있다고 보장하지 않는다.

| 업데이트 대상 | 반영 후보와 한계 |
| --- | --- |
| 공통 skill 절차, 실행 코드, hook 처리 코드 | 새 배포본으로 프로젝트 파일의 후보를 만들고 이전 기준, 현재 편집과 대조. 연관 skill, script, hook, 설정을 함께 검증한 뒤 해당 프로젝트에 적용 |
| 설치기가 만든 프로젝트 진입 파일, hook 연결 항목 | 이전 설치 기준과 현재 내용을 대조해 확인된 소유 범위만 갱신. 기존 항목을 무조건 추가하는 대신 교체/유지/제거 계획을 만들며 사용자 항목은 보존 |
| 프로젝트 설정, 추가 규칙, 전용 스크립트 | 기본 보존. 새 공통 기능과의 호환성 검사 대상이며, 입력 규격 변경이 필요하면 이전 후보를 별도로 제시 |
| 사용자가 수정한 생성 skill, 연결 항목과 새 템플릿의 변경이 겹침 | 이전 생성본, 현재 수정본, 새 생성 후보를 비교. 의미가 불명확하면 해당 갱신 묶음을 적용하지 않고 조정 후보를 제시 |
| WIKI 본문, 요구사항, ADR | 공통 업데이트로 재작성하지 않음. 문서 내용 보강은 별도 WIKI 작업 |

예를 들어 프로젝트가 정한 검사 명령을 그대로 두고 공통 실패 처리만 개선하는 업데이트는 공통 배포본과 필요한 연결의 갱신으로 끝낼 수 있다. 반면 사용자가 skill에서 정한 ‘특정 검사는 생략’과 새 공통 절차의 ‘그 검사는 필수’가 충돌하면 문법상 병합에 성공해도 정책 판단이 필요하다. AI는 근거, 차이, 조정 후보를 제시할 수 있으나 임의로 우선순위를 정하지 않는다. 프로젝트 전용 skill을 유지해 일부 개선을 적용하지 못했다면 그 제한을 표시하고, 필수 기능, 호환 조건을 충족하지 못하면 새 버전 완료로 기록하지 않는다.

‘코어만 변경’은 **프로젝트 지식, 고유 정책을 의도 없이 바꾸지 않는다**는 목표로 해석한다. 호환되는 변경은 공통 부분 중심으로 반영할 수 있지만, 항상 프로젝트 파일을 한 바이트도 바꾸지 않는다는 뜻은 아니다. 공통 함수의 입력이나 hook 연결 규격이 바뀌면 연결, 설정을 함께 이전해야 한다. 안전한 이전을 준비하지 못하면 기존 구성을 유지하고 업데이트를 보류한다.

중복 방지는 파일명만으로 판단하지 않는다. 설치 기록과 실제 활성 출처를 함께 대조해 같은 기능의 옛 연결이 새 연결과 동시에 남지 않는지 확인한다. [Codex skills](https://learn.chatgpt.com/docs/build-skills)는 같은 이름을 자동 병합하지 않고, [hooks](https://learn.chatgpt.com/docs/hooks)는 여러 출처를 함께 읽는다. hook 정의가 바뀌면 신뢰 재확인이 필요할 수 있으므로 파일 반영, 활성화, 실제 동작 확인을 나누며 필요한 사용자 조작을 숨기지 않는다. 지원 클라이언트가 재시작/재로드를 요구하면 그 뒤의 동작까지 확인한다.

첫 구현은 정상, 호환 범위의 자동 반영과 충돌 시 원문 보존, 중단에 집중하는 것을 추천한다. 모든 사용자 편집을 자동 의미 병합하는 기능은 추가하지 않는다. 비교, 적용, 복원의 구체 순서는 아래 절을 따르고, 같은 업데이트 재실행 시 추가 변경/중복 등록 없음, 사용자 편집 보존, 설정 이전 필요, 옛 skill만 남는 불완전 갱신, 중간 실패 복원을 검증한다. 아직 이 제품의 업데이트 시험을 통과한 것은 아니다.


## 버전 확인과 실행 도구

설치와 업데이트는 같은 관리 도구가 제공한다. 11/11 Git 릴리스의 Python 도구를 프로젝트 밖에 준비해 실행하는 수단을 채택했다. 배포 사본은 재사용하거나 더 이상 필요 없을 때 정리할 수 있으며 별도 업데이트 프로그램을 프로젝트마다 복사하지 않는다. 도구 자체를 새 버전으로 교체할 때도 프로젝트 변경은 별도 적용 절차를 거친다. 정확한 진입 명령, 사본 보관 위치는 후속 명세에서 정하고 첫 배포에 패키지 관리자나 자기 갱신 경로까지 병행 구현하지 않는다.

아래는 사용 흐름을 설명하는 **가상 명령**이다. 실제 설치 가능한 명령이나 확정 인터페이스가 아니다.

```text
<도구> install          최초 설치 계획과 차이를 확인한 뒤 적용
<도구> update --check   현재/제공 버전, 호환 조건, 변경 안내만 조회
<도구> update           적용할 버전과 변경 계획 확인 후 갱신
```

관리 도구는 프로젝트 밖에 있고 일상 실행 파일은 프로젝트에 남는다. 관리 도구 자체의 갱신과 프로젝트 하네스의 갱신은 별개이며 도구만 업그레이드해 여러 프로젝트를 자동 변경하지 않는다. 갱신 담당자가 설치된 파일, 선택 기능, 설치 기준의 변경을 준비해 팀의 검토/공유 절차를 따른다. 다른 팀원은 반영된 결과와 필요한 기기 조건만 준비하며 갱신 절차를 반복하지 않는다. 기준의 [보관과 소비 — 「설치 기록과 단계 연결」](install.md)는 관리 작업을 위한 것이며 일반 개발의 선행 읽기 조건이 아니다.

버전 조회는 일반 코드의 메타데이터 요청이며 모델 추론이 필요 없다. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)는 공개 릴리스 조회에 인증을 필수로 요구하지 않지만 [요청 제한](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)이 있다. Git 릴리스 + Python 제공 수단은 채택됐으며, 이 API의 구체 사용, 인증, 호환 버전 선택 규칙은 후속 명세다. AI 세션이 명령, 출력을 읽는 대화 비용까지 없어지는 뜻도 아니다.

조회에는 제한된 대기, 재시도와 확인 시각을 두고, ‘신버전 없음’, ‘호환 가능한 신버전 있음’, ‘더 최신 버전은 있으나 환경/이전 절차 필요’, ‘조회 실패’를 구분한다. 원격의 latest를 지원 환경의 최신 호환 버전으로 간주하지 않는다. 필수 의존성이 없거나 관리 도구가 새 규격을 이해하지 못하면 준비 방법을 안내하고 적용을 멈춘다. 네트워크 실패로 기존 동작을 바꾸거나 검사 실패를 최신 상태/PASS로 표시하지 않는다.

자동 적용보다 **명시적 조회 → 변경 요약, 이전 조건 확인 → 요청한 갱신**을 기본 후보로 추천한다. 무인 적용은 별도 조건을 검증한 후속 범위다. 단순 버전 조회가 AI 실행, 환경 업그레이드, 전체 WIKI 분석을 시작하지 않도록 한다. 같은 버전 조회 결과만으로 현재 설치의 정상 동작을 검증했다고 보지도 않는다.


11/18 명령 연결: [사용 단계별 호출 — 「설치부터 관리까지의 호출 순서」](entry.md)에서 갱신은 외부 관리 도구가 담당한다. 관리 도구를 정리했으면 지원되는 고정 배포본을 다시 확보하고, 중단된 갱신이 있으면 그 요청과 대상 버전을 먼저 식별한다. 이어가기 위해 다른 최신 버전의 새 업데이트를 시작하지 않는다. 배포본 변경이 필요하면 기존 이력/형식을 읽을 수 있는지 확인한 뒤 계획 변경으로 다룬다. 프로젝트의 세션 `resume`을 업데이트 재시도 명령으로 사용하지 않는다.

갱신 결과에는 현재 사용 가능한 구성과 미확인 범위, 다음 조치가 함께 표시돼야 한다. 실패 뒤 ‘이전 구성 사용’ 선택은 아래 복원/검증을 실행하는 요청이고 단순 종료가 아니다. 해당 선택과 정리 확인을 입력 없이 추정하거나, 외부 도구의 성공 종료를 프로젝트 전체의 갱신 완료로 간주하지 않는다. 구체 반환과 도움 안내는 [명령 입력과 결과 안내](entry.md)를 따르며 이 문서에서 별도 종료 코드 체계를 만들지 않는다.

## 변경분과 충돌의 판정

비교 대상은 **이전 설치 당시 배포 기준, 현재 실제 파일, 새 버전으로 만들 후보**다. [설치 기록과 단계 연결](install.md)에 공유를 권장하는 설치 기준과 로컬 실행 자료의 파일/소비 초안을 뒀다. 정확한 파일명, 필드와 저장 수단은 후속 명세에서 정하고 기기별 절대 경로, 비밀값을 공유 기록에 넣지 않는다. 기준 본문은 고정 배포물, 당시 생성 설정 또는 보존한 기준 사본으로 확보해야 하며 해시만으로 복원하지 않는다. 기준을 확보할 수 없으면 해당 갱신 반영을 보류한다. 최초 설치처럼 강제 덮거나 일반 하네스 실행 전체를 막는 근거로 사용하지 않는다.

사용자가 제안한 ‘공식 버전 사이 변경을 사용자 수정과 충돌하지 않는 범위에서 적용’은 이 **3방향 비교, 병합(three-way merge)**으로 구체화할 수 있다. [Git merge-file](https://git-scm.com/docs/git-merge-file)은 공통 기준본과 양쪽 변경본을 받아 병합하고 겹친 변경을 충돌로 표시하는 기능을 제공한다. Git 저장소 전체를 병합하거나 제품에 이 명령을 바로 채택한다는 뜻은 아니다. 우리에게는 설치기가 관리하는 파일/항목의 원문 밖 후보 작성 수단이며, 자동 반영 범위는 별도 검증, 합의 대상이다.

| 비교 자료 | 준비할 내용 |
| --- | --- |
| 이전 기준본 | 이전 공식 배포본과 당시 프로젝트 입력으로 생성한 결과. 프로젝트 값을 채운 파일이라면 배포 템플릿 원문과 구분 |
| 현재 파일 | 그 뒤 사용자, AI가 수정한 실제 파일. 미커밋, 비추적 변경도 포함 |
| 새 기준 후보 | 새 공식 배포본과 정한 프로젝트 입력/이전 규칙으로 만든 결과. 사용자 수정본을 먼저 덮지 않음 |

이전 기준본→현재 파일에서 사용자 변경을, 이전 기준본→새 후보에서 공식 개선과 명시한 설정 이전을 구분한다. AI 분석이 포함돼 같은 입력으로 동일 본문을 재생성할 수 없다면 당시 생성 기준 사본을 보존해야 한다. 새 템플릿을 다시 AI에 채우게 한 결과를 과거 기준본으로 간주하지 않는다.

11/11 질문의 ‘사용자가 추가, 변경한 부분은 업데이트하지 않는다’는 **사용자 편집을 자동 덮어쓰지 않는다는 조건**으로 설명한다. 사용자가 손댄 파일 전체를 영구 동결하면 그 파일의 다른 부분에 필요한 공식 수정도 받을 수 없다. 별도 사용자 파일은 쓰기 대상에서 제외하고, 모듈 설치 파일 안의 편집은 나머지 공식 변경과 함께 비교한다. 같은 줄뿐 아니라 설정/호출 관계가 충돌해도 해당 갱신 묶음을 보류하며, 아무 파일도 충돌 없이 항상 자동 갱신된다는 보장은 하지 않는다.

검증 수준도 구분한다. [11/10 Git/Python 예제](../../evidence/experiments/runtime/2026-11-10_17-07-48-external-install.md)에서 사용자 변경 보존, 연속 갱신, 텍스트/의미 충돌 차단, 부분 실패 복원을 실제로 시험했다. 이는 비교 방식의 좁은 실행 근거이며 **이번 프로젝트 내 배치에서 실제 AGENTS, skill, hook 전체를 갱신한 제품 검증은 아니다.** 전용 폴더가 있어도 그 안의 사용자 파일 보호, 새 clone의 기준 복원, 호환성 검증은 남는다.

버전은 각 skill, hook의 코드 주석에 반복해서 쓰기보다 **설치 정보 한 곳**에 공식 릴리스와 고정 revision/무결성 정보를 기록하는 후보를 유지한다. 관리 파일, 구간과 생성 기준을 연결하고 원문 비교에 필요한 내용을 확보한다. 주석의 버전 문자열이나 해시만으로 사용자 변경의 위치, 의미를 알아낼 수는 없다. 이는 공식 배포 출처이며 사용자 수정에 별도 모듈 버전을 부여하지 않는다. 공유할 비밀 없는 설치 정보와 로컬 후보/복구 사본은 분리하고 기존 Git 추적 정책을 보존한다.

프로젝트 설치 파일, 공유 설정 항목, 설치 기준을 같은 갱신 묶음으로 검토한다. 새 기준 본문은 사용자 편집이 섞인 최종 파일과 분리해 확보하고, 팀의 새 clone에서도 접근 가능한 비밀 없는 범위로 관리한다. 실패 시 옛 코드뿐 아니라 함께 바꾼 연결, 설정, 기준까지 맞춰야 하며 뒤에 생긴 사용자 편집을 덮지 않는다.

| 현재 상태와 새 배포의 관계 | 처리 후보 |
| --- | --- |
| 공통 파일이 이전 기준 그대로이고 새 배포만 바뀜 | 허용된 갱신 계획에 포함 |
| 사용자가 바꿨고 배포 내용은 그대로 | 사용자 변경 보존. 새 구성과의 호환성은 별도 확인 |
| 사용자와 배포 양쪽에서 바뀌었지만 텍스트 병합이 가능함 | 사용자 변경을 보존한 별도 후보 생성 가능. 양쪽 변경만으로 영구 충돌이라 단정하지 않되 규격, 정책, 연결 검증 전 원문 적용은 보류 |
| 양쪽 변경이 겹치거나 정책/동작이 충돌함 | 차이, 근거, 조정 후보를 제시하고 해당 갱신 묶음 중단. 사용자/공식 변경 한쪽을 자동 우선하거나 AI 의미 병합을 확정하지 않음 |
| 새 파일 이름에 이미 다른 자료가 존재 | 같은 이름만으로 소유를 주장하지 않고 중단 |
| 사용자가 기존 파일을 삭제/이동함 | 자동 재생성하지 않고 의도, 필수 연결 확인 |
| 새 배포가 기존 공통 파일을 제거함 | 모듈 소유, 미편집, 유입 연결 정리를 확인한 경우에만 제거 계획에 포함 |
| 기존 AGENTS, 공유 hook 설정, Git 제외 규칙 | 확인된 관리 구간/설정 항목만 변경 후보로 만들고 다른 규칙 보존 |
| 프로젝트 WIKI 본문, ADR, 위치표의 프로젝트별 분류 | 공통 템플릿으로 덮거나 재분류하지 않음. 필요한 규격 이전은 별도 후보 |

‘변경된 것만 적용’은 가능하지만 서로 의존하는 script, 설정, hook, 문서 연결을 임의로 골라 혼합 버전으로 만드는 뜻은 아니다. 선택한 기능과 의존성을 만족하는 묶음으로 계획, 검증하고 모두 확인돼야 해당 버전의 적용 완료를 기록한다. 내려받을 때 릴리스 전체를 받더라도 실제 쓰기는 필요한 변경에 한정할 수 있으며, 별도의 차분 다운로드 시스템까지 만들 필요는 없다.

갱신 완료 뒤 다음 비교의 기준은 **새 공식 배포/정한 입력으로 만든 기준본**이다. 사용자 수정까지 섞인 최종 파일을 공식 기준본으로 바꾸면 다음 갱신에서 그 사용자 변경을 구별하지 못한다. 새 기준본과 실제 반영 결과를 구분해 기록하고, 충돌, 부분 실패가 남은 단위를 완료된 새 기준으로 표시하지 않는다. 독립 단위를 나눌 때의 기록은 [부분 완료 — 「적용 단위와 부분 완료」](update.md#%EC%A0%81%EC%9A%A9%20%EB%8B%A8%EC%9C%84%EC%99%80%20%EB%B6%80%EB%B6%84%20%EC%99%84%EB%A3%8C)를 따른다. 후속 갱신에서도 사용자 변경이 유지되는지 연속 두 번의 업데이트로 확인한다.

새 문서 템플릿은 이후 작성할 문서에 적용할 수 있다. 기존 본문 재작성이나 위치표 규격 변경이 꼭 필요하면 원문을 보존한 이전 후보, 차이, 복원 조건을 따로 제시한다. 미선택 기능 추가나 문서 폴더 재분류를 조용히 끼워 넣지 않는다. [Copier 갱신](https://copier.readthedocs.io/en/stable/updating/)도 이전 생성본과 사용자 차이를 다루며 충돌과 복구 제약을 설명한다. 이는 비교 방식의 근거이며 Copier 도입이나 우리 원문 보존의 검증 결과는 아니다.


## 적용 단위와 부분 완료

11/11 사용자 질문으로 복원의 범위를 보강하고 **독립 완료 유지, 실패 보고/단위 복원, 합의 후 해결/재개 원칙을 채택했다.** 이전 초안의 ‘적용한 묶음’은 프로젝트 전체나 과거 작업 전체를 뜻하지 않았으나, 완료한 별도 묶음의 보존과 실패 이후 실행을 충분히 구분하지 못했다. **완료한 것을 유지할지, 실패한 부분을 어떻게 복구할지, 아직 시작하지 않은 부분도 계속 실행할지**는 서로 다른 판단이다. 정확한 단위 목록, 기록, 실제 동작 검증은 후속이며 제품은 미구현이다.

적용 단위는 함께 검증, 활성화, 복구해야 하는 파일과 설정 항목의 묶음이다. 예를 들어 한 검사 기능의 skill, 호출 script, 입력 설정은 파일 세 개여도 한 단위가 될 수 있다. 그중 skill 쓰기만 성공한 것은 기능 완료가 아니다. 폴더명, 파일 수나 실행 순서만으로 독립성을 정하지 않으며, 공유 진입점, 규격 변경과 기존/새 구성 사이 호환성도 확인한다. 분리할 근거가 없으면 큰 한 단위로 다루고, 그 단위 전체가 복구 대상이 될 수 있다.

| 범위, 진행 방식 | 이점 | 비용, 제한 |
| --- | --- | --- |
| 이번 요청 전체를 한 단위로 복원 | 적용 상태와 기준이 단순함 | 서로 독립적으로 완료한 변경도 다시 해야 할 수 있음 |
| 완료한 독립 단위 유지 + 실패한 단위 복구 + 남은 적용 일시 중단 — 원칙 채택 | 검증된 결과를 지키면서 실패 확산과 재작업을 줄임 | 단위 경계, 완료 기록, 호환성 검증이 필요. 남은 독립 작업도 확인 후 재개 |
| 위 보존/복구 후, 실패와 무관한 나머지 단위까지 자동 실행 | 같은 실행에서 가능한 작업을 더 끝냄 | 실패의 영향 범위, 공통 장애, 새 입력 변화까지 판단해야 함. 첫 기본 동작으로는 보류 추천 |

채택한 방식에서는 계획 때 단위, 선행 조건, 완료 검증을 정하고 순차 적용한다. 실패를 감지하면 새 적용을 멈추고 실패 지점, 완료한 독립 단위, 부분 변경, 영향과 복구 가능 여부를 즉시 보고한다. 검증이 끝난 독립 단위는 유지하며, 실패한 단위의 이번 변경만 아래의 사전 허용 조건으로 복원하고 결과를 보고한다. 원인 수정, 선택 변경, 남은 독립/의존 단위의 진행은 사용자와 범위를 확인한 뒤 같은 계획에서 재개한다. 이전 PASS는 입력과 직접 의존이 그대로인 경우에만 재사용한다. 사용자는 완료한 작업을 다시 처음부터 수행하거나 같은 해결 범위의 기계적 단계를 반복 승인할 필요가 없다.

사전 점검으로 알 수 있는 충돌, 의존성 부재는 쓰기 전에 알린다. 부분 완료를 남길 수 있다는 이유로 알려진 실패를 안고 적용하지 않는다. 실패가 공통 설정, 복구 기록, 파일시스템 같은 기반의 신뢰를 깨면 ‘다른 기능’이라는 이유로 계속하지 않는다. 앞서 끝낸 단위도 유효성을 잃으면 완료 주장을 보류하고 영향 범위를 다시 판단한다. 모르는 범위를 자동으로 되돌리거나 정상으로 숨기지 않는다.

11/12 보강: 의존성 부재로 멈췄다면 [의존성 준비와 설치 재개](install.md)에 따라 사용자가 준비한 뒤 같은 계획을 재실행한다. 완료 기록과 현재 입력/결과의 유효성을 확인해 유지하며, 새 범위, 후속 편집, 불확실한 효과까지 무조건 계속하는 허가로 확대하지 않는다.

완료 단위의 실제 반영 내용, 공식 출처, 비교 기준과 실패/미착수 단위를 구분해 남긴다. 공식 릴리스는 하나이며 사용자별 공식 버전이나 skill별 버전명을 만드는 뜻이 아니다. 요청 전체가 끝나기 전에는 새 릴리스 적용 완료로 표시하지 않는다. 재개 시 이미 적용한 공식 변경을 사용자 편집으로 오인하거나 중복 적용하지 않아야 한다. 첫 구현은 확인한 단위와 선행 조건만 사용하며 임의 프로젝트를 AI가 추측해 분할하는 범용 실행기를 선행 구현하지 않는다. 정확한 단위, 기록 형식은 파일별 명세에서 정한다.

공식 도구도 실패 처리가 하나로 같지는 않다. [CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/stack-failure-options.html)은 성공 자원 보존을 선택하면 실패한 의존 경로를 멈추고 독립 경로는 계속 진행한다. [Terraform apply](https://developer.hashicorp.com/terraform/cli/commands/apply)는 부분 변경을 상태에 기록하고 오류로 종료하며 자동으로 전체를 롤백하지 않는다. 이는 완료 보존과 자동 계속 실행을 구분할 근거이지, 파일 기반 하네스가 같은 안전성을 이미 갖췄다는 증거는 아니다. 위 추천은 첫 배포 기한과 우리 보존, 검증 부담을 고려한 판단이다.

이 절은 **설치와 갱신의 파일 반영**에 관한 것이다. WIKI 역공학의 분석 결과, 근거, 완료 범위는 [WIKI의 범위별 완료 판정](../knowledge/wiki.md)을 따른다. 뒤 분석이 멈췄다는 이유로 앞서 유효하게 완료한 WIKI나 분석 후보를 모두 삭제하는 정책으로 확대하지 않는다.


### 업데이트 실패 후 선택

11/16 사용자는 대응 방법의 사전 안내와 업데이트 중단 후 기존 구성의 사용을 요구했다. 이어 **실패 단위 복원/검증 → 원인과 재시도 조건 확인 → 재시도 또는 이전 구성 사용 선택**을 채택했으며, 이전 구성 선택 시 성공한 단위를 포함해 이번 업데이트의 변경 전체를 복원하는 범위도 확인했다. [ADR 0011 — 「업데이트 중단 후 선택」](../../decisions/runtime/0011-preservation.md)에 기존 원칙과의 관계를 남긴다. 안내의 노출 위치는 [실행 전 안내와 중단 시 도움](install.md)이 소유한다. 제품 구현이나 무중단 보장은 아니다.

진행 중 완료한 단위를 보존하는 것은 재시도 때 유효한 작업을 다시 하지 않기 위한 것이다. 실패한 필수 변경을 제외하고 되는 부분만 사용하게 하거나, 부분 상태를 새 릴리스 또는 이전 전체 구성으로 표시하는 뜻이 아니다. 요청한 선택 기능과 필수 의존 관계를 모두 검증한 뒤에만 새 버전 사용을 안내한다. 영향받는 구성의 실행 제한과 사용 중 파일 보호는 [실행 중인 구성의 갱신](update.md#%EC%8B%A4%ED%96%89%20%EC%A4%91%EC%9D%B8%20%EA%B5%AC%EC%84%B1%EC%9D%98%20%EA%B0%B1%EC%8B%A0)을 따른다.

채택한 흐름은 다음과 같다.

1. 실패 지점과 현재 상태를 보고하고 새 반영을 멈춘다. 기존에 허용한 안전 조건을 충족할 때 실패 단위의 이번 변경을 복원한다. 강제 종료 뒤나 다른 편집이 있는 경우에는 기존 복원 확인 절차를 따르며, 복원 자체가 실패하면 그 사실부터 해결한다.
2. 복원 결과와 재시도에 필요한 원인/환경을 확인한다. 도구/권한/공간/사용 중 파일, 사용자 변경과의 충돌, 공식 배포 결함을 구별하고 필요한 조치를 제시한다. 자동으로 환경을 변경하거나 같은 실패를 무한 재시도하지 않는다. 확인은 알려진 방해 조건을 제거했는지의 판단이며 성공 보증이 아니다.
3. 현재 가능한 선택과 영향을 보여준다. 사용자의 재시도 또는 기존 구성 복원 선택을 받으며, 필요한 정보가 없으면 중단 상태와 자료를 보존한다. 사용자나 AI가 조정한 입력은 변경 계획에 반영하고 관련 검증을 다시 수행한다.

| 선택 | 반영/검증할 범위 | 완료와 사용 안내 |
| --- | --- | --- |
| 문제를 해결하고 업데이트 재시도 | 같은 요청의 유효한 완료는 재사용하고 실패/미착수와 영향받은 의존을 처리. 대상 버전이나 범위를 바꾸면 후속 계획으로 연결 | 요청한 구성 전체와 통합 조건이 통과한 뒤 새 버전 사용 안내 |
| 업데이트를 그만두고 이전 구성 사용 | **이번 업데이트가 이미 반영한 모든 변경**을 요청 시작 직전 상태로 되돌릴 계획. 성공한 단위의 변경도 포함하며 실패 단위만 복원한 상태로 끝내지 않음 | 관련 파일/설정/연결/설치 기준과 실제 기존 기능을 확인한 뒤 기존 구성 사용 안내. 업데이트 완료로 표시하지 않음 |
| 지금 선택하거나 안전하게 복원할 수 없음 | 사본, 후보와 실행 기록 보존. 미완료인 영향 기능의 사용 제한과 필요한 조치를 표시 | 기존 또는 새 구성이 정상이라는 안내 금지. 후속 재개로 연결 |

여기서 이전 구성은 사용자의 편집을 포함한 **이번 업데이트 직전 프로젝트 설치 상태**다. 옛 공식 배포본을 다시 복사하거나 Git HEAD로 전체 프로젝트를 되돌리는 방식이 아니다. 이번 도구가 바꾼 항목만 의존 관계에 맞게 복원하고, 중단 후 생긴 사용자 편집과 무관한 코드/WIKI/index는 보존한다. 공유 파일은 항목별 변경을 대조한다. 복원 순서, 기존 실행과 DB 형식의 호환성도 검증해야 하며, SQLite rollback 하나로 파일/호스트 상태를 되돌릴 수 있다고 가정하지 않는다. 실행 이력은 지우지 않고 복원 시도와 실제 결과를 연결한다.

[DB 형식과 이전 구성의 호환](../workflow/storage.md)은 이 선택을 위한 반영 전 조건이다. 파일을 되돌려도 기존 코드가 남아 있는 DB를 읽고 쓸 수 없다면 이전 구성을 정상으로 표시하지 않는다. 새 이력을 지우지 않는 호환/변환 경로가 없으면 해당 업데이트를 적용 전에 보류한다. 정확한 저장 필드와 실제 역변환/사용 검증은 후속이다.

기존 원칙에 추가한 부분은 **사용자가 업데이트를 포기했을 때, 앞서 성공한 단위의 이번 변경까지 명시적으로 복원하는 것**이다. 재시도 준비/대기 중에는 유효한 완료를 유지하고, 이전 구성 사용을 선택한 뒤에는 그 요청의 복원 범위에 포함한다. 실패 즉시 프로젝트 전체를 자동 복원하거나 모든 개발 이력을 되돌리는 정책은 아니다. 정확한 복원 순서와 진입 제어, 결과 안내는 구현/검증 대상이다. 최초 설치에는 기존 구성이 없을 수 있으므로 같은 선택지를 무조건 표시하지 않는다.

반영 전 취소/충돌이면 기존 파일을 유지한다. 일부 반영 뒤에는 복원과 실제 사용 확인이 필요하므로 강제 종료 직후부터 기존 구성이 항상 동작한다고 약속하지 않는다. 복원 실패나 손상으로 사용을 재개할 수 없다면 사용 불가/미확인 범위와 다음 조치를 드러내고 자료를 보존한다. 언제나 즉시 이전 전체 구성을 사용할 요구가 추가되면 별도 배치/전환 방식과 비용을 다시 비교해야 한다.

[CloudFormation의 실패 선택](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/stack-failure-options.html)도 성공한 자원을 유지한 상태에서 재시도, 수정 후 실행 또는 이전 안정 상태로의 복원을 구분한다. 이 구별을 참고하되 자원 병렬 실행이나 해당 서비스의 보장을 가져오는 것은 아니다. [복원 실패 안내](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-continueupdaterollback.html)는 복원 자체도 해결이 필요할 수 있음을 보여준다. 실패 자원을 건너뛰어 완료시키는 기능은 우리 추천에 포함하지 않는다.

## 적용 순서와 실패 처리

아래는 채택한 보존/복구 원칙의 **후속 구현 명세를 위한 처리 흐름**이다. [적용 단위와 부분 완료](update.md#%EC%A0%81%EC%9A%A9%20%EB%8B%A8%EC%9C%84%EC%99%80%20%EB%B6%80%EB%B6%84%20%EC%99%84%EB%A3%8C)로 범위를 나누고 [실패 뒤 복구 방식](update.md#%EC%8B%A4%ED%8C%A8%20%EB%92%A4%20%EB%B3%B5%EA%B5%AC%20%EB%B0%A9%EC%8B%9D)을 그 단위 안에 적용한다. 비교 기준은 팀이 사용할 비밀 없는 설치 기록에서 확보하고, 해당 단위의 적용 직전 사본, 후보, 반영 진척은 로컬 `.harness/`에서 관리한다. 로컬 자료는 [제외 준비 — 「제외 규칙의 자동 설정」](../workflow/recovery.md)를 확인한 뒤 기록하며 정확한 저장/잠금, 제품 구현, 실사용 검증은 아직이다.

**업데이트 비교는 이전 공식 기준, 실패 복원은 적용 직전의 실제 상태를 사용한다.** 복원에는 사용자의 미커밋 수정도 포함하며 옛 배포본이나 Git HEAD로 대신하지 않는다. [Git restore](https://git-scm.com/docs/git-restore)는 지정한 출처의 상태로 경로를 돌리는 명령이므로 그 출처가 이번 적용 직전 상태인지 별도로 확보해야 한다. 설치 복구가 사용자의 staged 상태, 무관한 파일, 다른 작업을 바꾸거나 저장소 전체를 reset/clean하는 방식은 제외한다.

| 상황 | 원문과 적용 상태 | 다음 처리, 완료 조건 |
| --- | --- | --- |
| 정상 후보 | 이전 기준, 현재 편집, 새 배포를 대조하고 의존 관계를 만족하는 후보만 적용 | 실제 연결, 기존 기능, 보호 자료를 확인한 뒤 설치 기준과 완료 상태 갱신 |
| 충돌 또는 계획 뒤 편집 | 해당 묶음은 적용 전에 멈추고 원문, 기존 기준 유지 | 차이와 후보 보존. 충돌 조정 또는 입력 재확인 뒤 영향받은 검증부터 수행 |
| 이전 기준 부재 | 현재 파일을 공식 기준으로 간주하거나 새 배포로 덮지 않음 | 보존 기준 또는 고정 출처/입력으로 정확한 기준 확보. 불가능하면 자동 갱신 보류, 별도 채택/이전 계획 필요 |
| 일부 반영 뒤 오류, 중단 또는 검증 실패 | 실패한 단위는 일부가 바뀌었을 수 있어 원문 유지, 갱신 완료로 표시하지 않음. 남은 적용과 영향 기능 실행 보류 | 아래 정책으로 실패 단위를 복구하고, 앞서 검증한 독립 단위는 유효성을 확인해 유지. 각각의 코드, 연결, 설정, 기준과 전체 미완료 상태 대조 |
| 복구 전에 사용자 후속 편집 | 이번 작업이 쓴 상태와 다르면 자동 덮어쓰기 복원을 중단 | 새 편집과 복구 후보를 함께 보존하고 차이를 해결. 되돌릴 수 없는 부분이 남으면 복구 완료로 표시하지 않음 |

같은 명령의 재실행은 완료된 파일/등록을 중복 생성하거나 미완료 기록을 새 작업으로 덮지 않아야 한다. 적용/복원 중에는 영향받는 하네스 기능을 실행하지 않는 조건이 필요하다. 미완료 표시 파일만으로 기존 hook, 직접 script 호출이 실제 차단된다고 주장하지 않는다. 실제 진입점의 검사와 동시 쓰기 방지는 후속 명세, 검증 대상이며, 확인할 수 없는 상태에서 적용을 강행하지 않는다. CI/AI 세션 전체를 임의로 중단하는 정책으로 확대하지 않는다.

1. 대상 프로젝트, WIKI, 현재 설치 기준, 선택 기능과 새 버전의 지원 조건을 확인한다. 허용된 변경 범위, 의존성, 필요한 규격 이전을 미리 계산한다.
2. 원문 밖에서 후보와 생성/변경/삭제/보존/충돌 목록을 만든다. 충돌을 풀지 못하면 해당 갱신 묶음을 적용하지 않는다. 사용자는 변경 내용과 필요한 선택을 확인할 수 있어야 한다.
3. 허용 범위의 적용 직전 내용, 경로 존재 여부와 필요한 파일 속성을 보존하고 원본을 재대조한다. 복구 정보가 충분하지 않으면 쓰기를 시작하지 않는다. 다른 실행/편집이 없는 조건과 부분 반영 기록은 [동시 편집과 반영](install.md)의 계약을 따른다.
4. 허용한 변경을 반영하고 경로, 역할, 규격, 도구의 실제 로드, 관련 기존 기능을 확인한다. 검증 실패나 부분 적용이면 새 버전 완료, 해당 후속 실행을 보류한다.
5. 해당 단위가 모두 통과하면 실제 반영, 비교 기준을 기록하고, 선택한 전체 단위와 통합 확인이 끝나야 새 릴리스 적용 완료로 표시한다. 관련 파일이 다른 브랜치 변경과 섞이지 않게 검토 가능한 변경 묶음으로 남긴다. 자동 commit, push, PR 승인까지 포함하는 기능으로 확대하지 않는다.
6. 실패 시 아래 정책으로 실패 단위의 변경부터 복구한다. **완료한 단위, 복구한 단위, 보류/미착수 단위**를 따로 보고하며 복원 성공을 전체 설치 성공으로 바꾸지 않는다. 이어 [실패 후 선택 — 「업데이트 실패 후 선택」](update.md#%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8%20%EC%8B%A4%ED%8C%A8%20%ED%9B%84%20%EC%84%A0%ED%83%9D)을 적용하고, 이전 구성 사용을 선택했다면 이번 업데이트의 성공한 변경도 복원 범위에 포함한다. 옛 실행 파일만 되돌리는 것과 변환된 설정/상태까지 복구하는 것은 다르며, 복구 불가능한 변경을 자동 적용에 포함하지 않는다. 확인이 끝나기 전 복구 자료를 정리하지 않는다.

첫 배포의 목표는 모든 미래 충돌, 누락, 버그가 없다는 보장이 아니라, **허용하지 않은 변경을 하지 않고, 알려진 충돌, 불완전 적용을 감지하며, 검증하지 못한 상태를 성공으로 표시하지 않는 것**이다. 실제 지원 환경의 실패 주입, 복원 시험으로 이 조건을 확인해야 한다. 여러 파일 전체와 두 저장소의 갱신은 원자적이지 않으며 앱/WIKI 작업 연계는 [기존 작업 단위 계약](../../decisions/integration/0017-work-sync.md)을 따른다.


## 파일 반영과 핸들 수명

11/16의 **Windows 우선 검증 후보**다. 기존 사용자 편집 보존 계약을 파일 처리에 연결하며 API의 최종 채택이나 실제 안전성 통과가 아니다. 설치/갱신의 텍스트 파일, 공유 설정, `.gitignore`에 적용할 후보이고, WIKI 후보와 active를 저장할 때도 필요한 파일 보호 부분을 재사용한다. WIKI의 분석 완료 정책을 설치 복원 정책으로 바꾸지 않는다. SQLite DB는 엔진이 저장하므로 아래 방법으로 DB 파일을 직접 고치지 않는다.

### 수단 비교와 우선 후보

| 수단 | 이점 | 비용과 판단 |
| --- | --- | --- |
| 완성한 임시 파일로 원본 교체 | 원본에 본문을 조금씩 덮어쓰는 구간을 줄임. 완성본을 준비한 뒤 공개 가능 | 원본 확인과 교체 사이 외부 편집을 별도로 배제해야 함. 기존 파일의 조건부 교체 수단을 검증하기 전 기본으로 확정하지 않음 |
| 원본의 같은 배타적 핸들로 확인하고 쓰기 | 확인한 파일을 닫고 다시 열지 않아 그 사이의 일반 파일 쓰기 경합을 줄임. 기존 사전 보존/반영 기록 사용 | 쓰기 자체는 원자적이지 않아 강제 종료 때 부분 내용이 남을 수 있고 잠깐 다른 읽기도 제한. 우선 검증 후보 |
| 원본을 보존 이름으로 옮긴 뒤 새 파일 생성 | 새 경로에 다른 파일이 생기면 덮지 않고 중단 가능 | 원래 경로가 비는 구간과 이름/복원 관리가 추가됨. 첫 후보로 추천하지 않음 |

[Git의 lockfile 절차](https://git-scm.com/docs/api-lockfile)는 별도 파일에 쓰고 이름을 바꿔 반영한다. 다만 그 잠금 규약을 따르지 않는 편집기까지 차단한다는 뜻은 아니다. 이는 우리 적용에 대한 해석이다. [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)도 기대 원본 해시/ID를 받지 않으며 자체 파일 열기, 같은 볼륨 등의 조건이 있다. 배타적 원본 핸들을 닫은 뒤 호출하면 그 사이의 편집 가능성이 남는다. 일부 실패에서는 파일 배치가 달라질 수 있어 오류를 무변경으로 처리하거나 속성/ACL 보존 오류를 무시하지 않는다.

우선 후보는 외부 편집 보존을 중시한 판단이며 원자적 교체보다 항상 우월하다는 결론이 아니다. 짧은 접근 제한과 중단 복구 부담을 실제 Windows에서 비교한다. 지원 편집기에서 저장 실패가 빈번하거나 복구 조건을 충족하지 못하면 자동 반영을 보류하고 위 대안을 다시 비교한다. 이 단위를 위해 별도 서버, 사용자별 공식 버전이나 새 공유 잠금 폴더를 추가하지 않는다.

### 기존 파일과 새 파일

2026-11-28 구현에서 기존 파일의 보호 읽기만 `oneploom/files.py`에 연결했다. `OPEN_EXISTING`과 공유 모드 0으로 파일을 읽고, 루트부터 부모 디렉토리를 열어 쓰기/삭제 공유를 제한한다. 열린 실제 경로와 종류, 기존 하드 링크를 대조하고 같은 읽기 전용 스트림을 사용한다. 부모를 잡아도 관계없는 자식 파일을 모두 잠그지는 않는다. 정상/오류/프로세스 종료와 실제 경합의 [Windows 관측](../../evidence/experiments/recovery/2026-11-28_20-15-24-file-protection.md)을 남겼다. 아래 쓰기/생성 순서 전체의 구현은 아직이다.

같은 실험에서 **배타적 핸들을 유지해도 새 하드 링크 생성은 가능**했다. 그 링크를 통한 새 쓰기는 보호 중 거부됐지만, 링크 자체의 추가를 막은 것은 아니다. 따라서 최초 링크 수 검사나 공유 모드만으로 이후 쓰기의 영향 경로까지 고정됐다고 판단하지 않는다. 현행 함수는 OS 핸들부터 읽기 전용이며 쓰기 옵션을 제공하지 않는다. 실제 반영 전에 대상의 소유/메타데이터 변경과 파일 교체 대안을 함께 재검토해야 한다. 단순히 쓰기 직전 링크 수를 한 번 더 읽는 것만으로 검사와 쓰기 사이의 경합이 없어졌다고 보지 않는다.

핸들은 운영체제가 열어 준 **그 파일에 대한 접근 참조**다. 경로를 여러 번 다시 여는 대신 확인한 참조를 저장까지 유지한다. 먼저 [실행 소유 — 「실행 소유의 식별과 반환」](../workflow/recovery.md)와 허용된 대상/후보를 대조하고, 후보 생성과 사용자 확인은 파일을 배타적으로 열기 전에 끝낸다.

| 순서 | 기존 파일 | 새 파일 |
| --- | --- | --- |
| 준비 | 예상 원문과 변경 후보 준비. 실제 쓰기 직전 상태의 보존 필요 | 부재를 전제로 한 생성 계획과 검증한 후보를 먼저 기록 |
| 열기와 재대조 | `CreateFileW`의 `OPEN_EXISTING`, 읽기/쓰기 접근, 공유 모드 0 후보. 파일을 먼저 비우지 않고 실제 식별, 내용과 필요한 속성 대조 | `CREATE_NEW`, 공유 모드 0 후보. 이미 생긴 파일은 덮지 않음. 생성 직후 식별 관측과 기록 실패도 미완료로 처리 |
| 쓰기 전 보존 | 같은 핸들에서 확인한 실제 원문과 사전 보존본의 일치, 준비 기록 저장 확인. 실패하면 쓰지 않음 | 새 파일이라는 사실과 시도/대상의 연결 유지. 파일 존재만으로 생성 완료를 기록하지 않음 |
| 쓰기와 확인 | 같은 핸들의 처음 위치부터 후보 바이트 쓰기, 실제 길이 설정, 저장/재읽기 대조 | 같은 절차로 본문을 완성하고 대조. 생성부터 완성까지 한 번에 원자적으로 끝났다고 보지 않음 |
| 관측과 반환 | 실제 결과를 기록한 뒤 핸들 반환. 이후 단위 검증에서 기준이 달라졌으면 관련 결과 재검토 | 같은 원칙. 기록 없이 중단됐다면 현재 내용이 같다는 이유만으로 소유를 단정하거나 자동 삭제하지 않음 |

[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)의 공유 모드는 핸들 수명 동안 적용된다. 기존 읽기/쓰기 핸들이 충돌하거나 쓰기 가능한 매핑이 있으면 배타적 열기가 실패할 수 있다. 접근 거부, 공유 위반, 읽기 전용과 대상 부재를 구분해 반환하며 프로세스 강제 종료, ACL 변경, 느슨한 공유 모드로 우회하지 않는다. 속성/확장 속성 접근은 이 공유 모드만으로 차단되지 않으므로 모든 메타데이터 보호를 보장하지 않는다.

쓰기에서는 [WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile)의 성공 여부와 실제 바이트 수를 확인한다. 짧아진 본문이나 빈 파일은 [SetEndOfFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setendoffile)로 길이까지 맞춰야 하며 0바이트 쓰기로 대체하지 않는다. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)는 파일 저장 경계에서 사용하고 작은 조각마다 반복하지 않는 후보다. 같은 핸들로 재읽어 내용/길이를 대조하며 저장 시간만으로 성공을 판단하지 않는다. 이 순서도 DB와 파일의 일괄 원자성이나 모든 전원 장애의 무손실을 보장하지 않는다.

허용하지 않은 인코딩, BOM, 줄바꿈과 속성을 바꾸지 않는다. 재분석 지점, 하드 링크, 경로 별칭이나 대상 디렉토리 교체 때문에 다른 파일에 영향이 갈 수 있으면 실제 대상과 허용 범위를 확인하기 전 쓰지 않는다. 지원하지 못하는 파일 유형은 조용히 일반 파일로 취급하지 않는다. 읽기/쓰기 핸들을 잡은 채 AI, 사용자 응답이나 긴 검사 실행을 기다리지 않는다.

쓰기 오류를 실행 중 잡았고 같은 보호와 보존본이 유효하면 [조건부 복원 — 「실패 뒤 복구 방식」](update.md#%EC%8B%A4%ED%8C%A8%20%EB%92%A4%20%EB%B3%B5%EA%B5%AC%20%EB%B0%A9%EC%8B%9D)을 적용한다. 프로세스가 사라졌다면 부분 파일이 남을 수 있으므로 다음 명시적 재개에서 현재 내용과 기록을 대조해 복원/재개 계획을 제시한다. 핸들 반환 후 사용자가 바꾼 내용을 옛 보존본으로 덮지 않는다. 저장/재읽기/기록 중 어느 단계가 실패했는지 남기며, 복원까지 실패하면 완료로 표시하지 않는다.

### 삭제와 이름 변경

승인된 변경 계획에 있는 개별 파일만 대상으로 한다. 기존 파일을 먼저 비우지 않고 내용/식별/필요 속성을 확인해 보존하며, 필요한 `DELETE` 접근을 포함한 배타적 핸들을 유지하는 후보를 사용한다. [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)의 `FileDispositionInfo`와 `FileRenameInfo`를 각각 삭제/이름 변경에 사용할 수 있는지 검증한다. 삭제 표시와 핸들 종료 뒤 실제 상태는 구분하고, 핸들을 닫은 다음 같은 경로를 다시 열어 무조건 삭제하지 않는다.

이름 변경은 [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)의 대상 덮어쓰기를 금지하는 후보로 시작한다. 목적지가 이미 있으면 충돌로 반환하며 다른 볼륨으로 복사 후 삭제하는 동작으로 자동 대체하지 않는다. 삭제 뒤 같은 이름으로 새 파일이 생겼어도 그것을 재삭제하지 않는다. 설치 후 정리는 [별도 확인/보존 계약 — 「설치 완료 뒤 정리」](install.md)을 유지하고, 이 API 후보를 폴더 전체 삭제 허가로 확대하지 않는다.

정리 명령이 이 파일 처리 경로를 사용할 때의 현재 의존, 고정 목록/승인과 claim/관측 순서는 [공통 입력과 파일 대조](../workflow/maintenance.md)가 소유한다. 갱신 파일의 반영/복원과 불필요한 보존 자료의 정리를 같은 승인으로 합치지 않으며, 공통 API를 사용한다는 이유로 각각의 검사 의무를 생략하지 않는다.

### 실행 중인 구성의 갱신

설치된 skill, hook과 script는 계속 프로젝트에서 관리한다. 첫 후보는 **비교와 후보 준비는 먼저 하되, 영향받는 실행이 끝난 안전한 경계에서 반영**하는 흐름이다. 실행 중인 코드를 실시간 교체하는 기능이나 프로젝트 밖 상시 실행본을 새로 도입하지 않는다.

1. 영향 단위의 실행과 자식 프로세스를 기존 시도 기록으로 확인한다. 실행 중이거나 종료를 확인하지 못하면 후보를 보존하고 필요한 종료/재개 조건을 안내한다. 파일 핸들이 비었다는 사실만으로 코드 실행까지 끝났다고 판단하지 않는다.
2. 외부에서 받은 관리 도구가 반영을 수행한다. 바꾸고 있는 설치본을 동시에 실행기로 삼지 않는다. 첫 쓰기 전에 미완료 기록을 남기며, 관리되는 진입점은 영향을 받는 코드를 읽거나 실행하기 전에 그 기록을 확인해야 한다. 진입점 자체를 바꿀 때도 기존 호출이 새로 들어오지 않는 조건을 검증한다.
3. 일반 Codex의 지침 읽기나 사용자의 직접 실행이 이 검사에 자동 참여한다고 가정하지 않는다. 제어하지 못하는 영향 호출이 남으면 해당 반영을 보류한다. 호스트의 종료/재시작이 필요한 경우 적용 전에 알리고, 지원 버전의 실제 로드 시점은 구현 시험에서 확인한다. 전체 AI 세션이나 무관한 CI를 임의로 종료하지 않는다.
4. 파일 반영 후에는 현재 반영 주체가 허용한 해당 단위의 검증만 수행하고 정상 기능 진입은 보류한다. 이 검증 경로를 명시해 ‘완료해야 검증할 수 있고, 검증해야 완료할 수 있는’ 순환을 피한다. 필요한 호스트 재로드/신뢰 확인과 실제 동작을 이 검증 경로에서 확인하고, 결과와 공유 기준, 단위 완료가 연결된 뒤 정상 진입을 허용한다. 파일 저장만으로 갱신 완료를 반환하지 않는다.

실제 진입 제어 없이 미완료 표시만 만든 것은 구현 성공이 아니다. [파일/사용 중 갱신의 검증 입력 — 「파일 반영과 실행 중 갱신의 검증 입력」](../../verification/acceptance.md)을 통과해야 한다.

## 반영 기록과 완료 연결

11/15의 입력/소비 초안이며, 11/16의 [실패 후 선택 — 「업데이트 실패 후 선택」](update.md#%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8%20%EC%8B%A4%ED%8C%A8%20%ED%9B%84%20%EC%84%A0%ED%83%9D)을 함께 적용한다. [설치의 단계 연결 — 「설치 기록과 단계 연결」](install.md)에 아래 자료를 전달한다. 같은 로컬 SQLite를 사용하되 설치 작업 기록과 [검증 계획/시도 — 「식별과 참조」](../workflow/records.md)는 책임을 구분해 참조한다. 파일을 썼다는 사실을 테스트 PASS로 표현하지 않는다.

| 기록 단위 | 필요한 내용 | 사용하는 곳 |
| --- | --- | --- |
| 설치 작업과 변경 계획 | 작업 식별, 대상 사본, 요청 종류, 고정 배포 출처, 선택 범위, 허용 변경, 이전 계획과 변경 이유 | 명시적 설치 재개. 실제 사용한 계획을 수정해 과거 실패/의무를 지우지 않음 |
| 적용 단위 | 단위 식별, 선행 조건, 함께 바꿀 파일/항목, 보호 범위, 확인할 검사와 조건부 복원 범위 | 실행 순서와 독립 완료 판단. 폴더나 파일 수만으로 자동 분할하지 않음 |
| 적용/복원 시도 | 같은 작업/단위, 수행하려는 동작, 실제 시작/종료/미확인과 앞선 시도 참조 | 재실행을 원래 실패와 연결. 읽기 대조만으로 적용이 실행됐다고 남기지 않음 |
| 파일/항목별 변경 | 경로와 관리 항목의 식별, 적용 직전 존재/본문/필요 속성, 예정 결과, 실제 관측과 자료 참조 | 반영 직전 검사, 부분 변경 대조와 복원. 공유 파일은 다른 항목도 보존 |
| 단위의 확인 결과 | 실제 반영 상태, 관련 검사 시도/결과 참조, 남은 조건, 공유 설치 기록에 반영한 기준 | 단위 완료와 전체 완료의 구별. 결과를 복제하거나 마지막 성공 하나로 앞선 실패를 닫지 않음 |

이 표는 자료의 의미이며 SQL 테이블이나 필드 수를 확정한 것이 아니다. [설치 단위와 반영 기록](../workflow/storage.md)에 변경 계획/단위, 시도별 원문/관측, 검사 참조와 완료 근거의 관계 후보를 연결했다. 공통 대상/파일 참조 규칙을 사용하고 의미가 다른 설치 계획을 검사 계획의 가짜 `check_id`로 넣지 않는다. 같은 단위 안의 파일 쓰기 순서와 의존 단위 사이 순서는 모두 재개 때 식별할 수 있어야 한다.

반영 기록은 다음 순서로 소비한다.

1. **쓰기 준비:** 원문 밖 후보와 적용 직전 사본을 확인한 뒤, 어느 단위/시도의 어떤 대상을 어떤 상태로 바꿀지 DB에 저장한다. 저장 실패면 해당 쓰기를 시작하지 않는다. 사본에는 삭제/생성의 구별도 필요하며 이전 공식 배포본으로 대신하지 않는다.
2. **반영과 관측:** DB 쓰기 트랜잭션 밖에서 파일/항목을 반영하고 실제 관측을 기록한다. 매 변경의 의도와 관측을 대응시켜 파일 사이에서 멈춘 경우를 구별한다. 일반 코드 내부 절차이며 각 기록마다 AI 요청을 추가하지 않는다.
3. **검증과 기준 반영:** 단위의 실제 연결과 보존, 필요한 검사 결과를 확인한 뒤 그 단위의 공유 설치 기준을 반영한다. 공유 기준의 실제 저장까지 확인해야 단위 완료를 기록한다. 공용 파일 전체가 바뀌었다는 이유로 무관한 단위의 검사를 모두 무효화하지 않고 관련 항목/의존을 대조한다.
4. **요청 완료:** 모든 필수 단위와 통합 조건을 대조한 뒤 전체 완료를 반환한다. 완료한 단위, 복원한 단위, 보류/미착수와 실제 상태가 불명확한 단위를 구분한다. 반환은 기존 기록으로 만든 조회 결과이며 별도 완료 원본 파일을 추가하지 않는다.

파일 교체와 DB 저장, 공유 설치 기준의 갱신은 하나의 트랜잭션이 아니다. 파일 반영 뒤 관측 저장 전, 또는 공유 기준 갱신 뒤 단위 완료 저장 전에 중단될 수 있다. 재개 시 예정 결과, 현재 파일과 남은 근거를 대조하며 DB 기록 부재를 미실행으로 취급하지 않는다. 공유 기준 파일만 새로워졌다는 이유로 설치 완료를 확정하지도 않는다. 필요한 검증 근거가 없다면 미확인으로 남기고 영향받는 확인부터 수행한다.

후속 편집이 있는 원문을 예정 결과에 억지로 맞추지 않는다. 파일이 예정 결과와 같더라도 도구가 쓴 것인지 확인되지 않으면 자동 삭제/복원의 근거로 삼지 않는다. 복원도 새 시도로 이전 시도와 연결하며, 되돌리기 전 의도와 실제 결과를 남긴다. 실패 단위만 복구할 때는 그 단위의 공유 기준 변경만 다루고 앞서 완료한 독립 단위의 기준을 옛 전체 파일로 덮지 않는다. 이전 구성 사용 선택에 따른 전체 복원은 요청 시작 시점의 기준으로 돌아가야 하며, 자료 연결과 이력 보존은 [설치 단위와 반영 기록](../workflow/storage.md)을 따른다.

재개는 설치 작업 식별과 현재 대상이 일치하는지부터 확인한다. 기록에 미완료가 여럿이면 최신 시각만으로 하나를 선택하지 않는다. 목표 릴리스나 기능 범위를 바꾸려면 후속 계획에서 차이와 남은 의무를 연결한다. 같은 입력의 유효한 완료는 재적용하지 않되 실제 파일/조건이 달라졌으면 관련 단위와 의존 결과를 재검토한다. 평소 Codex 진입이나 단순 문맥 복구에서는 이 쓰기 절차를 자동 실행하지 않는다.

공유 기준과 원문의 저장은 [파일 반영과 핸들 수명](update.md#%ED%8C%8C%EC%9D%BC%20%EB%B0%98%EC%98%81%EA%B3%BC%20%ED%95%B8%EB%93%A4%20%EC%88%98%EB%AA%85), 최초 제외 준비 전의 자료는 [첫 기록 생성과 인계](install.md)에 연결했다. 실제 실행을 차단할 수단이 없는 상태를 준비 완료로 표시하지 않는다. [선택과 전체 복원의 DDL 연결 — 「선택과 전체 복원의 연결」](../workflow/storage.md)을 작성했다. 전체 요청의 이전 계획도 복원 대조에 포함하며, 기록 형식 변경의 상세와 실제 Windows 복원은 남아 있다. 기존 자료에 비밀값이 있어 사본을 만들 수 없다면 값을 기록하지 않고 해당 변경을 멈춰 별도 처리 범위를 확인한다.

위 흐름은 우리 보존 요구의 설계다. [Copier](https://copier.readthedocs.io/en/stable/updating/#how-the-update-works)의 이전 생성본/사용자 차이 비교, [Git의 3방향 병합](https://git-scm.com/docs/git-merge-file), [SQLite의 DB 내부 commit](https://www.sqlite.org/atomiccommit.html)은 각 수단의 근거다. 이 자료가 위 단계 전체의 원자성, 무충돌이나 Windows 제품 검증을 보장하지는 않는다.

## 실패 뒤 복구 방식

11/11 조건부 복원 원칙을 채택했다. 아래는 **실패 단위 내부**의 복구 동작 비교다. 재시도를 위한 완료 유지와 즉시 보고는 [적용 단위와 부분 완료](update.md#%EC%A0%81%EC%9A%A9%20%EB%8B%A8%EC%9C%84%EC%99%80%20%EB%B6%80%EB%B6%84%20%EC%99%84%EB%A3%8C)가, 11/16에 추가한 이전 구성 사용 선택과 이번 업데이트 전체 복원은 [업데이트 실패 후 선택](update.md#%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8%20%EC%8B%A4%ED%8C%A8%20%ED%9B%84%20%EC%84%A0%ED%83%9D)이 소유한다. AI 문서 분석의 재개나 이미 공유한 Git 커밋의 되돌리기와는 다른 결정이다.

| 방식 | 장점 | 비용, 제한 |
| --- | --- | --- |
| 조건부 자동 복원 — 원칙 채택 | 실패 단위 안의 자신의 변경을 되돌려 불완전한 구성을 줄임. 정상 복구 때 추가 조작이 적음 | 계획의 사전 허용과 직전 사본, 실제 파일, 동시 편집 여부 대조 필요. 후속 편집, 불확실성, 복원 오류는 중단 |
| 복원 계획을 매번 확인 | 실패 뒤 추가 쓰기를 사용자가 먼저 확인 | 사용자가 대응할 때까지 불완전한 구성이 남으며 반복 확인 부담 |
| 미완료 적용의 재개 우선 | 이미 끝낸 반영을 활용할 수 있음 | 부분 상태, 중복 실행, 호환 조건 판단이 더 복잡함. 첫 배포의 작은 설치 묶음에는 추천하지 않음 |

채택 범위는 **실행 중 잡은 실패에 한정한 해당 단위의 조건부 자동 복원**이다. 최초 적용 계획에 단위 경계와 이 동작을 안내하고 허용 범위에 포함한다. 실패 사실을 먼저 보고한 뒤, 실패한 단위의 복구 사본, 반영 기록, 현재 파일이 충분히 대조되고 다른 편집이 없을 때만 도구가 바꾼 부분을 그 단위의 적용 직전으로 돌린다. 복원 직전에도 같은 편집 배제 조건을 확인한다. 사전 허용 밖의 복원, 새 판단이 필요하면 사용자 확인 전에는 실행하지 않는다. 일부 파일만 안전하다고 나머지 충돌을 숨기거나 기준 버전을 앞서 바꾸지 않는다.

프로세스 강제 종료, 전원 중단처럼 도구가 복원할 기회 없이 멈추면 미완료로 남는다. 다음 설치/복구 실행에서 실제 상태를 대조해 복원 또는 재개 계획을 먼저 보여주고 사용자가 선택한다. 평소 AI CLI를 시작했다는 이유만으로 파일 변경을 재개하지 않는다. 한 번 승인한 같은 복구 범위의 기계적 검사는 다시 승인받지 않는다.

반영 기록 직전/직후에도 중단될 수 있으므로 기록만 믿지 않는다. 파일이 적용 전과 같으면 미반영/복원 여부를, 도구의 예정 결과와 같으면 반영 여부를 함께 대조한다. 어느 쪽과도 맞지 않거나 누가 변경했는지 판단할 수 없으면 자동 복원하지 않는다. 새로 만든 파일도 이번 도구의 결과임을 확인할 때만 제거하며, 사용자 파일이 들어간 폴더를 통째로 삭제하지 않는다. 복원 자체가 실패하면 남은 차이, 사본을 보존하고 미완료로 알린다.

예를 들어 skill을 갱신한 뒤 연결 script 반영이 실패했다면, 새 skill과 옛 script를 섞어 완료하지 않는다. 위 조건이 맞을 때 **사용자 편집이 포함된 적용 직전 skill**로 되돌리고 연결, 기준을 대조한다. 실패 뒤 사용자가 그 skill을 더 수정했다면 자동으로 덮지 않고 차이 확인으로 전환한다. 설명용 사례이며 제품 시험 결과는 아니다.

최초 설치의 `.gitignore` 복원에는 순서 제약이 있다. `.harness/`에 복구 자료가 남아 있는 동안 제외 규칙을 먼저 제거하면 로컬 자료가 일반 Git 수집에 노출될 수 있다. 자료를 보존하면서 제외 효력을 유지할 정리/이전이 확인된 뒤 규칙을 복원한다. 불가능하면 제외와 자료를 유지하고 남은 차이를 명시하며 완전 복원으로 표시하지 않는다. 제외 준비 전의 임시 복구 위치, 정리 절차는 복구 명세에서 정하며, 실제 비밀값을 백업/기록하는 예외로 쓰지 않는다.

이 추천은 여러 파일의 원자적 처리를 약속하지 않는다. [Python의 os.replace](https://docs.python.org/3.10/library/os.html#os.replace)가 제공하는 성공 시 원자성은 한 경로 교체에 관한 것이고 파일시스템이 다르면 실패할 수 있다. 따라서 묶음의 부분 반영, 복원 중 재중단도 시험해야 한다. 복원 사본과 실행 기록의 대응, 형식 변경 초안은 [백업과 저장 형식 변경](../workflow/recovery.md)에 연결했다. 정확한 형식, 잠금, 명령은 후속 명세이며, 기본 동작과 [검증 입력 — 「설치 보존과 복구의 검증 입력」](../../verification/acceptance.md)을 함께 확인한다.
