# 설치와 기존 자료 보존

11/11 채택한 구성은 **외부의 Git 릴리스 + Python 도구로 설치와 갱신하고, 평소 실행 파일은 대상 프로젝트에서 관리**하는 방식이다. 첫 대상은 Windows 직접 실행이다. 예비 WSL 설계 세션과 도구는 유지하며 제품 실행 환경과 구분한다. 제품 설치, 실사용 검증은 아직이다.

처음 읽을 때는 「설치 결과의 소유와 공유」 → 「설치부터 평소 사용까지」 → 「설치 기록과 단계 연결」 → [갱신과 복원](update.md) 순서로 본다. 아래는 현재 설치 설계만 다룬다. 외부 실행본, plugin의 이전 비교와 시험은 [비교 이력](../../discussions/history/install.md)에 보존했다.

배치, 제공, 보존, 환경의 결정 원본은 ADR [0019](../../decisions/runtime/0019-project-install.md), [0010](../../decisions/runtime/0010-distribution.md), [0011](../../decisions/runtime/0011-preservation.md), [0020](../../decisions/runtime/0020-windows.md)이다. 갱신/복원 상세와 실제 실행 결과를 채택 상태와 구별한다.

## 채택 범위와 남은 설계

| 경계 | 현재 결정과 남은 설계 |
| --- | --- |
| 배포와 관리 도구 | Git 릴리스 + Python 관리 도구 채택. 고정 배포본을 외부에서 준비해 설치, 기능 추가, 갱신에 사용. 정확한 명령, 지원 버전, 배포 파일명은 후속 명세 |
| 프로젝트에 남길 구성 | 선택 기능의 skill, hook 연결/처리 코드, script, 설정을 프로젝트에 설치. 기존 발견 위치의 전용 항목과 프로젝트 내 전용 실행 영역을 조합 |
| 공유와 개인 상태 | 팀 공통 실행 자산, 공동 지침, 비밀 없는 설치 기준은 프로젝트 Git 공유 권장. 기존 추적 정책을 보존하고 자동 stage, 공개하지 않음. WIKI의 내부/외부 선택과 `.harness/` 로컬 제외 유지 |
| 기존 자료와 갱신 | 기존 WIKI, 지침, 사용자 편집을 보존하고 모듈 소유 변경만 후보로 제시. 충돌, 기준 불명, 연결 불일치는 해당 묶음의 적용을 보류. 채택한 보존 원칙에 따라 적용/복원 수단을 후속 명세 |

보존 원칙은 [ADR 0011](../../decisions/runtime/0011-preservation.md)에서 별도로 채택했다. 단위, 저장, 잠금과 실제 설치 구현은 후속 명세 대상이다. 프로젝트별 문서 이름, 위치는 [분류 과정 — 「프로젝트별 분류를 정하는 과정」](../knowledge/documents.md)을 따라 연결하며 설치를 이유로 기존 문서를 이동하지 않는다.

## 실행 환경과 사용 안내

11/11 [ADR 0020](../../decisions/runtime/0020-windows.md)으로 Windows 직접 실행 우선, WSL/Linux 후속을 채택했다. 정확한 도구 버전, 권한과 제품 설치, 실사용 검증은 남아 있다. 예비 WSL 연결 성공은 제품 Windows 지원의 증거가 아니다.

### 터미널 창과 셸, 프로젝트 위치

| 구분 | 첫 지원 방향 | 확인할 내용 |
| --- | --- | --- |
| 터미널 창 | IntelliJ 터미널 또는 Windows Terminal 등 | 창 이름보다 실제 셸, 호출 도구 확인 |
| 실제 실행 | Windows 11의 PowerShell, Windows Codex/Git/Python | 설치와 이후 작업 모두 Windows 실행 사용. 정확한 지원 버전은 검증 후 명세 |
| 프로젝트 저장 | Windows 로컬 코드 폴더 | 경로, 권한, 한글/공백, 줄바꿈, 실제 대상 명령 확인 |
| 문서 | 프로젝트 내부 또는 별도 Windows 로컬 WIKI | 같은 원본을 직접 접근. Obsidian 선택, 외부 쓰기 권한, 역할 연결 확인 |

Windows 기본 흐름에는 WSL 진입이나 `wslpath` 변환을 요구하지 않는다. WSL에서 Windows 파일을 읽는 예비 도구는 별개다. PowerShell은 진입 셸이고 공통 관리 로직은 Python으로 구현한다. Linux 명령을 그대로 호출하거나 사용자 셸, Git 설정을 몰래 바꾸지 않는다. [OpenAI Windows 안내](https://learn.chatgpt.com/docs/windows/windows-sandbox), [Microsoft 파일시스템 안내](https://learn.microsoft.com/en-us/windows/wsl/filesystems).

IntelliJ 터미널의 셸과 JDK, Gradle, 실행 설정은 각각 확인한다. WSL/Linux는 후속 지원 대상이며 Windows 폴더를 WSL에서 실행한 결과로 Windows 직접 실행 검증을 대체하지 않는다.

### 지원 조건의 확인 순서

11/18 실행 흐름 대조의 입력이다. Windows 11 직접 실행과 Git 릴리스 + Python 제공은 채택한 범위이고, 아래 점검을 실제로 통과한 제품은 아직 없다. 배포 README의 버전 표는 **검증한 도구 조합과 기능**을 기준으로 작성한다. 개발자 기기의 한 버전을 유일한 허용 버전으로 고정하거나, 최신 버전이라는 이유만으로 지원을 보장하지 않는다.

| 확인 순서 | 확인할 대상과 멈추는 범위 |
| --- | --- |
| Python 실행 전 | README에서 Windows Python 준비와 실행 방법 안내. Python 자체가 없으면 Python 도구가 안내할 수 없으므로 설치 안내를 먼저 제공 |
| 명령 인자 해석 뒤 | 실제 Python 경로/버전, 선택 동작에 필요한 표준 기능과 배포본 지원 정보 확인. 기록을 쓰는 동작은 sqlite3와 필요한 DB 기능 확인 뒤 변경. 도움 조회에는 무관한 의존성을 요구하지 않음 |
| 대상 연결 | 실제 코드 루트, 설치 파일과 로컬 WIKI, 필요한 읽기/쓰기 및 제외 상태 확인. Windows 로컬 경로의 한글/공백, 드라이브 차이를 시험하고 WSL 변환을 기본 경로에 섞지 않음 |
| 해당 기능 실행 전 | Git, Codex 또는 선택 기능의 도구/라이브러리, 실제 호출 경로와 필요한 인증/신뢰 확인. 선택하지 않은 AI/원격 기능의 계정이나 도구를 강제하지 않음 |
| 변경/재개 전 | 관리 도구와 설치 기준, 현재 DB 형식 및 중단 작업의 호환 확인. 모르는 형식이면 그 변경을 보류하며 지원되는 보존/조회 경로를 안내. 호환되지 않는 형식을 새 DB로 초기화하지 않음 |
| 도구/경로 변경 후 | 바뀐 조건과 의존 기능만 다시 확인. 유효한 기존 결과/허가는 재사용하고 같은 요구를 처음부터 반복하지 않음 |

[PowerShell의 명령 탐색](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence)은 별칭, 함수와 실행 파일이 같은 이름을 가릴 수 있으며 명시적 경로로 대상을 선택할 수 있음을 설명한다. 제품의 짧은 명령 등록과 의존 도구 발견에서 이 차이를 확인한다. 사용자 셸의 별칭과 Python 하위 프로세스의 탐색을 동일하다고 가정하지 않으며, 선택한 실행 경로와 버전을 진단에 표시한다. `.ps1` 제한이 있는 경우의 `.cmd` 또는 명시적 실행 경로는 실제 인자 전달까지 검증한 조합만 안내하고 실행 정책을 자동 완화하지 않는다.

11/22 [ADR 0022 — 「Codex 설치 지원 범위」](../../decisions/runtime/0022-wiki-entry.md)로 npm과 공식 Windows 독립 설치를 첫 Codex 지원 범위에 채택했다. [설치별 진입과 선택 규칙 — 「Codex 설치 형태와 실행 파일 선택」](entry.md)에 따라 이미 설치된 한 방식을 사용한다. 모듈의 Git 릴리스 + Python 배포와 구별하며, 선택하지 않은 설치 방식의 의존성을 강제하지 않는다. 이 결정으로 Codex/Node를 설치하거나 갱신하지 않았다. 두 방식의 실제 Windows 검증 뒤 확인한 조합과 미지원 안내를 배포 README에 반영한다.

정확한 최소/검증 버전과 Windows 진입 조합은 구현 후 수용 시험으로 채운다. 버전이 알려져도 필수 기능이 없으면 그 기능을 실행하지 않는다. 아직 검증하지 않은 버전을 확인만 하고 ‘지원’으로 표시하지 않으며, 지원 범위를 바꿔야 하면 별도 판단한다. [권한 선택 재사용 — 「권한 선택 재사용의 판단 순서」](entry.md)은 저장 옵션을 적용하기 전의 조건을 확인하며, 모델/문서 변경만으로 반복 허용을 요구하지 않는다. [사용 단계별 명령 — 「설치부터 관리까지의 호출 순서」](entry.md)에 준비 조건과 결과를 연결하고, 같은 진단을 각 명령에서 다시 전부 출력하지 않는다.

### README에 담을 순서

제품 전체의 [사용자 조작 최소화 원칙 — 「사용자 조작을 줄이는 실행 원칙」](../architecture.md)을 적용한다. 설치와 명령 관리의 실제 입력/안내는 [관리 진입 명세 — 「진입과 사용자가 할 일」](management.md)와 같은 흐름으로 작성하며 내부 처리마다 별도 실행 명령을 사용자에게 요구하지 않는다.

아래는 **배포 저장소의 사용자용 실행 안내 README** 구성 기준이다. 11/16 사용자 요청에 따라 실제 명령으로 처음 사용하기까지의 흐름을 짧게 보여주고, 상세 사용법과 내부 설계는 연결 문서로 분리한다. 현재의 긴 설계 점검 목록을 배포 README에 그대로 싣지 않는다. 아직 구현하지 않은 명령을 실행 가능한 예시로 제시하지 않는다.

| 읽는 순서 | README에서 바로 알 수 있어야 할 내용 |
| --- | --- |
| 1. 무엇을 하는가 | 조건부 하네스의 목적과 짧은 사용 예. 기존 프로젝트의 WIKI 복원도 제공하지만 모든 사용자에게 필수 실행 단계는 아님 |
| 2. 실행 준비 | 지원 환경과 검증된 도구 버전, 필수 준비물과 선택 기능의 준비물, 필요한 계정과 AI 사용 비용 조건. Python은 Python 명령보다 먼저 준비. 최초 도입 담당자와 이미 설치된 프로젝트를 받은 팀원의 시작 위치를 구분 |
| 3. 설치와 연결 | 공식 고정 배포본 받기와 출처/무결성 확인, 실행할 폴더와 실제 명령, 프로젝트와 내부/외부 WIKI 입력. 기본/선택 기능과 변경 계획, 필요한 권한을 확인한 뒤 적용 |
| 4. 첫 사용 | 최초 기기 준비 뒤 제품의 전용 시작 명령과 작은 개발 요청 예, 정상 결과와 확인 방법. 일반 `codex`는 필요한 권한이 준비된 호환 경로로 구분. 도구 발견, 호출과 문서/상태 연결까지 확인하고 파일 복사만으로 완료하지 않음 |
| 5. 완료 뒤 정리 | 설치/인계 검증 뒤 임시 자료의 삭제 여부를 묻는다는 짧은 안내. 보관해도 사용 가능하며 설치된 기능, 갱신 기준과 프로젝트 상태는 유지. 상세는 정리 안내로 연결 |
| 6. 다음에 할 일 | 평소 시작/재개의 대표 명령, 경로 변경, 선택 기능 추가, 갱신, 복원과 제거 안내 링크. 업데이트 명령 앞에는 중단 시 선택과 기존 구성 사용 조건을 짧게 표시. 문제 해결과 도움 요청, 기여, 라이선스 안내의 진입점 |

실행 안내는 **실행 위치 → 명령 → 필요한 입력 → 정상 결과/다음 행동**으로 읽히게 쓴다. [사용 단계별 호출 순서 — 「설치부터 관리까지의 호출 순서」](entry.md)에서 담당자와 팀원의 진입을 선택해 지원하는 기본 경로 하나를 먼저 보여주고 대안과 전체 옵션을 본문에 나열하지 않는다. 예시의 교체할 값과 셸을 명시하고 실제 자격증명이나 개인 경로를 넣지 않는다. 변경 대상, 필요한 권한과 AI 호출/비용처럼 실행 판단에 필요한 정보는 해당 명령 전에 짧게 알리며 상세 링크 뒤로 숨기지 않는다.

이미 설치된 프로젝트를 받은 팀원은 공통 설치와 WIKI 분석을 반복하지 않는다. [기기별 준비 — 「팀 도입과 기기별 준비」](install.md#%ED%8C%80%20%EB%8F%84%EC%9E%85%EA%B3%BC%20%EA%B8%B0%EA%B8%B0%EB%B3%84%20%EC%A4%80%EB%B9%84)의 코드/WIKI 사본 확보, 도구/계정, 로컬 연결, 실제 접근/신뢰 확인 뒤 첫 사용으로 이어지게 한다. 새 기기/clone과 경로 변경도 이 경로에 연결한다.

#### 실행 전 안내와 중단 시 도움

11/16 사용자 요구: 사용자가 대응해야 하는 충돌, 준비물 부재, 복원 실패를 README나 상세 매뉴얼 안에만 숨기지 않는다. 설치/업데이트의 실제 실행 경로에서도 필요한 내용을 보여주며, 해당 배포 버전의 안내로 바로 이어져야 한다. 사람이 문장을 이해했는지 기계적으로 보장할 수는 없지만, 기본 경로에서 핵심 안내를 생략하거나 관련 절을 직접 검색해야만 찾을 수 있게 만들지 않는다.

| --- | --- |
| README의 설치/업데이트 명령 직전 | 변경할 범위, 사용자 자료 보존, 중단 시 필요한 조치와 기존 구성 사용 조건의 짧은 요약. 상세 절의 정확한 제목과 링크 |
| 실행 계획 확인, 실제 반영 전 | 이번 대상/버전/선택 기능, 사용을 잠시 멈춰야 할 범위, 보존과 복원 조건, 실패 시 선택. 기존 적용 확인에 포함하며 같은 범위에 새 동의 질문을 중복 추가하지 않음 |
| 오류나 중단을 확인했을 때 | 실패한 단계와 관측한 원인, 완료/복원/미확인 범위, 지금 사용할 수 있는 구성, 필요한 사용자 조치, 재개 또는 보류 방법. 원인이 불명확하면 추측으로 단정하지 않음 |
| 해결 후 재개 또는 기존 구성 복원 | 확인할 조건과 실제 결과, 아직 남은 작업. 복원 성공과 업데이트 성공을 구분하고 다음에 사용할 검증된 명령/안내 위치를 표시 |

프로젝트 config를 변경해야 하는 연결은 먼저 [설정 소유와 공유 상태의 전환](entry.md)에 따라 기존 파일과 Git 상태, 이번 모듈 변경의 범위를 보여준다. 미추적 파일을 자동 제외하거나 기존 공유 파일을 자동 이전하지 않는다. 사용자가 로컬 전용 운영을 선택한 경우에는 **Git 제외가 백업이나 삭제 방지가 아니라는 점**과 나중에 공유로 전환하는 절차를 안내한다. 새 기기/clone, 브랜치 전환/무시 파일 정리 뒤의 재연결은 [적용 조건 — 「다른 도구의 사례와 적용 조건」](entry.md)에 연결한다. 긴 위험 목록을 Quickstart에 복제하지 않으며 충돌/설정 부재를 확인한 실제 경로에서 다음 행동을 제시한다.

[공통 원본에서 실행 설정을 생성하는 후보 — 「공유 설정과 개인 경로의 충돌 해결」](entry.md)는 이를 명시적으로 원하는 프로젝트의 미채택 비교안이다. 범용 설치 절차에 포함하지 않는다. 이 방식을 채택한다면 최초 기기 준비뿐 아니라 공통 설정 변경 뒤의 갱신도 안내해야 한다. Git pull만으로 생성본이나 열린 세션의 권한까지 최신화됐다고 설명하지 않는다.

[ADR 0022](../../decisions/runtime/0022-wiki-entry.md)에 따라 전용 시작/재개 명령을 기본 안내로 둔다. 현재 설치된 Codex 사용, 저장 WIKI 연결과 일반 codex 혼용 시 접근 차이만 필요한 순서로 설명한다. 11/22 결정에 따라 MCP 제공은 후속이다. 첫 배포 안내/준비물에 MCP 설치나 등록을 요구하지 않으며 기존 사용자 MCP 설정은 보존한다. 정확한 실행 예시는 Windows 제품 검증 뒤 확정한다. 배포 권리 안내는 [라이선스 기준 — 「라이선스와 저작권」](../module.md)을 따른다.

일반 터미널과 AI 내부 진입은 같은 상태/계획에서 안내를 만든다. AI가 호출하더라도 핵심 내용이 도구 로그에만 묻히지 않게 사용자에게 전달한다. 비대화형 경로의 출력에도 같은 핵심 정보를 남기고 새 선택이 필요하면 입력 필요 상태로 종료한다. 무응답/EOF를 재시도나 복원 동의로 해석하지 않으며, 이미 받은 같은 계획의 허용은 재사용한다. 출력 항목과 실제 UI/명령은 후속 구현에서 확정한다.

관련 상세 안내는 오류별 원인 확인, 지원 환경에서의 조치, 안전한 재개, 중단 유지와 도움 요청을 설명한다. 문서 링크를 열 수 없어도 즉시 필요한 조치와 현재 사용 가능 여부는 실행 결과에서 알 수 있어야 한다. 진단 자료를 외부로 자동 전송하거나 비밀값을 안내/로그에 넣지 않는다. [CLI Guidelines의 오류 안내](https://clig.dev/#errors)는 사람이 이해할 오류와 필요한 행동을 가까이 제시할 근거이며 제품 검증 결과는 아니다.

기존 구성의 사용과 실패 뒤 선택은 [갱신 문서 — 「업데이트 실패 후 선택」](update.md)가 소유한다. 재시도 준비를 확인했다는 사실만으로 다음 적용 성공을 보장하지 않는다. 이번 요구의 노출/사용성은 [README 검증 — 「배포 README의 사용성 검증」](../../verification/acceptance.md)에서 실제 실행 경로로 확인한다.

#### 공개 문서에서 참고한 구성

[GitHub의 README 지침](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)은 프로젝트 설명, 시작 방법과 도움 경로를 제시하고 긴 설명은 별도 문서로 분리하도록 권한다. [uv README](https://github.com/astral-sh/uv/blob/main/README.md)는 설치 명령을 직접 제시하고, [GitHub CLI README](https://github.com/cli/cli/blob/trunk/README.md)는 설치 안내와 상세 사용 매뉴얼을 연결한다. [Cookiecutter README](https://github.com/cookiecutter/cookiecutter/blob/main/README.md)의 Quickstart는 실행 명령, 질문에 답하는 과정과 생성 결과를 이어 보여준다. 2026-11-16 공개 원문을 확인했다.

공통으로 참고할 점은 사용자가 실행할 행동과 상세 문서의 진입점을 쉽게 찾는 구성이다. 하나의 보편적인 목차나 길이 제한이 있다는 뜻은 아니다. 위의 순서는 우리 제품에 맞춘 판단이며 다른 프로젝트의 설치 명령이나 의존성을 가져오는 결정이 아니다. Git 릴리스 + Python 제공과 Windows 우선 범위는 유지한다.

## 배포와 루트 배치

평소 실행 파일의 위치는 ADR 0019로 정했다. 제공 수단도 Git 릴리스 + Python으로 채택했고 정확한 명령, 지원 버전은 남아 있다. 설치 스크립트를 프로젝트 안에 영구 보관하거나 실행할 때마다 공식 원본을 내려받을 필요는 없다.

| 수단 | 쉽게 말하면 | 현재 판단 |
| --- | --- | --- |
| A. 애플리케이션 라이브러리 import | Gradle/Maven 등에 앱 실행 의존성 추가 | 개발 도구를 앱 언어/런타임에 결합하고 지침, hook 배치는 해결하지 못해 비추천 |
| B. 고정 배포물 + 설치와 갱신 도구 | 공식 릴리스를 준비해 프로젝트 파일의 변경 계획과 설치를 수행 | 11/11 Git 릴리스 + Python 제공 채택. 적용/보존 상세는 후속 협의 |
| C. Codex plugin + 설정 절차 | native plugin 배포, 발견을 활용하고 프로젝트 연결/생성을 수행 | 이전 시험의 공유 설치 상태, 사용자 직접 수정 요구를 따로 해결해야 함. 첫 수단으로 병행 구현하지 않음 |

공식 원본은 특정 앱과 독립된 모듈 Git에서 개발하고 유지보수자가 릴리스를 발행한다. 소비 프로젝트에는 선택한 기능의 실행 구성과 설치 기준을 남긴다. 모듈 개발 저장소 전체, 개발 이력, 테스트, 다른 프로젝트 WIKI를 복사하지 않는다. 사용자는 설치 파일을 직접 수정할 수 있고 이를 공식 원본으로 제출하거나 별도 공식 버전을 발행할 의무가 없다.

설치 결과의 Git 공유는 [추적 선택 — 「AGENTS와 Git 추적 선택」](install.md#AGENTS%EC%99%80%20Git%20%EC%B6%94%EC%A0%81%20%EC%84%A0%ED%83%9D), 파일별 소유는 [구성표 — 「설치 결과의 소유와 공유」](install.md#%EC%84%A4%EC%B9%98%20%EA%B2%B0%EA%B3%BC%EC%9D%98%20%EC%86%8C%EC%9C%A0%EC%99%80%20%EA%B3%B5%EC%9C%A0)가 소유한다. 프로젝트에 파일이 있다는 사실만으로 Codex, 언어 실행기, 권한, 외부 WIKI까지 준비됐다고 판단하지 않는다. 정확한 발견 경로와 명령, 이름은 후속 명세에서 정한다. 앞선 `project.json`, `install.json`은 설명용 이름이며 확정 인터페이스가 아니다.

### 배포 도구

11/11 비교 후 사용자가 **Git 릴리스 + Python 관리 도구를 채택했다.** 외부 도구는 설치, 추가, 버전 조회, 갱신, 제거를 관리하고 일상 실행은 프로젝트에 설치한 파일을 사용한다. Git의 공식 원본과 릴리스는 모든 후보에서 하나다. 아래 차이는 담당자가 도구를 받는 방법이며 실행 구성의 외부/내부 배치를 다시 선택하는 문제가 아니다. 11/23 최초 설치와 기기 명령 복구/제거의 기본 진입을 [관리 명세](management.md)에 연결했다. 지원 버전, 갱신/추가 명령과 실제 구현 검증은 남아 있다.

| 수단 | 담당자의 사용 흐름 | 장점과 남는 비용 |
| --- | --- | --- |
| Git 릴리스 + Python 관리 도구 — 채택 | 공식 버전의 배포 파일을 프로젝트 밖에 풀고 Python 진입 명령으로 대상 프로젝트를 지정. 다음 갱신 때 새 배포본 준비 | 별도 패키지 관리자, 레지스트리 없이 시작. 배포본 다운로드, 무결성 확인, 교체 안내와 짧은 진입 명령은 우리가 제공해야 함 |
| Python 패키지 + uv — 후속 검토 | uv를 준비하고 Git의 고정 commit 또는 배포 패키지로 도구를 설치/실행. 도구 버전 관리는 uv 활용 | 격리 환경, 명령 등록, 도구 갱신을 재사용. Python 패키징과 uv 준비/지원 범위가 추가됨. 공개 PyPI 등록은 필수가 아님 |
| npm 패키지 + 실행 명령 — 후속 검토 | Node/npm을 준비하고 버전을 지정한 패키지를 실행하거나 사용자 도구로 설치 | 익숙한 명령, 캐시, 배포 생태계. Node/npm과 패키지 배포를 지원해야 하며 Python 도구를 감싸기만 하면 두 실행 환경을 요구하게 됨 |

[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)는 Git tag에 연결한 배포 파일, 릴리스 설명과 읽기 권한에 따른 접근을 제공한다. 자동 제공되는 소스 압축본과 우리가 필요한 실행 자료만 선별해 첨부할 배포물은 구분한다. 비공개 시험에서는 허용된 계정의 저장소 접근이 필요하다. 배포물 준비를 모든 팀원의 별도 모듈 Git clone 의무로 만들지 않는다.

[uv 도구 안내](https://docs.astral.sh/uv/guides/tools/)는 Git commit 지정 실행, 격리 설치, PATH의 명령 제공과 도구 갱신을 지원한다. 설치할 도구는 [Python 패키지 구조](https://packaging.python.org/en/latest/tutorials/packaging-projects/)와 실행 진입점을 갖춰야 한다. [uv 환경](https://docs.astral.sh/uv/concepts/tools/#tool-environments)은 프로젝트 파일과 별개이며 캐시 정리를 프로젝트 설치 결과 제거와 혼동하지 않는다. [npm exec](https://docs.npmjs.com/cli/v11/commands/npm-exec/)도 버전 지정, 캐시 실행을 제공하며 프로젝트의 앱 의존성에 반드시 추가할 필요는 없다.

**선정 근거:** 첫 지원은 ADR 0020의 Windows 직접 실행이며, 제한된 환경에서 필수 기능을 먼저 검증해야 한다. 우선 표준 라이브러리와 Git으로 관리 로직을 구현할 수 있는지 확인하고 Git 릴리스로 제공하는 편이 초기 도구 준비를 줄인다. 이는 공수의 정량 실측 결과가 아니다. 사용 편의만 보면 명령 설치, 도구 갱신을 제공하는 uv/npm이 유리하다. 11/11 사용자 재확인으로 두 수단은 이후 버전에서 필요할 때 검토하며 첫 제공에 넣지 않는다. 외부 Python 의존성이나 배포 편의의 비중이 커지면 설치/보존 로직을 유지하면서 패키징을 재검토한다.

채택한 수단의 준비, 실행 흐름은 다음과 같다. 최초 설치의 명령은 [관리 진입 — 「진입과 사용자가 할 일」](management.md)을 따르고 실제 배포 README는 검증한 실행 예시만 제공한다.

1. **받기:** 유지보수자가 같은 공식 릴리스에 관리 도구, 선택 설치 자료, 버전/지원 정보와 사용법을 묶는다. 담당자는 고정한 배포물을 프로젝트 밖에 준비한다. 개발 저장소 전체나 다른 프로젝트의 문서는 적용 프로젝트에 복사하지 않는다.
2. **설치:** Windows의 대상 프로젝트에서 배포 도구 경로와 대상 루트를 전달한다. 대화형 설정 → 변경 계획/차이 확인 → 허용 범위 적용 → 실제 연결 검증으로 이어진다. 짧은 진입 명령을 제공하고 필요한 셸 설정 변경의 범위와 효과를 안내한다.
3. **일상 사용:** 검토한 프로젝트 파일, 설정과 팀 WIKI를 공유한다. 설치 도구가 없어도 설치된 하네스가 동작해야 한다. 팀원의 기기 준비는 [팀 도입과 기기별 준비](install.md#%ED%8C%80%20%EB%8F%84%EC%9E%85%EA%B3%BC%20%EA%B8%B0%EA%B8%B0%EB%B3%84%20%EC%A4%80%EB%B9%84)를 따른다.
4. **추가, 갱신:** 같은 관리 도구의 조회/갱신 흐름을 사용한다. 새 도구가 필요한 경우 새 고정 배포본을 별도로 준비해 실행하며, 기존 도구가 이해하지 못하는 규격을 그대로 적용하지 않는다. 첫 제공 후보는 README에서 안내하는 배포본 교체이며 별도의 자기 갱신 프로그램을 선행 구현하지 않는다. [변경분 판정 — 「변경분과 충돌의 판정」](update.md)과 검증이 끝난 뒤에만 프로젝트 적용 완료를 기록한다.

| 준비 대상 | 필요한 것과 경계 |
| --- | --- |
| 도입, 갱신 담당자 | 지원 Windows, Python, Git, 공식 배포본, 필요한 저장소 접근. 첫 제공에서 uv/npm은 요구하지 않으며 실제 지원 버전은 검증 후 고정 |
| 설치 결과를 사용하는 팀원 | Codex와 선택 기능의 실행 의존성, 프로젝트 파일, WIKI 접근, 기기별 경로, 신뢰. 도입 담당자용 다운로드/패키징 도구까지 일괄 요구하지 않음 |

관리 도구를 Python으로 제공해도 모든 설치 파일의 언어를 Python으로 확정하는 것은 아니다. 반대로 프로젝트에 Python script를 설치한다면 이를 쓰는 팀원에게도 Python이 필요하다. 현재 개발 기기에서 도구가 발견된 사실만으로 모든 사용자 환경이 준비됐다고 가정하지 않는다.

어느 제공 수단도 프로젝트 파일의 안전한 갱신을 대신하지 않는다. uv/npm으로 관리 도구를 바꿔도 기존 프로젝트가 저절로 갱신되지 않으며, 별도의 프로젝트 적용, 보존 검증을 거친다. 임시 배포 사본 제거 전에는 필요한 설치 기준/복구 자료가 남아 있는지 확인하고 프로젝트의 영구 참조가 그 사본을 가리키지 않아야 한다.

이전 Python/Git 예제는 좁은 비교, 보존 가능성의 근거이며 완성된 설치기가 아니다. 자체 패키지 저장소/의존성 해결기를 만들지 않고 상세 사용자 흐름은 [설치부터 평소 사용까지](install.md#%EC%84%A4%EC%B9%98%EB%B6%80%ED%84%B0%20%ED%8F%89%EC%86%8C%20%EC%82%AC%EC%9A%A9%EA%B9%8C%EC%A7%80)에 한 번만 둔다.

고정하는 대상은 공식 하네스 배포본이다. 사용자의 `codex`를 과거 절대 경로에 고정하지 않는다. 실행 환경에서 발견한 버전의 지원 여부를 검사하며 몰래 업그레이드, 다운그레이드하지 않는다. 관리 도구의 지원 범위와 프로젝트 실행 의존성은 각각 안내한다.

### 설치 결과의 소유와 공유

11/11 채택한 배치의 구성표다. **배치, 소유 경계는 채택했고 정확한 이름, 지원 발견 경로, 설치 기준의 저장 형식은 명세 후보다.** 필수/선택/후속 기능은 [첫 배포 범위 — 「첫 배포의 책임과 보류 항목」](../../decisions/architecture/0007-release-scope.md)가 소유한다.

| 자산 | 위치, 공유 | 설치와 갱신, 제거에서 할 일 |
| --- | --- | --- |
| 공식 모듈 소스, 템플릿, 자체 테스트 | 독립 모듈 Git, 유지보수자 관리 | 공식 출처로 릴리스. 적용 프로젝트에 개발 저장소 전체를 복사하지 않음 |
| 설치, 추가, 조회, 갱신, 제거 도구 | 배포본은 프로젝트 밖에 보관. 호출하는 현재 폴더와 대상 프로젝트는 별도로 확인 | 요청한 프로젝트의 후보를 준비. 이 도구만 새 버전으로 바꿔도 설치된 프로젝트는 자동 변경하지 않음 |
| PC에 등록한 `oneploom` 시작 프로그램 | 사용자 프로그램 영역의 OnepLoom. 해당 PC 사용자에게만 등록 | 현재 프로젝트의 설치본으로 인계. 다운로드 정리와 별개로 유지하며 [등록 소유 — 「기기 등록 정보와 소유」](entry.md)에 따라 관리 |
| 선택 기능의 skill, script, hook 처리 코드, 공통 설정 | 지원 진입 위치와 프로젝트 내 전용 영역. 팀 Git 공유 권장 | 설치 기준과 소유를 기록. 사용자가 본문/코드를 수정할 수 있으며 갱신은 현재 편집을 보존한 후보로 처리 |
| 기존 AGENTS, 공유 hook/config, Git 제외 규칙 | 기존 위치, 추적 정책 유지 | 파일 전체를 모듈 소유로 삼지 않음. 확인한 관리 항목, 최소 연결 차이만 변경 후보로 제시 |
| 프로젝트 검사 명령, 예외, 추가 skill/script | 프로젝트 소유, 공유할 정책은 프로젝트 Git | 원본 빌드/설정을 연결. 모듈 소유가 아닌 파일은 쓰기 대상에서 제외하며 호환성 문제는 설명 |
| 공식 출처, 선택 기능, 파일/항목 소유와 생성 기준 | 비밀 없는 재현 정보는 프로젝트 공유 범위에 보존. 아래 설치 기록의 파일/자료 후보 참조 | 새 clone에서도 이전 기준을 확보. 삭제/이동, 기준 누락은 자동 덮기 대신 확인. 개인 백업만 의존하지 않음 |
| 요구사항, ADR, 계약, 실패 지식 등 WIKI | 기존 내부 문서 또는 등록한 외부 원본/Git | 먼저 연결. 설치/업데이트로 본문 재생성, 재분류 금지. 부족한 내용은 별도 WIKI 작업 |
| 기기별 경로, 진행, 후보, 복구 자료 | 추적되지 않는 로컬 설정/`.harness/` | 제외 확인 후 생성. 팀 공통 실행 파일, WIKI를 이 안에 넣지 않음. 사용자 후속 편집을 보존하며 복구 |
| 명령 등록용 wheel과 외부 관리 도구 | 공식 Release에서 제공. 적용 프로젝트 Git에는 기본 포함하지 않음 | [팀원 첫 준비 — 「팀원 첫 준비의 배포 자료」](install.md#%ED%8C%80%EC%9B%90%20%EC%B2%AB%20%EC%A4%80%EB%B9%84%EC%9D%98%20%EB%B0%B0%ED%8F%AC%20%EC%9E%90%EB%A3%8C)에서 Windows 사용자별 한 번 등록. 프로젝트 소스/공유 기준과 별도 관리 |
| 다운로드, 해제 자료 | 프로젝트 밖의 사용자 선택 로컬 폴더. 프로젝트 커밋 불필요 | 다른 프로젝트의 설치에 재사용하려면 보관. 더 이상 필요 없고 참조/복구 의존도 없을 때 사용자 확인 후 정리 |

파일 단위와 공유 설정의 항목 단위를 구분한다. 전용 디렉토리 안의 사용자 파일도 자동으로 모듈 소유가 되지 않는다. 설치 기준의 **본문**은 해시만으로 되살릴 수 없으므로 보존한 기준 또는 고정 배포본과 입력으로 확인한다. 공유할 수 없는 정보를 포함하면 그대로 커밋하지 않고 로컬/공유 분리와 갱신 가능 범위를 정한다. 개인 `.harness/`에만 기준이 있는 상태를 팀 갱신 준비 완료로 표시하지 않는다. 이 기준은 다음 업데이트 담당자가 공식 변경과 프로젝트 편집을 구별하기 위한 것이며 WIKI 본문 전체를 복제하는 자료가 아니다.

팀 공유 권장이 기존 Git 정책이나 공개 범위를 자동 변경하는 근거도 아니다.

변경 전후를 비교하면 다음과 같다.

| 동작 | 이전 외부 실행본 안 | 채택한 프로젝트 설치 |
| --- | --- | --- |
| 평소 skill/hook 실행 | 프로젝트 연결에서 외부 공통 프로그램 호출 | 프로젝트의 skill/연결에서 같은 프로젝트의 script, 설정 사용 |
| 사용자가 처리 코드를 바꿈 | 공유 파일 영향 또는 프로젝트 사본 전환 관리 | 설치된 프로젝트 파일을 직접 수정. 일반 코드/설정 책임은 논리적으로 분리 |
| 공식 업데이트 | 외부 릴리스 준비와 참조 전환, 프로젝트 차이 대조 | 외부 도구가 프로젝트 설치 파일/항목의 후보를 만들고 편집, 호환성 대조 |
| 팀원의 새 clone | 공유된 연결 외에 같은 외부 실행본 준비 | 공유된 설치 결과와 기준을 받음. Codex, 실행 의존성, 로컬 경로, 신뢰는 별도 준비 |

### 설치기 위치와 재실행 판단

11/23 사용자는 현재 위치/옵션으로 프로젝트를 선택하는 질문이 **설치기 실행에 관한 것**임을 정정하고, `oneploom` 시작 명령의 보완도 함께 검토하도록 했다. 설치기는 대상에 하네스를 설치/관리하고, 시작 명령은 이미 준비된 프로젝트의 작업 환경을 연다. 두 프로그램에 필요한 대상 확인은 [공통 확인 순서 — 「설치기와 시작 명령의 대상 확인」](entry.md)를 사용하며 이후 동작과 완료 기준은 합치지 않는다.

내려받은 배포본은 사용자가 선택한 **프로젝트 밖의 읽기/실행 가능한 로컬 폴더**에 둔다. README에는 다운로드 폴더 등의 예시를 제공하되 모든 사용자에게 같은 절대 위치를 요구하지 않는다. 배포본 안의 템플릿과 설치 자료는 배포본의 위치를 기준으로 찾고, 대상 프로젝트는 명시 입력 또는 확인한 현재 작업 폴더를 기준으로 결정한다. 호출 폴더가 달라도 같은 배포 자료를 사용하며, 대상은 위 입력 기준으로 선택한다. 배포본 보관 위치를 설치 대상 대신 사용하지 않는다.

예를 들어 설치기를 `D:/tools/OnepLoom-installer`에 보관하고 `D:/work/A`에서 호출하면 A가 대상 후보가 된다. 다른 곳에서 호출하면서 B를 명시하면 B만 확인한다. 두 경로는 설명용이며 아직 실행할 명령이나 필수 디렉토리 이름이 아니다. 관리 도구의 정확한 명령/옵션 문법은 후속이고 사용자 지정 설치 위치의 저장/발견은 [프로젝트 실행본 명세 — 「설치 위치의 저장과 발견」](project-entry.md)에 연결했다.

대상을 확정한 뒤 설치 요청과 현재 상태를 다음처럼 구분한다. 같은 유효 범위의 확인/허가는 재사용하되 변경 범위를 자동 확대하지 않는다.

| 확인한 설치 상태 | 설치기가 할 일 |
| --- | --- |
| 설치 기록과 관리 파일이 없고 신규 대상/범위가 확인됨 | 필요한 준비와 변경 계획을 보여주고 허용된 최초 설치 수행. 대상 폴더를 자동 생성하거나 Git을 임의 초기화하지 않음 |
| 같은 공식 기준/기능의 정상 설치가 완료됐고 현재도 유효 | 변경 불필요와 평소 실행 방법을 안내. 설치를 반복하거나 Codex를 자동 실행하지 않음 |
| 같은 설치가 중단됐거나 반영 여부가 불명확 | 기존 계획/시도와 실제 결과를 대조하고 기존 [재개 절차 — 「의존성 준비와 설치 재개」](install.md#%EC%9D%98%EC%A1%B4%EC%84%B1%20%EC%A4%80%EB%B9%84%EC%99%80%20%EC%84%A4%EC%B9%98%20%EC%9E%AC%EA%B0%9C) 적용. 완료 표식이나 폴더 존재만으로 건너뛰지 않음 |
| 설치는 완료됐지만 요청한 공식 버전/기능이 다름 | 기존 기준과 사용자 편집을 보존하며 별도 갱신/추가 계획으로 분기. 배포본을 바꿔 실행했다는 이유만으로 덮어쓰지 않음 |
| 사용자가 설치된 코드/skill/설정을 수정함 | 허용된 프로젝트 편집으로 먼저 대조. 차이가 있다는 이유만으로 손상이나 신규 설치로 판정해 원본 템플릿으로 초기화하지 않음 |
| 관련 파일은 있는데 설치 기준이 없거나 다른 프로젝트의 기록임 | 소유/기준 불명으로 변경 보류. 신규 상태로 위장하거나 다른 작업의 DB로 대신 진행하지 않음 |

`oneploom` 시작 명령에 같은 입력을 주었을 때는 [시작 명세 — 「시작과 재개의 명령 흐름」](entry.md)를 따른다. 정상 설치라면 작업 환경을 열고 미준비라면 안내 후 멈춘다. 설치기의 재실행, Codex 대화 재개와 완료 뒤 WIKI 복원 재실행은 각각 다른 요청이다.

설치기 보관/삭제는 사용자의 선택이다. 다른 프로젝트에 재사용하려면 배포본을 보관할 수 있고, 정리했다면 다음 설치/갱신에 필요한 고정 배포본을 다시 준비한다. PC의 시작 프로그램에 설치 자료 전체가 항상 들어 있다거나 별도 배포본 없이 신규 설치도 수행한다고 약속하지 않는다. 설치 중단 기록은 다운로드 위치와 별도로 보존하며 [첫 기록 생성과 인계](install.md#%EC%B2%AB%20%EA%B8%B0%EB%A1%9D%20%EC%83%9D%EC%84%B1%EA%B3%BC%20%EC%9D%B8%EA%B3%84)를 따른다.

### 설치부터 평소 사용까지

아래는 프로젝트의 도입, 업데이트 담당자가 수행할 흐름이다. 다른 팀원은 검토, 공유된 결과를 받고 자기 기기만 준비한다.

1. **배포본 준비:** 담당자가 README에 명시한 실행 도구, 계정/권한과 Git 릴리스의 배포본을 프로젝트 밖에 준비한다. 설치기는 그 위치의 경로로 호출하며 현재 작업 폴더와 설치 대상은 따로 확인한다. [외부 oneploom.py install — 「진입과 사용자가 할 일」](management.md)을 기본 진입으로 명세했고 실제 지원 버전/명령 검증은 구현에 연결한다.
2. **대상, 기존 구성 확인:** [대상 확인 순서 — 「설치기와 시작 명령의 대상 확인」](entry.md)로 명시 입력 또는 현재 위치에서 코드 루트를 확인한 뒤 내부/외부 WIKI와 선택 기능을 보여준다. 위 재실행 표로 신규/완료/중단/변경 요청을 나누고, 필요한 도구, 권한과 기존 AGENTS, skill, hook, Git 정책, 이름 충돌을 쓰기 전에 확인한다.
3. **후보 생성:** 필요한 실행 파일과 프로젝트 입력을 준비하고 생성/변경/보존/충돌을 구분한다. 기존 빌드/문서를 연결하며 같은 값을 여러 파일에 하드코딩하지 않는다. AI 의미 분석이 필요한 범위는 일반 설치 처리와 구분하고 무단 전체 분석을 시작하지 않는다.
4. **설치, 연결:** 허용한 파일/항목만 적용하고 지원 위치에서 실제 발견, 호출, 기존 기능 보존을 확인한다. 공유 설치 기준과 로컬 `.harness/`를 분리한다. 필요한 프로젝트/hook 신뢰를 우회하지 않는다.
5. **완료와 정리 확인:** 설치와 인계 검증을 마친 뒤 정리 가능한 자료 묶음을 보여주고 사용자 응답을 받아 처리한다. 보관, 취소, 정리 실패와 설치 결과를 구분하며 상세는 [설치 완료 뒤 정리](install.md#%EC%84%A4%EC%B9%98%20%EC%99%84%EB%A3%8C%20%EB%92%A4%20%EC%A0%95%EB%A6%AC)를 따른다.
6. **평소 사용:** 최초 기기 준비 뒤 프로젝트의 전용 시작/재개 명령으로 현재 설치된 Codex를 열고 평소 개발 요청을 한다. [프로젝트 안에서는 바로 시작하고 밖에서는 등록 목록을 선택 — 「여러 프로젝트의 선택과 실행」](entry.md)하며 선택한 프로젝트의 저장 WIKI 경로를 전달한다. 매번 긴 --add-dir나 활성화 skill을 요구하지 않는다. 일반 codex는 기존 권한/프로젝트 기능을 사용하는 호환 경로로 유지한다. skill/hook은 프로젝트 파일을 사용하며 임시 배포 사본 제거 뒤에도 동작해야 한다. [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 기본 흐름과 외부 WIKI 접근, 같은 세션 재개를 실제 환경에서 검증한다.
7. **팀 공유, 사용자 수정:** 담당자가 설치 결과/기준과 필요한 WIKI 작업을 검증하고 팀의 검토 절차로 공유한다. 팀원은 같은 결과를 받아 기기별 준비 후 사용하며 설치, WIKI 생성을 반복하지 않는다. 이후 사용자, AI는 설치된 skill, script를 수정할 수 있고, 저장된 템플릿으로 매 실행마다 초기화하지 않는다.
8. **기능 추가, 업데이트:** 외부 도구를 다시 실행해 공식 기준, 현재 편집, 새 후보를 대조한다. 의존하는 파일/항목을 한 묶음으로 검증하며 충돌, 불완전 적용이면 기존 구성을 보존하고 완료 처리를 보류한다. 제거도 소유가 확인된 범위만 대상으로 한다.

기존 WIKI는 연결해 사용하고 신규 프로젝트는 확인된 초기 지식부터 쌓는다. 상세 역공학은 사용자가 범위, 모델을 선택해 별도로 실행한다. 설치 결과에 자동 commit, push, 공개를 포함하지 않으며 개인 시작 도구의 성공을 이 사용자 흐름의 제품 검증으로 대신하지 않는다.

### 의존성 준비와 설치 재개

11/12 사용자 요청으로 **필요한 준비 안내 → 중단 → 사용자의 설치/조치 → 같은 작업 재실행**을 설치와 이식 완료까지 적용한다. [독립 완료의 보존 — 「적용 단위와 부분 완료」](update.md)과 [복구 상태 — 「작업과 실행의 상태」](../workflow/recovery.md)를 사용하며 별도 설치 캐시나 범용 실행 엔진을 추가하는 결정은 아니다. 제품 구현, 실제 재개 검증은 아직이다.

| 단계 | 처리와 사용자에게 보일 결과 |
| --- | --- |
| 실행 전 준비 | README에 지원 Python과 필수/선택 의존성, 공식 설치 경로를 명시. Python 부재는 Python 스크립트가 실행되어 안내할 수 없으므로 진입 전 준비에서 다룸 |
| 사전 점검 | 선택한 기능에 필요한 도구/라이브러리/파일, 버전, 접근 권한을 확인. 선택하지 않은 기능의 준비물을 강제하지 않음. Python의 sqlite3 등 기록에 필요한 기반이 없으면 프로젝트 변경을 시작하지 않음 |
| 부재, 불일치 발견 | 필요한 항목, 이유, 준비 방법, 완료/미완료 범위, 재실행 방법을 알리고 새 적용 중단. 임의 설치, 권한 변경, 다른 저장 수단 전환 금지 |
| 사용자 준비 후 재실행 | 같은 프로젝트, 설치 계획, 공식 기준, 선택 범위를 식별하고 기록과 현재 결과를 대조. 입력, 의존성, 산출물이 여전히 유효한 완료 단위는 다시 적용/생성하지 않음 |
| 계속 진행 | 유효한 완료 이후의 미완료 단위부터 진행. 사용자 준비와 같은 계획의 명시적 재실행은 그 범위의 재개 요청으로 보며 같은 기계적 작업을 다시 승인받지 않음 |
| 최종 완료 | 선택한 필수 단위와 실제 연결 검증이 모두 끝났는지 확인하고 완료, 남은 선택 사항을 구분해 보고. 기록 존재나 파일 복사 성공만으로 설치 전체를 완료 처리하지 않음 |

사전 확인 가능한 부재는 쓰기 전에 모두 알린다. 실행 중 환경이 바뀌거나 새 필요가 드러난 경우에도 이미 검증된 독립 완료를 지키고 멈춘다. 부분 반영이 있으면 위 보존/복구 원칙에 따라 처리하며, 준비물을 설치했다는 이유로 실패한 단위를 성공으로 바꾸지 않는다.

재개는 완료 표식만 보고 건너뛰는 방식이 아니다. 관련 입력, 도구 조건, 산출물이 바뀌거나 유효성을 확인할 수 없으면 영향받는 단위와 그 의존 결과를 다시 판단한다. 무관한 유효 결과까지 전부 무효화하지 않는다. 사용자 후속 편집을 덮거나, 성공 여부가 불명확한 파일/PR 작업을 자동 반복하지 않는다. 새 범위, 권한, 비용 또는 복구 판단이 생기면 관련 부분은 협의하며 기존 기록 부재/손상을 새 빈 작업으로 숨기지 않는다.

배포물 자체의 누락/무결성 오류는 공식 사본 재확보 문제이고, 사용자 소유 입력 부재는 올바른 경로, 제공 범위 확인 문제다. 둘을 임의 파일 생성이나 추정 내용으로 대체하지 않는다. 프로그램 설치 뒤 기존 셸의 발견 경로가 갱신되지 않았다면 그 상태와 필요한 재진입을 안내한다. 실제 설치 명령, 지원 버전, 재개 식별/검사 항목은 후속 명세에서 정한다.

[Docker의 캐시 무효화](https://docs.docker.com/build/cache/invalidation/)처럼 조건이 유효할 때 이전 결과를 재사용한다는 비유는 가능하다. 다만 사용자 편집, 외부 WIKI, 원격 효과가 있는 우리 작업은 별도로 확인해야 한다. 재개 시의 가벼운 현재 상태 점검은 반복하되 유효한 완료 작업의 비싼 생성, 적용을 반복하지 않는 방향이다. 검사의 실행/결과 재사용은 기존 [ADR 0002](../../decisions/workflow/0002-pass-validity.md)를 따르며 새 범용 PASS 캐시를 도입하지 않는다.

설치 재개는 이 설치 작업을 명시적으로 다시 실행할 때의 흐름이다. 평소 개발 세션의 compact, 재접속에서 설치를 자동으로 이어서 적용하지 않는다. [공통 복구 경계 — 「복구의 대상과 경계」](../workflow/recovery.md)의 기록, 조회 책임을 사용하되 설치의 완료/복원 판단은 이 절과 갱신 문서가 소유한다. WIKI 초기 내용 분석을 이어갈 때는 해당 분석 기능의 계획, 후보, 근거를 연결한다.

### 설치 기록과 단계 연결

11/15의 4단계 명세다. 위 사용 흐름에 필요한 자료와 소비자를 연결하며 새로운 설치 정책을 채택하거나 제품을 실행한 결과는 아니다. 설치와 업데이트, 기능 추가는 같은 준비/반영 절차를 사용하고 요청한 변경 범위만 다르게 정한다. 사용자가 일반 CLI에서 입력하든 Codex 안에서 요청하든 [연결 결과 — 「결과를 받는 절차」](entry.md)를 같은 설치 절차에 전달한다.

먼저 **업데이트 담당자가 사용할 설치 기준**과 **그 기기에서 수행한 작업의 진행 기록**을 구분한다. ADR 0019에서 채택한 것은 담당자가 설치/갱신 결과를 공유하고, 비밀 없는 설치 기준도 함께 보존하도록 권장하는 원칙이다. 모든 팀원이 설치기를 반복 실행하거나 설치 이력을 직접 관리한다는 뜻은 아니다.

`install.json`은 11/15에 제안한 파일명 후보다. 이 이름의 독립 파일, 정확한 디렉토리, 무조건 Git 추적하는 정책을 확정한 것은 아니다. 아래는 설치 기준을 프로젝트의 설치 결과와 함께 공유하는 권장 배치이며, 기존 추적 정책과 공개 범위를 보존한다. 로컬 기록은 [설치의 저장 관계 — 「설치 단위와 반영 기록」](../workflow/storage.md)에 연결했다. 전체 DDL/직렬화와 Windows 보호의 실증은 남아 있다.

| 자료와 후보 위치 | 내용과 소비자 |
| --- | --- |
| 프로젝트 전용 설치 영역의 설치 기준 파일. `install.json`은 이름 후보이며 `.harness/` 밖 배치를 권장 | 공식 출처와 고정 revision/배포물 무결성, 설치한 기능, 단위별 파일/관리 항목과 비교 기준의 참조. 담당자의 관리 도구가 기록/조회하며 개인 경로, 실행 로그, active는 넣지 않음 |
| 공유 가능한 생성 기준 본문 | 고정 배포본과 비밀 없는 생성 입력으로 정확히 재현하거나 공유 가능한 기준 사본으로 확보. 설치 기록에서 위치와 내용 기준을 참조. 현재 사용자 편집본이나 적용 직전 백업과 구분 |
| `.harness/state/state.db`의 설치 기록 | 같은 프로젝트/작업 사본의 설치 요청, 변경 단위, 적용/복원 시도와 실제 반영 관측. 공통 저장 코드가 관리하되 검증의 PASS/FAIL 결과로 대신 표현하지 않음 |
| 같은 로컬 상태 영역의 계획/시도별 자료 | 실행 전 후보는 계획, 적용 직전 사본과 보고서는 시도에 연결. [파일 배치 후보 — 「파일과 소유」](../workflow/records.md)에 따라 필요한 자료만 생성하고 역할/내용 기준 참조 |

설치 기준은 공식 변경과 사용자 편집을 비교하는 자료이고 DB는 로컬 실행 이력이다. 같은 진행 상태를 양쪽에서 수정 가능한 원본으로 관리하지 않는다. `project.json`과 `.harness/local.json`의 현재 경로 설정도 복제하지 않는다. 생성 당시 값이 비교에 꼭 필요하면 그 기준만 보존하며 현재 설정을 자동으로 과거 값으로 돌리지 않는다. 설치 기준이 없거나 해석할 수 없으면 기준이 필요한 관리 작업의 반영을 보류하고 확인한다. 파일이 없다는 이유로 최초 설치나 새 모듈 소유로 추정하지 않는다.

기기 명령 등록은 [등록 작업과 기존 DB — 「등록 작업과 기존 DB의 연결」](entry.md)에 따라 기존 DB의 별도 작업으로 연결한다. `registration.json`은 프로젝트의 `install.json`을 대체하지 않으며 그 안에 설치 진행을 복제하지 않는다. 최초 기록을 프로젝트로 인계하기 전에 등록 작업과 그 `pending` 참조 해제를 마친다. 등록이 미완료면 참조 중인 외부 DB/사본을 정리하거나 옮기지 않는다.

프로젝트 설치를 되돌리거나 해당 프로젝트를 지워도 다른 프로젝트가 쓸 수 있는 기기 명령을 자동 제거하지 않는다. 기기 명령만 복구하는 경우에는 외부 설치기의 같은 보존/재개 절차를 쓰되 프로젝트 인계는 하지 않는다. 실제 기기 효과에 필요한 [저장 확장 — 「기기 등록 효과의 저장 경계」](../workflow/storage.md)은 제품 구현 전에 연결해야 하며, 현재 프로젝트 파일용 DDL의 검사 결과로 대체하지 않는다.

일반 팀원은 설치된 skill/script와 프로젝트 설정을 사용하고 자기 기기의 WIKI 경로와 권한만 준비한다. 공유한 설치 기준 파일이 clone에 함께 들어오더라도 직접 열거나 편집할 의무는 없다. 평소 개발, 문서 읽기, 세션 재개마다 이 파일을 AI에게 읽히거나 설치 이력을 검사하는 공통 선행 조건도 두지 않는다. 담당자가 기능 추가, 갱신, 제거 또는 설치 상태 진단을 요청할 때 관리 도구가 필요한 기준을 읽는다. 기준 누락으로 해당 관리 작업이 보류되는 것과 이미 설치된 정상 하네스의 일상 사용은 구분한다.

**유지할 대상은 갱신 비교에 필요한 기준이며 `install.json`이라는 특정 이름 자체가 아니다.** 이 파일 후보를 채택하면 설치 후에도 남기고, 기능 추가/업데이트가 실제로 완료된 범위에 맞춰 갱신한다. 프로젝트 밖의 다운로드/해제 사본은 필요 참조와 복구 의존이 없어지면 정리할 수 있지만 비교 기준까지 지우지 않는다. 기준 본문을 외부 배포물에서 다시 확보해야 한다면 고정 출처의 접근 가능성도 확인한다. 공유 기준은 로컬 상태 정리 대상이 아니며, 모듈 제거 때의 처리는 제거 명세에서 정한다.

담당자 로컬에만 기준을 두는 방식도 기술적으로 가능하다. 다만 기기 교체, 기록 유실, 다른 브랜치/clone 또는 담당자 인계에서 그 기준을 따로 전달하거나 재확보해야 한다. 재현할 수 없는 기준이 사라지면 현재 편집본을 과거 기준으로 대신할 수 없다. 현재는 설치 결과와 최소 기준을 함께 보존해 Git 이력과 대응시키는 방식을 추천한다. 설치를 한 명이 수행하는 것과 그 기준의 유일한 사본을 한 기기에만 두는 것은 별개의 선택이다. 로컬 전용 보관을 기본으로 바꾸려면 ADR 0019의 인계 조건과 별도 보존 수단을 함께 재검토한다.

[Copier](https://copier.readthedocs.io/en/stable/updating/)는 대상 프로젝트의 answers 파일과 이전 템플릿으로 갱신 비교를 준비한다. [Cookiecutter replay](https://cookiecutter.readthedocs.io/en/stable/advanced/replay.html)는 입력을 사용자 홈의 JSON에 보존해 재생성에 사용한다. 두 보관 방식 모두 실제 사례가 있지만 목적과 갱신 기능이 같지는 않다. 공유 기준을 추천하는 근거는 우리 설계의 사용자 편집 보존과 담당자 인계 요구이며 모든 도구가 같은 위치를 쓴다는 주장은 아니다.

공유 설치 기록에는 검증된 단위의 실제 출처와 기준을 반영한다. 일부만 완료된 경우 이전 단위의 기준을 모두 새 릴리스로 바꾸지 않는다. 목표 릴리스는 로컬 요청 기록에, 실제 적용된 출처는 공유 설치 기록에 구분해 남긴다. 전체 완료 여부는 선택한 필수 단위와 통합 확인 결과로 판단한다. 이는 사용자별 공식 버전을 만드는 방식이 아니다.

설치 요청은 다음 입력을 받는다. 이미 확인한 연결은 참조로 전달하고 전체 프로젝트를 다시 조사하지 않는다. 실제 반영 직전에는 바뀔 수 있는 해당 입력을 다시 대조한다.

| 입력 | 확인할 범위 |
| --- | --- |
| 요청과 대상 | 최초 설치/업데이트/기능 추가 중 요청한 동작, 확인한 코드 작업 트리, 필요한 WIKI 루트와 설정 출처. 재개이면 기존 설치 작업 식별자도 전달 |
| 배포와 기능 | 명시한 공식 릴리스, 배포물 내용 기준, 요청 기능과 필수 의존. 같은 요청 도중 다시 조회한 최신 릴리스로 바꾸지 않음 |
| 기존 설치와 현재 파일 | 소유 기록, 이전 생성 기준, 실제 파일/관리 항목과 사용자 편집, 필요한 지원 도구와 제외 효력 |
| 변경 허용 범위 | 생성/변경/제거할 대상과 단위 경계, 보호 대상, 필요한 검증, 사전 허용한 조건부 복원. 새 권한이나 범위는 기존 승인에 포함된 것으로 추정하지 않음 |

대상 루트, 배포물, 기존 구성은 읽기 점검부터 한다. Python이나 기록 기반이 없으면 아직 기록할 수 없다는 사실과 준비 방법을 반환하며 설치 작업을 만들었다고 표시하지 않는다. 최초 `.gitignore` 변경 전 필요한 외부 보존 위치의 비교와 인계 조건은 [첫 기록 생성과 인계](install.md#%EC%B2%AB%20%EA%B8%B0%EB%A1%9D%20%EC%83%9D%EC%84%B1%EA%B3%BC%20%EC%9D%B8%EA%B3%84)에서 다룬다. **제외가 준비되지 않은 `.harness/`에 DB나 후보부터 생성하지 않으며, 보존 수단을 확보하지 못하면 프로젝트 파일의 첫 쓰기도 시작하지 않는다.** 외부 보존 위치는 아직 협의 중이며 실제 생성하지 않았다.

| 단계 | 만들어 다음 단계에 전달할 것 | 다음 단계의 조건 |
| --- | --- | --- |
| 준비 | 대상/설정 출처, 지원 도구, 배포물, 기존 설치 기준과 미확인 목록 | 요청 범위의 알려진 의존성 부재, 소유/경로 충돌이 해소됨. 확인 성공은 설치 완료가 아님 |
| 변경 계획 | 단위와 선행 조건, 파일/관리 항목별 변경 또는 보존 이유, 현재 기준, 별도 후보, 필요한 검사와 복원 범위 | 후보와 허용 범위가 대응하고 보호 원문, 미선택 기능을 변경하지 않음 |
| 적용 준비 | 같은 계획/단위의 적용 직전 사본, 예정 결과와 쓰기 순서, 새 적용 시도 | 기록과 사본을 확인한 뒤 원본 재대조. 다른 편집이 배제되지 않으면 적용 보류 |
| 반영 | 파일별 실제 관측과 미확인, 실패 지점 | [반영 기록 — 「반영 기록과 완료 연결」](update.md)을 사용. 복사 성공으로 다음 단위의 기능을 먼저 활성화하지 않음 |
| 연결 검증 | 필요한 검사 계획/시도의 참조, 실제 발견/호출, 보호 자료 확인과 남은 조건 | 같은 적용 결과에서 필수 검증이 충족됨. 별도 도구의 경로 읽기 성공만으로 Codex 접근을 통과 처리하지 않음 |
| 단위 완료 | 실제 반영 결과와 공유 설치 기준의 대응, 완료 근거 | 완료 표시와 기준 갱신이 중단되면 실제 파일까지 재대조. 유효한 독립 완료만 유지 |
| 요청 종료 | 완료, 복원, 보류/미착수, 미확인과 사용자의 다음 행동 | 필수 단위와 통합 확인이 끝나야 전체 완료. 실패 후 남은 적용은 합의 전 자동 진행하지 않음 |

검사가 명령 실행을 필요로 하면 [검증 기록 — 「계획 필드」](../workflow/records.md)의 계획/시도를 연결한다. 같은 종료 결과를 설치 기록에도 별도 PASS로 복제하지 않는다. 사용자 신뢰 확인처럼 아직 수행할 수 없는 조건은 사유와 함께 남기며 그 단위를 완료 처리하지 않는다. 단계별로 AI를 한 번씩 호출하는 구조가 아니라, 일반 코드가 자료를 전달하고 필요한 선택/의미 검토에서만 사람이나 메인에게 반환하는 흐름이다.

### 첫 기록 생성과 인계

11/17 사용자가 [최초 DB의 위치 전환 B — 「최초 인계 방식 재검토」](../workflow/storage.md)를 채택했다. 아래 첫 보존/제외/확인 순서는 유지한다. 초기 설치 전용 DB를 새 후보에 보존하고 수신, 원본 확인과 활성화 뒤 프로젝트에서 계속한다. 기존 정상 DB는 재사용하고 관계없는 DB와 자동 병합하지 않는다. 실제 Windows 설치/인계 구현은 아직이다.

11/16의 설계 후보다. 최초 설치에서 `.gitignore`를 고치기 전에는 프로젝트 상태 영역의 제외가 준비되지 않을 수 있다. 이때 기존 파일과 허용한 변경을 먼저 보존해야 하므로, **첫 제외 준비에 한정한 외부 보존 공간**을 비교한다. 추천 뒤 사용자가 진행을 요청해 사용자별 앱 데이터 후보를 기준으로 상세를 작성했다. 위치는 추천 상태이며 실제 생성이나 호스트 설정 변경은 하지 않았다. 모든 개발 기록을 사용자 홈으로 옮기는 안이 아니며, 일상 작업은 기존 `.harness/state/`를 사용한다.

| 보존 위치 | 이점 | 비용과 현재 판단 |
| --- | --- | --- |
| Windows 사용자별 로컬 앱 데이터의 제품 전용 하위 영역 | 매 설치마다 경로 입력 없이 같은 사용자 계정에서 중단 자료를 다시 찾기 쉬움 | 프로젝트 밖에 자료가 남으며 접근 확인과 정리 안내 필요. 기본 추천으로 상세 명세 작성, 실제 배치 전 |
| 설치할 때 사용자가 지정한 로컬 보존 폴더 | 사용자가 위치와 디스크를 직접 선택 | 입력과 경로 검사가 늘고 재실행 시 위치를 다시 찾을 수 있어야 함. 대안이며 기본/추가 지원 범위 미확정 |
| 자동 정리되는 임시 폴더 또는 종료 시 삭제되는 임시 객체 | 준비와 정리가 간단함 | 복구 자료의 지속 보존을 맡길 수 없어 유일한 보존 위치로 추천하지 않음. 일반 교체용 임시 파일과 구별 |

현재 제품 이름에 맞춘 최초 보존 위치는 실제 LocalAppData의 `OnepLoom/setup/<작업 식별자>/`다. 등록 프로그램 위치와 구분하며 현재 생성한 폴더는 아니다. [Windows Known Folders](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)는 LocalAppData를 사용자별 폴더로 정의하며 [SHGetKnownFolderPath](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)로 실제 위치를 조회할 수 있다. 특정 사용자명이나 C 드라이브를 하드코딩하지 않는다. 위치 조회 성공을 쓰기 권한, 안전한 보존이나 다른 기기로의 동기화 보장으로 취급하지 않는다.

[Python 임시 파일 문서](https://docs.python.org/3/library/tempfile.html)는 자동 정리되는 객체와 명시적으로 정리하는 저수준 API를 구분한다. 따라서 ‘임시’라는 이름만으로 보존/정리 시점을 판단하지 않는다. 외부 최초 보존 자료에도 [자동 보존과 명시적 정리 — 「복구 자료의 보관과 정리」](../workflow/recovery.md) 원칙을 적용한다. 미완료 자료를 설치기 종료나 다음 실행 시작 때 지우지 않는다.

위치 선택과 별개로 다음 순서를 지켜야 한다. 이는 공통 보존 원칙을 설치 시작에 연결한 명세이며 실제 Windows 구현/시험 결과가 아니다.

| 순서 | 확인하거나 남길 것 | 실패와 재실행 |
| --- | --- | --- |
| 읽기 준비 | 도구 의존성, 실제 코드/WIKI/상태 경로, 기존 추적/제외와 진행 기록. 기존 정상 상태가 있으면 그 기록을 사용 | 의존성 부재나 충돌은 안내하고 멈춤. 평소 개발, 정상 재개와 이미 준비된 갱신마다 외부 최초 공간을 만들지 않음 |
| 최초 보존 | 해당 작업/시도와 대상, 기존 `.gitignore`의 정확한 내용 또는 부재, 허용한 변경 후보와 복원 범위. 기록과 사본을 실제로 다시 읽어 대조 | 보존이 확인되기 전 프로젝트 파일을 수정하지 않음. 첫 보존이 불완전하면 다시 실행할 때 준비 완료로 읽지 않음 |
| 제외 적용 | 적용 직전 원본을 재대조한 뒤 허용한 변경만 반영. 기존 공유 제외 계약에 따라 실제 추적/제외 효력 확인 | 다른 편집, 접근 거부, 부분 반영이나 효과 불명은 기존 복구 계약으로 반환. 파일이 후보와 같다는 사실만으로 도구의 쓰기 소유를 단정하지 않음 |
| 프로젝트 기록 준비 | 제외가 유효한 뒤 새 후보에 초기 DB와 필요한 파일을 보존하고 내용/제약/참조를 검증 | 기존 DB를 덮거나 읽기 실패를 빈 새 DB로 대체하지 않음. 파일 기록이 끝났다는 사실을 설치 전체 완료로 처리하지 않음 |
| 인계 확인 | 같은 대상/작업과 필요한 참조, 보존 내용이 프로젝트 기록에서 다시 조회되는지 확인 | 인계 도중 끊기면 남은 양쪽 자료를 대조. 같은 최초 기록을 중복 등록하거나 시간만 보고 어느 사본이 원본인지 선택하지 않음 |

첫 보존에도 SQLite 기록 코드를 재사용하고 원문은 파일로 둔다. 보존할 항목은 [최초 자료 형식 — 「최초 보존 자료의 형식」](../workflow/records.md), 전달 순서는 [프로젝트 기록으로 인계](../workflow/records.md), 수신 식별과 중복/전환의 DB 관계는 [인계 저장 — 「최초 기록 인계의 저장」](../workflow/storage.md)이 소유한다. 초기 진행을 확정한 뒤 DB 전체 이력과 보관 파일을 [인계 목록 — 「인계 파일의 목록과 참조」](../workflow/storage.md)으로 대조하고, 수신과 원본 확인을 거쳐 활성화한 프로젝트 DB에서만 다음 설치를 진행한다. 논리 DB 식별과 revision을 초기화하지 않으며 이후 업데이트도 이 기록에 이어 쓴다. 외부에 남은 자료는 복구 근거이며 두 번째 장기 진행 원본이나 팀 공용 DB가 아니다.

예를 들어 `.gitignore` 적용과 프로젝트 DB 수신까지 끝난 직후 종료됐다면, 다음 실행은 같은 수신 기록을 대조해 인계 확인부터 마친다. 이미 적용한 제외를 다시 쓰거나 새 설치 작업을 중복 생성하지 않는다. 실제 파일이 달라졌거나 결과를 확인할 수 없다면 그 차이를 먼저 처리한다. 인계 완료는 설치 전체 완료나 파일/원격 변경의 자동 롤백을 뜻하지 않는다.

일반 설치 재실행은 명시한 프로젝트에 대응하는 미완료 초기 기록부터 확인한다. 서로 다른 설치 작업이 여럿이거나 프로젝트가 이동/교체돼 대상이 불명확하면 범위를 확인하며 가장 최근 폴더를 임의로 고르지 않는다. 재실행 위치와 보존 위치를 사용자가 다시 찾을 수 있도록 실패 출력과 README에서 안내한다. 읽기 전용 상태 조회가 새 DB나 새 설치 작업을 만들지는 않는다.

[Windows 실행 소유 후보 — 「실행 소유의 식별과 반환」](../workflow/recovery.md)는 프로젝트 상태 영역이 없어도 등록한 실제 코드 루트를 식별한다. 초기 진행 생성과 첫 제외 반영 전에 같은 반영 진입점에서 미완료 초기 기록을 재대조하며 인계와 정리에서도 기준을 바꾸지 않는다. 사용자 확인은 밖에서 받고 적용 전에 다시 확인한다. 잠금 이름, 접근이나 대상 식별이 실패하면 다른 임시 잠금으로 우회하거나 중복 설치 작업을 만들지 않는다. 이는 설치 순서의 보호 조건이며 실제 제품 구현 결과는 아니다.

외부 보존 폴더와 프로젝트가 다른 드라이브일 수 있으므로 단순 이동 한 번으로 안전한 인계를 보장하지 않는다. [Python 파일 교체 문서](https://docs.python.org/3/library/os.html#os.replace)도 다른 파일시스템 간 교체가 실패할 수 있음을 설명한다. 필요한 자료의 대상 측 저장과 내용/참조 확인이 끝나기 전 유일한 원본을 제거하지 않는다. 첫 `.gitignore`의 기존/신규 쓰기도 [파일 반영 후보 — 「기존 파일과 새 파일」](update.md)를 따르며 초기 외부 기록에 준비와 실제 결과를 남긴다. DB와 파일의 저장은 별도이고 실제 Windows 검증 전 전원 장애까지 무손실이라고 보장하지 않는다.

프로젝트 기록 준비가 실패해 로컬 자료가 남았다면 `.gitignore`부터 되돌려 자료를 노출시키지 않는다. 현재 남은 자료와 안전한 외부 보존을 확인한 뒤 허용된 복원 범위만 처리한다. 자동 인계가 자동 삭제나 모듈 제거를 뜻하지 않으며 정리 여부는 기존 명시적 정리 절차가 판단한다.

첫 설치 안내에는 실제 쓰는 외부 보존 위치와 목적을 표시한다. AI 안에서 설치를 호출할 때도 [호스트 권한 경계 — 「승인의 재사용과 한계」](entry.md)를 따르며 사용자 앱 데이터 전체의 쓰기 권한을 요구하는 방식으로 확대하지 않는다.

### 설치 완료 뒤 정리

11/16 사용자 채택: 최초 설치가 검증된 뒤 정리 가능한 자료를 차례로 제시하고, 사용자가 확인하면 그 묶음을 정리한다. **설치기 삭제가 필수 완료 단계는 아니다.** 11/23 구분에 따라 다른 프로젝트에 재사용할 배포본은 보관할 수 있고 PC의 시작 프로그램은 이 다운로드 정리 대상과 다르다. 복구 자료의 보호 원칙은 [보관과 정리 — 「복구 자료의 보관과 정리」](../workflow/recovery.md)를 사용한다. 여기서 완료는 파일 복사 종료가 아니라 요청한 설치 단위와 필수 연결 검증, 초기 자료 인계가 충족됐고 미확인/부분 반영이 남지 않은 상태다. 실행하지 않은 검사를 PASS로 두고 정리를 시작하지 않는다.

| 순서 | 사용자에게 보여주고 처리할 것 |
| --- | --- |
| 1. 완료 결과 | 설치된 기능, 검증 결과와 유지할 위치. 정리 가능 여부는 별도 표시 |
| 2. 외부 최초 보존 자료 | 해당 설치의 DB와 사본 묶음, 실제 경로, 예상 용량, 남는 프로젝트 기록과 삭제 영향. 인계와 참조를 확인한 후보만 제시 |
| 3. 다운로드/해제 자료 | 설치기 임시 사본 등 실제로 제거 가능한 별도 묶음. 공유 기준, 고정 원본 재확보와 현재 실행 의존이 있으면 보관 사유 표시 |
| 4. 최종 결과 | 삭제 완료, 보관 선택, 취소, 실패/미확인과 재실행 안내. 프로젝트 상태와 설치 자산이 유지됨을 확인 |

파일 하나마다 확인을 반복하기보다 함께 보존하거나 정리해야 할 자료를 묶는다. 질문에는 실제 대상과 삭제 영향을 먼저 보여주고 입력의 의미를 명시한다. 구체 입력안은 `삭제할까요? [y/N]`로, `y` 또는 `yes`는 삭제, Enter 또는 `n`/`no`는 보관이다. 사용자 예시의 Enter 상호작용은 지원하되 빈 입력을 무심코 삭제로 처리하지 않는 기본안이다. 잘못된 입력은 다시 안내하고, 취소, EOF, 무응답을 동의로 취급하지 않는다. 비대화 실행에서 대상과 연결된 명시적 확인이 없으면 자료를 보관한 채 후속 정리 방법을 반환한다. AI 진입에서 같은 대상과 영향을 보여주고 받은 확인은 공통 처리에 전달해 같은 질문을 반복하지 않는다. AI가 단순 설치 요청을 삭제 동의로 만들어 전달해서는 안 된다.

사용자 응답을 기다리는 동안 DB 쓰기 트랜잭션이나 파일 반영 잠금을 붙잡지 않는다. 응답 뒤에는 표시한 대상의 소유, 내용과 참조를 다시 확인하고 달라졌으면 기존 확인으로 삭제하지 않는다. 상위 폴더 전체를 지우거나 연결 경로를 따라 무관한 파일을 정리하지 않는다. 이 확인은 제품의 삭제 의사 확인이며 OS/AI 호스트가 실제로 요구하는 권한을 대신하지 않는다.

삭제 직전 허용한 묶음과 진행을 프로젝트 기록에 남기고 파일을 처리한다. 정리 도중 종료되면 이미 없는 파일, 남은 파일, 새로 바뀐 파일을 구분하며 기존 확인 범위를 확대하지 않는다. 재시도에 필요한 기록을 삭제할 외부 공간에만 두지 않는다. 보관, 취소 또는 정리 실패 때문에 설치를 반복하거나 설치 결과를 롤백하지 않으며 `설치 완료 / 정리 미완료`처럼 두 결과를 분리한다.

현재 실행 중인 설치기나 다음 명령에 필요한 파일을 안전하게 제거할 수 없다면 그 묶음은 보류한다. 별도 백그라운드 자기 삭제를 기본으로 추가하지 않고 종료 후 설치된 정리 기능으로 처리할 수 있게 안내한다. 프로젝트의 `.harness/state/`, 설치된 실행 파일/설정, 갱신 비교 기준, 사용자 코드와 WIKI는 이 설치 후 정리에서 제거하지 않는다. 파일별 대상과 남길 기록은 [정리 명세 — 「정리 대상과 남길 기록」](../workflow/maintenance.md)에 연결했다. 11/17에 채택한 완료 작업의 큰 자료 정리도 같은 확인/보호 절차를 사용하되, 원래 실패/성공 이력과 정리 사실을 남기고 잃는 재검증/복원 범위를 보여준다. 정확한 명령과 Windows 삭제/재실행 동작은 구현과 시험으로 확인한다.

### 기능 추가의 연결

첫 선택 기능인 설명/학습 문서 확장은 위 설치 절차를 다시 사용한다. 기능 목록, 기존 버전과 경로를 읽고 해당 역할의 안내, 템플릿과 필요한 절차만 후보에 포함한다. 이미 같은 기능이 설치되어 있고 연결이 유효하면 현재 상태를 알려주고 중복 파일, hook 등록이나 빈 문서를 만들지 않는다.

새 기능이 현재 기반과 호환되면 그 단위와 필요한 연결만 변경한다. 기반 업데이트가 필요하면 그 의존 변경을 같은 계획에 보여주고 범위를 확인한다. 기능 추가 요청만으로 전체 버전 업그레이드, 다른 기능 활성화나 WIKI 상세 분석을 시작하지 않는다. 사용자에게 같은 질문을 반복하라는 뜻이 아니라 처음 허용한 변경과 달라졌는지를 확인하는 조건이다.

예를 들어 기존 요구사항/ADR을 사용하는 프로젝트에 설명 문서 기능을 추가하면, 기존 본문은 보존하고 설명 역할을 실제 선택한 경로와 연결한다. 기존 설명 문서가 있다면 새 사본을 만들기보다 채택 가능 여부를 확인한다. 새 내용을 작성할 때 필요한 폴더와 인덱스를 함께 갱신하며 설치만으로 예상 도메인 폴더나 문서 본문을 채우지 않는다. 구체 문서 역할은 [선택 확장 — 「선택 확장과 실행 방식」](../module.md), 실패/재개는 [부분 완료 — 「적용 단위와 부분 완료」](update.md)를 따른다.

### 팀 도입과 기기별 준비

11/11 확인한 **Git 공유의 운영 구분**이다. 프로젝트 도입, 갱신은 작업 담당자가 준비하고 검토한 결과를 공유하며 팀원은 그 결과를 받아 사용한다. 담당자는 영구히 한 사람으로 고정되는 역할이 아니며 이후 다른 팀원이 맡아도 된다. 여러 사람이 다른 범위를 작업할 때도 기존 후보 분리, 단일 반영, 충돌 검토 기준을 유지한다.

| 단계 | 담당자가 준비할 결과 | 다른 팀원이 할 일 |
| --- | --- | --- |
| 최초 도입 | 필요한 하네스 설치, 프로젝트 연결, 요청한 범위의 WIKI 복원/보강, 실제 동작과 기존 자료 보존 검증 | 검토, 반영된 프로젝트 설치 결과와 팀 WIKI를 받음 |
| 일상 사용 | 팀 공통 파일, 지식 변경을 기존 검토/공유 절차로 관리 | 자신의 실행 도구, 계정 권한, WIKI 로컬 경로, 필요한 신뢰만 준비하고 공유 결과 사용. 로컬 작업 상태는 각 작업 공간에서 생성 |
| 공식 모듈 갱신 | 공유된 이전 설치 기준, 현재 프로젝트 편집, 새 공식 배포를 비교하고 후보/검증 결과를 공유 | 검토, 반영된 변경을 받아 사용. 새 의존성, 신뢰 변경이 있다면 해당 기기 조건만 확인 |

팀 공용 WIKI는 권한이 있는 팀원이 사용할 수 있는 공유 원본과 동기화 경로가 있어야 한다. 사용자 환경에서는 별도 private WIKI 저장소를 사용하며, 앱 저장소만 pull했다고 외부 WIKI까지 갱신됐다고 판단하지 않는다. 관련 변경은 [앱, WIKI 작업 연결 — 「저장과 공유 흐름」](../sync.md)에서 정한 작업/버전 대응으로 확인한다. 두 저장소의 commit, merge는 원자적이지 않으므로 필요한 두 결과가 준비, 검증되기 전에 팀 도입/갱신 완료로 표시하지 않는다. 작업용 브랜치의 중간 커밋까지 금지하거나 최초 이식이 끝날 때까지 모든 이력 저장을 미루는 뜻은 아니다.

기기 준비는 공유 결과의 재생성, 개인 자격증명의 공유와 구분한다. 자동화 가능한 준비는 제공 수단 설계에 포함하되, 기존 권한, hook 신뢰 확인을 우회하거나 clone만으로 모든 환경 준비가 끝난다고 보장하지 않는다. 팀원은 [프로젝트 연결과 시작 — 「설치부터 관리까지의 호출 순서」](entry.md)을 사용하며 프로젝트 초기화/WIKI 복원을 다시 수행하지 않는다. 명령이 없는 사용자는 아래 [공식 배포 자료 — 「팀원 첫 준비의 배포 자료」](install.md#%ED%8C%80%EC%9B%90%20%EC%B2%AB%20%EC%A4%80%EB%B9%84%EC%9D%98%20%EB%B0%B0%ED%8F%AC%20%EC%9E%90%EB%A3%8C)로 자기 Windows 계정의 명령을 먼저 준비한다. 필요한 실행 의존성은 [지원 조건 — 「지원 조건의 확인 순서」](install.md#%EC%A7%80%EC%9B%90%20%EC%A1%B0%EA%B1%B4%EC%9D%98%20%ED%99%95%EC%9D%B8%20%EC%88%9C%EC%84%9C)에 따라 해당 기기에서 확인한다.

11/23 [사용자별 프로젝트 목록 — 「등록과 이동, 목록 제거」](project-selection.md)을 채택 흐름에 맞춰 구체화했다. 설치 담당자와 다른 팀원 모두 자신의 기기 준비에서 확인한 작업 사본을 등록하며 팀 전체가 같은 절대 경로나 목록을 공유하지 않는다. 준비 과정은 별도 수동 입력을 반복시키지 않고 같은 등록 처리를 호출한다. 목록 저장 실패는 설치/연결 결과와 구분해 남기고 재등록 방법을 안내한다. 이를 프로젝트 재설치로 해결하거나 모든 준비 완료로 숨기지 않는다. 정상 대상의 현재 위치/명시 경로 시작은 유지한다. 목록 파일/관리 명령은 [프로젝트 선택 명세](project-selection.md)가 소유하고, 목록 제거와 실제 설치 결과/기기 명령 제거는 구분한다.

11/15 보강: 배포 README에는 팀원이 처음 사용할 때 아래 절차를 반드시 거치도록 별도 진입을 둔다. 설치 담당자뿐 아니라 각 팀원의 새 기기/작업 사본이 대상이다. 이미 유효한 등록과 허가가 있으면 재사용하며 매 실행마다 다시 입력하는 절차는 아니다.

1. **공유 결과 받기:** 코드 저장소와 필요한 WIKI 저장소에서 팀이 공유한 설치 결과와 문서를 받는다. private WIKI의 Git 접근 권한은 각자 준비한다. 설치 기준 파일을 팀원이 직접 점검하거나 설치를 재실행하는 절차는 아니다. 담당자의 `.harness/`, DB, 절대 경로를 복사하지 않는다.
2. **자기 기기 연결:** 명령이 없으면 공식 배포 자료로 한 번 등록하고, 프로젝트에 설치된 연결 절차가 공유 설정을 읽는다. 내부 WIKI는 코드 루트 기준 상대 경로로 해결하므로 새 경로 입력이 불필요할 수 있다. 외부 WIKI는 그 팀원의 로컬 위치를 최초 등록하고 `.harness/local.json`에 보존한다. 이미 유효한 등록이 있으면 재사용하며 누락/잘못된 원본은 빈 WIKI로 대체하지 않는다.
3. **실제 실행 확인:** 자기 도구와 계정, 필요한 프로젝트/hook 신뢰, 실제 Codex의 WIKI 접근을 확인한다. Git 읽기 권한과 CLI의 로컬 파일 접근 권한은 구분한다. 기록된 허가를 재사용하되 다른 팀원의 승인을 승계했다고 처리하지 않는다.
4. **사용과 변경:** 준비한 연결을 제품의 시작/재개에서 재사용한다. 일반 codex에서 이미 권한이 충분하면 그대로 사용하고 부족한 기능은 연결 대안을 안내한다. 두 경로의 성공을 혼동하지 않는다. WIKI 이동/새 clone은 해당 연결만 다시 검사/등록하며 경로 등록 자체로 clone/pull, WIKI 생성이나 Obsidian 실행을 수행하지 않는다.

기본 지속 연결은 ADR 0022의 제품 시작/재개 명령으로 처리하며, 팀원별 [최초 실행 선택과 재사용](entry.md)을 적용한다. WIKI 경로와 필요한 반복 실행 선택은 자신의 로컬 연결에 두고 Codex 전역 설정을 수정하지 않는다. 프로젝트 config의 새 생성, 공유 원본 분리나 Git 제외를 이 기본 경로의 필수 단계로 요구하지 않는다.

앞서 비교한 [프로젝트 로컬 권한 설정 — 「지속 권한 설정의 배치」](entry.md)과 [Git 로컬 제외 — 「로컬 제외의 자동 처리」](entry.md)는 해당 대안의 검토 내용이다. 선택 MCP를 제공할 때는 그 등록 범위와 기존 config 소유를 따로 대조한다. 이미 추적한 config에 개인 경로를 넣거나 추적 해제하지 않고 기존 공유 방식을 유지하며, 기존 sandbox/사용자 정책을 무조건 변환하거나 여러 clone의 경로를 한 권한에 누적하지 않는다.

Codex가 요구하는 프로젝트 신뢰는 해당 도구의 사용자 절차로 진행하며 모듈이 전역 trust 값을 쓰지 않는다. 실제 TUI가 사용자 선택에 따라 자체 신뢰 기록을 저장하는 것과 모듈이 전역 설정을 수정하는 것은 구별한다. 새 팀원이 준비할 사항은 실행 README에 명시하고 설정 조회/합성 제외 시험을 일반 Codex 사용 완료로 확대하지 않는다.

예를 들어 같은 private WIKI를 한 팀원은 `C:/Work/team-wiki`, 다른 팀원은 `D:/Projects/team-wiki`에 둘 수 있다. 같은 설치 결과와 공유 문서를 사용하되 로컬 연결과 실행 DB는 각자 관리한다. Obsidian은 선택 편집기이므로 팀원이 설치하지 않아도 이 연결을 사용할 수 있어야 한다. 일반 CLI와 열린 Codex 안의 입력 방식은 [기존 연결 절차 — 「일반 Codex에서 연결하기」](entry.md)를 사용하고 로직을 다시 만들지 않는다.

### 팀원 첫 준비의 배포 자료

**현재안: 공식 Release의 명령을 Windows 사용자 계정마다 한 번 준비하고, 적용 프로젝트 Git에는 wheel을 기본 포함하지 않는다.** 11/23 전체 정리에서 사용자가 위임한 재평가 기준에 따라 B안을 채택했다. [공식 사례와 대안 비교](../../discussions/runtime/distribution.md), [결정 이력 — 「첫 준비 자료의 배포 결정」](../../decisions/runtime/0023-command-registration.md)을 근거로 하며 실제 Windows 구현 완료를 뜻하지 않는다.

| 대상 | 처음 필요한 일 | 이후 재사용 |
| --- | --- | --- |
| 최초 도입 담당자 | 외부 관리 도구의 프로젝트 설치 안에서 명령 등록까지 함께 처리 | 같은 계정의 다른 프로젝트에서 명령을 다시 설치하지 않음 |
| 새 팀원 또는 새 Windows 사용자 계정 | 같은 공식 배포 자료의 `command install`로 명령만 준비 | 기존 프로젝트의 설치/전체 WIKI 복원을 반복하지 않음 |
| 이미 유효한 명령이 있는 사용자 | 프로젝트의 `connect`로 자기 WIKI와 필요한 실행 조건을 연결 | 같은 작업 사본의 유효한 경로/선택은 재입력하지 않음 |

여기서 기기는 **현재 Windows 사용자 계정의 프로그램 환경**을 뜻한다. 담당자의 명령 등록이 다른 팀원의 PC에 전파되지는 않는다. 팀원에게 가상환경, pip, PATH와 등록 JSON을 각각 조작하게 하지 않고 [관리 도구의 한 실행 — 「시작 명령만 처음 준비하기」](management.md)이 처리한다. 프로젝트별 WIKI 연결은 별도 로컬 값이므로 각자의 위치와 권한을 확인해야 한다.

공식 배포와 프로젝트에 복사되는 OnepLoom 자산에는 [ADR 0025](../../decisions/development/0025-license.md)에 따른 MIT 저작권 고지와 허가문을 포함한다. 고지는 OnepLoom 전용 설치 영역에서 보존하고, 사용자의 기존 루트 LICENSE나 WIKI 라이선스를 덮어쓰지 않는다. 외부 자산에 별도 고지가 필요하면 해당 조건도 유지한다.

공식 배포에는 외부 `oneploom.py`, 연결용 wheel, 검증할 출처/파일 기준과 필요한 고지를 넣는다. wheel은 작은 프로젝트 발견/인계 프로그램이며 하네스 본체가 아니다. 프로젝트의 `oneploom/`에는 편집 가능한 skill, script, 공유 설정과 설치 기준이 남는다. 새 clone에서 이 기준을 읽되 wheel, 가상환경과 다른 사람의 `.harness/`를 복사하지 않는다. `oneploom/bootstrap/`에 wheel을 넣던 이전 상세는 [관측 기록 (정리 전 기록)](../../evidence/experiments/design/2026-11-23_07-38-22-wiki-reconcile.md)에 보존하며 현재 설치 계약으로 사용하지 않는다.

준비에 쓸 wheel은 릴리스의 정확한 파일로 확인한다. 실제 파일명은 [PyPA wheel 규격](https://packaging.python.org/en/latest/specifications/binary-distribution-format/)의 공식 배포명/버전/호환 태그를 따른다. 폴더의 첫 파일, 임의의 최신 파일이나 다른 프로젝트가 요구하는 버전으로 자동 전환하지 않는다. 이미 등록한 명령과 프로젝트의 호환성은 [프로젝트 인계](project-entry.md)에서 검사한다. 같은 프로젝트의 소스 편집은 명령 재빌드/재설치 사유가 아니다.

기본 흐름에서 최초 공식 자료 확보는 필요하다. 오프라인 사용자는 미리 준비한 동일 배포 자료로 등록할 수 있지만, clone만 받아 모든 기기의 준비가 끝난다고 약속하지 않는다. `connect`가 몰래 원격 파일을 내려받거나 기기 명령을 설치/갱신하지 않는다. 명령 준비가 안 된 경우에는 필요한 공식 자료와 다음 명령을 안내하고, 준비된 프로젝트 실행 파일의 명시 경로 사용도 유지한다.

다운로드 폴더와 wheel은 정상 등록/설치가 확인되고 미완료 작업이나 복원에서 참조하지 않을 때 [설치 뒤 정리 — 「설치 완료 뒤 정리」](install.md#%EC%84%A4%EC%B9%98%20%EC%99%84%EB%A3%8C%20%EB%92%A4%20%EC%A0%95%EB%A6%AC) 대상으로 보여줄 수 있다. 다른 프로젝트 설치나 오프라인 복구에 쓸 사용자는 보관한다. 삭제해도 설치된 사용자 명령, 프로젝트 하네스와 WIKI는 유지돼야 한다. 새 기기 준비/복구 때 자료가 없다면 같은 공식 배포본을 다시 확보해야 한다.

[표준 등록 처리 — 「표준 명령 등록 후보의 흐름」](entry.md)의 Python/venv/pip 준비, 외부 다운로드 차단, 출처와 소유 확인, 중단 뒤 대조를 그대로 적용한다. SHA-256 일치만으로 배포자를 신뢰하지 않는다. 외부 구현 코드는 이번 조사에서 복사하지 않았으며 실제 배포에 포함하는 Python 패키지, 생성 실행 파일과 고지는 해당 파일/버전별로 검증한다.

### AGENTS와 Git 추적 선택

11/11 팀 공통 자산의 Git 공유 권장과 기존 추적 정책 보존을 채택했다. 파일이 있는 위치, Codex가 읽는 방법, Git 추적, 공개 여부는 다른 판단이다. [공식 AGENTS 지침](https://learn.chatgpt.com/docs/agent-configuration/agents-md)은 사용자 공통 위치와 프로젝트 루트부터 현재 작업 위치까지의 탐색을 설명한다. 임의의 외부 폴더에 AGENTS를 두는 것만으로 그 프로젝트 지침이 되지는 않는다. 프로젝트 규칙을 사용자 전역 지침에 넣어 다른 프로젝트로 전파하지 않는다.

| 현재 상태, 선호 | 설치 후보 | 남는 조건 |
| --- | --- | --- |
| 기존 AGENTS 또는 등록된 지침이 있음 | 위치, 내용, 추적 상태를 보존하고 필요한 연결 차이만 제시 | 추적/비추적 변경, override 생성으로 원문 가리기를 자동 수행하지 않음 |
| 지침이 없고 팀이 같은 규칙을 공유함 | 프로젝트 루트에 짧은 AGENTS 후보를 만들고 Git 공유를 추천 | 실제 stage, commit은 별도 작업. 공개 범위는 저장소 정책을 따름 |
| 지침이 없고 개인 로컬 사용을 원함 | 같은 루트 AGENTS를 로컬 전용으로 두고 합의한 제외 수단을 연결 | 다른 기기/팀원/CI는 따로 준비. 자동 발견과 Git 공유를 동일시하지 않음 |
| 프로젝트 안에 지침 파일 자체를 두지 않길 원함 | 외부 지침과 명시적 시작/도구 연결을 별도 검토 | 일반 codex 실행의 발견, 권한, 재개를 따로 검증. 같은 자동 동작을 미리 보장하지 않음 |

공개된 실제 예로 [Cloudflare Workers SDK의 AGENTS](https://github.com/cloudflare/workers-sdk/blob/main/AGENTS.md)는 저장소에 빌드, 검사, 경로별 작업 안내를 둔다. 파일 내용도 기존 설정을 원본으로 삼고 중복 목록이 낡지 않게 하도록 안내한다. 이 사례가 모든 회사의 공개 정책을 뜻하지는 않는다. 이 하네스의 AGENTS 역시 프로젝트 작업의 최소 안내와 근거 연결을 맡기며 개인 대화, 전체 WIKI, 자격증명을 모아 넣지 않는다.

11/11 공식 저장소 확인: [Microsoft VS Code의 AGENTS](https://github.com/microsoft/vscode/blob/main/AGENTS.md)는 공개 Git에 있으며 [상세 작업 지침](https://github.com/microsoft/vscode/blob/main/.github/copilot-instructions.md)으로 연결한다. 대기업의 공개 프로젝트에도 AI 작업 지침을 코드와 함께 공개한 사례가 있다는 근거다. 기업 내부의 비공개 프로젝트나 모든 문서의 공개 정책을 추정하는 근거는 아니다. `AGENTS.md`라는 파일명 자체를 숨기는 것보다 실제 공개할 내용의 범위를 정하는 것이 중요하다는 것이 이 설계의 판단이다.

팀이 함께 사용할 설치 skill, script, 검사 설정, 비밀 없는 설치 기준, 공동 AGENTS는 프로젝트 Git 공유를 추천한다. 새 clone에서도 설치 기준과 변경 소유를 대조할 수 있어야 하며, `.harness/`의 개인 복구 사본만 있어야 갱신 가능한 구조로 만들지 않는다. 재생성할 수 없는 생성 기준은 적절한 공유 범위에서 보존해야 한다. 실제 stage, commit, 공개는 설치와 별도다.

공개 여부는 WIKI/비WIKI라는 확장자, 폴더 분류만으로 정하지 않는다. 공개 코드의 빌드, 검사, 규칙과 일반 실행 코드는 공개 후보지만, script, config에도 내부 주소, 개인 경로, 비공개 정책이 들어갈 수 있다. 실제 비밀값은 어느 문서/저장소에도 넣지 않는다. 사용자의 앱 WIKI, ADR, 의미 있는 작업 기록은 기존 private WIKI 방침을 따르고, active, 임시 후보, 개인 실행 기록은 로컬 제외를 유지한다. `.gitignore`로 팀 공통 실행 자산까지 일괄 숨기는 안을 추천하지 않는다.

개인 제외에는 실제 Git 경로의 `info/exclude`, 팀 공통 제외에는 `.gitignore`를 사용할 수 있다. [Git 문서](https://git-scm.com/docs/gitignore)에 따르면 이미 추적한 파일에는 ignore가 적용되지 않으므로 기존 추적 파일을 숨기려고 제외만 추가하거나 자동 untrack하지 않는다. 추적 상태, 기존 정책과 의도가 불명확할 때만 설치 중 선택을 확인하고 갱신 때 유지한다. 로컬 제외는 접근 권한 통제나 다른 기기로의 동기화를 제공하지 않는다.

이미 합의한 `.harness/` 로컬 상태 제외와 원문 보호는 별개로 유지한다. 기존 설정이 이 필수 조건과 충돌하면 조용히 바꾸지 않고 해당 설치를 멈춰 차이와 선택을 제시한다.

### 기존 구성과 전용 설치 영역

11/11 **기존 도구의 발견 위치를 유지하고 그 안의 모듈 전용 항목과 프로젝트 내 전용 실행 폴더를 조합하는 원칙**을 채택했다. 파일 종류별로 기존 자산 사이에 모두 흩어 놓는 안보다 소유와 정리가 쉽고, 모든 파일을 임의 폴더 하나에 넣는 안에서 생기는 발견 문제를 줄인다. 등록 지점과 실행 코드 폴더를 연결하는 비용은 남지만 둘 다 프로젝트 안의 설치 결과이며 외부 공통 실행본을 다시 도입하는 뜻은 아니다.

11/13의 파일/소비자 대응과 AGENTS 최소 연결 A, 11/22 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 직접 접근 우선/MCP 후속 제공은 [진입 설계](entry.md)가 상세를 소유한다. 기존 규칙과 충분한 권한을 재사용하며 정확한 실행 명령, 지원 설치 형식과 제품 구현 완료는 후속이다.

```text
프로젝트/
├── AGENTS.md                         기존 공동 지침, 필요한 최소 연결 후보
├── .agents/skills/onep-check/SKILL.md  도구가 찾는 위치의 모듈 전용 skill 예시
├── .codex/hooks.json                 기존 형식에 필요한 모듈 hook 항목만 추가
├── tools/onep_harness/               설치된 script, 설정, 설치 기준의 전용 영역
└── .harness/                        개인 상태, 후보, 복구 자료, Git 제외
```

위 `onep-check`, `onep_harness`, `tools`는 설명용 이름이다. 배치 원칙은 채택했고 정확한 이름, 경로, 파일명은 미확정이다. 기존 `tools`가 없다는 이유로 빈 하위 구조를 모두 만들지 않는다. WIKI는 기존 내부 문서나 등록한 외부 저장소를 사용하므로 위 예시에 새 문서 트리를 강제하지 않는다.

- 지원 도구가 실제 발견하는 위치, 기존 등록, 동일 이름을 먼저 확인한다. Codex는 [공식 skill 경로](https://learn.chatgpt.com/docs/build-skills)에서 skill을 찾으며 같은 이름을 자동 병합하지 않는다. 임의의 사용자 경로가 모두 자동 호환된다고 보장하지 않고, 기존 위치가 미지원이면 별도 연결 후보를 설명한다. 전용 폴더와 skill 이름은 충돌을 줄이는 수단이지 충돌 부재의 증명은 아니다.
- AGENTS는 기존 범위, 내용을 유지하고 필요할 때 최소 연결 차이만 제시한다. 전용 폴더에 별도 AGENTS를 넣는 것만으로 프로젝트 전체에 적용되지는 않는다. [공식 지침 탐색](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- hook은 기존 JSON 또는 TOML 표현을 존중해 필요한 항목만 추가한다. 전체 파일 교체나 다른 출처의 기존 hook 비활성화는 하지 않는다. [공식 hook 안내](https://learn.chatgpt.com/docs/hooks)에 따르면 출처가 여러 개면 함께 로드되므로 중복과 실행 순서를 확인하고 필요한 사용자 신뢰를 우회하지 않는다.
- 전용 폴더 안에도 사용자가 추가한 파일이 있을 수 있다. 폴더 전체를 모듈 소유로 간주하지 않고 설치기가 만든 파일/등록 항목과 이전 기준을 기록한다. 이름이 같고 소유 근거가 없으면 덮지 않으며 기존 사용자 skill, script는 설치/갱신/제거 대상에서 제외한다.
- skill은 조사, 의미 판단, 절차 안내를 맡을 수 있지만 파일 소유 확인, 차이 생성, 쓰기 범위 제한, 충돌 차단은 일반 코드의 검사로 보장하는 설계가 필요하다. 좋은 프롬프트만으로 원문 보호가 보장됐다고 판단하지 않는다.

단순한 읽기, 구문 검사와 별도로 새 clone, 하위 경로에서 시작, 기존 같은 이름/여러 hook 출처, 사용자 파일 추가, 이동, 후속 갱신, 제거에서 실제 연결과 보존을 검증해야 한다. 정확한 지원 경로, 계약은 파일별 명세에서 정한다.

### 프로젝트 설치 위치 후보

11/22 사용자가 프로젝트 루트 바로 아래의 `oneploom/`을 제안했고, 설치 도구와 프로젝트에 남는 파일, Git 공유와 인터넷 공개를 구분한 설명 뒤 그 방향으로 진행하도록 확인했다. **신규 설치의 기본 위치는 대상 코드 프로젝트 루트의 `oneploom/`이다.** 기존 프로젝트 파일을 여기로 이동시키는 규칙은 아니다. 이름은 [제품 이름과 변경 기준](../module.md), 공유 범위는 [AGENTS와 Git 추적 선택](install.md#AGENTS%EC%99%80%20Git%20%EC%B6%94%EC%A0%81%20%EC%84%A0%ED%83%9D)을 따른다.

여기서 상대 경로의 시작점은 **설치 대상으로 확정한 코드 프로젝트의 루트**다. Git 저장소를 대상으로 하면 해당 작업트리의 루트와 등록한 프로젝트를 대조한다. 설치기를 내려받은 위치, 현재 터미널 위치, WIKI 루트나 여러 저장소를 모아 둔 상위 작업 폴더를 자동으로 시작점으로 삼지 않는다. 예를 들어 `C:\work\shop\backend`를 대상으로 선택했다면 기본 위치는 `C:\work\shop\backend\oneploom`이다. 같은 상위 폴더에 있는 `frontend`와 `wiki`는 별도 대상이며 이 설치에 따라 같이 바뀌지 않는다.

| 위치 | 장점 | 비용과 판단 |
| --- | --- | --- |
| **`oneploom/`** | 최상위에서 제품의 설치 영역을 찾고 Git 변경을 검토하기 쉬움. 불필요한 상위 폴더가 없음 | 기본 배치. 프로젝트 최상위에 폴더가 하나 생기며 기존 동명 경로와 소유 확인은 필요 |
| `tools/oneploom/` | 팀이 이미 쓰는 도구 폴더 아래로 모을 수 있음 | 이전 추천. 팀 규칙에 맞춰 선택할 대안이며 `tools` 자체가 고유성을 보장하지 않음 |
| `.oneploom/` | 최상위에서 모듈 파일을 한 폴더로 찾을 수 있음 | 공유할 실행 파일인데 개인 설정 폴더로 오해하기 쉽고, 이미 채택한 `.harness/` 로컬 영역과 시각적으로 비슷함 |

`공유할 설치 결과`는 해당 프로젝트의 팀원이 Git으로 함께 관리할 파일을 뜻한다. PC의 여러 프로젝트가 하나의 변경 가능한 하네스 실행본을 쓰는 배치가 아니다. 설치/갱신용 다운로드는 프로젝트 밖에서 준비하고, 평소 사용할 실행 파일은 프로젝트에 남긴다. 임시 다운로드의 정리 조건은 [설치 완료 뒤 정리](install.md#%EC%84%A4%EC%B9%98%20%EC%99%84%EB%A3%8C%20%EB%92%A4%20%EC%A0%95%EB%A6%AC)가 소유한다.

OnepLoom은 설치하며 소유를 기록한 항목만 관리한다. `oneploom/` 안의 사용자 파일이나 대안 경로의 `tools` 전체를 소유로 취득하거나 삭제/일괄 무시하지 않는다. 기존 `tools/other-tool/`과 함께 존재하는 것만으로 충돌하지 않는다. 같은 이름의 파일, 프로젝트 밖으로 향하는 링크, 소유가 확인되지 않은 자료가 있으면 아래 충돌 확인과 다른 경로 선택 절차를 따른다. 고유한 이름을 선택했다는 이유로 이 검사를 생략하지 않는다.

채택한 기본 위치의 배치 예시다. 세부 파일명과 제품 구현, 실제 명령 등록은 남아 있다.

```text
프로젝트/
├── AGENTS.md                              기존 지침에 필요한 진입 연결만 반영
├── .agents/skills/oneploom-<역할>/SKILL.md
├── .codex/hooks.json                      필요한 hook이 있을 때 기존 등록에 연결
├── oneploom/                              팀이 공유할 설치 결과
│   ├── cli.py                            프로젝트 실행 진입점
│   ├── project.json                      공유할 연결 설정 후보
│   └── ...                               필요한 처리 코드, 규칙, 설치 기준
└── .harness/                             기기별 설정, 작업 상태와 복구 자료
```

11/23 후속 명세에서 `cli.py`를 [프로젝트 실행 진입점 — 「프로젝트 실행본으로 넘기는 입력」](project-entry.md)으로 구체화했다. 실제 하위 코드 분리는 책임과 사용처가 생길 때 정하며 빈 폴더/예상 기능 파일을 먼저 만들지 않는다. 기본 외 위치는 기존 로컬 연결의 `module_path`로 보존하며 새 clone의 첫 준비도 [같은 절차 — 「처음 준비와 위치 변경」](project-entry.md)에 연결한다. WIKI는 등록한 기존 내부/외부 위치를 유지한다. `.harness/`에는 공유 실행 코드나 WIKI를 넣지 않으며 현재 로컬 상태의 기본 이름을 새 브랜드로 교체하지 않는다.

기기의 짧은 명령은 11/23 [표준 Python 등록](../../decisions/runtime/0023-command-registration.md)을 채택했다. 릴리스에 작은 명령 연결용 wheel을 포함하고 사용자 전용 환경에서 준비하며, 프로젝트 실행 파일과 WIKI의 소유 위치는 위 구조를 유지한다. 배포용 다운로드의 정리와 계속 사용할 등록 환경의 제거를 구별한다. 기기 준비도 완료/미완료를 나눠 안내하고 [등록과 갱신의 중단 복구](entry.md)를 따른다. [등록 소유 정보 — 「기기 등록 정보와 소유」](entry.md)와 기존 DB 참조의 문서 명세를 연결했으며 실제 저장/반영 구현과 제품 설치는 아직이다.

Codex가 프로젝트 skill을 찾는 기본 위치는 현재 [공식 안내의 `.agents/skills`](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)를 기준으로 한다. skill의 실제 지침은 발견 위치에 한 벌만 두고 프로젝트 script/규칙을 필요할 때 참조한다. 같은 skill을 전용 실행 영역과 발견 경로에 복제하거나 심볼릭 링크를 필수 준비물로 만들지 않는다. 기존 지원 위치를 사용하는 프로젝트는 현재 설치본의 발견 여부를 확인해 보존하며 새 기본 위치로 강제 이동하지 않는다.

hook은 [현재 프로젝트 등록 형식](https://learn.chatgpt.com/docs/hooks#where-codex-looks-for-hooks)에 필요한 항목만 연결한다. 기존 `config.toml`에 같은 역할의 hook이 있으면 새 `hooks.json`에도 중복 등록하지 않는다. `AGENTS.md`에는 기존 [최소 연결 원칙 — 「AGENTS 연결 방식」](entry.md)을 적용한다. 전용 폴더 안의 파일만으로 프로젝트 전체의 지침/skill이 자동 발견된다고 가정하지 않는다. 공식 안내가 재사용 배포에 plugin을 권장하는 것과, 우리 설치 결과를 프로젝트에서 직접 수정/공유하려는 소유 정책은 구별한다. 이 경로 조사로 기존 배포 결정을 plugin 방식으로 변경하지 않는다.

설치 경로 선택과 이후 실행의 연결은 다음 조건을 만족해야 한다.

1. 설치 전에 같은 이름의 파일/폴더, 대소문자만 다른 경로, Git 추적과 무시 규칙, 기존 등록과 링크의 실제 대상을 확인한다. 소유 근거 없는 파일은 내용이 같아도 덮거나 모듈 소유로 편입하지 않는다. 기존 `.harness/`도 이름만으로 새 모듈 소유라고 판단하지 않는다.
2. 기본 경로가 사용 중이거나 팀 규칙에 맞지 않으면 프로젝트 안의 다른 전용 경로를 선택할 수 있게 한다. 프로젝트 밖 경로/링크를 공통 실행본으로 자동 채택하거나 `.gitignore`를 임의 해제하지 않는다. 경로 검사와 후보 차이 확인은 기존 설치 절차를 따른다.
3. 채택한 설치 상대 위치와 소유 기준은 기존 [설치 기록 — 「설치 기록과 단계 연결」](install.md#%EC%84%A4%EC%B9%98%20%EA%B8%B0%EB%A1%9D%EA%B3%BC%20%EB%8B%A8%EA%B3%84%20%EC%97%B0%EA%B2%B0)에 한 번 연결한다. AGENTS, skill, hook, 명령 진입점이 같은 설치본을 소비하는지 검사한다. 실행 때마다 폴더 이름을 추측하거나 고정된 `parents[n]` 계산으로 대상 프로젝트를 정하지 않는다.
4. 단축 명령은 현재 대상 프로젝트의 설치본으로 연결돼야 한다. 먼저 등록한 프로젝트 A의 경로를 전역 별칭에 고정해 프로젝트 B에서도 A를 실행하는 방식은 사용하지 않는다. 프로젝트를 확정할 수 없으면 선택을 요구하고 마지막 사용 프로젝트로 자동 대체하지 않는다. 기기 등록은 [표준 등록 명세 — 「짧은 명령의 등록과 프로젝트 선택」](entry.md), 대상 확정 뒤 발견/인계는 [프로젝트 실행본](project-entry.md)을 따른다. 실제 Windows 검증은 남아 있다.
5. 새 clone에서는 공유 설치본을 그대로 사용하고 로컬 WIKI/실행 선택만 준비한다. 사용자가 설치 위치를 옮겼다면 지침/skill/hook과 저장된 기준의 불일치를 먼저 해결하며 새 기본 경로에 또 설치하지 않는다. 업데이트, 제거는 폴더 전체가 아니라 기록한 소유 항목을 대상으로 한다.

예를 들어 기본 경로의 프로젝트 루트에서는 `py -3 .\oneploom\cli.py start`가 명시 경로 진입의 후보가 된다. `oneploom start`는 같은 처리를 호출할 편의 명령의 목표이며 아직 등록되거나 검증된 명령이 아니다. 둘의 차이는 파일을 찾는 방법이고 WIKI/권한 판단 코드를 두 벌 만들지 않는다. Windows 하위 폴더 진입, 명령 충돌, 두 프로젝트 전환과 실제 skill/hook 발견은 [수용 입력 — 「명명과 설치 위치의 검증 입력」](../../verification/acceptance.md)에서 확인한다.

### 프로젝트별 값의 연결

**프로젝트에 설치한 공통 코드도 프로젝트 값을 입력으로 받아 동작할 수 있다.** 논리적 분리를 위해 실행 파일을 물리적으로 밖에 둘 필요는 없다. 원본, 명시적 정책/보정, 파생 결과의 경계는 [ADR 0004 — 「어디에 있든 분류할 프로젝트 종속성」](../../decisions/architecture/0004-portability.md)를 따른다.

공식 배포본에는 실행할 파일과 생성용 템플릿이 있을 수 있다. 설치는 선택한 기능의 실행 파일을 프로젝트에 놓고 프로젝트 값, 기존 지침, 문서 연결을 준비한다. 템플릿으로 생성한 파일도 프로젝트에 남으며 사용자가 수정할 수 있다. 이후 일상 트리거는 그 설치 결과를 사용하고 템플릿으로 매번 덮지 않는다.

| 프로젝트 차이 | 연결, 수정 위치 |
| --- | --- |
| 검사 명령, 경로, 예외가 다름 | 기존 빌드/정책 원본과 필요한 설정을 설치된 검사 script가 읽음. 같은 값의 skill, hook, config 복제 방지 |
| AI가 따를 검토 순서, 정책이 다름 | 프로젝트에 설치된 skill, 지침을 수정. 설정만으로 표현하도록 강제하지 않음 |
| hook 시점, 상태 위치가 다름 | 기존 hook 형식의 관리 항목에서 프로젝트 내 처리 코드와 입력을 연결 |
| 설정으로 표현되지 않는 처리 변경 | 설치된 script를 수정하거나 프로젝트 소유 확장을 추가. 공식 코어에 특정 프로젝트명 분기를 요구하지 않음 |

평소 흐름은 `프로젝트 skill/hook → 프로젝트의 처리 script + 프로젝트 입력 → 결과와 로컬 상태, 허용한 WIKI 작업`이다. skill의 설정 참조는 실제 읽기 절차로 연결해야 하며 파일을 만들었다고 AI가 자동으로 읽거나 본문 변수가 치환되지는 않는다. 같은 이름의 skill 추가가 자동 대체를 뜻하지 않으므로 기존 연결과의 중복도 검사한다. [공식 skills](https://learn.chatgpt.com/docs/build-skills).

설치된 파일 안의 사용자 편집과 모듈이 만든 항목을 구분한다. 새 사용자 파일은 쓰기 대상에서 제외하고, 모듈 설치 파일을 수정한 경우에는 공식 갱신과 대조한다. 상세는 [skill과 hook의 업데이트](update.md)에 있다. 이름이 전용 폴더 아래에 있다는 사실이나 동일한 본문만으로 소유를 추정하지 않는다.

11/09 현재 코드의 읽기 확인에서는 프로젝트 hook, 두 단계 상위로 루트를 계산하는 검사 script, `sample-*` 선택 규칙, `docs/followup/active` 고정 상태가 관측됐다. 이는 당시 코드의 사실이며 통째 복사한 결과가 다른 프로젝트에서 동작한다는 근거가 아니다. 설치 위치가 아니라 확인한 대상 루트, 문서 역할, 검사 입력을 연결하고, 이름, 경로, 명령이 다른 두 프로젝트에서 공식 배포본 수정 없이 설치, 동작하는지 검증해야 한다.

### 최초 설치에서 만드는 것

11/09 후속 질문에 대한 협의안이다. 최초 설치는 선택한 기능을 실제로 사용할 최소 실행 구성, 도구 진입 연결, 프로젝트 설정, 설치 기준을 준비한다. 기존 지침이나 설정이 있으면 변경 후보를 먼저 비교한다. 설치에 필요한 폴더와 실제 문서 진입점은 만들 수 있지만 예상 도메인별 빈 폴더, 빈 ADR, 전체 WIKI 본문을 일괄 생성하지 않는다.

기존 WIKI는 먼저 등록하고 없는 역할을 미확인으로 표시한다. 새 프로젝트는 확인된 초기 요구, 규칙과 문서 진입점부터 시작한다. 기능별 문서와 하위 폴더는 실제 내용을 만들 때 함께 연결하며, 상세 역공학은 사용자가 범위, 모델을 정해 별도로 실행한다. 이 차이는 [프로젝트별 분류 — 「프로젝트별 분류를 정하는 과정」](../knowledge/documents.md)와 [도입 경로 — 「제품의 중심과 도입 경로」](../architecture.md)를 따른다.

설치 완료는 모든 WIKI 내용의 완성을 뜻하지 않는다. 경로 등록만 하고 실제 hook, skill, 검사, 재개 연결을 확인하지 않은 상태도 설치 완료로 취급하지 않는다. 선택 기능은 의존성을 확인하며 이후 추가할 수 있고, 새 버전이 나왔다는 이유만으로 미선택 기능을 켜지 않는다.

## 기존 자료 보존

기존 시험 프로젝트는 기존 지식을 채택하는 경로를 사용한다. 분석기는 기존 자료를 읽어 위치, 근거, 불일치를 찾고, 없는 정보의 후보만 만든다. 기존 문서를 더 깔끔하게 다시 쓰거나 번호를 재배열하는 일을 설치에 포함하지 않는다.

| 대안 | 장점 | 단점, 판단 |
| --- | --- | --- |
| A. 전체 재생성 후 Git diff 검토 | 출력 형태를 통일하기 쉬움 | 미추적/ignored 자료는 Git만으로 복구 불가. 의미, 링크, 역사 유실 위험이 커 비추천 |
| B. 기존 자료 보호 + 별도 후보 — 원칙 채택 | 원문을 지키며 불일치, 새 내용을 검토 가능 | 자동 완료 범위가 줄고 필요한 규칙 변경을 따로 검토해야 함 |
| C. 다른 경로로 복사해 새 WIKI 운영 | 구문서 사본이 남음 | 두 원본, 깨진 참조, 갱신 불일치 발생. 임시 시험 이외에는 비추천 |

채택한 보존 원칙을 구체화할 설치 계약은 다음과 같다. 상세 기록, 잠금 수단은 후속 명세다.

1. 대상 루트, 적용 범위를 정하고 기존 파일 목록, 내용 해시, 관련 링크를 기록한다. 보존 대상은 Git 추적 여부와 무관하며, 스냅샷 범위에서 제외된 자료도 수정 대상에 넣지 않는다. 민감 자료를 외부로 전송하지 않는다.
2. 기존 WIKI, ADR, 현재 프로젝트 규칙은 보호 대상으로 분류한다. 새 파일도 같은 이름이 있으면 덮지 않는다. 새로운 ADR 후보는 기존 번호와 충돌하지 않아야 한다.
3. 분석, 문서 후보 생성은 대상 원문을 쓰지 않는 별도 단계로 수행한다. 기존 버그, 옛 논의를 최신 요구사항이나 채택 ADR로 자동 승격하지 않는다.
4. 설치 계획에 생성, 갱신, 보존, 충돌을 구분하고 적용 대상의 이전 해시를 고정한다. 원문 변경 없이 공통 기능을 연결할 수 없으면 충돌을 보고하고 활성화를 보류한다.
5. 적용 직전에 해시를 다시 확인한다. 계획 후 편집이 발생했거나 다른 설치가 실행 중이면 중단한다. 폴더 복사/동기화의 삭제 옵션이나 강제 덮어쓰기를 기본 동작으로 두지 않는다.
6. 허용된 변경만 기록하며 적용한다. 파일별 임시 쓰기/교체와 작업 기록을 사용하되 여러 파일 전체가 자동으로 원자적이라고 주장하지 않는다. 중간 실패 상태에서 실행되지 않도록 활성화와 설치 완료 표시를 구분한다.
7. 보호 파일의 존재, 내용 해시와 링크, 공통 기능의 연결을 대조한다. 의도하지 않은 차이가 있으면 설치 성공으로 닫지 않는다. 승인한 규칙 변경은 보호 원문과 별도의 허용 목록, 차이로 검증한다.
8. 복원은 해당 설치가 바꾼 파일만 대상으로 한다. 설치 이후 사용자가 편집했다면 자동 덮어쓰기 복원을 멈추고 차이를 보존한다. 실제 복원 시험을 거치기 전에는 무손실을 보장했다고 하지 않는다.

특히 기존 `AGENTS.md`에 새 규칙을 넣어야 하는 경우에는 **검토 가능한 수정 후보**를 먼저 만든다. `AGENTS.override.md`를 몰래 만들어 기존 규칙을 가리는 방식도 사용하지 않는다. 보호된 문서가 그대로라는 사실과 새 하네스가 모순 없이 활성화됐다는 사실은 각각 확인한다.

기존 `.codex` 파일은 설치 기록이 없으므로 새 모듈의 소유라고 추정하지 않는다. 최초 채택에서는 어떤 파일을 대체할지 원본, 차이, 복원 범위를 따로 확인하고, 이후 업데이트부터 기록된 해시로 공통 설치 파일을 관리한다. 분석, 갱신, 제거에서도 사용자 문서를 함께 삭제하지 않는다.

더 이상 쓰지 않는 공통 설치 파일은 소유 기록, 현재 해시가 일치하고 제거 계획에 포함된 경우에만 정리한다. 소유가 불명확한 파일이나 사용자가 편집한 파일은 자동 삭제하지 않는다. 과거 hook/skill 연결을 남겨 새 연결과 이중 실행되는 경우도 이전 계획에서 처리한다.

보존 설계의 근거, 대안은 [ADR 0011](../../decisions/runtime/0011-preservation.md)에 둔다. 백업은 보조 수단이며 비의도적 변경을 허용하는 근거가 아니다.

### 동시 편집과 반영

11/09 기본 메인 순차 진행, 별도 후보, 단일 반영과 보존 방향을 사용자가 수용했다. 아래의 구체 권한, 잠금, 교체, 복구 수단은 미구현 후보이며 실제 차단/무손실 검증은 남아 있다. 역할, 폴더 분리는 충돌 방지 장치가 아니며 설치와 WIKI 갱신 모두 기존 원문 보존 조건을 따른다. 같은 파일의 덮어쓰기, 다른 파일 사이의 의미 충돌, 오래된 입력으로 만든 후보, 여러 파일의 부분 반영을 구분한다.

1. **입력 고정:** 코드와 WIKI의 기준 revision뿐 아니라 선택 범위의 미커밋, 미추적 입력도 식별한다. 분석 중 원문이 바뀌면 혼합된 시점의 결과로 닫지 않고 영향 단위를 다시 확인한다. 항상 전체 저장소를 복사해야 한다는 뜻은 아니며 필요한 근거를 재확인할 기준을 남긴다.
2. **후보 분리:** 보조는 작업별 상세 초안, 근거, 변경 제안만 반환하고 원본 WIKI나 위치표, 같은 로컬 작업의 active를 직접 갱신하지 않는다. 공통 요구, 이벤트 계약처럼 겹치는 기능은 소유 단위를 정하고 다른 단위는 참조/수정 제안을 반환한다. 결합이 크면 같은 단위로 묶거나 순차 처리한다. 서로 다른 파일로 나눴다는 이유만으로 독립 처리하지 않는다.
3. **반영 경로 단일화:** 메인이 의미, 범위, 충돌을 대조한 뒤 실행 코드가 허용된 변경 묶음을 해당 로컬 작업 사본에 반영한다. 같은 로컬 작업의 중복 반영, 늦은 결과를 확인한다. 팀원별 별도 작업 사본의 독립 작업은 서로 기다리지 않고 Git, PR 흐름으로 통합한다.
4. **변경 감지와 쓰기 조정:** 반영 전 현재 원문과 후보의 기준을 대조하고 다르면 덮지 않는다. 다만 해시 확인과 쓰기는 별개 동작이므로 그 사이의 외부 편집까지 막는 장치는 아니다. 첫 지원 후보는 짧은 반영 구간에서 다른 편집자의 동일 대상 쓰기가 없는 조건이다. 이 조건을 확보, 검증할 수 없으면 후보만 보존하고 자동 반영하지 않는다. 분석 중 원문 편집까지 항상 금지하는 안은 아니다.
5. **부분 반영과 복구:** 변경 목록, 이전/이후 상태, 반영 진척을 기록하고 문서와 연결표를 한 검증 단위로 대조한다. 여러 파일의 쓰기를 한 번의 원자적 갱신으로 보고하지 않는다. 부분 반영이면 하네스의 해당 갱신 완료, 후속 실행을 보류하고 복구한다. 이후 사용자가 바꾼 파일은 자동 되돌리기로 덮지 않으며 차이를 보존해 해결한다. 일반 편집기의 화면까지 여러 파일을 동시에 전환하는 보장은 별개다.

WIKI가 프로젝트 안에 있든 별도 저장소이든 각자의 로컬 파일을 편집하고 Git으로 공유한다. [로컬 편집과 Git 공유 — 「WIKI의 로컬 편집과 Git 공유」](../workflow/recovery.md)가 이 경계를 소유한다. 공통 조정 폴더를 요구했던 제안은 철회했으며 설치/협의의 대기 항목으로 남기지 않는다. 기존 로컬 실행 기록, 반영 기준 대조, 원문 보호는 유지한다.

‘수정하지 말라’는 지시와 실제 원문 쓰기 권한의 제한은 다르다. WIKI 복원에서는 분석 실행을 원문 읽기 중심으로 제한하고 결과 저장/반영을 별도 코드가 맡는 구성을 검토한다. [Codex 공식 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls)는 native subagent가 부모 sandbox를 상속하며 agent 지시만으로 별도의 읽기 전용 sandbox가 생기지 않는다고 설명한다. 실제 차단은 지원 실행기에서 확인해야 한다.

Windows Obsidian, 다른 CLI, 동기화 도구가 모듈의 잠금 규칙을 지킨다고 가정하지 않는다. 로컬 잠금은 협조하는 실행끼리의 조정이며 다른 기기의 clone까지 제어하지 않는다. 팀 Git 작업은 별도 브랜치/작업 사본의 제안을 현재 대상 기준으로 병합, 검토하는 흐름을 사용하고, 같은 공유 폴더의 무제한 동시 편집을 첫 지원 범위로 두지 않는 것을 추천한다. WIKI Git과 앱 Git의 연계가 두 저장소의 원자적 변경을 뜻하지는 않는다.

실제 기능 코드를 여러 작업자가 수정하는 경우에는 별도 작업 사본이 필요할 수 있다. [Git worktree](https://git-scm.com/docs/git-worktree)는 작업 트리를 분리하지만 둘이 같은 외부 WIKI 경로를 참조하면 문서는 분리되지 않는다. `git worktree lock`도 작업 트리 관리 정보의 정리를 막는 명령이며 문서 편집 잠금이 아니다. [Git merge](https://git-scm.com/docs/git-merge#_how_conflicts_are_presented)의 텍스트 병합 성공은 서로 다른 문서의 의미가 맞는다는 증거가 아니다. 같은 기능의 코드 변경은 첫 지원에서 한 담당 흐름으로 처리하고 독립 조사, 검토만 나누는 편이 단순하다.

반영 수단과 실제 실행 환경은 [Windows 반영 보호](../workflow/recovery.md)와 [파일 반영과 핸들 수명](update.md)에서 구분한다. 같은 핸들 쓰기는 중단 때 부분 내용이 남을 수 있고 임시 파일 교체는 확인/교체 사이 편집을 별도로 막아야 한다. 어느 수단도 문서 묶음 전체의 트랜잭션을 대신하지 않는다. 사용 중 hook/script의 반영, 호스트 재로드와 실제 동작 검증도 남아 있다.

필요한 검증 사례는 같은 원문의 두 후보, 다른 파일 사이 계약 충돌, 계획 후 Obsidian 편집, 반영 구간의 쓰기 조정, 동일 WIKI의 경로 별칭/복수 세션, 파일 묶음 중간 실패, 실패 후 사용자 편집, 늦은 결과의 중복 반영이다. 모두 미실행이며 실제 검증 전 무손실, 동시성 해결 완료를 주장하지 않는다.

## 실제 로드 확인

10월 28일의 설치 흔적과 11월 9일에 다시 확인한 공식 지원 기능을 구분한다. 채택 버전에서 확인해야 할 조건이며 제품 설치본을 실제 검증한 결과가 아니다.

- `AGENTS.md`: 프로젝트 루트부터 현재 작업 디렉토리까지 지침을 찾는다. override, 용량, 상위 지침의 영향도 확인해야 한다. 기존 파일을 바꿨다면 새 실행에서 실제 읽은 지침을 확인한다. [공식 지침 탐색](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- skills: 공식 repo 탐색 위치는 `.agents/skills`다. 이 세션에 `.codex/skills`가 제공된 사실만으로 일반 배포 호환성을 확정하지 않는다. 두 위치에 같은 skill을 무조건 복제하지 않고 선택한 지원 버전에서 한 경로로 발견되는지 확인한다. [공식 skill 경로](https://learn.chatgpt.com/docs/build-skills).
- hooks: 프로젝트 `.codex/hooks.json`을 사용할 수 있다. 프로젝트 계층과 변경된 hook의 신뢰 확인이 필요하며, 여러 출처의 hook은 함께 로드될 수 있다. plugin, 전역, 프로젝트에서 같은 처리를 중복 실행하지 않는지 확인한다. 설치가 신뢰 승인을 우회하지 않는다. [공식 hook 로드, 신뢰](https://learn.chatgpt.com/docs/hooks).

2026-10-28에 읽은 로컬 npm 메타데이터는 Codex `0.165.0`이었다. 당시 제품의 `.codex/hooks.json`에는 PreCompact, PostCompact, SessionStart 연결이 있었고 정의만 확인했다. 11/10의 별도 0.167.0 시험은 [비교 이력 — 「Codex 연결 시험 결과」](../../discussions/history/install.md)에 구분한다. 기존 제품의 모든 hook이나 최초 지원 버전 전체를 검증한 것으로 확대하지 않는다.

### 문맥과 토큰 비용

외부 설치라는 파일 위치만으로 모델 호출이 추가되지는 않는다. 경로 해석, 등록, 버전 확인은 일반 코드로 처리할 수 있다. 다만 AI가 명령이나 결과를 읽는 비용은 남으며 총사용량이 반드시 같거나 줄어든다고 단정하지 않는다.

[Skill의 단계적 읽기](https://learn.chatgpt.com/docs/build-skills)는 초기 이름, 설명, 경로와 사용 시 읽는 본문을 구분한다. 비교할 것은 실제 들어간 지침/메타데이터, 본문, 도구 출력, 탐색/재시도다. 전역 기능 과다 등록, 프로젝트와 plugin의 중복 지침, 긴 경로/로그, 실패 후 추가 탐색은 차이를 만들 수 있다. 같은 모델, 기능, 입력, 읽기 범위, 검사 기준으로 초기 문맥과 전체 작업 사용량을 비교해야 하며 현재 실측은 없다. 보관 위치가 같다는 이유로 문맥이 같다고 보거나, Git 비추적을 모델 비공개로 오인하지 않는다.

## 유지할 요구와 남은 책임

11/11 채택한 B는 **외부에서 준비한 Git 릴리스의 Python 도구로 프로젝트 실행 파일을 설치와 갱신하는 수단**이다. 예전 외부 실행본의 상시 사용과 구분한다. 다음 조건은 유지하며 제품 구현, 검증은 아직이다.

| 유지할 요구 | 현재 구성 | 남는 책임 |
| --- | --- | --- |
| 공식 SOT, 독립 프로젝트 적용 | 하나의 공식 릴리스에서 선택 기능을 각 프로젝트에 설치 | 한 프로젝트의 수정/갱신이 다른 프로젝트를 바꾸지 않음. 사용할 출처가 없으면 조용히 최신판으로 대체하지 않음 |
| 간단한 평소 사용, 자유 수정 | 일반 프로젝트 CLI에서 설치된 skill, script, hook 사용, 사용자 직접 수정 허용 | 지원 발견 위치, 기기별 준비, hook 신뢰, 재개, 실제 동작 검사 |
| 지침, WIKI, 편집, Git 정책 보존 | 모듈 소유 변경과 사용자 자료를 구분해 후보에서 대조 | 최초 채택, 충돌, 부분 실패, 후속 편집과 새 clone의 기준 확보 |
| 최소 구성, 기능 추가, 상세 WIKI | 선택한 기능과 의존 파일만 설치. WIKI 분석은 별도 요청 | 설치를 전체 AI 분석으로 확대하거나 미선택 기능을 자동 활성화하지 않음 |
| 도구 확장, 기한 내 배포 | 공통 정책과 Codex 연결을 논리적으로 분리하고 첫 제공 수단 하나에 집중 | 여러 플랫폼/설치 모드, 자동 의미 병합을 선행 구현하지 않음 |

공식 버전은 모듈 유지보수자가 발행한다. 사용자 수정에 별도 모듈 버전을 요구하지 않으며 설치 출처와 실제 편집 상태는 [갱신과 복원](update.md)에서 구분한다. 이전 실험의 프로젝트 이름, 버전은 [비교 이력](../../discussions/history/install.md)에 보존하며 제품의 실제 릴리스 이력과 구별한다.

공식 skills/hooks의 지원 경로를 쓰더라도 중복, 권한, 신뢰, 실행은 확인해야 한다. 외부 설치 사본을 지운 뒤에도 프로젝트의 하네스 기능이 동작해야 하며, Codex, 언어 실행기 같은 명시한 의존성까지 없어진다는 뜻은 아니다. 이전 작은 시험을 이 배치의 실사용 통과로 사용하지 않는다.
