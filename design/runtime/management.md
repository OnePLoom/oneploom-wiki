# 설치와 명령 관리

11/23 파일별 명세다. [사용자 조작 최소화 원칙 — 「사용자 조작을 줄이는 실행 원칙」](../architecture.md)을 최초 설치와 기기 명령 관리에 적용한다. 아래 명령은 **구현에 사용할 설계이며 아직 실행 가능한 배포물이 아니다.** Git Release + Python, 프로젝트 내 실행 구성과 표준 명령 등록의 채택을 구체화하며 다른 배포 수단이나 자동 업데이트를 추가하지 않는다.

## 진입과 사용자가 할 일

Git 릴리스의 관리 도구 진입 파일을 `oneploom.py`로 명세한다. 내려받은 배포 폴더에 두고 절대 경로로 호출하며 이 파일 자체를 PATH에 올리지 않는다. 평소의 `oneploom`은 이미 등록한 시작 명령이고, 인자 없이 `start`를 수행한다. 설치기와 시작 명령이 이름 일부를 공유해도 무인자 동작을 합치지 않는다.

| 목적 | 기본 진입 | 사용자에게 필요한 행동 |
| --- | --- | --- |
| 새 프로젝트 도입 | 외부 `oneploom.py install` | 프로젝트/WIKI 등 해결되지 않은 입력과 기능을 선택하고 실제 변경 계획 확인. 내부 파일 배치와 연결을 직접 하지 않음 |
| 새 팀원/새 계정의 명령 준비 | 외부 `oneploom.py command install` | 명령만 한 번 등록한 뒤 프로젝트별 `connect`. 공유 하네스/WIKI를 다시 설치하지 않음 |
| 평소 개발 | 등록한 `oneploom` | 준비된 현재 프로젝트에서는 바로 시작. 프로젝트 밖에서는 기존 목록 선택 규칙 적용 |
| 현재 Windows 사용자 계정의 시작 명령 복구 | 외부 `oneploom.py command repair` | 복구 대상과 필요한 변경만 확인. 기존 프로젝트 설치/전체 WIKI 분석을 반복하지 않음 |
| 시작 명령 제거 | 외부 `oneploom.py command remove` | 같은 계정의 모든 프로젝트에서 짧은 시작 명령을 못 쓰게 된다는 영향과 실제 제거 범위를 확인 |

기본 문법은 다음과 같다. `PATH`는 설명용 자리이며 그대로 입력할 값이 아니다. 대괄호는 선택 옵션이다.

```text
py -3 "<배포 폴더>\oneploom.py" install [--project PATH] [--preview [--json]]
py -3 "<배포 폴더>\oneploom.py" command install [--preview [--json]]
py -3 "<배포 폴더>\oneploom.py" command repair [--preview [--json]]
py -3 "<배포 폴더>\oneploom.py" command remove [--preview [--json]]
```

`py -3`은 Windows 안내의 예이며 지원 Python 준비와 실제 선택을 먼저 확인한다. 배포 도구 위치는 해당 파일에서, 프로젝트 대상은 [기존 대상 규칙 — 「설치기와 시작 명령의 대상 확인」](entry.md)에서 해결한다. `install --project`를 생략하면 현재 위치의 프로젝트 루트를 확인하며 여러 하위 프로젝트를 재귀 탐색해 자동 설치하지 않는다. `command` 관리는 현재 사용자 등록을 대상으로 하고 프로젝트 선택을 요구하지 않는다. `--project`, 세션 ID나 Codex 인자를 이 관리 명령에 붙이면 잘못된 입력으로 처리한다.

관리 도구의 무인자 실행은 도움말만 표시한다. `--help`, `--version`도 도움/배포본 정보만 반환하고 프로젝트, WIKI, DB, 권한 변경이나 AI 호출을 시작하지 않는다. 오타, 축약 옵션, 중복 대상과 미지원 명령을 추정 실행하지 않는다. 하위 명령 뒤의 옵션 배치와 오류 안내는 [기존 명령 규약 — 「명령과 설정의 표준 적용」](entry.md)을 사용한다.

첫 설치의 WIKI/기능 입력과 AI 진입의 확인 전달은 아래 [같은 계획 확인 — 「CLI와 AI에서 같은 계획 확인하기」](management.md#CLI%EC%99%80%20AI%EC%97%90%EC%84%9C%20%EA%B0%99%EC%9D%80%20%EA%B3%84%ED%9A%8D%20%ED%99%95%EC%9D%B8%ED%95%98%EA%B8%B0)으로 연결한다. 위 문법은 기본 진입이며 준비/적용의 비대화형 옵션은 해당 절이 소유한다. 무인 대량 설치, 임의 Python 자동 교체나 모든 향후 관리 기능의 CLI까지 완성한 것은 아니다.

## 최초 설치와 같은 요청의 재실행

정상 설치에서는 **한 번의 관리 도구 호출 안에서 필요한 입력 → 계획 확인 → 적용과 검사 → 완료 안내**로 이어진다. 사용자에게 가상환경 생성, pip 실행, 설치 파일 복사나 등록 JSON 편집을 각각 시키지 않는다. 부족한 선행 프로그램은 [의존성 준비 — 「의존성 준비와 설치 재개」](install.md)대로 공식 준비 방법을 알리고 멈춘다. 이 두 상황을 구분한다.

1. 배포본의 출처/지원 조건, 대상 프로젝트와 기존 설치를 확인한다. 입력이나 저장값으로 이미 해결한 내용은 다시 질문하지 않는다. 경로를 추측해야 하는 경우에는 선택을 받는다.
2. 선택 기능에 필요한 준비물을 함께 점검하고 생성/변경/보존/충돌을 나눈 계획을 제시한다. 프로젝트 파일 반영과 기기 명령 등록의 영향은 한 안내에서 구분한다. 이미 유효한 기기 등록은 재사용하고 다시 만들지 않는다.
3. 같은 계획의 허용을 받은 뒤 기존 [설치 단계 — 「설치부터 평소 사용까지」](install.md)와 [등록 처리 — 「표준 명령 등록 후보의 흐름」](entry.md)를 호출한다. 내부 단계가 넘어갈 때마다 승인을 다시 받지 않는다. 새 권한/비용/충돌/범위 변경이 생기면 해당 변경만 알려 선택받는다. 제품의 계획 확인이 OS나 Codex의 승인을 대신하지 않는다.
4. 설치, 연결, 현재 명령의 사용 가능 여부를 확인하고 결과를 나눠 안내한다. 현재 셸이 옛 PATH를 유지해 새 창 확인이 필요하면 그 행동만 안내한다. 작업을 자동 시작하거나 AI 검증 비용을 숨겨 발생시키지 않는다.
5. 필수 완료 뒤 [정리 확인 — 「설치 완료 뒤 정리」](install.md)을 제시한다. 보관/취소를 선택해도 설치 결과를 유지한다. 정리는 설치 허용과 별개의 삭제 의사이며 정상 사용의 필수 과정이 아니다.

같은 명령을 다시 실행하면 [설치 상태별 판단 — 「설치기 위치와 재실행 판단」](install.md)을 사용한다. 정상 완료면 변경 불필요와 시작 방법을 안내하고, 중단 작업이면 기록과 현재 결과를 대조해 유효한 완료 부분을 재사용한다. 사용자에게 DB 경로나 내부 작업 ID를 찾아 입력하게 하는 것을 기본 절차로 만들지 않는다. 여러 기록/clone이 충돌하면 프로젝트, 목적과 진행 상태로 선택을 받으며 도구가 내부 식별자로 연결한다. 안내하는 재실행 명령은 확인된 대상과 배포본을 포함하고 셸에 맞게 경로를 표현한다.

동일한 설치 요청의 재실행은 자동 업데이트나 완료된 WIKI의 재분석 요청이 아니다. 다른 릴리스/기능/사용자 편집은 기존 비교와 선택으로 처리한다. 새 선택을 줄이겠다는 이유로 다른 작업의 기록을 재사용하거나 누락된 기준을 생성하지 않는다.

## 시작 명령만 처음 준비하기

`command install`은 새 팀원이나 새 Windows 사용자 계정에서 **시작 명령만** 등록한다. 공식 배포 자료를 사용하며 프로젝트, WIKI 또는 Codex 로그인은 이 등록의 선행 조건이 아니다. 최초 담당자의 `install`도 명령 등록이 필요하면 같은 등록 절차를 내부에서 호출한다. 프로젝트 설치 뒤 별도의 동일 등록을 다시 요구하지 않는다.

1. 배포 출처와 정확한 wheel, 지원 Python/venv/pip, 현재 계정의 명령/소유/미완료 등록을 확인한다. 최초 설치에 필요한 준비가 빠졌다면 공식 준비 방법을 안내하고 멈춘다.
2. 유효한 호환 등록이 있으면 변경 불필요를 반환한다. 동일 등록의 중단이면 기존 기록과 실제 상태로 재개한다. 출처 불명 파일이나 다른 명령을 자동 덮지 않는다. 기존 등록의 손상은 `command repair`, 버전 불일치는 명시적인 변경 계획으로 연결하며 최신화/다운그레이드를 몰래 수행하지 않는다.
3. 등록할 프로그램 위치와 명령/PATH 변경 범위를 한 계획으로 보여주고, 같은 범위의 확인을 재사용한다. 일반 사용자는 JSON이나 pip 명령을 작성하지 않는다. 실제 처리는 [표준 등록 — 「표준 명령 등록 후보의 흐름」](entry.md)과 [등록 복구 — 「등록과 갱신의 중단 복구」](entry.md)를 사용한다.
4. 명령 등록 결과를 확인한 뒤 프로젝트의 `oneploom connect`를 안내한다. 새 셸이 필요한 경우만 그 행동을 설명한다. 기기 명령 준비와 프로젝트 WIKI 연결 완료를 같은 성공으로 표시하지 않는다.

사용자는 새 계정에서 한 번 준비하고 여러 프로젝트에 재사용한다. 실제 등록 파일/기록의 소유는 [등록 정보 — 「기기 등록 정보와 소유」](entry.md)와 [저장 경계 — 「기기 등록 효과의 저장 경계」](../workflow/storage.md)가 정하며, 별도 상시 기기 DB를 추가하지 않는다. 프로젝트 없는 등록이 끝나도 필요한 근거는 보존/명시적 정리 규칙을 따른다. 아래 준비/적용 규약은 `command install`에도 동일하게 적용한다.

## CLI와 AI에서 같은 계획 확인하기

11/23 후속 명세다. **일반 CLI는 한 실행 안에서 필요한 입력, 계획 확인과 적용을 이어가고, AI 진입은 같은 계획을 준비한 뒤 사용자가 확인한 그 계획을 적용한다.** 사용자에게 내부 식별자를 외우거나 두 번 같은 질문에 답하도록 요구하지 않는다. 두 경로의 계획 작성, 확인 저장과 반영 코드는 같으며 질문을 보여주는 부분만 다르다.

| 처리 방식 | 이점 | 비용과 이번 판단 |
| --- | --- | --- |
| 매번 현재 입력으로 계획을 다시 만들고 포괄적 yes 전달 | 인자가 짧음 | 보여준 내용과 적용할 내용이 달라질 수 있어 사용하지 않음 |
| 별도 계획 JSON 파일을 내보내고 다시 가져옴 | 다른 도구가 파일을 전달하기 쉬움 | 기존 DB와 두 번째 원본, 보관/유출/변조 대조가 생김. 기본으로 추가하지 않음 |
| 기존 DB의 고정 계획과 확인 범위를 참조 | 보여준 계획과 적용 대상의 대응, 중단 뒤 허용 재사용 가능 | 계획의 보존과 현재 상태 대조 필요. 이번 구체화에 적용 |

[Terraform의 저장 계획 적용](https://developer.hashicorp.com/terraform/cli/commands/apply#saved-plan-mode)은 검토한 계획을 별도로 적용하고 추가 계획 옵션을 섞지 않는 공개 동작의 참고다. OnepLoom은 Terraform의 파일 형식이나 코드를 가져오지 않고 기존 작업 DB를 사용한다. 이 사례가 사용자의 동의 진위나 우리 Windows 반영의 안전성을 증명하는 것은 아니다.

### 입력과 준비, 적용의 구분

기존 기본 명령에 아래 동작을 연결한다. 아래는 구현 명세이며 현재 실행할 제품 명령이 아니다. 파일 또는 표준 입력으로 데이터를 전달하는 옵션은 `--input FILE`과 `--input -`다. 표준 입력은 다른 프로그램이 내용을 넘기는 통로이며 일반 사용자의 정상 설치에는 JSON 작성을 요구하지 않는다.

```text
oneploom.py install [--project PATH] [--input FILE|-] [--preview|--prepare] [--json]
oneploom.py install --apply --input FILE|- [--project PATH] [--json]
oneploom.py command install [--preview|--prepare] [--json]
oneploom.py command install --apply --input FILE|- [--json]
oneploom.py command repair [--preview|--prepare] [--json]
oneploom.py command repair --apply --input FILE|- [--json]
oneploom.py command remove [--preview|--prepare] [--json]
oneploom.py command remove --apply --input FILE|- [--json]
```

실제 외부 호출에는 앞 절의 Python과 배포 파일 경로를 붙인다. `--preview`, `--prepare`, `--apply`는 서로 함께 사용할 수 없다. 초기 입력을 새로 받는 준비와 이미 고정한 계획을 적용하는 입력도 섞지 않는다. `--apply`의 `--project`는 계획에 고정된 실제 대상을 대조하는 선택 옵션이며 대상을 바꾸지 않는다. 불일치하거나 새 기능/WIKI 경로를 함께 넘기면 입력 오류다. `--json`은 숨은 질문을 띄우지 않는다. 필요한 선택이 빠졌다면 `needs_input`과 `required_inputs`를 반환한다.

| 동작 | 저장과 결과 |
| --- | --- |
| 옵션 없는 대화형 설치/관리 | 필요한 입력을 받은 뒤 내부에서 계획 준비와 확인, 적용을 연결. 같은 대상/계획의 유효한 확인은 재사용 |
| `--preview` | 기존 읽기 전용 조회 유지. DB/후보 생성, 환경/PATH 변경이나 AI 호출 없음. 적용에 쓸 계획 참조를 발급하지 않음 |
| `--prepare` | 현재 조건과 입력을 확인하고 기존 상태 DB에 변경 계획과 필요한 후보를 보존. 준비용 로컬 자료의 쓰기를 포함하지만 변경 대상 프로젝트 파일/사용 중 등록/PATH를 반영하지 않음. 실제 보존을 확인한 뒤 `plan_ref` 반환 |
| `--apply` | 전달한 고정 계획과 확인을 대조하고 허용한 미완료 부분만 반영/검증. 현재 입력으로 새 계획을 만들어 대신 적용하지 않음 |

프로젝트 설치를 준비할 때 기존 정상 프로젝트 DB가 있으면 그것을 사용한다. 프로젝트 없는 `command install/repair/remove`는 기존 외부 최초 보존 공간을 사용하며 현재 폴더의 프로젝트 DB를 임의 선택하지 않는다. 아직 로컬 제외가 준비되지 않았다면 기존 [최초 보존 공간 — 「첫 기록 생성과 인계」](install.md)을 사용한다. 준비 때문에 별도 전역 승인 DB, 계획 JSON 원본이나 빈 실행 시도를 만들지 않는다. 사용하지 않은 후보도 기존 보관/명시적 정리 대상이며 준비 호출 종료와 함께 삭제하지 않는다. 같은 유효 요청의 준비를 재시도하면 기존 계획을 조회하고 새 ID/후보를 무조건 늘리지 않는다.

최초 설치의 JSON 입력은 다음 의미를 갖는다. 이미 존재하는 프로젝트의 값은 확인해 재사용하고 잘못된 저장값을 새 기본값으로 가리지 않는다. CLI 옵션과 JSON에 같은 대상을 중복 지정하면 우선순위를 추정하지 않고 오류로 반환한다.

| 입력 | 의미 |
| --- | --- |
| `project_root` | 대상 경로. CLI의 `--project`와 같은 역할. 둘 다 없으면 기존 현재 위치 규칙을 따름 |
| `wiki_root` | 외부 WIKI의 확인할 로컬 위치. 내부/저장 연결로 해결되면 재입력 불필요. 미해결 상태를 빈 경로로 대신하지 않음 |
| `features` | 릴리스가 제공하는 선택 기능 ID의 목록. 필수 기능은 자동 포함. 명시한 빈 목록은 선택 확장 없음이며 미지원/중복 ID를 거부 |
| `register_command` | 기기 명령 등록의 boolean 선택. 유효한 기존 등록은 재사용. false를 기존 명령 제거 요청으로 해석하지 않음 |

제공하지 않은 선택은 기존 유효 설정/실제 안내한 기본값으로 해결할 수 있을 때만 사용한다. 새 기능, AI 분석 범위/모델/비용이 미정이면 별도 분석을 임의 시작하지 않는다. 이 입력은 최초 연결/관리의 준비 입력이며 상세 WIKI 분석의 요청 형식을 대신하지 않는다. UTF-8, 중복 키, null/빈 값과 모르는 필드의 검사는 [기존 값 규칙 — 「저장 값의 형식」](../workflow/storage.md)을 사용한다.

### 계획 참조와 확인의 재사용

저장 연결은 [변경 계획의 확인 기록](../workflow/storage.md)을 사용한다. 정상 CLI는 아래 참조를 내부에서 전달하고, AI 연결은 같은 입력을 프로그램으로 전달한다. 기본 `--json` 호출도 확인이 필요한 계획을 자동 승인하지 않으며 해당 계획과 needs_input을 반환한다. 적용된 상태를 조회하거나 이미 유효한 허용으로 같은 작업을 재개하는 경우는 새 선택을 만들지 않는다.

`plan_ref`는 일반 코드가 만들어 그대로 전달하는 작은 참조다. AI가 ID나 해시를 새로 계산하거나 본문을 고쳐 작성하지 않는다. 입력이 변형되면 추정 보정하지 않고 원래 준비 결과를 다시 조회한다. 사용자가 직접 이 값을 작성하는 절차는 기본 안내에 넣지 않는다.

| 값 | 의미 |
| --- | --- |
| `state_root`, `db_id` | 계획을 보존한 상태 위치와 기존 DB 식별. 허용한 상태 루트와 실제 소유/DB를 확인하고 읽음. 임의 경로의 DB를 같은 작업으로 신뢰하지 않음 |
| `plans` | 확인할 `{task_id, plan_id, decision_id}` 목록. `decision_id`는 해당 계획의 마지막 확인 기록이며 아직 없을 때만 null. 계획은 모두 같은 DB의 change 종류이고 중복/누락/표시하지 않은 작업 혼입을 거부 |
| `sha256` | 사용자에게 보여준 변경 범위와 허용 조건을 고정하는 해시. 아래 입력을 일반 코드로 계산. 사람의 동의나 실행 권한을 증명하는 비밀 토큰은 아님 |

프로젝트 설치와 기기 등록을 한 화면에서 확인하더라도 기존의 별도 작업/계획 책임은 유지한다. 두 계획을 모두 `plans`에 넣고 같은 범위의 사용자 응답을 두 기록에 한 트랜잭션으로 연결한다. 그래서 파일 단계마다 새 질문을 하지 않아도 된다. 독립된 다른 DB나 다른 프로젝트를 편의상 한 확인에 묶는 기능은 추가하지 않는다. 완료한 등록 계획을 재시도 때 목록에서 빼서 확인 범위를 바꾸지 않고 진행 상태만 별도로 알린다.

해시 입력은 DB 식별, 요청 operation, 각 task/plan 식별과 고정 계획의 의미 있는 내용이다. 대상의 실제 루트/소유, 배포 출처/실행 코드 기준, 기능과 권한/비용 범위, 변경 순서/단위, 기준 파일과 후보 참조/내용, 검증 및 허용 복원 조건을 포함한다. plans는 task_id, plan_id 순으로 정렬하고 기존 JSON 직렬화 규칙을 사용한다. 결정 ID, 진행 관측, 재시도 횟수와 현재 시각은 넣지 않는다. 계획 해시와 참조만으로 실제 파일 검사를 생략하지 않는다.

적용 입력은 반환받은 `plan_ref`, `decision`과 확인 근거 `evidence`다. decision은 `approved` 또는 `cancelled`이고, evidence에는 확인을 받은 경로(terminal 또는 agent), 실제 응답과 제공되는 경우 그 사용자 입력의 참조를 남긴다. 응답에 섞인 비밀값은 제거하고 전체 대화/계정을 복사하지 않는다. 필요한 선택 의미를 확인할 수 없는 입력을 임의로 동의로 정규화하지 않는다. 도구가 계획과 표시할 중요 내용을 만들고 AI는 사용자에게 대상/영향/필요한 선택을 전달한다. 단순 설치 요청을 아직 보여주지 않은 삭제/권한/비용 계획의 승인으로 확대하지 않는다.

확인 근거는 신뢰한 호출 경로의 감사 기록이며 서명된 본인 인증이 아니다. AI가 넘긴 응답을 기계적으로 사람의 직접 입력이라고 증명할 수 있다고 설명하지 않는다. 실제 사용자 확인이 없거나 연결할 수 없으면 적용하지 않고 필요한 선택을 반환한다. 제품의 확인은 OS, AI 호스트나 저장소의 권한 허가를 대체하지 않는다.

같은 계획의 재시도는 아래처럼 처리한다.

1. 실제 상태 루트/DB, 요청 동작, 계획과 현재 대상, 해시를 다시 대조한다. DB 인계가 끝났다면 기존 인계 근거로 같은 기록의 현 위치를 찾으며 옛 위치가 없다고 새 DB를 만들지 않는다.
2. 최신 결정이 같은 범위의 approved이고 이후 철회가 없다면 재사용한다. 이전 적용 입력이 정확히 다시 전달된 경우 같은 사실을 중복 저장하지 않는다. 기존 결정의 previous_id, 범위와 확인 근거까지 비교하며 같은 ID에 다른 값을 덮지 않는다.
3. 최신 결정이 cancelled이거나 준비 뒤 결정이 바뀌었다면 오래된 입력으로 다시 승인하지 않는다. 새 준비 결과가 현재 decision_id를 반환하고 실제 새 사용자 선택이 그 상태를 기준으로 전달돼야 한다.
4. 파일/범위가 바뀌면 쓰기 전에 멈추고 영향받은 계획을 다시 준비한다. 이미 도구가 반영하고 확인한 완료 결과는 기존 시도/관측으로 대조하므로, 자체 진행 때문에 모든 승인을 무효화하거나 완료 파일을 재적용하지 않는다.
5. 입력을 기다리는 동안 쓰기 트랜잭션이나 파일 잠금을 유지하지 않는다. 확인 저장 뒤 실제 반영 직전에도 최신 결정/실제 대상을 대조하고 기존 단일 반영과 복구 규칙을 사용한다.

반환의 `plan/ready`는 준비 완료이고 승인/적용 완료가 아니다. 결과 불명, 기록 유실, 원문 변경이나 필요한 새 선택은 기존 reason/status로 구별한다. 처음부터 끝까지 같은 계획을 수행할 때의 확인 재사용과, 새 계획에 대한 확인을 구분한다. 이 과정의 해시/상태 대조는 일반 코드의 일이며 별도 LLM 호출을 추가하는 이유가 아니다. 실제 시간/토큰 효과는 구현 뒤 측정한다.

## 시작 명령의 복구

`command repair`는 사용 중인 기기 명령의 확인된 소유와 연결을 복구한다. 명령 자체나 기반 Python이 고장 나도 사용할 수 있도록 **지원 Python으로 실행한 외부 관리 도구**가 담당한다. 프로젝트가 없어도 실행 가능하며 가짜 프로젝트나 WIKI를 만들지 않는다. 프로젝트 코드/skill/WIKI를 고치는 명령과 구별한다.

| 확인한 상태 | 처리 |
| --- | --- |
| 등록, 실행 파일/환경과 명령 선택이 정상 | 변경 불필요를 안내. 재설치/새 환경/반복 확인을 만들지 않음 |
| 등록은 정상이고 열린 셸만 옛 환경을 사용 | 새 환경을 받는 터미널 또는 확인한 명시 경로를 안내. 사용자 PATH를 중복 추가하지 않음 |
| 소유와 기존 기준이 확인되고 파일/환경 복구가 필요 | 기존 기록, 배포본과 지원 Python을 확인한 뒤 필요한 복구 계획만 적용. 새 환경 준비와 명령 전환은 기존 등록 절차를 사용 |
| 기반 Python 부재 또는 지원 불일치 | 필요한 준비를 안내하고 멈춤. 사용자에게 임의 파일 수정/환경 이동을 시키거나 다른 Python으로 조용히 교체하지 않음 |
| 중단된 등록 작업이 있음 | 실제 결과와 해당 작업부터 대조. 새로운 복구 작업을 겹쳐 만들거나 현재 정상 명령을 무조건 차단하지 않음 |
| 등록이 없거나 소유/기록이 손상됨 | 최초 준비가 필요한 상태와 소유 불명을 구분. 같은 이름의 파일을 새 공식 설치로 간주해 덮지 않음 |

복구에 사용하는 릴리스와 설치 형식의 호환을 확인한다. 새 배포본을 받았다는 이유로 기기 명령을 자동 업그레이드하거나 전체 프로젝트를 갱신하지 않는다. 공식 버전 변경이 필요하면 그 변경과 영향을 새 계획에 드러낸다. 새 환경은 최종 위치에서 준비하며 기존 명령은 전환 전 검사까지 보존한다. 실패 후 계속 쓸 수 있는 구성은 실제 확인한 범위만 안내한다.

진행은 [기존 DB 연결 — 「등록 작업과 기존 DB의 연결」](entry.md)을 사용한다. 사용자가 직접 wheel, PATH와 `registration.json`의 값을 맞춰야 하는 정상 복구 절차는 제공하지 않는다. 상세 진단은 도움을 요청하거나 원인을 조사할 때의 별도 자료다.

## 시작 명령의 제거

`command remove`는 현재 Windows 사용자 계정의 OnepLoom 시작 명령에 한정한다. 프로젝트의 하네스, WIKI, `.harness/`와 사용자별 프로젝트 목록은 제거 대상이 아니다. 목록을 지우거나 각 프로젝트를 순회하며 설치를 해제하지 않는다. 파일 소유와 PATH의 기준은 [보존 규칙 — 「등록과 제거에서 보존할 것」](entry.md)을 따른다.

1. 실제 소유 파일/환경, PATH의 해당 항목, 사용 중인 자원과 미완료 등록 작업을 확인한다. 중단된 다른 작업과 충돌하면 새 제거부터 진행하지 않는다. 현재 관리 도구나 Python이 제거 대상 안에서 실행 중이면 외부 배포본으로 다시 실행하도록 안내하고 자기 삭제를 예약하지 않는다.
2. 모든 프로젝트의 짧은 명령에 미치는 영향, 실제 제거 대상과 남길 자료를 함께 보여준다. `제거할까요? [y/N]`에서 `y`/`yes`만 동의이며 Enter는 보류다. 같은 계획의 확인은 내부 파일별로 반복하지 않는다. EOF나 무응답은 동의가 아니다.
3. 삭제 대상 밖의 기존 최초 보존 공간에 계획, 현재 기준과 필요한 복원 자료를 남긴 뒤 효과를 적용한다. 상세 처리/중단 사실은 해당 작업 DB가 소유한다. 적용 직전 다시 대조하고 사용자 변경, 다른 프로그램의 PATH 편집이나 파일 사용 중 거부를 발견하면 무조건 밀어붙이지 않는다.
4. 현재 명령/PATH와 소유 환경의 제거 결과를 확인한다. `registration.json`은 결과 확인 전에 없애지 않고, 제거 작업의 최종 정리 단계에서 처리한다. 그 뒤 기록 저장이 끊겨도 외부 작업 기록으로 남은 효과를 대조할 수 있어야 한다. 파일/등록 정보/DB/PATH가 한 번에 commit된다고 가정하지 않는다.
5. 제거 완료와 보존/정리 미완료를 구분한다. 모르는 파일, 사용자 편집과 사용 중 환경은 상위 폴더째 삭제하지 않는다. 부분 실패이면 실제 남은 상태와 같은 제거를 재실행할 방법을 알린다. 확인된 완료 또는 원래 등록 없음은 변경 불필요로 처리하지만, 등록 파일이 없다는 사실만으로 중단된 제거를 완료 처리하지 않는다.

복구 자료와 정리 기록은 기존 보존 정책을 사용한다. 명령 제거 완료가 그 기록까지 자동 삭제하는 허가는 아니다. `oneploom projects remove`는 목록 항목만 지우는 별개 명령이며 시작 명령이나 프로젝트 파일을 제거하지 않는다. 두 기능의 도움말에는 대상 차이가 드러나야 한다.

## 미리보기, 반환과 안내

`--preview`는 필요한 현재 상태를 읽어 계획과 미확인을 보여주고 변경하지 않는다. DB/등록 파일 생성, 환경 준비, PATH 변경, 자동 다운로드와 AI 호출도 하지 않는다. 미래에 수행할 검사를 미리보기의 PASS로 표시하지 않는다. `--json`은 미리보기와 준비/적용의 결과를 같은 형식으로 반환하며, 미완성 입력은 질문 없이 `needs_input`으로 반환한다. 준비에서만 보존한 plan_ref를 반환하고 미리보기에는 만들지 않는다. 해석할 수 없는 명령은 입력 오류와 해당 도움을 제공한다.

반환은 [공통 형식 — 「명령 결과의 형식」](entry.md)을 확장한다. `operation`은 `install`, `command.install`, `command.repair`, `command.remove`, `stage`는 `plan` 또는 `apply`로 구별한다. `plan/ready`는 계획 확인을 위한 준비가 끝났다는 뜻이며 적용 허가/성공이 아니다. `apply/ready`는 그 작업의 필수 효과와 완료 검증까지 끝난 경우다. 계획/범위가 달라지면 옛 확인을 재사용하지 않는다. 내부 DB 테이블이나 상태 파일 전체를 출력 계약에 복제하지 않는다.

기존 종료 코드 0~5와 `message`, `reason`, `next_action`을 사용한다. 새 입력/동의가 필요하면 3, 미지원이면 5, 실행 중 실패/결과 불명이면 1로 구별하며 인자 오류는 2다. 사용자가 보류/취소한 경우는 4이며 최초 필수 변경 전이면 변경하지 않는다. 설치 이후의 선택적 정리 취소는 앞선 설치 성공을 취소로 바꾸지 않는다. `command` 관리에 프로젝트/WIKI 경로를 임의로 채우지 않는다. 실패한 일부 단위가 있는데 전체를 성공으로 반환하지 않는다.

사용자 안내는 대상 → 수행 중인 작업 → 완료/미완료 → 필요한 다음 행동으로 구성한다. 긴 진행에는 현재 단계와 취소 방법을 보이고 원인이 필요한 경우만 상세 로그 위치를 연결한다. 오류 메시지에 내부 예외 추적만 보여주거나, 정상 완료 뒤 내부 파일 경로를 사용자가 기억해야 할 필수 정보로 나열하지 않는다. 오프라인에서도 즉시 필요한 조치를 알 수 있게 하고 비밀값은 안내/로그에 넣지 않는다.

## 근거와 구현 전에 확인할 것

[CLI Guidelines의 상호작용](https://clig.dev/#interactivity)과 [하위 명령](https://clig.dev/#subcommands)은 사람에게 필요한 질문과 자동화 입력을 구분하고 명령 간 표현을 일관되게 두는 참고 근거다. 이 문서의 이름/반환은 OnepLoom 설계이며 공통 표준이라고 주장하지 않는다.

[pipx의 제거 구현](https://github.com/pypa/pipx/blob/main/src/pipx/commands/uninstall.py)은 환경과 노출한 앱 경로를 찾아 제거하고 다른 쪽이 소유한 복사/링크를 제외하는 공개 사례다. [MIT 원문](https://github.com/pypa/pipx/blob/main/LICENSE)을 확인했으며 코드를 복사하지 않았다. 이 사례가 OnepLoom의 PATH 소유, 복구 DB, Windows 중단 안전성을 대신 증명하지는 않는다.

제품 구현에서는 [수용 입력 — 「설치와 명령 관리의 검증 입력」](../../verification/acceptance.md)을 실제 배포 경로로 실행한다. 필요한 기기 효과의 저장 코드, 제거 도중 재개, 셸별 명령 선택과 사용 중 파일 처리는 아직 미검증이다. 설치 계획의 입력/확인 전달은 위 절, 팀원 준비 자료는 [등록용 배포 자료 — 「팀원 첫 준비의 배포 자료」](install.md)로 구체화했다. 저장 확장/연결 구현을 마치기 전 이 계약의 동작이나 제품 완료를 주장하지 않는다.
