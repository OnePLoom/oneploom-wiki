# 프로젝트 설치본 발견과 실행 인계

11/23 채택한 [기기 명령 등록](../../decisions/runtime/0023-command-registration.md)과 [프로젝트 선택](project-selection.md)을 실제 프로젝트 실행본에 연결하는 명세다. 제품 코드나 Windows 실행을 검증한 결과는 아니다. 여기서 기기 명령은 사용자가 입력하는 `oneploom`, 프로젝트 실행본은 선택한 저장소 안의 하네스 코드다. 전자는 대상을 찾아 넘기고 후자가 WIKI 연결과 Codex 실행을 처리한다.

## 비교와 소유

| 설치 위치를 찾는 방법 | 판단 |
| --- | --- |
| 기존 로컬 연결에 프로젝트 기준 상대 경로 저장 | 기존의 프로젝트별 준비 흐름을 구체화. 별도 파일/전역 설정 없이 작업 사본마다 위치 확인 가능. 사용자 지정 위치의 새 clone은 처음 한 번 준비 필요 |
| 프로젝트 루트에 공유 위치 파일 추가 | clone에서 위치를 바로 알 수 있으나 새 파일/소유/추적 규칙이 필요. 현재는 기존 로컬 연결로 충분하므로 추가하지 않음 |
| 사용자별 프로젝트 목록에 실행 경로도 저장 | 선택과 실행 정보를 한 곳에서 찾지만 프로젝트 설정과 중복되고 목록 없이 시작하는 계약과 충돌. 채택하지 않음 |
| 프로젝트 전체에서 실행 파일 검색 | 최초 입력을 줄일 수 있으나 다른 도구/옛 설치본을 구별해야 하고 범위/비용이 커짐. 자동 검색은 하지 않음 |

공개 구현의 참고 사례로 [Angular CLI의 초기 진입 코드](https://github.com/angular/angular-cli/blob/main/packages/angular/cli/lib/init.ts)는 현재 위치를 기준으로 프로젝트의 CLI를 찾고 로컬 버전을 사용한다. 이는 기기 진입과 프로젝트 실행본을 나누는 방식의 실재 근거다. 해당 구현의 전역 CLI 대체, Node 의존성과 버전 분기를 그대로 가져오지 않는다. [MIT 라이선스](https://github.com/angular/angular-cli/blob/main/LICENSE)를 확인했으며 코드나 파일을 복사/동봉하지 않았다. 이 사례가 OnepLoom의 Windows 인자/종료 동작을 증명하지는 않는다.

## 설치 위치의 저장과 발견

기존 `.harness/local.json`에 **`module_path` 하나를 선택 필드로 추가**한다. 설정 형식과 나머지 필드는 [연결 설정 — 「연결 설정의 필드와 읽기 규칙」](entry.md)을 따른다. 아래는 사용자 지정 위치와 내부 WIKI를 쓰는 작업 사본의 예시다.

```json
{
  "project_id": "example-project",
  "project_root": "D:/work/B",
  "module_path": "tools/oneploom"
}
```

- 기준은 확인한 프로젝트 루트다. `module_path`는 그 아래 설치 디렉토리의 상대 경로이며 셸 명령, 실행 인자나 WIKI 경로가 아니다.
- 기본 `oneploom/`이면 필드를 생략한다. 내부 WIKI이고 다른 로컬 선택도 없다면 이 필드 때문에 로컬 파일을 만들지 않는다.
- 빈 값/null, 절대 경로/드라이브 상대 경로/URI, 프로젝트 루트 자체, `..`로 벗어나는 경로를 허용하지 않는다. 실제 링크 대상도 같은 작업 사본의 허용한 영역인지 확인한다. `.harness/`나 다른 저장소를 공유 실행 영역으로 사용하지 않는다.
- 다른 위치가 등록돼 있으면 그 위치만 사용한다. 없거나 손상됐다고 기본 위치의 다른 설치본을 실행하지 않는다. 기본 이름의 무관한 폴더도 탐색/수정 대상에 넣지 않는다.

기기 명령의 발견 순서는 다음과 같다.

1. [프로젝트 선택 — 「시작 대상과 명령 문법」](project-selection.md)에서 정한 루트를 확인한다. 하위 폴더, 중첩 저장소와 worktree는 기존 [대상 확인 — 「설치기와 시작 명령의 대상 확인」](entry.md)을 따른다.
2. 로컬 연결이 있으면 UTF-8 JSON 구조/중복 키와 발견에 필요한 `project_root`, `project_id`, `module_path`를 확인한다. 전체 WIKI/권한 설정을 기기 명령에서 해석하거나 다시 저장하지 않는다. 해당 설정을 실제로 소비하는 프로젝트 코드가 자기 필드의 전체 검사를 맡는다.
3. `module_path`가 있으면 등록 위치, 없으면 기본 위치 하나를 확인한다. 경로 불일치나 읽기 실패는 부재로 바꿔 기본값을 적용하지 않는다.
4. 해당 설치 영역의 `project.json`, 설치 기준과 `cli.py`의 대응을 확인한다. `cli.py`를 이번 프로젝트 진입점으로 구체화하며 파일 이름만 같은 다른 스크립트를 실행하지 않는다. 공유/로컬 프로젝트 ID, 실제 루트와 설치 소유를 대조한다.
5. 호출할 Python과 프로젝트 진입점의 절대 경로를 확보한 뒤 아래 인계로 진행한다. 처음 확인한 폴더와 실제 실행 직전의 대상이 달라졌다면 멈춘다.

기기 명령이 다른 책임의 설정 필드를 해석하지 않는 것은 그 값을 삭제하거나 유효하다고 인증하는 뜻이 아니다. 발견에 필요한 값이 미지원/불명확하면 기기 단계에서 중단하고, 프로젝트 코드가 자기 설정의 오류를 발견하면 Codex 시작 전에 중단한다. 동일 ID는 clone 간에 유지될 수 있으므로 작업 사본의 동일성을 ID 하나로 판단하지 않는다. [Git 루트 조회](https://git-scm.com/docs/git-rev-parse)와 실제 경로 대조는 설치 허가나 코드 안전성의 증명도 아니다.

## 처음 준비와 위치 변경

기본 위치의 새 clone은 같은 기본 경로에서 공유 설치본을 찾는다. 사용자 지정 위치의 새 clone은 팀 README에 기재된 실제 프로젝트 진입 파일로 처음 연결 준비를 한다. 예를 들어 프로젝트 루트에서 다음처럼 실행하는 형태다. 아래 명령도 구현 명세이며 현재 배포 명령은 아니다.

```powershell
py -3 .\tools\oneploom\cli.py connect --project .
```

이때 프로젝트 코드가 자기 파일의 실제 위치와 지정한 프로젝트를 대조하고 `module_path`를 계산한다. 사용자에게 이미 확인한 경로를 다시 타이핑하게 하지 않는다. 필요한 외부 WIKI/실행 조건을 함께 준비한 뒤 기존 보호 절차로 로컬 연결을 저장하고, 기기 명령과 프로젝트 목록을 연결한다. 공유 하네스의 재설치나 WIKI 재분석은 수행하지 않는다. 기존 유효 연결은 반복 저장/승인 없이 재사용한다. 명령이 없는 사용자는 [공식 배포 자료 — 「팀원 첫 준비의 배포 자료」](install.md)의 `command install`로 자기 계정의 명령을 한 번 준비한다. 프로젝트 Git에는 wheel을 기본 포함하지 않는다. 이 예시는 사용자 지정 설치 위치이며 신규 기본 위치는 `oneploom/`이다.

여기서 연결 준비와 기기 명령의 최초 등록은 같은 효과가 아니다. 이미 준비한 기기 명령은 재사용한다. 없는 기기 명령의 등록은 [외부 관리 도구 — 「시작 명령만 처음 준비하기」](management.md)가 담당하며 프로젝트 connect가 대신 설치하지 않는다. `connect` 입력만으로 알리지 않은 PATH/가상환경 변경을 수행하지 않는다. 등록이 남아 있으면 현재 가능한 명시 경로 사용과 미완료 준비를 구분해 안내한다.

설치 폴더를 바꾸는 것은 경로 필드 한 줄 변경으로 끝나지 않는다. 설치 관리 절차에서 skill/hook/지침과 설치 기준의 참조, 사용자 파일 보존을 함께 확인해야 한다. `connect`는 폴더를 옮기는 명령이 아니다. 준비된 새 설치 위치를 검사한 뒤 그 연결만 저장하며 실패하면 이전 설정/복구 자료를 보존한다. 다른 프로젝트의 실행 파일에서 A를 지정하거나 잘못 복사한 로컬 연결로 준비하는 경우에는 덮어쓰지 않는다.

로컬 연결 유실은 공유 설치본의 유실과 구분한다. 명시 경로로 자기 기기 연결을 다시 준비할 수 있지만 없어진 DB/복구 이력을 재생성했다고 보고하지 않는다. 전체 프로젝트 폴더를 이동한 경우에는 `project_root`와 WIKI 연결을 다시 확인하고 목록의 새 경로 등록/옛 항목 제거도 별도로 처리한다.

## 프로젝트 실행본으로 넘기는 입력

기기 명령은 프로젝트 코드를 자기 프로세스로 import하지 않고 **확인한 Python으로 프로젝트 `cli.py`를 실행**한다. Python의 [subprocess](https://docs.python.org/3.13/library/subprocess.html#popen-constructor)는 프로그램/인자 배열, 작업 폴더, 표준 입출력과 종료 결과를 지정할 수 있다. 이 API 선택이 모든 Windows 셸의 인자/중단 보존을 자동 보장하지는 않는다.

| 전달 항목 | 계약 |
| --- | --- |
| 프로그램/진입 파일 | 기기 등록에서 확인한 Python 절대 경로와 대상 설치 영역의 `cli.py` 절대 경로. 매번 PATH의 임의 `python`이나 다른 프로젝트 코드를 선택하지 않음 |
| 요청 동작 | 사용자가 요청한 start, resume, connect 또는 check. 무인자는 start로 정규화. 선택 화면은 기기 단계에서 처리해 프로젝트에서 다시 질문하지 않음 |
| 대상 | `--project` 뒤에 확인한 프로젝트 루트의 절대 경로 하나 전달. 프로젝트 코드도 자기 위치/설정과 다시 대조 |
| resume 세션 | 사용자가 준 식별자는 그대로 전달. 없으면 기존 세션 선택 흐름 유지. 최근 세션/새 세션으로 자동 대체하지 않음 |
| 준비/적용과 JSON | 해당 동작이 지원하는 preview, prepare, apply, input, JSON 옵션을 그대로 전달. input의 상대 파일 경로는 원래 cwd 기준이고 표준 입력을 기기 단계에서 먼저 소비하지 않음. 프로젝트 결과 앞뒤에 별도 성공 JSON을 추가하지 않음 |
| Codex 인자 | 최초 `--` 뒤 문자열 배열을 순서/값 그대로 전달. 셸 명령으로 합치거나 따옴표를 임의 제거하지 않음. 프로젝트 코드의 기존 경로/권한 충돌 검사는 유지 |
| 호출 작업 폴더 | 최초 호출 폴더를 자식의 `cwd`로 유지. 모듈/기기 프로그램 폴더로 바꾸지 않음. 프로젝트 대상은 별도 절대 경로로 전달 |
| 입출력/수명 | 실제 시작에서는 기존 콘솔의 입력/출력/오류를 연결하고 종료까지 기다림. 정상 TUI에 짧은 timeout이나 캡처용 파이프를 끼우지 않음. 잠금/DB 핸들을 자식에게 넘기지 않음 |

connect --apply에서도 선택한 대상은 --project로 전달하되 [고정 계획의 대상 — 「연결 준비의 입력과 확인 전달」](entry.md)과 같아야 한다. 다른 프로젝트의 plan_ref를 받으면 재연결/새 계획으로 우회하지 않고 적용 전에 거부한다. 이 옵션은 이미 확인한 계획을 수정하는 입력이 아니다.

예를 들어 A 폴더에서 B를 선택한 경우, 프로젝트 실행본은 B의 절대 경로로 호출하되 원래 작업 폴더는 A로 유지한다. B의 프로젝트 코드가 B의 설정을 읽고 Codex에 B를 작업 대상으로 전달한다. WIKI 상대 경로는 B 또는 B의 WIKI 기준이고, 사용자에게서 받은 Codex 인자의 상대 경로는 같은 호출 폴더에서 대상 B를 지정해 Codex를 직접 실행한 경우와 대조한다. Codex 옵션의 의미를 기기 명령이 추측해 다시 해석하지 않는다. 지원 호스트에서 이 대응을 확인하지 못한 경로 인자는 그대로 실행해 성공을 주장하지 않고 명시적인 절대 경로 사용 또는 미지원 안내로 처리한다.

미리보기의 `launch`에는 기존 `program`, `args`와 함께 실제 `cwd`를 포함한다. 작업 폴더가 다른데 인자만 같다고 같은 실행으로 표시하지 않는다. 실제 실행 후에는 자식 종료 코드를 유지한다. Ctrl+C, 정상 종료, 자식 생성 실패와 부모의 갑작스러운 종료는 Windows에서 각각 확인하며, 임의의 사용자 Codex/백그라운드 서버를 종료하거나 실패한 실행을 자동 재시작하지 않는다.

## 호환성, 실패와 제거

기기 프로그램과 프로젝트 적용본은 같은 공식 릴리스 원본에서 나오지만 서로 다른 시점의 버전이 함께 남을 수 있다. 프로젝트가 자신의 명령 입력과 Python/설정 지원 조건을 **Codex 실행이나 관리 쓰기 전에** 검사하도록 한다. 확인되지 않은 조합을 코드가 있다는 이유만으로 실행 가능 처리하지 않는다. 기기 코드의 발견과 프로젝트 코드의 준비를 구분하며, 호환 확인을 위해 새 AI 요청이나 매번 별도 `--help` 프로세스를 실행하는 방식은 기본으로 넣지 않는다.

기존 공식 설치 기준/패키지 메타데이터와 명령 계약을 사용한다. 사용자 편집에 새 버전을 부여하거나 파일명에 v1/v2를 붙이지 않는다. 현재는 독립적인 인계 버전 필드/호환 DB도 추가하지 않는다. 첫 릴리스의 명령 계약을 회귀 입력으로 유지하고, 실제 호환을 깨는 변경이 생길 때 공식 버전의 지원 범위와 이전 절차를 명시한다. 이전 기기/새 프로젝트, 새 기기/이전 프로젝트 조합을 시험하기 전에는 장래 버전의 호환을 보장하지 않는다.

| 상태 | 대응 |
| --- | --- |
| 기본 위치에 설치본이 없고 등록 위치도 없음 | `needs_input` / `module_not_found`, 준비 코드 3. 실제 설치 또는 사용자 지정 진입 파일의 연결 준비 안내 |
| 등록 위치 유실/손상, 설정 형식 오류 | 기존 `invalid_config` 등으로 원인을 구분하고 보존. 기본 위치 재설치나 다른 프로젝트 실행으로 대체하지 않음 |
| 프로젝트/작업 사본 불일치 | `project_mismatch`로 중단. 로컬 파일의 ID/루트를 임의 수정하지 않음 |
| Python 또는 입력 계약의 미지원 | 확인한 미지원은 코드 5, 잘못된 명령 문법은 코드 2로 구분. 필요한 준비/지원되는 진입 방법 안내. 기기나 프로젝트를 자동 갱신하지 않음 |
| 프로젝트 프로세스 생성 실패 | `launch_failed`로 보고. 생성되지 않은 자식을 성공/정상 종료로 표시하지 않음 |
| 프로젝트 코드가 시작된 뒤 실패/취소 | 그 단계의 출력/종료를 보존. 입력 문제인지 Codex 실행 뒤 결과인지 구분하고 전체 명령 자동 재시도 없음 |

명시 경로 실행은 기기 명령의 발견/등록 문제를 우회할 수 있는 대안이다. 손상된 프로젝트 설치본, 부족한 Python/권한이나 잘못된 WIKI를 해결하는 만능 복구로 안내하지 않는다. 사용할 Python과 정확한 프로젝트 진입 경로를 함께 보여주며 사용자 입력의 비밀값은 진단에 남기지 않는다.

프로젝트 목록 제거, 기기 명령 제거와 실제 프로젝트 모듈 제거는 기존 소유 경계를 유지한다. 설치 위치의 참조를 해제할 때도 현재 값이 제거 대상과 일치하는지 확인하고 다른 로컬 설정/WIKI/DB를 함께 지우지 않는다. 기기 명령 복구를 위해 사용자 지정 프로젝트를 기본 위치로 옮기거나 그 적용본을 공식 원본으로 덮지 않는다.

## 확인할 조건

[설치본 발견과 인계 검증](../../verification/acceptance.md)은 기본/사용자 지정 설치, 새 clone, 실제 경로와 인자/종료/호환의 미실행 조건이다. 의존성 준비, 파일 반영, 기기 명령의 저장/제거는 해당 설계와 연결하며 이 문서만으로 구현 완료를 선언하지 않는다. 실제 Windows 실행과 변경 중 보호가 확인되지 않은 부분은 남은 구현 항목으로 유지한다.
