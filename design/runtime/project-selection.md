# 프로젝트 선택 명령과 사용자별 목록

11/23 채택한 [ADR 0024](../../decisions/runtime/0024-project-selection.md)를 명령과 로컬 파일에 연결한 구현 명세다. **아래는 전체 구현 명세이며, 현재 확인한 부분은 「현재 구현 범위」에서 구분한다.** 현재 프로젝트 우선, 밖에서는 선택, 선택 결과는 해당 실행에만 적용하는 정책을 유지한다. 명령 등록은 [기기 프로그램 — 「짧은 명령의 등록과 프로젝트 선택」](entry.md), WIKI/권한은 [프로젝트 연결 — 「연결 설정의 필드와 읽기 규칙」](entry.md), 설치/갱신은 [관리 도구 — 「설치기 위치와 재실행 판단」](install.md)가 소유한다.

## 현재 구현 범위

2026-11-25 첫 구현은 무인자/start/resume의 입력과 대상 선택, 도움/개발 버전, `projects list`와 설정 읽기까지다. [실제 Windows 검사](../../evidence/experiments/runtime/2026-11-25_16-13-58-project-discovery.md)에서 확인한 범위와 모의 입력을 구분한다. 아래 목록 저장/등록/제거와 실제 실행을 포함한 전체 명세가 완료된 것은 아니다.

개발 작업본의 실행법은 코드 저장소 README가 소유한다. `oneploom` 명령 등록은 아직 제공하지 않는다. 설치 설정을 발견한 start/resume도 실행 연결이 아직 없음을 `runtime_not_implemented`/코드 5로 알리며 실행 준비 완료를 반환하지 않는다. 기존에 채택한 최종 사용법은 아래에 유지한다.

## 시작 대상과 명령 문법

아래는 구현할 사용법이다. 대괄호는 선택 입력, 세로줄은 둘 중 하나를 뜻하며 그대로 입력하는 문자가 아니다. 실제 Codex 인자/지원 여부는 기존 호스트 연결에서 검사한다.

```text
oneploom
oneploom start [--project PATH | --select] [--preview [--json]] [-- CODEX_ARGS...]
oneploom resume [SESSION] [--project PATH | --select] [--preview [--json]] [-- CODEX_ARGS...]
oneploom projects list [--json]
oneploom projects add --project PATH [--json]
oneploom projects remove --project PATH [--json]
```

| 입력 | 처리 |
| --- | --- |
| 인자 없는 `oneploom` | `oneploom start`와 같은 처리. 빈 문자열 인자가 있는 요청과 구별 |
| `start --project PATH` | 최초 호출 폴더 기준으로 경로를 해석하고 그 대상만 확인. 다른 프로젝트로 대체하지 않음 |
| `start --select` | 현재 폴더와 관계없이 등록 목록 표시. 명시 경로와 함께 주면 입력 오류 |
| 대상 옵션 없는 start | 정상 프로젝트 안이면 바로 시작. 현재 프로젝트가 미설치/손상/호환 불명이면 해당 준비 안내. 프로젝트 밖이면 대화형 목록 선택 |
| resume | 같은 대상 선택 후 기존 재개 절차 사용. 프로젝트 선택과 대화 선택을 구분하고 대상이 다른 세션을 조용히 재개하지 않음 |
| `projects list` | 등록 경로만 조회. Codex, WIKI, 작업 DB를 열거나 목록을 정리/갱신하지 않음 |
| `projects add --project PATH` | 확인한 설치/기기 준비 대상 루트를 목록에 등록. 설치나 WIKI 연결을 자동 수행하지 않음 |
| `projects remove --project PATH` | 그 경로의 목록 항목만 제거. 프로젝트, WIKI, `.harness/`, 기기 프로그램은 삭제하지 않음 |

옵션은 해당 하위 명령 뒤에 둔다. `oneploom --project ...`를 start로 추정하지 않는다. `oneploom --help`, `oneploom --version`과 각 하위 명령의 `--help`는 대상이나 목록 저장 없이 처리한다. `oneploom projects`만 주면 관리 명령 도움을 보여준다. 알 수 없는 명령/옵션, 빈 경로, `--project` 중복과 `--project`/`--select` 동시 지정은 쓰기나 실행 전에 거부한다.

[argparse](https://docs.python.org/3.13/library/argparse.html#allow-abbrev)의 하위 명령/상호 배타 옵션과 `allow_abbrev=False`를 사용해 파싱하는 방향이다. 지원 Python에서 확인한 기능만 사용하며 조사한 문서 버전을 제품 고정 버전으로 삼지 않는다. 자동 오타 보정이나 미인식 옵션을 Codex로 넘기는 처리는 하지 않는다. 최초 `--` 뒤 인자만 원래 배열로 인계하며, 명령 문자열로 다시 합쳐 셸에 실행시키지 않는다. 뒤에 준 경로/권한 옵션도 기존 충돌 검사를 거쳐야 하고 선택한 루트를 다른 루트로 덮어쓰는 근거가 될 수 없다.

## 목록 화면과 입력 종료

목록에는 폴더 이름과 등록된 전체 경로를 함께 표시한다. 모든 프로젝트의 WIKI/설치본을 미리 열지 않으며 목록 표시는 실행 가능 판정이 아니다. 같은 이름의 clone/worktree는 경로로 구분하고, 화면 번호와 그때 읽은 경로를 메모리에서 연결한다. 선택 후 실제 위치/설치/연결을 확인한다. 다른 실행이 목록 순서를 바꿨다고 새 목록의 같은 번호를 선택하지 않는다.

- 정상 번호는 그 경로 하나를 선택한다. 숫자 범위 밖/잘못된 입력은 다시 입력하거나 취소하도록 안내하며 AI에게 의도를 추측시키지 않는다.
- 빈 입력, `q` 또는 선택 단계의 Ctrl+C는 취소다. 항목 하나도 자동 실행하지 않는다.
- 목록이 없거나 비어 있으면 준비/등록 또는 명시 경로를 안내한다. 하위 폴더나 디스크 전체를 검색하지 않는다.
- 입력을 받을 터미널이 없거나 `--json`을 요청하면 질문을 띄우지 않는다. 유효한 현재/명시 대상은 그대로 처리하고, 선택이 필요하면 기존 `needs_input`으로 반환한다. `--select --json`도 사람의 선택을 받은 것으로 추정하지 않는다.
- EOF는 확인되지 않은 입력으로 처리한다. 선택을 기다리는 정상 대화형 실행을 임의의 짧은 타임아웃으로 종료하지 않는다.

`--preview`는 선택/준비 결과만 보여주고 Codex를 실행하지 않는다. start/resume의 `--json`은 `--preview`와 함께만 허용한다. 실제 인계 뒤에는 기존 Codex 표준 입출력/종료 코드를 유지하며 목록 화면의 취소 코드와 섞지 않는다. 선택한 B는 이번 실행의 대상일 뿐 다른 A 창의 작업 위치나 WIKI/권한을 바꾸지 않는다.

## 목록의 저장 위치와 형식

사용자별 목록은 Windows의 실제 `FOLDERID_LocalAppData` 아래 `OnepLoom/projects.json`에 둔다. 기본 배치의 예시는 `%LOCALAPPDATA%\OnepLoom\projects.json`이다. [Known Folder 정의](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)와 [경로 조회 API](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)를 기준으로 현재 사용자의 위치를 구하며 계정 이름/C 드라이브나 다른 사용자 폴더를 고정하지 않는다. 조회 실패를 현재 프로젝트에 파일을 만드는 대안으로 숨기지 않는다.

이는 사용자 프로그램 영역의 `OnepLoom/registration.json`과 다른 책임이다. 전자는 프로젝트 경로 목록, 후자는 노출 명령/환경과 등록 소유의 확인 정보다. Codex 전역 설정을 수정하지 않고 프로젝트 Git에도 이 목록을 넣지 않는다. 실제 사용자 폴더나 파일은 이번 설계 작업에서 생성하지 않았다.

파일은 UTF-8 JSON의 **경로 문자열 배열 하나**다.

```json
[
  "D:/work/Project-A",
  "D:/work/Project-B"
]
```

| 형식 조건 | 이유/처리 |
| --- | --- |
| 각 값은 확인한 프로젝트 루트의 Windows 절대 경로 | 상대 경로, 빈 문자열, URI, 드라이브 상대 경로를 등록값으로 사용하지 않음. 입력의 상대 경로는 먼저 실제 루트로 해결 |
| 저장 표기는 `/` 구분자를 사용 | JSON 예시와 진단에서 경로를 읽기 쉽게 유지. 같은 대상인지는 문자열의 소문자 변환만으로 판단하지 않음 |
| 이름/선택 순서/최근 프로젝트/기본 프로젝트 필드 없음 | 이름은 경로에서 표시하고 선택은 실행별 메모리에만 유지 |
| WIKI/권한/버전/프로젝트 ID/상태 DB/세션 필드 없음 | 실제 프로젝트의 원본 설정과 중복 저장하지 않음. 같은 프로젝트 ID를 공유하는 서로 다른 clone도 별개 위치 |
| 빈 배열은 등록 없음, 파일 부재는 미등록 | 조회 시 폴더나 파일을 생성하지 않음. 읽기 거부/손상/지원하지 않는 형식을 부재로 바꿔 덮지 않음 |

새 래퍼 객체나 형식 버전 필드는 현재 필요가 없어 추가하지 않는다. JSON 숫자/객체/중첩 배열, 잘못된 경로와 동일 문자열의 중복은 정상 파일로 조용히 보정하지 않는다. 경로 별칭의 실제 중복은 등록 시 별도로 대조하며 단순 list 조회를 모든 프로젝트의 접근 가능 검사로 확대하지 않는다. 향후 형식 변경은 실제 릴리스의 호환/이전 절차로 다룬다. 등록값이 있다는 사실만으로 그 프로젝트를 실행할 수 있거나 현재도 존재한다고 판단하지 않는다. 절대 경로 형식을 만족해도 기존 Windows 로컬 작업 사본의 지원 조건을 따라야 하며 네트워크 저장소 지원을 자동 추가하지 않는다.

## 등록과 이동, 목록 제거

설치/기기 준비와 `projects add`는 같은 등록 처리를 호출한다. 준비에서 확인한 루트를 넘기며 새 설치/팀원의 clone마다 자동 등록할 내용과 목적을 안내한다. 같은 유효 항목에 반복 승인을 요구하지 않고, 이미 등록돼 있으면 불필요하게 파일을 다시 쓰지 않는다. 현재 위치/명시 경로 start는 목록을 읽거나 갱신하지 않아도 동작해야 한다.

등록 전에는 실제 작업 사본, 설치 기준과 필요한 로컬 연결의 대응을 확인한다. 경로 별칭과 중복은 실제 파일/디렉토리 식별로 대조하며 [samefile](https://docs.python.org/3/library/os.path.html#os.path.samefile) 같은 수단의 접근 실패를 다른 대상으로 추정하지 않는다. 같은 이름의 서로 다른 루트는 유지한다. 사용자 지정 설치 위치는 [프로젝트별 발견 명세 — 「설치 위치의 저장과 발견」](project-entry.md)로 해결하며 목록에 실행 파일 경로를 복제하지 않는다.

목록 제거는 기록된 루트를 대상으로 한다. 삭제된 프로젝트도 목록에서 지울 수 있어야 하므로 대상 폴더가 현재 존재할 것을 요구하지 않는다. 현재 존재하면 실제 위치를 대조하고, 없어졌다면 목록에 표시된 전체 경로와 저장 표기를 정확히 대조한다. 이름만 같거나 접두어가 같은 항목, 다른 clone을 함께 지우지 않는다. 없는 항목 제거는 변경 없음으로 끝나며 다른 항목은 보존한다.

프로젝트를 이동했다면 새 위치의 기기 연결을 먼저 검사/준비하고 `projects add`로 등록한 뒤 옛 항목을 `projects remove`로 정리한다. 자동 추적/디스크 검색/같은 이름으로 재연결하지 않는다. 이 명령은 프로젝트 자체의 이동이나 WIKI 경로 변경을 수행하지 않는다.

목록 저장 실패는 프로젝트 설치/연결의 실제 결과와 구분해 안내한다. 목록 때문에 정상 프로젝트 파일을 롤백/초기화하지 않으며, 재등록 또는 현재 위치/명시 경로 시작 방법을 제공한다. 설치 절차가 요청한 목록 등록까지 마치지 못했다면 모든 준비가 완료됐다고 표시하지 않는다. 설치기의 기존 기록에는 해당 준비 결과를 연결하되 평소 목록 조회/관리마다 새 작업 DB나 개발 active를 만들지 않는다.

## 기록 중단과 동시 갱신

JSON 배열을 매번 원본 파일에 조금씩 덮지 않는다. **같은 사용자의 목록 갱신끼리만 짧게 조정하고, 최신 목록을 읽어 한 변경을 합친 뒤 완성한 파일로 교체하는 흐름**으로 명세한다. 프로젝트 개발 세션을 통째로 잠그는 절차가 아니다. 설치/사용자 문서의 [파일 보존 정책 — 「파일 반영과 핸들 수명」](update.md)을 이 보조 목록의 방식으로 바꾸지 않는다.

1. 쓰기 요청과 대상 검사를 먼저 끝낸다. 목록을 바꾸는 짧은 구간에 같은 데이터 폴더의 `projects.lock`으로 작성자 간 접근을 조정한다. Windows 표준 [msvcrt.locking](https://docs.python.org/3.13/library/msvcrt.html#msvcrt.locking)의 고정 바이트 영역/비대기 잠금을 구현 후보로 삼는다. 파일 존재를 실행 중 증거로 보거나 PID/시간만 보고 잠금 파일을 지우지 않는다.
2. 조정에 성공한 뒤 현재 목록을 다시 읽고 형식/기존 항목을 검사한다. 이전 화면의 배열을 그대로 덮어써 다른 등록을 잃지 않는다. 실패하면 변경 없이 필요한 대응을 반환한다. 잠금 충돌이 확인되면 사용 중을 알리고 무한 대기/자동 재시도하지 않는다.
3. 같은 폴더에 이 호출이 소유한 임시 파일을 배타적으로 만들고 완성한 UTF-8 배열을 저장/검사한다. [os.replace](https://docs.python.org/3/library/os.html#os.replace) 같은 교체 수단으로 반영하고 재읽어 해당 결과를 확인한다. 원본과 후보를 다른 파일시스템에 두지 않는다.
4. 성공/실패/취소 모두 핸들을 정리한다. 갱신 조정은 Codex 자식 실행 전에 끝내고 핸들을 자식에게 물려주지 않는다. 잠금용 파일은 빈 목록이나 성공 기록이 아니다. 사용 중 파일을 삭제/재생성해 서로 다른 파일을 잠그는 상황을 만들지 않는다.
5. 중단 뒤 남은 임시 파일을 정식 목록으로 자동 승격하지 않는다. 재실행은 현재 정식 목록을 읽고 같은 추가/제거의 실제 반영 여부를 대조한다. 원문이 손상됐거나 반영 여부를 설명할 수 없으면 보존하고 실패를 안내하며 빈 배열로 초기화하지 않는다.

이 조정은 OnepLoom의 같은 규약을 사용하는 작성자 사이의 것이다. 임의 외부 편집기를 동시에 사용해도 손실이 없다는 보장은 하지 않는다. 읽은 뒤 교체 전 외부 변경을 발견하면 중단하고, 프로그램이 관리하는 목록은 위 명령으로 수정하도록 안내한다. 운영체제 호출의 성공을 전원 차단 후 영속성이나 모든 저장장치의 무손실로 확대하지 않는다. 실제 파일 사용 중/권한/강제 종료/두 작성자 시험을 통과해야 구현 완료다.

## 결과와 오류의 연결

[기존 결과 형식 — 「명령 결과의 형식」](entry.md)과 준비 종료 코드를 사용한다. 목록 명령은 `operation`에 `projects.list`, `projects.add`, `projects.remove`, `stage`에 `catalog`를 사용한다. 성공한 `projects.list --json`만 `projects` 경로 배열을 추가하고, 이 결과의 `ready`는 목록 조회 완료를 뜻한다. 등록된 모든 프로젝트의 실행 준비를 확인했다는 뜻이 아니다. add/remove는 성공 설명 또는 기존 오류 필드로 결과를 알리며 전체 목록을 매번 반환하지 않는다.

| 상황 | status / reason / 준비 종료 코드 |
| --- | --- |
| 목록 조회/추가/제거 성공 또는 변경 불필요 | `ready` / reason 생략 / 0 |
| 명령/옵션 충돌, 빈 경로 등 입력 문법 오류 | `error` / `invalid_input` / 2 |
| 자동 처리/JSON에서 대상 선택 필요 | `needs_input` / `project_selection_required` / 3. 목록은 별도 list로 조회 |
| 대화형 선택 취소 | `cancelled` / `user_cancelled` / 4 |
| EOF 등 필요한 선택을 받지 못함 | `needs_input` / `project_selection_required` / 3 |
| 목록을 읽거나 검증할 수 없음 | `error` / `invalid_project_catalog` / 1. 접근 오류와 형식 오류는 설명에서 구분 |
| 확인된 다른 작성자의 잠금 충돌 | `error` / `project_catalog_busy` / 1 |
| 목록 저장/확인을 완료하지 못함 | `error` / `project_catalog_write_failed` / 1. 무변경/반영 확인/불명을 설명 |

대상 경로/설치/연결의 오류는 기존 `project_mismatch`, 미지원/입력 필요 등의 분기를 그대로 사용한다. 실제로 해결한 `project_root`만 결과에 넣으며 제거한 오래된 경로를 현재 유효 프로젝트로 표시하지 않는다. 결과의 한글 문구를 자동 판별에 사용하지 않고 `status`/`reason`을 소비한다. `--json`에는 질문/로그/배너를 섞지 않으며 상세 진단은 stderr로 분리한다.

## 구현 전에 유지할 확인 항목

이번 명세는 목록 형식/위치와 명령 경계를 닫는다. 사용자 지정 하네스 위치의 발견과 시작 프로그램의 인자/호환 인계는 [프로젝트 실행본 명세](project-entry.md)로 연결했다. 잠금/교체 API 후보, 실제 Windows의 한글/공백 인자, 표준 사용자 권한과 중단/동시 갱신은 구현 때 [프로젝트 목록 형식과 명령 검증](../../verification/acceptance.md)으로 확인한다. 별도 라이브러리/서버/모델 호출을 이 명세의 필수 준비물로 추가하지 않았으며 외부 코드를 복사하지 않았다.
