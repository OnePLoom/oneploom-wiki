# 선택형 보조 역할

최초 작성: 2026-10-23, 로컬 AI 학습 보강: 10-27, 통합: 10-29. 11/09 기본 메인의 순차 진행, 별도 후보, 단일 반영과 선택 보조 경계를 채택했다. 11/11 [원문 전달과 추가 요청 흐름 — 「코드와 WIKI 접근」](local-ai.md#%EC%BD%94%EB%93%9C%EC%99%80%20WIKI%20%EC%A0%91%EA%B7%BC)은 실제 검증을 전제로 설계 방향을 수용했다. 구체 역할, 호출, 권한, 병렬/로컬 실행과 복구 수단은 **후속 후보**다. 실제 장비, 모델, 비용, 품질은 미확인이고 설치, 호출, 구현은 없다. 로컬 AI의 개념과 사례는 [학습](../../explanations/local-ai.md), 첫 실험 대안은 [ADR 0006](../../decisions/integration/0006-local-assist.md)을 본다.

기본 구조와 필수 이식, 문서 복원은 이 역할을 확정하지 않아도 진행한다. 적용 시점은 [진행표](../../development/roadmap.md)의 선택 분기다. 추천은 코드 우선, 메인 판단/통합, 한 번에 하나의 제한된 보조 호출이며, 역할 수만큼 agent, 서비스, skill을 만드는 안이 아니다.

WIKI 복원의 채택된 기본 진입은 [비대화형 실행 — 「비대화형 실행과 서브에이전트」](../../discussions/knowledge/reconstruction.md)이다. 여기서 메인은 `codex exec`로 실행한 분석 AI이며 일반 실행 코드와 다르다. 서브에이전트는 그 메인에 추가할 선택적 분업이다. 대화형 Codex에서 조건부 하네스를 사용할 때도 작업 책임의 구분은 같지만, 대화형 진입을 채택된 WIKI 실행 B의 대체안으로 적용하지 않는다.

## 서브에이전트와 로컬 보조

10/30 시스템 날짜의 의미 정리다. 최초 모듈 표의 '협업'은 Codex 내부 서브에이전트였고, 이 문서의 로컬 보조는 별도 미채택 후보다. 이름을 하나로 묶어 문서 확장의 설치 선택과 혼동하지 않는다. 기본은 클라우드 메인의 직접 처리이며, 아래 예는 호출 허가나 실험 결과가 아니다.

| 종류 | 실제 의미 | 적합한 예 | 확인할 비용, 한계 |
| --- | --- | --- | --- |
| Codex 서브에이전트 | 메인이 범위를 정해 다른 Codex 작업자에게 맡기고 결과를 검토 | 아직 읽지 않은 제한된 모듈의 호출/테스트 위치 탐색, 명확한 계약 기준의 독립 읽기 리뷰 | 메인과 같은 전체 문맥을 중복 읽으면 손해. 클라우드 사용량이 사라지지 않음 |
| 로컬 보조 | 클라우드 메인을 유지하며 지정 자료의 처리를 로컬 추론기에 요청 | 코드 필터로 부족한 긴 실패 로그의 근거 추출, 한 기능의 코드/이력 사실 후보 정리 | 장비, 모델 품질, 누락, 추가 검토, 실패 비용을 포함한 비교 필요. 아직 도입 미확정 |
| 다른 메인/외부 AI | 주작업자를 바꾸거나 외부 provider에 별도 위임 | 후속 호환성 검토 대상 | Codex 내부 분업, 로컬 보조와 다른 인증/도구/세션 조건. 현재 지원을 뜻하지 않음 |

예를 들어 메인이 API 변경 방향을 검토하는 동안, 독립적인 검토자가 지정된 계약, diff, 테스트만 대조해 누락 후보를 반환할 수 있다. 메인은 결과를 통합하고 검사를 선택한다. 관련 변경이 계속되는 중이면 기준 revision과 입력을 고정하거나 다시 대조해야 한다. 단일 파일 설명, 이미 메인이 모두 읽은 자료 요약, 같은 파일을 동시에 수정하는 작업은 적합한 첫 분업 사례가 아니다.

현행 repository skill/contract는 독립적으로 끝나는 범위, 허용 읽기/수정 경로, 짧고 검토 가능한 출력, 중복 문맥 비용보다 큰 이득을 조건으로 둔다. Explorer, Worker, Reviewer, Analyst는 상시 실행 팀이 아니다. 해당 절차를 읽은 이번 설계 설명에서도 실제 서브에이전트를 호출하지 않았다.

[공식 subagent 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)는 개별 작업자의 모델/도구 사용으로 비교 가능한 단일 작업보다 토큰이 늘 수 있음을 설명한다. custom agent는 부모 provider, 권한, MCP 서버를 상속하며 custom agent 파일에서 이들을 덮어쓸 수 없다고 명시한다. 따라서 cloud Codex의 native subagent 설정에 로컬 모델 이름만 적어 원하는 로컬 위임이 완성된다고 가정하지 않는다. 이는 별도 도구를 통한 로컬 호출이 불가능하다는 뜻도 아니다.

11/09 같은 공식 문서에서 확인한 제약: 현재 Codex는 직접 요청 또는 적용되는 AGENTS/skill 지시에 따라 위임하며, agent 지시에 “수정하지 말라”고 적어도 별도의 읽기 전용 sandbox가 생기지 않는다. 비대화형 실행에서 새 승인을 받을 수 없으면 승인이 필요한 동작은 실패로 돌아온다. 아래 읽기 중심 후보는 작업 책임의 제한이며 기술적 격리를 검증한 결과가 아니다. 지원 버전에서 원본 보존, 권한 경계를 실제 확인해야 한다.

추천은 **같은 WIKI, 계획, 검증, 복구 흐름 안에 보조 분기만 두는 것**이다. 위임 규칙의 기본 포함과 실제 보조 호출의 활성화는 분리한다. 로컬을 채택하면 모드 전환, 실패 처리, 재개의 일관성은 해당 기능의 필수 완료 조건이며, 모든 사용자의 로컬 모델 설치/상시 실행을 뜻하지 않는다. 하나의 흐름/모드별 분리/외부 조정의 세 대안은 [ADR 0014 — 「후속 협의: 문서 확장과 작업 위임」](../../decisions/knowledge/0014-features.md)에서 비교한다.

Codex(OpenAI)와 Claude(Anthropic)는 서로 다른 제공자의 도구다. 첫 적용 메인은 Codex이며 클라우드 메인이라는 표현을 Claude의 즉시 호환 지원으로 확대하지 않는다. 기본 단독 처리에서 native 분업을 어떤 조건으로 허용할지는 별도 정책으로 확인하고, 로컬 보조 ON이 native 분업까지 자동 허용하지 않도록 한다.

## 공개 사례와 적용 후보

11/09 사용 사례 검토다. 아래는 기업이 공개한 제품 구조와 공식 사용 지침이며, 업계 전체의 도입률이나 이 하네스의 효과를 측정한 자료는 아니다. 사례의 운영 구조와 이 프로젝트에 대한 추천을 구분한다.

| 공개 사례 | 맡기는 일과 통합 방식 | 참고할 점 |
| --- | --- | --- |
| [Anthropic Research](https://www.anthropic.com/research/multi-agent-research-system) | 메인이 조사 주제를 나누고 보조들이 서로 다른 방향을 탐색한 뒤 결과를 통합 | 넓은 조사에 적합. 목표, 출력, 출처, 범위가 불명확하면 중복 탐색과 누락 발생 |
| [Harvey Playbook Review](https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system) | 계약 검토 규칙별로 보조를 배정하고 공통 맥락을 제공. 문서 분기에서 만든 수정 제안을 메인이 대조, 통합 | 단일 에이전트의 품질을 먼저 확인한 뒤 지연을 줄이려고 분업. 공유 원문 동시 수정과 충돌을 별도로 처리 |
| [Claude Code Review](https://support.claude.com/en/articles/14233555-set-up-code-review-for-claude-code) | 여러 에이전트가 PR의 서로 다른 오류 유형을 검토하고 검증, 중복 제거 후 보고 | 검토 결과를 곧 승인이나 정답으로 취급하지 않음. 현재 하네스에 해당 유료 제품을 도입한다는 제안은 아님 |
| [Claude Code subagents](https://code.claude.com/docs/en/sub-agents#common-patterns) | 코드 탐색, 긴 로그 등의 작업을 별도 문맥에서 수행하고 관련 결과를 메인에 반환 | 주 대화의 문맥 점유와 전체 사용량은 별개. 같은 문맥을 계속 공유해야 하는 작업에는 메인 직접 처리를 권장 |

현재 구조에 대한 추천은 다음 세 후보로 좁힌다. 별도 상시 에이전트 세 개를 설치한다는 뜻이 아니며 기존 역할과 요청/결과 계약을 사용한다.

| 후보 | 구체 작업 | 유효한 조건과 한계 |
| --- | --- | --- |
| WIKI 근거, 누락 검토 | 작성한 문서의 중요한 주장과 코드, 테스트, 이력을 대조해 근거 없는 단정, 잘못된 인용, 빠진 실패 흐름을 반환 | 정확성이 핵심인 현재 목표에 가장 가까운 Codex 보조 후보. 검토자도 틀릴 수 있어 메인의 근거 대조와 범위별 완료 판단을 대체하지 않음 |
| 한 기능의 코드, 이력 조사 | 메인이 아직 분석하지 않은 기능 범위의 사실, 출처, 연관 경계, 미확인을 정리 | 기능 간 결합이 낮고 입력 경계가 명확할 때. 디렉토리 단위 기계 분할로 공통 계약을 누락하지 않으며 상세 근거를 짧은 요약으로 대체하지 않음 |
| 긴 실패 기록의 원인 후보 분석 | 코드 필터로 좁힌 로그, 실패 테스트, 관련 변경에서 원인 후보와 반증할 검사를 제안 | 단순 오류 추출은 코드로 수행. 보조의 추측을 원인 확정이나 실패 검사 PASS로 바꾸지 않음 |

예를 들어 이벤트 처리 WIKI가 중복 부작용을 막는다고 서술했다면, 검토자는 중복 처리 키, DB 반영과 메시지 확인 사이의 실패 구간, 관련 테스트가 그 서술을 뒷받침하는지 확인할 수 있다. 반환할 것은 문제 지점, 근거, 미확인 조건이며 메인이 원문을 확인해 보정한다. 이는 가상의 적용 예시이고 특정 프로젝트의 실제 결함을 발견했다는 뜻이 아니다.

단독 복원과 독립 검토 한 건의 비교에 더해, 사용자가 여러 기능의 병렬 복원을 제안했다. [범위별 병렬 복원](local-ai.md#%EB%B2%94%EC%9C%84%EB%B3%84%20%EB%B3%91%EB%A0%AC%20%EB%B3%B5%EC%9B%90)에서 작업 크기, 의존성과 검토 비용에 따라 비교한다. 역할표의 수만큼 agent를 만들 필요는 없다. 파일 수집, 해시, JSON 형식, 링크 존재 검사는 코드로 유지하고, 사용자와의 범위 합의, 채택 확인, 최종 반영, 전체 재개 상태는 메인의 책임으로 유지한다. 보조 결과의 문맥 전달과 재조회는 [요청과 결과](local-ai.md#%EC%9A%94%EC%B2%AD%EA%B3%BC%20%EA%B2%B0%EA%B3%BC), 중단 처리는 [실패와 기본 경로 복귀](local-ai.md#%EC%8B%A4%ED%8C%A8%EC%99%80%20%EA%B8%B0%EB%B3%B8%20%EA%B2%BD%EB%A1%9C%20%EB%B3%B5%EA%B7%80)를 따른다.

이 추천은 첫 Codex 보조의 검증 후보를 설명한 것이며, 로컬 R-05/R-09의 품질, 비용 비교나 제품 구현을 승인한 것은 아니다. 비교에서는 누락, 잘못된 주장, 오탐, 최종 수정량과 메인/보조/재검토의 총사용량, 시간을 함께 본다. 같은 모델의 검토도 동일한 실수를 반복할 수 있으므로 테스트, 원문, 사람이 확인한 사례와 대조한다. 실제 이득이 확인되지 않으면 메인 단독을 유지한다. 현재 선택, 실험 입력, 예산은 계속 협의 중이다.

### 검증 비용을 줄이는 로컬 보조

11/11 테스트 실행, 중복, 토큰 검토에 이어 로컬 AI의 활용과 공개 사례를 대조했다. **선택적 로그 해석 보조를 비교할 가치가 있다는 추천이며 도입, 실험 실행, 첫 배포 포함은 미채택**이다. [ADR 0006](../../decisions/integration/0006-local-assist.md)의 코드 기준선과 비교하는 방향을 구체화하며, 검증 계획/결과 계약보다 구현을 앞당기지 않는다.

| 공개 근거 | 확인한 기능, 결과 | 적용 한계 |

| [Continue Ollama 연결](https://docs.continue.dev/guides/ollama-guide) | 로컬 모델과 역할별 설정을 지원하며 chat/edit와 autocomplete에 다른 모델을 지정하는 예시 제공 | 역할 분리 가능성의 근거. 모든 모델의 도구 사용 품질이나 클라우드 대비 절감을 보장하지 않음 |
| [Goose 다중 모델](https://goose-docs.ai/docs/guides/multi-model/)와 [보조 설정](https://goose-docs.ai/docs/guides/context-engineering/subagents/) | 작업 중 모델 전환과 보조별 provider/model 선택을 문서화 | 과거 Lead/Worker와 후속 Planning Mode는 [현재 원문](https://github.com/aaif-goose/goose/blob/main/documentation/blog/2025-06-16-multi-model-in-goose/index.md)에 제거됐다고 명시. 그 방식을 현행 표준으로 추천하지 않음 |
| [Aider architect/editor](https://aider.chat/docs/usage/modes.html#architect-mode-and-the-editor-model)와 [Ollama 연결](https://aider.chat/docs/llms/ollama.html) | 해결 방향과 실제 편집을 다른 모델에 맡길 수 있고 로컬 모델 연결도 지원 | 공식 설명도 두 번의 요청이 시간, 비용을 늘릴 수 있다고 경고. 역할 분리가 절감의 증거는 아님 |
| Meta [TestGen-LLM](https://arxiv.org/html/2402.09171v1) | 내부 모델로 기존 테스트의 개선 후보를 생성하고 빌드, 안정적 통과, 커버리지 개선으로 걸러 Instagram/Facebook에서 적용 | 실제 테스트 개발 사례지만 사용자 PC의 작은 로컬 모델 + Codex 절감 사례는 아님. 생성 품질은 실행, 검토로 확인해야 함 |

따라서 유사한 구성 요소와 실무 활용은 확인했지만, **대기업이 사용자 PC의 로컬 모델로 CI 로그를 요약해 Codex에 전달하는 방식이 널리 쓰인다는 근거는 확보하지 못했다.** Microsoft의 [실제 분류 파이프라인 검토](https://www.microsoft.com/en-us/research/blog/technical-approach-for-classifying-human-ai-interactions-at-scale/#prompt-compression)도 압축으로 정확도가 떨어지거나 처리 시간이 더 길어질 수 있음을 설명한다. 연구, 도구 지원, 실제 배포, 우리 제품 검증을 구별한다.

첫 비교 후보의 동작은 다음과 같다.

1. 기존 실행 코드가 테스트를 수행하고 실제 종료 상태, 모든 실패의 식별/상태, 비밀값을 제외한 근거를 보존한다. 정형 보고서 파싱, 중복 문자열 정리, 검색은 코드가 맡는다.
2. 코드로 정리한 뒤에도 해석할 자료가 크고 보조 사용이 허용된 경우, 메인에 전체 로그를 먼저 출력하지 않고 로컬에 필요한 범위만 전달한다. 짧은 오류, 정형 결과만 필요한 경우에는 호출하지 않는다. 자동 길이 기준은 아직 정하지 않는다.
3. 로컬은 같은 원인으로 보이는 실패의 묶음, 원인 후보, 근거 위치, 반증할 확인과 부족한 정보를 반환한다. 원문과 실패 목록은 보존하고 어느 실패를 아직 설명하지 못했는지도 남긴다. 이를 로컬의 원인 확정이나 검사 완료 선언으로 사용하지 않는다.
4. 메인은 후보의 핵심 근거, 설명되지 않은 실패, 상충하는 구간을 확인해 수정과 추가 검사를 판단한다. 누락, 왜곡이 의심되면 원문을 더 읽는다. 이후 같은 공통 검증 경로로 원래 실패와 수정 영향 범위를 확인한다.

**가상 예시: API 변경 뒤 12개 테스트가 실패했다.** 아래 수와 원인은 흐름 설명용이며 기존 시험 프로젝트에서 실행하거나 발견한 결과가 아니다.

| 순서, 담당 | 입력과 처리 | 다음 단계에 남기는 것 |
| --- | --- | --- |
| 1. 일반 코드 | 테스트를 실행하고 보고서, 종료 상태를 수집. 정형 오류와 반복 문자열을 추림 | 실패 12개와 각각의 원문 위치. 원인과 수정 방향은 미확정 |
| 2. 선택 로컬 | 지정한 실패 기록, 관련 설정에서 다른 형태의 오류가 연결되는지 분석 | ‘11개는 동일 DB 연결 문제에서 파생됐을 가능성, 1개는 응답 검증 문제로 보임’이라는 후보와 각 근거, 미확인 |
| 3. 메인 | DB 연결 후보와 별도 응답 오류의 원문, 코드, 계약을 대조 | 근거가 확인된 조치와 필요한 검사. 로컬의 묶음이 틀리면 분리, 정정하고 자료가 부족하면 추가 확인 |
| 4. 일반 코드 + 메인 | 허용한 수정 뒤 원래 실패와 수정 영향 범위를 실행, 대조 | 실제 재검증 결과와 남은 실패. 로컬의 ‘해결 가능’은 PASS가 아님 |

메인은 위임 목적과 필요한 자료를 정하지만 로그 전체를 먼저 상세 분석할 필요는 없다. 사용자가 두 AI 사이에서 내용을 복사하는 대신 연결 도구가 자료와 결과를 전달하는 후보이며 아직 구현하지 않았다. 예시의 관계를 파서만으로 충분히 밝힐 수 있으면 로컬 호출도 생략한다. 이점은 메인의 긴 자료 탐색 감소이고, 단점은 모델 준비, 지연, 오진, 추가 검토 비용이다. 오류를 잘못 묶거나 별도 실패를 숨길 수 있으므로 모든 실패의 기록과 원문을 유지한다.

절감 대상은 **클라우드가 읽고 분석할 자료와 반복 조사**다. 로컬이 테스트 실행 횟수, 필수 범위, PASS 판정, 재사용 유효성을 임의로 바꾸지 않는다. 형식 검사 통과나 모델 자신감은 내용의 정확성을 입증하지 않는다. 같은 입력을 재개할 때는 이미 실행 중이거나 저장된 결과부터 확인하며, 로그를 다시 분석하려고 원래 테스트를 반복하지 않는다. 입력이 달라졌으면 이전 후보를 그대로 적용하지 않는다. 상태, 중복 처리의 세부 명세는 공통 검증/복구 계약에 연결한다.

테스트 초안, 경계 사례 후보 생성은 다음 비교 후보다. 계약과 기대 결과를 기준으로 메인이 검토하고 실제 실행으로 확인해야 하며, 구현을 그대로 따라 만든 assertion의 통과만으로 정답을 증명하지 않는다. WIKI 상세 복원, 독립 교차 검토도 별도 품질 평가이며 로그 보조의 성공을 전용하지 않는다. 입력 전체의 불투명한 압축, 로컬의 검사 생략 결정, 로컬이 코드를 자유 수정하는 반복 작업은 첫 적용으로 추천하지 않는다.

일반 사용자 관점에서는 로컬이 없어도 같은 필수 기능을 완료하고, 검증한 실행기, 모델, 가용 자원 조합에서만 선택 보조를 켤 수 있어야 한다. 작성자 장비로 최소 사양을 정하거나 모든 사용자에게 GPU, 모델 설치를 강제하지 않는다. 현재 제품의 Windows 지원 조건과 실제 응답/자원 검증은 별도로 남아 있다. 로컬 추론도 토큰, 문맥, 메모리 한계와 전력, 대기, 운영 비용이 있고, Codex로 보낸 결과는 클라우드 입력이다. 실패 시 허용된 기본 경로로 돌아가는 조건은 [실패와 기본 경로 복귀](local-ai.md#%EC%8B%A4%ED%8C%A8%EC%99%80%20%EA%B8%B0%EB%B3%B8%20%EA%B2%BD%EB%A1%9C%20%EB%B3%B5%EA%B7%80)를 따른다.

효과는 [평가 조건 — 「효과를 확인할 조건」](local-ai.md#%ED%9A%A8%EA%B3%BC%EB%A5%BC%20%ED%99%95%EC%9D%B8%ED%95%A0%20%EC%A1%B0%EA%B1%B4)에 따라 코드만 정리한 동일 입력, 검사 범위와 비교한다. 위임 안내, 결과, 추가 원문 확인, 재작업까지 합친 클라우드 사용량이 줄어야 하며, 이미 메인이 읽은 자료를 다시 요약시키면 그 입력 비용을 되돌릴 수 없다. 구독 한도, API 금액과 토큰을 동일시하지 않는다. 로컬 실행 성공만으로 채택하지 않으며 품질, 전체 시간, 설치/유지 부담까지 확인한다. 현재 측정값은 없다.

## 범위별 병렬 복원

11/09 사용자 제안의 비교안이며 미채택이다. 기능별 상세 복원은 기존 목표에 맞지만, 디렉토리 수만큼 무조건 병렬 실행하는 정책은 추천하지 않는다. [Google Research의 비교](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)에서도 병렬화 가능한 작업과 순차 의존이 큰 작업은 효과가 달랐다. 그 연구의 수치를 이 하네스의 예상 성능으로 사용하지 않는다. 전체 기한, 보존, 지원 부담을 포함한 [기본 구조의 추천 — 「목표와 추천」](../architecture.md)은 단위별 순차 복원과 단일 반영이며, 아래 병렬 흐름은 독립 범위에 선택할 확장 후보다.

추천 후보는 다음 흐름이다.

1. 일반 코드와 메인이 선택 범위, 기존 WIKI, 공통 계약, 필요 의존을 확인하고 작업 단위와 완료 조건을 정한다. 메인이 모든 본문을 먼저 상세 분석하는 단계는 아니다. 읽을 수 있는 의존 자료와 WIKI를 작성할 범위는 구분한다.
2. 공통 용어, API/이벤트 계약은 소유 위치와 기준 입력을 공유한다. 독립 단위만 정한 동시 실행 수 안에서 배정한다. 선행 결론이 필요한 단위는 기다리거나 함께 묶고, 숨은 의존을 발견하면 해당 단위를 재분류한다. 큰 단위 하나가 끝없이 커지지 않도록 추가 입력, 분할을 요청할 수 있어야 한다.
3. 보조는 기존 원문을 읽고 **상세 문서 후보와 근거, 처리 범위, 미확인, 연관 단위**를 반환한다. 공식 WIKI, 공유 위치표, active를 각각 수정하지 않는다. 후보는 작업별 허용 위치에 코드가 저장하거나 제한된 후보 저장 권한으로 기록하며 실제 수단은 후속 검증한다.
4. 코드는 결과 형식, 경로, 등록된 근거, 입력 기준, 누락된 작업을 대조한다. 원문과 초안의 의미 검토는 메인 또는 적합성이 검증된 검토 보조가 수행한다. 검토 보조도 메인이 배정하며 재귀 위임을 기본으로 만들지 않는다.
5. 메인은 단위 사이 계약, 용어, 상충 주장과 전체 처리 범위를 대조한다. 중요한 충돌, 근거 부족, 정책 판단은 원문 확인 또는 사용자 협의로 해결한다. 작업자/검토자의 성공 보고를 전체 완료로 바꾸지 않는다.
6. 허용된 후보만 기존 보존 계약에 따라 반영하고 WIKI 연결을 갱신한다. 적용 직전 원본이 바뀌었으면 영향받은 결과를 다시 확인한다. 중단, 늦은 결과, 부분 재시도는 [기존 복구 조건 — 「실패와 기본 경로 복귀」](local-ai.md#%EC%8B%A4%ED%8C%A8%EC%99%80%20%EA%B8%B0%EB%B3%B8%20%EA%B2%BD%EB%A1%9C%20%EB%B3%B5%EA%B7%80)을 사용한다.

| 비교 구성 | 이득 | 부담과 적합한 조건 |
| --- | --- | --- |
| 메인 단독, 단위별 순차 복원 | 문맥 전달, 통합 부담이 작음 | 좁은 범위, 강한 의존에 적합. 넓은 독립 조사에는 시간이 걸림 |
| 범위별 보조 복원 + 메인 검토/통합 | 독립 탐색의 병렬 처리와 문맥 분산 | 공통 입력 중복, 통합 병목, 사용량 급증, 중단 처리가 추가됨. 여러 독립 단위가 있을 때의 추천 후보 |
| 위 구성 + 별도 검토 보조 | 작성과 다른 관점의 검토, 메인 검토량 분산 가능 | 검토 입력, 오탐, 재검토 비용 증가. 모든 단위의 의무 이중 호출로 고정하지 않고 중요한 주장, 충돌 범위부터 비교 |

병렬화는 구독 한도를 늘리지 않으며 같은 한도를 빨리 소모할 수 있다. 전체 시간도 가장 느린 단위와 메인의 통합에 묶일 수 있다. 첫 구현 검증은 단위 하나의 전달, 보존, 재개부터 확인하고 소수 단위의 병렬 시험을 비교하는 추천이며, 현재 기한을 이유로 그 비용을 생략하지 않는다. 이 제안을 병렬 복원 채택이나 모델 호출 허가로 해석하지 않는다.

이 흐름은 논리적인 분업 구조다. 한 `codex exec`에서 native subagent를 호출하는 방식과 실행 코드가 단위별 `codex exec` 작업을 관리하는 방식은 문맥 전달, 출력 강제, 권한, 재개 방법이 다르다. 후자는 자동으로 native subagent가 되는 것이 아니다. 기존 명령 진입 B를 유지하며 구체 호출 수단은 지원 버전, 복구 계약과 함께 결정한다.

역할을 나눠도 같은 기능, 공통 문서가 겹칠 수 있다. 보조 후보를 분리하고 공식 반영을 한 경로로 모으는 것 외에 원문 권한, 입력 변화, 동일 WIKI의 여러 세션, Obsidian 편집, 부분 실패를 확인해야 한다. 이 공통 책임은 [동시 편집과 반영](../runtime/install.md)이 소유한다. Git의 충돌 없는 병합이나 마지막 파일 해시 확인만으로 동시성 문제가 해결됐다고 보고하지 않는다.

## 공통 규칙과 호출 범위

11/09 채택한 경계는 **기본은 메인 직접 처리, 공통 위임 규칙은 기본 제공, 실제 보조 호출은 명시적으로 허용한 작업에서만 선택**하는 방식이다. 규칙을 설치하는 것과 agent/로컬 서버를 실행하는 것은 다르다. 여기서 작업은 합의한 복원/개발 범위이며, 하위 단위나 대화 턴마다 같은 승인을 받는 뜻이 아니다. 보조 기능이 없어도 채택한 WIKI 복원, 검증, 재개를 수행할 수 있어야 한다. 비교와 구체 미정 사항은 [ADR 0014 — 「후속 협의: 위임의 공통 책임」](../../decisions/knowledge/0014-features.md)가 소유한다.

| 항목 | 공통으로 지킬 책임 | 실제 호출의 조건 |
| --- | --- | --- |
| 작업과 입력 | 질문, 완료 범위, 허용 경로, 기준 버전, 필요한 근거를 전달 | 독립적으로 처리 가능하고 메인이 이미 한 탐색을 반복하지 않을 것 |
| 허용과 비용 | 사용할 보조 종류, 대상, 입력 반출, 작업 범위, 시간/사용량 제한을 확인 | 사용자 요청이나 승인된 프로젝트 설정이 있어야 하며 도구가 존재한다는 사실만으로 허용하지 않음 |
| 결과 | 사실/후보, 출처, 미확인, 처리하지 못한 범위를 구별 | 메인이 입력 기준과 핵심 근거를 대조한 뒤 통합. 보조 종료를 전체 완료로 보지 않음 |
| 변경 | 처음 검증할 보조는 탐색, 근거 추출, 독립 검토만 맡고 최종 파일 반영은 메인이 소유 | 같은 파일의 동시 수정, 보조의 재위임은 첫 지원 범위에서 제외. 수정 금지 지시와 실제 권한 격리는 별도로 검증 |
| 복구 | 작업 식별, 입력, 미완료, 반영 여부를 기존 로컬 상태와 연결 | 늦게 도착한 결과, 재개, 재시도에 동일한 보존 기준 적용. 실행자별 active/WIKI 원본을 만들지 않음 |

첫 검증은 Codex의 제한된 보조 한 건부터 제안한다. 원본 수정 없이 후보를 반환하고 메인이 검토하는 흐름을 확인한 뒤, 독립 작업의 병렬화나 보조의 코드 수정이 실제로 필요한지 판단한다. 메인이 아직 해야 할 핵심 일을 그대로 보조에 넘겨 대기하거나 전체 대화를 매번 복제하는 방식은 이득을 먼저 확인한다. 최소 입력만 전달한다고 해도 적용할 규칙과 필수 근거까지 빼지는 않는다.

로컬 연결은 같은 규칙을 사용하는 별도 후보이며 품질, 총비용 비교를 통과한 역할만 대상으로 한다. 이 구조 추천이 로컬 시험을 무조건 뒤로 미루거나, 첫 배포에 반드시 넣거나, 로컬 단독 실행을 채택한다는 뜻은 아니다. 같은 상세 WIKI 기준에서 입력, 모델, 환경, 허용 차이, 비용을 정한 뒤 실험한다. 아직 자료를 보지 않은 단계에서 특정 사용자의 하드웨어나 모델을 공통 기본값으로 고정하지 않는다.

## 위임할 조건

11/08 [WIKI 생성, 보강 검토 — 「로컬과 클라우드」](../../discussions/knowledge/reconstruction.md)는 로컬 단독 실행, 로컬 후보+상용 검토, 메인의 로컬 위임을 구분한다. 기존 로그 정리 후보를 폐기하거나 WIKI 역할을 먼저 구현하자는 채택이 아니다. 입력, 근거, 누락 점검과 전체 비용을 비교한 뒤 역할별로 판단하며 현재 로컬 도입은 미확정이다.

1. **일반 코드로 충분한가?** 그렇다면 AI 역할을 만들지 않는다.
2. **클라우드가 실제로 많이 읽거나 생성하는 구간인가?** 짧고 이미 메인 문맥에 있는 일은 위임 준비, 검토가 더 비쌀 수 있다.
3. **입력과 완료 조건을 좁힐 수 있는가?** 저장소 전체를 다시 이해해야 하면 첫 로컬 후보에서 제외한다.
4. **내용, 누락을 검증할 수 있는가?** 인용 위치의 존재 확인만으로는 충분하지 않다.
5. **실패하면 원래 경로로 복귀할 수 있는가?** 실패, 시간 초과, 재검토 비용까지 포함해도 이득이 있어야 한다.

따라서 비용 절감용 위임은 클라우드 사용량이 크고 범위가 명확하며 결과를 확인할 수 있는 일이 후보다. 독립 검토는 오류 발견, 병렬 복원은 처리 시간, 문맥 분산처럼 목적이 다를 수 있다. 각각의 이득을 준비, 중복 입력, 통합, 재검토 비용과 비교한다. 분류를 위한 별도 학습형 router나 gate별 AI를 초기 도입하지 않는다.

### 로컬 AI 교차 검토

11/11 사용자는 다른 모델이 메인이 놓친 WIKI 오류를 발견할 수 있는지 재확인했다. **토큰 절감용 분담과 품질 보강용 교차 검토는 목적이 다르다.** 후자는 자료를 의도적으로 다시 읽는 비용이 들 수 있다. 여러 agent가 같은 모델을 쓰는 경우와 서로 다른 모델을 쓰는 경우도 구분한다. 모델이 다르다는 사실만으로 오류가 독립적이거나 검토 능력이 충분하다고 보지 않는다.

| 실제 공개 사례 | 맡기는 역할 | 우리 설계와의 경계 |
| --- | --- | --- |
| Meta [Catching JiTTests](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/) | 여러 LLM이 생성된 테스트, 실행 결과, 코드 변경, 의도를 평가하고 규칙 기반 판정으로 보완 | 실제 운영 사례. LLM의 비결정적 판단만으로 품질을 확정하지 않으며 사용자 PC 로컬 모델의 WIKI 성능을 입증하지 않음 |
| Google DeepMind [AlphaEvolve](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/) | Gemini Flash는 넓은 후보 탐색, Pro는 깊은 제안에 기여하고 생성 프로그램은 별도 평가기로 실행, 채점 | 여러 모델의 역할 분담과 실행 검증 사례. 일반 WIKI 검토나 로컬/클라우드 혼합의 직접 실험은 아님 |

WIKI의 첫 교차 검토 후보는 한 문서의 조건 누락, 근거 없는 단정, 상충 설명을 찾는 일이다. 검토자는 같은 기준 버전의 원문, 초안, 확인할 기준을 받고 문제 후보, 출처, 미확인을 반환한다. 작성자의 ‘정답’이나 자신감으로 판단을 유도하지 않으며, 필요한 입력이 없으면 추측 대신 추가 자료를 요청한다. 코드로 정확히 확인할 수 있는 일은 모델로 바꾸지 않는다.

가상 예시로 초안이 ‘모든 실패 요청을 재시도한다’고 쓰고 실제 구현은 ‘통신 오류만 재시도, 권한 오류는 즉시 중단’이라면, 로컬은 문장과 해당 분기를 대조해 과도한 일반화를 지적할 수 있다. 메인은 다른 호출 경로, 관련 테스트도 확인해 문장을 보정한다. 로컬은 코드만으로 당시 선택 이유를 만들어 ADR에 추가하거나 WIKI를 직접 덮지 않는다. 로컬 지적에 근거가 있으면 메인 초안을 정정하고, 반영하지 않으면 근거와 미확인을 남긴다. 메인이 더 강한 모델이라는 가정만으로 의견을 기각하지 않는다. 이는 설명 사례이며 실제 모델의 발견 결과가 아니다.

첫 후보는 추가 의견 제공이다. 검증된 품질 없이 로컬의 ‘문제 없음’을 필수 의미 검토의 대체나 자동 승인으로 사용하지 않는다. 중요한 계약이거나 의존 범위가 크거나 근거가 부족하면 메인이 원문을 확인한다. 모델끼리 의견이 같다는 사실은 증거로 취급하지 않는다. 해결되지 않은 충돌은 미확인으로 남기고 요구, 정책 판단이 필요하면 사용자와 협의한다. [Anthropic 평가 지침](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)은 코드, 모델, 사람 평가를 조합하고 모델 판단을 전문가 기준과 대조할 것을 권한다. 평가 자료에는 실제 오류, 정상 사례, 자료 부족을 함께 넣고 누락, 오탐, 재작업을 본다.

단독 작성과 작성 + 로컬 검토를 비교할 때는 같은 예산의 메인 자체 재검토도 대안으로 본다. 새로 잡은 중요한 오류, 잘못된 지적, 최종 잔여 오류, 전체 토큰/시간을 함께 측정해야 다른 모델을 추가한 가치와 단순 추가 검토량의 효과를 구별할 수 있다. 상세 복원 평가는 [WIKI 품질 비교 — 「품질 비교 방법」](../../discussions/knowledge/reconstruction.md)가 소유한다. 검토 기능 채택, 첫 배포 포함, 모델 실행은 계속 미합의다.

로컬 추론에는 구독형 클라우드 호출료가 없어도 하드웨어, 메모리, 전력, 대기, 설치/운영, 재검토 비용이 있다. [Ollama FAQ](https://docs.ollama.com/faq)는 병렬 요청의 메모리 증가와 자원 부족 시 대기를 설명한다. 배포 설계는 사용자별 모델, 실행기, 가용 자원에 맞춰 지원 조건을 확인하며 작성자 PC만으로 품질을 보장하지 않는다.

로컬 실행은 입력의 외부 전송을 줄일 수 있으나 전체 흐름의 보안을 자동 보장하지 않는다. 실행기 cloud 기능, 외부 도구, 로그, 접근 권한을 구분하며, 로컬 결과/인용을 Codex에 보내면 그 내용은 클라우드 입력이다. Ollama도 로컬 실행과 cloud 모델을 구분하고 cloud 기능을 끄는 설정을 제공한다. 로컬 전용 자료의 실패를 클라우드 재요청으로 조용히 바꾸지 않는다. 실제 비밀값은 기존 비기록 기준을 그대로 따른다.

## 역할표

`R-xx`는 협의 대상을 식별하는 번호다. 별도 프로세스, agent 이름이 아니며 역할 수는 통합, 분리할 수 있다. 아래의 ‘메인’은 Codex, ‘코드’는 일반 도구, script, 작은 실행기를 뜻한다. 모두 제안 상태다. 11/11 보정: 로컬/클라우드는 실행 위치이고 능력의 서열이 아니다. 역할은 실제 모델의 품질, 문맥, 권한, 실패 비용으로 평가한다.

| 실행 주체 | 맡길 책임 | 이 위치에 두는 이유 | 맡기지 않을 책임 |
| --- | --- | --- | --- |
| 일반 코드 | 파일/차이 수집, 경로, 형식, 입력 기준 대조, 실행 결과 기록 | 계산, 형식, 실행 사실을 재현 가능한 규칙으로 처리 | 요구 해석, 과거 의도 추정, 내용 정확성의 최종 판단 |
| 메인 AI | 요구/정책 해석, 작업 분할, 위임 선택, 결과 대조, 통합, 변경, 검증, 완료 보고 | 사용자 합의와 여러 자료의 문맥을 잇고 한 곳에서 반영 책임을 유지 | 근거 없는 과거 결정 생성, 사용자 의사결정의 임의 대체 |
| Codex 서브에이전트 | 지정 범위 탐색, 독립 검토와 근거/미확인 반환 | 분리 가능한 조사, 검토를 별도 문맥에서 수행 | 전역 계획, 정책 채택, 전체 완료 결정. 첫 제안에서는 공유 파일 직접 수정도 제외 |
| 선택 로컬 보조 | 품질 확인을 통과한 제한 자료의 사실, 근거 추출, 좁은 오류 후보 검토 | 큰 자료의 일부 해석을 옮기거나 다른 관점의 문제 후보를 얻되 영향 범위를 제한 | 자유 저장소 탐색, 임의 도구 실행, 정책 채택, 원본 덮어쓰기 |

정형 반복 처리는 우선 코드, 제한된 의미 처리는 검증된 보조, 넓은 의존 관계와 통합은 충분한 문맥을 가진 메인에 두는 추천이다. 보조가 전체 계약의 최종 결론을 내리고 메인이 요약만 승인하면 위 경계를 지킨 것이 아니다. 범위가 좁아도 어려운 검토일 수 있으므로 ‘단순 업무’라는 이름만으로 약한 모델에 배정하지 않는다. 후속 모델 평가로 역할 범위를 바꿀 수 있지만 실행 중 임의로 권한, 검증 책임을 교환하지 않는다.

## 기존 subagent와의 관계

| 기존 capability | 대응 역할 | 로컬로 그대로 옮기지 않는 이유 |
| --- | --- | --- |
| Explorer | R-02, R-09 | 무제한 저장소 탐색은 문맥, 도구 loop가 커진다. 코드가 수집한 범위의 후보 정리, 근거 추출부터 검토 |
| Worker | R-07, R-08, 일부 R-09 | 구현, 문서 반영은 계약 이해, 수정 권한을 동반한다. 첫 로컬은 입력만 처리하고 결과 후보를 반환 |
| Doc Governance Reviewer | R-10 | 정형 위반과 의미 판단을 먼저 분리. 공식 채택 권한을 옮기지 않음 |
| Verification Analyst | R-05, R-06, R-11 | 로그 추출, 인과 판단, 기계적 PASS 유효성 비교는 서로 다른 능력. 앞부분만 첫 로컬 후보 |

기존 packet의 목적, scope, 근거, 미확인, 최소 다음 확인 개념은 활용할 수 있다. 다만 큰 packet 전체를 매번 메인이 다시 쓰거나, cloud-native subagent를 한 번 더 거쳐 로컬을 호출하는 계층은 초기 권하지 않는다. 역할 이름을 유지하는 것보다 중복 문맥과 통합 비용을 줄이는 것이 목적이다.

## 협업 선택과 연결

모드 이름은 설명용이다. 아래 문자열이나 `/mode`가 현재 실제 명령으로 존재하는 것은 아니다.

| 모드 후보 | 메인 | 보조 | 초기 범위 |
| --- | --- | --- | --- |
| Codex 기본 | Codex | 없음 | 기본값, 보조 서비스 의존 없음 |
| 로컬 협업 | Codex | 로컬 모델 | 첫 추가 대상, 직렬, 범위 제한 |
| 다른 AI 협업 | Codex | 지정한 외부 AI | 요청/결과 계약과 인증, 기능 확인 뒤 추가 |
| 로컬 단독 | 로컬 모델의 agent loop | 필요 시 별도 | 주작업자 전환, 인계라는 후속 기능 |

추천 제어 방식은 native `/model`을 개조하지 않고 명시 호출 skill과 작은 명령 도구로 보조 허용 상태를 바꾸는 것이다. [공식 명령 문서](https://learn.chatgpt.com/docs/developer-commands)의 `/model`은 현재 모델 선택이며 우리 모듈의 보조 위임 정책 전환 명령이 아니다. [공식 skills 문서](https://learn.chatgpt.com/docs/build-skills)는 `/skills`나 `$skill-name`으로 skill을 선택하는 흐름을 안내한다. 실제 전환 skill/명령은 아직 없으며 임의의 slash 명령이 지원된다고 약속하지 않는다. skill은 진입 안내를 맡고, 실행기는 저장된 허용 상태, 대상, 작업 범위를 확인하는 안이다. 설정 위치, 지속 범위, 재개 동작의 채택과 구현은 별도다.

- 모드 ON은 매 요청마다 보조를 호출한다는 뜻이 아니다. 허용된 작업이고 이득이 기대될 때만 메인이 요청한다.
- 11/09 보정 추천: 선택은 특정 작업과 허용 범위에 묶는다. 다른 작업에 이전 선택을 자동 승계하지 않고, 승인된 프로젝트 설정이 있다면 적용 범위를 확인한다. 같은 작업의 재개는 저장한 선택, 연결, 권한, 남은 비용 범위를 먼저 대조한다. 모두 유효하면 매 호출/재개마다 같은 승인을 반복하지 않는다. 대상, 반출, 권한, 비용이 달라졌거나 상태를 확인할 수 없으면 영향받는 호출을 보류한다. 앞선 재개 때마다 재활성화하자는 후보를 이 조건부 유지안으로 좁혔으며 아직 미채택이다.
- compact 뒤에는 대화 요약만 믿지 않고 저장된 모드와 작업 식별, 유효성을 대조한다. 동일 세션의 유효한 선택을 임의 초기화할 필요는 없지만, 상태가 불명확하면 기본 모드로 두고 알린다. 실제 hook 적용은 별도로 검증한다.
- 첫 전환은 보조 작업이 없는 경계에서만 허용한다. 진행 중 provider 교체, 강제 취소, 중복 실행은 지원하지 않는다.
- OFF, 상태 누락, 오류이면 보조 진입점이 송신을 거부한다. 보조 실패를 검증 PASS로 바꾸거나 다른 외부 AI로 조용히 전송하지 않는다.
- 연결 불가 시 미완료 상태와 재처리 비용을 알린다. 기본 Codex 경로의 처리가 이미 허용한 입력, 비용 안일 때만 이어가며, 로컬 전용 자료의 클라우드 반입, 새 외부 provider, 예산 확대는 자동 대체하지 않는다.

검증할 첫 연결 후보는 현재 shell 도구에서 호출하는 작은 실행 명령과 로컬 추론 서버의 문서화된 HTTP API로 좁힌다. 실행기는 모드, 입력, 응답을 확인하고 기록한다. 흐름의 설계 방향은 수용됐지만 정확한 명령, 설정, 실험 실행은 후속이다. MCP 서버는 처음부터 필수가 아니며 다른 클라이언트가 같은 도구 계약을 실제로 필요로 할 때 wrapper로 추가한다.

모드 확인은 이 보조 진입점의 제어다. 임의 shell, 네트워크 경로까지 막는 보안 경계는 아니다. 안정된 작업/세션 식별과 재개 복구를 구현할 수 없으면 자동 지속 모드를 먼저 포기하고 명시적 단건 위임으로 축소한다. 이 단건 방식도 맞지 않으면 협업 기능을 보류한다.

### Ollama 연결 후보

11/11 사용자는 로컬을 도입한다면 Ollama 사용을 고려한다고 밝혔다. **Ollama는 모델 자체가 아니라 모델을 내려받고 실행, 호출하는 도구**다. 첫 연결 후보는 기존의 로컬 chat API로 유지하며 특정 모델, 도입, 설치가 채택된 것은 아니다. [공식 Windows 지원](https://docs.ollama.com/windows)은 native 앱과 localhost API를 제공하므로 현재 제품의 Windows 직접 실행 방향에 맞는 후보지만, 우리 모듈에서의 실제 연결, 중단/재개, 지원 모델 품질은 미검증이다.

추천 흐름은 ‘설정한 모델, 역할 확인 → 허용 범위의 자료 전달 → Ollama가 선택 모델 실행 → 연결 코드가 응답 형식, 출처를 대조 → 메인 검토’다. [모델 목록 API](https://docs.ollama.com/api/tags)는 생성 호출 없이 설치 목록을 조회하고, [구조화 출력](https://docs.ollama.com/capabilities/structured-outputs)은 JSON schema에 맞는 반환을 지원한다. 목록에 존재하거나 JSON이 유효하다는 사실은 업무 품질의 보증이 아니다. 사용자별 모델, 양자화, 컨텍스트, 가용 자원과 해당 역할의 실제 결과를 평가하고, 없는 모델을 임의 다운로드하거나 낮은 품질의 모델로 조용히 대체하지 않는다. 핵심 정책은 Ollama 전용 형식에 결합하지 않고 연결 부분에서 변환한다.

[Ollama FAQ](https://docs.ollama.com/faq)는 cloud 기능을 끄는 로컬 전용 설정을 제공하며, localhost 주소만으로 로컬 추론을 인증하지 않는다. 로컬 전용 설정, 설치 모델, 송신 경계를 확인한다. Codex 메인이 클라우드인 협업 모드 전체를 오프라인, 외부 전송 없음으로 설명해서도 안 된다.

[Ollama API 호환 문서](https://docs.ollama.com/api/openai-compatibility)의 일부 호환만으로 Codex 세션 전체를 endpoint 변경으로 옮길 수 있다고 가정하지 않는다. [Codex subagent 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)의 provider 상속과도 구분한다.

## 첫 위임 후보

아래는 로컬 처리의 시험 후보다. 첫 Codex 보조의 호출/반영 검증과 구분하며, 역할별 효과, 준비 상태를 보고 실제 실험 범위를 정한다.

### R-05 — 실패 로그의 근거 연결형 추출

- 입력 후보: 메인이 정한 분석 질문, 명령, 실패 종류에 대한 필수 메타데이터, 코드가 보존한 로그의 제한된 구간과 구간 ID. 길면 처리 범위를 명시해 나눈다.
- 코드의 선행 일: 종료 코드, 실패한 테스트 등 이미 정형인 값 추출, 중복 제거, 범위 선택, 원시 stdout/stderr와 잘림 여부 보존. 이것으로 충분하면 로컬을 호출하지 않는다.
- 로컬의 일: 오류, 증상 후보 분류, 관련 구간 묶기, 원문이 뒷받침하는 내용과 추론 구분, 추가 문맥 필요 표시.
- 결과 후보: `관측 사실 / 근거 구간 ID / 해석 후보 / 모르는 것 / 추가 확인 요청`. 원인 확정과 해결 명령은 필수 출력으로 요구하지 않는다.
- 메인의 일: 필수 실패 신호와 핵심 근거 원문 확인, 코드, 계약과 대조한 원인, 수정 판단, 같은 실패 검증의 재개.
- 기각 조건: 코드 필터만으로 충분함, 필수 오류를 자주 누락함, 메인이 결국 로그 대부분을 다시 읽음, 로컬 대기, 재처리가 이득을 상쇄함.

| 반례 후보 | 확인할 것 |
| --- | --- |
| 마지막 구간에만 실제 실패가 있음 | 앞부분만 처리하고 ‘주요 오류 없음’으로 끝내지 않는가 |
| 과거 오류, 경고, 예상된 실패와 현재 실패가 섞임 | 실행 맥락, 부정 표현을 구분하는가 |
| 서로 떨어진 구간이 함께 있어야 원인이 보임 | 불충분한 chunk에서 원인을 단정하지 않는가 |
| 입력 일부 누락, 너무 긴 출력, 근거 ID 불일치 | 불완전함을 표시하고 재조회/승격하는가 |
| 로그에 지시문, 위험한 명령, 민감 정보가 섞임 | 이를 실행 지시로 따르거나 원문을 불필요하게 재전송하지 않는가 |

### R-09 — 문서와 코드, 이력에서 사실 후보 추출

- 입력 후보: 하나의 기능, 변경 범위, 질문과, 코드가 수집한 관련 파일/이력의 제한된 묶음. 저장소 전체에서 자유롭게 REQUIREMENTS, ADR을 완성하는 요청은 제외한다.
- 로컬의 일: 확인 가능한 동작, 제약, 변경 사실, 서로 다른 자료의 모순, 명시된 결정 문구를 근거 위치와 함께 정리한다.
- 메인의 일: 현재 코드와 과거 이력을 구분하고, 최신 공식 기준과 대조하며, 제품 요구, 정책, 과거 결정에 대한 추가 확인을 사용자에게 요청한다.
- 출력 제한: ‘코드에서 이렇게 보임’, ‘당시 기록에 이렇게 명시됨’, ‘이유는 확인 불가’를 구분한다. 자료에 없는 설계 의도를 자연스럽게 채우지 않는다.
- 기각 조건: 근거 대조에 원문 전체 재독이 필요함, 넓은 맥락의 모순을 반복 누락함, 작은 자료라 위임 준비가 더 큼.

문서 복원은 이 역할의 응용이다. 분석 결과는 근거와 대상 문서의 현재 상태를 대조한 뒤 반영한다.

## 요청과 결과

역할을 나눠도 매번 메인이 장문의 지시, 메타데이터를 작성하면 절감 목적과 충돌한다. 다음의 세 층을 구분하는 방향을 제안하며, 전체 schema는 아직 확정하지 않는다.

| 층 | 누가 채우는가 | 내용 후보 |
| --- | --- | --- |
| 판단 입력 | 메인 | 작업 종류, 질문, 완료 범위, 허용 입력 선택, 필요한 의미상 제약 |
| 실행 envelope | 코드 | job 식별자, revision, 입력 hash, 실행 조건, 모드/권한 확인, 예산, 시간, artifact 위치, 검증 기록 |
| 모델 입출력 | 코드가 필요한 것만 전달, 모델이 결과 생성 | 작업 규칙, 자료 구간, 역할에 따른 상세 문서 후보, 사실/근거, 미확인. 모델이 실행 완료를 자가 인증하지 않음 |

모델이 자기 입력의 hash, 실행 증거, 권한 준수를 스스로 증명하게 만들지 않는다. 코드는 메타데이터를 자동 부착, 대조하고, 모델에는 의미 처리에 필요한 부분만 보낸다. 기존 packet의 모든 필드를 모델 입력에 복제하는 것은 아니다.

원문은 로컬 artifact로 남고 메인은 필요한 구간을 다시 볼 수 있어야 한다. **원문 위치가 유효하다는 검사와 요약의 내용, 완전성 검사는 별개**다. 결과가 짧고 JSON이 유효하다는 이유로 검토를 끝내지 않는다. 모델의 높은 자신감도 근거가 아니다.

### 코드와 WIKI 접근

11/11 사용자는 아래 전달, 추가 요청 흐름을 **실제 구현과 문제 여부를 검증할 설계 방향으로 수용**했다. 같은 방향을 다시 선택받지 않되 구현 가능성, 품질, 총비용을 확인해 보완하거나 적용 여부를 판단한다. 로컬 최종 도입, 첫 배포 포함, 모델, 실험 입력/예산은 아직 미확정이다.

여기서 **메인 AI**는 현재 Codex를 통해 사용하는 GPT 같은 모델이다. **Codex CLI**는 그 모델과 대화하고 도구를 실행하는 터미널 프로그램이다. 모델이 다음 작업과 확인할 근거를 판단하고, 프로그램이 실제 명령을 실행한다. 두 대상을 묶어 “메인 Codex”라고 부르지 않는다.

**로컬 연결 프로그램**은 로컬 보조를 도입할 경우 모듈에 구현할 일반 코드다. 메인 AI의 도구 요청에 따라 Codex CLI가 이 프로그램을 실행하면, 등록된 파일을 읽고 Ollama API로 전달한 뒤 결과를 돌려준다. Ollama는 선택한 로컬 모델을 실행하는 프로그램이고, 실제 분석은 그 로컬 모델이 한다. 로컬 연결 프로그램은 아직 구현하지 않았다.

| 필요한 정보 | 어디에서 받는가 | 프로그램이 수행하는 일 |
| --- | --- | --- |
| 질문, 이번에 읽을 파일/범위, 의미상 제약 | 메인이 명령 인자나 요청 파일로 전달 | 전달받은 작업을 구성. 어떤 자료가 관련 있는지 임의 추론하지 않음 |
| 프로젝트/WIKI 루트, 선택 모델, 허용 조건 | 사용자가 등록한 설정과 작업 입력 | 상대 경로 해석, 접근/입력 크기 확인, 호출 대상 선택 |
| 실제 파일 본문 | 위 경로의 파일시스템 | 원문 읽기, 출처/기준 버전 부착, API 요청에 포함 |
| 결과, 추가 자료 요청 | 로컬 모델의 응답 | 형식 확인, 결과 보존, 메인에 전달 |

즉, **메인은 파일 내용 전체 대신 질문과 읽을 대상 정보를 전달한다.** 대상조차 모르면 메인/검색 도구가 먼저 후보를 찾는다. 미리 정한 경로, 위치표, 검색 조건으로 후보를 수집할 수는 있지만, 프로그램이 아무 입력 없이 의미상 필요한 파일을 알아내는 것은 아니다. 메인이 모든 파일을 먼저 분석하거나 사용자가 두 AI 사이에서 내용을 복사할 필요는 없다. 같은 원본을 사용하므로 로컬용 WIKI 사본이나 Obsidian 연결도 따로 만들지 않는다.

[Ollama chat API](https://docs.ollama.com/api/chat)는 요청의 메시지, 자료를 입력으로 받는다. 폴더 경로만 전달한다고 본문을 읽거나 메인 대화, 읽기 이력, 지침, 권한을 자동 상속하지 않는다. 등록된 루트는 연결 코드의 경로 해석 기준이며 모델의 무제한 파일 접근 허가가 아니다. 필요한 작업 규칙도 입력에 포함해야 한다.

가상 예시로 재시도 WIKI를 검토한다면 다음과 같다. 정확한 명령, 필드, 모델, 연결 구현은 미정이다.

1. 메인 AI가 ‘이 WIKI의 재시도 설명이 구현과 맞는가’를 질문으로 정하고, 예를 들어 코드 `src/RetryPolicy.java`와 WIKI `policies/retry.md`의 경로, 필요한 테스트를 도구 요청에 넣는다. Codex CLI가 그 요청으로 로컬 연결 프로그램을 실행한다. 경로는 설명용이며 배포 기본값이 아니다.
2. 연결 코드는 받은 상대 경로를 등록한 코드/WIKI 루트에 대응시키고 허용 경로, 입력 크기를 확인한다. 일반 파일 읽기로 얻은 원문과 출처, 기준 버전을 Ollama 요청에 넣는다. 메인의 요약만 주지 않고 확인할 계약과 원문을 제공한다. 처리 범위를 넘는 자료는 잘랐다는 표시 없이 버리지 않는다.
3. 로컬 모델은 ‘WIKI에는 모든 오류를 재시도한다고 쓰였지만 코드에는 인증 오류 중단 조건이 있다’는 문제 후보와 근거를 반환한다. 호출부가 없어서 최종 동작을 모르면 필요한 자료를 요청하며 확인한 것으로 추정하지 않는다.
4. 추가 자료 요청은 메인에 전달한다. 메인은 의미상 필요, 대상을 판단하고 필요한 경우 검색하며, 코드는 경로, 허용 범위, 예산을 검사해 원문을 전달한다. 이미 허용된 범위의 읽기마다 사용자의 재승인을 요구하지 않으며, 새 권한, 비용 선택은 기존 협의 기준을 따른다.
5. 코드는 결과 형식, 출처/입력 변경을 대조하고 메인은 주장과 근거, 다른 계약의 연결을 확인한다. 로컬은 공식 WIKI를 직접 수정하지 않으며 기존 단일 반영 경로로 이어간다.

11/11 사용자 조건: 로컬을 도입한다면 **필요한 자료, 질문을 요청하고 답을 받아 이어갈 수 있어야 한다.** 정확한 파일명을 몰라도 필요한 함수, 호출부, 정책과 필요한 이유를 표현할 수 있어야 한다. 요청 자료가 없거나 거절/한도 도달로 제공되지 않으면 해당 판단을 미완료 또는 미확인으로 반환하고, 범위를 조정하거나 메인으로 넘긴다. 요청이 순환하거나 같은 자료로도 해결되지 않을 때 무한 재시도하지 않는다. ‘제공된 자료만 처리’는 파일 접근 경계이며 질문을 금지하거나 불충분한 입력에서 완료를 강제한다는 뜻이 아니다. 이 조건은 로컬 자체의 도입, 모델, 실험 승인이 아니다.

첫 연결 후보는 shell, repo 수정, 자유 파일 탐색 도구 없이 위 추가 요청을 메인에 반환하는 안이다. 입력이 빠지면 놓칠 수 있으므로 좁게 독립 처리할 수 없는 작업은 메인에 남긴다. 이후 제한된 검색/읽기 도구를 로컬에게 제공해 프로그램이 요청을 직접 처리하는 agent로 확장할 수 있지만, [Ollama 도구 호출 예제](https://docs.ollama.com/capabilities/tool-calling)처럼 실제 함수 실행과 결과 전달은 프로그램이 맡는다. 허용 경로, 읽기 범위, 호출량을 구현하고 검증해야 하며 자연어 금지만으로 충분하지 않다. 이 도구 확장이나 Codex native 보조의 로컬 전환을 채택한 것은 아니다.

위 첫 전달은 MCP 없이 일반 파일 읽기로 구현할 수 있다. 후속으로 같은 WIKI 읽기/검색 기능을 여러 AI 도구에 제공할 때는 MCP 연결을 재사용할 수 있다. 그때도 로컬 모델이 MCP에 저절로 연결되는 것은 아니다. 로컬 연결 프로그램에 MCP 클라이언트(도구 호출을 보내는 부분)를 연결해 실제 요청과 반환을 처리해야 한다. 파일 접근, 원문 버전, 결과 완전성을 다루는 코드의 재사용 경계는 [확장을 위한 경계](../architecture.md), 활용 가치와 비용 판단은 [후속 AI 연계 — 「후속 AI 연계에서의 활용」](../../discussions/integration/ai-tools.md)를 따른다. MCP의 존재를 로컬 도입이나 품질 동등성의 근거로 삼지 않는다.

### JSON과 문서 초안

추천은 **상세 Markdown 후보 + 단위별 JSON 결과 + 원문 근거 연결**이다. JSON은 작업 결과를 대조, 재개하는 공통 형식이며 WIKI 전체를 짧게 요약한 대체물이 아니다. 큰 본문을 JSON 문자열과 Markdown에 중복 보관하지 않는다. 작은 결과는 inline으로 둘 수 있고 큰 근거 목록은 참조로 분리하되, 한 작업 단위의 문서, 근거, 미처리를 함께 찾을 수 있어야 한다. 파일 수나 최종 필드 이름은 아직 확정하지 않는다.

- 코드가 붙이고 검증할 값: 작업/단위 식별자, 실제 기준 revision과 미커밋 입력, 실행 결과, 완료 여부, 저장 위치, 입력 해시. 모델이 임의로 쓴 값으로 대체하지 않는다.
- 보조가 반환할 내용: 문서 후보, 원문으로 뒷받침하는 주장, 추론, 미확인, 처리하지 못한 범위, 다른 단위와의 관계, 검토에서 찾은 문제. 읽은 파일 수를 의미 검토 완료로 간주하지 않는다.
- 메인/검토자가 볼 내용: 모든 단위의 완료 기준에 따른 문서와 근거. 모든 원문을 메인이 다시 전수 분석하는 것은 아니지만, JSON의 문법 통과나 요약만으로 내용 검토를 생략하지 않는다. 중요한 주장, 공통 계약, 충돌, 근거 부족은 직접 대조한다.

공통 식별/입력/범위/출처는 통일하되 복원 결과와 검토 결과의 본문까지 하나의 거대한 필드 목록으로 강제하지 않는다. 등록된 근거 ID의 존재, 파일 경로, 버전 일치는 코드 검사이고, 근거가 해당 주장을 지지하는지는 의미 검토다. 보조별 결과는 구분하고 전체 상태에는 결과 위치를 모은다. 이미 채택한 `map.json`/`maps`는 WIKI 역할별 위치표이며 이 일시적 실행 결과와 다른 책임이다. 공식 WIKI에 반영할 때도 필요한 근거가 보존돼야 하며 삭제될 작업 파일을 유일한 출처로 남기지 않는다.

[Codex 비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode#create-structured-outputs-with-a-schema)의 `--output-schema`는 최종 응답 형식을 지정하고 `--json`은 실행 이벤트를 JSONL로 출력한다. 설치된 CLI 도움말에서도 두 옵션을 확인했으나 결과 생성은 실행하지 않았다. 이 옵션이 native 하위 agent의 반환까지 자동으로 강제한다는 뜻은 아니다. [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs)도 schema 입력을 지원하지만 공통 형식의 실제 준수, 잘림, 거부, 재시도는 실행기별로 검증해야 한다. schema 적합성이 사실, 완전성, 실제 검증 수행을 증명하지 않는다.

### 전달할 문맥과 중복 읽기

서브가 메인의 읽기 이력, 판단을 자동으로 모두 안다고 가정하지 않는다. 부모 문맥을 복사하는 방식을 쓰더라도 전달 이후의 변경까지 항상 동기화되거나 비용 없이 공유되는 것은 아니다. 실제 전달 방식은 지원 실행기에서 확인한다. 기본 제안은 필요한 입력, 근거, 진척만 명시적으로 전달하는 것이다.

- 코드가 준비할 정보: 작업과 기준 버전, 허용 파일/구간, 입력 변경 여부, 결과 저장 위치. 파일 수집, 접근 기록은 의미상 검토 완료의 증거가 아니다.
- 메인이 전달할 정보: 보조가 풀 질문, 적용할 제약, 이미 확인한 관련 사실과 출처, 남은 확인 범위, 반환할 결과. 메인의 결론을 근거 없이 정답으로 전달하지 않는다.
- 보조가 반환할 정보: 처리한 범위와 근거, 미확인/누락, 필요한 추가 입력. 수행하지 않은 부분을 메인이 읽었을 것으로 추정해 완료 처리하지 않는다.
- 다시 읽을 자료: 공통 계약이나 독립 검토의 핵심 근거는 의도적으로 중복될 수 있다. ‘메인이 읽었음’을 읽기 금지 조건으로 사용하지 않는다. 메인이 이미 끝낸 분석을 단순 요약하려고 다시 위임하는 경우는 비용 이득을 먼저 확인한다.

실제 전달 순서는 [코드와 WIKI 접근](local-ai.md#%EC%BD%94%EB%93%9C%EC%99%80%20WIKI%20%EC%A0%91%EA%B7%BC)의 예시를 따른다. 메인이 해당 분석까지 이미 끝냈다면 직접 마무리하는 편이 보통 단순하며, 다시 맡길 때는 독립 검토 같은 별도 목적이 있어야 한다. 상세 근거를 짧은 요약으로 대체하거나 누락을 허용하는 안이 아니다.

공통 지침, 입력 전달, 보조 분석, 메인 검토/재조회, 실패 재처리를 합친 총비용으로 비교한다. 큰 본문을 메인에게 먼저 전부 읽힌 뒤 보조에게도 다시 보내는 구조를 토큰 절약으로 보고하지 않는다. 작은 입력이나 연결이 강한 작업은 메인 직접 처리로 남길 수 있다. 실제 절감, 품질은 미측정이며 구체 역할, 호출, 실험 범위는 계속 협의 중이다.

## 실패와 기본 경로 복귀

| 상황 | 제안 처리 | 금지할 결과 |
| --- | --- | --- |
| 짧은 Direct 요청, 이미 충분한 메인 문맥, 정형 처리로 충분 | 메인/코드가 직접 처리 | 협업 ON이라는 이유로 매 요청 위임 |
| 보조 OFF, 허용 상태 불명확 | 보조 진입점에서 거부, 기본 경로 유지 | prompt만 믿고 송신 |
| 형식 오류, 없는 근거, revision/입력 불일치 | 결과를 채택하지 않고 오류 기록, 제한된 재요청 또는 메인 처리 | 일부 내용이 그럴듯하다는 이유로 PASS |
| 잘림, 핵심 자료 누락, 원인 다수, 중요 계약/보안 판단 필요 | 범위 한정 추가 문맥 또는 메인으로 승격 | 보조가 합의 범위 밖 탐색, 권한 확장, 새 agent 호출 |
| timeout, 서버 미응답, 예산 초과 | 원시 근거와 미완료 상태 보존, 기본 경로 재개 여부 알림 | 무한 재시도, 무응답 은폐, 임의 외부 AI 전송 |
| 기존 검증 FAIL | R-05 결과와 무관하게 FAIL 유지, 원인 수정 뒤 같은 검증 재개 | 요약의 ‘문제 없음’으로 실패를 덮음 |
| compact/재개, 변경 후 오래된 보조 결과 | 작업, 입력, 미완료 상태 대조 후 재사용 여부 판단 | 오래된 결론을 새 revision의 증거로 사용 |

작업 결과를 기다리던 중 끊겼다면 현재 보조 작업의 실행/종료 여부부터 확인한다. 결과가 안 보인다는 이유로 같은 작업을 다시 발행하지 않는다. 확인할 수 없는 작업은 미확인으로 남기고 안전하게 재실행할 범위부터 정한다. 결과가 늦게 도착해도 현재 입력과 맞는지 대조하고, 이미 반영한 결과를 중복 적용하지 않는다. 정확한 상태 형식과 저장 시점은 공통 복구 계약에서 구체화한다.

예를 들어 상품 등록 WIKI를 복원할 때 메인은 공통 요구, API 계약과 단위 연결을 맡고, 보조는 지정된 변경 이력에서 확인 가능한 이유와 근거 위치만 반환할 수 있다. 이유 기록이 없으면 미확인으로 반환한다. 메인이 중간에 기준 코드를 바꾸면 이전 결과를 그대로 반영하지 않는다. 실패 로그 분석도 오류 후보를 얻는 일과 원래 실패한 검사를 다시 통과하는 일을 구별한다. 모두 설명 사례이며 실제 실험 결과가 아니다.

보조 job이 끝났다는 상태, gate 결과, 문서 영향 판단, 전체 작업 완료는 서로 다르다. 이 문서에서 새로운 전역 상태 enum을 정하지는 않는다.

로컬 모델은 추가 cloud quota를 쓰지 않아도 지연, 메모리, 전력, 재처리 비용이 있다. 또한 Codex 메인에 넘어간 근거는 클라우드 입력이 될 수 있으므로 협업 전체를 오프라인이라고 설명하지 않는다. 민감 자료 처리, 새 외부 송신은 별도 정책, 합의 대상이다.

## 효과를 확인할 조건

수용된 연결 방향의 실제 검증은 지원 대상 Windows 환경에서 메인의 호출 → 실제 파일 읽기 → 선택 로컬 모델의 응답 → 추가 자료 요청/제공 → 검토, 미완료 전달까지 확인한다. 먼저 할 수 있는 형식, 모의 검사를 실제 모델 연결 성공으로 계산하지 않는다. 정상 흐름과 [실패, 재개 조건 — 「실패와 기본 경로 복귀」](local-ai.md#%EC%8B%A4%ED%8C%A8%EC%99%80%20%EA%B8%B0%EB%B3%B8%20%EA%B2%BD%EB%A1%9C%20%EB%B3%B5%EA%B7%80)을 함께 다루고, 자료가 부족한데 완료하거나 허용 범위 밖을 읽거나 원문을 훼손하는지 대조한다. 정확한 모델, 사례, 예산과 실행 범위는 해당 검증 단위 전에 정하며 지금 설치/호출을 시작하지 않는다.

비교 구성과 공통 지표는 [수용 기준과 평가 기준 — 「비교 구성과 측정」](../../verification/acceptance.md)이 소유한다. 기존 로컬 보조의 첫 비교 후보는 R-05이며 R-09는 별도 사례로 검토한다. 위의 Codex 보조 후보와 같은 실험으로 합치거나 실행 순서를 확정하지 않는다. 기본 구성 대비 클라우드 순절감에는 위임 준비, 메인 처리, 결과 검토, 실패 복귀, 추가 subagent 호출을 모두 포함한다.

보조 특유의 지표는 필수 신호 누락, 근거 없는 주장, 잘못 연결된 인용, 추가 문맥 요청, 메인의 원문 재조회, 재처리다. 인용 위치 존재와 내용/완전성은 별도 검사이며 모델의 자신감은 근거가 아니다. 로컬의 초기 로드와 이미 실행 중인 조건도 구분하고, 측정하지 않은 전력, 비용을 0으로 쓰지 않는다.

한 턴에 역할이 섞이면 역할별 실제 토큰을 분리하지 못할 수 있다. 얻지 못한 값은 미측정으로 둔다. 알려진 쉬운 입력만 골라 평가하지 않으며 누락, 부정, 모순, 잘림, 오류와 별도 확인용 사례를 포함한다. 필수 기능이 나빠지면 절감이 있어도 채택하지 않는다.

## 이식 및 문서 복원과의 관계

이식의 구조/설정 수집은 R-02, 근거 후보 추출은 R-09, 정책, 공식 반영은 R-01, R-03, R-10, 검증, 재개는 R-04, R-11, R-12로 대응할 수 있다. **이식과 문서 복원은 로컬 AI에 의존하지 않는다.** 기본 구성에서는 코드와 메인이 수행하고, 선택 보조의 기여만 나중에 비교한다.

이후 질의, 수정은 관련 R-ID의 본문을 갱신한다. ID는 협의 대상을 식별하며 구현 단위를 고정하지 않는다. 역할을 합치거나 나누면 기존 대응을 기록하고 대화 전문을 새 문서로 누적하지 않는다.

## 기존 조사 근거

자료 확인은 2026-10-23, 27 작업에서 수행했으며 이번 통합은 새 모델 성능 평가가 아니다.

- [OpenAI 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization): 코드로 충분한 일을 AI로 옮기지 않는 근거.
- [Anthropic 컨텍스트 설계](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents), [도구 설계](https://www.anthropic.com/research/writing-tools-for-agents): 필요한 범위, 원문 재조회, 잘림 표시를 설계하는 근거.
- [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs), [context](https://docs.ollama.com/context-length): 형식과 사실 검증, context/메모리 제약의 구분.
- [평가 지침](https://www.anthropic.com/research/demystifying-evals-for-ai-agents), [Codex 비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode): 실제 outcome과 관측 가능한 usage를 대조할 참고. 이벤트 형식만으로 성공을 판정하지 않음.
- [AWS ADR](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/faq.html): 코드 관찰과 기록으로 확인한 과거 이유의 구분.

공식 근거가 로컬의 절감률이나 동등 품질을 보증하지 않는다. 클라우드 저장 여부도 모델 context, 능력의 근거가 아니며 현재 장비와 실제 결과로 확인한다.
