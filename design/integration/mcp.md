# MCP의 WIKI 읽기와 검색

11/22 현재는 [세 방식의 실제 비교 — 「세 방식 비교와 첫 제공 판단」](mcp.md#%EC%84%B8%20%EB%B0%A9%EC%8B%9D%20%EB%B9%84%EA%B5%90%EC%99%80%20%EC%B2%AB%20%EC%A0%9C%EA%B3%B5%20%ED%8C%90%EB%8B%A8)를 완료했다. 짧은 값 후보는 원문 반환과 값 전달이 보존됐지만 완료 보고/답변 품질이 미충족이며, 사용자가 직접 접근 우선/MCP 후속 제공을 채택했다. 아래 후보 계약/안전 조건은 후속 검토 자료로 유지하며 첫 배포의 선행 작업으로 두지 않는다.

다음은 11/18~19 당시 후보와 후속 관측의 설명이다. 11/18 실제 비교에서 드러난 범위 입력 오해, 중복 원문과 합산 출력 잘림을 보완하는 **배포 후보의 명세**다. 사용자 지정 11/19 후속 작업에서 [사본 분포와 설치본 설정 파싱](../../evidence/experiments/wiki-access/2026-11-20_00-33-30-mcp-read-contract.md)을 확인한 뒤 [후보 코드와 Windows 부분 검사](../../evidence/experiments/wiki-access/2026-11-20_03-42-30-wiki-reader.md)를 진행했다. 원문 처리와 SDK 전송은 확인한 사례에서 통과했고 실제 Codex의 부분 수신은 아래의 후속 관측에서 확인했다. 당시 모델 품질/비용과 제품 설치 검증은 남아 있었으며 이후 비교는 위의 현재 결정으로 연결한다. 과거 임의 제한 시험과 FAIL/PARTIAL을 새 결과로 덮지 않는다. 일반 연결 설명은 [진입 명세 — 「MCP 읽기의 남은 보완」](../runtime/entry.md), 입출력 계약은 이 문서, 수용 범위와 남은 사례는 [읽기 보완의 검증 입력 — 「MCP 읽기 보완의 검증 입력」](../../verification/acceptance.md)이 소유한다.

| 대안 | 판단 |
| --- | --- |
| 기존 limit에 설명만 보강 | 변경은 작지만 줄 수/끝 줄 오해와 합산 출력, 변경된 원문을 이어 읽는 문제를 함께 닫지 못함 |
| 두 도구의 입력/반환을 명확히 하고 호출 지침과 공통 의미 검토를 연결 | 우선 시험할 안. 기존 읽기/검색과 보호 책임을 재사용하며 아래 조건을 검증 |
| 묶음 검색/읽기, 검색용 AI나 영속 검색 상태 | 서로 다른 대안이다. 11/21 묶음 구현/코드 검사와 11/22 실제 두 요청 비교를 마쳤지만 값 전달 오류가 남음. 검색용 AI나 영속 색인은 채택하지 않음 |

## 동등성의 목표와 경계

기본 진입은 전용 시작 명령을 통한 직접 접근이며 MCP는 비교 중인 선택 연결이다. 이미 시작 명령이 경로 인자를 넣어 주므로, 긴 경로를 매번 입력하지 않는 편의만으로 MCP를 우선하지 않는다. 일반 Codex 진입에서 등록된 도구를 찾는 흐름과 후속 여러 AI 도구의 동일 계약 재사용이 비교할 이점이다. 로컬 보조의 첫 전달에는 MCP가 필수적이지 않다. [채택 근거 — 「직접 접근 대비 MCP의 채택 근거」](../../discussions/integration/ai-tools.md)와 [문서 처리 코드의 경계 — 「확장을 위한 경계」](../architecture.md)를 따르며, 미래 확장 가능성으로 현재 오류나 유의미한 비용 차이를 정당화하지 않는다.

11/19 후속 질문의 원문 누락, 입력 범위, MCP 추가 실패는 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 선택 연결 검증을 구체화하는 내용이다. 별도 우선 과제나 MCP 채택으로 바꾸지 않는다. 목표는 같은 허용 WIKI와 원문 버전에서 같은 문서 작업을 요청했을 때 필요한 정보와 결과를 정확히 제공하는 것이다. 호출 문법, 전송 JSON, 전체 모델 입력까지 같게 만드는 목표와 구별한다.

| 비교 대상 | 같아야 하는 것과 허용되는 차이 |
| --- | --- |
| 입력의 의미 | 같은 프로젝트, 원문 버전, 파일/구간 또는 검색 대상과 조건. 셸 명령 문자열과 도구 JSON 인자는 달라도 같은 작업을 표현해야 함 |
| 읽기와 검색 결과 | 요청한 본문의 문자, 줄 경계와 순서, 같은 검색 조건의 결과 집합과 위치. 요약이나 묵시적 제외로 대체하지 않음. 페이지 수, JSON 포장, 부가 진행 정보는 달라도 됨 |
| 완료와 실패 | 필요한 범위가 남거나 접근/통신에 실패하면 미완료로 표시. 원인이 다른 오류까지 같은 문구/코드로 만들 필요는 없지만 빈 성공이나 전체 부재로 바꾸지 않음 |
| 쓰기를 제공할 경우 | 같은 확정 변경에 대해 기대 파일 내용과 변경 대상 밖의 내용 보존을 검증. AI가 서로 다른 변경안을 생성하는 것과 도구의 적용 정확성을 구별. 현재 읽기 검증으로 쓰기 지원을 통과시키지 않음 |
| 비교 범위 | 하네스가 요구하는 WIKI 작업을 대상으로 함. 임의 셸 명령 전체를 MCP로 복제하지 않으며, 필요한 기능이 빠지면 제한/보완/채택 보류를 판단. 두 결과를 맞추려고 필수 범위를 줄이지 않음 |

직접 접근의 출력도 정답 원본으로 간주하지 않는다. 두 경로가 같은 부분을 빠뜨려도 서로의 비교만으로는 드러나지 않으므로 각각 독립 원문과 기대 결과에 대조한다. 전송 표현을 해제한 본문의 일치와 실제 호스트 수신을 나누고, 최종 모델 입력을 관측할 수 없으면 그 구간은 미확인으로 남긴다. 완전한 수신 이후에도 도구 설명과 탐색 경로의 차이가 모델 행동에 영향을 줄 수 있으므로 실제 답변 품질/비용 비교는 별도로 필요하다. 추가 실패 지점이 사라졌다거나 모든 미래 환경의 무결함을 보장하는 조건은 아니다.

## 요청한 범위를 보존하는 기준

11/18 사용자 확인의 핵심은 접근 방식과 관계없이 필요한 전체 문서 또는 지정 구간을 정확히 읽는 것이다. 현재 조건부 하네스 구조를 고정하거나 검증 흐름 전체를 새로 설계하라는 요청이 아니다. 전체 읽기를 검색 발췌, 앞부분이나 요약으로 축소하지 않으며 지정 구간을 임의로 바꾸지 않는다. 여러 번 나눠 받더라도 같은 원문의 요청 구간에 빠짐/겹침이 없는지 확인해야 한다. 필수 응답이 잘렸거나 이어 읽지 못했으면 해당 범위는 미수신이고 완료로 처리하지 않는다. 도구의 전송과 AI의 실제 수신/활용은 구별한다.

코드 실행을 거쳐 원문을 읽는 경우에도 반환 본문과 진행 정보가 모델이 읽는 도구 출력에 남아야 한다. 코드 안에서만 본문을 처리하고 길이, 해시나 완료 정보만 출력한 것은 원문 읽기 완료의 근거가 아니다. 현재 후보 지침은 응답 하나를 전달한 뒤 다음 응답을 요청하고, 같은 결과의 structuredContent 또는 content 중 하나만 전달하도록 한다. 본문을 최종 사용자 답변에 다시 붙이는 의무는 아니다. 지침 준수와 실제 출력은 따로 검증하며 이 지침만으로 모든 호스트의 잘림이나 모델의 누락을 막는다고 보장하지 않는다. 호출과 모델 판단이 늘어나는 비용도 전체 완료 기준으로 측정한다.

## 읽기 입력과 이어 받기

첫 요청은 path와 선택적인 start_line/end_line/revision을 받는다. path는 등록 WIKI 안의 상대 Markdown 경로이며 줄 번호는 1부터 시작하고 끝 줄도 포함한다. start_line 생략/null은 1, end_line 생략/null은 파일 끝까지의 요청이다. revision이 있으면 같은 원문인지 먼저 확인한다. `limit`을 끝 줄이나 줄 수로 겸용하지 않는다.

이어 읽기에는 도구가 반환한 next 객체를 같은 read_note의 인자로 그대로 사용한다. cursor는 원래 파일/범위/원문 식별과 다음 바이트 위치를 묶은 불투명한 값이다. 호출자가 해석하거나 줄 번호를 다시 계산하지 않는다. 초기 입력과 cursor는 함께 받지 않으며 null은 생략과 같은 의미다. 한 줄이 길어도 같은 줄 안에서 전진할 수 있어야 한다. JSON Schema와 실행 검사에서 첫 요청/이어 요청의 조건을 동일하게 적용한다.

```json
{"path":"규칙/반품.md","start_line":100,"end_line":180}
```

다음은 응답에서 얻은 next를 사용하는 호출 형태다. cursor 문자열은 설명용 표식이며 실제 값은 도구만 생성한다.

```json
{"cursor":"<직전 응답의 next.cursor>","page_bytes":16384}
```

| 반환 정보 | 의미와 후속 행동 |
| --- | --- |
| path, revision | 현재 연결/상대 경로/원문 해시에 대응하는 식별. 새 권한을 주는 토큰이 아니며 매 호출의 경로/접근 검사는 유지 |
| span, text | span은 반환 본문의 start_line/end_line과 start_byte/end_byte. 줄은 1부터, 바이트는 파일 처음을 0으로 한 시작 포함/끝 제외 구간. 부분 줄도 어느 원문 구간인지 확인할 수 있게 함. UTF-8, BOM, CRLF/LF와 마지막 개행 보존. 빈 파일은 span=null, text=""로 구별 |
| stop_reason | 요청 끝 도달 `range_end`, 파일 끝 `eof`, 반환 예산 도달 `output_limit`을 구별. 앞의 둘도 WIKI 전체 검토 완료라는 뜻은 아님 |
| next | 남은 구간이 있을 때 cursor와 현재 page_bytes를 담은 다음 요청 인자. 원래 범위와 revision은 cursor에 연결. 완료면 null. 출력 제한이 줄었다면 page_bytes만 낮춰 같은 구간을 다시 요청할 수 있음 |

가상 예로 1018~1035행을 요청해 1025행 중간까지 반환했다면 next는 그 줄의 다음 UTF-8 문자부터 원래 1035행 끝까지 이어 간다. UTF-8 문자 안이나 CRLF 사이에서 끊지 않는다. 여러 페이지의 span은 빠짐/겹침 없이 이어져야 하고, 이어 붙인 text는 독립 원문 구간과 같아야 한다. 요청 중이거나 다음 요청 전 원문/연결이 바뀌면 옛 위치와 새 본문을 섞지 않고 해당 근거를 다시 확인하도록 반환한다. 실제 파일 판별과 핸들 보호는 [파일 반영과 핸들 수명](../runtime/update.md)에 연결하며 해시만으로 완전한 동시 편집 격리를 보장하지 않는다.

0/음수/소수부가 있는 수/불리언 줄 번호, end_line < start_line은 입력 오류다. JSON Schema의 integer 의미에 맞춰 `1`과 `1.0`은 같은 정수로 처리하고 유한한 정숫값으로 정규화한다. 숫자 문자열과 NaN/Infinity는 받지 않는다. page_bytes에도 같은 숫자 규칙을 적용한다. [공식 숫자 규격](https://json-schema.org/understanding-json-schema/reference/numeric)에 따라 도구 schema가 허용한 값을 Python의 타입 차이만으로 거부하지 않도록 앞선 표현을 보정했다. 시작이 파일 밖이면 오류이며, 끝만 파일 밖이면 실제 끝과 eof를 반환한다. 빈 파일은 처음/전체 읽기에 한해 빈 본문과 eof로 구별하고 존재하지 않는 뒤쪽 줄을 정상으로 만들지 않는다. 바이트 위치는 UTF-8과 원문에서 구하며 호스트의 문자 수나 토큰 수로 대체하지 않는다. 메타데이터와 다음 한 문자조차 반환할 수 없으면 진행 불가 오류이며 같은 next를 무한 반환하지 않는다.

cursor는 해당 연결/원문/요청 종류에 묶고 읽기 권한을 새로 주지 않는다. 잘못된 값, 다른 도구에 사용한 값, 연결 변경이나 서버 재시작 뒤에는 재확인을 요구한다. 만료된 값을 오래된 원문으로 성공 처리하지 않는다. 재생성 가능한 조회용 값이며 SQLite나 active에 저장하지 않는다. 내부 후보와 비용은 아래 절에서 정한다. 응답 유실 시에는 그 응답에서 못 받은 next를 추측하지 않고 직전 요청을 재시도하되, 대상/원문이 같을 때만 결과를 재사용한다.

## 커서의 구성과 수명

[기존 소스 검토](../../evidence/experiments/wiki-access/2026-11-20_03-20-37-mcp-implementation-review.md)에서는 검색에 프로세스별 키와 HMAC을 이미 사용하고 있다. HMAC은 내용이 발행 뒤 바뀌었는지 확인하는 값이며 암호화나 파일 접근 권한이 아니다. 아래는 이전 방식과 새 후보의 경계다. 11/22 실제 입력 변형 이후의 선택 과정은 [이어 읽기 전달 방식의 선택](mcp.md#%EC%9D%B4%EC%96%B4%20%EC%9D%BD%EA%B8%B0%20%EC%A0%84%EB%8B%AC%20%EB%B0%A9%EC%8B%9D%EC%9D%98%20%EC%84%A0%ED%83%9D)에 있다.

| 방식 | 이점 | 비용과 판단 |
| --- | --- | --- |
| 원래 요청과 위치를 담고 HMAC으로 확인 | 요청별 저장소/정리 주기가 필요 없음. 같은 요청 재시도가 진행 상태를 소비하지 않음 | 이전 시험본. 실제 긴 값 변형을 관측했으므로 이 방식만을 최종 추천으로 유지하지 않음 |
| 짧은 ID로 프로세스 메모리의 요청 정보 참조 | 요청 경로/검색어를 매번 값 안에 반복하는 부담을 줄일 후보 | 동시 요청, 메모리 상한, 퇴출과 재시도 수명 관리가 추가됨. 원문 재검사 I/O까지 자동으로 줄지는 않음. 후속 후보 구현 범위로 수용. 실제 AI 효과와 첫 제공은 미확정 |
| 조회 상태나 사본을 영속 저장 | 서버 종료 뒤에도 같은 사본을 이어 볼 수 있음 | 새 보존/정리/권한/복구 책임이 생김. 이번 읽기 범위에는 추가하지 않음 |

이전 후보는 읽기/검색 종류, 현재 연결 식별, 원래 path/범위 또는 query/scope, 원문 기준과 다음 바이트 위치를 담아 서명했다. 새 후보는 위치와 임시 요청 식별자를 서명하고 나머지 요청 정보는 서버 프로세스에 보관한다. [요청 보관 후보의 동작](mcp.md#%EC%9A%94%EC%B2%AD%20%EB%B3%B4%EA%B4%80%20%ED%9B%84%EB%B3%B4%EC%9D%98%20%EB%8F%99%EC%9E%91)이 현재 구현 경계를 소유한다. 읽기는 파일 revision, 검색은 정렬한 대상 경로와 각 파일 revision의 집계값에 묶는다. 검색 위치는 다음 파일/줄의 바이트 위치로 표시하고 결과 개수만으로 원문 위치를 추측하지 않는다. 전체 본문이나 파일 목록을 cursor에 넣지 않는다.

키는 기존 secrets 기반 생성 책임을 유지하고 서버 프로세스 메모리에만 둔다. 로그, 문서, 설정이나 DB에 저장하지 않는다. 서명과 검증은 [Python HMAC](https://docs.python.org/3.13/library/hmac.html)의 표준 기능을 사용하고 자체 암호 알고리즘을 만들지 않는다. 전달 문자열에는 비밀값/호스트 절대경로를 넣지 않는다. 인코딩된 값도 비밀 보관 수단으로 취급하지 않는다.

매 호출에서 서명과 입력 종류, 현재 연결/허용 범위, 원문 기준과 위치를 다시 대조한다. 종료/재시작, 연결 변경 또는 확인한 원문 변경이면 기존 cursor로 합쳐 읽지 않는다. 임의 시간 만료나 별도 갱신 명령은 첫 후보에 추가하지 않는다. 이전의 긴 cursor는 발행 가능한 응답 크기를 기준으로 검사했다. 새 후보는 고정된 88자 형식과 서명, 보관 정보, 위치를 검사하며 잘못된 인코딩이나 값 변형을 명시적으로 거부한다. page_bytes는 서명 밖의 별도 요청 인자이므로 축소해도 원래 범위/위치가 바뀌지 않는다.

같은 cursor의 재시도는 같은 위치에서 다시 읽는 요청이다. 다음 호출을 먼저 했더라도 이전 cursor를 소비하거나 폐기하지 않는다. 원문이 같으면 응답 유실 후 재시도할 수 있고, 원문이 바뀌면 앞의 성공과 섞지 않는다. 첫 응답을 받기 전에 유실돼 revision을 확보하지 못했다면 같은 버전을 복원했다고 주장할 수 없다. 그 초기 요청을 다시 하고 새 기준으로 시작한다.

검색 집합의 변경 대조는 여러 파일을 동시에 잠근 원자적 스냅샷이 아니다. 파일별 실제 내용과 식별, 전후 목록/관측을 확인하고 감지한 변경은 미완료로 처리한다. 동일 시점의 전체 WIKI를 보장한다고 쓰지 않으며 Windows 경합 검증을 통과하기 전 파일 보호 완료로 표시하지 않는다. 지속적인 편집 때문에 기준을 유지할 수 없으면 재검색 필요를 알린다. 복구 DB나 팀 공유 잠금을 새로 만드는 방식으로 해결하지 않는다.

## 검색 범위와 계속 찾기

첫 요청은 비어 있지 않은 query와 선택적인 scope를 받는다. scope 생략/null은 `.`이며 등록 WIKI의 허용 Markdown 문서 집합을 뜻한다. 문자열, 대소문자 구분, 일치한 줄마다 한 결과를 기본으로 하며 정규식이나 의미 검색을 암묵적으로 추가하지 않는다. query의 앞뒤 공백도 검색 문자로 보존한다. 한 줄 검색이므로 CR/LF가 든 query는 입력 오류로 안내하며 임의로 여러 검색으로 나누지 않는다. 기존 시험의 100자 제한이나 casefold는 제품 계약으로 가져오지 않는다. 같은 줄에 여러 번 일치해도 줄 결과는 한 번이다. 숨김/ignore 기본값 때문에 허용 문서를 몰래 제외하지 않으며 경로 보호는 그대로 적용한다. 비교 시 직접 검색도 같은 대상/조건으로 맞춘다.

```json
{"query":"반품 가능 기간","scope":"규칙"}
```

이어 검색은 read_note와 같이 next의 cursor/page_bytes만 사용한다. query/scope와 cursor를 함께 받지 않는다. 파일 경로와 원문 바이트 위치 순으로 일관되게 정렬하며 임의 셸 출력 순서까지 복제하지 않는다.

반환에는 실제 scope, 경로/행/파일 revision과 원문 발췌를 가진 matches, next와 stop_reason을 둔다. 발췌에는 일치 위치와 excerpt_truncated를 표시하고 발췌가 전체 줄/문서를 읽었다는 뜻으로 쓰이지 않게 한다. 긴 일치 줄은 일치 위치를 포함한 발췌와 read_note에 전달할 파일/줄/revision을 제공한다. 일치 항목 자체를 페이지 경계 때문에 버리거나 다음 페이지에서 같은 줄을 중복하지 않는다. 최소 결과도 담을 수 없으면 진행 불가를 알린다.

cursor는 현재 연결, 검색어, scope와 탐색 기준에 묶는다. 원문/대상 목록 변경이나 서버 재시작으로 기준을 확인할 수 없으면 만료/재검색 필요를 알린다. 검색용 영속 DB/active 기록을 추가하지 않으며 [커서의 구성과 수명](mcp.md#%EC%BB%A4%EC%84%9C%EC%9D%98%20%EA%B5%AC%EC%84%B1%EA%B3%BC%20%EC%88%98%EB%AA%85)의 후보로 변경 감지 비용을 검증한다.

next=null만으로 완료를 추정하지 않는다. stop_reason이 complete이고 검사할 문서/구간이 남지 않았을 때만 해당 문자열/범위의 검색 완료다. output_limit은 결과 페이지가 찬 경우이며 next를 제공한다. 파일 부재, 접근 거부, 디코딩 실패나 탐색 중단은 오류와 미완료 범위를 알리고 결과 0개로 바꾸지 않는다. 작업을 내부적으로 나눠 빈 중간 페이지를 반환할 경우에는 scan_limit과 전진한 next로 표시해야 하며 마지막 complete 전까지 전체 부재의 근거로 쓰지 않는다. 문자열이 없다는 결과를 같은 의미의 요구사항도 없다는 판정으로 확대하지 않는다.

[MCP 페이지 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination)은 도구 목록 등의 list 연산을 다룬다. 위 검색의 cursor/next와 읽기 인자는 **우리 도구의 계약**으로 구현해야 하며 MCP가 자동 제공하는 검색 페이지가 아니다.

## 반환 정책과 크기의 기준

기본 page_bytes는 **16,384바이트(16KiB)**를 배포 후보로 사용한다. 원문과 위치/진행 정보를 담은 논리 결과의 UTF-8 JSON 크기이며 모델 토큰 수나 호스트의 출력 한도가 아니다. 새 후보와 Windows 코드/SDK 검사는 같은 값을 사용했다. 다음 실제 Codex 연결에도 같은 코드와 설정을 사용해 적합성을 판단한다. 기존 서버 등록과 사용자 Codex 설정은 변경하지 않았다.

[분포 근거](../../evidence/experiments/wiki-access/2026-11-20_00-33-30-mcp-read-contract.md)의 60개 사본은 본문 기준 55개가 16KiB 이하, 59개가 32KiB 이하다. 각각의 산술 페이지 하한은 68/62개다. 32KiB에서 하한은 6개 줄지만 실제 호출 감소량을 측정한 것은 아니다. 16KiB를 우선 후보로 두어 구조화/텍스트 중복과 포장 증가를 감안하되, 이 분포만으로 실제 수신 안전성이나 토큰 우위를 결론내리지 않는다. 최대 줄은 355바이트라 긴 한 줄의 경계 검증에는 별도 입력이 필요하다.

| 구분 | 설계 후보와 완료 조건 |
| --- | --- |
| 반환 단위 | 도구가 만든 결과 JSON 한 개의 UTF-8 바이트를 페이지 목표의 단위로 사용. 본문뿐 아니라 경로/구간/revision/next 등의 메타데이터도 포함. SDK나 호스트의 토큰 한도로 부르지 않음 |
| 요청 범위 | 페이지 목표는 한 번의 전달량이며 전체 문서/지정 구간을 줄이는 상한이 아님. 원래 범위를 끝까지 이어 받고 실제 본문을 대조해야 완료 |
| 기본값과 변경 | 후보의 contract.py가 16KiB 기본값을 소유. 기존 프로젝트 연결 `.harness/local.json`의 project_id/wiki와 선택 page_bytes를 읽으며 별도 설정 파일을 만들지 않음. 설정의 page_bytes는 양의 정수이고 생략하면 기본값 사용. 입력별 축소와 구별하며 사용자 Codex 버전별 숫자표나 전역 변경 없음 |
| 요청별 축소 | 두 도구의 page_bytes 생략/null은 설정값 사용. 양의 정수만 허용하고 설정값보다 큰 요청은 명시적으로 거부. 작은 값으로 원래 범위를 다시 요청할 수 있으며 next에도 그 값을 유지. 전체 검색/읽기 범위를 줄이는 옵션이 아님 |
| 긴 한 줄 | UTF-8 문자와 CRLF 경계를 지키며 부분 줄을 반환하고 byte span과 cursor로 이어 받음. 검색의 짧은 발췌와 read_note의 원문 부분 반환을 구별 |
| 큰 파일과 많은 문서 | 스트리밍으로 탐색하고 페이지가 차거나 범위가 끝날 때 반환하는 후보. 이번 작은 분포만으로 파일 크기/개수/전체 탐색 바이트 상한을 추가하지 않음. 실제 규모에서 시간/메모리 보호를 위해 작업을 나눠야 하면 남은 구간/진행을 보존하는 조건으로 검토. 호스트 timeout/취소를 완료로 처리하지 않음 |
| 진행 불가 | 필요한 메타데이터조차 담지 못하는 설정, 계속 전진하지 않는 cursor, 원문/연결 변경은 이유와 남은 범위를 반환. 같은 요청의 무한 재시도나 조용한 범위 축소 금지 |

이 후보의 페이지 목표는 **원문, 위치와 진행 정보를 담은 논리 결과**를 기준으로 한다. 같은 결과에서 MCP의 `structuredContent`와 호환용 텍스트를 생성해 서로 다른 원본을 만들지 않는다. 전체 응답의 전송 비용은 두 표현, JSON 이스케이프와 SDK 메타데이터까지 포함해 별도로 측정한다. 논리 결과가 페이지 목표 안에 든다는 사실만으로 전송/호스트 수신도 같은 크기라고 보장하지 않는다.

[공식 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#structured-content)은 구조화 결과의 호환용 텍스트 표현을 권고하고, outputSchema를 선언했다면 그에 맞는 구조화 결과를 요구한다. 우선 이 표준 표현을 유지하는 후보로 진행한다. 본문을 한 번만 넣는 반환이나 resource link로 바꾸는 최적화는 호스트가 필요한 원문과 진행 정보를 실제로 읽는지 확인한 뒤 비교한다. 크기를 줄이기 위해 한 표현만 임의로 지우지 않으며, 링크 반환만으로 문서 읽기를 완료하지 않는다.

## SDK 전송과 호스트 수신의 대조

| 단계 | 책임과 검사 대상 |
| --- | --- |
| 공통 읽기/검색 코드 | 요청 범위와 원문, 페이지 진행 정보 생성. 모델/SDK 버전과 독립된 의미 검증 |
| MCP 연결과 설치된 SDK | 같은 결과로 표준 표현 생성, 지원 규격에 맞는 변환. 소유가 다른 SDK 내부 코드를 복사하거나 공통 읽기에 버전별 필드 제거를 넣지 않음 |
| 실제 전송 | SDK가 덧붙이는 필드, JSON-RPC와 STDIO 형식까지 관측. 수기 JSON이나 클라이언트 정규화 객체를 전송 원문으로 대신하지 않음 |
| Codex와 모델 | 호출 묶음 뒤 실제 본문/필수 필드/미수신 구간 확인. 바이트를 토큰으로 등치하지 않고 의미 검토까지 분리 |

11/19 [Windows SDK 결과 변환 확인](../../evidence/experiments/wiki-access/2026-11-19_15-35-59-mcp-output.md)에서 보존된 실제 문서 사본 3개의 본문이 두 규격의 결과 변환 뒤 유지됐다. 2025-11-25 변환 결과에는 없던 `resultType`이 클라이언트 공통 객체에 생겨, 같은 진단용 JSON 인코딩의 크기가 24바이트 달랐다. 실제 서버는 규격에 따라 다른 메타데이터도 붙일 수 있다. 이는 앞선 검사에서 정규화 객체를 wire로 취급한 문제를 좁힌 근거이며, 고정 24바이트 보정이나 실제 Codex 수신 PASS의 근거가 아니다. 옛 내부 시험의 FAIL과 실제 답변 PARTIAL은 그대로 보존한다.

호스트의 유효 한도는 [확인 수단과 미확인 처리 — 「실행 조건의 확인과 미확인 처리」](../runtime/entry.md)를 따른다. 수신 잘림이 확인되면 같은 원문에서 남은 구간을 더 작은 전달 단위로 요청하는 후보를 사용하되, 자동 조정/종료 조건의 구현과 실제 행동 검증은 남는다. 표시 없는 잘림을 서버만으로 모두 감지한다고 보장하지 않는다. 호출을 하나씩 확인하는 지침도 실제 배포 경로에서 검증하며 시험 때만 묶음을 작게 바꾸지 않는다.

작은 페이지는 호출과 모델 판단을 늘릴 수 있다. 16KiB 후보를 실제로 검증할 때 전체 요청을 마칠 때의 호출, 재시도, 시간, 토큰을 함께 본다. 한 번에 끝낼 수 있는 요청을 불필요하게 나누는 비용도 포함한다. 현재 설치본에서 MCP 도구별 output_token_limit의 양수 파싱은 확인했으나 mcp get 응답에는 해당 값이 노출되지 않았다. 이를 실행 중 대화의 유효 한도 조회로 쓰지 않는다. 이 키는 자동 주입하지 않고 사용자 기본값을 유지한다. 공개 설정 설명의 토큰 수/직렬화 여유와 우리 page_bytes를 같은 단위로 환산하지 않는다.

호스트 잘림이 확인되면 **잘린 응답을 만들었던 요청**의 page_bytes를 낮춰 다시 요청한다. 다음 페이지부터 시작하면 빠진 원문이 남으므로 그 응답의 next로 건너뛰지 않는다. 같은 원문인지 확인한 뒤 이미 검증한 앞부분과 겹치는 구간을 대조한다. 잘림을 관측할 수 없거나 필요한 메타데이터가 유실돼 확인할 수 없으면 미확인이다. 축소 횟수/호스트의 탐지 수단과 후보의 실제 적합성은 검증 전이며 단순 재시도로 모든 환경의 완전성을 보장하지 않는다.

### 잘림을 구별하고 다시 읽는 순서

11/20 [기존 출력과 현재 소스 대조](../../evidence/experiments/wiki-access/2026-11-21_00-23-11-mcp-delivery-review.md)에서 정상 페이지 분할과 호스트 잘림을 구분했다. 앞선 실제 비교에는 직접 접근과 MCP 모두 잘림 경고가 남아 있다. 현재 후보의 한 응답씩 전달하는 지침은 합산 위험을 줄이기 위한 보완이며 모든 호스트에서 잘림이 없어졌다는 증거는 아니다.

| 관측한 상태 | 처리 |
| --- | --- |
| 본문과 진행 정보가 온전하고 `output_limit`/next가 있음 | 정상 페이지다. 해당 본문을 확인한 뒤 같은 범위의 다음 페이지를 요청 |
| Codex가 출력 일부를 잘랐다는 경고가 있음 | 경고가 걸린 반환 범위는 미완료. 다음 페이지로 건너뛰지 않고 아래 절차 적용 |
| 결과를 해석할 수 없거나 필수 본문/위치/완료 정보가 빠짐 | 잘림, 변환 오류 등 원인을 먼저 구분. 빈 성공이나 문서 부재로 바꾸지 않음 |
| 잘림 여부나 받은 범위를 확인할 근거가 없음 | 확인된 부분과 미확인 부분을 나눠 보고. 끝 표식이나 길이만 보고 전체 완료로 처리하지 않음 |

현재 일반 Codex 경로에서 재요청을 결정하는 주체는 도구 결과를 받은 메인 AI다. WIKI 서버는 원문과 진행 정보를 만들고 요청받은 page_bytes를 적용한다. 서버는 호스트가 그 결과를 모델에 얼마나 전달했는지 직접 알지 못하며, 별도 AI나 DB를 붙여 이 간극을 자동으로 해결한 것으로 설명하지 않는다. 코드 안에서 출력 전 길이/해시를 확인한 결과도 출력 후 수신의 증명이 아니다.

1. 각 반환을 사용하기 전에 경로, 원문 버전과 본문/구간, 완료 상태를 함께 확인한다. 같은 결과의 구조화 표현과 텍스트 표현 중 사용할 수 있는 한 표현을 해석한다. 문서 본문에 적힌 `truncated` 등의 문자열을 호스트 경고로 오인하지 않는다.
2. 잘림이 확인되면 마지막으로 검증한 지점과 **잘린 응답을 요청할 때 쓴 입력**을 유지한다. 예를 들어 두 번째 페이지가 잘렸으면 그 페이지를 요청한 cursor를 다시 쓰며, 잘린 반환 속의 다음 cursor로 세 번째 페이지에 넘어가지 않는다.
3. 같은 입력의 전달량을 줄여 다시 읽고 원문 버전과 겹치는 부분을 대조한다. 첫 응답에서 버전조차 확보하지 못했다면 재요청의 현재 원문을 새 기준으로 삼았음을 구분한다. 바뀐 원문과 옛 페이지를 합치지 않는다.
4. 원문을 식별할 수 없거나, 입력/오류가 진행을 막거나, 축소해도 완전한 반환을 확인하지 못하면 해당 읽기를 미완료로 남기고 이유와 다음 행동을 알린다. 동일한 실패 요청의 무한 반복이나 문서 전체 범위의 조용한 축소로 해결하지 않는다.

요청별 작은 페이지를 지원하는 코드와 위 절차를 실제 AI가 수행하는 것은 별개다. 현재 분리 후보에는 한 응답씩 본문을 전달하는 지침과 아래 B안의 재시도/중단 조건을 반영했다. **호스트 잘림 판별과 축소 재요청의 실제 실행은 미검증**이다. 지침만으로 표시 없는 모든 잘림을 검출한다고 보장하지 않는다.

### 축소 재시도의 범위와 종료 조건

11/20 [후보 코드 검토](../../evidence/experiments/wiki-access/2026-11-21_01-58-41-mcp-retry-policy.md)에서 같은 cursor에 더 작은 page_bytes를 지정하는 기능은 확인했다. 그러나 첫 요청에서 page_bytes를 생략하면 서버의 설정값을 쓰고, 최종 결과에는 적용한 크기를 따로 반환하지 않는다. 또한 너무 작을 때의 `page_too_small` 안내는 크기를 늘리라고 한다. 호스트 잘림 때문에 줄인 뒤 이 안내만 따라 다시 늘리면 실패를 반복할 위험이 있다. 이는 정적 관찰이며 실제 반복 장애를 재현한 결과는 아니다.

| 안 | 동작 | 이점과 비용 |
| --- | --- | --- |
| A. 잘림을 확인하면 즉시 중단 | 미완료 범위와 재요청에 필요한 정보를 안내 | 추가 재시도 비용이 없지만 자동으로 해결할 수 있는 경우에도 개입이 필요 |
| B. 제한된 자동 축소 | 크기를 확인할 수 있을 때 절반으로 줄여 같은 요청을 재시도. 한 논리 요청에서 최대 2회 | 간단한 불일치는 자동 해결할 여지가 있고 실패 반복 비용을 제한. 두 번으로 해결 못 하는 환경은 미완료로 남음 |
| C. 가능한 크기까지 계속 축소 | 같은 요청을 절반씩 줄여 성공하거나 더 줄일 수 없을 때까지 반복 | 더 작은 크기에서 성공할 가능성은 있지만 AI 판단/호출과 같은 원문 재탐색이 더 늘 수 있음 |

**11/20 사용자 채택: B로 진행한다.** 첫 크기 미확인과 AI의 횟수 준수 한계를 인지한 상태의 채택이며, 이 한계가 해결됐거나 실제 복구가 검증됐다는 뜻은 아니다. 2회와 절반은 모듈의 재시도 정책이지 Codex의 토큰 한도, 버전별 상수나 실측 최적값이 아니다. 시간 제한이나 전체 문서 읽기의 호출 제한도 아니다. 예를 들어 당시 입력에 16,384가 명시됐다면 8,192, 4,096 순으로 같은 시작 위치를 요청한다. 첫 축소가 성공하면 두 번째 축소는 하지 않는다. 정상 페이지를 이어 받는 횟수는 재시도에 포함하지 않으며 성공한 작은 크기로 원래 범위를 끝까지 읽는다. 작은 크기를 유지하면 정상 호출 수 자체도 늘 수 있으므로 총비용은 별도로 측정한다.

여기서 논리 요청은 한 문서의 전체/지정 구간 읽기, 하나의 requests 묶음 전체 또는 같은 query/queries와 scope의 검색이다. 페이지가 바뀔 때마다 두 번을 새로 부여하지 않는다. 같은 작업의 실패를 새 요청이라고 이름만 바꾸거나, 원문 변경/재연결을 이유로 자동 횟수를 초기화하며 반복하지 않는다. 서로 독립된 요청은 구분하되 여러 요청을 포함한 작업의 전체 비용도 확인한다.

채택한 실행 조건은 다음과 같다.

1. **정상 이어 받기:** 본문과 진행 정보가 온전한 `output_limit`은 실패가 아니다. 실제 본문을 확인한 뒤 반환된 next를 사용한다. 검색은 일치 결과의 이어 받기이며 발췌를 문서 전체로 해석하지 않는다.
2. **축소 시작:** 실제 호스트 잘림이 확인됐고, 잘린 응답을 만든 입력과 그때 명시적으로 전송한 양수 page_bytes를 보존했을 때만 자동 축소한다. 반환 속 다음 cursor로 넘어가지 않는다. 과거 기본값, 모델 이름, 잘린 JSON 조각에서 크기를 추정하지 않는다.
3. **같은 위치 확인:** 입력의 path/줄 범위 또는 cursor는 유지하고 page_bytes만 정수 나눗셈으로 절반으로 줄인다. 같은 원문 버전과 실제 구간/일치 위치를 확인한다. 이미 본 앞부분과 겹치면 대조하되 중복 누적하지 않는다. 첫 응답의 원문 버전이 없었다면 새 기준으로 읽은 사실을 구분한다.
4. **성공 후 계속:** 온전한 반환을 확인했을 때만 그 결과의 next로 진행한다. 요청 안에서는 확인한 작은 크기를 유지하고 더 큰 값으로 자동 복귀하지 않는다. 사용자 설정이나 전역 기본값에 저장하지 않는다.
5. **진행 불가:** 두 번을 소진했거나 더 작은 양수를 만들 수 없으면 미완료로 중단한다. 축소 중 `page_too_small`이 나와도 다시 키우며 왕복하지 않는다. 입력/원문 식별 유실, 새 반환의 위치 불일치나 전진 없음도 중단 사유다. 잘린 본문 뒤에 수신하지 못한 구간을 남긴 채 완료하지 않는다.
6. **다른 오류:** `changed_source`, `expired_cursor`, 권한/입력/연결 오류는 아래 오류 계약에 따른다. 이를 크기 문제로 바꿔 줄이거나 동일 요청을 계속 반복하지 않는다. 사용자 중단과 호스트 사용량 제한도 재시도 허가가 아니다.

첫 요청의 page_bytes가 생략됐고 호스트 잘림 때문에 적용값을 확인하지 못했다면, 현재 두 도구만으로 자동 축소를 완결할 수 있다고 보장하지 않는다. 이때는 마지막 확인 범위와 부족한 연결 정보를 알리고 멈춘다. 정상 기본 읽기는 계속 허용한다. 이 한계를 감추기 위해 설정 파일을 임의로 읽게 하거나 새 조회 도구/필드를 바로 추가하지 않으며, [진입 정보의 책임 — 「MCP 읽기의 남은 보완」](../runtime/entry.md)에서 보완 필요성을 추적한다.

위 조건은 [관측 기록 (분리 후보의 서버 지침)](../../evidence/experiments/wiki-access/2026-11-21_02-36-11-mcp-retry-instructions.md)에 반영했다. 두 도구 설명도 같은 지침을 참조하며, `page_too_small`의 세 안내는 무조건 크기를 키우라는 표현을 제거했다. 작은 크기로는 필요한 정보를 담을 수 없다는 오류와 미완료 상태는 유지한다. 새 skill, 조회 도구/필드, DB나 자동 호출 루프를 추가하지 않았다. 기존 Windows 시험 연결은 보존하고 승인받은 새 시험 위치에 배치했다. [실제 읽기와 검색](../../evidence/experiments/wiki-access/2026-11-21_04-19-04-mcp-retry-run.md)에서 새 지침의 노출, 정상 읽기 5페이지의 전체 원문과 검색 3페이지의 71개 일치 줄을 독립 원문에 대조했다. 두 요청 모두 잘림이 없어 자동 축소와 최대 두 번 준수는 미관측이다.

[Windows 코드/SDK 검사](../../evidence/experiments/wiki-access/2026-11-21_02-36-11-mcp-retry-instructions.md)는 같은 위치에서 축소한 뒤 전체 문서 72,422바이트와 검색 결과 71개를 누락/중복 없이 이어 받는 것을 확인했다. 두 통신 규격의 지침 전달과 오류 반환도 확인했다. 이는 검사 코드가 명시적으로 작은 크기를 요청한 결과이며, AI가 실제 잘림을 감지하고 재시도 횟수를 지킨 결과가 아니다. 초기 검사기의 revision/정렬 가정 오류와 보정 결과는 같은 근거에 보존했다.

WIKI 서버는 한 호출의 입력/원문/크기를 검사하고, 메인 AI는 호스트 결과와 재요청 횟수를 판단하는 현재 책임을 유지한다. 현재 입력에는 사용자 작업 전체의 확정된 식별자가 없고 서버는 호스트 잘림을 관측하지 못한다. 같은 문서/검색이라는 이유만으로 전역 횟수를 세면 독립 요청까지 제한할 수 있다. 이를 해결한 것처럼 임의의 서버 카운터를 추가하지 않으며 **최대 두 번은 현재 AI의 실행 규칙이고 코드가 강제한 총호출 상한은 아니다.** 실제 행동 검증과 첫 MCP 제공 판단의 미해결 항목으로 유지한다. [AWS의 재시도 안내](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)와 [Google Cloud의 재시도 주의사항](https://docs.cloud.google.com/storage/docs/retry-strategy#retry_anti-patterns)은 책임을 한곳에 두고 실패 종류와 반복 비용을 구분하는 근거다. 이 자료가 우리의 2회/절반 값을 검증한 것은 아니다.

실무 사례도 오류 원인과 API의 계약에 따라 처리한다. [Google의 페이지 설계 지침](https://google.aip.dev/158)은 기본 크기와 이어 받기 토큰을 처음부터 제공하도록 한다. 정상 페이지 분할은 장애 복구가 아니다. 아래는 공개된 실제 서비스의 대응이며 전체 업계의 사용 빈도를 측정한 자료가 아니다.

| 원인과 사례 | 공식 대응과 우리 설계에 참고할 점 |
| --- | --- |
| 일시적 통신 실패/과부하 | AWS와 Google Cloud는 재시도 가능한 오류를 구분하고 횟수/비용을 제한. 대기 간격을 늘리는 backoff와 동시 재요청을 분산하는 jitter를 사용. 명시된 재시도 시각이 있으면 존중하며, 출력 크기 문제를 기다림만으로 해결하지 않음 |
| 조회가 너무 무거움 | [GitHub GraphQL](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#query-optimization-strategies)은 작은 페이지와 쿼리 분할 등을 권고. 필수 원문을 빼는 것이 아니라 요청 단위를 나눠 원래 필요한 결과를 확보 |
| 일부 항목만 처리됨 | [DynamoDB BatchGetItem](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_BatchGetItem.html)은 처리하지 못한 키를 반환하고 그 항목만 재요청. 정상 수신한 결과를 전부 반복하는 방식과 구별. 호스트가 본문을 잘랐는데 서버의 다음 위치만 믿는 것은 이 사례와 다름 |
| 이어 받기의 원문 기준이 사라짐 | [Kubernetes 목록 조회](https://kubernetes.io/docs/reference/using-api/api-concepts/#retrieving-large-results-sets-in-chunks)는 버전이 일정한 결과와 이어 토큰을 사용하고, 만료되면 다시 조회하도록 안내. 일관된 결과가 필요할 때 서로 다른 버전을 혼합하지 않음 |
| 권한/입력 오류 또는 복구 조건 부재 | 원인을 고치기 전 같은 요청을 반복하지 않음. [MCP 오류 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling)처럼 조치 가능한 오류 정보를 전달하고 미완료 유지 |

크기를 얼마나 줄이고 성공 후 언제 늘리는지에 관한 공통 표준값은 위 자료에서 확인되지 않았다. 성공한 작은 크기를 같은 요청에서 유지하는 B안은 실패 왕복과 구현 복잡성을 줄이려는 선택이며, 비용 우위는 실제 측정 전이다. SDK의 adaptive 재시도처럼 **호출 빈도**를 조절하는 기능을 **반환 크기** 자동 조절과 동일시하지 않는다.

일반 통신 클라이언트는 오류 코드와 완료 정보를 받아 코드로 재시도를 제어할 수 있다. 예를 들어 [HTTP/1.1의 불완전 응답 규칙](https://www.rfc-editor.org/rfc/rfc9112.html#section-8)은 불완전 수신을 완료로 기록하지 않도록 한다. 현재 로컬 STDIO MCP에서는 서버 응답을 받은 뒤 호스트가 모델에 보여줄 내용을 자르는 단계가 추가로 있다. 이 잘림은 서버가 받은 네트워크 오류가 아니므로 기존 SDK의 통신 재시도만으로 해결되지 않는다. 현재 AI 지침을 기계적으로 강제되는 SDK 재시도와 같은 보장이라고 설명하지 않으며, 서버가 모르는 최종 수신 범위는 기존 호스트 검증/미확인 처리로 남긴다.

### 남은 검증과 비교 조건

정상 읽기/검색의 수신을 확인한 것과 오류 복구, 답변의 의미를 확인한 것은 구분한다. [후속 비교 입력](../../evidence/experiments/wiki-access/2026-11-21_04-39-32-mcp-comparison-plan.md)으로 승인한 두 요청을 [실행하고 대조](../../evidence/experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md)했다. 한 쌍의 결과로 아래 미검증 항목을 통과시키지 않는다.

| 남은 조건 | 현재 동작과 확인 범위 | 다음 판단 |
| --- | --- | --- |
| 첫 기본값 요청이 잘려 적용 크기를 모름 | 현 지침은 추정하지 않고 미완료로 중단. 정상 첫 요청 성공은 이 오류 행동을 입증하지 않음 | 현재 B안의 한계로 유지. 자동 복구 확대가 필요하면 현재 크기의 전달 책임부터 설계하며 임시 숫자/조회 도구를 덧붙이지 않음 |
| AI의 축소 최대 두 번 준수 | 코드/SDK는 같은 위치의 작은 요청을 처리. 실제 AI의 축소/종료는 미관측이고 횟수는 지침 | 총호출/비용의 기계적 상한으로 설명하지 않음. 하드 제한이 필요하면 호스트의 작업 식별/제어까지 별도 검토. 현재 문서/경로별 전역 카운터를 추가하지 않음 |
| 처리 중 취소, 늦은 결과와 표시 없는 누락 | 호출 사이 중단 후 독립 읽기는 확인. 내부 처리 중 취소와 최종 모델 입력 전체는 미관측 | 관측 가능한 위치와 실제 수신만 판정. 정상 표본 반복, 임의 지연/작은 한도로 검증했다고 대체하지 않음 |
| 원문을 읽었지만 답에서 필수 조건을 빠뜨림 | 11/20 후속 비교에서도 MCP가 영구 삭제 뒤 복구 제외 조건을 누락. 해당 내용을 설명한 본문은 수신했고 직접 답변은 반영 | 원문 전달과 탐색/답변 검토를 분리해 보완. 한 표본의 직접 접근 성공을 공통 누락 위험의 해소로 보지 않음 |
| 이어 검색 값의 정확한 전달 | 도구가 반환한 cursor 472자와 다음 호출의 476자가 달라 expired_cursor로 거부됨. 같은 서명에 다른 본문이 붙은 호출이며 실제 만료로 단정하지 않음 | AI의 값 전달, 도구의 오류 분류와 재개 안내를 함께 검토. 이번 비교 중 후보를 바꾸거나 실패를 없앤 재실행은 하지 않음 |

**현재 추천은 기본 전용 시작 명령/직접 접근과 채택한 B안의 안전한 미완료 처리를 유지하고, 확인한 입력 전달/답변 누락과 호출 비용을 함께 보완하는 것**이다. [기록 분석](../../evidence/experiments/wiki-access/2026-11-21_05-58-03-mcp-cost-review.md)에서 비슷한 입력 크기에 더 많은 내부 모델 응답이 쌓였음을 확인했다. 한 쌍으로 일반 우위를 확정하지 않되 현재 후보를 그대로 확대하지 않는다. 아래 개선안의 통합 범위는 11/21 선택됐고 별도 코드/SDK 검사를 진행했다. 서버/호스트 책임과 첫 배포 선택을 모두 확정한 결과는 아니다. 자동 복구를 검증했다고 홍보하거나 MCP 첫 제공을 확정하는 판단은 남은 조건을 검토한 뒤 별도로 한다. 실제 잘림이 발생하면 그 실패와 비용을 그대로 보존하고 같은 논리 요청의 처리만 평가한다. 실패를 없던 것으로 만든 새 실행은 하지 않는다.

[MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)은 도구의 설명/입력과 모델의 호출을 정의하며, [초기화 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)은 서버 지침을 전달한다. 이 규격에 지침을 실었다는 사실을 우리 요청의 최대 횟수나 모델 수신 보장으로 해석하지 않는다. 위 책임 판단은 현재 후보 코드와 실제 로그를 함께 대조한 결과다.

## 호출 비용과 개선 순서

11/20 질문은 큰 WIKI에서도 필요한 정보를 정확히 읽으면서 현재의 반복 호출 비용을 감당할 수 있는지에 대한 보완이다. [실제 토큰 해석과 공개 사례 — 「실제 비교의 토큰 해석」](../../discussions/integration/ai-tools.md)를 판단 근거로 삼는다. MCP의 존재 자체를 목표로 하지 않으며 직접 접근 기본안과 프로젝트별 연결, 원문 보존, 조건부 라우팅을 유지한다.

현재 후보는 한 문자열씩 검색하고 합산 잘림을 피하려 한 응답을 출력한 뒤 코드 실행을 마치게 안내한다. 실제 MCP 표본에는 순차 검색/읽기가 많았고 네 검색을 묶은 코드도 두 번 있었다. 직접 방식은 OR 검색과 여러 파일/구간을 묶었다. 따라서 `functions.exec` 같은 코드 실행 도입 자체가 해결책은 아니며, 검색 입력의 표현력과 반환 묶음, 필수 원문 확인을 같이 검토해야 한다. 현재의 한 응답 지침은 보호 이유 없이 제거하지 않는다.

| 대안 | 기대 효과 | 비용/위험과 현재 추천 |
| --- | --- | --- |
| 현 후보와 지침 유지, 페이지 크기만 확대 | 일부 이어 받기 감소 가능 | 많은 별도 검색과 값 복사 오류, 필수 예외 누락은 남는다. 호스트 잘림도 커질 수 있어 핵심 개선안으로 추천하지 않음 |
| 기존 라우팅 + 복수 질의/구간의 묶음 처리 | 같은 목적의 검색과 독립 읽기 사이 모델 판단을 줄이고 반환 중복을 줄일 가능성 | 합산 출력, 일부 실패, 구간별 완료와 원문 변경 처리가 필요. 먼저 계약을 구체화할 추천 후보이며 절감량은 미측정 |
| 검색용 색인과 의미 검색/재정렬 | 큰 자료에서 후보 문서 찾기와 반복 스캔을 개선할 가능성 | 갱신 지연, 재구축, 누락 판정과 추가 설치/로컬 자원 부담. 문서 증가만으로 도입하지 않고 위 후보 뒤 필요성 판단 |
| MCP 제공을 미루고 직접 접근만 제공 | 현재 검증/유지보수 범위를 줄이고 기본 경로에 집중 | MCP 표준 도구의 선택 연결은 미제공. 개선 효과가 작거나 필수 품질/기한을 맞추지 못하면 합리적인 대안이며 첫 제공 선택은 미확정 |

예를 들어 문서 복구 정책을 묻는 요청은 기존 역할/경로 매핑으로 관련 요구와 ADR의 위치를 찾고, 필요한 검색어를 묶어 탐색한 다음, 본문과 예외가 있는 구간을 확인하는 흐름이다. 검색할 문자열마다 AI가 새로 판단하거나 이미 확보한 같은 본문을 반복 출력할 필요를 줄이는 목적이다. 읽기 전에 관련 없다고 확정할 수 없는 영역, 공통 규칙과 연결된 결정은 검색 편의를 위해 제외하지 않는다.

아래 책임을 함께 확인하며 11/21 통합 후보는 기존 두 도구의 선택 입력을 확장한다. 정확한 필드와 검사 결과는 아래 「통합 후보 구현과 검사」에 연결한다. 제품의 최종 배포 계약과 실제 호스트 검증은 별도다.

1. **탐색과 원문 읽기의 구별:** 발견용 검색은 경로/제목/출처가 있는 발췌로 읽을 위치를 안내한다. 전체 문서나 전체 일치 줄을 요청한 경우에는 현재의 완전성 계약을 그대로 지킨다. 상위 몇 결과, 요약, 해시나 개수만으로 완료를 대신하지 않는다. 상세 WIKI 복원은 합의한 전체 파일/이력 범위의 처리 여부를 확인해야 하므로 일반 질문의 좁은 탐색과 구별한다.
2. **묶음 처리와 수신:** 독립 질의/구간을 같은 코드 단계에서 처리하되, 단순히 모든 페이지를 모아 한 번에 출력하지 않는다. 원문은 실제 모델이 받는 출력에 포함하고 결과별 범위/오류/이어 받기를 보존한다. 겹친 같은 원문은 한 번 전달하면서 각 요청의 대응을 남길 수 있어야 한다. 묶음의 합산 출력과 현재 호스트 수신 가능 범위를 확인할 수 없으면 안전한 개별 전달을 유지한다. 서버가 호스트 한도를 아는 것처럼 가정하지 않는다.
3. **이어 받기 정보의 전달:** 반환된 next 객체를 호출 코드가 그대로 전달해 모델의 긴 문자열 재작성을 줄이는 방식을 우선 검토한다. 실행 호출 사이에 객체를 보존하는 호스트 기능과 수명은 실제 지원 여부를 확인한다. 짧은 조회 ID는 서버 상태/재시작/메모리 수명 설계가 필요한 별도 대안이다. 서명 검사를 풀거나 잘못된 문자열을 추정해서 고치지 않으며, 입력 손상과 실제 만료의 안내도 구별한다.
4. **검색 상태의 책임:** 반복 스캔이 병목이면 재구축 가능한 로컬 색인을 비교한다. 색인은 원문을 대체하지 않으며 변경/삭제/연결 변경 때 갱신 여부를 확인해야 한다. 오래된 색인의 무결과를 전체 부재로 판정하지 않는다. 설치/복구 이력의 state.db에 검색 상태를 임의로 섞지 않고, 영속 색인이나 로컬 모델을 이번 개선의 필수 전제로 넣지 않는다.
5. **품질과 비용의 공동 판정:** 받은 원문의 예외와 조건을 답에 반영했는지 공통 의미 검토를 유지한다. 더 적게 읽은 실패를 절약으로 계산하지 않는다. 도구 호출, 내부 모델 응답, 입력/캐시/출력, 시간과 실패 후 복귀 비용을 같은 사용자 작업의 완료 기준으로 비교한다. 명령으로 서버가 반환한 사실만으로 실제 AI 사용성을 통과시키지 않는다.

서버 안의 일반 코드로 검색/병합/진행 검사를 처리하는 것과 검색용 로컬 AI를 추가하는 것은 별개다. 우선 일반 코드와 기존 라우팅으로 줄일 수 있는 반복을 다루며, 클라우드 비용을 숨은 추가 모델 호출이나 필수 로컬 모델 설치로 옮기지 않는다. CLI와 MCP가 같은 원문 처리 책임을 공유하는 구조도 검토할 수 있지만 임의의 외부 셸 실행 기능을 MCP에 열거나 허용 WIKI 밖으로 범위를 넓히지는 않는다.

아래 11/21 구체안은 이 후보를 읽기/검색 계약, 호출 지침, 오류/완료 표현과 [비교 수용 조건 — 「후속 비교의 질문과 판정」](../../verification/acceptance.md)에 대응한다. 개선 범위의 선택과 후보 구현/새 AI 시험, 의미 검색 채택이나 첫 MCP 제공은 구분한다.

### 첫 개선 후보와 선택 범위

**11/21 사용자 범위 선택: 시간 제약을 고려해 여러 파일 읽기까지 포함하고, 확인된 문제를 가능한 한 함께 보완한다.** 복수 검색, 묶음 읽기, 정확한 next 전달, 합산 출력과 일부 실패/원문 변경을 통합 개선 범위로 잡는다. 처음 제안한 검색/값 전달만 우선하는 작은 범위 대신 아래 통합안을 진행한다. 이는 개선 범위의 채택이며 정확한 코드/반환 형식의 검증, 새 AI 시험 횟수/비용이나 MCP 첫 제공 확정은 아니다.

| 대상 | 현재 | 첫 개선 후보 | 그대로 유지할 책임 |
| --- | --- | --- | --- |
| 검색 입력 | `query` 문자열 하나 | 같은 `scope`에서 `queries` 문자열 배열을 선택 입력으로 제공. 어느 문자열이든 일치하면 찾는 OR 검색 | 리터럴 검색, 대소문자 구분과 현재 허용 경로. 의미 검색이나 자동 검색어 확장 아님 |
| 검색 반환 | 일치 줄과 경로/위치, 다음 요청 | 같은 파일/버전/줄은 한 번 반환하고 어떤 입력 문자열이 일치했는지 연결 | 발췌와 전체 줄의 구별, 원문 위치, 실제 검색 범위와 완료/오류 |
| 원문 읽기 | `read_note`의 전체/구간 읽기 | 기존 단일 입력을 보존하고 `requests` 배열로 여러 파일/구간을 함께 요청 | 각 요청의 원문/범위/오류와 전체 완료를 구별. 검색 결과만으로 전체 문서를 읽었다고 판단하지 않음 |
| 이어 받기 | 반환 next를 다음 호출의 인자로 사용 | 지원 호스트에서는 코드가 next 객체를 보관하고 그대로 다시 전달 | 서명, 연결과 원문 변경 검사. AI가 긴 cursor를 다시 작성하거나 고치지 않음 |
| 출력과 판단 | 한 반환을 전달한 뒤 다음 판단 | 서버가 한 논리 페이지 안에서 여러 결과를 묶고 합산 크기를 관리. 그 반환을 확인한 뒤 계속 읽음 | 여러 MCP 응답을 호스트 출력에 무제한 합치지 않음. 실제 본문 전달과 필수 예외 반영 |

예를 들어 같은 정책 범위에서 `복구`, `영구 삭제`, `브라우저 세션`을 각각 검색하던 세 호출을 다음 한 검색으로 표현할 수 있다. 이 단어들은 동작 설명용이며 제품 기본 검색어가 아니다.

```json
{"queries":["복구","영구 삭제","브라우저 세션"],"scope":"docs"}
```

결과가 한 페이지에 다 들어가지 않으면 나머지는 기존 next로 받는다. **검색 요청 세 개를 합쳐도 모델 응답이 반드시 세 번에서 한 번으로 줄지는 않는다.** 넓어진 일치 집합 때문에 페이지와 읽을 근거가 늘 수도 있다. 줄어드는 것은 중복된 입력/탐색 기회이고 실제 비용은 품질을 충족한 결과로 측정한다.

입력은 기존 단일 `query`, 새 `queries`, 이어 받기 `cursor` 중 하나만 허용한다. 빈 배열이나 빈 문자열, 잘못된 타입과 서로 겹친 입력은 오류로 알린다. 정확히 같은 검색어의 중복 입력도 조용히 버리지 않고 수정하도록 안내한다. 공백/정규화/동의어를 임의로 바꾸지 않으며 배열은 하나의 OR 질의라는 의미를 도구 설명과 입력 선언에 함께 노출한다. 기존 단일 입력의 정상/거부 결과는 바꾸지 않는다.

복수 검색의 cursor는 원래 문자열 집합, scope, 연결/원문 기준과 다음 위치에 묶는다. 같은 줄에 여러 문자열이 있으면 원문 줄은 한 번만 보내되 각 일치 문자열과 위치를 잃지 않아야 한다. 긴 줄의 일부 발췌에 모든 일치 위치가 들어가지 않으면 기존의 불완전 발췌 표시와 원문 읽기 연결을 유지한다. 전체 일치 줄을 요청받았는데 발췌/개수만 반환해 완료 처리하지 않는다. 허용 가능한 입력/메타데이터 크기를 넘으면 이유를 알리고 나눠 요청하도록 하며 검색어 목록을 몰래 잘라 처리하지 않는다. 별도 입력 개수 상수를 추가하지 않았다. 현재 설정의 논리 페이지에 요청/반환 메타데이터가 들어가지 않는 경우를 오류로 처리하는 후보 검사는 수행했으며, 모든 큰 입력의 자원 비용을 검증한 것은 아니다.

### 묶음 읽기의 입력과 부분 실패

기존 두 도구를 확장하며, 일반 도구 이름/실행 코드를 받아 호출하는 새 범용 실행기를 만들지 않는다. `read_note`는 기존 path/줄 범위 방식 또는 다음 `requests` 배열을 받는 후보로 구체화한다. 예시는 동작 설명용 경로이며 현재 사용자 WIKI를 읽는 실제 호출이 아니다.

```json
{"requests":[{"path":"requirements.md","start_line":20,"end_line":45},{"path":"decisions/recovery.md","start_line":1,"end_line":70}]}
```

배열 항목은 기존 단일 읽기의 path/줄 범위/revision만 사용한다. 항목별 page_bytes나 cursor를 섞지 않고, 첫 묶음의 page_bytes와 이어 요청의 cursor/page_bytes를 바깥에 둔다. 기존 단일 입력, requests, cursor의 non-null 입력은 함께 쓰지 않는다. 구조/타입/경로 경계를 먼저 검사하고 잘못된 입력을 조용히 일부만 처리하지 않는다. 파일 부재나 접근 실패처럼 실제 읽기에서 발견되는 문제는 아래처럼 요청별로 구분한다.

| 책임 | 통합 후보의 처리 |
| --- | --- |
| 요청과 결과 대응 | 배열 순서의 인덱스로 원래 요청을 식별. 결과에는 그 요청과 실제 파일/버전/범위, 본문, 완료 또는 오류를 연결. 결과 순서만 보고 대응을 추측하지 않음 |
| 중복과 겹침 | 같은 파일/버전의 겹친 원문은 한 번 반환하되 어떤 요청의 어느 구간을 충족했는지 연결. 서로 다른 버전의 본문을 합치거나 같은 문장이라는 이유로 다른 출처를 제거하지 않음 |
| 합산 크기 | 기존 페이지 크기의 단위인 논리 JSON 전체에 모든 본문과 메타데이터를 포함. 파일마다 한도 전체를 사용한 뒤 합산하는 방식 금지. 서버가 이 크기를 관리하더라도 호스트 수신 보장은 별도 |
| 정상 분할 | 한 페이지에 못 담은 본문/요청은 이어 받기로 남김. 아직 시작하지 않은 요청과 일부만 읽은 요청을 구분하며, 순서를 정하고 매 호출의 전진을 확인. 원래 전체 범위는 줄이지 않음 |
| 일부 파일 실패 | 성공한 원문과 실패한 요청, 아직 처리하지 않은 요청을 구별해 전달. 도구 오류 표시는 유지하고 성공 부분을 빈 배열로 버리거나 전체 성공으로 바꾸지 않음. 호스트가 오류와 부분 본문을 함께 전달하는지는 실제 검사 |
| 후속 처리 | 독립적으로 유효한 수신 결과는 재사용. 없는 파일/권한 오류를 자동 반복하지 않으며 원인을 해결한 요청만 다시 확인. 처리하지 않은 독립 요청은 계속할 수 있어도 원래 묶음의 실패는 해소 전까지 남김 |
| 원문 변경 | 각 파일의 revision과 실제 반환 위치를 대조. 바뀐 파일의 옛/새 페이지 혼합 금지. 이미 반환한 파일도 묶음 완료 판단 때 확인할 대상에 포함. 여러 파일의 단일 시점 스냅샷을 보장하는 계약은 아님 |
| 전체 완료 | 모든 원래 요청에 필요한 구간과 유효한 근거가 있고 미해결 오류가 없을 때만 완료. next가 없다는 이유만으로 완료하지 않으며 일부 실패로 종료된 상태를 구별 |
| 입력/자원 한계 | 요청 목록과 이어 받기 메타데이터조차 담을 수 없으면 항목을 생략하지 말고 분할 필요를 알림. 실제 상한과 큰 요청의 자원 비용은 지원 환경에서 정하고 검사. 임의의 시험 제한으로 통과시키지 않음 |

예를 들어 두 문서 중 첫 문서는 읽었지만 둘째 문서가 없으면 첫 본문과 둘째의 not_found를 함께 알린다. 첫 문서를 매번 처음부터 읽을 이유는 없지만, 둘째 근거가 필요했던 답을 완료로 보고해서는 안 된다. 파일이 나중에 생기거나 경로가 정정됐다면 그 부분을 다시 읽고 사용한 첫 문서의 버전도 확인한다.

묶음의 이어 정보에는 원래 요청 집합, 진행 위치와 해소하지 못한 실패의 대응이 유지돼야 한다. 일반적인 정상 분할을 오류로 바꾸지 않되, 실제 실패가 있으면 MCP의 오류 계약을 지킨다. 정확한 반환 필드와 스키마는 이 조건에 맞춰 코드와 함께 검사한다. 특히 구조화 반환/오류를 호스트가 일부만 보여 주는 경우에는 성공으로 판단하지 않고 표현을 보완해야 한다.

검사는 복수 검색, 겹친 구간, 일부 파일 오류, 원문 변경, 다음 값 보존, 합산 잘림과 취소를 독립적으로 구성한다. 배포 후보와 실제 비교는 통합된 개선안 하나로 진행할 수 있지만, 별도의 분리 실험이 없으면 수치 향상을 개별 변경 하나의 효과로 주장하지 않는다. 페이지 축소 B안의 한 논리 요청은 새 묶음 전체이며 파일/페이지마다 횟수를 다시 부여하지 않는다. 서로 다른 사용자 작업을 한 전역 카운터로 묶지도 않는다.

### 이어 받기 값의 보관과 실제 수신

Code Mode는 Codex 안에서 일반 코드로 여러 도구를 호출하는 기능이다. 11/21 확인한 [공식 store/load 구현](https://github.com/openai/codex/blob/main/codex-rs/code-mode-runtime/src/runtime/callbacks.rs)은 직렬화 가능한 값의 저장과 조회를 제공하고, [세션 실행 코드](https://github.com/openai/codex/blob/main/codex-rs/code-mode-runtime/src/session_runtime/mod.rs)는 메모리 보관과 실행 완료 시 반영을 구분한다. 현재 설계 대화의 도구 설명에도 이 기능이 있지만 **Windows 시험 설치본의 사용 가능 여부와 취소/재개 수명을 확인한 결과는 아니다.** 공개 main의 구현을 모든 사용자 설치본의 지원 보장으로 쓰지 않는다.

추천하는 호출 흐름은 다음과 같다. 별도 서버 상태 저장이나 파일/DB 생성 없이 해당 호스트에서 가능한 값 재사용만 먼저 확인한다.

1. 최초 호출의 실제 입력과 도구가 반환한 원문 식별, next를 코드가 연결한다. 반환 전체를 검토 없이 다음 위치로 바꿔 저장하지 않는다.
2. 본문과 범위/완료 정보를 모델이 확인할 출력에 전달한다. next의 보관 성공은 본문 수신 완료의 증거가 아니다.
3. 온전한 수신을 확인한 뒤 다음 호출에서 보관한 next를 같은 도구의 인자로 전달한다. 검색과 읽기, 다른 프로젝트나 별도 요청의 값을 섞지 않는다.
4. 출력이 잘렸다면 next로 전진하지 않고 **잘린 응답을 만든 입력**으로 채택한 축소 정책을 적용한다. 따라서 다음 값만 남기고 직전 요청을 먼저 버리는 구성은 부적절하다.
5. 값이 없거나 취소/재시작 뒤 상태를 확인할 수 없으면 대화에 보인 cursor 조각으로 재구성하지 않는다. 원래 요청을 확인해 새 기준으로 시작하거나 미완료를 알린다. 옛 본문과 새 원문을 합쳐 완료하지 않으며 재시도 횟수를 이름만 바꿔 초기화하지 않는다.

논리 요청별로 값을 구분하고 같은 요청을 동시에 전진시키지 않는다. 현재 연결/요청과 맞는지 확인한 뒤에만 사용하며 쓰지 않는 전체 본문을 계속 저장하지 않는다. 이 임시 보관은 active나 설치/기능 복구 DB의 대체가 아니다. 서버의 서명/원문 검사는 남으며, 지원하지 않는 호스트에서 조용히 된다고 가정하거나 MCP 서버가 모델 출력을 관측하는 것처럼 설명하지 않는다. 지원 부재는 해당 개선의 미지원 조건으로 기록하고 대안을 다시 판단한다.

형식이 깨진 cursor와 현재 연결에서 검증할 수 없는 cursor는 확인 가능한 범위에서 안내를 구별한다. 서명 검사 실패만으로 실제 시간 만료나 재시작을 확정하지 않는다. 짧은 ID로 서버 메모리에 조회 상태를 두는 안은 호스트 의존을 줄일 수 있지만 메모리 상한, 퇴출, 재시도와 재시작 처리가 추가되므로 이번 후보와 별도 선택이다.

### 대안과 통합 범위의 경계

| 대안 | 장점 | 이번 판단 |
| --- | --- | --- |
| 복수 검색 + 지원 호스트의 next 객체 재사용만 우선 | 기존 안전 경계를 유지하며 원인을 작은 범위로 비교 가능 | 최초 추천이었으나 사용자 시간 제약에 따라 여러 파일 읽기까지 이번 범위에 포함. 별도 작은 단계로 나누지 않음 |
| 기존 읽기/검색 도구에 복수 검색/묶음 읽기와 값 재사용 통합 | 추가 범용 도구 없이 반복 탐색과 읽기, 중복 원문/값 전달을 함께 보완 | **선택한 개선 범위.** 합산 반환, 일부 실패, 여러 파일 버전과 호스트 수신의 검사를 함께 수행해야 함 |
| 검색과 읽기를 한 새 범용 묶음 도구로 교체 | 호출 표면을 하나로 묶을 수 있음 | 검색 결과에 따라 읽을 대상을 정하는 의존 단계까지 자동으로 처리하지는 못함. 새 복합 스키마/발견 비용이 있어 이번에는 기존 두 책임을 유지 |
| 짧은 조회 ID와 서버 메모리 상태 | 긴 cursor 재작성 위험과 일부 재탐색을 줄일 여지 | 별도 상태 수명과 자원 관리 필요. 실제 값 전달 실패 뒤 최소 요청 보관 후보로 범위를 좁혀 별도 구현/검사. 첫 제품 제공은 미확정 |

[Google의 Batch Get](https://google.aip.dev/231)은 원자적 결과와 페이지 분할 금지를 전제로 하고, [DynamoDB의 BatchGetItem](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_BatchGetItem.html)은 처리하지 못한 항목을 돌려준다. 따라서 “묶음 처리는 항상 전부 성공하거나 항상 일부 성공을 허용한다”는 공통 규칙을 가져오지 않는다. 향후 여러 파일을 묶더라도 같은 시점의 파일 스냅샷을 자동 보장하지 않으며, 어느 요청이 완료/미완료/실패했는지와 독립 재시도 범위를 먼저 정해야 한다.

통합 범위는 확인된 문제와 직접 연결되는 검색/읽기/전달/실패 처리다. 일반 목적의 새 도구, 영속 색인, 로컬 AI나 서버 조회 DB까지 한꺼번에 도입하는 뜻은 아니다. [MCP 구조화 반환](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#structured-content)은 데이터를 전달하는 형식이며 그 자체로 이런 사용자 정의 검색이나 호출 수 절감을 제공하지 않는다.

공식 코드의 [Apache-2.0 표시](https://github.com/openai/codex/blob/main/LICENSE)를 확인했고 이번에는 동작을 조사해 설명했으며 구현/문서 원문을 복제하거나 의존성을 동봉하지 않았다. 별도 후보에서 입력 선언/파서/본문 처리/설명과 영향 검사를 함께 보완했고 현재 시험 연결과 닫힌 근거는 보존했다. 다음 실제 AI 비교는 같은 환경의 기존/개선 후보에 각 한 요청을 제안하며 사용자가 이 두 요청의 실행 범위를 수용했다. 이후 결과는 개인 [트러블슈팅 사례](../../evidence/cases/mcp-cost.md)에 기존 관측과 구별해 연결한다.

### 통합 후보 구현과 검사

11/21 작업의 [별도 후보](../../evidence/experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)에 복수 검색과 묶음 읽기를 구현했다. Windows 코드/SDK 42개 검사에는 기존 단일 입력/원문 보호와 새 요청 대응/겹침/일부 실패/원문 변경/취소가 포함된다. 최초 긴 검색어 발췌 오류와 수정 후 영향 재검사도 보존했다. 이는 실제 Codex 답변 품질이나 비용 개선의 통과 결과가 아니다.

| 후보 반환 | 소비 기준 |
| --- | --- |
| 복수 검색의 queries, query_matches | query_index는 입력 배열의 0부터 시작하는 번호. 같은 줄의 각 검색어 첫 일치 위치를 보존하며 긴 줄의 모든 일치가 발췌 안에 들어간다는 뜻은 아님 |
| 묶음 읽기의 results, request_indices, span | 각 본문이 충족하는 요청 번호와 실제 바이트/줄 구간. 겹친 원문을 중복 출력하지 않고 요청별 확인 범위를 재구성 |
| errors, complete, stop_reason | 실패 요청의 번호/경로/이유를 유지. 오류가 있으면 isError=true이며 마지막도 partial_error/complete=false. 정상 부분 결과와 next는 함께 보존 |
| next | 같은 묶음의 아직 전달하지 않은 범위. next=null만으로 전체 성공 판정 금지. 같은 연결에서 원문/실패 상태가 바뀌면 옛 페이지를 섞지 않음 |

SDK의 두 규격에서는 부분 오류와 정상 본문을 함께 전송하고 반환된 next를 다음 요청에 그대로 전달하는 것을 확인했다. [관측 기록 (호스트 호출 예시)](../../evidence/experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)와 모의 검사는 값 재입력을 줄이는 흐름을 보여 주며 실제 Windows Codex의 store/load 지원이나 본문 수신을 증명하지 않는다. 파일/범위 재확인과 더 큰 도구 선언의 비용도 있으므로 호출 수 감소를 실제 토큰 절감으로 단정하지 않는다.

11/22 [실제 비교](../../evidence/experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)는 같은 Windows Codex 0.171.0 / GPT-5.6-Sol low에서 기존/개선 각 한 요청으로 마쳤다. 두 답은 사전 필수 사실 15개를 충족하고 관측된 본문도 원문과 일치했다. 내부 응답은 21→14회, 캐시 포함 입력+출력은 781,204→480,497이지만 캐시 제외 합계는 40,212→42,225로 늘었다. 직접 접근은 기존의 별도 기준이다. 단건 변동과 오류를 포함한 수치이며 비용 개선 완료로 판정하지 않는다.

### 실제 호출에서 남은 연결

개선본은 묶음 검색/읽기를 사용했지만 store/load나 호출 예시를 사용하지 않고 cursor를 재작성했다. [관측 기록 (실제 입력 대조)](../../evidence/experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)에서 검색 토큰의 528→527자 변형, 같은 길이의 읽기 토큰 안 파일명 변형을 확인했다. 둘 다 거부됐고 시간 만료/서버 재시작이 원인이라는 증거는 없다. 예시와 지침이 있다는 사실을 실행 연결 완료로 취급하지 않는다.

또 page_bytes=22000은 등록 상한 16384보다 커 거부됐고 AI가 15000으로 수정했다. 실제 출력 잘림은 아니며 오류 후 페이지 축소 검증으로 세지 않는다. 도구 입력 선언은 양수만 표시하고 현재 등록 상한을 표시하지 않아 추측을 줄일 연결이 필요하다. 첫 묶음과 광역 검색 일부가 미완료로 남은 사실, 최종 오류 설명의 빠진 항목도 보존한다.

보완은 **현재 등록값 안내 → 이어 읽기 전달 방식 선택/구현 → 실제 사용 검증 → 첫 제공 판단** 순서로 진행한다. 현재 값을 알리는 변경은 아래 별도 후보의 Windows 코드/SDK 9개 조건에서 확인했으며, 서버 상태 저장이나 새 도구까지 채택한 것은 아니다. 원문 확인을 제거하거나 틀린 값을 추정 복구하지 않는다. 추가 AI 요청은 이미 완료한 두 요청에 포함하지 않는다.

#### 현재 설정값의 안내

[입력 안내 후보](../../evidence/experiments/wiki-access/2026-11-22_18-26-09-mcp-inputs.md)는 `tools/list`(도구 목록 조회) 시 현재 프로젝트 연결의 page_bytes를 읽어 모든 초기/이어 입력 분기에 최대값과 기본값을 표시한다. 단위는 UTF-8로 표현한 한 논리 JSON 응답의 바이트 수다. 토큰 수, Codex의 출력 상한이나 모델별 한도를 뜻하지 않는다. 생략/null은 현재 설정값을 사용하고, 초과 입력은 실제 허용값과 수정 방법을 알려 거부한다. 값을 자동으로 올리거나 사용자 설정을 변경하지 않는다.

입력 상한은 JSON Schema의 [maximum](https://json-schema.org/understanding-json-schema/reference/numeric#range)을 사용한다. 기본값 표시는 설명이며 값을 자동 삽입하는 기능으로 가정하지 않는다. 실행할 때도 같은 연결 설정으로 검사한다. 등록값 변경 뒤 호스트에 예전 도구 선언이 남아 있을 수 있으므로, 실제 호출의 판정과 오류 안내가 현재 값을 기준으로 해야 한다. 재조회하면 최신값을 반환하되 모든 호스트가 자동 재조회한다고 보장하지 않는다. 자동 알림/감시 기능은 이번 변경에 추가하지 않았다.

#### 이어 읽기 전달 방식의 선택

사용자는 곧바로 안을 선택하는 대신 공식 자료와 실제 사례를 충분히 조사해 현재 요구에 가장 적합한 구조를 판단하도록 요청했다. [관측 기록 (확장 조사와 기존 로그 재집계)](../../evidence/experiments/wiki-access/2026-11-22_18-26-09-mcp-inputs.md) 결과, **값을 어디에 보관할지와 누가 후속 호출을 실행할지는 별개 선택**이다. 프로그램이 next를 그대로 전달하는 방식과 짧은 서버 cursor는 함께 사용할 수 있다. 아래 비교는 현재 일반 Codex 연결에서 무엇을 먼저 구현할지에 관한 것이며, 한 방식이 모든 환경에서 최선이라는 결론은 아니다.

cursor는 다음 위치를 가리키는 불투명한 값이다. 호출자는 내용을 해석하거나 다시 만들지 않고 돌려줘야 한다. [MCP의 목록 페이지 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination)도 이 원칙을 사용한다. 다만 그 규격은 `tools/list` 같은 목록 기능에 관한 것이며, 우리 `read_note`/`search_notes`의 본문 이어 읽기를 자동으로 구현해 주지는 않는다.

추천 후보는 서버 프로세스 메모리에 **요청별로 원래 검색어/파일/구간, 프로젝트 연결과 원문 기준을 한 번 보관**하는 방식이다. 이어 위치는 짧은 cursor에 연결하되 같은 입력을 다시 쓸 수 있는 불변값으로 다룬다. 페이지마다 문서/응답 사본이나 동일 요청 본문을 쌓는 안은 추천하지 않는다. 기존 두 도구를 유지하며 WIKI 본문 캐시, 색인, 세션 복구 SQLite나 새 상주 서비스를 도입하지 않는다. 재시작 뒤에는 원래 범위를 다시 확인한다. 현재도 프로세스별 서명 키가 사라지면 기존 cursor를 사용할 수 없다.

후속 구현은 아래 조건을 대상으로 코드 검사를 진행했다. 구체 구현/결과는 다음 절이 소유하며, 실제 AI 수신/비용을 통과한 것으로 확대하지 않는다.

- 식별자는 추측하기 어려운 값으로 만들고 프로젝트/도구/요청을 교차 사용하지 못하게 한다. 유효한 요청과 현재 원문/연결을 다시 대조하며, 긴 서명 문자열을 줄인다는 이유로 접근 보호를 없애지 않는다.
- 발급한 이어 위치를 “클라이언트가 읽음”으로 처리하지 않는다. 같은 입력을 재시도하면 같은 위치를 재확인하고, 응답 유실/취소 때 다음 페이지로 건너뛰지 않는다. 같은 문서의 겹친 요청도 별개로 구분한다.
- 보관량은 요청 수와 요청 정보 크기를 기준으로 제한하고, 페이지 수만큼 본문/요청 사본이 누적되지 않는지 검사한다. 오래 사용하지 않아 퇴출된 요청은 명시적으로 거부하고 가까운 요청으로 대체하지 않는다. 처리 중인 요청의 정보는 호출 종료까지 보존하며 상태 접근의 동시성만 보호하고 파일 I/O 전체를 잠그지 않는 방향을 검토한다. 보관 한도와 정리 규칙은 다음 절의 후보 값으로 구현/검사했다. 사용자 환경 전체의 최적값이나 첫 배포 확정값으로 확대하지 않는다.
- 현재 반환 오류의 `expired_cursor` 이름만으로 시간 만료를 확정하지 않는다. 관측한 사실이 “이어 값을 검증할 수 없음”이면 그 범위만 보고한다. 어떤 보관 방식을 선택해도 코드가 실제 모델 수신/이해를 보장할 수는 없다.

이 비교에서 선택한 시험 대상은 **기본 직접 접근을 유지한 채 최소 요청 정보/짧은 cursor 후보를 검증하는 것**이었다. 실제 비교 뒤 첫 제공에 관한 최신 추천은 아래 「세 방식 비교와 첫 제공 판단」에서 구분한다. 후속 로컬 연결 프로그램처럼 우리가 호출 흐름을 실제로 소유하는 경우에는 반환값을 코드로 그대로 전달하게 한다. 일반 Codex를 별도 호스트로 교체하거나 전역 설정을 바꾸는 방식으로 그 조건을 지금 강제하지 않는다. [AWS의 SDK 반복 처리](https://docs.aws.amazon.com/boto3/latest/guide/paginators.html)와 [Anthropic의 코드 실행 방식](https://www.anthropic.com/research/code-execution-with-mcp)은 이 역할 분리의 근거이며, 필요한 원문을 모델에 안 보여도 전체 읽기로 처리할 근거는 아니다.

[관측 기록 (기존 로그 재집계)](../../evidence/experiments/wiki-access/2026-11-22_18-26-09-mcp-inputs.md)에서 개선본의 cursor 입력은 두 번/합계 1,579자였고 읽기 본문량도 기존보다 많았다. 이 수치를 토큰으로 환산하거나 cursor 단축만으로 전체 비용/시간 차이가 사라진다고 가정하지 않는다. 잘못된 값 거부, 필요한 범위/최종 답변의 정확성, 실제 모델 수신과 비용을 각각 검증한다. 앞선 조사 요청만으로 구현을 승인받은 것으로 취급하지 않았다. 조사 결과 설명 뒤 사용자가 출력 기준을 반영하고 이어서 진행하도록 요청해 후보 구현/코드 검사를 진행했다. 추가 AI 실행은 별도 합의 대상이다.

#### 요청 보관 후보의 동작

[짧은 cursor 후보](../../evidence/experiments/wiki-access/2026-11-22_19-16-43-mcp-cursor.md)는 기존 두 도구의 초기/이어 입력 형식을 유지한다. 처음에는 경로/검색 조건을 보내고, 이후에는 반환된 next를 그대로 보낸다. 내부에서는 임시 요청 식별자, 두 정수 위치와 HMAC 서명을 고정된 88자로 표현한다. 단일 읽기는 바이트 위치, 묶음은 구간 번호/바이트 위치, 검색은 정렬된 파일 번호/줄의 바이트 위치를 사용한다. 검색의 원문 집합 검사를 유지하므로 파일 번호가 같은 다른 원문을 섞지 않는다. 이 형식은 클라이언트가 해석하거나 생성할 계약이 아니다.

서버는 도구 종류, 프로젝트 연결, 원래 요청과 원문 기준만 한 번 보관한다. 같은 요청의 다음 페이지를 만들 때 기록을 추가하지 않으며 본문/응답 사본은 저장하지 않는다. 페이지 크기를 계산하는 중간 후보는 보관소에 등록하지 않고, 원문/연결 검사를 마친 실제 반환 결과에 next가 있을 때만 등록한다. 최종 검사 전에 오류/취소된 초기 요청은 기존 보관 자료를 밀어내지 않는다. 등록 뒤 전송 중 취소되거나 응답이 유실되면 기록이 남을 수 있으므로, 등록과 클라이언트의 실제 본문 수신을 구분한다.

후보의 실제 기본 한도는 **요청 128개, 직렬화한 요청 정보 합계 1MiB**이며 `--request-limit`와 `--request-bytes` 실행 인자로 바꿀 수 있다. Python 객체/현재 읽기 버퍼/SDK를 포함한 전체 RAM 상한은 아니다. 시간 경과만으로 만료시키는 TTL은 두지 않는다. 한도에 도달하면 현재 서버 호출에서 사용 중인 기록을 보호하고, 나머지 중 가장 오래 사용하지 않은 요청부터 정리한다. 본문이 사용자에게 반환된 뒤 다음 호출을 기다리는 요청도 정리 대상이 될 수 있다. 논리적 작업 전체를 영구 고정하는 방식이 아니다.

같은 이어 값을 재시도하면 같은 위치를 다시 확인하고, 완료 후에도 보관 중인 이전 값은 재사용할 수 있다. 한 요청이 너무 크거나 모든 후보가 호출 중이라 자리를 만들 수 없으면 `cursor_capacity`로 중단하며 기존 보관 내용을 먼저 지우지 않는다. 값 변형/다른 연결/서버 재시작/정리로 사용할 수 없는 값은 `expired_cursor`로 알린다. 이 오류 이름만으로 시간 만료를 단정하지 않는다. 필요한 원문을 다시 읽지 못했으면 전체 완료로 표시하지 않는다.

Windows 코드/SDK에서 기존 원문/검색/경로 보호, 두 규격, 취소와 새 수명/보관/재시도 조건을 합쳐 **63개 조건의 최종 PASS**를 확인했다. 첫 실행의 62개 중 1개는 앞선 상한 안내를 반영하지 않은 검사 기대값이라 수정 후 해당 검사만 재실행했고, 실제 SDK 기본 한도/정리 검사를 1개 추가했다. 새 후보의 43페이지 읽기는 요청 정보 1건/219바이트를 유지했다. 이 수치는 합성 코드 검사이며 실제 AI 토큰, 최적 메모리 설정이나 큰 프로젝트의 성능 보장은 아니다. 당시에는 새 AI 실행 없이 코드/원문 경계만 확인했다. 이후 별도 승인한 실제 세 요청의 결과는 다음 절과 연결하며 코드 검사 PASS를 제품 수용으로 확대하지 않는다.

### 세 방식 비교와 첫 제공 판단

11/22 승인한 직접 접근, 긴 값 MCP, 짧은 값 MCP의 각 한 사용자 요청을 모두 마쳤다. 같은 Windows Codex 0.171.0 / GPT-5.6-Sol low와 사본 60개, 같은 질문 본문을 사용했다. [실제 비교 결과](../../evidence/experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)에 요청별 원문 수신, 의미 검토와 전체 수치를 보존했다. 세 요청 모두 사용자가 추가 승인창이 없었다고 확인했다.

짧은 값은 88자 cursor 5개를 정확히 전달했지만 입력 상한 초과 1회, 첫 검색의 90개 미수신 결과를 알리지 않은 완료 보고, 받은 원문의 필수 답변 기준 1개 부분 누락이 남았다. 긴 값도 이번 표본에서는 이어 값 10개를 정확히 전달했으므로 오류 감소를 값 단축의 효과로 확정하지 않는다. 원문/위치 대조 PASS와 최종 작업 수용은 별개다.

짧은 값의 질문 처리 시간은 91.486초, 캐시 제외 입력과 출력은 52,092토큰이다. 직접 접근은 66.596초/32,121토큰, 긴 값은 168.568초/82,904토큰이었다. 짧은 값이 긴 값보다 적게 썼어도 검색 범위와 답변 품질이 달라 동등 품질의 절감 성과로 인정하지 않는다. 직접 접근에도 최초 출력 잘림과 인용 두 줄 미수신이 있으므로 완전한 기준선으로 취급하지 않는다. 단일 표본, 질의/읽기 범위 차이와 전역 설정 해시 변화의 한계는 실행 근거에 남겼다.

| --- | --- | --- |
| 첫 배포에서는 직접 접근에 집중하고 MCP 제공은 후속 검토 | 조건부 하네스의 필수 기능과 검증에 시간을 쓸 수 있음. 일반 Codex의 선택 MCP 연결과 여러 AI의 도구 재사용 편익은 미뤄짐 | 11/22 사용자 채택. 후보/조사/실패 근거는 보존 |
| 첫 제공 전에 MCP 보완을 계속 진행 | 필요한 문서 처리 규칙을 도구로 재사용할 가능성을 더 검증할 수 있음. 미완료 범위의 보고, 입력 처리와 최종 사실 검토를 호출 흐름에 연결하고 실제 비용을 다시 확인해야 함 | 새 보완 범위와 AI 비용 합의 필요. 지침 추가만으로 무누락이나 시간 개선을 보장하지 않음 |

현재 결과만으로 MCP 전체를 부적합하다고 단정하지 않는다. 그러나 현재 사용 목적에서 직접 접근보다 더 드는 비용과 보완 부담을 상쇄하는 편익도 입증하지 못했다. 사용자가 11/22 직접 접근 우선 진행에 동의해 [ADR 0022 — 「11월 22일 첫 제공 범위」](../../decisions/runtime/0022-wiki-entry.md)에 첫 제공 범위를 반영했다. 기본 전용 시작 명령/직접 접근을 유지하고 부모 4단계 파일별 변경 명세로 복귀한다. MCP 쓰기/복원과 남은 수용 검증을 완료로 표시하지 않으며, 기본 경로의 필수 WIKI 기능은 계속 제공/검증할 대상이다.

## 오류와 답변 품질의 책임

MCP 연결부는 [공식 오류 구분](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling)에 맞춰 프로토콜 오류와 도구 실행 오류를 구별한다. 도구 실행 오류는 `isError: true`와 짧은 이유/다음 행동으로 모델에 전달한다. 성공 형태의 빈 matches/text, 내부 traceback이나 비밀값/절대 경로를 대신 반환하지 않는다. 정상적으로 나눈 페이지는 도구 오류가 아니지만 요청 전체 완료도 아니다.

| 상황 | 다음 행동 |
| --- | --- |
| 잘못된 줄/경로/검색 입력 | 잘못된 항목과 허용 형태를 알려 입력 수정. 예시 때문에 범위 검사를 느슨하게 하지 않음 |
| 파일/연결 변경, 만료 cursor | 영향받은 원문/검색 기준만 새로 확인. 옛 페이지와 새 페이지의 혼합 완료 금지 |
| 권한 거부/범위 이탈 | 관련 읽기를 중단하고 허용 범위/준비 상태 확인. 다른 도구로 제한을 우회하지 않음 |
| 파일 부재/UTF-8 오류/페이지 진행 불가/범위 미완료 | 확보 범위와 부족한 입력을 구별해 안내. 누락을 숨긴 성공 금지 |
| 일시적 I/O/통신 실패, 응답 유실/취소 | 읽기 요청의 대상/원본이 같은지 확인한 뒤 필요한 요청만 재시도. 무조건 반복이나 쓰기 재시도로 확대하지 않음 |

한 호출의 끝을 대화/프로젝트 작업 전체의 끝으로 취급하지 않는다. 해결된 중간 입력 오류를 매번 사용자 질문으로 돌리지 않되, 남은 근거 공백/품질 영향은 완료 보고에 포함한다. 잘린 부분을 같은 인자로 반복하거나 해소하지 못한 오류를 성공으로 누적하지 않는다.

최종 답변은 [원문 수신과 답변의 완전성](../workflow/verification.md)의 공통 검토를 따른다. MCP가 본문을 전달했거나 JSON 검사를 통과했다고 의미 검토까지 통과하지 않는다. 다음 순서는 실제 배포 코드/설정/제한과 사용 경로 확인 → 같은 조건의 기능별 검증 입력 준비 → 해당 경로의 실제 실행/상호작용 검증 → 첫 제공 범위 판단이다. 모델 없는 내부 검사는 필요한 코드 결함 확인에 보조로 쓰며 이 순서를 대체하지 않는다. 새 지원/비용 선택이 생기면 그 지점에서 확인하며 쓰기/복원 시험은 자동 추가하지 않는다.

## 구현과 회귀검사의 범위

11/19의 [정적 소스 검토](../../evidence/experiments/wiki-access/2026-11-20_03-20-37-mcp-implementation-review.md)를 바탕으로 구현한 후보 범위다. 과거 근거의 source를 수정하거나 그 시험에서 사용한 상한을 다시 실행하지 않았다. 후보는 기존 두 도구를 유지하고 원문 처리와 MCP 연결 책임을 분리한다. 아래 대응표의 파일명은 검토한 기존 소스 기준이다. 새 후보의 파일 구성과 실제 검증은 [후보 코드와 부분 검증](mcp.md#%ED%9B%84%EB%B3%B4%20%EC%BD%94%EB%93%9C%EC%99%80%20%EB%B6%80%EB%B6%84%20%EA%B2%80%EC%A6%9D)에 연결하며 배포 경로/제품명을 확정하지 않는다.

| 변경 위치 | 재사용할 책임 | 후보에서 바꿀 부분과 회귀 범위 |
| --- | --- | --- |
| wiki.py의 연결/경로 검사 | 프로젝트/WIKI 식별, 상대 경로, 범위 이탈과 링크/junction 거부, 파일 변경 확인 | 시험 부모 폴더 제약을 제품 연결 정책과 분리. 등록된 내부/외부 WIKI를 공통 연결로 해결. Windows의 드라이브/UNC/ADS, `..`, reparse point와 실제 연 핸들의 대상 검증 유지. R-05/12/14 |
| 원문 읽기 | 바이너리 입력, 원문 해시와 줄 의미 | 파일 전체 read/줄 배열을 스트리밍 처리로 교체. 작은 버퍼에서 UTF-8 문자와 CRLF를 보존하고 긴 한 줄도 byte span으로 분할. R-01/03/04/13 |
| 검색 | 같은 허용 집합, 경로와 위치의 안정된 순서 | 전체 본문/일치 결과 배열을 없애고 한 페이지 본문만 모음. 일치 줄/발췌/전체 읽기를 구별. cursor에 원래 질의와 다음 원문 위치를 포함. R-06/07/08 |
| 입력과 결과 형식 | JSON 검증, 한 결과에서 표준 표현 생성 | 아래 초기/이어 요청 조건을 한 소유 위치에 둠. 출력 schema의 단순 object 선언을 성공/오류와 필수 진행 정보로 구체화. 논리 JSON 크기와 SDK/실제 전송 계수를 분리. R-02/04/09/10 |
| server.py의 실행 | 공식 SDK의 STDIO/도구 목록과 오류 분류 | 긴 동기 I/O로 통신 루프를 막지 않도록 실행/취소 책임을 연결. 취소된 요청의 늦은 결과를 성공으로 전달하지 않음. R-07/10/13 |
| test_reader.py와 test_sdk.py | 독립 기대 원문, 기존 파일/연결/거부 입력 | 숫자만 고친 옛 시험을 재사용하지 않음. 후보 schema/크기 단위/부분 줄에 맞춰 기대값을 수정하고 원문과 실제 wire 관측을 분리. 관련 R-01~14 |

최소 입력 대조는 다음과 같다. JSON Schema의 [조건부 검증](https://json-schema.org/understanding-json-schema/reference/conditionals)과 실행 검사를 같은 기준으로 구현한다. 형식 검사는 JSON 타입/분기를 다루고, 설정값 초과나 현재 파일/권한 검사는 실행 시 다룬다. schema만으로 현재 파일의 존재를 보장하지 않는다.

| 입력 | 처리 |
| --- | --- |
| read의 path 또는 search의 query, cursor 생략/null | 초기 요청. 필수 문자열은 비어 있지 않아야 하며 null도 필수값을 대신하지 못함 |
| 유효 cursor, 초기 요청의 다른 필드 생략/null | 이어 요청. page_bytes만 선택적으로 지정. path/query/scope/줄/revision의 non-null 혼용은 거부 |
| `1`, `1.0`, 양의 정숫값 | 줄/page_bytes의 같은 정수 의미로 정규화. `true`, `1.5`, 문자열 `"1"`, 0/음수/비유한 값은 거부 |
| 알 수 없는 필드, 옛 limit/offset, 비어 있는 cursor | 입력 오류. 오타를 무시해 기본 범위로 읽지 않음 |
| 긴 query/경로 또는 최소 페이지 | 원래 입력을 잘라 바꾸지 않음. 필수 진행 정보와 최소 결과를 담을 수 없는 경우 진행 불가를 반환 |

경로 허용 집합은 직접 읽기와 검색이 공유한다. 기존 시험의 모든 점 접두어 거부는 일반 문서의 허용 정책으로 조용히 복제하지 않는다. Git 내부, 로컬 상태, 호스트 설정처럼 WIKI 자료로 허용하지 않은 위치와 허용된 숨김 Markdown을 구별한다. 제외 규칙의 실제 이름/소유 위치를 후보 연결과 대조하고 범위에 영향을 주는 제외를 숨기지 않는다. 범위 밖 링크를 허용하거나 민감한 설정을 읽는 것으로 문서 누락을 해결하지 않는다. 미확정 허용 집합으로 실사용 비교를 통과 처리하지 않는다.

### 메모리와 변경 확인 비용

원문은 바이너리로 읽어 [Python의 텍스트 읽기](https://docs.python.org/3.13/library/functions.html#open)가 적용할 수 있는 줄바꿈 변환을 피한다. LF를 줄 경계로 하고 CRLF는 보존하며 독립된 CR을 새 줄로 바꾸지 않는다. UTF-8 디코더의 부분 문자와 검색어가 버퍼 경계를 가로지르는 경우를 검사한다. 한 줄 전체를 메모리에 담는 readline만으로 긴 줄 지원을 끝내지 않는다.

파일 식별/해시는 본문을 계속 보관하지 않고 계산한다. 검색은 정렬할 경로/식별 정보는 필요하지만 모든 파일 본문과 matches를 쌓지 않는다. 최초 후보에서는 이전 기준과 비교하려고 이어 요청마다 파일 또는 검색 범위의 내용을 다시 읽을 수 있다. 페이지가 찼어도 변경 기준 확인을 위한 읽기는 계속될 수 있으므로 ‘페이지가 차면 모든 I/O가 즉시 끝난다’고 설명하지 않는다. 전체 읽기량, 최대 메모리, 페이지/재시도 수를 실제 규모에서 측정하며 이 비용을 모델 토큰 절감으로 숨기지 않는다.

Windows 식별 필드는 [Python 파일 정보](https://docs.python.org/3.13/library/os.html#os.stat)의 지원 조건을 확인한다. 과거 ctime/birthtime 오판 수정과 내용 해시를 보존하되 시간만 같으면 불변이라고 판단하지 않는다. 경로 조회와 실제 핸들의 대상이 같다는 검사, 원문 변경과 접근 거부는 별도다. 쓰기용 배타적 잠금이나 DB 트랜잭션을 읽기에 자동 적용하지 않는다.

재검사 비용이 실제 사용을 방해하면 위 메모리 조회 상태와 비교하되, 기존 원문/진행 보존 조건을 삭제해 속도만 맞추지 않는다. 아직 검증하지 않은 큰 규모까지 지원한다고 표시하거나 시간 제한을 임의로 늘려 성공시키지 않는다. 새로운 자원 정책이 필요하면 실제 규모와 실패를 근거로 같은 구현/설정에 반영한다.

### 실행과 취소

이전 시험의 async handler는 동기 읽기/검색을 직접 호출했다. 이는 [Python 실행 문서](https://docs.python.org/3.13/library/asyncio-task.html#asyncio.to_thread)의 통신 루프 차단 주의에 해당하는 정적 위험이며 과거 취소 실패를 재현했다는 뜻은 아니다. 새 후보는 [AnyIO의 협력적 취소](https://anyio.readthedocs.io/en/stable/threads.html#reacting-to-cancellation-in-worker-threads)를 사용해 파일 처리를 worker thread로 옮기고 버퍼/파일 경계에서 해당 요청의 취소를 확인한다. 스레드를 남겨 둔 채 호출만 종료하는 옵션은 사용하지 않는다.

후보는 설치된 SDK의 실행 방식에 맞춰 파일 I/O를 분리하고, 요청별 취소 신호를 버퍼/파일 경계에서 확인한다. 단순히 스레드로 옮겼다고 실행 중인 스레드가 취소되는 것은 아니므로 정리와 종료를 확인한다. 무한한 작업 스레드나 요청별 별도 서버를 만들지 않는다. 실제 동시 요청 제어와 SDK의 취소 전달은 후보에서 함께 검증하며 숨은 시간 제한으로 정상 작업을 종료하지 않는다.

[MCP 취소 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)에 맞춰 해당 요청의 자원을 정리하고 늦은 결과를 새 요청의 성공으로 쓰지 않는다. 호스트 취소 뒤 반드시 사용자에게 오류 응답이 도달한다고 보장하지 않는다. 독립된 다른 요청을 취소하거나 정상 Codex 프로세스 전체를 종료하지 않으며 완료/취소가 경합한 경우도 검사한다.

실제 화면의 중단, 도구 호출 사이의 중단과 MCP 요청 처리 중의 취소는 관측한 위치에 맞춰 구별한다. 코드 실행 도구가 진행 중이었다는 기록만으로 내부 MCP 요청의 취소 전달이나 파일 작업자 종료를 입증하지 않는다. [현재 실행 방식의 중단 시험](../../evidence/experiments/wiki-access/2026-11-21_00-03-04-mcp-cancel-plan.md)에서는 첫 페이지 반환 후 다음 호출 전에 중단됐고, 같은 대화의 새 구간 읽기와 원문/답변 일치를 확인했다. 내부 MCP 처리 중 취소와 실제 늦은 응답은 관측하지 못했다. 그 사례를 통과로 표시하거나 시험용 지연/임의 제한으로 실제 사용 결과를 만들지 않는다.

후보 코드와 공통 설정, 실제 등록할 schema/설명, 독립 기대값과 Windows 검사 명령을 함께 보존했다. 이후 실제 Codex 수신과 오류 후 사용은 아래의 개별 관측으로 구분한다. 코드/SDK 경계 검사와 일부 사용자 표본을 전체 기능의 성공으로 대신하지 않는다.

## 후보 코드와 부분 검증

[11/19 실행 근거](../../evidence/experiments/wiki-access/2026-11-20_03-42-30-wiki-reader.md)의 source에 후보를 보존했다. contract.py는 입력/결과 형식과 기본값, files.py는 등록된 Windows 경로/핸들과 원문 스트리밍, reader.py는 범위/검색/이어 요청, server.py는 공식 SDK 연결과 취소를 담당한다. 조회용 DB나 실행 상태를 추가하지 않았다. 서버가 켜질 때마다 새 서명 키를 메모리에 만들며 이를 기록하지 않는다.

경로 허용 기준은 직접 읽기와 검색이 공유한다. `.agents`, `.codex`, `.git`, `.harness`, `.obsidian`은 도구 설정/로컬 상태로 제외하고 검색 결과의 excluded_dirs에 표시한다. 일반 숨김 Markdown은 읽고 `.gitignore`를 문서 제외 규칙으로 사용하지 않는다. 연결의 내부/외부 WIKI를 모두 확인했으며 옛 시험의 부모 폴더 제약은 없다. Windows 경로 검사 뒤 실제 연 파일의 대상도 확인해 밖으로 연결된 junction의 본문을 반환하지 않는다. 이 검사가 모든 파일시스템 경합과 악의적 로컬 변경을 완전히 격리한다는 보장은 아니다.

| 확인한 범위 | 결과와 해석 |
| --- | --- |
| 원문/입력/Windows 경계 | 파일 검사 21개 통과. 실제 사본 60개 전체 읽기와 독립 원문 일치, 긴 줄/UTF-8/CRLF, 범위, 검색/재시도, 변경/거부와 최종 핸들 대조 포함 |
| 실제 SDK 전송 | 3개 검사 통과. 2025-11-25 규격의 전체/구간 읽기, 검색 페이지와 오류, 2026-07-28 규격의 짧은 원문 전달, 실행 중 취소 뒤 별도 읽기를 확인. 규격별 확인 깊이는 같지 않음 |

실제 전송을 검사하던 최초 시도에서 새 규격에 옛 initialize 절차를 사용한 검사기 오류가 있었다. [공식 SDK 연결 설명](https://py.sdk.modelcontextprotocol.io/protocol-versions/)과 설치 소스를 대조해 검사기의 server/discover/요청별 메타데이터를 보정하고 실패한 항목만 재검사했다. 제품 후보에 수기 버전 분기나 고정 바이트 보정을 추가하지 않았다. SDK가 담당할 변환과 우리 원문 처리를 구별한다.

큰 입력은 별도로 만든 9MiB/18MiB 파일과 취소용 32MiB 파일이다. 실제 사본의 분포와 혼합해 일반 성능을 주장하지 않으며 시간/메모리의 표본과 계측 비용은 실행 근거에 둔다. 원문 품질이 같다는 이유만으로 이 후보가 더 저렴하다고 판단하지 않는다. 이 코드/SDK 검사 뒤 진행한 Codex 수신 표본은 아래 절에 연결한다. 잘림/의미/비용 비교, 사용자 설치/환경 변경, 쓰기/복원과 첫 MCP 제공 판단은 아직이다.

### 실제 Codex 수신 시험

[시험 준비](../../evidence/experiments/wiki-access/2026-11-20_04-22-37-codex-receipt.md)에 같은 후보 코드와 기본 설정의 연결 초안, 원문 기대값, 세 요청문과 기록 수집기를 보존했다. 실제 사본의 18행 구간, 72,422바이트 전체 문서, 9개 문서/71개 일치 줄의 검색을 차례로 확인한다. 각 결과를 대조한 뒤 다음 요청으로 넘어가며 실행 시 사용자의 현재 모델과 도구 버전을 기록한다. 초기 요청은 각각 한 번이고 실제 토큰과 내부 호출 수는 실행 후 확인한다.

원문 span과 본문, 검색 위치와 next/완료 표시를 독립 사본과 비교한다. Codex 기록에 있는 도구 출력을 수집하는 것과 최종 모델 입력을 관측하는 것은 다르다. exec에서 합산/변환한 출력이나 로그의 잘림을 서버 원문과 구별하고, 관측할 수 없는 본문을 해시나 AI의 완료 주장으로 대신 통과시키지 않는다.

사용자가 구체안을 승인한 뒤 [실제 Windows 시험](../../evidence/experiments/wiki-access/2026-11-20_04-55-27-codex-receipt-run.md)을 시작했다. 새 프로젝트에서 두 도구가 연결됐고 첫 구간의 18행/1,328바이트가 실제 로그와 독립 원문에서 일치했다. 실제 붙여넣기는 마지막 답변 형식 안내가 빠져 계획 요청문과 바이트가 다르며, 읽을 범위는 유지됐음을 확인했다. 이 부분 결과를 최종 모델 전송 전체나 자유 탐색의 품질/비용 통과로 확대하지 않는다.

같은 관측에서 Codex에 표시된 입력 선언의 선택 필드가 누락됐다. 기존의 공통 properties와 부분 oneOf 분기 대신, 같은 공통 정의로 각 분기의 완전한 객체 형식을 생성하도록 contract.py를 보완했다. 입력 허용/거부의 비교 17,596건과 영향받은 Windows 검사 8개를 통과했고, 재개한 실제 호스트에서도 선택 필드가 표시됨을 확인했다. 읽기/검색 코드와 기본 페이지, 보호 정책은 유지한다. [관측 기록 (최신 보정 소스)](../../evidence/experiments/wiki-access/2026-11-20_04-55-27-codex-receipt-run.md)는 이 수신 시험에 보존하며 앞선 소스를 덮지 않는다.

첫 전체 읽기는 코드가 페이지별 길이와 완료 정보만 출력해 원문 수신을 확인하지 못했다. 이 결과를 통과시키지 않고 server.py의 지침을 보완했다. 두 SDK 규격의 지침 전달 확인 뒤 실제 Codex에 재적용했고, 전체 읽기 재시도에서 5개 페이지의 72,422바이트가 독립 원문과 일치했다. next의 실제 재사용, 구간 연속성과 본문 중복 없음도 확인했다. 추가 AI 요청 한 회와 첫 실패 기록을 보존하며 최종 모델 입력 전체를 관측한 것으로 확대하지 않는다.

검색도 같은 시험 대화의 3개 응답에서 71개 일치 줄/9개 파일, 발췌와 위치가 독립 기대값과 일치했다. 초기 세 요청과 전체 읽기 재시도 한 회의 사용량을 모두 보존했다. 자유 탐색의 품질/비용 비교, 추가 실패 처리와 첫 제공 판단은 기존 수용 순서대로 남아 있다.

### 오류 후 사용의 검증 순서

11/20에는 [기존 수용 입력 — 「MCP 읽기 보완의 검증 입력」](../../verification/acceptance.md)을 현재 근거와 다음 실제 사용 시험에 대응했다. 새로운 필수 기능이나 별도 복구 체계를 추가하는 작업이 아니다. 같은 후보와 설정의 유효한 검사는 재사용하고, 실제 호스트에서 아직 보지 못한 행동을 다음 순서로 확인한다.

[다음 시험 준비](../../evidence/experiments/wiki-access/2026-11-20_18-47-33-mcp-failure-plan.md)는 새 Windows 시험 폴더에 실제 문서 한 개를 복사하는 안이다. 첫 요청은 그 문서의 첫 반환분과 없는 파일을 읽는다. 두 번째 요청 전에는 시험 사본의 첫 제목과 마지막 절만 바꾸고 같은 서버에 옛 이어 읽기 정보를 전달한다. 서버의 `changed_source` 오류 뒤 AI가 원문을 다시 읽으면 새 사본 전체와 대조한다. 오류를 알리고 멈춘 경우에는 안전한 중단과 문서 작업 완료를 따로 판정한다.

이 두 요청 사이에 Codex나 MCP가 재시작됐거나 옛 cursor가 실제로 전달되지 않았다면 원문 변경 사례를 실행한 것으로 세지 않는다. 재시작으로 인한 cursor 만료와 원문 변경은 다른 원인이기 때문이다. 첫 요청의 부분 읽기는 사용자가 지정한 범위이며, 제품의 기본 페이지/읽기 한도를 낮추는 설정이 아니다. 원본과 이전 시험 사본, 후보 코드는 보존한다.

사용자가 승인한 두 요청을 현재 Windows Codex 0.171.0, GPT-5.6-Sol low로 실행했다. [실행 기록](../../evidence/experiments/wiki-access/2026-11-20_19-20-33-mcp-failure-run.md)에서 옛 이어 읽기 정보의 실제 사용, 변경 오류와 새 본문 미전달, AI의 미완료 안내를 확인했다. 사용자는 두 요청 모두 추가 승인창이 없었다고 보고했다. 내부 모델 응답은 여섯 회이며 재독은 실행되지 않았다. 관측한 버전/모델을 고정하거나 안전한 중단을 전체 읽기 완료로 바꾸지 않는다.

원문 변경과 서버 재시작에 따른 이어 읽기 정보의 만료는 다른 사례로 유지한다. 아래 재개와 「실행과 취소」의 후속 중단 표본을 구분하며, 다음 수신/환경 입력에서도 미관측 취소 조건을 유지한다. [MCP 취소 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)상 취소 뒤 오류 응답이 반드시 오는 것은 아니므로, 응답 부재만으로 자원 정리나 후속 사용의 성공을 판정하지 않는다.

[재연결 시험](../../evidence/experiments/wiki-access/2026-11-20_20-16-32-mcp-reconnect-plan.md)은 같은 사본의 새 cursor 확보 뒤 시험용 MCP 작업자 한 개를 종료하고, 같은 대화에서 이어 읽기를 한 번 요청했다. Windows Codex 0.171.0의 이번 요청은 `Transport closed`로 실패했으며 새 본문은 없었다. AI의 정확한 부분 범위/미완료 안내는 확인했지만 자동 재연결 성공으로 해석하지 않는다.

후속 [일반 재개와 실제 읽기](../../evidence/experiments/wiki-access/2026-11-20_20-51-32-mcp-reopen-plan.md)에서는 시험 화면을 종료하고 같은 대화를 다시 열어 새 MCP 초기화를 확인했다. 추가 요청 한 회에서 실제 옛 next가 `expired_cursor`로 거부됐고, 새 본문 다섯 개의 72,577바이트/1,197행과 연속된 next가 현재 사본에 일치했다. 이전 반환분을 합치지 않고 현재 문서 전체를 완료한 이번 표본의 결과다.

현재 설치본에서 서버 하나만 재시작하는 사용자 명령은 확인하지 못했으며, 여러 대화에 영향을 줄 수 있는 내부 갱신이나 공용 서버 재시작은 사용하지 않았다. 사용자에게 만료/미완료와 정상 재개 뒤 다시 읽는 방법을 안내할 근거로 삼는다. 모든 버전의 즉시 재개 성공이나 자동 재연결을 보장하지 않으며, 명시한 오류 후 재독과 자유 탐색의 자율 복구도 계속 구별한다. 후속 중단 표본과 남은 수신/환경 입력은 위 대응표를 따른다.
