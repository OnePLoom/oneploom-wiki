# WIKI의 역할과 연결

조건부 하네스가 작업에 필요한 지식을 찾아 읽고 개발과 함께 갱신하는 WIKI를 다룬다. 기존 프로젝트의 지식이 부족할 때는 선택한 범위의 개발 과정과 결과, 선택에 이른 흐름을 근거에 따라 상세히 복원한다. 11/09 채택한 기초 파악 → 범위별 상세 복원 → 관계, 누락 대조는 그 복원 작업의 방식이며 신규 프로젝트의 선행 의무가 아니다. 제품의 중심과 신규/기존 도입은 [구조 — 「제품의 중심과 도입 경로」](../architecture.md), AI 분석 실행은 [실행 검토](../../discussions/knowledge/reconstruction.md), 비공개 실행 상태는 [작업 상태](../workflow/recovery.md)가 소유한다.

판단 날짜, 채택 상태는 연결된 ADR을 따른다. 문서 분할, 템플릿, 라우팅, 갱신 시점의 후속 비교는 [문서 구성](documents.md)이 소유한다. 상세 복원의 품질을 유지할 때만 로컬 사용을 검토하는 조건은 [품질 비교 — 「품질 비교 방법」](../../discussions/knowledge/reconstruction.md)에 연결한다.

## 최소 WIKI

2026-10-30에 작성하고 11/08 깊이, 초기 범위, 11/09 필수 정보, 위치 연결, 완료 판정을 구체화했다. **11/09 위치표 구성에 이어 WIKI 내용 구성, 분할 상세 복원, 완료 기준을 채택했다. 상세 필드, 고정 경로는 후속이며 제품은 미구현**이다. 아래 여섯 역할은 정보의 책임 구분이며 여섯 파일, 폴더의 필수 생성 목록이 아니다. 초기 채움 범위의 세 대안과 채택 범위는 [ADR 0014 — 「이번에 확인할 범위」](../../decisions/knowledge/0014-features.md)에 둔다.

### 복원할 깊이와 완료 목표

11/08 사용자 재확인: 최종 WIKI는 기초 정보만 담는 안내서가 아니다. **합의한 대상 범위의 개발 과정과 결과, 선택에 이른 흐름을 근거가 허용하는 수준까지 상세히 복원**하고 요구, 결정, 구조, 계약, 검증의 관계를 따라갈 수 있어야 한다. 여기서 최소는 필수 역할과 첫 준비의 범위이며 최종 지식의 깊이를 낮추는 조건이 아니다.

해당 범위에서 문제/요구와 제약, 검토한 대안과 선택 이유, 실제 구현 변화, 시험, 관측 결과, 실패, 한계, 이후 변경을 연결한다. 기록에서 확인할 수 있는 주요 전환, 기각, 번복을 최신 결론 하나로 지우지 않는다. 원본을 보존하면서 관련 변경들을 의미 있는 흐름으로 묶는다. 모든 코드 줄, 커밋 본문, 로그를 WIKI에 복사하는 것은 이 목표와 다르다.

사실, 근거를 연결한 추론, 확인 불가능한 내용은 구분한다. 추론에는 근거와 다른 해석 가능성, 확인할 점을 남기며 실제 과거 의도나 채택된 ADR처럼 쓰지 않는다. 새로 복원한 문서의 작성 시점과 확인된 과거 사건 시점도 구별한다. 없는 자료에서 오차 없는 과거 의도를 보장할 수는 없다. 자료가 소실된 경우 조사한 범위와 복원 한계를 명시하고, 실제 미처리를 자료 부재로 숨기지 않는다.

다음 세 범위는 각각 결정한다.

| 구분 | 기준 |
| --- | --- |
| 최종 보존할 지식 | 선택한 대상, 허용한 이력의 상세 사실, 판단 흐름과 출처, 관계. 토큰 때문에 근거 있는 중요한 내용을 삭제하지 않음 |
| 한 번에 복원할 단위 | 기능, 결정, 변경 흐름과 필요한 의존을 묶어 분할. 전체 요청의 나머지도 처리 목록에 유지 |
| 한 요청에서 읽을 문맥 | 짧은 진입 안내에서 관련 상세, 결정, 계약, 근거로 확장. WIKI 전체를 매번 입력하지 않음 |

채택한 B는 **범위별 상세 복원**을 기본 진행 방식으로 삼는다. 기초 정보를 첫 단계로 만들되, 상세 복원을 나중에 우연히 해당 코드를 수정할 때만 할 일로 남기지 않는다. 합의한 복원 범위마다 필요한 정보와 관계를 점검하고 전체 요청에는 단위 사이 대조까지 포함한다. 구체적인 복원 대상, 순서, 검토 예산은 실제 작업 시작 전에 확인한다.

### 기본으로 제공할 역할

| 역할 | 현재 기존 시험 프로젝트의 위치 | 기본 제공할 정보, 절차 후보 | 읽기, 갱신 조건 |
| --- | --- | --- | --- |
| 진입, 탐색 | AGENTS, docs/경로 README, 문서 관련 gate | 작업 규칙과 관련 정보의 위치, 역할, 사용 조건을 짧게 안내 | 적용 지침에서 시작해 해당 작업 경로만 탐색. 역할, 경로, 규칙이 바뀔 때 연결 갱신 |
| 요구, 계약 | REQUIREMENTS, guides, contract, 관련 ADR | 채택 요구와 금지 조건, 변경 대상의 기대 동작, 완료 기준. 관측한 현재 구현과 구분 | 제품 동작, 외부 계약을 판단/변경할 때 관련 부분 확인. 합의된 의미 변경만 현재 기준에 반영 |
| 구조, 실행 | README, 빌드, 테스트 설정, 검증 matrix, 설명 문서 | 모듈/주요 경계, 실행, 검사 방법과 환경 조건, 예외의 근거 위치 | 대상 코드, 검증 범위를 정할 때 사용. 경로/빌드/검사 설정 변경 시 관련 안내를 대조 |
| 논의, 결정 | discussions, decisions | 미채택 대안, 장단점과 실제 채택 이유, 상태, 근거를 구별해 기록 | 기존 판단에 영향이 있거나 중요한 선택을 할 때 관련 기록만 확인. 새 결정, 수정 시 이력 보존 |
| 실패, 대응 | runbook, troubleshooting 진입, 실행 결과 | 증상, 재현 조건, 확인 원인, 처리, 실제 재검증을 연결. 재사용할 대응 지식만 정리 | 관련 실패, 반복 위험일 때 읽기. 새 유효한 대응이 생기면 같은 주제에 통합. 단발 실패도 실행 상태에서는 보존 |
| 진행, 검증 | followup active, scope, 검증 결과, 로그 | 목표, 제약, 변경 범위, 실패/미완료 검사, 다음 행동과 증거 위치 | 장기 작업, 상태 전환, 재개 때 대조. 현재 상태와 과거 원시 결과의 역할을 분리 |

`explainers` 확장을 설치하지 않아도 작업에 필요한 구조, 경계 정보는 기본에서 찾을 수 있어야 한다. 선택 확장은 긴 해설, 도식, 학습 문서의 작성 흐름을 더하는 것이며 기본 구조 파악 능력을 제거하는 옵션이 아니다. `learn`, 커밋 보조의 선택 분류와 로컬 도입 미확정 상태는 유지한다.

여섯 역할은 하네스가 사용하는 정보의 구분이지 전부 WIKI 저장소에 넣는다는 뜻이 아니다. 진행, 검증의 현재 상태와 임시 실행 기록은 [로컬 상태 — 「작업 상태와 Git 제외」](../workflow/recovery.md)에 두고, WIKI에는 검토를 마친 요구, 결정, 재사용할 지식과 필요한 근거 연결을 남긴다.

기계 조회에서는 이 묶음 안의 요구/계약, 구조/실행, 논의/결정을 필요한 만큼 구별한다. [조회 역할 후보 — 「조회할 역할」](map.md)는 같은 정보를 다른 파일로 복제하거나 현재 active를 공유 WIKI에 넣는 변경이 아니다. 역할 이름, 공통/기능 범위, 절 선택의 상세는 위치표 명세 한 곳에서 관리한다.

WIKI가 명령, 설정, 검증 결과의 두 번째 원본이 되어서는 안 된다. 빌드 설정은 원래 도구가, 실행 사실은 결과 기록이 소유하고, WIKI는 해석, 정책, 연결을 담당한다. 표의 경로는 현행 위치 예시다. 다른 프로젝트에서 같은 역할을 기존 README의 절로 제공하면 그곳에 연결하며 고정 디렉토리로 이동시키지 않는다.

### 요구사항과 다른 정보의 경계

요구사항에는 **사용자가 기대하는 동작, 반드시 지킬 조건, 완료를 확인할 기준**을 담는다. 누가 어떤 조건에서 무엇을 할 수 있어야 하는지, 무엇은 허용하지 않는지와 채택 근거를 확인한다. 관련 있을 때 권한, 데이터 보존, 오류 처리, 성능 같은 조건도 포함하되, 코드에 임시로 들어 있는 값이나 근거 없는 목표 수치를 요구사항으로 만들지 않는다. 이 목록은 검토 관점이며 모든 기능에 빈 항목을 만들어 넣을 템플릿이 아니다.

현재 코드의 처리 순서, 경로, 관측한 제한은 현재 구조/동작 설명에 둔다. API, 이벤트, DB의 상세 형식은 계약의 원본을 연결하고, 판단에 필요한 의미와 불변 조건만 설명한다. 예를 들어 “중복 요청이 와도 처리는 한 번만”은 요구이고, 요청 식별자와 중복 응답 형식은 계약이며, 현재 구현이 이를 실제로 지키는지는 검증할 사실이다. 이 예시는 특정 프로젝트의 구현을 확인한 결과가 아니다.

요구, 현재 동작, 계약의 내용 구성은 [채택한 기본 구성 — 「비교와 추천」](documents.md)을 따르며 고정 파일, 상세 템플릿은 후속이다. 지금은 내용의 책임을 나누며, 같은 설명을 REQUIREMENTS, 구조 문서, ADR에 반복하지 않는다. 기존 채택 근거가 없는 요구 후보는 확인 전 상태를 유지한다. 실제 분석에서의 사실, 정책, 과거 이유, 추정 구분과 품질 판정은 [품질 기준](../../discussions/knowledge/reconstruction.md)을 따른다.

### 현재 구조에서 달라질 점

| 현재 확인된 방식 | 수정 후보 | 확인해야 할 변화 |
| --- | --- | --- |
| docs 경로와 프로젝트 전용 matrix에 문서, 검사 관계가 들어 있음 | 역할과 프로젝트 원문 위치를 연결하고 공통 절차에서 소비 | 문서 이름을 바꿔도 관련 계약, 검사가 빠지지 않고 원문이 유지됨 |
| 일부 문서 작업에서 고정 prompts/topic/worklog를 요구 | 필요한 판단, 진행 역할을 실제 소유 위치에 기록 | 선택하지 않은 기록 경로를 요구하지 않으며 중요한 판단/실패는 남음 |
| 조건부 읽기는 지침과 메인 판단에 의존 | 필요한 문맥의 선택, 충돌 처리와 검증 사례를 함께 정의 | 필요한 문서 누락과 불필요한 읽기를 모두 관측. 강제 실행이 구현됐다고 주장하지 않음 |
| 기존 감사에 복구, 검증 결과의 의미 결함이 있음 | WIKI의 상태 요약과 실제 검사/복구 계약을 구분해 연결 | 요약을 썼다는 이유로 실패 해결, 자동 재개, quota 사전 저장 성공으로 보지 않음 |

현행 근거는 [구조 감사 — 「설계 의도와 현재 구현의 관계」](../../discussions/architecture/baseline-audit.md)와 [기준 구현의 관측 (문서 운영 기준)](../../discussions/architecture/baseline-audit.md)이다. 이번에는 원래 코드를 재시험하거나 결함을 수정하지 않았다.

### 최초 준비와 점진적 채움

채택한 초기 범위 B는 **기초 파악 → 합의 범위의 상세 복원 → 관계, 누락 대조**를 단위별로 수행하는 방식이다. 설치는 탐색, 기록, 초기화 능력을 제공하고, 내용 분석은 선택한 범위와 예산에서 실행한다. 설치 직후 숨은 AI 호출, 전체 커밋 분석을 시작하지 않는다. 기초 파악을 끝냈다는 이유로 상세 복원 작업을 완료하지 않는다. [기존, 빈 WIKI 사례 — 「기존 문서 채택과 새 문서 복원」](wiki.md#%EA%B8%B0%EC%A1%B4%20%EB%AC%B8%EC%84%9C%20%EC%B1%84%ED%83%9D%EA%B3%BC%20%EC%83%88%20%EB%AC%B8%EC%84%9C%20%EB%B3%B5%EC%9B%90)에 따라 유효한 원문은 재사용하고, 부족한 내용만 작성한다.

최초에 확인할 정보는 아래 다섯 묶음이다. 이미 있는 유효한 내용은 연결하고 부족한 부분만 후보로 작성한다. 이는 다섯 파일이나 폴더를 생성하라는 목록이 아니다.

| 정보 | 기초 파악에서 확보할 수준 | 기초 파악에서 다루지 않는 내용과 후속 처리 |
| --- | --- | --- |
| 대상과 목적 | 어느 프로젝트의 어떤 기능/범위를 다루는지, 확인된 목적과 제외 범위 | 요청하지 않은 다른 제품의 분석, 근거 없는 사업 목적 추정 |
| 지침과 문서 위치 | 적용할 작업 규칙, 기존 요구, 계약, 결정 등 역할별 위치. 없거나 아직 못 찾은 역할은 구별 | 관련 ADR, 기각/번복은 상세 단위에서 확인. 기존 원문의 일괄 재작성은 하지 않음 |
| 주요 구조와 실행 | 주요 모듈, 외부 시스템의 경계, 빌드/실행/검사 방법의 원본, 환경 조건과 확정 예외 | 단위별 API, 데이터, 실패 경로의 상세는 후속 복원에 포함. 실제 기동은 별도 검증 범위 |
| 이미 확인된 요구와 제약 | 공통으로 지킬 현재 정책과 첫 작업에 직접 필요한 요구, 계약의 근거 | 선택 범위의 상세 요구, 과거 흐름은 단위별로 복원. 전체 요청에서 다른 기능을 누락시키지 않음 |
| 확인 범위와 공백 | 읽은 자료, 기준 버전/미커밋 상태, 아직 안 본 범위, 충돌, 필요한 확인, 다음 대상 | 재개 로그 전체의 WIKI 복사, 빈칸을 채우기 위한 추측 |

명령과 테스트 위치를 발견했어도 실제 실행 여부, 결과는 따로 표시한다. 단순히 문서가 없다는 것, 아직 조사하지 않았다는 것, 원문들이 충돌한다는 것을 모두 같은 “없음”으로 표시하지 않는다. 출처는 문서/기능 단위에서 다시 찾을 수 있게 연결하고 모든 문장에 같은 메타데이터를 반복하지 않는다.

세 완료 판단을 구분한다.

1. **설치, 연결 확인:** 지원 환경에서 필요한 경로, 지침, 문서에 접근하며 보호 원문에 허용 밖 차이가 없다. 초기 분석을 했다면 위 다섯 묶음의 확인 결과와 남은 공백이 보인다. 파일 배치, 기초 정보 작성만으로 개발 준비나 전체 복원 완료가 되지는 않는다.
2. **해당 작업의 준비:** 바꿀 동작과 지킬 제약, 영향받는 호출/데이터 경계, 확인할 검사와 확정 예외가 설명된다. 변경에 중요한 미해결 질문이 있으면 그 변경을 보류한다. 과거 선택 이유가 없다는 것만으로 관련 없는 작업까지 막지 않는다. 읽기 전용 탐색은 필요한 공백을 확인하기 위해 진행할 수 있다.
3. **WIKI의 범위별 복원:** 합의한 범위의 상세 내용, 출처, 관계, 보존을 [범위별 완료 판정](wiki.md#%EB%B2%94%EC%9C%84%EB%B3%84%20%EC%99%84%EB%A3%8C%20%ED%8C%90%EC%A0%95)으로 확인한다. 후보 작성, 검토, 반영과 전체 요청의 완료를 구분하며, 자료 부재와 실제 미처리를 같은 완료로 처리하지 않는다.

예를 들어 이벤트 처리 수정을 준비한다면 중복, 실패 시 기대 동작, 발행/소비 경계와 관련 검사까지 필요하다. 소비 코드를 보지 못했다면 그 제한을 표시하고 해당 동작의 확인을 이어간다. 무관한 화면이나 모든 과거 커밋의 복원을 먼저 끝낼 필요는 없다. 의존 자료를 읽는 범위와 그 기능의 WIKI까지 작성하는 범위는 구분한다.

전체 프로젝트 복원을 요청한 경우에도 B는 유효하다. [합의한 전체 범위를 단위로 나눠 — 「범위 선택」](../../discussions/knowledge/reconstruction.md) 처리하고 마지막에 단위 사이 계약, 용어, 누락을 대조한다. 사용자가 승인한 전체 작업을 첫 단위만 채운 뒤 임의로 축소하지 않는다. 이 기준은 배포 모듈의 프로젝트 분석에 관한 것이며 개인 기술 검토 자료 검토의 절차를 제품 기능으로 가져오는 것은 아니다.

초기 탐색, 사람의 검토, 최신성 관리에는 비용이 든다. 첫 작업의 영향이 넓거나 숨은 의존이 발견되면 필요한 조사도 커진다. 범위, 비용 조건을 넘는 확장은 실행 전에 협의한다. 정량 절감률, 고정 문서 수, 준비 시간을 아직 주장할 수 없다.

### 상세 지식을 찾아 읽는 연결

진입 안내에는 해당 문서가 답하는 질문, 적용 범위와 위치를 짧게 두고, 상세 본문에는 관련 요구, 판단, 계약, 구현, 검증 근거를 연결한다. 예를 들어 재시도 정책을 바꾸는 작업은 현재 정책, 그 정책을 고른 이유, 중복 처리 계약, 실패 후 검증 결과를 함께 확인해야 한다. 최신 정책과 폐기된 결정을 구별하고 같은 이름의 다른 기능으로 잘못 안내하지 않아야 한다.

링크 수를 늘리는 것만으로 누락 방지가 되지 않는다. 해당 작업에서 확인해야 할 관계와 참고 관계를 구별하고, 작업 유형, 영향 범위에 따라 필수 근거가 실제로 읽혔는지 대조한다. 관계의 의미는 소유 문서에 두고, 진입 위치는 아래 연결에서 찾는다. 문서 분할, 읽기/갱신 조건은 [구성 초안 — 「읽기 경로」](documents.md)이 소유한다.

이 방식의 목표는 상세 지식을 보존하면서 반복 작업의 불필요한 읽기를 줄이는 것이다. 최초 복원, 관계 작성, 의미 검토 비용까지 사라지는 것은 아니다. [품질, 탐색 평가 — 「품질 기준」](../../discussions/knowledge/reconstruction.md)에서는 필요한 근거의 도달/내용 정확성을 먼저 확인하고, 같은 품질에서 복원, 사용, 갱신 비용을 각각 측정한다. 적게 읽었다는 이유만으로 성공 처리하지 않는다.

### 역할별 위치 연결

11/09에 비교한 역할과 경로의 연결 방식이다. 이 표의 B를 JSON 위치표, 명시적 등록, 선택 조회 구성으로 채택했다. 다른 ADR의 B안이나 최소 WIKI의 나머지 후보를 일괄 채택하지 않는다.

| 방식 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 목차와 본문 링크 | README에서 사람이 읽듯 관련 문서를 찾음 | 기존 문서에 가깝고 별도 설정이 적음 | 자동 절차가 같은 이름의 문서, 여러 후보를 고를 때 재탐색과 모호함이 남음 |
| B. 역할별 위치와 본문 링크 | 작은 위치표로 역할, 범위의 진입 원본을 찾고 상세 관계는 본문에서 따라감 | 원본을 유지하며 반복 탐색, 공통 코드의 경로 하드코딩을 줄일 수 있음 | 위치표 갱신과 경로 검사에 더해 원문 내용의 일치 여부도 확인해야 함 |
| C. 전체 색인, 관계 검색 | 모든 문서/코드를 색인하고 검색으로 관련 내용을 찾음 | 넓고 다양한 자료의 탐색을 보조 | 수집, 갱신, 검색 누락 평가 비용. 검색 결과만으로 필수 계약 도달을 보장할 수 없음 |

**B를 채택**했다. 자동 실행이 사용할 명시적 진입점과 사람이 유지보수할 본문을 함께 확보할 수 있기 때문이다. A는 상세 설명의 탐색 방식으로 남고, C는 규모, 실측 이득이 있을 때의 보조 후보로 둔다. 토큰 절감은 아직 측정하지 않았다.

위치표에 필요한 것은 **정보 역할, 적용 범위, 원본 위치**다. 원본 위치는 등록된 코드/WIKI 등 어느 원본의 경로인지 구별하고 필요한 절까지 지정한다. 예를 들어 ‘요구 / 상품 등록 / WIKI의 기존 상품 문서 해당 절’, ‘API 계약 / 상품 등록 / 코드의 기존 명세’를 찾게 한다. 이는 설명용 예시이며 특정 파일, YAML 키를 고정한 것은 아니다.

- 공통 요구와 기능 요구가 함께 적용되면 둘 다 찾는다. 같은 범위, 역할에 상충하는 후보가 여럿이면 파일명, 최신 날짜로 하나를 고르지 않는다. 하나의 문서가 여러 역할을 맡거나 여러 자료가 함께 한 역할을 충족하는 경우도 허용한다.
- 위치 원본은 하나만 둔다. README, AGENTS, skill, matrix에는 그 진입점을 연결하며 같은 표를 따로 유지하지 않는다. 채택한 JSON 설정에서 조회하고, 해석 결과는 다시 만들 수 있는 파생 자료로 구별한다.
- 모든 클래스, 커밋, 문장에 매핑 행을 만들지 않는다. 기능별 진입과 공통 계약을 연결하고, 구체 출처, 의존 관계는 해당 소유 문서에서 설명한다. 경로 이동 시에는 유입 참조와 소비 지점을 함께 대조한다.
- 호스트의 절대 경로, 권한은 로컬 설정, 조사 입력의 코드/WIKI 버전, 미커밋 상태는 실행 기록이 소유한다. WIKI에는 관련 기준점과 출처만 남기며 현재 파일 링크와 과거 근거의 고정 버전을 구별한다. 비공개 자료의 경로, 링크도 공개해도 되는지 확인한다.

예컨대 요구 문서를 찾았다는 결과는 ‘그 위치를 읽을 수 있음’까지만 뜻한다. 그 내용이 현재 승인된 요구인지, 관련 코드/계약과 맞는지는 별도 분석이다. 잘못된 프로젝트, 없는 원본, 깨진 필수 연결은 빈 문서나 다른 사본으로 조용히 대체하지 않는다. [프로젝트 WIKI 연결](wiki.md#%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20WIKI%20%EC%97%B0%EA%B2%B0)의 루트, 권한, 기존 문서 보호 조건을 함께 적용한다.

11/09 질문에서 말한 ‘의미 검토’는 이 **원문 간 내용 대조**를 뜻한다. 일반 코드는 형식, 경로를 검사하고, AI는 요구, 코드, 명세, 결정 기록의 내용과 근거를 비교한다. 근거로 확정할 수 없는 중요한 정책, 의도, 충돌은 차이와 선택지를 사용자에게 제시한다. 모든 문서를 사용자가 다시 읽거나 통상적인 사실 갱신마다 승인하는 절차를 뜻하지 않는다. 품질 평가용 기대 정보의 사람 검토와 일상 작업의 확인 요청도 구분한다.

### 위치표를 저장하는 방식

채택한 구성은 **작은 JSON 위치표 + Markdown 본문**이다. 위치표에는 역할, 범위, 원본 위치만 연결하고 상세 지식은 본문에 둔다. 실제 필드와 조회/갱신 계약은 [위치표 명세](map.md)가 소유한다.

위치표는 프로젝트가 소유하는 연결 자료다. 코드가 공개되고 WIKI가 비공개라면 연결표도 공개 범위를 확인하며, 실제 호스트 절대 경로, 권한은 로컬 설정으로 분리한다. Markdown/JSON/TOML의 장단점과 선택 근거는 [형식 비교 — 「위치표를 저장하는 방식」](../../discussions/history/map.md)에 보존했다.

### 사람이 읽고 관리하는 위치표

정상 유지보수는 AI와 일반 도구가 수행하고 사람이 필요할 때 이해, 수정할 수 있게 한다. JSON은 AI의 내부 사고나 버려도 되는 캐시가 아니다. 본문, 목차는 JSON 도구 없이 읽을 수 있어야 하며, 위치표에는 필드 설명, 오류 위치, 좁은 변경 내역을 제공한다. 유효한 직접 편집을 자동으로 되돌리지 않는다.

저장 크기, 실제 모델 입력, 변경 범위는 다르다. 관련 결과만 조회해 전달하고 전체 설정을 매번 문맥에 넣지 않는다. 형식 검사와 내용의 의미 검토는 구별하며 총토큰, 재탐색, 갱신 비용의 우위는 아직 측정하지 않았다. 상세 판단은 [관리 기준 비교 — 「사람이 읽고 관리하는 위치표」](../../discussions/history/map.md)에 남겼다.

### 프로젝트 규모와 위치표 분리

첫 범위부터 단일 파일과 필요한 기능/흐름별 한 단계 분리를 지원한다. 작으면 단일 파일로 두고, 독립적인 경계, 담당, 변경이 있으면 나눈다. 역할마다 파일을 만들거나 줄 수만으로 자르지 않는다. 서비스/기술 검토라는 이름만으로 규모를 정하지 않는다.

공통 연결은 한 곳에 두고 하위 파일 내용을 루트에 복제하지 않는다. 실제 구조와 예시는 [저장 형식](map.md), 비교 대안은 [분리 검토 — 「프로젝트 규모와 위치표 분리」](../../discussions/history/map.md)에 있다. 기존 문서의 자동 이동, 강제 분할이나 빈 폴더 일괄 생성은 하지 않는다.

### 분할 파일을 찾는 방식

루트의 **명시적 파일 목록 + 도구의 등록 갱신**을 사용한다. 파일 추가/이동 때 하위 파일과 목록을 같은 변경으로 대조한다. 폴더에 존재한다는 이유로 초안을 자동 포함하지 않으며, 미등록 후보는 알리되 조용히 채택하지 않는다. 재귀 include, 계층 상속, 원격 자동 수집은 첫 범위에서 제외한다.

AI는 의미와 범위를 판단하고 도구가 조회, 검사, 허용된 갱신을 맡는다. 목록/하위 파일의 부분 반영과 누락을 발견해야 하며 쓰기 두 번을 원자적 처리라고 보장하지 않는다. 상세 계약은 [등록과 갱신](map.md), 폴더 탐색, 계층 목록과의 예시는 [발견 방식 비교 — 「분할 파일을 찾는 방식」](../../discussions/history/map.md)에 보존했다.

### 위치표를 사용하는 절차

설정 읽기, 형식/경로 검사는 일반 코드가 처리한다. AI는 처음 자료의 역할을 판별하거나 실제 내용을 비교할 때 사용한다. 모델에 전달한 경로 목록, 본문은 문맥 비용이 있으므로 ‘설정을 읽는 데 AI 호출이 없다’를 ‘전체 작업의 토큰 사용이 없다’로 표현하지 않는다.

| 시점, 입력 | 처리 책임 | 결과와 다음 연결 |
| --- | --- | --- |
| 최초 설정: 사용자가 정한 프로젝트/WIKI | 도구가 접근, 기존 자료 위치를 찾고 AI가 필요한 범위에서 역할 후보를 제안 | 확인된 연결과 미확인 후보 구별. 애매한 역할, 기존 연결 충돌은 사용자 확인 후 설정 반영 |
| 일상 읽기: 메인이 정한 정보 역할, 작업 범위 | 도구가 위치표에서 공통/관련 기능의 진입점을 찾고 형식, 경로를 검사 | 관련 위치와 누락/충돌 반환. 본문은 필요한 만큼 읽으며 모든 연결을 자동 확장하지 않음 |
| 내용 대조: 선택한 원문과 기준점 | AI가 요구, 현재 동작, 계약, 결정, 결과를 비교 | 근거 있는 후보, 차이, 미확인 반환. 중요한 미해결 의도는 질문하고 원문을 자동 정답으로 삼지 않음 |
| 반영: 허용 변경, 후보와 현재 원문 | 도구가 입력 변화, 변경 범위를 확인하고 합의한 범위에서 반영 | 관련 연결도 함께 확인. 변경 후 관측과 남은 실패를 기록하며 기존 보호 원문 보존 |
| 경로 변경, 재개: 기존 연결/기준점과 현재 파일 | 도구가 위치, 입력 차이를 대조하고 AI가 내용 변경의 영향을 재검토 | 영향 연결/후보만 보정. 이전 결과를 그대로 덮어쓰거나 누락된 원본을 새 문서로 대체하지 않음 |

메인은 기존 작업 범위와 문서 관계로 필요한 역할을 정한다. 무엇이 관련되는지 불명확하면 좁은 추가 탐색으로 확인하며, 위치표 자체가 모든 작업의 영향 범위를 알아낸다고 가정하지 않는다. skill은 이 공통 연결 절차를 사용하고 특정 프로젝트의 경로를 따로 하드코딩하지 않는다. hook은 상태 확인 신호를 전달하며 WIKI 내용의 정답을 판정하는 역할을 맡기지 않는다. 실제 도구별 연결과 복구 저장 형식은 후속 명세다.

형식과 경로 검사에서는 미지원 역할/원본, 같은 키의 중복, 빠진 필수 값, 존재하지 않거나 허용 원본 밖으로 벗어난 경로, 모호한 절을 조용히 보정하지 않는다. 서로 다른 자료가 같은 역할을 함께 맡는 정상 사례와 충돌 후보는 구별한다. 심볼릭 링크도 실제 대상이 허용 범위인지 확인하며 다른 원본이 필요하면 먼저 등록, 접근 범위를 확인한다. 실패 시 기존 설정과 문서는 유지하고, 영향받는 작업만 보류한다.

### 작업 중 읽기와 갱신

요청 → scope, 위험에 필요한 정보 선택 → 관련 원문/근거 확인 → 실행, 검증 → 영향 문서와 재개 상태 반영 순서다. 이는 매 요청의 고정 전체 파이프라인이 아니다.

- 저장소 정보가 필요 없는 질문에는 WIKI 탐색, 작성, 검사를 강제하지 않는다. 관련 문서를 읽은 뒤 작업에 필요한 근거가 충분하면 무관한 링크, 과거 기록으로 확장하지 않는다.
- 요구/계약의 채택 상태, 관측한 코드, 테스트, 문서 위치와 revision, 미커밋 변경 여부, 확인 범위를 구별한다. 출처가 가리키는 내용과 주장이 실제로 맞는지도 대조한다. 모든 문장에 메타데이터를 복제하거나 날짜만으로 유효성을 판정하지 않는다.
- 이미 읽은 원문과 전제가 그대로면 재사용한다. 관련 코드, 규칙, 경로 변경, 충돌 신호, 재개로 이해를 신뢰하기 어려운 경우에 필요한 범위만 다시 확인한다. 구체 감지/저장 방식은 후속 구현 설계다.
- 설치, 재분석에서 보호 원문은 별도 변경 후보로 다룬다. 이후 개발에서는 승인된 작업 범위와 프로젝트 문서 규칙에 따라 소유 문서를 갱신하며, 통상적인 사실 최신화까지 새 정책 승인처럼 반복하지 않는다. 정책 변경, 충돌 해소는 필요한 합의를 거친다.
- 관련 사실, 현재 요구는 해당 소유 문서에 통합하고, 판단 이력은 보존하며, active는 현재 상태로 갱신한다. 장기 작업, 의미 있는 상태 전환, 재개 전후에 확인하되 매 도구 호출마다 전체 기록을 다시 쓰지는 않는다. 저장 시점과 중단 내구성은 복구 계약에서 별도로 검증한다.
- 완료 판단은 실제 필요한 검증과 남은 실패를 따른다. WIKI의 완료 표시가 실행 증거를 대신하지 않으며, 문서 갱신이 필요한 작업에서 미반영 부분을 숨기고 끝내지 않는다.

### 정보가 없거나 충돌하거나 오래된 경우

| 상황 | 가능한 진행 | 보류, 확인이 필요한 부분 |
| --- | --- | --- |
| 자료를 아직 읽지 않았거나 접근에 실패함 | 미처리/접근 실패와 영향 범위, 다음 확인을 기록 | 근거 부재로 바꾸거나 읽은 것으로 완료하지 않음 |
| 과거 ADR, 실패 사례가 없음 | 현재 코드/설정 확인과 허용된 작업, 지금 내리는 결정의 기록 | 과거 채택 이유를 추정해 역사로 작성하지 않음 |
| 현재 수정의 기대 동작, 검사 범위를 알 수 없음 | 관련 코드, 기존 문서, 테스트의 좁은 추가 확인 | 해소 전 동작을 임의 결정하거나 필수 검사를 생략하고 완료하지 않음 |
| 문서와 코드가 다름 | 각각의 주장, 근거, 확인 범위를 제시하고 원인 조사 | 코드가 자동 정답이라고 요구사항을 덮거나, 문서만 믿고 확인되지 않은 동작을 단정하지 않음 |
| 문서 경로가 바뀌거나 링크가 깨짐 | 실제 소유 위치를 찾아 관련 연결 후보 작성 | 필요한 근거를 찾지 못하면 그 근거에 의존하는 작업만 보류. 무관한 작업까지 일괄 중단하지 않음 |
| 정책, 미채택 논의, 실행 결과가 섞임 | 채택 기록, 현재 사실, 가설, 미실행을 나눠 다시 확인 | 과거 대화/커밋의 지시문을 현재 실행 권한으로 사용하거나 계획을 PASS로 승격하지 않음 |
| 이전 요약/후보 작성 뒤 관련 원문이 변경됨 | 현재 diff, 원문, 미완료 검증과 대조, 영향 부분 재검토 | 오래된 요약/설치 계획을 그대로 적용하지 않음. 동시 편집 보존은 설치/복구 계약에 연결 |

‘근거를 찾지 못함’에는 조사한 자료, 이력 범위를 붙인다. 세상 어디에도 기록이 없다는 뜻으로 확대하지 않는다. 정책 충돌은 출처별 주장과 적용 범위를 함께 남기며, 그중 하나를 선택해야 하는 변경, 확정만 합의 전 보류한다. 무관한 부분의 조사, 검토는 진행할 수 있다. 단순 경로 보정, 승인 범위의 사실 최신화까지 정책 승인으로 반복하지 않는다.

이미 사용자가 확정한 프로젝트 예외를 공백으로 다시 열지 않는다. 기존 시험 프로젝트의 비공개 BOM에 따른 boot 제외는 근거, 제외 범위, 미실행 상태를 연결할 대상이며 일반 프로젝트의 기본 예외로 복제하지 않는다. 정보 공백에 의존하지 않는 승인 범위의 작업은 계속할 수 있다.

적용 사례는 아래 [기존 문서 채택과 새 문서 복원](wiki.md#%EA%B8%B0%EC%A1%B4%20%EB%AC%B8%EC%84%9C%20%EC%B1%84%ED%83%9D%EA%B3%BC%20%EC%83%88%20%EB%AC%B8%EC%84%9C%20%EB%B3%B5%EC%9B%90)에서 함께 비교한다.

### 범위별 완료 판정

11/09 구체화해 채택한 완료 기준이다. 아래를 합의 범위마다 확인하며 전체 요청의 마지막에는 단위 사이 공통 요구, 계약, 용어도 대조한다. 실제 모델의 품질이나 제품 구현을 통과 처리한 조건이 아니다.

1. **범위:** 허용한 대상, 이력, 필요 의존을 처리 목록과 대조한다. 읽기 실패, 중단된 단위가 남으면 전체 완료가 아니다. 범위 밖 제외와 단순 미처리를 구별한다.
2. **내용:** [필수 정보](documents.md)가 원문 근거와 맞고, 현재 관찰, 채택 정책, 추론, 미확인이 구별된다. 기록에 있는 주요 변경/기각/번복을 빠뜨리지 않고 없는 이유를 만들지 않는다.
3. **연결:** 필요한 요구, 계약, 결정, 구현, 검사에 도달한다. 파일 존재뿐 아니라 대표 작업에서 내용, 버전, 적용 범위가 맞는지 검토한다. 모든 링크를 매번 재귀적으로 읽는 방식은 요구하지 않는다.
4. **판단:** 현재 기준을 정할 수 없게 하는 중요 충돌은 해결하거나 영향 범위를 보류한다. 자료 자체의 한계는 조사 완료와 지식 복원 불가를 따로 보고하고 수용 여부를 확인한다. 이미 합의한 범위의 사실 정리에 새 승인을 반복하지 않는다.
5. **보존, 반영:** 후보와 원문 차이, 허용 변경, 적용 직전 입력 변화를 대조한다. 허용 밖 변경, 기존 사용자 편집 유실, 비밀값 유입이 없고, 반영했다면 관련 목차, 연결도 맞아야 한다. 상세 적용/복원 수단은 [보존 설계](../../decisions/runtime/0011-preservation.md)에서 정한다.
6. **결과:** ‘후보 작성’, ‘검토 완료’, ‘반영 완료’ 중 실제 수행한 범위를 보고한다. 검사 미실행, 자료 한계, 남은 단위, 다음 행동을 함께 남기며, 한 단위의 완료를 전체 WIKI나 제품 테스트 PASS로 바꾸지 않는다.

문서 복원은 애플리케이션의 모든 결함을 고치는 작업이 아니다. 확인된 실패나 미실행 검사를 정확히 설명하고 근거, 영향, 한계를 연결할 수 있다. 다만 문서의 결론에 실행 결과가 꼭 필요하면 해당 검증이 남은 상태로 표시하고, 코드 관찰만으로 성공을 단정하지 않는다. 실제 검사의 범위와 프로젝트 예외는 검증 계약을 따른다.

예를 들어 과거 선택 이유가 허용 자료에 없다면 ‘현재 동작과 변경 이력은 확인, 당시 이유는 복원 불가’로 남길 수 있다. 이를 ‘모든 과거 의도 복원’이라고 보고하지 않는다. 반대로 소비자 코드를 아직 읽지 못해 주요 이벤트 계약이 불명확한 경우는 단순한 역사 자료 부재가 아니므로 해당 범위의 완료를 보류한다.

현재 후보를 모델이 스스로 빠짐없다고 평가하는 것만으로 닫지 않는다. 원문 목록, 차이, 링크의 기계 검사와 AI의 내용 대조를 함께 사용하며, 중요한 미해결 정책, 의도는 사용자에게 확인한다. 실제 품질 평가에서는 사람이 검토한 기대 내용으로 중요한 요구/결정, 필수 근거의 누락을 대조한다. 상세 평가 입력과 허용 기준은 [품질 비교 — 「품질 비교 방법」](../../discussions/knowledge/reconstruction.md)에서 실행 전에 확정한다. 이 기준은 일상 작업마다 전수 수동 검토를 요구하거나 미지의 사실까지 절대 누락 없음을 증명하는 규칙이 아니다.

### 근거와 검증 범위

- 11/08 추가 확인: [arc42의 요구 개요](https://docs.arc42.org/section-1/)는 짧은 요약과 기존 요구 문서 연결을, [맥락과 범위](https://docs.arc42.org/section-3/)는 시스템 경계와 외부 인터페이스의 설명을 제시한다. 초기 요약과 상세 원본을 구분하는 참고이며 arc42 전체 틀을 필수로 채택한 것은 아니다.
- [C4의 상세 수준 안내](https://c4model.com/diagrams)는 가치가 있는 수준을 선택하도록 한다. 이를 참고해 최초부터 모든 클래스, 코드 구조를 문서화하지 않는 안을 제안한다. 다섯 정보 묶음, 완료 조건은 이 모듈의 설계 판단이며 아래 자료가 그 효과를 검증하지는 않는다.
- [OpenAI AGENTS 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md): 시작 시 지침 발견, 조합을 설명한다. 일반 WIKI 링크의 자동 재귀 로딩을 보장하는 자료가 아니므로 이 설계의 탐색 절차와 실제 로드 확인은 따로 검증한다.
- [OpenAI best practices](https://learn.chatgpt.com/docs/learn/best-practices#make-guidance-reusable-with-agentsmd): 실용적이고 짧은 지침에 구조, 실행, 검사, 완료 기준을 담고 상세 문서로 연결하는 근거다. 모든 자료를 AGENTS에 합치라는 뜻으로 사용하지 않는다.
- [Anthropic context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents): 경량 참조와 필요 시 탐색, 외부 기록을 통한 지속성을 설명하며 탐색 비용의 절충도 다룬다. 이 역할 수나 파일 구조를 정답으로 증명하지 않는다.
- 11/08 재확인: 위 Anthropic 자료는 최소 문맥을 단순히 짧은 문맥과 동일시하지 않으며, 탐색 중 필요한 정보 누락, 불필요한 우회 가능성도 설명한다. 상세 복원의 깊이를 줄이는 근거로 쓰지 않는다. [Nygard의 ADR 원문](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)은 판단 맥락, 결과와 대체된 결정의 보존을 설명한다. 기록 없는 과거 의도를 확정할 수 있다는 근거는 아니다.
- 11/09 확인: [arc42의 요구 참조](https://docs.arc42.org/tips/1-5/)는 기존 ID, 안정된 링크로 요구를 식별하는 방식을 설명한다. [Diátaxis 참조 문서](https://diataxis.fr/reference/)는 사실 설명과 다른 문서 역할의 연결, 자동 생성 참조만으로 충분하지 않음을 다룬다. 이를 기존 원본 연결, 내용 검토의 근거로 삼되, 위치표 B와 완료 조건의 구체 형태, 효과는 이 모듈의 제안과 검증 대상이다.
- [Anthropic 장기 작업 사례](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents): 초기 환경, 진행 기록, 기능 검증을 나누는 참고 사례다. 사례의 전체 기능 목록 선작성, 매 세션 테스트/커밋을 이 모듈의 상시 절차로 복사하지 않는다.

여섯 역할과 초기 범위는 위 자료, 현행 연결, 사용자 목표를 결합한 설계 판단이다. [수용 후보 S-18~24 — 「최소 WIKI 수용 후보」](../../verification/acceptance.md)로 원문 보존, 필요 정보 확보, 거짓 확정 방지, 불필요 읽기, 재개를 확인할 계획이며 아직 실행하지 않았다. 첫 지원 버전의 실제 로드/호출, 문서 의미의 정확성, 토큰 효과는 별도 검증 대상이다.

## 프로젝트 WIKI 연결

11/05 연결 기준을 **등록한 프로젝트, 문서 루트와 정보 역할**로 구체화했다. Obsidian 사용 여부나 특정 파일명을 전제로 하지 않는다. 아래는 ADR 0004의 분석과 설정 연결안을 구체화한 추천으로, 파일명, 설정 형식, CLI, 설치 수단까지 채택한 명세는 아니다.

| 필요한 연결 정보 | 예시, 동작 | 소유 |
| --- | --- | --- |
| 프로젝트 식별, 코드 루트 | 어느 코드의 지식인지 구분하고 검사 명령의 실행 위치를 고정 | 식별은 프로젝트, 기기별 실제 경로는 호스트 |
| WIKI 루트 | 프로젝트 내부 docs 또는 외부 문서 폴더/저장소의 로컬 작업 사본 중 선택 | 사용자, 프로젝트가 선택, 외부 절대 경로는 호스트 |
| 문서 진입점, 역할별 위치 | 기존 문서 목차, 요구사항, 구조, 결정, 실패 대응의 상대 경로, 필요한 절 | 해당 프로젝트의 문서/연결 설정. 이름으로 추측한 후보와 확인된 매핑 구분 |
| 진행, 검증 상태의 저장 위치 | 작업 시작, 중단 후 재개에 필요한 실제 상태를 생성, 갱신 | 코드 작업 공간의 로컬 상태. WIKI, Git 추적 대상에서 분리하며 [작업 상태 계약 — 「작업 상태와 Git 제외」](../workflow/recovery.md) 적용 |

문서 내부 연결은 가능한 WIKI 루트 기준으로 해석하고, 호스트의 실제 경로와 공유 가능한 설정을 분리한다. 특정 사용자 계정 경로나 문서 이름/내용을 공통 배포물이나 다른 프로젝트의 기본값으로 넣지 않는다. `docs`도 기본 위치 후보일 뿐 모든 프로젝트에 강제하는 폴더명이 아니다. 공개 프로젝트에 넣을 설정에는 공개해도 되는 정보만 남기고 외부 WIKI의 민감한 위치, 인증은 호스트에서 관리한다.

첫 설정과 사용 흐름은 다음과 같이 추천한다.

1. **위치 선택:** 사용자가 프로젝트와 내부/외부 WIKI 위치를 지정한다. 설치기는 해당 범위의 접근, 기존 파일, 충돌을 확인한다. 외부 폴더를 임의 탐색해 선택하거나 문서를 먼저 옮기지 않는다.
2. **기존 자료 연결:** README, 요구사항, ADR 등의 후보를 찾고 역할별 위치를 제시한다. 경로/파일 존재는 기계적으로 확인하고, 내용 역할, 충돌은 필요한 범위의 분석과 확인으로 정한다. 애매한 후보가 여러 개면 확정하지 않는다. 기존 내용은 보호한다.
3. **진입 연결:** 지원 AI 도구가 실제 인식하는 프로젝트 지침, skill/hook 위치에 필요한 연결을 둔다. 예를 들어 Codex의 루트 AGENTS를 vault로 옮기는 대신, 기존 지침을 보존하며 문서 진입점과 공통 절차를 연결한다. 외부 WIKI의 실제 경로, 접근 권한은 별도로 해결한다. 모델이 필요한 문서를 읽는지까지 확인한다.
4. **없는 지식의 초기화:** 문서가 없으면 합의한 최소 진입 구조를 만들고, 사용자가 정한 범위에서 AI가 코드, 테스트, 허용한 이력을 분석해 문서 후보를 작성한다. 과거 결정과 미래 요구를 코드에서 자동 확정하지 않는다. 설치, 파일 생성과 의미 분석의 완료를 구분한다.
5. **일상 사용과 재개:** 요청에 필요한 역할만 따라 읽고 갱신한다. 새 장기 작업의 상태는 그때 생성하며, 최초 도입에 과거 작업 기록의 존재를 요구하지 않는다. 이미 진행 중인 상태는 보호하고 실제 코드, 문서, 검증 상태와 대조한다. 중요한 정보가 없으면 해당 작업을 보류하고 필요한 탐색을 진행한다.
6. **위치 변경, 재연결:** 새 경로를 입력받아 프로젝트/문서 식별, 연결, 권한을 확인하고 호스트 매핑을 갱신한다. 파일 이동, 링크 보정, Obsidian 등록은 구분해 검증한다. 같은 프로젝트의 여러 사본이나 누락된 원본을 조용히 새 문서로 대체하지 않는다.

설치 도구는 위치 등록, 구조/연결 점검, 변경 미리보기, 지원 도구의 진입 배치, 재연결을 자동화하고, AI는 선택한 범위의 내용 분석, 후보 작성에 사용한다. 불확실한 역할, 정책과 기존 파일 충돌은 사용자 판단으로 남긴다. 초기 수동 연결은 공통 계약을 검증하는 단계이며 최종 자동 분석 목표를 없애지 않는다. 대안, 장단점은 [ADR 0004 — 「비교한 방안」](../../decisions/architecture/0004-portability.md)의 수동 설정 / 분석 후 검증된 연결 / 프로젝트별 전용 생성 비교를 따른다.

입력 UI는 최초 대화형 안내와 이후 항목별 변경 명령이 같은 설정 검증, 저장을 사용하는 안을 추천한다. 이는 사용자 경로 입력을 편리하게 만드는 층이며 AI의 문서 역할 판단, 내용 복원을 대신하지 않는다. 여러 프로젝트의 연결을 분리하고, 기존 설정, 문서는 실패나 취소 시 보존한다. 설정 갱신과 파일 이전은 구분한다. 비교 근거와 개인 적용의 세부 절차는 [저장 검토](../../evidence/environment-observations.md)에 있다.

첫 배포의 Windows 외부 WIKI는 Windows 도구가 직접 접근할 로컬 경로로 등록한다. 제품의 기본 흐름에서 WSL 경로로 변환하지 않는다. 내부 WIKI는 프로젝트 기준 상대 경로를 사용하며 경로 검사와 저장의 소유는 [연결 명세 — 「연결 설정의 필드와 읽기 규칙」](../runtime/entry.md)에 둔다.

Obsidian은 선택한 문서 폴더를 vault로 여는 편집기다. `.obsidian`, MCP, 유료 동기화가 하네스 연결의 필수 조건은 아니다. 같은 폴더를 vault로 등록하는 것만으로 앱 Git에서 분리되는 것도 아니다. 기존 docs를 외부로 옮기는 경우에는 링크, 검사, Git 추적/공개 범위, 복구를 별도 이전 작업으로 검토한다. 특정 시험 사본의 삭제 허가를 다른 프로젝트 WIKI의 삭제 허가로 재사용하지 않는다. [Obsidian 저장 방식](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data).

프로젝트 지식과 실행 상태는 모듈 업데이트로 초기화하지 않는다. 원본 버전, 적용 설정, 이후 편집을 구분해 충돌을 처리해야 한다는 점은 [Copier 갱신 문서](https://copier.readthedocs.io/en/stable/updating/)를 참고한 설계 판단이며 Copier 채택은 아니다. 실제 제품 연결, 빈 문서 초기화, 재개, 이동 검증은 아직 수행하지 않았다.

## 설치와 AI 분석

설치와 WIKI 분석의 경계를 명시한다. 설치 제공 수단은 ADR 0010의 Git 릴리스 + Python 도구로 채택했지만 제품 구현은 아직이며, 파일 배치 성공을 WIKI 복원 완료로 계산하지 않는다. [개발 요구 검토 — 「설치와 AI 분석」](../../discussions/knowledge/requirements.md)의 질문, 근거와 아래 책임을 연결한다.

| 책임 | 맡을 일 | 남은 설계 |
| --- | --- | --- |
| 설치, 연결 | 공통 실행 파일, 지침, 설정의 배치, 기존 자료 보호, 경로, 도구 발견 확인 | 배포 수단, 버전, 권한, 충돌 처리 |
| 분석 실행, 진행 관리 | 대상 범위와 허용 자료 선택, 수집, 분할, 중단/재개, 기존 결과 대조 | 사용자 진입, 명령/skill, 작업 기록, 분석 예산 |
| AI 분석과 검토 | 코드, 테스트, 이력, 기존 문서의 의미를 대조해 근거 있는 후보 작성. 사실, 현재 요구, 과거 이유, 추정 구별 | 요구 문서의 내용, 분할, 템플릿, 후보 검토, 채택과 누락 점검 |

검토할 흐름은 `설치 후 연결 확인 → 분석 범위 선택 → 필요한 자료 수집 → AI 후보 작성 → 검토 후 채택 → 검증과 진행 상태 저장`이다. 설치와 분석을 사용상 한 진입점에서 연결할 수 있어도 책임, 완료 상태는 분리한다. 모델이 후보를 썼다는 사실만으로 요구사항의 사실성이나 중요 항목의 완전성을 보장하지 않는다.

최초 설치 이후에도 사용자가 같은 기준으로 필요한 영역을 다시 분석, 보완할 수 있어야 한다. 이미 확인한 자료, 사용자 수정, 이후 변경을 대조하고, 전체 이력 재분석이나 원문 덮어쓰기를 기본값으로 삼지 않는다. 11/08 [ADR 0018](../../decisions/knowledge/0018-reconstruction.md)의 B 기본 실행을 채택했다. 일반 코드가 모델 목록을 조회하고 선택을 받는다. 복수 경로와 작업 범위를 미리 보여준 뒤 사용자가 확인하면 Codex 분석을 기능별로 진행한다. 상세와 비교는 [WIKI 생성과 보강 — 「설치한 작업 실행」](../../discussions/knowledge/reconstruction.md)이 소유한다. 정확한 명령, skill 추가, 구현 언어, 모델 평가, 템플릿은 후속이며 일반 개발 전체의 실행 방식을 바꾸는 결정이 아니다.

실제 AI 호출을 script로 연결하는 수단은 존재한다. OpenAI 공식 문서의 `codex exec`와 세션 재개는 그 예이며, 이 모듈의 권한, 인증, 원문 보존, 분석 누락, 사용량 한도 대응까지 제공하는 완성품은 아니다. 이번에는 호출하지 않았다. [OpenAI non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)

## 기존 문서 채택과 새 문서 복원

아래는 같은 하네스의 도입, 지식 준비가 입력 상태에 따라 어떻게 달라지는지 보여주는 예상 동작이다. 신규 프로젝트의 초기 기록을 역공학 복원으로 부르지 않는다. 실제 이식, 복원을 수행한 결과가 아니며, 문서가 있다는 사실만으로 충분하다고 보거나 비어 있다는 이유로 모든 역할의 빈 파일을 생성하지 않는다.

| 입력 상태 | 진행할 내용 | 완료 범위와 남길 한계 |
| --- | --- | --- |
| 유효한 기존 WIKI | 합의 범위의 코드, 문서 기준점을 대조하고 역할/경로를 연결. 필요한 연결 보정 외에는 원문을 유지 | 상세 정보, 관계가 이미 충분하면 새 본문 없이 연결, 대조로 마침. 기존 ID, ADR 번호, 이력 보존 |
| 코드, 이력은 있고 WIKI는 비어 있음 | 기초 파악 후 합의한 기능, 흐름별로 요구, 현재 동작, 과거 결정, 검증 근거를 복원. 기존 README, 명세, 테스트는 연결해 재사용 | 단위별 내용 확인 후 공통 요구, 계약, 용어, 누락을 대조. 첫 단위 완료를 전체 완료로 보고하지 않음 |
| 기존 WIKI 일부가 낡았거나 충돌함 | 원문과 출처별 주장을 보존하고 차이, 부족분만 후보로 제시 | 현재 정책을 선택해야 하는 부분은 합의 전 보류. 관계없는 유효한 문서까지 재작성하지 않음 |
| 코드, 이력이 없는 새 프로젝트 | 확인한 목적, 첫 기능, 현재 선택부터 기록하고 개발과 함께 보강 | 현재 요구, 설계 준비로 보고. 없는 코드, 과거 ADR을 복원했다고 표시하지 않음 |

기존 지식의 도입은 최종 설치 형태와 소비 계약을 설계하는 데 유용하지만 빈 문서의 복원 성공을 대신하지 않는다. 현재 감사에서 이미 불일치가 발견됐으므로 기존 문서도 관련 scope에서 대조한다. 유효한 자료는 연결하고 충돌, 부족분만 후보로 제시한다.

기존 문서가 풍부한 사례와 코드만 있고 문서가 없는 사례를 구분한다. 입력 상태는 직접 확인하고, 코드에서 관측할 사실과 운영 데이터 정책, 멱등성 요구, 과거 선택 이유를 구별한다. 실제 근거를 확인한 뒤 후보를 채우며 모든 사례의 읽기/갱신/공백 처리에는 [최소 WIKI](wiki.md#%EC%B5%9C%EC%86%8C%20WIKI)의 기준을 적용한다.

중단, 접근 실패가 생기면 어느 사례든 미처리 단위를 남기고, 재개 시 입력 변경을 대조한 뒤 이어간다. 이미 확인한 단위도 직접 의존이 바뀌면 다시 확인한다. 반대로 허용된 자료를 조사했지만 당시 이유가 없으면 조사 범위와 복원 불가를 기록한다. 두 경우의 완료 판단은 [범위별 완료 판정](wiki.md#%EB%B2%94%EC%9C%84%EB%B3%84%20%EC%99%84%EB%A3%8C%20%ED%8C%90%EC%A0%95)을 따른다. 재개를 위해 남기는 처리 상태와 공유할 WIKI 지식은 구분한다.

역공학에서는 코드의 현재 동작, 과거 결정 이유, 앞으로 원하는 요구사항을 구분한다. 코드만으로 의도, 당시 이유를 확정할 수 없으면 미확인으로 둔다. 기존 버그를 새 요구사항으로 승격하거나 과거 ADR을 꾸며내지 않는다. 채택 문서에는 근거와 확인한 코드/이력 범위를 남기고, 재실행 시 수정한 문서의 보존도 확인한다. 상세 원본, 정책, 파생 결과 구분은 [ADR 0004](../../decisions/architecture/0004-portability.md)를 따른다.

빈 프로젝트 시험은 마지막 배포 직전까지 미루지 않는다. 초기 공통 경계를 만들 때부터 작은 예제로 실행하고, 실제 다른 프로젝트 도입으로 하드코딩과 분석 누락을 확인한다.

11/23에는 완료 후 같은 복원 명령을 다시 실행하는 [상태별 보완 흐름 — 「완료 후 다시 실행하는 흐름」](../../discussions/knowledge/reconstruction.md)을 기존 설계와 대조한 뒤 [ADR 0018 — 「완료 후 재실행」](../../decisions/knowledge/0018-reconstruction.md)에 채택했다. 기존 재사용/사용자 편집 보존 원칙을 상세화한 것으로, 입력이 같아도 명시적인 추가 검토는 허용한다. 완료 표시만으로 재사용하거나 전체 재생성하지 않으며, 필요한 검사는 기존 검증 계약을 따른다. [검증 입력 — 「완료 후 재실행의 검증 입력」](../../verification/acceptance.md)은 미실행이며 구현 완료나 무충돌 보장으로 취급하지 않는다.
