# WIKI 위치표 명세

작성일: 2026-11-09. JSON, 명시적 목록, 필요한 기능별 한 단계 분리, 등록 갱신 자동화, 선택 조회는 [ADR 0004 — 「문서 연결의 채택 범위」](../../decisions/architecture/0004-portability.md)에서 채택했다. 아래 필드, 조회 결과, 실패 처리는 그 방향을 구체화한 **입출력 초안**이며 구현, 효과 검증은 하지 않았다. 첫 파일 이름과 세부 형식을 모두 채택한 것으로 읽지 않는다.

이 문서는 기계가 처리할 연결 자료를 소유한다. WIKI의 정보 역할, 본문 관계는 [WIKI 설계](wiki.md), 형식, 분리의 비교 이유는 [검토 이력](../../discussions/history/map.md), 원문 보호는 [설치와 보존](../runtime/install.md)이 소유한다. 중단 내구성의 상세는 후속 복구 계약에서 구체화하며 현재 해당 계약은 미완성이다.

11/09 후속 확인: 현재 구성은 유지하고 구현에서 문제가 드러나면 관련 근거와 함께 재검토한다. 아래 역할, 범위, 절 선택은 다음 설계를 위한 구체안이며 이름, 파서, 오류 코드까지 지금 모두 확정하는 절차가 아니다.

## 입력의 경계

- 입력은 등록된 코드/WIKI 원본, 사용할 위치표, 요청의 정보 역할과 기능 범위다. 실제 절대 경로, 권한은 로컬 연결 설정이 소유한다. 공유 위치표에 작성자의 기기 경로를 넣지 않는다.
- AI는 요청과 원문을 분석해 필요한 역할, 범위와 연결 변경을 판단한다. 일반 도구는 위치표 조회, 형식/경로 검사, 허용된 갱신을 수행한다. 파일 조회 자체에 모델 호출을 요구하지 않는다.
- 위치표는 상세 본문, 전체 커밋, 실행 로그를 담지 않는다. 현재 작업 상태, 조회 결과와 섞지 않고, 프로젝트의 WIKI 연결 자료로 버전 관리한다.
- 예시의 상품 기능과 경로는 가상 자료다. 실제 프로젝트를 분석하거나 해당 파일을 생성한 결과가 아니다.

## 조회할 역할

[기본 여섯 역할 — 「기본으로 제공할 역할」](wiki.md)은 정보 책임의 묶음이다. 조회 이름은 그 안에서 별도로 찾을 필요가 있는 정보만 나누는 안을 추천한다.

| 방식 | 이점 | 비용, 판단 |
| --- | --- | --- |
| 여섯 묶음을 그대로 조회 | 이름이 적고 설명과 바로 대응 | 요구와 계약, 논의와 결정처럼 필요한 자료를 따로 고르기 어려움 |
| 조회 목적별 공통 이름 — 추천 | 프로젝트가 달라도 같은 역할로 찾고 서로 다른 종류의 근거를 구별 | 지원 목록을 한 곳에서 관리하고 연결 의미를 확인해야 함 |
| 프로젝트마다 자유로운 역할 | 각 팀의 용어를 그대로 사용 | 같은 의미가 여러 이름으로 갈리고 공통 절차, 확장 기능의 조회가 누락될 수 있음 |

첫 목록 후보는 아래와 같다. 11/09 통용 용어 우선 요청에 따라 이름을 재검토했다. 이 목록은 널리 쓰이는 개념을 참고한 우리 모듈의 조회 이름이며 업계 공통으로 정해진 아홉 역할 표준은 아니다. 역할 수는 필수 문서, 파일 수가 아니며 문서 하나가 여러 역할을 맡을 수 있다. 실제 자료가 없는 역할은 미확인으로 남긴다.

| 역할 값 후보 | 찾을 정보 | 기존 책임 묶음 |
| --- | --- | --- |
| `index` | 무엇이 어디에 있고 언제 읽는지 알려주는 문서 진입점 | 진입, 탐색 |
| `requirements` | 기대 동작, 지켜야 할 조건, 완료 기준과 그 채택 근거 | 요구, 계약 |
| `contract` | API, 이벤트, 데이터의 형식과 경계 계약 원본 | 요구, 계약 |
| `architecture` | 현재 구성, 처리 흐름, 외부 의존, 책임 경계 | 구조, 실행 |
| `development` | 빌드, 개발 실행, 검사 방법, 전제 환경과 예외의 근거 | 구조, 실행 |
| `discussion` | 검토 중인 대안, 미확정 질문, 미채택 제안 | 논의, 결정 |
| `decision` | 확인된 결정의 이유, 상태, 변경 이력 | 논의, 결정 |
| `runbook` | 증상, 확인 원인, 대응, 재검증 등 재사용할 실패 대응 지식 | 실패, 대응 |
| `evidence` | 공유할 수 있도록 정리한 검증, 관측 결과와 근거 위치 | 진행, 검증 중 공유 지식 |

역할은 읽을 자료의 분류다. `development`를 찾았다고 명령을 실행하거나 `decision`으로 등록됐다고 현재 유효한 정책으로 확정하지 않는다. 미채택 ADR, 폐기된 결정도 원문의 상태를 확인하며, 파일명만으로 채택 여부를 판단하지 않는다. 현재 active, scope, 임시 로그는 로컬 실행 상태에서 읽고 이 공유 위치표에 사용자별 경로를 넣지 않는다. `index`가 AI 도구의 지침 발견, 우선순위 규칙을 대체하지도 않는다.

지원 역할의 정의, 검사, 목록 안내는 하나의 원본을 사용하고 skill마다 목록을 복제하지 않는다. 임의 역할, 오타는 알려주되 기존 파일을 조용히 고치지 않는다. 새 확장은 실제 필요한 조회 의미가 있을 때 같은 정의를 보완한다. 학습, 해설 자료는 기존 본문 링크로도 찾을 수 있으므로 확장 이름마다 새 역할을 미리 만들지 않는다.

이 목록은 이 프로젝트의 조회 목적에 맞춘 제안이다. [arc42의 요구 개요](https://docs.arc42.org/section-1/)와 [결정 기록](https://docs.arc42.org/section-9/)은 상세 원본을 참조하고 판단 근거를 구분하는 참고이며 위 아홉 이름을 규정하지 않는다. [Diátaxis의 참조 문서 설명](https://diataxis.fr/reference/)도 코드에서 생성한 참조만으로 필요한 설명이 모두 채워지지는 않음을 지적한다.

### 이름 선택의 근거

기존 후보 `structure`는 `architecture`, `run`은 개발 안내라는 현재 범위에서 `development`로 보정했다. 여전히 설계 후보이며 제품 설정, 파일, 호환 별칭을 구현한 변경은 아니다. 앞선 판단과 원문은 작업 근거에 보존하며 기존 자료를 일괄 리네이밍하지 않는다.

| 이름 | 판단, 근거와 한계 |
| --- | --- |
| `index` | 유지. [MkDocs](https://www.mkdocs.org/user-guide/writing-your-docs/#file-layout)의 index 페이지처럼 문서 진입점에 쓰이는 관례가 있다. 검색용 내부 색인과 구별해 설명하며 실제 파일을 index.md로 강제하지 않음 |
| `requirements` | 유지. 요구사항을 뜻하는 일반적인 명칭이며 [arc42](https://docs.arc42.org/section-1/)도 기존 requirements 문서를 참조. 별도 SRS 형식을 필수로 요구하지 않음 |
| `contract` | 유지. [Pact](https://docs.pact.io/)도 시스템 사이 요청, 메시지의 합의에 contract를 사용. 형식만으로 드러나지 않는 기대 동작, 호환 조건을 함께 확인하며 Pact 파일을 필수로 뜻하지 않음 |
| `architecture` | 기존 structure보다 의도가 선명함. [arc42 구성 요소](https://docs.arc42.org/section-5/)와 [실행 시나리오](https://docs.arc42.org/section-6/)처럼 정적 구성과 동작, 관계 모두를 설명하는 범위 |
| `development` | 기존 run은 명령 실행, 실행 한 번, 실행 안내 중 무엇인지 모호했음. [Python 개발자 안내](https://devguide.python.org/getting-started/setup-building/)처럼 개발 환경, 빌드, [테스트](https://devguide.python.org/testing/run-write-tests/) 안내를 찾는 후보. 운영 배포, 복구 전체까지 뜻한다면 operations/runbook과 범위를 다시 대조해야 함 |
| `discussion` | 유지. 일반 검토, 질문, 대안을 폭넓게 연결. [Rust RFC](https://rust-lang.github.io/rfcs/)처럼 정해진 제안/검토 절차를 사용하는 자료도 포함할 수 있으나 모든 논의를 RFC라고 명명하지 않음 |
| `decision` | 조회 역할로 유지하고 아키텍처 결정 문서에는 ADR을 우선 사용. [AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)와 [Microsoft](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)는 ADR의 맥락, 결정, 영향, 상태를 설명. 기존 비 ADR 결정 기록도 연결해야 하므로 역할 자체를 ADR 형식으로 제한하지 않음 |
| `runbook` | 유지. [AWS](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_ready_to_support_use_runbooks.html)는 정해진 결과를 얻는 절차로 설명하며 장애 대응 외 운영 절차에도 사용. 우리 후보는 우선 실패 대응 지식을 연결하므로 일반 의미보다 좁게 사용하는 범위를 명시 |
| `evidence` | 유지 후보. 검증, 관측 근거를 묶는 일반어이며 이 역할 목록의 표준 명칭이라고 주장하지 않음. test-results로 바꾸면 테스트 외 측정, 관측 근거를 충분히 표현하지 못함. 실제 자료 유형에 맞는지 구현 전에 확인 |

ADR은 Architecture Decision Record를 뜻한다. 역할 이름, 문서 유형, 채택 상태는 각각 판단한다. `decision`을 ADR로 바꾸거나 `discussion`을 RFC로 바꾸는 것만으로 기록의 의미, 상태, 품질이 좋아지지는 않는다. 공식 명칭을 우선하되 의미가 맞는 곳에 쓰는 기준은 [이름과 변경 이력](../module.md)을 따른다.

## 공통과 기능 범위

`common`은 프로젝트 전반에 적용되는 연결, 나머지는 해당 프로젝트가 정한 기능, 흐름 이름으로 사용한다는 초안을 유지한다. 범위는 코드 폴더와 반드시 일치하지 않는다. `product`, `checkout` 같은 이름은 예시이며 공통 배포 코드에 프로젝트 이름 목록을 넣지 않는다.

조회는 **요청한 역할 중 공통 항목 + 명시한 기능/흐름 항목**을 합친다. 공통이라는 이유로 모든 역할의 문서를 읽거나 기능 항목이 공통 정책을 덮어쓰게 하지 않는다. 여러 범위는 한 요청에 함께 지정할 수 있다. 현재 사용 가능한 범위는 등록 항목에서 찾고 같은 목록을 별도 설정으로 반복 관리하지 않는다.

예를 들어 상품 변경에서는 `product`의 요구, 계약과 관련 공통 요구를 찾는다. 구매 흐름에서 재고, 결제까지 영향이 드러나면 그 관계의 원문을 읽고 필요한 범위를 더 조회한다. 이름의 접두어, 폴더 포함 관계로 의존 기능을 자동 확정하지 않는다. 의존 자료를 읽는 것과 해당 기능 전체를 수정, 복원하도록 범위를 늘리는 것은 구별한다.

빈 입력, 모르는 범위를 전체 조회로 바꾸지 않는다. 범위 변경, 이름 변경은 관련 항목과 그 이름을 쓰는 소비 지점을 함께 대조한다. 공통으로 부를 정보가 적으면 적게 두며 모든 기능의 목록을 `common`에 복사하지 않는다. 정확한 이름 허용 문법, 정규화는 구현 계약에서 확인한다.

## 저장 형식

루트 `map.json` 예시다. 공통 진입점과 하위 위치표 목록을 함께 두며 하위 내용을 복제하지 않는다.

```json
{
  "entries": [
    {
      "role": "requirements",
      "scope": "common",
      "root": "wiki",
      "path": "REQUIREMENTS.md"
    }
  ],
  "maps": ["maps/product.json"]
}
```

하위 `maps/product.json` 예시다. 같은 기능에 필요한 여러 역할을 한 파일에서 연결할 수 있다.

```json
{
  "entries": [
    {
      "role": "requirements",
      "scope": "product",
      "root": "wiki",
      "path": "features/product.md",
      "section": "등록 조건"
    },
    {
      "role": "contract",
      "scope": "product",
      "root": "code",
      "path": "api/product.json"
    }
  ]
}
```

단일 파일 구성은 루트의 `entries`에 필요한 항목을 두고 `maps`를 생략한다. 루트의 `entries`, `maps`는 필요한 쪽만 두되, 둘 다 비어 있으면 미설정으로 보고 조회 준비 완료로 취급하지 않는다. 하위 파일은 실제 항목이 있을 때 만들며 다른 `maps`를 포함하지 않는 초안이다. 참조 단계 하나와 물리 디렉토리의 깊이는 구별한다.

| 필드 | 의미와 제약 초안 |
| --- | --- |
| `entries` | 원문 연결의 배열. 여러 항목을 함께 사용할 수 있으며 순서로 우선순위를 정하지 않음 |
| `maps` | 루트에서 사용하는 하위 위치표의 명시적 경로 배열. 폴더 자동 탐색, 목록의 재귀 참조는 첫 범위에서 제외 |
| `role` | [조회할 역할](map.md#%EC%A1%B0%ED%9A%8C%ED%95%A0%20%EC%97%AD%ED%95%A0)의 공통 이름. 첫 목록은 후보이며 AI가 임의의 새 역할을 만들어 정상값처럼 쓰지 않음 |
| `scope` | 프로젝트가 정한 기능/흐름 범위. 초안에서는 `common`을 공통 범위로 두고 다른 값은 정확히 일치시킴. 코드 폴더 이름으로 자동 추정하거나 문자열 접두어로 상속하지 않음 |
| `root` | 등록된 원본의 이름. `wiki`, `code`는 예시. 이름이 없는 원본에 임의 접근하지 않음 |
| `path` | 해당 원본 기준 상대 경로. 실제 대상까지 허용 범위 안인지 확인 |
| `section` | 필요한 절이 명확할 때만 추가. 생략하면 문서 진입점을 뜻하며 본문 전체를 항상 모델에 전달한다는 뜻은 아님 |

이 초안은 역할, 범위, 원본, 경로를 필수 항목으로 두고 절만 선택한다. 설정 상속, 자동 우선순위, 별도 ID, 수정 차수용 버전 필드는 추가하지 않는다. 정확한 지원 역할, 문서 형식별 절 선택자는 후속 명세로 닫는다. 현재 Markdown 예시의 같은 제목이 여러 곳에 있으면 하나를 임의 선택하지 않고 모호함을 반환하며 기존 제목을 강제로 바꾸지 않는다.

## 문서 안의 절 선택

파일만 연결할 수 있게 두고, 필요한 정보의 위치가 뚜렷할 때 `section`을 더하는 안을 추천한다. 모든 연결에 절을 요구하면 기존 문서를 바꾸게 될 수 있고, 파일만 허용하면 긴 문서에서 같은 탐색을 반복할 수 있다. 제목은 이동하기 쉬운 줄 번호보다 의미가 드러나지만 이름 변경, 중복에는 여전히 대응해야 한다.

첫 후보는 Markdown의 **문서 안에서 유일하게 찾을 수 있는 제목**이다. 찾은 절은 해당 제목부터 다음 같은 수준 또는 상위 제목 전까지이며 하위 절을 포함한다. 상위 제목의 맥락, 관련 공통 조건도 필요한 만큼 확인한다. 한 절을 찾았다는 이유로 그 절만으로 작업 근거가 충분하다고 판단하지 않는다.

제목을 못 찾거나 여러 곳에 있으면 경로와 후보를 돌려주고 절 선택은 미해결로 남긴다. 자동으로 첫 항목을 고르거나 기존 제목을 바꾸지 않는다. AI는 파일의 목차, 주변 내용을 읽어 연결 후보를 보정할 수 있지만 실패한 절 선택을 성공으로 바꿔 보고하지 않는다. 지원하지 않는 문서 형식은 파일 진입점과 해당 형식의 기존 검색 수단을 사용한다. JSON 경로, 코드 심볼, Obsidian 전용 블록 식별자를 모두 한 문법에 추가하지 않는다.

제목 해석에는 [CommonMark의 ATX, Setext 제목](https://spec.commonmark.org/0.31.2/#atx-headings)과 코드 블록 구별을 반영해야 한다. [GitHub 제목 링크](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links)는 제목 변환과 중복 번호 규칙을 사용하며 제목/순서 변경으로 주소가 바뀔 수 있다. 따라서 웹 앵커 문자열을 모든 도구의 공통 제목 식별자로 가정하지 않는다. 인라인 서식, 유니코드, 제목 계층의 정확한 비교와 파서 선택은 구현 시 실제 입력으로 검증한다.

## 경로 해석과 연결 검사

`maps`는 그 목록 파일이 있는 위치, 항목의 `path`는 등록한 `root`를 기준으로 해석한다. 모델의 현재 작업 디렉토리를 암묵적 기준으로 쓰지 않는다. 파일 경로와 문서 절은 각각 `path`, `section`으로 구분한다.

하위 위치표는 등록한 WIKI 범위 안에서 찾고, 연결 원문은 해당 `root` 범위 안에서 찾는다. 심볼릭 링크의 실제 대상, 파일 누락, 읽기 권한, 같은 실제 파일의 중복 등록을 확인한다. 대소문자를 무조건 바꾸거나 작성자 기기의 절대 경로를 끼워 넣어 보정하지 않는다. 원격 URL 자동 다운로드는 이 위치표 로더의 첫 범위에 넣지 않는다.

[JSON 표준](https://www.rfc-editor.org/rfc/rfc8259)은 객체 키의 중복을 피하도록 설명한다. 이 초안은 같은 객체 안의 중복 키를 오류로 다루고 마지막 값으로 조용히 덮지 않는다. 위치표의 같은 연결 반복과 서로 다른 자료가 같은 역할을 함께 맡는 경우도 구별한다. 같은 문서가 여러 역할에 연결됐다는 이유만으로 삭제하지 않는다. 읽을 본문은 중복을 줄이되 역할 관계는 보존한다.

## 조회와 AI에 반환할 정보

요청 예시다. AI가 작업의 의미를 판단해 필요한 역할과 범위를 선택하고 도구에 넘긴다.

```json
{
  "roles": ["requirements", "contract"],
  "scopes": ["product"]
}
```

도구는 루트와 등록된 하위 위치표를 읽어 해당 역할의 공통 항목과 선택 범위의 항목을 찾는다. 루트에 경로만 적혀 있으므로 하위 역할/범위를 확인하려면 하위 위치표도 읽어야 한다. 이를 모델이 모든 파일 본문을 읽는 것과 혼동하지 않는다. 범위를 빠뜨렸다고 전체 WIKI로 조용히 확대하지 않으며, 등록 범위를 조회하고 필요한 선택을 이어간다.

결과 초안은 `entries`와 `issues` 두 묶음이다. `entries`에는 선택한 연결을, `issues`에는 누락, 잘못된 입력, 모호한 대상과 해당 설정/원문 위치를 돌려준다. 오류 문구만으로 모든 실패를 같은 것으로 만들지 않고 아래 상황을 구분한다. 반환할 오류의 정확한 키, CLI 종료 코드는 구현 명세에서 확정한다.

| 상황 | 반환, 후속 처리 |
| --- | --- |
| 공통 요구와 상품 요구가 모두 연결됨 | 둘 다 반환. 기능 항목으로 공통 항목을 덮어쓰지 않음 |
| 요청한 역할/범위의 연결이 없음 | 미등록/미확인으로 표시. 문서 자체가 없거나 복원이 끝났다는 결론을 내리지 않음 |
| 등록한 하위 위치표, 원문 파일이 없음 | 누락된 경로와 연결 출처를 반환. 빈 문서를 생성해 성공 처리하지 않음 |
| 읽을 권한이 없거나 원본 이름이 미등록 | 접근 실패와 미등록 원본을 구별. 같은 이름의 다른 사본으로 대체하지 않음 |
| 문서 절, 연결 의미가 모호함 | 후보, 충돌을 반환. 날짜나 배열 순서로 하나를 자동 채택하지 않음 |
| 중복 키, 잘못된 형식, 허용 범위 밖 경로 | 잘못된 입력으로 보고 원문/설정을 유지. 영향받는 조회, 갱신을 보류 |

`issues`가 비어 있어도 문서 내용의 정확성, 필수 근거 전체 확보, 테스트 PASS를 뜻하지 않는다. 모든 역할×범위 조합에 별도 문서를 요구하지도 않는다. 공통 문서로 충분한지, 미등록 연결이 작업에 필수인지, 어떤 추가 근거가 필요한지는 AI가 본문과 요청을 대조한다. 중요한 미해결 의도는 기존 협의 기준에 따라 확인한다.

단일 기능 조회가 서비스 사이의 계약을 자동으로 모두 찾아주는 구조는 아니다. 상세 관계는 원문에 두고 AI가 필요한 관련 범위를 추가 조회한다. 같은 관계를 JSON과 본문에 독립적으로 중복 작성하지 않는다. 조회 결과가 많으면 작업 범위를 나누어 처리하되 필수 근거를 조용히 자르지 않는다. 결과 제한, 나누어 반환하는 세부 수단은 후속 명세다.

## 등록과 갱신

AI가 변경 범위, 역할을 판단 → 도구가 현재 원본과 변경 후보를 대조 → 허용된 파일/목록을 함께 반영 → 연결 검사와 내용 대조 순서다. 정상적으로 승인된 작업 범위의 갱신마다 사람의 재승인을 요구하지 않으며, 새 범위, 중요 정책, 의도 충돌은 별도로 협의한다.

문서 본문만 바뀌면 연결을 불필요하게 다시 쓰지 않는다. 원문 경로가 바뀌면 해당 항목과 유입 링크를, 하위 위치표가 추가, 이동되면 그 파일과 등록 목록을 함께 확인한다. 무관한 항목의 재정렬, 전체 재생성, 원문 덮어쓰기를 피한다. 후보를 찾았다는 이유만으로 사용 대상으로 자동 등록하지 않는다.

후보 작성 후 원본이나 설정이 바뀌면 기존 후보로 덮지 않고 차이를 다시 대조한다. 두 파일의 쓰기가 자동으로 원자적이라고 주장하지 않는다. 중단, 부분 반영은 미완료로 남기고 연결이 일관되지 않은 상태를 정상 입력으로 사용하지 않아야 한다. 저장 시점, 복구 기록, 동시 편집 처리의 구체 수단은 후속 복구 계약과 함께 확정한다.

## 검증과 남은 명세

[S-18, 23, 24 — 「최소 WIKI 수용 후보」](../../verification/acceptance.md)에 다음 확인 항목을 연결한다.

- 단일 위치표와 분할 위치표에서 같은 조회 결과가 나오는지, 공통 요구와 기능별 요구를 모두 찾는지 확인한다. 같은 원문이 여러 역할을 맡는 경우도 포함한다.
- 누락된 자료와 중복 키, 모호한 절, 잘못된 원본을 구별하는지 확인한다. 부분 갱신에서도 원문을 보존하는지 확인한다.

AI의 정보 누락, 잘못된 연결과 전체 시도의 토큰/수정 비용을 우선 관측하고 사람의 개입 가능성도 보완 확인한다. 현재는 설계 문서와 JSON 예시 문법만 확인하며 로더, AI, 실제 복구 시험은 미실행이다.

조회 역할, 공통/기능 범위, 절 선택의 추천을 이번 문서에 구체화했다. 정확한 역할 값, 이름/제목 비교, 오류/결과 분할, 저장과 복구는 구현 계약에서 실제 입력과 함께 닫는다. 현재 구성을 뒤집을 문제나 새로운 사용자 선택이 드러나면 그 부분만 다시 검토한다. WIKI 내용, 완료 범위와 위임/설치의 기본 경계는 이미 채택됐다. 이 문서의 미정 입력 계약은 후속 명세에서 닫으며 다음 작업 순서는 [진행표](../../development/roadmap.md)만 관리한다.
