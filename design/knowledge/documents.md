# WIKI 문서 구성과 읽기 경로

최초 작성: 사용자 작업일 2026-11-08. **11/09 짧은 공통 요구/색인과 기능, 흐름별 상세의 기본 구성을 채택했다. 제품은 미구현**이다. 기존 문서는 강제 분할하지 않으며, 아래 가상 예시의 이름, 고정 파일, 모든 상세 템플릿까지 확정한 것은 아니다. [상세 복원 목표 — 「복원할 깊이와 완료 목표」](wiki.md), 채택된 [역할과 경로 분리](../../decisions/knowledge/0008-document-scope.md), [AI 분석, 품질 — 「품질 기준」](../../discussions/knowledge/reconstruction.md)을 전제로 한다.

## 비교와 추천

| 구성 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 한 문서 중심 | REQUIREMENTS에 요구, 흐름, 결정, 검증을 모음 | 작고 단순한 프로젝트는 찾기 쉬움 | 규모가 커지면 긴 읽기, 중복, 충돌이 늘고 현재 요구와 이력이 섞임 |
| 색인과 기능별 상세 | 짧은 공통 요구/색인에서 기능, 흐름별 상세, 공통 계약과 결정 원본으로 연결 | 상세 복원과 조건부 읽기를 함께 지원. 파일 수를 필요에 맞춰 늘릴 수 있음 | 소유 위치와 기능 사이 연결을 관리해야 함. 기본 구성 채택 |
| 코드 디렉토리별 문서 | 모듈, 패키지 구조를 따라 문서를 분할 | 코드 위치에서 문서를 찾기 쉬움 | 한 기능이 여러 모듈을 거치면 흐름이 분산되고 코드 이동마다 문서 구조도 흔들림 |

채택한 기본 구성은 **색인과 기능별 상세**다. 작을 때는 기존 문서의 절로 시작하고 독립적으로 읽고 갱신할 필요가 생기면 나눈다. 일정 줄 수를 넘었다는 이유만으로 쪼개거나 코드 파일마다 문서를 만들지 않는다. 기능이 코드 모듈과 일치하면 그 경계를 사용할 수 있지만 반드시 일치시킬 필요는 없다.

기존 프로젝트에 충분한 요구, 계약, ADR 문서가 있으면 그 구조를 연결한다. 아래 예시로 강제 이동하거나 이름을 바꾸지 않는다. 세 방식은 같은 상세 정보, 원문 보존, 검토 기준으로 비교하며, 짧은 출력만 만든 안을 비용 면에서 유리하다고 판정하지 않는다.

### 도메인과 흐름의 경계

REQUIREMENTS를 상품, 검색, 거래 같은 도메인/기능 섹션으로 나누고, 공통 요구와 각 상세 문서의 위치를 안내할 수 있다. 작은 상세는 같은 문서의 절로 두며, 따로 읽고 갱신할 필요가 생겼을 때 파일로 나눈다. 상위 색인과 하위 문서에 같은 상세 요구를 복제하지 않는다.

문서 경계는 코드의 하위 모듈과 반드시 같지 않다. 예를 들어 상품, 결제, 재고를 거치는 구매 흐름은 흐름 전체의 상태 전이, 실패, 보상을 한 곳에서 설명하고, 각 도메인 계약으로 연결하는 편이 낫다. 도메인별 탐색과 여러 도메인에 걸친 흐름을 함께 제공하되 같은 계약의 정의는 한 곳에서 관리한다. 실제 프로젝트의 기능, 모듈, 기존 자료를 확인하기 전 이 예시를 고정 분류로 만들지 않는다.

역공학은 선택한 범위의 근거와 기존 연결을 확인해 이 탐색 경로를 채우는 작업이다. 상위 도메인 링크가 있다고 모든 하위 파일을 자동 분석하거나 읽는다는 뜻은 아니다. 복원한 범위와 미처리 범위를 구별하며, 어떤 요청에서 어떤 공통 요구, 상세, 계약을 따라갈지 연결한다.

## 각 문서가 소유할 내용

아래 경로는 빈 WIKI에 적용할 **예시**다. 내부 docs와 외부 WIKI 저장소 모두 같은 역할을 사용할 수 있다. 실제 경로, 파일명은 기존 자료와 설치 매핑을 확인한 뒤 정하며 빈 폴더, 문서를 미리 생성하지 않는다.

| 역할, 위치 예시 | 소유할 내용 | 중복을 피하는 기준 |
| --- | --- | --- |
| README.md | 프로젝트/범위 개요, 구조, 실행 정보의 위치, 무엇을 찾을 때 어디로 갈지 | 상세 정책, 전체 요구를 복사하지 않음 |
| REQUIREMENTS.md | 제품 목적, 적용 범위, 공통으로 지킬 요구, 제약, 기능별 요구 위치 | 기능별 상세 요구의 본문은 해당 문서 한 곳에만 둠 |
| features/order.md | 한 기능 또는 여러 모듈에 걸친 흐름의 요구, 현재 동작, 경계, 검증과 근거 연결 | 공통 계약, 결정의 원문은 연결하고 다시 정의하지 않음 |
| 기존 계약 원본 또는 필요한 계약 문서 | API, 이벤트, 데이터 형식과 여러 기능이 공유하는 불변 조건 | OpenAPI, 스키마 등 원본이 있으면 전부 옮겨 적지 않음. 코드 형식만으로 드러나지 않는 의미는 설명 |
| decisions/의 기존 ADR | 중요한 선택의 당시 맥락, 대안, 이유, 결과, 변경 이력 | 기능 문서는 결정 위치와 적용 상태만 안내. 기각/대체된 결정을 삭제하지 않음 |
| 필요한 실패 대응 문서 | 재현 조건, 확인 원인, 대응, 재검증 등 재사용할 지식 | 단발 실행 로그, 현재 active 전체를 WIKI에 복사하지 않음 |

짧은 요구 색인은 최종 WIKI가 짧다는 뜻이 아니다. 상세는 해당 기능, 계약, 결정 문서에 보존한다. 기능을 나누더라도 공통 권한, 데이터 보존 같은 조건을 빠뜨리지 않아야 한다. 공통 규칙과 기능 규칙이 충돌하면 더 가까운 파일을 자동 정답으로 삼지 말고 차이를 확인한다.

### 문서가 늘어날 때의 분류와 탐색

11/09 추가 질문의 협의안이다. 한 폴더에 문서를 계속 쌓아 전체 목록을 스크롤해야 하는 사용성을 피하고, AI도 관련 범위의 진입점부터 읽도록 한다. 파일 수 자체를 본문 읽기량, 토큰 비용과 동일시하지 않으며 폴더 분리만으로 관련 근거 도달이 보장되지는 않는다.

| 방식 | 장점 | 비용, 판단 |
| --- | --- | --- |
| 단일 폴더와 짧은 색인 | 작을 때 단순하고 위치가 안정적 | 수가 늘면 탐색/검토가 어려워질 수 있음. 기존 구조는 강제 이동하지 않고 우선 연결 |
| 역할별 루트 + 필요한 범위별 하위 폴더, 색인 | 사람의 탐색과 AI의 선택 읽기를 함께 제공 | 범위 소유, 공통 결정, 이동 참조 관리 필요. 새 문서 구성과 성장 시 추천 |
| 파일은 그대로 두고 태그/검색만 사용 | 여러 관점으로 분류 가능, 이동 적음 | 편집기, 색인 도구 의존과 갱신/누락 검증 부담. 첫 필수 수단으로 두지 않음 |

추천은 기존 역할별 진입점을 유지하고, 내용의 소유 범위가 생길 때 하위 분류를 추가하는 방식이다. 코드 패키지마다 폴더를 만들거나 20개/100개 같은 숫자를 넘었다는 이유로 자동 이동하지 않는다. 요구, 계약, 실패 대응도 같은 원칙을 사용하되 소유 경계가 다른 자료를 형태만 맞추려고 한 트리에 복제하지 않는다.

ADR 분류의 **예시**는 다음과 같다. 실제 이름, 폴더 깊이, 번호 발급 방식은 확정하지 않았으며 필요한 분류만 생성한다.

```text
decisions/
├── README.md                  범위별 진입점과 현재 결정 안내
├── common/                    여러 기능에 적용되는 결정
│   └── adr-0001-...md
├── catalog/                   상품 범위의 결정
│   └── adr-0007-...md
└── checkout/                  주문, 결제 흐름의 결정
    └── adr-0012-...md
```

공통 ADR의 본문은 한 곳에 두고 각 기능에서 연결한다. 상위 색인은 범위별 링크를, 하위 색인은 필요한 결정, 상태, 순서를 안내해 하나의 거대한 목록으로 되돌아가지 않게 한다. 전체 연대순 조회가 필요하면 별도 보기로 제공하되 ADR 본문, 상태의 또 다른 원본을 만들지 않는다. 절차 문서는 실행 순서, ADR은 최초 날짜, 식별자, 대체 관계를 유지한다. 상태가 바뀔 때마다 폴더를 옮기는 방식은 링크 불안정 때문에 피한다.

새 ADR은 한 WIKI 안에서 중복되지 않는 안정된 식별자를 쓰는 쪽을 추천한다. 분류를 바꿔도 기존 번호, 날짜, 내용을 다시 쓰지 않고 번호 충돌은 반영 전에 확인한다. [MADR의 분류 결정](https://adr.github.io/madr/decisions/0010-support-categories.html)은 폴더별 번호와 전역 번호 등을 비교하며 자체 안에서는 폴더별 번호를 선택했다. 여기의 전역 식별자 추천은 여러 범위를 잇는 참조의 모호함을 줄이려는 별도 판단이며 업계의 단일 표준으로 주장하지 않는다.

[Nygard의 ADR 설명](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)과 [AWS 지침](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html)은 판단 이력과 대체된 기록의 보존 근거다.

모듈이 제공할 후보는 생성할 문서의 범위/소유 위치 안내, 색인, 위치표 갱신, 누락/중복 ID, 깨진 링크 검사다. 이는 조건부 하네스의 지속적인 문서 관리에도 쓰며 역공학 실행에만 한정하지 않는다.

### 프로젝트별 분류를 정하는 과정

프로젝트마다 도메인, 명명이 달라도 적용할 수 있도록 공통 정보 역할과 프로젝트의 기능 범위, 실제 경로를 분리하는 안이다. 위 예시의 `catalog`, `checkout`을 배포 기본 폴더로 고정하지 않는다. 기존 [위치표](map.md)의 역할, 범위, 진입점 연결을 사용하며, ADR마다 전역 행이나 분류용 데이터베이스를 추가하지 않는다.

| 단계 | 처리 후보 | 자동화의 경계 |
| --- | --- | --- |
| 기존 구조 확인 | 등록된 위치표, README, 기존 WIKI와 허용 범위의 코드 모듈/이름을 수집 | 일반 코드가 사실을 수집. 디렉토리 이름만으로 도메인이나 결정의 소유를 확정하지 않음 |
| 분류 제안 | AI가 기존 용어, 문서 역할, 기능 관계를 근거로 재사용 위치와 필요한 분류를 제안 | 새 경계, 모호한 공통 기능은 사용자와 협의. 설치만으로 전체 저장소 AI 분석을 시작하지 않음 |
| 연결, 생성 | 확인한 분류를 위치표에 연결하고 실제 문서를 만들 때 필요한 폴더, 색인을 함께 생성 | 기존 문서는 제자리에서 먼저 연결. 내용 없이 예상 도메인 폴더를 전부 만들지 않음 |
| 검사, 후속 사용 | 허용 루트, 경로 충돌, 중복 식별자, 진입점, 유입 링크를 검사하고 승인한 분류를 재사용 | 정형 통과는 의미 분류의 정답 보장이 아님. 같은 규칙의 문서 추가를 매번 재승인받는 절차로 만들지 않음 |

예를 들어 상품/주문 서비스는 기존 `product`, `order`, 예약 서비스는 기존 `reservation`, `venue` 명명을 쓸 수 있다. 이미 ADR을 `architecture/adr`에서 관리한다면 처음부터 `decisions`로 이동시키지 않고 그 경로를 연결한다. 새 분류가 필요할 때만 소유 범위, 읽기 흐름을 확인한다. 이런 이름은 설명 예시이며 업종별 고정 목록이 아니다.

코드, 기존 지식이 없는 프로젝트에서는 도메인을 추론할 근거가 없다. 사용자가 제시한 목적, 확정 요구와 최소 진입점부터 연결하고 개발 중 정보가 생길 때 분류를 보충한다. ‘필요할 때 생성’은 필수 실행 파일까지 비워 둔다는 뜻이 아니다. [최초 설치 — 「최초 설치에서 만드는 것」](../runtime/install.md)의 동작에 필요한 구성은 설치 시 준비한다.

분류 변경은 파일 이동, 유입 링크, 색인, 위치표, 공통 참조를 한 변경 계획으로 다룬다. 기존 번호, 이력, 사용자 편집을 유지하고, Windows 문서 경로의 대소문자 충돌, 허용되지 않는 이름, 등록 루트 밖 경로도 검사 대상으로 둔다. 설치나 모듈 버전 갱신을 문서 재분류의 허가로 해석하지 않는다. 프로젝트별 의미 판단이 필요하므로 모든 구조의 무확인 자동 분류를 보장하지 않는다.

## 입출력 계약과 테스트 데이터

기업의 기획, 설계 절차가 하나로 정해져 있지는 않다. 공개된 [Zalando의 API First 지침](https://opensource.zalando.com/restful-api-guidelines/#100)은 구현 전 명세와 소비자/동료의 조기 검토를 요구하지만, 전체 요구와 API를 처음에 모두 확정해야 한다는 뜻은 아니며 반복 개선을 허용한다. 이를 참고한 아래 역할 분담은 현재 설계의 추천이다.

| 대상 | 정할 내용과 시점 | 원본 위치 후보 |
| --- | --- | --- |
| 제품 요구, 기능 기획 | 사용자 목적, 필요한 정보, 업무 규칙, 허용/거절 조건과 완료 기준 | 공통 REQUIREMENTS와 기능 문서 |
| 외부 입출력 계약 | 구현 전 관련 개발자와 요청/응답, 이벤트 필드, 타입, 필수/누락/null 의미, 단위, 오류, 상태, 호환 조건을 검토 | 기존 API/이벤트 명세. 필요하면 OpenAPI, 스키마, 계약 문서 |
| 코드의 DTO | 합의된 계약을 표현하는 클래스/record와 직렬화, 검증, 매핑을 구현 설계에서 정함 | 해당 소스 코드. 중요한 설명만 WIKI에서 연결 |
| DB 구조 | 저장, 조회, 정합성 요구에 따른 관계, 제약, 인덱스와 변경 절차 | 기존 데이터 설계, 스키마, 마이그레이션. API DTO와 구별 |
| 문서용 입출력 예시 | 설계 검토, 사용법 설명을 위한 대표 JSON | 명세의 예시 또는 연결된 예제 파일 |
| 테스트 fixture | 정상, 경계, 실패, 중복 등에 필요한 데이터와 상태를 테스트 설계/구현 때 준비 | 테스트 코드, 리소스. WIKI에는 의도와 검사 위치를 연결 |

DTO의 클래스명, 내부 필드와 실제 JSON은 직렬화 설정 등에 따라 다를 수 있다. DTO만 보고 외부 계약을 확정하지 않는다. [Microsoft의 DTO 설명](https://learn.microsoft.com/en-us/aspnet/web-api/overview/data/using-web-api-with-entity-framework/part-5)도 DB 엔터티를 그대로 노출하는 것과 전송할 데이터 모양을 구별한다. DTO를 모두 문서에 전사하거나 DB, API 형식을 무조건 통일하는 설계를 채택하지 않는다.

`fixture`가 단순한 입출력 양식을 뜻한다면 여기서는 스키마, 예시라고 구별한다. 테스트 fixture는 테스트가 사용할 알려진 데이터/객체/상태다([JUnit 설명](https://junit.org/junit4/cookbook.html)). JSON 파일뿐 아니라 생성 코드, DB 초기 상태 등일 수 있다. 개발 환경의 대량 초기 데이터와도 목적, 수명, 실행 조건이 다르다.

예시 JSON 한 건만으로는 필수 필드, 허용 범위, 오류 동작을 알 수 없다. [OpenAPI의 본문 설명](https://learn.openapis.org/specification/content.html)은 구조를 표현하는 schema와 예시를 구별한다. 스키마로 표현되지 않는 업무 조건은 기능 설명이나 계약의 의미 설명에서 보완한다.

### 작성 방식의 대안

| 방식 | 장점 | 부담, 한계 |
| --- | --- | --- |
| 명세 먼저 | 입출력을 먼저 합의해 프런트, 백엔드 등 소비자와 병행 개발하기 좋음 | 실제 직렬화, 오류, 상태가 명세와 맞는지 검사 필요. 문서만 맞아도 구현은 다를 수 있음 |
| 코드에서 명세 생성 | 기존 코드에 도입하기 쉽고 구조를 중복 작성하는 양을 줄임 | 코드에 드러나지 않는 정책, 과거 이유는 복원하지 못함. 현재 버그도 정상 계약처럼 설명될 수 있음 |
| 테스트에서 문서 생성 | 실행한 요청/응답 사례와 문서를 연결 | 테스트 작성, 유지 비용이 있고, 테스트하지 않은 사례까지 보장하지 않음. 구현 전 계약 협의는 별도로 필요 |

첫 방식의 실제 기업 근거는 위 Zalando 지침이다. 두 번째는 [springdoc-openapi](https://springdoc.org/)가 설정, 클래스, 애너테이션을 읽어 명세를 생성하는 방식, 세 번째는 [Spring REST Docs](https://spring.io/projects/spring-restdocs/)가 설명과 테스트에서 만든 조각을 결합하는 방식으로 확인할 수 있다. 도구 기능의 존재가 모든 기업에서 같은 절차를 쓴다는 근거는 아니다.

현재 목표에 대한 추천은 **신규/변경 계약은 필요한 범위를 먼저 합의하고 구현, 테스트와 대조하며, 기존 프로젝트 복원은 기존 명세, 코드, 테스트를 대조해 현재 사실과 불일치를 먼저 기록**하는 것이다. 기존 명세를 생성 결과로 덮거나 관측한 현재 동작을 과거에 승인된 요구로 바꾸지 않는다. 구체 도구는 대상 프로젝트의 기존 자산을 확인한 뒤 선택하며 특정 도구 조합을 공통 필수 항목으로 만들지 않는다.

### WIKI와 코드의 연결

가상 상품 등록 예라면 기능 문서는 등록 조건과 가격 제한의 의미, 계약은 필드, 단위, 응답/오류, DTO는 직렬화할 코드 구조, fixture는 정상 가격, 경계값, 누락/오류 입력을 담당한다. 각 위치를 연결해 요구와 실제 동작을 대조한다. 실제 프로젝트의 가격 정책이나 테스트 결과를 확인했다는 뜻은 아니다.

빌드, 테스트가 소비하는 명세와 fixture는 해당 코드/공유 계약 저장소의 기존 관리 방식을 우선한다. 외부 WIKI가 별도 저장소여도 이 파일을 WIKI에 중복 저장하거나, 일반 코드 검사에 별도 WIKI 접근을 필수로 만들지 않는다. WIKI는 역할별 원본과 기준 버전을 연결한다. 코드, WIKI 변경의 버전/PR 연결은 기존 [작업 동기화](../../decisions/integration/0017-work-sync.md)를 따르며 이 보충으로 새 자동화를 채택하지 않는다.

## 템플릿 후보

반복해서 쌓는 문서 역할에는 기본 템플릿과 짧은 작성 안내를 배포한다. 현행 자산에 양식이 없으면 새 설계에서 필요한 정보에 맞춰 준비한다. ADR, 요구/기능 상세, 문제 해결 기록 등이 대상이며, 설명/학습 양식은 해당 확장을 선택했을 때 연결한다. 정확한 제공 목록, 필드, 파일명과 번호 규칙은 파일별 명세에서 정한다.

템플릿은 필요한 내용을 빠뜨리지 않게 하는 안내다. 근거 없는 문장이나 장식용 빈 절을 채우는 양식이 아니다. 기존 문서가 같은 역할을 충족하면 형식을 강제로 바꾸지 않는다. 문서 전체에 적용되는 출처, 확인 범위는 한 번 적고, 다른 근거가 필요한 주장에만 해당 출처를 연결한다.

기본 양식을 제공하는 것과 실제 기록을 만드는 시점은 구분한다. [최초 설치 — 「최초 설치에서 만드는 것」](../runtime/install.md)에는 필요한 진입과 연결을 준비하고, ADR 등 누적 기록은 해당 결정이나 작업이 생겼을 때 작성한다. 사용자는 프로젝트용 양식과 생성 문서를 수정할 수 있다. 라우팅이나 검증에서 사용하는 이름, 경로, 정보를 바꾸면 연결과 검사도 함께 맞춘다. 양식 변경을 기존 문서의 일괄 재작성으로 확대하지 않으며, 갱신은 [사용자 편집 보존 — 「변경분과 충돌의 판정」](../runtime/update.md)을 따른다.

현재 파일의 숫자 접두어나 제목을 배포 규칙으로 고정하지 않는다. [이름과 변경 이력](../module.md)에 따라 정하되 도구가 인식하는 표준 이름과 문서 식별/연결에 필요한 계약은 보존한다. 상위 운영 규칙은 템플릿마다 복제하지 않는다.

### 양식을 정하는 근거

11/13 **외부 근거로 기본 양식을 설계하고, 채택한 모듈 요구와 현재 프로젝트 사례로 적합성을 확인하는 방식**을 사용자와 합의했다. 현재 양식을 일반화하기만 하면 프로젝트 편향을 물려받을 수 있고, 외부 양식을 그대로 가져오면 해당 조직의 승인 절차나 불필요한 항목까지 늘어날 수 있다. 상세 형식은 아직 미확정이며 이 기준의 채택을 모든 배포 템플릿의 구현 완료로 보지 않는다.

같은 요청에서 배포 템플릿의 제목, 본문, 항목별 작성 안내와 예시 설명은 **한글**로 구성하기로 했다. 도구가 요구하는 파일명, 설정 키, 명령과 표준 식별자는 공식 규격을 유지하고 필요한 설명을 한글로 붙인다. 출처와 원래 기술 용어를 확인할 수 있게 연결하며, 기존 사용자의 문서를 임의로 번역하거나 이름을 바꾸지 않는다.

| 문서 목적 | 이번에 확인한 1차 자료 | 참고할 내용과 적용 경계 |
| --- | --- | --- |
| 중요한 결정 | [Nygard의 ADR 원문](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | 배경, 결정, 상태, 결과와 하나의 중요한 결정에 집중하는 구성. 현재 ADR 양식의 출처와 별도로 기본 구조를 검토할 수 있음 |
| 기능 제안과 설계 | [Kubernetes KEP 템플릿](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md) | 목표, 제외 범위, 위험, 설계와 테스트 계획. Kubernetes의 승인/릴리스 항목을 모든 프로젝트의 요구사항 양식으로 복제하지 않음 |
| 구조 설명 | [arc42 개요](https://arc42.org/overview/) | 목적별 구조 설명과 필요에 맞춘 조정. 열두 절을 모든 문서에 강제하지 않음 |
| 장애 회고 | [Google SRE의 postmortem 사례와 템플릿 안내](https://sre.google/workbook/postmortem-culture/) | 영향, 원인, 시간 흐름, 후속 조치와 팀에 맞춘 양식 조정. 사건 회고를 반복 실행할 복구 절차인 runbook과 같은 문서로 취급하지 않음 |

후속 명세에서는 문서의 목적과 생성 시점을 먼저 정하고, 후보 항목마다 필요한 이유와 필수/조건부 여부를 설명한다. 짧은 공통 정보와 필요한 상세를 연결하는 기존 구성을 유지하며, 현재 프로젝트 자료로 누락을 점검하고 신규 프로젝트나 다른 구조에서도 불필요한 빈 항목 없이 사용할 수 있는지 검증한다. 현재 자료에 있다는 이유만으로 채택하거나 외부 자료에 없다는 이유만으로 합의한 기능을 제거하지 않는다. 초안, 채택 이유, 연결과 검증 조건을 사용자에게 제시한 뒤 구체 양식을 확정한다.

외부 자료는 **무엇을 기록할지** 정하는 근거다. 실제 적용 프로젝트의 본문은 그 프로젝트의 코드, 테스트, Git 이력, 기존 문서와 사용자 확인으로 채운다. 다른 조직의 사례를 해당 프로젝트의 사실이나 과거 결정 이유로 옮기지 않는다. 실행 코드와 설정의 생성 템플릿은 지원 도구의 공식 인터페이스와 실행 검증도 별도로 충족해야 한다.

| 확인할 정보 | 남길 내용 | 충분하다고 볼 수 없는 경우 |

| 출처, 관계 | 주장에 맞는 원문과 필요한 공통 정책, 다른 기능, 결정의 연결 | 링크는 열리지만 다른 버전, 기능이거나 필요한 관계가 빠짐 |

관련 항목의 정보가 없으면 [공백 처리 — 「정보가 없거나 충돌하거나 오래된 경우」](wiki.md)에 따라 미조사, 접근 실패, 조사 범위 내 근거 부재, 충돌을 구별한다. 적용되지 않는 항목까지 빈 절로 남기지 않되, 중요한 경계를 제외한다면 이유를 표시한다. 입력 파일별 처리 현황, 해시는 로컬 실행 기록이 소유하고, WIKI에는 장기적으로 필요한 기준점, 근거, 한계를 남긴다.

### 작성 형태

기능 문서의 시작 형태는 다음처럼 추천한다. 제목과 절의 이름은 설명용이며 배포 템플릿을 확정한 것은 아니다.

```markdown
# 기능 이름

이 문서의 범위와 확인한 기준점. 사실, 검토 중, 미확인인 부분을 구별한다.

## 목적과 요구
기대 동작, 허용하지 않는 동작, 적용 조건과 완료를 판단할 기준.

## 동작과 경계
현재 처리 흐름, 상태/데이터, 외부 호출, 오류, 재시도 조건과 계약 원본.

## 선택과 변경
주요 변경의 이전/이후와 결정 기록. 근거가 없는 당시 이유는 추론으로 표시.

## 검증과 한계
관련 검사, 실행 여부, 결과의 근거, 남은 실패, 미확인.

## 근거와 관련 문서
요구, 결정, 계약, 코드/커밋, 검증 원문의 위치와 확인한 버전.
```

선택의 전체 논의가 ADR에 있으면 기능 문서의 선택 절에는 적용된 결정과 바뀐 점만 연결한다. 별도 ADR이 없는 국소 변경은 기능 문서에서 근거와 함께 정리할 수 있다. 중요한 항목을 모르면 해당 공백을 표시하되 관련 없는 항목을 일괄 생성하지 않는다. 실제 비밀값은 예시, 출처 사본에도 넣지 않는다.

요구사항별로는 기대 동작, 조건/예외, 확인 기준, 채택 근거가 식별돼야 한다. 기존 요구 ID나 안정된 링크가 있으면 재사용하고 모든 문장에 새 번호를 붙이지 않는다. 상세 검증 결과는 원래 결과 기록에 두며 요구사항에 PASS 문구만 복제해 오래 남기지 않는다.

## 읽기 경로

프로젝트 진입 지침은 공통 절차와 문서 진입점으로 안내한다. 구체적인 역할/기능별 위치는 [역할별 위치 연결](wiki.md)의 한 원본에서 관리하고, skill은 필요한 역할과 범위로 실제 위치를 찾는다. JSON, 명시적 목록, 선택적 한 단계 분리는 채택했고, [조회 역할, 범위, 절 선택 — 「조회할 역할」](map.md)을 구체화했다. 정확한 값, 도구별 발견 경로, 강제 수단은 후속 구현 명세다.

| 작업 | 먼저 읽을 내용 | 필요한 추가 확인 |
| --- | --- | --- |
| 저장소와 무관한 설명 질문 | 추가 WIKI 읽기 불필요 | 요청이 제품 사실을 요구할 때만 전환 |
| 기능 변경 | 적용 규칙, 관련 공통 요구, 기능의 현재 요구/동작 | 변경되는 계약, 관련 결정, 검사, 직접 의존 기능 |
| 동작을 유지하는 리팩터링 | 변경 코드의 역할, 관련 계약, 검사 | 기존 의미가 유지되는지 확인. 새 요구를 자동 작성하지 않음 |
| 실패 분석 | 원래 실패와 해당 범위의 구조/계약 | 관련 대응 기록, 실제 결과. 무관한 runbook 전체 탐색은 하지 않음 |
| WIKI 복원, 보강 | 합의 범위, 기존 문서/연결, 입력 기준점 | 해당 기능, 결정, 이력의 원문과 관계, 미처리 목록 |
| 중단 후 재개 | 코드 작업 공간의 로컬 상태와 입력 변경 | 영향받은 원문, 미완료 검사. 상태를 WIKI에 복제하지 않음 |

읽기 경로는 기능 설명에서 멈추지 않는다. 예를 들어 재시도 변경이면 관련 소비/보상 계약과 실패 검증까지 필요한지 확인한다. 링크가 순환한다고 같은 문서를 계속 읽거나, 정해진 읽기 횟수를 넘었다고 필수 근거를 생략하지 않는다. 근거가 충분하면 관련 없는 문서로 확장하지 않고, 부족하면 필요한 범위를 더 확인하거나 작업을 보류한다.

## 갱신 시점과 보존

- 요청을 받은 시점: 새 요구/정책의 후보와 실제 합의를 구별한다. 질문, 검토안만으로 현재 REQUIREMENTS를 바꾸지 않는다.
- 요구를 확정할 때: 소유 문서의 현재 요구와 관련 계약/결정을 함께 맞춘다. 같은 내용을 모든 문서에 반복하지 않는다.
- 구현, 검증 뒤: 실제 변경된 동작과 결과, 한계를 갱신한다. 구현 관측을 승인된 정책으로 자동 승격하지 않는다.
- 설치, 재분석할 때: 기존 문서와 사용자 편집은 보호하고 필요한 후보를 대조한다. 파일 배치 성공을 의미 검토 완료로 처리하지 않는다.
- 경로, 이름, 공통 계약이 바뀔 때: 영향받는 진입점, 유입 링크, 소비 문서를 함께 확인한다. 과거 결정, 원시 근거는 새 결론으로 덮지 않는다.

기존 REQUIREMENTS에 내용이 많더라도 처음부터 자동 분할하지 않는다. 읽기 연결은 유지한 채 분할 후보, 이동할 내용, 참조 변경, 복원 방법을 제시하고 별도 변경 범위를 확인한다. 실제 이동은 대상과 변경 범위를 확인한 뒤 진행한다.

## 한 기능의 복원 예제

11/09에 작성한 **설명용 가상 상품 등록 예제**다. 실제 프로젝트를 분석한 복원 문서나 실행 가능한 시험 프로젝트가 아니다. 역할과 예상 처리 내용을 가정한 설계 토의용 입력이며, 실제 검증에는 코드, 이력과 기대 결과가 있는 별도 입력을 준비한다. 필요한 사례에 맞춰 보충/수정할 수 있고 제품 완성 뒤에만 진행할 필수 실험 단계는 아니다.

### 입력과 읽을 범위

등록 요청부터 상품 저장까지를 상세 복원하고, 검색 반영은 그 완료 의미를 확인하는 연결 범위로 가정한다. 관련 공통 권한, 외부 계약, 직접 호출은 포함하되 검색 알고리즘이나 결제 내부까지 자동 확장하지 않는다. 범위 밖에서 필수 근거가 발견되면 필요한 자료, 이유를 표시해 범위 변경 여부를 확인한다.

| 역할, 원본 예시 | 입력으로 가정한 내용 | 해석할 때 주의할 점 |
| --- | --- | --- |
| REQUIREMENTS와 상품 기능 문서 | 등록은 로그인 사용자만 가능하고 가격은 0원 이상이라는 승인된 요구가 있음 | 이 문서의 가상 입력이다. 실제 프로젝트의 정책으로 채택한 것이 아님 |
| API 명세 | 가격은 필수 정수, 원 단위, 최솟값 0. 성공 응답의 상품 식별자와 오류 형식을 정의 | 대표 JSON 한 건으로 명세 전체를 대신하지 않음 |
| 요청 DTO와 호출부 | 가격의 검증 애너테이션이 양수만 허용하고 호출부가 해당 검증을 적용 | 0을 거절하는 코드 조건과 요구/명세가 불일치. 실제 HTTP 동작은 실행 미확인 |
| 상품 저장, 검색 반영 코드와 기존 설명 | 상품 저장 뒤 검색 반영을 별도로 처리하는 흐름이 보임 | 저장 완료, 검색 완료를 구별하되 실패/유실 방지까지 검증됐다고 추정하지 않음 |
| 테스트와 fixture | 정상 가격의 테스트 코드만 있고 가격 0의 기대 결과, 실행 기록은 없음 | 테스트 존재, 빠진 사례, 실제 실행 결과를 따로 기록 |
| 관련 커밋과 결정 기록 | 양수 검증이 추가된 변경은 있으나 선택 이유, 승인 기록은 없음 | 변경 사실은 연결하고 유료 상품만 허용하려 했다는 이유를 만들지 않음 |

이 자료를 같은 코드/문서 기준점에서 대조한다. 파일명이나 최신 수정 시각만으로 어느 쪽이 정책상 우선인지 정하지 않는다. 입력 버전, 문서 승인 상태가 확인되지 않으면 그 한계부터 남긴다.

### 작성할 후보의 모습

상위 REQUIREMENTS는 상품 상세로 안내하고, 상품 문서에는 아래처럼 근거와 차이를 기록한다. 실제 DTO, API 명세, fixture를 새 WIKI 사본으로 복제하지 않는다. 괄호 속 원본 위치는 실제 적용 시 확인한 파일, 절, 커밋/버전으로 연결한다.

```markdown
# 상품 등록

## 요구와 현재 구현
- 요구: 로그인 사용자만 등록할 수 있고 가격은 0원 이상이다. (승인된 요구 원문)
- 명세: 가격의 최솟값은 0이다. (기존 API 명세)
- 코드 관측: 요청 검증은 양수만 허용한다. (DTO와 검증 호출부)
- 불일치: 가격 0의 처리가 요구/명세와 다르다. 원문을 덮지 않고 확인 대상으로 남긴다.

## 처리 흐름과 관련 계약
- 상품 저장과 검색 반영의 완료 시점은 구별한다. (처리 코드, 기존 설명)
- 요청/응답 형식은 API 원문, 검색 반영 조건은 검색 문서로 연결한다.

## 선택 이력과 검증
- 양수 검증이 추가된 변경은 확인되나 당시 선택 이유, 승인은 확인되지 않았다. (관련 커밋)
- 정상 가격의 테스트 코드가 있다. 실제 실행 결과는 확인되지 않았다. (테스트, fixture)
- 가격 0, 누락, 음수, 권한 없음의 기대 결과와 검사 범위는 추가 확인이 필요하다.
```

위 내용은 검토할 후보로 만들 수 있지만 불일치가 해결된 최종 요구나 정상 동작으로 확정할 수는 없다. 기존 문서를 보호하고 차이가 없는 부분과 보류할 부분을 나눈다. 누락 목록이 비어 있다는 이유만으로 선택 이유나 검증 근거까지 존재한다고 판단하지 않는다.

### 후속 요청의 읽기와 갱신

| 후속 상황 | 읽고 확인할 것 | 바꿀 대상, 완료 판단 |
| --- | --- | --- |
| 가격 검증 수정 요청 | 적용 규칙, 공통 요구 → 상품 문서의 불일치 → 요구/명세, DTO, 호출부, 관련 검사 | 승인된 기존 요구를 지키는 수정인지 정책 변경인지 먼저 구별. 코드/검사 변경 후 실제 결과를 기록하며 같은 요구를 여러 문서에 다시 정의하지 않음 |
| 요청 필드 이름 변경 | 상품 요구, API 원본, 직렬화, 호출하는 프런트/소비자, fixture | 명세, 코드, 소비자, 검사, WIKI 연결의 변경 범위와 호환성을 함께 확인. 현재 선택 범위를 넘으면 자동 수정하지 않음 |
| 검색 반영 실패 조사 | 등록/검색 완료 의미, 전달 계약, 관련 처리, 실패 근거 | 필요한 검색 경계까지 연결. 무관한 검색 순위 알고리즘은 읽기 대상에서 제외 가능 |
| 분석 중 원본 변경 또는 중단 | 저장한 입력 기준점, 처리/미처리, 후보와 현재 원문 | 달라진 입력과 영향 후보를 대조한 뒤 재개/재분석. 옛 후보로 새 원문을 덮지 않음. 상세 상태 형식은 후속 복구 계약에서 정함 |

이 예제의 검토 기준은 요구/명세/코드의 불일치, 근거 없는 선택 이유, 테스트 존재와 실행 결과의 차이, 검색 완료 경계, 미처리/변경 입력을 놓치지 않는 것이다. 모델 비교에도 이런 기대 정보를 사용할 수 있으나 실제 평가 입력, 모델, 허용 차이, 비용을 확정하거나 평가를 실행한 것은 아니다.

## 확인할 조건

1. 기존 WIKI는 원문 보존과 역할 연결만으로 사용할 수 있고, 빈 WIKI는 선택한 범위의 상세 후보를 채울 수 있다.
2. 대표 변경에서 필수 요구, 계약, 결정, 검사에 도달한다. 링크가 유효해도 필수 계약을 빠뜨리거나 폐기된 결정을 현재 규칙으로 읽으면 실패다.
3. 기능 이름 변경, 공통 계약 변경, 새 기능 추가 뒤 목차와 유입 참조가 맞는다. 필요한 지식의 소유 위치는 하나이며 미완료 연결을 숨기지 않는다.
4. 작은 문서는 불필요하게 쪼개지 않고, 큰 문서는 무관한 부분까지 항상 읽지 않아도 된다. 상세 정보, 중요 근거의 충족을 먼저 검사한 뒤 탐색/갱신 비용을 비교한다.
5. 로컬, 상용, 혼합 분석은 같은 내용, 보존, 읽기 계약을 사용한다. 모델에 맞춰 WIKI 깊이나 필수 검사를 낮추지 않는다. 품질과 비용의 판단은 [비교 기준 — 「품질 비교 방법」](../../discussions/knowledge/reconstruction.md)을 따른다.
6. 여러 도메인을 거치는 흐름에서 필수 공통 계약을 찾고, 요구, 명세, 실제 직렬화, fixture의 역할과 기준점을 구별한다. 예시 한 건이나 생성 명세만으로 계약 전체, 검증 완료, 과거 합의를 확정하지 않는다.

모두 미실행 조건이다. [위치 연결 — 「역할별 위치 연결」](wiki.md)과 [범위별 완료 판정](wiki.md)을 함께 검토한 뒤 실제 입력, 설치/분석/검증 설계에 연결한다.

## 근거와 남은 선택

[arc42](https://docs.arc42.org/tips/1-5/)는 기존 요구를 식별해 참조하는 방법을 설명한다. [Diátaxis](https://diataxis.fr/reference/)는 기술적 참조의 객관성과 구조를 구별하며 자동 생성 참조만으로 모든 문서가 충족되지 않음을 지적한다. 두 자료를 참고해 요구, 현재 구조, 결정의 원본을 연결하되, 해당 틀 전체나 위 경로가 유일한 정답이라는 뜻은 아니다.

채택한 기본 구성은 **기존 구조를 존중하면서 짧은 공통 요구/색인과 기능, 흐름별 상세를 제공하는 방식**이다. [기존, 빈 WIKI 사례 — 「기존 문서 채택과 새 문서 복원」](wiki.md)와 함께 비교한 채택 범위는 [ADR 0014 — 「이번에 확인할 범위」](../../decisions/knowledge/0014-features.md)에 있다. 기본 이름, 정확한 분할 기준은 실제 자료와 함께 좁힌다. 현재는 설계 문서이며 템플릿, 라우팅, skill/hook을 구현한 상태가 아니다.
