# 복구 자료의 백업과 정리

2026-11-17 파일별 명세 초안이다. [복구 적용 경계 — 「복구의 대상과 경계」](recovery.md)와 채택한 자동 보존/명시적 정리를 구체화한다. 매 대화에 백업을 추가하지 않으며 제품 구현, Windows 검증이나 새 보존 정책의 채택 결과가 아니다. 일반 설치/갱신의 파일 복원은 [갱신 명세 — 「업데이트 실패 후 선택」](../runtime/update.md)를 따른다.

## 파일 구성과 보장 범위

아래 경로는 적용 프로젝트의 `.harness/state/` 안에서 필요한 때만 만드는 후보다. 자료 보존과 정리는 제품의 명시적 정리 계약을 따른다.

| 자료 | 역할과 보호 |
| --- | --- |
| `state.db`, `active.md` | 현재 진행 원본과 문맥. 정리할 설치기 사본과 구분하며 전체 폴더 삭제 대상이 아님 |
| `plans/<plan_id>/`, `runs/<attempt_id>/` | 기존 후보, 적용 전 사본과 결과. 백업은 선택한 복구 범위에 필요한 자료를 내용 기준으로 수집 |
| `backups/<backup_id>/state.db` | SQLite Backup API로 만든 별도 DB 사본. 원본과 연결을 공유하거나 이 사본에서 작업을 계속하지 않음 |
| `backups/<backup_id>/files/` | 복구에 필요한 파일 사본. 원래 역할/경로와 백업 내부 상대경로의 대응을 목록에 남김 |
| `backups/<backup_id>/manifest.json` | DB와 파일 목록, 대상과 복구 가능 범위를 설명하는 불변 목록. 저장과 검사를 마친 뒤 마지막에 확정하며 실행 진행의 두 번째 원본이 아님 |
| `runs/<attempt_id>/` 안의 변환 후보 DB와 검사 결과 | 지원하는 형식 변경에만 생성. 기존 DB를 보존하며 새 쓰기 원본으로 전환하기 전까지 후보로 구별 |

백업 목록에는 백업 식별자, 원본 DB 식별/형식, 프로젝트 대상, 포함한 작업/계획 기준, DB와 파일의 크기/해시, 부재 상태, 제외한 범위와 미해결 상태를 담는다. JSON의 논리 필드는 아래 백업 목록 절이 소유하며 엄격한 입력 검사와 직렬화 코드는 후속이다. 파일 참조는 목록 안의 상대경로로 검증하고 경로 탈출, 중복 대응, 링크를 통한 외부 파일 혼입은 허용하지 않는다. 기기별 실제 경로가 필요한 기록은 로컬 제외 영역에만 둔다.

**DB 사본에 과거 이력이 들어 있다는 것과 그 이력 전부를 복구할 수 있다는 것은 다르다.** 선택한 작업의 계획, 의무, 원래 시도, 복원 시도와 필요한 파일까지 참조를 따라 확인한다. 범위 밖 작업의 파일을 제외했다면 제외 사실을 표시한다. 백업 폴더를 다시 백업 안에 재귀 복사하지 않는다. 다른 백업에만 의존하는 후보는 자체 복구 가능한 완성본으로 표시하지 않는다.

예를 들어 업데이트 두 단위가 같은 파일을 바꿨다면, 마지막 파일의 사본만으로 요청 시작 전 상태를 설명할 수 없다. 해당 요청의 적용 순서와 앞선 사본도 포함해야 한다. 사용자 코드/WIKI 전체의 재해 복구, 다른 작업의 모든 시점 복구, 장치 전체 유실 보호까지 제공하는 안은 아니다.

## 백업 생성과 다시 읽기

[SQLite Backup API](https://www.sqlite.org/backup.html)와 [Python의 backup](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.Connection.backup)은 DB의 일관된 사본을 만드는 수단이다. DB 밖의 로그, active와 복원 사본까지 같은 시점으로 묶어주지는 않으므로 아래 대조는 제품 코드의 책임이다.

1. 필요한 작업과 파일을 정하고 기존 [실행 소유 — 「실행 소유의 식별과 반환」](recovery.md)로 관리되는 새 반영과 정리를 조정한다. 긴 AI 실행이나 계속 기록되는 로그는 종료 여부를 먼저 판단한다. 끝나지 않은 출력을 완료 근거로 포함하지 않는다.
2. 새 백업 폴더에 DB 사본을 만들고 사본에 기록된 참조를 기준으로 파일을 수집한다. 필요한 active가 원래 없으면 부재를 기록한다. 긴 파일 복사 동안 SQL 쓰기 트랜잭션을 유지하지 않는다.
3. 파일 내용과 실제 대상, 원본의 관련 계획/진척 기준을 다시 대조한다. 수집 도중 새 반영이나 참조 변경이 있으면 해당 후보를 완료로 확정하지 않는다. 잠금 이름의 존재만으로 외부 편집까지 막혔다고 판단하지 않는다.
4. DB 무결성, 외래 키와 필수 참조, 백업 내부 파일의 내용을 검사한다. 저장과 닫기가 확인된 뒤 완성 목록을 마지막으로 확정한다. 정확한 Windows 저장/교체 수단과 강제 종료 내구성은 실제 구현 시험 대상이다.
5. 다시 읽을 때도 목록 존재만 믿지 않고 DB 식별/형식, 포함 범위와 파일 대응을 확인한다. 중단, 용량 부족이나 목록 저장 실패의 잔여물을 유효본으로 승격하지 않으며 직전 유효본을 보존한다.

DB 사본에서 `integrity_check`가 성공해도 외래 키, 파일 존재와 업무 의미까지 검증된 것은 아니다. 세 검사는 각각 필요한 범위로 수행한다. 복구의 필수 자료가 빠지면 무엇이 빠졌는지 알리고 관련 반영을 보류한다. 자동으로 백업 범위를 줄이지 않는다.

오래된 사본을 읽어 기록 복구 후보를 만들 때는 현재 DB와 파일을 먼저 보존한다. 특히 일부 작업만 보장하는 백업으로 전체 `state.db`를 자동 교체하면 다른 작업의 후속 기록을 잃을 수 있다. 전체 전환에 필요한 작업과 후속 효과를 대조할 수 없다면 기록 비교까지만 진행하고 쓰기 전환을 보류한다. 과거 DB의 미실행 상태를 근거로 이미 실행한 파일 반영이나 PR 생성을 반복하지 않는다.

## DB 형식 변경과 전환

공식 모듈 버전과 DB 형식은 별개다. 같은 형식을 지원하는 업데이트에는 변환을 추가하지 않는다. 형식 변경이 필요하면 [이전 실행의 읽기와 쓰기 호환 — 「DB 형식과 이전 구성의 호환」](storage.md)을 먼저 확인하고, 기존 구성 사용으로 돌아갈 수 있는 경로까지 반영 전 조건에 포함한다.

| 순서 | 처리와 중단 시 기준 |
| --- | --- |
| 지원 확인 | 원본의 `metadata.schema_version`과 배포물의 지원 변환 경로 확인. 알 수 없는/새 형식이나 손상은 초기화하지 않음 |
| 기준 보존 | 관련 실행을 정리하고 검증된 백업 확보. 변환 중 원본에 새 쓰기가 생겼다면 해당 후보를 그대로 전환하지 않음 |
| 후보 변환 | 지원하는 출발/도착 형식에 정해진 코드만 별도 DB 사본에 실행. 원래 작업, 시도와 의무의 식별/의미를 보존 |
| 후보 검사 | DB/외래 키, 참조 파일, 데이터 대응과 실제 조회/쓰기 계약을 확인. 원본과 후보의 단순 전체 해시 일치는 요구하지 않음 |
| 전환 | 열린 DB 연결과 관련 작성자가 없는 조건에서 기존 DB를 보존하고 검증한 후보를 연결. 원본/후보 식별, 변환 기준과 전환 의도를 전환 전에 보존 |
| 사용 확인 | 실제 연결 대상/형식과 다음 조회/쓰기를 확인한 뒤 정상 진행. 전환 후 새로운 기록이 있으면 옛 DB를 덮어쓰는 복귀 금지 |

전환 직전/도중/직후에 끊기면 현재 경로의 DB, 보존 원본, 후보와 전환 전 근거를 함께 대조한다. 파일명이나 최신 수정 시각만으로 새 원본을 선택하지 않는다. DB 경로가 비었거나 양쪽의 내용/진척이 예상과 다르면 재개 쓰기를 멈추고 원본을 모두 보존한다. 전환 의도의 저장/조회는 아래 「DB 전환 의도」를 따르며 실제 Windows 교체와 재개 검증은 후속이다. 단일 파일 교체 호출만으로 여러 자료의 원자적 전환을 보장하지 않는다.

[SQLite의 손상 안내](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)는 실행 중 파일의 임의 복사와 DB에 대응하는 journal의 유실/혼합을 경고한다. 사용 중 DB를 덮거나 `-journal`, `-wal`, `-shm`을 임시 파일처럼 정리하지 않는다. 정상 종료/복구와 연결 해제를 확인한 DB만 전환 대상으로 삼고, 복구가 필요한 원본과 보조 파일은 대응을 보존한다.

## 기존 DDL과 인계의 연결

[DDL](schema.sql)은 정상 실행에서 이력 변경/삭제와 완료 근거의 뒤늦은 추가를 제한한다. 따라서 기존 행을 빈 DB에 임의 순서로 삽입하거나 최신 DDL을 실행하면 곧바로 인계/변환이 끝난다고 볼 수 없다.

- 같은 형식의 백업 사본은 SQLite Backup API로 만든다. 일반 INSERT로 종료된 시도의 관계를 재생성하는 우회를 기본으로 삼지 않는다.
- 형식 변경은 변환 대상 사본 안에서만 버전별 절차로 수행한다. 제약을 재구성해야 한다면 최종 외래 키, 트리거와 view를 복구하고 정상 실행용 연결에서 거부 조건까지 검사한 뒤 채택한다. 동작 중인 원본의 보호 장치를 해제하지 않는다.
- 최초 인계 B는 같은 형식의 전체 DB 사본을 새 후보에 만든 뒤 [인계 단계와 쓰기 허용](storage.md)을 따른다. 논리 DB 식별과 이력을 보존하되 대상 수신, 초기 원본 확인과 대상 활성화를 별도로 검증한다. 사본 생성만으로 실제 인계를 완료 처리하지 않는다.

SQLite의 [형식 변경 안내](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes)는 테이블 재구성 시 관련 인덱스, 트리거, view와 외래 키 검사를 함께 다룬다. 이는 제품 변환 절차를 설계할 근거이며, 현재 SQL의 어느 제약이든 자유롭게 끄도록 허용하는 안이 아니다. 변환 전후 행 개수만 맞추는 검사도 충분하지 않다.

### 사본과 인계와 형식 변경의 구분

11/17 채택한 [최초 인계 B — 「최초 인계 방식 재검토」](storage.md)는 새 후보에만 사본을 만들고 수신/확인/활성화 뒤 진행 위치를 전환한다. 살아 있는 기존 DB를 덮거나 복사만으로 인계 완료를 인정하지 않는다. 기존 행별 수신과 당시 검사는 [판단 이력 — 「최초 기록의 행별 수신안」](../../discussions/history/install.md)으로 보존한다.

| 목적 | 보존할 내용과 완료 전 확인 |
| --- | --- |
| 같은 형식의 DB 백업 | DB 식별/형식, 행과 제약을 그대로 보존. 파일 사본/목록과 실제 복구 범위를 별도로 검사. 새 대상의 수신 사실은 생성되지 않음 |
| 최초 기록 인계 | 초기 설치 DB의 전체 이력과 논리 식별/revision을 보존하고 진행 위치만 전환. 실제 원본/대상, 필요한 파일과 수신/원본 확인/활성화 대응 필요 |
| DB 형식 변경 | 같은 진행 원본의 의미와 이력을 지원 형식으로 변환. 출발/도착 형식별 대응, 최종 제약과 읽기/쓰기 호환 검증 필요 |

[Backup API](https://www.sqlite.org/backup.html)는 대상 DB의 기존 내용을 사본으로 대체하므로 살아 있는 프로젝트 DB에 직접 실행해 인계를 대신하지 않는다. 새로운 백업/후보에만 사용하고, 최초 인계에는 [유지 관리 기록의 인계 순서](storage.md)를 적용한다. [7개 합성 검사](../../evidence/experiments/recovery/2026-11-17_10-01-07-maintenance-handoff.md)의 사본 대조는 같은 DB 식별과 전체 스키마/행의 보존을 확인했으며 target 수신/활성화나 새 형식의 성공이 아니다.

형식 변경이 필요한 배포마다 출발/도착 형식의 명시적 대응을 둔다. 지원하는 변경이 없으면 변환을 시작하지 않는다. 현재는 배포된 옛 형식과 새 형식 사이의 실제 변환 코드가 없으며, 합성 metadata 숫자를 지원 버전으로 안내하지 않는다. 변환 후보는 아래 조건을 모두 대조한 뒤에만 전환할 수 있다.

1. 원래 요청/계획/의무, 결과와 반영/복원 연결의 의미를 보존한다. 필드 이름이나 형식이 달라져도 원래 실패/성공, 입력 범위와 관계를 임의로 생략하지 않는다.
2. 백업/전환/보호/정리 기록을 함께 대응한다. 해제된 보호가 다시 활성화되거나 정리 확정된 근거가 새 완료/복원에 쓰일 수 있게 되면 실패다. 과거 전환의 출발/도착 형식을 새 형식으로 덮지 않는다.
3. DB 무결성/외래 키와 예상 테이블, 인덱스, 트리거, view 정의를 확인한다. 정의 존재뿐 아니라 현재 보호 자료 정리, 정리된 근거 재사용과 확정 이력 변경이 계속 거부되는지 별도 시험 사본에서 검사한다. 변환 후보에 시험 행을 남기지 않는다.
4. 자료 목록의 실제 파일, 남은 복구 범위와 지원 실행의 조회/쓰기 호환을 확인한다. 내용 해시가 다른 새 후보를 원본의 변환 전 해시와 같아야 한다고 요구하지 않는다. 대신 명시한 의미 대응과 후보 자체의 확정 해시를 사용한다.
5. 원본 기준이 달라졌거나 중단/오류로 대응을 확정할 수 없으면 후보를 채택하지 않는다. 원본, 검증된 보존본과 미완료 근거를 유지하며 자동 초기화/역변환으로 진행하지 않는다.

현재 DDL의 정상 쓰기 경로에 과거 상태를 다시 입력할 때의 한계는 [과거 형식 변경 기록의 수신 경계](storage.md)에 남겼다. 형식 변환 후보의 재구성과 최초 인계의 수신을 무조건 같은 함수나 트랜잭션으로 합치지 않는다. 수신 보완과 구체 변환 경로가 검증되기 전에는 전체 이관 가능으로 표시하지 않는다.

## 정리 대상과 남길 기록

[설치 완료 뒤 정리](../runtime/install.md)의 확인 흐름과 후속 명시적 정리 명령은 아래 판별을 공유한다. 정리는 날짜순 삭제나 DB `VACUUM`과 구분한다.

| 자료 묶음 | 후보로 제시할 조건 | 계속 보호할 조건 |
| --- | --- | --- |
| 다운로드/해제 사본 | 설치 완료, 실행 의존 없음, 필요한 공식 기준 확보 | 현재 실행기나 이후 갱신의 유일한 기준 |
| 최초 외부 보존 묶음 | target 인계/활성화와 실제 사용 확인, 사본 대응 확인 | 수신/전환 미확인, target 손상/누락, 다른 미해결 참조 |
| 미완성 후보, 사용하지 않은 백업 묶음 | 소유와 내용 확인, 필수 복구와 다른 보존본의 의존 없음 | 직전 유효본, 유일한 필요한 사본, 소유 불명 |
| 완료 작업의 큰 로그, 후보와 복원 사본 | 11/17 범위 채택. 현재 의존을 대조하고 잃는 복구 범위를 안내한 뒤 확인 | 작업 이력/정리 사실은 DB에 보존. 미해결/재사용/복원 의무와 연결된 자료 보호 |
| 현재 DB, active, 설치 자산, 코드/WIKI 원문 | 설치 후 정리 대상이 아님 | 경로가 정리 폴더 안으로 잘못 연결돼도 원문 보호 |

삭제 전에 보여줄 목록은 묶음 식별, 실제 소유 경로, 파일/부재 기준, 예상 회수 용량, 잃는 복구 범위와 남는 유효본을 포함한다. 관련 실행/참조가 생기면 필요 여부를 다시 판단한다. 대상이나 삭제 영향이 달라졌으면 기존 확인으로 삭제하지 않으며, 무관한 기록 변경만으로 같은 확인을 다시 받지는 않는다. 경로만 같은 새 파일, 경로 밖으로 나가는 링크, 모르는 파일은 삭제하지 않는다. 부모 폴더를 통째로 지우는 방식으로 목록 확인을 대신하지 않는다.

삭제의 대상/확인과 진행 근거는 지울 외부 사본이 아니라 프로젝트의 보존 기록에 남긴다. 삭제 중 종료되면 남은 같은 파일, 이미 없는 파일과 바뀐 파일을 나눠 재개한다. 파일이 없다는 사실만으로 우리가 삭제에 성공했다는 이력을 새로 만들지 않는다. 앞선 결과와 대조해 부재 관측을 남기며, 바뀐 자료는 보존하고 안내한다. 같은 묶음의 재시도에 확인을 반복하지 않되 허용 범위를 확대하지 않는다.

정리 범위는 아래 [정리 허용과 실제 제거](maintenance.md#%EC%A0%95%EB%A6%AC%20%ED%97%88%EC%9A%A9%EA%B3%BC%20%EC%8B%A4%EC%A0%9C%20%EC%A0%9C%EA%B1%B0)의 11/17 사용자 선택과 필드 후보로 구체화했다. [schema.sql](schema.sql)에 승인, 정리 확정과 관측 관계를 반영했다. 실제 파일 삭제 구현은 아직이다. 일반 apply/restore 성공으로 정리 결과를 가장하거나 모든 테이블의 삭제 보호를 해제하지 않는다. 아래 소비자의 재사용/복원 차단까지 구현/검증하기 전에는 정리 가능하다고 표시하지 않는다.

DB 안의 논리 자료 정리와 실제 용량 회수도 다르다. [VACUUM 공식 설명](https://www.sqlite.org/lang_vacuum.html)에 따르면 DB 재구성에는 추가 디스크 공간과 실행 조건이 필요하다. 정리할 자료를 결정하는 기능으로 사용하지 않으며, 매 작업 뒤 자동 실행하지 않는다. 회수량은 실제로 확인하고 공간 부족 때문에 보호 자료를 먼저 지우지 않는다.

## 저장 필드와 소비자

11/17 후속 명세다. 기존 `tasks`, `plans`, `attempts`의 요청/계획/시도 구분과 짧은 트랜잭션을 재사용한다. 아래 관계는 [DDL](schema.sql)에 반영한 설계 후보이며 메모리 SQL 검사와 실제 제품 구현을 구분한다. 별도 진행 DB나 JSON 상태 엔진을 추가하지 않는다. 백업/형식 변경/정리는 파일 적용 성공과 의미가 달라 기존 `apply`/`restore` 결과로 가장하지 않는다.

| 기존 관계 | 확장 후보와 소비 |
| --- | --- |
| `plans.kind` | `maintenance`를 추가해 변경되지 않는 대상, 사전 조건과 완료 조건을 보존. 일반 설치 단위의 파일 패치 계획과 구별 |
| `attempts.kind` | `backup`, `migrate`, `cleanup`을 추가. 현재 시도 식별, 이전 시도, 준비/미확인/종료와 짧은 저장을 재사용. 이 종류에는 가짜 검사 명령, exit code나 설치 unit을 넣지 않음 |
| 종류별 연결 제약 | 새 종류는 유지 관리 계획에만 연결. 기존 verify/apply/restore/handoff와 단위/명령 제약은 유지 |
| 결과 조회 | 실행 종료와 작업 완료를 구별. 파일 대조와 종류별 완료 근거가 있어야 완료로 반환하며 SQL 저장 성공만으로 판정하지 않음 |

### 백업 목록과 등록

`manifest.json`은 완성된 백업의 불변 내보내기 자료다. 현재 작업 진행은 DB가 소유한다. DB의 백업 등록은 이 파일의 위치/내용을 참조하며 같은 목록을 별도 수정 가능한 JSON 열과 파일 양쪽에서 관리하지 않는다.

| 목록 필드 후보 | 의미와 검증 |
| --- | --- |
| `id`, `attempt_id`, `created_at` | 백업과 생성 시도, 기록 시각. 재시도마다 이전 완성 목록을 덮지 않음 |
| `source` | 원본 `db_id`, `schema_version`, 작업 사본 식별과 코드/WIKI 루트의 역할. 개인 인증이나 불필요한 환경 전체를 수집하지 않음 |
| `scope` | 포함한 task/plan, 기준 revision과 필수 의무의 참조. revision은 해당 원본에서의 비교값이며 다른 DB의 저장 횟수와 혼동하지 않음 |
| `database` | 사본의 백업 내부 상대경로, 바이트 크기와 SHA-256. 복사 중인 DB의 중간 해시를 완성본 기준으로 쓰지 않음 |
| `files` | 항목별 역할, 원래 root/path, artifact 참조가 있으면 그 ID, 백업 내부 상대경로, 존재/부재와 크기/해시. 부재에는 사본 경로/해시를 만들지 않음 |
| `excluded`, `unresolved` | 제외한 범위와 미해결 사실. 빈 값과 확인하지 못한 값을 구별하고 복구 가능 범위를 함께 표시 |

DB의 `backups` 후보에는 `id`, 생성 `attempt_id`, 목록 경로/해시, 완성 관측 시각을 둔다. 목록 자체의 해시를 목록 안에 넣지 않으며 DB 사본 안에 자기 완성 등록이 반드시 있어야 한다고 요구하지 않는다. **사본 생성 → 목록 확정 → 현재 DB에 등록** 순서이므로 생성 중인 자신의 완료 기록을 백업에 넣으려는 순환을 피한다.

목록 확정 뒤 등록 전에 끊겼으면 준비 시도와 실제 목록/파일을 대조해 등록을 마친다. 폴더 스캔에서 발견한 임의 파일을 자동 등록하지 않는다. 같은 ID/같은 목록이면 기존 등록을 재사용하고 다른 내용이면 보존 후 충돌로 반환한다. 등록 뒤에도 파일 대조가 실패하면 현재 사용할 수 없는 백업으로 표시하며 과거 완성 사실 자체는 지우지 않는다.

### DB 전환 의도

전환 의도를 바꿀 DB 안에만 저장하면, 그 경로가 비거나 잘못 연결된 중단에서 의도 자체를 읽지 못할 수 있다. 이를 위해 **전환 직전의 불변 `state/transition.json` 한 개**를 후보로 둔다. 진행 이벤트를 계속 추가하는 두 번째 원본이 아니라, DB 연결을 바꿀 때 사용할 원본/후보 대응표다. 동일 상태 영역에서 둘 이상의 전환을 동시에 준비하지 않는다.

| 필드 후보 | 역할 |
| --- | --- |
| `attempt_id`, `source`, `candidate` | 같은 형식 변경 시도, 원본과 후보의 DB 식별/형식, 상태 영역 안의 위치와 닫힌 파일의 해시 |
| `backup_id`, `manifest_sha256` | 전환 전에 확인한 보존본. 다른 백업의 완료 결과를 대체하지 않음 |
| `target`, `compatibility` | 실제 교체 대상과 검증한 지원 실행/이전 구성의 읽기/쓰기 조건에 대한 결과 참조 |

같은 DB의 `transitions`에는 `attempt_id`, `source_version`, `target_version`, `candidate_path`, `backup_id`, `report_id`, `activated_at`, `activation_json`을 둔다. 후보 경로는 준비 때 고정하고 닫힌 파일의 최종 해시는 전환 의도에 보존한다. 검사 자료는 같은 시도의 assessment이며 실제 전환 관측은 별도로 추가한다. 준비 기록을 원본에 저장하고 후보를 만든 뒤, 원본/후보의 연결을 닫고 추가 쓰기를 멈춘 상태에서 파일 해시를 계산해 의도를 확정한다. 그 뒤 원본 DB에 목록 해시를 쓰느라 기준 바이트를 다시 바꾸지 않는다. 후보의 전환 완료는 실제 대상 연결을 확인한 뒤 저장한다.

설치/갱신 등 관리하는 변경의 진입은 남은 의도를 먼저 대조하고, 미완료 전환을 무시한 채 일반 쓰기를 시작하지 않는다. 일반 설명이나 문서 읽기마다 이 파일/DB를 조회하는 방식으로 확대하지 않는다. 전환 성공 뒤에는 의도 사본을 해당 시도 자료에 보존한 다음 임시 진입 표시를 해제하는 순서를 검증한다. 이때도 앞선 의도가 남았다고 무조건 형식 변경을 반복하지 않는다. 보존/해제 도중 종료와 새 쓰기 이후의 상태를 대조하며, 정확한 파일 교체/저장 내구성은 Windows 시험 대상이다. 보조 파일이나 DB 연결이 남은 상태의 해시만으로 전환을 강행하지 않는다.

### 정리 허용과 실제 제거

11/17 사용자 선택으로 **완료됐고 현재 복구에 필요 없는 큰 로그, 후보와 복원 사본도 명시적 정리에 포함**한다. 작업 이력과 정리 사실은 DB에 남긴다. 아직 필요한 자료는 보호하며, 단순히 과거 행에 ID가 있다는 이유로 모든 완료 파일을 영구 보존하지는 않는다. 역사적 참조와 현재 유효한 복구/재사용 의존을 구별해야 한다.

| 관계 후보 | 주요 필드와 책임 |
| --- | --- |
| `cleanup_plans` | 계획별 고정 목록/영향 해시와 항목 수. JSON 해시 계산은 공통 코드, 확인과 목록의 대응은 SQL이 검사 |
| `cleanup_items` | 유지 관리 `plan_id`, `item_id`, 역할/소유 위치, 실제 파일 식별/내용 기준, 예상 크기, artifact 또는 backup 참조, 삭제 영향. 승인 전에 확정한 파일 목록이며 상위 폴더 전체 삭제 권한이 아님 |
| `cleanup_decisions` | `id`, `plan_id`, `previous_id`, 표시한 목록/영향의 해시, `approved`/`kept`/`cancelled`, 확인 출처/시각. 비밀 대화나 계정 토큰은 저장하지 않음. 같은 확인은 재사용하고 범위 확대는 새 계획/확인이 필요 |
| `cleanup_claims` | 승인, 시도와 항목의 연결, 제거 직전 재대조 근거. 이 항목을 현재 재사용 후보에서 제외했다는 사실이며 삭제 완료를 뜻하지 않음 |
| `cleanup_observations` | 시도/항목과 앞선 관측, `removed`/`absent`/`changed`/`blocked`/`unknown`, 실제 관측과 오류 원인, 시각. 수정 대신 새 관측을 연결하며 원래 실패를 지우지 않음 |

삭제 순서는 **목록/영향 제시 → 확인 → 현재 의존/내용 재대조 → DB에서 정리 항목 확정 → 파일 처리 → 관측 저장**이다. 확인 대기나 실제 파일 삭제 동안 DB 트랜잭션을 계속 열지 않는다. 정리 항목 확정과 새 재사용/복구 참조의 등록은 같은 공통 기록 경로에서 충돌을 검사해, 대조 직후 새 의무가 생겼는데 삭제하는 일을 막는다. 사용자나 외부 도구의 임의 DB/파일 편집까지 트리거가 통제한다고 보장하지 않는다.

정리 확정 뒤부터 해당 파일은 새로운 결과 재사용과 복원 대상에서 제외한다. 삭제가 실패해 파일이 아직 있어도 자동으로 재사용 가능 상태로 돌리지 않는다. 재개하면 같은 확인과 항목 기준으로 남은 삭제를 대조하고, 보관으로 바꾸려면 현재 파일과 의존을 재확인한다. 오래된 PASS를 되살려 검사나 복원을 생략하지 않는다. 정리가 끝나지 않아도 설치 성공을 취소하거나 설치를 반복하지 않는다.

파일이 이미 없으면 부재 관측을 남긴다. 삭제 호출 성공과 직후 부재를 확인했을 때의 `removed`, 호출 여부를 확인할 수 없지만 현재 없는 `absent`를 구별한다. 다른 내용으로 바뀌었거나 소유/참조를 판단할 수 없으면 보존하고 이유를 반환한다. 재시도는 새 시도로 같은 승인/항목에 연결하며, 어느 파일에서 멈췄는지 남긴다. 확인을 보관/취소로 바꾸면 마지막 결정을 따라 새 삭제를 멈춘다. 이미 수행된 효과의 뒤늦은 관측은 보존하며 취소를 과거 사실 삭제로 사용하지 않는다.

### 현재 필요한 자료의 보호

`resource_holds`는 현재 의무가 어떤 artifact 또는 backup을 필요로 하는지 기록한다. 과거 참조 전체를 보호 목록으로 복제하는 테이블이 아니다. 보호를 등록한 작업, 자료 식별, 이유/시각을 남기고 필요가 끝나면 해제 시각과 이유만 한 번 추가한다. 행을 지우거나 옛 해제를 취소하지 않는다. 새 필요는 새 보호 기록으로 남긴다.

예를 들어 옛 테스트 결과를 다음 단위의 근거로 쓰려면 필요한 로그를 보호한다. 먼저 보호가 등록됐다면 정리 확정이 거부되고, 정리 확정이 먼저 됐다면 새 보호와 결과 사용이 거부된다. 같은 로컬 DB의 짧은 쓰기 트랜잭션에서 두 순서를 대조한다. 팀 전체의 공용 잠금이나 매 대화의 등록 절차가 아니다.

**보호 행이 없다는 사실만으로 삭제해도 된다고 판단하지 않는다.** 공통 코드는 진행 중/미해결 작업, 재사용/복원 의무, 필수 기준과 백업에서 필요한 자료를 따라가며 보호를 등록하고 해제한다. 이 연결이 누락되거나 소유를 판단하지 못하면 정리를 보류한다. SQL은 미등록 의존이나 실제 파일의 사용 여부를 추론하지 못한다. DB 형식 전환 준비에는 현재 작업이 보호하는 백업을 요구한다.

### SQL에서 막는 범위

- 정리 목록이 완성되기 전 확인, 목록/영향 해시가 다른 확인, 마지막 승인이 아닌 확인으로 새 정리 확정을 만들 수 없다. 목록을 보여준 뒤 항목을 추가하거나 승인 이력을 수정/삭제하지 않는다. 정리용 재대조 자료 자체도 같은 정리에서 제거하지 않는다.
- `cleanup_claims`가 생기면 `retired_artifacts`, `retired_backups`, `retired_results` 조회가 새 소비에서 해당 자료를 제외한다. 파일 삭제 성공을 기다리는 표식이 아니므로 실패해 파일이 남아도 오래된 근거를 자동으로 되살리지 않는다.
- 결과 재사용과 새 단위/전체 복원 완료, 후보의 새 적용, 사본의 새 복원, 전환 백업과 새 보호에 이 제외 조건을 연결했다. 준비 뒤 정리가 확정된 경우도 완료 때 다시 대조한다. 과거 results와 완료 행은 바꾸지 않는다.
- `result_artifacts`에는 그 결과를 지지하는 필수 근거만 연결하며 그중 하나라도 정리되면 새 완료용 조회에서 제외한다. 선택적인 진단 파일은 별도 artifact로 보존한다. 선택 로그와 필수 근거를 나누는 의미 판단은 공통 코드가 맡고, 이미 완료에 쓴 목록을 뒤늦게 줄이지 않는다.
- `cleanup_observations`는 항목별 한 방향의 관측을 보존한다. 정리 확정 없는 제거 완료, 다른 항목으로의 연결과 관측 덮어쓰기를 거부한다. `observed_cleanups`는 모든 항목의 removed/absent 관측이 있는 계획을 조회할 뿐 실제 삭제/용량 회수나 제품 완료의 증명은 아니다.

SQL이 비교하는 파일 위치는 저장된 root/path/해시다. Windows 경로 대소문자, 다른 경로로 연결된 같은 파일, 링크와 파일 ID, 사용자 편집/권한은 공통 코드에서 다시 확인해야 한다. 해시 문자열 일치도 실제 파일 해시를 계산했다는 증명이 아니다. 삭제 직전 최신 승인과 목록을 다시 확인하고 실행 소유를 유지한 채 파일을 다루는 구현이 필요하다.

[SQLite의 외래 키](https://www.sqlite.org/foreignkeys.html)는 연결마다 활성화해야 한다. [RAISE(ABORT)](https://www.sqlite.org/lang_createtrigger.html#the_raise_function)는 실패 문장을 거부하므로 호출자는 [명시적 트랜잭션](https://www.sqlite.org/lang_transaction.html)의 앞선 저장도 취소할지 처리해야 한다. 정리 확정 저장이 취소됐는데 파일부터 삭제하는 순서는 허용하지 않는다.

### 정리 뒤 조회와 복구

| 소비자 | 지켜야 할 결과 |
| --- | --- |
| 이력 조회 | 당시 성공/실패와 정리 사실을 함께 표시. 로그가 정리됐다고 과거 결과를 FAIL로 바꾸지 않음 |
| 검사 결과 재사용/새 완료 판정 | 필요한 artifact가 정리 확정됐거나 없으면 해당 근거로 새 완료를 만들지 않음. 일부 로그만 지웠다면 그 자료가 필수였는지 검사 의무에서 판단 |
| 파일 복원 | 필요한 사본이 없으면 복원 가능하다고 안내하지 않음. 해시나 후보 내용을 이용해 원문을 추정 생성하지 않음 |
| 백업과 DB 형식 변경 | 현재 필요한 참조는 보호. 과거 완료 파일의 의도된 정리와 무단 유실을 구별하고 오래된 백업으로 후속 정리 이력을 없애지 않음 |
| 용량 안내 | DB 이력, 남은 파일/백업과 실제 회수량을 분리. 날짜/추정 크기만으로 자동 삭제하지 않음 |

완성된 백업이 필요한 파일을 자기 폴더에 독립 사본으로 보존했다면, 같은 artifact ID가 그 DB 사본에 남아 있다는 이유만으로 현재 실행 폴더의 파일까지 영구 보관할 필요는 없다. 백업의 자체 사본/목록이 유효한지 확인하고 현재 작업의 의존은 별도로 검사한다. 반대로 원래 파일 없이는 복구할 수 없는 백업은 그 파일을 정리할 근거가 아니다. 백업 안의 사본 자체를 지우는 것은 별도의 정리 묶음과 영향 확인을 따른다.

보호할 대상은 미해결/진행 중인 작업, 현재 재사용 대상으로 확정된 의무, 유지해야 하는 비교 기준, 필요한 백업과 실제 사용 중 파일에서 시작해 관련 사본까지 따라간다. 이 범위를 확정할 수 없으면 정리하지 않는다. 이력의 ID 참조는 유지하므로 기존 행의 일반 DELETE 보호와 양립하며, SQL 완료용 조회와 애플리케이션의 근거 조회 양쪽에 정리 상태를 연결해야 한다. `cleanup_claims`를 만들기만 하고 소비자가 계속 옛 결과를 재사용하면 구현 실패다.

## 공통 입력과 파일 대조

아래는 앞선 DDL을 호출할 일반 코드의 입력 계약이다. 별도 진행 DB나 수정 가능한 목록 파일을 추가하지 않는다. 저장 값의 공통 형식은 [저장 값의 형식](storage.md), 실행 조정과 파일 API 후보는 [파일 반영과 핸들 수명](../runtime/update.md)을 따른다. 현재는 명세이며 해당 검사 코드나 Windows 삭제 기능을 구현한 상태가 아니다.

예를 들어 끝난 검사에만 쓰인 로그 A와 아직 실패한 업데이트를 복원할 사본 B가 있다면, A는 잃는 근거를 안내한 뒤 정리 후보가 될 수 있지만 B는 보호한다. 승인 뒤 A의 경로에 다른 파일이 생겼다면 그 파일을 지우지 않는다. A를 이미 정리한 뒤 재실행했을 때도 같은 이름의 새 파일을 다시 삭제하지 않는다.

### 현재 의존을 찾는 입력

정리 후보에서 관련 작업과 소비자를 따라간다. 모든 이력 본문을 AI에 전달하거나 과거 외래 키 참조 전부를 현재 보호로 복제하지 않는다. 같은 실제 파일을 가리키는 다른 ID/경로와, 현재 요청의 이전 계획에서 남긴 효과도 확인 범위다.

| 소비자 | 확인할 근거와 보호 해제 조건 |
| --- | --- |
| 진행 중이거나 효과가 미확인인 시도 | 현재 계획, 준비/실행 상태, 미해결 이유와 실제 효과. 프로세스가 없거나 시도가 종료됐다는 이유만으로 사본을 해제하지 않음 |
| 검사 재사용과 완료 판정 | 해당 의무, 현재 입력과 연결된 결과/필수 근거. 같은 의무를 유효한 후속 검사로 대체했거나 그 의무의 필요가 끝났는지 확인. 다른 작업의 PASS로 대체 금지 |
| 적용과 복원 | 이번 요청의 모든 반영 단위, 이전 계획의 반영, 복원 선택과 필요한 사본. 단위 하나의 성공을 요청 전체 완료로 취급하지 않음 |
| 인계와 DB 전환 | 원본/대상의 수신, 확인, 활성화 및 실제 연결. 미완료 인계나 남은 전환 의도가 필요한 자료는 유지 |
| 공식 비교 기준과 백업 | 현재 필요한 기준, 보존해야 하는 유효본과 참조 파일. 대체본의 범위/내용/복구 가능성을 확인하기 전 기존 보호 해제 금지 |

각 소비자의 판정은 `required`, `not_required`, `undetermined`와 이유, 작업/계획/시도/결과 참조, 대조한 revision과 입력/파일 기준으로 남긴다. 이 묶음은 기존 assessment 자료의 `dependencies` 목록에 담는 후보다. 각 항목은 `resource`, `consumer`, `requirement`, `reason`, `basis`를 가지며, DB 열의 상태를 다시 수정하는 원본이 아니다. 파일 이름이나 이유 문장을 파싱해 소비자를 추론하지 않는다. 후보에 연결된 소비자 중 하나라도 필요하거나 판단 불가이면 정리를 막는다.

현재 DDL에는 요청 전체의 완료를 뜻하는 단일 상태 열이 없다. 따라서 `running` 시도가 없거나 단위별 성공 행이 있다는 사실만으로 `not_required`를 만들지 않는다. 기능별 완료/대체 근거를 확인하고, 그 근거가 아직 정의되지 않은 소비자는 `undetermined`로 보존한다. 옛 실패도 같은 의무가 유효하게 해소됐다면 그 이유만으로 영구 보호하지 않는다.

새 소비를 채택할 때는 필요한 `resource_holds`를 해당 계획/시도 참조와 같은 짧은 저장 트랜잭션에서 등록한다. 같은 작업이 여러 용도로 필요로 하는 자료는 그 용도들이 모두 끝나야 그 작업의 보호를 해제할 수 있다. 다른 작업의 보호는 독립적으로 남는다. 해제 판단의 근거는 assessment에, 이유는 기존 `release_reason`에 남기며 시각/기간 경과만으로 해제하지 않는다. 최소 유효 백업도 필요한 범위를 보장하는 대체본을 확인하기 전 보호한다.

정리 준비에서 누락된 현재 의존을 찾으면 보호를 보완하고 정리를 멈춘다. 보호 행이 없다는 이유로 진행하지 않는다. 오래된 보호가 보이면 소비자 근거를 확인한 뒤 해제하며, 알 수 없는 행을 자동 만료시키지 않는다. 대조 뒤 관련 계획/의무가 바뀌면 필요한 범위만 다시 판정한다. 이 등록/해제와 조회 연결은 아직 구현 검증 전이며 SQL만으로 누락을 발견할 수는 없다.

### 최초 인계에서 같은 입력을 사용할 때

최초 인계도 위 소비자와 원문 대응을 사용하지만 정리와 목적이 다르다. 현재 의존이 없다는 사실은 인계할 파일을 생략하거나 삭제할 허가가 아니다. 보관 중인 등록 파일은 함께 보존하고, 이미 정리된 자원의 이력과 현재 필요한 자료의 유실을 구분한다. 구체 목록과 단계 입력은 [인계 파일의 목록과 참조](storage.md)가 소유한다.

DB의 과거 루트/파일 관측을 새 위치의 관측으로 덮지 않는다. 인계가 만든 같은 논리 자료의 대상 사본은 현재 인계 확인으로 연결하며, 새 계획의 조회/복원은 그 현재 연결을 사용한다. 원래 부분 백업의 보장 범위도 그대로 유지한다. 물리적 원본을 정리할 때는 현재 진행이 대상 사본과 필요한 원문으로 독립적으로 이어지는지 확인하고, 아직 남은 의존/소유 불명 자료가 있으면 보존한다.

최초 인계의 성공은 초기 폴더 전체를 바로 지울 권한이 아니다. 기존 정리 명세로 실제 대상과 영향, 마지막 사용자 확인을 대조한다. 원본/대상 위치가 바뀐 사본에 옛 삭제 승인을 자동 적용하지 않는다. 같은 대상/영향의 재시도는 기존 승인을 재사용한다.

### 고정 목록과 승인 입력

| 기존 저장 위치 | 입력과 대조할 내용 |
| --- | --- |
| `plans.context_json` | DB 식별, 프로젝트와 정리 역할의 연결 기준. 실제 루트 위치/식별과 소유가 달라졌는지 확인할 로컬 입력. 팀 공유 설정에 개인 경로를 쓰지 않음 |
| `cleanup_items.identity_json` | 열린 대상의 볼륨 식별과 파일 ID, 파일 유형 및 필요한 속성 관측. 크기/내용 해시는 기존 열을 사용하며 문자열 경로만으로 동일성 판정 금지 |
| `cleanup_items.impact_json` | 이 파일 정리로 잃는 재검사 근거/복원 범위, 관련 작업, 남는 유효 백업의 ID와 목록 해시. 큰 본문이나 비밀값은 넣지 않음 |
| `cleanup_decisions.evidence_json` | 실제 확인 입력의 출처, 표시한 계획/목록/영향과 응답의 대응. AI가 생성한 동의나 다른 요청에서의 동의로 대체 금지 |
| 정리 시도의 assessment | 관련 의존 판정, 최신 결정, 실제 루트/파일 관측과 불일치. 최초 정리 확정의 `recheck_id`가 참조하며 같은 정리에서 이 자료를 삭제하지 않음 |

목록 해시는 DB/계획 식별, 정리 루트의 연결 기준, 항목 수와 `cleanup_items`의 대상 필드에서 계산한다. 항목은 `item_id`의 대소문자를 보존한 문자열 오름차순으로 고정한다. 각 항목에는 ID, root/path, identity, 내용 해시/크기, artifact/backup 참조를 포함한다. 영향 해시는 같은 순서의 항목 ID와 `impact_json`에서 별도로 계산한다. 기존 [JSON 직렬화 — 「저장 값의 형식」](storage.md)를 사용하고 해시 자신, 진행 관측, 무관한 기록 revision과 현재 시각은 이 두 입력에 넣지 않는다. 동일 ID 재전달은 정규화한 전체 입력도 대조한다.

현재 마지막 결정이 `approved`이고 대상/영향이 같다면 재시도에서도 그 승인을 재사용한다. 완료 항목을 숨기거나 남은 항목으로 원래 목록을 다시 만들지 않고, 같은 고정 목록의 진행 상황을 별도로 보여준다. 파일 교체, 루트 변경, 대상 추가나 복구 영향 변경은 새 계획과 확인이 필요하다. 새 의존이 생겼다면 보호를 우선하며, 사용자의 삭제 승인으로 필요한 자료 보호를 우회하지 않는다. 의존 해소 후에도 승인 범위가 같은지는 다시 대조한다.

최신 보관/취소 결정은 다음 파일 처리 전에 반영한다. 확인의 등록과 파일 처리 진입도 같은 로컬 실행 소유 규칙을 따른다. 이미 시작했거나 발생한 삭제를 뒤늦은 취소로 되돌렸다고 표시하지 않는다. 사용자 입력을 기다리며 파일 핸들이나 쓰기 트랜잭션을 유지하지 않으며, EOF/무응답은 동의가 아니다.

### Windows 파일의 동일성과 소유

정리 경로는 등록한 `state`, `bootstrap`, `download` 루트 아래의 **알려진 개별 파일**만 받는다. 상대경로를 접합한 뒤 문자열 접두어만 검사하지 않고 실제 루트/상위 경로와 열린 대상을 확인한다. 절대경로, 드라이브 상대경로, `..`, 장치 경로, 대체 데이터 스트림 경로, 해석이 달라지는 끝 공백/마침표나 예약 장치 이름을 상대경로 입력에서 거부한다. 한글과 정상 공백은 허용하며 위험한 입력을 임의로 고쳐 삭제하지 않는다. 이 기준은 Windows의 [파일명과 경로 규칙](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)을 고려한 제품 입력 제한이다.

대상 식별은 [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex)의 `FileIdInfo`와 볼륨 식별을 사용하는 후보다. 실제 열린 경로도 [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)로 대조하되 경로 문자열이나 파일 ID 하나만으로 소유를 증명하지 않는다. [Microsoft의 파일 ID 설명](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information)은 삭제 후 ID 재사용과 파일시스템별 차이를 명시한다. 생성/보존 기록, 실제 유형과 내용도 대조하며 동일성을 확정하지 못하면 보존한다.

재분석 지점, junction, 하드 링크, 경로 별칭이나 새 스트림 때문에 승인 범위와 다른 자료에 영향이 갈 수 있으면 정리하지 않는다. 첫 구현에서 안전하게 검증하지 못하는 유형은 제한 사유를 반환한다. 등록 루트 안에 있다는 이유로 현재 DB/active, 대응 journal, 설치 실행 파일이나 사용자 코드/WIKI를 정리 대상으로 허용하지 않는다. 실행 중 사용 여부, 읽기 전용/권한과 공유 위반도 별도로 확인하며 속성이나 보안을 풀어 삭제하지 않는다. 일반 파일의 크기 합계는 예상 논리 용량이고 실제 회수량의 보장이 아니다.

### 파일별 실행과 재개

| 순서 | 동작과 중단 처리 |
| --- | --- |
| 1. 남은 항목 선택 | 원래 목록과 마지막 결정, 현재 의존을 대조. 이미 `removed`/`absent`인 항목은 재삭제하지 않음 |
| 2. 대상 열기 | `OPEN_EXISTING`과 읽기/삭제 접근으로 열어 같은 핸들에서 식별/크기/내용 확인. 승인 대기나 AI 실행 중에는 잡지 않음 |
| 3. 정리 확정 저장 | 재대조 assessment를 보존하고 관련 revision/의존/승인을 짧은 트랜잭션에서 다시 대조한 뒤 claim 저장. commit 성공을 확인하기 전 삭제 금지 |
| 4. 파일 처리 | 같은 핸들에 삭제를 요청하고 종료 뒤 실제 상태 확인. 경로를 다시 열어 무조건 삭제하지 않음 |
| 5. 관측 저장 | 호출 결과와 실제 부재/변경/실패를 구분해 append. DB 저장이 실패하면 전체 정리 완료로 표시하지 않고 다음 재개에서 실제 파일과 기존 기록 대조 |

열기 단계에 `FILE_FLAG_DELETE_ON_CLOSE`를 쓰지 않는다. 대조/DB 저장 실패로 핸들을 닫는 것만으로 삭제돼서는 안 된다. 삭제 요청 후보와 한계는 [삭제와 이름 변경](../runtime/update.md)이 소유한다. 파일 대조/삭제 동안 SQL 트랜잭션을 계속 유지하지 않으며 DB와 파일의 일괄 원자성을 주장하지 않는다. 상위 경로 교체나 다른 작성자 때문에 소유를 확정하지 못하면 처리하지 않는다.

재시도에서는 이미 존재하는 claim을 새로 만들거나 옛 `recheck_id`를 바꾸지 않는다. 새 정리 시도의 assessment로 현재 의존/승인/파일을 다시 확인하고 새 관측의 `details_json`에서 그 근거를 참조한다. claim이 있다는 이유로 현재 대조를 생략하지 않는다. commit 결과가 불명확하면 삭제 없이 같은 키의 기록을 읽어 확인한다. 최종 관측 뒤 같은 경로에 새 파일이 생긴 경우에는 별도 대조 자료에 남기며 완료한 관측을 수정하거나 그 파일을 기존 승인으로 삭제하지 않는다.

대상이 없을 때도 등록 루트/부모가 정상이고 해당 파일만 없다는 점을 확인한다. 접근 거부, 부모 경로 유실이나 조회 실패를 `absent`로 바꾸지 않는다. 삭제 성공과 직후 부재를 관측했으면 `removed`, 호출 성공을 확인할 수 없지만 현재 부재가 확실하면 `absent`로 남긴다. 미확인 효과, 다른 파일로의 교체와 차단 이유는 구분해서 보존한다. 정리 실패를 최초 설치 재실행으로 해결하지 않는다.

## 검증과 다음 단위

[백업 수용 입력 — 「복구 자료와 백업의 검증 입력」](../../verification/acceptance.md)에 파일 누락, 부분 범위, 전환 중단, 제약 재구성과 정리 중 변경을 연결한다. 현재는 설계, 메모리 SQL 검사와 문서 정합성 검토이며 실제 백업/변환/삭제/인계를 시험한 결과가 아니다. SQL 메모리 검사의 통과도 이 절차의 Windows 동작을 증명하지 않는다.

[이전 SQL/행별 수신 관측 — 「최초 기록의 행별 수신안」](../../discussions/history/install.md)은 당시 근거로 보존한다. B의 [메모리 검사](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md)는 인계 16개와 저장/유지 관리 회귀 65개를 통과했다. 같은 형식의 사본, 이력/제약 보존, 단계 저장 실패와 재시도, 활성화 전 쓰기 및 옛 초기 사본의 후속 쓰기 차단을 확인했다. 실제 위치는 시험용 입력이며 Windows 파일/프로세스와 형식 변환은 검증 전이다. 그 뒤 [인계의 파일/위치 입력 — 「실제 원본과 대상의 확인」](storage.md)과 [미실행 파일 검증 조건 — 「최초 인계 파일과 위치의 검증 입력」](../../verification/acceptance.md)을 연결했다. 실제 제품 파일/소유, 전체 중단/재개와 형식 변환 시험은 후속이며 기존 메모리 결과를 이 범위의 성공으로 계산하지 않는다.

일반 코드가 사본/해시/DB 검사를 수행하고 AI에는 필요한 대상, 결과와 막힌 이유만 전달한다. 모든 파일/이력을 다시 프롬프트에 넣거나 SQL 저장마다 모델을 호출하지 않는다. 토큰 절감량은 미측정이며, 지원 환경의 백업 시간, 추가 용량, 재개 비용과 함께 판단한다.
