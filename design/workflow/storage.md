# SQLite 저장 규칙

2026-11-17에 유지 관리 관계를 보강한 4단계 명세 초안이다. [기록의 의미와 파일](records.md)을 관계, 키, 저장/조회 규칙으로 옮긴다. 검증/설치/인계와 업데이트 전체 복원의 **DDL 후보를 [schema.sql](schema.sql)에 작성**했다. 저장 값, 연결과 형식 호환 조건을 적용한 관계 정의다. WSL의 메모리 SQLite에서 기존 저장 29개, 인계 6개와 유지 관리 29개 관계 검사를 통과했지만 제품 저장 코드, Windows 내구성과 실제 복원은 미검증이다. 설치/인계의 고유 효과는 해당 명세의 의미를 유지하고, 같은 DB를 사용한다는 이유로 가짜 검사나 PASS로 바꾸지 않는다.

읽는 순서는 저장 값/연결 조건 → 관계의 의미 → [DDL과 저장 코드의 경계](storage.md#DDL%EA%B3%BC%20%EC%A0%80%EC%9E%A5%20%EC%BD%94%EB%93%9C%EC%9D%98%20%EA%B2%BD%EA%B3%84) → 필요한 SQL 정의다. 백업/형식 변환/정리의 관계와 [공통 입력/파일 대조 — 「공통 입력과 파일 대조」](maintenance.md)는 유지 관리 명세에 연결했다. 현재 의존과 승인/파일을 대조하는 코드, 전체 인계/변환과 실제 재중단 검증은 남아 있다. SQLite 채택과 이 설정 후보의 실증을 구분하며 공통 기능의 구조를 이 문서 한 번으로 구현 완료 처리하지 않는다.

2026-11-28에는 아래 연결 계약 중 기존 파일의 조회/쓰기와 짧은 트랜잭션을 코드 `oneploom/storage.py`에 구현하고 Windows에서 부분 검증했다. 이 결과는 전체 DDL, 최초 생성과 인계, 계획/승인 및 파일 반영의 완료가 아니다. [Windows 연결 검사](../../evidence/experiments/recovery/2026-11-28_17-57-33-state-connection.md)의 범위와 한계를 따른다.

## 저장할 내용의 구분

| 대상 | 저장 후보 | 이유와 제한 |
| --- | --- | --- |
| 작업/계획/시도 ID, 검사 의무, 상태, 결과, 참조 | 관계형 열과 키 | 다른 작업의 결과 혼입, 누락 참조와 중복을 DB에서도 거부하고 좁게 조회 |
| 당시 설정, 명령 인자, 범위/입력 목록, 작성 판단의 상세 | 해당 행의 JSON 텍스트 열 | 실행 당시 묶음을 보존. 검색하지 않는 모든 항목을 별도 테이블로 나누지 않음 |
| 로그, 보고서와 원문 사본 | 기존 파일 + DB의 위치/내용 참조 | 큰 본문을 DB와 JSON 파일에 중복 적재하지 않음 |

열로 분리한 ID/상태를 JSON 안에 다시 넣어 독립적으로 수정하지 않는다. JSON에는 [기록 명세 — 「계획 필드」](records.md)의 나머지 필드를 대응시킨다. 저장 전에 일반 코드가 필수 값, 형식, 중복 키, 유효한 경로와 허용 목록을 검사하고, 객체 키의 순서/공백만 다른 표현은 같은 내용으로 비교한다. 의미 있는 배열 순서, 부재와 `null`, 문자열은 임의로 바꾸지 않는다. 해시 일치만으로 다른 본문을 무조건 같은 사실로 취급하지 않는다.

SQLite의 JSON 확장, ORM이나 별도 서버를 첫 필수 의존성으로 추가하지 않는 후보다. JSON 유효성 검사와 바인딩은 Python 코드가 담당하며 SQL에 값을 문자열로 이어 붙이지 않는다. DB 저장 자체는 모델을 호출하지 않는다. 열과 제약은 schema.sql이 소유하고, JSON의 의미와 저장 코드가 할 검사는 아래 대응표에서 구분한다.

### 저장 값의 형식

SQL 열과 JSON의 형식은 같은 입력 검사에서 확인한다. JSON으로 옮겼다는 이유로 참조, 필수 값이나 선택 정책 검사를 생략하지 않는다. 관계형 열에 둔 식별/상태는 JSON의 두 번째 원본으로 받지 않는다.

| 값 | 저장 후보와 대조 기준 |
| --- | --- |
| ID, 종류와 상태 | 비어 있지 않은 문자열. ID의 대소문자와 바이트 표현을 보존하고 종류/상태는 해당 명세의 허용 값만 받음. 시각이나 파일명에서 ID를 추론하지 않음 |
| revision, 순서, 종료 코드 | SQL `INTEGER`. Python 입력에서 정수 여부와 64비트 범위를 확인하며 `True`, 문자열 `"1"`, 소수를 정수로 자동 변환하지 않음. 미관측 종료 코드는 `NULL` |
| 시각 | 시간대가 확인된 UTC 문자열로 저장. 일정한 ISO 8601 형식의 `Z` 표기를 사용하되 관측하지 않은 시각을 생성하지 않음. 정렬 시각으로 인과 관계/최신 유효 결과를 대신 판정하지 않음 |
| 선택 필드 | SQL 열에서는 허용된 `NULL`만 사용. JSON의 키 부재와 명시적 `null`은 계약대로 구분. 빈 문자열, 빈 목록으로 미확정을 숨기지 않음 |
| 경로/파일 | 기존 `root`와 상대 `path`, 원문 바이트의 SHA-256 참조. Windows의 다른 경로 표기가 같은 파일인지 별도로 확인하며 경로 문자열 해시로 파일 소유를 증명하지 않음 |
| JSON 상세 | UTF-8로 표현 가능한 객체/목록과 명세된 기본형. 문자열 키, 중복 키 금지, `NaN`/무한대 금지. 현재 필드에 없는 임의 값을 묵시적으로 버리고 재저장하지 않음 |

JSON 읽기는 중복 키를 감지하는 `object_pairs_hook`과 비유한 상수 거부를 사용한다. 기록용 정수 필드에 `1.0`이 들어오면 같은 값으로 바꾸지 않고 입력 오류로 돌린다. 필드별로 허용한 숫자/문자열만 받고, 수집한 원문 안의 문자열을 숫자로 해석하지 않는다. 잘못된 UTF-8, 짝 없는 surrogate와 처리 한도를 넘는 자료도 원인을 반환하며 조용히 잘라 완료시키지 않는다. 정확한 크기/깊이 한도는 실제 명세 자료의 크기와 Windows 측정으로 정한다.

정상화된 기록용 JSON은 `ensure_ascii=False`, `allow_nan=False`, `sort_keys=True`, `separators=(',', ':')`로 직렬화한 UTF-8을 대조하는 후보다. 이는 이 저장 형식의 규칙이며 범용 JSON 서명 표준을 구현했다는 뜻은 아니다. 객체의 키 순서/공백 차이는 제거하되 배열 순서, 문자열의 대소문자/유니코드 구성, 부재와 `null`은 보존한다. 이 규칙은 계획/인계 기록에만 적용하며 사용자 파일, 로그와 복원 사본을 재직렬화하지 않는다. 같은 ID의 재전달은 정규화한 내용과 소유 참조까지 비교하며 해시 하나로 기존 사실을 덮지 않는다.

[Python JSON 문서](https://docs.python.org/3.13/library/json.html#standard-compliance-and-interoperability)는 기본 파서의 중복 키와 비유한 수 허용을 설명한다. 따라서 `json.loads()` 성공만으로 위 입력 조건이 충족됐다고 보지 않는다. 별도 JSON 원본 파일이나 추가 모델 호출을 만드는 변경은 아니다.

이 규칙을 사용하는 정리 목록/영향 해시와 확인 입력의 구성은 [고정 목록과 승인 입력](maintenance.md)이 소유한다. 진행 관측을 목록에 섞어 재시도마다 승인 해시를 바꾸거나, SQL의 문자열 일치로 실제 파일 대조를 대신하지 않는다.

## 연결 준비와 내구성

현재 추천은 **짧은 명시적 트랜잭션, rollback journal의 `DELETE`, `synchronous=EXTRA`**다. 로컬의 작은 상태 저장과 재개가 목적이므로 먼저 이 구성으로 실제 Windows 비용/중단 시험을 한다. 설정값의 추천이며 내구성 실측이나 모든 장치의 전원 장애 보장이 아니다.

### 실행 준비와 연결 순서

Python 표준 `sqlite3`를 사용하고 별도 DB 서버, SQLite CLI나 MCP 설치를 요구하지 않는다. Python 자체와 포함된 SQLite 라이브러리 버전은 구분해 확인한다. 아래 API 후보는 Python 3.12 이상의 `autocommit` 인자를 사용하며, 최종 지원 Python/SQLite 조합은 5단계의 지원 버전 선정과 Windows 시험으로 정한다. 준비 확인 실패 시 설치 안내와 중단/재개를 사용하고 라이브러리를 자동 설치하거나 데이터 보호 설정을 낮추지 않는다.

| 연결 목적 | 열기와 처리 |
| --- | --- |
| 기존 상태 조회 | URI `mode=ro`. 없는 DB를 만들지 않으며 대상/형식 확인 뒤 필요한 범위만 조회. journal 모드나 DB 형식을 바꾸지 않음 |
| 기존 상태의 저장/재개 | URI `mode=rw`. 확인한 기존 DB만 열고 쓰기 지원 형식/설정과 실제 대상 재대조. 없으면 새 설치로 우회하지 않음 |
| 명시적 최초 생성 | 기존 제외/보존과 실행 소유 조건을 충족한 생성 단계에서만 수행. 다른 DB가 이미 생겼으면 덮거나 `CREATE IF NOT EXISTS`로 정상 초기화된 것처럼 처리하지 않음 |

URI는 Windows 경로의 공백, 한글, `#`, `?`를 파일 URI로 인코딩한 뒤 모드 인자를 연결한다. 입력 경로 문자열에 모드 옵션을 직접 이어 붙이지 않는다. 읽기 전용 연결이라도 중단된 트랜잭션의 journal 복구가 필요하면 읽기에 실패할 수 있다. 그때는 지원하는 복구 경로를 안내하고 `immutable=1`, journal 삭제나 빈 DB 생성으로 우회하지 않는다. [Python의 SQLite URI](https://docs.python.org/3.13/library/sqlite3.html#how-to-work-with-sqlite-uris), [SQLite의 hot journal 처리](https://www.sqlite.org/lockingv3.html#dealing_with_hot_journals).

연결 후보는 다음 순서를 사용한다.

1. Python 측 `autocommit=True`로 열어 암묵적으로 시작된 트랜잭션에 의존하지 않는다. 쓰기 전에 외래키를 켜고 `PRAGMA foreign_keys`가 1인지 확인한다. 새 DB는 정한 journal 모드를 설정/재조회하고, 기존 DB의 다른 모드는 조용히 변환하지 않는다. 쓰기 연결의 `synchronous`도 설정/재조회한다.
2. 읽기 묶음은 명시적 `BEGIN`, 쓰기 묶음은 `BEGIN IMMEDIATE`로 시작한다. 대상, 현재 revision과 필요한 참조를 다시 대조한 뒤 바인딩한 SQL 문장을 실행한다. 파일 반영, 모델 호출, 사용자 대기는 트랜잭션 밖이다.
3. 성공은 SQL `COMMIT`으로 확정하고, 오류는 실제 트랜잭션 상태를 대조해 SQL `ROLLBACK`한다. `autocommit=True`에서 Python의 `commit()`/`rollback()` 메서드를 호출한 것만으로 묶음이 닫혔다고 판단하지 않는다. commit 응답이 불확실하면 기존 ID로 실제 기록을 대조한다.
4. 여러 문장 중 뒤 문장이 실패하면 앞선 문장도 같은 묶음에서 취소됐는지 확인한다. 저장 경로에 `executescript()`를 섞거나 `with connection:`만으로 원자성을 추정하지 않는다. 사용한 연결을 명시적으로 닫고 종료/저장 실패를 새 실행 성공으로 바꾸지 않는다.

이 선택은 필요한 `BEGIN IMMEDIATE`와 연결 설정 시점을 명시하려는 것이다. Python의 `autocommit=False`도 가능한 대안이지만 자동으로 여는 트랜잭션과 외래키 설정 순서를 별도로 다뤄야 하므로 두 제어 방식을 혼합하지 않는다. [Python 트랜잭션 제어](https://docs.python.org/3.13/library/sqlite3.html#transaction-control-via-the-autocommit-attribute)가 각 방식의 차이를 설명한다.

DB 잠금 대기는 실제 AI/검사 명령의 실행 제한이 아니다. BUSY면 적용하지 못한 저장 단계와 재개 조건을 반환하며 기존 실행을 죽이거나 결과를 FAIL로 꾸미지 않는다. 짧은 대기/재시도의 수치는 Windows 관측으로 정하고 무한 반복은 두지 않는다. 소유가 다른 프로세스, 미확인 실행과 새 사용자 변경은 단순 재시도 대상으로 합치지 않는다.

### 기존 DB 연결의 구현 범위

`transaction(path, db_id, schema_version, write)`은 내부 저장 코드가 사용할 짧은 묶음이다. 호출자는 허용된 상태 루트와 작업 사본의 소유를 먼저 확인하고, 기대하는 DB 식별자와 자신이 지원하는 정확한 형식 번호를 전달한다. 형식 번호는 제품 릴리스 버전과 다르며 이 함수가 임의로 최신 번호를 추정하지 않는다.

- 실제 로컬 파일과 최종 파일의 일반 파일 여부, hard link/reparse 여부를 확인한다. 경로를 파일 URI로 변환한 뒤 조회는 `mode=ro`, 쓰기는 `mode=rw`로 열어 부재 시 새 DB를 만들지 않는다.
- 외래키 활성화를 재조회한다. 쓰기 연결은 기존 DELETE 방식을 확인하고 EXTRA를 설정/재조회한다. 다른 journal 방식을 자동 변환하지 않는다.
- 조회는 `BEGIN`, 쓰기는 `BEGIN IMMEDIATE`로 시작하고 같은 트랜잭션에서 metadata 한 행의 DB 식별/형식을 확인한다. 그 뒤 호출자의 SQL을 처리하고 명시적 `COMMIT` 또는 `ROLLBACK`, 연결 종료를 수행한다.
- 잠금 대기는 현재 구현에서 0초다. 다른 작업의 잠금을 즉시 알리고 명령 내부에서 반복하지 않는다. 자동 재시도나 최적 대기 시간은 아직 정하지 않았다. 이 값은 SQLite 잠금에만 적용하며 AI/호스트 실행 시간 제한이 아니다.
- commit이나 연결 종료 실패는 같은 작업 식별자로 실제 기록을 확인하도록 안내한다. 오류 응답만 보고 파일 작업이나 저장을 다시 실행하지 않는다. 그 조회/재개 소비자는 아직 구현 전이다.

호출 본문에는 내부 코드의 바인딩된 SQL만 두고 사용자 대기, AI 호출, 파일 변경, ATTACH와 별도의 트랜잭션 제어를 넣지 않는다. 이 연결은 외부 사용자가 SQL을 자유롭게 실행하는 API나 악성 DB에 대한 보안 경계가 아니다. metadata 일치만으로 프로젝트 소유, 전체 스키마의 정상성, 작업 승인이나 Windows 경로 교체 경쟁까지 증명하지 않는다. 보호된 상태 루트와 실제 파일 소유를 확인하는 상위 절차를 연결해야 한다.

현재 Windows Python 3.13.9/SQLite 3.50.4의 [실제 파일 검사](../../evidence/experiments/recovery/2026-11-28_17-57-33-state-connection.md)는 위 기반과 실패를 다뤘다. Python 3.12 미만과 sqlite3 부재는 준비 필요로 반환하며, 전체 배포 지원 버전과 CLI의 연결 저장 완료를 선언한 것은 아니다.

### 설정의 비교와 확인 범위

| 후보 | 이점 | 비용과 판단 |
| --- | --- | --- |
| `DELETE` + `EXTRA` — 우선 시험 | 짧은 저장 묶음에 필요한 DB 복구를 사용. WAL checkpoint 운영을 기본에 추가하지 않음 | 읽기와 쓰기가 서로 기다릴 수 있고 디스크 동기화 비용이 있음. 트랜잭션을 짧게 유지하고 실제 저장 지연을 측정 |
| `WAL` + `FULL` | 읽기와 쓰기의 동시성이 필요한 경우 비교 가능 | WAL/공유 메모리 보조 파일, checkpoint와 백업 대응을 추가 검증해야 함. 현재 요청 빈도에서 더 낫다는 실측은 없음 |

`NORMAL`, `OFF`, 메모리 journal을 속도 때문에 자동 선택하지 않는다. [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)는 rollback 모드의 `FULL`과 `EXTRA`, WAL의 `NORMAL`과 `FULL`에서 장애 내구성이 다를 수 있음을 설명한다. [WAL 문서](https://www.sqlite.org/wal.html)의 읽기/쓰기 이점만으로 우리 기본값을 정하지 않는다. `DELETE`도 journal 보조 파일을 사용할 수 있으므로 DB 파일 하나만 복사하거나 남은 journal을 임시 쓰레기로 삭제하지 않는다.

필수 기능은 외래키, CHECK/NOT NULL, 복합 유일 참조와 부분 유일 인덱스다. 일반 테이블에 명시적 제약을 두는 기존 후보를 유지하고, [STRICT](https://www.sqlite.org/stricttables.html)는 첫 필수 기능으로 추가하지 않는다. STRICT도 손실 없는 형변환을 허용하므로 위 입력 검사를 대신하지 못한다. 실제로 연결된 SQLite의 버전과 필요한 제약의 동작을 준비/지원 시험에서 확인하며, 낡은 버전도 문법이 된다는 이유로 배포 지원을 약속하지 않는다.

명세/변환 검증에서는 DB 구조 검사와 `foreign_key_check`를 구별한다. `integrity_check` 성공은 외래키 오류, 파일 사본의 존재나 사용자의 의미를 증명하지 않는다. 모든 일반 조회마다 전체 DB 검사를 실행하지 않고 초기 명세 시험, 변환/백업 후보와 손상 의심에 필요한 검사만 수행한다. [SQLite 검사 범위](https://www.sqlite.org/pragma.html#pragma_integrity_check).

내구성은 DB 설정만으로 닫히지 않는다. 사본 파일의 저장 확인이 먼저이고 그 참조를 DB에 남겨야 한다. OS/장치가 저장 완료를 실제로 지키는지와 파일 교체의 동작은 [Windows 반영 보호](recovery.md)의 별도 실증 대상이다. 프로세스 강제 종료 시험을 전원/디스크 장애 시험으로 확대하지 않는다. [SQLite의 하드웨어 전제](https://www.sqlite.org/atomiccommit.html#_hardware_assumptions).

## 관계와 키

다음은 공통 식별과 검증 부분의 테이블 후보다. 설치 연결에서 필요한 종류와 자료 소유를 보강했으며 구체 관계는 아래 절에서 이어진다. WIKI/PR의 효과까지 모두 같은 결과 형식으로 합치지 않는다.

| 관계 | 키와 필수 연결 | 막아야 할 잘못된 저장 |
| --- | --- | --- |
| `tasks` | 작업 `id`. 현재 변경 계획과 검증 계획을 구별하고 참조는 같은 작업의 행만 가리킴 | 같은 프로젝트 ID만으로 다른 작업 사본의 진행 사용, 검사 생성으로 설치 계획 교체 |
| `plans` | `id`, `task_id`, `kind`, 선택적 `previous_id`. `(task_id, id)` 유일, 이전 계획도 같은 작업/종류 | 다른 작업/종류로 계획 교체, 사용한 계획 본문 덮어쓰기 |
| `checks` | `(plan_id, check_id)` 기본키. 계획 외래키와 검증 종류 검사 | 한 계획의 검사 중복, 변경 계획을 검사 의무로 대체 |
| `attempts` | `id`, `task_id`, `plan_id`, `kind`, 선택적 `unit_id`와 `previous_id`. 아래 종류별 필수 연결 적용 | 같은 ID로 새 실행 생성, 설치/검사 사실 혼합, 다른 작업의 재시도와 연결 |
| `attempt_checks` | `(attempt_id, check_id)` 기본키와 `plan_id`. 시도/검사의 계획을 복합 외래키로 대조하고 시도 종류 검사 | 다른 계획의 동명 검사나 파일 반영 시도를 검사 실행으로 연결 |
| `results` | 관측 `id`, `(attempt_id, check_id)`, 선택적 `previous_id`. 해당 실행의 검사 연결과 이전 관측을 참조 | 실행하지 않은 검사 결과, 다른 시도/검사의 관측으로 보충 |
| `artifacts` | `id`, `plan_id`, 선택적 `attempt_id`, 역할과 위치/내용 기준. 시도를 가리키면 같은 계획 | 계획 후보를 위해 가짜 실행 생성, 다른 시도의 파일을 이번 실행 근거로 조용히 대체 |
| `result_artifacts` | `(result_id, artifact_id)` 기본키. 두 참조가 같은 시도에 속하는지 복합 외래키로 대조 | 결과에 무관한 로그를 연결해 근거가 있는 것처럼 처리 |

예를 들어 `attempt_checks`는 `(plan_id, attempt_id)`로 시도를, `(plan_id, check_id)`로 의무를 참조한다. 부모 `attempts`에도 `(plan_id, id)` 유일 키가 필요하며 다른 복합 참조에도 같은 규칙을 적용한다. ID의 존재뿐 아니라 **어느 작업/계획에 속하는지**를 검사한다. 새 계획/시도와 현재 참조 변경은 한 짧은 트랜잭션에 저장하고, 처음에는 참조를 비운 뒤 부모/자식을 만든 후 연결한다. 오래된 실행의 사실은 자기 기록에 남길 수 있지만 현재 작업 참조나 active를 과거로 돌리지 못한다.

ID와 필수 참조는 `NOT NULL`과 빈 값 검사를 명시한다. `requirement`, `stage`, `execution_policy`, 시도 상태, 결과의 `source`/`conclusion`은 기록 명세의 값만 `CHECK`로 허용한다. `not_run`과 `pass`의 조합은 거부하며, 실제 종료 코드의 부재는 `NULL`로 보존한다. SQLite는 일반 테이블에서 기본키의 `NULL`이나 `CHECK`의 `NULL` 평가에 주의가 필요하므로 키/CHECK만으로 필수 값 검사를 대체하지 않는다. [SQLite 제약 문서](https://www.sqlite.org/lang_createtable.html).

공통 저장 코드가 연결마다 트랜잭션을 열기 전에 `PRAGMA foreign_keys=ON`을 실행하고 1로 조회되는지 확인한다. 부모 키의 열 순서/타입/비교 규칙을 맞추고, 이력 참조에는 자동 연쇄 삭제/갱신을 사용하지 않는다. 외래키는 기본 활성화를 가정할 수 없고 트랜잭션 안에서 켜도 적용되지 않는다. [SQLite 외래키 문서](https://www.sqlite.org/foreignkeys.html#fk_enable).

계획/시도/관측의 이전 참조는 자신을 가리킬 수 없고 이미 존재하는 같은 대상의 선행 기록만 받는다. 생성 뒤 참조를 바꾸지 않는다. 외래키만으로 긴 순환이 막히지는 않으므로 저장과 인계 검사는 순환을 거부하며, 읽을 때 비정상 연결을 무한히 따라가지 않는다. 필수 의미 검토, 현재 파일과 입력의 일치, 실행 여부까지 SQL 제약이 증명하는 것은 아니다.

## 공통 기록과 기능별 연결

검사와 설치에 별도 식별/재개 엔진을 만들기보다는 작업, 계획, 실행 시도와 자료 참조를 재사용하는 후보를 우선한다. 다만 모든 내용을 임의 JSON 한 칸에 넣으면 잘못된 연결을 놓치기 쉬우므로, 아래 종류와 기능별 관계는 명시한다. 공통 헤더를 위해 클래스 계층이나 범용 workflow 실행기를 먼저 구현하는 뜻은 아니다.

`plans.kind`는 `verification`, `change`, `maintenance`를 구별한다. 검증 계획은 검사 의무를, 변경 계획은 설치/갱신/기능 추가의 고정 출처, 범위, 단위, 허용 반영을 소유한다. 기존 유지 관리 계획의 상세는 [백업과 정리 — 「저장 필드와 소비자」](maintenance.md)가 소유한다. 같은 작업에 속해도 다른 종류를 이전 계획으로 연결하지 않는다. 검증 계획의 생성/수정이 현재 변경 계획을 바꾸거나 그 의무를 지워서는 안 된다.

| `attempts.kind` 후보 | 필요한 계획/단위 | 사실과 완료의 구별 |
| --- | --- | --- |
| `verify` | 검증 계획. `unit_id` 없음 | 명령의 실행/종료와 검사 결과를 기존 형식으로 기록 |
| `apply` | 변경 계획과 그 계획의 단위 | 파일 반영 관측. 종료됐다고 단위 설치 완료는 아님 |
| `restore` | 변경 계획/단위와 복원할 이전 적용 시도 | 원래 적용 직전 자료를 연결. 복원 성공을 새 버전 설치 성공으로 표시하지 않음 |
| `handoff` | 변경 계획. `unit_id` 없음 | 같은 설치의 기록 전달. 대상 전환 완료가 설치 전체 완료는 아님 |

종류별 필수/금지 값은 CHECK와 같은 DB의 복합 참조로 제한하고, 의미 검사는 공통 저장 코드가 수행한다. 검사 전용 `argv`, PID, 종료 코드를 파일 쓰기/인계에 억지로 채우지 않는다. 시도에는 공통 준비/관측 상태를 사용하되 해당 동작의 실제 근거로 판정한다. `previous_id`는 같은 작업의 관련 선행 시도만 받고, 복원은 같은 단위의 적용/복원 관계도 확인한다. 검증과 설치 사이의 연결은 아래 의무 참조를 사용한다.

자료도 실행 전 계획 후보와 실제 시도 근거를 구별한다. 후보는 계획 소유, 적용 직전 사본과 로그/보고서는 시도 소유다. 검사 결과에 연결할 로그/보고서에는 해당 검증 시도가 필수다. 파일 위치만 같다는 이유로 다른 시도에 소유를 바꾸지 않으며, 복원은 원래 적용 시도의 사본을 명시적으로 참조한다. 원문 위치와 Git 공유 여부는 [기록의 파일 배치 — 「파일과 소유」](records.md)를 따른다.

### 변경 계획의 확인 기록

11/23 [CLI와 AI의 계획 확인 — 「계획 참조와 확인의 재사용」](../runtime/management.md)에 필요한 저장 확장이다. 기존 DB 안에 `plan_decisions` 관계를 추가하는 논리 명세이며 **현재 schema.sql이나 저장 코드에 구현된 상태는 아니다.** 별도 승인 DB, 수정 가능한 계획 JSON 원본, 사용자별 전역 허용 목록을 만들지 않는다.

| 필드 | 의미와 연결 |
| --- | --- |
| `id`, `plan_id` | 확인 기록의 식별과 같은 DB의 변경 계획 참조. 작업은 plans에서 찾으며 중복 task_id를 두지 않음 |
| `previous_id` | 같은 계획의 직전 확인 기록. 첫 기록만 null이며 기존 기록/참조를 덮어쓰지 않음 |
| `decision`, `scope_hash` | approved 또는 cancelled, 실제 보여준 전체 계획 묶음의 해시. 범위 구성과 계산은 관리 명세가 소유 |
| `evidence_json` | 실제 확인 경로/응답과 가능한 입력 참조, 함께 확인한 operation과 계획 참조. 계획 본문/전체 대화를 다시 복제하지 않음 |
| `created_at` | 확인을 실제 기록한 UTC 시각. 시각만으로 최신 선택이나 실행 완료를 판단하지 않음 |

계획별 확인 기록은 한 줄기의 추가 이력이다. 저장 코드는 준비 결과의 decision_id가 현재 마지막 기록과 일치하는지 확인하고, 읽은 상태의 비교와 새 기록 저장을 같은 짧은 쓰기 트랜잭션으로 처리한다. 서로 다른 후속 선택이 같은 previous_id에서 갈라지지 않도록 DB 제약도 구현한다. null인 최초 기록의 중복도 별도로 거부해야 하며 단순 UNIQUE만으로 처리됐다고 가정하지 않는다.

설치와 기기 등록처럼 한 화면에서 확인한 여러 계획은 같은 DB 안에서 모두 저장되거나 모두 취소된다. 일부 계획만 승인된 채로 적용하지 않는다. 같은 입력의 재전달은 소유, 이전 참조, 범위와 실제 확인 근거를 함께 대조해 기존 기록을 반환한다. 다른 입력이 먼저 반영됐거나 이후 취소가 있으면 오래된 승인 입력을 재적용하지 않는다. 이력을 지워 마지막 상태를 맞추거나 이미 사용한 계획의 본문을 수정하지 않는다.

사용자 입력을 기다리는 동안 트랜잭션을 열어 두지 않는다. 반영 직전의 최신 확인과 파일 상태 대조는 저장 성공과 별개로 필요하다. 같은 계획의 자체 진행/완료는 승인 범위 변경이 아니며 기존 시도 관측으로 대조한다. 최초 DB 인계 때 이 확인 이력도 같은 DB와 함께 보존하고, 새 위치의 같은 db_id/계획인지 확인한 뒤 사용한다. 다른 clone이나 복사한 로컬 상태에 승인 효력을 넘기지 않는다.

기존 `choices`는 업데이트 실패 뒤 retry/restore 선택을, `cleanup_decisions`는 정리 계획의 삭제 확인을 소유한다. 두 관계에 임의 값을 넣어 설치 승인을 표현하지 않는다. 반대로 새 plan_decisions도 실패 복원 선택이나 정리 확인을 대신하지 않는다. 필요한 확인의 반복 여부는 해당 기능의 기존 허용 범위와 실제 조건으로 판단한다.

이 필드의 DDL, 동일 입력 재전달, 동시 선택, 취소 뒤 재시도, 최초 인계와 실제 적용 전 검사는 첫 저장 구현에 포함한다. 기존 SQL 검사 통과를 새 확인 관계의 통과로 재사용하지 않는다. 확인 기록은 동작 감사 자료이며 입력한 사람의 신원이나 OS 권한을 암호학적으로 증명하는 장치가 아니다.

## 설치 단위와 반영 기록

[설치 단계 — 「설치 기록과 단계 연결」](../runtime/install.md)와 [부분 완료/조건부 복원 — 「적용 단위와 부분 완료」](../runtime/update.md)을 아래 관계에 연결하는 후보다. 단위의 의미와 복원 정책을 이 표에서 다시 정하지 않는다.

| 관계 후보 | 키와 참조 | 보존/소비할 내용 |
| --- | --- | --- |
| `units` | `(plan_id, unit_id)`. 변경 계획만 참조 | 선택/필수 범위, 단위 완료 조건, 보호/허용 범위 |
| `unit_dependencies` | 같은 계획의 단위와 선행 단위 쌍 | 중복/자기 참조 거부. 순환은 코드가 거부하며 참조 존재만으로 독립성 입증 불가 |
| `changes` | `(plan_id, change_id)`, 같은 계획의 단위와 단위 안의 순서 | 대상 경로/관리 항목, 생성/수정/삭제/이름 변경, 계획 때 기준과 후보 자료 참조 |
| `attempt_changes` | `(attempt_id, change_id)`. 적용/복원 시도와 변경이 같은 계획/단위 | 적용 직전 존재/부재와 사본, 예정 결과, 실제 관측/오류/미확인. 변경 의도와 관측 사실 구별 |
| `unit_checks` | 적용/복원 시도와 검증 계획/검사 의무의 조합 | 같은 작업의 의무를 연결하고 채택한 결과 관측을 참조. PASS 본문이나 종료 코드를 복제하지 않음 |
| `unit_outcomes` | 적용/복원 시도별 하나. 해당 단위와 근거 참조 | 검증/기준 반영이 끝난 `completed` 또는 확인한 `restored`. 전자는 적용, 후자는 복원 시도에만 허용 |

실행 준비에서 적용/복원 시도와 필요한 `attempt_changes`, 사본 참조를 한 짧은 DB 트랜잭션으로 저장한다. 실제 파일은 그 밖에서 반영한다. 존재하지 않던 원문은 부재로 기록하며 빈 파일의 사본과 구별한다. 행 부재나 기록의 `prepared`만으로 미실행을 단정하지 않는다. 새 실행/복원에는 새 시도를 쓰고, 관측 수집만 재개할 때는 기존 시도를 유지한다.

파일별 준비 내용은 확정 뒤 바꾸지 않는다. 새로 확인한 사실은 해당 시도의 revision과 현재 관측을 대조해 보강하며, 이미 확인한 결과와 상충하면 기존 사실을 보존한 채 미확인 사유/충돌 근거를 남긴다. 실패한 적용을 복원했다는 이유로 원래 반영 관측을 성공이나 미실행으로 바꾸지 않는다. 복원의 실제 결과는 새 복원 시도에 남긴다. 파일별 준비와 관측은 `attempt_files`, 원래 적용 시도는 `restore_of`로 연결한다. [SQL에 옮긴 필드](storage.md#SQL%EC%97%90%20%EC%98%AE%EA%B8%B4%20%ED%95%84%EB%93%9C)에서 JSON과의 경계를 확인한다.

시도 아래의 변경 관측과 검사 근거 선택도 부모 시도의 revision을 같은 트랜잭션에서 대조한다. 대조에 실패하면 자식 행의 변경까지 취소하고 현재 상태를 확인한다. 완료 근거를 확정한 뒤 그 근거 목록을 조용히 교체하지 않는다. `unit_checks`가 가리키는 결과는 선택한 검증 계획/의무의 실제 관측이어야 하며, 다른 작업이나 같은 이름의 다른 검사 결과는 거부한다.

`changes`의 순서는 단위 안의 쓰기 순서이며, 단위 사이 선행 조건과 다르다. 같은 실제 파일/관리 항목에 충돌하는 후보가 있으면 반영 전에 합치거나 의존 순서를 다시 검토한다. 공유 파일의 서로 다른 항목도 전체 본문 교체로 상대 변경을 지울 수 있으므로 이름만 다르다는 이유로 독립 처리하지 않는다.

단위 완료는 변경 계획에 정한 완료 조건에서 시작한다. `unit_checks`에 연결된 결과만 훑어 의무 목록을 만들지 않는다. 계획에 필요한 검사가 있는데 연결이 없으면 미완료이며, 검사가 필요 없다는 판단에도 해당 조건과 근거가 있어야 한다. 다음 연결을 확인한 뒤 완료를 저장한다.

1. 해당 적용 시도의 실제 파일/연결과 보호 조건을 확인한다. 필요한 `unit_checks`의 근거는 같은 의무/대상 입력에 유효해야 하며, 후속 검사를 위한 계획 변경으로 실패를 숨기지 않는다.
2. 검사 명령 밖의 신뢰/활성화 확인도 필요한 경우 그 근거와 미확인을 남긴다. 이를 가짜 명령이나 테스트 PASS로 만들지 않는다.
3. 그 단위의 공유 설치 기준을 별도 파일 반영으로 기록하고 실제 결과를 대조한다. 다른 완료 단위의 기준을 옛 전체 파일로 되돌리지 않는다.
4. 미확인이 없으면 채택한 검사 결과/추가 확인/기준 반영을 묶어 `unit_outcomes`를 저장한다. 완료 근거는 불변이며 후속 편집으로 효력을 잃으면 현재 유효성 판정을 보류한다. 과거 완료 사실 자체를 지우지 않는다.

기준 파일 저장 뒤 DB 완료 저장 전에 끊겼다면 실제 기준과 이전 검증 근거를 대조해 남은 기록부터 처리한다. 파일을 다시 쓰거나 검사를 모두 재실행하지 않는다. 내용 일치만으로 쓰기 소유/검증을 확정할 수 없으면 미확인으로 반환한다. 요청 종료는 현재 계획의 모든 필수 단위와 통합 의무를 확인한다. 후속 계획에서 이전 완료를 유지하려면 원래 단위/완료 참조와 재사용 이유, 현재 입력/의존의 대응이 필요하다.

11/16 채택한 [이전 구성 사용 선택 — 「업데이트 실패 후 선택」](../runtime/update.md)은 완료 보존의 명시적 분기다. 사용자의 선택은 대상 작업/계획과 허용한 복원 범위에 연결하며, 이번 업데이트에서 성공한 단위를 포함한 실제 변경을 복원 시도로 추적한다. 이전 `completed` 근거를 지우거나 그 결과를 `restored`로 덮지 않고 새 복원 시도/결과를 연결한다. 이미 복원한 단위도 실제 상태를 확인하며, 전체 요청의 복원/사용 검증이 끝나기 전 기존 구성을 정상으로 안내하지 않는다.

복원 대상은 이번 업데이트 시작 직전의 관리 항목 상태다. 같은 파일에 여러 단위가 순서대로 썼다면 사본/변경 연결과 의존 순서를 대조해 그 상태를 재구성하고, 단위별 사본을 임의 순서로 덮어 다른 단위나 사용자 편집을 지우지 않는다. DB 기록 자체를 과거 사본으로 바꿔 현재 실패/복원 이력을 없애지 않는다. 명시적 선택과 전체 복원 완료는 [선택과 전체 복원의 연결](storage.md#%EC%84%A0%ED%83%9D%EA%B3%BC%20%EC%A0%84%EC%B2%B4%20%EB%B3%B5%EC%9B%90%EC%9D%98%20%EC%97%B0%EA%B2%B0)에, 기존 실행/DB 호환 조건은 [형식 호환 — 「DB 형식과 이전 구성의 호환」](storage.md#DB%20%ED%98%95%EC%8B%9D%EA%B3%BC%20%EC%9D%B4%EC%A0%84%20%EA%B5%AC%EC%84%B1%EC%9D%98%20%ED%98%B8%ED%99%98)에 연결한다. 실제 형식 변환 수단은 후속이다. 이번 보강을 해당 분기의 실행 검증 완료로 계산하지 않는다.

### 기기 등록 효과의 저장 경계

11/23 [기기 등록 정보 — 「기기 등록 정보와 소유」](../runtime/entry.md)의 후속 저장 요구다. 작업/계획/시도, 보존 자료, 관측/복원이라는 기존 책임은 재사용하되 **현행 DDL의 파일 범위를 기기 전체에 그대로 적용하지 않는다.** `attempt_files.root`는 현재 `code`, `wiki`, `state`만 허용한다. Python 설치 명령을 기록할 수 있다는 사실도 기기 파일/PATH 반영 복구의 완성을 뜻하지 않는다.

| 연결할 자료 | 범위와 저장 조건 |
| --- | --- |
| 등록 작업의 대상 | `tasks.target_json`에 `kind: command_registration`과 확인한 `registration_root`를 사용하도록 논리 계약을 분기. 현재 사용자의 실제 프로그램 폴더 아래 OnepLoom인지 대조. 프로젝트 없는 명령 최초 등록/복구/제거에 가짜 code/WIKI 루트나 프로젝트 ID를 넣지 않음 |
| 계획과 입력 | 같은 작업의 변경 계획에 고정 wheel 출처, 선택 Python/환경, 허용한 명령과 PATH 항목, 보존/검사 조건을 연결. 정상 프로젝트 검증의 context를 기기 작업에 강제하지 않음 |
| 기기 파일 효과 | 등록 루트 아래의 관리 파일/환경을 제한된 대상으로 표현. 새 파일용 루트 분기와 실제 경로/연결 검사가 필요하며 `state/../...` 또는 임의 절대 경로로 현행 제약을 우회하지 않음 |
| 사용자 PATH 효과 | 해당 사용자의 PATH에 대한 허용 항목 추가/제거. 원래 값/형식, 의도한 한 항목과 실제 관측을 보존. 시스템 PATH나 임의 레지스트리 키를 받지 않고 파일의 SHA-256 관측으로 대신 표현하지 않음 |
| 등록 정보 반영 | `current`와 `pending`의 변경도 실제 파일 효과. 준비/반영 관측은 DB에, 마지막 확인과 작업 참조만 JSON에 보존. DB 완료와 참조 해제 사이 중단은 재조회로 처리 |

등록 작업은 프로젝트 설치와 별도 작업 ID를 사용하므로 프로젝트의 전체 복원 대상에 섞이지 않는다. 같은 DB에 있다는 이유로 작업 간 `unit_checks`나 시도 외래키를 넘겨 연결하지 않는다. 프로젝트 준비에서는 확인한 등록의 현재 기준을 입력으로 대조하며 다른 작업의 PASS를 자신의 실행 결과로 복제하지 않는다.

등록 진행에 필요한 사본/후보는 기존 `resource_holds`로 보호한다. DB에 완료 근거를 남긴 것만으로 보호를 풀지 않고 `pending` 해제와 현재 복구 의존을 대조한 뒤 기존 정리 조건을 적용한다. DB 자체의 이동/인계도 등록 참조가 남았는지 별도로 확인한다. 이 보호 참조는 JSON에 단계 기록을 복제하는 근거가 아니다.

파일 외 효과의 관측 관계, 허용 대상 검증과 완료 조회의 연결은 **등록 구현 전 필요한 DDL/저장 코드 작업**이다. 현재 SQL에는 이 효과가 없으므로 이번 문서 변경에 기존 SQL PASS를 그대로 적용하지 않는다. 한 JSON 열에 넣을 수 있다는 이유로 구현됐다고 판단하지 않으며, 누락된 PATH 관측이나 무관한 등록 루트가 완료 근거로 채택되지 않는 거부 사례까지 검사해야 한다. 현재 `schema.sql`과 기존 프로젝트 기록의 제약/시험 근거는 변경하지 않았다.

프로젝트 없는 등록 작업의 DB는 기존 외부 최초 보존 위치에 남는다. 프로젝트로의 인계는 없고 완료 후 정리 조건은 기존 [보존과 정리 — 「파일 구성과 보장 범위」](maintenance.md)를 따른다. 프로젝트 설치 중 사용하는 최초 DB를 인계할 때는 등록 작업 완료와 `pending` 해제를 먼저 대조한다. 진행 중 참조를 새로운 위치로 자동 추정하거나 두 DB를 동시에 진행 원본으로 열지 않는다.

## 최초 기록 인계의 저장

2026-11-17 사용자가 **B의 위치 전환**을 채택했다. 초기 상태 DB의 같은 형식 사본을 새 후보에 보존하고 수신/확인/활성화를 마친 뒤 프로젝트에서 이어 쓴다. 설치 초기 기록과 같은 논리 `db_id`, 기존 작업/시도/관측 및 revision을 유지한다. 기존 정상 프로젝트 DB는 재사용하며 다른 DB와 자동 병합하지 않는다. [처음부터 이어 쓰는 의미 — 「설치부터 업데이트까지 이어 쓰는 기록」](storage.md#%EC%84%A4%EC%B9%98%EB%B6%80%ED%84%B0%20%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8%EA%B9%8C%EC%A7%80%20%EC%9D%B4%EC%96%B4%20%EC%93%B0%EB%8A%94%20%EA%B8%B0%EB%A1%9D)와 [첫 설치 조건 — 「첫 기록 생성과 인계」](../runtime/install.md)을 함께 따른다.

### 인계 기록과 실제 위치

`handoffs`는 같은 `handoff` 종류의 `attempt_id`를 사용한다. 원본에서 준비한 행도 DB 사본에 포함한다. 각 사본의 역할을 불변 `side`로 고정하던 초안을 단계 상태로 바꾸고, 어떤 위치의 연결인지 공통 저장 진입에서 따로 검증한다. 원본/대상의 DB ID가 같다는 사실은 쓰기 권한이 아니다.

| 필드 | 의미와 소비 |
| --- | --- |
| `attempt_id` | 같은 최초 인계의 시도. 응답 유실만으로 새 ID나 새 설치를 만들지 않음 |
| `state` | 아래의 준비/수신/원본 확인/대상 활성화 상태. 사본의 물리적 위치를 대신하지 않음 |
| `source_json`, `target_json` | 확인한 작업 사본과 저장 위치의 대응. 공통 코드가 실제 코드 루트와 상태 위치, 접근한 파일을 대조. 같은 경로 문자열이나 DB ID만으로 판정하지 않음 |
| `payload_json`, `payload_sha256` | 동결한 DB 내용의 형식/식별/내용 기준과 필요한 파일 목록의 불변 대조 자료. 진행 상태의 두 번째 원본이 아님 |
| `receipt_id` | 검증한 대상이 수신 때 한 번 발급한 식별. 같은 수신 재개에서는 재사용하며 원본의 확인과 일치해야 함 |
| `source_confirmation_json` | 같은 인계/내용/receipt와 실제 대상에 대한 원본의 확인 근거. 대상 활성화 시 다시 대조 |
| `activated_at` | 대상에서 사용 전환을 확인한 사실. 시각이 크다는 이유로 다른 사본보다 우선하지 않음 |

확정 내용에는 지원 스키마와 초기 DB의 모든 기록을 포함한다. **현재 인계 행 자체만 내용 지문에서 제외**해 자기 자신의 payload/상태 변경이 지문을 바꾸지 않게 한다. 그 행의 불변 입력과 상태는 별도로 대조하며, 현재 인계 시도 행을 포함한 나머지 기록을 통째로 제외하지 않는다. 인계 시도는 마지막 확인 뒤 대상 활성화와 같은 트랜잭션에서 종료한다. 정상 전환 뒤의 재개에서는 후속 진행으로 바뀐 DB 전체를 초기 지문과 다시 같게 만들지 않고 보존한 수신/확인과 현재 상태를 사용한다.

파일은 [인계 파일의 목록과 참조](storage.md#%EC%9D%B8%EA%B3%84%20%ED%8C%8C%EC%9D%BC%EC%9D%98%20%EB%AA%A9%EB%A1%9D%EA%B3%BC%20%EC%B0%B8%EC%A1%B0)에 따라 기존 `root: state` 참조와 내용 기준으로 보존할 원문/사본을 연결한다. 이미 정리된 자료의 사실과 현재 필요한 파일의 누락을 구별하며 없는 파일을 재생성하지 않는다. 새 후보의 파일 소유와 실제 위치, 모든 필수 파일의 준비를 확인하기 전 수신/활성화하지 않는다. 정확한 Windows 파일 대조와 파일 목록을 포함한 전체 직렬화는 제품 구현/시험 대상이다.

### 인계 단계와 쓰기 허용

| 단계 | 원본 DB | 대상 DB | 다음 조건 |
| --- | --- | --- | --- |
| 준비 확정 | `prepared` | 전용 빈 후보 확보, DB 내용 복사 전 | 최초 변경의 결과와 남은 실행을 확인하고 일반 진행 동결. 같은 형식의 Backup API 사본을 새 후보에만 생성 |
| 대상 수신 | `prepared` | 사본의 `prepared`를 검증한 뒤 `received`와 receipt 저장 | 스키마/기록/파일과 실제 대상 확인. 복사만 끝났다는 이유로 수신이나 설치 완료 인정 금지 |
| 원본 확인 | `released`와 같은 receipt/확인 근거 | `received` | 원본/대상의 고정 내용과 수신을 재대조. 원본은 더 이상 일반 진행 위치가 아님 |
| 대상 활성화 | `released` 보존본 | 인계 시도 종료와 `active`를 한 트랜잭션에 저장 | 원본 확인과 같은 receipt/내용/대상인지 확인. 그 뒤 프로젝트에서 남은 설치와 후속 작업 진행 |

원본에서는 `prepared → released`, 대상에서는 사본에 든 `prepared → received → active` 순서다. DB 둘이 한 트랜잭션으로 바뀌는 것이 아니며, 각 단계는 앞 단계의 확인된 사실을 소비한다. 단계 저장 중 오류는 그 DB의 짧은 트랜잭션을 명시적으로 rollback하고 실제 저장 여부를 확인한다. 이미 확인한 receipt/원본 입력/확인/활성화 사실은 덮거나 뒤로 돌리지 않는다. 같은 요청의 다른 내용은 충돌이다.

SQL은 준비 상태로 시작, 필수 필드, 허용된 단계 순서와 확정 사실의 불변을 검사한다. **SQL만으로 실제 source/target 위치나 다른 DB의 확인이 참인지 증명할 수는 없다.** 공통 쓰기 진입은 실행 소유를 확보한 뒤 현재 연결, 인계 ID/내용과 단계를 다시 읽어 다음을 적용해야 한다.

- `prepared`, `received`, `released`인 사본에는 새 설치 효과, 일반 검사/갱신/정리 기록 등 다른 작업의 쓰기를 허용하지 않는다. 읽기와 해당 인계의 재개/확인만 구분해 처리한다. 정상 관리 작업마다 별도 우회 플래그를 추가하지 않는다.
- 수신과 활성화는 실제 대상에서, 원본 확인은 실제 원본에서만 수행한다. 정상 프로젝트의 후속 쓰기는 대상의 `active`와 현재 실행 소유를 확인한 공통 경로에서 수행한다. 모든 저장 소비자를 이 진입에 연결해야 한다.
- 명령 시작 때 읽은 상태를 계속 믿지 않고 짧은 쓰기 트랜잭션 안에서 현재 상태/기준을 재대조한다. 복사나 파일 확인, 사용자 응답을 기다리며 DB 쓰기 트랜잭션을 유지하지 않는다.
- 최초 인계가 필요 없었던 정상 프로젝트는 기존 생성/저장 계약을 사용한다. 모든 프로젝트에 인계 행을 강제로 만들거나 매 대화마다 DB를 읽지 않는다.

이는 [로컬 실행 소유 — 「실행 소유의 식별과 반환」](recovery.md)와 연결할 계약이다. 임의 외부 프로그램의 직접 SQL까지 공통 진입을 따르게 만들거나 메모리 검사를 Windows 프로세스 보호 성공으로 확대하지 않는다. 실제 공통 저장 코드와 모든 호출부의 연결은 제품 구현에서 확인한다.

### 인계 파일의 목록과 참조

11/17 B의 파일 입력 보완이다. **DB의 이력 보존과 그 이력이 가리키는 원문 보존을 함께 확인한다.** 단순 백업의 선택 범위와 달리, 최초 인계에서 현재 필요 없다는 이유만으로 아직 보관 중인 원문을 생략하지 않는다. 이미 채택한 명시적 정리 외에 새로운 자료 폐기 정책을 끼워 넣지 않는다.

| 원본의 자료 | 인계에서 처리할 범위 |
| --- | --- |
| 현재 `state.db`와 SQLite 보조 파일 | DB는 앞선 Backup API 사본 절차. journal/WAL/SHM을 일반 파일 목록으로 섞어 복사하거나 삭제하지 않음 |
| `root: state`의 등록된 후보, 적용 전 사본, 로그, 보고서/assessment | 아직 보관 중인 원문 바이트와 상대경로 유지. 현재 복구에 필요한 파일은 필수이며 완료 이력의 보관 파일도 임의 생략하지 않음 |
| 등록된 백업 목록과 그 안의 사본, 형식 변경 후보 | 해당 목록과 참조로 범위를 확인. 닫힌 사본만 다루며 백업 폴더 전체를 무조건 재귀 수집하지 않음. 안의 과거 DB를 현재 진행 원본으로 열지 않음 |
| 기존 `active.md` | 존재하면 본문 바이트를 보존하고 기록 참조 대조. 애초에 없으면 부재를 남기고 빈 active를 만들지 않음 |
| 이미 정리된 원문 | DB의 정리 사실과 기존 참조를 유지. 원문을 새로 만들거나 같은 이름의 다른 파일을 과거 자료로 받아들이지 않음 |
| 코드/WIKI 원문, 다운로드한 설치 도구와 기기 설정 | 기존 역할/위치 유지. 이번 인계를 이유로 코드/WIKI 전체를 상태 폴더에 복사하거나 설치 도구를 장기 실행 의존성으로 남기지 않음 |
| 소유/참조를 알 수 없는 파일, 계속 바뀌는 출력 | 자동 수집/삭제하지 않고 보존. 인계 범위와 고정 가능한 내용이 확인되지 않으면 수신을 보류 |

`payload_json.files`에 인계할 파일과 확인한 부재를 고정한다. 기존 JSON 직렬화 규칙을 사용하며 별도 수정 가능한 진행 목록 파일을 만들지 않는다. 각 항목은 기존 자료 참조(`refs`), `root: state`와 상대 `path`, `presence`, 확인 근거(`basis`)를 갖는다. 존재하는 자료에는 원문 `sha256`과 `size`를 함께 둔다. 부재에는 원래 미생성인지 확인된 정리인지와 해당 근거를 남기며 빈 바이트의 해시로 부재를 표현하지 않는다. 현재 필요한 자료의 유실/접근 실패는 허용된 부재가 아니다.

동일한 보관 파일을 여러 기록이 가리키면 그 참조를 한 항목에 묶는다. 복사할 서로 다른 항목이 Windows에서 같은 대상 경로로 해석되면 충돌로 반환한다. 과거에 정리된 자원과 같은 이름으로 생긴 새 자원은 내용/소유 참조로 구분하며, 과거 정리 기록을 새 파일의 부재 주장이나 삭제 허가로 쓰지 않는다. 정렬은 상대경로와 정렬한 기존 참조를 기준으로 고정하고 대소문자/유니코드 구성은 보존한다. 처리할 때의 실제 경로 충돌 검사는 이 정렬과 별개다.

원본과 대상의 `state` 루트는 각각의 인계 연결로 해석하되 `artifacts.root/path`, 백업 내부 상대경로와 과거 기록은 고쳐 쓰지 않는다. `code`와 `wiki`는 원래 연결을 유지한다. 과거 `context`나 파일 관측 속 실제 경로/파일 ID는 당시 근거이며 새 실행의 설정 원본이 아니다. 인계가 끝난 뒤 필요한 원문을 읽을 때 옛 외부 폴더를 몰래 대체 경로로 사용해서는 안 된다.

필요한 자료는 [현재 의존을 찾는 입력](maintenance.md)으로 대조하고, 등록 자료와 실제 상태 폴더의 대응을 함께 확인한다. 해제된 보호가 있다는 이유로 원문을 빼거나 정리된 자료를 새 완료/복원 근거로 되살리지 않는다. 백업은 등록된 목록에 명시된 내부 파일과 복구 범위를 따라가고, 다른 백업을 무한히 포함하거나 원래 부분 백업을 전체 백업으로 바꾸지 않는다. 목록 해시도 전체 `payload_sha256`의 입력이며 파일별 복사 진척은 고정 내용에 섞지 않는다.

### 실제 원본과 대상의 확인

DB 식별은 같은 이력인지, 물리적 식별은 지금 어느 사본에 접근했는지를 확인한다. 양쪽의 파일 ID가 같아야 한다고 요구하지 않는다. 다른 드라이브로 복사하면 원본과 대상은 다른 파일이다. 경로/파일 ID만으로 소유를 인정하지 않고 현재 프로젝트, 생성/보존 근거, 내용과 단계를 함께 대조한다.

| 기존 필드 | 고정할 연결과 사용 시점 |
| --- | --- |
| `source_json` | 같은 코드 작업 사본, 실제 초기 상태 루트와 원본 DB의 대응. 준비 전에 열린 대상과 소유를 확인 |
| `target_json` | 같은 코드 작업 사본, 등록한 프로젝트 상태 루트와 새 후보 DB의 대응. 관계없는 기존 DB를 덮지 않고 이 인계가 준비한 대상인지 확인 |
| `payload_json.files` | 옮길 원문의 내용/상대 참조와 확인한 부재. 아직 생성하지 않은 대상 파일의 ID를 예상해 채우지 않음 |
| `source_confirmation_json` | 같은 인계/내용/receipt/대상에 대한 확인과 파일 대조 결과. 원본에서 확정한 사실을 대상 활성화에 사용하고 최종 대상에도 보존 |

루트와 DB의 실제 대응에는 등록 경로, 확인한 최종 경로/유형, 볼륨과 파일 식별, 생성/기존 보존 근거를 사용한다. 새 후보 DB는 비어 있는 전용 대상으로 먼저 확보하고 그 연결을 준비 기록에 고정한다. `state.db`라는 이름으로 존재한다는 사실만으로 소유하거나 활성화된 것으로 보지 않는다. 후보 확보와 준비 기록 사이에 끊겨 소유를 확인할 기록이 없다면 빈 파일도 임의로 덮거나 삭제하지 않는다.

[CreateFileW의 CREATE_NEW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)는 기존 파일이 있으면 생성을 실패시키는 수단이다. 새 대상 확보는 이런 배타적 생성과 실제 열린 대상의 확인을 조합하는 후보이며, 먼저 존재 여부를 검사한 뒤 덮어쓰는 두 호출로 대신하지 않는다. [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex)의 파일 정보는 열린 객체의 대조에 사용한다. 실제 경로/링크/소유와 ID 재사용의 제한은 [Windows 파일의 동일성과 소유](maintenance.md)를 재사용한다.

파일 대조 결과는 고정 목록의 항목 참조와 관측한 원본/대상, 내용 일치 또는 확인한 부재를 연결한다. `source_confirmation_json.files`에 그 대응을 보존하며 기존 목록의 본문을 복제하거나 과거 파일 관측을 새 위치의 관측으로 덮지 않는다. 대상 활성화 직전에 그 대응과 실제 파일을 다시 확인한다. 새 사본이 만들어졌다는 사실은 옛 물리 파일에 내렸던 삭제 승인까지 새 위치로 이전하는 근거가 아니다. 정리의 대상/영향 변경은 기존 [승인 입력 — 「고정 목록과 승인 입력」](maintenance.md)을 따른다.

### 파일 확인과 중단 후 재개

| 단계 | 파일/위치 확인과 중단 후 행동 |
| --- | --- |
| 준비 | 제외 효력, 현재 실행 소유, 원본/새 후보와 고정 목록 확인. 작성 중인 자료는 고정 가능 여부부터 판단하며 미확인 효과는 기록에서 지우지 않음 |
| DB/파일 사본 | DB 사본과 일반 파일 복사를 구별. 같은 인계가 소유한 새 대상에만 쓰고 원문 바이트/크기/내용을 대조. 완료된 같은 파일은 확인 후 재사용하며 소유 불명/부분 파일을 자동 덮지 않음 |
| 대상 수신 | 고정 DB 내용과 전체 목록의 파일/참조/부재 확인. 알려진 일부 파일만 맞는 상태에서 receipt를 발급하지 않음 |
| 원본 확인 | 같은 receipt와 현재 원본/대상을 재대조한 뒤 확인 사실 저장. 파일 복사 뒤 바뀐 원문이나 같은 경로의 다른 대상을 놓치지 않음 |
| 대상 활성화 | 원본 확인, 목록과 현재 대상의 대응 확인 뒤 짧은 DB 트랜잭션으로 시도 종료/활성화. 파일 복사 중에는 이 트랜잭션을 열어 두지 않음 |
| 활성화 뒤 | 후속 설치/업데이트는 프로젝트 상태에서 계속. 초기 사본 없이 필요한 자료를 읽을 수 있음을 확인하고 나서 별도의 명시적 정리 절차 적용 |

같은 목록/수신에 대한 재시도는 완료된 단계와 파일 검증 결과를 현재 기준에서 재사용한다. 그러나 파일 쓰기 성공과 그 사실을 저장했다는 것은 다르다. 소유/내용을 확정할 수 없는 잔여 파일, 바뀐 루트, 누락된 필수 파일이나 맞지 않는 수신은 보존하고 원인을 보고한다. 기존 확인 사실을 수정해 억지로 같은 요청으로 만들거나 새 설치를 시작하지 않는다. 이미 `released`/`active`인 기록을 뒤로 돌리는 예외도 추가하지 않는다.

원문 읽기와 대상 쓰기의 실제 핸들, 링크/별칭 대조, 저장/닫기와 재열기는 [파일 반영과 핸들 수명](../runtime/update.md)의 공통 계약에 연결한다. [Python 파일 복사 문서](https://docs.python.org/3.13/library/shutil.html)는 기존 대상 덮어쓰기와 Windows 소유자/ACL/추가 스트림을 모두 복사하지 않는 한계를 설명한다. 따라서 `copyfile`/`copy2` 성공이나 해시 일치만으로 보존/접근 범위 검사를 마치지 않는다. 현재 지원하지 않거나 보호를 확인할 수 없는 유형은 사유를 알리고 보류한다. 정확한 API 조합, 보안 속성과 중단 내구성은 Windows 제품 시험에서 확인한다.

이번 보완은 파일 입력과 확인 책임의 명세다. 기존 메모리 16개는 실제 파일 목록/소유 검사를 하지 않았으며, 이번 문서 보완으로 그 검증 범위가 늘어난 것은 아니다. 새 DB 열이나 별도 복구 엔진, 매 대화의 모델/DB 호출을 추가하지 않는다.

### 대상 DB에 쓰는 순서

이 제목은 이전 링크의 진입점으로 유지한다. 행별 재등록 초안은 [이전 인계안 — 「최초 기록의 행별 수신안」](../../discussions/history/install.md)에 보존했고 현행은 위 인계 단계다. B는 종료된 과거 작업을 준비 상태부터 재구성하지 않는다. 일반 INSERT 보호를 낮추거나 기존 DB를 사본으로 덮어 통과시키지 않는다.

### 유지 관리 기록의 인계 순서

B에서는 백업/전환/보호/정리의 원래 행과 관계를 같은 형식 사본에 보존한다. 과거 완료와 현재 재사용 가능성의 구분, 해제된 보호와 남은 보호, 정리 관측과 새 소비 차단도 유지해야 한다. 이 조건은 [사본과 형식 변경 — 「사본과 인계와 형식 변경의 구분」](maintenance.md)과 [수용 입력 — 「유지 관리 인계와 형식 변환의 검증 입력」](../../verification/acceptance.md)에 연결한다. 예전 7개 행 순서/사본 검사는 당시 초안의 부분 관측이며 B의 전체 인계 결과가 아니다.

### 과거 형식 변경 기록의 수신 경계

E-022에서 현재 형식과 다른 과거 출발 형식을 일반 INSERT로 넣으면 새 전환 검사에 걸리는 것을 확인했다. B는 과거 행을 재등록하지 않고 같은 형식 DB의 사본을 사용해 이 정상 경로의 충돌을 피한다. 11/17 [B 관계 검사](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md)는 현재 형식 값 2와 과거 1→2 기록을 함께 보존하고 정상 보호가 유지되는 것을 확인했다. 숫자는 합성 입력이며 실제 지원 형식이나 변환 성공이 아니다.

따라서 **채택한 최초 인계 경로는 보완됐지만 실제 파일/Windows 인계와 다른 형식으로의 변환은 아직 미검증**이다. [E-022 — 「E-022 — 과거 상태의 수신과 새 실행 검사의 충돌」](../../evidence/issues.md)를 실제 사용자 환경 해결 완료로 닫지 않는다. 임의 DB 병합이나 과거 이력의 일반 INSERT를 지원한 것으로도 해석하지 않는다.

### 최초 인계 방식 재검토

11/17 사용자가 **B를 채택**했다. 아래는 선택 근거이며 A/C는 비교 이력이다. E-022의 직접 원인은 과거 사실에 새 실행 검사를 적용한 것이다. 더 앞선 전제는 최초 설치의 저장 위치 변경을 행별 수신으로 설계했다는 점이다. [설치 진입 — 「첫 기록 생성과 인계」](../runtime/install.md)은 유효한 기존 프로젝트 기록이 있으면 그대로 사용한다. 최초 외부 공간은 설치 작업별로 분리하므로, 정상 최초 경로에 무관한 프로젝트 기록과의 병합이 꼭 필요한지는 별도로 판단해야 한다.

| 안 | 처리 | 이점과 비용 |
| --- | --- | --- |
| A. 행별 수신 보완 | 필요한 행을 기존 대상에 등록하고 과거 사실을 검증하는 별도 수신 경로 설계 | 선택 전달과 기존 기록 병존에 유리. 현재 일부 검사 재사용 가능. 기능이 늘 때마다 과거 순서, 잠긴 관계와 재시도 조건을 수신에도 반영해야 하며 E-022 해결이 필요 |
| B. 최초 전용 DB의 위치 전환 — 채택 | 한 설치의 DB와 필요한 파일을 새 후보 위치에 보존하고 검증한 뒤 진행 원본 전환. 기존 정상 프로젝트는 그 DB에서 재개 | 과거 기록을 새 실행으로 재등록하지 않아 원래 값과 관계를 보존하기 쉬움. 기존 다른 DB와의 자동 병합은 제공하지 않으며 수신 확인, 활성화와 물리적 위치 대조는 여전히 필요 |
| C. 별도 후보 DB에서 병합 후 교체 | 기존 대상의 사본에 과거 자료를 재구성하고 모든 제약을 복구/검증한 뒤 전환 | 원본을 건드리지 않고 복잡한 병합을 준비할 수 있음. 병합 범위, 대상 변경 감지, 전체 의미 검증과 교체 복구가 추가돼 최초 설치 목적에는 부담이 큼 |

추천 근거는 설치, 재개와 형식 변경의 책임을 나누는 데 있다. 초기 DB를 프로젝트 안으로 옮기기 위해 과거 실행을 재구성할 필요를 줄이고, 실제 형식 변경은 [전용 변환 절차 — 「DB 형식 변경과 전환」](maintenance.md)에 남긴다. B를 채택하더라도 임의 DB 복사, 새 형식으로의 자동 변환, 두 DB의 내용 병합을 허용하는 것은 아니다. 기존 사용자 자료를 보존한다는 요구도 유지한다.

#### 설치부터 업데이트까지 이어 쓰는 기록

두 안 모두 **최초 설치의 중요한 기록을 보존하고 이후 관리 작업의 기록을 프로젝트 상태 DB에 이어 쌓는 것**이 목표다. B의 ‘최초 전용 DB’는 처음에 한 설치의 기록만 담는다는 뜻이다. 설치 후 버리거나 업데이트마다 새로 만드는 DB를 뜻하지 않는다.

첫 제외 설정 전에는 프로젝트 안에 기록을 안전하게 둘 준비가 끝나지 않았으므로 [외부 최초 보존 공간 — 「첫 기록 생성과 인계」](../runtime/install.md)에서 시작한다. 여기에는 제외 설정 자체의 변경 전 자료와 진행도 남긴다. 이 시작 조건은 두 안이 같다.

| 단계 | 기존 행별 수신 초안 | B의 위치 전환 |
| --- | --- | --- |
| 설치 시작 | 외부 DB에 초기 기록 저장 | 동일 |
| 프로젝트 안으로 인계 | 다른 대상 DB에 필요한 기록과 참조를 행별로 다시 등록하고 현재 상태 구성 | 초기 DB 전체의 같은 형식 사본과 필요한 파일을 새 위치에서 검증한 뒤 진행 전환. 과거 행을 새 실행으로 재등록하지 않음 |
| 인계 이후 | 프로젝트 DB에 남은 설치/후속 관리 기록 추가 | 초기 기록을 이어받은 프로젝트 DB에 남은 설치/후속 관리 기록 추가 |
| 후속 업데이트 | 유효한 프로젝트 DB 사용 | 동일. 최초 외부 보존과 위치 전환을 매번 반복하지 않음 |

평소 새 진행을 기록하는 DB는 한 개다. 안전한 인계와 복구를 위해 외부 보존본, 후보나 백업 파일이 잠시 함께 존재할 수 있으므로 물리적인 DB 파일이 언제나 정확히 하나라는 보장은 아니다. 전환 뒤 옛 사본에는 새 진행을 쓰지 않으며, 조건을 충족하면 기존 명시적 정리 절차로 정리한다.

업데이트에서는 같은 DB에 새 요청/계획과 시도를 만들고 기존 설치 이력을 유지한다. 반영/검사 결과, 실패와 재시도 또는 이전 구성으로의 복원 사실도 연결한다. 업데이트를 취소하고 이전 구성을 복원하더라도 그 업데이트가 시도됐다는 이력까지 지우지 않는다. 상세는 [반영 기록과 완료 연결](../runtime/update.md)이 소유한다.

공식 배포본 업데이트와 DB 저장 형식 변경은 별개다. 저장 형식이 그대로면 기존 DB를 사용하고, 형식 변경이 필요하면 [호환 조건 — 「DB 형식과 이전 구성의 호환」](storage.md#DB%20%ED%98%95%EC%8B%9D%EA%B3%BC%20%EC%9D%B4%EC%A0%84%20%EA%B5%AC%EC%84%B1%EC%9D%98%20%ED%98%B8%ED%99%98)에 따라 후보에서 기존 기록을 보존/변환하고 검증한 뒤 전환한다. 이때도 빈 DB로 새로 시작하지 않는다. 단순 대화마다 DB 기록을 강제하거나 모든 WIKI 본문/로그를 DB에 넣는 범위로 확대하지 않으며, [파일과 소유](records.md)의 역할을 유지한다.

#### B의 사용 흐름과 기존 자료

1. 현재 프로젝트의 제외 효력과 기록을 확인한다. 이미 유효한 프로젝트 DB가 있으면 그 DB에서 계속하고 초기 DB를 새로 만들지 않는다. 기존 DB는 있으나 제외가 깨졌거나 내용이 불명확하면 보존한 채 기존 준비/복구 절차로 반환하며 빈 DB로 대체하지 않는다.
2. 첫 설치라면 그 설치만의 외부 DB에 준비와 실제 결과를 기록한다. 제외 준비가 끝나면 같은 프로젝트의 실행 소유 아래 새 효과를 멈추고 인계할 기록과 파일 목록을 확정한다.
3. 같은 지원 형식의 DB를 **새 후보 파일**에 Backup API로 보존하고 필요한 파일을 대조한다. 기록된 원래 값, 참조, 정리 사실과 정상 보호가 유지되는지 확인한다. 기존 프로젝트 DB에 Backup API를 직접 실행하지 않는다.
4. 확인한 후보의 수신, 원본의 확인과 대상 활성화를 순서대로 기록한다. 활성화 전에는 어느 사본에서도 다음 설치 효과를 실행하지 않는다. 이후 프로젝트 DB에서만 계속하고 외부 사본은 보존/명시적 정리 대상으로 둔다.
5. 다시 실행하면 같은 인계와 실제 대상을 대조해 완료 다음부터 진행한다. 같은 인계의 미완료 후보는 확인 후 재개하고, 이미 진행한 프로젝트 DB를 옛 사본으로 덮지 않는다. 관련 없는 DB나 충돌하는 후보가 발견되면 병합하지 않고 차이를 보고한다.

예를 들어 제외 설정을 마친 뒤 복사 중 종료됐다면 남은 초기 기록으로 **인계부터** 이어간다. 이미 프로젝트에서 다음 단계까지 진행했다면 그 진행을 유지한다. 일반 업데이트는 이 최초 복사를 반복하지 않고 현재 프로젝트 DB를 사용한다.

#### 연결한 계약과 남은 검증

records/install의 최초 인계, 이 절의 식별/수신과 공통 쓰기 조건, maintenance의 사본/변환, state의 실행 소유와 수용 입력을 B에 맞췄다. DDL의 불변 side를 위 단계로 바꾸고 대상 DB의 식별/revision을 재발급하던 초안은 철회했다. 현재 SQLite/공통 진입 예제는 메모리 검사이며 제품 설치기는 아니다.

B도 DB 둘과 외부 파일을 하나의 트랜잭션으로 처리하지 못한다. 후보/파일 목록과 실제 소유 입력은 위 명세에 연결했으며, 모든 저장 소비자의 공통 진입 구현, 실제 Windows 파일/프로세스 중단과 재개, 다른 형식의 변환/이전 실행 호환 검증은 남아 있다. 실제 시간, 토큰 차이나 전체 구현 공수는 측정하지 않았다.

#### 공식 근거와 현재 판정

- [SQLite Backup API](https://www.sqlite.org/backup.html)는 DB 사본을 만들며 대상의 기존 내용을 대체한다. 그래서 B의 목적지는 새 후보여야 한다. [API 계약](https://www.sqlite.org/c3ref/backup_finish.html)은 완료 전 중단과 원본 변경 시 재시작을 설명하므로, 제품의 진행 동결과 복사 완료/수신 확인을 구별해야 한다.
- [Python sqlite3.backup](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.Connection.backup)은 같은 API를 사용할 수 있는 공식 인터페이스다. 별도 서버나 행별 재생 엔진이 필요한 근거는 아니다.
- [SQLite 형식 변경 절차](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes)는 테이블과 연결된 인덱스, 트리거, view, 외래 키를 함께 재구성/검증한다. 이는 C와 실제 형식 변환의 참고 근거이며 B의 단순 복사만으로 그 검증이 끝났다는 뜻은 아니다.
- [AWS의 멱등 요청 설계](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)는 같은 요청 식별과 원래 입력의 대조를 설명한다. B에도 재시도 식별을 유지하되 원격 서비스의 원자성을 로컬 파일 인계에 그대로 주장하지 않는다.

기존 7개 검사의 Backup API 사례는 같은 형식의 스키마와 행 보존만 확인했다. 이후 [B 검사](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md) 16개에서 위치를 주입한 공통 진입 예제와 단계/중단을 확인했다. 실제 위치 식별, 파일 인계, 원본/대상 유실과 Windows 강제 종료까지 검증한 결과는 아니다. 채택, 부분 검사와 실제 제품 구현 완료를 구분한다.

## 중복 전달과 뒤늦은 관측

**같은 요청의 재전달은 같은 ID를 사용하고, 실제 새 실행은 새 시도를 사용한다.** 명령/본문이 같다는 이유로 사용자가 요청한 별도 실행까지 합치지 않는다. 계획, 확정 관측과 파일 참조는 기본적으로 추가 보존하며, 같은 ID/같은 사실이면 기존 기록을 반환하고 다른 사실이면 충돌을 반환한다.

`INSERT OR REPLACE`로 중복을 처리하지 않는다. SQLite의 REPLACE는 충돌하는 기존 행을 지운 뒤 새 행을 넣을 수 있다. 무조건 IGNORE하는 방법도 내용이 다른 요청을 성공처럼 숨길 수 있으므로 사용하지 않는다. 저장 코드는 어떤 키가 충돌했는지와 기존 사실을 대조한다. [SQLite 충돌 처리](https://www.sqlite.org/lang_conflict.html).

11/15 초안의 `(attempt_id, check_id)`는 **실행별 검사 묶음의 식별**로 유지하고, 저장된 관측 하나에는 `id`를 추가하는 후보로 보강한다. 결과가 미확정이었다가 기존 실행의 종료/보고서를 확보한 경우, 이전 행을 고치거나 새 실행을 꾸미는 대신 `previous_id`와 보충 근거를 가진 관측을 추가한다. 이는 모든 상태 변화를 별도 이벤트 저장소로 옮기는 방식이 아니다.

| 상황 | 처리 |
| --- | --- |
| 같은 관측이 응답 유실 뒤 다시 도착 | 같은 ID와 사실을 확인해 기존 기록 반환. 행/재실행 추가 없음 |
| 미확정 관측 뒤 같은 실행의 추가 근거 확보 | 같은 시도/검사에 후속 관측 추가. 원래 미확정과 그 이유 보존 |
| 확정된 PASS/FAIL과 충돌하는 보고서 도착 | 자동 덮어쓰기나 새 ID만으로 정정 금지. 이미 관측한 종료/결과를 지우지 않고 시도의 미확인 사유와 충돌 근거 참조를 저장해 반환. 재개 조회에서도 누락하지 않으며 해소 전 완료 불가 |
| 수정 뒤 검사를 실제 다시 실행 | 새 `attempt_id`에 결과 저장. 원래 실패를 해소할 근거가 되는지 별도 대조 |

관측 연결은 같은 시도/검사 안에서 하나의 시작점과 한 방향의 후속만 허용한다. 첫 관측에는 `(attempt_id, check_id) WHERE previous_id IS NULL`의 부분 유일 인덱스를, 후속에는 `previous_id`의 유일 제약과 같은 묶음을 참조하는 복합 외래키를 사용한다. 동시에 두 보충이 오면 한쪽을 임의로 최신으로 삼지 않고 내용을 대조한다. 시각의 최댓값 대신 후속이 없는 끝 관측을 찾되, **끝 관측이라는 사실만으로 유효한 PASS는 아니다.** [SQLite 부분 유일 인덱스](https://www.sqlite.org/partialindex.html#unique_partial_indexes).

확정 판정을 뒤집는 정정 인터페이스는 아직 명세하지 않았다. 첫 자동 경로는 근거를 확인한 미확정 보충에 한정하고, 충돌 자료는 해당 시도의 근거로 보존한다. 새 관측 ID가 원래 실패를 우회하는 수단이 되지 않아야 한다.

## 조건부 갱신과 트랜잭션

계획 본문과 결과 관측을 덮는 작업과, 실행 중인 시도의 관측 상태를 보강하는 작업은 구분한다. 상태 전환은 [기존 실행 상태 — 「작업과 실행의 상태」](recovery.md)를 따르며 짧은 실행의 `prepared` → `ended`도 실제 근거가 있을 때 허용한다. 취소 요청은 종료 사실을 대신하지 않는다.

수정 가능한 작업 참조와 시도 행에는 충돌 확인용 정수 `revision`을 두는 후보를 사용한다. `NOT NULL`인 0 이상의 정수로 제한한다. 읽은 뒤 다른 저장이 있었는지 비교하기 위한 값이며 제품 릴리스나 파일명 버전이 아니다. 내용이 실제 바뀔 때만 증가하고 중복 전달/조회마다 올리지 않는다. 상태가 다른 값을 거쳐 원래 값으로 돌아와도 오래된 쓰기를 구별할 수 있어 상태 문자열만 비교하는 것보다 한 값을 더 두는 근거가 있다.

아래는 조건부 갱신 모양을 설명하는 SQL 조각이며 완성된 저장 함수가 아니다. 실제 종료/프로세스 관측 필드도 같은 저장 요청에 포함한다.

```sql
UPDATE attempts
SET state = :state, revision = revision + 1
WHERE id = :id
  AND revision = :expected_revision
  AND state = :expected_state;
```

영향 행이 1개인지 확인하고, 0개면 현재 기록을 다시 읽어 중복 완료인지 충돌인지 구분한다. 새 값을 읽어 무조건 덮어쓰는 재시도는 하지 않는다. 일반 코드가 허용 전환과 증거를 먼저 검사하며 CAS 조건만 맞았다고 임의 상태 전환을 허용하지 않는다. 늦은 결과 수집과 현재 작업 진행/active 반영도 따로 판단한다.

| 저장 경계 | 한 DB 트랜잭션에 포함할 것 | 밖에서 수행할 것 |
| --- | --- | --- |
| 계획/시도 준비 | 해당 종류의 계획/의무 또는 변경 단위, 시도와 필요한 현재 참조 연결 | 후보 분석과 사용자 확인, 실제 명령 실행/파일 반영 |
| 결과 수집 | 종료 관측, 파일 참조, 결과 관측/연결과 조건부 상태 갱신 | 로그/보고서 보존, 실제 실행/내용 대조 |
| 설치 단위 완료 | 유효한 검사/추가 확인과 공유 기준의 실제 반영 참조, 단위 완료 근거 | 파일 반영, 검증 실행과 공유 기준 저장 |
| 인계 수신 | 필요한 설치 행/참조와 수신 사실의 중복 대조/저장 | 원본 DB 확인, 파일 복사. 원본 확인과 대상 전환은 각각의 후속 트랜잭션 |

쓰기에는 짧은 `BEGIN IMMEDIATE`로 현재 사실을 재대조하고 관련 문장을 저장하는 후보를 사용한다. 한 번에 한 작성자를 허용하는 DB 잠금은 Windows의 실행 소유와 파일 보호를 대신하지 않는다. DB 잠금 대기는 실제 검사/AI 실행의 시간 제한과 별개이며, 바쁘다고 기존 프로세스를 종료하지 않는다. [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html).

SQL 문장 실패가 앞선 문장까지 전부 취소했다는 가정은 금지한다. 작업 묶음에서 오류가 나면 트랜잭션 상태를 확인해 rollback하고, commit의 성공 여부가 불명확하면 같은 ID로 저장된 사실을 다시 대조한다. DB 저장을 재확인하기 위해 파일 반영이나 검사를 다시 실행하지 않는다. commit 시 BUSY로 트랜잭션이 남은 경우도 구분하며 재시도 한도/안내는 저장 구현에서 정한다. [오류와 commit의 동작](https://www.sqlite.org/lang_transaction.html#response_to_errors_within_a_transaction).

## 필요한 범위의 조회

아래 순서는 검증 의무의 조회다. 설치 요청은 앞의 단위 완료/복원과 인계 상태도 확인하며, 검증 미완료 목록이 비었다는 이유로 설치 전체를 완료하지 않는다. 평소 문맥 인계는 필요한 작업 참조만 읽고 설치 조회/쓰기를 자동 시작하지 않는다.

재개는 기존 DB만 여는 경로를 사용한다. 조회는 읽기 전용, 쓰기 재개는 기존 파일 열기 모드를 구별하고 파일 없음/접근 거부/손상/미지원 형식을 빈 정상 결과로 바꾸지 않는다. 여러 SELECT로 한 판단 자료를 만들 때는 짧은 읽기 트랜잭션의 일관된 시점을 사용하고 AI 판단을 기다리며 연결/트랜잭션을 유지하지 않는다. [Python SQLite URI](https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris), [SQLite 읽기 트랜잭션](https://www.sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions).

1. 명시한 작업과 현재 계획을 확인하고 해당 의무 목록에서 시작한다. 결과 행이 있는 검사만 조회하면 미실행 의무가 사라지므로 의무를 기준으로 결과를 연결한다.
2. 관련 시도/관측과 파일 참조를 가져온다. 현재 계획만 남기고 과거 의무를 버리지 않으며 후속 계획의 제외/변경 근거와 원래 실패도 따라간다. 미확인 시도는 필요에 따라 실제 프로세스/산출물 대조로 넘긴다.
3. 일반 코드와 메인이 [현재 입력과 재사용 기준 — 「재사용을 판단하는 순서」](verification.md)에 따라 근거를 판정한다. 같은 의무의 유효한 후속 성공은 과거 실패를 해소할 수 있지만 다른 검사 PASS, 미실행, 근거 부재나 필수 CI 대기는 전체 완료가 아니다.
4. 기존 `unresolved`, `pending`, `unknown_attempts`, `evidence_refs`로 필요한 요약만 반환한다. 조회 한도가 있으면 남은 항목과 이어 읽을 기준을 알리고, 조회 도중 기준이 바뀌면 대조한다. 전체 이력/로그를 모델에 매번 보내지 않는다.

조회용 인덱스는 작업별 계획, 계획별 시도, 미완료 시도와 시도/검사별 관측, 외래키 자식 참조부터 검토한다. 기본키/유일 제약이 이미 만든 인덱스를 중복 생성하지 않는다. 실제 쿼리와 누적 자료로 실행 계획/비용을 확인한 뒤 확정하며 모든 열이나 JSON 내용에 인덱스를 미리 붙이지 않는다.

## DB 형식과 이전 구성의 호환

DB의 `schema_version`은 기존 메타데이터 한 곳에서 관리한다. SQL 테이블뿐 아니라 그 형식에 속한 JSON 필드/종류/의미의 호환도 함께 판단한다. 공식 모듈 릴리스 번호와 같게 올리거나 파일/필드 이름에 버전 접미어를 붙이지 않는다. SQLite 엔진의 `schema_version` PRAGMA는 앱의 형식 번호로 쓰지 않으며 `user_version`에 같은 값을 중복 저장하지 않는다. [SQLite의 내부 schema_version](https://www.sqlite.org/pragma.html#pragma_schema_version).

각 공식 실행 버전은 읽을 수 있는 형식과 쓸 수 있는 형식을 구분해 확인한다. 알 수 없는 열/JSON을 버리고 다시 저장하거나 버전 숫자만 낮춰 구버전처럼 보이게 하지 않는다. 열을 추가했다는 사실만으로 옛 코드의 쓰기까지 호환되는 것은 아니다. 새 종류/상태를 옛 코드가 해석하는지, 필수 값과 완료 판정의 의미가 같은지 확인해야 한다.

| 업데이트의 기록 변화 | 반영 전 조건 | 이전 구성 선택 시 처리 |
| --- | --- | --- |
| DB 형식이 그대로임 | 새 코드와 기존 코드가 같은 자료를 읽고 쓰는 지원 범위와 실제 자료 대조 | 기존 파일/설정과 연결을 복원하고 현재 DB의 실패/복원 이력을 유지 |
| 새 형식이지만 기존 실행도 지원함 | 기존 실행의 조회뿐 아니라 재개/추가 저장과 의무 판정을 검증 | 파일을 복원한 뒤 같은 DB에서 기존 실행의 실제 사용 확인. 새 형식 번호를 임의로 낮추지 않음 |
| 기존 실행이 새 형식을 지원하지 않음 | 새로 쌓일 실패/복원 기록까지 보존하는 역변환과 재중단 복구를 별도 후보로 검증해야 함 | 검증된 변환 경로가 있을 때만 후보 전환 후 기존 사용 확인. 경로가 없으면 해당 업데이트는 첫 쓰기 전에 보류 |

첫 구현은 같은 저장 형식을 유지하는 업데이트부터 검증한다. 향후 형식 변경 자체를 금지하는 것은 아니며, 상세 변환은 [백업과 저장 형식 변경](recovery.md)에 연결한다. 지원 정보는 공식 배포물과 현재 DB를 비교하고, 실제 변환이 필요하면 보존한 사본으로 대조한다. 일반 개발 요청마다 예전 실행기를 다시 돌리는 기능이나 매 업데이트에서 전체 DB를 새로 만드는 방식을 추가하지 않는다.

예를 들어 skill 파일만 갱신하고 DB 형식은 그대로라면 그 파일의 이번 변경을 되돌린 뒤 동일 DB에서 복원 결과를 확인할 수 있다. 반대로 새 코드만 이해하는 필수 기록이 생겼다면 파일 복원만으로는 충분하지 않다. 이전 DB 사본을 덮어 실패/복원 기록을 지우는 방식은 채택한 이전 구성 사용을 만족하지 못한다.

사용자의 선택은 원래 업데이트 작업과 당시 변경 계획, 확인한 복원 범위에 연결한다. 같은 요청에서 계획을 보완하며 진행했다면 마지막 계획만이 아니라 그 요청이 실제로 반영한 이전 계획의 변경도 대조한다. 선택 기록은 실행 완료가 아니며 새 복원 시도와 현재 사용 검증으로 이어진다. 대기/재시도의 완료 보존과 명시적 전체 복원을 구별하고, 복원 중 재중단돼도 원래 선택/대상과 실제 남은 변경을 확인한다. 같은 범위의 허용은 재사용하되 새 사용자 편집이나 범위 변경을 과거 선택으로 승인하지 않는다. 선택 관계와 완료 참조는 아래 DDL 후보에 연결했으며, DB 형식을 바꾸는 실행 코드는 아직 없다.

이 조건은 [업데이트 실패 후 선택](../runtime/update.md)의 구현 전제다. 복원 가능성이 없다는 것을 알면서 먼저 적용하고 나중에 사용자에게 옛 버전 사용을 선택하게 하지 않는다. 지원 범위 밖의 장애는 사용 가능 여부를 보장하지 않고 실제 상태와 남은 자료를 보존한다.

## DDL과 저장 코드의 경계

[schema.sql](schema.sql)은 이번 범위의 테이블, 제약, 조회용 view와 검사 트리거의 원본이다. 설치/갱신/복원의 기록을 검증 기록에 연결한 설계 후보이며, 제품 설치기나 기존 state.db에 실행할 마이그레이션 스크립트가 아니다. 빈 시험 DB에서만 검사했다. 실제 제품에 넣을 패키지/모듈 경계와 지원 버전은 개발 준비에서 정한다.

별도 DB 서버, ORM, JSON 확장이나 추가 AI 호출은 요구하지 않는다. 보통 개발 대화마다 이 모든 테이블을 조회하거나 쓰는 구조도 아니다. 기존 [조건부 기록 시점 — 「기록이 필요한 때와 비용」](records.md)을 그대로 따른다.

### SQL에 옮긴 필드

관계형 열에 있는 ID/종류/상태를 아래 JSON에 다시 저장하지 않는다. 아래 JSON은 공통 저장 코드가 필수 키, 형식과 기존 논리 계약을 검사한 뒤 바인딩한다. SQL의 JSON 텍스트 열은 JSON 구문이나 내용까지 검사하지 않는다.

| 논리 자료 | SQL 배치와 JSON에 남길 내용 |
| --- | --- |
| DB 식별과 형식 | `metadata` 한 행의 `db_id`, `schema_version`. 형식 번호는 릴리스 태그와 별개. 최초 예제의 값은 제품 지원 버전 선언이 아님 |
| 작업과 현재 참조 | `tasks`: 요청 ID, 두 종류의 현재 계획, 현재 선택, revision. `target_json`은 작업 사본/루트 식별, `request_json`은 목표와 허용 범위 |
| 계획 | `plans`: 종류, 이전 계획, 이유, 소유. `context_json`은 records의 context, 검증 `details_json`은 change_kind/gates/test_authoring. 변경 계획의 상세는 고정 배포 출처, 선택 기능과 허용/보호 조건 |
| 검사 의무 | `checks`: 필요성, 단계, 실행 정책, 이유. `details_json`에 scope/selection/exclusions/command를 저장. 검사 목록은 이 테이블이며 계획 JSON에 복제하지 않음 |
| 변경 단위와 파일 후보 | `units`, `unit_dependencies`, `changes`. `completion_json`에 적용/복원 검사 판단의 이유, 추가 확인과 공유 기준 반영 조건. `changes.details_json`에 대상 경로/관리 항목과 계획 때의 기준, 별도 `candidate_id`에 후보 파일 참조 |
| 실행 시도 | `attempts`: 종류, 원래 적용, 재시도, 상태/관측과 revision. `input_json`은 records의 input, `command_json`과 `process_json`은 해당 명령/프로세스 상세. `check_ids`는 attempt_checks로 저장 |
| 결과와 원문 근거 | `results`, `artifacts`, `result_artifacts`. 실제 관측과 소유는 열에, 큰 로그/사본은 파일에 보존. 추가 조건을 대조한 `assessment` 자료는 확인 과정의 근거이며 가짜 검사 PASS가 아님 |
| 실제 파일별 준비와 관측 | `attempt_changes`가 논리 변경에 연결하고 `attempt_files`가 각 위치의 원래 존재/부재, 사본, 예상 내용과 관측을 저장. `observation_json`은 관측한 식별/내용, 오류/확인 시점 등. 파일을 읽었다는 사실과 도구가 썼다는 증거를 구별 |
| 백업과 유지 관리 | `backups`, `transitions`, `resource_holds`, 정리 계획/항목/확인/확정/관측. 정확한 필드와 소비는 [백업과 정리 — 「저장 필드와 소비자」](maintenance.md)에 통합 |
| 인계 | `handoffs`: 원본/대상 식별, 고정 전달 내용/해시, 실제 receipt, 원본 확인과 대상 활성화. JSON 내용과 DB 사이 대응은 전달 코드가 검사 |

이름 변경은 원래 위치 `source`와 새 위치 `target`을 각각 보존한다. 기존 목적지 파일도 있었다면 그 사본까지 필요하다. 일반 생성/수정/삭제는 `target` 하나를 사용한다. 부재를 빈 파일로 대신하지 않으며 복원 시 `restore_from`은 원래 적용 시도의 같은 변경/위치를 참조한다. 예상 복원 내용도 그 사본/부재와 대조한다. 경로 재배치, 링크/파일 ID, 실제 작업 종류에 맞는 존재/내용의 의미 검사는 여전히 저장 코드의 책임이다.

### 필수 의무에서 완료 확인

`unit_requirements`는 **계획이 요구한 검사**, `unit_checks`는 **이번 시도에 채택한 관측**이다. 하나로 합치면 결과가 없는 검사가 목록에서도 사라질 수 있어 구별했다. 검사 불필요 판단은 단위의 정책과 이유에 남기며, 의무가 필요하다고 적고 실제 의무 목록을 빼면 완료를 거부한다.

`unit_outcomes` 저장 때 필요한 파일 관측, 의무의 결과, 실제 종료, 미확인 여부와 추가 확인 자료를 검사한다. `completion_results`는 이때 쓸 구조 조건을 한 곳에서 조회하는 view다. 독립 PASS 저장소가 아니며 입력 변경이나 나중에 드러난 충돌이 있으면 과거 완료를 현재 유효한 것으로 사용하지 않는다. 신뢰/활성화, 공유 기준의 의미, 실제 테스트 내용과 현재 파일은 저장 코드가 대조한다.

계획의 본문/이전 참조와 결과는 불변이다. 계획을 현재 참조로 공개하거나 시도/선택/다른 의무에 사용한 뒤에는 자식 의무를 추가하지 않는다. 보완은 새 계획으로 연결한다. 완료에 사용한 결과 파일 목록과 단위 선택 근거도 뒤늦게 바꾸지 않는다. 일반 DELETE는 계속 막으며 파일 정리의 확인/관측은 [유지 관리 관계 — 「정리 허용과 실제 제거」](maintenance.md)에 추가한다. 과거 이력은 지우지 않고 정리된 근거의 새 소비를 막는다. DB를 직접 조작할 수 있는 사람에 대한 보안 경계로 트리거를 해석하지 않는다.

### 선택과 전체 복원의 연결

| 관계 | 역할 |
| --- | --- |
| `choices` | 사용자 선택, 요청/당시 계획, 허용 범위와 앞선 선택. `retry` 또는 `restore`이며 선택 시점까지의 적용 순서 `apply_limit`을 보존 |
| `restore_targets` | 해당 요청의 적용 시도 각각을 대조. 아직 미확인, 실제 무반영 확인, 기존/새 복원 완료 참조를 구별 |
| `restore_checks` | 이전 구성의 필수 사용 검증 의무에 대응하는 관측. 같은 이름의 다른 검사 결과를 가져오지 않음 |
| `restore_outcomes` | 이번 요청의 변경 전체와 기존 사용을 확인한 근거. 사용자 선택이나 일부 단위 복원만으로 생성하지 않음 |

예를 들어 첫 계획에서 A를 고쳤고 보완 계획에서 B를 고치다 실패했다면, 이전 구성 선택은 A/B 양쪽의 적용 시도를 대조한다. 현재 계획의 B만 복원했다고 전체 완료할 수 없다. 이미 실패 단위를 복원한 기록이 있으면 실제 상태를 다시 대조해 연결하며, 없는 일을 만들려고 복원을 재실행하지 않는다. 아무 파일도 바꾸지 않은 시도는 실제 무반영 확인으로 닫고 준비 기록만으로 추정하지 않는다.

`attempts.sequence`와 `attempt_files.write_order`는 같은 요청 안의 준비 순서다. 시각이나 여러 계획의 단위 번호만으로 순서를 추측하지 않는다. 전체 복원은 이 순서, 실제 반영/복원 관측과 의존을 함께 대조해 요청 전 상태를 재구성한다. 먼저 준비한 작업이 실제로 먼저 썼다는 사실은 SQL만으로 증명되지 않는다. 공통 실행 경로의 순서 준수, 같은 파일 식별과 짧은 반영 소유 확인이 전제이며 임의의 역순 파일 덮기는 허용하지 않는다. 원래 적용이 일부만 반영된 경우와 뒤늦은 사용자 편집도 확인한다.

현재 선택이 전체 복원이면 새 적용을 막는다. 재시도를 다시 선택하면 새 선택으로 연결한다. 같은 허용을 매번 새 선택/확인으로 만들지 않으며, 재개는 기존 선택과 실제 범위를 대조한다. 요청 전체 복원 완료는 모든 적용 시도, 미확인, 필수 사용 검사에서 시작하므로 목표 목록에서 한 시도를 빼서 완료를 만들 수 없다. 기록 자체를 과거 DB로 덮는 동작은 추가하지 않았다.

### SQL 밖에서 반드시 검사할 것

- JSON의 필수 값/타입/중복 키, 원문/명령의 비밀값 배제와 경로 이탈, 실제 Windows 파일/작업 사본의 동일성.
- 준비 묶음의 완전성, 계획/단위 의존 순환, 허용 상태 전환과 같은 ID/내용의 재전달. CAS는 기대 revision으로 갱신하고 자식 변경과 같은 트랜잭션에서 영향 행을 확인한다. 트리거의 revision 증가 검사만으로 오래된 쓰기를 막았다고 보지 않는다.
- 검사 내용과 현재 입력의 유효성, 파일 반영 소유, 사용자 편집, 공유 기준과 신뢰/활성화. 문자열 `matched`, PASS 또는 assessment 파일의 존재가 이 의미 검사를 대체하지 않는다.
- 인계 두 DB의 실제 수신/확인, 원문 파일의 저장 내구성, 옛 실행의 DB 읽기/쓰기 호환과 전체 복원 뒤 실제 사용.
- 유지 관리 목록/영향 해시의 실제 계산, 현재 필요한 자료의 보호 등록/해제, 최신 정리 승인과 실제 파일 동일성. SQL에 관계가 있다는 사실만으로 안전한 파일 정리가 구현된 것은 아님.

트리거는 같은 DB의 다른 행을 검사하고 잘못된 저장을 거부하는 용도로만 사용했다. 실행/파일 변경이나 완료 근거 자동 생성은 넣지 않았다. [SQLite 외래키](https://www.sqlite.org/foreignkeys.html)의 소유/존재 검사와 [트리거](https://www.sqlite.org/lang_createtrigger.html)의 행별 검사를 구분한다. 제약 실패 후 같은 묶음의 앞선 문장을 취소할 책임은 위 명시적 트랜잭션 계약에 남는다.

## 다음 연결과 검증

[DDL 검사 기록](../../evidence/experiments/recovery/2026-11-16_19-13-46-storage-ddl.md)에 SQL 원본, 검사 입력과 원시 결과를 보존했다. 첫 24개 검사 통과 뒤 완료 근거의 추가 변경 차단과 대응 사례를 보강했고 최종 29개가 통과했다. 실제 환경은 WSL Python 3.10.12/SQLite 3.37.2의 메모리 DB다. 후보 Python 3.12+ 연결 API, 파일 journal/잠금/강제 종료나 실제 Windows 제품 동작을 시험한 결과가 아니다. 시험 JSON/보고서는 관계 검사에 필요한 최소 가상 자료이며 제품 입력 검사를 통과한 자료로 사용하지 않는다.

[SQL 입력 — 「SQL 저장 규칙의 검증 입력」](../../verification/acceptance.md), [저장 형식/연결 입력 — 「저장 형식과 연결의 검증 입력」](../../verification/acceptance.md), [설치/인계 입력 — 「설치 기록과 인계 관계의 검증 입력」](../../verification/acceptance.md)을 유지한다. 부분 SQL 통과로 이 수용 사례 전체를 통과 처리하지 않는다. [백업과 정리의 파일별 명세](maintenance.md)는 사본 범위, 형식 전환과 정리 대상의 보호를 연결한다. 일반 DDL의 삽입/변경/삭제 제약과 [최초 인계/변환 — 「기존 DDL과 인계의 연결」](maintenance.md)의 작성 순서는 별도 대조가 필요하다. 11/17에는 [유지 관리 관계 — 「저장 필드와 소비자」](maintenance.md)를 DDL에 반영했다. [새 검사 기록](../../evidence/experiments/recovery/2026-11-17_08-11-05-maintenance-ddl.md)은 유지 관리 29개와 기존 저장 29개, 인계 6개의 통과를 보존한다. 이전 인계 fixture의 회귀 확인이며 새로운 유지 관리 행까지 전달하는 인계/변환 전체를 검증한 것은 아니다. 이후 [공통 입력과 파일 대조](maintenance.md)를 명세하고 Windows 수용 입력에 연결했다. [유지 관리 이력 순서 — 「유지 관리 기록의 인계 순서」](storage.md#%EC%9C%A0%EC%A7%80%20%EA%B4%80%EB%A6%AC%20%EA%B8%B0%EB%A1%9D%EC%9D%98%20%EC%9D%B8%EA%B3%84%20%EC%88%9C%EC%84%9C)의 7개 합성 검사를 추가했으며 B의 수신/확인/활성화 관계와 공통 쓰기 계약을 보정했다. 이번에는 파일 목록/실제 소유와 단계별 중단 입력을 연결했으며 실제 Windows 시험은 남아 있다. 다음 설계 단위는 [현재 진행표](../../development/roadmap.md)의 사용자 실행 흐름과 지원 조건 대조다. 실제 삭제, 전환과 제품 정리 완료로 해석하지 않는다.
