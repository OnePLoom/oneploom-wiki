## 작업 상태와 Git 제외

11/08 사용자 확인: active는 WIKI의 공유 지식이 아니라 **해당 코드 작업 공간의 실행 상태**로 둔다. 앱 Git과 별도 WIKI Git 모두에 올리지 않는다. 후속 합의로 새 배포는 문서 밖의 상태 폴더와 B 공유 제외, 자동 설정을 채택했다. 기본 상태 경로는 `.harness/state/`로 정리한다. 후속 합의로 `.harness/` 전체를 로컬 실행 자료 전용으로 예약하고 `/.harness/`를 제외한다. 설치기, hook, 복구의 실제 연결 구현은 이후 단계이며 현재 훅의 경로를 먼저 바꾸지 않는다.

외부 WIKI를 선택해도 코드 쪽 상태 폴더는 남는다. `docs` 전체를 외부 WIKI로 이동하거나 심볼릭 링크로 바꾸지 않고 지식 문서의 역할만 외부 원본에 연결한다. 기준은 임의의 터미널 현재 폴더가 아니라 등록한 코드 저장소의 작업 트리 루트다. 다른 worktree의 상태를 공유하거나 덮어쓰지 않는다. 같은 작업 트리에 진행 중인 상태가 있으면 새 작업으로 초기화하지 않고 재개/전환을 확인한다.

별도 저장소의 `docs`라는 이름이 같다는 이유로 Git이 충돌하지는 않는다. 문제는 `docs/**`를 통째로 WIKI로 판단하거나 복사, 분석할 때 실행 상태까지 포함되는 것이다. 문서 역할은 등록한 WIKI 루트에서 찾고 실행 상태는 코드 루트의 별도 영역에서 찾는다. 외부 WIKI 폴더 이름은 `project-wiki`, `wiki`, `docs` 등 사용자가 선택할 수 있으며 코드 쪽 이름과 일치시킬 필요가 없다. 상대 문서 링크는 WIKI 루트를 기준으로 보존한다.

```text
코드 작업 폴더/               앱 Git
  .gitignore                 /.harness/ 제외 규칙
  .harness/                  로컬 전용: 상태, 캐시, 임시 자료, 기기별 연결
    state/                   active, 복구용 로컬 파일
  docs/                     내부 WIKI를 선택한 경우의 문서 후보

외부 WIKI 작업 폴더/          외부 WIKI를 선택한 경우의 별도 Git
  README.md                 지식 문서의 진입점
  ...                       요구사항, ADR, 검증 근거
```

두 WIKI 위치는 선택에 따른 예시이며 같은 지식을 두 원본으로 유지하지 않는다. 내부 WIKI도 상태와 문서를 분리한다. 기존 혼재 구조는 입력/이전 명세에서 분리하며 기존 문서를 임의로 옮기지 않는다.

Git 제외와 경로 대안은 [ADR 0016 — 「작업 상태의 Git 제외」](../../decisions/knowledge/0016-storage.md)이 소유한다. **배포 기본값은 공유 `.gitignore` B와 설치기의 자동 등록, 검사다.** A는 비교 기록으로 남기며 첫 구현에 별도 모드나 자동 fallback을 추가하지 않는다. 상태/문서 경계, 제외 방침은 채택됐고 아래 설치, 복구 구현은 아직이다.

1. **설치, 재연결:** 코드/WIKI 루트와 상태 경로가 올바르게 분리됐는지 확인한다. 상태 파일이 이미 추적 중인지 먼저 검사하고, 발견하면 내용을 기록하기 전에 중단한다. 자동으로 추적을 해제하거나 과거 커밋을 고치지 않는다.
2. **제외 준비:** 설치기가 공유 `.gitignore`의 변경 계획을 보여주고, 설치 적용 시 필요한 규칙을 파일 맨 아래의 관리 구간에 자동으로 기록, 검사한다. 파일이 없으면 생성하고 기존 내용은 보존한다. 사용자가 경로를 직접 붙여 넣는 절차가 아니다. 설치 변경을 팀에 공유하는 commit, PR은 기존 프로젝트 절차로 진행한다. `.git` 디렉토리나 `/mnt/c`를 직접 조합하지 않으며 오류를 성공으로 처리하지 않는다.
3. **실제 작업 시작:** 이어받을 상태가 필요한 작업은 범위, 입력을 확정한 뒤 첫 실행 전에 active를 만든다. 역공학도 첫 처리 단위 전에 미완료 범위와 재개 지점을 남긴다. 단순 질의까지 active를 만들거나 설치만 마친 상태를 작업 완료로 기록하지 않는다. 커밋된 제외 규칙은 clone할 때 전달되지만 active 본문은 전달되지 않는다. 모듈 상태를 사용하는 시작, 재개 때 추적 여부와 실제 제외 효력을 검사하며 모델 추론은 사용하지 않는다.
4. **갱신, 재개:** active, 기계 기록과 필요한 복원 사본은 [기록 명세 — 「파일과 소유」](records.md)의 로컬 제외 영역에 둔다. 기존 scope/marker의 범위와 현재성 대조 목적은 유지하되 옛 `.scope`/`.state` 파일 형식을 제품 계약으로 고정하지 않는다. 코드/WIKI 버전과 남은 작업을 대조하고, 입력이 바뀌면 과거 PASS나 다음 단계를 무조건 재사용하지 않는다. 외부 WIKI 입력의 변경 감지, 보존은 복구 계약에 포함하며 기존 저장소 내부 `.scope` 검사만으로 해결됐다고 보지 않는다.
5. **기록, 배포:** 작업에서 확정한 결정, 검증 근거만 검토해 WIKI로 남긴다. active 원문과 로컬 상태는 WIKI 후보 수집, 커밋 묶음, 배포물에서 제외한다. Git 제외는 백업이 아니므로 미완료 상태는 로컬 복구 자료로 보존한다. 다른 기기로의 재개는 별도 인계이며 새 clone만으로 상태가 복구된다고 약속하지 않는다.

선택 기능을 설치한다고 그 기능 전체를 Git에서 제외하지 않는다. 공유할 skill, hook, 설정은 버전이 확인되는 설치물/프로젝트 자산으로, 실행 중 상태, 임시 결과는 로컬 제외 영역으로 관리한다. 기능이 남기는 장기 지식은 WIKI의 공개 범위와 역할에 따른다. `.harness/`에는 이런 로컬 자료만 넣으며 폴더 전체를 제외한다. 공유할 실행 코드, skill, hook, 프로젝트 설정은 이 폴더 밖에 둔다. 새 기능도 공유 자산과 로컬 산출물을 구분해 배치하고, 로컬 자료는 같은 제외 영역을 사용한다. 기기별 연결 정보에도 비밀값을 저장하지 않는다.

11/15 후속 확인: `.harness/`를 세션 전용으로 좁힌 적은 없으며 위 `state/`가 이미 하위 책임을 구별한다. `session/`으로 다시 감싸거나 기능마다 DB를 늘리는 대신 [로컬 영역의 확장](records.md) 기준으로 필요한 자료만 배치한다. 실제 제품 폴더/DB를 생성한 것은 아니다.

### 제외 규칙의 자동 설정

11/08 B 공유 제외와 자동 설정을 채택했다. `.gitignore` 수정은 **모듈 설치기가 구현할 작업**이며 아래 절차는 아직 미구현이다. 별도 관리 도구나 사용자의 수동 편집 단계를 추가하지 않고 기존 설치, 기능 추가, 경로 변경에 연결한다.

설치와 갱신에서 모듈이 관리하는 제외 구간은 프로젝트 루트 `.gitignore`의 **맨 아래**에 둔다. 기본 규칙은 `/.harness/`다. 앞의 `/`는 루트 기준, 끝의 `/`는 디렉토리 전체를 뜻하므로 `/**`를 붙이지 않아도 모든 하위 로컬 자료가 제외된다. `/docs/`, `/docs/**`를 제외하지 않으며 WIKI와 공유 자산은 `.harness/` 안에 배치하지 않는다. 기존 `.harness/`에 공유 자산이 있으면 넓은 제외를 먼저 적용하지 말고 충돌로 알린다. [Git 패턴 기준](https://git-scm.com/docs/gitignore).

설치기, 런처, hook, 백업, 제외 규칙은 같은 상태 경로 정의에서 파생하고, WIKI 연결은 별도 문서 루트를 사용한다. 실제 해석된 경로가 같거나 상태 영역과 등록한 WIKI 내용이 겹치면 설치를 완료하지 않는다. 기존 혼재 입력은 이전 명세에서 분리하며 이름만 바꿔 중복 원본을 만들지 않는다. 현재 기존 시험 프로젝트의 기존 active 경로 재사용은 예비 문서 연결을 위한 호환 범위다.

| 실행 시점 | 자동 처리 |
| --- | --- |
| 최초 설치 | 코드/WIKI/상태 경로 대조 → 기존 추적/제외 검사 → `.gitignore` 맨 아래 관리 구간의 변경 계획 → 적용, 효력 확인 → 상태 파일 생성 허용 |
| 재설치, 기능 추가 | 관리 구간은 끝에서 갱신하고 같은 규칙을 중복 추가하지 않음. 새 기능이 기존 상태 영역을 사용하면 제외 범위를 늘리지 않음. 추가 범위가 꼭 필요할 때만 변경 계획에 포함 |
| 상태 경로 변경 | 새 경로의 제외를 먼저 준비, 검사한 뒤 보존/이전. 이전 상태가 남아 있으면 기존 제외 규칙을 성급히 제거하지 않음 |
| 일반 시작, 재개 | 추적 여부와 제외 효력을 검사. 규칙 누락, 충돌은 정상 설치로 처리하지 않고 설치 복구로 안내. 매번 `.gitignore` 끝에 규칙을 붙이지 않음 |

적용은 반복해도 같은 결과가 나와야 한다. 기존 동일/상위 규칙과 예외의 효력을 먼저 대조하고, 관리 구간의 소유와 이동을 변경 계획에 표시한다. 끝에 둔다는 이유로 기존 사용자 규칙을 임의 재정렬하거나 같은 줄을 계속 붙이지 않는다. 소유가 불명확하거나 예외와 충돌하면 기존 보존 계약대로 확인한다. 주석, 다른 도구 규칙, 사용자 수정은 보존하고, 기존 추적 파일, 쓰기 실패는 자동 추적 해제나 광범위한 덮어쓰기로 처리하지 않는다. 적용 중 다른 변경을 발견하면 중단하며 실패 복원도 이번 도구 변경 범위에 한정한다.

상태 생성 전에 `git ls-files`로 실제 추적 여부를, `git check-ignore`로 실제 제외 효력을 확인한다. 검사가 성공해야 다음 분석 단계로 넘어간다. 설치기가 `.gitignore`를 수정하는 일과 commit, push, PR 승인은 별개이며 기존 Git 작업 권한을 따른다. 이 처리는 일반 파일/Git 명령으로 구현하고 AI 추론을 호출하지 않는다.

설치 실패로 `.gitignore`를 복원할 때도 남은 로컬 자료의 제외를 유지해야 한다. 제외 규칙을 먼저 지워 복구 자료가 노출되거나, 일부 복원만 끝난 상태를 완료로 표시하지 않는다. 11/11 채택한 보고, 보존, 조건부 복원 원칙은 [실패 뒤 복구 방식](../runtime/update.md)을 따르며 정확한 저장/정리 절차와 제품 구현은 후속이다.

첫 `.gitignore` 변경을 보존할 때 아직 이 제외가 준비되지 않은 순환은 [첫 기록 생성과 인계](../runtime/install.md)에서 다룬다. 사용자별 앱 데이터는 기본 추천이며 외부 최초 보존 → 제외 적용/확인 → 프로젝트 기록 준비/인계의 순서다. [기록 형식과 인계 — 「최초 보존 자료의 형식」](records.md)는 SQLite 기록 코드를 재사용하고 같은 작업의 진행 원본을 한 곳으로 전환하는 초안이다. 일상 상태를 외부로 옮기거나 정상 개발마다 이 초기 절차를 반복하는 조건이 아니다.

일반 `git add`의 제외와 강제 추가 차단은 다르다. 이미 추적한 파일, `git add -f`, 우선순위가 높은 제외 취소 규칙을 고려해 모듈이 제공하는 커밋/배포 준비 단계에서도 상태 파일 포함 여부를 확인해야 한다. 사용자가 모듈 밖에서 실행하는 모든 Git 명령까지 막는 보안 장치는 아니다. 비밀값 비기록 원칙은 로컬 상태에도 적용한다. 앱 이미지처럼 Git을 통하지 않는 파일 수집은 별도의 제외 검사 대상이다.

[관측 기록 (격리 Git 관측)](../../evidence/experiments/recovery/2026-11-08_14-35-31-active-storage.md)은 정상 추가, 추적된 파일, 강제 추가, 규칙 우선순위, 새 clone, worktree의 10개 기대 관측을 확인했다. 실제 설치기, native hook, 모델 재개, 상태 백업 구현은 검증하지 않았다.

[관측 기록 (이전 패턴 관측)](../../evidence/experiments/recovery/2026-11-08_15-03-41-state-pattern.md)은 하위 state만 제외하던 경계의 기록이다. 당시 `.harness/config.json`을 제외하지 않는 기대는 이후 전체 로컬 영역 합의로 대체됐다. 새 공유 설정은 `.harness/` 밖에 둔다. 실제 설치기의 맨 아래 배치, 중복 방지, WIKI 경로 검증을 통과한 결과는 아니다.

[관측 기록 (전체 로컬 영역 관측)](../../evidence/experiments/recovery/2026-11-08_15-15-41-local-state.md)은 `/.harness/` 아래 상태, 캐시, 연결 설정, 추가 기능 임시 자료의 제외와 밖의 WIKI, skill, hook, 공유 설정, 다른 작업 영역의 보존, 총 9개 기대를 확인했다. 실제 설치기의 변경, 충돌 처리, 반복 적용을 검증한 것은 아니다.

## 세션 중단과 재개

세션 복구는 아래 적용 경계의 한 흐름이다. [검증 계약 — 「채택 원칙과 남은 명세」](verification.md)의 계획/시도, 원래 실패, 재사용 조건을 유지하고, 각 흐름이 필요한 기록만 연결한다. 공통 저장, 조회 책임을 공유하되 서로 다른 자동 실행이나 복원 권한을 합치지 않는다.

### 복구의 대상과 경계

**복구는 이어갈 문맥이나 실행 사실이 불충분할 때 필요한 범위를 확인하는 절차다.** 오류 발생, 상태 기록, 복구는 같은 의미가 아니다. 정상적인 실패 처리는 기존 개발, 재시도 흐름이 맡고, 기록은 이후 중단에 대비해 필요한 경계에서 남긴다.

| 상황, 진입 조건 | 읽거나 대조할 것 | 허용되는 다음 흐름 |
| --- | --- | --- |
| 문맥, 결과가 분명한 일반 질의/편집/검사 FAIL | 현재 요청과 해당 작업의 필요한 근거. 복구를 위한 active/DB 재독은 강제하지 않음 | 기존 조건부 개발, 수정, 재검증. 검사 시도 기록은 검증 계약에 따라 남김 |
| compact, 재접속, 새 세션에서 진행 중 작업을 이어받음 | 해당 active의 목표, 조건, 부모/현재/다음 단계와 필요한 참조 | 문맥 복구. 미확인 실행이 없으면 설치/PR, 전체 DB 대조로 확장하지 않음 |
| WIKI 분석, 검사, PR 연계 등 모듈 기능이 중단됐거나 결과/반영 여부가 불명확함 | 해당 계획, 시도, 결과와 실제 프로세스/파일/필요한 원격 상태 | 완료 단위 유지, 미확인 확인 후 남은 단위 재개. 같은 대화 안에서도 필요할 수 있음 |
| 사용자가 중단된 설치, 초기화, 갱신을 재개함 | 해당 적용 계획, 사전 조건, 완료/부분 반영, 현재 파일 | [설치 재개 — 「의존성 준비와 설치 재개」](../runtime/install.md)와 [단위 복원 — 「실패 뒤 복구 방식」](../runtime/update.md)의 허용 범위에서 처리. 평소 AI CLI 시작만으로 파일 반영을 재개하지 않음 |

진행 중 작업이 없는 새 세션에 복구용 active를 미리 만들지 않는다. 반대로 진행 중이던 작업의 기록이 사라졌다면 새 작업으로 조용히 초기화하지 않고 사용 가능한 근거로 확인한다. 사용자 취소는 재시작 허가가 아니며, [공유 Git 변경 취소](../../decisions/integration/0017-work-sync.md)도 별도의 요청, 보존 조건을 따른다.

세 흐름은 필요한 저장, 조회 코드를 공유한다. 기능별 기록을 복구용으로 복제하거나 설치 전용/개발 전용 DB 엔진을 각각 만든다는 결정이 아니다. 작업 단위, 시도와 실제 효과를 구별하는 책임은 공통이고, 어떤 기록을 읽고 무엇을 변경할 수 있는지는 각 기능이 소유한다. 설치 뒤 수행하는 WIKI 보강과 검사도 이 실행 기록을 사용할 수 있다.

기존 B도 모든 임의 CLI 명령을 감시하거나 매 요청 전체 상태를 읽는 안은 아니었다. 11/12 보정은 공통 보호 조건과 상황별 실행 경로를 구별한 것이다. 기존 SQLite, 검증/보존 원칙은 유지한다. 정상 경로의 추가 비용과 중단 후 재탐색/재실행 비용은 합쳐 평가하며 실측 전 토큰, 속도 우위를 단정하지 않는다.

이 분기는 필요한 검사의 면제가 아니다. 원래 실패, 미완료 의무, 입력 변경과 재사용 유효성, 부분 반영, 후속 사용자 편집, 필요한 기록의 저장 성공과 실제 효과 대조는 해당 작업에서 계속 확인한다. 복구 흐름을 좁혔다는 이유로 이 검사가 빠지면 설계 또는 연결의 결함으로 수정한다. 매 요청 전부 반복하지 않는 것과 발동 조건을 충족한 검사를 생략하는 것은 구분한다.

복구 상태는 코드 작업 트리의 로컬 영역에 둔다. 공유 WIKI의 정책, 요구, 결정을 active에 복제해 또 다른 원본으로 만들지 않는다.

### B안에서 저장하고 읽을 정보

다음은 논리적인 책임 구분이다. SQLite 저장 원칙은 채택됐고 로컬 검증의 필드, 파일과 active 연결은 [기록 명세](records.md)에 구체화했다. 제품 구현과 실제 저장 시험은 아직이다. 메인은 AI이고, 실행 기록, 검사는 모듈의 일반 코드가 담당하며, hook은 그 절차를 지원 이벤트에 연결한다.

| 자료 | 작성 책임과 내용 | 재개 때의 사용 |
| --- | --- | --- |
| 짧은 진행 상태 | 메인: 목표, 조건, 부모/현재 단위, 합의/미합의, 다음 행동, 필요한 문서/기록 참조 | 현재 active의 역할 유지. 테스트 성공을 이 문장만으로 확정하지 않음 |
| 실행 사실 | 모듈의 실행 경로: 계획/시도, 대상, 시작/종료, 실행/미실행/재사용 근거, 원문 결과 참조 | 기존에 채택한 검사/분석 기록을 사용. 실제 실행과 저장 완료를 확인하며 별도 복구용 로그로 다시 복제하지 않음 |
| 변경, 재개 점검 | 일반 코드의 경로/작업/파일 대조와 메인의 의미 판단 | 코드, 외부 WIKI, 설정, 결과가 현재 작업과 대응하는지 확인. 불명확한 항목만 추가 확인 |

조건부 복구가 필요한 긴 작업은 첫 실행 전에 범위와 돌아갈 지점을 남긴다. 이후 바뀐 의미와 실행 사실의 저장 시점은 아래 [저장 시점](recovery.md#%EC%A0%80%EC%9E%A5%20%EC%8B%9C%EC%A0%90)에 연결한다. 단순 질문까지 active 생성이나 모든 지침 재독을 요구하지 않는다.

기계적 실행 기록은 모듈이 관리하는 실행 경로에서 남긴다. 터미널의 모든 임의 명령, 외부 편집까지 포착했다고 주장하지 않는다. 지원되는 도구 이벤트는 추가 단서로 쓸 수 있지만 같은 실행을 다시 기록하지 않고 시도에 연결한다. 시작 기록과 실제 프로세스 시작 사이, 종료와 결과 저장 사이에도 중단될 수 있으므로 시작 기록만으로 실제 실행을 확정하지 않는다. 현재 프로세스, 결과, 실제 파일을 확인할 수 없으면 미확인으로 두고 중복 실행/자동 성공을 피한다.

hook은 재개 점검을 연결하는 도구별 수단이다. 미지원, 비활성, 권한 실패 환경에서는 정상 자동 복구로 표시하지 않고 명시적 재개 경로를 제공하는 안을 검토한다. quota 경고는 사용할 수 있을 때의 보조 입력이며 없거나 이미 추론이 차단돼도 읽을 수 있는 저장 상태가 먼저 필요하다. Stop에서 요약을 위해 모델을 계속 호출하거나 비율 하나로 무조건 종료하는 정책은 이 추천에 포함하지 않는다.

재개는 **짧은 상태 → 연결된 계획, 미해결 실행 → 바뀐 코드/WIKI와 필요한 근거** 순서로 읽는 방향이다. 전체 대화, WIKI, 로그를 매번 다시 넣지 않고, 요약이 오래됐으면 실제 근거로 정정한다. 저장 호출과 의미 요약에도 토큰/시간이 들며 절감은 미측정이다. 변경 없는 상태를 반복 작성하거나 로그를 보기 위해 명령을 다시 실행하는 비용부터 줄인다.

### 저장 누락과 재개 오인 방지

B의 보강은 저장 지침을 추가하는 데서 끝나지 않는다. **필요한 시점의 기록 → 내용과 근거의 대응 → 저장 성공 → 올바른 작업에서 읽기 → 재개 후 실제 행동**을 연결해야 한다. 파일 존재, 최신 시각, hook 호출, AI의 “읽었다”는 보고 하나로 이 연결을 통과 처리하지 않는다. 검출 가능한 실패와 의미 검토가 필요한 누락을 구별한다.

- 모듈이 관리하는 중요한 실행/반영 경로에서는 필요한 작업, 계획 기록의 존재와 대응, 쓰기 결과를 일반 코드로 확인하는 방향이다. 없거나 저장 실패면 그 기록에 의존하는 새 변경을 그대로 시작하지 않는다. 이미 진행된 효과는 실제 대상과 대조하며, 모든 임의 명령을 감시하는 장치로 설명하지 않는다.
- 사용자 조건, 허용 범위, 다음 행동이 바뀌면 메인이 해당 의미를 갱신한다. 형식, 해시, 시도 연결 검사만으로 사용자 의도의 누락까지 자동 판별할 수 없다. 중요한 실행 전과 재개 때 현재 요청, 남은 의무와 대조하고, 모르는 부분을 새 사실로 채우지 않는다. 모든 턴의 전체 대화를 복제하거나 별도 요약 AI를 항상 호출하는 정책은 추가하지 않는다.
- 재개할 때 작업 트리, 대상 작업, 연결한 WIKI와 기록의 대응부터 확인한다. 새 사용자 지시와 오래된 active가 다르면 과거 승인을 그대로 실행하지 않으며, 입력 변경은 기존 검증 재사용 조건과 연결한다. 단순히 가장 최근 시각의 파일을 고르는 것으로 처리하지 않는다.
- hook 누락, 전달 실패, 잘못된 경로, 실제 미독해를 각각 구분한다. 명시적 재개 경로에서도 같은 대조 절차를 사용하고, 자동 연결이 안 된 상태를 정상 자동 복구라고 표시하지 않는다. 읽기 호출 이후에 목표, 미완료, 원래 실패가 실제 다음 행동에 유지되는지는 모델을 포함한 시험으로 확인한다.

복구 성공과 안전하게 멈춘 결과도 구분한다. 근거가 부족하면 부족한 항목과 마지막 확인 지점을 보존, 보고하는 것이 맞지만 이를 작업을 정상 재개한 성공으로 세지 않는다. 파일 저장, 실행 사실 검사는 일반 코드, 의미의 일치와 행동 검토는 메인이 맡으며 시험에서는 별도로 준비한 기대 결과로 양쪽을 평가한다. 상세 실패 입력, 판정은 [복구 성공 기준](../../verification/acceptance.md)이 소유한다.

### 작업과 실행의 상태

11/11 후속 초안은 **요청한 작업 단위의 진행**과 **그 안에서 수행한 실행 시도의 사실**을 구분한다. 상태 이름은 설명용이며 최종 enum, 필드, 파일을 정한 것이 아니다. 별도 실행 시스템을 만드는 대신 [기존 계획, 시도, 결과 — 「계획과 결과의 연결」](verification.md)에 붙인다.

작업 단위는 미착수 → 진행 → 완료를 기본으로, 해결되지 않은 실패, 충돌, 사용자 판단이 있으면 보류한다. 완료는 그 단위에 필요한 검토, 반영, 검증이 충족됐다는 뜻이다. 검사 실패도 ‘명령의 종료’는 확인할 수 있지만 작업 완료는 아니다. WIKI 후보 생성도 검토, 반영이 남으면 해당 전체 작업의 완료가 아니다. 취소된 범위를 완료로 세거나 삭제하지 않고 이유와 남은 범위를 보존한다.

| 실행 시도의 상태 | 확인한 사실 | 허용되는 다음 판단 |
| --- | --- | --- |
| 준비 | 실행 대상, 현재 계획, 시도가 저장됐음. 실제 실행 시작은 아직 확인하지 못함 | 같은 실행자가 시작 전임을 확인하고 실행. 세션 중단 뒤 발견한 준비 기록만으로 미실행을 단정하지 않음 |
| 실행 중 | 해당 시도가 시작됐거나 실행 중임을 관측했음 | 기존 실행을 조회, 기다리고 중복 시작하지 않음. 과거의 실행 중 기록이 현재 생존의 증거는 아님 |
| 종료 확인 | 해당 시도의 종료와 결과가 대응함 | 성공/실패/중단 결과와 필요한 산출물을 확인. 종료 코드 0만으로 문서 반영, 전체 검증 완료 판정 금지 |
| 미확인 | 실행 여부, 종료, 결과 대응 중 필요한 사실을 확정할 수 없음 | 프로세스, 파일, 지원되는 원격 상태를 대조. 확인 전 재실행, 완료, 자동 취소/복원 금지 |

정상 흐름은 준비 → 실행 중 → 종료 확인이다. 중단 뒤 오래된 준비/실행 중 기록이나 현재 시도와 연결되지 않는 결과는 미확인으로 대조한다. 이미 확인한 시작, 결과 사실을 지우는 뜻은 아니다. 매우 짧은 실행은 중간 관측 없이 종료 결과가 올 수 있으므로, 같은 시도와 종료 결과의 대응이 확실하면 실행 중 표식을 만들려고 다시 실행하지 않는다.

미확인에서 실제 실행을 찾으면 그 시도를 계속 추적한다. 현재 결과를 찾으면 검증 후 종료 확인으로 연결한다. 실행하지 않았다는 충분한 근거가 있는 경우에만 현재 승인 범위에서 새 시도를 준비한다. 프로세스가 안 보임, 로그가 없음, 시간이 오래됨만으로는 미실행을 증명하지 못한다. 새 재시도는 기존 실패/시도를 덮지 않고 같은 의무에 연결한다.

**사용자의 취소 의도와 프로세스 종료도 별개다.** 중단 요청 뒤 새 실행을 시작하지 않되, 남은 프로세스가 사라졌다고 가정하지 않는다. 사용자가 재개를 요청해도 이전 실행이 살아 있으면 중복 실행하지 않는다. 재시도 준비/진행에서는 완료한 독립 단위를 유지하며, 뒤의 실패가 그 근거를 무효화하면 영향을 다시 판단한다. 업데이트에서 명시적으로 [이전 구성 사용 — 「업데이트 실패 후 선택」](../runtime/update.md)을 선택한 경우에는 이번 요청이 반영한 변경 전체의 복원/검증으로 분기한다. 단순 중단이나 EOF를 그 선택으로 해석하지 않는다. 완료 근거가 남았지만 active 갱신만 실패한 경우에도 결과를 없애거나 재실행하지 않고 갱신 미완료를 복구한다.

### 기록 위치와 저장 처리

위치는 이미 채택한 코드 작업 트리의 `.harness/state/`를 사용한다. 하위 파일 후보와 작성/조회 조건은 [파일과 소유](records.md)가 소유한다. 검사/분석 기록이 다른 로컬 하위 경로에 정해지면 그 원본을 참조하고 복제하지 않는다.

```text
코드 프로젝트/
  .gitignore                 /.harness/ 규칙
  .harness/
    state/
      active.md              메인이 읽고 갱신하는 짧은 현재 상태
      state.db               기계 기록의 원본. 별도 수정 가능한 JSON 원본을 두지 않음
      runs/<attempt_id>/...   해당 시도의 필요한 로그와 보고서

WIKI 원본/                   요구사항, ADR 등 공유할 지식
```

active와 실행 기록은 앱/WIKI Git, 배포물에 포함하지 않는다. 제외 규칙의 자동 설정, 추적 여부 확인은 위 [기존 계약 — 「제외 규칙의 자동 설정」](recovery.md#%EC%A0%9C%EC%99%B8%20%EA%B7%9C%EC%B9%99%EC%9D%98%20%EC%9E%90%EB%8F%99%20%EC%84%A4%EC%A0%95)을 따른다. `git add -f`나 이미 추적된 파일까지 `.gitignore` 하나로 막을 수 있다고 약속하지 않는다.

B의 저장 흐름은 **중요한 실행 전 필요한 상태가 저장됐는지 확인 → 실행 → 결과 저장 확인 → active에서 그 근거 참조**다. 실행 기록은 일반 코드가 쓰고, 메인은 의미가 바뀐 부분만 갱신한다. 사용자가 매번 파일을 작성하거나 Git에 올리는 절차가 아니다. 저장 실패 때 다음 변경을 그대로 시작하지 않으며, 도중 저장이 끊기면 직전 유효본과 실제 결과를 대조하는 방향이다.

구체 수단은 임시 파일 작성, 검사 후 교체, 직전 유효본 보존, 동시 작성자 충돌 방지 등을 비교한다. 단일 파일 교체와 여러 파일의 일괄 반영, 프로세스 중단과 전원/디스크 장애의 보장을 구분한다. atomic rename만으로 모든 파일, 외부 시스템의 원자성이나 전원 장애 내구성이 확보됐다고 설명하지 않는다. 전체 원문, 토큰/API 키, 명령의 비밀 인자를 무조건 로그로 복사하지 않는다. 원시 대화도 별도로 통째로 복제하는 구조를 기본으로 두지 않는다.

### 저장 수단과 자료의 소유

11/11 후속 비교와 11/12 채택의 원본은 [ADR 0021](../../decisions/workflow/0021-recovery-storage.md)이다. **기계 기록만 로컬 SQLite에 두는 저장 원칙을 채택했으며 미구현**이다. 아래는 자료별 책임 구분이고 실제 파일/명령을 생성한 결과가 아니다.

| 자료 | 원본과 작성 책임 | 읽고 복구할 때 |
| --- | --- | --- |
| 목표, 사용자 조건, 부모/현재 단위, 다음 행동 | 메인이 작성하는 active Markdown. 모듈의 저장 절차는 쓰기, 기준 변경을 확인 | AI와 사람이 직접 읽음. DB가 의미를 생성하거나 본문을 자동 덮지 않음 |
| 계획, 시도, 실행 사실, 결과 참조, 진행 대조 정보 | 일반 코드가 관리하는 로컬 SQLite. 같은 수정 가능한 기록을 별도 JSON에도 유지하지 않음 | 일반 조회 코드가 현재 작업에 필요한 정보만 반환. AI의 SQL 작성/전체 DB 읽기를 기본으로 요구하지 않음 |
| 원문 로그, 후보, 적용 전 사본 | 실행별 일반 파일. DB는 해당 자료의 위치, 대응 근거를 참조 | 필요한 범위만 조회. 참조 존재, 입력/시도의 대응과 내용 보존 확인 |
| 공유 WIKI, 프로젝트 코드 | 기존에 정한 해당 프로젝트의 원본, Git 정책 | DB/active에 복제하지 않으며 실제 반영과 원격 효과는 별도 대조 |

active와 DB의 내용을 두 개의 완료 판정 원본으로 만들지 않는다. active는 설명과 근거 참조를 담고 실제 검사 결과는 시도 기록에서 확인한다. 실행이 사용한 active/계획의 기준과 현재 본문이 다르면 의미 대조가 필요하며 시각 하나로 최신 상태를 고르지 않는다. active를 전체 DB의 자동 생성 뷰로 바꾸는 안은 아니다.

로컬 DB의 파일명 후보는 `.harness/state/state.db`이며 상세 필드는 [기록 명세](records.md)가 소유한다. WIKI vault, 앱/WIKI Git에 올리거나 팀원 간 실시간 동기화하지 않는다. 각 clone/작업 트리의 실행 상태가 따로 생기고 팀의 지식/PR은 기존 공유 경로를 사용한다. 첫 검증은 로컬 저장을 대상으로 하며 네트워크 공유, 동기화 중인 DB의 동시 접근을 지원 완료로 보지 않는다.

SQLite의 트랜잭션은 **DB 내부 기록만** 함께 저장한다. 모듈이 관리하는 실행은 다음 경계를 사용한다.

1. **실행 전:** 계획, 입력, 시도를 짧은 트랜잭션으로 저장하고 commit을 확인한다.
2. **실제 실행:** DB 쓰기 트랜잭션을 닫은 상태에서 해당 작업의 모델 호출이나 검사, 파일 반영을 수행한다. 긴 실행, 사용자 응답 대기를 DB 잠금 안에 두지 않는다.
3. **결과 확보 뒤:** 결과 파일과 실제 효과를 확인하고, 시도 결과, 참조, 진행 변경을 짧은 트랜잭션으로 연결한다. 의미가 바뀌면 active를 갱신한다.
4. **중단 후:** SQLite의 유효한 기록과 실제 실행/산출물을 대조한다. 결과 파일만 남거나 active만 낡은 경우도 구분한다. 완료 기록 부재를 미실행으로 취급하지 않는다.

작업 단위 전체가 하나의 SQL 트랜잭션인 것은 아니다. DB 저장 중 중단되면 해당 DB 변경 묶음의 일관성을 엔진이 처리하지만, 이미 실행된 검사, 파일, PR이나 저장되지 않은 AI 문맥은 되돌리지 않는다. 설치 파일 복원은 적용 전 사본과 [기존 복원 조건 — 「실패 뒤 복구 방식」](../runtime/update.md), 공유 Git 변경 취소는 그 별도 계약을 따른다.

DB 엔진의 복구와 모듈 작업의 복구는 역할이 다르다. [SQLite의 rollback journal](https://www.sqlite.org/atomiccommit.html)이나 [WAL](https://www.sqlite.org/wal.html)은 DB 트랜잭션의 일관성을 지키는 내부 수단이다. 모듈의 계획, 시도, 완료/미완료, 산출물 대응 이력은 우리가 별도로 기록해야 한다. 엔진 로그를 영구 작업 이력이나 이미 commit한 작업의 되돌리기 기능으로 사용하지 않는다. 11/16의 우선 시험 후보와 대안은 [연결 준비와 내구성](storage.md)이 소유하며 실제 Windows 검증은 남아 있다.

MySQL의 [redo](https://dev.mysql.com/doc/refman/8.4/en/innodb-redo-log.html)와 [undo](https://dev.mysql.com/doc/refman/8.4/en/innodb-undo-logs.html)도 DB 복구/트랜잭션의 맥락이지 우리 파일/PR을 자동 취소하는 기능은 아니다.

기록 연결의 변경은 짧은 트랜잭션으로 처리하되 읽었던 기준과 현재 기준도 대조해야 한다. DB가 쓰기를 순서대로 처리해도 오래된 정보를 읽은 작성자가 뒤늦게 덮어쓰는 의미 충돌까지 자동으로 막지는 않는다. 충돌, 쓰기 불가, 손상은 성공이나 새 빈 DB로 바꾸지 않고 기존 자료를 보존한다.

DB와 active, 산출물, 적용 전 사본은 아래 [복구 자료의 대응](recovery.md#%EB%B3%B5%EA%B5%AC%20%EC%9E%90%EB%A3%8C%EC%9D%98%20%EB%8C%80%EC%9D%91)으로 연결한다. 백업 완성, 복원, 형식 변경은 [백업과 저장 형식 변경](recovery.md#%EB%B0%B1%EC%97%85%EA%B3%BC%20%EC%A0%80%EC%9E%A5%20%ED%98%95%EC%8B%9D%20%EB%B3%80%EA%B2%BD), 보존/삭제의 채택 원칙은 [복구 자료의 보관과 정리](recovery.md#%EB%B3%B5%EA%B5%AC%20%EC%9E%90%EB%A3%8C%EC%9D%98%20%EB%B3%B4%EA%B4%80%EA%B3%BC%20%EC%A0%95%EB%A6%AC)가 소유한다.

### 복구 자료의 대응

11/12에 채택한 SQLite, active, 파일의 책임을 구체화한 **미구현 초안**이다. 11/15에는 [식별과 참조](records.md), [시도와 결과 필드](records.md), [active의 연결 — 「active의 참조와 본문」](records.md)을 작성했다. 아래 표는 자료의 책임, 기록 명세는 구체 필드와 소비를 소유한다. 기록을 읽는 것, 기록이 현재 결과와 맞는 것, 그 결과가 작업의 완료 조건을 만족하는 것을 구별한다.

| 연결할 대상 | 보존할 대응 근거 | 재개 때 확인할 것 |
| --- | --- | --- |
| 프로젝트, 작업, 계획 | 코드/WIKI의 등록 대상, 선택 범위, 의무, 계획 기준 | 같은 저장소 URL이나 최근 시각만으로 같은 작업으로 취급하지 않음. 다른 clone, 작업 트리, WIKI 연결과 구분 |
| 실행 시도, 입력 | 어떤 계획의 시도인지, 필요한 코드/설정/도구 조건, 시작, 종료와 미확인 사실 | 재시도는 새 시도로 연결해 원래 실패 보존. 전체 장비를 무조건 해시하지 않고 해당 실행의 입력과 의존을 대조 |
| 결과, 후보, 적용 전 사본 | 같은 시도/적용 단위의 자료인지, 역할, 위치, 내용 확인 근거 | 파일이 실제로 있고 내용이 맞는지 확인. 원본 경로가 옮겨졌다는 이유만으로 다른 파일을 연결하지 않음 |
| active | 메인이 확인한 계획/진행 기준과 다음 행동 | DB 기록이 더 진행됐으면 실제 근거를 읽어 의미를 갱신. 오래된 active의 완료 문구로 DB/실제 결과를 덮지 않음 |
| 실제 반영, 원격 효과 | 적용 전 상태, 예정 결과, 확인한 반영 사실, 원격 대상/작업 대응 | DB를 복구해도 현재 파일과 PR은 그대로일 수 있음. 기존 효과를 조회하고 중복 실행/자동 취소하지 않음 |

내용 해시는 파일 대응을 확인할 수 있지만 요구사항 충족, AI 의미 정확성, 안전한 재실행을 증명하지 않는다. 종료 코드와 파일 존재도 같은 한계가 있다. 필요한 입력을 특정할 수 없으면 재사용을 보류하고 [검증 재사용 기준](../../decisions/workflow/0002-pass-validity.md)을 따른다.

결과 파일은 시도별로 구별하고 확정한 원문을 재시도로 덮지 않는 방향이다. 기록할 수 있는 결과와 내용 확인을 마친 뒤 DB에서 참조한다. 파일 저장 후 DB 기록 전에 끊겼다면 그 파일은 대응 확인 전까지 미확인 자료로 남기며 즉시 삭제하거나 성공으로 채택하지 않는다. DB에 참조가 있어도 파일이 없거나 다르면 그 근거에 의존하는 완료/재사용을 보류한다. active가 뒤처졌을 때는 확인된 결과를 다시 실행하는 대신 필요한 의미만 갱신한다.

복구용 사본은 이미 허용한 작업 범위에서 확보한다. 입력 프로젝트 전체, 개인 대화, 비밀값을 수집하는 새 허가로 확대하지 않는다. 경로 재등록 시에도 같은 대상인지와 접근 권한을 확인하며, 모르는 경로를 새 빈 WIKI/상태로 자동 대체하지 않는다.

### 백업과 저장 형식 변경

백업은 **작업 재개용 기록의 사본**과 **파일 적용 직전의 복원 사본**을 구분한다. 전자는 아래 절차로 기록을 복구할 후보를 만들고, 후자는 기존 [실패 뒤 복구 방식](../runtime/update.md)의 조건에서만 실제 파일을 되돌린다. 전체 코드/WIKI의 재해 복구나 모든 과거 시점으로의 복원을 제공하는 안은 아니다.

[SQLite Backup API](https://www.sqlite.org/backup.html)와 [Python backup](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.Connection.backup)은 일관된 DB 사본을 만드는 수단이다. 외부 파일의 같은 시점 사본까지 만들지는 않으며, SQLite는 [실행 중 파일을 임의 복사/교체하거나 journal을 잘못 대응시키는 경우](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)의 손상 위험을 설명한다. 따라서 DB 파일 하나를 복사한 뒤 백업 완료로 표시하는 방식을 쓰지 않는다.

권장 처리 초안은 다음과 같다. [파일별 명세 — 「파일 구성과 보장 범위」](maintenance.md)에 백업 묶음, 완성 목록과 후보 전환을 연결했다. 정확한 저장 필드와 Windows 전환 수단은 후속 검증 대상이다.

1. **범위와 경계 확인:** 백업 대상 작업과 그 복구에 필요한 기록, active, 참조 자료를 정한다. 새 반영/기록을 잠시 멈출 수 있는 경계에서 같은 기준을 확보한다. 긴 AI 실행 중 쓰이는 로그를 완성된 결과처럼 복사하지 않는다.
2. **사본 준비:** 기존 유효 백업을 유지한 채 별도 후보에 DB 사본과 필요한 파일을 담는다. 대상, 계획 기준, 자료 목록/내용 대응, 미해결 실행을 함께 확인할 정보를 남긴다. 이 정보는 백업의 설명이며 두 번째 수정 가능한 실행 원본이 아니다.
3. **복구 가능 범위 확인:** DB를 읽을 수 있는지, 선택한 작업의 필수 참조가 사본 안에서 실제로 대응하는지 확인한다. 변하는 active, 입력은 복사 전후 기준을 대조하며 변했다면 후보를 완료로 표시하지 않는다. DB에 과거 기록이 있어도 그 산출물을 제외했다면 해당 과거 작업의 복구까지 보장하지 않는다.
4. **완성 처리:** 파일 저장, 참조 검사가 끝난 사본만 사용 가능한 백업으로 표시한다. 중간 종료, 디스크 부족, 접근 거부로 남은 후보는 미완성으로 구분하고 직전 유효본을 덮지 않는다. 표시 자체의 저장 실패도 성공으로 숨기지 않는다.
5. **복원 후 대조:** 필요한 경우 보존한 사본에서 별도 복구 후보를 만든다. 현재/손상 기록과 더 최신일 수 있는 자료를 보존하고 실제 파일, 실행, 원격 효과를 대조한 뒤 전환한다. 과거 기록 복구가 당시 이후의 성공을 미실행으로 바꿔 중복 적용하게 해서는 안 된다.

DB 구조의 정상 여부만으로 이 대응 검사를 대신하지 않는다. 임의 외부 편집자는 하네스의 잠금을 따르지 않을 수 있으므로 필수 복구 자료의 일관된 기준을 확보하지 못하면 그 자료에 의존하는 새 변경을 보류한다. 범위를 줄여도 되는지는 사용자와 확인하며 복구 조건을 조용히 완화하지 않는다. 동일 장치의 `.harness/` 사본은 장치 전체 고장, 폴더 전체 유실까지 보호하지 않는다. 외부 장치/클라우드 백업을 자동 추가하거나 원문을 업로드하는 결정도 아니다.

저장 형식이 바뀌는 업데이트에는 **지원 여부 확인 → 검증된 사본 확보 → 별도 후보 변환/검증 → 새 작성과 DB 연결이 정리된 상태에서 전환 → 재개 대조**를 권장한다. 현재 형식은 그대로 사용하고, 지원하는 이전 형식만 정해진 일반 코드로 변환한다. 새 형식, 알 수 없는 형식, 손상은 빈 DB 초기화나 추정 변환으로 처리하지 않는다. 변환 중 중단되면 어느 사본이 유효하고 전환이 어디까지 됐는지 확인할 때까지 쓰기를 보류한다.

형식 식별은 공식 모듈 버전과 별개로 호환 여부를 판단하는 내부 정보다. [기록 명세 — 「저장과 조회 순서」](records.md)의 메타데이터 `schema_version` 한 곳을 사용하며 내부 PRAGMA와 혼동하거나 같은 값을 중복 저장하지 않는다. [DB 형식과 이전 구성의 호환](storage.md)에서 옛 실행의 읽기/쓰기, 실패/복원 이력 보존을 반영 전 조건으로 연결한다. 파일/필드명에 수정 차수의 버전 접미어를 붙이는 정책이 아니다. DB를 정상 조회한 사실만으로 모든 새 프로그램 동작이 호환된다고 판단하지 않는다.

변환 검증에는 계획, 시도, 원래 실패, 미해결 의무와 산출물 참조 보존을 포함한다. 이전 사본으로 되돌리는 경우에도 변환 후 발생한 기록/파일 변경이 있으면 자동 덮어쓰지 않는다. 구버전 모듈의 재설치를 새 형식의 자동 역변환으로 취급하지 않으며 지원 경로, 자료가 없으면 보존한 채 안내한다.

### 복구 자료의 보관과 정리

11/12 사용자 선택으로 **첫 배포는 자동 보존 + 명시적 정리 명령**을 채택했다. 11/16에는 **최초 설치 완료 뒤 정리 가능한 자료를 순서대로 제시하고 사용자의 확인을 받아 정리하는 흐름**을 추가로 채택했다. 별도 정리 명령은 나중에 다시 실행할 수 있도록 유지한다. 복원에 필요한 자료는 자동 보존하며 사용자 응답 없는 자동 삭제로 바꾸지 않는다. 정확한 명령, 구현/시험은 후속이다. 정상 DB 기록, 시도별 산출물 보존과 백업 복사는 구별하며 모든 도구 호출마다 전체 사본을 추가하는 안은 추천하지 않는다. 파일 적용 직전과 저장 형식 변경 같은 복구 경계에서 필요한 자료를 확보하고, 상태의 직전 유효본과 대응 자료를 유지하는 방향이다.

| 방식 | 이점 | 비용, 제한 |
| --- | --- | --- |
| 자동 보존 + 확인 후 정리 — 채택 | 최초 설치 완료 뒤 확인 절차 또는 후속 정리 명령을 사용. 도구가 가능한 범위와 영향을 제시하고 사용자 응답 뒤 처리 | 보관을 선택한 자료는 남으며 필요할 때 정리 명령 실행 |
| 자동 보존 + 조건을 정한 자동 정리 — 후속 검토 | 반복 사용에서 별도 조작과 누적 용량을 줄임 | 기간/용량, 최소 보존본, 참조 관계, 중단된 정리까지 검증해야 함. 일반 사용자의 복구 기간을 임의로 정할 수 없어 추가 합의 필요 |

어느 안이든 진행/미확인/미해결 작업이 필요로 하는 자료와 그 복구에 필요한 유효본을 정리 대상으로 삼지 않는다. 작업이 완료됐다는 표식 하나로 판정하지 않으며, 다른 현재 작업이나 보존할 백업의 복구에 필요한 자료, 소유/용도를 확인할 수 없는 자료도 보호한다. 독립 사본을 갖춘 백업의 역사적 ID 참조와 현재 파일에 대한 의존은 [정리 뒤 조회 — 「정리 뒤 조회와 복구」](maintenance.md)에서 구별한다. 정리 후보의 범위, 예상 용량, 더 이상 가능한 복구가 무엇인지 알리고, 삭제 직전 관계가 바뀌었다면 진행하지 않는다. 사용자 원문 WIKI, 코드, 설치 파일은 이 정리 대상이 아니다.

파일별 후보와 기존 SQL 삭제 보호의 경계는 [정리 대상과 남길 기록](maintenance.md)이 소유한다. 11/17 사용자 선택으로 완료됐고 현재 필요 없는 큰 로그, 후보와 복원 사본까지 확인 후 정리하되 DB 이력과 정리 사실은 보존한다. [정리 필드/소비자 — 「정리 허용과 실제 제거」](maintenance.md)를 DDL에 반영하고 메모리 관계 검사를 마쳤다. 실제 파일 정리와 현재 의존의 자동 등록/해제는 구현 전이다. 보호 트리거를 해제하거나 정리한 근거를 새 완료에 재사용하지 않는다.

최초 설치의 확인 화면과 후속 정리 명령은 같은 대상 판별, 참조 대조와 삭제 절차를 사용한다. 같은 자료를 두 구현에서 서로 다르게 판정하지 않는다. 확인은 표시한 자료 묶음에 한정하고 이전 설치나 미래 정리 전체의 삭제 동의로 저장하지 않는다. 이미 처리한 같은 묶음에 불필요한 확인을 반복하지 않으며 범위나 영향이 달라지면 다시 보여준다.

날짜/용량을 이유로 조용히 삭제하지 않는다. 공간이 부족하면 복구 자료를 버려서 실행을 강행하지 않고 필요한 조치를 알린다. 자료 크기, 정상 백업 비용, 정리 빈도는 미측정이며 추후 자동 정리를 추가해도 같은 보호 조건을 유지해야 한다. 설치 완료의 판정과 사용자에게 보여줄 순서는 [설치 완료 뒤 정리](../runtime/install.md)가 소유한다.

### DB의 수명과 누적 용량

11/15 후속 질문에 대한 저장 수명 보강이다. **같은 로컬 작업 사본에서는 설치 뒤 검증, 기능 추가와 업데이트에도 같은 `state.db`를 사용**하는 설계다. 작업/시도를 구분해 저장하며 새 세션이나 공식 업데이트마다 DB를 초기화하지 않는다. 형식이 바뀌면 위의 지원 여부/보존/변환 절차를 따른다. 다른 팀원, 새 clone이나 작업 트리의 로컬 DB까지 합치는 방식은 아니다. 최초 제외 준비 전의 기록 위치와 인계는 [설치 단계 — 「설치 기록과 단계 연결」](../runtime/install.md)에 연결했다. 11/17 [최초 인계 B — 「최초 기록 인계의 저장」](storage.md)를 채택해 논리 DB 식별과 이력을 보존하는 단계/DDL을 연결했고 메모리 사례를 확인했다. 실제 파일과 Windows 인계는 검증 전이다.

짧은 DB 트랜잭션을 실행 경계마다 commit한다는 것은 SQL 트랜잭션을 하나 열어 프로젝트 개발 기간 내내 유지한다는 뜻이 아니다. 계속 누적되는 것은 우리가 보존하는 계획, 시도와 결과 데이터다. SQLite의 내부 journal은 그 이력의 원본이 아니며 매 commit마다 전체 DB 사본을 하나 더 보관하는 구조도 아니다.

| 자료 | 누적과 관리 기준 |
| --- | --- |
| 계획, 시도, 결과, 경로/해시 참조 | DB 안에 저장. 현재 작업/의무와 관련된 범위만 조회하며 실제 조건에 맞는 인덱스는 SQL 명세에서 정함 |
| 긴 로그, 후보와 적용 전 사본 | 시도별 일반 파일. DB에는 참조를 두고 원문을 중복 저장하지 않음. DB 밖이라고 용량 문제에서 제외하지 않음 |
| journal과 선택한 저장 모드의 보조 파일 | SQLite의 복구/쓰기 자료. 실제 사용 모드/버전에 맞춰 관리하며 사용자가 임의로 삭제하지 않음 |
| 완료 자료와 백업 | 위의 명시적 정리 정책 적용. 미해결 의무나 다른 보존 자료가 참조하면 보호하고 날짜만으로 자동 삭제하지 않음 |

[SQLite의 적용 안내](https://www.sqlite.org/whentouse.html)는 기기 로컬 앱 저장과 낮은 쓰기 동시성에 적합하다고 설명한다. 현재의 각자 로컬 기록에서는 하나의 DB로 시작하는 것이 타당하다는 판단을 유지한다. 다만 이론적 최대 파일 크기를 우리 제품의 성능 근거로 쓰지 않는다. 긴 쓰기, 전체 이력 스캔, 대량 출력/사본, 디스크 여유 부족은 별도로 확인해야 하며 아직 제품 용량/속도를 실측하지 않았다.

규모를 설명하는 산술 예시로, 시도 하나에 속한 DB 자료가 평균 5 KiB라면 1만 시도의 원자료는 약 48.8 MiB다. **이 평균은 가정이며 실제 예상치나 합격선이 아니다.** 인덱스, 페이지 여유, 보조 파일과 DB 밖 로그/복원 사본은 별도로 더해진다. 파일 수가 많은 설치 시도와 작은 검사 시도의 크기도 같다고 가정하지 않는다.

조회가 느려지는지는 파일 개수보다 조회 범위와 인덱스, 결과량에 영향을 받는다. [공식 조회 계획 설명](https://www.sqlite.org/queryplanner.html)은 전체 스캔과 인덱스 탐색의 차이를 설명한다. 따라서 같은 작업의 미해결/미완료 조회를 기준으로 누적 기록을 늘려 시간, 실제 조회 계획과 반환 크기를 확인한다. 데이터가 커진다는 이유만으로 AI에 보내는 이력도 늘리지 않는다.

WAL을 선택한다면 [checkpoint와 긴 읽기](https://www.sqlite.org/wal.html#ckpt)를 다뤄 보조 파일의 과도한 성장을 확인해야 한다. 현재 첫 후보는 [DELETE + EXTRA — 「연결 준비와 내구성」](storage.md)이며 WAL은 비교 대안이다. 최종 지원과 실제 설정의 검증은 남아 있다. DB 내부 데이터를 정리해도 파일이 즉시 작아지는 것은 아니며, [VACUUM](https://www.sqlite.org/lang_vacuum.html) 같은 공간 회수에는 추가 공간과 실행 시간이 필요하다. 매 작업 뒤 자동 실행하는 정책을 이번 질문으로 추가하지 않는다.

첫 구현에서는 DB, 보조 파일, 로그/후보/복원 사본, 백업의 용량을 구분해 확인하고 누적 상태의 조회/저장/정리/재개를 시험한다. 필요한 정리를 사용자에게 안내할 수 있어야 하지만 경고 기준과 자동 실행 수단은 후속 명세다. 실제 조회 조정과 안전한 정리로도 지원 환경의 부담을 해결하지 못할 때 기록 분리나 저장 방식 변경을 재검토한다. DB 파일을 날짜나 기능별로 미리 쪼개면 작업 간 참조, 백업과 재개 비용이 늘므로 근거 없이 선행 도입하지 않는다.

### 배포 사용자의 준비와 조회

11/12 채택한 **SQLite 저장 원칙의 사용 설계**다. 구현, 사용성 검증은 아직이다. 일반 사용자는 상태 확인, 재개, 내보내기를 모듈 명령으로 수행하고 SQL이나 DB 서버를 관리하지 않는다. 내부 저장은 일반 코드가 처리하되 미완료, 필요한 준비, 사용자 판단 지점은 숨기지 않는다. 이 경계를 위해 불필요한 래퍼나 별도 서버를 추가하지 않으며 명령 이름, 출력 필드는 후속 명세다.

| 항목 | 채택한 구성에서 사용자에게 필요한 것 | 모듈이 확인, 처리할 것 |
| --- | --- | --- |
| 실행 준비 | 기존 Git 릴리스 + Python 방식의 지원 Python | sqlite3 모듈과 실제 SQLite 버전 확인. 부재 시 안내, 중단, 재실행은 [설치 재개 — 「의존성 준비와 설치 재개」](../runtime/install.md)를 따르며 자동 설치, 빈 저장소 전환으로 숨기지 않음 |
| DB 실행 | 로컬 파일/디렉토리에 접근할 OS, 실행기 권한 | Python 프로세스가 DB 파일을 직접 열고 닫음. 별도 서버, 포트, DB 계정, 상주 데몬 불필요 |
| 보통의 조회 | 모듈의 상태 확인, 재개 명령 | 현재 작업, 남은 의무, 최근 시도, 근거 위치를 선별해 텍스트로 제공. 전체 DB를 AI에 매번 전달하지 않음 |
| 상세 조사 | 필요할 때 텍스트/JSON 내보내기. 전용 GUI는 선택 사항 | 읽기 전용 조회, 내보내기와 오류 안내 제공. 내보낸 사본을 두 번째 수정 원본으로 쓰지 않음 |
| MCP, 네트워크 | 로컬 저장/조회 자체에는 불필요 | 설치 다운로드, AI 호출, GitHub PR 요청과 별개. DB 연결을 위해 MCP나 클라우드 서비스를 추가하지 않음 |
| 토큰, 성능 | 저장용 AI 요청은 필요 없음 | 일반 코드의 저장/조회는 추론하지 않음. AI가 받는 호출/결과, 필요한 의미 갱신에는 토큰이 들며 출력 범위, 도구 왕복, 재작업을 합쳐 측정 |

[Python sqlite3](https://docs.python.org/3.13/library/sqlite3.html)는 표준 라이브러리의 인터페이스이고 [SQLite는 같은 프로세스에서 로컬 파일에 접근](https://www.sqlite.org/serverless.html)한다. Python 표준 라이브러리를 포함한 [Windows 공식 설치](https://docs.python.org/3.13/using/windows.html#the-full-installer)를 지원 후보로 삼을 수 있지만, 모든 Python 빌드, 축소 설치에 구성 요소가 있다고 가정하지 않는다. 우리 모듈의 Python 최소 버전이나 저수준 SQLite 기능 요건을 이번 설명만으로 확정하지 않는다. 정확한 지원 조합과 준비 안내는 설치 명세에서 정한다.

DB 내용은 일반 Markdown 편집기에서 바로 읽는 자료가 아니다. 모듈 조회가 고장 났을 때도 원본을 보존하고 내보낼 절차가 필요하다. Python 3.12 이상에는 [간단한 SQLite CLI](https://docs.python.org/3.13/library/sqlite3.html#command-line-interface)도 있지만 일반 사용자에게 SQL 수작업을 정상 복구 절차로 요구하지 않는다. 이 기능의 버전을 제품 최소 Python 버전으로 자동 채택하지 않는다.

최신 상태 하나만 필요하다면 JSON 한 파일의 검사, 교체가 더 간단할 수 있다. 현재는 계획, 여러 시도, 결과 참조, 미해결 의무의 대응이 필요해 DB를 추천하는 것이며 파일 방식이 불가능해서가 아니다. AI의 조건 누락, 틀린 판단, 저장 절차를 거치지 않은 외부 행동을 SQLite가 발견해 주지는 않는다.

운영 비용도 남는다. 바이너리 형식의 조회 도구, 형식 변경과 이전 실패 처리, 백업/보존 기간, 잠금 경합, 용량/권한 오류, Python에 포함된 SQLite의 갱신을 모듈이 다뤄야 한다. 저장 장치 쓰기, 동기화 비용은 있으며 더 빠르거나 토큰이 줄었다는 수치는 아직 없다. 작은 상태를 한꺼번에 읽는 JSON과 비교해 무조건 비용이 낮다고 설명하지 않는다.

DB는 각 작업 트리의 로컬 상태로 유지한다. [SQLite의 동시 작성, 원격 저장 제약](https://www.sqlite.org/whentouse.html)에 따라 공유 폴더나 팀 동기화로 DB를 공동 수정하는 방식은 첫 지원으로 삼지 않는다. 로컬 폴더라도 OneDrive 등에서 파일을 동기화하는 경우는 별도 조건이며 `.gitignore`는 그런 동기화를 막지 못한다. 실행 중에는 [journal 등의 보조 파일](https://www.sqlite.org/tempfiles.html)이 생길 수 있어 파일 하나만 복사/삭제하는 절차로 운영하지 않는다. 백업과 실제 파일 대응은 위 저장 소유 절을 따른다.

DB 형식 자체가 비밀 보호 장치는 아니다. 기존 비기록 기준과 OS 파일 권한, 실행기의 허용 경로를 유지한다. 로컬 저장이라는 이유로 파일 접근 승인이나 기업 정책을 우회하지 않으며, MCP를 쓰지 않는다는 사실을 모든 도구 실행의 무승인 보장으로 해석하지 않는다.

### 작성 범위와 동시 작업

팀원은 **각자의 로컬 작업 사본을 편집하고 Git으로 공유, 통합**한다. 프로젝트 안의 WIKI도 프로젝트 밖의 별도 WIKI 저장소도 같은 원칙이다. 다른 사람의 독립 작업을 기다리게 하거나 팀 전체를 한 작성자로 직렬화하지 않는다. 현재 설계에 별도 공통 조정 폴더, 실시간 동기화 서비스를 추가하지 않는다. 잘못 확대했던 위치 비교의 철회 이유는 [ADR 0021](../../decisions/workflow/0021-recovery-storage.md)에 보존한다.

11/13 설명 보강: 여기서 동시성의 주체는 **같은 로컬 작업이나 파일에 접근하는 실행과 편집기**다. 여러 팀원이 하나의 active나 SQLite 파일을 공유한다는 뜻이 아니다. 한 사람도 같은 작업을 두 번 실행하거나, 이전 실행이 남은 상태에서 재개하거나, AI 분석 중 편집기로 원문을 바꿀 수 있다. 아래는 방어해야 할 가능성을 설명한 예시이며 실제로 발생했다고 관측한 결과는 아니다.

| 같은 PC에서 가능한 상황 | 겹치는 대상과 필요한 확인 |
| --- | --- |
| 두 터미널에서 같은 작업의 재개 명령 실행 | 같은 진행 기록과 반영 대상. 기존 실행이 있는지 확인하고 같은 작업을 중복 시작하거나 반영하지 않음 |
| 연결이 끊긴 뒤 재개했지만 이전 실행이 아직 동작하거나 결과가 늦게 도착 | 해당 실행 시도의 기록과 결과. 새 진행을 과거 결과로 덮지 않고 시도와 입력을 대조. 연결 단절이 모든 자식 프로세스의 종료를 뜻한다고 가정하지 않음 |
| AI가 읽어 둔 WIKI를 사용자가 Obsidian이나 IDE에서 수정 | DB가 아니라 WIKI 원문. 후보의 기준과 현재 파일을 대조하고 사용자 수정을 보존. 편집기가 모듈의 잠금에 협조한다고 가정하지 않음 |
| 다른 팀원이 자기 clone에서 작업 | 서로 다른 로컬 상태와 파일이므로 이 잠금의 대상이 아님. 팀 변경은 기존 Git 통합과 검토로 처리 |

**DB 잠금과 작업의 중복 실행 방지는 다른 책임이다.** [SQLite의 연결 간 격리](https://www.sqlite.org/isolation.html)에 따르면 같은 DB를 여러 연결이 열 수 있지만 쓰기는 한 번에 하나씩 처리한다. 이 엔진 처리는 DB 밖의 active나 WIKI를 보호하거나, 두 실행이 같은 작업을 수행하는지 판단해 주지는 않는다. DB 저장은 짧은 트랜잭션으로 처리하고, 작업 재개와 파일 반영에서는 기존 실행 및 현재 입력을 별도로 대조한다. 일반 저장과 조회는 코드가 수행하며, AI에 판단할 내용이 필요할 때만 관련 정보를 전달한다.

기본 진행은 메인 하나의 순차 실행과 단일 반영 경로를 유지한다. 동시성을 설명하기 위해 hook과 메인이 active를 동시에 쓰거나 여러 작성자를 상시 실행하는 구성을 추가하지 않는다. 문서의 ‘소유자’는 이 로컬 작업을 계속 실행하거나 반영할 주체를 뜻한다. Windows의 구체 후보는 아래 [실행 소유의 식별과 반환](recovery.md#%EC%8B%A4%ED%96%89%20%EC%86%8C%EC%9C%A0%EC%9D%98%20%EC%8B%9D%EB%B3%84%EA%B3%BC%20%EB%B0%98%ED%99%98)에 두며 팀 전체나 프로젝트의 무관한 작업을 묶는 잠금으로 확대하지 않는다.

#### WIKI의 로컬 편집과 Git 공유

프로젝트 내부 WIKI는 코드와 같은 로컬 작업 사본에서, 별도 WIKI는 각 사용자가 받은 로컬 WIKI 작업 사본에서 읽고 수정한다. 공유, 검토는 기존 [앱과 WIKI의 작업별 버전 연결](../../decisions/integration/0017-work-sync.md)을 따른다. 같은 원격 저장소를 쓴다는 사실을 같은 물리적 폴더를 함께 편집한다는 뜻으로 해석하지 않는다.

| 상황 | 처리 범위 |
| --- | --- |
| 팀원이 독립된 기능/문서를 변경 | 각자 작업, 검사, commit/push, PR 진행. 다른 팀원의 로컬 실행 기록/작성 상태를 기다리거나 공유할 필요 없음 |
| 변경이 같은 부분이나 공통 요구/계약에 영향 | Git 통합 과정의 충돌 해결과 관련 문서의 정합성 검토. 영향이 없는 문서까지 일괄 재검토하지 않음 |
| 자기 작업 중 입력 변경, 중단, 늦은 결과 발생 | 해당 로컬 작업의 기록, 실제 파일, 후보 기준을 대조. 기존 복구/원문 보존 계약 적용 |

[git pull](https://git-scm.com/docs/git-pull)은 원격 이력을 로컬 브랜치에 통합한다. [Git merge](https://git-scm.com/docs/git-merge#_pre_merge_checks)의 충돌/미커밋 변경 보호와 문서 의미 검토는 구분한다. 분석 뒤 pull/병합으로 입력이 바뀌면 영향받는 후보, 검증 근거만 다시 확인한다. 이 설명으로 자동 pull, stash, commit, push를 허가하거나 새 팀 동기화 정책을 추가하지 않는다.

#### 소유 확인과 인계

아래는 **한 로컬 작업의 중단 후 재개와 파일 반영을 위한 초안**이며 팀원 간 작성권을 배분하는 절차가 아니다. 로컬 active, SQLite, 실행 자료의 위치와 Git 제외는 앞서 채택한 계약을 유지한다. 정확한 잠금 API, 저장/교체 수단은 명세와 실제 Windows 시험에서 정한다.

1. **대상, 기준 확인:** 허용된 코드/WIKI 로컬 경로와 후보의 입력 기준을 확인한다. 분석 결과는 후보로 보존하고 원문 반영은 기존 단일 반영 경로가 담당한다.
2. **현재 실행 대조:** 같은 로컬 작업의 이전 실행, 미완료 반영, 실제 파일을 확인한다. 살아 있는 실행을 중복 시작하거나 이전 결과를 최신 상태로 덮지 않는다. PID, 시각, 잠금 해제만으로 완료를 판정하지 않는다.
3. **기록 후 반영:** 필요한 적용 전 자료, 실행 시도가 저장됐음을 확인하고 승인된 변경 단위를 반영한다. DB 저장과 외부 파일 쓰기를 하나의 트랜잭션으로 간주하지 않는다. 긴 AI 실행이나 사용자 응답 대기 동안 DB 쓰기 트랜잭션을 유지하지 않는다.
4. **결과 확인과 재개:** 실제 결과, 기록의 대응을 확인하고 다음 단위로 진행한다. 중단되면 미완료 범위와 현재 효과를 대조하며 중복 적용하지 않는다. 실패 후 보고, 조건부 복원, 사용자 합의는 [기존 복구 계약 — 「실패 뒤 복구 방식」](../runtime/update.md)을 따른다.

같은 로컬 상태에 대한 기록 경합은 짧은 SQLite 트랜잭션과 읽었던 기준의 대조로 처리하는 후보이며, active, 실제 파일의 쓰기 보호는 별도로 검증한다. [Windows 잠금 해제](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)는 해당 실행의 완료를 증명하지 않는다. 늦은 결과나 오래된 백업으로 현재 소유/완료를 덮지 않으며 임의 프로세스 종료, 잠금 제거로 해결하지 않는다.

최초 설치의 저장 위치를 넘길 때는 [인계 단계와 쓰기 허용](storage.md)을 같은 진입에서 확인한다. 복사된 두 DB의 논리 ID가 같아도 일반 쓰기는 활성화된 대상에만 허용한다. 초기 원본의 준비/인계 확인 상태를 일상 작업의 쓰기 허가로 해석하지 않으며, 활성화 뒤에는 남은 초기 사본 없이 후속 작업을 진행할 수 있어야 한다. 실제 위치와 실행 소유의 검증은 메모리의 주입된 위치 값 검사와 구별한다.

#### Windows 반영 보호

11/16 후속 명세는 보호할 대상을 아래처럼 구분한다. 첫 구현 후보는 **공통 반영 진입점에서 같은 로컬 실행을 조정하고, Windows 파일 처리에서 실제 접근/교체 조건을 확인하는 조합**이다. DB의 작성 잠금 하나로 설치 파일과 WIKI까지 보호하거나, 시간만 보고 이전 실행을 만료시키는 방식은 사용하지 않는다. 구체 API 조합과 잠금 식별/배치는 아직 구현 전이다.

| 보호 대상 | 적용 구간과 반환 조건 |
| --- | --- |
| 같은 작업 사본의 설치, 갱신, 인계와 정리 | 실제 쓰기 직전에 현재 실행/시도와 입력 기준을 대조해 하나의 반영만 허용. 확인 응답이나 긴 AI 분석을 기다리는 동안 DB 쓰기 트랜잭션을 유지하지 않고, 다시 반영할 때 소유/기준 재확인 |
| DB와 active | 짧은 DB 트랜잭션과 읽었던 기준의 대조, active 파일의 저장 보호를 구분. 오래된 실행 결과는 근거로 보존할 수 있어도 현재 진행/본문을 덮지 않음 |
| 설치된 hook, script와 공통 설정 | 변경 묶음의 기존 실행이 필요한 파일을 사용 중인지 확인. 반영 중 새 호출이 부분 설치를 읽지 않도록 진입을 조정하고, 안전한 정지 경계를 확인할 수 없으면 후보를 보존해 해당 반영 보류 |
| 사용자 코드, WIKI와 `.gitignore` | 편집기와 Git이 모듈의 조정 규칙을 따른다고 가정하지 않음. 실제 파일 접근, 입력 변경과 교체 결과를 별도 확인하며 원문 보존 조건을 만족하지 못하면 자동 반영하지 않음 |

Windows의 [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)는 프로세스 종료나 핸들 닫기 뒤 잠금이 풀릴 수 있으며 메모리 매핑 접근까지 막지는 않는다. 따라서 잠금 획득은 이전 작업 성공, 자식 실행 종료나 외부 편집 중단의 증명이 아니다. 바쁜 실행이나 불명확한 소유를 만나면 상황과 재개 조건을 반환하고 임의 프로세스 종료나 잠금 파일 삭제로 우회하지 않는다.

파일 열기와 교체의 제약, 일부 반영 뒤 실제 상태 대조는 [파일 반영과 핸들 수명](../runtime/update.md)이 소유한다. 11/16에는 같은 배타적 핸들로 확인/쓰기하는 후보를 임시 파일 교체와 비교하고, 기존 파일/신규 파일/삭제/이름 변경을 구분했다. 중단 시 부분 내용과 접근 제한의 비용이 있어 최종 채택 전 실제 Windows 검증이 필요하다. 접근 권한이나 속성 보존 오류를 무시해 성공을 만들지 않는다.

아래 실행 조정과 파일 보호, [실행 중인 구성의 갱신](../runtime/update.md)은 서로 다른 책임이다. 여러 파일의 반영과 단위 검증, 호스트 활성화가 끝나기 전 새 구성의 정상 사용을 허용하지 않는다. 구체 호출과 지원 도구의 재시작 조건은 구현 시험으로 확인하며, 추가 설치 서버나 팀원 간 공용 잠금으로 확대하지 않는다.

#### 실행 소유의 식별과 반환

11/16의 첫 구현 후보는 **Windows 이름 있는 뮤텍스(named mutex)로 같은 코드 작업 사본의 짧은 반영 구간을 조정하고, 기존 작업/시도 기록으로 중복 실행과 늦은 결과를 구별**하는 조합이다. 뮤텍스는 같은 이름을 사용하는 실행 중 하나만 해당 구간에 들어가게 하는 운영체제 객체다. 완료 기록이나 파일 백업을 저장하는 곳이 아니며 별도 서버를 설치하지 않는다. 이 절은 설계 후보이고 실제 Windows 통과 결과나 API의 최종 채택은 아니다.

| 비교할 수단 | 현재 판단 |
| --- | --- |
| 이름 있는 뮤텍스 | 프로젝트에 제외 영역이 생기기 전부터 같은 이름을 사용 가능. 마지막 핸들이 닫히면 객체가 사라져 잠금 파일 정리와 분리됨. Windows API 연결과 이름 공간/접근권 검증이 필요하며 우선 후보 |
| 전용 파일을 열어 `LockFileEx` 사용 | 파일 기반으로 실행을 조정할 수 있음. 최초 제외 준비 전후에 일관된 위치를 확보하고 잠금 중 삭제/교체를 금지해야 함. 사용자별 외부 경로만 쓰면 다른 경로/계정의 같은 대상을 놓칠 수 있어 대안으로 보존 |

SQLite는 기존대로 짧은 DB 저장을 담당한다. DB의 쓰기 잠금만으로 실제 설치 파일이나 초기 외부 공간까지 조정하지 않는다. 반영 요청의 대상/시도 확인은 일반 코드가 처리하며 이 확인을 위해 AI를 별도 호출하지 않는다.

**대상 식별**은 등록한 코드 작업 루트를 기준으로 한다. 명령을 실행한 하위 폴더, Git 원격 주소, 공유 `project_id`나 경로 문자열만으로 잠금 이름을 만들지 않는다. `CreateFileW`로 실제 디렉토리 핸들을 열고 `GetFileInformationByHandleEx(FileIdInfo)`의 볼륨/파일 식별값을 확인하는 후보를 사용한다. 같은 루트의 허용된 별칭 경로는 같은 대상을, 다른 clone/worktree의 루트는 다른 대상을 가리켜야 한다. 이 조정은 같은 코드 작업 사본에 한정하며, 별도 코드 루트가 같은 외부 문서에 쓰는 경우까지 보호했다고 확대하지 않는다.

잠금 이름 후보는 `Global\<제품 식별자>.<루트 식별값의 해시>`다. `Global`은 같은 Windows 기기의 여러 로그인 세션에 통하는 이름 공간이며 팀이나 원격 기기를 뜻하지 않는다. 이름에 사용자, 설치 단계나 배포 버전을 넣어 같은 대상의 잠금이 갈라지게 하지 않는다. 입력 경로와 식별을 다시 대조하며, 루트가 삭제/교체됐거나 식별 조회가 실패하면 경로 문자열만의 별도 잠금으로 우회하지 않는다. 이 식별값은 현재 대상 대조용이며 영구 프로젝트 ID나 사용자 허가를 대신하지 않는다.

| 순서 | 공통 실행 코드의 처리 |
| --- | --- |
| 1. 진입 확인 | 설정의 허용 루트와 실제 대상을 대조하고 해당 뮤텍스를 생성/열기. 자식에게 핸들을 상속하지 않음. 접근 거부, 다른 종류의 객체와 이름 충돌, 미지원 식별은 구별해 반환 |
| 2. 반영 구간 획득 | 초기 소유 없이 연 뒤 `WaitForSingleObject`로 획득 여부 확인. 먼저 0 대기로 바쁜 상태를 반환하는 후보이며 기존 실행에 제한 시간을 걸거나 종료시키지 않음. 다른 이름으로 재시도해 보호를 우회하지 않음 |
| 3. 현재 상태 대조 | 잠금 안에서 현재 진행 원본, 해당 `task_id`와 `attempt_id`, 미완료 반영, 관측한 프로세스와 입력을 다시 확인. 같은 시도가 살아 있거나 종료를 모르면 새 시도를 중복 시작하지 않음 |
| 4. 준비/반영/기록 | 해당 경계의 준비 기록을 짧게 commit한 뒤 허용된 효과를 수행하고 실제 결과를 기록. 파일 보호 조건까지 충족한 단위만 반영. DB 트랜잭션을 유지한 채 AI, 사용자 응답이나 외부 명령 종료를 기다리지 않음 |
| 5. 반환 | 결과를 기록하거나 미완료로 보존한 뒤 획득한 스레드가 `ReleaseMutex`, 핸들 닫기 수행. 반환/저장 오류는 성공으로 숨기지 않음. 예외 경로에서도 정리하며 소유하지 못한 실행은 반환을 시도하지 않음 |

긴 분석이나 확인 대기는 뮤텍스 밖에서 수행한다. 다시 반영할 때 같은 진입점을 거쳐 현재 기준을 대조한다. 단순 조회나 일상 대화마다 잠금/복구를 실행하는 흐름이 아니다. 같은 작업 사본의 짧은 반영은 순서대로 처리할 수 있지만 다른 팀원의 clone, 독립 읽기와 긴 분석 전체를 기다리게 하지 않는다.

뮤텍스를 반환해도 진행 중인 시도의 기록은 사라지지 않는다. 긴 실행을 시작할 때 준비/프로세스 관측을 남기고, 다른 재개가 들어오면 그 기록을 먼저 대조한다. PID나 시각만으로 생존/종료를 단정하지 않으며 확인되지 않은 실행은 `unknown`으로 남긴다. 뒤늦은 결과는 자기 시도의 근거로 보존할 수 있어도 현재 작업이 이어받은 시도와 입력이 다르면 active, 현재 진행이나 원문을 덮지 못한다. 별도의 수정 가능한 소유 상태 파일을 추가하지 않는다.

`WAIT_ABANDONED`는 이전 소유 스레드가 정상 반환 없이 끝났다는 신호다. 다음 실행이 잠금을 얻어도 실제 효과를 재대조해야 한다. 모든 핸들이 사라져 객체를 새로 만든 경우에는 이 신호조차 남지 않으므로 **일반 획득에서도 미완료 기록을 확인**한다. 자식 프로세스 종료나 외부 편집 정지를 잠금 반환으로 추정하지 않는다. 초기 외부 기록에서 프로젝트 DB로 인계할 때도 같은 루트 기준을 유지하며, 미완료 인계를 새 설치로 우회하지 않는다.

이름 있는 객체의 접근권과 기존 객체 충돌도 시험 대상이다. 예측 가능한 이름은 다른 프로그램이 먼저 점유할 수 있으므로 신뢰 경계나 보안 보장으로 쓰지 않는다. 실패를 사용자 설정/ACL 변경이나 무단 관리자 실행으로 해결하지 않으며, 실제 접근권 문제가 크면 파일 잠금 대안을 같은 보호 기준으로 재평가한다.

제품의 반영 경로와 새 호출은 미완료 설치 기록을 확인해 부분 설치를 사용하지 않아야 한다. 다만 이 뮤텍스가 일반 `codex`의 지침 읽기나 외부 편집기를 자동으로 중단시키지는 않는다. 사용 중인 hook/script와 호스트 재로드는 [갱신의 실행 경계 — 「실행 중인 구성의 갱신」](../runtime/update.md)에 연결했다. 이 후보만으로 설치 중 모든 외부 접근이 차단됐다고 설명하지 않는다.

공식 근거: [CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw)의 수명/소유/접근권, [Windows 이름 공간](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces), [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)의 반환 상태, [디렉토리 열기](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [파일 식별](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)과 [조회 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex). 11/16 공식 자료를 대조했으며 실제 지원 파일시스템, 접근권과 강제 종료 시험은 아직이다.

#### 외부 편집과 반영

자기 로컬 WIKI를 편집기에서 수정했거나 Git으로 갱신한 경우에도 후보 기준과 현재 파일을 대조해 사용자 변경을 보존한다. 변경 전 해시 확인만으로 쓰기 도중의 모든 경합이 차단됐다고 주장하지 않는다. 실제 반영 구간의 보호 수단은 Windows 파일 열기, 교체 동작과 함께 시험하고, 안전한 반영 조건을 확인할 수 없으면 후보를 유지해 해당 반영을 보류한다. 이 내부 보호를 팀 전체의 작업 대기나 새로운 공유 저장소의 요구로 확대하지 않는다.

실행 조정 후보를 골라도 파일 반영은 별도 검증이 필요하다. [기존 파일과 새 파일](../runtime/update.md)의 후보는 확인부터 쓰기까지 같은 핸들을 유지하되 강제 종료 시 부분 내용이 남을 수 있다. active와 WIKI에도 필요한 파일 보호를 연결하지만, 매 요청마다 설치/복원을 실행하거나 DB 파일까지 같은 방식으로 저장하지 않는다. 실제 편집기의 접근 제한과 중단 뒤 사용자 변경 보존을 확인하기 전 자동 반영의 안전성을 통과 처리하지 않는다.

[SQLite](https://www.sqlite.org/lang_transaction.html)의 트랜잭션과 [Python os.replace](https://docs.python.org/3.13/library/os.html#os.replace)는 각각 DB 기록과 한 경로의 교체 수단이다. 여러 파일, 원격 효과의 일괄 원자성은 별도이며, [소유, 인계 검증 입력 — 「작성 소유와 인계의 검증 입력」](../../verification/acceptance.md)을 실제로 확인하기 전 복구/보존 성공으로 보고하지 않는다.

### 저장 시점

저장은 종료 hook의 마지막 기회에 맡기지 않고 **다음 행동에 필요한 근거가 바뀌는 경계**에서 확인한다. 아래의 기계 기록은 모듈이 관리하는 실행, 반영 경로가 담당한다. 일반 CLI의 임의 명령이나 외부 편집까지 자동 기록했다고 설명하지 않는다.

| 시점 | 누가 무엇을 남기는가 | 저장을 확인한 뒤 할 일 |
| --- | --- | --- |
| 복구가 필요한 작업의 첫 단위 전 | 메인이 목표, 허용 범위, 부모/현재 단위, 미해결 조건, 다음 행동을 정리. 일반 코드는 연결, 제외, 쓰기 가능 여부 확인 | 첫 실행 준비. 의미 없는 빈 active나 완료 상태를 설치 때 미리 만들지 않음 |
| 사용자 조건, 승인 범위 변경 | 메인이 바뀐 조건과 영향을 기존 상태에 반영 | 변경된 조건에 의존하는 실행. 철회된 승인을 옛 기록에서 가져오지 않음 |
| 긴 실행, 부분 변경 가능한 실행 직전 | 일반 코드가 현재 계획과 시도, 대상, 필요한 적용 전 자료의 저장을 확인. 메인은 의미 상태가 바뀐 경우만 갱신 | 실제 실행 시작. 기록 확인 없이 먼저 실행하고 나중에 저장하지 않음 |
| 결과 수집, 부분 반영 확인 직후 | 일반 코드가 해당 시도의 종료/결과, 산출물과 실제 반영 범위를 연결 | 결과에 의존하는 다음 단위나 완료 판단. active에 결과가 아직 없다고 같은 실행을 반복하지 않음 |
| 단위 완료, 실패, 보류 또는 다음 행동 변경 | 메인이 완료 근거 참조, 남은 의무, 다음 행동을 갱신 | 승인된 다음 단계. 실패한 반영의 진행은 기존 보고/복원/협의 원칙을 따름 |
| 정상 턴 종료, compact, 재개 | 지원 이벤트와 메인이 변경된 복구 정보가 남았는지 확인 | 변경이 없으면 전체 재작성하지 않음. 이벤트가 안 온 경우도 앞선 저장으로 대조 가능해야 함 |

필수 기록 저장이 실패하면 그 기록에 의존하는 새 변경과 완료 선언을 멈추고 보고한다. 확인 가능한 읽기, 진행 중 실행 조회까지 무조건 금지하는 것은 아니다. 결과 저장 실패와 실제 작업 실패를 구분하며, 저장을 다시 시도하려고 실제 명령을 다시 실행하지 않는다. 디스크가 계속 쓰기 불가능하면 오류 기록도 남지 않을 수 있으므로 보고/저장 여부 자체를 구분한다.

이는 모든 읽기마다 동기 저장하거나 전체 대화를 복제하는 정책이 아니다. 기존 기록의 변경 없는 부분은 재사용하고 다음 실행의 안전성에 필요한 저장만 기다린다. [LangGraph 저장 모드](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes)도 다음 단계 전 저장과 비동기/종료 시 저장의 내구성, 성능 차이를 구분한다. 여기서는 필요한 경계를 먼저 정한다는 원리를 적용하며 해당 프레임워크나 저장 구현을 채택한 것은 아니다.

### 비정상 중단에서의 처리

아래는 B에 필요한 복구 계약 후보이며 아직 실제 시험하지 않았다. **마지막 정상 저장 이후의 미기록 판단까지 완전히 복원하는 보장은 없다.** 중단 때 추가 모델 호출 없이 남아 있는 근거로 확인할 수 있게 만드는 것이 목표다.

| 상황 | 남겨야 할 단서와 재개 판단 | 보장하지 않는 것 |
| --- | --- | --- |
| 구독 사용량 제한, 모델 요청 거부 | 이전에 저장한 목표/범위, 현재 단위, 호출/결과를 읽음. 제한 해소 뒤 미완료 단위부터 확인하며 부분 응답을 완료로 쓰지 않음 | 한도 도달 직전에 반드시 요약할 기회, 다른 모델/유료 API로 자동 우회 |
| 네트워크 단절, 응답 유실 | 요청 실패와 작업 미실행을 구별. 로컬 프로세스, 저장 결과, 지원되는 원격 상태를 조회한 뒤 필요할 때만 다시 실행 | 화면에 응답이 없으니 서버 작업도 취소됐다는 판단, 조회 수단 없는 외부 작업의 무조건 중복 방지 |
| CLI의 사용자 중단 | 지원되는 Interrupt 등은 기계 기록 보조로 사용. 새 작업을 시작하지 않고 종료/남은 실행 상태를 확인. 사용자 재개 지시 뒤 이어감 | Ctrl+C가 항상 모든 자식 프로세스를 종료하거나 같은 이벤트를 발생시킨다는 가정, 사용자 취소 뒤 자동 재시작 |
| 프로세스 강제 종료, 터미널 소실, PC 재시작 | 종료 hook 없이도 직전 유효 상태를 읽고 시작만 남은 시도, 부분 쓰기, 실제 파일을 대조. 종료 확인 없는 시도는 미확인으로 둠 | 종료 직전 자동 저장, 프로세스 메모리 복원, 저장소 자체가 유실된 경우의 복구 |

특히 **외부 변경은 성공했지만 완료 기록을 쓰기 전에 끊기는 구간**이 있다. WIKI 반영이나 PR 생성에서 같은 작업을 다시 적용하기 전에 대상 상태와 이전 시도를 대조해야 한다. 재시도해도 같은 결과가 되도록 만들 수 있는 연산은 그 조건을 사용하고, 외부 서비스가 지원하지 않는 중복 방지까지 있다고 가정하지 않는다. 확인할 수 없으면 필요한 단위만 멈추고 보고한다. 전체 자동 rollback이나 무조건 처음부터 재실행하는 정책으로 바꾸지 않는다.

Codex의 대화 재개는 사용할 수 있는 기존 대화를 잇는 기능이고, 이 계약은 실제 작업의 진행/근거를 복구하는 것이다. 사용자에게 접속, 모델 선택, 권한 변경을 매번 다시 요구하려는 뜻이 아니다. 대화/디스크에 남지 않은 정보는 복원하지 못하므로 사용 가능한 이력, 실제 파일로 확인하고 필요하면 사용자에게 묻는다.

### 재개 판단 순서

먼저 [적용 경계 — 「복구의 대상과 경계」](recovery.md#%EB%B3%B5%EA%B5%AC%EC%9D%98%20%EB%8C%80%EC%83%81%EA%B3%BC%20%EA%B2%BD%EA%B3%84)에서 문맥 복구, 기능 재개, 설치 재개 중 필요한 흐름을 고른다. 아래는 그 범위 안의 대조 순서다. 순수 문맥 복구에 미확인 실행이 없으면 3번의 실행/반영 조회는 필요하지 않다. 정상 개발의 확인된 실패는 이 순서 대신 기존 수정, 재검증으로 이어간다. 취소 뒤 자동 재시작하거나 스스로 새 세션을 여는 정책이 아니다.

진입 절차에서 받은 대상/설정과 실패 이유는 [실패 뒤 돌아갈 위치](../runtime/entry.md)를 따른다. `resume`은 선택한 CLI 세션을 여는 동작이고 아래 작업 복구의 완료를 뜻하지 않는다. 연결 실패 때문에 읽지 못한 active/실행 기록을 없는 기록으로 초기화하지 않는다. 접근이 가능해진 뒤 해당 작업을 대조하고, 원래 작업의 미완료나 사용자 취소 상태를 연결 성공으로 덮지 않는다.

1. **대상 확인:** 등록한 코드 작업 트리, 작업, WIKI 연결과 현재 요청을 확인한다. 다른 작업의 상태를 가져오거나 기존 상태 부재를 새 작업으로 조용히 처리하지 않는다.
2. **기록 확인:** 문맥 복구는 해당 active와 필요한 참조를, 실행/설치 재개는 해당 계획, 시도와 미해결 상태를 확인한다. 형식, 시각이 정상이어도 의미 최신성을 확인한 것으로 보지 않는다.
3. **실행/반영 대조:** 진행 중, 미확인 시도와 실제 프로세스/산출물/적용 대상을 확인한다. 같은 PR, 파일 반영 등을 다시 실행하기 전에 이미 수행됐는지 대조한다.
4. **변경 영향 확인:** 이어갈 단위에 관련된 코드, WIKI, 설정, 허용 범위의 변화를 확인한다. 원래 실패/미완료 의무를 유지하고 입력이 바뀐 결과만 재검토한다.
5. **다음 행동 결정:** 승인 범위와 근거가 그대로면 남은 단계로 이어간다. 새 정책, 추가 비용, 권한, 불명확한 외부 효과, 충돌 해결은 관련 단위를 보류하고 선택지와 추천을 제시한다. 같은 기계적 단계의 반복 승인은 요구하지 않는다.
6. **대조 결과 저장:** 정정한 상태와 근거, 남은 미확인, 다음 행동이 있으면 저장한 뒤 그 내용에 의존하는 작업을 진행한다. 변경 없는 active를 다시 쓰기 위한 단계로 사용하지 않는다. 전체 완료와 부분 재개, 보류를 구별한다.

| 대조 중 발견한 상황 | 처리 경계 |
| --- | --- |
| 현재 상태 파일만 손상, 직전 유효본과 실행 결과 존재 | 손상 자료를 덮지 않고 유효본에서 실제 결과를 대조해 현재 상태 후보 구성. 자료가 충분하면 상태 기록을 복구하되 작업 결과 재실행/원문 복원과 구분 |
| 기록이 없거나 참조 결과도 없음 | 사용 가능한 요청/작업 근거로 확인한 부분만 재구성. 미기록 의도, 실행 여부를 추측하지 않고 필요한 입력을 사용자에게 확인 |
| 같은 로컬 작업의 다른 세션/남은 실행이 상태나 대상을 쓰는 중 | 소유를 임의 해제하거나 덮지 않음. 현재 실행을 대조해 같은 작업의 재개, 인계를 판단. 다른 팀원의 별도 clone 작업까지 기다리게 하지 않음 |
| 소유자가 종료된 것 같거나 오래된 잠금 존재 | 시각/PID 하나로 잠금 제거, 프로세스 종료하지 않음. 실제 실행과 상태를 대조한 뒤 해제/인계 범위를 정함 |
| 후속 사용자 편집, 부분 적용, 지원하지 않는 기록 형식 | 확인한 완료는 보존하고 해당 변경을 보류. 상태를 빈 값으로 덮거나 최신 시각의 파일을 무조건 승자로 선택하지 않음 |

위 표의 잠금과 인계는 [같은 로컬 작업의 실행 — 「작성 범위와 동시 작업」](recovery.md#%EC%9E%91%EC%84%B1%20%EB%B2%94%EC%9C%84%EC%99%80%20%EB%8F%99%EC%8B%9C%20%EC%9E%91%EC%97%85)을 대상으로 한다. 다른 팀원의 active나 DB를 조회하거나 기다리는 절차가 아니다. DB 내부 쓰기, 같은 작업의 중복 실행, 외부 편집과의 충돌을 구분하며 하나의 잠금으로 모두 해결했다고 보지 않는다. 정확한 잠금과 인계 수단은 후속 명세에서 정하고, 현재 입력 대조와 반영 중 변경 감지의 한계도 함께 검증한다.

이미 발생한 외부 효과는 상태 파일을 되돌린다고 취소되지 않는다. [LangGraph의 재실행 경계](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#treat-a-missing-acknowledgement-as-unknown)는 응답 부재를 미실행으로 보지 않고 외부 상태를 확인하도록 설명한다. [Microsoft의 보상 처리](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)도 다른 작성자의 변경 때문에 단순 원상복원이 안전하지 않을 수 있음을 설명한다. 이 원리를 기존 [ADR 0011](../../decisions/runtime/0011-preservation.md)에 연결하며, 강제 종료 후 파일 복원, 원격 취소를 자동 실행하는 허가로 확대하지 않는다.

### 중단과 재개의 예시

아래는 설명용이며 아직 실행한 시험이 아니다. WIKI 복원 단위 A의 후보가 검토, 반영, 확인됐고 B는 분석 중일 때 세션이 중단됐다고 가정한다.

1. 재개한 메인이 저장된 목표, A 완료 근거, B의 실행 참조, 남은 범위를 읽는다. 동일 프로젝트/작업인지와 현재 입력을 확인한다.
2. B가 계속 실행 중이면 같은 분석을 새로 시작하지 않는다. 종료됐으면 그 시도의 결과를 확인하고, 실행/종료를 확인할 수 없으면 미확인으로 남긴다.
3. A의 내용, 근거가 그대로라면 A를 처음부터 다시 만들지 않는다. 그동안 관련 코드나 WIKI가 바뀌었다면 영향받는 완료 주장, 후보만 재검토한다. 저장된 완료 문구를 무조건 믿지 않는다.
4. 분석 후보만 생성됐는지, 검토/반영까지 됐는지 구분한다. 반영 중 중단이면 실제 파일과 반영 근거를 대조하며 임의 재적용, 원문 덮어쓰기, 자동 rollback으로 이어가지 않는다.
5. 확인한 B의 재개 지점과 남은 단위를 현재 상태로 갱신하고 이어간다. 새 범위, 비용, 권한, 정책 선택이 생기는 부분만 사용자와 협의한다.

일반 개발의 문맥 복구에서도 API 실패와 core 성공을 구별해 원래 API 검증 의무를 유지한다. 문맥과 결과가 유지된 일반 오류 처리는 기존 재시도 흐름을 따른다. 같은 대화에서도 실행 효과가 미확인이면 해당 시도만 대조하며, 새 대화의 인계는 저장된 목표, 조건을 먼저 확인한다.

### 현재 연결과 확인된 한계

11/11 현재 기존 시험 프로젝트의 followup skill, hook 설정, `followup_compact_guard.py`, 검증 결과 기록과 기존 감사/실험을 읽어 대조했다. 제품 코드를 수정하거나 새 native 시험을 실행하지 않았다. 현재 복구는 **메인이 작성하는 active + 읽기/최신성 확인을 돕는 hook + 일부 검사 상태 기록**의 조합이다.

- 기존 `followup-handoff`도 이미 긴 실행 전, 결과 수집 뒤, 범위/다음 행동 변경 때 active 갱신을 판단한다. 종료/compact 직전에만 저장하는 방식이 아니다. 이 원칙을 B의 새 기능처럼 설명하지 않는다.
- `SessionStart`는 active 확인 지시를 모델 문맥으로 전달한다. 기존 PostCompact 출력은 UI 경고이고, PreCompact의 stale 처리는 변경 경로 등 기계 정보만 남긴다. active의 목표, 결정, 미해결 상태를 자동으로 작성하지 않는다.
- marker는 일부 파일의 fingerprint와 시각을 확인한다. 실제 의미 상태를 읽고 정확하게 갱신했는지를 증명하지 않는다. 현재 `.scope`는 코드 루트 밖 경로를 거부하므로 등록된 외부 WIKI 변경까지 확인하는 제품 계약이 별도로 필요하다.
- 검사 상태 파일도 이미 있다. 예를 들어 `check-doc-implementation.sh`는 `--result-file`이 주어지면 종료 뒤 결과를 쓴다. 다만 이 경로에는 실행 전 저장된 고유 시도와 진행 중/종료 미확인을 대조하는 연결이 없고, `gate_write_result`는 지정 파일을 직접 덮어쓴 뒤 의존 정보를 추가한다. 현재 기록의 존재와 중단에 견디는 시도별 보존을 구분한다.
- 기존 [E-011 — 「E-011 — quota 임박 지침과 감지 후 저장하는 연결의 부재」](../../evidence/issues.md), [E-013 — 「E-013 — 복구 상태 입력 손상과 시각 경계 처리 부족」](../../evidence/issues.md)은 quota 신호 연결 부재와 손상/미래 시각 처리의 반례다. 파일 기록도 현재는 직접 쓰며, 부분 저장, 동시 실행의 안전성이 검증된 제품 저장 수단이 아니다.

11/11 사용자는 중단 전에 active를 저장하지 않거나, 원하는 내용이 저장, 로드되지 않은 경험이 여러 번 있었다고 설명했다. 사용자 보고로 보존하며 각 사례의 원인, 발생률을 측정한 것으로 쓰지 않는다. 아래의 누락 방지와 [복구 시험 — 「복구 시험에 넘길 조건」](../../verification/acceptance.md)에 연결하고, 기존 기계 검사 통과를 의미 복구 성공으로 확대하지 않는다.

현재 [OpenAI Docs의 hooks](https://learn.chatgpt.com/docs/hooks)는 `SessionStart`의 문맥 전달, `Interrupt`의 사용자 중단 알림, `PostModelRequest`의 요청 결과, `SessionEnd`의 정해진 종료 이벤트를 설명한다. 중단/종료 hook은 짧은 기계 기록의 보조 후보로 활용할 수 있지만 강제 종료, 전원 중단 전에 반드시 실행된다는 계약은 아니다. 도구 hook의 관측 제외 경로도 있고, transcript 형식도 안정된 인터페이스로 보장하지 않는다. 정확한 지원 버전, Windows 동작을 확인해 필요한 이벤트만 연결하며 현재 세 hook에 나머지가 이미 설치됐다고 설명하지 않는다.

### 복구 기본 방식의 대안

현재 구성에서 유지할 것과 보강할 것을 먼저 구분한다. 11/15 코드 읽기 대조는 `followup_compact_guard.py`, followup skill, `check-doc-implementation.sh`와 `gate-common.sh` 기준이며 새 실행 시험은 아니다.

| 책임 | 현재 개발 브랜치 | 제품 B안의 보강 |
| --- | --- | --- |
| 의미 있는 진행 상태 | 메인이 active에 목표, 조건과 다음 행동을 작성. 긴 실행 전후에도 갱신 필요성을 판단 | 같은 역할 유지. 검사 사실은 연결된 기록에서 확인하고 변경 없는 본문 재작성은 강제하지 않음 |
| scope와 marker | 지정 파일의 존재, 크기, 수정 시각과 SHA-256, 15분 확인 유효기간을 대조 | 관련 입력/현재 active 기준을 대조하는 역할 유지. 외부 WIKI도 등록 범위에서 다뤄야 하며 marker의 정확한 보관/호출은 후속 hook 명세에서 정함 |
| compact 전 snapshot과 재개 안내 | marker가 오래되면 변경 후보와 Git 상태 등을 저장하고 재개 때 active 확인 안내. snapshot은 파일 본문 백업이나 의미 요약이 아님 | 안내는 계속 보조로 사용. 종료 hook이 오지 않아도 관리 경로에서 이미 저장한 계획/실행 근거로 대조 |
| 검사 결과 | 실행 뒤 결과 파일을 쓸 수 있으나 지정 결과 파일을 덮어쓰는 경로가 있음 | 같은 계획에 시도를 연결하고 원래 실패를 보존. 실행 준비, 실제 종료, 미확인과 결과 판정을 구별 |
| 중단 후 판단 | 메인이 active와 흩어진 근거를 찾아 진행 판단 | 일반 코드가 해당 시도/결과의 대응을 조회하고 메인이 목표, 남은 의무와 다음 행동을 판단. 기록되지 않은 의도를 자동 복원하지는 못함 |

marker가 유효하다는 것은 확인한 파일 기준이 유지된다는 단서다. 필요한 사용자 조건이 active에 실제로 들어 있는지, 테스트가 성공했는지까지 증명하지 않는다. SQLite도 이 의미 검토를 대신하지 않는다. scope 대조, 결과 연결과 hook 안내가 같은 검사를 각각 반복하거나 서로 다른 완료 원본을 관리하지 않도록 연결해야 한다.

예를 들어 테스트 결과까지 DB에 저장됐지만 active를 갱신하기 전에 CLI가 종료됐다고 가정한다. 재개 뒤 같은 시도와 현재 입력이 맞으면 결과를 참조하고 active의 다음 행동을 고친다. 결과를 확인할 수 없다면 미확인으로 남긴다. 오래된 active만 보고 무조건 테스트를 다시 실행하거나 DB에 준비 기록만 있다고 성공 처리하지 않는다.

아래 A/B/C는 **복구 방식**에 관한 비교다. 앞서 채택한 검증 기록 B, 재사용 C를 다시 선택하는 표가 아니다. 모든 안은 그 계약을 충족해야 한다.

| 안 | 동작 | 장점 | 부담, 한계 |
| --- | --- | --- | --- |
| A. 기존 active와 hook의 국소 보강 | 이미 있는 작업 경계 저장, marker, 검사 결과를 유지하고 손상, 경로, 안내의 결함을 수정. 중단된 실행은 메인이 기록을 찾아 판단 | 초기 변경이 작고 현재 사용법과 가까움 | 실행/응답 유실, 부분 반영, 동시 작업을 일관되게 판별하는 책임은 여전히 남음. 원래 검증 기록 계약도 충족해야 함 |
| B. 기존 방식에 실행, 저장, 재개 계약 보강 — 검증 전제 수용 | active와 hook을 유지. 채택한 계획/시도 기록에 실행 전, 결과 저장과 재개 대조를 연결하고 부분 저장, 소유 충돌을 처리 | 정상 종료 hook이 오지 않아도 이미 저장한 근거로 확인 가능. 일반 개발, 검사, WIKI 분석의 미완료 판단을 연결하며 별도 중앙 서비스 없이 구현 가능 | 기록 저장, 작업 식별, 대조 코드와 실패 시험이 추가됨. 기록하지 않은 판단과 저장 중 유실까지 완전히 복구할 수는 없음 |
| C. 외부 실행 관리기 중심 | 별도 관리기가 작업 단계, 모델 호출, 도구 실행, 재개를 지속 관리 | 관리기를 통과한 작업의 실행 추적, 다중 작업 제어를 확장하기 쉬움 | 기존 AI CLI와 책임, 권한, 상태가 겹치고 설치/운영, 장애 검증 범위가 커짐. 이를 거치지 않은 일반 CLI 작업은 여전히 별도 |

11/11 재검토: A와 B는 완전히 다른 복구 구조가 아니다. A에 중단된 실행의 판별, 저장 내구성, 원래 계획/시도의 연결을 충분히 보강하면 실질적으로 B의 범위가 된다. **B는 기존 active + hook을 교체하는 안이 아니라, 그 위에 부족한 계약을 채우는 안**으로 정의한다. checkpoint, 검사 기록 자체를 새 발명이나 현재 구조에 없는 것으로 제시하지 않는다.

**사용자는 이 보강 범위의 B를 실제 검증 전제로 수용했다.** 사용량 제한, 네트워크, 사용자 중단은 이미 요구된 상황이고, 계획/시도 보존도 채택했다. 따라서 같은 기록을 활용해 실행 상태가 불명확한 때의 처리를 정하는 편이 목적과 구현 범위에 맞다. A보다 무조건 빠르거나 적은 토큰을 쓴다는 실측은 없다. 짧은 질의만 다룬다면 A로 충분할 수 있지만, 장기 WIKI 분석, 검사, 파일 반영을 다루는 이 제품에서는 미완료 누락, 중복 적용을 제어할 이점이 크다고 판단한다. 최초에는 새 DB 의존성을 우선 두지 않았으나 저장 수단 비교 후 [ADR 0021](../../decisions/workflow/0021-recovery-storage.md)에서 기계 기록에 한정한 로컬 SQLite를 추천했고 11/12 채택했다. 별도 workflow/DB 서버, 복구 전용 AI 호출을 도입하는 안은 아니다.

### 공개 사례와 적용 범위

공식 구현, 문서에서 확인한 설계 패턴이다. 기업 전체의 사용률이나 우리 B안이 검증됐다는 근거로 쓰지 않는다.

11/15 재대조에서도 진행 문서, 단계 경계 저장과 응답 유실 뒤 실제 효과 대조를 구별하는 원칙을 확인했다. 아래 Microsoft 사례는 파일 저장도 제공하므로 이 자료를 SQLite만이 정답이라는 근거로 쓰지 않는다. [LangGraph의 저장 모드](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes)는 저장 시점에 따른 내구성과 실행 비용을 비교한다. 우리의 추천은 그 원칙과 여러 계획/시도 참조를 관리할 요구를 함께 고려한 판단이며, 정상 경로의 부담과 복구 성능은 [실제 비용 비교 — 「저장 비용을 비교할 입력」](../../verification/acceptance.md) 전까지 미측정이다.

| 사례 | 확인한 방식 | 이 설계에 적용할 점, 한계 |
| --- | --- | --- |
| [Anthropic 장기 작업 사례](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) | 작업을 작게 진행하고 progress 문서, Git 기록을 다음 세션에서 읽음 | 현재 active의 의미 기록 방향을 지지. 임의 강제 종료 직전 판단까지 저장하는 보장은 아님 |
| [Anthropic 공개 hook 예제](https://github.com/anthropics/cwc-long-running-agents) | 작업 중 진행 문서를 갱신하고 hook을 보조 수단으로 결합 | active와 hook의 공존 사례. 저장소는 유지보수하지 않는 행사 예제라고 명시하므로 제품 완성도 근거로 사용하지 않음. 자동 커밋, 추가 평가 모델은 그대로 도입하지 않음 |
| [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) | 단계 경계에서 실행 상태를 저장. 로컬 파일 저장소를 쓰면 새 프로세스에서도 읽을 수 있음 | 메모리 내 저장과 디스크 보존을 구분할 근거. 관리되는 workflow의 상태이며 일반 Codex 세션 전체를 대신 저장하는 기능은 아님 |

이 사례들의 공통점은 작업 중 저장된 상태에서 복귀한다는 점이다. 정상 종료 시 한 번 저장하는 수단만으로 중단을 처리하지 않는다. 어떤 정보, 시점, 내구성 수준이 필요한지는 이 모듈의 범위와 실제 시험으로 정한다.

### 후속으로 정할 복구 세부

논리 상태, 저장 경계, 재개 순서와 저장/동시 작성 후보를 위 초안에 통합했다. [ADR 0021](../../decisions/workflow/0021-recovery-storage.md)의 **기계 기록에 SQLite 사용**은 11/12 채택했다. 제품 구현을 앞당기지 않으며 이후 남은 명세는 다음과 같다.

- 로컬 검증과 active의 [기록 명세](records.md), 검증/설치/인계의 [SQLite 관계 후보](storage.md)를 연결했다. [전체 DDL 후보와 저장 코드의 경계 — 「DDL과 저장 코드의 경계」](storage.md)를 작성했고 SQL 제약의 부분 검사를 마쳤다. 지원 SQLite/연결 API와 내구성 설정의 실제 환경 대조는 남아 있다. WIKI 반영과 원격 효과는 각 기능의 의미를 유지한다. [백업과 저장 형식 변경](recovery.md#%EB%B0%B1%EC%97%85%EA%B3%BC%20%EC%A0%80%EC%9E%A5%20%ED%98%95%EC%8B%9D%20%EB%B3%80%EA%B2%BD), 자동 보존/명시적 정리의 정확한 파일, 삭제 단위, 참조 대조와 재중단 처리도 남아 있다. 부분 쓰기/손상, 미래 시각, 중복 기록, 전환 중단을 단일 파일 교체 성공으로 통과 처리하지 않는다.
- 각자의 로컬 편집, Git 공유를 기준으로 [소유 확인과 인계](recovery.md#%EC%86%8C%EC%9C%A0%20%ED%99%95%EC%9D%B8%EA%B3%BC%20%EC%9D%B8%EA%B3%84)의 저장/반영 수단과 실제 시험을 명세한다. 공통 조정 위치 선택은 현재 진행 항목에서 철회했다. 기존 로컬 중단 복구, 늦은 결과, 사용자 편집 보존 조건은 유지한다.
- 등록한 외부 WIKI, 경로/권한 변경, 현재 입력과 결과의 대조 수단, 지원하지 않는 상태 형식의 처리와 보존 수명. 미완료 복구 자료 정리를 정상 완료로 오인하지 않는다.
- Windows의 공통 입력, 저장/반영 중단 지점, 실제 CLI 재개, 행동 판정은 [복구 시험 명세 — 「실제 환경에서의 검증 순서」](../../verification/acceptance.md)에 정리했다. 4단계에서 제품 파일/함수와 관측 지점을 연결하고 해당 기능 구현 뒤 실행한다. 정확한 명령, 반복/비용은 실행 전에 정하며 일반 코드 시험과 실제 AI의 의미 복구를 구분한다.

4단계의 기록 필드와 전체 DDL 후보, 메모리 DB의 제약 검사, 아직 남은 명령과 저장/잠금의 실제 검증을 구별한다. 저장/잠금 선택이 복구의 보장을 바꾸면 먼저 협의한다. 정상 경로의 저장/읽기 비용과 중단 후 미완료 누락, 잘못된 완료, 중복 실행/반영, 재개 시간/토큰을 함께 비교한다. 제품 구현, 실제 전환/복구 시험은 아직이다.
