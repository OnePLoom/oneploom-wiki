## 확정된 작업 조건

2026-10-27 사용자 보충을 반영했다. 명명, 문체, 중복 제거, 모듈화의 지속 기준은 [개발 원칙](../../development/standards.md)에 두며 최종 배포, 테스트 완료까지 적용한다. 이 조건의 반영과 아래 검증 방식의 채택은 구분한다.

boot 테스트 제외는 팀원의 비공개 platform 기반 BOM과 관련 자원에 접근할 수 없어 둔 **현재 프로젝트 전용 예외**다. 사유는 사용자에게 확인했으며 이번에 자원 접근을 시험하지 않았다. 예외 해제를 다음 단계의 선행 조건으로 두지 않는다. 적용 대상, 사유, 미실행 상태를 명시하고, 다른 프로젝트의 기본 제외로 복제하지 않는다.

남은 범위 검토는 의도한 제외와 실제 테스트 선택의 대응이다. 기존 9개 include 목록이 나머지 검사를 의도치 않게 빠뜨리는지는 이 문제와 구별한다. 제외 사유를 다시 협의하거나 boot 전체를 면제하는 검토가 아니다.

## 이식성을 위한 공통 제약

다른 프로젝트에서 재사용하고 대상 코드, 기록을 분석해 설정과 문서를 채우는 것은 사용자가 재확인한 최종 필수 목표다. 로컬 AI 도입 여부와 독립적이며, 구체 초기화 구현은 후속이어도 현재 계약부터 적용한다. [ADR 0004](../../decisions/architecture/0004-portability.md)에 비교안과 경계를 남겼다.

이 문서의 sample-*, API/core, Gradle은 현행 반례와 첫 연결부의 예다. 공통 계획, retry, 결과 형식에 해당 이름이나 Gradle 전용 task를 내장하지 않는다. 공통 처리는 해석 완료된 프로젝트 설정과 연결부가 제공하는 검사 목록을 소비한다. 다른 언어/빌드 도구의 지원도 같은 계약으로 확장하고 모르는 대상은 미지원, 미확인으로 반환한다.

## 실제 사용 환경과 검증 조건

11/18 사용자 재확인: 기능 검증의 기준은 배포물을 받은 사용자의 실제 준비와 설치, 실행, 기능별 상호작용이다. 시험하기 편한 별도 경로를 만들고 그 결과를 배포 환경의 성공으로 대신하지 않는다. 아래 조건을 먼저 확인하고 맞춘 뒤 해당 기능을 검증한다.

| 확인 대상 | 실제 사용과 맞출 조건 |
| --- | --- |
| 배포 대상과 실행본 | 사용할 배포 후보의 코드/설정 식별과 의존성 버전. 시험 전용 reader나 별도 호출 함수가 제품 실행 경로를 대신하지 않음 |
| 사용자 환경 | 지원 OS, 파일시스템, 셸, Python/CLI/SDK, 설치 방법, 실제 작업 위치와 내부/외부 WIKI 배치 |
| 권한과 진입 | 사용자가 안내에 따라 시작하는 명령, 인증/신뢰/권한 선택, 저장 후 재사용, 필요한 재시작. 시험 실행기의 넓은 권한을 사용자 권한으로 간주하지 않음 |
| 제한과 기본값 | 실제 적용되는 출력, 파일/탐색 범위, 시간 제한과 설정 주체. 값, 단위, 출처, 기본값/사용자 변경 여부를 확인하며 배포에 없는 작은 값을 임의로 추가하지 않음 |
| 기능별 상호작용 | 실제 사용자 요청/선택을 입력으로 정상 결과와 취소, 오류, 변경 후 재실행을 확인. 해당 기능에 필요한 경우만 재개하며 항상 같은 세션을 요구하지 않음 |
| 데이터와 판정 | 실제 사용에 맞는 자료 규모와 형식, 요청한 전체/부분 범위, 결과와 보존. 원본을 지키기 위한 독립 사본은 사용하되 읽을 양이나 완료 조건을 임의로 줄이지 않음 |

코드, 설정이나 제한이 아직 미정이면 **환경 일치 확인 전**으로 남기고 그 조건부터 정한다. 알려지지 않은 호스트 한도를 바이트/토큰 추정치로 채우거나 사용자의 전역 설정을 바꿔 시험 조건을 맞추지 않는다. 시험 뒤에는 실제 사용한 조건과 결과를 함께 남겨 같은 배포 후보의 어떤 기능이 확인됐는지 추적한다. 구현이나 조건을 바꿨다면 영향받은 실제 사용 검증을 다시 확인한다.

작은 경곗값, 오류 주입, 모의 호출은 코드의 결함을 찾는 보조 검사로 구분한다. 그런 검사에 합격해도 실제 환경과 사용 경로의 검증을 완료한 것으로 세지 않는다. 배포 조건에서 실행하지 못했거나 기능이 없으면 미검증/미구현이고, 실패가 남았으면 그대로 기록한다. 결과가 불리하다는 이유로 필요한 입력, 한도, 판정 기준을 바꿔 성공으로 만들지 않는다.

### 사용자 환경의 변경과 호환성

11/18 사용자 재확인: 시험 당시의 Codex 버전과 관측한 제한값은 재현을 위한 기록이다. 이를 모든 사용자의 고정 버전이나 제품 상수로 옮기지 않는다. 제품은 사용자가 설치한 실행본과 선택한 모델/설정을 사용하며, 설치본이 갱신되면 다음 실행에서 현재 설치본을 확인한다. 이미 실행 중인 프로세스를 임의로 교체하거나 자동으로 업그레이드/다운그레이드하지 않는다.

출력 제한은 버전 번호 하나로 정하지 않는다. 해당 실행에서 확인 가능한 모델, 적용 설정과 도구 계약을 함께 대조하고 값의 출처, 단위와 적용 범위를 구분한다. 캐시나 디스크 설정만 읽었다고 현재 세션의 유효 한도를 모두 안다고 가정하지 않는다. 조회되지 않은 값은 미확인으로 두며 과거 숫자나 바이트 환산으로 채우지 않는다. 모듈이 배포하는 SDK 의존성의 재현 가능한 관리와 사용자의 Codex 버전 고정은 별개다.

설치본, 모델 또는 관련 설정의 변경이 실제 반영된 경계에서 영향받는 연결/반환 조건을 다시 확인한다. 이전 예산으로 계산한 완료 판단은 그대로 재사용하지 않되 요청한 원문 범위는 유지한다. 조회 수단과 변경 감지의 구현은 아직이며 매 도구 호출마다 전체 설정 조회나 모델 호출을 추가하는 결정은 아니다. 필요한 기능의 지원이나 수신 완전성을 확인할 수 없으면 그 기능의 미확인/미완료와 대응을 알린다. 무관한 정상 작업까지 차단하거나 사용자 전역 설정을 고쳐 해결하지 않는다.

검증에는 같은 버전의 다른 모델/설정, 설치본 업데이트 후 다음 실행, 조회 불가와 필요한 기능 미지원도 포함한다. 비교 실험 한 묶음의 조건을 맞추는 것과 배포 사용자 환경을 고정하는 것은 다르다. 확인된 지원 조합과 한계를 보고하며 아직 검증하지 않은 미래 버전까지 자동 호환을 보장하지 않는다.

## 현재 구조와 확인된 문제

현재의 의도는 메인이 필요한 gate를 선택하고 script가 검증을 실행하며, 실패 수정 뒤 영향받은 선행 PASS와 원래 실패 검증만 다시 실행하는 것이다. 자동화 전체를 늘리는 것이 현재 설계의 목표는 아니다.

| 현재 요소 | 실제 동작 | 확인된 한계 |
| --- | --- | --- |
| [기준 구현의 관측 (구현 검증 script)](../../discussions/architecture/baseline-audit.md) | scope로 Gradle floor를 계산하고 `--run`이면 구체 명령으로 확장한다. | 계획의 floor와 실제 argv가 다를 수 있다. boot는 실제로 9개 include selector를 사용한다. |
| [기준 구현의 관측 (gate 공통 처리)](../../discussions/architecture/baseline-audit.md) | gate, 판정, scope/의존 fingerprint와 일부 파일, pattern을 state에 기록한다. | 최초 실제 명령, 선택 조건, 작업/workspace 식별이 없다. 기록한 입력만으로 전체 영향 범위를 보장하지 못한다. |
| [기준 구현의 관측 (retry script)](../../discussions/architecture/baseline-audit.md) | 실패 gate, change-kind를 읽고 새 scope로 해당 gate를 재호출한다. | API 실패를 core-only retry PASS로 끝내는 E-012 반례가 있다. 선행 PASS도 자신의 최초 계획 대신 새 scope로 재실행된다. |
| PASS 영향 판정 | 등록된 의존 파일 해시와 pattern을 비교한다. | gradlew 변경, core 변경에도 API PASS가 REUSED인 E-005 반례가 있다. |
| 계획, 비활성, 실행 결과 | 계획 JSON, 비활성, 실제 성공에 PASS가 사용된다. | 기계 소비자가 PASS만 읽으면 실행 사실을 확정할 수 없다. 빈 배열, 전체 테스트 boolean 불일치도 관측됐다. |
| 결과 저장 | 최초 실패는 보존하고 retry는 `.retry`에 기록한다. | 두 번째 이후 retry는 같은 경로를 덮어쓸 수 있다. 다른 검사도 gate/change-kind만 같으면 같은 것으로 취급하는 분기가 있다. |
| 검사 대상 선택 | 바뀐 모듈의 task를 floor로 제안하고 충분성 판단은 메인에 남긴다. | core의 소비 모듈 검사까지 자동 포함한다는 보장은 없다. 정적 설계 공백이며 실제 제품 회귀 누락을 재현한 것은 아니다. |

E-005, E-007, E-012의 원시 근거는 [문제 대장](../../evidence/issues.md)과 [관측 기록 (2026-10-26 실행 메타데이터)](../../evidence/experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)를 본다. stub 기반 script 반례이며 실제 제품 테스트, 모델의 오판률은 아니다. 이번 설계 중 이를 다시 실행하거나 수정하지 않았다.

| 테스트, fixture만 변경 | `verification-only`여도 구현 경로의 모듈 floor로 계산 | 자동으로 특정 테스트만 실행하는 구현은 아님. 해당 검사와 공유 fixture의 소비 범위를 별도 확인해야 함 |
| wrapper 설정, 추가 검사 도구 | 현재 후보 패턴은 루트 `build.gradle`, `settings.gradle`, `gradlew` 등을 명시 | `gradle/wrapper/gradle-wrapper.properties`, CI, 하네스 script의 검증을 이 경로 판별 하나에 맡길 수 없음. 메인의 별도 판단이 필요 |
| CI | `.github/workflows/ci.yml`의 `./gradlew --no-daemon clean test`; 계약 검사, Compose, 빌드도 별도 단계 | Java 17, wrapper 8.14.3 선언과 외부 contract/private package 의존을 확인. 실제 자격증명, 서비스 접근, CI 성공은 미확인 |

boot의 확인된 로컬 제외는 `org.example.api.resource.ResourceLifecycleTest` 하나다. 현재 스크립트는 제외 필터 대신 포함 목록을 쓰며, 그 목록의 `org.example.boot.SchemaIntegrationTest`는 실제 소스의 `org.example.schema.SchemaIntegrationTest`와 다르다. 고정한 이름 9개 중 소스와 일치하는 이름은 8개다.

[기준 구현의 관측 (실행 목록)](../../discussions/architecture/baseline-audit.md)과 [기준 구현의 관측 (실제 선언)](../../discussions/architecture/baseline-audit.md)을 대조했다.

실행 시 발견, 보고서, 종료 상태는 아직 확인하지 않았고, 이 문서 작업에서 제품 파일을 고치거나 제외 사유를 바꾸지 않았다.

공통 테스트 설정에도 private BOM 의존이 있으므로 boot 테스트 하나의 제외만으로 모든 모듈의 실행 준비가 끝났다고 보장할 수 없다. 기존 승인 예외는 유지하되 실행 환경 미준비와 코드 실패를 구별한다. CI에 같은 제외를 추가하거나 없는 테스트를 성공으로 간주하는 것은 이 설계의 결론이 아니다.

### 공통 모듈의 검증 범위 후보

대상 프로젝트의 실제 명령, 계약, 기존 검사 도구에서 범위를 정한다. 공통 모듈은 `sample-*`나 고정 테스트 이름 대신 검사 목적, 선택 범위, 환경, 예외, 현재 결과를 연결한다. 하네스 자체의 검증과 하네스를 설치한 앱의 검증도 구별한다.

| 변경 유형 | 개발 중 먼저 확인할 범위 | 완료, CI에서 확인할 조건 |
| --- | --- | --- |
| 표현, 링크, 일반 설명만 수정 | 바뀐 문서와 참조. 체계/규칙 변경이면 관련 문서 정합성까지 | 제품 검증을 자동 강제하지 않음. 계약 의미가 바뀌면 아래 행으로 재분류 |
| 코드 동작, 외부 계약 변경 | 변경 동작, 경계값, 버그 재현에 대응하는 검사. 기존 테스트로 충분한지부터 확인 | 연결된 소비 기능과 프로젝트가 정한 완료 검사. 로컬/CI 분담 원칙은 ADR 0005에 채택 |
| 테스트, fixture 변경 | 바뀐 테스트와 공유 데이터의 소비 검사 | 제품 코드가 같아도 기대 결과를 약화하거나 실제 검사를 없애지 않았는지 확인. 무관한 전체 검사는 자동 강제하지 않음 |
| WIKI 생성, 역할/라우팅 변경 | 필요한 문서에 도달하는지, 근거와 사실/추정, 누락, 기존 편집의 보존 | 링크 검사와 의미 검토를 함께 수행. 본문 길이나 링크 정상만으로 상세 복원을 완료 처리하지 않음 |
| skill, script, config, hook, 검사 계획 변경 | 변경한 진입/입출력, 잘못된 입력, 이전 기능과 연결 | 지원하는 실제 CLI에서 발견, 호출, 결과 소비를 확인. script 단위 성공을 native 이벤트 성공으로 대체하지 않음 |
| 설치, 기능 추가, 갱신, 복원, 제거 | 별도 작업 공간의 허용 변경, 보호 자료, 충돌, 실패 단위 | README와 실제 배포 후보로 기존/빈 프로젝트, 내부/외부 WIKI를 확인. [보존 조건 — 「적용 단위와 부분 완료」](../runtime/update.md) 적용 |
| 상태 저장, 재개, 문맥 압축 | 저장 입력, 부분 기록, 다른 작업 혼입, 후속 편집 | 실제 재개와 이벤트, 중단 후 대조 필요. 적용 경계, 논리 계약은 state, 정확한 수단은 파일별 명세에서 연결 |
| 앱/WIKI PR 연계 | 로컬 버전 연결, 상태 해석, 중복/실패 처리 | 실제 권한, 두 PR, CI, 한쪽 완료/실패, 비공개 정보 보존. [원격 범위 — 「첫 배포의 PR 연계 후보」](../sync.md)의 제품 실증 전에는 모의 결과만으로 통과 처리하지 않음 |

첫 선택 기능인 설명/학습 문서 확장은 문서, 라우팅 행을 따른다. 커밋 보조, 다른 provider, 로컬 AI, 실제 병렬 작업은 채택한 첫 범위 밖이므로 이 표를 근거로 실행하지 않는다. 기존 사용자의 필수 검사, 추적/권한 정책도 임의 교체하지 않는다.

### 실행 시점과 실패 뒤 확인

현재 `implementation-check`는 진행 중 최소 검사와 검증 대기 시 최종 검사를 구분하지만, 테스트 작성 전용 skill은 아니다. **테스트를 작성할 필요, 무엇을 실행할지, 어느 시점에 실행할지는 서로 다른 판단**이다. 작성 필요성과 별도 skill 여부는 [테스트 작성 절차](verification.md#%ED%85%8C%EC%8A%A4%ED%8A%B8%20%EC%9E%91%EC%84%B1%20%EC%A0%88%EC%B0%A8)에서 비교한다.

11/11 채택한 흐름은 **관련 로컬 검사 → 영향에 따른 보완/확대 → CI의 필수 회귀 검사**다. 수정한 테스트 파일만 고르는 뜻이 아니며 영향받는 기존 테스트와 소비 기능을 포함한다. 로컬 완료와 전체 완료를 구분하고, 사전 배정한 CI 검사를 기다리는 상태와 검사 실패를 구별한다. 실행 시점, 확대 조건, 대안은 [ADR 0005 — 「로컬 완료와 CI의 분담」](../../decisions/workflow/0005-verification-selection.md)가 소유한다. 유효한 로컬 근거의 반복 여부는 ADR 0002에서 별도로 정하며 로컬 성공으로 필수 CI를 생략하지 않는다.

실패 후에는 원래 검사, 선택 조건을 유지하고, 수정으로 영향받은 검사와 추가 검사를 함께 대조한다. 예를 들어 API FAIL 뒤 core를 고치면 core만 확인해 종료하지 않고 원래 API 검사도 현재 코드에서 확인한다. 선택 범위, 예외, 도구 변경이 필요하면 새 판단을 합의하고 기존 미해결을 보존한다. 계획/시도와 실행, 제외, 미실행의 구별은 ADR 0001, 0003의 채택 원칙에 연결한다. 재사용 정책과 실제 명령, 보고서/입력 대응의 상세는 후속이며 G-01~G-10 전체를 일괄 채택한 것은 아니다.

### 실행 반복과 토큰 비용

11/11 사용자가 구현, 테스트 작성 중 실행 시점/범위, 중복, 누락, 토큰 비용을 실무 근거로 다시 확인해 달라고 요청했다. 이 보충 이후 ADR 0001, 0003 B의 기록/판정과 ADR 0002 C의 재사용 원칙을 채택했다. 아래 중복 식별, 출력 방식의 정확한 구현 수단은 계속 **협의안**이다.

**일반 테스트의 계산 비용과 AI가 처리하는 토큰은 다르다.** 모델을 호출하지 않는 테스트의 CPU, 메모리, 대기 시간이 곧 LLM 토큰은 아니다. 하지만 에이전트의 호출 판단, 도구 요청, 반환된 로그, 오류 해석, 수정/재시도는 문맥과 사용량에 영향을 준다. OpenAI Docs도 파일, 지침, 대화와 함께 도구 출력을 문맥으로 설명한다. 테스트가 LLM/API를 직접 호출한다면 그 비용도 별도다. 실행 횟수나 로그 바이트만으로 구독 한도 차감량을 계산하지 않는다. [Codex 용어 안내](https://learn.chatgpt.com/docs/glossary).

하네스의 실제 Codex 호출, skill/재개 시험은 모델을 사용할 수 있으므로 일반 파싱, 기록 처리의 단위 검사와 구분해 실행 조건, 예산을 정한다. 토큰을 줄이려고 필요한 실제 사용 검증을 모의 검사로 대체하지 않는다. 실제 연결의 완료 조건은 [수용 기준](../../verification/acceptance.md)이 소유한다.

공개된 프로젝트의 실제 지침과 도구 기능은 다음과 같다. 회사 전체의 사용 비율이나 우리 환경에서의 절감률을 입증하는 자료는 아니다.

| 근거 | 확인한 방식 | 적용할 점 |
| --- | --- | --- |
| [Next.js AGENTS](https://github.com/vercel/next.js/blob/canary/AGENTS.md) | 로그 검색 조건을 바꾸려고 같은 테스트를 다시 실행하지 않고, 한 번 저장한 출력을 검색하도록 안내. 개별 파일, 패턴 실행도 제공 | 출력 분석과 테스트 실행을 분리. 예시의 Bash 명령, 임시 경로를 Windows 제품에 그대로 복사하지 않음 |
| [GitLab pipelines](https://docs.gitlab.com/development/pipelines/)와 [testing strategy](https://docs.gitlab.com/development/testing_guide/testing_strategy/) | 관련 테스트를 선택하고 공통 설정, 의존성 변경 등의 경우 확대. 단계별 CI 범위와 기존 테스트 대조를 명시 | 수정한 테스트 파일만 확인하지 않고 소비 관계, 확대 조건을 함께 판단. GitLab의 예측 도구, 파이프라인 전체를 도입하는 결정은 아님 |
| [Gradle Build Cache](https://docs.gradle.org/current/userguide/build_cache.html) | 선언된 입력/출력에 기반한 재사용. 누락 입력은 잘못된 캐시 적중을 일으킬 수 있음 | 검증된 도구 기능 활용과 하네스 자체 캐시를 구별. 같은 명령, HEAD만으로 결과 유효성을 단정하지 않음 |
| [Anthropic 도구 설계](https://www.anthropic.com/research/writing-tools-for-agents) | 관련성이 높은 응답, 로그 검색, 필터/범위 조회를 권고하며 도구 호출 수, 시간, 토큰, 오류를 함께 평가 | 결정적 코드로 필요한 결과를 추려 반환. 긴 로그를 줄이려고 별도 AI 요약 호출을 기본 추가하지 않음 |

실행 시점은 파일 저장 횟수보다 **검증 가능한 변경 단위와 새 근거의 필요성**을 기준으로 정한다.

| 시점 | 실행, 대조할 범위 |
| --- | --- |
| 변경 시작 | 버그 재현, 전후 비교가 필요한 경우 해당 동작을 좁게 확인. 모든 작업의 시작에 전체 검사를 강제하지 않음 |
| 구현, 테스트 작성 중 | 연관 수정이 실행 가능한 단위가 됐을 때 관련 사례를 확인. 파일 하나, assertion 하나를 고칠 때마다 전체 묶음을 실행하지 않음 |
| 실패 분석 | 해당 시도의 저장된 근거에서 실패 이름, 원인 주변, 선택/실행 정보를 조회. 출력 형식만 바꾸려고 다시 실행하지 않음 |
| 원인 수정 후 | 원래 실패한 검사와 수정 영향으로 필요한 검사를 실행. 바뀌지 않은 실패를 근거 없이 성공할 때까지 반복하지 않음 |
| 로컬 완료, PR 준비 | 현재 변경에 필요한 의무와 확보한 근거를 대조하고 부족하거나 무효화된 범위를 보완. 단계 이름만 바뀌었다고 동일 검사를 의무적으로 반복하지 않음 |
| 필수 CI | 프로젝트의 공유 검증 환경, 검토 버전에서 정한 검사 수행. 로컬 성공을 CI 생략 근거로 사용하지 않음 |

작성 과정의 빠른 검사도 같은 공통 검증 경로에 연결한다. 작성 skill, 구현 skill, 완료 확인이 각자 같은 명령을 독립 호출하지 않도록 **실행 책임과 해당 작업의 결과 소비를 한곳으로 모으는 안**을 추천한다. 새 서비스나 중앙 scheduler를 요구하지 않는다. 같은 작업, 계획, 입력, 실행 조건의 중복 요청은 합치거나 진행 중인 실행을 확인하되, 입력이 바뀌었거나 대응을 확인할 수 없으면 같은 실행으로 취급하지 않는다. 구체 중복 식별, 저장은 계획/결과 계약 이후 명세한다.

여기서 세 가지를 구분한다. 저장된 로그를 다시 읽는 것은 재실행이 아니다. 현재 작업에서 이미 충족한 검사를 완료 보고 때문에 다시 요구하지 않는 것은 중복 의무 정리다. **이후 변경된 입력에 과거 PASS를 적용해 실행기 호출을 생략하는 것은 별도의 재사용 판단**이다. 마지막 기능을 임의의 캐시로 구현하지 않는 ADR 0002 C를 채택했다. 현재 입력, 환경과 대응을 확인하지 못하면 필요한 task를 호출하고 검증된 도구의 증분 기능을 쓰거나 새로 검사한다.

AI에 반환할 내용은 실제 검사/선택 범위, 성공, 실패, 미실행/재사용 요약, 남은 필수 의무, 관련 보고서 위치와 필요한 오류 부분으로 제한하는 안이다. 비밀값을 제외한 근거는 로컬 상태 영역에 남기고 추가 조회할 수 있게 한다. 파싱 실패, 출력 잘림을 숨기거나 `tail`의 짧은 출력만으로 PASS를 만들지 않는다. 요약/검색 명령의 성공이 원래 테스트 종료 코드를 덮지 않게 하며, 장시간 실행에서는 같은 출력을 반복 반환하는 조회도 줄인다. 정확한 출력 한도, 형식은 실제 사용 검증에서 정한다.

평가는 동일한 작업, 검사 의무에서 실행 요청 수/실제 시작 수, 테스트 본문 실행/도구 재사용, 전체 시간, 모델이 받은 출력, 실제 사용량, 원래 실패 보존, 누락, 재작업을 함께 비교한다. 수정 뒤 필요한 재실행과 CI의 독립 검증을 낭비로 세지 않는다. 출력이 작아도 실패 원인이 누락돼 재실행, 재질문이 늘면 개선으로 판정하지 않는다. 현재 이 비교를 실행하지 않았으며 실제 절감률은 미측정이다.

로컬 AI로 추가 절감할 수 있는지는 [검증 비용을 줄이는 로컬 보조](../integration/local-ai.md)에서 공개 사례, 동작, 한계를 비교했다. 후보는 코드가 보존한 실패 사실에 대한 제한된 해석 보조이며, 검사 실행, 필수 범위, 완료 판단을 로컬에 넘기는 안이 아니다. 로그 분석의 효과를 테스트 생성이나 WIKI 상세 복원의 품질로 확대하지 않는다. ADR 0006의 연결 흐름은 검증 전제로 수용됐지만 실험, 최종 도입은 아직이며, 기록 B, 재사용 C의 채택과 별개다.

### 원문 수신과 답변의 완전성

WIKI의 사실, 정책이나 결정 이유를 답하는 작업에서는 **필요한 근거 확보와 최종 답변의 의미**를 구별해 확인한다. MCP/직접 파일 접근에 같은 기준을 적용하며 단순 인사나 문서가 필요 없는 Direct 요청에 새 게이트, DB 기록이나 별도 검증 모델을 추가하지 않는다. 기존 작업의 범위/검토 책임 안에서 필요한 확인만 수행한다.

| 확인할 것 | 완료를 판단할 근거 |
| --- | --- |
| 필요한 주장과 범위 | 질문별 현재 정책, 적용 대상, 예외/제외, 상태와 결정 근거를 구별. 관련 절/ADR의 연결을 따라가며 검색어 하나로 충분성을 단정하지 않음 |
| 실제 수신한 원문 | 경로와 revision/반환 구간을 대조. 호출/서버 실행 성공, 검색 발췌, 잘린 본문을 해당 절 전체를 읽은 근거로 쓰지 않음 |
| 답변에 반영된 의미 | 확보한 원문의 필수 조건과 답변을 대조. 예외 누락, 과거안/현재안 혼합, 문서 정책을 구현/테스트 완료로 확대하는 오류 확인 |
| 인용과 부재 판단 | 인용 구간 안에 해당 근거가 있고 실제로 수신했는지 확인. 못 찾은 경우 검색한 범위/방법의 한계를 알리며 전역 부재나 임의 수치를 만들지 않음 |

예를 들어 “5분 이내 문서 복구”와 “영구 삭제된 문서는 제외”가 같은 기준에 있으면 답에도 둘의 관계가 드러나야 한다. 후자를 읽지 못했으면 필요한 부분을 더 읽고, 이미 읽었다면 답변을 보완한다. 같은 원문을 다시 받는 것만으로 해결됐다고 판단하지 않는다. 자동 검사는 경로/구간/해시/형식의 대응을 확인할 수 있지만 조건의 의미와 충분성은 그것만으로 증명할 수 없다.

이는 [11/18 두 답변의 누락 관측](../../evidence/experiments/wiki-access/2026-11-18_16-50-18-codex-wiki-usage.md)에 대응하는 기존 의미 검토의 구체화다. 회귀 평가에서는 모델 실행 전에 정한 필수 사실, 금지 추론과 원문을 평가자가 대조하고 자기 평가/문자열 일치만으로 합격시키지 않는다. 정답표는 시험 모델 입력에서 제외한다. 실제 작업에는 미리 정답이 없으므로 불확실한 근거를 표시하고 관련 내용을 확인하며 같은 수준의 무오류 보장을 주장하지 않는다.

필수 근거가 미수신이거나 답변에서 빠졌으면 완전 품질 PASS로 표시하지 않는다. 부분 결과와 남은 의무는 기존 [입력과 실행 결과의 판정](verification.md#%EC%9E%85%EB%A0%A5%EA%B3%BC%20%EC%8B%A4%ED%96%89%20%EA%B2%B0%EA%B3%BC%EC%9D%98%20%ED%8C%90%EC%A0%95)에 연결한다. 장기 작업의 이어갈 위치가 실제로 바뀌면 기존 복구 기록을 사용하되 검색/읽기 호출마다 active/DB를 갱신하지 않는다. 도구 반환/오류 계약은 [MCP 읽기 보완 — 「MCP 읽기의 남은 보완」](../runtime/entry.md)이 소유한다.

## 테스트 작성 절차

테스트 품질 요구와 실행 정책은 이미 정해져 있다. [프로필의 테스트 작성 품질](../../development/standards.md)은 필요한 정상, 경계, 제한, 오류, 검증 사례를 꼼꼼히 다루라는 사용자 요구이고, ADR 0005는 관련 로컬 검사, 조건부 확대, 필수 CI 분담을 채택한 기록이다. 아래 비교를 이유로 이 두 기준을 다시 승인받지 않는다.

11/11 **짧은 진입 규칙 + 지침 중심의 조건부 테스트 작성 skill + 공통 검증** 배치를 채택했다. 사용자는 선택적으로 필요한 절차만 읽는 기존 조건부 하네스와의 연결, 위험 대응을 요구했고, 현재 AGENTS와 mode/gate의 구체 구조는 후속 설계에서 변경할 수 있음을 확인했다. 아래 연결 명세는 초안이며 실제 skill, 라우팅, 효과는 구현과 검증 모두 미완료다. 현재 기존 시험 프로젝트의 `implementation-check`는 검사 선택, Gradle 실행, 결과 반환을 담당한다. 이를 읽은 것은 현행 조사이며 제품 검사나 skill 변경을 실행한 것이 아니다.

2026-11-11 사용자 요청으로 기업 소유 공개 저장소 6개와 Anthropic의 공식 skill 예시를 확인했다. 아래는 공개된 파일에 명시된 배치이며 회사 전체의 내부 표준, 사용 비율, 성능 비교를 입증하지 않는다. 링크의 `main`, `canary`는 변경될 수 있고, 해당 저장소의 지침을 이 작업의 실행 명령으로 적용하지 않았다.

관측에서 도출한 해석은 **기본 규칙, 상세 작성 지침, 실행 도구의 책임을 구분하고 필요한 연결을 명시한다**는 것이다. skill 또는 AGENTS 한 종류로 통일하는 업계 표준은 이 자료들로 확인되지 않는다. skill 파일의 존재만으로 누락률, 품질, 토큰 절감 효과가 검증됐다고 할 수도 없다.

배치와 내용은 따로 평가한다. 예를 들어 Warden에는 낮은 가치의 엣지 사례를 줄이려는 지침이 있으나, 이를 우리의 중요한 경계, 실패, 보존 사례 생략 근거로 쓰지 않는다. 특정 프레임워크, 통합 테스트 우선 정책, 파일 이름도 적용 프로젝트의 계약과 대조한다. VS Code의 `applyTo`는 해당 도구의 [파일별 지침 기능](https://code.visualstudio.com/docs/agent-customization/custom-instructions)이며, 그 파일을 Codex 설치본에 복사하기만 하면 자동 적용된다고 가정하지 않는다.

### 절차를 둘 위치

채택한 배치는 **짧은 진입 규칙에서 필요한 작업에 작성 skill을 연결하는 방식**이다. 일반 문서 참조는 비교한 대안으로 남긴다. `AGENTS.md`와 skill은 함께 사용하며 별도 에이전트나 테스트 생성 서비스를 추가하지 않는다.

| 안 | 동작 | 장점 | 부담, 한계 |
| --- | --- | --- | --- |
| 기존 개발 흐름 + 조건부 지침 참조 | 짧은 진입 규칙에서 관련 작성 기준으로 연결. 메인이 기존 테스트와 요구를 대조하고 필요할 때 보강한 뒤 공통 검증으로 전달 | 새 skill 등록 없이 구현/테스트 문맥과 기존 경로 규칙 활용. 상세 기준을 매번 전부 읽지 않아도 됨 | 지침으로 가는 연결을 빠뜨릴 위험. 읽기 조건과 결과 인계를 실제 사례로 검증해야 함 |
| 짧은 진입 규칙 + 조건부 테스트 작성 skill — 채택 | 기본 구성에 작성 skill을 제공하고 필요한 작업에서 같은 메인이 사용. 상세 작성 판단을 소유하고 실행은 공통 검증 절차로 전달 | 여러 프로젝트에 같은 작성 절차를 설치와 갱신하며 책임을 분명히 함. 일반 개발과 테스트만 보강하는 요청이 같은 진입점을 사용 | 발견 경로, 이름 충돌, 호출/미호출, 결과 인계 검증 필요. 기존 지침과 규칙을 복제하면 유지 비용이 증가 |

채택한 책임 분리는 아래와 같다. 작성과 실행을 같은 메인의 기존 작업에 연결하며, 현재 `implementation-check`에 모든 작성 설명을 합치지 않는다. 실제 파일, 이름, 도구별 발견 경로는 파일별 명세에서 정한다.

1. **진입 규칙:** 기능/계약의 동작 변경, 버그 수정, 테스트 작성/보강 요청에서 작성 검토가 필요한지 판단하고 해당 skill로 연결한다. 메인이 요청과 변경의 의미를 판정하며, 단순 문서 편집이나 작성 검토가 불필요함을 확인한 변경은 호출하지 않는다. 적용 프로젝트의 AGENTS 등 기존 지침을 보존한다.
2. **작성 skill:** 아래의 작성 판단, 품질 기준을 소유한다. 관련 요구, 기존 테스트를 먼저 읽고 필요한 사례만 보강한다. 기존 검사로 충분하면 새 테스트를 강제하지 않는다. 공통 절차에 프레임워크, 명령, fixture, 파일 위치를 하드코딩하지 않고 대상 프로젝트의 기존 기준을 따른다. 처음에는 지침 중심으로 제공하며 생성 엔진, 프레임워크별 script를 선행 구현하지 않는다.
3. **검증 연결:** 작성한 사례, 변경 파일, 남은 공백을 같은 작업의 검증 판단에 연결한다. 작성용 두 번째 실행기, 독립 상태 저장소, 별도 AI를 요구하지 않는다. 로컬/CI 실행 기준은 ADR 0005를 유지한다.

전용 skill도 같은 메인이 사용할 수 있고 지침만 담을 수도 있다. 별도 AI, 서브에이전트, 추가 모델 호출을 필수로 만드는 것은 아니다. 공식 Codex 문서는 처음에는 skill의 이름/설명 등을 보고 선택 시 본문을 읽는다고 설명한다. 조건부 문서 참조도 실제 읽은 본문은 문맥을 소비하므로, skill 유무만으로 어느 안의 토큰이 더 적다고 단정하지 않는다. [OpenAI Docs: Build skills](https://learn.chatgpt.com/docs/build-skills).

여러 프로젝트에 재사용할 작성 절차를 배포, 갱신하고 책임을 분명히 하려는 선택이다. 일반 지침 참조에서 추천을 바꾼 이유와 채택 범위는 [ADR 0005의 작성 절차 연결 — 「테스트 작성 절차의 연결」](../../decisions/workflow/0005-verification-selection.md)에 보존한다. 공개 사례의 우열이나 실측 품질 차이가 결론을 입증한 것은 아니다.

설계에 반영할 부작용과 확인 조건은 다음과 같다.

| 위험 | 처리, 검증 기준 |
| --- | --- |
| 호출 누락, 불필요한 호출 | 짧은 진입 규칙과 skill 설명의 조건을 맞춘다. 기능 변경, 회귀 보강, 기존 검사로 충분한 변경, 문서 편집에서 실제 호출/미호출을 확인. 지침만으로 무누락을 보장하지 않음 |
| 기준 중복, 프로젝트 규칙 충돌 | 진입 규칙은 연결, skill은 공통 작성 절차, 프로젝트는 도구/배치/업무 계약을 소유. 충돌하거나 기대 결과가 없으면 확인하며 기존 지침을 덮지 않음 |
| 불필요한 테스트, 범위 확대 | 누락된 중요한 동작만 보강. 단순 편집에 새 테스트나 전체 커버리지 측정을 강제하지 않음. WIKI 역공학만 요청했을 때 제품 테스트 전면 보강으로 확대하지 않음 |
| 잘못된 테스트의 통과 | 기대값을 현재 구현에서 베끼지 않고 요구, 채택 계약, 재현 근거로 판단. 테스트 수, 커버리지, 종료 0만으로 충분성을 판정하지 않음 |
| 실행/복구의 이중 관리 | 기존 검증, 실패 재시도, 재개 기록을 사용. 작성 완료를 검사 PASS로 기록하지 않으며 skill 전용 실행 상태를 추가하지 않음 |
| 토큰, 도구 종속 | 필요한 프로젝트 기준만 읽고 AGENTS에 상세 본문을 복제하지 않음. 총토큰 효과는 실제 호출, 읽기, 재작업으로 측정. 공통 절차와 도구별 발견/호출 연결을 분리하고 다른 도구의 호환성은 후속 검증 |

배치 채택 뒤에도 제품 구현은 기존 순서대로 진행한다. 아래 연결 초안을 검증 결과 계약과 맞추고, 파일별 변경 명세, 개발 준비 뒤 실제 skill을 만든다. 기술 검토 근거는 skill 파일의 수가 아니라 조건에 맞는 호출, 중요한 검사 누락 방지, 프로젝트별 기존 구조 보존과 재작업 비용의 관측이다.

### 조건부 실행과 완료 판단

현재 AGENTS의 작업 수준, 독립 gate에 연결하는 **명세 초안**이다. [조건부 구조의 변경 범위 — 「현재와 변경 후보」](../architecture.md)에 따라 이름, 개수, 구현을 고정하지 않는다. 보존할 것은 필요한 범위만 읽기, 작성/실행 필요성의 분리, 불명확한 판단과 미완료를 숨기지 않는 동작이다.

메인은 요청으로 초기 작업 수준과 필요한 절차를 판단하고, scope, 변경 내용, 새 위험이 드러나면 영향을 받은 판단만 갱신한다. 작성 skill을 사용한다는 이유로 모든 작업을 Harness로 올리거나 모든 gate를 켜지 않는다. 현재의 일반 `skill` gate에 작성 절차를 연결할 수 있으며 별도 mode나 gate 추가는 아직 결정하지 않았다.

| 상황 | 작성 절차 | 검사, 추가 읽기 |
| --- | --- | --- |
| 설명만 요청하거나 문서의 표현, 링크만 수정 | 테스트 작성 skill을 읽지 않음 | 필요한 문서 확인만. 문서 의미가 실제 계약을 바꾸는지 불명확하면 먼저 좁게 확인 |
| 동작 유지 수정이고 기존 테스트로 충분함을 확인 | 새 작성 검토를 생략할 수 있음 | 구현 검증은 별도 판단. 관련 기존 회귀 검사까지 OFF로 만들지 않음 |
| 기능/계약 변경, 버그 수정, 테스트 보강에서 사례 검토 필요 | 작성 skill을 읽고 기존 사례, 중요한 누락을 대조 | 해당 요구, 기존 테스트, 경로 기준만 읽음. skill 사용이 새 테스트 생성 의무는 아님 |
| 의미, 영향, 기대 결과를 확정할 수 없음 | 미확정을 OFF로 처리하지 않음 | 관련 근거부터 확인. 중요한 요구/정책 선택은 사용자와 협의하며 미확정 상태로 완료하지 않음 |
| 작업 도중 영향이 공통 코드, 다른 모듈로 확대됨 | 영향받은 작성 판단을 다시 확인 | 관련 소비 기능, 검사 범위를 보완. 무관한 문서, 성공한 검사까지 일괄 반복하지 않음 |

진입 규칙에 조건과 연결이 있어야 skill 본문을 읽기 전에도 선택할 수 있다. 상세 품질 규칙을 AGENTS에 복제하거나 skill을 읽기 위해 모든 요구, ADR, runbook을 먼저 열지 않는다. 같은 작업에서 읽은 지침이 바뀌지 않았다면 재독하지 않으며, 새 세션, 압축 뒤에는 현재 상태와 변경 여부를 확인한다. 이 원칙을 필요한 계약, 검사 근거까지 생략하는 허가로 해석하지 않는다.

입력은 메인이 정한 작업 목적, scope, 변경 성격과 관련 요구/테스트/프로젝트 기준이다. skill은 작업 수준 전체를 다시 판정하지 않고 새 위험만 메인에 반환한다. 산출물은 작성/보강 여부와 이유, 사례가 보호하는 동작, 근거, 변경한 테스트, 남은 공백이다. 기존 검증 계획, 결과 흐름이 이를 소비하며 테스트 작성 전용 JSON, 상태 파일, 실행기를 추가하지 않는다. 정확한 필드와 저장 형식은 ADR 0001~0003 이후에 정한다.

코드, 계약 변경의 완료 전에는 **현재 변경과 작성 판단, 선택한 검사, 실제 결과, 남은 공백**의 연결을 대조한다. “필요 없음”의 근거가 없거나 현재 scope와 맞지 않으면 필요한 판단으로 돌아간다. 이 대조는 같은 검증 절차의 완료 조건이며 모든 요청의 전체 gate 재판정이나 같은 테스트 재실행이 아니다. 필수 CI 대기, 미실행, 실패는 [ADR 0005](../../decisions/workflow/0005-verification-selection.md)의 완료 범위 구분을 유지한다.

AGENTS의 지시는 그 자체로 기계적 실행 차단 장치가 아니다. 코드가 연결 누락, 필수 결과 부재를 확인할 수 있는 부분과 AI가 요구, 사례의 충분성을 판단할 부분을 구분한다. 후자는 의미 검토가 필요하며, 형식 검사나 AI의 “확인했다”는 응답만으로 무누락을 보장하지 않는다.

구현 때는 위 표의 호출/미호출에 더해 skill 누락, 잘못된 연결, 기존 규칙 충돌, 작업 도중 scope 확대, 실패 후 재개, 문맥 압축을 실제 지원 Windows/Codex 경로에서 확인한다. 지침 발견, 필요한 문서 읽기, 검사 선택, 미완료 표시를 함께 관측하며, 구조 검사 통과만으로 실제 AI 호출 성공으로 표시하지 않는다. 불필요한 읽기, 호출과 중요한 누락, 재작업을 함께 비교한다. 토큰 절감률과 모든 입력에서의 무오류는 아직 입증하지 않았다.

### 작성 필요성과 품질 기준

1. **기대 동작 확인:** 요구, 채택 계약, 재현된 버그에서 기대 결과를 찾는다. 현재 구현이 내놓는 값을 그대로 정답으로 복사하지 않는다. 근거가 충돌하거나 기대 결과가 불명확하면 그 판단을 사용자와 확인한다.
2. **기존 검사 대조:** 해당 동작, 실패 조건을 검증하는 기존 테스트를 먼저 읽는다. 충분하면 새 테스트 없이 사용하고, 누락된 동작, 경계, 회귀만 추가/수정한다. 모든 함수, 사소한 편집에 새 테스트를 강제하지 않는다.
3. **필요한 사례 작성:** 기존 프레임워크, fixture, 명명과 격리 방식을 따른다. 이번 변경에 필요한 정상, 경계, 실패/보존 사례를 선택한다. 예상과 다른 동작이면 실패하는 assertion인지 확인하며, 통과시키려고 기존 기대값을 약화하지 않는다.
4. **실행과 결과 연결:** 작성한 파일, 검증하는 동작, 남은 공백을 같은 작업의 검증 판단에 연결한다. 실행 범위는 채택한 ADR 0005를 따르고, 실제 명령/실행/실패/미실행 기록은 후속 결과 계약을 사용한다. 테스트 작성용 별도 상태 파일이나 두 번째 실행기를 기본으로 만들지 않는다.

버그 수정에는 가능하고 허용된 환경에서 원래 결함을 잡는 회귀 사례를 확인한다. 검증되지 않은 과거 실패를 실행했다고 기록하거나 실제 사용자 데이터를 손상시켜 재현하지 않는다. 테스트가 통과해도 기대 결과의 근거, 검사 범위, 실제 실행 여부가 확인되지 않으면 요구 충족으로 확대하지 않는다. 메서드 호출 순서처럼 구현 세부를 검사할 필요가 있는 경우에도 그 순서가 보호할 계약인지 먼저 구별한다.

단순 문서 표현, 링크 수정은 문서 검사로 처리한다. 동작을 유지하는 리팩터링에는 관련 기존 회귀 검사를 사용하고 새 테스트는 확인한 공백이 있을 때만 보강한다. 설치, 복구, 외부 연계는 단위 테스트만으로 실제 사용자 환경 검증을 대신하지 않으며 [공통 검증 범위 — 「공통 모듈의 검증 범위 후보」](verification.md#%EA%B3%B5%ED%86%B5%20%EB%AA%A8%EB%93%88%EC%9D%98%20%EA%B2%80%EC%A6%9D%20%EB%B2%94%EC%9C%84%20%ED%9B%84%EB%B3%B4)를 따른다.

Google의 테스트 지침은 구현 방식보다 관찰 가능한 동작을 검증하면 변경에 덜 취약한 테스트를 만들 수 있다고 설명한다. Microsoft VS Code는 별도 작성 지침에서 프로젝트의 테스트 유형, 기존 배치, 정리 규칙을 안내한다. 이는 작성 기준을 명확히 둘 근거이며 전용 Codex skill의 필수성을 입증하는 자료는 아니다. [Google Testing Blog](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html), [VS Code 작성 지침](https://github.com/microsoft/vscode/blob/main/.github/instructions/writing-tests.instructions.md).

구현 시에는 기존 검사로 충분한 수정, 회귀 보강이 필요한 버그, 공유 fixture 변경, 문서만 수정, 기대 결과가 미정인 요청을 구분해 이 절차가 과잉 작성이나 검사 누락을 만들지 않는지 확인한다. 현재는 배치 채택과 연결 초안 작성까지이며 테스트 생성, 모델 품질, 토큰 비용을 실측하지 않았다.

### API 테스트 범위와 커버리지

11/11 사용자 요구: 테스트를 실제 작성할 때 해당 기능의 중요한 정상, 경계, 제한, 오류, 검증 상황을 꼼꼼히 다룬다. 작성 절차에 연결할 품질 조건이며 제품 테스트 구현을 앞당기는 요청은 아니다. 전용 skill의 후속 채택은 [절차를 둘 위치](verification.md#%EC%A0%88%EC%B0%A8%EB%A5%BC%20%EB%91%98%20%EC%9C%84%EC%B9%98)에서 구분한다. 모든 입력 조합의 완전 탐색, 무결점 보장은 할 수 없으므로, 다음 범위를 요구, 계약과 대조해 필요한 사례와 남은 공백을 명시하는 방식을 추천한다.

| 검토 축 | 해당 기능에서 확인할 사례 |
| --- | --- |
| 정상 동작, 응답 계약 | 주요 업무 흐름, 반환 값, 상태, 필드와 저장/외부 호출 결과. 상태 코드만 검사하고 내용, 부수 효과를 빠뜨리지 않음 |
| 입력과 경계 | 누락, null, 빈 값, 형식 오류, 최소/최대와 바로 밖의 값, 크기/페이지 제한. 서로 다른 동작을 만드는 입력군을 구분 |
| 인증, 권한 | 인증 없음/실패, 역할 차이, 다른 사용자 자원, 변경 금지 필드 접근. 적용되는 정책을 근거로 판정 |
| 업무 규칙, 상태 전이 | 없는/삭제된 자원, 중복, 허용되지 않는 상태, 선행 조건 위반, 실패 후 기존 데이터 보존 |
| 동시성, 재시도 | 관련 기능의 중복 요청, 멱등성, 경합, 오래된 상태, 부분 반영/롤백. 시간 지연만으로 성공을 추측하지 않음 |
| 외부 의존 실패 | DB, 외부 API의 오류/응답 지연, 연결 끊김, 합의된 재시도, 오류 변환, 복구. 실제 운영 자원에 장애를 주지 않음 |
| 격리, 운영 조건 | 실행 순서와 무관한 재현, 테스트 데이터 정리, 적용되는 자원 제한, 민감 정보 비노출. 부하 시험은 필요한 계약과 실행 조건을 별도로 정함 |

표는 이 프로젝트를 위한 검토안이다. 모든 API에 모든 사례를 기계적으로 복사하지 않으며 해당 없음의 이유와 중요 미검증 범위를 구별한다. 기대 오류, 권한, 재시도 정책이 비어 있으면 구현에서 임의로 정답을 만들어 테스트하지 않는다. 위험한 조합은 추가하되 입력군, 경계값, 파라미터화로 같은 의미의 반복을 줄인다. 인증, 자원 권한, 자원 소모 위험은 [OWASP API Security](https://api-security.owasp.org/editions/2023/en/0x11-t10/)도 별도로 다룬다.

API당 테스트 개수나 모든 회사에 적용되는 커버리지 합격선은 이번 조사로 확인하지 못했다. Google의 2020년 공개 지침은 60, 75, 90%를 참고 수준으로 제시하면서도 제품별 위험과 필요에 따라 목표를 정하고 획일적으로 강제하지 말라고 설명한다. 수치만 높이는 중복 검사보다 미검사 동작과 assertion의 의미를 검토한다. [Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html?hl=it_IT).

추천은 **요구/실패 조건의 누락 검토 + 라인, 분기 커버리지의 공백 확인**이다. 커버리지는 실행하지 않은 부분을 찾는 보조 근거이며 결과의 정확성, 동시성, 입력 조합을 보장하지 않는다. 실제 도구와 기존 측정값을 확인한 뒤 목표 범위, 제외 사유, 임계값을 협의하고, 지금 80/90/100% 같은 필수 수치나 새 도구 도입을 확정하지 않는다. 테스트가 부족한 기존 프로젝트 전체를 한 번에 재작성하는 범위로도 확대하지 않는다.

### 테스트 위치와 분리

적용 프로젝트의 프레임워크, 기존 소스 배치, 실제 실행기가 발견하는 테스트 이름을 우선한다. Java/Gradle의 기본 `src/test/java`, `src/test/resources`와 현재 기존 시험 프로젝트의 모듈별 배치는 일치한다. 소유 기능의 패키지 아래에서 동작별로 묶고, 단위, HTTP 계약, DB/여러 계층 통합처럼 의존 환경과 책임이 다르면 분리하는 안을 추천한다. [Gradle Java project layout](https://docs.gradle.org/current/userguide/java_plugin.html#sec:java_project_layout).

현재는 API에 컨트롤러/검증 관련 테스트, infrastructure에 서비스 관련 테스트, boot에 애플리케이션 통합 테스트가 있다. 이 관측을 배포 모듈의 고정 Java 디렉토리나 모든 프로젝트의 계층 규칙으로 복사하지 않는다. 새로운 Python 모듈의 테스트 배치는 해당 도구와 파일별 명세에서 정한다.

하나의 API를 거대한 테스트 파일 하나에 모두 넣거나 사례마다 파일을 만들지 않는다. 같은 준비, 같은 책임의 입력 변형은 파라미터화할 수 있고, fixture는 필요한 가장 좁은 범위에서 공유한다. DB 제약, 트랜잭션, 경합을 mock 단위 테스트만으로 검증했다고 하지 않으며, 핵심 사용자 흐름에는 필요한 통합 검사를 연결한다. 분리한 테스트가 로컬과 CI에서 실제 발견되는지 확인하고 파일 수, 줄 수를 임의 분리 기준으로 강제하지 않는다. 이 상세안의 위치, 형식과 실행 효과는 구현과 검증 모두 미완료다.

## before / 추천 after

| 책임 | 현재 | 추천 후보 |
| --- | --- | --- |
| 게이트, 의미 판단 | 메인이 조건부 활성화 | 메인 유지. 모든 요청에 전체 파이프라인을 강제하지 않음 |
| 구체 검사 선택 | 프로젝트 이름이 내장된 script와 별도 matrix | 프로젝트 원본/정책을 해석한 검사 목록을 연결부가 제공 |
| 계획, 재시도 | gate+새 scope로 다시 계산 | 실제 검사 명세 보존, 수정 입력과 추가 검사 별도 처리 |
| 실행, 판정 | 요약 floor, exit, state 중심 | 실제 argv, 선택, 도구 결과, 보고서 대응 확인 |
| 재사용 | 등록된 파일/pattern으로 실행 생략 | 초기 자체 캐시 보류. 조건을 확인한 빌드 도구 재사용 또는 새 검사 |
| 완료 범위 | 최소 floor와 메인의 충분성 판단 | 관련 로컬 검사, 확대 조건, 필수 CI를 명시하고 각각의 완료 근거 확인 |

흐름은 `메인 판단 → 프로젝트 정보 해석 → 검사 계획 → 실행/재시도 기록 → 필수 근거 대조 → 메인 완료 판단`이다. 이는 논리적 책임 구분이며 새 서버나 여섯 개의 agent를 만드는 제안이 아니다.

```text
현재
API 검증 FAIL
  → core 수정 scope 전달
  → 같은 gate가 core 테스트를 새로 선택
  → core PASS로 retry 성공 (API FAIL은 여전히 재현됨)

추천 후보
API 검증 계획 P1 → 실행 A1 FAIL
  → core 수정은 영향 분석, 추가 검사 입력으로 사용
  → 필요하면 core 검증 P2 추가
  → 수정된 현재 코드에서 P1의 API 검증 재실행 A2
  → P1과 추가 필수 검증이 모두 충족돼야 완료 후보
```

**보존하는 것은 검사 대상과 조건이지 과거의 실패 코드가 아니다.** 코드 수정은 각 실행의 입력을 바꾼다. 검사 선택, 예외, 도구가 바뀌면 후속 계획으로 관계를 남겨야 한다.

### 복구 계약으로 넘길 입력

복구의 상세 소유 문서는 [작업 상태와 복구 — 「복구의 대상과 경계」](recovery.md)다. 11/12에는 세션 문맥, 설치/갱신, 개별 기능 재개의 경계를 확인했다. 현재 문맥과 결과가 명확한 검사 FAIL은 기존 수정, 재검증으로 이어가고, 중단 또는 실행 효과가 미확인일 때 해당 시도만 대조한다. 검증 기록을 복구용으로 다시 복제하지 않는다.

설정 조회와 시작/재개의 결과는 [진입 결과의 소비 — 「결과를 받는 절차」](../runtime/entry.md)에 연결한다. 준비 부족으로 실행하지 못한 검사도 원래 계획의 의무를 유지한다. 실제 실행 전이라는 근거가 분명하면 준비를 보완해 그 검사부터 진행하고, 이미 시작했을 가능성이 있으면 해당 시도를 먼저 대조한다. 연결 확인 성공으로 기존 FAIL이나 종료 미확인을 해소하지 않는다.

- **복구 설계:** 의미 상태, 실행 근거, 저장 시점, 손상/늦은 작성, 재개 대조의 논리 계약과 Windows 시험 명세를 작성했다. SQLite, 자동 보존/명시적 정리는 채택됐으며 구현, 실증은 아직이다.
- **파일별 명세:** 식별자, 정확한 필드/상태 표현, 명령, 파일 배치, 연결부 결과 해석, 기존 자료 이전을 정한다. 채택한 저장 원칙 안에서 정확한 필드, 저장/잠금 수단을 연결하고, 보장 범위를 바꾸는 선택만 다시 협의한다.
- **개발 준비, 검증:** 지원 Windows 도구 버전, 원래 실패 재현, 도구 재사용, 실제 hook/재개, 외부 WIKI, 필수 CI를 확인할 실행 조건과 독립 기대 결과를 고정한다. 현재 준비된 clone이 제품 검증을 통과했다는 뜻은 아니다.

새로운 정책 선택이 발견되면 그 항목만 협의한다. 이미 채택한 원래 실패 보존, 기록 구분, 재사용, 로컬/CI 기준을 다시 승인받거나, 세부 저장 명세가 미정이라는 이유로 채택한 원칙을 재논의하지 않는다.

| --- | --- | --- |
| 최초 검증을 어떻게 보존할까 | A 기존 state 국소 보강 / B 계획+별도 실행 기록 / C workflow 엔진 | **11/11 B 기록 원칙 채택**. 재시도 대상과 수정 입력을 직접 구별한다. 정확한 gate/저장 구현은 후속. [ADR 0001](../../decisions/workflow/0001-verification-identity.md) |
| PASS 재사용을 누가 판단할까 | A 매번 새 검사 / B 하네스의 전체 의존 fingerprint / C 실행기 호출+검증된 도구 재사용 | **11/11 C 원칙 채택**. 현재 의무의 중복을 줄이고 초기 자체 캐시는 보류한다. 입력 불명, 실패 복구는 새 검사를 요구한다. [ADR 0002](../../decisions/workflow/0002-pass-validity.md) |

| 프로젝트 차이를 어떻게 수용할까 | A 수동 설정/템플릿 / B 분석+보정+공통 코어/연결부 / C 프로젝트별 실행 코드 생성 | **B**. 원본과 파생 정보를 나누고 공통 로직의 복제를 줄인다. 초기 명시 설정은 분석기 개발의 기반이다. [ADR 0004](../../decisions/architecture/0004-portability.md) |

각 ADR에 쉬운 설명, 장단점, 추천 이유, 감수할 비용을 남겼다. 새로운 서버, provider 추상화, 언어 변경을 이번 선택의 전제로 두지 않는다.

## 계획과 결과의 연결

11/11 사용자가 [ADR 0001](../../decisions/workflow/0001-verification-identity.md), [ADR 0003](../../decisions/workflow/0003-plan-and-result.md)의 **B 기록/판정 원칙을 함께 채택**했다. 작성 skill의 입력, 산출물을 검증 계획/시도 보존과 완료 판단에 연결한다. 11/15 로컬 검증의 필드, 파일과 저장/조회 초안은 [기록 명세](records.md)에 작성했으며 제품 구현과 검증은 아직이다. 두 개의 실행 체계를 새로 만드는 선택이 아니며, 이후 채택한 결과 재사용 정책은 아래 [ADR 0002 C의 의미 — 「PASS 재사용의 구체적 의미」](verification.md#PASS%20%EC%9E%AC%EC%82%AC%EC%9A%A9%EC%9D%98%20%EA%B5%AC%EC%B2%B4%EC%A0%81%20%EC%9D%98%EB%AF%B8)와 연결한다.

채택한 B는 **검사 계획을 보존하고, 실행, 재시도마다 그 계획을 참조하는 기록을 남기는 방식**이다. 코드 수정은 새 실행의 입력이고, 무엇을 검사하는지 바뀌면 이유를 가진 후속 계획으로 연결한다. 파일과 필드의 소유는 위 기록 명세, 보관/정리의 원칙은 [복구 계약 — 「복구 자료의 보관과 정리」](recovery.md)으로 구분한다.

```text
요청, 현재 변경, 작성 판단
  → 검사 계획: 필요한 검사 / 제외, 미확정 사유 / 명령, 선택 조건
  → 실행 기록: 어느 계획을 어느 입력에서 실행했는지 / 실제 결과, 근거
  → 완료 대조: 필수 검사, 미해결 실패, 미실행, 필수 CI
```

이 흐름은 [조건부 실행 — 「조건부 실행과 완료 판단」](verification.md#%EC%A1%B0%EA%B1%B4%EB%B6%80%20%EC%8B%A4%ED%96%89%EA%B3%BC%20%EC%99%84%EB%A3%8C%20%ED%8C%90%EB%8B%A8)에서 검증이 필요한 작업에 연결한다. 설명 요청까지 검증 계획 파일을 만들거나 전체 gate를 켜지 않는다. 테스트 작성 skill의 결과는 사례, 근거, 남은 공백을 계획 판단에 전달하며 별도 실행 결과로 취급하지 않는다. 메인이 검사 범위와 의미를 판단하고, 프로젝트 연결부는 실제 명령, 선택, 보고서를 해석하며, 공통 처리는 기록 간 대응, 필수 근거 유무를 확인한다. 테스트 자체의 충분성은 이 형식 검사만으로 증명하지 않는다.

### 재시도를 읽는 예시

아래는 설명용 가상 흐름이며 새 실험 결과가 아니다. API와 core 검사를 둘 다 필요하다고 정한 작업을 가정한다.

| 시점 | 남길 사실 | 완료 판단 |
| --- | --- | --- |
| 계획 작성 | API, core 검사와 각 선택 조건, 필수 CI를 정함 | 계획 준비만 완료. 아직 테스트 PASS 없음 |
| 최초 실행 | API FAIL, core PASS와 당시 입력/보고서 | API 실패가 미해결 |
| core 수정 뒤 core만 성공 | 새 입력의 core 결과를 새 기록으로 추가 | 원래 API 실패는 여전히 미해결. 최신 기록 하나만 보고 전체 PASS로 바꾸지 않음 |
| 수정 후 API 재검증과 필요한 현재 로컬 근거 확인 | API 성공이 어느 실패를 해소했는지 연결. 최초 FAIL 기록은 보존 | 모든 필수 로컬 조건이 충족되면 로컬 완료. 필수 CI가 남으면 전체 검증 대기 |
| 해당 검토 버전의 필수 CI도 충족 | 로컬/CI 근거와 현재 검토 대상의 대응 확인 | 미해결 실패, 근거 공백이 없을 때 전체 완료 후보 |

과거 FAIL을 남긴다고 영원히 완료하지 못하는 구조가 아니다. 유효한 후속 근거로 미해결 의무를 닫되 과거 관측은 바꾸지 않는다. 반대로 다른 검사, 다른 작업, 다른 검토 버전의 성공은 그 실패를 해소하지 못한다. 어떤 이전 로컬 근거를 현재 입력에도 사용할 수 있는지는 ADR 0002에서 별도로 정한다.

### 미실행과 완료 범위

| 확인된 상황 | 기록, 판정 조건 |
| --- | --- |
| 테스트 작성 완료, 계획 산출, 명령 미리보기 | 작성/계획 산출물만 남기며 테스트 실행 성공으로 소비하지 않음 |
| 검증이 불필요하다는 근거가 있음 | 적용 제외와 사유를 남김. 가짜 실행 기록이나 테스트 PASS를 만들지 않음 |
| 분류 충돌, 연결 누락, 기대 동작 미정 | 미확정으로 유지하고 필요한 근거/사용자 선택 확인. 제외로 치환하지 않음 |
| 필요한 검사 중 일부 실패, 미실행, CI 대기 | 미해결 실패와 남은 의무를 함께 표시. 전체 완료 금지 |
| 실행 시작 뒤 종료/보고서를 확보하지 못함 | 중단, 수집 실패, 실행 중 가능성을 구별할 때까지 결과 미확인. 종료 코드 0을 만들어 넣지 않음 |
| 필요한 테스트가 없거나 실행이 생략됨 | 사전 적용 조건, 도구 결과를 확인. 단순 exit 0이나 오래된 보고서만으로 통과 처리하지 않음 |

재개 때 끝나지 않은 실행이 있으면 먼저 같은 시도의 실제 상태를 대조한다. 세션이 끊겼다는 이유만으로 동일 명령을 중복 실행하거나 성공으로 처리하지 않는다. 프로세스 식별, 중단 처리, 기록 저장의 구체 수단은 다음 복구 계약에서 정하며 이번 안으로 자동 종료, 무제한 재시도를 채택하지 않는다.

기록은 채택된 프로젝트 로컬 상태 영역에 연결하고 WIKI/Git에 실행 로그를 기본 적재하지 않는다. 재개 시에는 현재 계획, 미해결 항목, 관련 시도를 우선 읽고 전체 로그는 필요한 부분만 조회한다. 요약은 근거 기록에서 다시 확인할 수 있어야 하며 독립적으로 바뀌는 두 번째 판정 원본을 만들지 않는다. 실제 자격증명은 명령, 로그 사본에도 남기지 않는다.

형식과 대응의 자동 검사는 다른 종류의 기록, 누락 결과, 다른 작업의 혼입을 거부하는 역할이다. 기대값의 타당성, 선택 범위의 충분성, 테스트 약화 여부는 의미 검토가 필요하다. 구현 시 V-01~V-04, V-09~V-15, V-20~V-21에서 실제 소비자의 완료 판단까지 확인하며, 문서 작성이나 직렬화 성공만으로 통과 처리하지 않는다.

## 최소 입출력 후보

아래 표는 재시도에 필요한 정보의 의미를 소유하며 구체 필드/파일은 [계획 필드](records.md)와 [시도와 결과 필드](records.md)에 대응했다. 로컬 검증의 [SQL 저장 후보](storage.md)는 키/참조와 후속 관측을 연결하며 전체 DDL/직렬화 검증과 정확한 명령 옵션은 아직이다. 프로젝트 식별과 설정 출처는 [연결 조회 결과 — 「결과를 받는 절차」](../runtime/entry.md)를 받아 아래 계획/시도에 대응시키며, 검증기가 같은 루트 탐색과 권한 확인 절차를 따로 복제하지 않는다. 입력이 바뀌거나 실제 실행에서 거부되면 관련 조건을 다시 확인한다.

| 자료 | 최소 정보 | 필요한 이유 |
| --- | --- | --- |
| 검증 계획 | 저장 형식 버전의 확인, 계획 식별자, 작업/workspace, gate, 변경 성격 | 다른 작업 결과와 구별. 형식 버전의 원본은 DB 메타데이터 |
| 작성 판단 연결 | 작성/보강 여부, 이유, 관련 요구/사례, 남은 공백의 참조 | 작성 완료와 실행 성공을 구별하며 필요한 검사 선택으로 연결 |
| 프로젝트 연결 정보 | 원본 설정, 명시 정책/보정의 출처, 해석 결과와 실행 연결부의 식별, 버전/해시 | 설정 변경이나 다른 프로젝트 값을 같은 검사로 오인하지 않음 |
| 계획의 검사 목록 | 검사 식별자, 최초 scope 경로 목록, 실제 argv 배열, cwd, 선택/제외 조건, 실행 정책 | `test` 같은 요약을 실제 실행과 혼동하지 않음 |
| 적용 여부, 선택 근거 | required / not_required / undetermined, 최소/완료 검사 구분, 선택 사유, 예외 | 비활성, 입력 충돌을 검사 성공과 구분하고 검사 충분성의 판단 범위를 드러냄 |
| 실행 기록 | 실행 식별자, 계획 참조, 최초/이전 시도 참조, 이번 입력 manifest, fingerprint, 실행 도구/설정 식별 | 수정 후 코드와 재시도 계보를 확인 |
| 검사별 결과 | 실제 명령 대응, 관측한 종료 코드와 종료/수집 여부, 실행, 빌드 도구 재사용, 미실행의 출처, 로그/보고서 참조, 판정과 사유 | 실제 수행 범위와 전체 결과를 대조. 종료를 확인하지 못하면 성공 코드로 채우지 않음 |
| 수정 영향 입력 | 원래 실행 이후의 수정 경로와 상태, 추가 검사, 선행 결과 영향 | 최초 검증을 바꾸지 않고 필요한 검사만 확장 |

입력 기록은 Git 미커밋, 관련 미추적 파일과 추가, 삭제도 다뤄야 한다. 비밀 환경값을 통째로 저장하지 않는다. scope, artifact는 현재 작업과 허용된 경계 안인지 검사하고, 실행에 영향을 주는 환경을 확인할 수 없으면 재사용을 허용하지 않는다. 이 기록을 남긴다는 것이 곧 하네스 자체 캐시용 완전한 입력 추적기를 만든다는 뜻은 아니다.

빌드 도구의 전체 task 입력 추적을 하네스 manifest에 복제하지 않는다. 하네스는 작업 revision/변경, 계획/정책, 도구 식별과 실제 수행 근거를 보관하고, 도구 재사용의 입력 판정은 연결부가 확인한 해당 도구의 기능을 활용한다. 두 범위를 혼동해 기록용 hash를 완전한 캐시 키로 승격하지 않는다.

plan ID는 검사 계획의 식별자이고 입력 fingerprint는 그 실행이 본 코드/설정의 식별자다. 수정 후 fingerprint가 달라졌다는 이유만으로 같은 검증을 재시도할 수 없게 만들면 안 된다. 반대로 ID가 같다는 이유만으로 다른 도구, 예외를 같은 검사라고 인정할 수도 없다.

초기에는 검증 대상 입력을 실행 도중 편집하지 않는 운용을 전제로 한다. 감지된 변경은 현재 결과를 완료 근거로 사용하는 것을 막지만, 실행 전후 hash만으로 완전한 snapshot 격리를 달성했다고 주장하지 않는다. 동일 workspace의 동시 편집, 병렬 실행 지원은 별도 설계 대상이다.

## 검사 선택의 초기 추천

모듈별 floor는 출발점이며 충분성은 변경 동작, 소비 관계, 기존 정책에 비춰 판단한다. 채택한 기본과 보정 이유는 [ADR 0005의 추천과 이유](../../decisions/workflow/0005-verification-selection.md), 시점별 범위는 [로컬 완료와 CI의 분담](../../decisions/workflow/0005-verification-selection.md)을 따른다. 10/27 C 추천 이력과 11/11 A 보완안의 채택을 구분한다.

확정된 boot 예외는 유지하며 이름 불일치는 별도 수정 대상으로 남긴다. 예외, 미실행, CI 대기를 PASS로 표현하지 않는다. 자동 영향 선택기의 도입과 도구 재사용은 각각 별도 판단이고, 검사 시간과 모델 토큰 절감은 아직 측정하지 않았다.

## PASS 재사용의 구체적 의미

11/11 기록 B에 이어 **ADR 0002 C의 재사용 원칙을 채택**했다. 기록을 보존한다는 결정만으로 과거 PASS를 현재 입력에도 인정하거나 검사 호출을 생략할 수 있는 것은 아니다. 대안 A는 검사 본문의 새 실행 우선, B는 하네스 자체의 전체 입력 추적/캐시, C는 필요한 도구 호출과 확인된 도구 재사용이다. 대안별 장단점은 [ADR 0002 — 「비교한 방안」](../../decisions/workflow/0002-pass-validity.md)가 소유한다.

제품 테스트는 해당 프로젝트의 빌드/검증 도구를 호출해 결과를 수집하는 C안을 따른다. 현재 프로젝트의 첫 연결부는 Gradle이며 필수 계획의 task를 호출한다. 하네스가 호출을 생략하는 것과 빌드 도구가 검사 본문을 생략하는 것은 다르다. 적절한 재사용이면 신규 테스트 실행으로 세지 않고 근거를 기록한다. 대상 도구에 신뢰할 수 있는 재사용 기능이 없으면 새 실행을 사용한다.

이 방향은 Gradle 시작 비용이 남는 대신 자체 의존성 캐시의 유지 부담을 줄이는 절충이다. 선택 범위는 ADR 0005의 정책으로 정한다. 현재 API 검증 의무는 core 수정 뒤에도 유지하며 추가 검사나 넓은 완료 묶음에 포함돼야 한다. 빌드 도구가 모든 비즈니스 영향, 테스트 충분성을 선택해 주는 것으로 해석하지 않는다.

초기 자체 PASS 캐시는 보류한다. 문서 검사도 일단 실행하고, 비용이 문제가 될 때 입력 완전성과 실제 이득을 근거로 별도 판단한다. 현재 governance 구현의 입력 추적이 완전하다고 확인한 것은 아니다.

DB, 외부 서비스 상태를 보는 검사는 재사용 조건을 증명하기 어렵다. 필수 범위에 포함된 이런 검사는 새 실행을 기본으로 하며, 실제 실행을 강제하는 설정은 프로젝트의 Gradle `8.14.3` 동작을 확인한 뒤 정한다. 위에서 확인한 접근 제한 예외의 테스트를 다시 실행 대상으로 넣는다는 뜻은 아니다. 기존 boot 선택 범위를 이번 문서 작업에서 변경하지 않는다.

원래 실패한 검사 본문도 복구 시 새 실행을 기본으로 한다. 컴파일 등 준비 작업의 유효한 도구 재사용은 가능하다. 계획에 명시한 새 실행 정책에 따라 실제 argv가 달라지는 것과 검사 선택, 예외를 바꾸는 것은 구별해 기록한다.

### 재사용을 판단하는 순서

아래는 채택한 처리 원칙이며 실제 시험 결과가 아니다. 입력, 설정, 환경과 기록의 대응을 확인하는 정확한 수단은 후속 명세에서 정한다.

| 확인된 상황 | C안에서의 처리 | 남길 근거 |
| --- | --- | --- |
| 같은 검사를 이미 실행 중인데 다른 skill이 다시 요청 | 기존 실행을 확인하고 중복 시작하지 않음 | 작업, 검사와 진행 중인 시도의 연결. 실제 실행 여부를 모르면 먼저 확인 |
| 현재 작업의 같은 검사 의무를 이미 충족했고 관련 입력/조건의 동일성이 확인됨 | 완료 보고를 위해 다시 실행하지 않고 같은 결과를 참조 | 현재 의무와 유효한 시도의 대응. 이후 변경의 PASS 생략 캐시와 구분 |
| 검사 입력/조건이 바뀌었거나 기존 근거의 대응이 불명확함 | 필요한 검사 도구를 호출해 새 근거 확보 | 현재 계획/입력, 실제 명령, 도구 결과 |
| 입력 선언, 환경 조건을 확인한 검사가 도구의 재사용 결과를 반환 | 확인된 도구 재사용으로 기록하고 계획의 의무와 대조 | 실제 실행과 구분된 재사용 출처. 누락/생략을 재사용으로 치환하지 않음 |
| 원래 실패한 검사, 외부 DB 등 조건을 확인할 수 없는 검사, 재사용 기능 없는 도구 | 필요한 검사 본문을 새로 실행 | 새 실행과 결과. 준비 작업의 적절한 재사용과 별개 |
| 과거 로그의 일부만 다시 확인하고 싶음 | 저장된 원문에서 조회 | 같은 실행의 근거 참조. 로그 출력만 바꾸려고 테스트 재실행 금지 |

예를 들어 구현 중 API 검사가 성공한 뒤 같은 입력에서 완료 절차만 이어지면 해당 결과를 참조한다. 이후 API가 사용하는 core 코드를 수정했다면 현재 의무를 다시 판단하고 필요한 검사를 호출한다. 도구가 유효한 입력 비교에 따라 일부 준비 작업/검사 결과를 재사용할 수 있지만, 하네스가 예전 API PASS만 보고 현재 검사를 생략하는 것은 C안에 넣지 않는다. DB 상태가 결과에 영향을 주거나 이전 검사 실패를 고친 경우에는 필요한 검사 본문의 새 실행을 요구한다.

[Gradle task 결과](https://docs.gradle.org/current/userguide/more_about_tasks.html#sec:task_outcomes)는 실행, `UP-TO-DATE`, `FROM-CACHE`, 생략을 구별하고, [캐시 입력 선언](https://docs.gradle.org/current/userguide/build_cache.html#sec:task_input_output)은 누락된 입력이 잘못된 캐시 적중을 만들 수 있다고 설명한다. 이는 도구 결과를 근거와 함께 확인할 이유이며, 도구를 호출했다는 사실만으로 현재 테스트의 충분성, 정확성을 보증하지 않는다. C는 프로젝트의 캐시를 자동 활성화하거나 원격 캐시를 새로 만드는 결정이 아니다. 공식 current 문서의 개념 대조이며 대상 Windows 도구 버전의 실제 결과/옵션 검증은 아직이다.

## 입력과 실행 결과의 판정

계획 생성이 끝나면 계획 생성 성공을 알리되 테스트 PASS로 쓰지 않는다. `not_required`는 사유가 있는 비활성이고, `undetermined`는 최소 추가 확인이 필요한 상태다. 필수 검사 목록이 비어 있는데 실행 완료로 바꾸지 않는다.

실행 뒤에는 검사별 근거를 모아 `PASS`, `FAIL`, `UNCLASSIFIED`로 판정한다. 필요한 검사 하나라도 실패하면 전체 FAIL을 유지하고 미실행, 미확인도 함께 남긴다. FAIL은 없지만 결과, 대상 대응을 확정할 정보가 부족하면 UNCLASSIFIED다. 환경 문제를 확인한 경우 제품 결함과 구별해 이유를 남긴다. 중단된 실행은 성공 증거가 될 수 없다.

테스트가 필요한 계획에서 `SKIPPED`, `NO-SOURCE`, 0건 또는 보고서 누락이 발생하면 자동 성공으로 합치지 않는다. 테스트가 없는 모듈의 예외와 빌드 도구의 정당한 재사용은 별도로 근거를 확인한다. 최종 완료는 메인이 필수 검증과 미해결 상태를 대조한 뒤 판단한다.

디스크에 남은 이전 보고서는 현재 실행의 증거가 아니다. 현재 task 결과, 선택 범위와의 대응이 필요하다. 새 계획을 만들면서 원래 실패 검사를 없앤 경우에도 이전 의무가 어떻게 해소됐는지 설명해야 한다. 테스트를 통과시키기 위해 기대 동작을 약화했는지는 의미 검토에 남는다.

## 향후 회귀 검사와 수치화 사례

아래는 **아직 실행하지 않은 검증 시나리오**다. 사례 작성 자체를 PASS나 수정 효과로 보고하지 않는다. 최초 반례와 정상 대조군을 함께 유지한다.

| 사례 | 입력, 상황 | 개선 후 기대 판정 |
| --- | --- | --- |
| V-01 | API FAIL 뒤 core-only 수정 scope, API는 여전히 실패 | API 검증을 유지하고 FAIL. core PASS만으로 종료 금지 |
| V-02 | 원래 API 실패의 원인을 실제 수정 | 같은 API 검사, 조건을 현재 코드에서 확인한 뒤 PASS 후보 |
| V-03 | 수정으로 새 모듈 검사도 필요 | 기존 API와 추가 검사 모두 충족해야 완료 후보 |
| V-04 | selector 축소, 테스트 제외, 검증 도구 변경 | 계획 변경을 감지하고 후속 계획, 변경 근거 필요 |
| V-05 | core 변경 뒤 과거 API PASS | 과거 PASS만으로 호출 생략 금지, 필요한 task와 근거 확인 |
| V-06 | gradlew, 공통 설정, 검사 규칙 변경 | 기존 자체 PASS 재사용 거부, 현재 도구로 검증 |
| V-07 | 관련 입력에 파일 추가, 삭제, 이름 변경 | 실행 입력, 프로젝트 정보에 변화가 반영되거나 미확인 반환. 파일 목록 일부만 같다고 재사용하지 않음 |
| V-08 | 결정적 검사와 무관한 파일만 변경 | 새 검증 의무는 필요한 도구를 호출하고 유효한 도구 재사용을 구분. 이미 충족한 현재 의무의 중복 요청은 입력/조건 대응 확인 뒤 같은 결과 참조. 자체 PASS 캐시와 구분해 반복 비용 측정 |
| V-09 | 테스트 작성 완료, 계획 모드, 비활성 | 실행 결과와 테스트 PASS 생성 금지. 계획/작성 산출물을 실행 결과로 넘기면 소비자가 거부 |
| V-10 | 필요한 테스트가 0건, SKIPPED, NO-SOURCE | 사전 적용 예외가 없으면 완료 보류 |
| V-11 | Gradle UP-TO-DATE, FROM-CACHE | 신규 테스트 실행과 구분하고 정책, 보고서 근거 확인 |
| V-12 | 여러 필수 명령 중 일부 미실행, 실패, 중단 | 전체 PASS 금지 |
| V-13 | 같은 gate지만 다른 작업/workspace의 결과 | 입력 충돌을 반환하고 재사용, retry 거부 |
| V-14 | 반복 retry 또는 손상된 최초 기록 | 고유 시도 기록 보존. 입력 손상으로 성공 처리 금지. 유효 후속 성공으로 의무를 닫되 최초 FAIL은 보존 |
| V-15 | 계획은 전체 test지만 실제 명령에 include selector, 목록의 클래스명이 실제 소스와 불일치 | 실제 선택, 예외, 발견/보고서 대응을 확인. 의도하지 않은 누락과 “전체 테스트 완료” 과장 금지 |
| V-16 | 외부 DB 상태만 변함 | 파일 동일성만으로 재사용 금지, 현재 외부 상태 검사 |
| V-17 | core만 변경되고 소비 모듈 검사에 실패가 주입됨 | 완료 묶음에 해당 검사가 포함돼 실패를 드러냄. core floor PASS만으로 완료 금지 |
| V-18 | 분석 후 모듈/task/문서 경로가 변경됨 | 낡은 프로젝트 정보로 계획하지 않고 재해석 또는 미확인 반환 |
| V-19 | 검증 중 관련 입력 변경이 감지됨 | 결과를 현재 코드의 완료 근거로 쓰지 않음. 완전한 snapshot 격리 실험과 구분 |
| V-20 | 이전 성공 보고서가 남았지만 현재 필수 검사 실패, 미실행 | 이전 보고서로 성공 대체 금지. FAIL과 미확인 항목 보존 |
| V-21 | 필수 로컬 검사는 충족했지만 필수 CI가 대기 중이거나 다른 검토 버전의 결과만 존재 | 로컬 완료와 전체 검증 완료 구분. 현재 검토 대상의 유효한 CI 근거 전에는 전체 완료 금지 |

수정 후에는 실패 주입 중 잘못된 성공 판정 수/전체 실패 사례 수, 재시도에서 원래 검사 보존 여부, 불필요한 신규 검사 수, Gradle 호출/실제 검사/재사용 횟수와 시간을 구분해 측정한다. 이 고정 사례만의 결과를 일반적인 신뢰성으로 확대하지 않는다. 토큰 효과는 이후 모델 사용량을 포함한 비교에서 별도로 측정한다.

## 2026-10-27 재검토에서 바꾼 판단

사용자가 당일 두 요청을 다시 판단하도록 요청해 기존 추천을 전제로 삼지 않고 실제 script, 계약, 기존 재현, 공식 문서를 대조했다. 당시의 검토 기록이다. 이후 ADR 0005의 로컬/CI 분담 원칙은 11/11 채택했고 나머지 상태는 각 ADR을 따른다.

| 이전 초안 | 재검토 결과 | 이유 |
| --- | --- | --- |
| 계획 보존과 결과 분리를 각각 추천 | 추천 유지. 하나의 작은 공통 계약으로 구현할 수 있음을 명시 | 파일/프로세스 수가 안전성을 만드는 것은 아니다. 국소 보강도 계약을 만족하면 가능 |
| 빌드 도구 활용과 결정적 검사의 자체 캐시 | 초기 자체 PASS 캐시는 보류 | 완전한 입력과 실제 절감 효과가 확인되지 않은 캐시부터 만들 필요가 없음 |
| 필요한 task 선택은 짧은 설명에 남음 | 당시 선택 책임을 ADR 0005로 분리하고 넓은 회귀 묶음 C 추천. 현재 채택한 기본은 11/11 재검토한 [A와 CI 분담 — 「로컬 완료와 CI의 분담」](../../decisions/workflow/0005-verification-selection.md) | 빌드 도구의 재사용 판단만으로 검사 선택 누락을 해결하지 못함 |
| 분석한 값을 프로젝트 설정에 저장 | 원래 도구 설정, 명시 정책/보정, 파생 해석 결과를 구분 | 새로운 설정 파일이 낡은 두 번째 원본이 되는 문제 방지 |
| 이식, 문서 복원의 큰 방향 확인 | 필수 목표는 유지. 설치/갱신 소유권, 문서 주장별 근거, 실제 이식 판정을 추가 | 자동 치환과 문서 생성만으로 재사용성과 정확성을 증명할 수 없음 |

검증 결함 수정은 토큰 절감 실험의 신뢰도를 높이기 위한 선행 작업이다. 이것만으로 클라우드 토큰이 줄었다거나 기술 검토 경쟁력이 입증됐다고 평가하지 않는다.

## 근거와 적용 한계

- 현행 사실: `.codex/scripts`, gate-state 계약, 테스트 matrix와 앞선 격리 재현. 기준 HEAD는 `f6e33dd56baa2a651a70d7d0b2cc3ebde6575153`이며 이번 설계에서 개발 자산은 수정하지 않았다.
- [Gradle cache key](https://docs.gradle.org/current/userguide/build_cache_concepts.html): 검사 구현, 입력 동일성이 재사용 근거라는 개념. 직접적인 하네스 설계 지시는 아니다.
- [Gradle cache 입력 선언](https://docs.gradle.org/current/userguide/build_cache.html): 누락 입력은 잘못된 적중을 만들 수 있다. 완전한 manifest 없이 자체 재사용을 허용하지 않는 근거다.
- [Gradle task 결과](https://docs.gradle.org/current/userguide/more_about_tasks.html): 실행, 재사용, 생략, 입력 없음의 구분. 결과 수집 세부 구현은 아직 없다.
- [Bazel hermeticity](https://bazel.build/basics/hermeticity): 도구, 호스트, 외부 상태를 통제하지 않으면 입력 해시만으로 결과를 보장하기 어렵다는 근거다.
- [Python subprocess](https://docs.python.org/3/library/subprocess.html): 명령 인자 배열, cwd, 실행 결과를 분리해 표현할 수 있다. 언어 선택은 미확정이다.
- [ADR 원문](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions): 제안, 채택 상태와 결과를 남기는 기록 방식. 저장 위치는 사용자 지정이다.
- [Gradle CLI](https://docs.gradle.org/current/userguide/command_line_interface.html), [Gradle 9.x 변경 안내](https://docs.gradle.org/current/userguide/upgrading_version_9.html#deprecate_build_needed_build_dependents_tasks): task 선택/의존과 넓은 호출, 도구 재사용을 구분할 근거. 현재 프로젝트의 실제 실행 호환은 미검증이다.
- [Nx 설정 원본](https://nx.dev/docs/reference/project-configuration), [affected 선택](https://nx.dev/docs/features/ci-features/affected): 도구 원본, 파생 설정과 영향 선택의 입력 선언을 구분하는 참고. 도구 도입 결정은 아니다.
- [Copier 갱신](https://copier.readthedocs.io/en/stable/updating/), [Git 이력](https://git-scm.com/docs/git-log): 이식 후 변경 보존, 충돌과 문서 근거 수집의 한계. 상세 적용은 ADR 0004에 남겼다.

외부 문서는 `2026-10-27` 작업 중 본문을 확인했다. 접근한 Gradle current 문서 표시는 `9.8.2`이고 저장소 wrapper는 `8.14.3`이다. 8.14/8.14.3의 버전별 본문은 웹 도구에서 접근되지 않아 위 자료는 개념 근거로만 사용했다. 특정 플래그, 보고서 수집의 버전 호환을 확인한 것으로 보고하지 않는다.

11/11에는 [Gradle 테스트 필터](https://docs.gradle.org/current/userguide/java_testing.html#test_filtering)의 완전한 클래스명, 복수 `--tests`와 보고서 구분, [task 결과](https://docs.gradle.org/current/userguide/more_about_tasks.html)의 실행/재사용을 다시 확인했다. current 본문은 9.9 계열이며 8.14.3 본문은 이번에도 웹 도구에서 접근하지 못했다.

표의 소스 불일치는 로컬 파일 대조로 확인했고 필터의 실제 동작, 시간은 실행 전이다.

[GitHub의 로컬/CI 명령](https://docs.github.com/en/actions/tutorials/build-and-test-code/java-with-gradle#building-and-testing-your-code)과 [Google의 테스트 검토](https://google.github.io/eng-practices/review/reviewer/looking-for.html#tests)는 실행 시점, 작성 책임의 비교 근거이며 새 skill이나 정책 채택을 대신하지 않는다.

11/11 계획/결과 연결 검토에서는 [Python subprocess](https://docs.python.org/3/library/subprocess.html)의 실행 인자, 반환 코드, 출력 구분, [Gradle task 결과](https://docs.gradle.org/current/userguide/more_about_tasks.html)의 실행/재사용/생략, [GitHub check runs](https://docs.github.com/en/rest/checks/runs)의 진행 상태와 결론 분리를 확인했다. 역할을 구분하는 근거이며 이 자료만으로 우리의 저장 형식, GitHub API 수단을 채택하지 않는다. current 문서의 개념 확인이고 지원 Windows 도구 버전에서의 실제 실행, 결과 수집 검증은 아직이다.
