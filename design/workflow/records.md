# 검증과 복구 기록

2026-11-15의 4단계 파일 명세 초안이다. [검증 계획과 결과 — 「계획과 결과의 연결」](verification.md), [복구 자료의 대응](recovery.md)을 파일, 필드, 작성자와 소비자에 연결한다. 채택한 SQLite 저장 원칙을 구체화하며 제품 구현이나 Windows 시험 결과는 아니다.

중심 범위는 **로컬 검증 기록과 active의 연결**이며, 11/16에는 최초 설치의 보존 자료 형식과 프로젝트 DB 인계 초안을 보강했다. [SQLite 저장 규칙](storage.md)은 검증 관계에 설치 단위/반영과 인계 수신을 연결한다. 이 문서는 필드의 의미와 소비를 소유한다. 설치의 변경 단위, WIKI 후보 반영, 원격 PR의 실제 효과는 각 기능의 명세에서 이 기록과 연결한다. 모든 기능을 검사 결과 한 종류에 억지로 담지 않는다. 복구가 발동하는 때는 [기존 적용 경계 — 「복구의 대상과 경계」](recovery.md)가 소유한다.

## 파일과 소유

아래는 적용 프로젝트의 파일명 후보다.

```text
코드 프로젝트/
  .harness/
    local.json                 기기별 연결 설정. 진입 명세 소유
    state/
      active.md                목표, 조건과 다음 행동
      state.db                 계획, 실행 시도, 결과와 파일 참조
      plans/<plan_id>/         실행 전에 필요한 계획 후보 자료
      runs/<attempt_id>/       해당 시도의 사본, 로그와 필요한 보고서
```

| 파일 | 작성자 | 생성과 조회 조건 |
| --- | --- | --- |
| `active.md` | 메인이 의미를 작성하고 공통 저장 코드가 기준 대조, 보존과 저장 확인 | 이어갈 작업의 문맥을 남길 필요가 있을 때. 단순 설명이나 새 설치만으로 빈 파일을 만들지 않음 |
| `state.db` | 공통 기록 코드. 검사 선택의 의미는 메인이 전달 | 프로젝트 DB는 관리하는 실행 기록이 필요하고 제외/저장 준비가 끝났을 때 생성. 그 전 첫 제외 준비는 [최초 보존 자료 — 「최초 보존 자료의 형식」](records.md#%EC%B5%9C%EC%B4%88%20%EB%B3%B4%EC%A1%B4%20%EC%9E%90%EB%A3%8C%EC%9D%98%20%ED%98%95%EC%8B%9D)로 연결. 재개 조회 실패를 새 DB 생성으로 처리하지 않음 |
| `plans/<plan_id>/` | 후보 준비 코드 | DB에 넣을 설명 외에 별도 후보 파일이 필요할 때만 생성. 계획의 두 번째 JSON 원본이나 빈 폴더를 만들지 않음 |
| `runs/<attempt_id>/` | 해당 실행과 결과 수집 코드 | 적용 직전 사본이나 필요한 출력이 있을 때 생성. 새 시도는 새 경로를 사용하며 이전 결과를 덮지 않음 |

백업이 필요할 때 만드는 `state/backups/<backup_id>/`의 DB/파일 사본과 완성 목록은 [백업 파일 구성 — 「파일 구성과 보장 범위」](maintenance.md)이 소유한다. 진행 원본을 추가하는 위치가 아니며 빈 폴더를 미리 만들지 않는다.

Git 제외와 공개 금지는 [상태 제외 계약 — 「작업 상태와 Git 제외」](recovery.md)을 따른다. WIKI에는 공유할 요구, 결정과 필요한 검증 설명만 선별한다. DB, 실행 로그, active를 팀원끼리 동기화하지 않는다.

기기 명령의 [등록 정보 — 「기기 등록 정보와 소유」](../runtime/entry.md)는 OnepLoom 사용자 프로그램 영역의 `registration.json`이 소유한다. 마지막 확인한 명령/환경과 PATH 소유만 남기며 진행 중일 때만 기존 `state_root`, `db_id`, `task_id`를 참조한다. 단계/결과를 JSON에 복제하지 않고 프로젝트/WIKI 전역 목록도 만들지 않는다. 첫 프로젝트가 없어져도 완료된 등록 정보는 남는다.

[등록 작업과 기존 DB — 「등록 작업과 기존 DB의 연결」](../runtime/entry.md)는 같은 작업에 DB 하나를 유지한다. 프로젝트 설치 중에는 그 실행의 기존 DB에 별도 등록 작업을 연결하고, 프로젝트 없는 명령의 최초 등록/복구/제거는 외부 최초 보존 방식으로 그 작업만 기록한다. 등록 작업은 프로젝트 설치의 자동 복원 범위와 분리한다. 프로젝트 없는 작업에 검증 전용 `project_id`/WIKI 문맥을 억지로 채우지 않으며, 필요한 저장 확장은 [등록 효과의 경계 — 「기기 등록 효과의 저장 경계」](storage.md)를 따른다.

`pending`이 참조하는 DB와 복구 자료는 사용 중인 의존성이다. 최초 DB 인계 전에는 등록 작업과 그 참조 해제를 마치고, 정리에서는 미완료 참조를 보호한다. 참조 경로가 없어졌거나 DB 식별이 다르면 새 DB 생성/작업 완료로 우회하지 않는다. 상세 기록의 명시적 정리 뒤에도 현용 등록/환경을 남기되 잃은 과거 복원 범위를 안내한다.

같은 작업의 진행 원본은 DB 하나다. 최초 인계 중 남는 외부 DB는 아래 전환 조건에 따라 보존하며 프로젝트 DB와 동시에 작업을 진행하지 않는다. 조회 결과를 JSON으로 반환할 수 있지만 수정 가능한 `plan.json`, `result.json`을 별도 원본으로 관리하지 않는다. 빌드 도구의 기존 보고서는 위치와 내용 기준을 참조하고, 보존이 필요한 경우만 해당 시도 아래에 사본을 둔다. 로그를 보기 위해 검사를 재실행하지 않는다.

아래 구체 계획/시도 필드는 로컬 검증을 대상으로 한다. 설치 작업도 같은 로컬 DB를 사용하되 [설치 기록 — 「설치 기록과 단계 연결」](../runtime/install.md)과 [반영 기록 — 「반영 기록과 완료 연결」](../runtime/update.md)의 의미를 별도로 보존한다. [공통 기록과 기능별 연결](storage.md)에서 계획/시도 종류를 구별하며 연결 코드가 호출 목적에 맞는 종류를 설정한다. 사용자에게 내부 종류를 추가 입력하게 하지 않는다. 설치가 실행한 검사는 아래 기록을 참조하고, 파일 반영 자체를 검사 결과로 바꾸지 않는다. `install.json`은 담당자의 관리 도구가 사용할 비교 기준의 파일명 후보이며 로컬 진행 상태의 JSON 복사본이 아니다. 공유 권장과 일반 팀원의 사용 범위는 설치 명세가 소유한다.

### 로컬 영역의 확장

`.harness/`는 세션 전용이 아니라 Git에서 제외할 프로젝트 로컬 자료의 상위 영역이다. `local.json`은 기기별 연결, `state/`는 계속 이어갈 작업의 상태를 소유한다. 이미 하위 책임을 구별한 구성이며 `.harness/` 바로 아래에 모든 실행 파일을 늘어놓는 방식이 아니다.

현재 `state/`에는 문맥 인계용 active와 실행 사실의 DB/원문이 함께 있다. 실행은 Codex 세션이 바뀌어도 같은 작업으로 이어질 수 있어 전체를 `session/`이라고 부르면 책임을 좁게 오해할 수 있다. `state`는 이 설계의 역할에 맞춘 이름이며 모든 도구가 따라야 하는 표준 폴더명이라고 주장하지 않는다.

새 기능에 로컬 자료가 필요하면 보존 목적과 수명을 기준으로 하위 위치를 정한다. 같은 계획/시도 기록이면 기존 상태를 참조하고, 삭제해도 재생성 가능한 캐시 등 다른 책임이 실제 생기면 별도 하위 폴더로 분리한다. 기능마다 중복 DB나 빈 확장 폴더를 먼저 만들지 않는다. 공유할 skill, hook, 실행 코드와 WIKI는 기존 [공유/로컬 경계 — 「작업 상태와 Git 제외」](recovery.md)대로 이 제외 영역 밖에 둔다.

같은 작업 사본에서 DB를 재사용하는 수명, 누적 용량과 조회/정리 조건은 [DB의 수명과 누적 용량](recovery.md)이 소유한다. 모든 사용자 요청을 기록하거나 같은 DB를 팀원끼리 공유하는 방식으로 확대하지 않는다.

### 기록이 필요한 때와 비용

`state.db`는 로컬 SQLite 데이터베이스 파일이다. 코드가 관련 기록을 짧은 트랜잭션으로 함께 저장하는 대상이며, 오류가 난 뒤에만 생성하는 사고 보고서나 Git 커밋이 아니다. 실행 전후의 근거가 남아 있어야 중단 후 실제 수행 여부를 대조할 수 있다. DB commit은 DB 기록만 확정하며 실행한 코드, WIKI나 PR을 함께 되돌리지 않는다.

| 상황 | DB 기록/조회 | active와 모델 입력 |
| --- | --- | --- |
| 짧은 질문, 일반 파일 읽기, 연결 확인만 수행 | 그 요청 때문에 실행 DB를 만들거나 복구 이력을 읽지 않음 | 이어갈 목표/조건이 바뀌지 않으면 active 재작성 없음 |
| 모듈의 관리 경로로 검사를 실행 | 계획이 새로 필요하거나 바뀌면 보존. 시도의 준비와 관측한 결과를 기록 | 계획 판단에 필요한 정보와 검사 결과를 사용. 매 SQL 쓰기마다 AI에 별도 요청하지 않음 |
| 정상 문맥에서 결과가 명확한 검사 FAIL | 실패를 보존하고 수정 뒤 새 시도를 연결 | 정상 수정/재검증. 전체 세션 복구를 먼저 호출하지 않음 |
| 목표, 허용 범위, 현재 단위나 다음 행동 변경 | 기계 기록도 바뀐 경우 그 부분만 갱신 | 메인이 필요한 의미를 active에 반영. 변경 없는 본문 전체를 반복 생성하지 않음 |
| compact/재접속 뒤 작업 인계 | 필요한 계획 참조가 있을 때 관련 부분 조회 | 해당 active와 필요한 근거만 읽음. 미확인 실행이 없으면 모든 DB 이력 조회 없음 |
| 종료/반영 여부가 불명확한 중단 | 해당 시도와 실제 실행/산출물을 대조 | 메인이 미확인과 다음 행동을 판단. 오류의 심각도보다 문맥/실행 사실의 부족 여부가 기준 |

설치/갱신과 WIKI/PR 기능도 각자의 실행 경계에서 기록을 사용하되 그 상세 필드는 후속 명세다. 평소 개발의 모든 편집, 명령을 DB 트랜잭션으로 감싸는 안으로 확대하지 않는다.

11/23 채택한 [완료 후 WIKI 재실행 — 「완료 후 다시 실행하는 흐름」](../../discussions/knowledge/reconstruction.md)도 이 경계를 따른다. 기존 분석 근거의 조회, 중단된 시도 대조와 새 검토 의도를 구분하고 실제 새 분석/반영의 준비와 결과만 필요한 상태에 연결한다. WIKI 본문 재사용을 아래 검사 결과의 `tool_reused`나 테스트 PASS로 기록하지 않는다. WIKI 전용 처리 상태와 필드 대응은 후속 명세이며 별도 DB나 진행 원본을 추가하지 않는다.

예를 들어 메인이 검사 실행을 한 번 요청하면 일반 코드 안에서 **준비 저장 → 검사 실행 → 결과 저장 → 필요한 요약 반환**을 처리한다. DB 저장 요청을 위해 메인에게 매번 제어를 돌렸다가 다시 SQL 호출을 지시하게 만들지 않는다. 긴 실행의 진행 확인이나 실패 처리에 필요한 호출은 별도이며, 한 요청으로 항상 끝난다는 보장은 아니다.

SQL, 해시 계산, 파일 저장 자체에는 모델 추론을 사용하지 않는다. 그러나 모델이 만드는 계획/실행 요청, 반환된 요약, active 작성/읽기와 재개 판단은 토큰을 사용한다. hook도 모델 문맥에 전달하는 내용은 비용 비교에 포함한다. [OpenAI Docs](https://learn.chatgpt.com/docs/hooks#sessionstart)는 `SessionStart`의 추가 문맥 전달을 설명하므로, hook이 일반 코드라는 이유로 출력까지 모두 토큰이 없다고 보지 않는다.

추가되는 로컬 I/O, 조회/저장 코드와 고장 처리 부담도 있다. 현재 판단은 기록의 일관성과 중복 실행 방지를 위해 이 부담을 좁게 수용하자는 것이며, 총토큰이나 속도 우위가 실측됐다는 뜻은 아니다. 정상 작업의 추가 비용과 중단 뒤 재탐색/재실행 비용을 [측정 입력 — 「저장 비용을 비교할 입력」](../../verification/acceptance.md)으로 나눠 확인한다. 안전성이 같고 비용 차이도 유의미하면 더 단순한 수단을 다시 비교한다.

## 식별과 참조

`task_id`는 이어가는 사용자 작업, `plan_id`는 그 작업의 고정 계획, `attempt_id`는 실제 실행을 구별한다. 검증 계획은 검사 의무를 담고, 변경/유지 관리 계획은 [종류별 계약 — 「공통 기록과 기능별 연결」](storage.md)을 따른다. ID는 일반 코드가 생성하는 불투명 식별자다. 파일명, 최근 시각, Codex 대화 ID를 그 대신 쓰지 않는다. 새 Codex 대화에서도 같은 작업을 명시적으로 이어갈 수 있고, 같은 대화 안에서도 작업은 달라질 수 있다.

| 대상 | 참조 기준 | 변경할 때 |
| --- | --- | --- |
| 작업 사본 | `project_id`와 확인한 `code_root`, `wiki_root`, 설정 출처. Windows 실행 조정에는 실제 코드 루트의 볼륨/파일 식별도 대조 | 같은 프로젝트 ID라도 다른 clone이면 로컬 상태를 가져오지 않음. 경로 변경은 재등록 후 현재 작업과 대조. 물리 식별을 영구 프로젝트 ID로 사용하지 않음 |
| 계획 | `id`, `task_id`, 선택적인 `previous_id` | 의무나 선택 정책이 바뀌면 후속 계획을 만들고 이유를 보존 |
| 검사 의무 | 계획 안의 `check_id` | 같은 의무의 재시도에서 유지. 검사 의미를 바꿔 같은 이름의 성공으로 대체하지 않음 |
| 시도 | `id`, `plan_id`, 선택적인 `previous_id` | 수정 뒤 재실행은 새 ID. 이전 시도와 최초 계획까지 참조를 따라갈 수 있어야 함 |
| 검사 결과 묶음과 관측 | 묶음은 `(attempt_id, check_id)`, 저장 관측은 `id`와 선택적 `previous_id` | 같은 관측 ID의 다른 값은 충돌. 같은 실행의 미확정 보충은 근거를 가진 후속 관측으로 남기며 확정 판정을 자동으로 뒤집지 않음 |
| 후보/결과 파일 | `artifact_id`, 소유 계획과 필요한 `attempt_id`, 위치와 내용 해시 | 검증 근거는 해당 시도 필수. 계획 후보와 시도 사본을 구별하고 원래 근거를 조용히 대체하지 않음 |

계획의 검사 목록을 줄여 이전 실패를 숨기지 않는다. 의무를 해제할 근거가 생기면 후속 계획에 제외 사유와 결정 참조를 남기며, 이를 테스트 PASS로 표시하지 않는다. 시간순으로 가장 마지막 결과 하나를 고르는 방식은 사용하지 않는다.

경로 참조는 `root`와 `path`로 표현한다. `root`는 확인된 `code`, `wiki`, `state` 중 하나이며 `path`는 해당 루트 기준 상대 경로다. 루트 밖 이탈과 허용하지 않은 연결 대상을 검사한다. 로컬 절대 루트는 비교용 기준이며 새 설정의 원본이 아니다. 실제 경로 결정은 [진입 연결 — 「공유 설정과 로컬 연결」](../runtime/entry.md)을 사용한다.

## 계획 필드

아래 context, 검사 선택과 의무 필드는 검증 계획에 대한 명세다. 설치/기기 등록의 변경 계획을 검사 계획으로 위장하지 않는다. 사용자가 확인한 변경 범위와 재사용 조건은 [확인 입력 — 「계획 참조와 확인의 재사용」](../runtime/management.md), 필요한 DB 연결은 [변경 계획의 확인 기록](storage.md)이 소유한다. 반환하는 plan_ref는 조회/적용용 참조이며 계획의 두 번째 원본이나 모든 요청에 붙일 필수 필드가 아니다.

아래는 저장/조회 코드가 공유할 논리 필드다. SQL 배치의 후보는 [관계와 키](storage.md), 내용 보존과 직렬화 후보는 [저장 값의 형식](storage.md)에서 다룬다. [DDL과 JSON의 대응 — 「SQL에 옮긴 필드」](storage.md)을 작성했고 관계 제약을 메모리 DB에서 확인했다. 저장 코드와 실제 Windows 동작은 아직이다. 아래 표의 행마다 테이블이나 클래스를 하나씩 만들라는 뜻은 아니다. 선택 필드 외에는 값이 필요하며, 빈 값으로 미확정을 숨기지 않는다.

| 필드 | 형식과 의미 | 소비자 |
| --- | --- | --- |
| `id`, `task_id` | 비어 있지 않은 식별자 | 시도 연결과 현재 작업 조회 |
| `previous_id`, `reason` | 이전 계획 ID는 최초 계획에서 생략. `reason`은 계획 선택/변경 이유 | 이전 의무와 달라진 범위 대조 |
| `context` | `project_id`, `code_root`, `wiki_root`, `config_refs`, `adapter` | 다른 작업 사본/설정 혼입 확인. `adapter`는 실행 연결부의 식별과 버전 또는 해시 |
| `change_kind`, `gates` | 메인이 판정한 변경 성격과 필요한 게이트 목록 | 검사 선택과 후속 절차. 기록 코드가 다시 전체 게이트 판정하지 않음 |
| `test_authoring` | `decision`, `reason`, `refs`, `gaps`. 작성/보강 필요 여부와 근거, 남은 공백 | 테스트 작성 결과가 계획에 반영됐는지 검토 |
| `checks` | 아래 검사 의무 목록 | 실제 실행과 완료 대조 |

`test_authoring.decision`은 `required`, `not_required`, `undetermined`를 사용한다. 작성이 필요 없다는 판단에도 이유가 필요하다. 작성 여부만 정했다고 작성이나 실행을 완료 처리하지 않는다. `refs`와 `gaps`는 해당 근거나 공백이 없으면 빈 목록이며 원문 전체를 복제하지 않는다.

각 `checks` 항목은 다음 값을 가진다.

| 필드 | 형식과 판정 조건 |
| --- | --- |
| `check_id` | 해당 의무의 안정적인 식별자. 같은 계획 안에서 중복 불가 |
| `requirement`, `reason` | `required`, `not_required`, `undetermined`와 선택/제외 근거. `undetermined`를 제외나 PASS로 취급하지 않음 |
| `stage` | `minimum`, `completion`, `ci`. 개발 중 최소 검사, 로컬 완료 검사, 필수 CI를 구별. 완료 때 최소 검사 의무도 함께 대조 |
| `scope`, `selection`, `exclusions` | 최초 대상 경로 목록, 실제 검사 선택 조건, 사유가 있는 제외 목록. 단순히 `test`라는 이름만 보존하지 않음 |
| `command` | 로컬 실행의 `argv` 문자열 배열과 `cwd` 경로 참조. 실행 불가/미확정이면 `null`과 사유를 유지. CI는 로컬 명령을 꾸며 넣지 않음 |
| `execution_policy` | `fresh` 또는 `tool_reuse`. 원래 실패한 검사 본문 등 새 실행이 필요한 경우 `fresh`. 재사용 출처의 적합성은 기존 검증 계약으로 판단 |

필수 CI의 대상과 결과 수집은 원격 연계 명세에서 구체화한다. 그 명세와 실제 근거가 없으면 CI 의무를 대기 상태로 반환하며 로컬 PASS로 전체 완료를 만들지 않는다.

## 시도와 결과 필드

아래 시도는 **공통 실행 경로가 수행하는 로컬 명령 한 번**이다. 한 명령이 여러 검사 의무를 수행할 수 있으므로 실행 사실과 검사별 결과를 구별한다. 모든 터미널 명령을 자동으로 기록한다는 뜻은 아니다.

| 시도 필드 | 형식과 의미 |
| --- | --- |
| `id`, `plan_id`, `check_ids` | 시도 ID, 보존된 계획 ID, 실제로 요청한 검사 의무의 ID 목록 |
| `previous_id` | 재시도/후속 실행이 이어받은 이전 시도. 최초 실행에서는 생략. 다른 작업의 시도를 연결할 수 없음 |
| `input` | 실행 직전의 관련 revision, 변경 경로/상태와 내용 기준, 설정/도구 기준, 확인하지 못한 조건. 아래 입력 규칙을 따름 |
| `command` | 실제 사용한 `argv`, `cwd`, 실행 도구 식별. 계획과 다른 인자가 필요하면 정책 근거를 함께 기록하고 선택 범위 변경과 구별 |
| `active_hash` | 실제로 읽어 기준으로 삼은 active의 SHA-256. active가 필요 없는 짧은 검증에서는 생략 |
| `state`, `reason` | `prepared`, `running`, `ended`, `unknown`. 의미는 [실행 상태 — 「작업과 실행의 상태」](recovery.md)를 따르며 미확인/실패 이유를 보존 |
| `created_at`, `process`, `ended_at` | 기록 생성 시각, 관측한 프로세스 식별/시작 근거, 실제 종료 관측 시각. 관측하지 못한 값은 생략하며 추정 생성하지 않음 |
| `exit_code` | 관측한 종료 코드인 정수 또는 `null`. `null`을 0으로 바꾸지 않음 |
| `cancel_requested_at` | 취소 요청이 있을 때만 기록. 종료 사실을 대신하지 않음 |

시각은 UTC로 표시하고 진단에 사용한다. `process`에는 연결부가 확인한 PID와 프로세스 시작 식별 근거를 남기며 PID 하나나 지난 시각만으로 현재 생존, 소유, 미실행을 단정하지 않는다. [실행 소유 후보 — 「실행 소유의 식별과 반환」](recovery.md)는 짧은 반영 조정과 이 기록의 대조를 결합한다. 잠금을 반환한 긴 실행도 진행 기록을 유지하며, 정확한 프로세스 관측과 실제 Windows 시험은 남아 있다.

`input`은 `revision`, `files`, `config_refs`, `tool`, `unknowns`를 포함하는 후보다. `revision`은 저장소가 없으면 `null`, `files`는 관련 파일의 경로, 추가/수정/삭제 상태와 내용 해시를 담는다. 미커밋/관련 미추적 파일도 포함하며 삭제는 내용 해시 대신 부재를 기록한다. `unknowns`에 실행 영향의 미확인 조건을 남기고 재사용/완료에 미치는 영향을 판단한다. 전체 디스크나 빌드 도구의 모든 task 입력을 재수집하지 않는다. 이 자료의 fingerprint는 대응 확인용이며 하네스의 독자적인 PASS 캐시 키가 아니다.

| 검사 결과 필드 | 형식과 의미 |
| --- | --- |
| `id`, `previous_id` | 관측 식별자, 같은 실행/검사의 이전 관측. 최초 관측은 이전 ID 생략. 추가 근거로 미확정을 보충할 때 이전 기록을 보존 |
| `attempt_id`, `check_id` | 대응하는 실행과 의무 |
| `source` | `executed`, `tool_reused`, `not_run`. 실제 실행, 확인한 빌드 도구 재사용, 미실행을 구별 |
| `conclusion`, `reason` | `pass`, `fail`, `undetermined`와 근거. 미실행, 결과 불명은 PASS 불가 |
| `artifact_refs` | 결과를 뒷받침하는 파일 참조 목록. 필요한 보고서가 없으면 판정의 근거 공백으로 반환 |

형식은 판정의 충분조건이 아니다. 연결부가 실제 실행 범위와 결과를 해석하고 메인이 원래 의무, 예외와 현재 입력에 대조한다. `pass`를 완료 근거로 쓰려면 해당 시도가 `ended`이고 필요한 결과가 대응해야 한다. `fresh` 정책에 `tool_reused` 결과를 통과시키지 않는다. exit 0, 로그 파일 존재, JSON 파싱 성공만으로 `pass`를 생성하지 않는다. 선행 컴파일 실패로 테스트가 실행되지 않았다면 그 원인과 `not_run`을 보존한다.

11/16 보강: 같은 시도의 미확정을 실제 추가 근거로 해소하는 것과, 수정 후 명령을 다시 실행하는 것을 구분한다. 전자는 후속 관측, 후자는 새 시도다. 같은 관측의 재전달, 확정 판정과 충돌하는 근거의 처리와 조회는 [중복 전달과 뒤늦은 관측](storage.md)이 소유한다. 결과를 확인하려고 가짜 실행이나 불필요한 재실행을 만들지 않는다.

파일 참조는 `id`, `plan_id`, 필요한 `attempt_id`, `role`, `location`, `sha256`을 가진다. 이번 검증의 `role`은 `log` 또는 `report`이고 해당 시도가 필수이며 `location`은 앞서 정한 경로 참조다. 설치 후보는 계획, 적용 직전 사본은 실제 시도에 연결하는 [자료 소유 — 「공통 기록과 기능별 연결」](storage.md)를 따른다. 같은 보고서를 여러 결과가 참조할 수 있고 사본을 매번 늘리지 않는다. SHA-256은 실제로 보존한 내용의 기준이며 요구사항 충족이나 비밀값 제거의 완전성을 증명하지 않는다.

실제 자격증명은 인자, 환경, 로그, 보고서 사본에 기록하지 않는다. 실행에는 별도 주입 수단을 쓰고 기록에는 설정 이름만 남긴다. 일반 출력도 무조건 복제하지 않고 [비기록 기준 — 「비밀값을 남기지 않는 문서화」](../module.md)에 맞는 수집 범위를 정한다. 필요한 근거를 안전하게 남길 수 없으면 그 제한을 보고하며 빈 로그로 성공을 꾸미지 않는다.

## active의 참조와 본문

active는 짧은 Markdown으로 유지한다. 기계가 읽는 연결 정보와 사람이 읽는 의미를 구별하기 위해, 제목 바로 아래 첫 `json` 코드 블록에 다음 참조를 두는 후보다.

```json
{
  "task_id": "example-task",
  "project_id": "example-project",
  "code_root": "C:/Work/app",
  "wiki_root": "C:/Work/wiki",
  "plan_id": "example-plan"
}
```

계획이 없는 순수 문맥 인계에서는 `plan_id`를 생략한다. 이런 경우 active를 읽기 위해 빈 DB를 만들거나 설치 이력을 조회하지 않는다. 루트는 이 active가 다룬 대상의 기준이므로 현재 연결과 다르면 대조한다. 파일을 읽었다는 이유만으로 설정이나 권한을 변경하지 않는다.

| 본문 제목 | 메인이 남길 내용 |
| --- | --- |
| 목표와 범위 | 부모 작업, 현재 단위와 이번에 다루지 않는 범위 |
| 조건과 합의 | 유효한 사용자 조건, 승인 범위와 미합의 선택. 호스트의 실제 권한 증명과 구별 |
| 현재 상태 | 확인한 완료, 남은 의무, 미확인 실행과 해당 기록 참조 |
| 다음 작업 | 다음 행동과 재개 전 확인할 항목, 필요한 문서/제목 |

모든 로그, 계획 필드, 지난 대화를 본문에 복사하지 않는다. 상태 문장은 설명이고 검사 결과의 원본은 DB다. 반대로 DB에 결과가 있어도 사용자의 의미, 다음 행동을 대신 생성했다고 보지 않는다. 메인이 active를 수정할 때는 읽었던 내용 해시를 저장 코드에 전달하고, 그 사이 다른 편집이 있으면 덮지 않고 대조한다. 해시 대조만으로 모든 파일 경합을 차단했다고 보장하지 않는다.

## 저장과 조회 순서

아래는 로컬 제외와 저장 준비가 끝난 뒤의 공통 기록 순서다. 최초 설치에서 아직 준비되지 않았다면 [첫 기록 생성과 인계](../runtime/install.md)의 보존 순서를 먼저 사용한다. 위치는 사용자별 앱 데이터를 기본으로 검토하는 초안이며, [최초 자료 형식 — 「최초 보존 자료의 형식」](records.md#%EC%B5%9C%EC%B4%88%20%EB%B3%B4%EC%A1%B4%20%EC%9E%90%EB%A3%8C%EC%9D%98%20%ED%98%95%EC%8B%9D)과 [인계 조건 — 「프로젝트 기록으로 인계」](records.md#%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EA%B8%B0%EB%A1%9D%EC%9C%BC%EB%A1%9C%20%EC%9D%B8%EA%B3%84)을 아래에 연결했다. SQL 저장 경계는 [조건부 갱신과 트랜잭션](storage.md)의 후보이며 제품 저장 구현과 실제 파일 기반 내구성 시험은 아직이다.

| 시점 | 일반 코드가 처리할 것 | 실패/중단 뒤 소비 |
| --- | --- | --- |
| 계획 보존 | 대상과 필드/참조를 확인해 계획을 저장. 사용한 계획 본문은 시도 뒤 수정하지 않음 | 계획을 못 저장했다면 해당 실행을 시작하지 않음 |
| 실행 직전 | 현재 입력, 실제 명령과 `prepared` 시도를 짧은 DB 트랜잭션에 저장하고 commit 확인 | 이전 준비 기록을 발견해도 실제 미실행으로 단정하지 않음 |
| 실행과 수집 | DB 쓰기 트랜잭션 밖에서 실행. 해당 시도의 관측 사실과 필요한 출력 확보 | 알려진 실행은 계속 추적하고 미확인은 대조. 기록을 고치려고 같은 명령을 재실행하지 않음 |
| 결과 보존 | 보존할 파일의 내용/대응을 확인한 뒤 결과, 파일 참조와 종료 사실을 함께 DB에 저장 | 파일만 남았다면 미확인 자료로 보존. 로그만으로 종료 코드를 만들어 넣지 않음 |
| 의미 갱신 | 결과가 바꾼 의미, 남은 의무와 다음 행동이 있을 때만 active 갱신 | DB가 진행됐지만 active만 낡았다면 근거를 읽어 본문 갱신. 확인된 실행을 반복하지 않음 |
| 조회와 완료 | 해당 작업/계획의 의무, 관련 결과와 미확인을 조회 | 현재 유효한 의무를 대조하며 최신 시도 하나로 전체 성공을 판정하지 않음 |

공통 코드의 입력 대조와 DB 제약으로 참조와 중복을 검사한다. 같은 관측 ID로 같은 사실을 다시 저장하는 요청은 기존 결과를 반환하고, 다른 사실이면 충돌로 거부한다. `prepared`에서 관측 사실이 추가되는 정상 전환과 이미 확정한 결과의 덮어쓰기는 구별한다. 참조가 없는 시도, 계획에 없는 검사 결과, 다른 작업의 이전 ID, 순환 참조를 허용하지 않는다.

연결별 외래키 활성화, 필수 값과 참조 제약은 [관계와 키](storage.md)를 따른다. DB의 형식 버전은 메타데이터의 `schema_version` 한 곳에 두고 지원하지 않는 형식은 보존한 채 안내한다. 버전 숫자를 파일명, 필드명마다 붙이지 않는다.

조회와 재개는 기존 DB를 여는 경로와 새 작업의 명시적 생성을 구분한다. Python의 일반 `sqlite3.connect()`는 파일이 없으면 DB를 만들 수 있으므로, 재개에는 기존 파일만 여는 모드와 오류 구분이 필요하다. [Python sqlite3 문서](https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris). 자료 없음, 권한 부족, 손상, 미지원 형식을 같은 빈 결과로 반환하지 않는다.

짧은 DB 트랜잭션이 active, 로그 파일, 원격 변경까지 함께 되돌리지는 않는다. [SQLite의 원자적 commit](https://www.sqlite.org/atomiccommit.html)은 DB 내부 변경의 보장이며 여러 자료의 대응, 백업/복원은 [기존 보존 계약 — 「백업과 저장 형식 변경」](recovery.md)을 따른다. 정확한 journal 모드, 내구성 설정과 파일 교체 수단은 Windows 시험 전 명세에서 정한다.

조회 결과는 필요한 계획과 다음 항목만 반환하는 후보다. 전체 DB나 모든 로그를 AI 입력으로 보내지 않는다.

| 조회 항목 | 용도 |
| --- | --- |
| `unresolved` | 아직 해소되지 않은 실패와 원래 시도 참조. 다른 검사의 성공으로 삭제하지 않음 |
| `pending` | 미실행, 입력 변화로 재확인이 필요한 의무, 미확정 선택과 필수 CI |
| `unknown_attempts` | 실제 실행/종료/결과 대조가 필요한 시도만 반환 |
| `evidence_refs` | 현재 대조에 쓴 결과 참조. 원문은 요청한 부분만 추가 조회 |

이는 저장 사실에서 얻은 조회 응답이며 별도 완료 상태 파일이 아니다. 도구는 구조와 필요한 근거를 점검하고, 메인은 검사 충분성과 현재 사용자 조건까지 확인한다. 필수 CI나 의미 검토가 남으면 목록이 일부 비었다는 이유로 전체 완료하지 않는다. 필요한 근거가 조회 한도를 넘으면 남은 항목이 있음을 표시해 이어 읽으며, 잘라낸 응답을 전체 목록인 것처럼 반환하지 않는다.

### 최초 보존 자료의 형식

11/16 명세 초안은 **첫 제외 준비도 같은 SQLite 기록 코드로 처리**하는 방식이다. 위치만 설치 명세의 외부 보존 공간을 사용하고, 원문 사본은 기존처럼 파일로 둔다. 별도 JSON 진행 엔진을 만들지 않아 상태 전환과 오류 처리를 재사용할 수 있지만, 프로젝트 DB로 옮기는 절차와 시험은 필요하다. 작은 변경 하나에는 JSON이 더 짧을 수 있으므로 코드량과 실패 처리의 실제 복잡성은 구현 때 비교한다. SQLite 채택을 모든 형식의 강제 통합으로 확대하지 않는다.

| 보존 내용 | 소비와 제한 |
| --- | --- |
| 설치 `task_id`, 적용 `attempt_id`, 요청 범위와 배포 출처 | 같은 설치의 재개와 새 설치를 구분. 검사 계획이나 PASS를 대신 만들지 않음 |
| 확인한 작업 사본, 코드와 WIKI 루트, 설정 출처 | 재실행 대상 대조. 같은 프로젝트 ID만으로 다른 clone의 상태를 이어받지 않음 |
| `.gitignore`의 원래 바이트 또는 부재, 후보와 허용한 복원 범위 | 미커밋 편집과 줄바꿈까지 보존. 내용 해시만 저장하고 원문을 버리지 않음 |
| 실제 반영 관측, 미확인 사실과 필요한 검사 참조 | 후보와 파일이 같다는 관측을 도구가 썼다는 증거나 설치 완료로 바꾸지 않음 |
| 사본의 `artifact_id`, 시도 참조, 상대 위치와 내용 해시 | 보존 완료와 인계 전후 내용 확인. 비밀값과 무관한 프로젝트 자료는 수집하지 않음 |

초기 DB 생성이 실패하면 프로젝트를 수정하지 않고, 보존 파일만 남았어도 준비 완료로 읽지 않는다. `root: state` 참조는 그 기록을 소유한 보존 공간을 기준으로 해석한다. 인계 뒤에는 복사와 검증이 끝난 프로젝트 상태 영역에 연결하며, 외부 경로를 장기 설정의 두 번째 원본으로 남기지 않는다. 이 초기 작업 때문에 빈 active나 전체 코드/WIKI 사본을 만들지는 않는다.

### 프로젝트 기록으로 인계

11/17 사용자가 [최초 DB의 위치 전환 B — 「최초 인계 방식 재검토」](storage.md)를 채택했다. **같은 사용자의 같은 로컬 설치에서 전체 기록을 보존하고 진행 위치를 프로젝트 안으로 넘긴다.** 처음부터 유효한 프로젝트 DB와 제외가 있으면 그 기록을 재사용한다. 팀원의 DB나 관계없는 기존 DB를 합치는 기능은 아니다.

초기 DB는 해당 설치 전용이며, 새 후보에 같은 형식의 일관된 사본을 만든다. 논리 DB 식별, 작업/시도, revision과 과거 이력을 그대로 보존한다. 살아 있는 기존 프로젝트 DB를 덮지 않으며, 손상/미지원 형식이나 다른 작업 사본이면 원인을 확인한다. 미완료 인계를 새 설치로 우회하지 않는다.

| 순서 | 처리와 다음 조건 |
| --- | --- |
| 1. 인계 준비 | 제외 효력과 실행 소유를 확인하고 허용된 새 후보를 확보한 뒤 초기 진행의 일반 쓰기를 멈춤. 인계 시도, 고정할 DB 내용과 파일 목록을 저장 |
| 2. 사본 준비 | 새 후보에 DB 사본과 필요한 파일을 보존. 원본과 내용, 제약, 참조를 대조하며 관계없는 기존 대상과 유일한 원본은 보존 |
| 3. 대상 수신 | 같은 인계와 고정 자료를 확인한 대상에 수신 사실을 저장. 아직 후속 설치/업데이트를 시작하지 않음 |
| 4. 원본 확인 | 대상 수신과 자료를 다시 확인하고 초기 DB에 인계를 넘겼다는 기록을 저장. 초기 사본의 일반 쓰기는 계속 차단 |
| 5. 대상 활성화 | 원본 확인과 같은 수신의 대응을 대조한 뒤 대상의 인계 시도 종료/활성화를 함께 저장. 다음 설치 단계부터 이 DB에 기록 |

[인계 파일의 목록과 참조](storage.md)에 보관 파일, 이미 정리된 자료와 외부 원문을 구분했다. 예를 들어 첫 제외 설정 전 `.gitignore` 사본이 `state/runs/<시도>/`에 있다면, 그 사본을 같은 상대경로로 보존해 프로젝트 DB에서 복원에 사용할 수 있어야 한다. 실제 코드의 `.gitignore`를 이 인계가 다시 쓰지는 않는다. DB만 옮긴 뒤 옛 외부 폴더에서 원문을 찾아오는 상태는 인계 완료가 아니다.

[인계 기록과 실제 위치](storage.md)는 DB 식별과 실제 사본의 역할을 구분한다. DB ID와 revision이 같다고 두 사본에 모두 쓸 수 있는 것은 아니다. [인계 단계와 쓰기 허용](storage.md)은 현재 위치, 단계와 목적에 따라 공통 쓰기 진입을 제한한다. 정확한 물리 위치/파일 소유와 Windows 프로세스 검증은 남아 있다.

같은 인계 시도와 같은 내용이면 기존 수신을 사용하고, 다른 내용이면 충돌로 처리한다. 현재 인계 행만 고정 내용 해시에서 제외하며 그 인계의 시도 행과 이전 이력은 포함한다. 수신/확인/활성화의 변경은 별도로 대조한다. 정상 활성화 뒤 후속 작업이 쌓였다면 불변 수신 자료로 최초 인계 사실을 확인하고 현재 DB를 초기 사본과 같게 되돌리지 않는다.

| 중단 뒤 남은 상태 | 이어갈 범위 |
| --- | --- |
| 준비 뒤 DB/파일 사본 작성 중 종료 | 원본과 남은 후보를 보존하고 같은 인계의 사본 검증부터 계속. 제외 적용을 반복하거나 참조 없는 파일을 자동 삭제하지 않음 |
| 대상 수신은 저장됐지만 원본 확인이 없음 | 같은 수신과 고정 내용을 대조해 원본 확인부터 계속. 수신 재발급과 후속 효과의 선실행 금지 |
| 원본 확인 뒤 대상 활성화 전에 종료 | 양쪽 대응을 확인해 대상 활성화부터 계속. 초기 DB의 일반 쓰기를 다시 열지 않음 |
| 대상 활성화 뒤 후속 작업 진행, 외부 보존 사본 정리 | 현재 프로젝트 DB에서 계속. 초기 사본을 필수 입력으로 요구하거나 오래된 사본으로 되돌리지 않음 |
| 필요한 사본/확인 자료 누락, 활성화된 대상의 손상/부재 | 남은 근거를 보존하고 복구로 반환. 낡은 초기 DB에서 현재 설치를 조용히 재개하지 않음 |

SQLite 트랜잭션은 [해당 DB의 저장 경계](https://www.sqlite.org/lang_transaction.html)다. 이 설계는 초기 DB, 대상 DB와 파일 복사 전체가 한 번에 commit된다고 가정하지 않는다. 각 단계의 저장 결과와 실제 파일을 대조하며, 실패한 트랜잭션의 상태와 실제 commit 여부를 확인하지 못하면 미확인으로 남긴다.

초기 사본의 삭제는 활성화와 별개로 [설치 완료 뒤 정리](../runtime/install.md)를 따른다. 남아 있는 현재 의존과 검증 결과를 확인하기 전 유일한 근거를 지우지 않는다. [새 메모리 검사](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md)는 보존과 단계/재시도를 부분 확인했으며 실제 파일 인계, Windows 강제 종료나 전원 장애 검증이 아니다. 이전 행별 수신안과 당시 결과는 [판단 이력 — 「최초 기록의 행별 수신안」](../../discussions/history/install.md)으로 보존한다.

## 재시도와 재개의 예시

API와 core 검사가 필수인 가상 계획을 가정한다. 아래 식별자는 설명용이며 실제 검사 결과가 아니다.

| 기록 | 뜻 | 다음 판단 |
| --- | --- | --- |
| P의 API 의무, A1의 API FAIL | 같은 계획/의무와 실패 근거 보존 | API 미해결 |
| A2의 core PASS | core 의무의 성공만 확인 | API 실패는 그대로 남음 |
| 수정 뒤 A3의 API PASS | A1과 같은 API 의무를 현재 입력에서 새 실행 | API의 현재 근거를 확인. 수정이 core에도 영향을 줬다면 core는 다시 대조 |
| A3 결과 저장 뒤 active 갱신 전 중단 | DB는 진행됐고 active는 과거 상태 | A3와 현재 입력을 확인해 active 갱신. API 무조건 재실행 금지 |
| 종료 기록 없이 로그 파일만 남음 | 내용은 있으나 종료/결과 대응 미확인 | 파일 보존과 실행 대조. 로그 존재만으로 PASS나 미실행을 단정하지 않음 |

원래 실패의 해소는 같은 의무의 유효한 후속 근거로 판단한다. 완료된 동일 입력의 근거를 다시 읽는 것과, 입력 변경 후 검사 호출을 생략하는 자체 캐시는 [기존 재사용 기준 — 「재사용을 판단하는 순서」](verification.md)대로 구별한다.

## 다음 명세와 시험

필드와 조회 계약을 초안으로 연결했으며 공개 인터페이스가 확정되거나 저장 코드가 구현된 상태는 아니다. 이 명세를 사용하는 [설치/기능 추가 — 「설치 기록과 단계 연결」](../runtime/install.md)와 [반영/완료 — 「반영 기록과 완료 연결」](../runtime/update.md)의 입력, 결과/실패 연결 초안도 작성했다. WIKI 반영과 CI/PR 근거는 각 기능의 자료 소유를 유지한다.

로컬 검증과 설치/인계의 관계 후보는 [저장 규칙](storage.md)에 작성했다. 11/16 연결/형식 호환 뒤 DDL을 작성했고, 11/17에는 [유지 관리 관계 — 「저장 필드와 소비자」](maintenance.md)와 [현재 의존을 찾는 입력](maintenance.md)을 연결했다. assessment는 당시 판정/근거를 보존하고 현재 보호/정리 관계는 DB에서 관리한다. 같은 상태를 별도 수정 가능한 JSON에 복제하지 않는다. 유지 관리 관계의 인계 순서와 형식 변경 보존 조건을 대조했으며 다음은 [과거 전환 기록의 수신 제한 — 「과거 형식 변경 기록의 수신 경계」](storage.md)을 해결할 저장 경로다. Windows 실행 소유, 파일 보호와 실제 재개 검증도 남아 있다. 이 항목을 구현 때 알아서 처리한 것으로 넘기거나 4단계 전체를 완료로 표시하지 않는다. 새로운 보장 범위의 선택이 필요하면 그 부분만 협의한다.

시험은 [최초 보존과 인계 — 「최초 기록 생성의 검증 입력」](../../verification/acceptance.md), [자료/백업 검증 — 「복구 자료와 백업의 검증 입력」](../../verification/acceptance.md), [중단 지점 — 「저장과 반영의 중단 지점」](../../verification/acceptance.md)에 연결한다. 형식 검사 뒤 실제 Windows 저장, 중단/재개, 실제 AI의 의미 복구를 각각 확인하며 문서나 모의 결과를 제품 PASS로 쓰지 않는다.
