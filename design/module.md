# 모듈의 소유와 구성

공통 원본, 프로젝트 적용본의 책임, 기본 모듈의 시작점과 기능 구성을 다룬다. 설치 절차는 [설치와 보존](runtime/install.md), 도구별 연결은 [진입 명세](runtime/entry.md), 시작 대상과 사용자별 목록은 [프로젝트 선택](runtime/project-selection.md), 정보 역할은 [WIKI](knowledge/wiki.md), 로컬 상태는 [작업 상태](workflow/recovery.md)가 소유한다.

프로젝트를 고른 다음 기본/사용자 지정 설치본을 찾고 그 코드에 실행을 넘기는 상세는 [프로젝트 설치본 발견과 실행 인계](runtime/project-entry.md)가 소유한다.

제품 전체의 [사용자 조작 최소화 원칙 — 「사용자 조작을 줄이는 실행 원칙」](architecture.md)을 설치, 평소 실행과 유지 관리에 적용한다. 외부 설치기의 프로젝트 설치와 명령만 준비/복구/제거하는 진입은 [설치와 명령 관리](runtime/management.md)가 소유한다.

제품의 중심은 조건부 하네스이며 역공학은 필수 제공하는 도입, 보강 기능이다. 신규/기존 프로젝트의 공통 사용 흐름은 [제품의 중심과 도입 경로](architecture.md)가 소유한다. 아래 ‘설치 파일’은 일상 실행에 필요한 구성과 임시 설치 도구를 구분해 읽는다([설치 도구와 설치 후 구성 — 「설치 결과의 소유와 공유」](runtime/install.md)).

11/08 문서 정리: 기존 주제 본문을 분리했다. 판단 날짜, 채택 상태는 원문과 연결된 ADR을 따른다.

## 원본과 적용본

공통 모듈과 프로젝트 WIKI는 도구와 그 도구의 설정, 입력 관계다. 함께 사용하는 것이 모순은 아니며, 어디서 수정하고 어떤 버전을 사용하는지를 분리해야 한다.

공통 배포 코드, 적용 프로젝트의 지식/상태, 사용자별 연결을 구분한다. 기존 작업 환경의 연결 도구를 제품 설치기로 이름만 바꾸지 않으며 일반 연결은 [프로젝트 WIKI 연결](knowledge/wiki.md)에서 다룬다.

```text
작업 공간/
├── module/          독립 Git 저장소: 공통 원본, 분석/설치, 자체 문서, 테스트
├── project-a/       첫 적용: 프로젝트 전용 지침, 설정, 연결, 기존 WIKI, 앱
├── project-b/       별도 설정을 사용하는 적용 사례
└── project-c/       추가 호환 검증 사례
```

`module`은 설명용 이름이다. 공식 원본과 릴리스는 독립 저장소 한 곳에서 관리하고, 소비 프로젝트는 설치 결과와 자기 변경을 소유한다. 위 트리는 개발 저장소와 적용 대상을 보여준다. 11/11 [ADR 0019](../decisions/runtime/0019-project-install.md)로 프로젝트 내 실행 구성 설치를 채택했다. 필요한 skill, hook, script, 설정은 소비 프로젝트에 남고 외부 도구는 설치/갱신을 맡는다. 현재 소유, 공유 기준은 [설치 구성표 — 「설치 결과의 소유와 공유」](runtime/install.md)를 따른다. 소비 프로젝트에 필요한 실행 파일을 설치하는 것과 모듈의 개발 원본, 이력 전체를 포함하는 것은 다르다. 개발자의 옆 디렉토리나 절대 경로를 실행 의존성으로 삼지 않는다.

### 수정 책임

| 대상 | 원본과 수정 책임 | 갱신 원칙 |
| --- | --- | --- |
| 공통 계획, 실행, 검증, 복구 코드 | 공식 원본은 모듈 저장소, 설치 결과의 사용자 변경은 적용 프로젝트 | 공식 릴리스는 유지보수자가 발행. 사용자는 설치된 코드도 수정할 수 있으며 갱신 때 그 편집을 보존, 비교. 공식 원본 반영이나 별도 버전 발행을 강제하지 않음 |
| 특정 도구의 공통 연결 코드 | 공식 원본은 모듈 저장소, 설치 결과는 적용 프로젝트 | 공식 지원 도구, 버전 계약 안에서 시험. 공식 기본값에 특정 제품 이름, 모듈 구조를 넣지 않으며 사용자 수정은 위 보존 원칙 적용 |
| 검사 명령, 모듈, 문서 경로, 예외 | 적용 프로젝트 | 원본 빌드 설정을 우선 읽고 필요한 정책/보정만 명시. 현재 boot 예외를 공통 기본값으로 복제하지 않음 |
| 요구사항, 설계, ADR, 운영 지식 | 적용 프로젝트 | 분석으로 후보를 작성하고 검토 후 채택. 사람이 편집한 문서를 설치 갱신으로 덮지 않음 |
| 기존 AGENTS, 도구 설정과의 연결 | 기존 파일은 프로젝트, 추가 영역은 소유 범위 명시 | 파일 전체 교체 대신 변경 후보를 제시. 공통 설치부와 사용자 편집을 구분하고 충돌 시 중단 |
| 공식 출처, 관리 범위와 이전 생성 기준 | 담당자의 관리 도구가 기록/조회. 비밀 없는 기준은 설치 결과와 공유 권장 | 갱신 비교와 관리 작업에 사용. 일반 팀원의 직접 편집이나 매 개발 요청의 선행 읽기 자료가 아님. 파일명/위치는 [설치 명세 — 「설치 기록과 단계 연결」](runtime/install.md)의 후보 |
| 실행 결과, 재개 상태, 원시 로그 | 해당 프로젝트/실행 | 로컬 상태, 캐시, 임시 출력은 .harness 전체 제외 원칙 적용. 공유할 검증 근거는 필요한 내용을 검토해 별도 문서로 기록. [상태 경계 — 「작업 상태와 Git 제외」](workflow/recovery.md) |

지원하는 Java, Gradle, Codex 같은 도구 의존성과 특정 제품의 모듈명, URL, 예외 의존성은 구분한다. 모든 상수를 없애는 것이 목표는 아니다. 공식으로 배포할 개선은 모듈 원본에 반영하되 소비 프로젝트의 원문 WIKI를 흡수하지 않는다. 사용자 설치본의 변경을 모두 공식 원본에 제출하도록 요구하지 않는다. 11/10에는 기존 표의 ‘프로젝트별 복사본 상시 수정 금지’가 사용자 수정 자유와 충돌함을 확인해 바로잡았다.

11/02 추가 요청의 도구별 skill/hook 경로는 [호환성 검토 — 「AI 도구 호환성」](../discussions/integration/ai-tools.md)와 채택된 [ADR 0015](../decisions/integration/0015-agent-support.md)에 연결했다. `.agents`로 전체 경로를 옮기는 결정은 하지 않았다.

WIKI의 내부/외부 원본, 선택 Obsidian, Git 운영 상세는 [저장 검토](../discussions/knowledge/storage.md)와 [ADR 0016](../decisions/knowledge/0016-storage.md)에서 협의한다. 11/05 외부 문서만 Windows에 두는 지원 방향을 수용해 ADR 0013을 보완했다. 같은 작업의 앱, WIKI 버전 연결과 PR 생성/연결, 검사 자동화, 사람의 승인 방향은 [ADR 0017](../decisions/integration/0017-work-sync.md)에 채택했다.

기록, 권한, 복구 상세는 후속 명세 대상이며 CI 구현을 기본 WIKI, 검증, 복구보다 먼저 진행하지 않는다. 저장 위치를 바꾸더라도 [정보 역할 — 「최소 WIKI」](knowledge/wiki.md)과 [원문 보존, 설치 조건 — 「기존 자료 보존」](runtime/install.md)을 충족해야 하며, 경로 이동만으로 연결 완료를 선언하지 않는다.

문서 구조는 현행 트리 전체 복사 / 최소 역할과 경로 연결 / 소수 거대 파일 중 **최소 역할과 경로 연결**을 2026-10-29에 채택했다([ADR 0008](../decisions/knowledge/0008-document-scope.md)). 저장소는 미추적 하위 폴더 / 독립 저장소 / submodule 중 **독립 저장소와 버전 지정 적용**을 채택했다([ADR 0009](../decisions/architecture/0009-repositories.md)). 장단점은 각 ADR에서 관리한다.

worktree는 같은 저장소의 작업 트리이므로 독립 모듈 저장소를 대신하지 않는다. submodule은 독립 이력을 참조하는 대안이나 첫 적용의 필수는 아니다. 독립 로컬 Git 기록과 원격 공개도 별개다. [Git worktree](https://git-scm.com/docs/git-worktree), [submodules](https://git-scm.com/docs/gitsubmodules), [init](https://git-scm.com/docs/git-init).

### 기본 모듈의 시작점

11/05 사용자가 모듈 세팅 B안인 **설계 → 독립 기본 모듈 준비, 검증 → 기준 커밋 → 기능별 발전**을 채택했다. 시작점의 세 대안과 비용은 [ADR 0009 — 「기본 모듈의 시작점」](../decisions/architecture/0009-repositories.md)에 있다. 아래 구성의 정확한 파일, 검사, 커밋 단위는 협의용이며 아직 구현하지 않았다. 여기서 기본 모듈은 개발 출발점이다. 최종 사용자가 받는 필수 설치 구성과는 다르며, WIKI, 검증, 복구 등 합의한 최종 목표를 축소하지 않는다.

| 준비할 것 | 기준점에 포함할 범위 | 이후 기능별로 발전시킬 부분 |
| --- | --- | --- |
| 공통 원본 | 현재 구조에서 재사용할 책임, 파일을 추려 독립 저장소에 배치. 배포 제외와 기존 소비 연결을 함께 정리 | 설계에 따른 기능 개선, 통합, 확장 |
| 프로젝트 연결 | 코드 프로젝트의 모듈명, 경로, 검사 명령, 문서 위치, 예외를 입력/설정 책임으로 분리. 필수 입력 누락을 조용히 기본값으로 처리하지 않음 | 코드, 이력 분석을 통한 연결 후보 생성과 증분 WIKI 보완 |
| 이름과 참조 | 합의한 파일, 필드, skill, config 등의 이름과 호출, 라우팅, 설명, 검사를 함께 변경 | 이후 새 기능에도 같은 명명 규칙 적용 |
| 실행 기준 | 남길 최소 흐름을 다른 이름, 경로의 작은 예제에서 실행하고 실제 결과 확인 | 검증, 복구 개선, 설치와 갱신, 보존의 전체 사례 |
| 개발 안내와 검사 | 지원 환경, 실행 방법, 현재 되는 범위, 미구현/알려진 결함, 기본 동작을 확인할 관련 검사와 시험 자료 | 기능별 회귀 검사, 실제 이식, 사용 문서 완성 |

현재 boot 예외나 제품 문서 내용은 공통 기본값으로 옮기지 않는다. 지원 도구가 요구하는 고정 경로, 식별자까지 임의로 바꾸지 않으며, 이름 변경 전에는 인식 조건, 호출부를 확인한다. 프로젝트 값을 제거한 자리를 빈 문자열이나 특정 제품용 숨은 기본값으로 채우면 독립화가 끝난 것이 아니다.

기준점의 완료 조건은 다음과 같이 제안한다.

1. 합의한 초기 파일, 기능과 모든 소비 연결을 확인하고, 원래 작업 폴더 없이 선언한 환경, 설정으로 실행한다.
2. 다른 이름, 경로의 작은 예제에서 정한 정상 흐름을 확인하고, 필요한 설정/입력이 없으면 명확한 미완료, 오류로 남긴다. 성공으로 표시하는 빈 구현을 두지 않는다.
3. 변경한 이름, 경로의 참조가 맞고 선택 범위에서 죽은 연결, 제품 전용 의존이 남지 않는다. 이름 검색만으로 확인을 끝내지 않고 실제 읽기, 호출, 결과도 대조한다.
4. 미구현 기능과 기존 결함을 명시한다. 남긴 흐름의 성공 판정이나 독립 실행을 깨뜨리는 결함은 기준점의 완료를 막으며, 기능 제외가 필요하면 범위를 협의한다. 기본 모듈 완료를 최종 제품 검증 통과로 표시하지 않는다.

`fixture`는 이 기본 모듈을 시험하는 예제 프로젝트, 입력, 상태를 가리키는 데 사용하고, 개발 대상 자체는 **기본 모듈**, 준비가 끝난 Git 위치는 **기준 커밋**으로 부른다. 준비가 작으면 하나의 세팅 커밋으로 닫을 수 있다. 크면 연결이 유지되는 준비 커밋으로 나누고 마지막 검증된 커밋을 기준으로 삼는 안이다. 이후 기능 변경과 큰 기계적 이름 변경은 검토, 회귀 확인 범위가 보이도록 분리한다.

기준 구현의 원래 상태는 전후 비교 근거로 보존한다. 종속 제거, 이름 변경을 거친 기본 모듈을 변경 전 원본과 동일하다고 보고하지 않는다. 원본 해시와 추출/수정 범위의 대응을 기록한다.

정확한 초기 파일, 남길 흐름, 검사, 커밋 단위는 기존 [진행표](../development/roadmap.md)의 파일별 명세와 개발 준비에서 확정한다. 그 뒤 첫 구현에서 기본 모듈을 만들고 검증한다. 이 설명을 이유로 현재 설계를 건너뛰어 저장소를 만들거나 초기 코드를 생성하지 않는다.

### 모듈 자체의 WIKI

OnepLoom은 코드 저장소와 독립된 개발 WIKI 저장소를 함께 관리한다. WIKI에는 요구사항, 상세 설계, 토의와 대안, 채택/철회 이유, 검증 계획과 실제 관측, 실패 분석 및 변경 이력을 남긴다. 공개할 WIKI라는 이유로 사용자 안내나 설계 요약만 남기지 않는다.

요구사항, 설계, 결정과 검증 결과를 서로 연결하고, 같은 상세는 소유 문서 한 곳에서 관리한다. 과거 토의는 당시 상태로 보존하며 현재 결정으로 이어 읽을 수 있어야 한다.

11/08에는 개발 WIKI를 독립 Git으로 관리하는 방향을 정했고, 11/23에는 코드와 WIKI를 형제 Git 저장소로 준비했다.

```text
workspace/
├── oneploom/    코드와 개발 규칙, 독립 Git
└── wiki/        OnepLoom의 개발 지식, 독립 Git
```

완료된 기술 내용의 기준은 이 WIKI다. 과거 토의는 당시 상태로 구분하고 최신 결정에 연결한다. 최초 커밋은 개발 기록의 시작이며 기능 완료나 릴리스가 아니다. 아직 원격 저장소를 생성하거나 공개하지 않았다.

여러 Git 저장소를 하나의 개발 프로젝트로 관리할 수 있지만 Git 이력과 접근 권한은 각각 별개다. GitHub Projects나 Organization을 도입했다는 뜻이 아니며, 실제 두 커밋/PR로 대응을 남긴다. [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects).

### 비밀값을 남기지 않는 문서화

분석과 문서 생성에서는 자격증명의 입력/출력 노출을 방지한다. Git 추적 범위를 나누는 것만으로 본문에 섞인 비밀값이 제거되지는 않는다. 아래는 제품에 적용할 조건이며 검출/차단 도구의 구현이나 자료 전체 감사가 끝났다는 뜻은 아니다.

- 분석 입력을 구성할 때 자격증명 파일과 비밀 설정을 제외한다. 허용한 코드, 커밋, 대화 자료에도 값이 섞일 수 있으므로 모델에 전달하기 전 선별, 제거하고, 출력 후보도 검토한다. 알려진 파일명만 제외했다고 안전을 확정하지 않는다.
- 문서, 템플릿에는 설정 이름과 주입 방법, 명백한 자리표시자만 둔다. 실제 값은 로그, 오류, 명령 예시, 근거 사본에도 복제하지 않으며 인증 수단에서 주입한다. 비공개 문서도 자격증명 보관소로 쓰지 않는다.
- 공개할 본문, 링크, 설정, 예시, 커밋 이력, 배포 파일을 확인한다. 미해결 의심 항목은 공개 완료로 처리하지 않는다. 자동 검출과 내용 검토는 보완 수단이며 모든 비밀값의 검출을 보장한다고 쓰지 않는다.
- 기존 자료의 값을 발견하면 원문을 출력하거나 새 백업/근거에 복제하지 않고 소유자에게 알린다. 이미 노출된 값은 삭제만으로 해결되지 않으므로 폐기, 교체와 필요한 이력 처리를 별도 범위로 다룬다. [GitHub 비밀값 관리](https://docs.github.com/en/get-started/learning-to-code/storing-your-secrets-safely).

### 이름과 변경 이력

통용 용어를 우선하고 수정 차수를 이름에 무분별하게 붙이지 않는 기준은 [개발 규칙](../development/standards.md)을 따른다. 명령/설정도 지원 도구의 표준과 연결하며 상세는 [명령과 설정의 표준 적용](runtime/entry.md)에 둔다. ADR 번호와 실제 지원 버전, 과거 관측의 버전은 보존한다.

명명 검토에서는 의미, 공식 용례, 기존 사용처를 대조한다. 문서 형식인 ADR, 그 문서를 찾는 정보 역할, 실제 파일 경로를 구별한다. 역할을 `decision`으로 부르더라도 중요한 아키텍처 결정은 ADR로 기록할 수 있고 기존 README 안의 결정도 연결할 수 있다. 형식 이름을 역할에 적용하려고 기존 문서의 내용을 바꾸거나 파일을 강제로 이동하지 않는다. 실제 적용 사례와 근거는 [위치표 이름 검토 — 「이름 선택의 근거」](knowledge/map.md)에 둔다.

공개 프로젝트의 운영 방식은 모두 같지 않다. 다음에서 확인한 공통점은 사용자에게 의미 있는 변경을 릴리스 기록에서 설명한다는 점이다.

| 근거 | 확인한 방식 | 적용할 점 |
| --- | --- | --- |
| [Click 변경 기록](https://click.palletsprojects.com/en/stable/changes/) | 버전별 변경과 폐기 예정 기능, 관련 변경 링크를 설명 | 내부 수정마다 이름을 바꾸는 대신 사용자 영향과 변경 근거를 찾을 수 있게 함 |
| [Vite 릴리스](https://vite.dev/releases) | SemVer, 변경 기록, 주요 버전 전환 안내 | 호환성 변화와 업그레이드 방법을 릴리스 단위로 설명 |
| [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) | 태그에 릴리스 설명과 배포 파일을 연결 | 배포 버전과 실제 코드 기준점을 연결 |

개발 중에는 역할을 나타내는 이름을 유지하고 수정 근거를 커밋/PR에 남긴다. 중요한 결정은 기존 ADR에 연결하며 코드에서 필요한 이유만 짧게 주석으로 설명한다. 변경 이력을 주석에 계속 쌓지 않는다.

11/09 사용자는 개발 중 작업별 커밋을 쌓고 필수 기능의 최초 배포가 준비되면 태그를 붙이며 이후에도 배포 단위로 버전을 관리할 방향을 재확인했다. 실제 작업 커밋은 [작업 단위와 시작점](../decisions/development/0012-branches.md)을 따른다. 기능 하나에 여러 커밋이 있을 수 있고, 여러 완료 기능을 한 릴리스로 묶을 수도 있다. 모든 커밋, 기능마다 태그를 의무화하지 않는다.

첫 배포 준비에서는 코드 저장소의 CHANGELOG에 사용자에게 의미 있는 변경을 모으고, 검증한 코드 커밋에 `v1.0.0` 태그와 GitHub Release를 연결하는 안을 구체화한다. 태그는 코드 기준점이며 Release는 배포물, 변경 내용, 사용 안내를 제공한다. 패키지 버전이 있다면 `1.0.0`과 같은 릴리스를 가리키게 한다.

기본 모듈의 세팅 커밋은 개발 기준점이고 정식 배포 완료 조건은 [첫 배포 ADR — 「첫 배포의 책임과 보류 항목」](../decisions/architecture/0007-release-scope.md)이 소유한다. [Git 태그](https://git-scm.com/book/en/v2/Git-Basics-Tagging), [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

두 저장소가 바뀐 작업은 관련 PR, 최종 코드/WIKI 커밋을 연결한다. 공개 릴리스에는 검증한 WIKI 커밋을 영구 링크로 연결하는 안을 추천한다. 코드 태그가 다른 저장소의 WIKI 버전까지 자동 고정하지는 않으며 WIKI에 매번 같은 태그를 붙일 의무도 없다. 변경 없는 저장소에 빈 커밋을 만들지 않고, 문서만 정정한 경우에는 해당 코드 버전과 정정 범위를 남긴다. 작업별 부분 반영, 복구는 [ADR 0017](../decisions/integration/0017-work-sync.md)이 소유한다. WIKI는 CHANGELOG를 다시 작성하지 않고 릴리스와 필요한 이행 안내를 연결한다.

후속 버전은 작업의 이름이나 크기보다 공개 계약의 호환성으로 판단한다. 호환되는 오류 수정은 patch, 호환되는 기능 추가는 minor, 호환되지 않는 공개 계약 변경은 major로 구분하는 SemVer를 추천한다. CLI 사용법, 설정/저장 형식, 연결 방식, 지원 조건 중 무엇을 공개 계약으로 보장할지는 첫 배포 전에 명시한다. 단순 내부 리팩터링이나 문서 정정만으로 새 major/minor를 만들지 않는다. 이미 공개한 릴리스 내용, 태그를 조용히 바꾸는 대신 수정 릴리스로 내며, 자동 릴리스 도구, 정확한 파일/절차는 아직 선택하지 않았다. [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), [SemVer](https://semver.org/).

실제로 함께 지원해야 하는 API, 저장 형식의 호환성 식별은 단순 수정 차수와 다르다. 필요하면 계약, 전환, 검증 범위를 먼저 정하고 식별을 유지하며, 기계가 읽어야 하는 버전 정보를 주석으로 대체하지 않는다. 이번 기준을 이유로 새 버전 필드나 버전별 복사 파일을 미리 만들지는 않는다.

### 라이선스와 저작권

11/18 지정한 지속 개발/배포 기준이다. 배포 인원이나 기술 검토 목적과 관계없이 적용한다. 2026-11-24 코드와 개발 WIKI의 MIT 적용을 [ADR 0025](../decisions/development/0025-license.md)로 채택했다. 자체 라이선스 선택이 외부 자산의 권리 확인까지 완료했다는 뜻은 아니다. 사용자에게 매 실행마다 법률 확인을 시키는 기능을 추가하는 뜻도 아니다.

외부 자료를 선택하거나 버전을 바꾸고 복사/수정/동봉/공개하기 전에 공식 출처의 해당 조건을 확인한다. 출처와 버전/커밋, 라이선스 원문, 실제 사용 형태, 요구되는 고지와 미확인을 남긴다. 같은 버전/사용 범위의 유효한 확인은 재사용하되 배포 범위나 조건이 바뀌면 다시 확인한다. 직접/간접 의존성, 코드/문서/템플릿/이미지와 모델을 쓴다면 그 모델의 조건도 실제 포함 범위에 따라 확인한다.

[GitHub의 라이선스 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)처럼 공개 열람 가능성과 재사용 허가는 다르다. 출처 표시만으로 복제 허가를 얻는 것은 아니며, 번역/이름 변경/AI 재작성으로 원래 권리를 없앨 수 있다고 판단하지 않는다. 참고한 사실과 원리를 자기 설계로 설명하는 경우와 보호되는 표현/코드를 가져오는 경우를 구분한다. 권리나 호환 조건을 확인하지 못하면 해당 편입/배포를 보류하고 허가 확인 또는 독립적인 대안을 찾는다. 기존 프로젝트의 다른 작성자 자산도 같은 기준을 적용한다.

| 이번에 확인한 대상 | 공식 근거와 적용 경계 |

| Codex 코드/바이너리를 복사 또는 수정해 배포 | 실제 배포 버전과 구성요소별 조건을 재확인. [Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0)의 라이선스 사본, 수정 사실, 해당 저작권/귀속 고지와 원본에 포함된 관련 NOTICE 의무를 처리. 현재는 동봉/수정 재배포를 선택하지 않음 |

위 확인일은 2026-11-18이며 외부 main의 이후 변경까지 보증하지 않는다. 시작 명령은 원래 `codex`를 덮거나 OpenAI 공식 제품으로 표시하지 않고 [고유 이름 기준 — 「명령 이름과 충돌 방지」](module.md#%EB%AA%85%EB%A0%B9%20%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EC%B6%A9%EB%8F%8C%20%EB%B0%A9%EC%A7%80)을 따른다. 모듈의 라이선스와 배포에 필요한 고지 파일은 실제 포함 자산/의존성이 정해지는 개발 준비와 릴리스 점검에서 확정한다. 코드와 공개 WIKI의 적용 조건도 구분하며 자동 검사 결과만으로 권리 문제가 없다고 선언하지 않는다.

### 명령 이름과 충돌 방지

11/15 사용자 요구: 배포 명령은 기존 명령과 충돌하지 않는 이름을 사용한다. 11/22 채택한 [제품 이름 — 「제품 이름과 변경 기준」](module.md#%EC%A0%9C%ED%92%88%20%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EB%B3%80%EA%B2%BD%20%EA%B8%B0%EC%A4%80)에 따라 **하나의 제품 명령 `oneploom` 아래 하위 명령과 옵션**을 둔다. `oneploom start`, `oneploom resume`, `oneploom wiki ...`는 사용 형태를 설명하는 예시이며 아직 설치된 명령은 아니다. 이름 채택으로 하위 명령의 미완료 계약까지 확정하지 않는다. 범용 단어 `init`, `start`, `check`와 기존 `codex`를 전역 별칭으로 덮지 않는다.

이름 선택만으로 모든 사용자와 미래 프로그램의 명령을 전역 예약할 수는 없다. 설치 시 대상 셸의 별칭, 함수와 PATH에서 같은 이름을 확인하고 충돌하면 등록하지 않은 채 실제 경로와 대체 명령을 안내한다. Windows의 대소문자와 `.cmd`/`.ps1` 등 실행 후보도 확인한다. 기존 명령을 시험 실행해 정체를 판단하거나 기존 별칭을 자동 제거하지 않는다. 이미 같은 모듈이 등록한 진입점이면 소유와 경로를 대조해 재사용하며, 제거할 때도 소유한 등록만 처리한다.

PowerShell은 별칭, 함수, cmdlet, 외부 실행 파일 순서로 이름을 찾으며 `Get-Command -All`로 같은 이름의 후보를 확인할 수 있다. 셸마다 탐색 규칙과 세션의 별칭이 다르므로 Python에서 PATH만 조회한 결과를 모든 충돌 검사로 대신하지 않는다. 등록 뒤 설치 경로와 `--help` 등 모델을 호출하지 않는 동작을 확인하고, 짧은 명령을 등록하지 못해도 명시적 경로로 실행할 수 있게 한다. [PowerShell 명령 우선순위](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_command_precedence).

11/23 명명 기준 보강: **고유성은 제품 진입점 oneploom으로 드러내고, 하위 동작은 의미가 익숙한 짧은 이름을 쓴다.** 예를 들어 start/connect처럼 역할을 바로 읽을 수 있게 하며 각 하위 명령마다 브랜드 접두어를 반복하거나 실행 의미가 불명확한 약어를 만들지 않는다. 사용 횟수가 적은 명령을 한 글자로 줄이기보다 목적별로 묶고, 평소 기본 진입은 무인자 oneploom을 유지한다.

옵션은 설명적인 --긴이름을 기준으로 하며 자주 쓰거나 통용되는 경우에만 -짧은이름을 같은 기능의 별칭으로 제공할 수 있다. 두 표기를 모두 지원하는 의무는 아니며 같은 기능에 불필요한 이름을 여러 개 만들지 않는다. 정확한 옵션과 전달 경계는 [명령 표준 적용 — 「명령과 설정의 표준 적용」](runtime/entry.md)이 소유한다.

명령과 하위 명령의 이름/옵션은 공개 인터페이스로 관리하고 수정 차수를 이름에 붙이지 않는다. skill 이름과 도구 내 트리거는 해당 도구의 발견/충돌 기준으로 확인한다. 새 셸을 지원할 때는 실제 검증 범위를 정하며 개발 환경의 기존 별칭을 그대로 제품 명령으로 복사하지 않는다.

### 제품 이름과 변경 기준

2026-11-22 사용자가 **OnepLoom**으로 진행하기로 선택했다. 표시 이름은 `OnepLoom`, 제품 명령의 소문자 표기는 `oneploom`으로 맞춘다. 나중에 더 적합한 이름을 찾으면 변경할 수 있으며, 명령과 설치 연결이 끊기지 않도록 영향 범위를 함께 확인한다. 이 절이 현재 이름의 소유 위치다.

| 적용 대상 | 현재 표기와 상태 |
| --- | --- |
| 제품 표시 이름 | **OnepLoom** 채택. 한글 발음 제안은 원피룸 |
| 제품 명령, 모듈 저장소 이름에 사용할 기본 표기 | **`oneploom`**. 로컬 개발 저장소 준비 완료. 제품 명령 등록/원격 생성은 아직 |
| 모듈의 공개 WIKI 저장소 이름 예시 | `oneploom-wiki`. 로컬 wiki Git은 준비했으며 원격 이름과 공개는 후속 확인 |
| 프로젝트 전용 설치 폴더 이름 | `oneploom`. 신규 기본 위치는 [코드 프로젝트 루트의 `oneploom/` — 「프로젝트 설치 위치 후보」](runtime/install.md). 기존 배치와 사용자 파일 보호는 설치 명세를 따름 |
| 제품이 제공할 skill 이름 접두어 | `oneploom-<역할>`. 실제 필요한 역할과 발견 경로는 설치 명세를 따름 |

제품 이름은 명령, 도움말, 설치물과 문서의 표기에 사용한다. 구현에서는 기존 배포 메타데이터 등 실제 필요한 선언 한 곳을 기준으로 연결하고, 이름을 관리하기 위한 새 설정 파일이나 추상화 계층을 미리 만들지 않는다. 모든 내부 타입과 필드에 접두어를 붙이지 않으며 `AGENTS.md`, `SKILL.md` 같은 호스트 표준 이름은 유지한다. 명령 등록과 프로젝트별 설치본 연결의 실제 구현은 이름 채택과 구분한다.

`.harness/` 로컬 상태 영역, 프로젝트 식별자와 사용자가 지정한 WIKI 경로는 제품 표시 이름에 맞춰 자동 변경하지 않는다. 과거 커밋, 릴리스와 실험 근거의 이름도 당시 값으로 보존한다. 이름을 바꾸더라도 같은 프로젝트의 연결과 작업 기록을 계속 찾을 수 있어야 한다.

첫 배포 전에는 제품명 선언, 생성할 명령/연결 경로, README/도움말과 해당 검사를 함께 바꿔 대조한다. 실제 파일을 옮길 때는 참조와 소유 기준도 함께 갱신한다. 문자열이 같다는 이유만으로 관리 범위 밖의 사용자 파일까지 일괄 치환하지 않는다.

배포 후에는 기존 사용자의 명령, 설치 경로와 기록을 먼저 확인한다. 이름 변경의 영향에 따라 이전 명령의 호환 연결, 사용 중단 안내, 설치 위치/기록의 이전과 복구 검증을 설계한다. 이를 첫 배포에 사용하지 않을 호환 계층을 미리 구현하라는 뜻으로 확대하지 않는다. 기존 공개 명령을 깨는 변경은 [릴리스 기준 — 「이름과 변경 이력」](module.md#%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EB%B3%80%EA%B2%BD%20%EC%9D%B4%EB%A0%A5)에 따라 다루며, [SemVer](https://semver.org/spec/v2.0.0.html)의 호환성 구분을 적용한다. GitHub 저장소 이름 변경의 자동 연결도 모든 참조를 해결하지 않는다. [GitHub 공식 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)는 로컬 remote 갱신을 권하고 해당 저장소의 Action 참조는 자동 연결되지 않는다고 설명한다.

따라서 `discussions`, `decisions`는 남는다. `platform` 등의 **공통 고정 의존을 제거**하되, 프로젝트가 실제 빌드, 계약 판단에 필요한 자료까지 못 읽게 만들지는 않는다. 경로 매핑은 기존 자료를 가리키면 되며 모든 문서를 새 폴더로 옮길 필요가 없다.

현재 [기준 구현의 관측 (구현 검사)](../discussions/architecture/baseline-audit.md)와 [기준 구현의 관측 (matrix)](../discussions/architecture/baseline-audit.md)는 `guides` 등 고정 경로를 사용한다.

[기준 구현의 관측 (거버넌스 검사)](../discussions/architecture/baseline-audit.md)와 [기준 구현의 관측 (갱신 matrix)](../discussions/architecture/baseline-audit.md)는 특정 `prompts/topics`, `worklog`를 요구한다.

[현행 자산의 대응표 — 「현재 파일의 대응」](../development/migration.md)에 이 소비 지점과 변경 방향을 연결했다. 위 표는 구성 역할을, 대응표는 실제 파일과 함께 바꿀 소비자를 다룬다. `platform.md`에 직접 hook이 연결됐다는 사실은 확인되지 않았으며, 실제 확인된 연결과 제거 후보를 구분한다.

폴더 감소 자체가 토큰 절감은 아니다. 읽지 않은 파일은 존재만으로 본문 토큰을 쓰지 않는다. 측정할 효과는 불필요한 기본 읽기, 라우팅, 생성/갱신 의무의 감소다. 문서를 한 파일로 합쳐 매번 전부 읽게 만들지 않는다.

## 기능 선택과 추가

2026-10-29 사용자가 확정한 사용 방식은 다음과 같다. 위 구성표의 항목을 모두 필수 설치로 채택한 것은 아니다.

1. 처음에는 필요한 최소 구성을 설치하고 원하는 선택 기능을 함께 고를 수 있다.
2. 처음 고르지 않은 제공 기능도 나중에 사용자가 요청하면 추가할 수 있어야 한다. 최초 선택으로 기능 확장을 막지 않는다.
3. 선택 기능의 추가는 사용자의 요청으로 시작한다. 자동으로 다른 기능을 내려받거나 활성화하는 방식을 이 요구에서 추론하지 않는다.
4. 프로젝트별로 필요한 구성을 사용하면서 공통 기능을 유지보수, 확장할 수 있어야 한다. 후속 추가에서도 기존 문서, 설정, 진행 상태의 보존 조건을 적용한다.

아래는 확정 입력과 남은 추천을 구분한 구성이다. **11/09 WIKI 내용 구성, 분할 상세 복원, 완료 기준과 기본 메인, 선택 보조 경계를 채택했다.** 설치 명세까지 확정한 것은 아니다. 철회한 WIKI 선택 추천의 구성표, 대안, 변경 이유는 [ADR 0014 — 「최초 구성표」](../decisions/knowledge/0014-features.md)에 보존한다. 기능별 배포 묶음, 저장소, 명령 이름은 별도 협의한다.

첫 배포의 필수 목표, 선택 기능, 후속 확장과 완료 조건은 [배포 범위표 — 「첫 배포의 책임과 보류 항목」](../decisions/architecture/0007-release-scope.md), 실제 설치 자산의 위치, 갱신 책임은 [설치 구성표 — 「설치 결과의 소유와 공유」](runtime/install.md)가 소유한다. 11/11 [첫 선택 기능](../decisions/architecture/0007-release-scope.md)으로 설명/학습 문서 확장을 먼저 제공하고 커밋 보조를 후속으로 두는 안을 채택했다. 아래는 첫 제공 시점과 별개인 기능의 의미, 의존성 표다.

### 선택 확장과 실행 방식

10/30 시스템 날짜의 후속 요청에서 사용자는 선택 기능을 `explainers`, `learn` 등의 문서 역할을 필요할 때 기존 설치에 연결하는 의미로 설명했고, 커밋 보조의 선택 분류에도 동의했다. 아래는 그 명확화와 11/09 채택한 기본 메인, 선택 보조 경계를 구분한 표다. 구체 보조 호출, 기능별 배포 묶음은 후속 협의이며 설치 제공 수단은 [ADR 0010](../decisions/runtime/0010-distribution.md)을 따른다.

| 구분 | 의미, 상태 | 연결 방식의 후보 |
| --- | --- | --- |
| 기본 구성 | 조건부 실행, 핵심 WIKI, 검증, 복구를 제공. WIKI 구성, 복원, 완료 기준은 채택 | 기존 자료를 연결하거나 합의 범위를 상세 복원. 세부 입력, 설치 명세는 후속 |
| 문서 확장 | 설명, 학습 문서를 최초 선택/후속 추가로 제공하는 첫 선택 기능 채택 | 필요한 README, 인덱스/라우팅, 템플릿을 연결하고 필요할 때만 skill/script 추가. 기본 문서의 규칙 소유권을 복제하지 않음 |
| 커밋 보조 | 선택 기능이며 첫 배포 뒤 후속 검토 | 기존 변경/index를 보존하며 명시 요청에만 stage, 메시지 절차 수행 |
| 서브에이전트 분업 | 최초 표의 '협업'이 뜻했던 Codex 내부 분업. 로컬 AI를 포함한 표현이 아니었음 | 공통 위임 규칙과 선택 호출의 경계는 채택. 상세 후보를 메인이 검토하고 단일 경로로 반영. 구체 역할, 호출, 별도 설치 여부는 미정 |
| 로컬 AI 보조 | 클라우드 메인을 유지하며 좁은 일을 로컬에 위임하는 별도 실행 선택. 도입 자체는 미확정 | 도입한다면 기본/보조 전환, 동일 WIKI, 검증, 복구, 실패 시 미완료 보존을 필수로 검증. 모델/서버 준비와 모드 활성화는 별개 |

설명 확장을 뒤늦게 추가할 때는 해당 역할의 진입 안내, 문서 규칙, 필요한 템플릿/절차를 기존 소유 위치에 연결한다. 없는 경로를 기본 gate가 요구하거나, 설명 문서를 추가했다는 이유로 제품 계약 검증을 바꾸거나, 모든 확장에 새 script/hook을 만드는 방식은 피한다. `learn`이 기본에 없다는 것은 후속 추가를 금지하거나 기존 학습 자료를 삭제한다는 뜻이 아니다. 기능별 정확한 파일, 소유, 보존 검증은 파일별 명세 단계에서 정한다.

서브에이전트/로컬 보조는 문서 역할을 더 받는 선택과 다른 축이다. 공통 위임 규칙과 실제 작업자 연결을 분리하면 필요한 실행기, 모델만 준비하면서도 기본/보조가 같은 완료, 실패, 복구 조건을 사용할 수 있다. 독립 패키지 수나 범용 router를 먼저 정하지 않는다. 구체 사례, 전환 대안, 공식 근거는 [보조 역할의 분업 구분 — 「서브에이전트와 로컬 보조」](integration/local-ai.md), 판단 상태는 [ADR 0014 — 「후속 협의: 위임의 공통 책임」](../decisions/knowledge/0014-features.md)와 [ADR 0006](../decisions/integration/0006-local-assist.md)에 둔다.

### 기능 제공과 설치, 실행의 구분

- 제품이 제공할 능력: 이식과 근거 기반 WIKI 복원은 필수 목표이며 로컬 AI 채택과 무관하다.
- 프로젝트에 설치할 구성: 핵심 WIKI, 조건부 실행, 검증, 복구를 제공하는 기본 경계와 선택 확장을 구분한다. 첫 제공 목록은 배포 범위표의 채택 범위를 따르며 세부 설치 자산은 명세에서 정한다.
- 요청마다 실행할 작업: 기본 설치도 매번 전체 문서 읽기, 검사, 역공학, 보조 호출을 뜻하지 않는다. 프로젝트 상태와 요청, 변경, 위험에 따라 필요한 절차만 실행한다.

기존 WIKI 연결과 빈 문서의 근거 기반 초기화는 다른 진입 경로다. 기본 포함을 원문 덮어쓰기나 설치 직후 전체 이력 재분석으로 해석하지 않는다. `roadmap`, `prompts`는 프로젝트가 필요할 때 사용하는 문서 역할 후보이며 각각 별도 설치 기능으로 늘리지 않는 안을 유지한다.

### 연결과 추가의 조건

아래는 기존 제안에서 유지하는 조건이며 아직 구현, 검증된 동작은 아니다. 상세 검사 계약은 [검증](workflow/verification.md), 복구의 다음 설계는 [진행표](../development/roadmap.md)가 소유한다.

- 진입, 실행, 복구는 내부 책임을 나누고 프로젝트 정책, 검사, 상태 경로를 연결한다. 메인이 최초 gate 판단과 결과 통합을 맡으며 두 번째 planner, 상시 agent, 자체 PASS 캐시를 기본으로 추가하지 않는다. 지원하지 않는 직접 호출까지 자동 통제한다고 보장하지 않는다.
- 구현/문서 검사, retry의 공통 상태는 원래 실패와 scope를 유지해야 한다. 다른 검사의 PASS로 원래 실패를 닫지 않고, 선택 확장이 없다는 이유로 기존 문서 규칙, 필수 검사를 면제하지 않는다. 필요한 입력, 검사, 상태가 없으면 설정 필요/미확인으로 남긴다.
- 기본 경로에 미설치 확장의 파일, 생성, 갱신 의무를 남기지 않는다. 의존이 생기면 파일, 버전, 변경 범위와 비용을 드러내며 숨은 다운로드, 유료 호출로 해결하지 않는다. 실행자별 공통 상태와 완료 의미를 재정의하지 않는다.
- 문서 확장 등을 후속 추가할 때 기존 버전, 설치 소유, 보호 원문 확인 → 의존, 변경, 충돌 제시 → 합의 범위 적용 → 실제 연결, 보존 확인 순서를 사용한다. 구체 입력/소비 초안은 [기능 추가의 연결](runtime/install.md)에 둔다. 기반 갱신이 필요하면 포함해 설명하고 호환되지 않으면 협의한다. 기존 진행 상태를 새 프로젝트처럼 초기화하지 않는다.
- 미설치, 비활성, 이번 요청에서 불필요, 실행 대기, 실패, 통과를 구분한다. hook 파일 배치와 신뢰, 실제 발동도 별개다. 의미 요약과 기계 실행 기록, 수동 재개와 자동 복구의 한계를 구분한다. 기본 설치가 전체 followup/runbook 선생성, 상시 읽기를 뜻하지 않는다.
- 커밋 보조는 후속 검토 대상이다. 도입 시 기존 index와 팀 규칙을 보존하고 명시 요청 범위만 다루며 설치 자체로 stage, commit, push하지 않는다. 갱신, 복원, 제거 인터페이스는 아직 확정하지 않았다.

### 근거와 확인할 것

- [Codex skills](https://learn.chatgpt.com/docs/build-skills)는 이름, 설명부터 제공하고 선택 시 본문을 읽는다. 설치 개수와 매 요청의 본문 읽기를 구분할 근거다. 메타데이터 비용도 있으므로 설치만 하면 비용이 0이라고 보지 않는다.
- [Codex hooks](https://learn.chatgpt.com/docs/hooks)는 여러 출처의 hook을 함께 로드하며 신뢰 확인을 요구한다. 따라서 선택 기능 추가에서 파일 존재뿐 아니라 중복 연결, 신뢰, 발동을 확인한다. 지원할 정확한 버전의 실제 동작은 별도 검증한다.
- [VS Code extension manifest](https://code.visualstudio.com/api/references/extension-manifest)는 함께 설치하는 묶음과 기능상 의존을 구별한다. 같은 구별을 설계에 참고했으며 VS Code 확장 도입을 제안하는 것은 아니다.

위 자료는 책임, 의존을 구분할 근거이며 이 구성의 효과를 실증하지 않는다. 필수 검사의 누락, 미연결, 중복 연결, 기존 자료 보존과 불필요 실행을 합의된 조합별로 확인해야 한다. [수용 기준 — 「대표 수용 시나리오 후보」](../verification/acceptance.md)의 S-13~15는 최초안 비교 기록이며 새 경계의 통과 기준으로 사용하지 않는다. 갱신할 구체 사례와 토큰, 성능 효과는 아직 미확정, 미측정이다.

## 브랜치와 통합

코드와 WIKI는 각각 main + 작업별 브랜치를 사용한다. 준비 문서부터 실제 검토 가능한 단위로 커밋하며, 제품이 완성될 때까지 이력을 미루지 않는다. 기존 다른 저장소의 브랜치 통합은 이 프로젝트의 선행 조건이 아니다. 명명과 연결은 [개발 준비](../development/workspace.md), [ADR 0012](../decisions/development/0012-branches.md)를 따른다.

## 제품 이름의 검토 이력

현재 제품 이름은 앞의 [제품 이름과 변경 기준](module.md#%EC%A0%9C%ED%92%88%20%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EB%B3%80%EA%B2%BD%20%EA%B8%B0%EC%A4%80)에 있는 OnepLoom이다. 아래 후보와 조회는 채택 전 판단 기록으로 보존하며 현재 명명 결정을 다시 여는 목록이 아니다. 공개 검색만으로 상표 사용 가능성이나 모든 환경의 명령 충돌 부재를 보장하지 않는다.

### 제품명과 명령 이름 후보

11/22 비교 뒤 사용자가 OnepLoom을 선택했다. 현재 표기는 [제품 이름과 변경 기준](module.md#%EC%A0%9C%ED%92%88%20%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EB%B3%80%EA%B2%BD%20%EA%B8%B0%EC%A4%80)을 따르며 아래 내용은 선택 전 대안과 판단 근거다. 사용자는 `onep`의 정체성과 함께 조건부 하네스, 로컬 WIKI 연결, 코드와 이력에 근거한 복원, 이후 지속적인 사용을 이름에 담길 원했다. 명명 채택을 상표/도메인 확인이나 기존 환경의 이름 변경으로 확대하지 않는다.

| 후보 | 의미와 장점 | 비용과 판단 |
| --- | --- | --- |
| Condharness / `condharness` | conditional harness에서 가져온 이름. 조건에 따라 필요한 절차를 사용하는 핵심 도메인이 드러나며 특정 AI나 WIKI 기능에 묶이지 않음 | 설명형 비교 당시 추천. 11자로 조금 길고 `cond`의 뜻은 첫 소개에서 풀어야 함. 독립 브랜드 인상은 아래 후보보다 약하다는 판단 |
| Harnesslane / `harnesslane` | 작업을 안내하는 하네스라는 인상. 이름을 읽고 발음하기 비교적 쉬움 | 대안. 조건부 실행의 의미는 소개 문구로 보충해야 하며 일반 하네스 제품과의 차이가 이름만으로 선명하지 않음 |

두 후보는 11/22 공개 API 조회에서 GitHub의 해당 문자열을 포함한 저장소 이름 검색 결과가 0건이었고, PyPI와 npm의 해당 패키지 조회는 404였다. 이는 해당 시점의 공개 조회 결과다. 비공개/미색인 저장소, 개인 명령, 예약 이름, 상표나 나중에 생길 충돌까지 없다는 뜻은 아니다. 현재 배포는 Git 릴리스 + Python이며 npm/PyPI 등록을 추가로 채택한 것이 아니다. [조회 결과와 한계](../evidence/experiments/design/2026-11-22_23-47-39-entry-naming.md)에 확인 범위를 남긴다.

`harness`는 [동명 개발 플랫폼](https://www.harness.io/products/try/software-delivery-agent)과 겹쳐 공개 명령 후보에서 제외한다. `Gateweave`와 `ScopeWeave`도 [Gateweave의 제품 페이지](https://gateweave.com/)와 [ScopeWeave](https://scopeweave.com/)에서 사용을 확인해 제외했다. 다른 제품의 소스, 문구, 로고를 가져오지 않았으며 이 조회를 라이선스나 상표 사용 가능성의 법적 확인으로 표시하지 않는다.

명령, 저장소, 폴더와 skill의 현재 표기는 위 채택 기준으로 통합했다. 짧은 `ch`, 일반 `start`, 기존 `codex`를 덮는 별칭은 기본 제공하지 않는다. 전용 폴더 안의 `project.json`처럼 역할이 이미 드러나는 파일에 제품명이나 버전 접미사를 다시 붙이지 않는다.

명령 이름만 정해도 실행 파일이 PATH에 등록되지는 않는다. 등록 위치/방법과 제거 시 소유 확인은 구현 명세에서 연결해야 한다. [명령 충돌 검사 — 「명령 이름과 충돌 방지」](module.md#%EB%AA%85%EB%A0%B9%20%EC%9D%B4%EB%A6%84%EA%B3%BC%20%EC%B6%A9%EB%8F%8C%20%EB%B0%A9%EC%A7%80)와 명시 경로 실행을 유지하며, 전역 Codex 설정이나 사용자 실행 정책을 바꾸는 방식으로 짧은 명령을 강제하지 않는다. 프로젝트별 설치본을 잘못 섞지 않는 연결 조건은 [설치 위치 후보 — 「프로젝트 설치 위치 후보」](runtime/install.md)에 둔다.

#### 브랜드형 이름 후보

제품명은 조건부 절차 선택뿐 아니라 코드/이력에서 지식을 복원하고 로컬 WIKI로 유지한다는 의미를 반영해 OnepLoom을 채택했다. 이전 OnepGate 후보는 절차 선택에 치우친다는 의견으로 보완했다. 아래는 당시 의미 비교이며 한글 발음은 제안이다.

명명 기준이 되는 제품 설명은 **코드와 이력에서 프로젝트 지식을 복원하고, 로컬 WIKI로 유지하면서 필요한 AI 개발 절차에 계속 연결하는 조건부 하네스**다. 검증과 실패 처리, 중단 후 재개, 프로젝트별 설치와 갱신도 이 기반을 뒷받침한다. 이는 기존 [제품의 중심과 도입 경로](architecture.md)를 이름 관점에서 요약한 것이며 새 기능 채택이 아니다. 신규 프로젝트에는 복원할 과거가 없어도 같은 하네스와 WIKI를 사용한다. 매 작업의 전체 이력 분석, 자동 무한 실행, 근거 없는 과거 결정의 생성을 뜻하지 않는다.

| 후보 | 의미와 제품 연결 | 단점과 판단 |
| --- | --- | --- |
| **OnepLoom / 원피룸 / `oneploom`** | loom은 직조기, 실을 규칙에 맞춰 엮는 틀. 코드와 이력의 근거를 WIKI로 엮고, 필요한 규칙과 도구를 골라 개발에 이어 쓰는 지속적인 기반을 상징. 명령은 8자 | 11/22 사용자 채택. 뜻을 한 번 설명해야 하며 기존 Loom 서비스와의 연상을 고려해야 함. 단독 Loom으로 줄이지 않는 표기를 제안 |
| **OnepLoop / 원피루프 / `oneploop`** | 코드/이력 → WIKI → 조건별 개발/검증 → WIKI 갱신으로 이어지는 반복 사용을 표현. 명령은 8자 | 사용 흐름은 설명하기 쉽지만 자동 agent loop나 무한 반복 도구로 오해할 수 있음. 조건이 맞을 때 필요한 단계만 실행하는 설계와 구분해 소개해야 함 |
| **OnepLore / 원피로어 / `oneplore`** | lore는 축적되고 전해지는 지식. 과거 근거에서 개발 지식을 복원하고 이후 작업에도 전한다는 의미. 명령은 8자 | 지식의 지속성은 잘 드러나나 WIKI/지식 저장 도구로 보이기 쉽고 실행 하네스의 역할은 소개 문구가 필요함 |
| **OnepRelay / 원피릴레이 / `oneprelay`** | relay는 이어 전달한다는 의미. 코드의 근거를 WIKI로, WIKI의 지식을 다음 작업과 재개로 전달하는 역할. 명령은 9자 | 연속성과 인계는 표현하지만 통신 중계 도구의 인상이 있고 지식을 복원하는 역할은 약함 |

OnepLoom은 엮는 행위보다 그것을 지속적으로 받쳐 주는 틀이라는 점에서 설치한 하네스와 잘 연결된다는 판단이다. 예를 들어 기존 저장소에서 복원한 요구와 결정을 로컬 WIKI에 두고, 다음 기능 개발에서는 관련 근거와 검증 절차를 선택해 사용한 뒤 확인한 변경을 WIKI에 반영하는 흐름을 설명할 수 있다. 이 의미 연결은 브랜드 제안이며 이미 구현한 동작이나 성능을 입증하는 근거가 아니다.

직조기 제조사 Schacht도 [직조기 구성품을 shaft/harness로 표기](https://schachtspindle.com/blogs/product-diagrams/standard-floor-loom-shaft-harness-parts)한다. 따라서 loom과 harness는 실제 분야에서도 함께 쓰이는 단어다. 이를 소프트웨어 harness의 어원으로 단정하지 않는다. 제품 소개 예시는 **OnepLoom — 프로젝트 지식을 복원하고 이어 쓰는 조건부 AI 하네스**다. `oneploom start`의 명령 접두어는 채택됐으며 실제 등록은 아직이다. 실이 틀 안에서 연결되는 도형은 미확정 디자인 후보로 남긴다.

저자 이름을 제품명으로 써야 한다는 규칙은 없다. [Python의 공식 이름 설명](https://docs.python.org/3/faq/general.html#why-is-it-called-python)은 창작자가 보던 Monty Python에서 이름을 가져왔다고 설명하고, [uv 공식 문서](https://docs.astral.sh/uv/)는 제품 uv와 제공자 Astral을 구분한다. 이는 서로 다른 작명 방식의 사례이며 업계 전체 비율의 근거는 아니다. 이번에는 사용자가 지정한 `onep`와 제품 전체를 설명할 수 있는 단어를 결합하는 편을 추천한다.

새 네 후보는 이번 공개 조회에서 GitHub 저장소 이름 검색 각 0건, PyPI와 npm의 해당 패키지 조회 각 404였다. [조회 결과와 한계](../evidence/experiments/design/2026-11-23_00-43-11-product-name-concept.md)를 보존했다. 다만 [Atlassian의 Loom](https://www.atlassian.com/software/loom)은 이미 있는 소프트웨어 서비스이므로 OnepLoom의 의미 적합성과 독자적인 인지도는 따로 평가한다. 전체 이름의 조회 부재를 유사 명칭이나 법적 충돌의 부재로 해석하지 않는다. 도메인/상표 사용 가능성과 모든 사용자 기기의 명령 충돌은 미확인이며 현재 배포 방식도 유지한다.

앞선 OnepGate/OnepWeave/OnepForge/OnepFlow와 당시 조회는 [직전 후보 기록](../evidence/experiments/design/2026-11-23_00-17-25-onep-naming.md)에 보존한다. OnepGate는 전체 가치의 설명이 좁다는 이번 의견에 따라 현재 추천에서 내렸다. ONPLIN/RENPLY는 [이전 브랜드 검토](../evidence/experiments/design/2026-11-23_00-03-17-brand-naming.md)에 남겨 두며 `onep`의 의미 단위를 살리지 못한 한계를 유지한다. 이름의 고유한 인지도는 README, 명령, 저장소와 향후 로고의 일관된 표기로 쌓으며 기존 명령 충돌 검사와 소유 보존 기준은 유지한다.
