# 개발 WIKI의 범위와 관리

## 포함할 내용

OnepLoom의 개발 지식과 판단 과정을 보존한다. 요구와 제약, 상세 데이터/명령/파일 계약, 설계 토의, 대안의 장단점과 채택/보류 이유, ADR, 검증 계획, 관측과 실패 분석, 변경 이력이 대상이다.

최신 설계와 과거 토의는 상태를 나눠 연결한다. 기각되거나 대체된 안도 판단 근거라면 남긴다. 원문에 없던 선택 이유나 미실행 결과를 보충해서 사실처럼 만들지 않는다. 기술 설명도 제품의 판단을 이해하는 데 필요한 범위에서 연결한다.

## 문서별 책임

요구사항은 기대 동작과 제약, 설계는 처리 계약, 토의는 대안과 논거, ADR은 결정과 변경 이유를 소유한다. 검증 문서는 계획과 실제 관측을 구분한다. 사용자 실행 안내는 코드 저장소 README에서 제공한다.

## 내용의 원본과 변경

완료된 개발 지식의 기준은 이 WIKI다. 설계가 바뀌면 해당 주제 원본과 직접 영향받는 요구사항, ADR과 검증 연결을 함께 갱신한다. 변경 전 판단은 토의나 ADR의 이력으로 보존한다.

파일명과 디렉토리는 역할을 따른다. 문서가 커지면 책임별로 나누고 상위 안내에서 연결한다. 날짜나 수정 차수를 무분별하게 이름에 붙이지 않는다. 기존 ADR 번호와 최초 날짜, 실제 도구 버전 및 실험 식별자는 근거이므로 유지한다.

## 날짜와 시각 표기

본문은 날짜만 필요하면 `2026-11-24`처럼 쓴다. 사건의 순서나 실행 시점을 구별해야 할 때는 `2026-11-24 15:30:00 KST`처럼 날짜, 시각과 시간대를 함께 적는다. 한국 시각의 기준은 KST(UTC+09:00)이며, 다른 시간대를 쓰면 그 시간대를 명시한다.

시간순 정렬이 필요한 관측 문서의 파일명은 `2026-11-24_15-30-00-observation.md` 형식을 쓴다. 날짜만으로 구별되면 `2026-11-24-topic.md`로 충분하며, 일반 설계 문서에는 날짜를 붙이지 않는다. 밑줄은 날짜와 시각을 구분하고, 시각의 콜론 대신 하이픈을 써 Windows에서도 사용할 수 있게 한다. 이 파일명은 프로젝트의 표기 규칙이며 ISO 8601 표준 형식이라고 부르지 않는다.

UTC 원본을 KST로 표시할 때는 같은 순간을 나타내도록 9시간을 더하고 날짜 변경도 반영한다. 설계 작업일과 실제 실행 시각은 서로 다른 정보이므로 파일명 날짜를 근거로 작업일을 바꾸지 않는다. 원시 로그, 기존 실행 식별자와 API/저장 계약에 필요한 기계용 시각은 보존하고 설명에서 읽기 쉬운 형식을 사용한다. 문서 이름을 바꿀 때는 참조와 제목 링크도 함께 확인한다.

[adr-tools의 날짜 결정](https://github.com/npryce/adr-tools/blob/master/doc/adr/0008-use-iso-8601-format-for-dates.md)은 연-월-일 표기의 공개 사례다. [Windows 파일 이름 규칙](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)은 파일명에 콜론을 사용할 수 없다는 제약을 설명한다.

## 변경 검토

변경한 요구 조건, 데이터 필드, 예외/복구 흐름과 검증 입력을 관련 문서와 대조한다. 대체된 안의 이유가 남아 있는지, 현재 계약이 서로 모순되지 않는지 확인한다. 파일 존재와 링크/제목 검사에 더해 실제 내용을 읽고 누락과 근거 없는 보충을 검토한다.

검토 가능한 작업 단위로 변경을 묶고 코드와 WIKI의 실제 커밋/PR을 연결한다. 준비 문서의 커밋을 기능 구현 완료나 릴리스로 표시하지 않는다. Git 운영은 [개발 공간](workspace.md)에서 확인한다.

## ADR의 결정 상태

설계 채택과 구현/검증 결과를 구분한다. 현재 상태는 각 ADR이 소유하고 [결정 목록의 상태 안내](../decisions/README.md#상태를%20읽는%20방법)에 연결한다. 부분 채택에는 적용할 범위와 남은 선택을 적는다. 후속 결정으로 대체한 과거 안은 이유와 연결을 보존한다. 목록의 상태와 본문의 채택 기록이 달라지면 함께 정정한다.

## 검증 상태와 근거

관측에는 입력 조건, 실행 환경, 결과와 한계를 남긴다. 단위 검사, 예비 도구 관측, 실제 제품 통합 검증을 구분하며 미실행을 PASS로 처리하지 않는다. 관측 설명만 있는 기록과 독립 실행 자료가 갖춰진 재현 결과를 구분한다. [기록 기준](../evidence/recording.md)을 따른다.

ADR은 맥락, 결정, 결과와 대체 이력을 유지하는 [원래 제안](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)을 참고했다. 구현 전에 설계와 토의를 검토하는 [Rust RFC 절차](https://github.com/rust-lang/rfcs/blob/main/README.md)도 개발 기록과 기능 구현 완료가 별개임을 보여주는 참고 사례다.
