# 개발 공간과 첫 커밋

## 코드와 WIKI

두 폴더는 같은 개발 프로젝트에 속하지만 독립 Git 저장소다. 코드 저장소에는 배포할 구현, 개발 규칙과 실행 안내를 둔다. WIKI에는 OnepLoom의 전체 개발 지식과 판단 근거를 둔다.

OnePLoom Organization 아래에서 다음 두 저장소를 관리한다.

| 저장소 | 역할 |
| --- | --- |
| [oneploom](https://github.com/OnePLoom/oneploom) | 제품 소스, 설치 자산, 테스트와 개발 안내 |
| [oneploom-wiki](https://github.com/OnePLoom/oneploom-wiki) | 요구사항, 상세 설계, 기술 토의, ADR과 검증 기록 |

```text
workspace/
├── oneploom/    코드 저장소
└── wiki/        개발 WIKI 저장소
```

위 경로는 배치 예시다. 사용자별 실제 위치를 공유 설정으로 고정하지 않는다. 두 로컬 저장소는 main으로 준비했고 2026-11-24 각각 대응하는 GitHub 저장소를 origin으로 등록했다. origin 등록은 로컬의 대상 주소 설정이며 원격 인증이나 push 성공을 뜻하지 않는다.

코드 저장소에는 제품 개발에 필요한 테스트, 빌드 설정과 개발 규칙도 함께 관리한다. 배포 파일은 실행 코드, 설치 자산과 필요한 안내를 패키징한 결과이며, 사용자의 프로젝트에는 설치 계획에 정한 구성만 생성하거나 통합한다. 개발 저장소 전체를 사용자 프로젝트에 복사하는 방식으로 구현하지 않는다. 개발용 AGENTS와 설치할 지침/템플릿도 책임을 구분한다. 제품의 상세 소유 기준은 [모듈의 소유 — 「원본과 적용본」](../design/module.md)을 따른다.

## 최초 커밋과 기본 모듈

두 저장소에 각각 준비 내용을 커밋한다. 코드 쪽은 README, AGENTS, CONTRIBUTING과 Git 설정이 대상이며 아직 없는 제품 코드를 만들어 넣지 않는다. WIKI 쪽은 요구, 상세 설계, 토의/ADR, 검증 기록과 안내를 대상으로 한다. 커밋 전에 실제 공개 범위와 문서 연결을 확인한다.

이 첫 커밋은 개발 기록의 시작이다. 기존 합의의 ‘검증된 기본 모듈을 기준으로 기능 개선’은 이후 최소 동작이 구현/검증된 시점의 기준 커밋을 뜻하며 저장소의 첫 커밋일 필요가 없다. 설계 이력부터 기록하는 것과 기능 완료를 구분한다.

## 브랜치와 원격

코드와 WIKI는 main + 작업 브랜치를 기본으로 사용하고, 하위 PR의 독립 검토가 필요할 때만 임시 통합 브랜치를 둔다. main PR의 기본 병합 방식은 Rebase and merge다. 이름, 커밋/PR 형식과 예외의 원본은 [코드 CONTRIBUTING](https://github.com/OnePLoom/oneploom/blob/main/CONTRIBUTING.md)의 「브랜치와 변경 단위」부터 「PR 작성과 코드/WIKI 연결」까지다. 원격 게시 전에는 코드 폴더의 로컬 파일에서 확인한다.

두 저장소의 작업은 실제 PR로 연결하고 병합 뒤 필요한 최종 SHA를 확인한다. 변경 없는 저장소에 빈 커밋을 강제하지 않는다. 대안과 채택 이유는 [ADR 0012 — 「독립 모듈의 브랜치 운영」](../decisions/development/0012-branches.md)에 보존한다.

GitHub 원격의 소유자와 저장소 이름은 위 주소로 정했다. 인증, 접근 권한, 공개 조건과 push는 로컬 주소 등록/커밋과 별도로 확인한다. 같은 Organization에 있다는 이유로 두 저장소의 인증 권한이나 CI 실행을 자동 통합하지 않는다. 초기 커밋은 릴리스 태그가 아니며 기능별 검증과 배포 조건을 충족한 버전에만 릴리스한다. [ADR 0012](../decisions/development/0012-branches.md).
