# 현행 자산과 변경 명세

2026-11-13, 4단계의 현행 자산 대응표다. **현재 파일이 맡은 책임을 채택한 제품 설계에 대응했고 [진입과 프로젝트 연결](../design/runtime/entry.md)의 AGENTS 최소 연결 A와 제품 시작 명령의 자동 연결을 채택했다.** 11/15 일반 진입은 열린 세션 안 트리거의 경로 등록/연결로 구체화하고, 연결 결과와 실패 이유를 검증/복구 소비자에 대응했다. [로컬 검증과 active 기록](../design/workflow/records.md)의 필드, 파일과 저장/조회 초안도 작성했다. 11/22 직접 접근 우선 선택 뒤 첫 실행기의 저장 책임과 개발 준비 인계를 아래에 연결했다. 정확한 명령/저장 형식과 실제 구현은 미완료다. 제품 파일은 수정하지 않았고 실제 실행도 검증하지 않았다.

처음에는 「현재 파일의 대응」에서 전체 범위를 보고, 「기능별 연결과 실패 처리」에서 호출 흐름을 확인한다. 상세 정책은 연결한 소유 문서를 따른다. 이 문서는 기존 정책을 다시 정의하지 않고 현재 자산에서 바꿀 지점과 함께 바꿔야 할 소비자를 관리한다.

## 대조 범위와 표의 의미

현행 기준은 기존 시험 프로젝트의 커밋 `f6e33dd56baa2a651a70d7d0b2cc3ebde6575153`이다. 해당 HEAD와 작업 트리의 추적 변경 없음을 확인한 뒤 AGENTS, `.codex` 추적 파일 25개, 직접 연결된 문서 규칙과 템플릿, Git 제외, CI를 읽었다. 모든 제품 문서의 본문을 감사하거나 현재 Windows 동작을 재시험한 것은 아니다. 과거 실행 결과는 [구조 감사](../discussions/architecture/baseline-audit.md)와 [근거](../evidence/README.md)에 남겨 둔다.

표의 현행 파일은 위 커밋의 이름이다. 「변경 후」는 현재 채택한 책임에 따른 대응 방향이며 새 파일명을 확정한 목록이 아니다.

| 구분 | 의미 |
| --- | --- |
| 유지 | 유효한 책임이나 규칙을 이어간다. 파일 전체를 그대로 배포한다는 뜻은 아님 |
| 수정 | 기존 책임의 입력, 출력이나 판단을 채택된 계약에 맞춘다 |
| 분리 | 공통 절차와 프로젝트 값, 도구 연결, 로컬 상태의 소유를 구분한다. 책임마다 별도 파일이나 계층을 강제하지 않음 |
| 통합 | 같은 정보나 실행 결과를 한 소유 위치에서 관리한다. 관련 문서를 거대 파일 하나로 합치는 뜻은 아님 |
| 제외 | 공통 배포본이나 기본 설치 대상에서 뺀다. 사용자의 기존 파일 삭제와는 다름 |
| 신규 | 필요한 책임을 제공하는 제품 구현이 아직 없다. 개인 실험 도구의 존재로 완료 처리하지 않음 |

공통 절차와 실행 코드는 공식 모듈에서 관리하고 필요한 적용본을 프로젝트 안에 설치한다. 검사 명령과 문서 위치는 프로젝트가, 기기 경로와 인증 참조는 호스트가, 진행 기록은 해당 로컬 작업이 소유한다. [책임 경계 — 「무엇을 누가 소유하는가」](../design/architecture.md), [설치 결과의 소유 — 「설치 결과의 소유와 공유」](../design/runtime/install.md)를 따른다.

기존 구현의 관측은 [기준 구현의 관측 (AGENTS)](../discussions/architecture/baseline-audit.md), [기준 구현의 관측 (Codex 자산 안내)](../discussions/architecture/baseline-audit.md), [기준 구현의 관측 (문서 라우터)](../discussions/architecture/baseline-audit.md)에서 확인할 수 있다.

| 현행 파일 | 현재 역할과 결합 | 변경 후 책임과 함께 맞출 대상 |

복구 적용 조건과 자료의 소유는 [작업 상태 — 「복구의 대상과 경계」](../design/workflow/recovery.md), 보조의 권한과 결과 인계는 [보조 역할](../design/integration/local-ai.md)가 소유한다. 현재 WSL 개인 hook과 launcher는 이번 대응표 때문에 교체하지 않는다.

### 자체 검사와 배포 제외

11/13 사용자는 `docs/platform.md`와 제품별 guides, contract가 본인 작업이 아니므로 모듈에 가져오지 않아도 된다고 확인했다. 해당 원문은 모듈의 공통 코드, 템플릿, 공개 WIKI로 추출할 대상에서 제외한다. 현재 기존 시험 프로젝트 원본의 삭제나 Git 이력 변경은 하지 않는다. 일반 적용 프로젝트의 계약 문서를 연결하고 검증하는 기능은 유지한다.

| 현행 자산 | 변경 후 처리 |
| --- | --- |
| `.codex/scripts/check-harness-scenarios.sh` | **수정, 분리.** 분기 회귀 사례를 모듈 개발 검사의 입력으로 활용. 현재 script의 출력과 종료값을 그대로 기대값으로 복사하지 않고 채택한 검증/복구 계약에서 기대 행동을 정함. 설치 후 연결 확인과 개발용 전체 검사를 구분 |
| `.github/workflows/ci.yml`, `.github/workflows/contract-check.yml`, `.github/workflows/cd.yml` | **제품 전용 구현 제외.** 현재 앱 CI는 앱의 빌드/계약/배포 책임. 모듈 자체 CI와 코드/WIKI PR 연계를 새로 연결해야 하며 앱 CI 성공은 모듈 검사 성공이 아님 |
| `docs/platform.md`, 제품별 `docs/guides/**`, `docs/contract/**` | **모듈 추출과 배포에서 제외: 사용자 재확인.** 현재 제품의 문서 세트나 본문을 새 모듈로 가져오지 않음. 원본은 보존 |
| 제품별 요구, ADR, runbook 본문 | **공통 본문 제외.** 적용 프로젝트에서 유효한 근거로 보존/참조. 선택 기능을 추가해도 기존 문서를 정리하거나 공개할 권한으로 확대하지 않음 |
| 설치와 실행의 수명 | 임시 설치 자료를 정리한 뒤에도 프로젝트의 실행 구성이 동작해야 함. 예비 도구 관측과 제품 설치 검증을 구분 |

### 추출 후보의 출처와 권리

기존 작업 계약과 ADR 양식은 여러 작성자의 변경이 섞인 자료다. 현재 blame의 작성자만으로 최초 양식의 저작자를 확정하지 않는다. 공통 템플릿은 공식/신뢰 가능한 자료를 참고해 새로 작성하고 출처와 이용 조건을 확인한다. 다른 제품의 본문이나 비공개 계약을 템플릿으로 복사하지 않는다. 감사에서 확인한 책임과 경계는 설계 입력이며 기존 코드 전체의 배포 권한을 뜻하지 않는다.

## 새로 구현해야 할 책임

기존 설계로 채택한 기능 중 현행 파일에 완성된 제품 구현이 없는 항목이다. 아래 행마다 새 서비스나 실행기를 하나씩 만든다는 뜻은 아니다.

| 책임 | 연결할 기존 자산 | 소유 설계와 완료 확인 |
| --- | --- | --- |
| 설치, 최초 선택과 후속 추가, 갱신/복원 | 추린 진입 규칙, skill, script, config, 템플릿 | [설치](../design/runtime/install.md), [갱신](../design/runtime/update.md). 외부 설치 도구를 제거한 뒤 프로젝트 내 실행, 기존 편집/추적 정책과 부분 완료 보존 |
| 프로젝트와 WIKI의 역할별 위치 연결 | 문서 라우터, 문서 작업 절차, 검사 대상 | [위치표](../design/knowledge/map.md). 기존 자료/빈 WIKI, 다른 이름/경로, 내부/외부 WIKI에서 필요한 자료 발견 |
| 상세 WIKI 생성과 보강 | 기존 요구/검토/ADR 형식과 문서 검증 | [분석 실행](../discussions/knowledge/reconstruction.md). 범위/근거/후보를 구분하고 단일 반영. 모델 목록과 범위 선택은 AI 본문 생성 전에 처리. [완료 뒤 재실행 — 「완료 후 다시 실행하는 흐름」](../discussions/knowledge/reconstruction.md)은 유효 결과 재사용과 새 보완/검토를 구분 |
| 조건부 테스트 작성 skill | 개발 진입, 기존 테스트와 검증 절차 | [작성 절차 — 「절차를 둘 위치」](../design/workflow/verification.md). 동일 메인이 필요한 사례를 보강하고 공통 검증으로 인계. 별도 실행기/DB 추가 금지 |
| 계획과 시도 기록, 조건부 재개, 보존/정리 | gate 결과, active, hook, 재시도 | [저장 수단 — 「저장 수단과 자료의 소유」](../design/workflow/recovery.md). SQLite의 기계 기록과 Markdown 의미 상태, 원문 파일을 연결. DB commit을 파일/PR 복원으로 해석하지 않음 |
| 코드/WIKI 저장소의 최소 PR 연계 | 프로젝트 Git 상태와 WIKI 변경, 사람의 검토 | [작업 연계](../design/sync.md), ADR 0017. 생성/재사용/연결/상태 검사와 한쪽 실패 대조. 승인/병합은 사람 |
| 설명/학습 문서의 선택 확장 | 기존 문서 분류와 라우팅 | [첫 선택 기능](../decisions/architecture/0007-release-scope.md). 최초/후속 추가 모두 연결하고 미설치 기능을 기본 검사에서 강제하지 않음 |

## 기능별 연결과 실패 처리

아래는 호출 순서의 대응표다. 명령 문자열이나 프로그램 함수 목록은 후속 명세이며, 첫 행부터 모든 작업에서 실행하는 일괄 파이프라인이 아니다.

| 기능과 진입 조건 | 설정에서 실행까지 | 결과를 소비하는 곳과 실패 시 흐름 |
| --- | --- | --- |
| 외부 연결 명령 또는 일반 Codex 안 연결 트리거 | 기존 설정 재사용 또는 사용자 입력 → 공통 connect/check로 경로 검사/저장 → 가능한 경우 현재 세션에서 사용 | [진입 결과 소비 — 「결과를 받는 절차」](../design/runtime/entry.md)를 따름. 입력 방식만 나누고 검사/저장 코드를 공유. 권한이 부족하면 해당 준비만 처리하며 전체 복구를 강제하지 않음 |
| 제품 시작/재개 | 현재 위치/명시 대상/사용자별 목록에서 실행 대상을 확정 → 그 프로젝트의 공유/로컬 설정 확인 → CLI 세션에 인계 | [실행별 선택 — 「여러 프로젝트의 선택과 실행」](../design/runtime/entry.md)을 적용하고 다른 창의 대상을 바꾸지 않음. 연결, 세션 열기와 작업 완료 구별. 일반 Codex 안의 연결 성공에 이 진입을 다시 요구하지 않음 |
| 일반 요청 | 짧은 진입 규칙 → 메인의 수준/게이트 판단 → 필요한 프로젝트 규칙과 WIKI만 탐색 | 메인이 작업 범위 결정. 필요한 정보가 없거나 충돌하면 관련 부분 확인. 단순 요청에는 전체 문서/DB 복구 없음 |
| 필요한 테스트 작성과 검증 | 작성 조건 판단 → 관련 요구/기존 테스트 → 작성 결과 인계 → 프로젝트 검사 계획 → 실제 명령 실행 | 메인이 실행 증거와 현재 의무를 대조해 로컬/전체 완료 판단. 미실행/불명확은 PASS 아님. FAIL이면 다음 행 |
| 명확한 검사 FAIL | 보존한 실패/검사 입력 → 원인 수정 → 영향받은 검사와 원래 실패 재실행 | 결과 소비자가 재시도 관계와 남은 의무 확인. 문맥이 충분하면 일반 재시도로 계속, 실행 효과 미확인일 때만 해당 시도 대조 |
| 세션 시작/재개/compact 후 이어갈 작업 존재 | 도구 연결의 안내 또는 명시적 재개 → 작업 확인 → 해당 active와 필요한 근거 | 목표/승인/다음 작업 복원. 실행 여부가 불명확한 부분만 실제 효과 대조. 다른 작업의 active나 관련 없는 설치 기록을 적용하지 않음 |
| 설치/갱신 명령 또는 그 작업 재개 | 대상/준비물/기존 자료 확인 → 변경 계획 → 필요한 보존 → 적용과 검사 | 완료 단위는 조건을 확인해 유지. 의존성 부족이나 충돌은 보고하고 관련 작업 중단, 합의/환경 보완 후 재검사. 무조건 전부 롤백하거나 남은 변경을 임의로 계속하지 않음 |
| WIKI 분석 명령 | 위치표/선택 범위와 기존 실행 상태 → 재사용/재개/새 검토 판단 → 필요한 분석 단위와 실행 입력 → 별도 후보 → 형식/의미/최신성 검토 → 단일 반영 | [재실행 계약 — 「완료 후 다시 실행하는 흐름」](../discussions/knowledge/reconstruction.md)에 따라 유효 결과를 유지. 실행 중 중복 시작 금지. 입력 변경 시 이전 후보 적용 중단/재대조. 중요한 내용 모순과 미완료를 구분하며 WIKI 재사용을 테스트 PASS로 바꾸지 않음 |
| 코드/WIKI PR 연계 요청 | 두 저장소의 준비된 로컬 변경/버전 → PR 생성 또는 재사용 → 상호 연결과 상태 검사 | 사람이 검토/승인/병합. 결과 불명 또는 한쪽 실패 시 실제 원격 상태부터 확인하고 중복 PR을 만들지 않음 |

안전 조건의 상세는 [검증 G 조건 — 「채택 원칙과 남은 명세」](../design/workflow/verification.md), [재개 판단 순서](../design/workflow/recovery.md), [적용 전 대조와 부분 완료](../design/runtime/update.md)에 있다. 외부 편집 보호, 로컬 중복 재개 방지와 SQLite 내부 쓰기 처리는 서로 대체하지 않는다. 팀원의 독립 clone은 Git으로 통합한다.

## 직접 접근 실행기의 개발 준비

11/23 WIKI 재실행 채택은 위 분석 기능의 구현 책임에 연결했다. [검증 입력 — 「완료 후 재실행의 검증 입력」](../verification/acceptance.md)을 실제 명령, 작업/시도 참조, 근거와 후보 보존, 반영 직전 대조와 완료 반환에 대응해야 한다. 검사 전용 필드를 의미가 다른 WIKI 처리 상태로 재사용하지 않는다. 이 상세 구현을 기본 실행기 등록의 선행 작업으로 끼워 넣거나 현재 완료로 표시하지 않는다.

11/22 [ADR 0022 — 「11월 22일 첫 제공 범위」](../decisions/runtime/0022-wiki-entry.md)에 따라 MCP 첫 제공을 후속으로 미루고 기존 4단계로 복귀했다. 첫 실행기 단위의 목표는 **등록한 프로젝트/WIKI와 사용자 입력을 보존해 현재 설치된 Codex에 인계하는 것**이다. 설치/역공학/업데이트 전체를 이 명령 하나로 실행하는 것이 아니다. 현재 WSL 예비 도구를 이름만 바꿔 배포하지 않는다.

| 구분 | 첫 단위에 연결할 대상 | 완료 또는 남은 조건 |
| --- | --- | --- |
| 이미 채택한 입력 | 코드 프로젝트, 내부/외부 WIKI, 위치표, 새 시작 또는 선택적 재개, 사용자 Codex 인자, npm/공식 Windows 설치 | 공유/로컬 설정의 책임과 일반 Codex 안 연결 지원 유지. 두 설치를 동시에 요구하지 않음 |
| 저장할 정보 | [연결 필드 — 「연결 설정의 필드와 읽기 규칙」](../design/runtime/entry.md)와 [명령 결과 — 「명령 결과의 형식」](../design/runtime/entry.md) | 공유/로컬 설정과 준비 반환의 후보 작성. 예시 JSON/표의 정합성 검사와 실제 저장/권한 검증은 구별 |
| 제품 구현 전에 확정 | [제품/명령 이름 — 「제품 이름과 변경 기준」](../design/module.md), [설치 위치 — 「프로젝트 설치 위치 후보」](../design/runtime/install.md)와 파일별 연결 | OnepLoom/oneploom과 프로젝트 루트의 `oneploom/` 기본 배치를 반영. [표준 명령 등록](../decisions/runtime/0023-command-registration.md)을 채택. 기기 소유/기존 DB 참조, [설치본 발견/인계](../design/runtime/project-entry.md)와 [최초 설치/명령 관리](../design/runtime/management.md)를 명세했다. 설치 계획의 확인 전달과 공식 배포 자료를 통한 팀원 준비를 명세했다. 실제 구현에서 그 계약을 확인한다. 기기 효과의 저장 구현은 별도 필수 조건. [설치별 진입 — 「Codex 설치 형태와 실행 파일 선택」](../design/runtime/entry.md), 설정/결과 필드와 [권한 재사용 명세 — 「권한 선택 재사용의 판단 순서」](../design/runtime/entry.md)를 입력으로 사용 |
| 구현하며 실제 확인 | 현재 설치본에 대한 옵션/권한 조회와 적용의 대응, 반복 선택 재사용, 대화형 시작/재개/종료 | 기존 저장 응답은 부분 근거. 두 설치 형태의 Windows 시험으로 확인하고 관리 정책/프로필 조회가 불완전하면 자동 재사용을 허용하지 않음 |
| 후속으로 분리 | MCP 등록/전송/쓰기 지원, 로컬 AI/다른 호스트 연결, 첫 범위 밖 설치 형식 | 첫 실행기의 필수 의존성으로 넣지 않음. 기존 연구/수용 조건은 보존 |

첫 개발 단위를 마쳤다고 판단하려면 경로 등록/확인/시작/재개가 같은 설정을 소비하고, 명시하지 않은 모델/인증/전역 설정/프롬프트를 바꾸지 않아야 한다. 실제 Windows에서 한글/공백/메타문자 인자, 다른 프로젝트의 연결 방지, 최초 선택 이후 재사용과 철회, 현재 Codex 업데이트 뒤 발견, 취소/종료를 확인한다. 실제 WIKI 읽기/수정과 다른 내용 보존도 준비 결과와 별도 관측한다. 이미 실행한 과거 시험을 제품 구현의 PASS로 재사용하지 않는다.

이 표는 4단계의 인계 점검이며 제품 개발/Git 작업을 시작한 결과가 아니다. 이름과 기본 설치 위치를 정했고 명령 등록/연결 명세를 닫은 뒤 기존 5단계의 저장소, 브랜치와 개발 단위 준비로 넘긴다. 권한 조회의 실제 호환성은 위 구현 검증의 완료 조건으로 유지한다. 공개 범위/라이선스와 모듈 저장소 및 선별 WIKI 구성은 기존 배포 결정에 따른다. 상세 WIKI 복원, 검증/복구, PR 연계의 필수 범위를 이 첫 실행기 단위로 축소하지 않는다.

현재 파일별 연결은 다음 문서가 소유한다. 아래는 구현할 책임의 연결표이며 같은 상세 규칙을 이 대응표에 다시 관리하지 않는다.

| 책임 | 명세 원본 | 구현 완료에 필요한 근거 |
| --- | --- | --- |
| 대상 확인, 목록, 프로젝트 인계 | [프로젝트 선택](../design/runtime/project-selection.md), [설치본 인계](../design/runtime/project-entry.md) | 다른 작업 사본/사용자 지정 위치, Python/인자/콘솔 전달과 취소/종료 |
| 최초 설치와 사용자별 명령 관리 | [관리](../design/runtime/management.md), [팀원 준비 — 「팀원 첫 준비의 배포 자료」](../design/runtime/install.md) | 최초 담당자와 새 팀원의 구분, 유효 등록 재사용, 공식 wheel/venv 등록과 정리 뒤 정상 사용 |
| 계획 확인, 중단 기록과 실제 효과 | [확인 기록 — 「변경 계획의 확인 기록」](../design/workflow/storage.md), [등록 효과 — 「기기 등록 효과의 저장 경계」](../design/workflow/storage.md) | 기존 DB 관계의 구현, 파일/PATH 대조와 재개. 기존 SQL의 파일용 제약만으로 기기 효과를 완료 처리하지 않음 |
| 직접 WIKI와 현재 Codex 연결 | [진입](../design/runtime/entry.md), [수용 입력 — 「전용 시작 명령의 검증 입력」](../verification/acceptance.md) | 두 공식 설치 형태, 조건/권한 재사용과 실제 읽기/수정, 원문 및 사용자 설정 보존 |

11/23 전체 정리로 공식 Release의 사용자별 명령 준비와 프로젝트 Git의 wheel 기본 제외를 채택했다. `command install`은 새 팀원/새 계정의 명령만 준비하고, 프로젝트 `install`은 필요한 등록을 같은 과정에서 처리한다. `connect`는 자기 작업 사본의 WIKI 연결을 담당하며 설치/전체 복원을 반복하지 않는다.

다음은 이 책임표를 [5단계 개발 준비안](workspace.md)의 저장소/브랜치/개발 단위에 연결하는 것이다. 기능별 명세와 수용 입력이 작성된 것과 제품 구현 완료는 구별한다. 상세 WIKI 복원/검증/복구/최소 PR 연계는 이후 필수 단위로 유지하며 첫 실행기만 완성했다고 배포 전체를 완료 처리하지 않는다. 기존 상세 경과는 [관측 기록 (정리 전 대응표)](../evidence/experiments/design/2026-11-23_07-38-22-wiki-reconcile.md)에 보존했다.

## 다음 명세와 완료 조건

첫 대응표와 [진입 연결](../design/runtime/entry.md)을 작성하고 AGENTS 최소 연결 A, 제품 시작 자동 연결과 일반 진입의 최소 보완을 채택했다. 연결 결과의 소비와 실패 복귀, [검증/복구 기록](../design/workflow/records.md), [설치/갱신과 기능 추가의 입력/소비 — 「설치 기록과 단계 연결」](../design/runtime/install.md)를 초안으로 연결했다. 4단계 전체가 끝난 것은 아니다. SQL 후보/부분 검사와 저장/보호 설계는 관련 문서에 연결됐고, 연결/관리 명령과 필드, 지원할 두 공식 설치 형식은 명세했다. 다른 필수 기능의 남은 상세와 Windows 구현/실증은 후속이다. 직접 접근 실행기의 개발 준비를 다음 명세로 좁히며 전체 구현이 끝났다고 표시하지 않는다. 전체 순서는 [진행표](roadmap.md)만 갱신한다.

4단계를 닫으려면 다음을 확인해야 한다.

1. 선택한 기본 모듈의 파일마다 원본, 설치 결과와 사용자/호스트 값의 소유가 분명하고 이름 변경의 모든 소비자가 연결돼 있다.
2. 기능에서 실제 진입, 입력, 실행, 결과 소비까지 빠진 연결이 없고 오류/중단 때 돌아갈 지점이 명확하다.
3. 검증의 계획/실행 구별, 원래 실패, 결과 불명, 사용자 편집/기존 자료 보존 조건이 파일별 명세에서도 유지된다.
4. [수용 기준](../verification/acceptance.md)의 해당 사례와 명세를 대응하고, 모의 검사와 실제 Windows/AI/PR 시험의 범위를 구별한다.

현재 `.codex/skills`가 이 세션에 제공되는 사실만으로 배포 사용자의 발견 경로를 확정하지 않는다. 정확한 도구 경로, hook 호출, 지원 버전은 실제 배포 조건으로 확인해야 한다. 새 중요한 선택이 생기면 해당 부분만 협의하며, 이미 채택한 프로젝트 내 설치와 Git 릴리스 + Python 방향은 다시 선택하지 않는다.
