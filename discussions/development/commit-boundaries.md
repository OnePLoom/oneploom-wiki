# 커밋 단위의 공개 사례와 OnepLoom의 선택

조사일: 2026-11-26. 문서 반영일: 2026-11-27. **작은 논리 단위와 Rebase and merge를 유지하면서, 준비 작업을 나눌 호환성 조건과 커밋 후 오류 수정 기준을 명확히 한다.** 이 문서는 공식 지침, 공개 이력과 대안의 장단점을 기록한다. 실행 규약의 원본은 [코드 CONTRIBUTING](https://github.com/OnePLoom/oneploom/blob/main/CONTRIBUTING.md)의 「브랜치와 변경 단위」와 「병합과 이력」이며, 채택 결정은 [ADR 0012](../../decisions/development/0012-branches.md)의 「작업 단위와 시작점」에서 확인한다.

## 조사 범위와 해석 방법

Git, Linux kernel, Google Engineering Practices, LLVM, Kubernetes, CPython, Go, Microsoft VS Code의 공식 지침을 확인했다. Microsoft, Google의 공개 자료를 해당 회사의 모든 내부 팀에 적용되는 규칙으로 확대하지 않는다. 서로 다른 배포 프로젝트의 기여 지침과 실제 공개 이력이 비교 대상이다.

실제 이력은 VS Code, CPython, LLVM에서 저장소마다 최근 갱신된 닫힌 PR 30개를 후보로 조회하고, 병합된 사례 중 변경 성격이 다른 6개를 골랐다. 최근 병합 순서로 뽑은 90개나 무작위 대표 표본이 아니다. 선택한 PR의 전체 커밋 목록, 변경 파일 목록, GitHub가 연결한 병합 결과 커밋과 핵심 diff를 대조했다. 프로젝트의 코드와 CI를 직접 실행한 검증은 아니다. [조사 사실 자료](../../evidence/experiments/development/2026-11-26-commit-boundaries.json).

비교할 때 세 단위를 구분했다.

- **작업 중 커밋:** 구현과 리뷰 중 저장한 단계다. 리뷰 수정이나 기준 브랜치 병합도 포함될 수 있다.
- **검토 단위:** PR 또는 CL이다. CL(change list)은 함께 검토하는 변경 묶음이며 항상 Git 커밋 하나와 같지는 않다.
- **최종 이력의 커밋:** main에 남는 단계다. Squash and merge는 여러 커밋을 하나로 합치고, 우리가 선택한 Rebase and merge는 개별 변경을 차례로 반영한다. GitHub rebase 병합 뒤 SHA는 달라질 수 있다.

따라서 다른 PR에 커밋이 7개 있다는 사실만으로 독립 기능을 7개로 나눴다고 판단하지 않는다. 문서가 개별 커밋 기준을 명시하지 않으면 관측한 사례만 설명하고, 숨은 조직 규칙을 만들어내지 않는다.

PR 안의 리뷰 수정 커밋을 그대로 최종 커밋의 모범으로 보지 않는다. |
| [Kubernetes, Pull Request Process의 Squashing](https://www.kubernetes.dev/docs/guide/pull-requests/#squashing) 및 [GitHub Workflow의 Squash commits](https://www.kubernetes.dev/docs/guide/github-workflow/#squash-commits) | 리뷰 중 수정은 새 커밋으로 보여주고, 최종적으로는 단순 수정 이력과 의미 있는 단계들을 구분한다. 후자는 유지할 수 있다. 각 커밋의 독립 빌드와 테스트는 목표지만 해당 지침은 필수라고 하지 않는다. | 모든 유명 프로젝트가 커밋별 검증을 같은 강도로 강제한다고 주장할 수 없다. 우리 검증 수준을 낮추거나 공유 이력을 재작성할 근거로 삼지 않는다. |
| [CPython, Quick reference의 Don’t force-push](https://devguide.python.org/getting-started/quick-reference/#don-t-force-push) | 리뷰어가 수정 이력을 볼 수 있도록 PR의 이력 재작성을 피하고, 병합 때 하나로 합친다. | 작업 중 커밋 경계와 최종 변경 경계가 다르다. 공개된 이력을 보존하는 부분은 우리와 맞지만 최종 병합은 다르다. |
| [Go, Contribution Guide](https://go.dev/doc/contribute) | Gerrit 경로는 한 변경을 한 커밋에 보완하며 같은 Change-Id로 리뷰 버전을 연결한다. GitHub 경로는 여러 커밋을 추가할 수도 있지만 최종적으로 하나로 합친다. | ‘브랜치당 한 커밋’은 해당 도구와 리뷰 절차의 조건이다. OnepLoom의 여러 작은 커밋과 PR 하나 방식이 잘못됐다는 근거가 아니다. |
| [Microsoft VS Code, Pull Requests](https://github.com/microsoft/vscode/wiki/How-to-Contribute#pull-requests) | 이슈별 PR, 작은 변경, 무관한 포맷 변경 배제와 가능한 테스트 포함을 안내한다. | 확인한 이 문서에서는 별도의 상세 커밋 분할 규칙을 찾지 못했다. 아래 실제 이력을 보되 Microsoft 전체 규칙으로 일반화하지 않는다. |

문서들 사이에도 강조점이 다르다. 새 API와 실제 사용을 함께 보여주라는 Google의 설명과 준비 API를 먼저 나눌 수 있다는 Linux/LLVM의 설명은, 사용처가 없는 선언을 무작정 허용하거나 모든 API와 모든 호출자를 항상 한 번에 바꾸라는 뜻이 아니다. 현재 동작, 의존 관계와 리뷰어가 이해할 근거를 갖췄는지 판단해야 한다.

## 현재 기준과 대조

| 현재 OnepLoom 기준 | 조사 결과와 대조 | 판단 |
| --- | --- | --- |
| 한 가지 목적의 작고 완결된 변경 | Git/Linux의 개별 단계와 Google의 검토 단위 설명에 부합 | 유지 |
| 앞선 커밋에 의존할 수 있지만 뒤 커밋이 오류를 고쳐야 하는 상태로 나누지 않음 | Git/Linux와 가깝고, 개별 커밋을 남기는 Rebase and merge에 적합 | 유지. 모든 과거 커밋이 무결함이라는 보장은 아님 |
| 구현, 필요한 호출부와 관련 테스트를 함께 포함 | 기본 방향은 맞지만 ‘모든 호출부를 항상 동시에 바꾼다’고 읽으면 준비 API와 점진 이전을 막을 수 있음 | 호환성을 기준으로 문구 보완 채택 |
| 독립 정리, 테스트와 문서 작업은 별도 커밋 가능 | Linux의 변경 분리, LLVM의 점진 개발과 테스트 전용 사례에 부합 | 이미 있는 규칙 유지 |
| 파일 종류나 일정 줄 수로 기계적으로 분할하지 않음 | 확인한 지침들은 이해와 변경 목적을 우선하며, 계층 분할도 조건에 따라 허용 | 유지. 파일/줄 수는 검토 부담을 찾는 단서로만 사용 |
| 실제 stage와 검사 입력 일치, 영향 없는 PASS 재사용 | 실제 변경과 검사 입력을 맞추고 영향 없는 결과만 재사용하는 기존 검증 기준에 부합 | 기존 기준 유지. 실제 입력이 달라지면 해당 결과를 재검증 |
| 작은 커밋 여러 개를 PR 하나로 묶되 PR도 독립 검토 가능해야 함 | 작은 커밋만으로 큰 PR의 검토 부담이 사라지지는 않음 | 이미 있는 규칙을 실제 작업 분할에 적용 |
| 공유 이력 보존, 자동 amend/강제 push 금지 | CPython의 리뷰 보존과는 맞지만 우리 최종 이력은 squash되지 않음 | 커밋 이후 수정의 목적과 처리 기준 명확화 채택 |

코드와 WIKI는 별도 Git이다. 다른 프로젝트의 ‘코드와 문서를 한 커밋에 포함’ 사례를 그대로 적용해 서로의 커밋 수를 1:1로 맞추거나 두 커밋이 동시에 성공한다고 가정하지 않는다. 같은 논리 작업의 설명과 검증은 공통 작업 이슈와 PR 관계로 연결한다.

## 선택 1: 준비 작업은 호환성과 실제 쓰임을 기준으로 분리

현재 ‘필요한 호출부를 함께 둔다’와 ‘사용처 없는 선언을 쌓지 않는다’는 기준은 유지한다. 다음 분리 조건을 명확히 하는 보완을 채택했다.

> 기존 호출이 계속 정상 동작하는 준비 변경은 자체 목적과 검증 근거, 실제 예정 사용처와 선행 의존을 설명할 수 있으면 별도 커밋으로 나눈다. 기존 계약을 깨는 변경은 영향받는 호출부를 함께 고치거나, 먼저 호환 가능한 이전 단계를 마련한다.

예를 들어 경로 처리 구조를 바꿀 때 기존 동작을 보존하는 정리와 테스트를 먼저 커밋하고, 다음 커밋에서 새 경로 선택 동작과 필요한 테스트를 추가할 수 있다. 반대로 함수 이름만 바꿔 기존 호출이 실패하는 상태를 먼저 커밋한 뒤 다음에 호출부를 고치는 분리는 피한다. 이 예시는 새 기능이나 추상화 도입 계획이 아니다.

**장점:** 준비 정리와 동작 변경을 따로 검토하고 변경 이유를 추적하기 쉽다. **비용:** 단계 사이 의존을 설명해야 하며, 중간 API나 호환 처리를 괜히 늘리면 오히려 복잡해진다. 우리 규모에서는 한 번에 고치는 편이 더 명료하면 억지로 중간 계층을 만들지 않는다.

이것은 Linux/LLVM을 그대로 복제한 규칙이 아니라 Google의 사용 근거 요구와 함께 고려한 OnepLoom의 선택이다. 파일 계층을 기준으로 무조건 나누거나 미정 미래를 위한 선언을 허용하지 않는다.

## 선택 2: 커밋 전 수정과 커밋 후 수정을 구분

Rebase and merge를 유지하므로 ‘리뷰 반영’, ‘테스트 수정’ 같은 불명확한 작업 로그도 그대로 main에 남을 수 있다. 다음 처리 기준의 명확화를 채택했다.

1. **커밋 전 검토에서 발견한 문제:** 같은 변경을 고치고 관련 검사를 다시 확인한 뒤 변경 이유를 설명할 수 있는 하나의 논리 단위로 커밋한다.
2. **이미 커밋한 뒤 발견한 문제:** 실제 오류나 보완 목적을 밝힌 새 커밋으로 처리하고 같은 작업에 연결한다. 예를 들어 `fix: 프로젝트 선택 취소 시 잘못된 대상 반환 방지`처럼 무엇이 달라지는지 드러낸다. 단순히 변경 수를 숨기려고 자동 amend/squash하거나 공유 브랜치를 강제 push하지 않는다.
3. **처음부터 필수 검사를 통과하지 못하는 분할:** 뒤 커밋에서 고칠 계획으로 먼저 확정하지 않는다. 검토 후 예상하지 못한 오류가 발견된 것과 의도적으로 깨진 중간 상태를 남기는 것은 다르다.

**장점:** 검토와 실제 반영 이력을 보존하며 오류 원인을 찾기 쉽다. **비용:** squash 방식보다 작은 후속 수정 커밋이 남을 수 있다. 이력의 개수를 줄이는 것보다 의미와 추적성을 우선하는 현재 선택에 맞다. 문구 보완이지 앞으로 모든 후속 오류를 방지할 수 있다는 보장은 아니다.

PR 제출 전에는 최종 diff뿐 아니라 남길 커밋의 목적과 의존도 간단히 확인한다. 이미 커밋별로 검토한 내용을 다시 전부 설명하는 절차나 새로운 CI를 추가하자는 뜻은 아니다. 이력 재정리가 꼭 필요하면 기존 정책과 다른 작업이므로 별도 판단하며, 이번 조사로 허용하지 않는다.

## 유지할 운영과 적용 예시

검증을 강화한다는 이유로 매 커밋마다 모든 Windows 통합 검사를 중복 실행하지 않는다. 변경 목적과 영향에 필요한 검사를 하고, 실제 커밋에 담기는 내용과 검사 입력이 같음을 확인하며, 최종 PR에서 전체 요구와 통합 결과를 검토하는 기존 원칙을 유지한다. 새 동작에 필요한 테스트를 나중으로 미루거나 이전 PASS를 입력 대조 없이 재사용해서도 안 된다.

변경 설명에는 아래 판단이 보이면 충분하다. 새 필수 서류나 고정 커밋 개수를 만들 필요는 없다.

- 이번 커밋이 해결하는 한 가지 목적과 이 단계에서 완료되는 범위.
- 먼저 있어야 하는 변경, 함께 바꾸는 계약과 뒤 단계로 남기는 범위.
- 실제 stage를 기준으로 무엇을 검사했으며 무엇이 아직 미확인인지.

예시 흐름은 `기존 발견 동작을 보존하는 경로 처리 정리 → 명시 경로의 새 오류 처리와 테스트 → 현재 위치 발견의 새 경계 처리와 테스트`다. 각 단계의 목적과 테스트를 설명하고 관련 요구를 만족한 시점에 PR을 준비한다. 첫 정리가 필요 없으면 생략하며 예상 단계 수를 맞추지 않는다.

첫 기능 PR을 작성하는 과정에서 운영 정책과 공개 양식 변경이 누적된 점은 별도 교훈이다. 이후 독립 운영 보완은 별도 PR로 나누는 기존 원칙을 적용한다. 당시 공유한 PR의 이력을 이번 조사만으로 분해하거나 재작성하지 않는다.

Google 지침은 검토 대기 동안 다른 변경을 진행하는 방법도 설명한다. 검토를 언제 요청할지는 프로젝트의 협업 방식에 맞춰 정하며, 작은 변경이라는 이유만으로 토큰이나 시간 절감 폭을 확정하지 않는다. 이번 비교에서는 절감 효과를 측정하지 않았다.

## 근거와 적용 범위

공식 지침을 프로젝트의 병합 방식, 의존 관계와 검토 비용에 맞춰 해석한 선택이다. 외부 코드나 템플릿을 제품에 복제하지 않았으며 링크, 공개 이력의 사실과 자체 비교를 제공한다. 사례의 조회 시각과 당시 상태는 조사 사실 자료에 보존한다. 다른 저장소의 정책 변경이나 더 넓은 규모의 효과까지 검증한 것은 아니다.

규칙의 문서 반영, 실제 작업에서의 적용과 그 효과 측정은 서로 다른 단계다. 이번 반영만으로 CI나 제품의 Git 자동화가 구현된 것은 아니다. 이 문서의 작업은 [문서 정리 이슈](https://github.com/OnePLoom/oneploom-wiki/issues/2)에서 추적한다.
