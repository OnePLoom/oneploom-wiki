# WIKI 위치표의 형식과 분리 비교

> 과거 검토 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

11/09의 비교, 예시, 추천 근거를 11/11 정리에서 옮겼다. JSON, 명시적 목록, 필요한 기능별 한 단계 분리, 도구 등록/선택 조회는 채택됐으며, 상세 필드는 후속 명세다. 현재 정보 역할은 [WIKI 설계](../../design/knowledge/wiki.md), 입력/조회 계약은 [위치표 명세](../../design/knowledge/map.md), 채택 원본은 [ADR 0004](../../decisions/architecture/0004-portability.md)가 소유한다. 아래의 미선택 대안도 함께 구현한다는 뜻은 아니다.

## 위치표를 저장하는 방식

역할별 원본 연결을 실행 절차가 읽을 형태로 좁힌 11/09 비교다. **JSON 형식은 채택**했으며 구체 필드, 조회/갱신 결과는 [위치표 명세](../../design/knowledge/map.md)의 초안이다. 실제 설정 설치나 제품 구현은 하지 않았다.

| 방식 | 장점 | 단점, 추가 책임 |
| --- | --- | --- |
| Markdown 표 | WIKI에서 설명과 위치를 함께 읽고 편집하기 편함 | 기계 입력으로 사용할 열, 문법 규칙이 필요. 표 편집과 설명 변경이 실행 입력에도 영향을 줄 수 있음 |
| JSON 설정 | 작은 자료 구조를 명확히 읽고 검사하기 좋음. WIKI 본문 편집과 분리 가능 | 주석을 넣을 수 없고 수동 편집 시 따옴표, 쉼표에 주의. 사용 안내와 친절한 오류가 필요 |
| TOML 설정 | 주석과 사람이 읽기 쉬운 설정 문법을 제공 | 여러 연결을 표현할 표/배열 규칙과 지원 파서를 정해야 함. 자동 작성 시 주석 보존도 고려 |

**작은 JSON 설정 + Markdown 본문**을 채택했다. AI가 연결의 의미와 변경을 판단하고 일반 도구로 조회, 검사, 갱신하며, 상세 설명은 Markdown에 남긴다. 사람이 개입할 수 있는 명확성을 유지한다. 손으로 설정을 자주 편집하는 사용성이 더 중요해지면 TOML을 다시 비교할 수 있지만 현재 선택을 미채택으로 되돌리는 뜻은 아니다. JSON을 쓴다고 내용이 정확해지거나 토큰 절감이 자동 보장되지는 않는다.

형식의 근거는 [JSON 표준](https://www.rfc-editor.org/rfc/rfc8259), [TOML 명세](https://toml.io/en/v1.0.0), [GFM 표 문법](https://github.github.com/gfm/#tables-extension-)이다. 선택과 유지 비용의 평가는 이 모듈의 설계 판단이며 각 표준이 우열을 정해 주지는 않는다.

초기 항목 예시는 [저장 형식 초안](../../design/knowledge/map.md)에 통합했다. 역할, 범위, 원본, 경로와 선택적 절을 연결하며, 가상 상품의 요구와 계약을 같은 기능 아래 구분한 예시다. 정확한 필드, 역할 값, 절 선택자는 아직 최종 입력 계약으로 채택하지 않았다. 기능 범위를 코드 디렉토리 이름만으로 확정하지 않는다.

위치표는 프로젝트가 소유하는 WIKI 연결 자료로 관리하는 안이다. 공통 배포물에는 빈 형식과 처리 절차만 제공하고 실제 경로, 내용은 해당 프로젝트가 채운다. `code`, `wiki`의 실제 절대 경로와 권한은 호스트의 로컬 설정에 둔다. 코드 저장소가 공개되고 WIKI가 비공개인 경우 위치표도 비공개 WIKI 쪽에 두며, 코드의 공유 지침에는 일반 진입 절차만 연결한다. 구체 설치 위치는 설치 계약에서 확정한다.

## 사람이 읽고 관리하는 위치표

11/09 명확화: **정상 사용, 유지보수는 AI가 중심이며, 사람이 이해하고 개입할 수 있다는 조건을 함께 유지한다.** 앞선 설명에서 사람만의 운영을 중심처럼 확장한 부분을 바로잡는다. JSON은 AI가 역할, 범위, 위치를 일관되게 다루고 일반 코드가 조회, 검사, 갱신할 연결 설정이다. 프로젝트가 설정과 이력을 소유한다는 것과 사람이 매번 직접 관리한다는 것은 다르다. AI의 내부 사고 기록이나 폐기 가능한 캐시로 취급하지 않으며, 다시 만들 수 있는 조회 결과, 색인과 구별한다.

| 대상 | 평소 사용 | 관리 책임 |
| --- | --- | --- |
| Markdown 본문, 목차 | 사람과 AI가 요구, 설계, 판단, 근거를 읽고 탐색 | 내용 소유자가 사실, 정책, 연관 링크를 관리 |
| 역할별 위치표 | AI가 연결의 의미, 변경 범위를 판단하고 도구를 사용해 유지보수. 일반 코드는 조회, 형식/경로 검사, 갱신을 담당 | 허용 범위 안에서 AI와 도구가 관리하고 사람이 필요할 때 필드, 변경 내역을 이해해 개입 가능해야 함 |
| 요청별 조회 결과 | 필요한 연결과 누락/충돌을 사람이 보기 쉬운 형태로 확인 | 설정에서 계산한 결과이며 별도 수동 원본으로 유지하지 않음 |

문서를 읽는 모든 사용자가 매번 JSON 전체를 검토하는 절차는 아니다. 그러나 최초 연결 확인, 경로 변경, 오류 진단, 관련 diff 검토에 필요한 설정은 사람이 확인할 수 있어야 한다. 자동 갱신은 이 책임을 숨기는 근거가 아니며 정상적인 갱신마다 사용자 재승인을 강제하는 뜻도 아니다.

아래는 AI 없이 개입할 수 있는 보완 조건이다. 이를 위해 별도의 완전한 수동 관리 제품이나 매번 사람 확인을 요구하는 절차를 추가하지 않는다.

- WIKI의 목차, 본문 링크로 원문을 찾아 읽고 수정한다. JSON 도구 실행이나 모델 구독을 문서 열람의 필수 조건으로 두지 않는다.
- 로컬 위치표의 조회, 형식/경로 검사와 허용된 연결 수정은 일반 프로그램으로 수행한다. 정확한 명령 이름과 인터페이스는 후속 명세다.
- 필드 설명, 작은 예시, 원본 경로 규칙과 오류 위치를 제공하고, 필요하면 사람이 텍스트 편집기로 직접 수정한 뒤 같은 검사를 실행할 수 있게 한다. 도구가 사용자의 유효한 직접 편집을 임의로 되돌리지 않는다.
- 기존 내용의 의미, 과거 결정의 근거, 정책 충돌은 AI가 없으면 사람이 판단한다. 기계적 연결 검사가 코드/문서의 의미 정확성을 대신하거나 AI 수준의 자동 역공학을 제공한다고 주장하지 않는다.

파일 길이는 **저장된 전체 크기, AI가 실제로 받는 정보량, 한 번에 수정하는 범위**로 나누어 판단한다. 경로만 담은 루트 목록이 길어져도 도구가 필요한 결과만 반환한다면 그 목록 전체가 모델 문맥을 차지하는 것은 아니다. 이 경우 사람이 자주 읽지 않는 목록을 짧게 보이게 만들려고 계층을 늘리는 이점은 작을 수 있다. 반면 무관한 기능을 매번 함께 읽고 다시 작성하거나 과도한 분할로 여러 파일, 공통 계약을 재탐색하면 비용과 오류 위험이 커질 수 있다.

기능/흐름별 분리는 AI가 관련 근거와 변경 범위를 함께 처리하기 위한 수단이다. 공통, 교차 기능의 연결을 보존하고 상세 본문, 실행 로그, 과거 분석 결과를 위치표에 쌓지 않는다. 들여쓰기, 일관된 필드, 불필요한 순서 변경 방지, 좁은 diff는 자동 검사와 사람의 개입에 함께 도움이 된다. 임의 줄 수만으로 잘라 필수 관계를 누락시키지 않는다. 실제 비용, 정확성의 우위는 아직 측정하지 않았다.

JSON, TOML, Markdown의 기존 비교는 유지한다. JSON 추천은 AI의 일관된 입출력과 일반 도구의 조회, 검사를 중심에 둔 판단이며, JSON이라는 문법 자체가 모든 모델의 이해도나 토큰 효율에서 우월하다는 실측은 없다. 주로 사람이 직접 편집하는 사용성으로 바뀔 때 TOML을 다시 비교한다는 조건이 현재의 AI 중심 전제를 바꾸지는 않는다. 형식만 바꾸어 과도한 정보량, 중복, 역할 혼합이 해결되지는 않는다. 보기용 표나 목차도 같은 위치 목록을 따로 수동 관리하는 두 번째 원본으로 만들지 않는다.

주된 비교는 같은 필수 근거, 원문 보존 조건에서 AI의 조회, 갱신 정확성, 전달/재탐색/재시도를 포함한 총토큰, 변경 범위와 검증 비용이다. 사람의 직접 개입은 필드 안내로 필요한 문서를 찾고 대표 연결 오류를 수정할 수 있는지 보완 확인한다. AI 분석, 관리와 사람의 개입 모두 아직 실험하지 않았다. [Anthropic의 문맥 관리 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 식별자로 자료를 필요할 때 조회하는 방식과 추가 탐색 비용의 절충을 설명한다. 이 일반 원칙은 우리 위치표 분할의 효과나 특정 JSON 형식의 우위를 검증한 근거가 아니다.

## 프로젝트 규모와 위치표 분리

11/09 추가 질문에 대한 보정이다. JSON은 저장 문법이며 한 파일만 써야 한다는 결정이 아니다. 기존 프로젝트, 배포 서비스, 팀 기술 검토라는 명칭만으로 규모를 판정하지 않는다. 운영 부하, 코드/이력 양, 독립적인 기능, 계약, 수정 담당, 위치표 항목 수는 다른 축이다. **분리 지원 여부는 첫 배포의 기능이고, 실제 분리 여부는 적용 프로젝트의 구성**으로 구별한다.

앞선 대화에서는 개발 부담을 줄이려고 단일 파일부터 구현하고 분리를 나중으로 미루는 안을 추천했다. 그러나 이미 복수 도메인과 서비스 간 계약을 가진 기존 프로젝트에 적용하려는 요구를 충분히 반영하지 못했다. 제한적인 분리 지원을 첫 범위에 포함하도록 보정했고 11/09 사용자와 채택했다. 제품 구현은 아직이다.

| 구성 | 장점 | 단점, 비용 |
| --- | --- | --- |
| 단일 파일만 지원하고 분리는 후속 | 최초 로더, 검사가 가장 단순함 | 이미 복잡한 프로젝트도 한 파일을 사용해야 하며 나중에 입력/검사 확장이 필요 |
| 공통 진입점 + 선택적 기능별 분리 | 단일/분할 배치를 같은 조회 절차에서 사용. 기존 경계, 팀 작업에 맞춰 구성 가능 | 처음부터 참조, 중복, 누락, 변경 시 일관성 검사가 필요. 11/09 채택 |
| 처음부터 모든 역할/기능을 별도 파일로 분리 | 담당별 편집 경계를 세밀하게 나눌 수 있음 | 작은 범위도 파일, 참조가 늘고 한 기능의 관련 변경이 흩어질 수 있음 |

채택한 방향은 **공통 진입점과 필요한 기능/흐름의 분리를 처음부터 지원**하는 것이다. 실제 항목이 작고 함께 바뀌면 단일 파일로 두고, 독립적인 경계, 담당, 변경이 있으면 도입 시점부터 나눈다. 역할은 각 항목의 분류로 유지하며 역할마다 별도 파일을 강제하지 않는다. 파일 수, 줄 수의 임의 기준만으로 자동 분할하지 않는다.

```text
프로젝트 WIKI/
├── map.json                # 공통 연결과 분할 목록
├── maps/
│   ├── product.json        # 상품 기능의 여러 역할
│   ├── search.json         # 검색 기능의 여러 역할
│   └── transaction.json    # 여러 서비스에 걸친 흐름
└── 기존 문서들
```

이름과 경계는 설명용이며 실제 프로젝트 분석 결과가 아니다. 공통 원본은 한 곳에 두고 각 기능에서 참조한다. 상위 목록은 분할 파일의 내용 전체를 복제하지 않는다. 첫 범위는 명시한 한 단계의 파일 참조이며 임의 재귀 include, 설정 상속/덮어쓰기, 원격 파일 자동 수집을 추가하지 않는다. 작으면 하위 파일이나 빈 폴더를 만들지 않는다. [입출력 초안](../../design/knowledge/map.md)에서 구체 필드와 경로, 조회, 갱신을 좁힌다.

분리 판단은 실제 역할/범위 연결 수와 구조, 공통 계약의 반복, 함께 변경되는 항목, 담당 간 충돌을 확인해 제시한다. 문서/코드가 많더라도 주요 진입점만 담은 위치표는 작을 수 있다. 반대로 코드가 적어도 여러 서비스의 계약, 결정 흐름을 복원하면 관리 경계가 필요할 수 있다. 설치 시 분석한 구성 후보를 확인하고 기존 파일의 자동 이동, 강제 분할은 하지 않는다.

첫 지원 검증에는 단일/분할에서 같은 요청의 필수 원본에 도달하는지, 분할 파일 누락, 중복 선언, 이름 변경, 부분 갱신을 발견하고 기존 자료를 보존하는지를 포함한다. 분리하면 AI가 덜 읽는다는 효과는 자동으로 성립하지 않는다. 공통/의존 관계를 빠뜨리지 않는 선택과 실제 전달량을 따로 측정한다.

[MkDocs](https://www.mkdocs.org/user-guide/writing-your-docs/#configure-pages-and-navigation)는 중앙 설정에서 여러 문서의 계층적 탐색을 정의하는 사례다. [Backstage의 Location](https://backstage.io/docs/features/software-catalog/descriptor-format/#kind-location)은 다른 카탈로그 파일들을 참조하는 사례다. [arc42](https://docs.arc42.org/section-5/)는 구성 요소, 의존 관계를 계층적으로 설명한다. 이 자료들은 가능한 조직 방식을 보여주며, 특정 파일 수의 분리 기준이나 우리 방식의 성능 우위를 입증하지 않는다. 해당 도구 전체를 채택하는 결정도 아니다.

## 분할 파일을 찾는 방식

11/09 비교 후 **A의 명시적 목록과 등록 갱신 자동화를 채택**했다. B 폴더 자동 탐색과 C 계층 목록은 채택하지 않았다. 앞 절은 **위치표를 어떤 기능/흐름으로 나눌지**, 여기서는 **나눈 파일 중 무엇을 사용할지 어떻게 찾을지**를 다룬다. 하위 위치표에 들어갈 정보량을 줄이는 세 방식이 아니다. 상세 요구, 결정은 Markdown, 역할, 범위, 위치는 위치표에 남기는 책임은 같다.

아래 JSON은 파일 발견 방식만 비교한 부분 예시다. 공통 문서 연결인 `entries`는 생략했고 필드, 이름은 최종 명세가 아니다. `maps`의 참조는 해당 목록 파일 기준, 각 문서 항목의 `path`는 등록한 `root` 기준으로 해석하는 예시다.

**A. 사용할 파일을 명시한 목록**

루트 `map.json`에 분할 파일의 위치만 나열한다. 하위 파일의 역할, 문서 경로, 본문을 복사하지 않는다.

```json
{
  "maps": [
    "maps/product.json",
    "maps/search.json",
    "maps/transaction.json"
  ]
}
```

상품 설명이 늘면 상품 문서나 `product.json`만 바뀐다. 독립된 결제 위치표를 추가할 때는 `payment.json`과 목록을 함께 갱신한다. 파일이 존재한다는 이유만으로 자동 포함하지 않는다. 공통/하위 위치표를 일반 코드가 읽어 조회하고, 필요한 결과만 모델에 전달할 수 있다. 목록에 경로만 있으므로 하위 역할/범위를 확인하려면 하위 위치표도 읽어야 한다.

**B. 정한 폴더에서 파일을 자동 탐색**

```json
{
  "map_dir": "maps"
}
```

이 예시는 지정 폴더 바로 아래의 `.json` 위치표를 모두 읽는다. `payment.json`을 넣으면 상위 설정 수정 없이 포함된다. 하위 폴더까지 탐색할지는 별도 규칙이며 이 예시는 재귀 탐색을 하지 않는다. 같은 폴더의 초안 JSON도 포함 대상이 되므로 완료 전 자료는 바깥에 두는 등의 운영 규칙이 필요하다. 등록 파일이 사라졌을 때 명시적 목록이 없으므로 의도한 삭제와 누락을 구별할 다른 기준도 필요하다.

**C. 목록을 여러 단계로 분리**

```text
map.json
└── maps/
    ├── catalog/
    │   ├── map.json
    │   ├── product.json
    │   └── search.json
    └── trade/
        ├── map.json
        └── transaction.json
```

루트 목록은 `maps/catalog/map.json`과 `maps/trade/map.json`만 연결한다. `maps/catalog/map.json`은 자기 위치 기준으로 다음을 연결한다.

```json
{
  "maps": ["product.json", "search.json"]
}
```

상품군에 위치표를 추가하면 상품군 목록만 바뀐다. 목록의 총량이 사라지는 것은 아니며 관리 책임을 여러 곳으로 나눈다. 여러 단계의 참조 누락, 중복, 순환과 경로 이동을 검사해야 한다. 서비스 간 거래처럼 여러 영역을 가로지르는 관계도 디렉토리 계층만으로 해결되지 않는다.

| 방식 | 유지보수 이점 | 비용, 실패 가능성 |
| --- | --- | --- |
| A 명시적 목록 | 사용 대상과 추가/제외 diff가 분명하고 등록 파일 유실을 발견하기 쉬움 | 파일 추가, 이동 때 목록도 변경. 등록 누락, 중앙 목록의 팀 충돌 가능 |
| B 폴더 탐색 | 상위 목록 관리와 그 편집 충돌을 줄임 | 우연한 포함, 조용한 제외 방지, 초안 배치, 탐색 깊이, 확장자 규칙이 필요 |
| C 계층 목록 | 넓은 범위의 담당별 목록 관리 가능 | 참조 단계와 진단 비용 증가. 파일 내용을 읽는 총량이 자동으로 줄지는 않음 |

채택한 구성은 **A의 명시적 목록과 도구의 등록 갱신을 결합**한다. AI가 기존 요구에 맞는 기능 경계, 연결 후보를 판단하고 도구로 허용된 범위의 파일 추가/이동과 목록 변경을 함께 준비, 검사한다. 사람의 개입 가능성은 유지하며 일반적인 승인 범위의 갱신마다 재확인하지 않는다. 미확정 의미나 충돌은 기존 협의 기준을 따른다. 이 자동화는 ‘폴더에 있는 파일을 모두 사용’하는 B와 다르다.

등록 누락 후보는 검사에서 알리되 자동 채택하지 않고, 필수로 정한 연결의 누락, 깨진 참조, 중복 충돌을 통과시키지 않는다. 목록과 하위 파일은 함께 검증할 변경 단위로 다룬다. 파일 두 개의 쓰기가 자동으로 원자적이라는 뜻은 아니며, 중간 실패, 부분 반영을 발견하고 복구하기 전 완료 처리하지 않는 상세 계약이 필요하다. 의미상 필요한 문서가 전부 존재하는지는 별도 내용 검토다.

이 추천은 현재의 원문 보존, 범위 제한, 누락 발견, 작은 구현 범위에 대한 판단이다. 명시적 목록도 길어질 수 있고 실제 충돌 빈도, 탐색 성능은 미측정이다. 폴더 탐색이 본질적으로 열등하다는 뜻은 아니며, 목록 관리가 실제 부담이면 B를 재평가한다. 처음부터 세 가지를 모두 구현하지 않는다. 어떤 방식을 쓰든 파일 탐색 자체는 일반 코드로 처리할 수 있고, 토큰 차이는 AI에 전달한 정보, 추가 탐색, 재작업을 측정해야 한다.

[Backstage Location](https://backstage.io/docs/features/software-catalog/descriptor-format/#kind-location)은 명시한 대상과 상대 경로 연결의 사례다. [Terraform 파일 구성](https://developer.hashicorp.com/terraform/language/files#directories-and-modules)은 정한 디렉토리의 설정 파일을 함께 읽고 하위 폴더를 자동 포함하지 않는 사례다. 두 사례는 가능한 발견 방식을 보여주며 이 JSON 예시나 추천을 그대로 규정하지 않는다.
