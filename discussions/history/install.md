# 설치 방식의 비교와 시험 이력

> 과거 검토 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

2026-11-11 문서 정리에서 이전 비교와 실험 해석을 옮겼다. 아래 내용은 당시 판단의 기록이며 현재 설치 지시가 아니다. 현재 배치는 [설치 설계](../../design/runtime/install.md), 갱신, 복원은 [갱신 설계](../../design/runtime/update.md), 결정 상태는 ADR 0010, 0011, 0019, 0020을 따른다. 원시 실험 파일은 변경하지 않았다.

## 실행 구성의 배치 재검토

11/09 외부 공통 실행본의 상시 사용을 부분 채택했다가 11/10 사용자 요청으로 재검토했다. **11/11에는 프로젝트 내 설치로 변경했다.** 사용자가 skill뿐 아니라 script, hook, 설정도 자유롭게 수정하고, 첫 배포의 사용 흐름을 단순하게 유지해야 한다는 요구가 결정 근거다. 이전 추천, 시험은 이력으로 보존하며 현재 설치 지시와 혼용하지 않는다.

| 비교한 배치 | 이득 | 비용, 판단 |
| --- | --- | --- |
| 실행 구성을 프로젝트에 설치 — 채택 | 같은 프로젝트 안에서 읽기, 수정, 검토, 공유. 별도 하네스 실행 경로 연결 감소 | 프로젝트별 파일과 사용자 편집의 갱신 검사가 필요 |
| 외부 공통 실행본 + 프로젝트 입력/일부 파일 — 이전 안 | 수정하지 않는 공통 파일의 중복 감소 | 같은 버전 준비, 경로/권한, 공유 파일 수정, 사본 전환, 중복 연결 관리가 필요 |
| 자산별로 외부/내부를 선택 — 첫 범위 제외 | 변경하지 않는 파일만 공유 가능 | 조합과 진단, 업데이트 경우가 늘어 현재 기한에 불리 |

공통 코드와 프로젝트 값을 논리적으로 나누는 원칙은 유지한다. 설치된 함수가 프로젝트 설정을 읽도록 만들 수 있으므로 물리적 외부 배치가 필수는 아니다. 공식 SOT의 독립성도 소비 프로젝트의 설치본 수정 금지를 뜻하지 않는다. 파일 위치, Git 추적, 외부 공개는 각각 판단한다.

[GitHub Spec Kit](https://github.github.io/spec-kit/installation.html)의 프로젝트 스크립트 설치는 채택한 배치의 공개 사례다. [uv tools](https://docs.astral.sh/uv/concepts/tools/)처럼 외부 도구도 유효한 패턴이므로 업계 전체의 우열로 해석하지 않는다. [Copier](https://copier.readthedocs.io/en/stable/updating/)는 프로젝트 생성본과 사용자 변경을 갱신할 수 있지만 충돌 처리도 필요함을 보여준다. 이 도구의 채택이나 공수, 토큰 우위의 실측 결과는 아니다.

동작 흐름과 소유는 아래 현재 표에 통합했다. 기존 14개 검사, Codex 부분 관측은 당시 환경의 근거이며 새 배치의 실사용 통과로 옮겨 쓰지 않는다. 새 검증은 임시 배포 사본 제거 뒤 일반 CLI 사용, 팀 clone, script 직접 수정, 연속 갱신, 충돌/복원, 외부 WIKI 보존을 포함한다.

## 첫 배포 수단 비교

이 절은 11/09~10의 수단 비교 이력이다. 당시 B는 외부 고정 실행 도구, C는 우리가 만든 하네스/연결부를 Codex plugin으로 포장하는 안이었다. 다른 제작자의 하네스를 가져오는 제안이 아니었다. 11/11 실행 구성의 프로젝트 내 설치를 채택한 뒤 B의 관리 도구 책임을 다시 정리했으며 현재 후보는 [B안의 구체 설치 후보 — 「배포 도구」](../../design/runtime/install.md)에 둔다.

공식 문서는 재사용 skill의 plugin 배포, 로컬 marketplace 제작/시험, Git 출처와 프로젝트별 활성화를 설명한다. 공용 디렉터리 등록 없이 로컬/허용된 private Git 출처를 시험할 수 있으나, private Git 인증과 우리 설치, 보존 조건의 충족은 별도 검증이다. 초기 비공개 사용과 실제 공개 시점도 별개다. [Skills](https://learn.chatgpt.com/docs/build-skills), [Plugin 제작, 배포](https://developers.openai.com/plugins/build/plugins).

C의 0.167.0 시험에서는 같은 plugin ID, 공유 설치 상태에서 프로젝트별 적용 버전 유지에 실패했다. 출처의 commit을 고정하는 것과 설치 상태의 분리는 같지 않았다. 프로젝트 비활성화와 설치본 제거도 구별해야 한다. 당시 B의 명시적 버전/연결 책임을 추천했지만 모든 plugin 형식, 클라이언트가 불가능하다는 결론은 아니다. 상세 관측, 최초 manifest 누락, 해석 보정은 [plugin 호환성 시험](install.md#plugin%20%ED%98%B8%ED%99%98%EC%84%B1%20%EC%8B%9C%ED%97%98)에 보존한다.

plugin은 배포, 발견 수단이며 분석, 보존, 상태 로직을 대신하지 않는다. B/C 모두 [AI 분석 실행 계약](../../decisions/knowledge/0018-reconstruction.md)과 [도구별 연결 경계 — 「확장을 위한 경계」](../../design/architecture.md)를 충족해야 한다. 신뢰 확인을 우회하거나 자체 서버, MCP, 패키지 관리자를 필수로 추가하지 않는다. 어느 수단도 실제 모델 품질, 토큰 효과를 설치 성공만으로 입증하지 못한다.

## B안의 최소 검증

사용자가 11/10 **작은 검증부터 진행**하도록 수용했다. 1~3은 `/tmp`의 두 예제 프로젝트, 실제 Git commit과 Python 처리 코드로 한 번 수행했고 14개 검사가 기대 결과를 통과했다. 보존한 실행에는 실제 timeout 오류가 없으며 설정 병합 시험의 시간 값은 예제다. 1~3 전체를 일반 사용자 설치 환경에서 다시 수행한 것은 아니다. 4는 Codex 0.167.0의 app-server 연결로 발견, 신뢰, 시작/재개 이벤트를 관측했다. [Codex 연결 시험 결과](install.md#Codex%20%EC%97%B0%EA%B2%B0%20%EC%8B%9C%ED%97%98%20%EA%B2%B0%EA%B3%BC)의 격리 환경 제한은 남는다. 제품 전체나 최종 설치 수단의 실사용 검증 완료를 뜻하지 않는다.

| 순서 | 시험 입력과 조작 | 통과 조건 |
| --- | --- | --- |
| 1. 선택과 재설치 | 서로 다른 이름, 명령, WIKI 위치를 가진 두 예제 프로젝트에 같은 시험용 배포본 연결, 한쪽에만 다음 revision 적용, 같은 설치 재실행 | 각 프로젝트가 기록한 배포본을 실제 호출. 다른 쪽 불변, 중복 연결 없음. 선택한 배포본 부재는 실패로 드러남 |
| 2. 편집 보존 | 프로젝트 연결 파일에 사용자 편집 후 공식 후보를 두 번 연속 변경. 겹치는 수정, 기준본 누락, 검사에 실패하는 텍스트 병합 후보 포함 | 비충돌 변경은 후보에서 함께 보존. 충돌/검사 실패는 원문과 적용 버전을 바꾸지 않음. 다음 기준본에 사용자 편집을 공식 내용으로 흡수하지 않음 |
| 3. 실패와 정리 | 계획 후 추가 편집, 적용 중간 실패, 실패 후 사용자 편집, 한 프로젝트 연결 해제 | 오래된 계획 적용 차단. 이번 작업이 쓴 것만 복원하고 후속 편집 보존. 다른 프로젝트, 보호 WIKI, 사용 중인 배포본 불변 |
| 4. Codex 연결 | 앞의 보존 경계 통과 후 격리된 Codex 상태에서 실제 skill 발견, hook 신뢰/호출, 하위 경로 시작, 재접속 확인 | 선택 버전, 단일 활성 연결, 올바른 프로젝트 입력 확인. 직접 스크립트 호출을 native hook 성공으로 대신하지 않음 |

실행 범위는 1~3의 **로컬, 모델 없는 시험**이다. [원시 근거](../../evidence/experiments/runtime/2026-11-10_17-07-48-external-install.md)에 실행 전 조건, 소스, Git 입력 bundle, 전후 내용, 실패/복원 결과를 보존했다. 두 번의 갱신에서 사용자 명령 옵션과 공식 기준본을 분리했고, 한쪽 변경/제거가 다른 프로젝트의 호출 버전, 파일을 바꾸지 않음을 확인했다. 시험 revision은 출시 태그가 아니며 상세 WIKI 품질, AI 실행, 토큰 효과, 원격 배포, 전체 복구를 PASS에 포함하지 않는다.

의도한 반례도 재현했다. Git의 텍스트 병합은 성공했지만 사용자 제한 시간과 공식 시도 횟수가 결합해 허용 시간을 넘는 후보는 별도 검사로 차단했다. 첫/두 번째 파일 반영 뒤 종료한 프로세스는 새 프로세스에서 복원했으나, 실패 후 추가 사용자 편집이 있으면 그 파일을 유지하고 실행/복구를 보류했다. **자동 병합 성공과 의미 검증, 자동 복원 가능 여부는 각각 판단해야 한다.** 작은 JSON 계약의 검사이며 모든 WIKI 의미, 동시 편집, 전원 장애를 검증한 것은 아니다.

4의 시험은 `.agents/skills`의 링크와 `.codex/hooks.json`을 사용했다. 기기 경로를 팀 Git에 넣거나 기존 연결을 덮어쓰도록 채택한 것은 아니다. 모델 추론 없는 발견/이벤트 검증과 실제 AI의 기능 사용은 분리한다. 다음은 이 결과와 원문 보존 조건을 설치, 첫 배포 명세에 반영하는 단위다. 중첩 sandbox 실패를 모든 환경의 지원 완료로 덮지 않는다.

## 갱신 방식과 배포 수단

11/09 사용자 수정 보존 질문에서 정리한 비교다. 11/11에는 실행 파일도 프로젝트에 설치하므로 **공식 고정 배포본으로 새 후보를 만들고, 설치된 파일/항목의 사용자 편집을 3방향으로 대조하는 흐름**에 연결한다. 공통 배포본 자체의 교체에 병합을 강제하거나, 모든 사용자 파일을 모듈 소유로 취급하지 않는다. 기준본, 충돌, 후속 갱신의 상세는 [변경분과 충돌의 판정](../../design/runtime/update.md)이 소유한다. 텍스트 병합 성공만으로 의미, 연결의 정상 동작을 보장하지 않는다.

| 해결할 문제 | 담당 수단 | 다른 수단으로 대체되지 않는 부분 |
| --- | --- | --- |
| 사용자 편집을 유지하며 공식 변경 반영 | 이전 기준본, 현재 파일, 새 후보의 3방향 비교와 검증 | plugin 설치만으로 프로젝트 파일의 보존, 병합이 구현되지 않음 |
| 프로젝트마다 선택한 공식 버전 사용 | 배포본 보관, 버전 선택, 실제 연결 | 3방향 비교로 공유 plugin 설치 상태를 분리할 수 없음 |
| Codex가 skill/hook을 발견, 실행 | 지원 경로, 설정, 신뢰 절차와 실제 호출 검증 | 파일 병합이나 패키지 설치 성공만으로 실행을 통과 처리할 수 없음 |

따라서 3방향 비교를 도입해도 현재 B 추천을 C 우선으로 바꾸지 않는다. C와 프로젝트 파일 갱신 도구를 함께 사용하는 구성도 가능하지만 버전 유지, 대상 CLI 연결 문제는 별도로 풀어야 한다. 프로젝트별 Codex 상태/인증 관리, 다른 plugin ID, 공통 plugin에서 별도 버전 도구를 호출하는 연결부를 추가하면 관리, 검증 범위가 늘어난다. 이 대안들은 미검증이며 첫 배포에 모두 구현하지 않는다.

B도 설치, 등록, 갱신, 복원 책임이 남으므로 무조건 구현량이 적거나 더 빠르다고 단정하지 않는다. 현재 요구, 기한에서는 버전과 연결을 명시적으로 관리하는 경로가 더 통제 가능하다는 판단이다. C가 지원 대상에서 같은 버전 유지, 실행, 보존 조건을 더 적은 관리 비용으로 충족하면 재검토할 수 있다. 이번 판단은 추천 보강이며 구체 패키지 수단, 자동 적용 범위, 제품 구현의 채택은 아니다.

## plugin 호환성 시험

대상은 현재 WSL의 Codex CLI 0.167.0이다. 실제 프로젝트와 개인 설정을 보존하고, Linux 임시 폴더의 작은 패키지, 예제 프로젝트, 별도 Codex 상태로 시작했다. `CODEX_HOME`은 자식 명령에만 적용했고 현재 셸, 세션의 설정은 바꾸지 않았다. 이 환경 변수는 설정, 인증, 세션 등의 상태 위치를 지정하는 공식 수단이다. [환경 변수 안내](https://learn.chatgpt.com/docs/config-file/environment-variables).

11/09의 1차 결과는 다음과 같다. [원시 기록과 한계](../../evidence/experiments/runtime/2026-11-09_14-30-52-plugin-install.md)에 최초 실패와 재개 입력을 모두 보존했다.

| 확인한 것 | 관측 결과 | 설계에 반영할 점 |
| --- | --- | --- |
| 로컬 목록 등록, 조회 | 성공 | 개인용 설치 경로의 일부를 실제 CLI에서 확인 |
| 루트 `plugin.json`만 있는 패키지 | 파일이 있지만 `missing plugin.json`으로 설치 실패 | 아래 입력 차이 때문에 이 형식 전체의 미지원으로 일반화하지 않음 |
| `.codex-plugin/plugin.json` 호환 manifest 추가 | 같은 설치 단계 성공, 설치본 내용 대조 | 이 CLI에서는 두 manifest를 둔 시험 구성이 동작. 최종 패키지 형식, 생성 기준은 아직 미확정 |
| 같은 버전 재설치 | 설치본 내용 동일 | 이 예제의 재실행 확인이며 모든 사용자 편집 보존 시험은 아님 |
| 같은 plugin ID를 0.1.0 → 0.2.0으로 갱신 | 새 버전 설치, 이전 캐시 사라짐 | 캐시를 이전 배포본의 보관소로 가정하지 않음 |
| 보존한 0.1.0 자료로 복귀 | 재설치, 내용 대조 성공 | 명시적 이전 자료 재설치이며 자동 rollback, 여러 프로젝트의 버전 유지 증거는 아님 |
| 없는 이름, 제거, 환경 보존 | 없는 이름은 오류, 시험 plugin/cache와 목록 등록 제거 성공. 보호한 설정, AGENTS 해시 동일 | 실패를 빈 성공으로 처리하지 않았고 시험 범위의 정리 확인 |

입력 재검토: 최초 루트 manifest는 이름, 버전, 설명만 포함했고 [공식 portable 예제](https://developers.openai.com/plugins/build/plugins)의 `$schema` 선언은 없었다. 따라서 그 입력의 실패와 호환 manifest 추가 후 성공만 확인한 것이다. `$schema`를 추가한 통제 시험은 하지 않았으므로 루트 형식 전체의 미지원이나 실패 원인을 확정하지 않는다. 이후 버전 유지 시험은 설치에 성공한 호환 형식을 사용했다.

모델 호출, 계정 로그인, 원격 저장소 생성/접근은 하지 않았다. 임시 상태에서 helper 실행 파일 생성을 거부한다는 경고도 출력됐으며 설치 명령은 동작했다. 이 경고를 실제 skill 실행이나 shell 도구 호환성의 성공/실패로 확대하지 않는다. 현재 모델, 구독 비용 비교와 제품 WIKI 복원 결과도 아니다.

2차 시험은 같은 plugin ID, 별도 고정 로컬 출처, 공유 Codex 상태를 쓰는 두 예제 프로젝트다. 아래 A/B는 각각 시험 프로젝트 `alpha`/`beta`이며 설치 방식의 대안 이름이 아니다. [원시 기록](../../evidence/experiments/runtime/2026-11-09_14-46-58-plugin-versions.md)에 입력, 명령, 기준 실패, 발견 결과를 보존했다.

| 작업 | 우리 설계의 기대 조건 | 실제 관측 |
| --- | --- | --- |
| A 0.1.0 설치 뒤 B 0.2.0 설치 | A 0.1.0, B 0.2.0 | 양쪽 목록과 남은 캐시가 0.2.0 |
| A만 0.3.0 갱신, 새 CLI 프로세스 조회 | A 0.3.0, B 0.2.0 | 양쪽이 0.3.0 |
| A에서 같은 plugin 제거 | B 0.2.0 유지 | B의 설치 목록, 캐시도 비어 있음. 프로젝트 사용 중지와는 다른 명령 |
| A 0.3.0 → B 0.2.0 재설치 후 native `skills/list` | A의 skill은 0.3.0, B는 0.2.0 | A → B → A 모두 0.2.0 경로와 본문을 발견 |

설치/조회 명령 14개는 종료 코드 0이지만 **우리 설계의 프로젝트별 버전 유지 기준은 FAIL**이다. native 발견도 프로젝트에서 선택한 출처의 버전과 달랐으며 실제 모델의 skill 사용이나 hook 실행은 시험하지 않았다. 보호 대상 파일, 배포 출처는 보존했고 시험 plugin/cache 제거, 별도 app-server 종료를 확인했다. 다른 CLI 버전, ID/상태 분리, 원격 출처까지 같은 실패라고 단정하지 않는다.

11/09 재검토에서 실행 코드는 각 프로젝트를 `cwd`로 지정하고 두 프로젝트를 신뢰 대상으로 설정했으며, 출처 조회도 서로 다른 고정 위치를 반환했다. native 발견은 해당 프로젝트 경로와 `forceReload`를 지정했다. 주된 관측을 잘못된 실행 위치나 동일 출처 지정 탓으로 돌릴 근거는 찾지 못했다. 다만 프로젝트별 marketplace 출처 설정을 프로젝트별 설치 버전 격리 보장으로 기대한 것은 우리 요구였으며, 공식 보장 여부와 구분해야 한다.

제거 결과의 해석은 보정한다. 로컬 `codex plugin remove --help`는 설치본과 캐시 제거를 설명하고, [공식 문서](https://developers.openai.com/plugins/build/plugins)는 프로젝트 설정의 `enabled = false`로 설치를 유지한 채 사용을 끄도록 안내한다. 프로젝트 폴더에서 제거 명령을 실행했다고 해당 프로젝트만 해제되는 것은 아니다. 표의 제거 결과는 관측으로 보존하되 Codex의 문서화된 동작 위반이나 버그의 증거로 쓰지 않는다. 이 보정과 별개로 한쪽 갱신이 다른 쪽의 발견 버전을 바꾼 결과는 남는다.

hook 지원도 설치 성공과 구분한다. 공식 plugin 제작 문서는 수동 설치한 Codex desktop plugin의 lifecycle hook을 명시하고, [일반 hooks 안내](https://learn.chatgpt.com/docs/hooks)는 활성 plugin의 hook과 CLI 확인 절차를 설명한다. 이 설명들만으로 현재 WSL CLI의 plugin hook 실행까지 확인됐다고 판단하지 않는다. CLI에서 불가능하다는 뜻도 아니며, 대상 버전, 클라이언트에서 실제 호출을 검증해야 한다.

이 결과로 당시 C 우선 추천을 B 비교로 바꿨다. 이후 외부 실행본의 작은 연결 관측은 아래에 보존한다. 11/11 채택한 프로젝트 내 배치에서도 두 프로젝트의 독립성, skill/hook, 터미널 진입, 기존 AGENTS/설정/WIKI 보존을 실제 설치 결과로 확인해야 한다. 모델 호출이 필요한 범위, 계정, 예산과 hook 신뢰는 실행 전에 확인한다. private Git 인증, 새 환경 재현은 실제 배포 출처 준비 뒤 검증한다. 구체 다음 순서와 합의 상태는 [진행표](../../development/roadmap.md)를 따른다.

각 묶음의 입력, 명령, 종료 코드, 설치본 해시, 미검증 범위를 남긴다. 예상 밖 실패가 발생하면 해당 지점에서 멈추고 원인을 확인하며, 영향을 받지 않은 앞선 결과는 재사용한다. 이 시험의 통과를 제품 설치와 갱신, 문서 보존 계약 전체의 통과로 보지 않는다.

## 실무 사례와 보관 경계

11/09 공식 기업 사례와 도구 문서를 대조했다. 사용자는 프로젝트에 실행 파일까지 설치하는 방식과 외부 공통 도구를 계속 사용하는 방식 중 실무에서 무엇을 많이 쓰는지 질문했다. **생성한 프로젝트 자산과 공통 실행 도구의 역할에 따라 두 패턴이 모두 확인된다.** 아래는 공개된 사례이지 기업 전체의 채택률 조사가 아니다. 특정 방식이 항상 대세이거나 더 빠르다고 단정하지 않는다.

| 실제 공개 사례 | 확인된 운용 | 이 설계에 주는 근거 |
| --- | --- | --- |
| [GitHub Spec Kit 설치 안내](https://github.com/github/spec-kit/blob/main/docs/installation.md) | CLI를 도구로 설치하거나 임시 실행해 프로젝트를 초기화하며, 선택한 자동화 스크립트를 프로젝트의 `.specify/scripts/`에 설치 | 설치 도구의 외부 보관과 설치 결과의 프로젝트 소유가 함께 가능함. AI workflow를 전부 외부 실행기로 두는 방식만 있는 것은 아님 |

도구의 **지원 기능**도 실제 기업 채택과 구분한다. [OpenAI plugin 문서](https://developers.openai.com/plugins/build/plugins)는 재사용 기능의 패키지와 프로젝트별 발견, 활성화 설정을 구분한다. 프로젝트에서 사용하는 plugin이라고 구현 전체가 프로젝트 Git에 있어야 하는 것은 아니다. 설치, 활성화, hook 신뢰, 지원 클라이언트가 서로 다른 조건이므로 설정 파일 존재만으로 준비 완료를 판단하지 않는다.

이 사례들을 근거로 11/09에는 외부 공통 실행본을 추천했지만, 사용자가 직접 수정할 범위와 연결 비용을 재검토해 11/11에는 프로젝트 내 설치를 채택했다. 기업 사례의 존재만으로 이 제품의 배치가 결정되지는 않는다. 이전 판단은 ADR 0010, 변경 결정은 ADR 0019에 보존하며 현재 구성은 아래 표를 따른다. 어느 배치가 더 빠르거나 토큰을 덜 쓴다는 실측은 없다.

## 외부 설치의 자동 연결

이 제목은 이전 외부 배치 검토의 참조를 위해 유지한다. 당시 외부 파일도 지원 발견 경로에 등록하면 사용할 수 있다는 가능성을 조사했다. **현재 설치는 프로젝트 파일을 지원 진입점에 연결하는 방식**이며 [설치부터 평소 사용까지](../../design/runtime/install.md)가 실행 흐름을 소유한다. 아래 공식 기능과 관측을 외부 실행본 유지 조건으로 읽지 않는다.

[공식 skill 문서](https://learn.chatgpt.com/docs/build-skills)는 저장소, 사용자, 관리자, 시스템 위치, skill 폴더의 심볼릭 링크와 plugin 배포를 지원한다. 외부 skill을 연결할 수 있다는 근거이며 모든 사용자 전역 skill을 모든 프로젝트에 활성화하자는 뜻은 아니다. [프로젝트 설정](https://learn.chatgpt.com/docs/config-file/config-advanced)은 신뢰된 프로젝트의 설정을 읽고, [hook 문서](https://learn.chatgpt.com/docs/hooks)는 활성화한 plugin과 사용자/프로젝트 hook의 발견, 신뢰 확인을 구분한다. 같은 hook을 여러 출처에 등록해 중복 실행하지 않는다.

발견, 사용자 선택/조건부 사용, 실제 명령 실행, 파일 읽기와 쓰기 권한은 별도로 확인한다. hook 정의나 포함 스크립트가 바뀌면 새 신뢰 확인이 필요할 수 있다. `--add-dir` 같은 쓰기 범위 설정만으로 지침/skill을 발견하는 것은 아니며 공통 패키지 읽기, 실행과 외부 WIKI 쓰기 권한도 다르다. 설치와 신뢰 확인을 마친 지원 조합에서 매번 경로를 입력하지 않는 사용성을 목표로 한다. 아래 작은 연결 관측을 전체 작업, 권한, 토큰의 동등성으로 해석하지 않는다.

## Codex 연결 시험 결과

11/10 [원시 근거](../../evidence/experiments/runtime/2026-11-10_17-41-18-native-connection.md)는 두 Linux 임시 프로젝트와 하나의 별도 Codex 상태를 사용한 부분 연결 시험이다. 자동 관측은 `codex app-server --stdio`와 시험용 클라이언트로 수행했고, TUI는 시험 hook의 신뢰 검토에 사용했다. 계정 인증을 복사하지 않았고 외부 AI 대신 연결 불가능한 loopback 주소에서 요청을 중단했다. 네 번의 native hook 완료와 17개 결과 대조는 Codex 내부 이벤트의 관측이며 일반 `codex`/`codex resume` 사용 전체, 실제 AI 응답, skill 작업 품질, 토큰 절감의 검증이 아니다.

| 확인 대상 | 관측과 설계 반영 |
| --- | --- |
| 외부 skill 발견 | 루트, 하위 폴더에서 각자 고른 commit의 skill 하나를 발견했다. A만 갱신해도 B의 경로는 유지됐다. |
| 프로젝트와 hook 신뢰 | 프로젝트 신뢰 전에는 hook이 발견되지 않았다. 프로젝트 신뢰 후에도 개별 검토가 필요했고, Codex 화면에서 생성한 시험 hook만 검토, 신뢰했다. 설치가 신뢰를 대신하지 않는다. |
| app-server 시작, 재개 | 목록 조회, 세션 생성만으로는 hook이 실행되지 않았다. 요청을 시작한 뒤 native 이벤트와 기록을 대조했고, 새 프로세스의 같은 시험 세션 재개에서도 프로젝트, WIKI, 배포본이 맞았다. |
| 갱신과 신뢰 | A의 호출 경로가 새 commit으로 바뀌자 `modified`가 됐고 재검토 전에는 실행되지 않았다. B의 신뢰는 유지됐으며 A를 다시 신뢰한 뒤 새 배포본이 실행됐다. |
| 중복과 해제 | 같은 이름의 skill, hook을 추가하자 각각 두 개가 발견됐다. 설치기는 기존 연결을 대조해야 한다. A 연결만 제거하면 A는 0개, B는 1개로 유지됐다. |

검증 환경의 제한도 발견했다. **10초는 시험 준비 코드가 hook에 지정한 `timeout: 10`이며 Codex 진입, 세션 수명이나 제품의 확정 기본값이 아니다.** 이 에이전트의 도구 sandbox 안에서 별도 Codex를 띄우자 hook은 기록을 남겼지만 종료한 자식 프로세스가 zombie로 관측됐고 Codex는 해당 제한 초과를 보고했다. 같은 시험을 승인받아 바깥에서 실행하니 native 완료가 기록됐다. 정확한 내부 원인은 미확정이며 시간만 늘려 해결됐다고 보거나 일반 사용자 환경의 장애로 확대하지 않는다. 시험 클라이언트의 응답 대기 제한, 의도한 offline 재연결도 hook 제한과 구분한다. [E-021 — 「E-021 — native hook의 완료와 격리 환경 차이」](../../evidence/issues.md)에 실패와 비교를 보존했다.

실사용 판정은 배포 후보를 README대로 설치한 뒤 **일반 Windows PowerShell → Windows 대상 프로젝트 → Windows `codex` 진입/재개 → 실제 skill/hook, WIKI, 상태 확인**으로 수행한다. 이 에이전트의 도구 안에서 Codex를 다시 띄우는 실행은 별도 조건이다. 모듈이 의도적으로 자식 CLI를 실행하는 기능은 그 실제 실행 경로로 검증한다. 시험용 app-server, offline provider, `--no-daemon`을 사용자에게 필요한 설치 절차로 복사하지 않으며, 이번 부분 시험으로 일반 진입의 검증을 대신하지 않는다.

이 결과는 당시 외부 공통 배포본의 부분 연결 관측이다. 11/11 채택한 프로젝트 내 설치의 성공이나 외부 배치의 우월성을 증명하지 않는다. 최종 설치 인터페이스, 기기 경로의 저장/공유, 실제 AI의 skill 실행, compact, Windows 권한, 원격 소비자 설치는 아직이다. 시험의 절대경로, 파일 이름, 수동 fixture 준비를 제품 계약이나 설치 자동화 완료로 복사하지 않는다.

## 최초 기록의 행별 수신안

11/16~17 초기 초안은 외부 상태 DB의 필요한 행을 대상 DB에 다시 등록하고 DB 식별/revision을 대상에서 새로 시작했다. 기존 대상의 무관한 기록을 보존할 수 있지만 과거 실행 순서와 불변/완료 관계를 수신에도 재구성해야 했다. [6개 행 순서 검사](../../evidence/experiments/recovery/2026-11-17_07-41-47-handoff-order.md)와 [7개 유지 관리 검사](../../evidence/experiments/recovery/2026-11-17_10-01-07-maintenance-handoff.md)는 당시 부분 관측이다.

E-022의 과거 형식 전환 수신 제한을 계기로 최초 설치/기존 정상 DB 재사용/형식 변경을 함께 검토했다. 사용자는 초기 기록을 그대로 보존해 위치만 전환하는 B가 요구에 더 맞는다고 확인하고 11/17 채택했다. 행별 수신과 대상 식별 재발급은 현행 절차에서 철회했으며 SQLite와 한 진행 원본, 기존 자료 보존 원칙은 유지한다.

대체 전 [관측 기록 (저장 명세 원문)](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md), [관측 기록 (기록 명세 원문)](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md), [관측 기록 (당시 DDL)](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md)을 그대로 보존했다. 원문의 상대 경로와 당시 추천 상태는 현재 실행 지시가 아니다. 현행은 [최초 인계 저장 — 「최초 기록 인계의 저장」](../../design/workflow/storage.md)과 [B의 선택 근거 — 「최초 인계 방식 재검토」](../../design/workflow/storage.md)를 따른다.
