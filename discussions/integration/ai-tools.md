# AI 도구와 WIKI 운용 검토

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

검토일: 2026-11-02. 정합성 반영: 11/11 이후 후속 기록 포함. 작업 분할, 도구 호환성, WIKI 저장과 PR 연계를 검토한다.

## 요청과 처리 범위

11/09 후속으로 WIKI 내용 구성, 초기 범위 B의 분할 상세 복원, 완료 기준을 채택했다. WIKI 역할과 기존 원문 보존은 유지하며 위임, 설치 상세는 후속이다. 작업 순서는 [진행표](../../development/roadmap.md)가 소유한다.

11/04에는 3번의 보충으로 본인 WIKI의 앱 Git 분리, 최소 비용 조건을 확인했다. [무료 운영 — 「무료 운영 대안」](../knowledge/storage.md)과 [두 저장소 운영 — 「두 저장소를 사용할 때」](../../design/sync.md)에 도구/저장 방식의 비교를 연결했다. Obsidian 자체와 유료 Sync를 구분하고, 매 변경에 문서 PR을 요구하던 설명을 작업 단위 저장, 선택 리뷰로 보정했다.

이어 Windows 앱 설치, 유지 선호와 WSL vault 오류를 확인해 [감시 문제와 배치 대안](../../evidence/environment-observations.md)을 보강했다. 직접 UNC 열기를 우선 추천에서 제외하고 Windows 문서 원본을 WSL에서 접근하는 추가 범위를 제안했다. 당시 기술 수단은 미채택이었으며 후속 채택은 다음 문단에 구분한다.

11/05 사용자는 Windows 문서 배치를 검증 후보로 삼아 지원을 추가하는 방향을 수용했다. ADR 0013의 범위를 보완했고, 이후 예비 연결 시험과 같은 세션 재접속까지 확인했다. 제품의 일반 지원 검증과는 구분한다. 작업별 앱, WIKI 커밋, 롤백은 [ADR 0017](../../decisions/integration/0017-work-sync.md)에 수동 기록, 작은 Git 보조, submodule을 비교했다.

후속 [PR/CI 질문 — 「PR과 CI 연결」](../../design/sync.md)에는 로컬에서 두 변경을 준비하고 PR 연결, 검사를 자동화하되 사람이 각 PR을 승인하는 2안을 추천했으며, 사용자가 같은 날 이 방향을 채택했다. 자동 승인 전달, 연쇄 병합은 후속 후보다. 11/11 최소 원격 PR 연계의 첫 제공 범위도 채택했다. 기록 형식, 권한과 실제 검증은 남았다. 과거 조합 재현과 공유 변경 취소를 구분하고 ADR, 실패 근거를 보존한다.

## 작업을 나누는 기준

주제별로 사실 확인, 대안, 관련 문서와 다음 진행을 구분한다. 제품 범위와 관계없는 운영 요청을 설계 완료 조건으로 넣지 않는다.

짧은 작업마다 승인을 반복한다는 뜻은 아니다. 이미 합의된 확인, 기계 작업은 진행하되 설계 선택은 검토 가능한 결과를 보고 협의한다. 갱신할 파일을 따로따로 끝내 일시적으로 서로 다른 최신안을 만들거나, 문서 저장 전까지 무한히 조사하는 방식은 피한다. 중단 가능성을 없앤다고 보장할 수는 없으므로 단계별 복구 정보를 실제로 남기고 미완료 동기화를 표시한다.

## AI 도구 호환성

### 먼저 구분할 것

사용자의 목표는 특정 회사 도구에만 묶이지 않고 다른 AI로도 같은 하네스 역할을 사용할 수 있게 만드는 것이다. 다만 모델, 그 모델을 사용하는 에이전트 도구, 실행 환경은 서로 다른 축이다. 여기서는 Codex CLI, Claude Code, Gemini CLI를 비교한다. 웹 채팅과 IDE의 모든 확장까지 지원했다고 해석하지 않는다.

모델은 입력을 처리하지만 파일 발견, 명령 실행, 권한, hook은 이를 감싼 도구가 제공한다. 따라서 로컬 모델 파일만 교체한다고 `.agents`를 읽는 기능이 생기는 것으로 설계하면 안 된다. 로컬 보조의 작업 위임과 메인 에이전트 전체 교체도 별도 판단이다. 기존 [보조 역할](../../design/integration/local-ai.md)의 조건은 유지한다.

### 공식 문서와 현재 환경에서 확인한 사실

아래는 2026-11-02 열어 확인한 공식 문서의 안내다. 해당 도구를 설치해 호환성을 시험한 표가 아니다.

| 도구 | 프로젝트 skill 경로 | hook 설정 예 | 해석 |
| --- | --- | --- | --- |
| Codex | `.agents/skills` | `.codex/hooks.json` 또는 `.codex/config.toml` | skill 경로를 바꿔도 설정, hook의 도구 전용 경로가 없어지지 않음. [skills](https://learn.chatgpt.com/docs/build-skills), [hooks](https://learn.chatgpt.com/docs/hooks) |
| Claude Code | `.claude/skills` | `.claude/settings.json` | 공식 skill 경로 표에서 `.agents/skills` 공용 탐색은 확인하지 못함. 심볼릭 링크 등 별도 연결 가능성과 자동 공용 탐색은 구분. [skills](https://code.claude.com/docs/en/skills), [hooks](https://code.claude.com/docs/en/hooks) |
| Gemini CLI | `.gemini/skills` 또는 `.agents/skills` | `.gemini/settings.json` | 같은 범위에서 `.agents/skills`가 `.gemini/skills`보다 우선. [skills](https://geminicli.com/docs/cli/skills/), [hooks](https://geminicli.com/docs/hooks/) |

[Agent Skills 규격](https://agentskills.io/specification)은 `SKILL.md`와 메타데이터, 지원 파일의 재사용 가능한 형식을 제공한다. 모든 도구가 하나의 설치 디렉토리, hook 이벤트, 권한 의미를 공유한다는 규격으로 확대 해석하지 않는다. 공통 형식 안에서도 도구 전용 지시나 메타데이터를 사용하면 추가 조정이 필요하다.

진입 지침도 경로만 같다고 동작이 같지 않다.

- Codex는 `AGENTS.md` 계층과 override/fallback 규칙을 문서화한다. [OpenAI Docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- 현재 Claude Code 문서는 `CLAUDE.md`와 조건부 `AGENTS.md` 지원을 안내한다. 기본 설정에서는 작업 디렉토리 및 상위에 CLAUDE 지침이 없을 때 AGENTS를 읽으며, 문서상 v2.1.277 이전과 플러그인 비활성 등에는 직접 지원되지 않는다. 두 형식의 hook, 외부 경로 로딩에도 차이가 있어 버전과 설정을 확인해야 한다. [Claude 지침](https://code.claude.com/docs/en/memory).
- Gemini CLI는 기본 `GEMINI.md`를 사용하고 `context.fileName`으로 파일명 목록을 설정할 수 있다. 따라서 AGENTS를 포함할 수 있지만 모든 사용자 환경의 기본값으로 가정하면 안 된다. [Gemini 지침](https://geminicli.com/docs/cli/gemini-md/).

당시 조사에서는 Codex npm 패키지 메타데이터 `0.166.0`과 WSL의 실행 경로를 확인했다. 11/10 별도 WSL 시험은 `0.167.0`이며 제품 Windows의 실제 지원 버전은 후속 검증 대상이다. 10/29의 `0.165.0` 기록은 당시 관측으로 보존한다. 프로젝트의 `.codex/skills`는 존재하고 `.agents/skills`는 없다. 이번 세션에 제공된 skill 목록에는 `.codex/skills` 파일들이 실제로 포함되어 있다. 다만 이 목록만으로 별도 CLI 설치에서의 자동 탐색 경로나 모든 버전의 legacy 지원을 입증할 수는 없다. 로컬 패키지 README는 설치 안내 위주라 공식 문서로 보완했으며 내부 로더 코드, 새 세션, 다른 도구를 실행해 검증하지 않았다.

따라서 현재 경로를 틀렸다고 단정하거나 디렉토리 전체를 즉시 이동하지 않는다. 개발 단계에서 원문 보호, 사용 경로 조사, 중복 발견 방지, 실제 로딩을 함께 확인한 뒤 이전 범위를 정한다.

### 추천하는 책임 분리

세 대안, 장단점, 선정 이유와 B 원칙 채택은 ADR 0015가 소유한다. 아래는 채택한 책임 경계의 개념이며 패키지, 경로, 설정 키를 확정한 명세가 아니다.

| 책임 | 공통으로 유지할 부분 | 도구별로 연결할 부분 |
| --- | --- | --- |
| 지침, WIKI | 정보 역할, 필요한 때 읽기, 근거와 채택 상태, 원문 보호 | 지침 발견, 파일 접근, 신뢰 확인과 실제 문서 위치 연결 |
| skill | 반복 절차의 내용, 입력과 완료 조건 | 설치 경로, 호출 문법, 도구 이름, 확장 메타데이터 |
| 검증 | 원래 검사 식별, 계획/결과 구분, 미완료 보존 | 명령 호출과 결과 수집 방식 |
| 복구 | 작업 범위, 진행, 실패, 근거, 복귀 위치 | 세션/압축 이벤트와 주입 가능한 정보 |
| 선택 보조 | 위임 입력, 권한 범위, 결과 후보, 메인 검토 | native 서브에이전트 또는 로컬 실행기의 호출, 제약 |

도구별 연결부(adapter)는 각 도구의 입력과 출력, 이벤트를 공통 계약에 맞추는 작은 부분이다. 에이전트 전체를 다시 만들거나, 세 회사별로 별도 WIKI와 검증 파이프라인을 복제하자는 뜻이 아니다. 아직 한 도구만 지원하는 시점부터 거대한 추상 클래스, 등록 시스템, 새 상주 서버를 만들 필요도 없다.

예를 들어 Gemini는 `PreCompress`, Codex는 `PreCompact`를 문서화한다. 이벤트 이름뿐 아니라 실행 가능 시점, 입출력, 실패 처리까지 비교해야 한다. 어느 도구에 필요한 이벤트가 없으면 완료 상태를 공유하는 수동 절차로 충분한지 검토하거나 해당 자동 기능을 미지원으로 표시한다. hook이 실제로 발동하지 않았는데도 복구가 보장된다고 표시해서는 안 된다. 위 hook 공식 문서들의 차이에 근거한 설계 판단이다.

### 확대 순서의 후보

- 첫 버전: [ADR 0020](../../decisions/runtime/0020-windows.md)의 Windows 직접 실행에서 Codex 경로를 먼저 검증한다. WSL/Linux는 후속이다. 공통 규칙, 결과, WIKI 데이터는 특정 도구 전용 필드와 분리한다.
- 후속 버전: 수요가 있는 도구 하나의 연결부를 추가하고, 같은 실패, 재개, 문서 보존 시나리오를 실제로 통과한 조합만 지원 목록에 올린다. Claude와 Gemini 중 무엇을 먼저 지원할지는 아직 정하지 않는다.
- 로컬 AI: 메인 도구 지원 확대와 독립된 선택 분기다. 모델, 실행기, 입력 길이, 도구 호출, 출력 품질을 역할별로 확인해야 하며, 로컬 도입이 메인 교체의 선행 조건도 결과도 아니다.
- `v1.x`, `v2`는 아직 확정 일정이 아니다. 기능을 추가하는 것과 기존 설치, 문서/상태 형식을 깨는 변경을 구분해 버전을 정한다. 여러 도구를 지원한다는 이유만으로 반드시 v2로 올릴 필요는 없다.

호환성은 `도구/버전 + 실행 환경 + 기능` 단위로 기록할 것을 추천한다. 필요한 기능의 부재를 숨겨 동작 차이를 만들지 않으며, 같은 계약을 사용해도 모델별 품질, 토큰, 시간이 같다고 주장하지 않는다. CLI 연결부를 만든 사실은 계정 구독, API 비용, 인증을 통합했다는 뜻도 아니다. 추가 호출, 과금, 계정 사용은 도입 단계에서 별도로 협의한다.

### 개발 전에 확인할 사례

이 항목은 지원 판단 후보이며 실행 결과가 아니다. 확정 후 수용 기준에 상세 시나리오로 연결한다.

1. 새 작업 공간에서 지침, 선택 skill을 발견하고 동일 이름의 중복 설치가 없는가.
2. hook 신뢰, 비활성, 미지원과 실제 호출 결과를 구분하는가. 복수 연결부가 같은 동작을 중복 실행하지 않는가.
3. 실패한 검사와 필요한 WIKI가 보존되고 도구 변경으로 다른 PASS가 이를 덮지 않는가.
4. 종료, 재개, 압축, 긴 작업의 상태를 실제로 복원하는가. native 대화 내용 전체가 도구 간 그대로 이동한다고 가정하지 않는가.
5. 기존 프로젝트 문서와 규칙을 보존하고, 선택 도구가 없을 때의 설치/실행 결과를 명시하는가.

다중 도구 지원을 동시 다중 작성자 허용으로 확대하지 않는다. 하나의 작업 상태를 동시에 수정하는 문제는 별도 동시성 설계가 필요하다. 현재 추천은 도구를 선택해 사용해도 같은 계약을 유지하는 것이다.

## 사용자 질문과 답변 위치

아래 표는 사용자 질문의 원래 범위를 보존한다. 3-1~3-6의 답변, 공식 근거, 한계는 [WIKI 저장과 Obsidian](../knowledge/storage.md), 대안과 추천은 [ADR 0016](../../decisions/knowledge/0016-storage.md)에 있다. 제품 환경의 현재 채택은 ADR 0020, 작업 연계는 ADR 0017, 완료된 개인 연결은 [이전 기록](../../evidence/environment-observations.md)에 구분한다.

### 토큰 비용 검토

11/02 후속 사용자 조건이다. Obsidian을 사용하는 경우 추가 토큰이 발생하는지, 얼마나 차이 나는지, 편의, 동기화 이점과 비교해 도입 판단을 바꿀 수준인지를 검토한다. 아래는 조사, 비교의 공통 조건이며 실제 측정 결과나 실험 실행 승인이 아니다.

- 비교 대상: 같은 문서, 작업을 프로젝트 내부에서 직접 읽는 경우, 외부 vault의 파일을 직접 읽는 경우, 선택한 MCP로 접근하는 경우를 구분한다. 검색/요약을 추가한다면 그 효과도 별도로 확인한다. Obsidian 편집기 사용, 파일 저장 위치, AI 연결 방식의 영향을 하나로 합쳐 평가하지 않는다.
- 비용 구간: 최초 설치, 색인/이관, 세션 시작 시 지침, 도구 설명, 요청별 검색, 반환 본문, 메타데이터, 재검색, 중복 읽기, 오류 재시도, 요약 비용을 나눈다. 항상 발생하는 비용과 사용 시에만 발생하는 비용을 구분한다.
- 비교 조건: 동일한 문서, 질문, 모델/도구 버전, 작업 범위, 완료 기준을 맞춘다. 새 세션과 재개 세션, 캐시 조건도 구분해 단순 파일 길이만으로 전체 사용량을 대신하지 않는다.
- 보고 방식: 가능한 경우 완료한 작업당 입력과 출력, 기타 제공되는 usage 항목과 전체 클라우드 토큰의 절대 차이, 증감률을 제시한다. 누락, 오답, 재작업, 소요 시간도 함께 대조해 필요한 정보를 덜 읽은 것을 절약으로 계산하지 않는다. 추정은 가정, 범위를 밝히고 실측과 구분한다.
- 사용량 한계: 관측 가능한 토큰과 구독별 할당량을 별도로 다룬다. 공식적으로 확인되지 않은 환산 규칙으로 할당량 소진 시점을 계산하지 않는다. 로컬 보조를 포함하면 로컬 자원과 클라우드 추가 검토 비용도 구분한다.
- 판단: 증가량이 미미한지, 편의, 정확도 이득과 교환할 수준인지, 현재 예산에서 도입을 보류할 수준인지 근거를 제시한다. 허용 증가량, 대표 작업, 유료 호출이 필요한 실험은 조사 결과로 구체화한 뒤 사용자와 정하며 임의의 합격선을 먼저 확정하지 않는다.

공식 자료의 일반적인 비용 발생 경로는 [토큰 영향](../knowledge/storage.md)에 정리했다. 11/02 비교 조건 작성 당시에는 실제 측정 전이었다. 이후 승인된 Windows 표본의 사용량과 품질은 아래에 연결하며, 그 결과를 배포 제품 전체의 비용이나 허용 증가량 확정으로 확대하지 않는다.

#### 실제 비교의 토큰 해석

11/20 사용자는 MCP의 큰 사용량 차이가 실제 개발 규모에서 부적절한 설계인지 질문했다. [닫힌 비교의 재집계](../../evidence/experiments/wiki-access/2026-11-21_05-58-03-mcp-cost-review.md)에서 MCP/직접 접근의 내부 모델 응답은 21/4회, 첫 입력은 16,481/16,569, 마지막 입력은 48,379/48,367토큰이었다. 응답당 평균 입력도 약 34,219/34,108로 비슷했다. 입력과 출력 합계 722,087/138,975의 차이는 이번 표본에서 주로 더 많은 응답에 문맥이 반복 포함된 모습으로 설명된다. MCP 메시지 포장 자체가 5배라는 측정은 아니다.

캐시 입력은 앞서 처리한 입력을 재사용한 부분이며 총입력에 포함된다. [OpenAI API의 캐시 안내](https://developers.openai.com/api/docs/guides/prompt-caching)는 캐시 사용을 별도로 계산한다. 캐시 입력을 뺀 입력+출력 41,639/38,879의 약 7% 차이를 실제 청구액 또는 구독 차이로 부르면 안 된다. 반대로 총토큰 약 5.2배를 주간 한도 5.2배로 환산할 근거도 없다. [Codex 사용 안내](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)는 모델, 문맥, 복잡도와 도구 등 사용 조건의 영향을 설명한다. 이번 로그만으로 계정별 환산을 확정하지 않는다.

이번 MCP 답변은 수신한 원문의 필수 복구 예외를 누락했고 처리 시간도 90.969초로 직접 방식의 58.014초보다 길었다. 따라서 현재 후보를 비용상 문제가 없거나 동등 품질이라고 평가하지 않는다. 다만 검색 조건, 묶음 호출과 오류 경로가 다른 한 쌍이므로 모든 MCP가 본질적으로 비효율적이라는 결론도 아니다.

11/22 [후속 세 방식 비교](../../evidence/experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)도 별도 표본으로 보존한다. 직접/긴 값/짧은 값의 캐시 제외 입력+출력은 32,121/82,904/52,092토큰, 시간은 66.596/168.568/91.486초였다. 짧은 값은 긴 값보다 적게 썼지만 첫 검색의 미수신 90줄을 보고하지 않고 사전 답변 기준 하나를 일부 누락했다. 이를 동등 품질의 절감 성과로 취급하지 않는다. 조회 범위 차이와 전역 설정 해시 변화도 있어 cursor 길이만의 인과 효과로 설명할 수 없다.

문서가 많으면 넓은 단일어 검색, 반복 페이지와 중복 근거로 내부 응답이 늘 수 있다. 현재 후보의 범위 재검사는 로컬 디스크 읽기도 늘릴 수 있다. 파일 수만으로 토큰 증가율을 예측하지 않으며, 원문을 읽는 데 필요한 입력과 불필요한 재탐색/반복 문맥 비용을 구별한다. 로컬 MCP 서버의 파일 검색 자체는 일반 코드지만, 그 결과를 클라우드 모델이 읽고 다음 행동을 판단하면 모델 사용량이 발생한다. 로컬 서버라는 이유로 모델 입력이 무료가 되지는 않는다.

공개 자료에서 확인한 공통 패턴은 **찾을 위치를 좁히는 검색과 선택한 원문 읽기를 구분하는 것**이다. 이것은 우리 설계에 적용할 수 있는 해석이지 모든 기업의 표준이라는 주장이나 정확도 보장이 아니다. Microsoft의 검색 결과 제한도 우리 전체 읽기/전체 일치 결과 요청을 생략할 근거로 사용하지 않는다. 발견용 발췌와 전체 검토의 완료 조건을 명시적으로 구별해야 한다.

[Anthropic의 MCP와 코드 실행 설명](https://www.anthropic.com/research/code-execution-with-mcp)은 불필요한 도구 정의와 중간 결과를 문맥에 넣는 비용, 호출 사이 데이터 복사 오류를 다룬다. 코드에서 반복/선별하고 필요한 결과만 전달하는 접근을 제시하지만, 우리 시험도 이미 코드 실행과 일부 검색 묶음을 사용했다. 따라서 해당 기능만 켜면 해결된다는 설명이나 그 자료의 절감률을 우리 예상치로 쓰지 않는다. 모델이 원문을 이해해야 하는 작업을 해시/개수만 출력하는 처리로 대체해서도 안 된다.

이번에는 구조를 조사하고 출처를 연결했으며 외부 코드나 패키지를 편입하지 않았다. 조회 시점의 원문은 [QMD MIT](https://github.com/tobi/qmd/blob/main/LICENSE), [Basic Memory AGPL-3.0](https://github.com/basicmachines-co/basic-memory/blob/main/LICENSE)이다. 추후 실제 버전의 코드/의존성을 채택하면 [라이선스 기준 — 「라이선스와 저작권」](../../design/module.md)에 따라 별도로 확인한다. 라이선스 이름만으로 우리 배포와 호환된다고 판정하지 않는다.

현재 추천은 기본 직접 접근을 유지하고, MCP의 [호출 비용과 개선 순서](../../design/integration/mcp.md)를 기존 입력 전달/원문 보존 조건과 함께 검토하는 것이다. 사례 조사만으로 새 검색 엔진, 임베딩 모델이나 외부 서비스를 필수 의존성으로 추가하지 않는다.

## 직접 접근 대비 MCP의 채택 근거

11/22 통합 비교 뒤 사용자는 MCP가 단순 파일 연결 이상의 이점을 제공하는지, 직접 접근에 가까운 토큰과 시간, 신뢰성을 확보해야 하는지 재검토를 요청했다. 아래는 기존 [ADR 0022](../../decisions/runtime/0022-wiki-entry.md)의 선택 MCP 판단을 구체화한 검토다. 첫 배포 포함이나 제외를 새로 확정한 결정은 아니다.

두 방식 모두 같은 로컬 Markdown을 사용한다. 직접 방식은 Codex의 파일/셸 도구가 읽고, MCP 방식은 Codex가 등록된 문서 도구를 호출하면 로컬 프로그램이 읽어 돌려준다. [MCP 공식 구조 설명](https://modelcontextprotocol.io/docs/learn/architecture)은 문맥 교환 규약을 다루며 모델의 문맥 사용 방법까지 정하지 않는다. 따라서 MCP 도입 자체가 검색 품질, 토큰 절감, 동기화나 원문 누락 방지를 보장하지 않는다.

| 도입 근거 후보 | 실제 이점과 현재 한계 |
| --- | --- |
| 일반 `codex`에서 프로젝트별 WIKI 도구 사용 | 등록 후 A/B 프로젝트와 하위 경로에서 읽기/검색을 확인했다. [공식 설정](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)은 신뢰한 프로젝트의 `.codex/config.toml` 등록을 지원한다. 기기별 경로 준비, 의존성, 서버 시작과 권한 확인이 없어지는 것은 아니다. |
| 여러 AI 도구에서 같은 기능 재사용 | [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)은 이름, 입력 형식과 결과를 공통 방식으로 전달한다. 다른 지원 클라이언트로 확장할 때 연결 코드를 줄일 가능성이 있다. 현재 후보의 타 플랫폼 호환은 검증하지 않았으므로 첫 배포의 확정 이득으로 계산하지 않는다. |
| 범위 제한, 원문 버전 확인, 일부 실패의 명시 | 이번 문서 도구가 제공하는 기능이다. 같은 일반 코드를 CLI에서도 사용할 수 있으므로 MCP만의 장점은 아니다. MCP 경로 밖의 직접 편집까지 자동으로 보호하지 않으며 현재 후보의 쓰기는 미구현이다. |

`--add-dir`는 문서를 모델에 넣는 명령이 아니라 추가 디렉토리의 쓰기 범위를 지정하는 옵션이다. 설치된 CLI 도움말과 [공식 명령 안내](https://learn.chatgpt.com/docs/developer-commands?surface=cli)를 대조했다. 읽기 가능 여부도 실제 권한에 따라 확인해야 하며 외부 파일 읽기에 항상 이 옵션이 필요하다고 설명하지 않는다. 기존 전용 시작 명령도 등록 경로를 자동 전달하므로 직접 방식에 매번 긴 옵션을 입력해야 한다는 전제로 MCP의 편의를 평가하지 않는다.

[관측 기록 (이번 기존/개선 MCP 비교)](../../evidence/experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)는 누적 토큰 781,204→480,497, 캐시 입력을 제외한 입력+출력 40,212→42,225, 처리 시간 110.402→100.618초, 도구 오류 0→3회다. 두 답은 사전 필수 사실 15개를 반영했지만 개선본의 긴 이어 읽기 값 재작성 오류 2회와 등록 크기 초과 입력 1회가 남았다. 직전 MCP 대비 일부 감소이며 직접 접근과의 동등 성능을 입증하지 않는다. 총토큰과 캐시 제외 합계 모두 구독 차감량이 아니고 과거 직접 접근 수치는 별도 참고다.

현재 추천은 기본 직접 접근을 유지하면서 **같은 일을 수행할 때 사용자가 얻는 추가 이점이 비용을 정당화하는지**를 먼저 판단하는 것이다. 다음 조건은 기존 비교 기준의 적용 설명이며 임의의 수치 합격선이나 새 실행 승인이 아니다.

- 원문 범위와 필수 사실, 수정 시 사용자 변경 보존을 먼저 확인한다. 같은 원문이 도착해도 모델의 이해와 최종 답까지 같다고 보장할 수 없다. 적게 읽어 얻은 절약은 개선으로 세지 않는다.
- 같은 작업량에서 별도 기능 이득이 거의 없다면 직접 접근에 가까운 사용량과 체감 시간을 목표로 삼는다. 유의미한 추가 이득이 확인된 경우에만 그에 비례한 비용을 검토한다. 정확히 같은 토큰 수나 밀리초를 요구하지는 않는다.
- 긴 값을 모델이 다시 쓰다가 바꾸는 문제, 알려주지 않은 현재 상한을 넘는 입력처럼 인터페이스에서 줄일 수 있는 실패를 먼저 보완한다. 이 긴 값과 페이지 계약은 우리 구현의 선택이지 MCP 규격이 강제한 형태가 아니다. 원문 변경, 파일 부재, 권한 거부와 연결 종료는 올바른 실패 보고와 복구가 필요하며 오류 수를 줄이려고 숨기지 않는다.
- 대표 작업의 전체 처리 시간, 반복 호출, 캐시 포함/제외 사용량과 오류 복구 비용을 함께 비교한다. 첫 연결과 반복 사용, 읽기와 쓰기, 실제 사용자 환경의 차이를 구분한다. 이번 단건 결과로 대규모 우위나 일반 실패율을 단정하지 않는다.

한정된 첫 배포에서 추가 이점과 비용을 입증하지 못하면 MCP를 후속으로 두는 편이 낫다는 판단이다. 기술 검토에는 기술을 무조건 채택한 결과뿐 아니라 비교와 보류 근거도 남길 수 있다. 기존 통합 개선 승인 범위는 유지하며, 다음 보완은 [남은 호출 문제 — 「실제 호출에서 남은 연결」](../../design/integration/mcp.md)를 이 채택 판단에 연결해 검토한다. 필요성을 만들기 위해 새 색인, 서버 DB나 도구를 계속 추가하지 않는다.

### 후속 AI 연계에서의 활용

11/22 후속 질문은 기존 계획의 로컬 보조, 다른 AI 도구 지원까지 포함한 MCP의 활용 가능성이다. **향후 이점이 가장 커질 곳은 여러 AI가 같은 WIKI 조회 기능을 재사용하는 경계**다. 지금의 Codex 단독 읽기 성능과 향후 연결 재사용의 가치를 구분하며, 후속 계획의 존재만으로 첫 배포에 MCP를 포함하지 않는다.

| 기존 계획 | WIKI 연결에서 얻을 수 있는 이점 | MCP의 필요성과 현재 상태 |
| --- | --- | --- |
| [AI 도구 지원 확대](../../decisions/integration/0015-agent-support.md) | Codex, Claude Code, Gemini CLI가 같은 검색/읽기 입력과 출처 형식을 사용하도록 연결 | 가장 직접적인 표준 연결의 이점. 각 도구의 등록, 권한, 출력 처리와 실패 복구는 별도 검증해야 하며 현재 후보의 타 도구 지원은 미검증 |
| [로컬 사실 추출과 추가 자료 요청 — 「코드와 WIKI 접근」](../../design/integration/local-ai.md) | 연결 프로그램이 필요한 원문을 읽어 로컬 모델에 전달. 도구를 사용하는 로컬 보조로 확장하면 같은 WIKI 도구를 재사용할 수 있음 | 첫 전달 흐름은 일반 파일 읽기와 Ollama API만으로 가능. 로컬 도입 자체에는 MCP가 필요하지 않으며 제한된 자율 검색은 후속 후보 |
| [독립 교차 검토 — 「로컬 AI 교차 검토」](../../design/integration/local-ai.md), [범위별 복원 — 「범위별 병렬 복원」](../../design/integration/local-ai.md) | 작업자별로 원문 위치, 버전, 실제 확인 구간과 미확인을 같은 형식으로 반환해 근거 대조를 돕는 구성 | 공통 근거 처리는 직접 호출로도 가능. MCP가 위임, 대화 공유, 동일 시점의 원문이나 검토 품질을 자동 보장하지 않음. 기본 순차 진행과 단일 반영 유지 |
| [WIKI 위치표의 역할 조회 — 「입력의 경계」](../../design/knowledge/map.md) | ‘이 기능의 요구사항과 결정 기록’처럼 같은 조회 기준을 여러 AI에서 사용. 프로젝트마다 다른 경로를 매번 추측하는 부담을 줄일 후보 | 위치표와 조회 코드는 공통 책임이고 MCP는 제공 수단. 현재 읽기/검색 시험본에 역할 조회 도구가 구현됐다는 뜻이 아님 |

[Claude Code](https://code.claude.com/docs/en/mcp)와 [Gemini CLI](https://geminicli.com/docs/tools/mcp-server/)는 공식적으로 MCP 도구 연결을 지원한다. 따라서 같은 기능을 재사용할 기술적 근거는 있다. 그러나 설정 형식, 도구 입력의 지원 범위, 출력 제한과 승인 동작은 다르므로 ‘등록만 바꾸면 전체 하네스가 호환된다’고 판단하지 않는다. 같은 서버 코드를 재사용하는 것과 모든 클라이언트가 하나의 상주 프로세스나 대화 상태를 공유하는 것도 다르다.

로컬 보조의 예로, 메인은 ‘재시도 WIKI와 구현에 조건 누락이 있는가’라는 질문과 허용 자료를 지정한다. 연결 프로그램이 해당 원문을 읽어 Ollama 모델에 전달하고, 로컬은 문제 후보와 근거, 부족한 자료 요청을 반환한다. 메인은 필요한 원문을 확인해 최종 반영을 결정한다. 이 순서는 [기존 전달 설계 — 「코드와 WIKI 접근」](../../design/integration/local-ai.md)이며 MCP 없이도 가능하다. [Ollama 공식 도구 호출 예제](https://docs.ollama.com/capabilities/tool-calling)에서도 모델의 함수 요청을 실제 실행하고 결과를 다시 보내는 역할은 프로그램이 맡는다.

같은 프로그램이 MCP 클라이언트 역할을 맡으면 WIKI를 읽는 부분을 기존 MCP 도구로 연결할 수 있다. 같은 프로세스 안에서 이미 공통 읽기 코드를 쓸 수 있다면 직접 함수 호출이 더 단순할 수 있다. 선택은 중복 코드 감소, 경계 유지, 실제 호출 비용을 비교해 판단하며 모든 로컬 읽기를 MCP로 강제하지 않는다. 코드와 Git 이력 수집은 현재 WIKI 읽기 도구의 범위 밖이며 필요한 별도 입력으로 준비해야 한다.

토큰 절감 가능성은 로컬이 적합한 범위를 처리해 메인의 긴 원문 처리와 반복 탐색을 줄일 때 생긴다. MCP는 그 전달 수단이 될 수 있지만 절감의 원인은 역할 분담과 자료 선택이다. 메인이 전체를 먼저 읽고 로컬도 다시 읽은 뒤 메인이 전부 재검토하면 이득이 작거나 비용이 늘 수 있다. 교차 검토는 추가 읽기로 오류를 찾는 목적일 수 있으므로 비용 절감과 별도로 평가한다. 모델이 다르다고 결과가 독립적이거나 더 정확한 것도 아니다.

이 관점에서 문서가 거의 없는 프로젝트의 최초 복원은 코드/이력 수집의 기여가 크고, 지식이 쌓인 뒤 여러 AI가 이를 조회하고 검토할 때 WIKI MCP의 재사용 가치가 커질 가능성이 있다. 기존 실패 로그 보조도 로그 전달이 중심이므로 WIKI 도구의 직접 이점은 관련 운영 문서를 함께 찾을 때로 제한된다. 팀의 Git 공유, 동시 편집 해결이나 세션 복구를 MCP가 대신하지 않는다.

추천은 이미 채택한 [공통 처리와 연결부의 분리 — 「확장을 위한 경계」](../../design/architecture.md)를 유지하고, 실제 두 번째 소비자가 필요한 시점에 같은 조회/출처 계약을 재사용할 수 있게 하는 것이다. 사용자별 장비와 역할 품질, 접근 범위, 중복 호출과 전체 시간을 검증하기 전에는 로컬 보조나 타 도구를 지원 완료로 표시하지 않는다. 현재 MCP 후보의 성능/오류 개선, 로컬 보조의 효과, 타 도구 호환은 서로 다른 검증이며 새 모델 실행이나 지원 확대는 이번 질문으로 시작하지 않았다.

11/22 후속 설계 정리에서는 메인 AI, Codex CLI, 로컬 연결 프로그램과 Ollama 모델의 구분을 [코드와 WIKI 접근](../../design/integration/local-ai.md)에 반영했다. “공통 코드”는 [문서 처리의 재사용 경계 — 「확장을 위한 경계」](../../design/architecture.md)로 구체화했다. 현재는 [세 방식의 실제 비교와 첫 제공 판단 — 「세 방식 비교와 첫 제공 판단」](../../design/integration/mcp.md) 단계다. 짧은 값 후보도 직접 접근보다 시간과 캐시 제외 합계가 컸고 답변/완료 보고가 미충족이므로, 사용자가 첫 배포는 직접 접근에 집중하고 MCP는 후속으로 미루는 안을 채택했다. 새로운 AI 연계의 구현/채택이나 MCP 전체의 부적합 판정으로 확대하지 않는다.
