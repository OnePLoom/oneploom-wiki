# WIKI 생성과 보강

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

2026-11-08 조사와 협의. B 기본 진입, 공식 모델 목록 선택, 범위 미리보기, 분할 원칙을 채택했고 제품 구현, 모델 비교 실험은 하지 않았다. [최소 WIKI](../../design/knowledge/wiki.md)의 정보 역할과 [원문 보존 — 「기존 자료 보존」](../../design/runtime/install.md)을 전제로 한다.

## 먼저 볼 결론

채택한 방향은 **설치한 실행 명령이 분석 순서, 검사, 저장, 재개를 관리하고, 필요한 분석 단계에서 Codex를 호출하는 B안**이다. 모델 목록 조회, 표시와 입력은 일반 코드가 맡고, 선택과 실행 범위 확인이 끝난 뒤 AI 분석을 시작한다. AI CLI 안에서 같은 실행 코드를 부르는 skill은 선택 입구 후보다. 사용자에게 매번 절차를 프롬프트로 작성하게 하지 않으며, 진행, 보존은 코드가, 의미 분석은 AI가 맡는다. 방향 채택과 구현, 문서 채택 완료는 구분한다.

11/08 사용자 재확인으로 최초 A 우선 추천을 보정했다. A에도 script를 포함할 수 있으므로 일반 채팅과 같다고 단정하지 않는다. 다만 앞선 설명은 설치형 작업의 명시적 실행과 프로그램의 제어 책임보다 대화에서 요청하는 예시를 앞세웠다. 구독, 지원 환경이 바뀐 때문이 아니라 기존 요구의 우선순위를 잘못 반영한 보정이다. 일반 개발 전체를 비대화형으로 바꾸거나 별도 서버를 도입하는 결정이 아니다.

로컬 AI로 같은 절차를 실행할 길은 열어 두되 첫 기본값으로 확정하지 않는다. 정확한 모델, 양자화, 문맥 설정, 작업 범위에 따른 품질 차이를 아직 모른다. 클라우드도 자동으로 정답이 되는 것은 아니다. 비교가 끝나기 전에는 전체 문서의 자동 채택이나 모르는 과거 의도의 복원을 보장할 수 없다.

## 같은 작업으로 비교하는 A안, B안, C안

세 안 모두 코드와 기록을 AI가 해석해 문서 후보를 만든다. 차이는 **AI 실행과 분석 진행을 누가 관리하는가**다. 아래는 구현 전의 사용 흐름 설명이며 실제 프로젝트를 분석한 결과가 아니다.

예를 들어 “사용자 참가 기능을 WIKI로 정리한다”면 다음 과정이 공통으로 필요하다.

1. 코드 기준 버전, 기존 문서, 분석할 기능을 정한다. 연결된 다른 기능은 필요한 부분만 확인하고 범위 밖 작업은 표시한다.
2. 일반 도구로 관련 파일, 커밋, 기존 문서를 찾는다. AI는 내용을 읽으며 실제 호출 흐름, 조건, 데이터 변경과 빠진 근거를 파악한다.
3. AI가 현재 동작, 근거 위치, 미확인을 문서 후보로 작성한다. 코드가 정원 초과 참가를 거절하더라도 그 이유가 기록에 없다면 이유까지 만들어 쓰지 않는다. 현재 구현을 바로 채택 요구사항이나 검증 PASS로 바꾸지 않는다.
4. 기존 WIKI와 중복, 충돌, 누락을 대조하고 사람이 채택 범위를 확인한다. 일반 도구는 파일 형식, 링크, 원문 변경 여부 등을 확인하며, 내용의 진실성을 모두 자동 판정하지는 못한다.
5. 승인된 변경을 적용하고 입력, 후보, 검사, 적용 여부와 다음 작업을 저장한다. 중단됐으면 저장된 상태와 현재 파일을 대조해 재개한다.

**A는 설치한 skill을 명시적으로 호출하고, 현재 Codex가 분석을 진행한다.** Codex가 정해진 절차에 따라 파일, 커밋을 읽고 후보를 만들며 모듈의 일반 도구가 입력 목록, 진행 상태, 원문 보존을 맡는다. 사용자에게 매번 절차를 설명하게 하거나 AI의 암묵적 skill 선택에만 맡기지 않는다. 현재 모델을 그대로 사용하기 쉽지만 Codex가 도구를 부르는 순서와 프로그램이 허용하는 다음 단계를 맞춰야 한다. 지시문만으로 검사 생략, 잘못된 완료를 막을 수는 없다.

**B는 설치한 실행 명령이 전체 작업을 관리하고 Codex 같은 AI CLI를 호출한다.** 저장한 프로젝트, WIKI 설정과 지정 범위로 작업을 만든다. 프로그램이 실행 전후 상태와 결과를 검사하고 다음 단계 진행, 중단을 결정하며, AI CLI는 한정된 입력의 코드 탐색과 의미 분석을 담당한다. 별도 실행에는 현재 대화나 일시적인 모델 선택이 자동 전달된다고 가정할 수 없으므로 실행 조건을 명시한다. skill을 제공한다면 같은 명령을 호출하는 입구로 둘 수 있지만, 초기 지원 여부와 중첩 실행의 권한, 비용, 취소 검증은 별도다.

**C는 우리 프로그램이 모델 API를 직접 호출한다.** 사용자의 요청을 받은 프로그램이 허용된 코드, 기록을 읽어 모델에 보내고 결과를 받는다. 추가 파일이 필요하면 미리 자료를 더 모으거나 모델의 도구 요청을 받아 허용된 읽기를 수행하는 절차도 직접 구현한다. 모델 자체가 사용자 디스크와 Git을 알아서 탐색하는 것은 아니다. A, B에서 AI CLI가 제공하던 인증, 도구 실행, 권한, 실패 처리를 어디까지 직접 맡을지 정해야 한다. 상용 API는 구독 CLI와 인증, 비용을 별도로 확인하며, 상시 서버, 대기열은 C의 필수가 아닌 추가 운영 선택이다.

| 같은 요청의 실행 흐름 | AI 탐색, 도구 실행의 주된 담당 | 모듈이 추가로 맡는 핵심 |
| --- | --- | --- |
| A: 사용자 → 실행 중인 Codex → 코드, 기록 → 후보 | 기존 Codex | 공통 분석 절차, 검사, 진행 저장 |
| B: 사용자 → 우리 명령 → 별도 AI CLI → 코드, 기록 → 후보 | 호출한 AI CLI | 공통 부분 + 단계 진행, 검사, 결과/중단 관리 |
| C: 사용자 → 우리 프로그램 ↔ 모델 API → 후보 | 우리 프로그램과 모델의 반복 처리 | 공통 부분 + 자료/도구 제공, 인증, 실행 제어 |

A가 수동 작업이고 B, C만 자동화인 것은 아니다. A도 정해진 범위에서 여러 분석 단계를 진행하도록 만들 수 있다. B, C도 해석 충돌, 새 비용, 범위 변경에는 사용자 확인이 필요하다. 시작 방식만 바꿔서는 품질이나 클라우드 사용 한도 문제가 해결되지 않는다.

아래 일곱 경로 표에서 A는 1번, B는 2번, C는 4번에 해당한다. 3번은 여러 작업을 계속 관리할 운영 형태, 5번은 자료의 수동 전달, 6번은 로컬 모델 연결, 7번은 화면, 도구 진입 경로다. 서로 조합할 수 있는 선택까지 함께 비교한 표이지 모두 같은 층의 독립 대안은 아니다. 로컬 모델을 선택하는 것과 로컬, 클라우드에 서로 다른 역할을 맡기는 것도 구분한다.

## 설치한 작업 실행

요구는 **설치한 기능을 명시적으로 실행하면 합의한 절차가 동작하고, 재실행, 보강, 중단 재개에도 같은 규칙이 적용되는 것**이다. 셸, skill, 실행 파일은 사용자가 들어오는 수단이고, 실행 순서, 상태, 검사, 원문 반영을 담당하는 코드가 제품의 중심이다. 설치 수단은 ADR 0010, 분석 실행 선택은 ADR 0018이며 서로 다른 결정이다.

사용 예시는 `tool wiki build --scope party`로 분석을 시작하고, 중단 후 `tool wiki resume <작업 ID>`로 이어가는 형태다. `tool`과 명령 이름은 설명용이며 실제 구현, 설치된 명령이 아니다. 초기 설정에서 경로, 지원 실행기, 인증/모델 조건을 확인하고 저장하면 이후에는 필요한 범위만 입력하도록 설계한다. 자연어로 범위를 받더라도 파일, 의존 범위로 해석한 결과가 불명확하면 확인받는다.

### 비대화형 실행과 서브에이전트

11/09 용어 보강: 채택한 B의 `codex exec`는 분석 AI를 스크립트에서 실행하는 방식이다. 그 호출 자체가 Codex의 서브에이전트 분업은 아니다. 이 작업에서 ‘메인 AI’는 실행 코드가 호출한 분석용 Codex를 뜻하며, 실행 코드 자체나 지금 설계를 논의하는 대화와 구분한다. 기본 흐름은 **사용자 명령 → 일반 코드의 선택/입력 준비 → codex exec의 AI 분석 → 검사, 검토, 반영**이다. 서브 없이도 이 흐름이 성립한다. [공식 비대화형 실행 안내](https://learn.chatgpt.com/docs/non-interactive-mode)

서브에이전트는 메인 AI가 분석 중 한정된 일을 추가 작업자에게 맡기고 결과를 통합하는 별도 선택이다. 여러 범위를 순서대로 `codex exec`에 전달하거나 같은 실행을 재개한다고 자동으로 서브에이전트 구조가 되는 것은 아니다. 보조 사용 조건, 지원 버전에서의 호출/복구는 별도 검증 대상이며 [기본 메인, 선택 보조 경계 — 「공통 규칙과 호출 범위」](../../design/integration/local-ai.md)는 채택됐으며 구체 호출, 권한, 복구 수단은 후속 검토다.

‘일반 코드로 충분한 일은 AI에 맡기지 않는다’는 설명은 경로, 파일 목록, 해시, JSON 문법처럼 정형 처리를 코드로 수행한다는 뜻이다. WIKI 내용과 과거 선택의 의미를 스크립트만으로 복원하거나 이미 채택한 AI 분석을 생략하는 뜻이 아니다. 파일을 수집하는 것, 메인 모델에 본문을 전달하는 것, 보조 모델이 그 본문을 읽는 것도 구분한다. 메인/보조의 중복 읽기는 [전달할 문맥 — 「전달할 문맥과 중복 읽기」](../../design/integration/local-ai.md)에서 판단한다.

### B에서 skill이 맡는 역할

B 내부에서도 분석용 지시, skill과 기존 조건부 문서 탐색, 검사를 활용할 수 있다. B는 skill을 배제하는 구성이 아니다. 앞서 말한 “skill 진입도 제공”은 **현재 AI CLI에서 사용자가 명시적으로 호출하면 B의 실행 명령을 시작하도록 안내하는 입구**를 뜻했다. 분석 AI에 주는 지침과 사용자의 시작 입구는 역할이 다르며, 두 역할 때문에 반드시 skill 파일을 두 개 만들어야 한다는 뜻도 아니다.

```text
일반 터미널 명령 ───────────────┐
현재 AI CLI → 시작 skill ───────┤
                               ↓
                 같은 B 실행 코드, 작업 상태
                               ↓
              분석용 Codex + 필요한 지침/skill
                               ↓
                    검사와 검토, 반영과 재개
```

이 구성은 B에 진입점이 둘 있는 것이다. 원래 A처럼 현재 Codex가 전체 분석 진행을 맡는 별도 경로까지 만드는 B+A와 구분한다. 시작 skill은 실행 코드의 범위, 상태, 검사 규칙을 복제하지 않고, 분석용 Codex가 같은 시작 작업을 다시 호출하는 재귀도 막아야 한다. 기존 workflow의 어떤 skill/script를 재사용할지는 파일별 연결 명세에서 정한다. 중요한 gate를 실행 코드와 skill 양쪽에서 중복 실행하거나 AI 선택에 따라 생략하지 않는다.

입구가 달라도 같은 설정을 사용한다. 터미널에서는 대화형 설정이 가능하지만 AI CLI가 호출하는 비대화형 실행에서는 부족한 입력을 구조화해 반환하고 현재 대화에서 채우는 후보가 적절하다. 자식 프로세스가 보이지 않는 입력 대기로 멈추게 하지 않는다. 시작 skill을 첫 버전에 포함할지는 미정이며, 포함한다면 현재 AI와 분석용 AI가 둘 다 동작할 수 있어 권한, 취소, 추가 문맥 비용을 따로 확인한다.

### 공통 실행 책임

| 순서 | 실행 코드의 책임 | AI의 책임 |
| --- | --- | --- |
| 준비 | 경로, 도구, 권한 확인, 코드/기존 WIKI 기준과 작업 ID 저장 | 필요 시 분석 범위 후보 제안 |
| 수집, 분할 | 허용 입력 목록과 작업 단위, 의존 관계 저장 | 코드 연결을 해석하고 추가 근거 요청 |
| 분석 | 단위별 지시, 입력 전달, 허용 범위에서 AI 실행, 종료/출력 수집 | 현재 동작, 근거, 미확인, 문서 후보 작성 |
| 검사, 검토 | 형식, 출처 위치, 누락 표시, 기존 원문 변경 대조, 미통과/미승인 상태 차단 | 의미 충돌, 근거의 타당성 검토 보조. 최종 채택은 정한 검토 절차 적용 |
| 반영, 재개 | 승인된 변경만 적용, 부분 적용/실패 기록, 재실행 시 입력과 상태 대조 | 필요해진 분석 부분만 다시 수행 |

기본 후보는 분석 AI가 코드와 기존 WIKI를 읽고 별도 결과를 반환하게 하고, 검토된 결과를 실행 코드가 반영하는 방식이다. 파일 쓰기 권한과 후보 저장 위치는 후속 계약에서 검증한다. 종료 코드 0, JSON 형식 통과, 모델의 “완료” 답변만으로 문서를 반영하지 않는다. 링크가 존재한다는 검사는 내용이 참이라는 검사가 아니므로 의미 검토는 별도로 남는다.

11/09 추가 제안인 [범위별 병렬 복원](../../design/integration/local-ai.md)은 위 흐름의 분석 단위를 나누는 미채택 후보다. 상세 Markdown과 JSON 결과의 책임은 [JSON과 문서 초안](../../design/integration/local-ai.md), 로컬 검토자의 조건은 [로컬 AI 교차 검토](../../design/integration/local-ai.md)가 소유한다. 범위별 의미 검토, 원문 보존 기준은 그대로 유지하며 여러 AI의 합의를 완료 근거로 대체하지 않는다.

중단 대비 기록은 AI에게 “마지막에 기록하라”고 맡기는 대신 실행 전, 단위 종료 시 프로그램이 남긴다. 중간 결과, 적용 완료, 미검토를 구분하고, 입력이 바뀌면 그대로 재사용하지 않는다. 실행 수, 재시도, 시간 등 합의한 제한과 실제 사용량 확인 가능 범위를 적용하며, 클라우드 한도 소진을 없애거나 종료 전에 항상 알림이 온다고 보장하지 않는다. 첫 실행은 상시 서버, 대기열 없이 로컬 명령과 저장 파일로 검토한다.

이 구분은 공식 기능과도 맞는다. [Codex skill](https://learn.chatgpt.com/docs/build-skills)은 명시 호출과 script 포함을 지원하며, [비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode)은 script에서 AI를 호출하고 구조화된 결과를 수집하는 수단이다. [공식 유지보수 사례](https://developers.openai.com/blog/skills-agents-sdk)도 반복 작업은 실행 코드로, 해석은 모델로 나눈다. 다만 이런 기능의 존재는 우리 WIKI의 정확성, 복구, 토큰 효과가 검증됐다는 뜻은 아니다.

기술 검토에서 검증할 가치는 명령어, exe 포장 자체보다 기존 문서 보존, 입력 변경 감지, 잘못된 완료 차단, 중단 후 재개, 기능별 누락/근거와 비용의 비교다. 같은 모델, 자료를 준 일반 요청 및 지시문만 제공한 경우와 비교해 효과를 확인해야 한다. 이러한 실행 구조 자체도 이미 쓰이는 방식이므로 독창성을 과장하지 않는다.

## 품질 기준

목표는 [선택 범위의 상세한 개발 과정과 결과, 선택에 이른 흐름을 복원 — 「복원할 깊이와 완료 목표」](../../design/knowledge/wiki.md)하고 근거와 관계를 확인할 수 있게 만드는 것이다. 기초 안내나 최신 결론만 작성하고 복원을 마친 것으로 보지 않는다. 상세 정보의 보존과 요청별 문맥 선택은 별도로 평가한다. 출력은 다음을 구별해야 한다.

| 정보 | 작성할 수 있는 근거 | 주의할 오류 |
| --- | --- | --- |
| 현재 관측 사실 | 고정한 코드, 설정, 실제 실행 결과 | 코드에 기능이 있다는 것과 실제 실행 PASS 혼동 |
| 채택 요구, 정책 | 기존 채택 문서 또는 사용자가 확인한 요구 | 현재 구현의 버그, 임시값을 요구사항으로 승격 |
| 과거 결정, 이유 | 당시 ADR, 검토 기록 등 직접 근거 | 코드와 커밋 제목만 보고 의도를 만들어 과거 ADR 작성 |
| 추정, 미확인, 충돌 | 해석의 근거와 부족한 입력 표시 | 자신감 있는 문체나 모델 점수로 사실처럼 확정 |

초기 데이터 적재 코드가 보인다고 운영 환경에도 같은 데이터를 넣어야 한다고 쓰지 않는다. Kafka 중복 확인 로직이 있다고 모든 실패 순서에서 멱등성이 보장된다고 쓰지 않는다. 이 예시는 평가 입력 설명이며 실제 적용 프로젝트에서 확인한 결과가 아니다.

| 평가 항목 | 확인 방법 | 실패 사례 |
| --- | --- | --- |
| 주장 정확성 | 검토한 주장 중 실제 근거가 지지하는 비율, 오류 건수, 심각도 | 근거가 같은 파일에 있지만 주장의 의미는 지지하지 않음 |
| 중요한 정보의 충족 | 사람이 미리 정한 범위별 필수 항목 중 정확히 기술한 항목 비율 | 파일 목록은 있으나 운영 조건, 실패 경로, 계약 누락 |
| 근거 추적 | 저장소/버전, 경로, 기호/구간을 통해 원문 재확인 | 존재하지 않는 인용, 다른 버전의 소스, 줄 번호만 남김 |
| 불확실성 처리 | 정보가 없는 입력, 상충하는 입력을 따로 평가 | 모든 항목을 미확인으로 회피하거나 빈칸을 추정으로 메움 |
| 원문 보존 | 허용 변경 목록과 전후 본문, 해시, 링크 대조 | 기존 ADR/사용자 편집을 자동 덮어씀 |
| 재실행, 재개 | 같은 입력 재실행, 중간 중단, 입력 변경 후 상태 대조 | 중복 문서, 누락한 범위의 완료 표시, 오래된 후보 적용 |
| 문서 사용성 | 해당 문서로 정한 질문, 작업을 해결하는지 확인 | 읽기 쉬우나 필요한 검사, 근거에 도달하지 못함 |
| 관계 탐색 | 대표 질문/변경마다 미리 정한 필수 사실, 근거에 도달하는지, 관련 외부 모듈 계약, 폐기/변경된 결정을 구별하는지 대조 | 링크는 유효하지만 필요한 계약이 누락되거나 오래된 결론을 현재 정책으로 읽음 |
| 전체 비용 | 최초 상세 복원, 반복 사용, 갱신을 구분해 모든 시도의 모델 사용량, 탐색/검토/수정 시간 집계 | 일상 읽기 토큰만 줄고 전체 복원, 관계 유지, 재검토 비용은 숨김 |

문서 길이, 링크 개수만으로 충실도나 탐색 정확성을 판단하지 않는다. 관계 탐색의 기대 자료는 사람이 확인한 대표 사례로 정하고, 필요한 근거 누락, 잘못된 확정 여부를 먼저 본 뒤 같은 품질에서 불필요한 읽기와 전체 비용을 비교한다. 이러한 시험도 모든 미래 작업의 무오류, 무누락을 보장하지 않는다.

**합격 하한 후보:** 평가한 사례에서 허위 확정, 허용 밖 원문 변경, 미검증 완료 표시가 발견되면 채택을 보류한다. 필수 항목은 답하거나 미확인과 필요한 입력을 드러내야 하며, 중요한 미해결 항목이 남으면 완료로 판정하지 않는다. 표본에서 문제 0건과 모든 프로젝트에서 오류가 없다는 보장은 다르다. 비핵심 항목의 허용 누락, 품질 차이, 시간 상한은 실험 전에 합의한다.

링크, 형식, 해시는 코드로 검사하고, 인용이 주장 전체를 지지하는지는 사람의 검토를 포함한다. 구조화된 JSON이나 schema 통과도 내용의 진실성을 증명하지 않는다. 모델 평가자는 보조로 쓸 수 있지만 같은 생성 모델의 자기 점검을 독립 정답으로 삼지 않는다. 작업별 기준과 사람 판단을 먼저 정하라는 근거는 [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)이며, 해당 문서의 예시 임계값을 이 제품의 합격 수치로 복사하지 않는다.

## 로컬과 클라우드

로컬은 실행 장소이고, 상용, 공개 가중치는 공급/배포 조건이다. 공개 모델을 원격에서 실행할 수도 있고 로컬 서버가 원격 모델로 요청을 전달할 수도 있다. 따라서 모델 이름과 `localhost` 주소만으로 비용, 데이터 이동을 판단하지 않는다.

### 현재 알 수 있는 것

- **WIKI 품질 차이의 크기는 미측정이다.** 이번 조사에서 비교한 공식 실행 문서와 연구는 이 모듈, 입력, 모델 조합의 동등성 자료가 아니다. 코딩 벤치마크나 최대 문맥 길이만으로 이 작업의 승자를 정하지 않는다.
- 로컬에서 내려받은 모델을 실행하면 그 추론에 상용 클라우드의 구독 한도를 쓰지 않을 수 있다. 그러나 RAM/VRAM, 문맥, 시간, 디스크, 전력과 실패 비용은 남는다. [LM Studio의 오프라인 실행](https://lmstudio.ai/docs/app/offline)은 모델을 미리 준비하는 조건을 명시한다.
- 실제 사용 문맥과 모델의 최대 문맥은 다를 수 있다. Ollama는 문맥을 늘리면 필요한 메모리가 늘어난다고 설명한다. 모델 크기, 양자화, 입력/출력 길이, 동시 요청도 기록해야 하며, 모든 사용자에게 같은 최소 VRAM이나 품질을 약속하지 않는다. [Ollama 문맥 설정](https://docs.ollama.com/context-length)
- 큰 문맥도 누락 방지 장치가 아니다. [NoLiMa, ICML 2025](https://arxiv.org/abs/2502.05167)는 당시 평가 모델에서 긴 입력의 의미 기반 검색 성능 저하를 관측했다. 이 결과는 현재 모델의 WIKI 점수가 아니며 범위를 나눠 근거를 확인해야 한다는 근거로만 사용한다.

### 환경별 경로

| 사용자 조건 | 가능한 경로 | 판단 |
| --- | --- | --- |
| 로컬 추론 자원이 없고 클라우드 사용 가능 | 일반 코드로 수집, 축소 + 선택한 상용 CLI | 첫 지원 후보. 로컬 설치를 필수 준비물로 두지 않음 |
| 작은 모델, 짧은 문맥만 실용적 | 좁은 범위의 추출/후보 또는 자료 정리, 필요 시 승인된 클라우드 검토 | 전체 구조, 정책 추론의 기본값으로 삼기 전에 평가 필요 |
| 충분한 로컬 자원, 검증한 모델 | 같은 후보/검사/재개 계약으로 로컬 분석 | 자원 보유와 품질 통과는 별개. 지원 조합을 명시해야 함 |
| 외부 모델 사용 불가 | 로컬 또는 수동 검토 | 한도/실패 때 클라우드로 자동 전환하지 않음. 불가한 범위는 미완료 표시 |
| 로컬, 클라우드 모두 가능 | 로컬 초안 + 클라우드/사람 검토 또는 메인의 선택 위임 | 양쪽 전체 시도와 검토 비용을 합쳐 이득을 평가 |

첫 비교는 같은 수집, 상태 도구를 쓴 **상용 CLI 단독 / 로컬 단독 / 로컬 후보+상용 검토**다. 일반 코드만으로 수집 가능한 항목은 먼저 처리하여 AI를 쓰지 않은 절감을 로컬 모델 효과로 계산하지 않는다. 상용 검토에는 요약뿐 아니라 원문 근거와 누락 점검 목록이 필요하다. 로컬이 빠뜨린 사실은 그 요약만 읽는 검토자가 발견하지 못할 수 있다.

사용자가 실행기 하나를 고르면 **공급자 호환성**, 로컬 결과를 클라우드가 검토하면 **단계별 협업**, 메인이 작업 중 로컬을 호출하면 **위임**이다. 뒤의 두 방식은 역할 간 입력, 실패, 비용 계약이 추가된다. 기존 [로컬 보조 ADR 0006](../../decisions/integration/0006-local-assist.md)의 로그 정리 후보와 이번 WIKI 후보를 같은 필수 작업으로 합치지 않는다.

### 로컬의 자동 실행

로컬 모델도 비대화형으로 호출할 수 있다. Codex는 실행 도구와 추론 모델을 구분하며, 공식적으로 Ollama, LM Studio를 사용하는 `--oss`와 `--local-provider`를 제공한다. `codex exec`에서는 공급자를 설정하지 않으면 선택을 기다리지 않고 오류가 난다. 현재 설치된 0.167.0 도움말에서도 이 옵션을 확인했으며 모델을 실행하지는 않았다. [Codex 로컬 공급자](https://learn.chatgpt.com/docs/config-file/config-advanced#oss-mode-local-providers)

| 연결 후보 | 실제 분석 주체 | 장점, 남는 부담 |
| --- | --- | --- |
| B → Codex exec의 로컬 모드 | 로컬 모델, 도구 실행은 Codex | 기존 실행 흐름을 재사용할 후보. 도구 호출, 출력, 문맥, 품질은 해당 조합으로 검증 필요 |
| B → 로컬 서버 API 직접 호출 | 로컬 모델 | 연결 제어가 자유롭지만 코드 탐색, 도구 실행, 결과 처리도 직접 구현해야 함 |
| B → 로컬 후보 → 클라우드 검토 | 단계별로 다른 모델 | 어려운 판단을 클라우드에 남길 수 있으나 재전송, 누락 점검, 재작업 비용이 늘 수 있음 |

첫 로컬 시험에는 첫 행을 우선 비교하는 것이 합리적이다. Codex 프로그램을 쓴다고 추론까지 OpenAI 클라우드에서 진행되는 것은 아니다. 현재 제품의 로컬 지원 채택이나 클라우드와 동등한 품질을 뜻하지는 않는다. 단순 파일 목록, Git 변경 수집은 세 안 모두 일반 코드로 처리한다.

로컬 선택 목록은 인터넷에 있는 모든 모델이 아니라 **연결한 서버에서 사용 가능한 모델**에서 얻는다. [Ollama 목록](https://docs.ollama.com/api/tags)과 [LM Studio 목록](https://lmstudio.ai/docs/developer/rest/list)은 추론과 별도 조회 기능이다. 생성용 모델인지, 필요한 도구 기능을 지원하는지, 실제 로드된 문맥과 사용자 자원에서 실행 가능한지를 추가로 확인한다. 내려받았다는 사실만으로 메모리에 적재되거나 WIKI 품질을 충족하지는 않는다. 불명확한 기능, 자원은 검증 전으로 표시하고 자동 설치, 모델 다운로드를 하지 않는다.

품질 목표는 문장 일치가 아니라 아래의 사실성, 중요 항목 누락, 원문 보존 기준이다. 로컬만으로 이를 충족하면 로컬 단독도 가능하고, 미달하면 역할을 좁히거나 사용하지 않는다. 클라우드 검토가 들어가면 그 사용량도 합산하며, 로컬이라는 이유만으로 절감 효과를 인정하지 않는다.

## 품질 비교 방법

아래는 실행 전 협의할 평가안이며 이번에 모델을 호출하지 않았다.

1. 입력을 고정한다. 코드 기준점, 미커밋 상태, 허용한 이력, 기존 문서, 대상 범위, 문서 작성 지침을 저장한다. 비교 조건으로 모델과 실행기 버전, 문맥 크기, 양자화 방식, 도구와 캐시 조건도 남긴다.
2. 사람이 기대 정보를 먼저 정한다. 작은 단일 모듈, 모듈 간 계약, 문서/코드 충돌, 과거 이유 부재, 기존 사용자 편집, 입력 변경, 중단 재개 사례를 포함한다. 기존 시험 프로젝트의 기존 문서만으로 비교하면 빈 WIKI 복원 평가가 되지 않는다.
3. 두 종류를 구분한다. 같은 원문 묶음을 주는 비교는 해석 차이를, 같은 탐색 권한/예산에서 자료부터 찾게 하는 비교는 누락과 전체 사용 흐름을 평가한다. 서로 다른 자료를 읽은 결과를 순수 모델 성능 차이라고 부르지 않는다.
4. 모델명을 가리고 같은 평가표로 검토한다. 실패, 미완료, 모든 재시도를 포함하고 중요한 오류의 원문을 남긴다. 반복 횟수, 표본 수, 허용 비용은 별도 합의하며 소수의 성공 예시로 일반화하지 않는다.
5. 필수 품질 하한을 통과한 조합끼리 비용을 비교한다. 클라우드 입력과 출력, 캐시, 추론 사용량은 공급자의 정의대로 기록하고 중복 합산하지 않는다. 로컬 토큰/초, 메모리, 검토 시간은 별도다. 서로 다른 토크나이저의 토큰 수나 구독 할당량을 그대로 환산하지 않는다.

11/08 사용자 재확인에 따른 판단 순서는 **상세 복원 품질 확보 → 클라우드 총사용량 절감과 감당 가능한 검토/운영 비용 확인**이다. 평균 문장 품질이나 비용 이득으로 중요한 누락, 근거 없는 과거 이유, 원문 훼손을 상쇄하지 않는다. 상용 모델의 출력 자체도 정답으로 삼지 않으며 원문과 사람이 확인한 기대 정보를 기준으로 평가한다.

| 실제 비교 결과 | 판단 |
| --- | --- |
| 같은 상세, 근거, 관계, 보존 기준을 충족하고 클라우드 총사용량 감소 | 검증한 모델, 환경, 작업 범위에서 로컬 사용 후보. 모든 사용자/프로젝트의 동등성으로 일반화하지 않음 |
| 로컬 단독은 부족하지만 특정 역할이나 상용 검토를 포함하면 품질과 절감 충족 | 해당 역할만 제한해 사용 후보로 검토. 원문 재검토, 누락 점검, 재시도 비용까지 합산 |
| 중요한 품질 차이 또는 재검토를 포함하면 절감 없음 | 품질을 확인한 상용 경로를 유지하거나 로컬 역할 보류. 가격이나 로컬 실행 여부만으로 선택하지 않음 |
| 표본, 근거 부족 또는 양쪽 모두 품질 미달 | 동등/우수 판정 보류. 입력, 분할, 검토 방법을 보완하고 미확인을 남김 |

11/11 보충: 작성 이후의 [로컬 교차 검토 — 「로컬 AI 교차 검토」](../../design/integration/local-ai.md)는 오류 발견을 위한 별도 후보다. 작성 + 로컬 검토와 단독 작성뿐 아니라 같은 예산의 메인 자체 재검토를 대조하고, 발견한 실제 오류, 오탐, 최종 잔여 오류, 전체 비용을 본다. 추가 검토의 품질 이득을 토큰 절감으로 자동 보고하지 않는다. 원문, 사람의 기준으로 판단하며 모델 간 합의나 형식 통과를 정답으로 쓰지 않는다. 특정 모델, Ollama 연결, 실험을 채택한 것은 아니다.

실험 전에 중요한 오류와 허용할 차이, 검토 부담을 정한다. “차이가 발견되지 않았다”는 소수 사례만으로 동등성을 확정하지 않는다. 모든 사용자에게 한 수치를 적용하지 않고 모델, 양자화, 문맥, 실행기, 환경과 작업 유형별 결과를 남긴다. 정확한 입력, 모델, 반복 수, 허용 차이, 시간/비용은 실험 전 합의하며 지금 임의로 정하지 않는다.

입력, 문서 형식과 작은 대표 범위를 정하면 초기에 비교할 수 있다. 전체 모듈 완성을 기다릴 필요는 없지만, 문서 구성 설계를 막는 선행 조건으로도 두지 않는다. 현재는 비교 설계만 확인했으며 모델 실행, 다운로드, 추가 과금, 품질 차이 실측은 수행하지 않았다. 실행기 지원 여부와 품질 검증 상태를 별도로 표시한다. [OpenAI 공식 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 작업별 평가, 사람 검토 원칙을 참고하며 특정 평가 서비스나 API 사용을 채택한 것은 아니다.

## 실행 방식

모델 공급자와 실행 진입점을 분리한다. 아래는 독립 제품 일곱 개를 구현하자는 제안이 아니라, 같은 범위, 출처, 후보, 상태 계약을 어디서 구동할지의 비교다.

| 방식 | 사용자 경험 | 장점 | 부담, 한계 | 첫 범위 판단 |
| --- | --- | --- | --- | --- |
| 1. 현재 CLI의 명시 작업/skill | 설치한 skill을 호출하고 현재 모델로 분석 | 기존 인증, 도구, 승인 흐름 재사용 | 진행이 대화에 의존, 중요 상태 전환은 별도 코드 필요 | 대안. B의 명령을 부르는 skill은 다른 분석기를 만드는 것이 아닌 선택 입구 |
| 2. 설치한 실행 명령 + AI CLI 호출 | 저장한 설정, 범위로 시작, 코드가 단계 진행, AI 호출, 검사, 재개 관리 | 대화 밖에서도 동일 계약, 진행, 실패를 직접 검사 가능 | 인증, 권한, 프로세스 중단, CLI 버전별 해석 추가 | **B 기본 경로 채택**. 제품 구현, 검증 전 |
| 3. 지속 실행 서비스 + 작업 대기열 | 한 번 등록한 범위를 여러 실행으로 처리 | 상태, 재시도, 관측을 프로그램으로 관리 | 서버 수명, 동시 실행, 취소, 설치/운영 비용 | 초기에는 과함. 다수 사용자/장기 자동화 필요 시 재검토 |
| 4. 모델 API 직접 호출 | 제품이 모델, 도구 실행을 직접 관리 | 구조화된 응답, 사용량, 실행 제어 | 별도 인증/과금, 도구 루프, 권한, 세션을 직접 책임 | CLI 경로의 제약이 실증될 때 검토 |
| 5. 준비한 자료를 수동 전달 | 범위별 자료/지시를 원하는 AI에 전달 | 실행기 제약이 작고 이식이 단순 | 복사, 결과 반입, 버전 연결 누락, 수동 비용 | 제한 환경의 보조 경로. 자동화 기본값으로 비추천 |
| 6. 로컬 추론 서버 직접 연결 | 내려받은 모델에 자료를 보내 후보 수신 | 클라우드 한도 회피 가능, 외부 전송 제한에 적합 | 장비, 모델, API 기능 차이, 파일 접근/루프는 별도 필요 | 로컬 평가 후보. 연결 성공을 품질 통과로 보지 않음 |
| 7. IDE/Obsidian 확장, MCP 진입 | 화면에서 범위 선택, 검토 | 사람의 문서 탐색/검토에 유리할 수 있음 | UI, 앱, 플러그인, 권한의 지원 범위 증가 | 핵심 동작 뒤 선택 UI. 필수 실행기로 두지 않음 |

로컬+클라우드 협업은 이 표의 진입점에 더할 수 있는 역할 배치다. 독립된 여덟 번째 설치 구조로 만들 필요는 없다. AI 없이 수집만 하는 script는 유효한 준비 도구지만 기록 없는 의미, 요구사항을 복원하는 대체재는 아니다.

SDK라는 이름만으로 4번에 분류하지 않는다. 기존 Codex를 프로그램에서 제어하는 [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)는 2번 계열 연결 후보이며, 모델 API를 직접 사용하는 구현과 다르다. [공식 통합 안내](https://developers.openai.com/blog/codex-as-a-platform)는 작은 작업의 exec, 프로그램 제어용 SDK, 지속적인 상호작용용 app-server를 구분한다. 첫 분석 실행은 exec로 설계하고 여러 분석 실행기를 동시에 만들지 않는다. 아래 app-server의 목록 조회는 분석 실행과 구분한 준비 기능이며 상시 서비스 도입을 뜻하지 않는다.

### 기본값과 사용자 선택

대안 1은 현재 Codex 모델을 쓰기 쉽고, 수정 추천 2는 별도 실행의 모델, 인증, 권한 조건을 명시해야 한다. 현재 대화의 일시적인 `/model` 선택이 외부 실행에 자동 승계된다고 보장하지 않는다. 특정 최신 모델 이름을 제품에 고정하지 않고 저장한 설정과 실제 선택의 확인 가능 범위를 기록한다. 지원 조합은 후속 검증 결과로 안내하며 모델/한도를 모르면 미확인으로 표시한다. 다른 공급자나 API 결제로 자동 전환하지 않는다.

B의 기본 순서는 **설치, 버전 확인 → 기존 공식 인증 확인 → 공식 목록에서 모델 선택 → WIKI, 코드 루트/범위 → 비용, 출력, 권한 요약 → AI 분석 시작**이다. 첫 실행기는 Codex이며 이후 공급자 확대는 별도다. 11/08 모델명 자유 입력 없이 선택하고, 조회, 선택을 일반 코드로 처리하는 원칙을 채택했다. 저장된 선택은 새 작업의 후보로 보여주되 현재 목록에서 다시 확인하고, 재개 중 모델이 사라졌다면 재선택, 영향 확인 전 중단한다. 매 실행의 확인 화면과 저장 설정 재사용 세부 UX는 미확정이다.

**목록에 존재함, 모듈의 실행 호환성, WIKI 품질 통과는 서로 다른 조건**이다. 계정 권한, 남은 한도, 서버 가용성도 실행 시 달라질 수 있어 목록 조회만으로 항상 성공을 보장할 수 없다. 실제 모델 호출이 필요한 확인은 사용량이 발생하는 검증으로 구분한다. 첫 지원은 ADR 0015의 Codex 우선 원칙을 유지하며 Claude, Gemini, 로컬을 이미 지원하는 선택지로 노출하지 않는다.

### 모델 목록 조회

Codex App Server의 공식 `model/list`는 선택 화면용 모델, 추론 강도 목록을 제공한다. 응답은 클라이언트, 계정에 따라 달라지므로 그 반환값을 사용하라는 공식 지침이 있다. 개발자가 새 모델 이름을 매번 코드에 추가할 필요는 없다. `codex exec`의 분석 실행과 이 목록 조회를 구분하며, 목록만 위해 상시 서버나 별도 분석 경로를 만들 필요는 없다. [OpenAI 공식 목록 기능](https://learn.chatgpt.com/docs/app-server#models)

이는 설치된 Codex와 통신하는 기능이며 익명 공개 HTTP API가 아니다. 분석 turn을 시작하지 않고 목록을 조회할 수 있으므로 메뉴 구성에 LLM 추론 토큰을 사용할 필요가 없다. 그 목록을 AI 대화에 넣으면 해당 텍스트는 문맥이 되고, 실행 시험을 하면 추론 사용량이 발생한다. 별도 API 키를 받는 [OpenAI API의 모델 목록](https://developers.openai.com/api/reference/resources/models/methods/list)을 ChatGPT 구독의 Codex 목록으로 대체하지 않는다.

기본 진입의 호출 주체는 **터미널 명령 → 일반 코드의 목록 요청, 선택 UI → 범위 확인 → Codex exec의 AI 분석**이다. AI에게 목록 조회나 선택 질문 작성을 맡기지 않는다. 선택한 모델의 작은 품질 시험도 선택, 시험 범위 확인 이후에 실행하며 실제 추론 사용량으로 기록한다. 시작 skill을 추가하면 메인 AI가 그 skill 요청을 해석하는 비용은 별도로 생길 수 있다.

현재 0.167.0에서 오프라인으로 생성한 schema의 `ModelListParams`는 `cursor`, `includeHidden`, `limit`이며 강제 최신화 인자는 확인되지 않았다. 실제 목록, 조회 지연, 과금 기록은 조회하지 않았다. Codex 내부 캐시, 클라이언트 버전까지 무시한 ‘항상 최신’이나 응답 시간 보장은 하지 않는다. 모델명 목록 관리 부담은 줄지만 CLI 업데이트, 연결 형식, 호환성 검증은 유지보수 대상이다.

| 목록 정책 | 장점 | 단점 |
| --- | --- | --- |
| 검증한 모델 고정 목록 | 지원 범위가 명확함 | 새 모델, 계정 차이 반영에 개발자 갱신 필요 |
| 공식 동적 목록 + 호환, 품질 상태 구분 | 이름 자동 반영, 미검증을 숨기지 않음 | 조회 실패 처리와 새 모델 평가 절차 필요 |
| 공식 목록 모두 즉시 정식 지원 | 새 모델 사용이 가장 빠름 | 목록 등재를 WIKI 품질 보장으로 오해하게 됨 |

**두 번째를 채택했다.** 실행기/버전, 필요 기능의 호환 기준과 모델별 품질 평가를 따로 관리한다. 새 모델은 자동 발견하되 검증 완료로 표시하지 않으며 작은 시험, 품질 확인을 거쳐 사용한다. 정확한 시험 입력, 합격 기준, 예산과 정식 적용 조건은 후속으로 구체화한다. 모델을 바꿔도 원문 보존, 검사, 재개 계약은 그대로 적용한다.

조회는 제한 시간을 두고 수행하고, 기다리는 동안 진행, 재시도, 취소를 제공한다. 캐시를 쓰면 조회 시점과 계정/공급자/CLI 조건을 구분하고 이전 목록임을 표시한다. 최신 목록을 확인하지 못했는데 캐시만으로 유효하다고 단정하거나 저장된 다른 모델로 자동 실행하지 않는다. 구체 시간 제한과 캐시 정책은 지연을 실측한 뒤 정한다. 목록의 페이지를 누락하거나 숨김 모델을 일반 선택지로 잘못 노출하는 경우도 검사 대상이다.

구독 CLI 인증과 직접 모델 API의 이용 조건은 구분하며, SDK라는 이름만으로 과금 방식을 단정하지 않는다. 배포 모듈이 계정 비밀번호, 세션 token을 받아 중개하지 않고 사용자가 공식 도구로 로그인하도록 한다. Claude의 공식 인증, 제품 연동 조건도 구독 자격을 임의 API 자격으로 바꾸는 방식을 허용한다고 해석하지 않는다. [Claude 인증](https://code.claude.com/docs/en/authentication), [인증 사용 조건](https://code.claude.com/docs/en/legal-and-compliance). 모든 사용자가 유료 구독을 필요로 한다고 일반화하지 않고 선택한 경로의 준비물만 README에 적는다.

### B의 남은 부담과 확인

B 실행 방식의 채택은 아래 문제가 해결됐다는 뜻이 아니다. 현재는 공식 실행 수단을 확인하고 처리 후보를 정리했으며, 제품 구현, 실제 AI 실행 검증은 전이다.

| 부담 | 처리 후보 | 구현 뒤 확인할 것 |
| --- | --- | --- |
| CLI 버전, 호출/결과 형식 | 첫 지원 버전을 좁히고 도구별 호출/결과 변환을 공통 진행 코드와 분리 | 지원 버전의 실행, 오류 해석, 미지원 버전의 명확한 중단 |
| 인증, 계정, 모델 | 공식 CLI 인증 활용, 지원표/설정 선택과 실제 실행 조건 대조 | 로그인 만료, 모델 접근 실패 시 무단 대체 없이 안내 |
| 파일 권한, 프로젝트 경계 | 코드/WIKI/결과 경로와 읽기와 쓰기 역할 확인 | 외부 WIKI 접근 거절, 다른 프로젝트 입력에도 원문 보존 |
| 중단, 취소, 부분 완료 | 실행 전/단위 종료 상태 저장, 작업 ID와 입력 지문, 자식 작업 취소, 종료 확인 | 강제 중단, 네트워크/한도 오류, 재시작 뒤 완료/미완료 구분과 중복 적용 방지 |
| 토큰, 시간 증가 | 불필요한 새 실행, 전체 기록 재전송을 줄이고 합의한 작업/재시도 한도 적용 | 같은 품질 기준에서 A/일반 요청 대비 총비용, 시간 실측. 절감 보장 안 함 |
| 문서 품질, 기존 수정 충돌 | 출처, 미확인, 후보를 분리하고 검사/검토 후 원문 대조 | 형식은 맞지만 잘못된 내용, 분석 후 사용자 수정, 근거 누락의 처리 |

플랫폼/모델 선택은 주로 인증, 실행 조건의 모호함을 줄인다. 권한, 복구, 품질, 토큰 문제는 별도 구현/검증이 필요하고, 한도 자체나 AI의 오류 가능성이 없어지지는 않는다.

## 범위와 재개

어느 진입점에도 같은 상태 계약이 필요하다. skill은 작업을 안내하거나 호출하고, 수집, 입력 식별, 후보 보존, 상태 저장, 적용 전 대조는 검증 가능한 코드가 맡는다. 수정 추천 B는 다음 단계 진행도 실행 코드가 관리한다. 문서의 `완료` 문자열만 보고 검증을 생략하는 구조로 만들지 않는다.

```mermaid
flowchart LR
    S[범위와 기준점 확인] --> I[자료 선택과 분할]
    I --> A[AI 후보와 출처]
    A --> V[형식 검사와 의미 검토]
    V --> H[사람이 채택 범위 확인]
    H --> P[원문 대조 후 적용]
    P --> C[연결 검사와 진행 저장]
    C --> N[합의한 다음 범위]
```

### 범위 선택

**사용자가 고르는 분석 대상과 실행 코드가 나누는 작업 단위는 별개**다. 입력을 한 폴더로 제한한다고 의미의 일관성이 보장되지는 않는다. 예를 들어 한 이벤트 흐름의 발행, 소비, 보상 코드가 여러 모듈에 흩어질 수 있다.

| 입력 방식 | 장점 | 단점 |
| --- | --- | --- |
| 상위 폴더 하나 | 입력, 범위 표시가 단순함 | 다른 모듈에 걸친 기능이나 일부 파일만 선택하기 불편 |
| 여러 파일/폴더 + 제외 경로 | 실제 원하는 범위를 명시하고 중복 제거 가능 | 의존 자료와 분석 대상을 구분하는 처리가 필요 |
| 기능을 말하면 AI가 경로 제안 | 경로를 모르는 사용자도 접근 가능 | 범위 판단에도 비용, 오류가 생기며 실행 전 확인 필요 |

**여러 파일/폴더와 제외를 받는 두 번째를 기본 방향으로 채택했다.** 한 항목도 허용하며 경로별 입력/목록 선택 같은 구체 UX는 후속이다. 경로 정규화, 존재/권한 확인, 중첩 중복 제거는 일반 코드로 처리한다. 따로 선택한 파일의 개수와 실행 단위의 개수를 같게 강제하지 않는다.

등록한 코드 루트, 선택한 분석 대상, 의존성 확인에 읽는 참조 범위, 생성/수정할 WIKI 위치를 구분한다. 의존 코드를 읽어야 한다고 그 모듈 전체의 WIKI 작성까지 자동 확대하지 않는다. 허용한 프로젝트 밖 입력, 심볼릭 링크의 외부 대상은 경계를 확인하고, 분석 범위 확장이 필요하면 사용자에게 이유와 영향을 제시한다.

Enter 기본값은 **현재 작업 디렉토리를 범위 후보로 선택 → 실행 전 목록 확인**으로 채택했다. 등록한 코드 프로젝트 안인지 먼저 확인하며, 설치 script 위치나 홈 폴더, 다른 저장소를 코드 루트로 오인하지 않는다. 프로젝트 최상단에서 실행했다면 전체 프로젝트가 후보가 될 수 있지만, 공백 입력만으로 재귀적으로 모든 내용을 AI에 전달하지 않는다. 빈 입력을 금지하는 안은 더 명확하지만 반복 입력이 늘고, 곧바로 전체 분석하는 안은 편하지만 범위, 비용을 확인하기 어렵다.

먼저 일반 코드가 파일 구조와 Git 상태를 조사한다. 선택할 경로와 제외할 경로, 작업 후보, 참조하는 의존 대상, 예상 규모를 보여준다. 의존 파일, 빌드 산출물, 생성 파일, 민감 자료를 내용 분석에 넣을지 구분하고 제외 이유도 기록한다. `.gitignore`만으로 중요한 설정이나 미커밋 입력까지 무조건 제외하지 않는다. 정확한 토큰 수를 모르면 추정 또는 미확인으로 표시한다. 의미상 분할에 AI가 필요하면 그 준비 호출도 범위, 비용에 포함한다.

사용자는 첫 단위, 일부 단위, 계획 전체 중 실행 범위와 예산을 확인한다. 전체를 골라도 기능/모듈, 관련 테스트/설정, 기존 문서, 필요 이력별로 나누어 처리한다. 처음부터 전체 Git 이력을 넣거나 파일을 같은 길이로만 잘라 기능 간 의미를 끊지 않는다.

| 사용 상황 | 기본 제안 | 완료 표시 |
| --- | --- | --- |
| 새 WIKI | 기초 파악 뒤 합의한 기능/이력 단위의 상세 복원 | 상세, 근거, 관계를 확인한 범위만 완료, 나머지 단위는 미완료로 유지 |
| 기존 WIKI | 역할 연결, 현재 코드 대조 후 누락/충돌 부분만 후보 | 기존 원문 보존과 허용한 보강 확인 |
| 후속 변경 | 변경된 소스와 영향받는 문서/경계 재검토 | 영향 범위 불명확 시 더 확인하고 재사용 보류 |
| 전체 프로젝트 요청 | 전체 범위를 작업 목록으로 나누고 실행, 검토 예산 합의 | 제외, 실패, 미확인을 남기며 전부 끝난 것처럼 표시하지 않음 |

기능별 문서와 짧은 상위 색인은 유력한 후보지만 REQUIREMENTS의 최종 분할, 템플릿은 아직 미합의다. 이번 실행안 때문에 모든 프로젝트에 같은 도메인/디렉토리를 강제하지 않는다. 중요한 항목의 분모도 범위와 함께 사람이 확인해야 한다.

### 분할과 문맥

각 단위에는 짧은 전체 구조, 공통 계약, 관련 원문, 의존 관계, 확정/미확인 상태만 전달한다. 요약만으로 누락을 막을 수 없으므로 원문 위치, 버전을 보존하고 필요할 때 다시 읽는다. 큰 단위는 세부 단계로 나누되 공유하는 스키마, 이벤트, 호출 계약을 연결한다. 모든 결과를 다음 대화에 계속 누적하지 않는다.

단위마다 출처, 누락, 문서 충돌을 검사하고 마지막에는 단위 사이 용어, 요구사항, 계약, 링크를 대조한다. 첫 단위를 마쳤다고 전체 WIKI를 완료로 표시하지 않는다. 모델의 실사용 문맥과 출력 여유, 작업 수, 시간, 재시도 한도를 기준으로 다음 단위 시작 여부를 판단한다. 구독의 남은 할당량을 정확히 얻을 수 없으면 아는 것처럼 예측하지 않고 한도 오류에도 아래 상태에서 재개하도록 한다. 분할은 중단 손실을 줄이는 수단이며 총토큰 절감을 보장하지 않는다.

### 저장할 최소 상태

분할 작업마다 프로젝트 식별, 코드/문서 기준 버전과 미커밋 입력 식별, 합의한 범위/제외, 의존, 입력 출처, 사용한 실행기/모델, 후보 위치, 검사, 채택, 적용 상태, 실패 원인과 다음 행동을 남긴다. 공급자의 세션 ID는 있으면 연결하지만 그것만 복구 원본으로 삼지 않는다. 파일 이름, 정확한 schema는 후속 복구/설치 계약에서 정한다.

### 중단과 적용

| 상황 | 필요한 처리 |
| --- | --- |
| 한도, 네트워크, 사용자 중단 | 작업 시작 전 범위/입력 저장, 후보, 검사 등 확인된 단계별 저장. 진행 중이던 단계는 중단으로 남기고 재대조 |
| 응답이 일부만 도착함 | 부분 결과와 검사 가능한 후보를 구별. 형식, 출처 미완성은 채택 금지, 필요한 단계부터 재실행 |
| 같은 요청을 다시 실행 | 입력, 범위, 기존 결과를 대조해 재사용 가능 부분과 재실행 대상을 구별. 모델 출력이 매번 같다고 가정하지 않음 |
| 후보 작성 후 사람이 원문 수정 | 저장했던 원문과 현재 원문 비교, 바뀐 부분은 적용 보류, 재검토. 이전 후보로 덮어쓰기 금지 |
| 여러 문서 적용 도중 중단 | 적용 예정 목록, 이전 내용, 실제 반영 내용을 대조하고 재개 또는 합의한 복원. 여러 파일/Git 저장소의 자동 원자성 주장 금지 |
| 모델, 실행기 교체/세션 소실 | 저장한 원문, 상태에서 다시 시작. 교체를 기록하고 영향받는 품질 검사를 다시 수행 |

한도 직전 알림이나 compact hook이 항상 먼저 실행된다고 가정하지 않는다. **예측 알림 없이 끊겨도 완료한 범위와 미완료 단계를 복구**해야 한다. 단계 사이 원자적 상태 저장과 보호된 후보가 필요하며 작성 도중 강제 종료를 포함한 시험은 아직 하지 않았다.

사용자가 한 번 시작해 여러 범위를 순서대로 처리하는 UX는 가능하다. 다만 범위, 작업 수/시간, 재시도, 비용 조건을 먼저 합의하고, 중단 후에는 같은 작업을 다시 지정해 재개한다. 구독 한도를 넘어서 자동 계속하거나 한 번의 명령으로 모든 규모의 프로젝트가 끝난다고 약속하지 않는다. 첫 버전에서는 상주 감시 서비스보다 사용자의 명시적 재개를 추천한다.

## 완료 후 다시 실행하는 흐름

2026-11-23 사용자가 기존 요구/설계와 충돌하지 않는 조건으로 진행을 승인했다. 아래 [기존 설계와의 연결](reconstruction.md#%EA%B8%B0%EC%A1%B4%20%EC%84%A4%EA%B3%84%EC%99%80%EC%9D%98%20%EC%97%B0%EA%B2%B0)을 대조하고 **상태 확인 후 필요한 범위 보완**을 기본 흐름으로 채택했다([ADR 0018 — 「완료 후 재실행」](../../decisions/knowledge/0018-reconstruction.md)). 기존 [중단과 적용](reconstruction.md#%EC%A4%91%EB%8B%A8%EA%B3%BC%20%EC%A0%81%EC%9A%A9)의 재사용/편집 보호 원칙을 구체화한 것으로, 설치기 업데이트나 매번의 일반 개발 요청에 전체 복원 절차를 추가하지 않는다. 구현과 실제 Windows/AI 검증은 미완료다.

### 대안과 추천

| 방식 | 장점 | 비용과 한계 | 판단 |
| --- | --- | --- | --- |
| 완료 후 재실행 차단 | 기존 자료 보호가 단순함 | 새 코드, 누락 발견과 사용자 보완 요청을 처리하지 못함 | 부적합 |
| 매번 확인 후 전체 재생성 | 사용자에게 설명할 분기가 적음 | 유효 자료도 다시 분석하며 반복 생성의 내용 차이와 충돌 범위가 커짐. 동의만으로 정확성이나 보존이 보장되지 않음 | 기본값으로 비추천 |
| 상태 확인 후 필요한 범위 보완 | 같은 명령으로 재개, 변경 반영과 추가 검토를 구별. 기존 유효 결과를 유지 | 근거/의존 관계 대조와 후보 검증이 필요. 변경 파일만 보고 영향 범위를 확정하면 누락 가능 | 11/23 채택 |

전체 재검토는 사용자가 범위를 선택할 수 있는 보완 방식으로 남긴다. 전체를 읽겠다는 선택도 기존 문서 전체를 자동 덮어쓰라는 뜻은 아니다. 재실행 횟수나 새 모델의 답변이라는 이유로 최신 결과를 정답으로 우선하지 않는다.

### 재실행 전에 구분할 상태

| 현재 확인 결과 | 채택한 동작 |
| --- | --- |
| 이전 실행이 아직 진행 중임 | 실제 실행/반영 상태를 확인해 안내. 중복 분석을 시작하거나 임의로 중단/종료하지 않음 |
| 앞선 작업이 중단됨 | 이전 작업의 입력과 실제 결과를 대조해 재개할 단계 안내. 완료된 복원을 다시 시작한 것으로 처리하지 않음 |
| 완료 결과, 범위와 관련 입력이 여전히 유효함 | 감지한 변경이 없고 이전 결과를 재사용할 수 있다고 안내. 추가 보완 의도가 없으면 새 분석 요청이나 문서 재작성 없이 종료 |
| 코드/문서/근거 변경, 새 범위 또는 미해결 정보가 있음 | 영향받는 범위와 연결된 요구/계약을 확인해 보완 계획 제시. 무관한 완료 자료는 유지 |
| 입력은 같지만 사용자가 더 상세한 설명이나 오류 재검토를 원함 | 같은 작업의 재시도와 구분한 새 검토로 처리. 구체적인 목표와 범위를 받아 후보 작성 |
| 완료 기록이나 비교 기준이 없음 | 새 팀원, 기록 정리/유실 등을 구분하고 현재 WIKI부터 보호. 기존 자료를 없는 것으로 간주하지 않으며 확인 불가 상태를 안내 |
| 필요한 원문을 읽지 못함 | 접근 실패를 변경 없음이나 근거 부재로 처리하지 않음. 영향받는 계획/반영을 보류하고 원인 안내 |

재사용 판단은 완료 표시나 Git HEAD 하나만으로 하지 않는다. [저장할 최소 상태](reconstruction.md#%EC%A0%80%EC%9E%A5%ED%95%A0%20%EC%B5%9C%EC%86%8C%20%EC%83%81%ED%83%9C)의 범위, 실제 입력과 미커밋 변경, WIKI 결과, 적용한 규칙과 필요한 검증 근거를 대조한다. 새 파일, 삭제와 이동, 공통 계약/의존 변경도 확인한다. 관련 상태를 확정할 수 없으면 필요한 확인 범위를 넓히며 단순 파일 변경 목록을 의미 영향의 완전한 목록으로 간주하지 않는다.

“변경 없음”은 기록한 범위의 기존 결과를 재사용할 수 있다는 뜻이다. 처음 복원한 내용에 누락이나 오판이 없음을 새로 증명한 결과는 아니다. 사용자가 지정한 재검토 목표를 캐시가 있다는 이유로 거부하지 않는다.

### 기존 설계와의 연결

채택 전에 다음 기준과 대조했다. 기존 정책을 바꾸는 충돌은 발견하지 않았으며, 적용 범위를 혼동할 수 있는 부분은 아래와 같이 구분한다.

| 기존 요구와 소유 문서 | 이번 흐름에서 유지하는 경계 |
| --- | --- |
| 조건부 진입과 [복구 적용 경계 — 「복구의 대상과 경계」](../../design/workflow/recovery.md) | 명시적 WIKI 분석/재실행에서 판단. 일반 질문, 파일 읽기나 CLI 시작마다 전체 복원/DB 조회를 추가하지 않음 |
| [범위별 완료 판정](../../design/knowledge/wiki.md) | 상세 복원, 근거와 단위 사이 검토 유지. 새 분석 생략을 미조사 자료나 필수 의무 생략으로 확대하지 않음 |
| [검사 재사용 ADR 0002](../../decisions/workflow/0002-pass-validity.md) | WIKI 본문/분석 결과 재사용과 테스트 PASS 재사용은 다름. 초기 자체 PASS 캐시를 도입하지 않고 필요한 검사는 기존 선택/실행 계약을 따름 |
| [원문 보존 ADR 0011](../../decisions/runtime/0011-preservation.md) | 계획 뒤 편집을 발견하면 이전 후보의 적용은 멈춤. 변경을 반영한 후보와 관련 검증을 다시 확인하기 전에는 쓰지 않음 |
| [기록 빈도 — 「기록이 필요한 때와 비용」](../../design/workflow/records.md)와 [작성 범위 — 「작성 범위와 동시 작업」](../../design/workflow/recovery.md) | 기존 로컬 기록과 단일 반영 경로 사용. 팀원 DB를 공유하지 않고 Git 협업/충돌 검토 유지. 파일 반영과 DB commit의 원자성 주장 없음 |
| [정리 뒤 조회와 복구](../../design/workflow/maintenance.md) | 정리/유실된 원문을 있는 것으로 간주하지 않음. 재사용할 근거가 없으면 필요한 재확인이나 보류로 분기 |
| [승인의 재사용과 한계](../../design/runtime/entry.md) | 같은 유효 범위의 확인은 반복하지 않음. 재실행 동의를 정책 변경, 공개, 삭제나 호스트 권한 우회로 확대하지 않음 |

이 대조는 설계 정합성 확인이다. 명령, WIKI 처리 상태의 필드와 호출, 실제 반영/복구 동작은 [파일별 구현 책임 — 「기능별 연결과 실패 처리」](../../development/migration.md)에 연결하며 현재 검증 기록만으로 제품 동작을 보장하지 않는다.

### 확인부터 반영까지

1. 일반 코드가 기존 처리 상태와 현재 파일/이력을 대조한다. 이 확인만을 위해 별도 AI 분석을 호출하지 않는다. 이미 AI 대화 안에서 실행한다면 도구 입력/반환의 토큰까지 없다고 설명하지는 않는다.
2. 보완할 대상, 이유, 재사용할 결과, 미확인 사항과 적용 범위를 보여준다. 예를 들어 “주문 취소 코드 변경에 따라 취소 조건과 관련 API 문서를 보완하며 결제 이력 문서는 보존”이라고 안내한다. 사용자는 범위를 조정하거나 종료할 수 있다.
3. 새 분석과 변경이 필요한 계획에 대해 기존 CLI 확인 방식으로 진행 여부를 받는다. 같은 구체 범위의 기존 허용은 재사용하고 질문을 반복하지 않는다. 동의하지 않거나 입력 채널이 없으면 새 작업을 실행하지 않고 필요한 선택을 알린다. 실제 명령 이름/옵션과 입력 형식은 공통 진입 명세에서 확정한다.
4. 분석 시작 때의 WIKI와 근거를 보존하고, 그 WIKI에 대한 필요한 변경만 별도 후보로 만든다. 원문, 추정, 미확인을 구분하며 문서의 기존 역할/식별자와 사람이 작성한 내용을 유지한다. 같은 설명을 새 문서나 ADR로 중복 생성하지 않는다.
5. 변경 후보의 출처, 요구/계약과 관련 문서 사이의 일관성, 링크, 누락을 검토한다. 반영 직전에는 분석에 사용한 코드/문서와 현재 파일을 다시 대조한다. 바뀐 입력에 의존하는 후보와 검사는 다시 확인한다.
6. 검증됐고 허용된 변경만 반영하고 실제 결과를 기록한다. 필수 미해결 항목은 미완료로 남긴다. 독립된 유효 작업을 보존할 수 있지만 필요한 단위가 남은 전체 범위를 완료로 표시하지 않는다. 적용 도중 중단은 기존 [중단과 적용](reconstruction.md#%EC%A4%91%EB%8B%A8%EA%B3%BC%20%EC%A0%81%EC%9A%A9)의 재대조를 따른다.

진행 상태는 기존 프로젝트 로컬 기록 계약을 사용하고, WIKI에는 공유할 지식과 출처를 남긴다. 이 기능을 위해 별도 상주 서버나 새로운 DB를 만들거나 도구 호출마다 전체 상태를 기록하는 안은 아니다. 이전 원문이 필요한 검사는 해시만으로 복원할 수 없으므로 보존 사본 또는 실제 접근 가능한 Git 원문이 필요하다. 자료가 정리됐거나 없으면 관련 재사용/복원 가능성도 다시 판단한다.

### 편집 충돌과 내용 모순

**파일 편집 충돌**은 같은 자료가 서로 다르게 수정된 경우다. 반영에 사용할 세 기준은 다음과 같다.

- 기준: 이번 분석을 시작할 때 보존한 WIKI 원문.
- 현재: 후보를 반영하기 직전의 WIKI 원문.
- 후보: 위 기준에 이번 보완 내용을 적용한 별도 결과.

이전 완료본과 이번 분석 시작본의 차이는 사용자 수정과 앞선 결과를 파악하는 자료다. 실제 반영의 공통 기준은 이번 후보가 출발한 원문이어야 한다. 예전 결과를 AI에게 다시 생성시켜 기준으로 쓰지 않는다.

현재 파일이 그대로여도 후보의 내용 검증은 필요하다. 분석 뒤 사람의 편집을 발견하면 이전 후보의 적용을 멈추고 현재 원문과 다시 대조한다. 수정 위치가 겹치면 해당 단위는 보존하고 조정을 요청한다. 서로 다른 부분의 변경을 병합할 수 있어도 병합 결과는 다시 검토할 후보이며, 관련 검증을 거쳐야 반영할 수 있다. 원본에 충돌 표식을 남긴 채 완료하거나 사람의 내용을 덮지 않는다. 자동 병합을 안전하게 지원할 수 없는 파일/편집 형태는 수동 검토로 보류한다.

**내용 모순**은 다른 줄이나 다른 파일이 서로 반대되는 의미를 담는 경우다. 예를 들어 요구사항에는 “보관 기간 30일”, 새 운영 문서에는 “90일”이라고 적혀 있으면 Git 병합이 성공해도 정책은 일치하지 않는다. 변경한 주장과 관련 요구사항, 계약, ADR, 코드/검사 근거를 대조하고 각각의 적용 대상과 시점을 확인해야 한다.

새 코드가 90일로 동작한다는 사실만으로 30일 정책을 폐기하지 않는다. 현재 구현, 채택 정책, 과거 결정의 차이를 근거와 함께 제시하고 정책 변경이 필요한 부분은 사용자 판단을 받는다. 의미가 같은 표현 차이는 통합할 수 있지만 근거 없는 새 주장을 보완으로 채택하지 않는다. AI 검토만으로 모든 모순을 발견했다고 보장하지 않는다. 중요한 미해결 모순과 그에 의존하는 문서의 반영/완료는 보류한다.

코드 삭제와 새 결론도 과거 ADR이나 판단 이력의 삭제 명령이 아니다. 현재 적용 상태와 대체 결정의 연결을 갱신하며 과거 근거를 유지한다. 잘못된 사실의 정정과 실제 정책 변경을 구분한다.

공개 소스는 11/23 작업에서 조회한 변경 가능한 브랜치다. 고정 커밋 기반 실행 검증이나 의존성 채택으로 기록하지 않는다. 기존 [11/10 부분 시험](../../evidence/experiments/runtime/2026-11-10_17-07-48-external-install.md)도 텍스트 병합 뒤 의미 오류가 남는 사례의 제한된 근거이며 Windows WIKI 복원 시험은 아니다.

추가 상태 대조와 기준 사본의 저장 비용은 생긴다. 반면 재사용 가능한 결과에 대한 새 분석을 생략하고 검토 범위를 좁힐 수 있다. **이 흐름의 실제 시간, 토큰 절감과 모순 탐지 성능은 아직 측정하지 않았다.** 링크/해시 검사만으로 품질 동등성을 선언하지 않는다. [완료 후 재실행의 검증 입력](../../verification/acceptance.md)을 실제 Windows 배포 경로와 AI 처리로 확인한 범위까지만 구현 완료로 인정한다.

## 비용과 구현 범위

첫 단계에서 모듈 목록, 파일 경로, Git 변경, 중복, 해시는 일반 코드로 수집하고, 필요한 자료만 AI에 준다. 의미 요약은 잃을 수 있는 정보와 근거를 함께 보존하며 원문을 지워 토큰 수만 줄이지 않는다. 문맥을 선별, 유지하는 접근은 [Anthropic의 context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)과 맞지만 우리 구조의 절감률을 입증한 것은 아니다.

로컬 기본 제공 / 전용 API 실행기 / 상주 대기열 / Obsidian 플러그인 / 벡터DB를 동시에 v1에 넣지 않는다. 현재 추천은 분석 절차 하나와 Codex 진입 하나, 필요한 수집, 상태, 보존 도구부터다. 로컬 실행 경로의 시험은 동등한 계약으로 따로 붙일 수 있게 설계한다. 현재 일정에서 기능별 예상 공수와 모델 효과는 미측정이므로 완료 날짜를 보장하지 않는다.

원문, 대화, 커밋의 명령처럼 보이는 텍스트는 분석 자료다. 실행 권한으로 해석하지 않는다. 자료 수집 범위, 외부 전송 허용, 후보 쓰기 위치를 분리하며 테스트/빌드/훅을 코드 읽기 단계에서 자동 실행하지 않는다. 클라우드 전송이 금지된 자료는 로컬 실패 때도 자동으로 전송하지 않는다.

## 배포 README

[Codex README](https://github.com/openai/codex)는 설치, 시작, 인증과 상세 안내를, [Repomix README](https://github.com/yamadashy/repomix)는 빠른 실행, 생성 결과, 자료 사용과 범위 설정을 나눠 설명한다. 여기서는 그 흐름을 참고하며 명령, 의존성, 전체 저장소 입력 방식을 그대로 채택하지 않는다. Repomix 같은 기존 수집 도구의 재사용도 후보지만 현재 필수 의존성은 아니다.

최종 README는 다음 순서의 검증된 짧은 경로를 제공한다. 지금은 요구 목록이며 동작하지 않는 설치/분석 명령을 완성된 사용법으로 제시하지 않는다.

1. 해결하는 문제와 지원 범위: WIKI 후보, 기존 문서 보존, 제외/미확인, 첫 OS/파일시스템, 도구 버전.
2. 준비물: 선택 경로의 CLI, 인증/한도, 필수 런타임. 로컬은 모델, 실행기, 자원, 라이선스/지원 조합, Obsidian은 선택.
3. 설치와 연결: 고정 배포 버전, 코드/WIKI 루트, 내부 docs, 외부 WIKI와 권한 확인. 초기 설계 파일 없이 시작.
4. 첫 분석: 사용자 모델 확인, 범위, 자료, 예산 선택, 예상 출력과 완료/미완료 의미.
5. 후보 검토와 적용: 출처, 차이, 공백 확인, 기존 원문 보호와 승인 범위.
6. 후속 변경과 중단 재개: 같은 작업 찾기, 바뀐 입력 처리, 실패한 단계와 다음 범위.
7. 갱신, 제거, 복원과 문제 해결: 인증, 지원하지 않는 모델, 메모리/한도, 경로 오류의 대응.
8. 상세 설계, 평가 근거, 선택 확장 링크. 앱/WIKI Git 연계는 관련 기능의 검증 범위대로 안내.

새 사용자 환경에서 README만으로 첫 분석, 기존 문서 연결, 한 번의 중단 재개를 재현해야 한다. 실행 명령, 도움말, 설명은 같은 계약을 따라야 하며 작성자의 체크아웃, 개인 절대 경로에 의존하면 실패다.

## 결정할 것과 다음 순서

B의 일반 명령 진입, 코드가 수행하는 모델 목록/선택, 범위 미리보기, 관련 기능별 분할은 채택했다. A의 명시 skill+공통 코드와 C의 모델 API 직접 호출은 ADR 0018에 비교 근거로 남긴다. 정확한 명령, skill 추가 여부, 구현 언어, 로컬 도입, 모델 시험 입력/합격 기준, 예산, 자동 채택, 지원 확대는 후속이다. 이번 합의를 제품 구현이나 실제 모델 시험 착수로 확대하지 않는다.

합의한 실행 방향은 ADR 0018에 반영했다. 11/09 WIKI 내용 구성, 분할 상세 복원, 출처/보존, 범위별 완료 기준을 ADR 0014에서 채택했다. 정확한 입력, 템플릿, 실제 평가 자료와 반복 수/예산은 후속 합의다. 현재 복귀할 단위와 선행 관계는 [진행표](../../development/roadmap.md)만 관리한다. 실행 방향 채택을 제품 구현 착수로 확대하지 않는다.
