# 개발 요구 검토

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 최초 작업일: 2026-11-05. 이어지는 설계, 개발 대화에서 나온 질문을 기존 주제에 연결하는 문서다. 10개 번호는 당시 요청을 찾기 위한 표식이며 별도 과제, 우선 처리 목록, 최종 요구 목록이 아니다. 이후 질문도 같은 방식으로 해당 소유 문서에 통합한다. 11/11에는 로컬/CI 분담 원칙을 채택하고 테스트 작성 절차, 품질과 지속 시험 공간을 검토했다. 각 주제의 채택, 미완료는 아래 표와 소유 문서에서 구분하며 제품 구현은 아직이다.

전체 순서는 [진행표](../../development/roadmap.md), 최종 목표와 관측 조건은 [수용 기준 — 「최종 목표 초안」](../../verification/acceptance.md), 작업 전 읽기, 협의 형식은 [문서 관리](../../README.md)가 소유한다. 날짜, 번호는 원문 식별용으로만 구별하고, 처리 순서는 기존 요구와의 의존 관계로 정한다.

## 역공학 품질과 실행 방식

11/08의 후속 질문이며 기존 3, 9, 10과 도구 지원, WIKI 저장 검토에 이어진다. 별도 우선 프로젝트를 만들지 않는다. Obsidian 검토 뒤 [WIKI 생성과 보강](reconstruction.md)에 품질, 환경, 실행 방식, 범위/재개, README 조사를 통합했다. [ADR 0018](../../decisions/knowledge/0018-reconstruction.md)의 B 기본 실행, 목록/범위 선택, 분할 원칙은 채택됐으며 제품 구현, 모델 품질, 토큰 비교는 미실행이다.

작성 기준, 자체 WIKI와 저장소 묶음의 요구는 [개발 규칙](../../development/standards.md), [모듈 자체 WIKI — 「모듈 자체의 WIKI」](../../design/module.md), [저장소 연계](../../design/sync.md)에 연결한다.

| 요청 | 보존할 내용 | 연결, 상태 |
| --- | --- | --- |
| Obsidian의 채택 이유 | private Git과 로컬 문서 연결만으로 충분한지, 편집기 이상의 실제 효용, 일반 편집기 대안, 기술 검토 근거를 비교 | [역할 비교 — 「Git만 쓸 때와의 차이」](storage.md)에 조사, 추천. 기능 확대 미채택 |
| 시험 링크 복원 | 잘못 입력된 `links.md`를 정상 연결로 되돌리고 이전 검증에 사용 | 11/06 작업에서 복원, 사용자 클릭 확인 완료. 11/08에도 당시 해시와 같음. 반복 덮어쓰기 불필요 |
| 로컬/상용 AI 품질 | 코드, 커밋 기반 문서 생성/복원/보강의 정확성, 누락, 규모, 컨텍스트, 한도, 시간, 자원, 검토 비용 비교. 기존 문서 보존과 지속 사용할 WIKI의 신뢰성을 우선 | [품질 기준과 비교](reconstruction.md) 작성. 실제 모델 차이, 비용, 합격 임계값은 미확정 |
| 실행 진입 | 설치한 작업을 명시적으로 실행하고 정해진 절차를 자동 진행. 일반 코드로 모델 목록, 선택, 범위 확인 후 AI 분석 시작 | [설치한 작업 실행](reconstruction.md)과 [실행 방식 일곱 경로](reconstruction.md). B 방향 채택, skill 입구, 정확한 명령, 품질 시험 상세는 후속 |

비교에 반영한 조건과 후속 실측에서 유지할 범위:

- 공통 배포 설계는 특정 개발 기기에 종속시키지 않는다. 로컬 실행 불가, 제한된 자원, 충분한 자원, 클라우드만 사용 등 환경별 가능한 경로와 지원 조건을 비교한다. 실제 장비는 실측 조합 하나로 사용하며 모든 환경의 동일 품질이나 무제한 실행을 전제하지 않는다.
- “로컬 실행”과 “클라우드가 로컬 보조에 위임”은 별개다. 사용자가 실행기 하나를 고르는 호환성, 실행 중 메인/보조가 결과를 주고받는 협업, 독립 초안 생성과 검토를 구분한다. 로컬 여부만으로 충분한 품질을 보장하지 않는다.
- 평가 대상은 글의 자연스러움뿐 아니라 근거 위치, 현재 구현 일치, 중요 항목 누락, 지어낸 과거 의도, 기존 문서 보존, 재실행 중복이다. 작은 작업의 벤치마크 점수를 큰 저장소의 WIKI 품질로 그대로 대체하지 않는다. 구체 측정, 합격 기준은 협의한다.
- 실행기/모델 기본값의 소유와 사용자 선택을 정한다. 외부 CLI 안내형 선택, 현재 도구 설정 상속, 지원 조합 제한, 유효성 확인을 비교한다. 예시 모델명은 설명용이며 확정된 기본 모델이 아니다. 구독 로그인과 API 과금, 인증을 구분하고, 자동 유료 전환이나 임의 모델 교체는 하지 않는다.
- 초기/후속 분석 범위, 분할 단위, 진행 기록, 한도, 네트워크, 사용자 중단 후 재개, 다음 범위 이동, 기존 후보, 원문 보호를 모든 실행 방식에서 비교한다. 스크립트의 결정적 수집/검사와 AI의 의미 분석, 문서 후보, 사람의 채택을 분리한다.
- 후보군은 현재 CLI의 skill/명시 프롬프트, 외부 launcher와 CLI 호출, 진행 상태를 저장하는 실행기, API/SDK, 로컬 실행기, 로컬 초안+클라우드 검토, 수동 packet 전달 등을 출발점으로 검토한다. 가능 여부, 중복, 지원 제약을 조사해 조정하며 모두 구현할 요구로 해석하지 않는다.
- README의 준비물은 사용자 구독, 권한, 지원 OS/경로 등 실제 필수 사항에 한정한다. 처음 사용, 기존 WIKI 연결, 증분 갱신, 중단 재개를 재현할 수 있어야 한다. 최종 문구는 구현 뒤 확정하되 사용 흐름의 요구는 설계부터 반영한다.

## 빠뜨리지 않을 세부 조건

1. **커밋과 이름**: 설계 뒤 실제 개발에 들어갈 때, 현재 구조의 재사용 부분에 프로젝트 종속 제거, 명명 등 준비 요구를 반영한 독립 기본 모듈을 먼저 만들고 커밋한다는 제안이다. 이를 시작점으로 기능별 개선, 호환성, 요구 반영을 쌓는다. 요청 시 원격에 공유된 변경도 작업 단위로 취소, 복구할 근거를 준비한다. 필드, 변수, 디렉토리, 파일, skill, config, matrix, 문서 이름을 기존 명명 기준으로 재검토한다. 시작 구성과 커밋 분할의 상세는 협의 대상이다.
2. **테스트**: 테스트 작성과 테스트 실행을 구분한다. 최초 요청은 별도 skill을 필수로 요구하지 않고 필요성을 비교하자는 것이었으며, 후속 채택은 위 표를 따른다. CI만 사용하는 경우, 로컬에서 영향 검사를 수행하고 CI로 최종 확인하는 경우, 반복 검사를 언제 줄일지 비교한다. 작은 코드 수정, 관련성 낮은 변경, 여러 모듈/공통 설정 변경의 범위를 구별하고 skill이 모든 검사를 강제하지 않게 검토한다. 하네스 자체 검사와 도입 프로젝트의 제품 테스트도 구별한다.
3. **요구사항**: 현재 자동화 여부, 갱신 조건, 시점, 범위, 관점을 확인한다. 요구, 정책, 상세 스키마/계약의 역할을 나눌지, 단일 문서/모듈/도메인/기능 분할을 쓸지 비교한다. 길이, 탐색 비용과 AGENTS, 라우팅의 누락/충돌을 함께 본다. 템플릿, 예외 형식, 역공학의 근거와 검토, 채택 단계를 포함한다.
4. **복구**: 현행 동작을 정상이라고 전제하지 않고 관측된 결함, 실제 재개를 먼저 확인한다. 유지, 국소 보강, 다른 방식의 대안을 비교하며 토큰, 복구 성공, 기록 누락을 관측한다. 사용자 표현의 '메모리 누수'가 문맥 손실인지 프로세스 메모리 증가인지 구분해 지표를 정하고, 후자는 실측 없이 있다고 단정하지 않는다.
5. **지속 비교**: runbook/디버깅, 복구, skill, 라우팅, gate 등 각 기능에서 현재/대안/추천과 이유, 부작용, 검증을 확인한다. 기존 결정과 현재 요구의 충돌을 숨기지 않는다.
6. **유지보수**: script를 포함해 같은 정보를 여러 곳에 하드코딩하지 않는다. 변경 이유, 책임이 같은 부분을 묶고 프로젝트 값, 정책을 교체하기 쉽게 한다. 중복, 장황한 반복, 무분별한 분기 추가와 동기화 실수를 줄인다. SOLID나 상속이라는 형태 자체보다 해당 언어와 실제 변경 경계에 맞는 간단한 구조를 비교한다.
7. **작업 단위**: runbook 개선이나 PASS/FAIL 처리처럼 검토 가능한 기능으로 나누고 직전 기준 커밋, 의존 상태를 식별한다. 작업 전 '계획 리뷰, 진행 내용, 확인할 것, 필요한 결정'과 필독 문서/절을 논리적 순서로 제시한다. 합의 후 해당 범위를 개발하고 관련 문서, 설정, 실행, 테스트를 함께 닫는다. 나눴을 때 기존 기능/연결이 깨지면 호환 단계를 두거나 하나의 묶음으로 조정한다.
8. **순서, 최신화**: 최신 설계와 의존 관계에 맞춰 진행한다. 오래된 전제, 누락 연결을 발견하면 소유 문서와 직접 영향받는 문서를 함께 고치고 복귀 상태를 남긴다. 필독 안내를 위해 모든 설계 문서를 매번 읽게 하지 않는다.
9. **AI 초기화**: 설치만으로 프로젝트의 의미, 이유가 복원된다고 가정하지 않는다. AI가 현재 코드, 테스트, 허용한 커밋/대화, 기존 문서를 근거로 후보를 만들고 검토, 채택하는 진입을 설계한다. 최초 설치 뒤뿐 아니라 사용자가 나중에 요청해도 같은 기준으로 동작해야 한다.
10. **완료 상태**: 조건부 하네스의 결함, 불필요한 연결을 정리하고 기능, 동기화를 검증한다. 빈 문서와 기존 WIKI 모두에서 필요한 범위만 생성/보완하며 중복, 원문 유실을 막는다. 요구 추출, 템플릿, 분할, 중요 항목 점검을 정하고, 전체 분석의 토큰 부담을 제한한다. 한 진입점에서 범위를 정하고 여러 묶음을 이어갈지, 재개를 별도 명령으로 둘지 비교한다. 이 목록은 추후 근거로 보완할 최종 목표 초안이다.

## 먼저 분명히 할 점

### 작은 작업과 커밋

작업을 작게 나누는 사용자 원칙을 적용한다. 분할 기준은 파일 수가 아니라 **한 변경의 동작, 연결, 검증을 함께 확인할 수 있는가**다. 규칙만 바꾸고 소비 script를 나중에 고치는 식으로 중간 상태를 깨뜨리지 않는다. 연관 테스트는 같은 변경과 함께 검토한다. Google의 작은 변경 지침도 독립적으로 이해 가능한 변경, 관련 테스트, 중간 빌드 유지와 큰 이름 변경의 분리를 설명한다. 이 근거를 모든 사소한 편집의 새 테스트 의무로 확대하지 않는다. [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)

| 분할안 | 장점 | 단점, 판단 |
| --- | --- | --- |
| 전체 개편을 한 묶음 | 중간 호환 단계가 적음 | 검토, 원인 추적, 되돌림이 커져 비추천 |
| 파일/계층별로 극소 분할 | 각 diff는 작음 | 선언과 사용처가 갈라지고 중간 동작이 깨지기 쉬움 |
| 기능, 책임별로 관련 연결을 함께 묶음 | 사용자 검토, 검증, 복구 단위가 선명 | 의존 기능과 회귀 검사를 함께 설계해야 함. 사용자 요구에 맞는 추천 |

이름 변경은 대상, 기존 이름, 새 이름, 참조 경로, 외부 사용 여부를 먼저 대조한다. 큰 기계적 변경과 동작 변경을 구분하되 참조, 라우팅, 문서가 깨지는 중간 커밋은 만들지 않는다. 이미 짧고 의미가 맞는 이름까지 교체하는 목록은 확정하지 않았다.

사용자는 **독립 기본 모듈의 세팅 커밋 → 설계에 따른 기능별 발전**을 제안했다. 앞선 답변이 앱 전체 복사를 경계하는 데 치우쳐 이 의도를 충분히 다루지 못했다. 합의한 최소 동작과 연결을 검증한 기본 모듈부터 시작하는 B 방향을 11/05에 채택했다. 시작점의 구성, 완료 조건은 [기본 모듈 — 「기본 모듈의 시작점」](../../design/module.md), 세 대안과 이유는 [ADR 0009 — 「기본 모듈의 시작점」](../../decisions/architecture/0009-repositories.md)가 소유한다. 시험용 입력, 상태인 fixture와 모듈 자체는 구분한다.

원격에 공유한 작업의 취소는 새 되돌림 커밋을 만드는 `revert`가 기존 이력을 보존하는 후보이며, 원격 이력을 강제 재작성하는 것과 구별한다. 후속 변경의 의존, 충돌 때문에 어느 커밋이나 즉시 독립 복구된다고 보장할 수 없다. 기준, 변경 묶음, 의존, 실제 검증을 남기고 필요한 조합으로 복구한다. 두 원격의 갱신은 하나의 Git 원자적 작업이 아니므로 한쪽 성공 상태도 처리해야 한다. [Git revert](https://git-scm.com/docs/git-revert), [Git push](https://git-scm.com/docs/git-push)

### REQUIREMENTS의 현재 동작

현재 [기준 구현의 관측 (AGENTS)](../architecture/baseline-audit.md)의 규칙은 요구/가정 변경 시 이유와 갱신 여부를 확인하고 수락한 내용을 반영하는 방식이다. 기존 요구 안의 버그 수정, 리팩터링, 문서 정리는 REQUIREMENTS 갱신 없이 가능하다. 따라서 매 개발 요청마다 내용을 자동 추출, 추가하는 계약이 아니다. 지침이 존재하는 사실을 실제 모든 요청에서 정확히 갱신됐다는 실행 증거로 보지 않는다.

11/08에 [상세 복원 목표 — 「복원할 깊이와 완료 목표」](../../design/knowledge/wiki.md)와 [문서 분할, 템플릿, 라우팅](../../design/knowledge/documents.md)의 비교 초안을 작성했다. 요청 3, 9, 10은 같은 내용, 분석 설계 축으로 연결한다. 11/09 공통 요구/색인, 기능별 상세, 위치표 구성, 범위별 상세 복원, 완료 기준을 채택했다. 상세 필드/템플릿과 제품 구현, 검증은 후속이다.

### 설치와 AI 분석

ADR 0010의 제공 수단은 **11/11 Git 릴리스 + Python 도구로 채택했으며 제품은 미구현**이다. 설치는 실행 파일, 지침, 설정의 배치와 연결 확인이고, 프로젝트 의미를 분석해 WIKI 후보를 만드는 것은 별도 책임이다. 설치 직후 숨은 AI 호출, 전체 이력 분석을 시작하지 않는다. 후속 협의에서 AI 분석 실행의 B 방향을 채택했으며 정확한 명령, 재개 계약은 남아 있다.

스크립트가 Codex를 호출하도록 만들 수는 있다. OpenAI 공식 문서는 `codex exec`의 script 실행과 특정 세션의 `resume`을 지원한다. 이는 AI 호출 수단의 존재이며 분석 누락 방지, 원문 보호, 중단 재개가 제품에 구현됐다는 뜻은 아니다. 현재 설치 CLI와의 버전, 권한, 인증 검증 및 실제 모델 실행은 하지 않았다. [OpenAI non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)

진입 방식의 비교와 채택은 [실행 검토 — 「실행 방식」](reconstruction.md), [ADR 0018](../../decisions/knowledge/0018-reconstruction.md)이 소유한다. B의 실행 코드가 진행을 관리하고 필요한 단계에서 AI를 호출하는 방향이며, 정확한 명령, skill 추가, 구현, 효과 검증은 후속이다. 한 명령으로 시작하는 사용성과 무제한 한 번에 완료하는 보장은 구별한다. 사용자 개입, 계정 한도, 중단이 있으면 실제 완료 범위와 남은 범위를 보존해야 한다.

### 하드코딩과 최종 보장

프로젝트 이름, 경로, 검사 선택, 변경 가능한 정책의 중복 하드코딩을 제거하는 요구는 기존 이식 목표와 맞는다. 다만 모든 문자열을 설정으로 빼거나 단순 script에 상속 계층을 만드는 방식까지 확정하지 않는다. 도구가 정한 고정 식별자와 프로젝트마다 달라지는 값은 구별하며, 추상화는 실제 교체, 검증 범위를 줄이는지로 판단할 후보를 제시한다.

'중요한 내용 누락 없음'을 코드와 제한된 기록에서 모든 의도를 추론할 수 있다는 보장으로 구현할 수는 없다. [최종 목표 초안](../../verification/acceptance.md)은 분석한 범위, 출처, 미확인, 충돌을 드러내고 필수 항목이 미해결이면 완료하지 않는 형태로 구체화했다. 범위별 상세 복원, 미확인 표시, 완료 기준은 ADR 0014의 채택을 따르며 구체 필드, 시험 입력은 후속 명세다. 토큰 비용, 복구 성공률, 누락률은 미측정이다.

## 현재 확인과 남은 검토

요청 1, 5, 6, 7, 8의 운영 원칙은 프로필, 문서 관리에 통합했다. 기본 모듈 세팅, 작업별 PR 연계, AI 분석 실행과 WIKI 내용/분할, 로컬/CI 분담, 조건부 작성 skill 배치를 채택했다. 후속 명세에서는 원격 복구 수단과 테스트 작성 연결의 입출력, 검사 명령과 결과 재사용 조건을 정한다. 문서의 세부 입력과 템플릿, 복구 기록의 저장 및 조회 수단, AI 분석 인터페이스도 구체화해야 한다. 제품 구현은 아직 없다. 복구 B와 SQLite의 원칙, 적용 경계는 합의했고 실제 시험은 남아 있다.

WIKI의 내용/범위, 문서 구조와 실행/재개는 검토 가능한 단위로 다룬다. 기본 모듈의 시작점을 논의했다고 설계와 검증을 생략하지 않는다. 구현 순서는 [개발 순서](../../development/roadmap.md)가 소유한다.
