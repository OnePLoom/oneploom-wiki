# 조건부 하네스의 차별성과 기술 대안

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

- 기준일: 2026-10-27. 현재 구현은 [구조 감사](baseline-audit.md), 향후 구상은 [추천 구조](../../design/architecture.md)와 ADR 0001~0006을 기준으로 구분했다.
- 상태: 10/27 본문은 당시 조사와 추천이다. 11/18과 11/20 후속 절의 채택/관측은 해당 절과 연결한 ADR/사례를 따르며 과거 평가 전체의 채택으로 확대하지 않는다.
- 검토 상태와 현재 제공 범위는 [개발 순서](../../development/roadmap.md)와 [ADR 0007](../../decisions/architecture/0007-release-scope.md)을 따른다.
- 2026-11-18 보충: [로컬 MCP의 추가 가치](../../explanations/mcp.md)는 현재 사용자 질문에 대한 후속 평가다. 아래 10/27의 관측/추천을 새 구현 결과로 바꾸지 않는다.
- 공식 문서, 공개 저장소와 원 연구를 우선했다. 공개 기능의 존재와 실제 설치/성능 검증을 구분한다. 특허 신규성 조사나 시장 전체 통계가 아니다.

## 1. 먼저 내릴 판단

**구성 원리는 이미 알려진 접근이다. 실제 가치는 필요한 문제를 좁혀 해결하고 보존, 검증, 재개와 이식 결과를 입증하는 데 있다. 현재 실증만으로 범용 제품 완성을 주장하지 않는다.**

| 질문 | 현재 판단 | 판단의 이유 |
| --- | --- | --- |
| 필요한 지침만 읽고 hook, skill, 상태 문서를 조합하는 발상이 드문가 | 드물다고 보기 어렵다 | 주요 코딩 도구가 비슷한 구성요소를 공식 제공한다 |
| 클라우드와 로컬 모델의 역할 분배가 독창적인가 | 그 자체의 독창성은 낮다 | 역할별 모델 선택과 계획/편집 분리는 기존 도구에도 있다 |
| 코드에서 WIKI, 문서 후보를 만드는 것이 새로운가 | 기능 자체는 이미 존재한다 | DeepWiki, 기존 프로젝트를 지원하는 명세 도구와 겹친다 |
| 현재 구현에 기술적으로 설명할 만한 고민이 있는가 | 있다 | 검증 범위, 잘못된 PASS 재사용, 중단 후 재개, 문서 소유권이라는 실제 문제를 다룬다 |
| 현재 실효성이 증명됐는가 | 아직 아니다 | 격리 재현은 있으나 수정 후 결과, 실제 이식, 모델 사용량, 복구율 자료가 부족하다 |
| 백엔드 신입 지원의 주력 사례가 될 수 있는가 | 조건부로 가능하다 | 재현 가능한 도구와 백엔드 성과가 연결되어야 한다. 경력, 학력을 상쇄하거나 합격을 보장한다고 판단할 자료는 없다 |

정확한 파일 배치가 다른 저장소에 없다는 사실은 중요한 차별점이 아니다. **어떤 실패를 왜 문제로 정했고, 기존 도구로 어디까지 해결되며, 추가한 코드가 무엇을 개선했는지**가 더 강한 설명이다. 반대로 필요 없는 자동화를 제거하거나 로컬 AI를 도입하지 않은 결정도 근거가 있으면 설계 역량을 보여준다.

새 모델이나 알고리즘을 발명했다는 주장보다, AI 개발 절차를 검증 가능하게 운영하는 소프트웨어 엔지니어링 문제로 평가한다.

## 2. 공개 도구와 얼마나 겹치는가

아래의 ‘겹침’은 공식 자료로 확인한 기능, 방법의 공통점이다. 해당 도구가 현재 발견한 모든 반례를 해결한다거나, 해결하지 못한다는 실행 판정은 아니다.

| 현재, 제안 요소 | 공개된 대응 사례 | 이 프로젝트에 남는 과제 |
| --- | --- | --- |
| AGENTS 진입 후 필요한 skill, 자료만 읽기 | Codex는 skill 메타데이터 → 선택된 본문 → 필요한 참조/스크립트의 점진적 로딩을 설명한다. [공식 문서](https://learn.chatgpt.com/docs/customization/overview) | 조건부 분류가 실제 읽기, 작업 비용을 줄이는지, 누락 없이 작동하는지 확인 |
| compact, 시작, 종료에 hook 연결 | Codex는 여러 lifecycle hook과 신뢰, 출력 계약을 제공한다. [hooks](https://learn.chatgpt.com/docs/hooks) | 설치 버전에서의 실제 발동, 경고와 모델 입력의 차이, 중단 시 저장 범위 확인 |
| 파일로 작업 상태를 이어받기 | Anthropic은 초기화, 점진적 작업, 진행 파일, 검증을 장기 작업 방법으로 제시한다. Cline도 Memory Bank 방법을 문서화했다. [Anthropic](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents), [Cline](https://docs.cline.bot/best-practices/memory-bank) | 상태가 오래됐거나 기록 도중 끊겼을 때 잘못된 완료를 피하고 재개할 수 있는지 |
| 필요한 코드 맥락 선별 | Aider는 토큰 예산 안에서 관련도가 높은 저장소 구조를 선택한다. [repo map](https://aider.chat/docs/repomap.html) | 우리 규칙, 업무 상태, 검증 근거에 필요한 최소 정보의 측정 |
| 모델별 역할 분담, 선택 모드 | Continue는 역할별 모델 선택, Aider는 계획/편집 모델 분리를 제공한다. [Continue](https://docs.continue.dev/customize/model-roles/00-intro), [Aider](https://aider.chat/docs/usage/modes.html) | 로컬로 옮긴 뒤 재검토까지 포함한 순절감과 실패 복귀의 일관성 |
| 명세, 계획, 작업, 검증 기록을 묶기 | Spec Kit은 재사용 절차, 템플릿, 확장, workflow를, OpenSpec은 변경별 명세와 기존 프로젝트 적용을 제공한다. [Spec Kit](https://github.com/github/spec-kit), [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 문서를 더 만드는 대신 현재 자산과 충돌 없이 필요한 계약만 연결하기 |
| 원래 실패를 다시 검증하기 | Spec Kit의 버그 수정 절차도 원래 재현을 실행하지 않은 테스트 통과를 충분한 근거로 보지 않는다. [버그 수정 가이드](https://github.github.io/spec-kit/guides/bugfix.html) | 이 원칙을 실제 실행 식별, 결과 판정, 잘못된 재시도 거부로 보장하는지 비교 |
| 코드 기반 WIKI 생성 | Cognition은 DeepWiki를 저장소 이해, 문서, 검색 도구로 공개했다. [발표](https://cognition.com/blog/deepwiki) | 현재 동작과 채택 정책의 구분, 근거 없는 과거 결정 생성 방지, 기존 편집 보존 |
| 실행 상태 저장, 재개 | LangGraph도 thread 단위 checkpoint 등 지속 상태 기능을 제공한다. [persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 별도 오케스트레이터 도입의 비용이 이 프로젝트의 작은 연결 코드보다 유리한지 |
| 입력에 따른 검사 결과 재사용 | Gradle은 입력과 출력 계약으로 캐시를 관리하며 입력 누락의 잘못된 재사용을 경고한다. [build cache](https://docs.gradle.org/current/userguide/build_cache.html) | 빌드 도구 위에 불완전한 별도 PASS 캐시를 중복 구현할 이유가 있는지 |

**검증 절차, WIKI, 역할 분담, 복구 파일 각각을 독자 발명처럼 소개하면 설득력이 떨어진다.** 특히 최신 Spec Kit은 단순한 명세 템플릿 묶음으로만 비교하면 안 된다. 현재 공식 README에는 선택적 버그 수정 절차와 품질 게이트, workflow, 확장도 있다.

반대로 구성요소가 흔하다고 프로젝트 가치가 사라지는 것은 아니다. 지원할 프로젝트의 제약을 정하고, 최소한의 연결을 구현하며, 오류를 재현하고, 도입 비용을 측정하는 일은 별도의 엔지니어링 작업이다. 지금은 ‘다른 도구에는 없는 기능’보다 **‘지원 범위에서 확인한 결과와 도입 비용’**을 주장하는 편이 정직하다.

## 3. 효과를 낙관하면 안 되는 연구 근거

### 지침을 늘리거나 WIKI를 만들었다고 자동으로 좋아지지는 않는다

관련 원 연구의 결과는 하나로 모이지 않는다.

| 연구 | 확인한 결과 | 그대로 일반화하면 안 되는 이유 |
| --- | --- | --- |
| Lulla 외, 2026-01 | 10개 저장소, 124개 PR의 Codex 비교에서 실행 시간, 출력 토큰 감소를 보고 | 작은 변경 위주이며 완전한 의미적 정확성 평가는 연구 범위 밖이다. 출력 토큰 감소를 전체 비용, 품질 개선으로 바꾸어 말하면 안 된다. [본문](https://arxiv.org/html/2601.20404v1) |
| Gloaguen 외, 2026-02 | 여러 agent에서 자동 생성한 맥락 파일이 평균 비용을 늘리고 일부 성공률을 낮췄으며, 사람이 작성한 파일은 다른 효과를 보임 | Python 중심 과제, 당시 모델, 평가 방법의 결과다. 모든 AGENTS나 조건부 하네스가 나쁘다는 뜻은 아니다. [본문](https://arxiv.org/html/2602.11988v1) |
| Khatri, 2026-07 | 3개 저장소에서 지침 없음, 상시 지침, 선택적 WIKI를 비교해 정확성 차이를 뚜렷하게 확인하지 못함 | 표본이 작고 WIKI 내용량, 주입 방식도 일부 다르다. 작은 효과나 장기 재개 효과까지 부정하지 않는다. [본문](https://arxiv.org/html/2607.27250v1) |

이 자료들은 공개된 연구 보고이며 동일한 실험의 반복이 아니다. **이 프로젝트의 장기 복구, 검증 계약 효과는 직접 측정해야 한다.** 유리한 논문 하나를 골라 ‘토큰 절감이 증명된 구조’라고 쓰거나 불리한 논문으로 전부 폐기하는 결론은 부적절하다.

설계상 함의는 짧은 진입 규칙, 필요할 때만 읽는 프로젝트 지식, 중복 문서 감소, 실제 사용량 비교다. 다만 선택적 로딩도 만능은 아니므로 지식을 잘못 선택하거나 필요한 검사를 누락하는 비용을 함께 본다.

### 체감 속도와 실제 생산성을 분리해야 한다

METR는 2025년 실험에서 특정 숙련 개발자, 도구 조건의 작업 지연을 보고했지만, 2026년 후속 보고에서는 도구 변화와 참가자, 과제 선택 편향 때문에 현재 효과의 크기를 신뢰하기 어렵다고 설명했다. 오래된 결과로 현재 AI가 항상 느리다고 말할 수도 없다. 이 프로젝트에서는 실제 작업 시간, 검토, 재작업 시간, 완료 품질을 함께 기록하는 근거로 사용한다. [METR 후속 보고](https://metr.org/blog/2026-02-24-uplift-update/)

DORA 2025 공식 요약도 AI 효과를 기존 개발 체계의 강점, 약점과 연결한다. 조직 수준 연구를 개인 프로젝트의 개선율로 옮길 수는 없지만, 모델 추가만으로 검증, 운영 문제가 해결된다고 가정하지 말아야 한다는 방향은 일치한다. [DORA 요약](https://dora.dev/research/2025/dora-report/)

Stack Overflow 2026 조사에서 해당 문항 응답자 14,304명 중 48.0%는 쉽게 검증할 수 있을 때 AI 결과를 신뢰한다고 답했다. 이는 검증 가능성의 중요성을 보여주는 자기보고 자료이지, 시장 전체나 이 도구의 효과를 입증하는 통계는 아니다. 출처: Stack Exchange Inc., ODbL 1.0. [원 데이터](https://survey.stackoverflow.co/2026/ai/data/ai-trust)

## 4. 현재 작업에서 실제로 남길 가치가 있는 문제

### 이미 근거가 있는 부분

| 문제 | 확보한 근거 | 아직 주장할 수 없는 것 |
| --- | --- | --- |
| 원래 API 검증이 계속 실패하는데 다른 범위 retry가 PASS | E-012의 격리 stub 재현, 실행 기록 | 실제 제품 오판 발생률, 수정 후 방지율 |
| 검증 도구, 의존 모듈 변경 뒤 과거 PASS 재사용 | E-005의 격리 재현과 의존 선언 확인 | 모든 입력을 완전하게 추적했다는 보장 |
| 계획 산출과 실제 실행 결과의 혼동 | E-007의 출력, 분기 관찰 | 이 상태가 실제 사용자에게 초래한 피해 규모 |
| 사용량 제한 전에 최신 의미 상태 저장이 안 될 가능성 | E-011의 사용자 보고, 현재 연결 부재 확인 | quota 감지 자동화나 실제 hook 복구율 |
| 프로젝트 전용 값과 공통 로직의 결합 | E-005 및 현행 파일 분석 | 다른 실제 프로젝트에서의 설치 시간, 무수정 이식 |

상세 증거와 한계는 [문제 대장](../../evidence/issues.md)에 있다. 현재의 테스트 통과 개수는 이 표의 빈칸을 채우지 않는다.

2026-10-27 재개 요청에는 사용량 경고 뒤 제한으로 조사가 중단된 대화 기록이 포함됐다. 진행 중 active는 있었지만 최종 비교, 계획 문서는 완료 전이었다. **사용자 제공 중단 기록**으로 남기며, quota API나 hook 실행 원시 로그를 확보한 것으로 취급하지 않는다. 이 경험은 복구 설계의 실제 동기다.

### 효과를 판단하기 위해 필요한 검증

자기 도구에 만든 버그를 고치는 것만으로는 외부 사용 가치가 약하다. 다음 연결이 필요하다.

1. AI가 여러 단계 작업 중 검사 범위, 실패 상태를 혼동할 수 있다는 일반 문제를 정의한다.
2. 현재 도구에서 발견한 반례와 정상 대조군을 고정한다.
3. 기본 Codex + 짧은 지침 + 프로젝트 검증 명령으로도 충분한지 비교한다.
4. 부족한 부분에만 코드를 추가하고, 다른 실제 프로젝트에서도 같은 보장과 비용을 확인한다.
5. 그 모듈을 사용한 성능 개선, 분산 처리 작업의 결과를 함께 보여준다.

기존 도구와 대조해서 추가 이득이 없다면 모듈을 줄여야 한다. 설계가 이미 진행됐다는 이유는 계속 개발할 근거가 아니다.

## 5. 추가 기술의 채택 기준

로컬 MCP의 가치는 도구 이름이 아니라 해결한 문제와 검증의 깊이로 판단한다. 팀원마다 다른 WIKI 위치, 등록 범위 밖 접근 거부, 원문 변경 보호, 응답 유실 뒤 중복 쓰기 방지 등을 검증할 수 있다. 직접 접근으로 같은 필요를 더 간단히 해결할 수 있는지도 비교한다.

11/20~22의 조회 비용/누락 사례에서는 개선 후보의 품질과 비용을 함께 검증했다. 짧은 값 전달 성공과 별개로 품질 미충족과 비용 부담이 남아 직접 접근 우선/MCP 후속으로 결정했다. [실제 비교](../../evidence/cases/mcp-cost.md)에 실패한 가설, 대안과 남은 한계를 보존한다.

## 6. 추천 방향과 다른 선택지

| 안 | 내용 | 장점 | 단점, 적합한 조건 |
| --- | --- | --- | --- |
| A. 기존 도구 조합 | Codex 기본 기능, 짧은 지침, 프로젝트 CI와 명세 도구를 조합하고 개별 프로젝트 개발에 집중 | 구현, 유지 비용이 가장 작고 도입이 빠름 | 독립 모듈 기여는 작음. 시간이 부족하거나 아래 B의 추가 이득이 없을 때 적합 |
| B. 작은 재사용 모듈 | 기존 도구 위에 필요한 검증 기록, 재개, 프로젝트 초기화/문서 근거 연결만 구현 | 현재 반례와 필수 이식 목표를 실제 작업으로 연결 가능 | 연결 코드도 테스트, 설치와 업데이트 책임이 생김. 지원 범위를 좁혀야 함 |
| C. 범용 오케스트레이터 | 여러 클라우드, 로컬 모델, 자동 역할 배치, 다양한 언어, 프로젝트를 한 번에 지원 | 장기 확장 가능성, 폭넓은 기능 시연 | 조합별 검증과 운영 비용이 큼. 첫 배포의 일정과 검증 범위를 크게 늘림 |

**B를 추천한다.** 다만 ‘직접 다 만들기’가 전제는 아니다. 기존 기능으로 충족되는 책임은 A의 방식을 사용하고, 확인된 차이만 B로 남긴다. 정해진 기간 안에 이득을 설명할 수 없으면 A로 축소한다. C는 후속 구상으로 보존한다.

첫 출시의 설명은 다음 정도가 적합하다.

> 기존 Java/Spring 프로젝트에 붙여, AI 작업의 검증 이력과 중단 상태를 이어가고 코드, 문서 근거를 필요한 때 확인하는 개발 보조 모듈.

이는 임시 설명이며 제품명이나 달성한 성과가 아니다. ‘모든 프로젝트 자동 분석’, ‘완전 자율’, ‘무제한 컨텍스트’, ‘오류 없는 AI’는 지원 약속에 넣지 않는다.

## 7. 현재와 수정 후보의 구조

현재 구조와 책임별 변경표는 [구조](../../design/architecture.md), 원본/적용본과 배포, 보존은 [모듈](../../design/README.md)이 소유한다. 초기 지원 후보는 Codex, WSL/Linux, Java/Gradle이며 범용 지원 실증은 없다. 아래에는 이 평가에서 비교한 문서 복원 대안을 남긴다.

### WIKI와 문서 복원 방식의 세 대안

| 안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 1. 전체 자동 생성 | 코드, 이력으로 모든 요구사항, ADR, WIKI를 채움 | 초기 분량과 시연 속도 | 없는 의도 생성, 중복, 오래된 정보, 검토 비용 위험 |
| 2. 근거 기반 후보 + 검토 | 기존 문서를 보존하고 선택 기능의 부족한 설명만 근거와 함께 작성 | 필요한 범위에서 정확성과 편집 보존 확인 가능 | 검토가 필요하며 모든 문서를 즉시 채우지는 못함 |
| 3. 기존 문서 색인만 | 현재 문서, 코드 위치를 연결 | 가장 작고 사실 추정이 적음 | 문서가 빈 프로젝트의 설명 복원은 부족 |

**2를 추천하고 3의 색인을 먼저 구현한다.** 첫 이식에서는 프로젝트의 실행, 검증 경로와 대표 기능 하나의 흐름만 복원한다. 자료마다 기준 revision과 근거 위치를 남기고, 현재 코드 동작, 사용자가 확정한 정책, 추정을 구분한다. 근거 없는 과거 선택 이유는 ‘확인 불가’로 둔다.

재실행 시 기존 사람이 편집한 문서를 덮어쓰지 않고 차이를 제안한다. 코드가 바뀌면 영향받은 주장에 재확인 필요를 표시한다. 모든 코드 변경에 전체 WIKI를 재생성하거나 매 요청마다 전부 읽히지 않는다. 이 방식의 세부 파일 계약은 [ADR 0004](../../decisions/architecture/0004-portability.md)의 후속이다.

프로젝트 WIKI에는 해당 제품의 개발 지식을 담는다. 공식 문서의 기존 위치를 우선하고 같은 요구사항을 이중 소유하지 않는다.

## 8. 검증할 경계와 지표

실패 범위 유실, 빈 검사, 계획 성공 오인, 중단, 손상, 다른 작업 상태 혼입, hook 미지원, 프로젝트 예외 누출, 문서 충돌, 기존 편집 보존을 확인해야 한다. 기대 동작과 측정 기준은 [수용 기준과 평가 기준](../../verification/acceptance.md)에 통합했다. 이 문서가 별도의 평가 절차를 만들지 않는다.

기본 Codex/프로젝트 검사, 현재 하네스, 수정 기본 구성, 선택 로컬의 비교 목적을 분리한다. 기존 반례 수정만으로 일반 생산성 우위를 주장하지 않고 모든 시도의 비용과 검증된 완료 수를 함께 본다. 예산, 반복 수는 실행 전 정하고 실제 결과를 남긴다.

이 모듈을 사용해 백엔드 개선을 수행한 사실과 개선이 하네스 때문에 가능했다는 인과 주장은 다르다. 모듈 밖 명령까지 통제하거나 hash로 악의적 위조를 막는다고 주장하지 않는다. 기존 CI와 의미 검토의 역할도 남는다.

## 10. 현재 우선순위

첫 제공의 필수 기능과 보존/복구/검증을 먼저 완성한다. 로컬 AI는 품질, 추가 검토 비용과 실제 완료 비용을 비교할 선택 실험으로 남기며, 이름만으로 도입을 확정하지 않는다. 현재 선택과 다음 구현은 [개발 순서](../../development/roadmap.md)와 [첫 범위](../../decisions/architecture/0007-release-scope.md)가 소유한다.
