# 명령 등록 도구와 프로젝트 공유 범위

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

2026-11-23 조사와 채택 근거다. **명령 등록용 wheel은 공식 Release에서 제공하고 적용 프로젝트 Git에는 기본 포함하지 않는다.** wheel은 Python 프로그램을 설치할 때 사용하는 배포 파일이다. 표준 wheel 등록, Git Release + Python 배포와 프로젝트 안의 하네스 실행은 이미 채택한 범위이며 이번에 되돌리는 대상이 아니다. 전체 정리 요청의 조건부 위임에 따라 재평가한 B안을 채택했다. [ADR 0023 — 「첫 준비 자료의 배포 결정」](../../decisions/runtime/0023-command-registration.md)이 결정 원본이며 제품 구현 결과는 아니다.

## 질문과 판단

사용자는 외부 라이브러리 설치본처럼 명령 등록 도구도 프로젝트 Git 밖에서 관리하는 것이 일반적인지, 실제 유사 도구의 방식과 현재 요구를 다시 대조하도록 요청했다.

조사 결과, **공식 배포 자료에서 사용자별로 시작 명령을 준비하고, 프로젝트에는 팀이 함께 사용할 설정과 생성된 소스를 공유하는 안을 추천한다.** OnepLoom의 wheel은 공식 Release에 포함하되 적용 프로젝트마다 복사하지 않는 것이다. 설치 프로그램을 Git에 반드시 넣어야 한다는 근거는 부족했다. 반대로 모든 준비 파일을 Git에서 빼야 한다는 규칙도 없다. 아래 Wrapper 사례처럼 작은 실행 준비 파일을 의도적으로 공유하는 방식이 존재한다.

이 판단은 공개된 사용 흐름과 구현을 우리 요구에 대입한 설계 추천이다. 기업 전체의 사용 비율 조사, OnepLoom의 설치 성공이나 성능 측정 결과는 아니다. 현재 stable/main 문서는 변할 수 있으며 고정 커밋의 실행 재현을 이번에 수행하지 않았다.

## Git에서 구분할 파일

여기서 Git은 **OnepLoom을 적용하는 사용자 프로젝트의 저장소**를 뜻한다. OnepLoom 개발 저장소의 자체 소스 관리, GitHub Release의 배포 파일과는 구분한다.

| 파일의 역할 | 실제 예 | 우리 설계에서의 위치와 공유 판단 |
| --- | --- | --- |
| 설치한 외부 프로그램과 의존성 | 가상환경, node_modules, 실행 파일과 캐시 | 사용자 환경에서 준비. 프로젝트 Git에 설치본을 기본 포함하지 않음 |
| 설치할 프로그램의 배포 파일 | wheel, 설치용 ZIP | 공식 Release에서 제공. 적용 프로젝트 Git에 기본 포함하지 않음 |
| 팀이 편집하고 함께 사용할 소스와 설정 | 프로젝트용 skill, script, 규칙, 공통 연결 설정 | 기존 결정대로 프로젝트에 두고 팀 공유 권장. 사용자의 기존 추적 정책 보존 |
| 버전과 설치 출처의 기준 | 도구 목록, 잠금 파일, 설치 기준 | 비밀 없는 필요한 기준만 공유. 기준을 공유하는 것과 설치본을 커밋하는 것은 다름 |
| 기기별 값과 실행 상태 | WIKI 절대 경로, 권한 선택, active, DB | 기존 `.harness/` 로컬 영역. 다른 팀원의 값을 Git으로 전달하지 않음 |

[npm의 package-lock 설명](https://docs.npmjs.com/files/package-lock.json/)도 의존성의 설치 상태를 재현할 정보를 저장소에 남기는 것과 node_modules 자체를 커밋하는 것을 구분한다. 다만 OnepLoom의 프로젝트용 script는 사용자가 직접 수정하고 갱신 비교할 소스이므로, 전부를 일반 외부 라이브러리 설치본으로 분류해 제외하면 기존 요구와 어긋난다.

## 실제 도구의 공식 사용 방식

| 사례 | 프로젝트에서 공유하는 것 | 설치본 또는 준비 자료의 처리 | 우리에게 가까운 부분과 차이 |
| --- | --- | --- | --- |
| GitHub Spec Kit | `.specify/`의 규칙, 템플릿, script와 AI 도구 연결 파일. 기기별 상태는 별도 제외 | Specify CLI를 설치한 뒤 프로젝트마다 init. CLI 설치와 프로젝트 생성물을 구분 | AI 작업 구조를 프로젝트에 이식한다는 점에서 가장 가까움. OnepLoom이 같은 패키지 관리자나 기능을 채택한다는 뜻은 아님 |
| Copier | 생성된 프로젝트와 갱신에 사용하는 답변/출처 기록 | Copier CLI를 pipx 또는 uv 등으로 별도 준비하고 템플릿을 적용 | 설치 프로그램과 이후 편집할 결과물을 분리. 갱신에도 충돌이 발생할 수 있어 자동 무충돌의 근거는 아님 |
| Husky | `.husky/pre-commit` 같은 팀 hook과 package.json의 준비 명령 | npm 개발 의존성으로 설치. 내부 hook 연결 파일은 로컬에서 생성 | 사람이 관리할 hook과 도구가 준비하는 파일을 구분. Node를 우리 필수 준비물로 추가하지 않음 |
| pre-commit | `.pre-commit-config.yaml`의 hook/버전 선택 | CLI와 hook 환경을 따로 준비하고 `.git/hooks`에 로컬 연결 설치 | 팀 정책은 공유하고 실행 연결은 각 작업 사본에서 준비. Git clone만으로 hook 연결이 끝나지는 않음 |
| Microsoft .NET local tools | `.config/dotnet-tools.json`의 도구/버전 목록 | 팀원이 restore. 실제 패키지는 NuGet 전역 패키지 위치에 저장 | 프로젝트 전용 도구라도 실행 파일 자체가 프로젝트 Git에 있어야 하는 것은 아님 |
| Apache Maven Wrapper | wrapper script와 버전/주소 설정 | 현재 기본 only-script는 wrapper JAR 없이 Maven을 받아 실행. bin 선택은 작은 JAR 포함 | 원격 준비 코드만 공유하는 대안의 실제 사례. 네트워크/다운로드 검사가 필요하며 우리 첫 범위에 자동 추가하지 않음 |
| Gradle Wrapper | wrapper script, 설정과 작은 wrapper JAR | JAR은 Git 공유를 권장하지만 Gradle 배포 전체는 사용자 영역에서 받아 재사용 | 바이너리를 공유하는 유효한 예외. 우리 wheel의 기본 동봉이 최선이라는 단독 근거는 되지 않음 |
| uv / pipx의 CLI 설치 | 적용 프로젝트에 프로그램 설치본을 남길 필요 없음 | 도구별 격리 환경을 사용자 영역에 준비하고 명령 노출. uvx는 캐시를 쓰는 일회 실행도 제공 | 한 사용자 환경의 명령을 여러 프로젝트에서 재사용하는 구현 참고. 첫 배포의 추가 의존성으로 채택하지 않음 |

표의 공식 근거는 다음과 같다.

- **Spec Kit:** [설치](https://github.github.io/spec-kit/installation.html), [초기화와 공유/로컬 구분](https://github.github.io/spec-kit/overview/core.html). CLI 설치 후 init이 프로젝트용 script와 연결을 만든다. 공식 문서는 여러 설치 수단을 섞으면 PATH에서 옛 명령이 먼저 선택될 수 있다고 경고한다. 우리도 기존 명령 발견과 재사용 검증을 유지해야 한다.
- **Copier:** [CLI 준비와 프로젝트 생성](https://copier.readthedocs.io/en/stable/), [답변 파일과 템플릿 출처](https://copier.readthedocs.io/en/stable/configuring/), [갱신과 충돌](https://copier.readthedocs.io/en/stable/updating/). 답변 기록은 갱신 기준이며 프로그램 설치본이 아니다. 이를 우리 install.json과 같은 형식이라고 단정하지 않는다.
- **Husky:** [공식 시작 안내](https://typicode.github.io/husky/get-started.html), [설치 코드](https://github.com/typicode/husky/blob/main/index.js). 공개 코드에서 `.husky/_`에 생성 파일을 두고 그 안의 `.gitignore`에 `*`를 쓰는 처리를 확인했다. 팀 hook과 이 생성 영역의 역할이 다르다.
- **pre-commit:** [설치와 hook 준비](https://pre-commit.com/), [저장소 구현](https://github.com/pre-commit/pre-commit/blob/main/pre_commit/store.py). 공개 코드의 기본 저장 위치는 PRE_COMMIT_HOME 또는 사용자 캐시 기준이다. 환경 재사용 사례이며 그 DB나 자동 준비 동작을 OnepLoom에 그대로 편입하지 않는다.
- **.NET:** [도구와 팀 공유 manifest](https://learn.microsoft.com/en-us/dotnet/core/tools/global-tools), [local tool의 실제 저장 위치](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-tool-install), [restore](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-tool-restore). manifest는 필요한 도구를 적은 목록이고, 목록을 공유한 뒤 각자 실행 환경에 도구를 복원한다.
- **Maven과 Gradle:** [Maven의 only-script/bin 선택](https://maven.apache.org/tools/wrapper/), [Gradle의 wrapper 공유와 사용자 배포 저장](https://docs.gradle.org/current/userguide/gradle_wrapper.html). Wrapper는 해당 프로젝트의 실행을 준비하는 작은 진입 파일이다. 두 도구도 전체 실행 배포물을 프로젝트 Git에 넣는 방식과는 구별된다.
- **uv / pipx:** [uv의 도구 환경과 수명](https://docs.astral.sh/uv/concepts/tools/), [pipx의 격리 환경과 명령 연결](https://pipx.pypa.io/stable/explanation/how-pipx-works.html). 공식 사용 경로의 참고이며 이번에 설치하거나 배포 방식으로 채택하지 않았다.

## 이전 추천에서 바로잡을 점

이전 [관측 기록 (팀원 준비 자료 명세)](../../evidence/experiments/design/2026-11-23_07-38-22-wiki-reconcile.md)는 프로젝트의 `oneploom/bootstrap/`에 wheel을 두면 새 팀원이 별도 자료 없이 등록할 수 있다는 편의를 우선했다. 이 방식은 구현 가능한 대안이지만 기본 추천을 뒷받침하는 비교가 부족했다.

1. **기기 최초 준비와 프로젝트마다 재설치를 혼동했다.** 사용자 명령을 한 번 설치해 여러 프로젝트에서 재사용하면, 새 프로젝트마다 전체 설치기를 다시 받아야 한다는 비용을 기본값으로 둘 수 없다. 새로운 기기, 손상 복구와 호환 변경은 별도 조건이다.
2. **오프라인 자료의 보관 위치를 너무 좁혔다.** [Spec Kit의 격리망 안내](https://github.github.io/spec-kit/install/air-gapped.html)처럼 필요한 wheel 묶음을 별도로 전달할 수 있다. Python의 [ensurepip](https://docs.python.org/3/library/ensurepip.html)는 Python 배포 안의 준비 자료 사례이며 소비자 프로젝트 Git 동봉의 근거와는 다르다.
3. **라이브러리 설치본과 프로젝트 소스를 구분해야 한다.** 우리 프로젝트용 skill/script는 사용자가 편집할 결과물이지만 명령 등록용 wheel은 공식 프로그램 배포 파일이다. 같은 oneploom 이름을 쓴다고 같은 보관 정책을 적용할 이유는 없다.
4. **Gradle의 선택을 일반 규칙으로 확대할 수 없다.** Wrapper의 작은 JAR을 공유하는 목적은 분명하지만 Maven에는 다른 기본 방식도 있다. OnepLoom의 명령 등록은 매번 프로젝트를 실행할 때 wheel을 읽는 동작도 아니다.

wheel을 Git에 넣는 것 자체를 보안 오류로 판단하지 않는다. 개인 경로/자격증명을 패키지에 넣지 않는다면 파일 공유로 팀원의 WIKI가 같은 위치를 가리키게 되지는 않는다. 이번 변경 추천의 주된 이유는 자료의 역할, Git 이력, 여러 프로젝트에서의 재사용과 배포 책임을 맞추는 것이다.

## 제공 방식의 대안

| 대안 | 이점 | 비용과 판단 |
| --- | --- | --- |
| A. 적용 프로젝트에 wheel 동봉 | 별도 자료 없이 clone한 사본으로 명령 등록 가능. 네트워크 차단 환경에서 편리 | 프로젝트별 배포 파일 중복과 이력, 출처/갱신 관리, 바이너리 금지 정책 문제. 별도 요구가 있을 때 검토할 대안 |
| B. 공식 배포 자료로 사용자 명령을 한 번 준비 | 프로젝트 Git에 wheel을 두지 않음. 같은 기기 명령을 A/B 프로젝트에서 재사용. 기존 표준 등록과 Git Release + Python 유지 | 최초 자료 확보, 비공개 Release 접근과 호환/복구 안내 필요. **11/23 채택** |
| C. 프로젝트의 작은 준비 script가 고정 배포를 다운로드 | 처음 한 명령으로 필요한 도구 확보 가능. 프로젝트에는 작은 소스/기준만 공유 | 네트워크, 인증, 출처/해시, 부분 다운로드/재시도와 오프라인 대안 구현 필요. 첫 범위 확대 없이 B를 먼저 구체화하는 쪽을 추천 |
| D. uv/pipx/npm 등 패키지 관리자로 제공 | 명령 설치, 격리 환경과 갱신의 알려진 절차 활용 | 추가 준비물, 게시/관리 채널과 현재 합의 변경. 기존 결정대로 후속 검토 |

채택한 B안은 새 배포 채널이나 두 번째 버전 관리 원본을 추가하지 않는다. **공식 Release의 외부 관리 도구에 `command install`을 명세**해 프로젝트 설치 없이 명령만 준비한다. 최초 담당자의 프로젝트 install도 같은 등록 절차를 사용한다. [관리 명세 — 「시작 명령만 처음 준비하기」](../../design/runtime/management.md)가 현재 진입을 소유하며 아직 실행 가능한 제품 명령은 아니다.

첫 제공부터 작은 등록 전용 ZIP을 따로 만들 필요는 없다. 기존 배포 자료를 한 번 받는 흐름으로 시작하고 실제 크기/준비 시간이 문제라면 같은 공식 빌드에서 작은 준비 묶음을 분리할 수 있다. 다운로드에 들어 있는 파일과 프로젝트에 설치하는 파일 목록을 구분하면 된다. [GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)의 배포 파일 제공과 적용 프로젝트의 Git 커밋도 별개다.

## 추천 구조와 사용 흐름

아래는 B안의 채택 이유를 설명하는 흐름이다. 정확한 명령과 준비 절차는 [현재 설치 명세 — 「팀원 첫 준비의 배포 자료」](../../design/runtime/install.md)를 따른다. 처음 사용할 때와 이미 준비된 사용자를 구분해 안내하며 사용자에게 wheel, pip, venv 내부 운영을 맡기지 않는다.

| 대상 | 보관할 것 | 일반 사용에서의 역할 |
| --- | --- | --- |
| 공식 Release / 내려받은 배포 자료 | 명령 wheel, 관리 도구와 공식 설치 자료 | 최초 준비, 필요한 복구/갱신에 사용. 적용 프로젝트마다 복사하지 않음 |
| Windows 사용자 프로그램 영역의 OnepLoom | 등록한 짧은 명령과 그 전용 실행 환경 | 프로젝트를 찾아 해당 프로젝트의 실행본에 인계. 처음 설치한 프로젝트를 영구 참조하지 않음 |
| 적용 프로젝트의 oneploom 영역 | 프로젝트용 하네스 소스, 공유 설정과 비밀 없는 설치 기준 | 팀이 수정/검토/공유하며 실제 프로젝트 동작 수행 |
| 프로젝트의 `.harness/` | 각자의 WIKI 경로, 로컬 선택과 작업 기록 | 각 사용자/작업 사본의 준비를 재사용. Git 공유 제외 |

1. **최초 도입 담당자:** 기존 외부 설치 도구로 프로젝트를 준비할 때 같은 공식 자료에서 기기 명령도 준비한다. 이미 정상 등록이 있으면 재사용한다. 프로젝트 설치와 기기 등록의 별도 소유/복구 기록은 유지한다.
2. **새 팀원, 명령 미설치:** 공식 자료로 자기 사용자 환경에 명령을 한 번 등록한다. 프로젝트 하네스 설치나 WIKI 복원을 다시 하지 않는다. 이어 공유 프로젝트의 connect로 자기 WIKI 위치와 필요한 실행 선택을 준비한다.
3. **이미 등록한 팀원:** 다른 프로젝트를 clone하면 그 작업 사본의 연결만 준비한다. 호환되고 유효한 기기 명령을 다시 설치하지 않는다. A와 B가 다른 WIKI를 사용할 수 있다.
4. **평소 작업:** 기존 `oneploom`/`oneploom start`가 선택한 프로젝트로 인계하고 그 프로젝트의 설정을 읽는다. 매번 Release 조회, wheel 설치나 업데이트를 수행하지 않는다.
5. **새 프로젝트 최초 이식 또는 공식 갱신:** 현재 설계의 외부 관리 도구를 사용한다. 짧은 시작 명령이 등록됐다는 사실만으로 그 도구 전체가 영구 설치됐다고 설명하지 않는다. 배포 자료를 보관했다면 재사용하고 정리했다면 필요한 공식 자료를 다시 준비한다.

Git을 공유한다고 OS/AI 호스트 권한이나 계정 인증이 전달되지는 않는다. 경로는 각자의 로컬 설정에 저장하고, 유효한 제품 확인은 같은 범위에서 재사용하며, Codex가 요구하는 최초 신뢰 절차는 별도로 따른다. Codex 전역 설정을 모듈이 수정하지 않는 기존 경계도 유지한다.

오프라인 준비가 필요하면 공식 자료를 Git 밖의 승인된 전달 수단이나 보관 위치로 먼저 확보한다. 이는 clone만 있으면 모든 최초 준비가 가능한 보장을 포기하는 대신 패키지를 모든 프로젝트 이력에 넣지 않는 선택이다. 이미 등록된 정상 시작은 배포 자료 다운로드에 의존하지 않아야 한다. 실제 온라인 Codex 서비스 사용 가능 여부와도 구분한다.

다운로드 정리는 현재 작업의 필수 검증과 복구 자료 보존을 확인한 뒤 기존 사용자 확인 절차를 따른다. 등록된 환경/짧은 명령과 프로젝트용 하네스는 그 삭제 대상이 아니다. 기기 명령이 손상되고 자료도 정리됐다면 공식 자료가 다시 필요하다는 한계는 README에 드러낸다.

## 기존 요구와 트레이드오프

| 요구 또는 비용 | B안에 대한 판단과 남은 조건 |
| --- | --- |
| 프로젝트별 직접 편집과 팀 공유 | 유지. 하네스 본체를 전역 라이브러리로 옮기지 않고 wheel만 프로젝트 배포 목록에서 제외하는 제안 |

| 업데이트/사용자 변경 보존 | 기존 프로젝트 갱신 기준 유지. 기기 명령의 호환을 별도 확인하고 한 프로젝트 때문에 다른 프로젝트의 동작을 몰래 갱신하거나 낮추지 않아야 함 |

| 토큰과 실행 시간 | 등록은 일반 코드로 처리할 수 있어 새 AI 호출이 필요하지 않음. WIKI 읽기 방식은 바뀌지 않으며 이번 위치 변경을 토큰 절감 성과로 주장하지 않음. 준비 시간과 평소 시작 비용은 실측 필요 |
| 첫 배포 구현 부담 | 등록 전용 진입/자료 안내와 호환 검사를 닫아야 함. 자동 다운로드나 새 패키지 관리자를 함께 추가하지 않는 범위로 제안 |

## 채택 뒤 필요한 연결과 검증

11/23 전체 정리에서 install, management, entry/project-entry, records/storage와 수용 조건을 B안에 맞췄다. 기존 ADR 0023의 표준 등록과 복구 계약을 유지했다. 아래는 구현 뒤 확인할 조건이며 문서 동기화만으로 실행 완료가 되지는 않는다.

필수 검증은 실제 Windows 배포 자료와 일반 사용자 환경에서 다음을 확인한다. 아래는 미실행 입력이며 다른 도구의 동작을 우리 PASS로 사용하지 않는다.

- 명령이 없는 팀원의 최초 준비에서 프로젝트 재설치/WIKI 분석 없이 명령만 등록되고, connect에서 자기 값만 저장되는가.
- 이미 정상 등록된 사용자와 A/B 프로젝트에서 반복 설치/다운로드/같은 질문이 없는가. 새 clone의 로컬 준비가 필요한 사실을 숨기지 않는가.
- 프로젝트 Git의 설치 파일 목록에 wheel/가상환경/개인 경로가 섞이지 않고, 필요한 공유 하네스 소스와 설치 기준은 남는가.
- 오프라인에서는 사전에 준비한 공식 자료로 등록할 수 있고, 자료/의존성이 없으면 원인과 다음 행동을 알려 기존 사용을 보존하는가.
- 새 프로젝트가 다른 공식 버전을 사용하거나 기기 명령이 오래된 경우 호환을 검사하고, 불명확한 자동 교체/하향과 다른 프로젝트의 수정이 없는가.
- 배포 다운로드 정리, 첫 프로젝트 삭제, Python 변경, 등록 중단/기록 유실과 명령 복구에서 기존 소유/복구 조건이 유지되는가.
- 처음 준비한 시간/용량/사용자 입력과 정상 재사용 비용을 관측하는가. 도움말 성공을 실제 Codex 시작/종료와 WIKI 연결 성공으로 확대하지 않는가.

같은 원칙의 독립 구현과 코드 복사/동봉은 구분한다. 실제 패키징을 진행할 때는 선택한 Python/pip/명령 생성 파일의 해당 버전과 필요한 고지를 다시 확인한다. 현재 조사 문서는 짧은 사실 요약과 출처 링크로 구성하며 외부 본문/코드를 배포 템플릿으로 가져오지 않는다.
