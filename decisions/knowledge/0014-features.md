# ADR 0014: 필수 기반과 선택 기능

- 날짜: 2026-10-29
- 설계 상태: `accepted` — 조건부 하네스와 WIKI 활용/상세 복원을 필수 기반으로 둔다. 2026-11-09 내용 구성, 범위별 복원과 단일 반영 경계, 11/11 설명/학습 확장의 첫 제공을 채택했다. 구체 파일/호출과 실행 검증은 별도다.
- 구현 및 검증: 현행 계약, 공식 자료 읽기와 설계 사례 대조만. 새 구성, 설치, native 동작, 토큰 효과 미검증
- 확정 입력: 최소 역할, 프로젝트별 연결, 최초 선택과 이후 사용자 요청에 따른 기능 추가. 현재 제품 환경은 [ADR 0020](../runtime/0020-windows.md)의 Windows 우선이며 이전 WSL 기준을 대체
- 상세 소유: [모듈의 기능 선택과 추가](../../design/module.md)

## 채택 범위와 남은 작업

필수 기반, 상세 복원 방식과 첫 선택 기능의 경계는 결정됐다. 아래 최초 WIKI 선택안과 당시 확인 질문은 판단 이력이다. 실제 기능별 파일/호출 계약, 권한/충돌/중단 처리의 연결과 검증은 관련 설계에서 구체화한다. 로컬 AI의 실제 도입은 별도 ADR 0006의 미채택 항목이며, 기본 동작의 필수 의존성으로 넣지 않는다.

## 현재 상태

11/09 제품 범위 재확인: 핵심은 조건부 하네스이며 역공학 WIKI 복원은 필수 제공 보조 기능이다. 신규 프로젝트도 역공학 실행 없이 기본 구조를 연결하고 개발 과정의 요구, 결정, 검증을 기록하며 사용한다. ‘WIKI가 핵심’과 ‘모든 사용자가 역공학을 실행해야 함’을 구별한다. 이 명확화는 채택한 상세 복원 품질, 범위별 완료 기준을 줄이지 않으며, 구체 도입 경로는 [구조 — 「제품의 중심과 도입 경로」](../../design/architecture.md)가 소유한다.

WIKI는 핵심이라는 사용자 요구를 구체화해, 11/09 짧은 공통 요구/색인과 기능, 흐름별 상세 구성, 기초 파악 뒤 합의 범위의 분할 상세 복원, 범위별 완료 기준을 채택했다. 기존 문서와 근거를 보존하며 원문이 충분하면 연결, 대조로 처리한다. 이어 기본 메인의 단위별 순차 진행, 별도 후보, 단일 반영과 선택 보조 경계를 수용했다. 설명/학습 문서와 커밋 보조는 선택 확장이며, 구체 보조 실행, 설치, 권한/복구 수단은 남아 있다. 최신 기능 설명은 [모듈 — 「선택 확장과 실행 방식」](../../design/module.md), WIKI 채택 범위는 [이번에 확인할 범위](0014-features.md#%EC%9D%B4%EB%B2%88%EC%97%90%20%ED%99%95%EC%9D%B8%ED%95%A0%20%EB%B2%94%EC%9C%84), 위임의 채택, 미정 경계는 [위임의 공통 책임 — 「후속 협의: 위임의 공통 책임」](0014-features.md#%ED%9B%84%EC%86%8D%20%ED%98%91%EC%9D%98%3A%20%EC%9C%84%EC%9E%84%EC%9D%98%20%EA%B3%B5%ED%86%B5%20%EC%B1%85%EC%9E%84)이 소유한다.

아래는 최초 제안 → WIKI 이견 → 확장/위임 명확화 → 최소 WIKI 범위 검토, 채택 순서의 판단 기록이다. 당시 미채택 설명을 현재 상태와 구별한다. 최초 B는 채택된 적 없으며 WIKI 선택 추천은 철회했다. 초기 구성안의 B와 마지막 절의 초기 채움 B는 서로 다른 비교이며 채택 상태를 합치지 않는다.

## 문제와 관측

현재 구현/문서 검사와 retry는 `gate-common.sh`를 공유하고, followup skill, compact guard, hook은 진행 상태 경로를 연결한다. 문서, 협업, 커밋 보조에도 각각 절차와 설정 의존이 있다. 파일 종류별로 skill/config/hook을 따로 고르면 기능의 일부만 설치되거나 동일한 실패, 진행 상태를 다르게 해석할 수 있다.

반대로 전부 필수로 두면 프로젝트가 필요한 기능만 받겠다는 요구와 맞지 않는다. 최소 설치의 크기뿐 아니라 정상 조합의 수, 필수 검사의 누락 방지, 후속 추가와 사용자 이해 비용을 함께 판단해야 한다.

| --- | --- | --- | --- |

철회한 WIKI 선택 경계의 비교 기록이다. 이전 모듈 문서의 표를 이곳으로 옮겼으며 현재 설치 명세로 사용하지 않는다. 당시 '협업'은 Codex 내부 서브에이전트만 뜻했다.

| 구성 | 설치 | 담당 역할 | 필요한 입력, 의존 | 없거나 준비되지 않았을 때 | 후속 추가 조건 |
| --- | --- | --- | --- | --- | --- |
| 공통 기반 | 필수 | 조건부 진입, 프로젝트 설정 연결, 검사 계획/실행/실패 구분, 원래 검사 재시도, 최소 작업 상태, 재개, 설치 소유, 버전 확인 | 지원 Windows Codex/Git/Python, 프로젝트 루트, 검사 명령/예외, 문서/상태 경로. 선택 기능에는 의존하지 않음 | 검사 명령, 필수 상태가 없으면 해당 작업을 미확인/설정 필요로 보고. 필수 검사를 생략하고 완료로 처리하지 않음 | 최초 설치 대상. 기능 추가 때문에 갱신이 필요하면 버전 변경, 영향을 먼저 제시 |
| WIKI | 선택. 제품 제공 목표는 필수 | 코드, 테스트, 커밋/작업 기록에서 요구사항, 검토, ADR 후보 구성, 문서 경로 안내, 최신화, 문서 체계 검사 | 공통 기반 + 허용한 소스/기록과 프로젝트 문서 정책 | 자동 복원, 문서 체계 구성 절차는 제공하지 않음. 기존 문서 읽기, 프로젝트 필수 규칙, 검사는 그대로 유효 | 보호 원문, 기존 경로를 확인하고 후보로 작성. 과거 결정 이유를 만들거나 기존 ADR을 덮지 않음 |
| 협업 | 선택 | Codex subagent에 좁은 작업 전달, 읽기/수정 범위, 결과 형식과 메인 통합 절차 | 공통 기반 + 지원 버전의 native subagent 기능, 권한 | 이 모듈의 분업 절차만 없음. Codex 자체 기능을 제거하지 않으며 메인이 기본 작업 수행 | 도구 지원, 작업 범위, 공통 상태 호환 확인. WIKI나 로컬 AI를 자동 설치하지 않음 |
| 커밋 보조 | 선택 | 요청한 변경만 stage하고 그 범위의 메시지 초안 작성 | 공통 기반의 scope, 설치 소유 정보 + Git, 기존 index 상태 | 이 모듈의 stage/메시지 절차만 없음. 일반 Git 사용은 가능 | 기존 staged 변경과 팀 규칙 확인. 설치 자체로 stage, commit, push하지 않음 |

## 최초 추천과 감수할 비용

당시에는 B를 추천했다. 아래 문단은 수정 전 판단이며 WIKI 선택 경계는 뒤의 후속 협의에서 철회했다. 이 프로젝트의 핵심 가치는 검사, 실패, 재개의 연결이며 이를 모두 선택 사항으로 만들면 가장 지켜야 할 조건부터 조합별로 달라진다. 처음에는 동일한 기반 위에서 목적이 다른 기능만 고르는 편이 유지보수와 실증 범위를 관리하기 쉽다. 내부 구현 책임은 분리하고 외부 설치 단위만 묶는다.

설치 필수와 실행 필수는 다르다. 기반을 받았다고 단순 질문마다 검증, 상태 저장을 실행하지 않는다. 선택 기능이 없다는 이유로 기존 프로젝트의 필수 검사, 문서 규칙을 생략하지 않는다. 위키 복원은 제품이 제공해야 할 필수 목표지만, 이미 지식이 있는 프로젝트에서는 그 기능의 설치, 실행을 선택할 수 있다.

WIKI, 협업, 커밋 보조의 의존은 공통 기반을 향하고 서로를 의무화하지 않는 안이다. 로컬 AI 도입, 각 기능의 별도 저장소/패키지, 설치 CLI, 경로, 첫 배포의 협업/커밋 포함 여부까지 자동 결정하지 않는다. 기본 기능이 과도하게 커지거나 실제 사용 사례에서 독립 설치의 이득이 확인되면 A의 일부 경계를 다시 검토한다.

기반의 파일 수, 메타데이터, 초기화 비용이 증가할 수 있다. 현재 이 비용이나 토큰 절감률을 측정하지 않았고 기능을 나누는 것 자체를 최적화 성과로 제시하지 않는다. 첫 채택에서는 무엇을 받는지와 무엇이 실행되는지를 각각 검증할 수 있어야 한다.

## 최초 안의 확인 항목

- 검증, 재시도, 최소 복구를 기반 필수로 둘지, 더 세분화해 사용자가 고르게 할지
- WIKI를 제품의 필수 제공 기능이자 프로젝트별 선택 기능으로 설명하는 경계가 요구에 맞는지
- 협업, 커밋 보조의 독립 선택 경계. 실제 첫 배포 포함 범위는 일정과 함께 별도 판단

채택 시에도 ADR 0001~0005의 세부 검증 방식이나 ADR 0010, 0011의 설치/보존 방식이 일괄 채택되는 것은 아니다. 기반 단독, 선택 조합, 후속 추가의 검증 후보는 [수용 기준 — 「대표 수용 시나리오 후보」](../../verification/acceptance.md)에 연결한다. 사용자 확인 전 관련 구현, 설치는 진행하지 않는다.

## 후속 협의: WIKI의 핵심 역할

2026-10-29 사용자는 WIKI가 조건부 하네스의 핵심인데 선택 설치로 빼면 최소 구성으로 무엇을 할 수 있는지 질문했다. 앞의 최초 B안은 채택되지 않았으며 그 경계를 후속 설치 설계의 전제로 사용하지 않는다.

최초 제안은 WIKI의 연결, 탐색, 갱신과 빈 문서의 역공학적 초기화를 한 선택 기능으로 묶었다. 기존 문서가 있으면 복원을 다시 할 필요가 없다는 사실에서 WIKI 기능 자체의 선택 설치를 도출한 것은 이 프로젝트의 목표에 부적절했다. 기존 문서도 필요한 때 찾아 읽고, 현재 코드/정책과 대조하고, 변경과 재개에 연결하는 기능이 계속 필요하다. ADR 0008의 최소 역할, 프로젝트별 연결은 WIKI 역할을 제거한다는 합의가 아니다.

이전 공통 기반만으로도 검사 명령, scope, 예외를 연결하면 실행 사실 기록, 원래 검사 재시도, 최소 작업 재개를 제공하도록 설계할 수 있다. 이는 미구현 능력이며 아무 설정 없이 동작한다는 뜻이 아니다. 요구사항, 결정 이유, 실패 경험을 유지하고 필요한 문맥으로 공급하는 제품 목표를 충족하기에는 부족하다. 또한 기존 문서를 가리키는 설정을 요구했던 만큼 최초 기반도 완전히 지식과 무관한 구조는 아니었다.

| WIKI 경계 대안 | 장점 | 단점, 판단 |
| --- | --- | --- |
| 실행, 복구만 필수, WIKI는 선택 | 지식 관리를 다른 도구에 맡기려는 사용자의 설치가 작음 | 이 제품이 약속할 조건부 지식 활용, 역공학 이식이 최소 구성에서 빠짐. 최초 추천 철회 |
| 최소 WIKI와 활용, 초기화 절차를 기본 제공 | 최소 설치에서도 지식→판단→실행→검증→기록, 재개를 연결 | 최소 정보, 최신성, 누락/충돌 처리 설계 필요. 수정 추천 |
| 설치 시 전체 WIKI, 과거 기록까지 완성 | 초기에 넓은 문서 범위를 확보할 수 있음 | 분석 비용, 추정 문서, 유지 부담 증가, 초기 도입 지연. 비추천 |

수정 후보는 공통 실행, 검증, 복구와 최소 프로젝트 WIKI를 함께 기본 제공하는 것이다. WIKI는 문서 파일뿐 아니라 짧은 진입 안내, 필요한 지식의 조건부 탐색, 요구/현재 사실/결정/미확인 구분, 관련 변경 시 갱신, 실패, 진행 상태 연결을 포함한다. 내부 구현은 책임별로 분리할 수 있으며 최소 제품 구성을 별도 선택 설치로 쪼개야 하는 것은 아니다.

초기화와 역공학은 기본 제공하되 실행은 프로젝트 상태와 사용자 요청에 따른다. 문서가 있으면 원문을 보존하고 기존 역할/위치를 연결해 부족분을 검토한다. 문서가 비었으면 허용한 코드/테스트/이력에서 필요한 범위의 후보를 만든다. 신규 프로젝트는 초기 요구를 기록하며 축적한다. 모든 프로젝트에서 전체 이력을 다시 분석하거나 유료 생성을 설치 직후 자동 실행하지 않는다.

필수인 것은 지식 역할과 연결 절차이며 모든 폴더의 선생성, 전체 본문 상시 읽기, 과거 ADR의 임의 작성이 아니다. 코드에서 관측한 동작을 자동으로 채택 요구사항으로 승격하지 않고, 낡은 문서와 코드의 충돌도 숨기지 않는다. 구체 파일 수, 경로, 최소 내용과 작업 시작 조건은 아직 미확정이다. 커밋 보조 선택은 이후 요청에서 명확해졌으며 다음 절에 반영했다. 위임의 상세 경계는 계속 협의한다.

근거: [OpenAI의 하네스 구축 사례](https://openai.com/index/harness-engineering/)는 짧은 AGENTS 진입점과 저장소 지식, 계획, 검증의 연결을 설명한다. [Anthropic의 context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 필요한 문맥의 단계적 탐색과 세션 밖 기록의 재사용을 설명한다. 두 자료가 모든 하네스에 동일한 WIKI 구조를 의무화하는 것은 아니다. 이 제품의 사용자 목표, ADR 0008, 현행 라우팅과 함께 판단한 수정 추천이며 설치/성능 실증은 없다.

당시 수정 후보는 모듈 본문에 연결하고 최초 구성표는 이 ADR에 보존했다. 이 절은 WIKI 선택안을 철회하던 시점의 기록이다. 현재 채택 범위는 문서 첫 상태와 아래 11/09 후속 판단을 따른다.

## 후속 협의: 문서 확장과 작업 위임

10/30 시스템 날짜의 후속 요청에서 사용자는 선택 확장을 `explainers`, `learn` 등의 역할을 처음/나중에 추가하고 기존 README, 라우팅, 필요한 절차에 연결하는 의미로 명확히 했다. 커밋 보조도 선택으로 둔다는 의견이다. 이는 확정된 입력으로 반영하되, 기능별 파일 구성, 모든 위임 방식의 채택까지 뜻하지 않는다.

최초 표의 '협업'은 `.codex/skills/subagent-orchestration`과 task contract에 해당하는 **Codex 내부 서브에이전트 분업**만 가리켰다. 로컬 AI는 ADR 0006과 assist에 별도 후보로 남아 있었다. 두 용어를 답변과 기능 분류에서 구별하지 않아 이전 목표가 빠진 것처럼 보이게 했다. 이후 문서 확장, 커밋 보조, 서브에이전트 분업, 로컬 보조를 구분한다.

수정 추천은 핵심 WIKI, 실행, 검증, 복구와 최소 위임 규칙을 공통 기반에서 공유하고, 문서/커밋 기능은 설치 선택, 보조 사용은 실행 선택으로 다루는 것이다. 기본은 메인 직접 처리이며, 위임의 입력, scope, 권한, 결과 검토, 실패 상태는 실행자가 달라도 유지한다. 이를 위해 첫 버전부터 범용 orchestration framework나 모든 provider 연결을 구현할 필요는 없다.

| 위임 경계 대안 | 장점 | 단점, 판단 |
| --- | --- | --- |
| 하나의 작업 흐름 + 명시적 보조 분기 | WIKI, 검증, 복구를 공유하고 기본 단독 실행 유지 | 보조의 입출력, 모드/권한, 실패 처리를 설계해야 함. 추천 |
| 실행 모드마다 파이프라인 분리 | 각 실행자에 맞춰 자유롭게 조정 가능 | 규칙, 검사, 복구의 중복과 불일치 비용. 비추천 |
| 외부 orchestrator가 모든 모델/작업을 조정 | 공통 조정 지점과 여러 실행자 관리 가능 | Codex와 상태/권한/계획 책임 중복, 첫 범위 확대. 실제 필요가 확인될 때 후속 검토 |

사용자가 강조한 로컬 도입의 핵심 조건은 기본 단독 처리와 로컬 보조를 간단히 선택하고 같은 동작 보장을 유지하는 것이다. **선택 실행은 중요도가 낮다는 뜻이 아니다.** 로컬을 채택하면 전환, 권한, 실패 복귀, 재개 일관성도 그 기능의 완료 조건이다. 현재 요청만으로 로컬 도입, 실제 명령, 서브에이전트 기본 자동 호출, 다른 메인 provider 지원을 승인하지 않는다.

실제 서브에이전트 조건, 로컬 작업 예, 명령의 의미는 [보조 역할 — 「서브에이전트와 로컬 보조」](../../design/integration/local-ai.md)이 소유한다. 위임 설치 경계는 이 설명을 바탕으로 협의한다. 원래 작업은 계속 진행표 1단계이며, 이 질문으로 WIKI 최소 범위나 후속 설치/검증 계약 협의를 건너뛰지 않는다.

## 후속 협의: 최소 WIKI의 초기 범위

2026-10-30, 사용량 제한으로 중단된 조사를 이어 비교안을 작성했다. 사용자 지정 작업일은 여전히 10/29이며 새 날짜 경계를 임의로 나누지 않는다. 최소 역할, 프로젝트별 연결과 WIKI의 핵심성은 기존 입력이다. 이번 판단은 **처음 어느 정도까지 정보를 준비한 뒤 개별 작업으로 넘어갈지**에 한정한다. 독립 저장소, 설치 수단, 위임 정책을 일괄 확정하지 않는다.

현재 구조는 조건부 탐색, 현재 요구, 검토/채택 구분, 실패, 재개 역할을 이미 갖는다. 이를 이식할 때 특정 폴더 목록만 복사하면 실제 작업에 필요한 정보가 비어도 준비됐다고 오판할 수 있다. 반대로 모든 과거 지식의 복원을 시작 조건으로 두면 미확인 이력과 넓은 분석 비용 때문에 도입이 지연된다.

| 초기 범위 | 쉬운 설명 | 장점 | 단점, 판단 |
| --- | --- | --- | --- |
| A. 위치 연결부터 | 기본 역할의 절차와 기존 자료 위치만 연결하고 구조, 실행 정보도 각 작업에서 찾음 | 초기 조사량이 작고 잘 정돈된 프로젝트에 유리 | 자료가 빈 프로젝트는 같은 탐색을 반복하기 쉽고 첫 작업의 공백이 늦게 드러남. 기존 정보가 충분한 프로젝트의 제한된 경로로 가능 |
| B. 기초 파악 후 범위별 상세 복원 | 합의한 복원 범위를 나누고 각 단위의 과정, 결정, 구현, 결과, 근거를 복원한 뒤 관계/누락을 대조 | 상세 목표를 유지하면서 분할, 재개 가능. 기존 문서가 충분하면 보존, 대조로 처리 | 단위 사이 계약, 이력의 정합성 관리가 필요하며 전체 복원 비용이 사라지지는 않음. 11/08 수정 추천 |
| C. 전체 지식 복원 후 시작 | 주요 기능, 요구, 전체 이력의 판단 후보를 넓게 구성하고 검토한 뒤 개발 시작 | 넓은 구조를 먼저 검토하기 쉽고 별도 전면 문서화 사업에 적합 | 비용, 검토 부담, 추정 혼입 위험이 크고 범위를 닫기 어려움. 현재 일정의 기본 경로로 비추천 |

세 안 모두 WIKI 역할과 기존 원문 보호를 전제로 한다. A의 미확인 정보도 필요해지는 시점에는 확인해야 하며, C도 과거 이유를 만들어 채우는 방법이 아니다. 완성된 자료를 가진 기존 시험 프로젝트에서 B를 적용하면 기존 내용을 연결하고 필요한 차이만 확인하므로 재작성 의무가 생기지 않는다.

추천 B는 상세한 지식 복원 목표를 유지하면서 실행을 나누는 안이다. A는 기존 WIKI가 충분할 때의 연결 경로로 유효하고, C는 개발 전 모든 범위를 마치는 방식이다. B에서도 선택한 전체 복원 범위를 개발 중 필요할 때만 채우는 방식으로 축소하지 않는다. 파일 수나 문서 길이가 작다는 이유만으로 토큰 절감을 주장하지 않는다. 확인되지 않은 데이터가 많거나 첫 기능의 영향 범위가 넓으면 초기 조사량도 늘어난다. 그 경우 범위, 비용을 다시 협의한다.

기본 역할은 진입/탐색, 요구/계약, 구조/실행, 논의/결정, 실패/대응, 진행/검증으로 제안한다. 구체 읽기, 갱신, 부족 정보 처리, 세 프로젝트 유형은 [모듈 상세 — 「최소 WIKI」](../../design/knowledge/wiki.md), 확인 사례는 [S-18~24 — 「최소 WIKI 수용 후보」](../../verification/acceptance.md)에 둔다. 요구와 현재 동작, 정책과 실행 사실의 구별은 ADR 0004, 0001~0003의 기존 방향과 연결한다. 자료를 보존하는 설치 수단은 ADR 0011에서 계속 협의한다.

11/08 초기 보강에서는 기초 정보와 완료 구분을 추가했다. 같은 날 후속 질문에 따른 최종 깊이, 상세 복원 보정은 다음 절에 둔다. [최초 준비 — 「최초 준비와 점진적 채움」](../../design/knowledge/wiki.md)는 대상/목적, 지침/문서 위치, 주요 구조/실행, 확인된 요구/제약, 확인 범위/공백을 다룬다. [요구와 계약의 경계 — 「요구사항과 다른 정보의 경계」](../../design/knowledge/wiki.md)를 명시하고 연결 확인, 작업 준비, 범위별 보강의 완료를 구별했다. 전체 프로젝트 복원을 요청하면 전체 범위를 단위별로 처리하며 첫 단위만 마치고 전체 완료로 보고하지 않는다. 원문 보호, 확인되지 않은 정보의 보류는 그대로 유지한다.

**확인할 선택은 상세 복원 목표와 아래 보정을 반영한 B의 진행 방식이다.** 여섯 역할의 세부 경계에 이견이 있으면 함께 수정한다. 이 선택을 확인하기 전에는 기능표, 시나리오를 후보로 유지하고 설치/분석기를 구현하거나 전체 이력을 분석하지 않는다. B에 동의해도 위임 규칙과 첫 로컬 도입, 설치 파일, 명령, 저장소 운영까지 채택한 것은 아니다.

역할 구분과 추천은 현행 연결, 사용자 목표와 공식 자료를 종합한 판단이다. [OpenAI의 실용적 지침](https://learn.chatgpt.com/docs/learn/best-practices#make-guidance-reusable-with-agentsmd)은 짧은 진입 안내와 상세 문서 연결을, [Anthropic의 context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 필요 시 정보 탐색과 지속 기록을 뒷받침한다.

[장기 작업 사례](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)는 초기 환경, 진행, 검증을 구분하는 참고다. 이들 자료가 이 역할 수나 이식/토큰 효과를 입증하지는 않으며 실제 구현, 실증은 남아 있다.

### 상세 복원으로 추천 보정

11/08 후속 질문에서 사용자는 개발 과정과 결과, 선택에 이른 흐름을 상세히 복원하고, 관련 문서에 누락 없이 접근하면서 불필요한 토큰을 줄이는 목표를 재확인했다. 앞선 “기초 정보 + 작업별 보강”은 최초 준비를 설명했지만 상세 복원을 필요할 때만 하는 일로 남길 수 있었다. 기존에도 전체 요청의 부분 완료 금지는 있었으나 최종 깊이, 관계 탐색 기준을 충분히 드러내지 못했다.

이를 [복원할 깊이 — 「복원할 깊이와 완료 목표」](../../design/knowledge/wiki.md)와 [찾아 읽는 연결 — 「상세 지식을 찾아 읽는 연결」](../../design/knowledge/wiki.md)로 구체화한다. 기초 정보는 준비 단계이며 합의 범위의 상세 복원, 근거/관계 대조가 완료 기준이다. 개발할 때 필요한 부분만 계속 채우는 방식은 복원 이후의 유지보수로 활용할 수 있지만 전체 복원의 대체 방식으로 추천하지 않는다.

문서의 최종 깊이와 한 번의 분석/읽기량을 구별하며, 자료가 없는 이유는 추론, 한계로 남기고 과거 사실로 확정하지 않는다. 상세 복원 목표는 사용자 요구이고, 이 실행, 완료 방식은 미채택 추천이다. 파일 분할, 라우팅 형식, 설치, 모델 실행을 구현한 것은 아니다.

### 필수 정보와 완료 판정 구체화

2026-11-09, 사용자가 가상 상품 예제를 확장 가능한 설계 설명으로 이해하고 후속 작업을 요청했다. 이를 실제 복원 자료나 후속안 전체의 채택으로 해석하지 않았다. [필수 정보](../../design/knowledge/documents.md)와 [범위별 완료 판정](../../design/knowledge/wiki.md)을 작성해 위 B의 결과를 검토할 수 있게 했다. 파일 수, 고정 양식보다 내용, 출처, 관계, 보존을 판단하며, 미조사/접근 실패와 조사 범위 내 자료 부재를 구분한다.

추천 이유는 상세 목표를 유지하면서 실행 단위를 나눌 수 있고, 근거 없는 빈칸 채우기와 부분 완료의 확대를 막을 수 있기 때문이다. 품질 평가에는 사람이 검토한 기대 정보와 실제 입력이 필요하다. 일상 작업에서는 AI가 원문을 대조하고 근거로 결정할 수 없는 중요한 정책, 의도만 사용자 확인으로 넘긴다. 구체 구성, 완료 방식은 협의 중이며 위임, 설치, 모델 도입을 함께 채택하지 않는다.

같은 날 사용자는 ‘의미 검토’의 뜻을 확인한 뒤 설계 진행을 요청했다. [원문 대조와 위치표 소비 — 「위치표를 사용하는 절차」](../../design/knowledge/wiki.md)에 이 경계를 명확히 했다. 설명 확인과 후속 설계 진행을 미제시 저장 형식, 제품 구현의 승인으로 확대하지 않는다.

### 이번에 확인할 범위

11/09 위치표 구성 채택과 명명 검토 뒤, 원래 WIKI 범위 협의로 복귀했다. 상세 지식 복원, 기존 원문 보존, 사실과 추론 구분은 이미 사용자 요구다. JSON 위치표 구성도 별도로 채택됐다. 사용자가 아래 두 기본값과 연결된 완료 기준을 검토하고 그대로 진행하도록 승인했다.

| 선택 | 추천 | 대안과 절충 |
| --- | --- | --- |
| 내용 구성 | 짧은 공통 요구/색인과 기능, 흐름별 상세. 작은 내용은 한 문서의 절로 유지하고 기존 원본을 연결 | 한 문서 중심은 작을 때 간단하지만 커지면 읽기, 충돌 부담이 증가. 코드 디렉토리별 분리는 위치를 찾기 쉽지만 여러 모듈의 흐름이 흩어짐. 추천도 소유 위치, 연결 관리가 필요 |
| 복원 진행 | 초기 범위 B: 기초 파악 뒤 합의 범위를 나눠 상세 복원하고, 마지막에 관계, 누락 대조 | A 연결 중심은 충분한 기존 문서에 적합하므로 추천 흐름 안에서 사용. C 전체 복원 뒤 개발 시작은 검토 부담이 커 기본값으로 두지 않음. 분할해도 전체 분석량은 남음 |

내용 구성의 상세는 [문서 비교 — 「비교와 추천」](../../design/knowledge/documents.md), 입력에 따른 진행은 [기존, 빈 WIKI 사례 — 「기존 문서 채택과 새 문서 복원」](../../design/knowledge/wiki.md)가 소유한다. 완료는 [필수 정보](../../design/knowledge/documents.md)와 [범위별 완료 판정](../../design/knowledge/wiki.md)을 적용한다. 중단, 미조사를 자료 부재로 처리하지 않고, 복원 불가한 과거 이유와 실제 미처리를 구분한다. 문서 복원 완료를 애플리케이션 결함 해결이나 테스트 PASS로 확대하지 않는다.

이 두 기본값과 완료 기준은 채택됐다. 역할별 고정 파일, 모든 상세 필드, 위임 정책, 설치 수단, 모델 채택, 제품 구현을 일괄 승인한 것은 아니다. 다음 순서는 위임 경계와 설치/보존 설계이며, 기초 파악만 마치고 합의한 상세 복원을 후일 개발에 맡겨 두는 안으로 되돌리지 않는다.

## 후속 협의: 위임의 공통 책임

11/09 WIKI 범위 채택 후 기존 위임 추천을 구체화했다. 아래는 첫 구현, 검증 범위의 비교이며 앞선 WIKI 채택에 포함되지 않는다. 모드별 파이프라인이나 새 외부 조정기의 필요성은 [기존 위임 경계 비교 — 「후속 협의: 문서 확장과 작업 위임」](0014-features.md#%ED%9B%84%EC%86%8D%20%ED%98%91%EC%9D%98%3A%20%EB%AC%B8%EC%84%9C%20%ED%99%95%EC%9E%A5%EA%B3%BC%20%EC%9E%91%EC%97%85%20%EC%9C%84%EC%9E%84)와 연결한다.

| 범위 | 장점 | 비용, 한계 |
| --- | --- | --- |
| 메인만 제공 | 구현, 권한, 재개 검증이 가장 작음 | 독립 탐색/검토와 큰 입력을 별도 문맥에서 다룰 기회가 제한됨. 첫 범위를 더 줄여야 할 때의 대안 |
| 공통 위임 규칙 + 선택 Codex 분업 | 같은 WIKI, 검증, 복구를 유지하고 제한된 보조부터 검증 가능. 추천 | 결과 대조, 입력 최신성, 권한, 실패 처리 필요. 토큰 절약은 보장하지 않음 |
| Codex, 로컬, 다른 provider를 함께 제공 | 처음부터 실행자 선택 폭이 넓음 | 인증, 입출력, 품질, 복구 조합이 증가. 현재 일정에서 동시에 구현하는 안은 비추천 |

추천 범위에서는 기본은 메인 직접 처리다. 공통 규칙이 있다고 보조가 자동 실행되지는 않는다. 사용자 요청이나 승인된 설정의 범위에서만 선택하며, 첫 검증은 보조 한 건의 탐색, 독립 검토부터 시작하고 원문 반영은 메인이 맡는다. 같은 파일의 동시 수정, 보조 재위임, 임의 provider 대체는 첫 범위에서 제외한다. 기술적으로 원본 수정을 막을 수 있는지는 지원 환경에서 별도로 검증한다.

상세 책임과 호출 조건은 [공통 규칙과 호출 범위](../../design/integration/local-ai.md), 실행자별 책임은 [역할표](../../design/integration/local-ai.md), 재개, 늦은 결과, 원래 실패 보존은 [실패 처리 — 「실패와 기본 경로 복귀」](../../design/integration/local-ai.md)가 소유한다. 같은 작업의 유효한 허용 범위는 재개 때 확인해 유지하고, 새 비용, 반출, 권한이 필요할 때만 다시 협의하는 안이다. 실제 도구, 저장 형식은 설치/복구 명세에서 정한다.

로컬 품질 비교는 별도로 준비할 수 있다. 같은 상세 WIKI 기준과 총비용 비교 없이 도입하지 않지만, 이 추천을 로컬 시험의 무조건 연기나 로컬 전체 기능 삭제로 해석하지 않는다. Codex 내부 분업, 부분 로컬 위임, 메인 전체 전환은 다른 선택이다.

11/09 후속 채택: 사용자가 기본 구조, 동시 편집과 반영, 범위별 병렬 복원을 읽고 현재 방향을 수용했다. 기본은 메인 하나의 단위별 순차 진행이며 상세 후보와 근거를 검토한 뒤 같은 WIKI의 한 반영 경로를 사용한다. 공통 위임 규칙과 제한된 보조 분기는 두되 상시 병렬 작성, 로컬 실행을 필수로 하지 않는다. 보조가 없어도 핵심 WIKI 복원, 검증, 재개를 수행해야 한다. 상세 품질, 범위별 완료 기준은 유지한다.

구체 모델, 권한, 잠금/원자성, 저장 필드, 병렬 수, 첫 보조 역할, 실험 예산, 외부 전송은 미확정이다. [동시 편집과 반영](../../design/runtime/install.md)의 처리 원칙과 실제 차단, 복구 검증을 구별하며, 구현 중 충돌이나 더 나은 대안이 확인되면 영향 범위를 다시 협의한다. 설치/보존 설계로 이어가되 이번 수용을 모델 호출, 제품 구현 승인으로 확대하지 않는다.
