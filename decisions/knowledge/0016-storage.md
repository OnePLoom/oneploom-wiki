# ADR 0016: WIKI 저장과 편집

- 날짜: 2026-11-02
- 설계 상태: `accepted` — Markdown/Git 기반의 WIKI 원본과 선택 편집기, 내부/외부 WIKI 연결을 지원하고 로컬 실행 상태는 분리한다. 2026-11-05 별도 WIKI의 작업 연결, 11/08 상태 영역의 공유 제외 자동 설정을 채택했다. 상세 저장/권한 계약의 제품 검증은 별도다.
- 구현 및 검증: 예비 연결 도구의 시작/재개 인자와 경로 분리를 검사했다. 실행 상태를 옮긴 뒤 27개 검사와 기존 hook 직접 호출, Git 제외 여부를 확인했다. 작은 Windows 시험에서는 양방향 수정과 이름 변경, 재열기, 내부 링크 및 HTTPS 링크를 사용자가 확인했다. 원문 참조 15개는 기존 커밋으로 연결했다.

  예비 문서 연결에서 양방향 수정, GUI 반영과 재열기 보존을 확인했다. 제품 설치와 복구 전체의 완료를 의미하지 않는다.
- 상세, 공식 근거: [WIKI 저장과 Obsidian](../../discussions/knowledge/storage.md)

11/08 후속: active는 코드 작업 공간의 로컬 상태로 두고 공유 WIKI와 분리한다. B 공유 제외를 설치기가 자동 설정하는 방향을 채택했으며 `.gitignore` 맨 아래 배치, 상태 영역 전체 제외와 문서 경로의 혼동/중복 방지가 조건이다. 제품 설치 구현은 아직이다.

## 채택 범위와 남은 작업

WIKI의 Markdown/Git 원본, 선택 편집기, 프로젝트별 연결과 로컬 상태의 분리는 결정됐다. 외부 저장소의 공개/비공개 범위는 사용자 정책을 따르며 같은 Git 안의 WIKI도 지원한다. 연결 변경, 권한 인계, 사용자 편집 보존과 중단 복구를 실제 제품에서 검증해야 한다. Obsidian Sync나 다른 동기화 제품, MCP의 첫 배포 도입을 이 결정에 포함하지 않는다.

## 문제

공개 코드와 내부 개발 지식을 같은 공개 범위로 두면 원치 않는 노출이 생긴다. 문서를 개발자별 로컬 파일로만 분산하면 공유, 이력, 복구가 어려워질 수 있다. 반면 모든 프로젝트를 Obsidian에 종속시키거나 외부 저장소를 필수로 만들면 설치, 경로, 동기화와 두 저장소 검토 비용이 늘어난다.

Git 저장소의 접근 범위와 Docker 실행 산출물, Obsidian 편집과 Sync 공유, AI의 문서 접근은 별도 경계다. 공통 Markdown 기반을 유지하고 원본의 소유, 수명, 접근 범위를 먼저 정해야 한다.

## 대안

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 코드와 WIKI를 같은 Git 저장소에서 관리. Obsidian은 선택 편집기 | 한 PR, 한 revision으로 변경을 연결, 현재 구조 적용이 단순 | 저장소가 공개되면 내부 WIKI도 노출될 수 있어 공개 범위가 다른 지식을 함께 둘 수 없음 |
| B | WIKI는 별도 private Git의 Markdown 원본. 프로젝트에서 로컬 경로, 버전을 연결하고 편집기는 선택 | 공개 코드와 내부 지식을 분리하고 Git 검토, 이력 유지 | 두 저장소의 변경, 버전, 권한, 링크, 부분 적용을 관리해야 함 |
| C | 외부 vault와 Obsidian Sync를 공유, 복원 수단으로 사용, 별도 문서 Git은 두지 않음 | 기기 간 공유와 앱 내 복원이 편리 | 구독, 충돌 처리, 권한 제약, 코드 revision과 문서 검토를 잇는 절차는 별도 필요 |

## 추천

11/04에는 코드와 문서의 공개 범위를 분리하면서 운영 비용을 낮추는 B를 검토하고, 같은 저장소를 사용하는 A와의 호환도 유지했다. 11/05에는 별도 private WIKI를 전제로 PR 연결, 검사 자동화 방향을 [ADR 0017](../integration/0017-work-sync.md)에 채택했다. 저장 원칙과 작업 연계는 채택된 상태이며, 파일 접근, 공유, 이전의 세부 계약을 계속 구체화한다. 어느 방식을 쓰든 WIKI 원본은 한 곳만 둔다.

Obsidian은 필수가 아닌 편집, 탐색 도구로 두고 일반 Markdown, Git을 원본으로 유지한다. 첫 AI 연결은 허용된 폴더의 파일 직접 접근을 추천한다. MCP, 자동 검색/요약은 필요한 기능과 실제 완료 비용에서 이점이 확인될 때 별도로 선택한다. 저장 원칙 채택을 Sync 구독, 플러그인 설치, 모델 호출이나 토큰 효과의 승인으로 해석하지 않는다.

첫 제품 환경은 11/11 [ADR 0020](../runtime/0020-windows.md)의 Windows 직접 실행으로 전환했다. WSL/Linux는 후속이며 과거 배치 관측은 아래 판단 이력으로 보존한다.

## 11월 4일 운영 보정

이전 문서의 저장소별 PR 절차는 기본 운영으로 너무 무거웠다. 별도 저장소에서도 매 앱 커밋마다 문서 커밋, PR이 필요한 것은 아니다. 저장 방식의 대안과 [무료 운영 대안](../../discussions/knowledge/storage.md)을 구분한다.

- 첫 추천은 별도 private Git에 실제 WIKI 변경을 작업 단위로 commit, push하는 방식이다. 개인 설명, 작업 기록에는 매번 PR을 요구하지 않고, 팀 정책, 중요 계약에는 리뷰를 적용하는 운영을 비교한다.
- Obsidian Git의 버튼, 자동 commit-and-sync는 후속 편의 수단이다. 현재 WSL/Windows Git 경계와 작성 중 파일 변경, 자동 stage 범위를 검증한 뒤 선택한다.
- Syncthing은 무료 기기 간 공유 대안이지만 충돌과 제한된 버전 보관을 감수해야 한다. 공식 Obsidian Sync는 소수 참여자도 구독이 필요하므로 최소 비용의 첫 추천에서 제외한다.
- 편집기 사용과 실제 외부 경로 이전, Git 초기화는 구분한다. 후속 오류 보고로 Windows 앱의 현재 WSL 폴더 직접 열기를 우선 사용안에서 제외했다. `--add-dir`는 Codex의 추가 쓰기 범위 옵션이며 자동 문서 연결이나 Git 권한을 대신하지 않는다.
- Git 공유도 PR 자동화도 모델 호출이 필수인 작업은 아니다. Obsidian, Git을 사용한다는 이유만으로 추가 LLM 토큰이 발생한다고 계산하지 않는다.

### Windows 앱과 vault 배치 보정

초기 환경에서는 Windows Obsidian이 WSL의 vault를 열 때 오류가 보고됐다. 오류 전문과 환경 일부가 확보되지 않아 원인을 확정하지 않았다. 문서를 Windows 로컬 폴더에 두고 해당 파일에 접근하는 배치, WSL 경로를 그대로 여는 배치와 다른 편집기를 비교했다. 작은 사본으로 양방향 수정, 이름 변경, GUI 반영과 재열기 보존을 확인했다.

이 예비 관측은 제품의 설치, 권한 지속과 복구 성공을 의미하지 않는다. 첫 제품 환경은 [ADR 0020](../runtime/0020-windows.md)의 Windows 직접 실행이며, 내부/외부 WIKI를 등록하고 원문을 보존하는 일반 계약을 별도로 검증한다. [파일시스템 안내](https://learn.microsoft.com/en-us/windows/wsl/filesystems), [Obsidian의 저장 방식](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data).

## 작업 상태의 Git 제외

11/08 구체화 후 채택: **배포는 B 공유 제외, 설치 자동 설정을 기본으로 한다.** WIKI와 로컬 실행 상태의 분리를 유지한다. 아래 대안은 판단 이력이며 WIKI 저장 대안의 A/B/C와 별개의 비교다.

| 안 | 방법 | 장점 | 단점 |
| --- | --- | --- | --- |
| A — 로컬 제외 | 코드 작업 트리의 active를 `info/exclude`로 제외 | 추적 파일에 개인 제외 규칙을 남기지 않음. 기존 상대 경로와 작업 공간 권한 활용 | clone마다 설치 필요. 이미 추적된 파일, 강제 추가는 보호하지 못하며 상충 규칙 확인 필요 |
| B — 공유 제외 | 같은 active 경로를 추적되는 `.gitignore`에 등록 | 팀의 새 clone에도 규칙 배포, 일반적인 프로젝트 생성물 관리 방식 | 저장소에 규칙 변경이 남음. 강제 추가, 기존 추적 문제는 A와 동일 |
| C — 작업 트리 밖 저장 | 사용자 로컬 상태 폴더에 프로젝트/worktree별 상태 보관 | 코드/WIKI의 일반 add 대상에서 구조적으로 분리 | 경로 식별, 외부 쓰기 권한, hook 연결, 백업/정리 책임 추가. 현재의 프로젝트 내부 재사용 요구와 덜 맞음 |

**팀 도입을 고려해 B를 추천했고 사용자가 채택했다.** 공통 제외 규칙을 PR로 검토하고 clone, 규칙 변경 때 함께 전달할 수 있다. 공유하는 것은 도구의 상태 경로 한 줄이며 실행 상태 본문, 사용자 이름, WIKI 절대경로가 아니다. 규칙 공유와 상태 공유는 다르므로 팀원별 active 병합도 발생하지 않는다. Git 역시 공유할 규칙은 `.gitignore`, 특정 사용자의 작업에만 필요한 규칙은 `info/exclude`에 두도록 구분한다. [Git 제외 기준](https://git-scm.com/docs/gitignore).

팀 안에서 혼자 사용하거나 추적 파일을 바꿀 수 없는 경우 A가 가능한 대안이라는 비교는 유지한다. 다만 이번 채택 범위에 A 모드, 자동 fallback을 추가하지 않는다. B 적용 권한/범위가 맞지 않으면 성공으로 처리하지 않고 확인한다. 현재 기존 시험 프로젝트는 기존 active 제외가 이미 적용돼 있으므로 같은 규칙을 중복 추가하지 않는다. C는 파일 경계가 더 명확하지만 현재 프로젝트 내부 상태 요구에 비해 별도 경로, 권한, 연결 비용이 크다.

처음에는 개인 흔적 비공개 조건에 무게를 두어 A를 기본 추천했다. 후속 질문에서 팀 배포를 다시 대조한 결과, 공통 도구의 제외 규칙과 개인 정보를 분리해야 하므로 위와 같이 추천을 보정했다. A가 틀린 Git 기능이라는 뜻이나 B가 강제 추가까지 차단한다는 뜻은 아니다. `.gitignore`를 커밋해 공유하기 전까지 다른 clone에 자동 반영되지 않으며, 두 방식 모두 실행 전 실제 제외/추적 검사가 필요하다.

B의 규칙 등록은 설치 적용에서 `.gitignore` 생성/보강, 중복 방지, 제외 검사로 자동 처리한다. 도구가 쓰는 관리 구간은 항상 파일 맨 아래에 두고, 후속 사용자 합의로 기본 패턴은 `/.harness/`로 정한다. 이 폴더는 상태, 캐시, 임시 자료, 기기별 연결 전용이며 공유할 코드, skill, hook, 설정과 WIKI는 밖에 둔다. 기존 공유 자산이 섞여 있으면 충돌로 처리하고 먼저 제외하지 않는다. 그 변경은 도입 commit, PR에 함께 반영한다. [자동 설정 절차 — 「제외 규칙의 자동 설정」](../../design/workflow/recovery.md)는 최초 설치, 기능 추가, 경로 변경에서 재사용하며 구현 전이다.

실행 상태와 기능 정의도 구분한다. 공통 skill, hook, 설정은 재현 가능한 버전으로 관리하고, 실행 중 active, 임시 결과만 제외한다. 공유 코드/설정과 로컬 생성물을 구분하는 사례로 [Terraform 공식 스타일 가이드](https://developer.hashicorp.com/terraform/language/style#gitignore)를 참고했다. Terraform의 상태 저장 기술을 채택한다는 뜻은 아니다.

설치기는 `.git`이 디렉토리라고 가정하지 않고 Git이 알려주는 제외 파일 경로를 사용해야 한다. linked worktree는 제외 설정을 공유할 수 있지만 active 본문은 각 작업 트리에 둔다. 실제 제외 결과와 index를 따로 확인한다. `check-ignore --no-index`만 통과했다고 이미 추적된 파일이 안전해지는 것은 아니다. [Git worktree](https://git-scm.com/docs/git-worktree), [git rev-parse](https://git-scm.com/docs/git-rev-parse), [git check-ignore](https://git-scm.com/docs/git-check-ignore).

[관측 기록 (격리 관측)](../../evidence/experiments/recovery/2026-11-08_14-35-31-active-storage.md)에서 정상 add, 강제 add, 기존 추적, 제외 취소, clone, worktree의 예상 동작을 확인했다. 이는 제외 설정의 한계를 확인한 실험이며 유출 방지 완성이나 설치기 통과가 아니다. 생성 시점, 보존, 재개, WIKI 선별은 [작업 상태 계약 — 「작업 상태와 Git 제외」](../../design/workflow/recovery.md)에 둔다. 로컬 active는 ADR 0017의 앱/WIKI 커밋 쌍에 포함하지 않으며 필요한 확정 지식만 WIKI로 옮긴다.

### 상태 폴더와 문서 폴더

후속 질문의 대상은 배포 모듈의 기본 경로다. 기존 도구의 상태 경로를 새 모듈에 그대로 고정하지 않는다.

| 배포 경로 후보 | 장점 | 단점, 판단 |
| --- | --- | --- |
| `docs/followup/active/` 유지 | 기존 hook 경로 재사용, 초기 이전 부담 작음 | 문서와 일시적 상태가 같은 상위 폴더에 섞여 수집, 이전, 역할 혼동 위험. 현재 호환 경로 |
| 도구 전용 폴더의 `state/` | WIKI와 수명, 추적 경계가 명확하고 AI 도구에 종속되지 않음 | hook, 런처, 복구, 설치의 경로 연결을 함께 수정, 검증해야 함. 11/08 배포 방향 채택 |
| `.codex/state/` | 기존 Codex 구성과 가깝고 최상위 폴더 증가를 줄임 | 다른 도구 지원 시 공통 실행 상태가 Codex 전용 영역에 남음. 공통 기본값으로 비추천 |

로컬 상태의 기본 위치를 `.harness/state/`로 정했다. 상태 폴더만 제외하던 초기안은 `.harness/` 전체 제외로 보완했다. 공통 경로 정의를 설치기, hook과 복구에 연결하며 기존 자료를 이 설계만으로 이동/삭제하지 않는다.

## 남은 조건

- 사용자용 앱 Git 분리 요구는 다시 승인받지 않는다. 일반 Markdown, 선택 편집기, 내부/외부 원본 연결의 구현 범위와 B의 저장 시점, 리뷰, 충돌 처리 수단을 협의한다.
- 개인 Windows vault 이전은 완료됐으며 [이전 기록](../../evidence/environment-observations.md)의 실제 관측 범위를 따른다. 원래 UNC 오류 전문, 앱/설치 프로그램 버전은 미확인이므로 원인 재현, 해결까지 완료했다고 주장하지 않는다. 제품의 Windows 직접 실행은 ADR 0020에서 별도로 검증한다.
- 제품의 지침, 문서 매핑, 허용 경로, 코드/WIKI revision, 복구 연결은 파일별 명세에서 구체화한다. 완료한 예비 문서 연결의 승인, 보존 조건을 일반 프로젝트 문서의 자동 이전 허가로 확대하지 않는다.
- 외부 저장소의 commit, push 및 필요한 PR을 원자적 동작으로 취급하지 않고, 검증한 두 revision과 부분 반영 상태를 남긴다. 자동 백업을 채택 정책의 승인으로 표시하지 않는다.
- 토큰 비용은 편집, 동기화와 모델의 읽기, 검색, 도구 호출을 분리한다. 서버나 모델을 선정하지 않은 상태에서 증가율을 만들지 않는다.
- 코드 공개, 실제 문서 이전, 과거 이력 처리, 사용자 파일 수정은 별도 개발 범위로 합의한다. ADR 0011의 원문 보존과 ADR 0014의 채택된 WIKI 구성, 상세 복원 범위를 유지한다.

개발은 진행표의 순서를 따른다. 채택 범위의 파일별 명세와 수용 기준을 연결한 뒤, 개발 준비, 작은 흐름의 구현/검증에서 내부 WIKI와 외부 WIKI를 각각 시험한다. 여러 자동 동기화 서비스, 전용 지식 서버, 자동 승인/연쇄 병합을 첫 범위로 확장하지 않는다.
