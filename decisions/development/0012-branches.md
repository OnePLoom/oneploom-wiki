# ADR 0012: 개발 브랜치와 통합 기준

- 날짜: 2026-10-28
- 설계 상태: `accepted` — 2026-11-23 main과 작업 브랜치를 채택했고, 11/24 필요한 경우의 임시 통합 브랜치와 main PR의 Rebase and merge를 보완 채택했다. 실제 원격 운영과 병합 검증은 별도다.
- 구현 및 검증: 첫 작업 브랜치와 커밋/push, 코드/WIKI PR의 이슈 연결 및 Project 등록을 확인했다. 실제 병합과 그 이후 마감은 미실행이다.
- 적용 범위: OnepLoom 코드와 개발 WIKI의 운영. 소비 프로젝트의 기존 브랜치와 이력은 해당 프로젝트의 정책에 따라 다룬다.
- 상세 운영 규약: 코드 CONTRIBUTING. 이 ADR은 대안, 채택 이유와 이력 보존의 판단을 기록한다.

## 현재 근거

작은 기능 변경을 여러 커밋으로 쌓고, 검토 가능한 단위의 PR로 통합하는 흐름이 필요하다. 두 저장소의 작업을 연결하되 Git 이력과 권한은 독립적이다. main/작업 브랜치만으로도 여러 커밋을 한 PR로 검토할 수 있으며, 하위 작업별 검토가 필요한 큰 기능에는 임시 통합 브랜치를 사용할 수 있다.

## 대안

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 기존 feature에 계속 추가 | 바로 이어갈 수 있음 | 기존 구조, 신규 적용의 검토/복구 경계 혼합 |
| B | 기존 변경 검증, dev 반영 후 새 적용 브랜치 | 독립된 기준과 비교, 리뷰 | 기존 변경의 독립 수용 가능성 확인 필요 |
| C | 현재 HEAD에서 자식 적용 브랜치, 통합은 후속 | dev를 먼저 바꾸지 않고 작업 격리 | 선행 브랜치 의존과 최종 통합 범위 관리 |

## 추천

위 A/B/C는 기존 프로젝트에 하네스를 적용할 때 가능한 통합 경로다. 기존 변경을 독립적으로 수용할 수 있으면 B로 기준을 정리하고, 먼저 통합하기 어려우면 C로 격리할 수 있다. 소비 프로젝트의 dev 병합을 OnepLoom 개발의 강제 선행 조건으로 만들지 않는다. 새 모듈 자체의 채택 결정은 다음 절을 따른다.

Git의 fast-forward는 조상 관계가 성립할 때 대상 포인터를 이동하는 처리다. 조상 관계나 텍스트 충돌 없음만으로 기능, 문서, 복구 연결의 보존을 증명하지 못한다. 실제 원격 상태와 영향받는 검증을 확인하며 원본 이력 재작성, 강제 push를 기본 절차로 두지 않는다. [Git merge](https://git-scm.com/docs/git-merge), [Git fetch](https://git-scm.com/docs/git-fetch).

## 독립 모듈의 브랜치 운영

11/23 main + 작업별 브랜치를 채택했고, 11/24 **기본 2단계에 필요한 경우만 임시 통합 브랜치를 추가**하도록 보완했다. 코드와 WIKI에 공통 적용한다. 작은 커밋 여러 개를 작업 브랜치 하나에 쌓고 PR로 검토할 수 있으므로 커밋 수와 브랜치 단계 수는 별개의 문제다. 고정 develop은 두지 않는다.

실행 규약의 원본은 [코드 CONTRIBUTING](https://github.com/OnePLoom/oneploom/blob/main/CONTRIBUTING.md)의 「브랜치와 변경 단위」, 「병합과 이력」이다. 규약의 로컬 반영과 GitHub 게시 여부는 구분한다. 원격에 게시하기 전에는 코드 폴더의 CONTRIBUTING을 읽는다. 이 ADR은 대안과 선택 이유를 소유한다.

| 대안 | 맞는 상황과 이점 | 비용과 이번 판단 |
| --- | --- | --- |
| main + 작업 브랜치 | 작은 커밋을 검토 가능한 PR로 묶고 통합 단계를 줄임 | 큰 작업을 무조건 하나의 거대한 PR로 만들면 검토가 어려움. 기본 채택 |
| 큰 기능별 임시 통합 브랜치 | 하위 PR을 따로 검토하고 여러 구성의 통합을 최종 검증할 수 있음 | base 관리, 하위/최종 검토와 변경 충돌 확인이 추가됨. 필요한 경우만 채택 |
| main + 고정 develop + 작업 브랜치 | 여러 기능을 릴리스 단위로 통합하고 안정화하는 단계가 명확함 | 상시 동기화와 릴리스 운영이 늘어남. 현재 별도 안정화 단계의 필요가 확인되지 않아 기본에서 제외 |

예를 들어 `feat/session-restore`에 작은 커밋을 쌓아 main으로 PR을 보내는 것만으로 기본 요구를 만족한다. 하위 작업별 PR이 필요해지면 그 브랜치를 임시 통합 대상으로 사용하고, 최종 검증/병합 뒤 미병합 변경을 확인해 정리한다. 이름이 특정 계층의 특별한 Git 객체를 만드는 것은 아니다.

GitHub flow는 작업 브랜치에서 여러 커밋과 PR 검토를 거치는 절차를 지원한다. Git의 공식 workflow도 topic/integration 브랜치를 설명하지만 소규모 프로젝트에 전체 절차가 필요하지는 않다고 명시한다. Google의 작은 변경 지침을 고려해 PR은 독립 검토 가능한 범위로 유지한다. 이를 OnepLoom의 현재 개발 규모와 코드/WIKI 연결 요구에 적용한 판단이며, 모든 기업의 단일 표준이나 최다 사용 비율을 주장하지 않는다.

### 병합 방식의 선택

11/24 main PR에 **Rebase and merge**를 기본으로 채택했다. 여러 작은 커밋의 의미를 보존하면서 선형 이력을 얻는다. Squash는 작은 변경별 이력을 합치므로 기본 목적에 덜 맞고, Merge commit은 SHA와 병합 경계를 보존하는 대신 병합 커밋이 추가된다. 당시 공유 의존이나 복잡한 통합 이력에 대한 Merge commit 예외를 검토했으나, 11/25 두 저장소가 rebase만 허용하도록 설정됐다. 다른 방식을 실제 사용하려면 별도 정책 검토가 필요하며 현재 절차에서 자동 선택하지 않는다.

GitHub의 rebase 병합은 새 SHA를 만든다. 따라서 코드/WIKI를 실제 PR로 연결하고 병합 후 최종 main SHA를 확인한다. 병합 전 식별자를 최종 적용 버전으로 고정하지 않는다. 공유 main/통합 브랜치를 임의로 rebase하거나 강제 push하는 운영은 채택하지 않았다. 충돌 해결 뒤 바뀐 결과는 관련 검증을 다시 받아야 한다.

11/25 원격 조회에서 두 저장소의 rebase 단독 허용, main 삭제/강제 push 차단, 선형 이력과 PR 요구, 미해결 대화 차단을 확인했다. 필수 승인 수는 0이며 필수 CI는 아직 없다. 관리자가 PR을 검토해 직접 병합하고, 실제 반영 결과를 확인해 공통 작업을 마감한다. 첫 코드/WIKI PR 생성과 정식 이슈 연결은 확인했으며 실제 병합은 검토 대기다. 현재 운영 규약은 위 CONTRIBUTING이 소유한다. 실제로 불가능한 rebase를 억지로 수행하거나 규칙 충돌을 자동 우회하지 않는다.

근거: [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow), [Git workflows](https://git-scm.com/docs/gitworkflows), [Gitflow 원문](https://nvie.com/posts/a-successful-git-branching-model/), [작은 변경의 검토](https://google.github.io/eng-practices/review/developer/small-cls.html), [GitHub 병합 방식](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github).

## 통합 완료 조건

- 갱신한 원격, 작업 브랜치, 병합 대상의 끝점을 고정하고 실제 결과 트리를 격리해 확인한다.
- 텍스트 충돌 여부와 main의 기능 보존을 각각 검증한다. 기존 코드, 계약, WIKI/ADR, 도구 연결을 범위별로 대조한다.
- 제품 회귀, 문서 보존, native hook/skill 연결의 결과를 남긴다. 확정 boot 예외를 모든 프로젝트에 확대하거나 PASS로 기록하지 않는다.
- 끝점, 설정, 직접 입력이 바뀌면 관련 PASS 효력을 재판단한다. 계획, 미실행, 미분류는 완료 증거가 아니다.
- 실제 원격 갱신, branch 생성, merge, push는 개발 범위 확정 뒤 수행한다. 이번 문서화에서 실행하지 않았다.

## 작업 단위와 시작점

11/11의 지속 시험 공간은 개발 브랜치 운영과 별개다. 기존 시험 프로젝트 사본에서 설치, 문서 보존, 복구를 시험하기 위한 worktree/독립 clone 비교는 [수용 기준의 지속 시험 공간](../../verification/acceptance.md)에 통합했다. Windows 우선 환경 합의 뒤 독립 기준 clone, 빈 시험 WIKI를 준비했다. 실제 Codex/제품 시험은 아직이며 위 개발 브랜치 대안을 채택하거나 원본 Git을 변경하는 허가로 해석하지 않는다.

사용자의 [기본 모듈, 작업 단위 질문 — 「작은 작업과 커밋」](../../discussions/knowledge/requirements.md)을 연결한다. 앞의 해시들은 최초 검토 당시 관찰값이며 실제 개발 시작 시 다시 고정해야 한다. 사용자가 말한 출발점은 현재 구조의 재사용 부분에 합의한 독립화, 명명, 연결 준비를 반영한 모듈이다. 시작점의 대안은 [ADR 0009 — 「기본 모듈의 시작점」](../architecture/0009-repositories.md), 구성, 완료 조건은 [기본 모듈 — 「기본 모듈의 시작점」](../../design/module.md)이 소유한다.

기존 시험 프로젝트의 기존 구조 기준과 모듈의 준비 완료 기준을 각각 남기는 안을 추천한다. 작은 준비는 한 커밋으로, 큰 준비는 연결이 유지되는 여러 커밋으로 나눌 수 있으며 마지막 검증된 커밋부터 기능 개선을 시작한다. 원본 해시와 추출, 수정 범위는 현재 위키에 대응시켜 기존 구조와의 비교 근거를 보존한다. 실제 초기 커밋 수와 포함 파일은 개발 준비에서 협의한다.

각 기능의 사전 리뷰에는 기준, 선행 의존, 변경 범위, 영향받는 기존 동작, 검증, 복구 단위를 포함한다. 코드, 관련 문서/설정, 테스트를 함께 검토하고 큰 이름 변경은 동작 변경과 구분하되 필요한 참조 갱신을 빠뜨리지 않는다. 한 기능에 여러 커밋이 필요하면 대응 범위와 의존 순서를 남긴다.

11/09 사용자가 예로 든 세션 복구, 디버깅, 테스트/문서 검증, 동기화는 작업 주제의 예이며 현재 skill을 그대로 새 모듈 구성이나 커밋 경계로 확정한 것이 아니다. 완료된 설계의 책임, 의존 관계로 나누고, 하나의 변경을 이해, 검증하는 데 필요한 코드/설정/테스트/문서를 함께 묶는다. 코드와 WIKI가 모두 바뀌면 두 저장소의 실제 커밋/PR을 같은 작업에 연결한다. 작은 변경은 전체 기능보다 작을 수 있으나 쓸 곳 없는 선언만 분리하거나 연결이 깨진 상태를 완료 단위로 남기지 않는다. [Google의 작은 변경 기준](https://google.github.io/eng-practices/review/developer/small-cls.html).

작업 커밋과 배포 태그는 구별한다. 최초 필수 기능의 검증을 마친 릴리스를 v1.0.0으로 내고 이후 배포 단위로 태그를 붙이는 사용자 방향은 [이름과 변경 이력](../../design/module.md)에 반영했다. 배포 태그의 기준과 개별 Git 작업의 실행 시점은 구분한다.

원격에 공유된 작업의 취소 수단은 후속 비교한다. 새 되돌림 커밋, 과거 상태의 별도 재현, 원격 이력 재작성은 다른 동작이다. 후속 의존, 충돌, 두 저장소의 부분 반영을 무시한 즉시 복구 보장은 하지 않으며, 실제 복구 가능한 범위와 확인 절차를 [ADR 0017](../integration/0017-work-sync.md) 및 후속 복구 계약에 연결한다. 원격에 쓰는 작업은 현재 수행하지 않았다.

## 개발 시작부터의 Git 운영

11/11 사용자는 실제 개발 착수부터 모듈, 모듈 WIKI 저장소를 만들고 작업별 커밋을 쌓으며, 현재 커밋 skill과 PR 작성 방식을 활용하자고 제안했다. 기존 독립 기본 모듈, 두 저장소, 작업별 이력 합의의 실행 순서로 적절하다. 완성 후 최초 커밋으로 합치는 대신 준비 변경부터 이력을 남기는 방식을 추천한다. 브랜치는 위 11/23 선택과 11/24 보완을 따른다. 코드와 WIKI의 원격 주소는 개발 공간 문서에 확정했고 실제 공유/병합은 별도로 확인한다.

| 순서 | 진행할 일 | 남길 근거 |
| --- | --- | --- |
| 저장소 준비 | 모듈 코드와 개발 WIKI를 각각 독립 Git 저장소로 준비 | 저장소별 소유, 기준 브랜치, 추적 범위 |
| 기본 모듈 구성 | 필요한 독립화, 명명, 연결 준비를 검토 가능한 크기로 커밋하고 정한 최소 동작 확인 | 준비 완료 커밋과 해당 WIKI 버전. 빈 틀의 최초 커밋과 구분 |
| 기능별 개발 | 한 변경을 이해, 검증하는 데 필요한 코드, 설정, 테스트, 공식 문서를 같은 작업 단위로 관리 | 기준, 관련 커밋, 검증. 변경 없는 저장소에 빈 커밋을 요구하지 않음 |
| PR 검토 | 각 저장소의 실제 PR diff, 관련 결정, 검증 결과를 작성하고 상대 PR/커밋 연결 | 두 변경의 대응, 검토, 필수 CI, 부분 반영 상태. 승인/병합은 사람 담당 |
| 배포 | 필수 기능, 설치/보존/복구와 사용 안내의 완료 기준을 충족한 조합에 태그, 릴리스 연결 | 검증한 코드/WIKI 버전, 배포물, 사용자에게 필요한 변경 내용 |

저장소 생성, 커밋, 원격 push, 공개 전환, 릴리스는 서로 다른 동작이다. 개발 중에도 Git 이력을 남길 수 있고, 태그를 붙였다는 이유로 검증 전 상태가 배포 가능해지지는 않는다. 공개 시점은 기존 공개 범위와 준비 상태로 정하며 소비 프로젝트의 기존 브랜치 통합은 그 프로젝트의 실제 상태와 정책에 따라 검토한다. [작은 변경의 검토 기준](https://google.github.io/eng-practices/review/developer/small-cls.html), [태그와 GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

### 커밋과 PR 작성 기준

개발 커밋은 실제 staged diff, PR은 base 이후 커밋의 경위와 공통 조상부터 head까지의 최종 diff를 근거로 작성한다. 중간에 추가했다가 취소한 변경을 최종 동작으로 소개하지 않으며 미커밋 변경이나 미실행 검증을 포함하지 않는다.

제목과 본문 형식의 소유 위치는 코드 CONTRIBUTING의 「커밋 메시지」와 「PR 작성과 코드/WIKI 연결」이다. 요약, 관련 요구/결정, 실제 검증과 검토 초점을 남기고 변경에 불필요한 항목을 강제하지 않는다. WIKI PR도 같은 방식으로 문서 변화와 근거, 대응하는 코드 작업을 설명한다.

개발 초기에는 실행 도구로 두 저장소의 실제 커밋/PR을 연결하고 결과를 확인한다. [ADR 0017](../integration/0017-work-sync.md)의 제품 기능이 준비되고 실제 검증을 통과하면 같은 흐름을 자체 적용한다. 현재 운영을 제품의 원격 연계 기능 검증 성공으로 계산하거나 제품 자동화 완성을 개발 시작 조건으로 만들지 않는다. GitHub Projects는 공통 이슈 중심으로 운영하며 PR은 이슈의 정식 관계로 확인한다. PR 카드를 별도로 등록하지 않는 방향을 11/25 재확인했다. 구체 운영과 제출 전 요구사항 검토는 코드 CONTRIBUTING이 소유한다. 보드는 두 Git 이력, 권한, 커밋을 하나로 합치지 않는다. [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects).
