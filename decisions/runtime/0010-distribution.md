# ADR 0010: 모듈 배포와 설치 방식

- 날짜: 2026-10-28
- 설계 상태: `accepted` — 2026-11-11 Git 릴리스 + Python 설치와 갱신 도구 채택. 실행 배치는 ADR 0019, 보존 상세, 명령, 지원 버전은 후속 명세
- 구현 및 검증: 제품 미구현. 11/09 C의 같은 ID, 공유 상태 버전 유지 기준 실패 관측. 11/10 B Git/Python 14개 검사와 Codex 0.167.0 app-server의 부분 연결을 관측. 11/18 Windows 로컬 설정/명시적 sandbox/합성 Git 제외를 부분 확인. 일반 CLI의 제품 실사용, 실제 AI 사용, 원격 배포는 미검증이며 앞선 중첩 sandbox 제한은 별도 보존
- 상세: [모듈, 설치](../../design/README.md)

현재 실행 배치는 **프로젝트 내 설치로 채택한 [ADR 0019](0019-project-install.md)**를 따른다. 이 ADR에서 11/09 부분 채택한 외부 공통 실행본 배치만 대체하며 설치 수단, 보존의 나머지 판단까지 폐기하지 않는다. 11/10 재검토 이유와 11/11 결정은 [배치 재검토 — 「실행 구성의 배치 재검토」](../../discussions/history/install.md)에 연결한다. 아래 날짜별 외부 실행본 설명, 시험은 당시 판단의 이력이다.

후속 현재 결정: 11/18 [ADR 0022](0022-wiki-entry.md)의 전용 시작 명령 기본을 유지하고, 11/22 실제 비교 후 직접 접근 우선/MCP 후속 제공을 채택했다. 아래 일반 codex 기본 요구의 당시 기록 중 기본 진입 조건만 이 결정으로 보완한다. 프로젝트별 연결과 전역 설정 비변경, 열린 Codex 안의 경로 등록/변경과 기존 충분한 권한 재사용은 유지한다.

공식 SOT, 사용자 설치본 수정 자유, 기존 추적 정책, 로컬 상태 제외, WIKI 저장 선택은 유지한다. Git 비공개와 물리적 외부 배치를 같은 조건으로 취급하지 않는다. 제공 수단은 아래 11/11 결정으로 확정했으며 제품 구현은 아직이다.

11/11 사용자 확인으로 팀 공통 자산의 Git 공유 권장, 기존 추적 정책 보존과 [기존 진입점 + 전용 설치 영역 — 「기존 구성과 전용 설치 영역」](../../design/runtime/install.md)의 원칙도 채택했다. 정확한 이름/지원 경로, 공개 실행, 구체 업데이트 계약은 별도다. 임의 경로의 자동 호환, 무충돌 갱신을 보장하지 않으며 새 clone의 기준 확보와 사용자 파일 보존을 확인해야 한다.

11/13에는 [AGENTS 연결 A — 「AGENTS 연결 방식」](../../design/runtime/entry.md)를 채택했다. 기존 규칙을 재사용한 뒤 부족한 연결만 짧은 관리 구역에 두며, 충분한 기존 구성이 있으면 중복 삽입하지 않는다. 의미 충돌과 중요한 정책 변경은 사용자 확인을 거친다. B/C 대안, Direct 비용과 실제 행동 검증의 한계는 같은 명세에 보존한다. 이어 [제품 시작 명령의 외부 WIKI 권한 자동 연결 — 「외부 WIKI 권한과 시작 방식」](../../design/runtime/entry.md)을 채택했다. 기기별 경로를 해당 시작/재개에 전달하는 흐름이며 공유 Codex 설정에 개인 경로를 넣지 않는다. 정확한 설정/명령과 Windows 제품 구현/검증은 후속이다.

11/15 보충: 사용자는 채택한 시작 명령을 유지하면서 [일반 Codex 안의 연결 트리거 — 「일반 Codex에서 연결하기」](../../design/runtime/entry.md)로 WIKI 경로 등록/변경과 필요한 연결도 진행하길 원했다. 처음 기록은 확인/안내만 첫 배포에 포함한다고 좁혔으나, 사용자의 후속 설명에 따라 열린 세션 안에서 공통 연결 코드를 실행하는 범위로 보정한다. 저장된 설정은 재사용하고 없으면 필요한 입력을 받아 검사/저장하며 권한이 준비된 현재 세션에서 기능을 사용한다.

외부 진입과 내부 트리거가 같은 연결 코드/설정을 사용하므로 처리 중복을 줄일 수 있다. 11/15 검토에서 후속 후보는 **Codex 호스트 권한 설정의 자동 생성/병합**이었으며 모듈의 로컬 WIKI 경로 등록까지 미루는 뜻은 아니었다. 현재 첫 지원 조건은 아래 11/18 보정을 따른다. 현재 세션의 권한이 부족하면 지원되는 사용자 선택을 거치고, 세션 안에서 해결할 수 없는 경우에만 같은 세션의 제품 명령 재개를 대안으로 안내한다. 재개 안내를 내부 연결 성공으로 세지 않는다. 추가 설계나 구현 검증에서 문제 또는 더 나은 대안이 확인되면 근거와 영향을 대조한다. [승인 경계 — 「승인의 재사용과 한계」](../../design/runtime/entry.md)와 [명령 충돌 방지 — 「명령 이름과 충돌 방지」](../../design/module.md)는 유지하며 현재 권한/설정 변경, 제품 구현이나 Windows 검증을 마친 것은 아니다.

11/18 사용 흐름 보정: 최초 설치/기기 준비 뒤 **일반 `codex`와 평소 요청만으로 조건부 하네스를 사용하는 방향을 사용자 수용으로 반영했다.** 외부 WIKI 연결도 변경 전까지 저장/재사용하며 별도 연결 명령으로 재설정한다. 11/13 제품 시작 명령은 선택 수단으로 유지한다. 11/15에 후속으로 둔 호스트 설정 자동화를 이유로 첫 지원 환경의 지속 연결 준비까지 미루지 않는다. 당시 [권한 배치 후보 — 「지속 권한 설정의 배치」](../../design/runtime/entry.md)는 프로젝트의 선택 이름과 사용자 설정의 정의를 나눴으며, 같은 날 아래 제약과 후속 요구에 따라 프로젝트 로컬 설정으로 보정했다. 기존 sandbox/사용자 정책, 새 팀원과 여러 작업 사본의 제약은 계속 확인한다. 다른 프로젝트로의 기본 권한 확대 방지, 기기 경로의 비공유, 기존 설정과 관리자 정책 보존을 검증해야 한다. 채택한 사용 방향과 구체 후보의 Windows 검증 완료는 별개다.

같은 날 [격리 설정 조회](../../evidence/experiments/runtime/2026-11-18_10-36-06-windows-config.md)에서 A/B의 선택과 함께 기본값 없는 미사용 프로젝트/프로필 미등록 기기의 시작 오류를 관측했다. 사용자 요구는 유지하고 구체 배치를 보완한다. 전역 기본값 추가나 config 제외 정책을 새로 채택한 것이 아니며 실제 사용자 설정은 변경하지 않았다.

11/18 후속 필수 조건: **모듈의 모든 과정에서 Codex 전역 설정을 생성/수정/삭제하지 않는다.** 전역 프로필 등록이나 기본 sandbox 변환으로 앞선 오류를 해결하지 않는다. 사용자는 프로젝트 로컬 설정 방향을 우선 진행하되 Git 노출과 수동 제외의 부담을 줄이길 요청했다. 이후 사용자 config의 소유와 추적 전환 문제를 지적해, 파일 전체 자동 제외/생성의 범용 기본 추천은 철회했다. 기존 충분한 권한을 먼저 재사용하고, 로컬 전용 운영을 명시적으로 선택한 경우에만 자동 제외 후보를 검토한다. 공통 원본에서 생성하는 안도 선택 가능한 미채택 비교안이다. 상세는 [설정 소유와 공유 상태의 전환](../../design/runtime/entry.md)이 소유한다. 새 공유 상태의 호환성을 검증한 것은 아니며 기존 `.harness/` 공유 제외와 일반 Codex 사용 방향은 유지한다.

[새 Windows 시험](../../evidence/experiments/runtime/2026-11-18_11-03-32-project-permissions.md)에서는 로컬 배치의 설정 조회 10개, 명시적 sandbox의 쓰기/재읽기 5개와 거부 4개, 자동 제외의 3가지 입력을 확인했다. 실제 사용자 config는 전후 동일했고 모델은 호출하지 않았다. 일반 TUI/세션 재개와 제품 연결기의 보존/갱신까지 검증한 결과는 아니다.

## 문제

11/12 사용자 요청으로 [의존성 준비와 설치 재개](../../design/runtime/install.md)를 보강했다. 필수/선택 준비물을 공식 README에 안내하고 누락 시 임의 설치 없이 멈춘다. 사용자 준비 후 같은 계획을 재실행하면 여전히 유효한 완료 결과를 유지하며 설치와 이식의 최종 연결 검증까지 이어간다. 정확한 명령, 구현, 검증은 후속이다.

독립 모듈을 다른 프로젝트에서 사용할 때 루트 지침, skill, hook, 설정을 실제 발견 가능한 위치에 배치해야 한다. 애플리케이션 라이브러리 의존성과 개발 도구 설치를 혼동하면 언어 결합이나 별도 설치 절차가 남는다. 모듈 개발 원본과 프로젝트에 필요한 설치 결과의 소유를 구분해야 한다.

## 추가된 사용자 조건 — 2026-10-29

최소 구성과 원하는 기능을 처음부터 선택하고, 이후에도 사용자 요청으로 다른 제공 기능을 추가할 수 있어야 한다. 최초 설치가 향후 기능 선택을 제한해서는 안 된다. [기능 선택과 추가](../../design/module.md)가 요구와 미정 사항을 소유한다. 이 조건의 확정은 아래 설치 스크립트, plugin, Git 관리 방식 중 하나를 채택한 것이 아니다.

## 대안

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 애플리케이션 라이브러리 import | 익숙한 의존성 관리 | 앱 언어/런타임에 결합, 지침, hook 배치를 해결하지 못함 |
| B | 고정 버전 배포물과 설치 스크립트 | 루트 배치, 차이, 보존, 복원을 직접 관리 | 설치/업데이트 계약 구현 필요 |
| C | Codex plugin과 프로젝트 설정 절차 | 공식 skills/hooks 배포 기능 활용 | 프로젝트 문서 보존, 루트 연결, 버전/신뢰 확인은 별도 필요 |

## 추천

11/11 사용자가 [Git 릴리스 + Python 관리 도구 — 「배포 도구」](../../design/runtime/install.md)를 첫 제공 수단으로 선택했다. 공식 릴리스의 도구를 프로젝트 밖에서 실행해 설치/갱신하고 평소에는 프로젝트 파일을 사용한다. 설치 도구, 자료는 같은 공식 릴리스로 묶으며 사용자 수정에 별도 공식 버전을 요구하지 않는다. 정확한 배포 이름, 지원 Python/Git, 명령, 경로, 공개 시점은 아직 정하지 않았다.

선정 이유는 첫 배포 기한에서 별도 패키지 관리자, 레지스트리 준비를 줄일 수 있다는 판단이다. 11/11 첫 환경을 [ADR 0020](0020-windows.md)의 Windows로 바꿔도 Git 릴리스 + Python 제공 원칙은 유지하며 실제 준비, 실행은 해당 환경에서 검증한다. 사용 편의만으로 최선이라고 주장하지 않는다. uv는 Git 출처의 도구 설치, 격리, 짧은 명령, 갱신을 제공하며 공개 PyPI 등록도 필수가 아니다. 이번 선택은 다운로드, 압축 해제, 도구 교체 절차가 남는 비용을 감수한다. 11/11 후속 확인으로 uv/npm은 이후 버전에서 필요할 때 검토하며 첫 제공에 포함하지 않는다. 이후 패키징을 바꿔도 설치/보존 로직은 재사용할 경계를 유지한다. 비교 근거와 흐름은 위 상세가 소유한다.

채택은 제공 수단에 한정한다. [ADR 0011](0011-preservation.md)의 적용/복원 상세나 제품 구현, 원격 공개의 승인이 아니다. 이전 공통 코드 중복 감소, 공수, 사용성의 정량 효과는 미측정이며, 다음 기록은 당시 추천과 변경 이유로 보존한다.

11/09 용어 보정: 임시 설치 도구, 다운로드 자료와 설치 후에도 사용하는 하네스 실행 구성을 구분한다. 프로젝트에는 필요한 연결, 설정을 남기고 임시 자료는 제거할 수 있다. 상시 실행에 필요한 공통 파일은 외부에 유지하는 경계를 사용자 확인으로 반영했다. [수명, 보관 비교 — 「설치 결과의 소유와 공유」](../../design/runtime/install.md)가 상세를 소유한다. 아래 B는 설치 스크립트의 프로젝트 내 영구 보관을 요구하지 않는다.

같은 날 후속: 설치, 조회, 갱신을 같은 관리 도구로 제공하고 그 도구는 프로젝트 밖에 두는 안을 추천한다. [버전 확인과 실행 도구](../../design/runtime/update.md)가 외부 설치/임시 실행, 관리 도구 자체와 적용 프로젝트의 버전 구별을 소유한다. 자동 조회는 가능하나 무인 적용, 패키지 관리자, 정확한 명령은 미채택이다. 최초 설치도 예상 도메인의 빈 문서를 전부 만들거나 전체 역공학을 자동 실행하는 뜻이 아니다.

초기에는 B와 필요한 공통 실행 파일, 지침, 설정, 버전 기록의 프로젝트 Git 포함을 함께 추천했다. 새 clone에서 파일을 함께 받는 편의를 우선한 판단이었고 모듈 전체 개발 저장소를 넣자는 뜻은 아니었다. 그러나 외부 고정 버전 준비가 복사본의 갱신, 충돌 관리보다 더 부담이라는 실측은 없었다.

11/09 기업 실무 질문을 조사한 뒤, 공통 기능과 프로젝트별 자산을 나누는 추천으로 보정했다. 공개 사례는 채택률 통계가 아니며 대규모 기업의 중앙 서버를 그대로 도입할 이유도 아니다. 여러 프로젝트의 중복, 갱신 부담을 줄이되 같은 버전 준비, 도구 발견, 권한, 복원을 확인해야 한다. [실무 사례와 보관 경계](../../discussions/history/install.md)가 공식 근거, 수정 추천, 남은 비용을 소유한다. 필요 시 프로젝트 복사안을 좁게 선택할 수 있다.

공식 문서는 재사용 skill 배포에 plugin을 권장하고 hooks/setup skill도 설명한다. 대상 WSL CLI의 실제 plugin hook 지원은 별도 확인해야 한다. 고정 릴리스, 설치 계획, 원문 보존은 유지할 제안이며 B와 C 모두 이를 구현할 수 있다. 기존 WIKI 보존만을 이유로 C를 후속으로 배제하지 않고 실제 지원 클라이언트의 제약으로 수단을 선택한다. 두 배포 경로를 동시에 구현하는 비용은 피한다. [Skills](https://learn.chatgpt.com/docs/build-skills), [Plugin packaging](https://developers.openai.com/plugins/build/plugins).

기존 `AGENTS.md`, WIKI, 공유 hook 설정은 파일 전체를 덮지 않는다. 필요한 변경 계획과 원문 해시를 확인한 뒤 적용한다. 상세 보존 계약은 [ADR 0011](0011-preservation.md)이 소유한다.

11/09 후속 질문: 외부 설치의 자동 발견, 토큰 차이, AGENTS의 위치/추적 선택, 초기화 뒤 프로젝트 종속성을 함께 검토했다. [자동 연결 — 「외부 설치의 자동 연결」](../../discussions/history/install.md), [추적 선택 — 「AGENTS와 Git 추적 선택」](../../design/runtime/install.md), [프로젝트 값 — 「프로젝트별 값의 연결」](../../design/runtime/install.md)에 통합했다. 외부 파일의 존재만으로 자동 사용을 보장하지 않으며 프로젝트 정책 보존을 모든 미지원 배치의 호환 보장으로 확대하지 않는다. 사용자가 이 경계를 확인했지만 구체 연결 수단, 구현은 미채택이고 토큰 효과도 미측정이다.

이어 사용자가 필수 기능의 v1.0.0 배포, 검증과 구현 현실성을 재확인했다. [첫 배포 수단 비교](../../discussions/history/install.md)는 C의 작은 호환성 시험을 우선 제안하고, 버전 고정, 연결/복원 조건을 충족하지 못하면 B를 검토하도록 했다. 둘을 동시에 구현하지 않는다. 11/09 후속 진행에서 모델 없는 로컬 설치 시험을 수행했다. 루트 manifest만으로는 실패했고 호환 manifest를 추가해 설치, 재실행, 이전 자료 재설치, 제거를 확인했다. 같은 plugin 갱신 시 이전 캐시가 사라져 프로젝트별 버전 유지 시험을 이어갔다. 상세와 원시 근거는 [시험 — 「plugin 호환성 시험」](../../discussions/history/install.md)에 연결한다. Git 배포 방향은 어느 수단에서도 유지한다.

같은 날 2차 시험에서는 고정 출처를 프로젝트별로 지정해도 같은 plugin ID, 공유 상태에서 한쪽 갱신이 다른 쪽의 설치본을 바꿨다. native `skills/list`도 프로젝트가 고른 버전과 다른 경로/본문을 반환했다. 명령 실행 성공과 우리 버전 유지 기준 FAIL을 구분한다. 이에 B를 현재 추천으로 바꾸되 다른 ID/상태 분리 대안까지 불가능하다고 확정하지 않는다. 사용자는 B가 설계, 요구사항에 맞는지 질문했으며 아직 채택 전이다. [요구사항 대조 — 「유지할 요구와 남은 책임」](../../design/runtime/install.md)에 설치, 연결, 갱신 책임과 남은 검증을 통합했다. B 구현이나 실제 모델/hook 호출로 넘어가지 않았다.

후속 재검토: [갱신 방식과 배포 수단](../../discussions/history/install.md)은 사용자 수정 파일의 3방향 비교와 설치 버전/발견 책임을 구분한다. 이 갱신 방식으로 C의 공유 설치 상태 문제가 해결되지는 않아 B 추천을 유지한다. 앞선 루트 manifest 시험의 입력 누락과 프로젝트 비활성화/설치본 제거의 구분을 [시험 해석 — 「plugin 호환성 시험」](../../discussions/history/install.md)에 보정했다. plugin 결함이나 모든 형식, 클라이언트의 미지원으로 일반화하지 않으며, 구체 설치 수단, 자동 반영 범위의 채택 상태는 유지한다.

이어 단일 SOT와 버저닝 주체를 재확인했다. 공식 배포/버전 발행은 모듈 유지보수자가 맡고, 적용 프로젝트는 설치 출처를 기록할 수 있지만 사용자 편집에 별도 모듈 버전을 요구하지 않는다. 설치본 수정 금지로 읽힐 표현은 [갱신과 복원](../../design/runtime/update.md)에서 보정했다. 이 설명 중 외부 참조와 프로젝트 독립 설치를 다시 선택하도록 물었으나, 사용자는 원래 논의하던 방식이라고 지적했다. 이에 배치 재선택 질문을 철회하고 기존 공통 외부 도구, 프로젝트 소유 지침/설정 경계를 유지한다. 새 정책 채택이 아니며 설치 수단 B의 미채택 상태도 임의로 바꾸지 않는다.

같은 협의의 실무 비교에서는 GitHub Spec Kit의 프로젝트 스크립트 설치, Gradle Wrapper의 외부 배포본 사용, Stripe의 규칙/공통 도구 분리를 대조했다. 채택률 통계로 일반화하지 않고 [실무 사례와 보관 경계](../../discussions/history/install.md)에 기존 경계의 근거로 연결했다. 모든 skill/hook의 외부 보관이나 두 설치 모드 동시 구현을 뜻하지 않는다. 공식 업데이트의 사용자 편집 보존은 기존 요구에 따른 검증이며, 이를 사용자별 버전 관리, 별도 원본, 추가 자동 병합 기능으로 확대하지 않는다. 다음은 기존 설치 수단, 연결, 보존 협의로 복귀한다.

11/08 B 공유 제외, 설치기의 자동 생성/보강, 검사 방식을 채택했다. 최초 설치, 후속 기능 추가, 경로 변경에 같은 절차를 사용하고, 모듈 관리 구간을 `.gitignore` 맨 아래에 두며 기존 규칙, 사용자 편집을 보존한다. `.harness/`는 로컬 자료 전용으로 전체 제외하고 공유 자산은 밖에 둔다. 상태 파일은 제외 검증 후 생성한다. 기본 상태 경로와 WIKI 경계는 ADR 0016, 상세 절차는 [제외 규칙의 자동 설정](../../design/workflow/recovery.md)이 소유한다. 이 범위의 채택을 배포 수단 전체의 채택이나 실제 설치 구현 완료로 확대하지 않는다.

11/05 경계 보강: 대상의 코드 루트, WIKI 루트, 역할별 문서 위치를 등록하고 도구별 실제 지침 발견 경로에 연결하는 안은 [프로젝트 WIKI 연결](../../design/knowledge/wiki.md)에 둔다. 내부 docs와 외부 vault를 지원하되 저장 위치, 기기별 권한, AI 분석, 실행 상태 생성을 구분한다.

## 확인 조건

11/10에는 B의 [구체 설치 후보 — 「배포 도구」](../../design/runtime/install.md) 중 Git 배포본 + 작은 Python 도구의 검증 진행을 사용자가 수용했다. [최소 검증 — 「B안의 최소 검증」](../../discussions/history/install.md) 1~3의 14개 검사로 버전 독립, 연속 갱신, 편집 보존, 실패 복원을 확인했다. 이어 4의 [Codex 연결 시험 — 「Codex 연결 시험 결과」](../../discussions/history/install.md)에서 선택한 skill 발견, hook 신뢰/재신뢰, app-server를 통한 시작/재개, 중복/해제를 관측했다. 외부 배포본과 프로젝트 입력의 경계는 유지하며, 중첩 sandbox의 timeout은 별도 제한으로 남긴다. 이 결과로 B 추천을 유지하지만 최종 설치 수단 채택, 제품 구현, 일반 CLI의 전체 사용 검증으로 확대하지 않는다.

이후 [설치 구성표 — 「설치 결과의 소유와 공유」](../../design/runtime/install.md)에 자산, 프로젝트 입력, 로컬 상태의 소유와 갱신 책임을 묶고, [실사용 검증 상태 — 「구성별 검증 상태」](../../design/runtime/install.md)와 [설치 이후 흐름 — 「설치부터 평소 사용까지」](../../design/runtime/install.md)을 작성했다. 당시 추천한 Git/Python 도구의 책임은 배치 재검토를 거쳐 11/11 ADR 0019와 위 제공 수단 채택에 맞춰 정리했다. 기존 부분 시험을 새 배치의 실제 사용 성공으로 계산하지 않는다. 첫 배포 기능표는 [ADR 0007 — 「첫 배포의 책임과 보류 항목」](../architecture/0007-release-scope.md)에서 협의하며 제품 구현은 아직이다.

- 11/05 요청: 설치와 AI 기반 WIKI 분석의 책임을 구분하고 최초/후속 요청, 범위 제한, 중단 재개를 설계한다. [모듈의 책임 구분 — 「설치와 AI 분석」](../../design/knowledge/wiki.md)에 연결했다. 이 요구는 설치 B안 채택이나 분석 실행 인터페이스 확정이 아니며 파일 복사만으로 지식 복원을 완료했다고 판단하지 않는다.

- 11/02 도구 지원 원칙은 [ADR 0015](../integration/0015-agent-support.md)에서 채택했다. 공통 규칙, 데이터와 도구별 발견, 권한, hook 연결을 구분하며 이 ADR의 구체 설치 수단을 대신하지 않는다. 외부 문서, 예비 문서 연결/로컬 상태는 [ADR 0016](../knowledge/0016-storage.md), 문서 Git의 작업 연결은 [ADR 0017](../integration/0017-work-sync.md)이 채택 범위와 미확정 상세를 소유한다. 예비 문서 연결 완료를 제품 설치 성공으로 계산하지 않는다.
- 대상 루트의 AGENTS, skill, hook을 실제 지원 버전에서 발견, 실행해야 한다. 현재 공식 repo skill 경로는 `.agents/skills`이며 기존 `.codex/skills`의 다른 설치 호환성은 별도 확인한다.
- 프로젝트 hook의 신뢰를 자동 우회하지 않고 중복 출처 실행을 검사한다. [Hooks](https://learn.chatgpt.com/docs/hooks).
- 설치와 갱신, 재실행, 충돌, 중간 실패, 복원, 제거와 새 clone의 재현을 시험한다.
- 최소 설치, 최초 선택 설치, 후속 기능 추가를 각각 확인한다. 기능별 의존성, 호환성, 활성화와 배포 묶음은 합의한 범위로 시험하고, 선택 기능의 부재를 전체 실패나 검증 PASS로 오인하지 않는다.
- 팀 공통 자산의 Git 공유 권장은 ADR 0019를 따른다. 기존 추적 정책의 실제 처리, 정확한 위치/이름, 언어, 지원 버전, 공개 저장소/라이선스는 해당 구현 전에 확정한다.

코드, 저장소, 배포물은 아직 만들지 않았다. [ADR 0009](../architecture/0009-repositories.md)의 원본 분리 추천을 구체화하며 기존 구조의 변경 허가를 뜻하지 않는다.
