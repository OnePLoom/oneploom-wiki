# ADR 0023: Python 표준 규격을 이용한 기기 명령 등록

- 날짜: 2026-11-23
- 설계 상태: `accepted` — 사용자가 표준 등록안으로 진행하도록 명시했다.
- 구현 및 검증: 설계 채택과 후속 명세. 패키지 생성, 기기 등록과 Windows 제품 검증은 미완료다.
- 관계: [ADR 0010](0010-distribution.md)의 Git Release + Python, [ADR 0019](0019-project-install.md)의 프로젝트 내 실행, [ADR 0022](0022-wiki-entry.md)의 직접 접근 우선을 유지한다.
- 상세: [등록 방식 — 「등록 파일 형식의 비교」](../../design/runtime/entry.md), [중단 복구 — 「등록과 갱신의 중단 복구」](../../design/runtime/entry.md), [수용 조건 — 「짧은 명령 등록의 검증 입력」](../../verification/acceptance.md).

## 문제와 근거

프로젝트에 실행 파일을 설치하는 것만으로 어느 하위 폴더에서든 `oneploom`을 입력해 실행할 수 있는 것은 아니다. 사용자는 짧고 고유한 명령, 기존 도구와 설정의 보존, 통용 규약에 맞는 배포를 원한다. 평소 실행은 인자 없는 `oneploom`과 `oneploom start`가 같은 처리를 사용해야 한다.

[PyPA의 console_scripts](https://packaging.python.org/en/latest/specifications/entry-points/#use-for-scripts)는 Python 패키지의 실행 진입점을 Windows 콘솔 실행 파일로 연결하는 규격이다. 이 규격은 PATH 등록이나 모든 셸의 인자 보존까지 보장하지 않는다. 기존 `.cmd` 전달의 해석 문제를 작은 문자열 수정으로 계속 보완하기보다 표준 명령 등록을 사용하고 실제 인계를 따로 검증한다.

## 대안과 결정

| 대안 | 이점 | 비용과 판단 |
| --- | --- | --- |
| 격리 환경에 로컬 wheel을 설치하고 표준 명령 생성 | 알려진 Python 패키지 규격과 콘솔 입출력을 사용. 프로젝트별 본체를 유지하면서 한 명령으로 연결 | **채택**. venv/pip 준비, 용량, Python 변경 뒤 복구와 기기 등록 관리가 추가됨 |
| 작은 `.cmd` 시작 파일 | 작고 읽기 쉬우며 패키지 설치 단계가 적음 | 셸의 추가 해석과 특수문자 전달 검증이 남음. 단순 전달만으로 안정성을 확정할 수 없어 기본으로 채택하지 않음 |
| 자체 Windows 실행 파일 | Python 명령 등록을 거치지 않는 진입점 | 빌드/CPU 대상/바이너리 배포와 유지보수가 늘어 현재 필요보다 비용이 큼 |
| 프로젝트 실행 파일의 명시 경로 | 기기 등록 없이 실행 가능 | 경로 입력이 필요하므로 평소 기본 명령의 대체가 아니라 항상 남길 대안 |

Git Release에 연결 프로그램의 작은 wheel을 포함하고, 선택한 Python의 별도 가상환경에 로컬 설치한다. OnepLoom 명령 하나만 사용자 전용 bin에 노출한다. 가상환경의 Scripts 전체를 PATH에 넣거나 매번 활성화하도록 요구하지 않는다. 실제 파일 복사/실행 방식은 Windows 검증을 거쳐 확정한다.

기기 프로그램은 현재 프로젝트를 확인해 그 안의 실행본에 인계한다. WIKI 연결, 조건부 하네스와 프로젝트별 처리는 계속 프로젝트의 `oneploom/`에 있다. 예를 들어 A에서 실행하면 A의 WIKI, B에서는 B의 WIKI를 사용하며, 준비되지 않은 C에서 마지막 프로젝트를 대신 선택하지 않는다.

같은 날 후속 [ADR 0024](0024-project-selection.md)에서 프로젝트 밖의 등록 목록 선택과 명시적인 선택 화면을 추가했다. 선택은 실행별로 적용하며 프로젝트 안의 바로 시작은 유지한다. 명령 설치 방식의 변경은 아니며 사용자별 경로 목록을 `registration.json`의 명령 소유/복구 기록이나 전역 WIKI 설정과 합치지 않는다.

## 감수하는 비용과 보호 조건

- venv/pip 사용 가능 여부와 추가 용량/시간을 사용자 준비 조건에 넣는다. 부족하면 알려 주고 멈추며 무단 설치나 외부 의존성 다운로드로 우회하지 않는다.
- Git Release와 공식 버전의 단일 관리 원본은 유지한다. PyPI 공개, uv/npm/pipx 설치, 프로젝트별 임의 버전과 상시 서버는 추가하지 않는다.
- 새 등록 환경은 최종 위치에 준비하고 검사한 뒤 명령을 전환한다. 기존 정상 환경과 복구 자료는 필요한 동안 보존하며 파일 교체/기록/PATH를 하나의 원자적 변경으로 간주하지 않는다.
- 한 프로젝트의 제거와 기기의 공용 명령 제거를 구분한다. 기존 사용자 PATH 항목, 동명 명령, Python 환경, Codex 전역 설정과 셸 정책을 임의로 덮거나 지우지 않는다.
- Python 삭제, 파일 사용 중, 불명확한 소유, 외부 설정 변경과 중단 뒤의 대응이 필요하다. 등록 기록/기존 DB 참조와 프로젝트 인계 형식은 아래 후속 명세로 연결하며 실제 구현/호환 검증은 남아 있다. 상시 기기 DB를 이번 결정으로 도입하지 않는다.
- 규격 활용과 외부 구현 코드의 복사는 다르다. 실제 생성/동봉할 파일의 출처, 버전과 고지는 배포 전 별도로 확인한다.

## 등록 정보와 작업 기록의 구체화

11/23 후속 진행에서 [등록 정보의 최소 필드 — 「기기 등록 정보와 소유」](../../design/runtime/entry.md)와 [기존 DB 연결 — 「등록 작업과 기존 DB의 연결」](../../design/runtime/entry.md)을 명세했다. 이는 채택한 표준 등록을 구체화한 것이며 기기 등록을 실행하거나 새로운 진행 엔진을 도입한 결과는 아니다.

OnepLoom 사용자 프로그램 영역의 `registration.json`은 마지막 확인한 명령/환경과 PATH 소유, 미완료일 때의 작업 참조만 갖는다. 패키지/Python의 표준 메타데이터를 우선 사용하며 단계/결과와 프로젝트별 WIKI 목록을 복제하지 않는다. 정상 사용은 첫 프로젝트나 과거 설치 기록에 의존하지 않는다.

프로젝트 설치 중의 등록은 기존 DB에서 별도 작업으로 구분한다. 프로젝트 없는 기기 복구는 기존 외부 최초 보존 절차로 그 작업을 기록하고 프로젝트 인계 없이 보존/명시적 정리를 적용한다. 프로젝트 전체 복원과 기기 명령 제거를 섞지 않으며, 미완료 등록이 참조하는 DB/자료는 이동하거나 정리하지 않는다.

패키지 메타데이터만 쓰는 안은 OnepLoom이 추가한 bin/PATH와 중단 참조를 충분히 설명하지 못한다. 반대로 상시 기기 DB나 JSON 단계 기록까지 추가하면 기존 진행 원본과 책임이 겹친다. 현재 명세는 작은 등록 정보와 기존 작업 기록을 연결하는 쪽이다. 그 대가로 기록/파일/PATH 사이의 중단 대조가 필요하고, 상세 기록을 정리하면 그에 의존한 과거 복원도 제한된다.

기기 파일/PATH의 효과는 현재 파일용 DDL의 범위 밖이다. [저장 경계의 확장 요구 — 「기기 등록 효과의 저장 경계」](../../design/workflow/storage.md)를 명시했으며 실제 저장/검증을 연결하기 전 등록 구현 완료로 판단하지 않는다. 기존 SQL의 통과 기록을 이 기능의 근거로 재사용하지 않는다.

같은 날 [프로젝트 실행본의 발견과 인계](../../design/runtime/project-entry.md)를 명세했다. 사용자 지정 상대 위치는 기존 로컬 연결에 두고 프로젝트 목록에는 복제하지 않는다. 기기 명령과 프로젝트 코드의 파싱/검사 책임, Python/인자/호출 폴더/입출력의 전달, 호환 불명/실패 시 대안을 연결했다. 실제 Windows 실행과 서로 다른 공식 릴리스의 호환 검증은 남아 있다.

## 첫 준비 자료의 배포 결정

11/23 처음에는 팀원 준비를 줄이기 위해 연결용 wheel을 프로젝트 설치 결과에 함께 넣는 상세를 제안했다. 이후 사용자가 외부 라이브러리/도구의 실제 배포 관행과 팀원별 준비를 다시 질문했고, [공식 사례 조사](../../discussions/runtime/distribution.md)에서 사용자별 최초 등록과 프로젝트별 재설치를 혼동한 점을 보정했다.

같은 날 전체 문서 정리 요청은 근거와 요구사항을 다시 대조한 뒤 추천이 여전히 타당하면 그 방향으로 진행하도록 위임했다. 이에 **B안인 공식 Release의 사용자별 명령 준비, 적용 프로젝트 Git의 wheel 기본 제외를 채택한다.** 표준 wheel/전용 환경 등록과 프로젝트 안의 편집 가능한 하네스는 유지한다. uv/npm/PyPI 배포나 외부 하네스 본체로 전환하는 결정은 아니다.

이후 사용자가 “그럼 B안으로 진행하자. 이어서 진행해줘”라고 명시적으로 확인했다. 앞선 조건부 위임에 의한 채택과 이 확인을 구분해 기록하며 같은 선택을 다시 묻지 않는다.

최초 담당자는 프로젝트 설치 안에서 명령까지 준비하고, 팀원은 각자의 Windows 계정에서 `command install`을 한 번 실행한 뒤 각 프로젝트의 WIKI를 연결한다. 이미 유효한 명령은 여러 프로젝트에 재사용한다. 최초 다운로드와 계정별 준비는 필요하지만 패키지 파일의 반복 커밋, 프로젝트별 wheel 갱신과 첫 프로젝트에 대한 수명 의존을 피한다. 오프라인 새 기기에는 사전에 확보한 배포 자료가 필요하다.

[배포와 팀원 흐름 — 「팀원 첫 준비의 배포 자료」](../../design/runtime/install.md), [관리 명령 — 「시작 명령만 처음 준비하기」](../../design/runtime/management.md)이 현재 명세의 원본이다. 이전 동봉안/당시 조사 결과는 [관측 기록 (정리 전 기록)](../../evidence/experiments/design/2026-11-23_07-38-22-wiki-reconcile.md)에 보존한다. 이번 결정과 정적 문서 검사는 제품 구현이나 실제 Windows 성공을 뜻하지 않는다.

## 검증과 남은 한계

설치 준비물 확인부터 새 터미널의 명령 발견, A/B 프로젝트 선택, 지원하는 두 Codex 설치 형태의 대화형 실행까지 연결해 검증한다. 인자, 종료/취소, Python 변경, 등록/갱신 중 중단, 이전 연결의 복원과 제거를 포함한다. 도움말 실행이나 문서 검사만으로 이 조건을 통과 처리하지 않는다.

추가 시간과 디스크 비용, Windows 교체/복구 동작은 아직 미측정이다. 사용자는 안정성을 위해 더 시간을 쓰는 방향을 요청했지만 무결함, 무중단이나 모든 사용자 환경의 호환성을 보장하는 결정은 아니다. 필수 요구와 실제 환경 검증을 유지하고 남는 한계는 명시한다.
