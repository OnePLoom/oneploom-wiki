# ADR 0011: 기존 문서와 기록 보존

- 날짜: 2026-10-28
- 설계 상태: `accepted` — 2026-11-11 기본 보존/복구 원칙 채택. 11/16 업데이트 재시도 또는 이전 구성 사용 선택 추가 채택. 상세 구현, 검증은 후속
- 구현 및 검증: 구현과 검증 모두 미완료
- 사용자 확정 조건: 처음부터 쌓인 WIKI, ADR를 도입 과정에서 비의도적으로 변경, 유실하지 않는다.

11/12 보강: 필요한 준비물을 안내하고 중단한 뒤 사용자가 조치, 재실행하면 [같은 계획의 유효한 완료부터 이어간다 — 「의존성 준비와 설치 재개」](../../design/runtime/install.md). 이는 기존 독립 완료 보존의 구체화다. 입력/산출물 변경이나 불확실한 효과를 무시하는 생략, 전체 자동 롤백, 실패한 검사의 PASS 전환은 허용하지 않는다.

## 문제

기존 시험 프로젝트는 새 역공학 출력처럼 취급할 빈 프로젝트가 아니다. 전체 재생성, 폴더 정리, AGENTS 교체는 사실, 결정 이력, 참조, 진행 상태를 잃게 할 수 있다. Git만으로 미추적/ignored 자료까지 복구할 수 없으며 기존 `.codex` 파일도 새 설치기의 소유가 아니다.

## 대안

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 전체 재생성 후 diff 검토 | 형식 통일이 쉬움 | 의미 손실, 이력 훼손, Git 밖 자료 복원 불가 |
| B | 원문 보호와 별도 변경 후보 | 기존 지식을 지키며 필요한 보정만 확인 | 기존 규칙 충돌은 별도 검토 필요 |
| C | 기존 문서를 복사해 새 WIKI 운영 | 원본 사본이 남음 | 두 원본, 참조, 갱신 불일치 부담 |

## 추천

11/11 B의 원문 보호, 별도 후보와 아래 단위별 보존/복구 원칙을 채택했다. 기존 파일은 읽기, 분석 대상으로 삼고 새 후보를 별도로 작성한다. 보호 파일 해시, 설치 계획, 허용 변경 목록을 만들고 적용 직전 다시 대조한다. 충돌, 계획 후 편집, 중복 설치는 멈추며, 적용 후 원문, 링크, 실제 연결을 확인한다.

기존 지침의 수정이 필요하면 차이를 검토한 별도 이전 작업으로 다룬다. override로 기존 규칙을 가리거나 내용을 자동 정리하지 않는다. 기존 ADR 번호, 상태, 날짜, 내용과 진행 중 followup을 초기화하지 않는다. 설치 완료와 새 기능의 활성화를 구분한다.

복원은 설치가 바꾼 파일만 다루며 이후 편집을 덮지 않는다. 업데이트 비교용 공식 기준과 복구용 적용 직전 상태를 구분해 사용자 미커밋 수정도 지킨다. 여러 파일의 부분 적용, 복원 실패를 감지하고 완료로 표시하지 않는다. 백업의 존재로 비의도적 원문 변경을 정당화하지 않는다.

11/09 갱신 보강: [변경분과 충돌의 판정](../../design/runtime/update.md)은 이전 배포 기준, 현재 파일, 새 후보를 비교한다. 사용자 편집, 공유 설정, 기존 WIKI와 모듈 소유 부분을 구분하고, 변경 파일만 적용하더라도 의존하는 구성의 일관성을 함께 검증한다. 템플릿 갱신은 기존 지식의 재작성 허가가 아니며 기준 부재, 양쪽 변경, 규격 이전 실패는 자동 덮어쓰기로 해결하지 않는다.

11/11에는 [적용 순서와 실패 처리](../../design/runtime/update.md)를 구체화했다. 후속 질문으로 완료 보존, 실패 복원, 남은 작업의 자동 실행을 [적용 단위와 부분 완료](../../design/runtime/update.md)에서 구분했고, 사용자가 문제 보고, 사용자 협의, 해결 후 재개 흐름을 확인하며 진행에 동의했다. 채택 범위는 **검증된 독립 단위 유지 + 실패 즉시 보고/남은 적용 중단 + 실패 단위의 허용된 안전 복원 + 합의 후 해결, 재개**다. 프로젝트 전체나 과거 작업을 되돌리는 정책이 아니며, 파일 하나의 쓰기 성공도 독립 완료로 보지 않는다. 공통 규격, 진입점, 새/옛 구성 호환성 때문에 분리할 수 없으면 같은 단위로 다룬다.

[실패 단위 복구 — 「실패 뒤 복구 방식」](../../design/runtime/update.md)는 실행 중 감지한 실패에 한정한다. 적용 계획에서 복원을 미리 허용했고, 직전 사본과 실제 상태가 확인되며, 다른 편집이 없다는 조건을 모두 충족할 때만 보고 후 기계적으로 복원한다. 후속 편집이 있거나 상태가 불확실하거나 복원 오류가 나면 중단한다. 강제 종료 뒤의 복구는 사용자 선택으로 진행한다. 원인 수정, 선택 변경, 남은 적용은 사용자와 범위를 확인한 뒤 이어간다. 완료 단위의 기준과 미완료 기록을 구별하고 전체 적용 완료로 표시하지 않는다. 실패 이후 무관한 단위까지 자동 실행하는 안은 첫 기본 동작에 넣지 않는다. 정확한 단위, 저장/잠금, 명령, 실사용 검증은 남아 있으며 원칙 채택을 구현 완료로 확대하지 않는다.

## 업데이트 중단 후 선택

2026-11-16 사용자는 실패 단위를 복원/검증하고 원인과 재시도 조건을 확인한 뒤, 재시도 또는 이전 구성 사용을 선택하는 흐름을 채택했다. **이전 구성 사용을 선택하면 성공한 단위를 포함해 이번 업데이트가 반영한 변경만 모두 복원하고 실제 동작을 확인한다.** 재시도를 위한 완료 보존과 평소 사용할 버전의 완성을 구분하기 위한 보강이다. 기존 독립 완료 유지 원칙은 재시도 준비와 진행에 유지하고, 명시적인 이전 구성 선택에는 그 요청 전체의 복원 범위를 적용한다.

실패 즉시 이번 업데이트 전체를 자동 복원하는 대안은 재시도 때 성공한 변경도 다시 적용해야 할 수 있고, 되는 변경만 남겨 평소 사용하는 대안은 부분 버전과 호환성 판단을 사용자에게 떠넘긴다. 채택안은 선택과 실제 상태 검증을 추가하는 비용을 감수한다. 복원 기준은 사용자 편집을 포함한 업데이트 직전 상태이며 무관한 코드/WIKI/index와 후속 편집을 덮지 않는다. 복원이 실패하면 기존 구성 사용을 보장한 것으로 표시하지 않는다.

사전 안내를 README와 실제 반영 전 흐름에 노출하고, 실패 결과에서 조치와 사용 가능 범위를 알린다. 상세 순서와 근거는 [업데이트 실패 후 선택](../../design/runtime/update.md), 안내 책임은 [실행 전 안내 — 「실행 전 안내와 중단 시 도움」](../../design/runtime/install.md), 미실행 입력은 [선택 검증 — 「업데이트 실패 뒤 선택의 검증 입력」](../../verification/acceptance.md)에 둔다. 명령, 기록 상세와 실제 Windows 복원/재중단 검증은 남아 있다.

## 확인 조건

- 기존 자료, 새 초기화, 파일명/ADR 번호 충돌, 중간 실패, 후속 편집, 복원을 각각 시험한다. 부분 반영, 강제 종료, 복원 실패, Git 제외 복원의 구체 입력은 [설치 보존 검증 — 「설치 보존과 복구의 검증 입력」](../../verification/acceptance.md)에 연결한다.
- 보존 대상의 비의도적 내용 변경, 삭제가 없어야 하며 승인한 규칙 변경은 별도 차이로 확인한다.
- 원문 유지와 실행 계약 일치가 모두 확인돼야 완료다. 내용이 보호돼도 연결이 모순이면 활성화하지 않는다.
- 신규 지식과 과거 사실, 추정, 사용자 의도를 구분하고 기존 문서를 검증된 정답으로 간주하지 않는다.

세부 절차는 [모듈, 설치](../../design/README.md)에 있다. 보존, 복구의 기본 원칙은 채택됐고 구현 수단과 실제 무손실 검증은 아직 미완료다.
