# ADR 0022: WIKI 연결의 기본 진입

- 날짜: 2026-11-18
- 설계 상태: `accepted` — 전용 시작 명령/직접 접근 우선. 11/22 실제 비교 후 MCP 첫 제공은 후속 검토로 전환. Codex의 npm/공식 Windows 설치를 첫 지원 범위로 채택
- 구현과 검증: 제품 미구현. [Windows 인자/실제 설치본 도움말 비교](../../evidence/experiments/runtime/2026-11-18_13-54-14-launch-arguments.md)와 시험용 시작 파일의 자동 검사 완료. [실제 터미널 첫 시작](../../evidence/experiments/runtime/2026-11-18_14-23-43-terminal-start.md)은 권한 오류로 종료됐고, 명시적 권한 선택 뒤 [로그인 후 WIKI 읽기와 수정 표본](../../evidence/experiments/runtime/2026-11-18_14-49-24-terminal-io.md)을 확인했다. 상태 한 줄 외의 바이트 보존과 같은 세션 재개 뒤 프로젝트/WIKI 권한, 대화/파일 보존을 확인했다. 최초 선택 저장/재사용과 전체 사용자 옵션/중단은 미검증. [선택 MCP 부분 시험](../../evidence/experiments/wiki-access/2026-11-18_15-21-34-mcp-read.md)은 SDK 통신과 A의 실제 Codex 읽기/검색까지 확인. [후속 MCP 시험](../../evidence/experiments/wiki-access/2026-11-18_15-50-14-mcp-projects.md)에서 B 사용, A 재개와 하위 경로 보정 후 실제 읽기 확인. 이후 [실제 세 방식 비교](../../evidence/experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)를 완료. 단건/조회량 차이와 품질 미충족을 보존하며 제품 설치, 최초 선택 재사용과 MCP 쓰기/전체 지원은 미검증
- 범위: [ADR 0010](0010-distribution.md)의 설치 후 기본 진입 보완. Git/Python 배포, 프로젝트 내 설치와 기존 사용자 자산 보존은 유지

## 문제와 변경 이유

11/13에는 제품 시작 명령으로 기기별 외부 WIKI 권한을 전달하는 방향을 채택했다. 11/18에는 일반 `codex`로만 진입해도 같은 연결을 유지하는 방향을 검토했다. 그러나 기기별 경로와 공유 config의 충돌, 전역 설정 비변경, 기존 config의 소유를 함께 보존해야 한다. 로컬 MCP는 가능한 대안이지만 의존성과 도구 호출/종료, 권한/편집 보호의 추가 검증이 필요하다.

사용자는 현재 설치된 Codex의 기능을 유지하는 전용 명령도 수용할 수 있다고 재검토를 요청했다. 두 방식을 함께 제공할 가치와 기술 검토 목적까지 비교한 뒤, 전용 명령 기본 + MCP를 작게 검증한 뒤 제공 범위를 정하는 추천에 동의했다. 이 결정은 기술 이름이나 학습 목적만으로 두 경로를 첫 배포의 필수 완성 범위에 넣지 않는다.

## 결정

1. 기본 사용은 프로젝트에 연결된 시작/재개 명령으로 현재 사용자 환경의 Codex를 연다. WIKI 위치는 한 번 등록해 재사용하고 변경 명령으로 바꾼다. 긴 `--add-dir` 입력을 매번 요구하지 않는다.
2. Codex 전역 설정, 별칭 `codex`, 사용자 인증/모델/세션 위치를 바꾸지 않는다. 고정 버전, 특정 세션 ID, 자동 요청문을 넣지 않으며 기본 Codex의 대화형 기능과 옵션을 보존한다. 명령은 `oneploom`, 첫 지원 형식은 npm과 공식 Windows 설치로 후속 채택했다. 현재 설치본 발견과 실제 인계의 호환성은 구현/검증으로 확인한다.
3. 기존 일반 `codex`도 계속 사용할 수 있다. 프로젝트 안의 하네스와 이미 충분한 권한은 그대로 활용한다. 외부 WIKI 권한이 부족한 기능만 명확히 안내하며, 열린 Codex 안의 경로 등록/변경 트리거는 유지한다. 권한 부족을 조용히 무시하거나 관리 제한을 우회하지 않는다.
4. 11/22 실제 비교 뒤 사용자가 직접 접근 우선 진행을 선택했다. 첫 배포는 기본 직접 접근에 집중하고 MCP 제공은 후속 검토로 둔다. MCP 의존성, 등록, 프로세스와 두 경로의 동등 지원을 첫 배포의 필수 조건으로 만들지 않는다. 기존 후보/실험/안전 조건은 보존하며, 재검토할 때 실제 편익과 품질/비용을 다시 판단한다. 사용자가 이미 쓰는 MCP 설정을 제거하는 결정은 아니다.

이로써 11/18 앞선 “정상 사용의 명령 이름은 반드시 codex” 조건을 변경한다. 프로젝트별 연결, 승인 재사용의 한계, 사용자 데이터 보존과 일반 Codex 안의 연결 지원은 없애지 않는다. 단순 읽기 시험을 필수 WIKI 기능 전체의 완료로 계산하지 않는다.

## 11월 22일 첫 제공 범위

사용자가 “그렇게 하자. 우선은 직접 접근 방식을 우선적으로 진행하자”라고 확인했다. 11/18에 미뤄 둔 첫 MCP 제공 판단을 닫은 보완이며 전용 시작 명령 기본 원칙은 유지한다.

[직접/긴 값/짧은 값 비교](../../evidence/experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)에서 짧은 값의 전달은 보존됐으나 미완료 검색 보고와 사전 답변 기준 일부가 빠졌다. 직접 접근보다 캐시 제외 합계와 시간도 컸다. 각 한 요청이고 조회량/설정의 한계가 있어 MCP 전체의 일반적인 부적합을 증명하지는 않는다. 다만 현재 사용 목적에서 추가 구현/지원 비용을 상쇄할 편익도 입증하지 못해 핵심 하네스의 첫 배포를 우선한다.

상세 WIKI 생성/보강, 읽기/수정, 검증/복구와 최소 PR 연계의 필수 범위를 줄이는 결정은 아니다. 직접 접근에서도 필요한 원문과 예외의 누락, 출력 잘림, 편집 보존과 권한 재사용을 검증해야 한다. MCP 후보와 실측 기록은 후속 개발 및 개인 트러블슈팅 자료로 남기며 재실험이나 환경 정리를 자동 실행하지 않는다.

### Codex 설치 지원 범위

11/22 사용자가 “두 공식설치 방식 지원으로 진행하자”라고 확인했다. 첫 실행기는 npm의 공식 `@openai/codex` 설치와 공식 Windows 독립 설치를 지원 대상으로 삼는다. 사용자가 이미 쓰는 설치를 활용하며, 두 설치를 동시에 요구하거나 우리 모듈의 Git 릴리스 + Python 배포를 바꾸지 않는다.

선정 이유는 [공식 제공 형태와 기존 인자 문제를 대조한 조사](../../evidence/experiments/runtime/2026-11-22_22-58-36-entry-contract.md)를 바탕으로, 정상 설치를 다른 방식으로 바꾸라는 요구를 줄이면서 호출 경로를 설명할 수 있기 때문이다. npm부터 지원하는 안보다 두 경로의 발견, 갱신과 종료 검증이 늘어나는 비용을 수용했다. 임의 셸 wrapper까지 형식 구별 없이 실행하는 안은 첫 지원에 포함하지 않았다. [진입 설계의 비교와 선택 규칙 — 「Codex 설치 형태와 실행 파일 선택」](../../design/runtime/entry.md)이 상세를 소유한다.

설정 처리와 사용자 흐름은 두 방식이 공유하고, 실제 Codex 진입점의 확인/호출만 설치 형태에 맞춘다. 특정 버전이나 개발자 경로를 고정하지 않는다. npm의 기존 시험은 부분 근거이며 Windows 독립 설치의 실제 실행은 아직 확인하지 않았다. [설치별 수용 입력 — 「진입 설정과 반환의 검증 입력」](../../verification/acceptance.md)을 제품 구현 뒤 각각 통과해야 지원 완료로 표시할 수 있다.

## 대안과 비용

| 대안 | 장점 | 감수할 비용/판단 |
| --- | --- | --- |
| 일반 codex와 지속 권한 설정 | 기존 명령 유지 | 개인 경로와 공유 config, 사용자 설정 소유의 충돌을 해결해야 함. 모든 기존 설정을 자동 수정하는 안은 채택하지 않음 |
| 일반 codex와 MCP를 기본 제공 | 파일 접근을 프로젝트 도구로 연결할 후보 | 의존성, 도구 시작/호출/종료와 편집 보호를 기본 사용 전에 검증해야 함 |
| 전용 시작 명령 기본, MCP는 후속 — 11/22 채택 | 현재 Codex 활용과 작은 기본 지원 범위, MCP의 효용을 별도로 확인 | 짧은 새 명령을 익혀야 하며 Windows 인자/터미널/재개 보존 검증 필요. MCP 추가 시 두 접근 경로 지원 비용 발생 |

시작 명령은 세션을 여는 준비이고 MCP는 실행 중 WIKI 도구의 통로다. 공존할 수 있으나 같은 쓰기를 양쪽에서 중복 실행하지 않는다. 모듈이 소유한 작업은 공통 연결/보호 로직을 재사용하되 직접 shell/apply_patch와 수동 편집까지 같은 코드를 지난다고 가정하지 않는다.

## 확인 조건

[전용 시작 명령 검증 — 「전용 시작 명령의 검증 입력」](../../verification/acceptance.md)과 [두 방식 비교 — 「두 방식의 비교 검증」](../../verification/acceptance.md)를 따른다. 현재 설치본/지원 버전, 프로젝트별 경로, 한글/공백/셸 메타문자, 입력/출력/종료, 실제 대화형 사용과 같은 세션 재개를 각각 확인한다. 모델 없는 인자 시험과 실제 사용자 성공을 구분한다.

공식 CLI와 Python 호출 제약, 두 방식의 상세 흐름은 [진입 설계 — 「전용 시작 명령과 MCP의 비교」](../../design/runtime/entry.md)가 소유한다. 실제 자료/의존성 편입 전 라이선스를 확인한다. 시간/토큰은 위 단건 실제 비교에서 관측했으나 일반 우위를 입증하지 않았다. 직접 접근의 실제 제품 흐름은 계속 검증하며 문제가 드러나면 이 결정의 전제를 다시 검토한다.
