# ADR 0019: 하네스 실행 구성의 프로젝트 내 설치

- 날짜: 2026-11-11
- 설계 상태: `accepted` — 프로젝트 내 실행 구성, 팀 공유 권장, 기존 진입점과 전용 영역의 조합 채택
- 구현 및 검증: 설계 동기화만. 새 배치의 제품 설치와 갱신, 실사용은 구현과 검증 모두 미완료
- 이전 결정: [ADR 0010](0010-distribution.md)의 11/09 외부 공통 실행본 배치 부분을 대체한다. 설치 수단, 원문 보존의 나머지 협의는 유지한다.
- 상세: [설치 결과의 소유와 공유](../../design/runtime/install.md)
- 후속 결정: 11/23 [ADR 0023](0023-command-registration.md)은 기기에 작은 명령 연결 프로그램만 등록한다. 하네스 본체의 프로젝트 내 소유는 유지하며 PC 전체 공통 실행본으로 되돌리지 않는다.

## 문제와 근거

사용자는 skill뿐 아니라 script, hook, 설정도 설치한 프로젝트에서 직접 수정, 확장하길 원한다. 외부 공통 실행본과 프로젝트 사본을 나누면 같은 버전 준비, 공유 파일의 수정 영향, 사본 전환, 중복 연결을 추가로 관리해야 한다. 공통 코드의 논리적 분리는 필요하지만 물리적으로 프로젝트 밖에 둬야 하는 것은 아니다.

11/10에 배치 자체를 재검토했고, 11/11 사용자가 요구, 트레이드오프상 최선이면 진행하도록 확인했다. 첫 필수 배포 기한과 자유로운 프로젝트 수정 요구를 함께 고려해 아래 프로젝트 내 설치를 채택한다. 개발 공수, 토큰 절감의 실측 결과에 따른 채택은 아니다.

## 대안과 결정

| 대안 | 이득 | 비용, 판단 |
| --- | --- | --- |
| 실행 구성을 프로젝트에 설치 — 채택 | 필요한 파일을 함께 읽고 수정, 검토, 공유. 평소 실행이 별도 하네스 설치 경로에 의존하지 않음 | 프로젝트마다 파일이 생기며 공식 변경과 사용자 편집의 대조, 검증이 필요 |
| 외부 공통 실행본 + 프로젝트 입력/일부 파일 | 수정하지 않는 공통 코드의 중복을 줄임 | 외부 경로, 버전 준비, 공유 파일 수정, 사본 전환을 관리. 현재 사용자 수정 요구에서 이득이 비용보다 크다는 근거 부족 |
| 파일별로 외부 공유와 프로젝트 사본을 선택 | 변경하지 않는 자산만 공유 가능 | 발견, 업데이트, 보존 조합이 늘어 첫 배포가 복잡해짐. 현재 필수 범위로 추가하지 않음 |

[GitHub Spec Kit](https://github.github.io/spec-kit/installation.html)의 설치 CLI와 프로젝트 스크립트 배치는 첫 대안의 공개 사례다. [uv tools](https://docs.astral.sh/uv/concepts/tools/)처럼 외부 도구도 유효한 패턴이므로 업계 전체의 우열로 일반화하지 않는다. [Copier 갱신](https://copier.readthedocs.io/en/stable/updating/)은 프로젝트 생성본과 사용자 변경을 비교하는 방식을 제공하지만 충돌 처리도 필요하다. 이 도구들을 그대로 채택했다는 뜻은 아니다.

## 채택 범위

- 외부 설치와 갱신 도구가 대상 프로젝트를 확인하고 선택한 기능의 skill, hook 연결/처리 코드, script, 설정을 설치한다. 평소 하네스는 프로젝트에 설치된 파일을 사용한다. 설치용 임시 배포 사본을 제거해도 동작해야 한다. Codex, 언어 실행기 등 명시한 도구 의존성은 별개다.
- 공식 원본과 릴리스는 독립 모듈 저장소에서 유지보수자가 관리한다. 사용자는 설치 결과를 수정할 수 있으며 공식 원본 반영이나 새 모듈 버전 발행을 요구받지 않는다. 프로젝트 값은 설치된 코드와 논리적으로 분리해 중복 하드코딩을 줄인다.
- 기존 지원 진입점에는 필요한 전용 skill, hook 항목, 최소 지침 연결을 두고, 관련 실행 파일은 프로젝트 내 전용 영역으로 묶는다. 기존 AGENTS, 사용자 자산의 위치/내용을 보존한다. 전용 폴더 이름, 정확한 발견 경로는 별도 명세 대상이며 임의 경로의 자동 호환을 보장하지 않는다.
- 팀 공통 실행 파일, 공동 지침, 비밀 없는 설치 기준은 프로젝트 Git 공유를 권장한다. 11/11 보충 확인: 작업 담당자가 도입/갱신 결과를 검토, 공유하고 다른 팀원은 결과를 받아 기기별 준비 후 사용한다. 기존 추적 정책을 임의 변경하거나 자동 stage, commit, 공개하지 않는다. Git 추적과 공개 여부는 별개다. WIKI의 내부/외부 원본과 `.harness/` 전체 로컬 제외는 유지한다.
- 갱신은 모듈 소유로 확인한 파일/항목에 한정한다. 이전 생성 기준, 현재 편집, 새 후보를 대조하고 충돌이나 연결 불일치는 해당 묶음의 적용을 보류한다. 전용 폴더 전체를 소유로 간주하거나 사용자 파일을 자동 덮지 않는다.

11/22 보충: 사용자의 루트 배치 제안과 후속 진행 확인에 따라 신규 기본 위치를 코드 프로젝트 루트의 `oneploom/`으로 구체화했다. 기존 경로와 사용자 편집을 보존하며 팀 Git 공유 권장은 인터넷 공개 강제가 아니다. 설치/갱신용 외부 다운로드와 프로젝트에 남는 실행 파일을 구분한다. [작은 기기 시작 파일의 등록 — 「짧은 명령의 등록과 프로젝트 선택」](../../design/runtime/entry.md)은 11/22 당시 미채택 후보였으나 11/23 [ADR 0023](0023-command-registration.md)으로 채택했다. 작은 기기 연결 프로그램에 한정하며 외부 하네스 본체로 복귀한 결정이 아니다. 세부 배치와 대안은 [설치 명세 — 「프로젝트 설치 위치 후보」](../../design/runtime/install.md)가 소유한다.

## 남는 비용과 확인 조건

1. 새 clone에서도 갱신 기준을 확보해야 한다. 재현 가능한 기준은 고정 배포본과 입력으로, 재현할 수 없는 생성본은 보존한 기준으로 확인한다. 개인 `.harness/` 백업만으로 팀 갱신을 성립시키지 않는다. 이는 담당자 교체 후에도 비교 기준을 확보하기 위한 조건이며 같은 결과를 팀원마다 새로 생성하는 조건이 아니다. 공유 형식과 민감 정보 제외는 후속 명세에서 정한다.
2. 일반 터미널의 최초 진입, 재개, 실제 skill/hook, 외부 WIKI 권한, 임시 설치 자료 제거 뒤 동작, 팀 clone, 사용자 script 수정, 연속 갱신, 충돌, 실패 복원, 제거를 실제 배포 후보로 검증한다.
3. 기존 외부 배치의 작은 Git/Python 시험과 Codex 부분 관측은 당시 근거로 보존한다. 새 배치의 실사용 통과나 무충돌 보장으로 바꾸지 않는다.
4. 제공 수단은 후속 [ADR 0010의 11/11 채택 — 「추천」](0010-distribution.md)을 따른다. 정확한 명령, 파일명, 지원 버전, 보존 상세, 첫 제공 기능은 계속 협의한다. 이 배치 결정은 제품 구현, 저장소 생성, Git 작업, 공개의 실행 허가가 아니다.
