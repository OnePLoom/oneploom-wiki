# ADR 0017: 앱과 WIKI의 작업별 버전 연결

- 날짜: 2026-11-05
- 설계 상태: `accepted` — 2026-11-05 작업별 버전 연결과 PR 자동화 2안의 방향 채택. 기록 형식, 권한, 구현 상세는 후속 협의
- 구현 및 검증: Git, GitHub 공식 문서와 기존 설계 대조만. 새 저장소, 커밋, PR, CI, 승인, push, 롤백, 실패 주입 시험 미실행
- 상세: [두 저장소 운영 — 「두 저장소를 사용할 때」](../../design/sync.md)

## 문제

사용자는 앱과 WIKI를 같은 Git에 보관하지 않으면서 같은 작업의 커밋, 롤백을 함께 다루길 원한다. 두 저장소를 각자 최신으로 유지하는 것만으로 검증한 코드, 문서 조합이 보존되지 않는다. 반대로 모든 앱 커밋에 빈 문서 커밋을 만들거나 문서 이력 전체를 되돌리면 불필요한 작업과 근거 유실을 만든다.

## 대안

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 작업별 두 버전, 검증, 미완료 상태를 수동 기록 | 개발 비용이 가장 작고 기존 Git 유지 | 누락, 오타, 중단 확인을 사람이 반복 |
| B | 같은 기록에 작은 상태 확인 절차와 선택 Git 보조를 연결 | 작업 단위 조회, 재개, 복구를 통일, 앱에 내부 WIKI를 넣지 않음 | 실패, 동시 변경, 원문 보존 검증 필요. 두 원격 원자성 없음 |
| C | submodule로 WIKI 커밋 고정 | Git 기본 기능으로 버전 대응 표현 | 앱에 gitlink, 연결 정보가 남음. 별도 인증, 갱신과 독립 push 유지 |

## 채택한 방향

B의 작업별 버전 연결을 바탕으로, 아래 PR 자동화 2안인 **로컬에서 두 변경 준비 → PR 연결, 버전/검사 확인 자동화 → 사람이 각 PR 검토, 승인**하는 방향을 채택했다. 사용자는 실제 적용 시 검증하고 피드백을 반영하며 진행하도록 요청했다. 한 작업의 코드, 문서 조합과 실제 검증, 부분 반영을 추적하며, 기본 정합성 확인과 선택 커밋, 복구 조작은 구분한다. 자동 승인 전달, 연쇄 병합은 이번 채택에 포함하지 않는다.

작업 기록은 비공개 WIKI 측에 둔다. 본문 커밋을 만든 뒤 두 버전을 연결하는 기록 커밋을 두는 후보로 자기 SHA 참조를 피한다. 기록 형식, 경로, 명령, 원격 정책은 아직 미정이며, 추가 기록 커밋과 부분 공유를 처리할 비용을 감수해야 한다.

과거 조합의 재현과 현재 공유 변경 취소를 구분한다. 전자는 별도 작업 공간에서 두 커밋을 함께 읽고, 후자는 새 되돌림 커밋과 현재 설명의 정정으로 새 검증 조합을 만든다. ADR, 실패, 측정 근거는 삭제하지 않는다. 미커밋, 미추적 자료와 실제 배포, 데이터 복구는 SHA 쌍만으로 복원되지 않는다.

## 구현 전에 구체화할 것

- 11/08 추가: 모듈 자체의 WIKI는 공개하고 일반 적용 프로젝트의 WIKI는 private로 운영하려는 요구를 구분한다. backend, frontend, infra가 분리된 경우 작업별 관련 저장소/기준 버전 목록으로 연결을 확장할 필요가 있다. [프로젝트와 저장소의 구분 — 「여러 저장소를 하나의 프로젝트로 관리할 때」](../../design/sync.md)에 조사와 후보를 정리했다. 공통 보드/소유자만으로 권한, 동시 커밋이 통합되지 않으며 다중 코드 루트 지원, 공개 기록 형식은 미구현이다.
- 기록 형식, 보관 경로, 명령과 추가 기록 커밋 필요 여부를 정한다. 위 방향 채택으로 본문 뒤 별도 기록 커밋이라는 세부 후보까지 확정하지 않는다.
- 실제 GitHub 플랜, 리뷰어, 권한, 비용, 검사 강제 가능 여부와 병합 순서를 확인한다. 조건이 맞지 않으면 수동 1안 등으로 바꾸는 판단을 사용자와 협의하며 자동 승인으로 우회하지 않는다.
- 공유 전, 후 취소, 한쪽만 성공, 뒤늦은 사용자 변경, PR 결과 변경에서 완료와 미완료를 구분하는 사례를 후속 검증/복구 계약에 연결한다.
- Windows 문서 연결, 최소 WIKI, 검증, 복구를 먼저 확인하고 로컬 두 작업본 연계 후 CI를 붙인다. 정확한 순서와 첫 배포 범위는 [진행표](../../development/roadmap.md)가 소유한다.

11/11 후속: 설치의 보존/실패 보고, 합의 후 재개 원칙은 ADR 0011에서 채택했다. 이어 [ADR 0007의 첫 PR 연계 범위](../architecture/0007-release-scope.md)에서 GitHub 코드/WIKI 각 1개 저장소의 최소 원격 연계를 첫 제공하는 안을 채택했다. 두 PR 생성/재사용, 연결, 상태 검사를 제공하고 검토, 승인, 병합은 사람이 맡는다. [구체 경계 — 「첫 배포의 PR 연계 후보」](../../design/sync.md)는 명세 입력이며 실제 원격 구현, 검증은 아직이다.

## 후속 검토: PR과 CI 연결

사용자는 앱 PR 생성, 승인, 반려를 WIKI에도 연결하는 방법과 로컬 미커밋 변경의 전달을 질문했다. 처음 세 범위를 비교한 뒤 11/05 후속 요청으로 2안의 방향을 채택했다. [상세 비교 — 「PR과 CI 연결」](../../design/sync.md)에서 기능, 권한, 비용, 실패 사례를 정리했다.

| 범위 | 장점 | 부담, 판단 |
| --- | --- | --- |
| 1. 로컬에서 두 변경, PR 준비, 수동 검토, 병합 | 구현, 권한 부담이 작음 | 두 PR 상태 확인은 사람의 책임. CI 제약이 크면 대안 |
| 2. 로컬 준비 + CI의 PR 연결, 버전/검사 확인 | 누락을 줄이면서 사람의 검토 의미 유지 | 11/05 방향 채택. 교차 저장소 권한, 실행 조건과 실제 동작은 검증 전 |
| 3. 한 번의 공동 검토로 승인 전달, 순차 병합/취소 자동화 | 조작 감소 | 두 diff 검토, 승인 권한, 새 커밋 무효화, 부분 병합, 복구 부담이 커 후속 후보 |

일반 hosted CI는 PC의 미커밋 WIKI를 가져올 수 없으므로 두 원격 branch 준비가 선행한다. PR 생성, 승인 API가 있어도 승인과 병합은 별개이고 작성자 자신의 승인 제한, 다른 필수 리뷰, 새 버전을 확인해야 한다. `Request changes`와 PR 미병합 종료, 이미 병합된 변경 취소도 구분한다. 봇의 승인 전달을 독립된 사람의 추가 리뷰로 표시하지 않는다.

private WIKI 접근에는 별도 권한이 필요하고, 기본 토큰의 후속 workflow 실행에는 제한이 있다. GitHub Free private 저장소의 보호 규칙 지원과 Actions 포함량을 확인하기 전 무료, 강제 동작을 보장하지 않는다. 현재 플랜, 실제 리뷰어, 정책은 미확인이다. 공개 앱에는 내부 WIKI 내용이나 민감한 링크를 노출하지 않는 연결을 유지한다.

## 근거

- [Git push](https://git-scm.com/docs/git-push): atomic 갱신은 한 원격 범위다. 두 저장소의 부분 실패를 감지해야 하는 근거다.
- [Git revert](https://git-scm.com/docs/git-revert), [Git worktree](https://git-scm.com/docs/git-worktree): 공유 변경 취소와 과거 상태 조회를 구분하는 근거다.
- [Git submodules](https://git-scm.com/docs/gitsubmodules): gitlink가 특정 커밋을 가리키고 연결 설정을 상위 저장소에 기록한다.
- [ADR 원문](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions): 뒤집힌 판단도 삭제하지 않고 대체 상태와 이유를 남긴다.
- [GitHub PR API](https://docs.github.com/en/rest/pulls/pulls), [review API](https://docs.github.com/en/rest/pulls/reviews): branch 기반 PR 생성과 리뷰 상태 변경, 병합 기능은 구분된다.
- 이벤트, 토큰, 작성자 제한, 플랜, Issue의 근거는 [PR 연결 검토 — 「PR과 CI 연결」](../../design/sync.md)에 연결했다.
