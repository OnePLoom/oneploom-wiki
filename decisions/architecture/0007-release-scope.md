# ADR 0007: 첫 배포 범위와 기술 검토 실증

- 작성: 2026-10-27
- 설계 상태: `accepted` — 첫 배포의 필수 기능과 후속 확장 경계를 채택했다. 2026-11-11 최소 PR 연계와 첫 선택 기능, 후속 Windows/직접 접근 결정을 포함한다. 상세 수용 계약의 구현과 검증은 미완료다.
- 구현 및 검증: 구현과 측정 모두 미완료
- 확정된 입력: 프로젝트 이식, 종속성 분리, 근거 기반 상세 문서 복원은 필수 축이다. 준비 문서와 예비 시험을 제품 완료로 계산하지 않는다.
- 2026-10-29 후속 입력: WSL2 Ubuntu와 Linux 파일시스템을 초기 실행 환경으로 선택했다. 당시 Windows 직접 실행은 후속이었다. 이후 ADR 0020에서 첫 배포 환경을 Windows로 전환했으며 이 문단은 이전 선택의 기록이다. 환경 선택과 이 ADR의 전체 기능 범위 채택은 구분한다.
- 2026-11-09 재확인: 필수 요구의 동작, 검증을 마친 `v1.0.0` 모듈 배포가 1차 목표다. 후속 호환성, 기능/리팩터링은 검증한 배포 단위로 확대한다. 이 목표와 실제 구현/검증 완료는 구분한다.

## 채택 범위와 남은 작업

첫 배포의 필수 목록과 설명/학습 확장 우선 순서는 결정됐다. 지원 도구의 실제 조합, 기능별 완료 계약과 실패/복구의 실행 검증은 남아 있다. 이들은 채택된 범위를 실현하기 위한 후속 작업이며 첫 배포 범위를 다시 미채택으로 돌리는 이유가 아니다. 범위를 줄이거나 필수 기능을 바꾸려면 별도의 결정을 남긴다.

## 문제

조건부 지침, hook, 진행 문서, 역할별 모델 배치, WIKI는 이미 공개 도구에서 사용한다. 구성요소 추가만으로 독창성이나 실효성을 주장하기 어렵다. 현재는 검증 범위 유실, 불완전한 PASS 재사용 등 반례가 있지만 수정 후 효과와 실제 이식 결과는 없다.

범용 자동 분석, 다중 모델과 로컬 AI를 첫 배포에 모두 넣으면 조합별 검증과 안정화 시간이 부족해질 위험이 크다. 먼저 증명할 문제와 기존 도구에 맡길 책임을 정해야 한다.


## 대안

| 안 | 쉬운 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 기존 도구 조합 | Codex, 프로젝트 CI, 필요한 명세 도구를 구성하고 개별 프로젝트의 개발에 집중 | 가장 작은 유지 비용, 빠른 도입 | 독립 모듈 기여가 작고 프로젝트별 연결을 직접 관리할 수 있음 |
| B. 작은 재사용 모듈 | 기존 도구 위에 부족한 검증 기록, 재개, 초기화/문서 근거 연결만 개발 | 실제 반례와 필수 이식 목표를 함께 증명 가능 | 지원 범위를 좁혀도 설치, 상태, 연결 검증이 필요 |
| C. 범용 오케스트레이터 | 다양한 모델, 역할, 언어, 프로젝트의 전체 작업을 통합 | 장기 확장성과 기능 폭 | 개발, 운영, 조합별 검증 비용이 가장 크며 첫 배포의 일정 위험 |

## 추천

**B를 추천하되 기존 도구가 충족하는 부분은 재사용한다.** 초기에는 일정, 추가 가치가 부족하면 A로 축소하도록 제안했지만, 11/09 재확인한 필수 모듈 배포 목표를 없애는 자동 축소안으로는 사용하지 않는다. 기한과 필수 범위가 충돌하면 선택 기능, 추가 지원 환경과 일정을 비교해 사용자와 조정한다. C와 로컬 협업 전체는 후속 구상으로 보존한다. 세부 범위의 추천은 채택이 아니다.

첫 환경은 11/11 [ADR 0020](../runtime/0020-windows.md)의 Windows 직접 실행, 로컬 프로젝트로 전환했다. 10/29 WSL 채택 이력은 0013에 보존하며 WSL/Linux 정식 지원은 후속이다. 정확한 도구 버전, 대상 프로젝트의 호환은 실제 검증한다. 현재 모듈명, 테스트, boot 예외를 공통 코드에 내장하지 않는다.

10/27 초기 WIKI 제안은 전체 자동 생성 / 근거 기반 후보와 검토 / 기존 문서 색인을 비교해 **근거 기반 후보와 검토**를 추천하고 대표 기능 하나에 한정했다. 당시 비교는 [평가 7절 — 「7. 현재와 수정 후보의 구조」](../../discussions/architecture/alternatives.md)에 보존한다. 11/09에는 [ADR 0014 — 「이번에 확인할 범위」](../knowledge/0014-features.md)의 범위별 상세 복원, 완료 기준을 채택했으므로, 대표 기능 하나는 첫 검증 사례로 사용하며 제품이 복원할 수 있는 총범위의 한도로 삼지 않는다. 선택 범위를 단위별로 나눠 상세 근거, 관계를 채우고 미완료 범위를 표시한다.

## 첫 배포의 책임과 보류 항목

11/10 작성, 11/11 보강한 범위표다. 이미 확인한 필수 목표에 이어 **최소 원격 PR 연계와 설명, 학습 문서 확장의 첫 제공, 커밋 보조의 후속 검토를 11/11 채택했다.** 설치 제공 수단은 ADR 0010, 원문 보존, 실패 보고, 합의 후 재개 원칙은 ADR 0011에서 채택했다. 오른쪽의 상세 완료 조건은 검증 계약에서 구체화할 후보이며 구현 완료를 뜻하지 않는다. 설치 자산의 보관, 수정 책임은 [설치 구성표 — 「설치 결과의 소유와 공유」](../../design/runtime/install.md), 기능의 의미, 의존성은 [기능 선택 — 「기능 선택과 추가」](../../design/module.md)이 소유한다.

| 구분, 상태 | 첫 배포에서 다룰 범위 | 완료 조건의 후보 |
| --- | --- | --- |
| 필수 목표 — 조건부 하네스 | 요청, 변경, 위험에 따른 문서 탐색과 gate, 필요한 절차만 실행 | 일반 프로젝트 CLI에서 필요한 지침, 근거, 검사를 빠뜨리지 않고 불필요한 전체 읽기/실행도 구별. 신규 프로젝트는 과거 WIKI 복원 없이 시작 |
| 필수 목표 — WIKI 기반 | 요구, 결정, 계약, 실패 지식의 역할/위치 연결과 필요한 때의 갱신 | 기존 문서 보존과 빈 프로젝트 초기화를 각각 확인. 역할→문서/제목→근거를 찾고 변경 뒤 연결, 정합성 유지 |
| 필수 제공 보조 기능 — 상세 복원 | 명시한 범위, 모델로 근거 기반 생성/보강, 작업 분할, 재개 | 설치와 별도 트리거로 실행. 코드/이력 근거, 사실/추정, 중요한 누락, 미완료를 표시하고 기존 편집을 보존. 전체 범위를 한 번에 처리하거나 기초 요약만으로 완료하지 않음 |
| 필수 목표 — 검증, 실패 처리 | 계획/실제/미완료 구별, 원래 실패 검사 유지, 관련 runbook 연결 | 실제 검사를 실행하고 다른 PASS로 실패를 닫지 않음. 정상, 실패, 불필요 차단을 확인. 테스트 작성 절차, 로컬/CI 범위는 다음 검증 계약에서 확정 |
| 필수 목표 — 상태, 복구 | 프로젝트별 로컬 상태, 중단 후 재개/문맥 압축과 실제 파일의 대조 | `.harness/` 제외 후 상태 생성. 새 프로세스, 중간 실패, 사용자 후속 편집을 확인하고 모르는 상태를 성공으로 복구하지 않음. 상세 저장/복원 계약은 후속 |
| 필수 목표 — 도입, 유지보수 | 최초/선택 설치와 후속 추가, 갱신, 복원, 제거, 기존 자료, 추적 정책 보존 | README만으로 지원 환경의 새 작업 공간에서 사용. 프로젝트별 버전, 사용자 변경, 다른 프로젝트를 보존. Windows 코드 프로젝트와 내부/외부 WIKI를 각각 검증 |
| 첫 포함 범위 채택 — 앱/WIKI 작업 연결 | 로컬 두 변경의 버전 연결 + GitHub 코드/WIKI 각 1개 저장소에서 PR 생성/재사용, 연결, 상태 검사. 검토, 승인, 병합은 사람 담당 | 실제 권한, 두 PR, 부분 실패, 한쪽 병합, 복구를 검증하며 모의 결과로 대체하지 않음 |
| 선택 기능 — 첫 목록 채택 | 설명, 학습 문서 확장은 첫 제공, 커밋 보조는 후속 검토 | 최초 선택과 후속 추가, 갱신/제거를 검증. 기본에 없는 기능을 요구하지 않으며 필수 WIKI, 검증, 복구를 선택 기능으로 내리지 않음 |
| 후속 검토 — 실행 확장 | 로컬 AI, 다른 provider, 실제 병렬 보조, 추가 실행 환경 | 기본 메인, 단일 반영, 선택 보조의 채택 경계는 유지. 실제 도입은 품질/비용, 권한, 충돌/복구를 검증해 별도 결정. WSL/Linux 정식 지원은 후속 |
| 보류 — 별도 가치 확인 필요 | 자체 PASS 캐시, 상시 로컬 의존, 자동 역할 배치, 모든 언어 자동 분석, 전용 UI | 필수 요구를 대신하지 않음. 무제한 전체 ADR/WIKI 재생성은 상세 복원의 기본 방식으로 채택하지 않음 |

아래 PR 연계 범위와 선택 기능의 첫 제공 목록은 채택됐다. Git 릴리스 + Python과 보존/복구의 기본 원칙도 다시 선택하지 않는다. 다음 검증 범위표에서 정확한 지원 조합, 완료 검사를 구체화하고 복구 계약, 파일별 명세로 연결한다. 미정 항목 때문에 합의된 핵심을 다시 선택하도록 요구하거나, 기한을 이유로 필수 요구를 조용히 제외하지 않는다.

11/15 도입 범위 보충: 제품 시작 명령을 기본으로 유지하면서 일반 `codex` 안의 트리거를 통한 WIKI 경로 등록/변경과 연결도 첫 배포에 포함한다. 준비된 권한에서는 현재 세션에서 계속 사용하고, 권한 부족은 지원 수단과 제한을 구별해 처리한다. 호스트 권한 설정 자동 생성/병합은 후속이며 모듈의 로컬 경로 등록과 구분한다. 이전 설명의 범위 보정, 채택 이유와 재검토 조건은 [ADR 0010](../runtime/0010-distribution.md), 실제 확인할 행동은 [진입 검증 입력 — 「진입과 프로젝트 연결의 검증 입력」](../../verification/acceptance.md)에 연결하며 시험을 통과한 상태는 아니다.

### 첫 PR 연계 범위

11/11 두 대안을 비교한 뒤 사용자가 **최소 원격 연계를 첫 배포에 포함**하는 안을 채택했다. ADR 0017의 로컬 준비, PR 연결/검사, 사람의 승인 방향을 따른다. 하나의 저장소에서 WIKI를 관리하는 사용자는 기존 PR로 처리하며 별도의 WIKI 저장소나 빈 PR 생성을 요구하지 않는다.

| 첫 제공 범위 | 장점 | 부담, 남는 범위 |
| --- | --- | --- |
| 최소 원격 연계 포함 — 채택 | 코드/WIKI 분리 사용의 실제 흐름을 첫 배포에서 확인. 채택한 자동화 방향과 맞음 | GitHub의 두 저장소부터 지원하고 별도 접근 권한, CI, 이벤트, 부분 실패를 실제 검증해야 함 |
| 로컬 버전 연결, 검사부터 제공, 원격 자동화는 후속 | 초기 인증, 원격 운영 부담 감소 | PR 생성, 상태 확인은 사용자가 수행. 채택한 PR 자동화의 첫 제공을 미루는 범위 조정이므로 별도 합의 필요 |

채택한 기능 경계는 **사용자가 준비한 원격 branch/commit → 같은 작업의 PR 생성 또는 재사용, 연결 → 현재 버전/검사/검토 상태 확인 → 사람이 각 저장소 정책대로 처리 → 실제 병합, 미완료 조합 기록**이다. 설치만 했다고 stage, commit, push하거나 PR을 만들지 않는다. 자동 승인 전달, 연쇄 병합, 자동 되돌림은 첫 범위에 넣지 않는다. 여러 앱 저장소와 GitHub 외 서비스의 자동 연계는 후속으로 검토한다. 상세 입력, 실패 사례는 [첫 PR 연계 상세 — 「첫 배포의 PR 연계 후보」](../../design/sync.md)에 둔다.

원격 연계를 고른 프로젝트는 같은 기능을 로컬 검사와 CI에서 사용하되 기본 하네스, 로컬 WIKI 작업이 CI 응답을 상시 기다리지는 않는다. 권한/CI가 없으면 해당 연계를 미구성, 미완료로 표시한다. 개인 검토와 GitHub의 필수 승인 충족은 구분하며 실제 리뷰어, 플랜, 보호 규칙은 연결 검증 전에 확인한다. 추천은 상대적인 범위 판단이며 현재 확정 마감일과 실측 공수가 없어 일정 내 완료를 보장한 견적이 아니다.

### 첫 선택 기능

‘선택 기능을 나중에도 추가할 수 있음’은 이미 요구사항이다. 이를 실제 제공 기능으로 검증하면서 첫 구현을 제한하도록 **11/11 설명, 학습 문서 확장을 먼저 제공하고 커밋 보조를 후속으로 두는 안을 채택했다.** 핵심 WIKI와 역공학, 검증, 복구는 필수 제공 범위를 유지한다.

| 첫 제공 목록 | 장점 | 부담, 판단 |
| --- | --- | --- |
| 설명, 학습 문서 확장 제공, 커밋 보조는 후속 — 채택 | 사용자가 예로 든 확장 사용 흐름을 검증하고 기존 문서 역할/연결을 재사용 | 후속 커밋 보조 전까지 stage, 메시지는 기존 도구/팀 절차 사용 |
| 문서 확장과 커밋 보조를 함께 제공 | 처음부터 작업별 stage, 메시지 지원 가능 | 기존 index, 다른 작업 변경 보존, 부분 stage, 취소와 조합별 검증이 추가됨 |

설명/학습 확장은 필요한 안내, 역할/라우팅, 템플릿을 최초 선택 또는 후속 요청으로 연결하고 실제 요청 때만 사용한다. 기본에 모든 폴더나 본문을 미리 만들지 않으며 기존 문서, 공개 범위, 원문 보존 정책을 따른다. 정확한 기능명, 파일, 묶음은 명세에서 정한다. 새 hook/script나 별도 배포 저장소를 확장마다 만들지 않는다.

PR 연계의 입력은 검토해 준비한 변경/버전이므로 자동 stage, 커밋 메시지 보조를 필수 의존성으로 삼지 않는다. 커밋 보조를 후속으로 둬도 Git 공유/작업 연결은 유지한다. 정확한 파일, 명령, 설치 묶음은 이 첫 목록을 기준으로 명세에서 정한다.

로컬 AI는 [ADR 0006](../integration/0006-local-assist.md)의 실험 후보로 유지한다. 같은 상세, 근거, 관계, 보존 기준을 충족하고 재검토/재시도까지 포함한 이득이 확인돼야 하며, 미실측 상태로 첫 배포의 필수 실행기로 삼지 않는다. 비교 준비는 핵심 설계와 독립적으로 진행할 수 있다.

보장 범위는 지원 환경, 모듈을 통과한 실행, 정한 검사로 한정한다. AI의 모든 행동과 의미적 정확성을 완전히 통제하거나 기존 CI, 필수 의미 검토를 대체한다고 주장하지 않는다. 부분 실험은 [실사용 검증 상태 — 「구성별 검증 상태」](../../design/runtime/install.md)와 구분한다.

`v1.0.0`은 기본 모듈 세팅이나 단일 시연만 마친 상태를 뜻하지 않는다. 확정한 지원 환경에서 필수 흐름, 기존 자료 보존, 중단/실패 처리, README를 따른 새 환경 도입을 검증하고, 미지원 범위와 공개 사용 계약을 명시한 첫 배포다. 모든 미래 환경을 지원할 필요는 없지만 필수 실패를 남겨 두고 태그만 붙이지 않는다. 상세 WIKI 복원은 선택한 범위를 나눠 처리하며 중요한 누락, 미검증을 숨기지 않는 기존 품질 조건을 유지한다.

## 확인 사항과 범위 축소 조건

1. 기본 Codex + 동일한 필수 검사/정책과 비교해 모듈의 추가 역할을 확인한다. 현재 구현의 버그 수정만으로 일반 생산성 우위를 주장하지 않는다.
2. 실패 반례뿐 아니라 정상 통과, 불필요한 차단, 실제 재개, 기존 파일 보존을 함께 검증한다.
3. 다른 실제 프로젝트의 코어 변경량, 설치 시간, 문서 검토량을 기록한다. fixture와 실제 이식 결과를 구분한다.
4. 비용 비교는 실패, fallback, 사람 검토를 포함한다. 백엔드 성능 개선과 하네스 자체의 인과 효과를 구분한다.
5. 최초 15일 예산안에서는 D10에 핵심 기능 추가를 멈추고 D15에 출시 여부를 판단하도록 제안했다. 이 날짜를 실제 진척으로 간주하지 않으며, 현재 준비 상태로 일정을 다시 배정한다. 핵심 계약이 닫히지 않으면 선택 기능, 지원 범위, 배포 일정의 조정을 협의한다. 필수 요구의 제외나 필수 실패를 남긴 완료 처리는 하지 않는다.

전체 일정, 준비 상태별 축소안은 [일정과 예산](../../development/roadmap.md)이 소유한다. 이 ADR은 기존 ADR의 구현 세부를 자동 채택하거나 이전 장기 목표를 폐기하지 않는다.
