# ADR 0004 — 프로젝트 종속성 분리와 근거 기반 초기화

- 작성일: `2026-10-27`
- 목표 상태: 사용자가 재확인한 최종 필수 요구. 다른 프로젝트 도입과 코드, 커밋 기록 기반 문서 복원은 로컬 AI 채택 여부와 독립적이다.
- 설계 상태: 부분 `accepted` — 2026-11-09 문서 역할/위치 매핑을 채택했다. 프로젝트 종속성 분리와 근거 기반 초기화는 필수 요구이며, 자동 탐지/보정과 초기화의 상세 처리 방식은 아직 검토 중이다.
- 추천: **B**
- 구현 및 검증: 구현과 검증 모두 미완료. 이식 성공, 자동 탐지 정확도, 문서 복원 품질은 측정하지 않았다.

## 채택 범위와 남은 작업

문서 역할/위치 매핑은 채택됐다. 자동 탐지의 지원 범위, 탐지 결과를 명시 설정과 충돌 없이 합치는 계약, 근거가 부족할 때의 보정 절차는 구현 전에 더 구체화해야 한다. 이 ADR의 부분 채택은 자동 분석 방식 전체를 승인했다는 뜻이 아니다. 설치 위치와 실행 진입은 후속 ADR 0019, 0023, 0024의 채택 결정을 따른다.

## 문서 연결의 채택 범위

2026-11-09 사용자가 최선으로 판단되면 추천한 방식으로 진행하라고 확인했고, 현재 요구, 비용, 구현 범위에서 해당 추천을 유지해 채택했다.

- 문서의 역할, 범위, 위치를 JSON으로 연결하고 상세 내용, 관계는 Markdown 원본에 둔다.
- 공통 진입점과 필요한 기능/흐름별 한 단계 분리를 지원한다. 작은 구성은 단일 파일을 허용한다.
- 사용할 하위 파일을 명시한 목록으로 관리한다. 폴더 자동 포함이나 여러 단계의 목록은 첫 범위에서 채택하지 않는다.
- AI가 연결 의미, 변경 범위를 판단하고 도구가 등록/갱신, 검사, 선택 조회를 수행한다. 정상적인 유지보수는 AI 중심이며 사람의 이해, 개입 가능성은 유지한다.

정확한 필드, 역할 값, 절 선택자, 조회 오류, 저장/복구 상세는 [위치표 명세](../../design/knowledge/map.md)의 초안과 후속 계약에서 검토한다. 이 채택을 ADR 0004의 모든 수단, ADR 0014의 최소 WIKI 전체 범위, 제품 구현, 설치, Git 변경의 승인으로 확대하지 않는다. 아래 후속 검토는 이 선택에 이른 이력을 보존한다.

같은 날 사용자는 현재 구성에 이견이 없으며 이후 구현에서 문제가 생기면 검토하기로 하고 다음 설계를 요청했다. 현재 구성은 유지하고 [조회 역할, 범위, 절 선택 — 「조회할 역할」](../../design/knowledge/map.md)을 구체화했다. 이 후속 명세를 지원 값, 파서까지 모두 채택한 결과로 확대하거나 이미 합의한 형식을 반복해서 협의하지 않는다.

## 기존 계획에 있던 것과 남은 공백

원본 Q&A의 Q8, Q9와 [1차 초안](../../discussions/history/initial-portability.md)은 공통 하네스와 프로젝트별 값 분리, 대상 코드, 주요 커밋을 이용한 문서 복원을 다룬다. 현재 [구조 추천안 — 「무엇을 누가 소유하는가」](../../design/architecture.md)에도 같은 방향이 있다.

다만 그 방향이 모든 script, README, config, matrix, skill, hook에 걸친 종속성 분류, 자동 탐지/명시 설정의 관계, 설치와 갱신, 문서 생성의 상세 계약으로 완성된 상태는 아니다. 이번 검증 초안의 Gradle도 공통 코어의 필수 전제로 굳어지지 않도록 범위를 명시해야 한다.

2026-10-27 재검토 결론: **목표와 큰 경계는 이전부터 고려했지만, 바로 구현할 수 있을 만큼 모든 종속성과 소비 지점을 설계한 상태는 아니다.** 특히 설정 원본, 파생 정보의 구분, 설정 변경 후 재분석, 생성 파일 소유권, 이식 완료 판정이 부족했다. 아래에 그 제약을 보완하며 상세 설치기, 파일별 분리는 후속으로 남긴다.

최종 목표는 지원 프로젝트의 차이를 공통 코어 수정 없이 수용하고, 새로운 스택은 연결부를 추가해 확장할 수 있는 구조다. 모든 미지의 언어, 빌드 방식, 과거 의도를 무검토로 자동 인식한다는 보장은 두지 않는다. 초기 지원 범위와 확장 경로를 공개하고, 모르는 구조는 누락, 미지원으로 반환해야 한다.

## 비교한 방안

| 방안 | 쉬운 설명 | 장점 | 단점, 비용 |
| --- | --- | --- | --- |
| A. 수동 설정과 템플릿 | 사용자가 모듈, 명령, 문서 경로를 입력하고 템플릿을 채운다. | 초기 구현이 작고 해석이 어려운 프로젝트에도 명시적으로 대응할 수 있다. | 분석, 입력 부담이 크고 설정 누락을 사람이 관리한다. 자동 분석, 채움이라는 최종 목표를 단독으로 충족하지 못한다. |
| B. 프로젝트 분석 → 설정 후보 → 검증, 보정 → 공통 코어 연결 | 대상의 기존 설정, 코드, 문서를 조사해 프로젝트별 설정을 만들고, 스택별 연결부와 공통 절차가 이를 사용한다. | 공통 로직을 유지하면서 도입을 보조하고, 설정 출처와 수정 지점을 추적할 수 있다. 기존 문서도 보존하며 필요한 내용을 생성할 수 있다. | 분석기, 연결부, 설정 계약과 충돌 처리가 필요하다. 자동 확인할 수 없는 정책은 추가 확인이 남는다. |
| C. 프로젝트별 하네스 생성 | 공통 템플릿에서 대상 전용 script, skill, 문서를 생성해 설치한다. | 각 프로젝트에서 독립 실행하기 쉽고 그 구조에 맞는 결과물을 만들 수 있다. | 생성된 코드가 프로젝트마다 달라져 업데이트, 검증, 원본 추적 비용이 늘어난다. 기존 파일과의 충돌, 수정 보존도 관리해야 한다. |

## 추천과 이유

B를 최종 방향으로 추천한다. 프로젝트마다 달라지는 값을 바꿀 때 공통 로직까지 고치지 않고, 분석 결과, 명시적 보정, 실제 실행이 같은 해석 결과를 참조하도록 만들기 때문이다. 필요한 README, skill, 문서의 일부는 그 결과와 템플릿에서 생성할 수 있다. 모든 절차를 생성 코드로 바꾸지는 않는다.

A는 초기 연결부 확인과 모르는 값의 보정 수단으로 사용할 수 있다. C도 얇은 진입점이나 프로젝트용 문서 생성에는 적합하다. 다만 프로젝트마다 실행 로직 전체를 재작성하는 것을 기본으로 삼지 않는 방향이다. 별도 Git 레포의 구체 배포 형식은 후속 판단이며 지금 확정하지 않는다.

구현 순서는 작은 공통 계약과 현재 프로젝트의 명시적 연결 → 다른 이름/경로 검증 → 지원 스택의 자동 탐지 → 실제 두 번째 프로젝트 이식이다. 초기 수동 연결은 분석기가 내놓아야 할 값을 확인하는 개발 단계이지, 자동 분석이라는 최종 요구를 없애는 선택이 아니다.

[Nx 공식 설정 문서](https://nx.dev/docs/reference/project-configuration)는 기존 도구 설정에서 추론한 값과 프로젝트 명시 설정을 결합하고, 정적으로 확인할 수 없는 의존을 따로 표현한다. 이는 자동 분석과 보정이 공존할 수 있다는 근거다. Nx 도입을 추천하거나 모든 프로젝트를 Nx가 인식한다고 판단한 것은 아니다.

[Copier의 갱신 문서](https://copier.readthedocs.io/en/stable/updating/)는 템플릿 버전, 생성 입력과 기존 프로젝트의 변경, 충돌을 함께 다룬다. 이를 참고해 최초 복사뿐 아니라 업데이트, 재실행도 이식 계약에 포함한다. Copier 설치는 이번 범위가 아니다.

## 어디에 있든 분류할 프로젝트 종속성

파일 단위로 공통/전용을 나누지 않고 내용과 실제 소비 지점을 분류한다. 대상은 script, README, config, matrix, skill, hook, 템플릿, 문서 링크 전체다.

11/09에는 프로젝트 값을 외부 공통 실행기에 전달하는 안을 검토했다. 이후 [ADR 0019](../runtime/0019-project-install.md)에서 평소 사용하는 skill/script/hook을 프로젝트 안에 설치하고 사용자 수정도 보존하는 방향으로 변경했다. 기기의 짧은 시작 명령만 [ADR 0023](../runtime/0023-command-registration.md)에 따라 프로젝트 밖에 등록한다. 공식 배포 원본, 프로젝트 설치본과 기기 명령을 구별하며, 아래 종속 정보 분류는 현재 프로젝트 설치본을 만들 때 적용한다. 현재 hook 호출, 검증 스크립트, 상태 경로의 결합 관측과 두 프로젝트 분리 검증 후보는 [프로젝트별 값의 연결](../../design/runtime/install.md)에 있다. 설치 위치 변경만으로 이식이 끝난다는 뜻은 아니다.

공통 모듈, 적용 프로젝트의 지식/상태와 호스트 설정의 소유를 구분한다. 도입 프로젝트에서 등록한 WIKI 역할/위치를 사용하며, 구체 연결 후보는 [프로젝트 WIKI 연결](../../design/knowledge/wiki.md)에 통합한다.

| 종속 정보 | 현재 프로젝트의 예 | 배치, 소비 방향 |
| --- | --- | --- |
| 제품 구조, 식별자 | sample-* 모듈, 패키지, 클래스명, 코드/테스트 경로 | 프로젝트 분석 결과와 확인된 프로젝트 설정 |
| 명령, 테스트 선택 | Gradle task, include selector, 연동 테스트 예외 | 프로젝트 설정 + 해당 도구 연결부. 예외의 정책 근거도 보존 |
| 문서 경로, 라우팅 | REQUIREMENTS, ADR, runbook 위치, repo/branch 링크 | 기존 문서 체계와 대조한 경로 매핑, 필요한 안내, 링크 생성 |
| 개발, 제품 정책 | Java/Spring 계층 규칙, 메시지 언어, 외부 서비스 책임 | 해당 프로젝트 정책. 현재 프로젝트의 기준을 다른 곳의 정답으로 복제하지 않음 |
| 클라이언트 동작 | hook 이벤트, skill 발견, 진입 방식 | 실행 클라이언트 연결부. 프로젝트 경로 값과 분리 |
| 머신별 값 | 절대 경로, 인증, 연결 주소, 자원 | 호스트 설정. 공통 배포물이나 프로젝트 자동 생성값에 비밀을 포함하지 않음 |
| 실제 기록 | 제품 요구사항, 과거 결정, 작업 상태, 원시 로그 | 각 프로젝트와 해당 실행에 귀속. 공통 배포물에는 템플릿, 명시적 예제만 포함 |

상태 이름, schema 버전, 지원 도구의 표준 파일명처럼 공통 계약이나 탐지 규칙 자체에 필요한 상수까지 제거하는 것은 목표가 아니다. 프로젝트 예제에는 구체 이름을 쓸 수 있으나 다른 프로젝트의 기본 설정으로 유출되지 않아야 한다.

2026-10-27 사용자 확인에 따라 현재 boot 테스트 제외는 비공개 platform BOM의 관련 자원 접근 제한에 따른 프로젝트 정책으로 분류한다. 공통 처리는 예외의 대상, 사유, 미실행을 표현할 수 있어야 하지만, 이 프로젝트의 클래스명, BOM, 제외 목록을 공통 기본값이나 다른 프로젝트의 탐지 결과로 복사하지 않는다. 해당 자원 접근 문제 해결은 이식 구조 설계의 선행 조건이 아니다.

## 분석과 설정, 문서 작성의 관계

```text
대상 코드, 빌드/테스트 설정, 기존 문서, 선택한 Git 이력
  → 확인한 사실, 출처, 충돌, 미확인 정보
  ├─ 프로젝트 설정 후보 → 검증, 필요한 보정 → 공통 코어/연결부가 소비
  └─ 현재 동작 설명, 요구사항/결정 후보 → 근거 검토 → 프로젝트 문서에 반영
```

자동 탐지는 기존 빌드, 테스트 설정을 우선 근거로 삼는다. 명시적 프로젝트 보정과 충돌하면 출처와 차이를 보여준다. 선언된 실행 후보를 확인 없이 실행하거나 코드에 있는 테스트 제외를 채택 정책으로 자동 복사하지 않는다.

기존 빌드 설정을 복사해 별도 manifest를 새 원본으로 삼지 않는다. **값별 원본과 해석 결과를 구분한다.** [Nx 설정 문서](https://nx.dev/docs/reference/project-configuration)는 원래 도구 설정을 원본으로 유지하면서 추론, 명시 설정을 합치는 사례다. 아래 분리는 이 프로젝트에 대한 설계 판단이다.

| 구분 | 역할 | 변경 시 처리 |
| --- | --- | --- |
| 기존 프로젝트 원본 | 빌드의 모듈, task, 의존, 테스트 설정, 기존 문서 | 원본에서 수정하고 관련 분석 결과를 무효화 |
| 명시적 하네스 정책, 보정 | 자동 추론할 수 없는 검사 예외, 문서 역할 매핑, 지원하지 못한 값의 확인된 보정 | 근거와 범위를 남기고 다시 해석. 도구 원본과의 충돌을 숨기지 않음 |
| 해석 완료된 프로젝트 정보 | 원본+보정에서 얻은 검사/경로 후보와 출처, 식별 | 재생성 가능한 파생 자료. script, README, matrix에 서로 다른 목록을 수동 유지하지 않음 |

이 해석 결과를 계획의 프로젝트 연결 정보로 고정한다. 재분석된 값이 달라지면 새 계획, 관련 증거의 유효성을 판단한다. 모듈 추가, 삭제, 경로 변경, 도구 설정 변경을 감지할 수 없는 분석 결과는 계속 유효하다고 주장하지 않는다. 파일 확장자만 보고 동적 빌드 구조까지 전부 알아냈다고 취급하지 않는다.

탐지 비용은 설치, 명시적 재분석, 관련 설정 변경 시점에 집중한다. 일반 요청에서 전체 저장소, 이력을 모델에 반복 입력하지 않는다. [Gradle lifecycle](https://docs.gradle.org/current/userguide/build_lifecycle_intermediate.html)처럼 도구 초기화, 설정 단계에서 빌드 코드가 평가되는 경우가 있으므로 메타데이터 조회를 단순 파일 읽기와 구분해야 한다. 구체 실행 방식은 구현 단계에서 정한다.

문서 복원에서는 기준 SHA와 미커밋 변경, 현재 관찰과 의도된 요구, 확인된 과거 결정과 추정을 나눈다. 기록이 없는 과거 이유, 채택, 검증 결과를 만들어 채우지 않는다. 기존 문서는 보존하고 추가/수정 후보, 충돌을 제시한다. [Git log 문서](https://git-scm.com/docs/git-log)가 제공하는 경로/변경 이력과 `--follow`의 단일 파일 제한 등을 확인해 기능별 근거를 수집하되, 이력 탐색이 과거 의도를 자동 증명한다고 해석하지 않는다.

문서 후보의 최소 근거는 주장, 코드/테스트/문서 위치와 revision, 관련 커밋, 기록, 관찰/추정/확인된 결정의 구분이다. 특정 코드가 존재한다는 근거는 현재 동작 설명을 지지할 수 있지만, 그것이 버그가 아닌 채택 요구사항이라는 증거는 별도로 필요하다. 커밋에서 이유를 찾지 못하면 ADR의 과거 이유를 상상해 채우지 않는다. 지금 내리는 결정이라면 현재 날짜의 새 결정으로 기록한다.

전체 역사 복원은 하네스가 처음 작동하기 위한 선행 조건이 아니다. 실행 연결과 제품 지식 복원을 분리해 필요한 기능부터 채우고, 이미 유효한 REQUIREMENTS, ADR이 있는 프로젝트도 정상 도입 대상으로 둔다.

## 설치와 갱신에서 지킬 소유권

공통 배포물이 소유하는 파일, 프로젝트가 소유하는 정책, 제품 문서, 재생성 가능한 부분을 구분해야 한다. 기존 AGENTS, README, skill, hook이 있다고 통째로 대체하거나, 다른 프로젝트의 요구사항, 진행 상태를 기본값으로 복사하지 않는다. 처음 설치한 버전, 입력과 이후 수정을 알아야 갱신 충돌을 설명할 수 있다는 점은 [Copier 갱신 문서](https://copier.readthedocs.io/en/stable/updating/)의 실제 문제와도 맞닿는다.

향후 설치기는 반영 예정 diff와 충돌을 검토할 수 있게 하고, 재실행 시 중복 삽입, 사용자 편집 유실을 막아야 한다. 수동 편집된 생성 부분의 처리는 후속 상세 설계에서 정한다. 최초 복사가 성공했다는 것만으로 배포 가능 수준의 이식이 끝난 것은 아니다.

## 후속 검토: 문서 위치 연결

아래는 11/09 채택 전의 검토 흐름이다. 최신 채택 범위는 [상단 — 「문서 연결의 채택 범위」](0004-portability.md#%EB%AC%B8%EC%84%9C%20%EC%97%B0%EA%B2%B0%EC%9D%98%20%EC%B1%84%ED%83%9D%20%EB%B2%94%EC%9C%84), 상세 입력은 [위치표 명세](../../design/knowledge/map.md)가 소유한다.

2026-11-09, 기존 원본, 정책/보정, 파생 결과의 경계를 문서 탐색에 구체화했다. [역할별 위치 연결](../../design/knowledge/wiki.md)에서 목차만 사용 / 역할별 위치와 본문 링크 / 전체 색인, 관계 검색을 비교한다. 추천은 작은 위치표로 역할, 범위의 원본을 찾고 상세 관계는 소유 문서에 두는 방식이다. 원문을 복제하지 않으면서 반복 절차가 사용할 명시적 진입점을 확보하려는 판단이다.

위치표의 갱신과 역할 확인 비용을 감수하며 경로 유효성만으로 의미 정확성을 보장하지 않는 안을 검토했다. 기존 요구의 ID, 안정된 참조를 활용하는 [arc42 지침](https://docs.arc42.org/tips/1-5/)을 참고했고, 당시 특정 저장 형식, 자동화는 미확정이었다. 이 단계에서는 ADR 전체가 `proposed`였으며 설치기, 라우팅 구현은 하지 않았다. 토큰 효과는 현재도 미측정이다.

같은 날 후속 설계에서 [위치표 저장 방식 — 「위치표를 저장하는 방식」](../../design/knowledge/wiki.md)을 Markdown 표, JSON, TOML로 비교하고 JSON을 추천했다. 도구가 위치표를 읽고 갱신하는 흐름을 우선하며 상세 설명은 Markdown 원본에 두려는 판단이다. 설정 파일이 추가되고 주석, 수동 편집의 불편이 남으므로 모든 프로젝트에 우월한 형식으로 단정하지 않는다. 이 비교 시점에는 형식, 필드, 배치 모두 미채택이었다.

[사용 절차 — 「위치표를 사용하는 절차」](../../design/knowledge/wiki.md)는 기계적 위치/형식 검사, AI 원문 대조, 근거로 확정할 수 없는 중요 사항의 사용자 확인을 구분한다. ‘의미 검토’는 자동 대조를 포기하거나 전 문서를 사람이 다시 읽는 절차가 아니다. 정확한 필드, 소비 지점, 실패 동작은 관련 범위 합의 뒤 구현 명세에서 확정한다.

같은 날 사용자는 역할별 JSON 분리와 기존 프로젝트의 규모를 질문했다. 앞선 대화의 ‘처음에는 단일 파일만 구현하고 나중에 분리 지원’ 추천은 초기 개발 편의를 앞세워 이미 복수 기능/계약이 있는 적용 대상을 충분히 고려하지 못했다. [규모와 파일 구성 비교 — 「프로젝트 규모와 위치표 분리」](../../design/knowledge/wiki.md)에서는 **공통 진입점 + 선택적 기능/흐름별 분리**를 첫 지원 범위로 추천한다. 단일 배치도 허용하고 프로젝트 규모에 관계없이 모든 항목을 쪼개지는 않는다.

감수할 비용은 분할 참조, 중복, 누락, 부분 갱신의 초기 검사였다. 복잡한 include/상속 체계까지 도입하지 않고 실제 역할, 경계, 변경 양상을 보고 배치를 제안했다. 이 보정 당시에는 미채택이었으며 제품 구현, 기존 문서 이동은 승인받지 않았다.

이어진 질문에서는 위치표의 정보량과 분할 파일을 발견하는 방식을 구별했다. [파일 발견 비교 — 「분할 파일을 찾는 방식」](../../design/knowledge/wiki.md)의 A 명시적 목록, B 폴더 탐색, C 계층 목록 중 A와 도구의 등록 갱신을 추천했다. 기존 원문, 허용 범위를 보존하고 누락된 등록 파일을 발견하기 쉬운 점을 우선했다. 목록 갱신, 충돌 비용은 남으며 자동 탐색 자체가 열등하다는 결론은 아니다. 후보 파일을 찾는 것과 사용 대상으로 포함하는 것은 구분한다. 이 비교 당시에는 형식, 자동화 상세, 첫 지원 범위가 미채택이었다.

같은 날 [사람의 개입 가능성 — 「사람이 읽고 관리하는 위치표」](../../design/knowledge/wiki.md)을 보강했으나, 설명이 사람만의 운영을 중심으로 확대됐다는 사용자 정정을 받았다. 정상 사용, 유지보수는 AI가 중심이고 사람의 이해, 개입은 함께 지킬 조건으로 바로잡았다. AI가 연결 의미, 변경 범위를 판단하고 일반 코드가 조회, 검사, 갱신을 담당하는 JSON 추천을 유지했다. 저장 크기와 실제 모델 입력, 수정 범위를 구별하고 정확성, 총토큰, 갱신/검증 비용, 구현 복잡성을 함께 비교했다. 이후 사용자가 상단의 문서 연결 구성을 채택했으며 효과 검증은 현재도 미완료다.

## 현재 설계에 바로 적용할 제약

- ADR 0001~0003의 공통 계획, 결과에는 특정 모듈명, Gradle task, 테스트 클래스가 내장되지 않는다. 해석 완료된 프로젝트 설정과 연결부가 구체 검사 목록을 제공한다.
- 계획/실행 기록은 사용한 프로젝트 설정과 연결부의 버전, 해시 등 식별 정보를 참조한다. 설정이 바뀐 뒤 과거 계획, PASS를 조용히 재사용하지 않는다.
- 현재 프로젝트의 Gradle은 첫 검증 사례다. 다른 스택에서도 같은 검증 보장을 쓰며, 해당 도구에 증분, 캐시 기능이 없거나 신뢰 조건이 부족하면 새 실행을 사용한다.
- 복구 설계에도 프로젝트별 작업 상태 저장 경로, 라우팅, 클라이언트 연결을 같은 방식으로 분리한다. 개인 `active.md`의 존재, 내용을 요구하지 않으며 새 작업 상태는 실제 실행에서 생성한다. 구체 위치, 필드와 파일별 변경은 이후 단계에서 정한다.
- 현재 단계에서 bootstrap, 모델 설치, 다른 프로젝트 변경을 시작하지 않는다. 제품 문서 복원 구현은 후속이지만 이식성 제약은 지금의 설계부터 적용한다.

## 최종 확인할 조건과 미정 사항

지원 스택 안에서 모듈, 폴더, 테스트, 문서 경로를 바꿔도 공통 코드 수정 없이 동작하는지, 다른 실제 프로젝트에서 기존 자산을 보존하며 도입 가능한지 확인한다. fixture의 이름 변경만으로 실제 이식 성공을 주장하지 않는다.

또한 미지원 스택, 충돌 설정, 이력 부족을 정직하게 반환하는지, 재분석, 재설치, 버전 갱신이 기존 수정과 문서를 보존하는지, 문서 주장에 코드/커밋 근거가 연결되는지 확인한다. 초기 지원 스택, 자동 탐지 범위, 설정 형식, 생성 파일 소유권, 배포, 업데이트 수단은 미정이다.

| 확인 축 | 남길 근거, 수치 후보 |
| --- | --- |
| 같은 스택의 이름, 구조 변화 | 코어 수정 필요 여부, 잘못 남은 프로젝트 전용 값, 누락/잘못 탐지한 항목과 전체 정답 항목 |
| 실제 다른 프로젝트 도입 | 대상별 도입 결과, 수동 보정량, 도입 시간, 기존 자산 보존, 검증/복구 동작 |
| 새로운 스택 확장 | 연결부, 프로젝트 정책 변경과 공통 코어 변경을 구분. 모든 스택을 이미 지원한다고 주장하지 않음 |
| 설정 갱신 | 새 모듈, task, 경로 변경의 탐지, 낡은 해석 결과, 계획 거부, 충돌 표시 |
| 문서 복원 | 검토한 주장 중 근거 부족/오류/충돌 수, 필수 사실 누락, 사용자 보정량. 생성 문서 개수를 품질로 대체하지 않음 |
| 재설치와 업데이트 | 같은 입력 반복의 불필요한 diff, 사용자 편집 유실, 해결하지 못한 충돌 |

현재 이 표는 측정 계획이다. 이후 작성한 [모듈 설계](../../design/README.md)와 ADR 0010, 0011에 설치와 갱신, 보존 후보를 연결했다. 현재 설치 위치는 ADR 0019, 기기 명령은 ADR 0023, 사용자 변경 보존과 갱신은 [갱신 설계](../../design/runtime/update.md)를 따른다. 11/09 외부 실행본을 현재 설치 방식으로 다시 적용하지 않는다. 파일별 종속성 목록, 지원 버전, 분석/문서 생성의 상세 구현도 미완료다. 기술 검토에는 실제 이식, 복원 근거만 사용한다.
