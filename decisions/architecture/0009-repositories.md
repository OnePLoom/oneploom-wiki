# ADR 0009: 모듈 원본과 적용 프로젝트 분리

- 날짜: 2026-10-27
- 설계 상태: `accepted` — 독립 모듈 원본, 적용 프로젝트와 개발 WIKI의 소유를 분리한다. 2026-11-05 기본 모듈 기준점, 11/08 개발 WIKI 분리, 11/23 두 로컬 Git과 11/24 조직 아래 두 원격 주소를 확정했다. 공개/릴리스 준비와 제품 검증 완료를 뜻하지 않는다.
- 채택 범위: 독립화, 명명, 연결과 정한 최소 동작을 검증한 기본 모듈을 기준으로 기능별 개선을 쌓는다. 코드와 개발 WIKI는 독립 저장소로 관리한다. 실제 커밋/원격 운영과 배포는 후속
- 구현 및 검증: 11/23 선별 문서와 로컬 Git 초기화, Windows 파일/경계 검사 완료. 제품 기능 구현/배포 검증은 미완료
- 상세: [모듈 경계 검토](../../design/README.md)

## 채택 범위와 남은 작업

독립 코드/WIKI 저장소와 적용 프로젝트의 소유 경계는 결정됐다. 로컬 기준 커밋, 원격 인증/공유, 배포 라이선스와 릴리스 준비는 각각 확인한다. 저장소 분리 결정만으로 패키지 동작이나 공개 준비가 완료되지는 않는다.

## 문제와 근거

최종 모듈은 현재 제품에 의존하지 않는 별도 Git 배포 대상이다. 개발 원본과 프로젝트별 설정, WIKI를 같은 원본처럼 편집하면 배포에 제품 정보가 섞이거나 두 복사본이 달라질 수 있다. 미추적 폴더에서 개발하면 버전, 롤백 근거도 약해진다.

공통 코드와 프로젝트 자료의 공존은 도구와 설정, 입력의 관계다. 독립성은 제품별 경로, 모듈, 예외, 문서를 원본 밖으로 분리하는 것이며, 지원하는 도구, 런타임 의존성까지 없애는 요구로 해석하지 않는다.

## 대안

| 안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 현재 저장소의 미추적 하위 폴더에서 모듈 개발, 적용본과 수동 맞춤 | 시작이 빠르고 한 작업 공간 | 모듈 이력 부재, 오반영, 복사본 불일치 위험 |
| B | 형제 디렉토리의 독립 Git 저장소에서 개발, 각 프로젝트는 버전 지정 적용 | 소유, 이력, 공개 범위 명확, 재현, 복구와 다중 소비자 시험 용이 | 설치/갱신과 저장소별 변경 기록 필요 |
| C | 독립 저장소를 submodule로 연결 | 별도 이력과 정확한 커밋 참조 | 상위 gitlink, 설정, clone/init/update 운영 부담 |

Git 공식 문서에서 submodule의 독립 이력, gitlink와 worktree의 같은 저장소 공유를 확인했다. 따라서 별도 worktree만 만드는 것은 B의 독립 저장소 생성과 다르다. 다만 적용 프로젝트의 격리 시험에는 유용하다. [Submodules](https://git-scm.com/docs/gitsubmodules), [Worktree](https://git-scm.com/docs/git-worktree).

## 추천과 비용

B를 추천한다. 공통 코드 원본은 모듈 저장소 하나, 제품 설정, 채택 WIKI는 각 프로젝트가 소유한다. 로컬 Git 기록과 원격 공개는 별개이므로 공개 준비가 끝날 때까지 모듈을 미추적으로 둘 필요가 없다. [Git init](https://git-scm.com/docs/git-init).

모듈 수정 → 버전/배포물 고정 → 대상 변경 미리보기 → 설치/연결 시험 → 확인한 버전 조합 기록 순서로 적용한다. 공식 원본과 사용자 설치본의 양방향 자동 동기화나 개발자가 프로젝트마다 별도 공통 코드 분기를 관리하는 구조는 두지 않는다. 사용자의 설치 결과 커스터마이징을 금지하거나 공식 배포 버전 발행을 사용자에게 요구하는 뜻은 아니다. 11/09 이 구분을 사용자 질문에 따라 보강했으며 [설치 기준과 사용자 변경 — 「갱신과 복원」](../../design/runtime/update.md)에 연결한다. 설치본은 개발자 모듈 체크아웃 없이도 실행돼야 한다. 이후 Git 릴리스 + Python 제공은 ADR 0010, 프로젝트 내 실행 배치는 ADR 0019에서 채택했고 정확한 패키징, 경로, 연결 명세는 후속이다.

업데이트는 소유별로 구분한다. 공통 설치 파일은 이전 해시와 대조하고, 예상 밖 편집, 기존 파일 충돌은 덮지 않는다. 프로젝트 설정, WIKI 변경은 별도로 검토한다. 초기에는 충돌 검출, 중단을 우선하며 자동 병합기의 직접 개발은 보류한다. Copier의 버전별 템플릿/대상 구분과 충돌 처리 원칙을 참고했으며 도구 채택은 아니다. [Copier 업데이트](https://copier.readthedocs.io/en/stable/updating/).

저장소 두 개의 변경은 원자적으로 커밋되지 않는다. 모듈 버전, 설정 규격, 대상 변경, 시험 결과의 조합을 남기고, 부분 설치, 규격 불일치, 복원 경로를 확인하는 비용을 감수한다.

## 기본 모듈의 시작점

2026-11-05 사용자 정정: 질문은 설계 뒤 **독립 기본 모듈의 준비를 먼저 커밋하고 기능별 개선을 쌓는 방식**에 관한 것이다. 현재 프로젝트 전체를 새 저장소에 넣자는 제안이 아니었다. 별도 저장소의 목표와 이 시작점 제안을 연결하되, 정확한 초기 구성, 커밋 수, 구현 착수는 아직 정하지 않았다.

| 출발 방식 | 장점 | 단점, 비용 |
| --- | --- | --- |
| 빈 폴더, 설정 틀만 먼저 커밋 | 준비가 빠르고 이후 변화가 모두 이력에 남음 | 실제 실행, 참조, 복구의 기준이 없어 사용자가 원하는 기본 모듈로는 부족 |
| 독립 실행에 필요한 준비와 최소 동작을 검증한 기본 모듈부터 시작 | 종속 정보, 명명, 연결을 정리한 기준에서 기능별 차이와 회귀를 확인하기 쉬움 | 기존 코드의 실제 의존을 찾아 분리하는 초기 작업과 작은 예제 검증 필요 |
| 전체 재설계, 기능 개선을 끝내고 최초 커밋 | 첫 버전에 완성된 구성을 담을 수 있음 | 첫 변경이 커지고 준비/기능 개선의 원인, 검토, 되돌림 경계가 흐려짐 |

두 번째 방식을 추천했고 2026-11-05 사용자가 **모듈 세팅 B안**으로 채택했다. 기본 모듈에는 합의한 독립성, 명명, 연결, 최소 동작의 준비를 담고, 이후 기능 개선은 별도 변경으로 쌓는다. 준비 작업 자체도 개발이므로 커지면 검토 가능한 커밋으로 나누고 **준비 완료 커밋**을 기능 개발의 기준점으로 삼는다. 이 기준점이 반드시 저장소의 첫 번째 커밋일 필요는 없다. 이는 작은 변경을 독립적으로 검토하고 관련 검사와 중간 동작을 유지하라는 [Google 지침](https://google.github.io/eng-practices/review/developer/small-cls.html)을 현재 작업에 적용한 판단이다.

기본 모듈의 내용, 완료 조건은 [모듈 문서 — 「기본 모듈의 시작점」](../../design/module.md), 기존 구조와 모듈 기준점의 기록, 커밋 분할은 [ADR 0012 — 「작업 단위와 시작점」](../development/0012-branches.md)가 소유한다. 기존 결함의 전부 해결, 역공학 완성, 다른 모델 지원을 초기 세팅 완료와 혼동하지 않는다. 시작점 채택과 설치/갱신의 상세 계약, 실제 개발 진행 상태는 구분한다.

## 모듈의 개발 WIKI

11/08에는 모듈 자체의 개발 WIKI를 공개하고 코드/WIKI의 작업별 버전 연결을 자체 적용하는 방향을 정했다. WIKI의 독립 Git 관리와 모듈 소스 저장소의 submodule 대안은 서로 다른 결정이다. [모듈 자체 WIKI — 「모듈 자체의 WIKI」](../../design/module.md)에 역할과 연결을 정리한다. 실제 로컬 배치는 11/23에 구체화했다.

개발 WIKI를 독립 관리하면 코드와 문서의 이력을 구분하고 작업별로 연결할 수 있다. 초기 기준 커밋과 첫 공개 배포는 별개다. 도구가 준비되기 전에 개발 WIKI를 자동 복원했다고 보고하지 않는다.

같은 응답에서 실제 비밀번호, 토큰, API 키 등의 비기록과 이름에 수정 버전을 무분별하게 붙이지 않는 기준을 추가했다. [비밀값 문서화 경계 — 「비밀값을 남기지 않는 문서화」](../../design/module.md)와 [이름, 변경 이력 — 「이름과 변경 이력」](../../design/module.md)을 따른다. 추적 범위 분리만으로 본문이나 이력의 안전성을 보장하지 않으며 자동 검출, 공개 검증은 구현 전이다.

## 채택 후 확인

11/23 코드와 WIKI를 형제 디렉토리의 독립 main 로컬 Git으로 준비했다. 개발 지식은 공개 WIKI 안에서 완결되게 유지하며 원격 생성/공개와 제품 기능 구현은 별도다. [개발 공간](../../development/workspace.md)에 소유와 순서를 연결한다.

- 모듈 배포물에 현재 제품의 필수 의존, 비공개 자료가 없어야 한다.
- 이름, 경로가 다른 작은 프로젝트와 실제 소비 프로젝트에서 공통 원본 수정 없이 동작해야 한다.
- 기존 시험 프로젝트의 기존 문서는 기존 작업에서 작성한 자료의 채택 사례로 확인한다. 새 모듈의 자동 역공학 성공으로 계산하지 않는다.
- 빈 문서 초기화, 기존 편집 보존, 갱신, 충돌, 부분 실패, 이전 버전 복귀를 별도로 시험한다.
- 로컬 저장소 위치와 main은 준비했다. 제품 실행/지원 조건은 실제 구현에서 검증하고 원격/공개/릴리스는 별도 확인한다.

[ADR 0004](0004-portability.md)의 이식 목표를 개발, 적용 소유 경계로 구체화한 결정이며, [ADR 0007](0007-release-scope.md)의 배포 범위를 자동 채택하거나 넓히지 않는다.

11/09 사용자는 모듈 코드, 관련 공개 WIKI의 저장소 분리와 작업별 커밋, 배포 태그를 재확인했다. 같은 개발 프로젝트로 관리하되 저장소의 Git 이력은 별개다. 당시 이름/브랜치도 미확정이었으며 제품명은 11/22, 새 모듈 브랜치는 11/23 후속 선택을 따른다. 11/24 OnePLoom Organization의 oneploom과 oneploom-wiki를 사용하기로 했고, 생성 완료 안내로 받은 두 주소를 각각 로컬 origin에 등록했다. 로컬 커밋과 push, GitHub Projects 보드, 라이선스 선택은 독립된 준비 단계다. 주소와 개발 원본/배포/설치 결과의 구분은 [개발 공간](../../development/workspace.md), 상세 소유와 태그/릴리스는 [모듈 자체의 WIKI](../../design/module.md)와 [변경 이력 — 「이름과 변경 이력」](../../design/module.md)이 소유한다.

11/11에는 실제 개발 착수부터 두 저장소에 준비, 기능 변경을 쌓고 현재 커밋/PR 작성 절차를 활용하자는 제안을 연결했다. [개발 시작부터의 Git 운영](../development/0012-branches.md)이 순서, 개발 도구와 배포 기능의 구분을 소유한다.

11/11 [ADR 0019](../runtime/0019-project-install.md)에서 프로젝트 내 실행 구성 설치, 팀 공유 권장, 기존 진입점/전용 영역의 조합을 채택했다. 이는 [ADR 0010](../runtime/0010-distribution.md)의 이전 외부 실행본 배치 부분을 대체하며 공식 원본의 독립성, 사용자 수정 자유, 기존 Git 추적 정책은 유지한다. 구체 제공 수단은 0010, 보존은 [0011](../runtime/0011-preservation.md), 브랜치는 [0012](../development/0012-branches.md)에 둔다.
