# ADR 0005 — 검증 대상 선택과 실행 재사용의 분리

- 작성일: `2026-10-27`
- 설계 상태: `accepted` — 2026-11-11 검사 선택, 확대, 로컬/CI 분담과 조건부 테스트 작성 skill 배치 채택. 상세 구현, 다른 검증 ADR은 별도.
- 채택: **A에 검사 확대 조건과 필수 CI 대기를 명시**. C는 넓은 로컬 검사가 필요한 경우의 대안, B는 선택 정확도, 비용 검증 후 확대 후보.
- 채택 근거: 사용자가 보정안 설명 뒤 “그렇게 하자”로 확인했다. 기존 프로젝트의 필수 검사, 예외를 유지하며 현재 제품 script, CI를 변경한 것은 아니다.
- 구현 및 검증: 구현과 검증 모두 미완료. 현재 제품의 회귀 누락률, 전체 검사 시간, 선택 최적화 효과는 미측정이다.

## 이번 재검토에서 분리한 문제

검사 선택은 **무엇을 확인해야 하는가**, 재사용은 **이미 선택한 검사를 다시 수행해야 하는가**에 대한 판단이다. [ADR 0002](0002-pass-validity.md)의 빌드 도구 활용만으로 앞의 문제가 해결되지는 않는다.

현재 script는 core-only 변경에서 `:sample-core:test`를 고른다. 실제 `sample-api/build.gradle`에는 core 의존이 있다. matrix는 이를 최소 floor로 설명하며 테스트 충분성의 최종 판단을 메인에 남긴다. 따라서 이 사실을 곧바로 현행 계약 위반이나 실제 API 회귀 누락의 재현으로 보고하지 않는다. **기계 계획만으로 완료 충분성을 보장하기에는 추가 판단이 필요하다는 정적 근거**다.

11/11에는 core의 추적된 테스트 소스가 없고, boot 포함 목록 한 항목의 패키지가 실제 테스트와 다름을 정적으로 확인했다. 로컬의 지정 목록과 CI의 필터 없는 `test`도 구분했다. 상세, 한계는 [현재 프로젝트의 검사 범위](../../design/workflow/verification.md)가 소유하며 제품 테스트를 실행하거나 수정한 결과는 아니다.

Gradle의 [CLI 문서](https://docs.gradle.org/current/userguide/command_line_interface.html)는 특정 task와 그 실행 의존을 다룬다. 선택한 task의 prerequisites 실행과 변경된 모듈을 소비하는 다른 모듈의 검사를 선택하는 것은 다르다. 별도 wiring이 없다면 소비 모듈 검사까지 자동 선택됐다고 가정할 수 없다. 현재 제품의 실제 task graph를 실행해 확인한 것은 아니다.

## 비교한 방안

| 방안 | 쉬운 설명 | 장점 | 단점, 비용 |
| --- | --- | --- | --- |
| A. 변경 경로의 최소 검사 + 메인 보완 | 현재처럼 바뀐 모듈부터 검사하고, 메인이 다른 영향 범위를 추가한다. | 변경량과 초기 비용이 작다. 구현 중 빠른 피드백에 적합하다. | 메인이 소비 모듈, 공통 설정, 계약 영향을 매번 놓치지 않아야 한다. floor PASS를 충분한 완료 근거로 읽으면 누락된다. |
| B. 검증된 영향 분석으로 좁은 검사 집합 선택 | 도구, 연결부가 변경 입력과 소비 관계를 설명하고 필요한 검사 집합을 제공한다. 모르는 관계는 확인하거나 확대한다. | 규모가 커질 때 수행량을 줄일 가능성이 크고 선택 사유를 기계적으로 남길 수 있다. | 입력과 출력, 의존 선언이 부족하면 선택부터 잘못된다. 지원 도구마다 연결, 검증 비용이 들며 범용 그래프를 자체 구현하면 부담이 크다. |
| C. 프로젝트가 명시한 넓은 완료 검증 묶음 호출 | 제품 검증이 필요한 작업의 완료 시점에 정의된 회귀 검사 묶음을 호출하고, 본문 재실행은 도구의 검증된 재사용 정책에 맡긴다. | 별도 정밀 영향 분석기 없이 누락 가능성을 줄이는 비교 기준을 만든다. 프로젝트별 검사 목록과 공통 실행 계약을 분리하기 쉽다. | 프로젝트 설정과 테스트 시작 비용이 늘 수 있다. 외부 상태 검사는 실제로 반복될 수 있으며 대규모 프로젝트에서는 비싸다. |

## 추천과 이유

채택한 기본은 **A를 바탕으로 관련 검사, 확대 조건, 필수 CI를 명시하는 방식**이다. 로컬에서는 변경 동작과 영향을 받는 기존 기능을 확인하고, 넓은 회귀, 환경 조합은 프로젝트가 정한 CI에서 확인한다. 공통 코드, 계약, 공유 fixture 변경이나 영향 범위 불명확성이 있으면 로컬 검사도 확대한다. 구체 흐름과 대안은 [로컬 완료와 CI의 분담](0005-verification-selection.md#%EB%A1%9C%EC%BB%AC%20%EC%99%84%EB%A3%8C%EC%99%80%20CI%EC%9D%98%20%EB%B6%84%EB%8B%B4)이 소유한다.

10/27부터 11/11 첫 질문까지는 네 제품 모듈의 선택 누락을 줄이려고 C를 우선 추천했다. 이후 사용자가 실무의 로컬/CI 분담을 물어 재검토했다. 최소 명령의 성공만으로 충분하지 않다는 관찰은 유효하지만, 이를 모든 적용 프로젝트의 넓은 로컬 회귀 의무로 확대할 근거는 부족하다. 조건부 실행, 첫 구현 부담, 기존 CI 활용을 함께 고려해 기본 추천을 보정했다. 이전 C가 채택됐거나 실제로 느렸다는 뜻은 아니며 검사 시간은 아직 미측정이다.

C는 전체 검사가 충분히 빠르거나, 기존 정책이 넓은 로컬 검사를 요구하거나, CI를 사용할 수 없는 프로젝트의 대안이다. B는 신뢰할 수 있는 영향 선택 도구가 이미 있거나 선택 비용, 정확도를 검증한 뒤 고려한다. 공통 코어가 모든 언어의 그래프를 새로 만드는 방식은 첫 목표로 두지 않는다. [Nx affected 문서](https://nx.dev/docs/features/ci-features/affected)는 이런 선택에 프로젝트 관계와 입력이 필요함을 보여주는 참고이며 Nx 도입을 결정한 것은 아니다.

## 추천 계약

검사 선택, 확대, 예외와 완료 범위의 구분은 이번 채택에 포함한다. 후속 ADR 0001, 0003에서는 계획 보존, 시도별 결과, 완료 구분을, ADR 0002에서는 C의 재사용 원칙을 별도로 채택했다. 정확한 형식/판별, 저장은 계속 협의하며 아래 연결 조건만으로 세부 계약을 일괄 채택하지 않는다.

- 메인은 gate 필요 여부와 변경의 의미를 판단한다. 프로젝트 설정, 연결부는 적용 가능한 검사 목록과 선택 사유를 제공하고, 공통 처리는 결과의 대응, 완전성을 확인한다.
- `작업 변경 범위`, `검사가 읽는 입력`, `완료에 필요한 검사 목록`을 같은 scope 하나로 취급하지 않는다. 계약 문서 변경은 코드 diff가 없어도 구현 검증을 요구할 수 있다.
- 완료 묶음은 이름이 `test`라는 이유만으로 정하지 않는다. 현재 실제 argv, 테스트 선택, 외부 환경, 제외 정책을 대조한다. boot 제외 사유는 2026-10-27 사용자가 비공개 platform BOM 관련 자원 접근 제한으로 확인했다. 이 프로젝트의 예외는 유지하고 9개 include가 의도한 제외와 나머지 검사 범위를 표현하는지만 확인한다.
- 넓은 묶음도 모든 테스트의 존재, 품질, 요구사항 충족을 증명하지 않는다. 확인된 예외로 제외한 검사는 미실행으로 표시하고, 그 밖의 필수 검증 미완료와 구분한다. 합의된 범위를 충족했는지 판단하되 제외한 검사까지 PASS라고 보고하지 않는다. 새 예외가 필요하면 기존 정책 협의 규칙을 따른다.
- 원래 실패 검사와 추가 필수 검사를 현재 완료 목록에 연결하고 중복 명령은 통합할 수 있다. 같은 종료 시점에 의미 없이 동일 묶음을 두 번 실행하도록 요구하지 않는다.
- 범위가 불명확하면 최소 추가 확인을 먼저 한다. 그래도 좁힐 수 없으면 사전에 정의한 넓은 묶음을 사용한다. 그 묶음도 없거나 실행 환경을 갖추지 못했다면 UNCLASSIFIED 또는 미완료 사유로 반환하며 임의 PASS로 끝내지 않는다.
- B를 도입할 때는 변경된 모듈의 소비자, 테스트만 바뀐 경우, 공통 빌드 설정, lockfile, 외부 계약, 새 파일의 영향을 대조한다. 테스트 수나 속도만 좋아졌다는 이유로 선택을 줄이지 않는다.

## 로컬 완료와 CI의 분담

11/11 범위표와 실무 사례를 대조해 C에서 A 보완안으로 기본 추천을 보정했고, 이후 사용자가 **관련 로컬 검사, 조건부 확대, 필수 CI 분담**을 채택했다. 아래 비교 이력은 보존하며 테스트 작성 절차의 후속 채택은 [작성 절차 연결 — 「테스트 작성 절차의 연결」](0005-verification-selection.md#%ED%85%8C%EC%8A%A4%ED%8A%B8%20%EC%9E%91%EC%84%B1%20%EC%A0%88%EC%B0%A8%EC%9D%98%20%EC%97%B0%EA%B2%B0), 다른 검증 ADR은 별도로 다룬다.

| 안 | 개발 중 → 로컬 완료 → CI | 장점 | 비용, 한계 |
| --- | --- | --- | --- |
| A — 관련 검사, 확대 조건, CI 분담 명시, 채택 | 관련 검사 → 소비 기능, 공통 변경에 필요한 검사 보완 → CI의 필수 회귀 검사 | 로컬 대기와 초기 구현 부담을 줄이고 기존 CI 활용 | 영향 판단을 놓치면 CI에서 늦게 발견할 수 있음. 확대 조건, 미완료 표시가 필요 |
| C — 넓은 로컬 완료 묶음과 CI | 관련 검사 → 프로젝트가 정한 넓은 로컬 회귀 묶음 → CI 필수 검사 | 정밀 영향 분석기 없이 공유 전 넓게 확인 | 로컬 시간, 준비 부담과 CI 중복. 전체 검사가 빠르거나 기존 정책이 요구할 때 적합 |
| B — 검증된 영향 선택 | 관계를 확인한 영향 범위를 로컬/CI에서 선택 | 큰 프로젝트에서 검사량 감소 가능 | 누락 없는 선택의 입력, 도구, fallback 검증이 필요. 범용 분석기를 먼저 만드는 부담 |

**채택한 A의 로컬 기준은 변경된 동작의 영향 범위다.** 수정한 테스트 파일뿐 아니라 기존 테스트, 소비 모듈, 공유 데이터와 계약을 함께 보고 필요한 검사를 선택한다. core의 테스트가 비어 있다는 이유로 이를 사용하는 API 동작까지 확인됐다고 판정하지 않는다. 테스트가 부족하면 무엇을 확인하지 못했는지 남기며 넓은 실행만으로 그 공백을 해결했다고 보지 않는다.

| 시점 | 채택한 확인 범위 |
| --- | --- |
| 개발 중 | 변경 동작, 새 버그 재현, 수정한 테스트를 좁게 실행해 빠르게 확인 |
| PR 준비 | 영향을 받는 기존 테스트와 필요한 빌드/정적 검사. 공통 코드, 외부 계약, 공유 fixture, 설치/복구 변경이면 관련 통합/보존 검사까지 확대 |
| CI | 프로젝트가 정한 필수 회귀, 통합, 환경 조합을 현재 PR/병합 대상 기준으로 확인. 변경 테스트의 재실행도 CI의 공통 기준에 포함될 수 있음 |

확대 조건은 기존 명령, 의존 관계, 명시 정책을 사용해 설명하며 범용 영향 분석기부터 만들지 않는다. 영향 범위를 좁힐 근거가 없으면 합의된 넓은 검사 묶음으로 확대한다. 그 범위나 실행 환경도 정해져 있지 않으면 필요한 선택을 물으며 최소 명령 PASS로 끝내지 않는다. 실제 사용자 자료를 바꾸는 설치/복원은 사전 보호 검증과 검토가 필요하고, 사후 CI만으로 원문 보존을 대신하지 않는다.

CI 전용 서비스/권한이 필요한 검사는 사전에 그 환경에 배정한다. 로컬에서 못 돌렸다고 임의 제외하거나 실패 검사를 조용히 CI 몫으로 옮기지 않는다. 선택한 필수 CI가 끝나기 전에는 로컬 확인 완료와 전체 검증 완료를 구분한다. CI가 없다면 다른 실행 환경이나 완료 범위를 협의한다. 기존 필수 검사, CI, 리뷰 규칙은 유지하며, 이번 원칙 채택은 현재 제품 테스트 실행이나 workflow 변경 허가가 아니다.

동일한 유효 로컬 근거를 PR 준비라는 이유만으로 반복하지 않지만, 입력 변경과 재사용 조건은 ADR 0002에서 따로 정한다. CI의 재실행은 공유 실행 환경, 검토 대상 버전을 확인하는 역할이 있어 단순 중복으로 제거하지 않는다. 테스트 실행 시간과 AI가 소비한 로그, 재작업 토큰도 따로 측정한다.

11/11 추가 질문의 구현 중 실행 단위, 작성/검증의 중복 호출, 출력 비용은 [실행 반복과 토큰 비용](../../design/workflow/verification.md)의 협의안에 통합했다. 채택한 로컬/CI 분담은 유지하며, 구체 실행 책임, 중복 식별, 로그 출력 계약과 ADR 0001~0003을 이 보충만으로 채택하지 않는다.

공개된 실무 근거는 범위를 나누는 접근을 지지하지만 모든 회사가 같은 절차를 쓴다는 통계는 아니다.

- Microsoft VS Code는 단위, 통합 검사를 구분하고 통합 검사만 실행하는 CLI 방법도 제공한다. 로컬에서 구분해 확인할 수 있다는 사례이며 모든 변경에서 넓은 로컬 검사를 요구한다는 근거는 아니다. [Writing Tests](https://github.com/microsoft/vscode/wiki/Writing-Tests#integration-tests).
- GitLab은 관련 검사부터 시작하고 MR 단계별로 전체 단위/통합, E2E 범위를 확대한다. 변경 파일의 의존 관계를 따라 기존 Jest 테스트를 선택하며 공통 설정, 의존성 등에는 넓은 검사를 사용한다. 이는 GitLab 자체 CI 사례이고, 같은 자동 선택기를 우리 제품에 새로 만들겠다는 제안은 아니다. [Testing Strategy](https://docs.gitlab.com/development/testing_guide/testing_strategy/), [Pipelines](https://docs.gitlab.com/development/pipelines/#jest-predictive-jobs).
- Google은 개발자가 변경을 충분히 확인한 뒤 리뷰하도록 하고 적절한 테스트를 같은 변경에서 검토한다. GitHub는 로컬 빌드/검사 명령을 CI에서도 사용하는 방식을 안내한다. 로컬 통과가 CI나 의미 검토를 대신하는 근거로 사용하지 않는다. [Google 코드 리뷰](https://google.github.io/eng-practices/review/reviewer/looking-for.html#tests), [GitHub Gradle CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/java-with-gradle).

작성 절차와의 연결은 아래 후속 채택을 따른다. 이어 계획/결과 보존은 ADR 0001, 0003 B, PASS 재사용은 ADR 0002 C의 원칙을 채택했다. 실제 지원 환경, 예외, 명령과 수용 입력을 고정하고 구현 단계에서 시간, 누락, 중복을 측정한다.

## 테스트 작성 절차의 연결

11/11 후속으로 **짧은 진입 규칙 + 지침 중심의 조건부 테스트 작성 skill + 공통 검증** 배치를 채택했다. 사용자의 “지금 네가 제안한 방식으로 진행하되”에 따라 반영하며, 기존 조건부 하네스의 선택적 읽기와 연결, 누락 대응을 요구했다. 현재 AGENTS와 mode/gate의 구체 형태는 개선 가능하며 고정하지 않는다. 배치 채택은 실제 skill 구현, 자동 호출 정확도, 품질, 토큰 효과의 검증 완료가 아니다.

최초에는 첫 배포의 진입점 수를 줄이려고 별도 일반 지침 참조를 추천했다. 전체 모듈의 재사용, 갱신 목적을 다시 대조해 지침 중심 skill로 추천을 바꿨다. 같은 메인이 사용하는 작성 절차를 명확한 단위로 배포할 수 있고, 기존 skill 연결, 공통 검증을 활용하므로 별도 AI나 실행 체계를 요구하지 않기 때문이다. 이전 추천에서 파일/등록 감소의 이점을 과하게 평가했다. 일반 문서 참조도 유효한 대안이며 공개 사례의 우열이나 측정된 효과가 이 선택을 입증한 것은 아니다.

채택한 배치, 책임, 조건부 연결 초안, 부작용, 대표 사례는 [테스트 작성 절차](../../design/workflow/verification.md)가 소유한다. 테스트 코드를 작성하거나 검토할 필요와 실제 검사를 실행할 필요를 따로 판단한다. 작성 skill을 쓰지 않아도 필요한 기존 검사는 실행한다. 반대로 skill을 쓴다는 이유만으로 새 테스트를 만들거나 모든 문서를 탐색하거나 전체 gate를 켜지는 않는다. 의미, 범위가 불명확하면 확인하며 미실행, 미완료를 성공으로 처리하지 않는다. 정확한 gate, 파일명, 입출력/결과 형식은 후속 명세이고 ADR 0001~0003의 일괄 채택으로 확대하지 않는다.

## 비용과 평가

동일한 수정, 시작 상태에서 A/B/C의 필수 검사 누락, 불필요한 선택, 실제 새 실행, 도구 재사용, 전체 시간과 메인에게 전달한 출력량을 비교한다. 모델 토큰은 별도로 실제 사용량을 측정한다. 테스트 실행 시간이 늘어나는 것과 클라우드 토큰이 같은 비율로 늘어나는 것은 다른 주장이다.

C를 넓은 대조군으로 쓸 때도 존재하는 테스트의 한계를 명시한다. 고정 실패 주입 사례에서 선택 누락을 비교할 수 있지만 제품의 모든 결함 검출률로 일반화하지 않는다. [검증 초안](../../design/workflow/verification.md)의 V-17이 새 선택 사례다.
