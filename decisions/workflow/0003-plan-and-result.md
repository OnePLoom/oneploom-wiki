# ADR 0003 — 계획, 비활성 상태와 실행 결과의 구분

- 작성일: `2026-10-27`
- 설계 상태: `accepted` — 2026-11-11 B의 판정 원칙 채택
- 채택: **B**
- 채택 근거: 사용자가 ADR 0001, 0003의 B를 함께 선택했다. 계획과 실행 근거를 구분하고, 계획 준비, 비활성, 일부 성공을 전체 테스트 PASS로 소비하지 않는다. 정확한 상태 이름, 필드, 저장과 ADR 0002의 재사용 정책은 별도다.
- 구현 및 검증: 후속 [기록 명세](../../design/workflow/records.md)와 [저장 후보](../../design/workflow/storage.md)를 작성하고 일부 SQL 제약을 검사했다. 제품 결과 소비/실행은 미완료이며 실제 오판 발생률은 미측정이다.

## 현재 문제

현재 구현 검증의 JSON 계획 산출과 gate 비활성에도 `PASS`가 사용되고, 실제 검증 성공도 `PASS`다. 종료 코드 0만으로는 무엇이 성공했는지 구분할 수 없다. [E-007](../../evidence/issues.md)에는 빈 배열이 `[""]`로 출력되고, 다중 모듈의 floor `test`와 `requires_full_test=false`가 함께 나오는 관측도 있다.

현재 사람이 메시지를 읽어 차이를 구분할 수 있다는 점과, 자동 소비자가 상태만 읽어도 올바르게 판단한다는 보장은 다르다.

## 비교한 방안

| 방안 | 쉬운 설명 | 장점 | 단점, 비용 |
| --- | --- | --- | --- |
| A. 기존 PASS에 실행 여부 추가 | 같은 결과 형식에 `executed`와 사유를 넣어 계획 PASS, 생략 PASS를 구별한다. | 기존 출력과 소비자 변경을 줄일 수 있다. | 소비자가 PASS만 읽거나 필드가 모순되면 오판 가능성이 남는다. 실행 여부만으로 캐시 결과, 검사 누락까지 설명하기 어렵다. |
| B. 계획과 실행 결과를 다른 구조로 표현 | 계획에는 필요 여부, 검사 목록을, 결과에는 그 계획의 실행 근거, 판정을 담는다. | 계획을 테스트 통과로 읽기 어렵고 ADR 0001의 재시도 식별과 자연스럽게 연결된다. | 결과를 읽는 기존 skill, script의 계약도 전환해야 한다. |
| C. 하나의 상태 목록을 확장 | `PLANNED`, `SKIPPED`, `RUNNING`, `PASS` 등으로 모든 경우를 한 state에서 표현한다. | 간단한 CLI의 현재 단계를 보기 쉽다. | 적용 여부, 진행 단계, 검증 판정이 한 목록에 섞인다. 이후 중단, 재사용 상태가 추가될 때 전이 규칙이 커진다. |

## 추천과 이유

B를 채택했다. 계획은 앞으로 할 일이고 결과는 확인된 사실이므로 데이터의 역할을 구분하는 편이 소비자의 실수를 줄인다. 기존 `PASS`, `FAIL`, `UNCLASSIFIED`는 검증 판정에 사용하는 후보이며, 계획 자체에는 테스트 PASS를 부여하지 않는다. 정확한 상태 표현은 후속 명세에서 정한다.

여기서 두 구조는 반드시 두 개의 사용자 명령이나 별도의 대규모 파이프라인을 뜻하지 않는다. 기존 진입 명령의 계획 모드, 실행 모드를 유지하면서 구조화 출력의 종류를 구분할 수 있다. 하나의 파일 안에 종류가 다른 record를 담는 구현도 가능하다. 저장 매체보다 소비자가 잘못된 종류를 거부하는지가 핵심이다.

2026-11-11 후속: [계획과 결과의 연결](../../design/workflow/verification.md)에 작성 skill 결과, 재시도, 필수 CI까지 포함한 설명용 흐름을 작성한 뒤 사용자가 B를 채택했다. 진행 여부, 검증 판정, 선택한 완료 범위를 구분하되 새 상태 이름을 무차별적으로 늘리지 않는다. 정확한 enum, 필드, 저장 형식은 후속 명세이며 실제 consumer 동작은 아직 검증하지 않았다.

## 추천 계약

계획, 실행, 완료의 구분은 채택됐으며 아래 상태/필드 이름, 보고서 대응 방식은 후속 명세 후보를 포함한다. 기존 형식의 그대로 재사용이나 모든 상세의 일괄 채택을 뜻하지 않는다.

- 계획은 `required`, `not_required`, `undetermined` 중 적용 여부와 사유를 표현한다. 비활성에는 실행 결과를 만들지 않는다. 입력 손상, 분류 충돌은 `not_required`가 될 수 없다.
- 필요한 검사가 없는 작업에는 검증 불필요와 사유를 보고한다. 테스트 작성, 계획 준비만 끝난 상태나 적용 제외를 실제 테스트 PASS로 보고하지 않는다.
- 결과는 해당 계획, 시도, 검사별 실행 여부, 실제 종료 코드, 로그/보고서, 실행 또는 재사용 근거를 참조한다. 전체 gate PASS에는 필요한 검사 전부의 유효한 근거가 필요하다.
- 명령 종료 코드 0만으로 “필요한 테스트가 실행됐다”고 하지 않는다. 예상 task, 테스트 선택과 보고서의 대응을 확인한다. 필요한 테스트가 0건이거나 근거가 없으면 완료를 보류한다.
- 빌드 도구가 결과를 재사용했다면 그 출처를 표시한다. `SKIPPED`, `NO-SOURCE`를 성공한 테스트 본문 실행으로 세지 않는다. 테스트가 없는 모듈의 예외는 사전에 명시한 적용 조건으로 처리한다.
- 한 계획에 명령이 둘 이상이면 각각의 결과를 남긴다. 일부 성공, 일부 미실행, 중단을 전체 PASS로 합치지 않는다.
- 종료나 보고서 수집을 확인하지 못한 시도는 미확인 근거를 남긴다. 종료 코드를 임의로 채우지 않으며 재개 때 실제 실행 상태를 대조하기 전에 같은 명령을 중복 시작하지 않는다. 구체 프로세스/저장 복구는 후속 계약이다.
- 배열, boolean, 필수 필드를 검증한다. 정확한 검사 목록을 원본으로 두고, 전체 테스트 여부 같은 중복 요약 필드는 제거하거나 같은 원본에서 유도한다.
- 보고서는 해당 계획, 현재 시도의 도구 결과와 대응해야 한다. 이전 실행의 XML이 디스크에 남아 있다는 사실만으로 현재 검사 성공을 만들지 않는다. 빌드 도구가 재사용을 보고한 경우에도 적용 정책, 선택 범위와 대응하는 증거인지 확인한다.
- 필수 검사에 미해결 FAIL이 있으면 전체 판정은 FAIL로 유지하고 미실행, 미확인 항목도 함께 남긴다. 이미 유효한 후속 근거로 해결한 과거 FAIL과 구별한다. 미해결 FAIL이 없지만 필수 근거가 모자라면 UNCLASSIFIED다. 완료 후보는 선택한 범위의 모든 필수 의무를 충족했을 때만 가능하며, 로컬 완료가 필수 CI까지 완료됐다는 뜻은 아니다.

2026-10-27 재검토: 이 ADR은 [ADR 0001](0001-verification-identity.md)의 기록을 어떻게 해석할지 정한다. 계획/결과를 나누는 것만으로 검사 선택이 충분해지거나 제품 정확성이 보장되지는 않는다. 선택 범위는 [ADR 0005](0005-verification-selection.md), 실행 재사용은 [ADR 0002](0002-pass-validity.md)가 따로 다룬다.

[Gradle task outcomes](https://docs.gradle.org/current/userguide/more_about_tasks.html)는 실제 실행, 이전 결과 재사용, 생략, 입력 없음이 서로 다른 결과임을 설명한다. 이 구분을 근거 기록에 반영하는 것은 이 프로젝트의 설계 판단이다.

## 채택 후 확인할 조건

dry-run, 명시적 비활성, 실제 성공, 실패, 캐시 적중, 테스트 0건, 부분 실행, 중단을 자동 소비자가 구분하는지 확인한다. 소비자의 전체 완료 판단까지 검사해야 하며 직렬화 성공만으로 충분하지 않다. [검증 계약 초안](../../design/workflow/verification.md)의 V-09~V-12, V-15가 관련 사례다.
