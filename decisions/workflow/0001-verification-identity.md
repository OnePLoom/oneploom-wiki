# ADR 0001 — 최초 검증과 재시도의 동일성

- 작성일: `2026-10-27`
- 설계 상태: `accepted` — 2026-11-11 B의 기록 원칙 채택
- 채택: **B**
- 채택 근거: 사용자가 ADR 0001, 0003의 B를 함께 선택했다. 검사 계획 보존, 현재 코드에서의 시도별 결과 연결, 원래 실패, 추가 검사와 완료 범위의 대조를 채택한다. 정확한 필드, 저장, 복구 수단과 ADR 0002의 재사용 정책은 별도다.
- 구현 및 검증: 후속 [기록 명세](../../design/workflow/records.md)와 [저장 후보](../../design/workflow/storage.md)를 작성하고 일부 SQL 제약을 검사했다. 제품 실행/복구는 미완료이며 아래 효과는 달성 수치가 아니다.

## 현재 문제

`verify-and-retry.sh`는 최초 실패의 gate와 change-kind를 복원하지만, 실행할 테스트는 재시도에 전달한 scope로 다시 계산한다. `gate-common.sh`의 state에는 원래 실행한 argv, 테스트 선택 조건이 없다.

[관측 기록 (E-012 재현)](../../evidence/experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)에서는 API FAIL → core scope retry PASS → 원래 API FAIL이 관측됐다. 같은 게이트라는 사실만으로 같은 검증이라고 할 수 없다. 기존 실패 원본을 보존하는 동작은 유지할 가치가 있다.

## 비교한 방안

| 방안 | 쉬운 설명 | 장점 | 단점, 비용 |
| --- | --- | --- | --- |
| A. 기존 state와 shell을 국소 보강 | 최초 scope, 실제 명령을 state에 추가하고 retry가 이를 다시 사용한다. | 변경량이 작고 빠른 결함 수정에 적합하다. | 계획, 실행, 입력 검사를 각 script에서 맞춰야 한다. 복수 명령과 반복 재시도 기록이 복잡해지면 다시 분리할 가능성이 크다. |
| B. 변경하지 않는 검증 계획 + 실행마다 별도 기록 | 무엇을 검사할지는 계획에 보존하고, 수정한 코드에서 실행한 결과는 매번 새 기록으로 남긴다. | 원래 검증, 수정 영향, 실행 이력이 구별된다. 기존 진입점과 선택 게이트를 유지하며 공통 처리를 묶을 수 있다. | 계획/결과 형식과 소비자를 함께 맞춰야 한다. 작은 공통 처리부와 호환 전환 작업이 필요하다. |
| C. 전체 workflow 엔진으로 전환 | 모든 게이트, 의존, 재시도를 하나의 작업 그래프와 상태 저장소로 관리한다. | 대규모 병렬 작업과 중앙 상태 추적에 유리하다. | 현재 결함 해결에 비해 구축, 운영, 이식 비용이 크다. 중앙 엔진 자체의 장애와 검증 범위도 늘어난다. |

## 추천과 이유

B를 채택했다. 이번 문제의 원인은 최초 검증의 식별 정보가 부족한 것이므로, 검증 계획을 보존하고 결과가 그 계획을 참조하게 만드는 것이 직접적인 해결이다. 기존 gate 선택과 의미 판단은 메인이 계속 담당한다. 상시 서버, DB, 범용 workflow 엔진 도입은 이 결정에 포함하지 않는다.

A도 필요한 정보를 빠짐없이 저장하고 검증하면 안전하게 구현할 수 있다. 파일을 분리한다는 사실 자체가 안전성을 만드는 것은 아니다. B를 추천하는 이유는 반복 재시도, 기계 소비, 프로젝트 이식에서 같은 계약을 공유하기 쉽기 때문이다. B가 토큰을 절약한다는 효과는 아직 측정하지 않았다.

2026-10-27 재검토: B는 논리적인 계획/시도 구분이다. 기존 shell 진입점과 작은 공통 처리로 구현할 수 있으며, 별도 프로세스, DB, 이벤트 저장소, 범용 실행 엔진을 요구하지 않는다. [ADR 0003](0003-plan-and-result.md)은 이 자료의 판정 의미를 정하는 연결된 선택이다. 두 ADR을 두 개의 새 시스템으로 구현하지 않는다.

2026-11-11 후속: 채택한 조건부 작성 skill과 로컬/CI 분담을 [계획과 결과의 연결](../../design/workflow/verification.md)에 반영해 협의한 뒤 사용자가 B를 채택했다. 초기 scope/검사 의무와 시도별 현재 입력을 구분하고, 작성 완료, 로컬 완료, 전체 완료를 섞지 않는다. 파일 수, 이름, 필드와 저장/복구 구현은 후속 명세이며 실제 구현, 실행은 아직이다. 현재 AGENTS의 구체 mode/gate 형태에 의존하는 별도 실행기를 만들지 않는다.

## 추천 계약

위의 기록 원칙은 채택됐으며 아래 정확한 식별 정보, 인자/저장 표현, 동시성 수단은 구현 명세에서 검토할 상세를 포함한다. 이 절 전체의 필드나 기존 구현을 그대로 확정한 것은 아니다.

- 계획은 작업, workspace, gate, 최초 scope 경로 목록, 검사별 실제 argv, 작업 디렉토리, 선택/제외 조건을 식별한다. 하나의 gate 안에서도 API와 core 검증을 구별한다.
- 같은 계획을 재시도해도 **코드는 수정 후 현재 코드**를 사용한다. 계획의 동일성과 실행 입력의 동일성을 혼동하지 않는다. 매 실행의 입력 fingerprint는 달라질 수 있다.
- 수정 scope는 추가 검증과 선행 PASS 영향 판단에 사용한다. 원래 실패 검증을 대체하는 입력으로 사용하지 않는다.
- 수정으로 core 검증이 추가로 필요하면 원래 API 검증과 추가 core 검증을 모두 유지한다. 단순히 새 scope로 다시 고른 core PASS로 API 실패를 닫지 않는다.
- 테스트 선택, 예외, 검증 도구가 바뀌어 기존 계획이 더는 유효하지 않으면 후속 계획과 변경 이유를 남긴다. 기존 FAIL을 PASS로 수정하지 않는다. 상위 계획이 하위 검증을 포함한다는 보장도 selector, 예외를 대조해야 한다.
- 범위 축소나 검사 제거는 메인이 근거를 명시한다. 요구사항, 외부 계약을 바꾸는 선택이면 기존 사용자 협의 규칙도 따른다. 기계적 재시도마다 새 사용자 승인을 요구하지는 않는다.
- 최초 FAIL과 각 retry 결과를 별도 식별자로 보존한다. 기존 `.retry` 파일 하나를 반복해서 덮어쓰는 방식을 대체하는 후보이며, 실제 저장 위치와 수명은 후속 설계에서 정한다.
- 유효한 후속 근거로 원래 실패의 의무를 닫되 최초 FAIL은 당시 사실로 보존한다. 이전 FAIL이 남아 있다는 이유로 영원히 미해결 처리하지 않고, 최신 시도 하나가 성공했다는 이유로 다른 미해결 검사를 지우지도 않는다.
- retry의 새 실행 강제 옵션처럼 계획에 이미 정의한 실행 정책의 적용은 검사 교체와 구분한다. 실제 적용 argv는 각 시도에 남긴다. 계획에 없던 selector, 예외 변경은 후속 계획으로 처리한다.
- 계획 변경은 미해결 검증 의무를 지우는 수단이 아니다. 원래 실패 검사를 제거, 대체하면 어떤 근거로 더는 필요 없거나 다른 검사가 이를 충족하는지 남긴다. 단순히 새 계획이 PASS라는 이유로 이전 FAIL을 해결 처리하지 않는다.
- 테스트 코드 수정 자체는 허용하지만, 기대 동작을 약화해 실패만 없앤 것은 올바른 복구라고 보장하지 않는다. 테스트 의미의 타당성은 diff와 요구사항을 보는 메인의 검토에 남는다.
- 초기 실행은 같은 workspace의 검증 대상 입력을 도중에 수정하지 않는 운용을 전제로 한다. 관련 입력의 변경이 감지되면 결과를 현재 코드의 완료 근거로 쓰지 않는다. 시작/종료 fingerprint가 같다는 것만으로 실행 중 모든 변화가 없었다고 증명하지는 않는다. 병렬 편집 격리 방식은 후속 구현 설계 대상이다.

명령은 문자열 재해석보다 인자 배열로 보존하는 방향을 추천한다. 인자 배열, 작업 디렉토리, 종료 코드를 제공하는 [Python subprocess 공식 문서](https://docs.python.org/3/library/subprocess.html)를 실행 계약의 참고로 사용했다. 구현 언어를 확정한 것은 아니다. 배열만으로 임의 명령이 안전해지는 것은 아니며 계획의 출처, 허용 검사도 확인해야 한다.

## 채택 후 확인할 조건

API 실패가 남아 있는 core-only retry는 전체 성공이 될 수 없어야 한다. 정상 수정 후 API 재검증, 추가 모듈 검사, 선택 테스트 변경, 잘못된 작업의 FAIL 혼입, 두 번째 retry를 함께 확인한다. 구체 사례는 [검증 계약 초안](../../design/workflow/verification.md)의 V-01~V-04, V-13~V-15에 있다.
