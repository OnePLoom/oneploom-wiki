# ADR 0021: 복구 기록의 저장 수단

- 날짜: 2026-11-11
- 설계 상태: `accepted` — 2026-11-12 active Markdown, 기계 기록만 로컬 SQLite, 원문 산출물 파일의 저장 원칙 채택. 상세 명세, 구현, 검증은 후속
- 구현 및 검증: 설계 DDL과 최초 인계 B의 단계/재시도 메모리 검사 확인. 제품 저장 코드, 실제 파일 인계/정리와 Windows 복구 시험은 미실행

## 문제

복구 B 방향과 논리 상태를 구체화한 결과, 계획, 시도, 결과, 현재 진행의 대응을 보존하고 중간 실패와 늦은 작성자의 덮어쓰기를 처리해야 한다. 단일 파일을 안전하게 교체하는 것과 관련 기록 여러 개를 함께 반영하는 것은 다르다. 저장 수단은 기록의 일관성을 돕지만 AI의 의미 누락이나 코드/WIKI, 원격 작업의 실제 효과까지 자동 복구하지 못한다.

기존 초안은 새 DB 의존성을 우선 도입하지 않는 방향이었다. 11/11 비교와 11/12 배포 부담 검토 뒤 사용자가 기계 기록에 한정한 SQLite 방향을 채택했다. 기존 active와 hook의 역할, 로컬 Git 제외는 유지한다.

## 대안

| 수단 | 장점 | 부담과 한계 |
| --- | --- | --- |
| Markdown, JSON 파일 교체 | 직접 읽고 비교하기 쉬움. 작은 상태 전체를 JSON 하나로 저장, 교체하면 관련 값도 함께 반영 가능 | 이력/산출물을 분리할 때의 대응, 작성자 충돌, 복구를 직접 설계. 모든 이력을 한 파일에 모으면 누적 크기와 전체 재작성 부담을 평가해야 함 |
| 추가 기록 파일과 현재 상태 요약 | 과거 사건을 덮지 않고 누적하며 텍스트로 확인 가능 | 잘린 마지막 기록, 중복/순서, 재생, 요약 갱신, 형식 변경을 처리해야 함. 작은 범위를 넘어가면 자체 저장 엔진에 가까워짐 |
| 기계 기록만 로컬 SQLite — 채택 | 관련 기록을 트랜잭션으로 묶고 저장 중 실패, 동시 쓰기의 기본 처리를 검증된 엔진에 맡김. 별도 DB 서버 불필요 | 조회/내보내기, 백업, 형식 이전이 필요. 한 DB에는 한 번에 한 작성자이며 긴 잠금 회피 필요. 바깥의 Markdown, 산출물, 원격 효과는 별도 대조 |

모든 자료를 DB로 옮겨 active를 읽기용 생성물로 만드는 안은 첫 추천에 넣지 않는다. 사용자가 이해, 수정할 진행 문서와 WIKI를 유지하려는 목적에 비해 변경 범위가 크다. 별도 원격 DB/워크플로 서버도 이번 로컬 복구의 선행 요소로 두지 않는다.

## 추천과 근거

**active는 Markdown, 계획, 시도, 결과의 기계 기록은 SQLite, 원문 결과, 후보, 복원 사본은 일반 파일**로 나누는 안을 채택했다. 같은 사실의 수정 가능한 원본을 두 곳에 만들지 않는다. AI는 active와 필요한 조회 결과를 읽으며 SQL을 직접 작성하는 것이 정상 사용 절차가 아니다. 상세 소유, 연결과 DB 자체 복구/작업 복구의 구분은 [저장 수단과 자료의 소유](../../design/workflow/recovery.md)에 둔다.

이는 로컬 실행 기록에 대한 선택이다. 이미 채택한 [문서 위치표의 JSON 구성](../../design/knowledge/map.md)이나 프로젝트 공유 설정, WIKI의 저장 형식을 바꾸지 않는다.

[Python의 sqlite3](https://docs.python.org/3.13/library/sqlite3.html)는 별도 서버 없는 디스크 DB와 트랜잭션, 백업 기능을 제공한다. 지원 Python 빌드의 모듈/SQLite 버전 확인은 필요하다. [SQLite의 원자적 커밋](https://www.sqlite.org/atomiccommit.html)은 DB 트랜잭션 내부 변경을 함께 반영하는 근거다. 파일시스템, 저장 설정의 전제와 예외가 있으므로 전원/디스크 고장까지 무조건 안전하다는 뜻은 아니다.

우리 조건에서는 파일 기반의 여러 기록을 맞추는 자체 저장, 복구 코드를 늘리는 것보다 기존 엔진을 좁게 사용하는 편이 유지보수와 실패 검증에 유리하다고 판단한다. 일반 코드 처리이므로 저장 자체에 모델 추론이 필요하지 않지만 AI가 읽는 요청, 결과의 토큰까지 없어지는 것은 아니다. 실제 코드량, 속도, 토큰 절감은 미측정이다.

11/12 보충 판단: 최신 상태 하나만 보존한다면 JSON 교체가 더 간단할 수 있다. 현재 요구에서는 계획에 연결된 여러 실행과 재시도를 추적하고, 해결해야 할 실패와 결과 참조를 함께 대조해야 하므로 SQLite 추천을 유지한다. 이는 **사용자에게 DB 서버, SQL, 전용 뷰어 관리를 요구하지 않고 모듈이 조회, 백업, 이전을 책임진다는 조건**의 판단이다. 정확한 데이터 양, 동시성, 공수로 우위를 실측한 결론은 아니다. 배포 준비와 비용은 [배포 사용자의 준비와 조회](../../design/workflow/recovery.md)에 둔다.

SQLite가 active의 의미를 자동 갱신하거나 Obsidian의 동시 편집, PR 중복을 막아 주지는 않는다. [작성 범위와 동시 작업](../../design/workflow/recovery.md)의 별도 소유/대조가 필요하다. 로컬 기록을 팀의 Git, 클라우드 동기화로 공유하는 방식도 아니다.

## 공개 구현에서 확인한 범위

11/12에 공식 문서와 공개 소스를 확인했다. 특정 기업 전체의 내부 운영이나 업계 채택 비율을 조사한 결과는 아니다.

| 사례 | 직접 확인한 사용 | 우리 판단에 적용할 범위와 한계 |
| --- | --- | --- |
| [Microsoft VS Code](https://github.com/microsoft/vscode/blob/main/src/vs/platform/storage/electron-main/storageMain.ts), [SQLite 저장 구현](https://github.com/microsoft/vscode/blob/main/src/vs/base/parts/storage/node/storage.ts) | 앱, 프로필, 작업 공간 상태를 SQLite 저장 계층으로 연결. 변경 묶음을 트랜잭션으로 처리 | 일반 사용자용 프로그램이 내부 로컬 상태에 SQLite를 쓰는 실제 구현. AI의 의미 복구나 우리 Python 배포를 검증한 사례는 아님 |
| [LangGraph SQLite Checkpoint](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-sqlite/README.md) | 에이전트 워크플로 상태의 SQLite 저장/조회. 로컬 개발, 시험, 가벼운 배포 대상으로 안내 | 로컬 에이전트의 중단 후 상태 보존에 사용 가능한 공식 구현. 대규모 분산 실행 전체의 권장 저장소라는 뜻은 아니며 이 패키지를 도입하는 결정도 아님 |
| [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) | 단일 기기, 로컬 작업에 FileCheckpointStorage도 제공 | 파일 방식도 유효한 실무 대안. 이름 있는 프로젝트가 SQLite를 쓴다는 이유만으로 DB가 항상 최선이라고 판단하지 않음 |

공통적으로 가져올 원리는 실행 상태를 명시적으로 저장, 읽고 검증하는 것이다. 각 프로젝트의 프레임워크, 직렬화 방식, 손상 시 초기화 정책을 그대로 복사하지 않는다. 우리 요구에서는 복구 근거를 잃은 상태를 새 빈 작업으로 조용히 대체하면 안 된다.

## 확인 조건과 남은 선택

- 저장 중 종료, 실패한 트랜잭션, 동시/늦은 저장, 백업/재개를 실제 지원 Windows에서 확인한다. 정상 경로의 지연, 복잡성도 파일 방식과 비교한다.
- DB에 없는 산출물, DB 결과는 있으나 오래된 active, 지원하지 않는 형식, 손상, 저장 공간/권한 오류를 성공이나 새 빈 DB로 처리하지 않는다.
- DB 조회 도구가 없어도 보존한 자료를 확인할 수 있는 조회/내보내기 안내와 올바른 백업을 제공한다. DB 백업만으로 외부 파일까지 복구됐다고 표시하지 않는다.
- 지원 Python의 sqlite3 제공 여부와 실제 SQLite 버전, 일반 사용자 권한, 한글/공백 경로, 저장/내보내기, 오프라인 상태 조회를 확인한다. 모듈에 없는 DB 서버/MCP/별도 계정을 사용자 준비물로 추가하지 않는다. 자세한 비용, 조회 조건은 위 배포 사용자 절과 수용 기준에 둔다.
- 이번 선택은 저장 수단의 원칙이다. 정확한 파일명, 테이블/필드, journal/동기화 설정, 잠금 API/경로, 보존 기간은 명세와 시험에서 정한다. 기존 `.harness/state/`, Git 제외 경계와 예비 WSL active는 바꾸지 않는다.

11/12 후속으로 [복구 자료의 대응](../../design/workflow/recovery.md)과 [백업, 형식 변경 — 「백업과 저장 형식 변경」](../../design/workflow/recovery.md) 초안을 작성하고 대응하는 미실행 검증 입력을 연결했다. 저장 수단 채택을 세부 구현/효과 검증으로 확대하지 않는다. [복구 자료의 보관과 정리](../../design/workflow/recovery.md)는 같은 날 사용자 선택으로 자동 보존 + 명시적 정리 명령을 채택했다. 날짜/용량에 따른 자동 삭제는 첫 기본 동작에서 제외하고 진행/미확인/미해결 작업과 다른 보존 자료가 필요한 근거를 보호한다. 정확한 명령, 구현/시험은 후속이다.

11/16 후속 채택: 사용자가 최초 설치의 확실한 완료 뒤 정리 가능한 자료를 차례로 보여주고, 확인 응답을 받아 정리까지 이어가도록 요청했다. 기존 보호 원칙과 후속 정리 명령은 유지하면서 설치 종료 흐름에 확인 절차를 연결한다. 외부 최초 보존 사본도 인계와 참조 검사를 통과하면 후보에 포함한다. 배포 저장소의 실행 안내 README에 보관/삭제, 취소/실패와 재실행을 설명한다. 상세는 [설치 완료 뒤 정리](../../design/runtime/install.md)가 소유하며 무응답 자동 삭제나 제품 구현 완료를 채택한 것은 아니다.

11/17 후속 채택: 명시적 정리에 **완료됐고 현재 복구에 필요 없는 큰 로그, 후보와 복원 사본**까지 포함한다. 사용자에게 잃는 복구 범위를 보여주고 확인받으며 DB의 작업 이력과 정리 사실은 보존한다. 진행/미해결 작업과 다른 현재 의존 자료는 계속 보호한다. 임시/중복 자료만 정리하는 대안보다 용량을 관리할 수 있지만, 정리된 근거가 새 검사 재사용/완료/복원에 쓰이지 않도록 모든 소비자를 연결하는 비용을 수용한다. 상세 필드와 조회 책임은 [정리 기록 — 「정리 허용과 실제 제거」](../../design/workflow/maintenance.md)에 둔다.

같은 날 작성 소유, 인계 검토에서 서로 다른 코드 작업 트리가 같은 물리적 WIKI 폴더를 직접 수정하는 상황을 먼저 가정하고, Windows 사용자 로컬 앱 데이터, WIKI 내부 조정 폴더, 별도 서비스를 비교했다. 사용자는 처음부터 각자의 로컬 WIKI 편집 후 Git 공유/충돌 해결을 전제로 했다고 재확인했다. 같은 원격 저장소와 같은 물리적 작업 폴더를 혼동하게 만든 **공통 조정 위치의 추천, 선택 요구를 철회**한다. 미채택 제안이었으며 제품 구현은 없었다. 현재 설계/진행표에서는 제거하고 이 판단 이력만 보존한다. 프로젝트 active, SQLite, 로컬 중단 복구, 사용자 편집 보존 계약은 유지하며 상세는 [로컬 편집과 Git 공유 — 「WIKI의 로컬 편집과 Git 공유」](../../design/workflow/recovery.md)에 연결한다.

11/12 적용 범위 보정: 사용자가 세션 복구와 설치/기능 재개의 혼동을 지적한 뒤, **세션 문맥 복구, 설치/갱신 복구, 개별 기능 재개를 구분하고 필요한 저장, 조회 책임은 공유하는 경계**를 수용했다. 기존 B도 조건부였으며 모든 일반 CLI 작업을 관리하던 구조를 새로 폐기한 것은 아니다. 정상 오류 처리, 중단 대비 기록, 실제 복구를 분리한 보정이고, SQLite 저장 원칙과 기존 보존/검증 요구는 유지한다. 상세 진입 조건과 읽기/변경 범위는 [복구의 대상과 경계](../../design/workflow/recovery.md)가 소유한다.

DB 트랜잭션은 기계 기록의 일부 저장을 보호한다. 실제 실행 전후의 짧은 저장 경계를 사용하며 작업 단위 전체, 파일, PR, 모델 문맥을 함께 롤백하는 안이 아니다. 설치 재개와 WIKI/검사 재개는 같은 기록을 필요한 범위에서 조회하고 실제 효과를 별도로 대조한다. 이 보정 뒤 파일별 명세 → 개발 준비 순서를 유지하며 제품 DB 생성, 기존 hook 변경, 실제 시험은 아직이다.

## 최초 DB의 위치 전환

2026-11-17 사용자는 최초 기록 인계의 B를 채택했다. 초기 설치 전용 DB의 같은 형식 사본을 새 후보에 보존하고 검증, 대상 수신, 원본 확인과 대상 활성화를 거쳐 프로젝트에서 이어 쓴다. 논리 DB 식별, 작업/시도, revision과 과거 기록을 유지하며 이후 설치/업데이트도 같은 이력에 쌓는다. 기존 정상 프로젝트 DB는 재사용하고 관계없는 기존 DB와 자동 병합하지 않는다.

이전 초안은 과거 행을 다른 DB의 정상 쓰기 경로로 다시 등록했다. 완료/고정 제약과 과거 형식 변경 기록을 새 실행으로 판단하는 E-022가 드러났고, 최초 위치 전환에 별도 역사 재생/병합 절차를 붙이는 비용이 커졌다. B는 원래 기록과 제약을 보존하는 사본으로 이 부담을 줄인다. 기존 정상 쓰기 보호를 해제하거나 과거 사실을 지워 해결하지 않는다. 실제 DB 형식 변경은 지원 버전별 변환/검증을 별도로 수행한다.

단순 복사만으로 인계를 완료하지 않는다. 실제 원본/대상, 같은 인계/내용/수신과 실행 소유를 대조하며 활성화된 프로젝트 사본만 후속 진행을 기록한다. DB 둘과 외부 파일이 한 트랜잭션으로 저장되는 것은 아니다. 옛 초기 사본은 보존/명시적 정리 대상으로 남고, 정상 활성화 뒤 후속 작업이 그 사본을 필수로 요구하지 않아야 한다.

현행 소유 문서는 [인계 저장 — 「최초 기록 인계의 저장」](../../design/workflow/storage.md)과 [프로젝트 기록으로 인계](../../design/workflow/records.md)다. 기존 행별 초안은 [판단 이력 — 「최초 기록의 행별 수신안」](../../discussions/history/install.md)에 보존했다. [부분 검사](../../evidence/experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md)에서 B 16개와 회귀 65개를 확인했지만 실제 Windows 위치/파일/프로세스, 지원 형식 간 변환이나 제품 전체 설치의 성공은 아니다.
