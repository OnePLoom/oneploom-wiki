# ADR 0002 — PASS 재사용의 책임과 조건

- 작성일: `2026-10-27`
- 설계 상태: `accepted` — 2026-11-11 C의 재사용 책임, 조건 원칙 채택. 판별, 저장, 실행 옵션은 후속 명세
- 채택: **C**
- 재검토: 초기 자체 PASS 캐시는 보류한다. 검사 선택은 ADR 0005에서 별도로 다룬다.
- 채택 근거: 사용자가 “C안이 제일 괜찮은 것 같아. 그걸로 진행하자”로 확인했다. 현재 의무의 중복 실행 방지와 새 입력의 재검증을 구분하며 초기 자체 PASS 캐시는 보류한다.
- 구현 및 검증: [재사용/검증 계약](../../design/workflow/verification.md)과 [기록 필드](../../design/workflow/records.md)를 후속 작성했다. 실제 판별/실행 연결은 미완료이며 재사용률, 실행 시간, 토큰 절감은 미측정이다.

## 현재 문제

현재 재사용 판정은 state에 등록한 파일 해시와 경로 pattern에 의존한다. [E-005](../../evidence/issues.md)의 재현에서는 gradlew 변경과 core 변경이 기존 API PASS의 재사용을 막지 못했다. 실제 `sample-api/build.gradle`은 core를 의존한다.

해시 알고리즘의 문제가 아니라 무엇을 해시에 포함하고 누가 영향 관계를 관리하느냐의 문제다. Git HEAD만 같아도 미커밋 코드, 추가 파일, 도구, 실행 환경이 달라질 수 있다.

## 비교한 방안

| 방안 | 쉬운 설명 | 장점 | 단점, 비용 |
| --- | --- | --- | --- |
| A. 필요한 검사 본문을 매번 새로 실행 | 하네스 PASS뿐 아니라 검사 본문의 도구 재사용도 허용하지 않는다. | 재사용 판정 누락을 줄이고 초기 대조군으로 쓰기 쉽다. | 영향 없는 검사도 반복한다. 단, 컴파일 등 준비 작업까지 모두 새로 할 필요는 없다. |
| B. 하네스가 전체 입력 fingerprint 관리 | 코드, 도구, 설정, 전이 모듈, 환경을 추적해 일치하면 실행기 호출도 생략한다. | 매우 빠른 재사용이 가능하고 여러 종류의 검사에 같은 방식을 적용할 수 있다. | Gradle 의존 그래프와 입력 관리를 별도로 유지하게 된다. 누락, 새 파일, 동적 의존, 외부 상태를 잘못 처리하면 현재 문제가 반복된다. |
| C. 실행기를 호출하고 검증된 도구 재사용만 허용 | 필요한 task는 호출한다. 입력 조건을 확인한 검사는 빌드 도구가 재실행을 판단하고, 조건을 모르는 검사, 실패 복구는 본문을 새로 실행한다. | 기존 증분 기능을 활용하면서 하네스의 중복 캐시를 줄인다. 초기 구현과 결과 출처가 단순해진다. | 도구 시작 비용이 남고 캐시 가능 검사와 새 실행 검사의 구분이 필요하다. 도구도 누락 입력, 외부 상태를 자동 보장하지 않는다. |

## 추천과 이유

C를 추천했고 11/11 사용자가 채택했다. 이미 선언된 task 입력의 변화 판정은 빌드 도구를 활용하고, 하네스는 검사 의무와 결과 근거를 관리하는 편이 현재 규모에 적합하다. 도구의 입력 선언이 충분한지는 연결부, 프로젝트 정책의 확인 대상이다. 단지 Gradle을 호출했다는 이유로 안전한 재사용이라고 인정하지 않는다.

2026-10-27 재검토로 초기 범위를 줄였다. 이전에는 결정적 문서 검사 등의 자체 PASS 재사용도 구현 후보에 함께 두었으나, 현재 입력 완전성, 호출 비용, 절감 효과가 확인되지 않았다. **초기에는 하네스가 과거 PASS를 보고 실행기 호출을 생략하는 캐시를 새로 구현하지 않는다.** 결정적 검사도 일단 실행하고, 비용이 실제 문제가 될 때 완전한 입력 선언과 대조 실험을 조건으로 별도 도입을 판단한다. 원시 증거 보관과 캐시 구현은 다른 일이다.

검사 선택과 재사용은 독립 문제다. 변경된 core의 task만 호출했다면, 도구의 cache key가 정확해도 선택하지 않은 소비 모듈의 테스트 충분성을 해결하지 못한다. [ADR 0005](0005-verification-selection.md)에서 선택 전략을 비교한다.

2026-11-11 후속: 구현, 테스트 작성 중의 중복 실행과 토큰 질문은 [실행 반복과 토큰 비용](../../design/workflow/verification.md)에 통합했다. 저장된 로그 재조회, 같은 작업에서 동일한 검증 의무의 중복 요청 정리, 이후 입력에서 과거 PASS를 재사용하는 판단을 구별한다. C가 모든 skill 진입, 완료 문구마다 같은 task를 반복하라는 의미는 아니다.

이미 충족한 현재 의무의 대응이 확인되면 같은 완료 판단에 사용하되, 입력/환경 변경이나 대응 불명확성이 있으면 이를 근거로 호출을 생략하지 않는다. ADR 0001, 0003 B의 기록 원칙에 이어 [재사용 판단 순서 — 「재사용을 판단하는 순서」](../../design/workflow/verification.md)를 설명하고 C를 채택했다. 정확한 동일성 판별, 기록 수단, 대상 버전의 실제 동작은 후속이다. 자체 PASS 캐시나 기존 프로젝트의 캐시 자동 활성화는 이번 채택에 포함하지 않는다.

이식성 보완: 이 ADR의 Gradle은 현재 프로젝트의 첫 연결부다. 공통 코어에 Gradle 전용 규칙을 내장하는 추천이 아니다. 다른 도구도 같은 계획, 결과 계약을 제공하며, 해당 도구가 신뢰할 수 있는 재사용을 제공하지 않으면 새 실행을 사용한다. 프로젝트 설정과 연결부 식별도 증거에 포함하는 제약은 [ADR 0004](../architecture/0004-portability.md)를 따른다.

이는 감사의 “관련 입력, 도구, 환경이 유효해야 PASS를 재사용한다”는 목표를 유지하면서, 초기 자체 fingerprint 구현을 보류하는 결정이다. 기존의 “영향 없는 PASS는 재호출도 생략한다”보다 제품 검사의 호출 비용이 늘 수 있다. 실제 시간 차이를 측정해 판단해야 하며 자동으로 비용 개선이라고 부르지 않는다.

[Gradle Build Cache](https://docs.gradle.org/current/userguide/build_cache.html)는 입력 누락이 잘못된 cache hit를 만들 수 있다고 설명한다. [cache key 개념](https://docs.gradle.org/current/userguide/build_cache_concepts.html)은 검사 구현과 입력도 키의 일부라고 설명한다. 이 사실은 B의 완전한 입력 추적 부담과 C의 한계를 함께 뒷받침하며, C를 직접 지정한 공식 권고는 아니다.

## 추천 계약

아래의 재사용 허용/거부, 결과 출처, 실패 복구 원칙은 C 채택 범위다. 정확한 필드, 동일성 판별, 저장 형식, 도구 옵션과 미래 자체 캐시 도입은 확정하지 않았다.

- 과거 하네스 PASS만 보고 실행기 호출을 생략하는 기능은 초기 구현에서 보류한다. 현재 필요한 계획의 검사만 호출한다. 더 넓은 완료 검증을 선택하는 조건은 ADR 0005에 두며 문서만 고친 요청의 제품 gate를 자동 활성화하지 않는다.
- Gradle의 `EXECUTED`, `UP-TO-DATE`, `FROM-CACHE` 등 원래 task 결과와 근거를 보존한다. 명령 호출과 테스트 본문의 신규 실행을 서로 다른 사실로 기록한다.
- 원래 실패한 검사 본문은 복구 시 새 실행을 기본으로 한다. 컴파일 등 준비 작업의 유효한 도구 재사용과 구분한다. 이전 FAIL 이후 성공한 근거가 없는 과거 PASS를 선택해 실패를 덮을 수 없다. 새 실행 정책의 실제 적용 옵션은 대상 도구 버전에서 검증해야 한다.
- DB, 네트워크, 시간, 기타 외부 상태에 의존하고 입력, 격리를 증명하지 못한 검사는 재사용 불가로 취급한다. 실제로 새 검사가 수행되도록 하는 설정, 실행 옵션은 프로젝트 버전에 맞춰 후속 단계에서 정한다.
- 추후 자체 캐시를 제안할 때는 도구, 규칙, 설정과 읽는 입력 전체의 manifest를 요구한다. 기존 파일 변경뿐 아니라 추가, 삭제, 이름 변경과 symlink 정책도 포함한다. 현재 scope의 일부 파일만 해시하는 것으로 충분하지 않다. 이는 미래 채택 조건이지 이번에 구현할 캐시가 아니다.
- 하네스의 계획, 증거를 다른 작업/workspace의 결과와 혼합하지 않는다. 빌드 도구의 로컬 캐시가 다른 실행의 산출물을 사용하는 것은 별도 계층이며, 해당 도구의 입력, 출처 조건으로 판단한다. 하네스 원격 증거 캐시를 새로 도입하거나 기존 도구의 원격 캐시 설정을 바꾸는 제안은 아니다.
- 입력, 환경, 증거가 부족하면 재사용을 허용하지 않는다. 필요한 최소 확인이나 현재 검증 실행으로 이어가며, 불확실한 결과를 PASS로 보지 않는다.

[Bazel hermeticity 문서](https://bazel.build/basics/hermeticity)는 실행 도구, 호스트 환경과 외부 의존이 결과에 영향을 줄 수 있음을 설명한다. 이를 참고해 검증 가능한 재사용 범위를 제한한다. Bazel 전환이나 완전한 격리를 이미 달성했다는 뜻은 아니다.

## 채택 후 확인할 조건

core, wrapper, 검증 도구, 테스트 선택 변경, 새 파일, 삭제, 외부 DB 변화, 실패 뒤 복구, 결정적 검사와 무관한 문서 변경을 포함한다. 실행기 호출 수, 검사 본문의 새 실행 수, 도구 재사용 수를 따로 기록하고, 잘못된 재사용뿐 아니라 시간과 불필요한 수행량도 측정한다. 관련 사례는 [검증 계약 초안](../../design/workflow/verification.md)의 V-05~V-08, V-16이다.
