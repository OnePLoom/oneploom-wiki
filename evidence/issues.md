# 관측한 문제와 트러블슈팅 후보

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

2026-10-22부터 유지한다. 과거 기록은 당시 수집한 원시 근거가 있는지 구분한다. 상태가 개선됨이어도 수치화, 효과 검증까지 끝났다는 뜻은 아니다.

## E-001 — 기록 방침과 실제 측정 근거의 간극

- 유형 및 상태: 관찰 / 최소 기록 구조 보완, 효과 측정은 미완료.
- 문제: 초기에는 별도 문제 대장과 보존된 실행 로그가 부족했다. 초안의 PASS 서술과 임시 백업만으로는 이후 비교 근거가 충분하지 않았다.
- 대응: 이 대장, 기록 기준과 기존 스크립트 검증의 원시 기준선을 보존했다. 자동 수집기를 설치한 것은 아니다.
- 근거: [script-baseline 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-21-37-script-baseline.md) — 1회, 16개 시나리오, assertion 36/36 PASS. 제품 테스트, AI 평가가 아닌 스크립트 분기 검사다.
- 다음 측정: 실제 개발에 들어가기 전 비교할 문제와 기대 판정을 고정한다. 현재는 전후 개선율, 실제 모델 작업 성공률이 없다.
- 기술 검토 판단: 측정을 위한 기반이며 그 자체를 주요 개발 성과로 내세우지 않는다.
- 후속 근거: [structure-probes 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-57-14-structure-probes.md)에 현재 경계의 고정 관측 10건과 조사 입력 해시를 추가했다. 기존 suite는 입력 해시, HEAD 불변을 대조해 재사용했다.

## E-003 — 백업 수명과 실패 시 보존

- 유형 및 상태: 회고와 예비 도구 관찰. 장기 운영 미검증.
- 문제: 초기 백업 도구에는 만료 정리가 없었다. 실제 디스크 고갈을 관측한 것은 아니다.
- 대응 이력: 새 백업 생성과 SHA-256 검증을 마친 뒤 만료 자료를 정리하는 순서를 예비 도구에 추가했다. 실행 시 정리이며 상시 스케줄러는 아니었다.
- 근거 한계: 임시 환경에서 만료 경계, 복원과 생성/검증 실패 시 보존을 확인했다고 기록했지만 당시 원시 실행 로그는 없다. 회고를 재측정 결과로 사용하지 않는다. 용량 감소율과 장기 무손실 운영은 미측정이다.
- 제품과의 관계: 이 예비 도구의 자동 만료 정책을 제품 기본값으로 채택하지 않았다. 제품은 [ADR 0021](../decisions/workflow/0021-recovery-storage.md)의 자동 보존과 명시적 정리, 복구 의존 자료 보호를 따른다. 정리 전에 새 보존본의 유효성과 삭제 영향을 확인해야 한다는 실패 처리 원칙만 연결한다.

## E-004 — compact 또는 재개 뒤 작업 제약 복구

새 세션 시작과 일반화된 복구 검증은 남음.
- 문제: 시작 스크립트의 첫 요청만으로는 compact 이후 작업 제약 확인을 보장하지 못한다. 현재 세션에서 읽는 것과 자동 강제는 다르다.
- 이동 전 사실: 기존 hook의 active followup 경로에는 `.gitkeep`만 있어 진행 상태를 찾지 못했다.
- 2026-11-08 재확인: 상태 문서는 별도 위치에 존재했지만 기존 hook은 이전 followup 경로만 검색했다. 읽기 전용 직접 실행에서 status는 `active followup: none`, session-start, post-compact는 `{"continue": true}`만 반환했다. 시작 스크립트의 지시와 native hook 연결을 구분했으며 당시에는 미해결이었다. 원본 해시, 명령, 출력은 [관측 기록 (active 경로 점검)](experiments/recovery/2026-11-08_13-41-39-active-routing.md)에 보존했다. 실제 lifecycle 이벤트 발동이나 모델의 읽기 여부를 검증한 결과는 아니다.
기존 hook 직접 호출이 상태를 발견하며 SessionStart의 additionalContext에 재개 경로가 포함된다. [관측 기록 (보정 근거)](experiments/recovery/2026-11-08_15-15-41-local-state.md). 제품 hook, 전역 설정은 변경하지 않았다. 실제 lifecycle 이벤트, 모델 읽기 문제까지 해결한 것으로 닫지 않는다.
- 2026-11-08 실제 관측: 자동 compact 기록과 SessionStart 안내 전달 뒤 첫 도구로 코드 쪽 active를 읽고 외부 문서에 기록한 작업 제약을 대조했다. 경로 옵션을 명시한 실제 재개 뒤에도 같은 순서를 확인했고 Windows 위키의 일반 권한 쓰기를 통과했다. [관측 기록 (압축 기록)](experiments/runtime/2026-11-08_15-25-53-wiki-transfer.md), [관측 기록 (재개 기록)](experiments/runtime/2026-11-08_15-25-53-wiki-transfer.md), [관측 기록 (쓰기 기록)](experiments/runtime/2026-11-08_15-25-53-wiki-transfer.md). 경로 옵션이 빠진 현재 프로세스를 옵션이 붙은 다른 프로세스와 혼동한 진단도 기록에서 정정했다.
제품 복구 단계에서는 compact, 재개 각각의 제약/미완료 검증 복구 성공 수와 실제 시도 수를 사전에 정한 조건으로 측정한다. 이번 소수 관측을 복구율이나 단위 테스트로 대체하지 않는다.
- 한계: PreCompact/PostCompact 각각의 dispatcher 실행, 실제 유실 사례, 복구율, 지속적 강제 동작과 외부 WIKI의 자동 변경 감시는 확인하지 않았다.
- 기술 검토 판단: 일반적인 상태 복구 문제로 범위를 좁혀 재현, 개선 효과를 증명하면 후보가 될 수 있다. 개발 기준 운용 자체를 제품 기능으로 옮기지 않는다.

## E-005 — 현재 프로젝트 결합과 검증 근거의 범위

- 유형 및 상태: 정적 관찰 + 격리 재현 / 개선안 채택 전.
- 관찰: 현재 스크립트에는 프로젝트 모듈명, 특정 테스트 선택 규칙이 있고, PASS 재사용 검사는 등록된 dependency, pattern 범위에 의존한다. 문서 matrix와 실행 로직의 기준도 한곳에서 생성되는 구조는 아니다.
- 근거: [1차 구조 분석](../discussions/history/initial-architecture.md)의 구현 검증, retry 설명과 이식 제약, 최초 기준선의 입력 파일 해시. 초안의 위험 추정과 실제 재현된 오동작은 구분한다.
- 해석: 새 프로젝트로 옮길 때 설정만으로 충분한지, 공통 검증 도구 변경을 놓치는지 별도 확인해야 한다. 현재 실제 누락, 오판 발생률이나 이식 실패율이 나온 것은 아니다.
- 다음 측정: 다른 모듈명 fixture에서 코어 수정 필요 여부, 등록되지 않은 공통 의존 변경에 대한 판정, 문서 기준과 실행 판정의 불일치 건수를 고정 사례로 검증한다. 실제 모델의 게이트 선택 평가는 별도다.
- 기술 검토 판단: 재사용 경계, 검증 증거 무효화, 계약 불일치 중 영향이 큰 문제만 선별한다. 현재 설계의 모든 후보를 한꺼번에 해결하는 범용 플랫폼으로 확대하지 않는다.
- 후속 재현: [structure-probes 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-57-14-structure-probes.md)에서 다른 모듈명은 UNCLASSIFIED, boot argv는 9개 include selector였다. 임시 gradlew를 성공→실패로 바꾼 경우 API PASS가 REUSED였고, 등록된 API source 변경 대조군은 RECHECK였다.
- 해석 한계: stub 기반 코드 동작 관측이며 실제 프로젝트 이식, Gradle 테스트, 메인의 최종 의미 판단 실패를 측정한 것은 아니다. 기존의 실패 전파 수정은 stub 실패에서 exit 1, state FAIL로 유지됐다.
- 2026-10-26 추가 관측: [recovery-retry-audit 관측 (2026-10-26)](experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)의 core-change-api-reuse에서 core source 변경에도 API PASS가 REUSED였다. 실제 `sample-api/build.gradle`은 core를 의존하지만 상태의 dependency/pattern은 해당 관계를 포함하지 않는다. 수정되지 않았다.
- 2026-10-27 재검토: [ADR 0002](../decisions/workflow/0002-pass-validity.md)의 초기 자체 캐시는 보류하고 검증된 도구 재사용을 추천했다. [ADR 0005](../decisions/workflow/0005-verification-selection.md)에는 검사 선택의 3개 대안을 추가했다. core-only floor와 소비 모듈의 관계는 정적 확인이며 실제 제품 회귀 누락을 새로 재현한 것은 아니다. 이 시점에는 모두 미채택, 미구현이었다. 이후 채택 범위는 각 ADR의 현재 상태를 따른다.
- 2026-10-27 사용자 확인: boot 테스트 제외는 팀원의 비공개 platform BOM 관련 자원 접근 불가에 따른 현재 프로젝트 전용 예외다. 제외 자체는 결함, 제거 대상으로 보지 않는다. 실제 9개 include가 의도한 제외 범위와 맞는지, 다른 프로젝트에 값이 섞이지 않는지는 별도 검토다. 접근 불가를 이번에 직접 검증한 근거로 쓰지 않는다.
- 2026-11-11 정적 대조: 같은 기준 HEAD의 추적된 boot 테스트 소스는 10개이며 고정 include 9개 중 실제 이름과 일치하는 것은 8개다. `org.example.boot.SchemaIntegrationTest`가 실제 `org.example.schema.SchemaIntegrationTest`와 다르며 승인된 resource 테스트 제외와 별개다. core에는 추적된 테스트 소스가 없고 API/infrastructure가 core를 소비한다. [범위표 — 「현재 프로젝트의 검사 범위」](../design/workflow/verification.md)에 소스, CI 차이, 환경을 연결했다. 파일 읽기 결과이며 Gradle 실행, 검사 누락률, 제품 수정/개선 결과로 계산하지 않는다.

## E-006 — compact scope 경계 검사의 비대칭

- 유형 및 상태: 격리 재현 / 수정, 실제 이벤트 검증 전.
- 문제: 상대 `../outside.txt`는 scope_error 없이 계속 진행했다. repo 밖 절대 경로는 marker가 있으면 중단했지만, marker가 없으면 snapshot에 scope_error만 기록하고 계속 진행했다.
- 근거: [structure-probes 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-57-14-structure-probes.md)의 relative-outside-scope, absolute-outside-scope-with-marker, absolute-outside-scope-without-marker.
- 원인: 상대 경로에는 resolve 뒤 경계 검사가 없고, marker 누락이 scope 검사보다 먼저 반환되는 경로가 있다.
- 다음 확인: 절대, 상대, symlink, marker 유무를 같은 안전 기준으로 검사하는 방안과 실제 native hook 적용을 검증한다.
- 한계, 후보성: 외부 dummy 파일만 사용했다. 비밀 유출이나 실제 compact 실패율을 주장하지 않는다. 재현 가능한 경계 오류 후보이며 아직 개선 성과는 없다.
- 2026-10-26 추가 관측: 위키 내부 fixture의 저장소 밖 dummy scope를 `.scope` symlink로 연결해도 mark가 성공했다. [recovery-retry-audit 관측 (2026-10-26)](experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)의 scope-symlink-mark에 보존했다. 원본 코드와 실제 개발 active는 변경하지 않았다.

## E-007 — 기계 소비용 계획과 실행 결과의 구분

- 유형 및 상태: 격리 재현 + 정적 관찰 / 인터페이스 초안 제안, 미채택, 미구현.
- 문제: multi-module floor가 `test`일 때 requires_full_test가 false였다. 계획 산출 PASS, 비활성 PASS, 실제 실행 PASS는 같지 않지만 소비자가 status만 보고 합칠 위험이 있다.
- 근거: [structure-probes 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-57-14-structure-probes.md)의 multi-module-plan과 현재 script 분기.
- 다음 확인: 실행 여부, 선택 범위, 완료 상태, 근거를 어떤 계약으로 나눌지 결정한 뒤, 자동 consumer의 오판 사례를 검증한다.
- 한계: 실제 외부 consumer가 잘못 실행하거나 모델이 오판한 사건을 관측한 것은 아니다.
- 2026-10-26 추가 관측: inactive-json-plan에서 빈 verification_floor가 `[]`가 아닌 `[""]`로 직렬화됐다. 원인은 shell 배열의 기본값 확장이다. 계획 산출, 비활성, 실제 실행 결과를 구별할 계약과 함께 수정할 후보이며 현재 미수정이다.
- 2026-10-27 설계 연결: [ADR 0003](../decisions/workflow/0003-plan-and-result.md)에 3개 대안을 비교하고 계획, 실행 결과 구조 분리를 추천했다. 현재 consumer의 오판율이나 개선 효과는 측정하지 않았다.

## E-008 — 문서 계약과 governance 자동 검사 범위의 차이

- 유형 및 상태: 격리 입력 재현 + 계약 대조 / 채택, 수정 전.
- 문제: matrix는 workflow-contract-change에 topic, worklog를 필수로 두지만, 두 경로가 없는 scope도 governance script에서 PASS였다. matrix가 실행 시 파싱되는 구조도 아니다.
- 근거: [structure-probes 관측 (2026-10-22)](experiments/baseline/2026-10-22_19-57-14-structure-probes.md)의 workflow-contract-without-topic-worklog, doc-update matrix와 governance script.
- 다음 확인: 일부러 사람에게 남길 검사와 자동 강제할 조건을 구분하고, 정책, 기계 설정의 원본과 회귀 사례를 정한다.
- 한계: script PASS가 전체 의미 검토 완료를 보증하지 않는 현재 계약도 존재한다. 모든 문서 정책을 자동화해야 한다는 결론은 아니다.

## E-009 — 기존 문서의 충돌과 공통 자산 추출 위험

- 유형 및 상태: 정적 관찰 / 수정 전.
- 문제: 루트 README의 모든 AI 작업 로그 규칙이 AGENTS, prompts의 조건부 기록과 다르다. `.github/CONTRIBUTING.md`는 현재 editor가 아닌 auth 라이브러리 규칙을 담고 있다.
- 근거: `../review/01-current-structure-audit.md`, 해당 조사 입력 manifest와 현재 README, AGENTS, `.github/CONTRIBUTING.md`.

## E-011 — quota 임박 지침과 감지 후 저장하는 연결의 부재

- 유형 및 상태: 사용자 보고 + 정적 관찰 + 보조 동작 격리 재현 / 설계 후보, 미구현.
- 문제: 사용자는 5시간/주간 사용량 제한 전에 active가 갱신되지 않는다고 보고했다. skill은 잔여 10% 미만이 보이는 경우를 조건으로 두지만, 실제 코드에는 quota 입력, 조회, 알림 소비자가 없다. 등록된 세 이벤트도 quota 이벤트가 아니다.
- 근거: followup skill 17, 42행, hooks JSON/Python, 공식 [hooks](https://learn.chatgpt.com/docs/hooks)와 [app-server](https://learn.chatgpt.com/docs/app-server). 후자에는 `account/rateLimits/read`, `account/rateLimits/updated`가 있지만 현재 연결되지 않았다.
- 격리 관측: [recovery-retry-audit 관측 (2026-10-26)](experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)의 no-active는 계속 진행, changed-source는 기계 snapshot만 생성하고 active 본문은 보존했다.
- 개선 후보: 의미 상태가 바뀌는 checkpoint를 기본 안전망으로 삼고, quota는 지원 환경에서 추가 조기 경고로 연결한다. 제한에 도달한 뒤 새 요약을 작성할 수 있다고 약속하지 않는다.
- 한계, 다음 측정: 실제 누락 사건 로그, quota 임박 이벤트, native hook 발동은 미확인. 현재 저장 시점, 신호 가용성, 중단 뒤 복구할 정보의 성공률을 별도 실험한다.
- 2026-10-27 후속 사용자 보고: 차별성 조사 도중 5시간 사용량의 25%, 5% 미만 경고, compact, 사용량 제한 중단이 이어진 대화 기록을 제공받고 재개했다. 진행 중 목표, 백업 위치를 적은 실행 상태는 있었으나 최종 평가, 계획 문서는 완료 전이었다. 경고 뒤마다 최신 연구 근거가 저장됐다는 확인은 없으며, quota API, native hook 원시 이벤트를 확보한 것은 아니다. 자동 저장 실패율, 유실량, 복구 시간을 계산하지 않는다. [평가](../discussions/architecture/alternatives.md)와 [계획](../development/roadmap.md)에 작업 경계 저장, 중단 상태 대조의 실증 후보로 연결했다. 구현은 여전히 미착수다.

## E-012 — retry가 최초 실패의 검증 범위를 보존하지 않음

- 유형 및 상태: 격리 재현 / 높은 우선순위, 미수정.
- 기대: 수정 후 최초 실패와 동일한 검증을 재개해야 한다.
- 관측: API 테스트를 항상 실패시키는 stub에서 최초 실행 exit 1. core만 든 새 scope를 retry에 전달하면 exit 0, PASS. 같은 API 검증을 다시 확인하면 여전히 exit 1이다. 실패 원본 파일은 그대로 보존됐다.
- 원인: retry는 실패 gate/change-kind만 복원하고, 테스트 범위는 현재 scope로 다시 계산한다. 원래 실행 계획을 복원하거나 새 scope와 동일성을 확인하지 않는다.
- 근거: [recovery-retry-audit 관측 (2026-10-26)](experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)의 original-api-failure, retry-with-core-scope, api-still-fails, 세 state, gradle-argv.log, stub 소스.
- 개선 후보: 검증 ID, 최초 선택 명령, scope, 예외를 저장하고, 수정 영향 분석과 원래 실패 검증의 재실행을 분리한다. 범위를 바꿔야 할 때는 명시적으로 재분류하고 원래 FAIL의 처리 근거를 남긴다.
- 한계, 후보성: 고정 반례 한 세트이며 실제 제품 Gradle, 메인의 최종 보고 오판률은 아니다. 정상 retry, 확대, 축소, 새 작업 혼입의 대조군을 추가해 전후 검증할 가치가 높다.
- 2026-10-27 설계 연결: [ADR 0001](../decisions/workflow/0001-verification-identity.md)에 국소 보강, 계획/실행 기록, workflow 엔진의 3개 대안을 비교하고 계획 보존을 추천했다. [검증 계약 초안](../design/workflow/verification.md)의 회귀 사례는 미실행이며 원래 버그는 미수정이다.

## E-013 — 복구 상태 입력 손상과 시각 경계 처리 부족

- 유형 및 상태: 격리 재현 / 미수정.
- 관측: marker JSON 배열에서 AttributeError, scope의 잘못된 UTF-8에서 UnicodeDecodeError로 exit 1. 1시간 미래 marker는 유효하게 처리됐다.
- 근거: [recovery-retry-audit 관측 (2026-10-26)](experiments/baseline/2026-10-26_19-03-55-recovery-retry-audit.md)의 marker-array, invalid-scope-encoding, future-marker.

- 한계: 실제 디스크 손상, 동시 쓰기, native hook의 오류 처리, 작업 유실률은 미측정. 예외가 발생했다고 곧바로 모든 호스트에서 도구나 compact가 차단된다고 단정하지 않는다.

## E-014 — 프로젝트 계약과 하네스 자체 변경의 탐지 경계

- 유형 및 상태: 정적 관찰 / 설계, 재현 확대 대기.

- 영향: 명시적인 변경 성격 없이 후보 없음으로 반환되는 결과를 전체 완료로 오해할 수 있다. 하네스 자체 코드도 제품 테스트 선택기와 별개의 검증 경로가 필요하다.
- 근거: 두 check script의 후보 정규식, docs 라우터, contract README, CI에 하네스 suite 호출이 없는 현재 구성.

- 한계: 경로 탐지는 최종 의미 판단이 아니며, 메인이 명시적으로 올바른 change-kind를 주는 경로는 남아 있다. 모델의 실제 누락 빈도는 미측정이다.

## E-016 — Windows Obsidian에서 WSL vault를 열 때의 감시 오류

- 유형 및 상태: 2026-11-04 사용자 증상 보고 + 외부 1차 사례. 이후 Windows 원본 배치의 작은 시험 확인. 원래 UNC 오류의 정확한 현장 오류, 버전, 자체 재현, 해결 검증은 전.
- 문제: 사용자는 Windows Obsidian에서 WSL 디렉토리를 vault로 열면 `Illegal…` 오류가 발생한다고 알렸다. Windows 앱 유지 선호, 앱 Git과 WIKI 분리, 최소 비용 조건이 있다.
- 근거: [Obsidian 포럼의 EISDIR watch 사례](https://forum.obsidian.md/t/cant-create-or-open-vault-in-wsl-folder/34688), [Microsoft WSL #7674](https://github.com/microsoft/WSL/issues/7674), [Node 파일 감시 제약](https://nodejs.org/api/fs.html#availability). 이 자료는 사용자 컴퓨터의 오류 전문이나 재현 로그가 아니다. 읽을 수 있었던 로컬 앱 로그에서는 오류, 버전을 확보하지 못했다.
- 원인 가설: 실제 오류가 `EISDIR ... watch`라면 Windows에서 WSL UNC 경로를 감시하는 계층의 제약과 부합한다. 파일 목록을 읽는 기능과 지속 감시를 구분하며, 경로 철자, 권한 문제로 단정하지 않는다.
- 최초 대응 후보: Windows 앱과 Windows 문서 원본을 함께 두고 WSL Codex가 해당 파일을 직접 사용하는 안을 우선 비교했다. Linux 앱, WSL 원본, 같은 Git 원격의 Windows/WSL 작업 사본 분리도 대안이다. 상세, 설계 영향은 [저장 검토](environment-observations.md)에 보존한다.
- 후속 관측(사용자 작업일 11/05, 시스템 날짜 11/06): [관측 기록 (별도 Windows 시험)](experiments/runtime/2026-11-06_00-49-05-vault-launch.md)에서 Obsidian 저장 표식을 WSL로 읽고, WSL 본문 수정, 파일 이름 변경을 확인했다. 사용자는 열린 앱의 변경 반영과 재열기 뒤 보존을 확인했다.
- 다음 확인, 측정: 실제 위키의 링크, 실행, 복원과 Codex 새 세션/재개를 확인한다. 원래 UNC 오류의 원인 판정에는 오류 전문, 앱/설치 프로그램 버전, 재현 로그가 여전히 필요하다. 일반 성공률, 반영 지연, 토큰 차이는 미측정이다.
- 기술 검토 판단: 환경 호환성과 원본/실행 경계의 후보 사례이며, 공개 이슈를 조사한 사실만으로 직접 결함을 수정하거나 성능을 개선했다고 주장하지 않는다.

## E-017 — WSL 외부 파일 링크의 열기 실패

- 유형 및 상태: 사용자 작업일 11/06의 GUI 관측. 내부 문서, 제목은 열렸으나 WSL `file://` 링크는 Obsidian, Windows 경고를 승인한 뒤에도 열리지 않았다. 링크 인식과 외부 파일 열기를 구분하며 E-016의 vault 감시 오류와 같은 원인으로 확정하지 않는다.
- 대응: 사용자가 기존 원격 커밋 링크를 선택했다. 시험 문서 5개의 원문 링크 15개를 보정하고, 대상 11개 파일의 로컬, 커밋, 원격 일치를 확인했다. 시험 `links.md`를 복원한 뒤 사용자가 내부/HTTPS 링크 모두 정상임을 확인했다. [관측 기록](experiments/runtime/2026-11-06_13-44-58-wiki-move.md).
- 대안, 공식 근거: [링크와 실행 경로](environment-observations.md)에 사본, IDE 경로, 고정 링크 비교와 외부 파일 열기 기능/버전 보고를 통합했다. 표기 변경, symlink, WSL vault로의 재배치가 현장 오류를 해결한다고 단정하지 않는다.
- 한계: HTTPS 대체 경로의 성공이며 WSL 파일 열기 결함 자체를 고친 것은 아니다. 실제 앱/설치 프로그램 버전, 동일 원인, 토큰 차이는 미확인이다. 후속은 실제 위키 복사와 전체 연결, 복원 확인이다.

## E-018 — Obsidian 제목 링크와 검사 기준의 불일치

- 유형 및 상태: 2026-11-09 사용자 GUI 보고, 정적 원인 확인, 링크 보정, 대표 링크 사용자 재확인.
- 관찰: `architecture.md`의 ‘모듈의 선택 확장과 실행 방식’은 파일을 열지만 제목을 찾지 못하고 상단으로 이동했다. 실제 제목은 `선택 확장과 실행 방식`, 링크는 GitHub식 `#선택-확장과-실행-방식`이었다.
- 검사 결함: 기존 검사기도 제목을 소문자, 하이픈 slug로 바꿔 검사했다. 따라서 당시 링크 검사 PASS는 Obsidian 제목 이동의 근거가 아니었다. 원시 검사, 결과는 고치지 않고 이 정정에 연결한다.
- 보정: 현재 읽는 Markdown의 내부 제목 링크를 실제 제목과 인코딩한 공백, 예약 문자로 맞췄다. 실제 제목 속 하이픈, 문서 본문, 외부 URL을 일괄 치환하지 않았다. 위키 [링크 기준](../README.md)과 새 정적 검사를 함께 보정했다.
- 검증 근거: [이번 검사](experiments/runtime/2026-11-09_06-06-50-obsidian-links.md)에 전후 목록, 검사 소스, 보존 확인을 남겼다. 사용자는 보정 뒤 해당 앵커가 정상 동작한다고 확인했다. 모든 링크를 GUI에서 클릭한 결과나 GitHub 렌더러 호환성 검증으로 확대하지 않는다.
- 범위: 문서 탐색과 검증의 예비 관측이다. 제품 기능 개선 실측으로 주장하지 않으며 사용하는 렌더러별 제품 검증은 별도로 수행한다.

## E-019 — plugin 형식 호환과 갱신 캐시의 보존 범위

- 유형 및 상태: 2026-11-09 WSL Codex CLI 0.167.0의 격리 로컬 시험 관찰. 제품 plugin은 미구현이며 지원 버전 전체를 검증한 결과가 아니다.
- 관찰: 루트 `plugin.json`이 존재하는데 설치는 `missing plugin.json`으로 실패했다. 같은 패키지에 `.codex-plugin/plugin.json`을 추가하고 실패 단계부터 재개하니 성공했다. 후속 입력 대조에서 공식 portable 예제의 `$schema` 선언이 없음을 확인했다. 이를 보완한 통제 시험은 없으므로 해당 입력의 실패만 기록하고 루트 형식 전체의 미지원, 실패 원인을 확정하지 않는다.
- 후속 관찰: 같은 plugin ID를 0.1.0에서 0.2.0으로 갱신하니 이전 캐시 파일이 사라졌다. 보존해 둔 0.1.0 자료를 다시 설치하면 내용이 복원됐지만 자동 rollback이나 두 프로젝트의 서로 다른 버전 유지가 입증된 것은 아니다.
- 2차 관찰: 같은 ID, 공유 상태에서 프로젝트별로 다른 고정 로컬 출처를 지정했다. A 0.1.0 뒤 B 0.2.0 설치 시 양쪽이 0.2.0, A 0.3.0 갱신 시 양쪽이 0.3.0이 됐다. A 제거 뒤 B의 설치 목록, 캐시도 비었다. native `skills/list`에서도 A가 선택한 0.3.0 대신 마지막 설치한 B의 0.2.0 경로, 본문을 확인했다. 명령 종료 코드 0과 별개로 버전 유지 기준은 FAIL이다.
- 근거: [설치 시험](experiments/runtime/2026-11-09_14-30-52-plugin-install.md), [버전 시험](experiments/runtime/2026-11-09_14-46-58-plugin-versions.md)에 입력, 명령, 출력, 발견 결과, 보호 대상 해시, 정리를 보존했다. 실제 모델/skill/hook 실행, 원격 인증은 없으며 다른 CLI 버전, ID/상태 분리는 미검증이다.
- 해석 보정: 프로젝트의 `enabled = false`와 설치본/캐시를 없애는 `plugin remove`는 다른 동작이다. A에서 제거 후 B도 사라진 결과만으로 Codex 버그라고 판단하지 않는다. 갱신과 native 발견의 버전 불일치는 별도로 남으며, 해당 시험의 `cwd`, 신뢰, 출처, 발견 입력은 프로젝트별로 지정돼 있었다. [시험 해석 — 「plugin 호환성 시험」](../discussions/history/install.md)에 공식 동작, 입력 한계, hook 미검증을 구분했다. 원시 결과는 수정하지 않는다.
- 당시 대응: [갱신 방식과 배포 수단](../discussions/history/install.md)에서 B 외부 고정 버전 실행 도구와 최소 연결을 추천했다. 사용자 수정 파일의 3방향 비교로 공유 plugin 설치 상태가 분리되지는 않는다는 관측은 유지한다. 이후 실행 배치는 [ADR 0019](../decisions/runtime/0019-project-install.md)의 프로젝트 내 설치로 채택됐고 제공 수단은 ADR 0010을 따른다. 이전 시험의 캐시 숫자, 목록 조회, 설치 성공을 새 배치의 실제 호출 검증으로 확대하지 않는다.

## E-020 — 텍스트 병합과 실패 복원의 자동 처리 한계

- 유형 및 상태: 2026-11-10 설계 위험의 격리 재현. 기존 제품의 장애나 수정 전후 성능 측정이 아니다. [B 설치 시험](experiments/runtime/2026-11-10_17-07-48-external-install.md)의 의도한 반례다.
- 병합 관측: 기준 설정은 2회 × 10초와 허용 60초였다. 사용자 20초 변경과 공식 4회 변경은 각각 유효했지만 Git이 충돌 없이 합친 결과는 4회 × 20초였다. 텍스트 병합 종료 0 뒤 별도 의미 검사로 적용을 차단하고 원문, 적용 버전을 보존했다. 시간 값은 예제 설정이며 실제로 80초 실행하거나 timeout 장애를 발생시킨 시험이 아니다. 보존한 suite, 명령 기록에도 실제 시간 초과 오류는 없고, 일반 사용자 설치 경로에서 재실행한 결과도 아니다.
- 복원 관측: 첫/두 번째 파일 반영 뒤 프로세스를 종료하고 새 프로세스에서 복원했다. 실패 후 사용자가 다시 수정한 경우에는 그 내용을 유지하고 복구, 실행을 보류했다. 최신 편집을 덮는 자동 복원을 성공으로 보지 않는다.
- 설계 반영: 기준본, 현재, 새 후보의 비교에 더해 후보의 계약 검사, 미완료 상태의 실행 차단, 복원 직전의 내용 대조가 필요하다. [갱신과 복원](../design/runtime/update.md)의 기존 조건을 실제 작은 사례로 확인했다.
- 한계: 작은 JSON 규칙, 프로세스 종료만 시험했다. 일반 문서 의미, 동시 편집/전원 장애, 원격 배포는 별도다. 후속 Codex 연결 관측은 [E-021 — 「E-021 — native hook의 완료와 격리 환경 차이」](issues.md#E-021%20%E2%80%94%20native%20hook%EC%9D%98%20%EC%99%84%EB%A3%8C%EC%99%80%20%EA%B2%A9%EB%A6%AC%20%ED%99%98%EA%B2%BD%20%EC%B0%A8%EC%9D%B4)과 설치 문서에 분리한다.

## E-021 — native hook의 완료와 격리 환경 차이

- 유형 및 상태: 2026-11-10 Codex 0.167.0의 별도 임시 상태, 두 프로젝트 연결 관찰. [실행 기록](experiments/runtime/2026-11-10_17-41-18-native-connection.md)에 처음 실패, 진단, 비교 입력과 원시 이벤트를 보존했다.
- 관찰: 외부 skill 링크는 루트/하위 폴더에서 선택한 commit을 찾았다. 프로젝트 신뢰와 개별 hook 신뢰는 별개였으며, 경로를 갱신한 hook은 재신뢰 전 실행되지 않았다. 같은 이름/정의의 중복 등록은 자동 제거되지 않고 각각 두 개가 발견됐다.
- 실패: 목록 조회, 세션 생성 응답은 hook 실행 근거가 아니었다. 요청을 시작하자 본문은 파일을 남겼지만 도구 sandbox 안에서는 자식 프로세스가 zombie로 남고 native 결과는 10초 timeout이었다. 이 10초는 보존한 `source/setup.py`가 시험 hook에 직접 지정한 값이며 Codex 진입 제한, 제품 기본값이 아니다. 직접 호출 종료 0도 native 성공을 대신하지 못했다.
- 비교: 같은 hook, 임시 프로젝트, 격리 Codex 상태를 sandbox 밖에서 실행하니 native 완료가 확인됐다. 이후 같은 세션 재개, 두 번째 프로젝트, 재신뢰한 갱신본까지 네 native 완료를 관측했다. 정확한 내부 원인은 미확정이며 제품 코드 수정이나 중첩 실행의 해결로 보고하지 않는다.
- 추가 제한: 연결 없는 loopback provider에 요청해 실제 모델 추론 없이 이벤트를 발생시켰다. retry 설정만으로 요청이 곧 끝날 것으로 가정한 관측기는 실패했고, 후속 관측에서는 hook 결과 뒤 요청을 명시적으로 중단했다. 이는 성공한 AI 응답, skill 품질, 토큰 효과가 아니다.
- 해석 보정: 자동 관측은 시험 클라이언트가 `codex app-server --stdio`를 호출한 결과이며 TUI는 hook 신뢰 검토에 사용했다. 일반 터미널의 `codex`/`codex resume` 전체 흐름을 재현한 것이 아니다. 11/10 사용자 지적에 따라 시험 제한의 출처와 실사용 차이를 설치, 수용 기준에 명시했다. 원시 자료, 체크섬은 수정하지 않는다. sandbox 밖 성공도 일반 사용자 진입 전체의 성공으로 확대하지 않는다.
- 반영: [설치 연결 — 「Codex 연결 시험 결과」](../discussions/history/install.md)의 신뢰 대기, 중복 검사, native 완료 확인, 지원 환경 구분을 유지한다. 자동으로 신뢰를 우회하거나 sandbox 안의 실패를 원인 확인 없이 성공으로 변경하지 않는다.

## E-022 — 과거 상태의 수신과 새 실행 검사의 충돌

- 날짜: 사용자 작업일 2026-11-17.
- 분류: 설계 DDL과 합성 메모리 입력의 관찰. 실제 제품/사용자 자료의 실패는 아니다.
- 관측: 해제된 보호를 최종 행으로 INSERT하거나 후속 취소를 과거 정리 확정보다 먼저 넣으면 거부된다. 또한 현재 형식 3인 대상에서 과거 1→2 전환을 새 준비로 INSERT하면 `transitions_insert`의 현재 출발 형식 검사에 걸린다. 숫자는 합성 입력이다.
- 근거: [7개 검사와 원시 결과](experiments/recovery/2026-11-17_10-01-07-maintenance-handoff.md). 보호/취소의 순서는 같은 수신 트랜잭션 안의 준비/관측 순서로 대조했고, 과거 출발 형식의 일반 수신은 해결하지 않았다.
- 영향: 테이블 단위 복사나 일반 실행 INSERT만으로 모든 과거 이력을 인계할 수 있다고 주장하면 안 된다. 이력을 빼거나 값을 현재 형식으로 고치면 과거 사실을 잃는다. 보호를 전역 해제하면 정상 실행의 안전 조건이 약해진다.
- 현재 대응: [유지 관리 인계 순서 — 「유지 관리 기록의 인계 순서」](../design/workflow/storage.md)와 [과거 형식 변경 기록의 수신 경계](../design/workflow/storage.md)를 명세했다. 해결되지 않은 수신은 원본/대상을 보존하며 보류한다.
- 다음 확인: 새 전환의 검사와 구분되는 과거 사실 수신 경로, 기존 대상 보존, 최종 제약/소비 차단과 중단 입력을 함께 검증한다. 실제 Windows 수신/변환이나 정상 설치 성공으로 보고하지 않는다.

11/17 후속 검토: 설치의 기존 정상 DB 재사용 조건까지 대조한 뒤 [최초 인계 방식 재검토](../design/workflow/storage.md)에 행별 수신, 초기 DB의 위치 전환, 별도 후보 병합을 비교했다. B의 위치 전환을 추천하지만 사용자 선택 전이며 SQL과 probe는 바꾸지 않았다. 수신/활성화 관계, 기존 자료 보존과 형식 변환의 검증이 남아 있어 E-022를 해결 완료로 바꾸지 않는다.

11/17 채택/부분 검증: 사용자가 B를 채택했고 초기 설치 DB의 같은 형식 사본, 같은 논리 식별과 기록 보존으로 방향을 바꿨다. `handoffs.side`를 사본의 불변 역할로 두던 초안을 단계 상태와 공통 쓰기 진입의 실제 위치 대조로 보정했다. [새 인계 검사](experiments/recovery/2026-11-17_11-21-50-handoff-snapshot.md) 16개에서 과거 전환 이력 보존, 단계별 저장 실패/재시도와 후속 쓰기를 확인했고 현재 DDL의 저장/유지 관리 65개도 통과했다. 일반 INSERT의 과거 출발 형식 거부는 그대로이며 B에서는 그 경로로 과거 행을 재등록하지 않는다. 이 최초 인계 경로의 보완과 실제 파일/Windows 인계, 지원 형식 간 변환 검증을 구별한다. 후자는 아직 남아 있으므로 제품 전체의 해결 완료로 표시하지 않는다.

## E-023 — 프로젝트별 권한 후보가 다른 프로젝트의 시작에 미치는 영향

- 날짜와 범위: 2026-11-18, Windows Codex 격리 설정 조회. 제품 설치/일반 TUI의 관측과 구분한다.
- 관찰: 같은 0.169.1 실행 파일에서 이름 있는 권한 프로필과 전역 기본값이 모두 없는 C는 조회됐지만, A/B용 프로필만 사용자 설정에 추가한 C는 기본값 누락으로 초기화 전 종료했다. 프로젝트의 기본 권한이 가리키는 프로필이 없는 D도 종료했다. 신뢰된 A/B/A의 프로필 선택은 각각 일치했다.
- 근거: [Windows 설정 조회](experiments/runtime/2026-11-18_10-36-06-windows-config.md). 초기 0.167.1 관측과 후속 0.169.1 관측을 분리했고 마지막 대조에서는 실행 파일 해시를 고정 확인했다. 신뢰 키의 경로 표기 차이도 별도 입력으로 대조했다.
- 영향: 사용자 설정에 프로필을 보관만 하면 다른 프로젝트에 영향이 없다는 가정은 이 입력에서 성립하지 않는다. 시험용 전역 기본값 추가로 C가 조회돼도 기존 동작 보존까지 입증한 것은 아니다. D에서는 내부 skill만 안내하면 최초 준비를 할 수 없다.
- 후속 요구와 보정: 사용자는 Codex 전역 설정 비변경을 필수로 지정했다. [로컬 배치 — 「지속 권한 설정의 배치」](../design/runtime/entry.md)에 선택값과 정의를 함께 두고, 새 로컬 config의 제외는 연결 코드가 처리하는 후보로 바꿨다. [후속 시험](experiments/runtime/2026-11-18_11-03-32-project-permissions.md)에서 C의 전후 설정 보존과 D의 연결 전/후 조회를 확인했다. 기존 실패 근거는 보존하며 모든 정책/버전에서 해결됐다고 확대하지 않는다.
- 추가 관측: 실제 Windows sandbox는 시험 환경의 SystemDrive 누락, 이어 출력 디코딩 오류를 거쳤다. 환경/UTF-8과 원시 bytes 보존을 보정한 마지막 실행에서 쓰기/재읽기 5개 성공과 다른 WIKI 쓰기 4개 거부를 확인했다. 두 번째 시도의 stdout 부재는 그대로 한계로 남겼다. Git 합성 입력에서는 제외 중복 방지, 추적 파일 보호와 재포함 충돌을 확인했다.
- 공식 자료 기반 위험 보강: Git 제외는 config 안의 팀 설정도 함께 가리며, 다른 브랜치의 같은 추적 경로로 전환하면 무시된 파일이 덮어써질 수 있다. 무시 파일을 포함하는 clean도 삭제할 수 있다. [적용 조건 — 「다른 도구의 사례와 적용 조건」](../design/runtime/entry.md)에 Git/IntelliJ/Claude Code 공식 근거와 대조를 연결했다. 이번 환경에서 덮어쓰기/삭제 피해를 관측한 것은 아니며 관련 시험은 아직이다.
- 공유 충돌의 후속 조사: 공개 팀 설정 예제와 Trail of Bits의 공개 양식은 config 전체가 비밀자료는 아니라는 근거다. 기업 서비스의 일반적 공개 비율까지 확인한 것은 아니다. 공식 계층/로더와 열린 #24961을 대조한 뒤 [공유 충돌 해결안 — 「공유 설정과 개인 경로의 충돌 해결」](../design/runtime/entry.md)에 공통 원본 + 로컬 생성, 제품 시작 인자와 별도 도구 연결을 비교했다. 생성 방식은 원본 변경 뒤 갱신과 기존 공유 config 전환 동의가 필요한 미채택 후보다.
- 소유와 공유 전환의 재검토: 사용자가 미추적 config의 향후 공유와 무관한 설정의 관리를 지적했다. [설정 소유와 공유 상태의 전환](../design/runtime/entry.md)에 Git 공식 근거와 상태별 보호를 연결했다. 파일 전체 자동 제외/생성의 범용 기본 추천은 철회하고, 명시적으로 그 운영을 원하는 프로젝트의 미채택 비교안으로 남긴다. 이미 무시/미추적인 파일도 사용자 소유이며 이전 로컬 운영 동의를 미래 공유 전환의 강제 취소로 해석하지 않는다.
- 공유 config 보존 후보: 공식 Codex MCP/권한 자료와 STDIO 표준을 확인해 [로컬 WIKI 도구 — 「로컬 WIKI 도구의 연결 후보」](../design/runtime/entry.md)를 구체화했다. 공유 config에는 공통 실행 등록만, 기기 경로는 `.harness/local.json`에 두는 우리 설계 후보다. shell의 외부 쓰기 허용과 다른 통제이므로 명시적 허용, 등록 루트/동작 제한, 파일 보호와 기존 복구를 연결해야 한다. 자동 제외/전역 설정 변경을 우회 해법으로 쓰지 않는다.
- 사용자 비용의 재비교: [진입 방식 비교 — 「전용 시작 명령과 MCP의 비교」](../design/runtime/entry.md) 뒤 사용자는 [ADR 0022](../decisions/runtime/0022-wiki-entry.md)의 전용 시작 명령 기본과 선택 MCP의 단계적 검증을 채택했다. 당시 MCP 첫 제공은 비교 뒤 판단하도록 남겼고 11/22에 직접 접근 우선/MCP 후속으로 정했다. 별도 PC/24시간 서비스 도입으로 설명하지 않는다.
- 상태와 다음: 기존 권한 시험은 보존하고 새 기본 진입을 검증한다. Windows 인자 전달의 새 관측은 E-024에 분리했다. 시간/토큰 비교는 미측정이다. 실제 TUI 읽기/쓰기와 같은 세션 재개 관측은 E-025에 연결한다. MCP 프로토콜 시험과 제품 구현은 아직이다. 사용자 설정과 개발 Git/index는 보존한다.

## E-024 — Windows 중계 파일의 인자 변환

- 사용자 작업일: 2026-11-18. ADR 0022의 시작 명령 구현 전 호출 조건 확인이다.
- 관찰: 합성 .cmd는 shell=False/True 모두 `%HARNESS_PROBE_VALUE%`를 시험 환경변수 값으로 바꿨다. 셸 없는 Python/Node 실행은 8개 입력을 모두 보존했다. 실제 Codex의 알 수 없는 옵션 오류에서도 `.cmd` 경로의 변환과 Node 공식 진입의 원문 보존을 확인했다.
- 근거: [Windows 실행 경로와 인자 전달](experiments/runtime/2026-11-18_13-54-14-launch-arguments.md). 합성 32회, 도움말/버전 6회, 실제 옵션 오류 2회이며 모델 호출은 0회다. 잘못된 옵션의 종료 코드 2는 의도한 관측이다.
- 영향과 보정: 종료 코드 0이나 도움말 출력만으로 모든 사용자 인자의 보존을 판단하면 안 된다. 제품은 확인한 설치 형식의 실행 경로를 사용하고 문자열 명령 연결이나 모든 사용자에 대한 codex.cmd 고정을 피한다. 현재 npm 공식 진입을 Node로 직접 호출하는 후보를 명세에 연결했다.
- 한계/다음: 관측은 현재 설치본과 유한 표본에 한정한다. 현재 설치 형식의 시작 파일과 TUI 읽기/쓰기, 같은 세션 재개 관측은 E-025에 연결한다. 실행 중 취소/비정상 종료, 전체 사용자 옵션/권한과 다른 설치 형식 지원은 남아 있다. 실제 제품의 버그 수정 완료나 모든 셸 위험의 해결로 표시하지 않는다.

## E-025 — 첫 터미널 시작에서 외부 WIKI 권한 거부

- 사용자 작업일: 2026-11-18. [시험 기록](experiments/runtime/2026-11-18_14-23-43-terminal-start.md)에 소스, Windows 자동 검사와 사용자 관측을 구분해 보존했다.
- 관찰: 사용자가 실제 Windows PowerShell에서 시작 파일을 실행했다. Codex 0.169.1이 현재 권한으로 추가 쓰기 루트를 허용하지 않는다고 출력하고 PowerShell로 돌아왔다. 인자 미리보기 성공은 실제 시작 성공이 아니었다.
- 원인 구분: 기본 Windows 사용자 config의 좁은 읽기에서는 명시적 권한과 해당 프로젝트 신뢰 기록을 찾지 못했다. 공식 같은 버전 소스의 신뢰 상태 미지정 시 읽기 전용 기본값은 유력한 설명이다. 모든 설정 계층/유효 권한을 직접 조회한 것은 아니므로 단일 원인 확정이나 사용자 설정 오류로 단정하지 않는다.
- 보정: 시험 파일에 명시적 `--sandbox workspace-write` 전달을 추가했다. 기존 기본값은 유지하고 모델, 승인 정책과 전역 config를 자동 변경하지 않는다. 영향받은 6개 검사/미리보기는 통과했으며 실제 재시도는 사용자가 조건을 확인해 실행한다.
- 후속 관찰: [명시적 선택의 재시도](experiments/runtime/2026-11-18_14-38-50-terminal-auth.md)에서 사용자가 Codex 입력 화면과 계정 인증 화면을 확인했다. 이 조건에서는 앞선 즉시 종료를 지나갔다. 이후 로그인과 [WIKI 읽기와 수정 표본](experiments/runtime/2026-11-18_14-49-24-terminal-io.md)을 확인했다. 요청한 상태 한 줄 외에는 보존됐고, 같은 세션 재개 뒤에도 프로젝트/WIKI 권한과 파일이 유지됐다. 사용자는 재개 대화 선택 외 추가 요청이 없었다고 보고했다. 이번 성공은 workspace-write를 명시한 조건이다. 제품의 최초 선택 저장/재사용과 다른 초기 권한 호환은 아직이며, 임의 사용자 설정을 workspace-write로 덮는 기본안은 채택하지 않았다.

- 11/20 후속 비교: [관측 기록 (직접 접근 시작)](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md)에서도 `--add-dir`만 지정한 첫 실행이 같은 권한 오류를 냈다. 사용자가 이번 실행에 workspace-write를 명시한 뒤 외부 사본 권한과 현재 모델을 확인했다. AI 요청은 그 후 한 번 실행됐고 추가 승인창은 없었다. 최초 준비와 정상 요청의 승인 재사용을 별도로 평가한다.

## E-026 — MCP 부분 검사와 실제 Codex 연결의 차이

- 날짜와 범위: 2026-11-18, 합성 Windows 읽기/검색 시험. [원시 근거](experiments/wiki-access/2026-11-18_15-21-34-mcp-read.md)에 실패와 보완을 보존했다.
- 첫 관찰: SDK 2.3.0의 bare dict 반환은 구조화된 결과를 만들지 않아 통신 검사가 실패했다. 명시적 반환 타입/출력 검사로 보완한 뒤 동일 통신 검사가 통과했다. 파일 처리 코드의 유효한 PASS는 재사용했다.
- 실제 호스트 관찰: SDK 연결이 통과해도 Codex TUI는 경로 없음 오류로 MCP 시작에 실패했다. 설정의 상대 cwd를 제거한 뒤 A 루트에서 두 도구 연결과 실제 검색/읽기를 확인했다. 사용자 보고뿐 아니라 해당 세션의 도구 기록과 원문 해시도 대조했다.
- 해석: 설정 발견, SDK 통신, 호스트 시작, 실제 도구 사용을 각각 검증해야 한다. 다른 설정의 상대 경로 규칙을 MCP 필드에 그대로 적용하거나 최신 안내를 설치 버전의 계약으로 단정하지 않는다.
- 후속 호스트 관찰: [B/재개/하위 경로 시험](experiments/wiki-access/2026-11-18_15-50-14-mcp-projects.md)에서 B 실제 사용과 A의 새 재읽기를 확인했다. A/nested는 같은 상대 명령이 다른 위치를 가리켜 os error 3으로 실패했다. Git 루트를 확인해 시험 서버를 실행하는 등록으로 바꾸고, 같은 후보 명령의 SDK 연결 5곳/경계 거부 2개 뒤 실제 A/nested 읽기까지 확인했다. 모델을 써서 경로를 고르는 방식은 아니다.
- 조건 구분: 당시 npm/설정 조회는 0.169.1, 세션 메타데이터는 0.170.0/source vscode다. 차이 원인은 미확인이고 사용자 실행 보고와 내부 표기를 구분한다. WSL 수집기의 Windows 경로 해시 대조 오류는 경로 부분 변환 뒤 같은 검사만 재실행해 통과했다.
- 실제 탐색 관찰: 후속 [Codex 비교](experiments/wiki-access/2026-11-18_16-50-18-codex-wiki-usage.md)에서는 패키지/사용자 status/세션 모두 0.170.0이었다. MCP가 줄 수를 끝 줄처럼 크게 요청하고 여러 결과를 합쳐 출력하면서 범위 오류와 잘림이 관측됐다. 뒤이어 좁게 다시 읽었지만 답변의 필수 조건 하나는 직접 접근과 MCP 모두 누락했다. 부분 파일/통신 PASS가 실제 탐색과 답변 완전성을 보장하지 않는 사례다.
- 남은 확인: 읽기 범위와 합산 출력의 전달, 오류 안내/필수 조건 검토, 반복/순서 통제가 있는 비용 비교, clone/worktree와 제품 설치, 쓰기/보호, 비정상 종료. 각 한 요청의 관측이나 정상 답변 완료를 모든 문제의 해결로 확대하지 않는다.

- 11/18 보완 명세와 후속 동기화: [읽기/검색 입력과 반환 — 「MCP 읽기의 남은 보완」](../design/runtime/entry.md), [공통 답변 완전성 — 「원문 수신과 답변의 완전성」](../design/workflow/verification.md), 현재 [R-01~14 시험 입력 — 「MCP 읽기 보완의 검증 입력」](../verification/acceptance.md)을 연결했다. 이후 [별도 내부 시험](experiments/wiki-access/2026-11-18_18-45-45-mcp-read-fidelity.md)에서 원문 범위 보존과 Windows 시간 필드 차이를 확인했지만 SDK 전체 반환 계수 검사는 실패했다. 임의 응답/파일/검색 제한을 실제 배포 검증의 기준으로 둔 진행도 사용자 지적으로 수정했다. 해당 제한의 추가 시험은 중지하고 배포 조건 대조를 먼저 한다. 과거 두 답변의 PARTIAL 판정은 유지한다.
- 11/19 진단: [Windows SDK의 결과 변환](experiments/wiki-access/2026-11-19_15-35-59-mcp-output.md)에서 사본 3개를 두 규격으로 변환해 본문 보존을 확인했다. 이전 크기 검사는 실제 전송 원문 대신 클라이언트 정규화 객체를 계수했고, 구형 규격 결과를 읽은 뒤 추가된 `resultType`이 진단용 인코딩에서 24바이트 차이를 만들었다. 고정 보정값을 넣지 않고 논리 페이지, 실제 전송과 호스트 수신을 나눠 검사하도록 명세했다. SDK 서버/실제 Codex를 새로 실행한 결과가 아니므로 기존 FAIL/PARTIAL은 유지하며 배포 페이지 설정과 전체 수신 검증은 남는다.

- 11/19 실제 수신: [후속 Windows 시험](experiments/wiki-access/2026-11-20_04-55-27-codex-receipt-run.md)에서 지정한 18행/1,328바이트의 로그 본문 일치를 확인했다. Codex 도구 선언의 선택 입력 누락은 각 oneOf 분기를 완전하게 생성하도록 보정한 뒤 Windows 영향 검사와 실제 선언 재확인으로 해당 관측을 해소했다. 표준 schema의 유효성과 호스트 표현은 구별한다. 첫 전체 읽기는 코드가 본문 대신 길이/완료 정보만 출력해 수신 미확인이었다. 서버 지침 보완 뒤 추가 한 요청에서 전체 72,422바이트가 로그와 독립 원문에 일치했다. 첫 시도의 TextEncoder 오류, 본문 미전달, 구간 읽기의 중복 출력과 붙여넣기 차이는 보존한다. 검색도 71개 일치 줄과 9개 파일의 본문 발췌/위치가 일치했다. 전체 사용 품질/비용은 별도이며 이 표본을 일반적인 무결함이나 비용 개선으로 확대하지 않는다.

- 11/20 후속 품질 비교: [같은 질문의 두 요청](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md)에서 MCP 원문 수신은 일치했지만 필수 복구 예외가 답에서 누락됐다. 직접 접근은 첫 검색 잘림과 한글 깨짐 뒤 UTF-8로 다시 읽어 세 사례의 필수 조건을 반영했다. 실패/재조회 비용과 품질 차이를 함께 기록하며 MCP의 새 cursor 문제는 E-029로 분리한다.

## E-027 — 조회 가능한 설정과 실제 실행 권한의 차이

- 유형과 상태: Windows 0.170.0 합성 입력 관찰. API 후보와 호환 한계 확인, 제품 대응은 미구현.
- 문제: config/read와 권한 프로필 목록을 실제 TUI의 최종 권한으로 간주하면 잘못된 준비 판정을 할 수 있다. 읽기 전용 명령 옵션에서도 쓰기 프로필 후보가 남았고, --profile은 도움말과 달리 실제 app-server 시작에서 거부됐다. 실제 권한을 우회한 사고를 재현한 것은 아니다.
- 세션 조회: 합성 원시 기록은 thread/read로 읽혔지만 DB 전용 목록은 비었다. 목록이 비었다고 전체 대화가 없다고 단정하거나 새 세션으로 대체하면 안 된다. 새 시작에는 이 조회가 필요하지 않다.
- 근거: [호스트 조회](experiments/wiki-access/2026-11-18_17-52-34-host-query.md), 요청/응답과 Codex stderr, 설치본 생성 스키마. 모델 요청 없이 합성 설정/기록을 사용했고 실제 사용자 config 해시를 보존했다.
- 대응: [실행 인계 — 「호스트 조회와 실행 인계」](../design/runtime/entry.md)에 조회의 적용 범위, 사용자 인자 보존과 자동 선택의 확인 조건을 연결했다. 옵션 제거, 설정 자체 재해석이나 성공으로의 자동 대체를 하지 않는다. 실제 profile/TUI/관리 정책 대응과 사용자 환경의 비용은 수용 시험에 남는다.
- 11/19 TUI 후속: [관측 기록 (수신 시험의 설정 대조)](experiments/wiki-access/2026-11-20_04-55-27-codex-receipt-run.md)에서 전역 config에 새 시험 프로젝트의 신뢰 절이 추가된 것을 확인했다. 해당 절만 제외하면 기존 해시와 일치했다. 실제 호스트의 신뢰 등록과 모듈의 설정 쓰기를 구별하고, 전체 해시가 달라졌다는 이유로 사용자 설정을 복원하거나 임의 초기화하지 않는다. 작성 프로세스는 직접 감사하지 않았고 모듈의 전역 설정 비변경 원칙도 유지한다.

## E-028 — MCP 서버 종료 후 이어 읽기의 연결 실패

- 유형과 상태: 11/20 Windows Codex 0.171.0의 실제 관찰. 자동 재연결 실패는 보존. 사용자 재개 후 새 연결과 전체 읽기 복구 확인.
- 문제: 시험용 WIKI 서버 하나를 종료한 뒤 같은 대화에서 유효했던 이어 읽기 정보를 보냈지만 `Transport closed`로 실패했다. 추가 본문은 없었고 자동으로 다시 연결해 읽지 못했다.
- 근거: [실행과 판정](experiments/wiki-access/2026-11-20_20-16-32-mcp-reconnect-plan.md). 승인한 두 AI 요청, 작업자 한 개의 실제 종료와 같은 next 호출을 대조했다. 최초의 오래된 PID는 종료 전 검사에서 거부됐고, 시험 서버 재식별은 시각과 요청 문맥에 따른 추론임을 보존했다.
- 확인한 대응: AI는 부분 행과 미완료를 정확히 알렸고 다른 도구나 반복 호출로 대신하지 않았다. 이 확인은 명시된 오류 처리 지시가 있는 표본이며 일반적인 자율 복구 성공이 아니다.
- 후속 대응: [같은 시험 대화의 일반 재개와 읽기](experiments/wiki-access/2026-11-20_20-51-32-mcp-reopen-plan.md)로 새 연결, 옛 next의 expired_cursor와 전체 재독을 확인했다. 새 본문 다섯 개의 72,577바이트가 현재 사본과 일치했다. 공용 서버 재시작이나 여러 대화의 연결을 갱신하는 내부 수단은 사용하지 않았다.
- 남은 범위: 정상 재개 후 다시 읽는 사용자 안내의 근거로 삼되, 자동 재연결이나 모든 버전의 복구 성공으로 일반화하지 않는다. 실행 중 취소/늦은 결과와 자유 탐색의 자율 복구는 별도 검증이다.

## E-029 — 이어 검색 정보가 호출 과정에서 달라짐

- 유형과 상태: 11/20 Windows Codex 0.171.0 / GPT-5.6-Sol low의 실제 비교에서 관측. 거부 동작은 확인했으며 자연스러운 이어 받기와 오류 안내의 보완은 남는다.
- 관찰: `QUERY_A` 검색의 다음 요청에 AI가 입력한 cursor가 도구의 반환값과 달랐다. 반환값 472자, 입력값 476자였으며 서명 바이트는 그대로이고 payload가 달랐다. 서버가 `expired_cursor`로 거부해 추가 본문은 없었다.
- 근거: [관측 기록 (실제 호출 대조)](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md), [관측 기록 (호출 기록)](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md), [해석](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md). 손상된 값을 실험자가 주입하지 않았고 원문/후보도 보존했다.
- 원인 경계: 입력 문자열 변경만으로 현재 후보의 서명 검사를 통과할 수 없는 상태다. 같은 오류 코드가 형식/서명 실패도 포함하므로 서버 재시작이나 시간 만료를 원인으로 단정하지 않는다. E-028의 실제 연결 재시작 표본과 다르다.
- 대응과 남은 판단: 잘못된 입력을 검증 없이 수용하도록 느슨하게 하지 않는다. AI가 값을 전달하는 방식과 이어 받기 식별자, 오류 분류를 함께 검토하고 기존 저장/연결 수명과의 영향을 비교한 뒤 후보를 정한다. 현재 비교 중 코드 변경이나 추가 AI 재실행은 없다.
- 11/22 후속: [관측 기록 (통합 후보의 실제 입력)](experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)에서도 두 변형을 관측했다. 검색 토큰은 528→527자, 읽기 토큰은 같은 1,052자 안에서 파일명이 달라졌다. 코드 값 재사용 예시는 실제 호출에 사용되지 않았다. 거부 보호는 유지됐지만 자연스러운 이어 받기와 “만료”로만 표현한 오류 설명은 보완이 남는다.

- 11/22 값 단축 후속: [세 방식 비교](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)에서는 긴 값 10개와 짧은 값 5개 모두 정확히 전달됐다. 값 전달 성공만으로 비용/답변 품질까지 해결된 것으로 처리하지 않으며, 이 표본에서 단축에 따른 오류 감소를 입증하지 않았다.

## E-030 — WIKI 조회에서 누적된 모델 호출 비용

- 유형과 상태: 11/20 문제 관측/재집계와 11/22 통합 후보의 새 전후 비교. 호출 감소를 관측했으나 값 전달 실패와 비용 해석의 한계가 남는다.
- 관찰: MCP/직접 접근의 내부 모델 응답은 21/4회, 누적 입력+출력은 722,087/138,975토큰이었다. 응답당 평균 입력은 비슷했다. 구독 요금/잔량의 차이를 뜻하지 않으며 품질 차이도 있어 동등 품질의 성능 비교로 보지 않는다.
- 근거: [응답별 재집계](experiments/wiki-access/2026-11-21_05-58-03-mcp-cost-review.md), [기존 비교](experiments/wiki-access/2026-11-21_04-48-10-mcp-comparison-run.md). 실제 자동 축소는 관측되지 않았고 실패/재조회 비용을 포함했다.
- 원인과 대안: 단일어 검색, 호출/출력 지침과 자료 활용을 함께 검토한다. 입력 크기만 늘리거나 보호 검사를 빼서 수치를 맞추지 않는다. 최신 후보는 [호출 비용과 개선 순서](../design/integration/mcp.md)가 소유한다.
- 기술 검토 판단: [상세 사례](cases/mcp-cost.md)에 새 기존본/개선본의 단건 수치를 함께 기록했다. 직접 접근은 별도 기준이다. 누적 토큰 감소만 강조하거나 구독 비용 감소/최적화 완료로 표현하지 않는다.
- 11/22 통합 후보의 실제 비교: [실제 비교](experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)에서 내부 응답 21→14회, 캐시 포함 토큰 781,204→480,497과 캐시 제외 입력+출력 40,212→42,225를 확인했다. 두 답 모두 사전 필수 사실을 반영했지만 개선본에 값 변형 2회와 등록 크기 초과 입력 1회가 있었다. 지침/예시를 실제 호출과 연결하는 보완과 최종 오류 설명의 누락 검토가 남는다.

- 11/22 세 방식 후속: [관측 기록 (직접/긴 값/짧은 값)](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)의 캐시 제외 입력+출력은 32,121/82,904/52,092, 시간은 66.596/168.568/91.486초였다. 짧은 값은 검색 미완료 보고와 답변 기준 일부가 빠져 동일 품질의 절감으로 인정하지 않는다. 이후 같은 11/22 작업에서 사용자가 직접 접근 우선/MCP 후속을 채택했다.

## E-031 — 이어 검색이 남은 상태의 완료 보고

- 유형과 상태: 11/22 짧은 값 후보의 실제 요청에서 관측. 서버 반환은 보존됐으나 작업 완료 판단과 보고가 미충족이다.
- 관찰: 첫 복수 검색의 실제 일치 283줄 중 193줄을 받고 90줄이 남은 next를 사용하지 않았다. 다른 좁은 검색 두 개는 완료했지만 최종 답에서 첫 검색의 미완료를 알리지 않았다. 별도의 상한 초과 입력 오류는 알렸다.
- 근거: [관측 기록 (검색 완료 대조)](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md), [관측 기록 (답변 검토)](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md), [관측 기록 (실제 반환)](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md). 완료한 요청의 반복 실행이나 의도적 실패 주입은 하지 않았다.
- 원인 경계: 서버는 남은 위치와 output_limit을 반환했다. 이어 읽지 않은 상태와 서버가 원문을 빠뜨린 상태는 다르다. 90줄 모두가 정답 필수 자료이거나 다른 읽기에도 전혀 없었다고 단정하지 않는다. 넓은 탐색을 충분한 근거 확보 후 중단하는 선택은 가능하지만 이번 요청의 미완료 보고 조건을 충족하지 못했다.
- 관련 품질: 이미 반환된 “일반 문서 조회는 빠르게 응답” 기준도 최종 답에서 빠져 필수 사실 15개 중 1개가 부분 충족이었다. 원문 반환 검사의 PASS로 의미 검토를 대신하지 않는다.
- 후속 판단: 값 길이/입력 설명 보완만으로 전체 작업을 해결했다고 취급하지 않는다. 계속 개발한다면 미완료 범위와 근거 검토를 실제 호출/답변 흐름에 연결할 대안을 검토해야 한다. 실패를 보존하고 [첫 제공 판단 — 「세 방식 비교와 첫 제공 판단」](../design/integration/mcp.md)을 거쳐 사용자가 직접 접근 우선/MCP 후속을 채택했다. 이 오류를 해결한 것으로 닫거나 추가 구현/AI 실행을 진행하지 않는다.
