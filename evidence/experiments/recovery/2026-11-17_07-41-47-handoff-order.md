# 최초 인계의 행 순서 검사

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일: 2026-11-17. 시스템 기록은 2026-11-17 07:41:47 KST다. 기존 [설계 DDL](../../../design/workflow/schema.sql)을 바꾸지 않고 수신 순서의 일부를 확인했다.

## 실행과 관측

- 소스: 수신 순서 검사 기록, fixture 준비 기록, DDL 사본 기록.
- 원시 결과: output 기록, 환경/명령/종료 코드: metadata 기록, 파일 무결성: checksums 기록.
- Python 3.10.12, SQLite 3.37.2, WSL Linux의 메모리 DB. 6개 검사 통과, 종료 코드 0.
- 같은 합성 초기 작업에 후속 계획, 실패한 검사와 반영 시도, 재시도 선택, 후속 성공과 인계 준비를 넣었다. 대상에는 무관한 기존 작업을 두었다.

| 사례 | 관측 |
| --- | --- |
| 부모 계획을 전부 넣은 뒤 의무 작성 | 후속 참조로 고정된 이전 계획의 변경으로 거부. 예상한 거부를 확인한 PASS |
| 계획별 준비와 시도/관측의 순서 연결 | 원본 의미 값과 실패/성공 보존. 대상의 무관한 작업 유지, 외래 키 검사 정상, DELETE 보호 유지 |
| 수신 관계 저장 전/후 commit 직전 SQL 오류 | 명시적 ROLLBACK 후 대상의 논리 내용이 실행 전과 같음 |
| 같은 요청을 대상 진척 이후 다시 수신 | 기존 receipt 재사용, 현재 내용/진척 덮어쓰기 없음 |
| 같은 인계 ID의 다른 내용 | 거부하고 대상 보존 |
| receipt 없는 같은 작업 ID 충돌 | 수신 묶음 취소, 기존 대상 보존 |

## 한계

이 코드는 이 fixture의 행 순서를 확인하는 실험용 코드다. 실제 설치기, 일반 DB 병합기나 배포 수신기가 아니다. 임시 준비 상태는 같은 트랜잭션 안에서만 최종 상태로 바꾸며 명령을 실행하지 않았다. 원본의 revision은 전달 자료에 남기고 대상의 로컬 revision은 새로 만들므로 의미 비교에서 해당 로컬 번호만 제외했다.

시험 JSON과 수신/활성화 표식은 최소 가상 값이다. 실제 경로/파일 저장, payload 형식 검사, source acknowledgment, Windows 연결 종료/강제 종료/전원/디스크 내구성, 전체 복원 선택과 모든 기록 그래프는 시험하지 않았다. 실패 주입은 Python 예외와 명시적 ROLLBACK이며 프로세스 강제 종료가 아니다. DB 형식 변환, 백업/정리의 제품 구현, 모델/원격 호출과 토큰 효과도 범위 밖이다.

## 재현

이 폴더에서 `python3 -B source/handoff_order.py --schema source/schema.sql`로 메모리 시험만 실행한다. `checksums.sha256`은 보존 파일 내용의 일치를 확인하는 자료이며 시험의 충분성이나 제품 성공을 보증하지 않는다.
