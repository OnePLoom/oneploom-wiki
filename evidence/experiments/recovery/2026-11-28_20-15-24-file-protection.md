# Windows 파일 보호 읽기와 하드 링크의 한계

## 목적과 구현 범위

프로젝트별 WIKI 연결을 저장하기 전, 기존 파일의 원문과 경로를 대조할 기반을 확인했다. 코드의 `oneploom/files.py`는 기존 파일과 부모 경로의 핸들(운영체제가 열린 대상을 참조하는 값)을 유지하고 읽기 전용 스트림을 반환한다. 파일이 없으면 생성하지 않고, 파일 종류와 실제 경로가 다르면 진행하지 않는다. CLI의 연결 저장은 아직 이 함수를 호출하지 않는다.

이번 단위는 앞선 [SQLite 연결](2026-11-28_17-57-33-state-connection.md)과 별개인 파일 접근 경계다. DB의 COMMIT이 실제 파일의 반영을 함께 확정하지 않으므로 두 책임을 따로 검증한다. 최초 DB 생성, 계획과 확인 기록, 사전 사본, 파일 반영/복원은 아직이다.

## 파일별 책임

| 파일 또는 함수 | 역할 |
| --- | --- |
| `oneploom/files.py`의 `FileInformation` | Windows가 돌려주는 속성/링크 정보의 메모리 배치. 오래된 64비트 file index로 전체 파일 식별을 대신하지 않음 |
| `file_api` | Windows 함수의 인자/반환 형식을 지정해 핸들과 경로의 잘림 방지 |
| `open_existing` | 기존 파일만 열고 부재, 공유 충돌, 접근 거부와 나머지 Windows 오류를 구분 |
| `check_handle` | 열린 실제 대상의 종류, 재분석 지점, 기존 하드 링크와 전체 경로를 확인 |
| `close_handle` | 부모 핸들 반환 실패를 성공으로 숨기지 않음 |
| `protected_file` | 부모부터 보호한 뒤 파일을 읽기 전용으로 열고, 정상/예외 종료 때 스트림과 부모 핸들을 반환 |
| `tests/test_files.py` | Windows의 합성 파일과 별도 프로세스로 접근 경계와 반환, 미지원 조건 검사 |

이 함수는 같은 파일을 경로로 반복해서 여는 대신 열린 스트림으로 읽게 한다. 보호 중에 AI나 사용자 응답을 기다리지 않는다. 부모의 쓰기/삭제 공유 제한은 폴더 자체의 열기 조건이며, 모든 하위 파일의 편집을 막는 폴더 잠금이 아니다. 실제 옆 파일 쓰기가 가능함을 검사했다.

## 실제로 확인한 한계

배타적 파일 핸들을 유지한 동안 다른 프로세스의 하드 링크 생성이 성공했고, 열린 파일의 링크 수가 1에서 2로 바뀌었다. 하드 링크는 다른 이름으로 같은 파일 내용을 참조한다. 새 링크를 통한 쓰기는 보호 중 거부됐지만, 보호가 끝난 뒤 그 링크에 쓰면 원래 이름에서도 바뀐 내용을 읽었다.

따라서 “열 때 링크가 하나였고 배타적 핸들이 있으므로, 쓰기 영향도 그 경로 하나로 제한된다”는 주장은 사용할 수 없다. 준비 과정의 쓰기 옵션은 유지하지 않았고 현재 구현은 OS 핸들과 Python 스트림 모두 읽기 전용이다. 이 관측은 [E-032](../../issues.md#e-032--배타적-파일-접근-중에도-새-하드-링크-추가-가능)와 [반영 설계](../../../design/runtime/update.md#기존-파일과-새-파일)에 연결했다.

## 검증 환경과 결과

- Windows 11 `10.0.26300`, Python `3.13.9`, Git `2.52.0.windows.1`, Windows PowerShell `5.1.26100.10068`.
- 최종 실행: `py -3 -B -X utf8 -W error::DeprecationWarning tools/run_tests.py`.
- 전체 140개 통과, 실패 0, 건너뜀 0. 신규 파일 보호 21개를 포함하며 unittest 실행 시간은 9.821초다. 최적 성능이나 모든 Windows 환경의 결과를 뜻하지 않는다.
- [최종 전체 검사 원시 결과](2026-11-28_20-15-24-file-protection.log).

실제 파일/프로세스로 확인한 범위는 바이트/BOM/CRLF와 파일 식별 보존, 없는 파일/부모의 미생성, 하드 링크/정션 거부, 기존 읽기 핸들과 쓰기 가능한 메모리 매핑의 충돌, 다른 프로세스의 쓰기 거부, 파일 삭제/교체와 부모 이름 변경 차단, 옆 파일 편집, 비정상 자식 종료 뒤 접근 재개다. 연결 중 KeyboardInterrupt/SystemExit 전달, API 정보 실패, 잘린 경로 반환, 스트림 변환과 반환 오류의 일부는 주입 검사다.

첫 전체 137개 검사에서는 실제 다른 프로세스의 쓰기 차단은 성공했지만 테스트가 Python의 `winerror=32`를 기대해 한 항목이 실패했다. 해당 파일 API의 실제 예외는 `PermissionError`와 `errno=EACCES`, `winerror=None`였다. 실제 차단, 원문 보존과 반환 뒤 쓰기 성공을 그대로 검사하면서 오류 표현의 가정을 수정했다. 이후 139개 검사 통과, 최종 종류/열기 오류 검사를 포함한 140개 통과를 구분한다. 첫 실패를 제품의 파일 쓰기 성공이나 최종 결과에서 없었던 일로 바꾸지 않는다.

## 근거와 적용 경계

- [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)는 기존 파일 열기, 공유 모드와 핸들 수명을 정의하며 속성 접근이 공유 제한의 대상이 아님을 설명한다. 이 계약과 실제 관측을 함께 사용했다.
- [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)의 실제 경로와 버퍼 길이 계약을 사용한다. 실패/잘림 때 임의 추정 경로로 진행하지 않는다.
- [Python msvcrt](https://docs.python.org/3.13/library/msvcrt.html#msvcrt.open_osfhandle)와 [C 런타임의 핸들 소유 이전](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/open-osfhandle?view=msvc-170)에 따라 스트림이 소유한 핸들을 중복 종료하지 않는다. 상속하지 않는 descriptor를 사용한다.
- [CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw)는 파일의 새 하드 링크 생성을 제공한다. 그 API 존재만으로 배타적 핸들과의 조합을 단정하지 않고 별도 프로세스로 확인했다.

새 외부 패키지나 Windows/Python 실행 파일을 배포본에 복사하지 않았다. 표준 라이브러리와 설치된 Windows API를 호출하는 구현이며, 위 문서의 예제 코드를 가져오지 않았다. 참고한 문서의 이용 조건은 [Microsoft Learn](https://learn.microsoft.com/en-us/legal/termsofuse), [Python 라이선스](https://docs.python.org/3.13/license.html)에서 확인한다.

## 남은 범위

실제 쓰기 방식은 새 하드 링크/메타데이터 변경, 비교 후 교체 사이의 경합, 중단 시 원문 복원과 사전 기록을 함께 평가해야 한다. 반복 속성 검사만으로 경합을 해결했다고 판단하지 않는다. 기존 사용자 파일과 새 파일, DB 파일 자체의 준비도 같은 동작으로 합치지 않는다.

현재 보호 읽기를 실제 WIKI 연결 저장, DB 최초 생성/인계, AI 세션 또는 전원 장애의 검증으로 확대하지 않는다. 파일 시스템별 동작과 Obsidian/IDE의 실제 사용 불편, 대안의 시간 비교도 아직 미검증이다.
