# 유지 관리 이력의 행 순서 검사

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일: 2026-11-17. 당시 소스 기록, SQL 기록, 원시 출력 기록, 명령과 환경 기록, 체크섬 기록을 보존한다. 기존 source의 storage/maintenance helper도 함께 보존했다.

## 목적과 입력

최초 인계에 백업, 전환, 현재/해제된 보호, 정리 승인/확정/관측이 포함되면 기존 6개 행 순서 fixture만으로 충분하지 않다. 이번에는 **이미 준비된 기초 검사/적용 기록 위에 유지 관리 관계를 추가하는 순서**를 검사한다. 제품 수신기나 임의 입력의 의존 순서 계산기를 구현한 것이 아니다.

입력은 합성이다. 과거 완료와 이후 정리된 필수 로그, 현재 보호 자료, 해제된 보호, 전환 준비/관측, 정리 후 취소된 승인을 포함한다. 전환의 1→2 관측은 행 작성 순서를 위한 fixture이며 실제 DB 형식을 변경하지 않았다. 별도 metadata 3 입력은 과거 1→2 이력을 현재 정상 INSERT로 받을 때의 제한을 확인한다. 이 숫자는 공식 모듈/DB의 배포 버전이 아니다.

## 관측

7개 테스트가 통과했다. WSL Python 3.10.12, SQLite 3.37.2의 메모리 DB이며 실행 명령과 소요 시간은 metadata에 있다.

| 검사 | 관측 |
| --- | --- |
| 준비/관측 순서로 관계 재구성 | fixture의 최종 테이블 행, 현재 보호, 과거 완료 보존과 정리된 근거의 새 완료 제외 일치 |
| 수신 뒤 새 소비 | 정리된 artifact/backup의 새 보호 등록과 확정 관측 삭제 거부 |
| 해제된 보호를 최종 행 그대로 INSERT | 보호 등록을 생략한 수신 거부, 대상 전체 rollback |
| 후속 취소를 과거 claim보다 먼저 작성 | 당시 승인을 재현하지 못하는 순서 거부, 대상 전체 rollback |
| 백업/보호 뒤, 전환 관측 뒤, claim 뒤, commit 직전 오류 | 네 지점 모두 기존 대상 보존. 명시적 예외/rollback 시험이며 실제 프로세스 강제 종료가 아님 |
| 같은 형식의 Backup API | 모든 테이블 행과 스키마 정의 보존, 무결성/외래 키 검사 통과. 같은 DB 식별이 복사되며 인계 receipt는 생기지 않음 |
| 현재 형식과 다른 과거 전환 INSERT | 현재 metadata 3에서 과거 출발 형식 1의 정상 INSERT 거부. metadata를 옛 값으로 바꾸는 일반 UPDATE도 거부 |

마지막 거부는 예상 동작을 확인한 테스트 PASS다. **과거 전환 이력을 받는 일반 인계가 해결됐다는 뜻은 아니다.** 새 전환 보호와 과거 사실의 수신을 구분하는 경로가 필요하며 [수신 경계 — 「과거 형식 변경 기록의 수신 경계」](../../../design/workflow/storage.md)에 미해결로 남겼다. 보호 트리거, 외래 키나 원래 형식 값을 바꾸어 시험을 통과시키지 않았다.

## 범위와 한계

원본 SQL, storage/maintenance와 이전 인계 probe는 변경하지 않았다. 기존 29/29/6개 결과는 입력이 바뀌지 않아 재실행하지 않았다. 이번 fixture의 준비 순서와 같은 형식의 사본 확인을 모든 초기 이력, 전체 복원 선택, 임의 관계의 수신으로 확대하지 않는다.

실제 source/target 수신 확인과 활성화, 파일 복사/정리, DB 형식 변경, Windows 권한/잠금/내구성, 강제 종료, 모델/원격 호출과 토큰 비용은 시험하지 않았다. 전체 제품 인계/변환은 보완된 수신 경로와 지원 환경 검증이 남아 있다.
