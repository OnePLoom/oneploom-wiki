# 유지 관리 관계와 정리 후 소비 검사

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일: 2026-11-17. 디렉토리 이름은 실제 UTC 실행 시각이다. 초기 설계 DDL과 합성 입력을 검사했으며 제품 정리 도구를 실행한 기록이 아니다.

## 입력과 결과

| 구간 | 유지 관리 | 기존 저장 | 기존 인계 | 변경 이유 |
| --- | --- | --- | --- | --- |
| 첫 검사 | 22개 통과 | 29개 통과 | 6개 통과 | 백업/전환, 확인/보호/정리 확정/관측과 새 소비 차단의 첫 대응 |
| 최종 검사 | 29개 통과 | 29개 통과 | 6개 통과 | 자체 재대조 자료와 준비 후 정리, 복원 검사/완료, 전환 출발 형식과 보관 선택의 경계 보강 |

첫 입력과 출력을 덮지 않고 `final/`에 보강한 입력과 결과를 별도로 보존했다. SQL이 바뀌어 직접 의존하는 세 묶음을 다시 검사했으며 실패를 숨기기 위한 반복은 아니다. 각 명령과 종료 코드는 metadata.json에 있다.

- 첫 근거: 소스 기록, 유지 관리 출력 기록, 저장 출력 기록, 인계 출력 기록, 실행 메타데이터 기록.
- 최종 근거: DDL 기록, 유지 관리 검사 기록, 유지 관리 출력 기록, 저장 출력 기록, 인계 출력 기록, 메타데이터 기록.
- 체크섬 기록은 소스, 출력, 메타데이터와 이 설명의 바이트를 확인한다.

## 확인한 경계

1. 유지 관리 종류에 설치 단위나 검사 명령을 잘못 연결하지 않는다. 백업 등록과 전환 준비/검사/활성화 관측을 구별한다.
2. 목록 누락, 확인 해시 불일치, 취소된 확인과 다른 계획/시도의 근거를 거부한다. 확인한 목록과 과거 관측을 뒤늦게 바꾸거나 지우지 않는다.
3. 보호 등록 뒤 정리 확정, 정리 확정 뒤 새 보호의 두 SQL 순서를 검사했다. 한 연결에서 순서를 바꾼 검사이며 실제 다중 프로세스 경합 시험은 아니다.
4. 정리 확정만으로 삭제 완료로 보지 않는다. 일부 관측/실패는 유지하고 같은 확인과 새 시도로 나머지 관측을 연결한다. 파일이 없다는 관측과 실제 삭제 성공의 증명은 별개다.
5. 옛 PASS와 완료 행은 남지만 정리된 로그로 새 의무/완료를 만들거나, 정리한 사본으로 복원을 준비할 수 없다. 준비 뒤 정리된 사본으로도 새 복원 완료를 만들지 않는다.
6. 중간 SQL 거부가 앞선 문장까지 자동 취소하지 않음을 확인하고 명시적 ROLLBACK으로 미확정 정리 기록만 되돌렸다. 파일 삭제는 수행하지 않았다.

## 한계와 다음 연결

WSL Python 3.10.12, SQLite 3.37.2의 메모리 DB다. JSON, 시각과 파일은 관계 검사를 위한 가상 값이며 제품 의미/입력 검사를 통과한 자료가 아니다. 파일 사본 생성, 삭제, 원본/후보 전환, 강제 종료나 실제 Windows 저장/권한/프로세스는 시험하지 않았다. 모델, 원격 작업과 토큰 측정도 없다.

기존 인계 6개는 원래 fixture의 회귀 확인이다. 새 유지 관리 관계를 포함한 전달/형식 변환 전체가 성공한다는 근거가 아니다. SQL 제약은 신뢰할 수 없는 임의 DB 편집에 대한 보안 경계가 아니다.

현재 필요한 의존을 찾고 resource_holds를 등록/해제하는 공통 코드, 실제 경로/내용/승인의 재대조와 파일 효과는 후속이다. 보호 행이 없다고 삭제해도 된다고 판단해서는 안 된다. 실제 제품에서는 파일의 부재/변경/정리 사실과 지원 버전도 확인해야 한다.
