# 프로젝트별 WIKI 연결의 읽기 전용 확인

## 목적과 범위

2026-11-28, [WIKI 연결과 Codex 시작 작업](https://github.com/OnePLoom/oneploom/issues/8)의 첫 구현 범위를 확인했다. 앞선 발견 코드는 설치 위치와 설정 형식까지만 확인했다. 이번에는 읽은 설정을 다음 처리에 전달하고, 내부 또는 외부 WIKI와 위치표의 실제 경로를 확인한다. 연결을 저장하거나 Codex를 실행하는 단계는 포함하지 않는다.

계약의 원본은 [연결 설정의 필드와 읽기 규칙](../../../design/runtime/entry.md#연결-설정의-필드와-읽기-규칙)이다. 다음 소비자는 연결 변경과 호스트 실행이다. 첫 확인 결과는 현재 읽을 수 있는 경로이며 설치 소유, 위치표 본문의 유효성이나 Codex 접근 권한의 증명이 아니다.

## 구현과 책임

| 코드 위치 | 변경과 이유 |
| --- | --- |
| `oneploom/project.py` | `find_module`이 설치 경로와 읽은 공유/로컬 설정을 `Module`로 반환한다. 소비 단계가 같은 파일을 다시 파싱하지 않는다. 기존 실제 드라이브 검사를 `check_local_path`로 나눠 프로젝트와 WIKI가 같은 로컬 경로 기준을 사용한다. |
| `oneploom/connection.py` | `execution_settings`가 저장된 실행 선택의 필드/값 형식을 확인한다. `resolve_connection`은 공유 WIKI 방식에 따라 위치를 정하고 실제 폴더, 영역 안의 위치표 파일과 읽기 가능 여부를 확인해 `Connection`을 반환한다. |
| `oneploom/cli.py` | 발견 결과를 연결 검사로 전달한다. 둘 다 통과한 경우에만 확인한 `wiki_root`를 반환하되, 호스트 실행의 미구현 상태는 유지한다. |

예를 들어 프로젝트 기준 `wiki.path`가 `docs`라면 명령을 하위 폴더에서 실행해도 프로젝트 루트의 `docs`를 사용한다. `wiki.path`가 `null`이면 해당 작업 사본의 로컬 `wiki_path`를 사용한다. 등록이 없거나 내부/외부 설정이 함께 남으면 다른 폴더를 임의 선택하지 않는다. `wiki.map`은 선택한 WIKI를 기준으로 찾는다.

설정에 적힌 문자열뿐 아니라 실제 폴더 연결 대상도 검사한다. 내부 경로가 junction(다른 디렉토리를 가리키는 Windows 연결)으로 프로젝트 밖이나 루트 자체를 가리키면 거부한다. 위치표도 WIKI 밖으로 연결되면 거부한다. [Python의 경로 해결](https://docs.python.org/3.13/library/pathlib.html#pathlib.Path.resolve)과 [Windows의 드라이브 종류 조회](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew)를 사용하며, 네트워크 또는 종류를 확인하지 못한 드라이브를 로컬 경로로 취급하지 않는다.

`launch.args`와 `launch.context`의 형식이 맞아도 저장된 권한 선택을 실행해도 된다는 뜻은 아니다. 실제 옵션의 의미, 현재 조건과 해시의 일치, 호스트의 허용 여부는 후속 실행 단계에서 검증해야 한다. 기본값을 쓰는 내부 WIKI에 불필요한 로컬 설정 파일을 만들지 않는다.

## 검증과 결과

기준은 코드 main `8bc065a54f4f8a9e7917d0b063c7d5ff41a3d566` 이후 이 작업의 첫 변경 묶음이다. Windows 11, Python 3.13.9, Git 2.52.0.windows.1, Windows PowerShell 5.1.26100.10068에서 기존 CI와 같은 전체 검사 진입점을 실행했다.

```powershell
py -3 -B -X utf8 -W error::DeprecationWarning tools/run_tests.py
```

**96개 통과, 실패 0, 건너뜀 0, 테스트 실행 시간 8.439초**다. 기존 69개에 27개를 추가했고 기존 프로세스 검사도 WIKI 경로 확인과 실제 위치표 읽기 거부를 검사하도록 보완했다. 수치의 원문은 [실행 로그](2026-11-28_16-53-13-wiki-connect.log)에서 확인한다. 단일 실행 시간이며 성능 개선 비교나 Codex 시작 시간은 아니다.

| 검사 | 관측과 범위 |
| --- | --- |
| 내부/외부 연결 | 내부 상대 경로와 외부 절대 경로, 한글/공백/따옴표, 하위 폴더 실행, 기존 연결의 반복 소비를 확인했다. |
| 프로젝트 분리 | 같은 `project_id`를 가진 두 Git 작업 사본이 각각 다른 로컬 WIKI를 반환했다. 기존 다른 clone의 설정 복사 거부도 통과했다. |
| 잘못된 연결 | 미등록 외부 WIKI, 내부/외부 충돌, 없어진 폴더/위치표, 디렉토리와 파일 혼동을 구분했다. 자동 생성이나 다른 파일 선택은 하지 않았다. |
| 실제 경계 | 실제 Windows junction으로 내부 WIKI와 위치표의 영역 이탈을 검사했다. 드라이브의 네트워크/미확인 분기는 반환값을 주입한 단위 검사이며 실제 네트워크 드라이브 시험은 아니다. |
| 읽기 실패와 중단 | Windows 파일 핸들로 공유 설정과 위치표 읽기를 실제 거부했을 때 원문을 유지하고 오류를 반환했다. 인터럽트는 주입 검사로 취소 반환과 미수정 여부를 확인했다. |
| 저장 선택의 형식 | 실행 경로, 옵션 배열, 필수 필드와 소문자 64자리 비교 값의 형식을 확인했다. 잘못된 입력값을 오류 메시지에 복사하지 않았다. |
| 보존 | 성공/실패/재조회에서 설정과 문서의 바이트를 대조했다. 내부 기본값에 `.harness`를 새로 만들지 않았다. |

## 남은 검증과 다음 단계

현재 `start`와 `resume`은 경로를 확인해도 `runtime_not_implemented`, 종료 코드 5를 반환한다. 위치표 파일은 열 수 있는지까지만 확인하며 본문 구조를 판정하지 않는다. 제품 전체 설치나 준비 완료로 해석하지 않는다.

다음은 연결 변경의 계획/확인/안전한 저장이다. 원본이 검사 뒤 바뀌는 경우의 재확인, 중간 종료와 동시 편집은 실제 파일 반영 계약에 연결해야 한다. 이번 읽기 검사는 이후 저장 시점까지 원본이 그대로라는 보장을 하지 않는다.

그 뒤 현재 Codex 설치 형태별 실행, 권한 상속/선택 재사용, 새 대화/선택 재개와 실제 Windows 터미널에서의 WIKI 접근을 검증한다. 이번에는 Codex 또는 모델을 실행하지 않았다. 공식 npm/Windows 설치 두 형태의 제품 연결, 전체 설치/갱신/복구와 원격 CI 실행은 이번 결과에 포함하지 않는다.
