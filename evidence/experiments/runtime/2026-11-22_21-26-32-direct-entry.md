# 직접 접근 우선 채택과 개발 준비 인계

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일: **2026-11-22**. 사용자가 직접 접근 우선 진행에 동의해 첫 배포의 MCP 제공은 후속 검토로 전환했다. 기존 전용 시작 명령을 유지하며 [ADR 0022 — 「11월 22일 첫 제공 범위」](../../../decisions/runtime/0022-wiki-entry.md)에 반영했다. 사용자 원문과 범위는 decision.json 기록에 있다.

## 반영한 범위

결정 원본과 목록, 진입/설치/모듈 안내, 수용 기준과 진행표, 현재 평가/문제 대장과 개인 트러블슈팅 사례를 동기화했다. MCP 후보와 [직전 실제 비교](../wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)는 당시 추천/관측까지 보존하며 닫힌 기록을 다시 쓰지 않았다. 첫 제공의 직접 접근 선택은 실측/품질/지원 비용을 함께 고려한 판단이며 MCP 전체의 부적합을 증명한 결과는 아니다.

일반 Codex와 기존 충분한 권한, 열린 세션 안의 경로 등록/변경, 프로젝트별 WIKI 재사용과 사용자 전역 설정 비변경을 유지한다. 필수 WIKI 생성/보강/편집/검증/복구와 PR 연계의 범위를 줄이지 않았다. 첫 설치에 우리 MCP 등록/의존성/프로세스를 요구하지 않으며 기존 사용자 MCP를 제거하지 않는다.

## 원래 작업으로 복귀

[직접 접근의 저장 항목과 실행 판단](../../../design/runtime/entry.md)을 기존 경로/권한 재사용 요구에서 구체화했다. 저장 경로, 명시적 반복 선택, 관련 조건의 비교 근거와 이번 실행 결과를 분리한다. 경로 등록, 실행 준비와 실제 WIKI 사용은 서로의 성공을 대신하지 않는다. 정상 시작마다 DB/active를 추가하는 구조가 아니다.

[첫 실행기의 개발 준비 — 「직접 접근 실행기의 개발 준비」](../../../development/migration.md)에 이미 채택한 입력/소비자, 구현 전 선택, 구현하며 확인할 Windows 조건과 후속 지원을 대응했다. 제품명/고유 명령, 정확한 설치 경로/필드/결과 형식과 지원 설치 형태는 미확정이다. 명령 예시를 확정값으로 코드에 고정하거나 4단계 전체를 완료 처리하지 않는다.

## 확인과 한계

이번 작업은 채택 범위 반영과 설계 인계다. 새 제품 코드, Windows 실행, AI 요청, Git stage/commit/push와 원격 작업은 없다. 기존 구현/실측의 PASS를 새 제품 검증으로 재사용하지 않는다. 기존 후보 코드 검사의 참조/해시는 보존 검사에만 사용하며 재실행하지 않는다.

document-check.json 기록은 수정 문서의 형식/링크/제목, 변경 범위와 원본/시험 준비/닫힌 비교/Git 보존을 확인한다. review.json 기록은 채택 상태, 소유 위치, 첫 제공/후속의 경계와 미검증 보존에 대한 검토다. 검사 소스와 최종 해시는 check_documents.py 기록, SHA256SUMS 기록에 남긴다. 이 정적 검사로 사용자 제품 동작을 보장하지 않는다.

다음은 직접 접근 실행기의 정확한 저장/결과 형식과 지원 설치 범위를 확정하는 명세다. 필요한 새 선택에서만 사용자에게 확인하고 이후 기존 개발/Git 준비 순서로 이어간다.
