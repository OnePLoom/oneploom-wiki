# Windows Codex의 프로젝트별 설정 조회

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일: 2026-11-18. **프로젝트 A/B의 설정 선택은 확인했지만 모듈 미사용 C와 미등록 D에서 시작 오류가 재현됐다.** 현재 후보는 보완이 필요하다. 배포 모듈, 일반 TUI, 실제 WIKI 파일 접근을 통과한 결과가 아니다.

## 확인한 결과

마지막 대조는 Windows Codex **0.169.1**의 동일 실행 파일로 진행했다. 전후 실행 파일 SHA-256이 같고 모든 성공 응답의 버전도 일치한다. 아래는 `control/`의 10개 관측이다.

| 입력 | 관측 | 판정과 한계 |
| --- | --- | --- |
| 프로필/전역 기본값 없는 사용자 설정, 모듈 미사용 C | 조회 성공, 기본 권한 값 없음 | 비교 기준. 실제 기본 sandbox 동작은 실행하지 않음 |
| A/B 프로필만 추가, 전역 기본값 없는 C | 초기화 전 종료 1, `default_permissions` 누락 오류 | A/B용 등록이 C에 영향 없다는 후보 가정이 성립하지 않음 |
| Windows 네이티브 표기로 신뢰한 A, 전역 기본값 없음 | 프로젝트의 `probe-a` 선택 | 신뢰된 프로젝트 설정 로딩의 부분 확인 |
| 신뢰 키만 슬래시 표기로 바꾼 A | 초기화 전 종료 1, 기본값 누락 오류 | 같은 실행 파일의 입력 차이. 모든 Windows 경로/버전의 미지원으로 확대하지 않음 |
| 시험용 전역 기본값 `:read-only`, A→B→A | 각각 `probe-a` → `probe-b` → `probe-a` | 설정 선택 일치. 실제 허용 경계는 별도 확인 필요 |
| 같은 시험용 전역 기본값의 C | `:read-only` 조회 | 오류 회피 대조군. 원래 암묵적 기본 동작과 같다는 증거가 아니므로 자동 적용안으로 채택하지 않음 |
| 프로젝트 D는 `probe-d` 선택, 사용자 설정에 해당 프로필 없음 | 초기화 전 종료 1, 정의되지 않은 프로필 오류 | Codex 내부 skill만으로 최초 연결하도록 안내할 수 없는 조건 |
| A의 새 프로필과 기존 `sandbox_mode` 혼합 | 두 값 모두 조회 | 실제 적용 권한은 미검증. 조회 성공을 새 방식의 적용 성공으로 판단하지 않음 |

시작 실패는 보존한 `stderr.txt`의 설정 오류다. 요청 시간이 지나서 끊긴 timeout이 아니다. 모든 프로세스는 stdin 종료 후 반환했으며 강제 종료가 필요하지 않았다.

## 방법과 보호 범위

- 도구: Windows Python 3.13.9, Git, 설치된 `codex.cmd`. Python이 명시한 Windows 작업 경로에서 `codex app-server --stdio --strict-config`를 자식 실행했다. PowerShell/일반 Codex TUI 진입 자체를 재현한 것은 아니다.
- 입력: `<WORKSPACE_PATH>`의 빈 프로젝트 A/B/C/D와 한글/공백 이름의 시험 WIKI 둘. 프로젝트는 Git 초기화만 했고 remote/커밋은 없다. 기존 app/wiki/records와 실제 제품, 개인 WIKI는 입력으로 사용하지 않았다.
- 격리: 시험 자식의 `CODEX_HOME`만 별도로 지정했다. 실제 계정 인증과 기존 세션/DB를 복사하지 않았다. 환경 변수를 제한하고 업데이트 조회와 analytics를 비활성화했다. 호스트 관리 설정까지 가상화한 환경은 아니며 조회 응답의 설정 출처도 보존했다.
- 호출: `initialize`, `initialized`, `config/read`만 전송했다. 모델 turn, 로그인, MCP 요청, sandbox 명령, 설정 쓰기 RPC는 호출하지 않았다. 각 단계가 확인한 실제 사용자 config의 전후 해시는 같았다.
- 비용: 시험 클라이언트의 모델 요청은 0회다. 현재 설계 대화의 토큰이 0이라는 의미나 제품의 토큰 절감 실측으로 사용하지 않는다.
- 대기: 요청 응답에 짧은 제한 시간을 두지 않았다. 검사 완료/오류 후 자식 종료만 10초 기다리고 필요하면 그 시험 자식만 정리하도록 했으며 이번에는 그 분기가 실행되지 않았다.

합성 프로젝트의 신뢰 설정은 로딩을 확인하기 위한 입력이다. 실제 설치기가 신뢰를 임의로 추가해도 된다는 허가나 설계가 아니다. 관측 코드의 고정된 시험 경로/메타데이터도 배포 제품의 경로, 버전, 지원 조건으로 복사하지 않는다.

## 실행 이력과 자료

1. 실행 준비: WSL sandbox의 Windows interop가 `UtilBindVsockAnyPort ... socket failed 1`로 막혔다. 승인 뒤 버전/도움말을 확인했다. PowerShell 5.1.26100.9818, 정책 Restricted였으며 전역 정책은 변경하지 않았다. UNC cwd의 cmd 경고를 피하도록 시험에 Windows cwd를 지정했다.
2. 첫 조회 `first/`: 버전 조회 0.167.1, 7개 관측. 슬래시 신뢰 키의 프로젝트 설정이 로드되지 않았고 기본값 누락 오류가 났다. 기존 sandbox가 있는 경우의 stderr에서 신뢰 경로 안내를 확보했다. 당시 소스, 입력, 실패 결과를 보존했다.
3. 출처 대조 `layers/`: 네이티브 신뢰 키와 명시적 기본값을 비교한 8개 관측. A/B 선택, 하위 폴더의 A 선택과 미등록 D 오류를 확인했다. 응답 버전이 0.169.1로 달랐으므로 첫 조회와의 차이를 경로 표기 효과만으로 단정하지 않았다.
4. 동일 실행 파일 대조 `control/`: 0.169.1의 실행 파일 해시를 전후 비교하고 위 10개 조건을 실행했다. 이 결과가 현재 설정 제약 판단의 근거다. 버전 변경의 원인/시점은 확인하지 않았으며 시험 코드에서 패키지를 갱신하지 않았다.

첫 소스는 `first/probe.py`, 후속 helper는 `layers/probe.py`와 `control/probe.py`에 보존했다. 필요한 설정 값/출처, 요청, stderr, 종료 코드는 각 `result-*`에 있다. 입력 TOML도 보존했으며 임시 Codex 상태/캐시, 인증 자료는 가져오지 않았다. `check.py`와 `check.json`은 이 자료의 대응 검사이며 제품 성공률 검사가 아니다. `SHA256SUMS`는 보존 후 무결성 확인용이다.

WSL Python 3.10에서 시험 도구의 `--help` 확인 시 `tomllib` import 오류가 있었다. Windows/버전 확인 뒤에 import하도록 옮겨 같은 검사가 통과했다. `script-check.json`에 실패와 수정을 남겼다. 이는 Windows 실행과 별개이며 Python 3.11 요구는 해당 시험 코드의 요구다.

## 설계에 반영할 것

일반 Codex 사용, 프로젝트별 연결, 다른 프로젝트 보존이라는 사용자 요구는 유지한다. 전역 기본값이 없는 기기에 이름 있는 프로필을 등록하는 기존 후보는 그대로 적용하지 않는다. 전역 기본값을 임의로 채우거나 기존 sandbox를 지워 요구를 완화하지 않는다.

다음은 기존 전역 정책을 보존할 수 있는 등록 조건과 프로젝트의 로컬 설정 배치를 비교하고, 새 팀원의 최초 준비/설정 공유와 연결해 판단하는 것이다. 현재 사용자 config와 Git 제외 정책은 바꾸지 않는다. 그 조건을 정한 뒤 실제 TUI의 문서 읽기/쓰기, 재개, 변경/해제, 여러 작업 사본과 중단 복원을 검증한다. 모든 Codex 버전이나 모든 사용자 환경의 가능/불가능을 확정하지 않는다.
