# 끊긴 WIKI 연결의 대화 재개 확인

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일: 2026-11-20. 앞선 [서버 종료 시험](2026-11-20_20-16-32-mcp-reconnect-plan.md)의 `Transport closed` 뒤, 같은 시험 대화를 일반 명령으로 다시 열었다. 새 MCP 초기화와 옛 이어 읽기 정보의 거부를 확인한 뒤, **현재 사본의 1,197행, 72,577바이트 전체가 새 도구 응답으로 전달됐음을 대조했다.** 사용자 재개 뒤의 복구 결과이며 자동 재연결 성공은 아니다.

## 복구 방법을 고른 이유

현재 Windows 설치본은 0.171.0이다. 실제 MCP 도움말 기록과 [공식 CLI 안내](https://learn.chatgpt.com/docs/developer-commands?surface=cli), 같은 태그의 slash_dispatch 소스에서 `/mcp`는 상태/진단과 로그인만 제공한다. 특정 WIKI 서버 하나의 재시작 명령은 확인하지 못했다.

같은 버전의 내부 `mcp_server_refresh_response`는 서버나 대화 선택값을 받지 않고 `reload_mcp_config`로 여러 대화를 순회한다. 이를 한 WIKI만 복구하는 API로 사용하지 않는다. `/daemon` 재시작도 다른 대화에 영향을 줄 수 있어 이번 입력에서 제외했다. 상세 파일/해시와 근거는 조사 기록 기록에 있다. 외부 코드는 읽기만 했고 제품 구현에 복제하지 않았다.

지원되는 기존 대화 재개 기록을 먼저 확인한다. 화면을 닫고 다시 열어도 실행 상태를 재사용할 수 있으므로, 화면이 열렸다는 사실만으로 새 연결이나 읽기 성공을 가정하지 않는다. 관련 공식 소스의 idle unload 시험은 정적 참고이며 여기서 실행한 테스트가 아니다.

## 실제 재개 관측

사용자는 작업이 없는 Windows 시험 화면에서 `/quit`로 나온 뒤, 같은 프로젝트에서 `codex.cmd resume <SESSION_ID>`를 실행했다. 모델, 권한, 설정을 덮는 옵션이나 최초 AI 요청문은 넣지 않았다.

사용자 화면 기록에서 Codex 0.171.0, GPT-5.6-Sol low, 같은 프로젝트/UUID와 `wiki_reader connected` 두 도구를 확인했다. 계정 식별자는 기록하지 않았다. 주간 잔량 17%는 사용자 화면의 관측이며 요청별 차감량으로 계산하지 않는다.

호스트 기록 기록은 해당 UUID의 재개와 연결된 request 11 / connection 9에서 11:52:10 UTC에 WIKI MCP 초기화가 완료됐음을 확인했다. 서버 종료 뒤 새 초기화가 생겼다는 근거이며, 실제 문서 본문을 받았다는 근거는 아니다. 공유 Codex 서버나 다른 프로세스를 종료하지 않았다.

## 실제 읽기와 판정

실행안 기록과 읽기 요청문 기록에 따라 같은 대화에서 현재 모델로 사용자 요청 한 회를 실행했다. 앞선 연결 실패 요청과 구별해 새 turn `<SESSION_ID>`를 지정했다. 실제 입력 기록의 줄바꿈/공백 차이는 보존하고 의미가 같음을 확인했다. 기존 수집 함수와 실제 입력을 사용했으며 기록에 맞추려고 모델을 다시 실행하지 않았다.

1. 종료 전 첫 반환분의 next(이어 읽기에 사용할 입력)를 그대로 보냈고 `expired_cursor`, `complete=false`, 본문 없음이 반환됐다.
2. AI는 만료 이유를 알린 뒤 현재 연결에서 원래 경로로 다시 읽었다. 기존 반환분은 새 본문 검사의 입력으로 쓰지 않았다.
3. 새 응답 다섯 개의 바이트 범위는 0~15,333, 15,333~30,787, 30,787~46,198, 46,198~61,454, 61,454~72,577이었다. 끝 위치를 포함하지 않는 범위이며, 매 본문과 이어 읽기 입력을 독립 사본과 대조했다. 부분 행도 바이트 위치로 이어져 누락/중복은 0이었다.
4. 마지막 응답은 `eof`, `next=null`이었다. 첫 제목과 마지막 절 제목, 1~1,197행 전체 완료라는 최종 답변도 원문과 일치했다. shell, 설정 변경이나 다른 도구로 대체한 호출은 없었다.

원시 도구 출력은 수집 결과 기록, 독립 대조는 검사 코드 기록과 판정 기록에 보존했다. 실제 로그의 본문을 검사했으며 메타데이터나 최종 답변만으로 완료 처리하지 않았다. 최종 모델 요청 전체의 내부 전달이나 문서의 의미 해석 품질까지 증명한 것은 아니다.

사용자 요청 한 회에서 도구 호출 여섯 회와 내부 모델 응답 일곱 회, 50.706초가 관측됐다. 총 사용량 267,468토큰은 입력 265,442와 출력 2,026의 합이며, 캐시된 입력 243,072는 입력의 부분이다. 문맥과 재독 비용이 포함된 값으로 구독 차감량이나 직접 접근 대비 개선으로 해석하지 않는다. 사용자 결과 기록에 완료와 중간 만료 안내를 보존했다. 추가 승인창 유무는 보고되지 않았으므로 미확인이다.

## 보존과 한계

독립 시험 문서, 후보 네 파일과 연결 설정은 이전과 동일하다. 기존 시험 프로젝트 원문, 이전 근거와 Git/index를 변경하지 않는다. 백업은 2026-11-20 20:48:19 KST 생성 백업(식별자 `y80p1tfY`)이며 SHA-256을 확인했다. 모델을 사용하는 후속 실행은 화면의 연결 확인과 별도 단계다.

이번 관측은 현재 설치본의 한 실제 복구 사례다. 모든 Codex 버전에서 `/quit` 뒤 즉시 재개하면 항상 연결이 교체된다는 보장이 아니다. 이 경로를 사용자 복구 안내의 후보로 남기되, 명시적 지시가 없는 AI의 자율 복구나 전체 MCP 제공 결정으로 확대하지 않는다. 실행 중 취소/늦은 응답, 실제 잘림과 자유 탐색의 품질/비용은 후속 검증이다.

대기 시점의 검사 기록은 당시 Markdown 5개와 내부 링크/제목 416개, 기존 제목, 원문 86개, 앞선 근거 35개, 백업의 다른 파일 3,026개, 후보 네 파일과 설정 세 개, 제품 Git/index 보존을 확인했다. Obsidian의 lastOpenFiles 변경은 사용자 화면 상태로 보존했다. 결과 반영 뒤의 문서/보존 검사와 실제 본문 판정은 각각 별도로 유지한다.

최종 기록 검사 기록은 결과를 반영한 Markdown 5개와 링크/제목 422개, 같은 원문/설정/근거의 보존을 다시 확인했다. 이 보고서를 연결하는 링크 한 개는 보고서 생성 뒤 별도로 확인했다. 현재 단위의 기록/검사는 완료됐고 대기 중인 모델 요청이나 추가 중단은 없다.
