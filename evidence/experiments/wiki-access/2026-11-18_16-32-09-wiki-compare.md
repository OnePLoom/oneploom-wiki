# 실제 문서 사본의 직접 호출과 MCP 비교

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 2026-11-18 작업. 사용자가 비교 실행을 허용했고 원문을 절대 변경하지 말라고 확인했다. [사전 조사](2026-11-18_16-15-26-wiki-corpus.md) 뒤 같은 파일 처리 코드를 직접 호출하거나 MCP로 호출하는 부분 시험을 수행했다. **AI 호출 없이 결과 일치와 통신 시간을 확인했다. 실제 Codex의 답변 품질과 토큰 비교는 아직이다.**

## 입력과 보존

기존 시험 프로젝트의 추적 Markdown 86개를 보존 대상으로 잡고 60개, 391,937바이트를 새 Windows `wiki-corpus`에 일반 파일로 복사했다. `platform`, `contract`, `guides`, `followup`, `learn`의 26개는 사전에 정한 시험 입력 범위에서 제외했다. 전체 경로와 이유는 선별 목록 기록에 있다.

비밀값 패턴 사전 검색에서는 후보가 없었다. 이것은 민감정보나 저작권 검토 전체의 완료가 아니다. 이번 자료는 사용자 요청의 로컬 시험 사본이며 배포물, 공개 자료나 작성자의 기여 주장으로 사용하지 않는다. 모델에 전달할 문맥과 이용 범위는 실제 AI 비교 전에 별도로 검토한다.

원본을 이동하거나 링크, junction, hardlink로 연결하지 않았다. 준비 기록 기록과 최종 보존 대조 기록에서 원본 86개, 사본 60개, 기존 A/B 시험 파일 16개의 바이트 해시와 제품 Git HEAD/index/상태가 그대로임을 확인했다. 원본의 OS 접근 시간까지 불변이라는 뜻은 아니다. 새 시험에는 Codex 설정을 등록하지 않았고 기존 A/B 서버, 전역 설정과 개인 시작 도구를 바꾸지 않았다.

참조 목록 검사 기록은 사본의 인라인 Markdown 링크에서 외부 참조 124개를 관측했다. 외부 자료를 가져오거나 링크를 수정하지 않았다. 코드 블록, 제목 앵커, 다른 링크 문법의 완전한 검사가 아니며 이번 검색/읽기는 선택한 파일 내용에 한정된다.

## 무엇을 바꿨나

기존 시험 도구는 64 KiB를 넘는 파일을 통째로 거부했다. REQUIREMENTS를 비교에서 빼지 않도록 읽기는 줄 범위와 `next_line`, 검색은 결과 위치와 `next_offset`을 반환하게 보완했다. 다음 위치가 남으면 추가 요청으로 이어 받는다. 읽기와 검색은 같은 `wiki.py`를 사용하며 MCP는 이 기능을 호출하는 통신 경로다.

한 번 반환하는 본문/검색 문장 합계는 64 KiB로 제한한다. 경로와 JSON 필드를 포함한 통신 전체 크기의 제한은 아니다. 검색은 페이지마다 60개 파일을 다시 순회한다. 100개 파일 한도, 한 줄 64 KiB 초과 거부는 남아 있다. 별도 색인, 페이지 사이의 변경 버전 고정이나 쓰기 보호를 구현한 제품이 아니다.

## 실행과 판정

- Windows Python 3.13.9, 기존 격리 환경의 공식 MCP SDK 2.3.0을 사용했다. 새 라이브러리를 추가하지 않았다. SDK 이용 조건은 [선행 시험의 확인 기록](2026-11-18_15-21-34-mcp-read.md)에 연결한다.
- 파일 처리 검사 기록: 13개 통과. 긴 한글/CRLF 문서의 전체 바이트 재구성, 검색 끝부분, 결과 나눠 받기, 범위/인코딩/연결 오류와 정적인 junction 거부를 확인했다.
- 측정 원본 기록: 읽기 3종과 검색 4종을 경로별 10번씩, 총 140번 실행했다. 같은 Windows 사본과 동일 처리 코드의 반환값이 모두 일치했다. 각 반복에서 사례 순서를 돌리고 직접/MCP 호출 순서를 교차했다.
- REQUIREMENTS 72,422바이트/1,191줄을 MCP로 6번 이어 읽어 원문 바이트와 정확히 대조했다. `검증`의 166개 일치 결과를 2번에 나눠 받아 별도 전체 사본 검색 결과와 대조했다. 범위 밖/절대/숨김 경로 3개는 MCP 오류로 거부됐다.
- STDIO 연결을 3회 열고 정상 문맥 종료했다. 협상한 프로토콜은 `2025-11-25`다. 이 결과는 실제 Codex의 프로토콜/연결이나 강제 종료 뒤 프로세스 정리 검사가 아니다.

범위 거부 시험에서 SDK는 예상한 ValueError를 일반 도구 오류로 반환하고 stderr에 traceback을 남겼다. 콘솔 수집본 기록은 도구 출력 한도 때문에 일부 잘렸으며 측정 JSON은 온전히 보존했다. 거부 성공을 사용자용 오류 안내 품질의 완료로 취급하지 않는다. 해당 로그를 얻으려고 통과한 성능 검사를 반복하지 않았다.

## 시간 결과

각 칸은 10회 표본의 중앙값이며 단위는 밀리초다. 전체 표본과 최솟값/최댓값은 측정 JSON에 있다.

| 작업 | 직접 함수 호출 | MCP 호출 |
| --- | ---: | ---: |
| 짧은 문서 읽기 | 0.423 | 1.673 |
| 긴 문서 첫 구간 | 0.474 | 1.687 |
| 긴 문서 마지막 구간 | 0.801 | 1.795 |
| `UNCLASSIFIED` 검색 | 26.500 | 27.085 |
| `검증` 첫 결과 | 26.061 | 27.466 |
| `검증` 다음 결과 | 26.338 | 27.066 |
| 없는 문자열 검색 | 25.908 | 26.761 |

서버 시작부터 SDK 연결 완료까지는 3회에 0.704~0.793초였다. 도구 목록 조회 이전까지의 시간이며 매 파일 요청마다 다시 시작한 것이 아니다. 초기 정확성 검사 뒤 같은 사본을 반복 읽었으므로 캐시가 준비된 조건이다. 새 프로세스 시작을 디스크 캐시가 없는 상태로 해석하지 않는다.

이 표본에서 MCP의 추가 호출 시간은 중앙값 차이 약 0.6~1.4밀리초였다. **이는 직접 함수 호출과 SDK 통신의 차이다.** 실제 Codex의 shell 시작, 도구 탐색, 모델 추론, 재시도와 승인 시간은 포함하지 않았다. 반환 JSON 바이트 수도 과금 토큰 수가 아니다. 수십 개 문서와 작은 표본만으로 대규모 성능, 사용자 체감이나 MCP 채택의 우위를 확정하지 않는다.

## 재현 자료와 다음 순서

실행 소스 기록, 읽기 구현 기록, 서버 기록, 테스트 기록, 사본 준비 기록을 보존했다. 현재 Windows 시험 배치는 `lab/mcp-20261118/project-corpus`, `wiki-corpus`, `checks/corpus`다. 준비기는 기존 대상이 있으면 덮지 않는다. 소스와 실제 실행 사본의 대응, 체크섬은 각각 보존 기록과 체크섬 목록 기록에 있다.

다음은 같은 버전/모델/질문으로 실제 Codex의 직접 파일 접근과 MCP를 비교하는 단위다. 현재 후보의 읽기/검색을 실제 호스트에서 확인하고, 원문에 근거한 정답과 누락부터 판단한 뒤 시간/전체 토큰을 비교한다. 이전 답을 새 시험 문맥에 주지 않는다. 사용자의 Codex 갱신 여부와 이전 패키지/세션 버전 표기 차이도 실행 전 대조한다. 수정/충돌/복구와 제품 채택은 이 결과로 완료 처리하지 않는다.
