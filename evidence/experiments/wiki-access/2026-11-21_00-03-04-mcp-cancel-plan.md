# 실제 화면에서 읽기 중단과 후속 사용 확인

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일은 2026-11-20이다. 시스템 날짜가 한국 시간으로 11/21이 되어도 사용자가 지정한 작업일을 임의로 바꾸지 않는다. 앞선 [사용자 재개 후 읽기](2026-11-20_20-51-32-mcp-reopen-plan.md)에 이어, **첫 페이지 반환 후 사용자가 읽기를 중단하고 같은 대화에서 새 구간을 정상적으로 읽은 것을 확인했다.** MCP가 파일을 처리하던 도중의 취소와 실제 늦은 응답은 이번 표본에서 관측하지 못했다.

## 목적과 실제 흐름

사용자가 WIKI 읽기를 중단한 뒤 다른 구간을 읽을 때, 앞선 작업을 계속하거나 뒤늦은 결과를 새 요청의 성공으로 사용하지 않는지 확인한다. 같은 Windows 시험 대화와 후보, 문서, 설정을 유지한다. 새 서버, 시험용 지연, 반복 복사한 큰 문서나 작은 출력 상한을 추가하지 않는다.

1. 현재 모델에서 전체 읽기 요청 기록을 한 번 실행한다. 실제 도구가 원문을 다시 읽게 하며 이전 대화의 내용으로 대신하지 않는다.
2. 사용자가 아직 작업 중인 화면의 중단 키를 한 번 누르고 같은 대화를 열어 둔다. 화면에 표시된 키를 따르며, 설정이나 실행 환경을 바꿔 특정 키를 강제하지 않는다.
3. 중단 관측을 확인한 뒤 독립 구간 읽기 기록을 한 번 실행한다. 1018~1035행의 원문과 진행 정보를 독립 기대값에 대조한다.

사용자 AI 요청은 최대 두 회이며 내부 모델 응답 횟수는 실제 기록으로 센다. 첫 요청이 이미 완료된 뒤 키를 눌렀다면 취소 성공으로 처리하지 않고, 원하는 시점이 나올 때까지 반복하지 않는다. 실제 범위와 입력은 실행안 기록, 대조할 18행/1,328바이트는 독립 기대값 기록에 있다. 기대값은 시험 모델에 전달하지 않는다.

## 취소 위치와 판정

화면에서 중단됐다는 사실만으로 MCP가 읽던 파일의 처리가 멈췄다고 보장하지 않는다. 작은 원문은 도구 처리가 빨리 끝나므로 중단 시점에 따라 아래 범위를 구별한다.

| 실제로 확인한 시점 | 판단할 수 있는 범위 |
| --- | --- |
| 첫 파일 호출 전 | AI 작업 중단. 파일 읽기 취소는 미실행 |
| 한 페이지 반환 후 다음 호출 전 | 여러 단계 읽기의 중단과 후속 사용. 개별 MCP 실행 중 취소는 미실행 |
| 코드 실행 도구가 진행 중 | 바깥 도구 요청의 중단. 내부 MCP 요청이 전달됐는지는 별도 근거 필요 |
| MCP 요청이 실제 진행 중임을 관측 | 해당 요청의 취소 전달, 종료와 후속 요청을 대조. 화면 표시만으로 판정하지 않음 |
| 도구가 먼저 완료됨 | 완료/취소의 시점 경합. 실행 중 취소 성공으로 표시하지 않음 |

실제 turn ID(요청 회차 식별자), call ID(도구 호출 식별자), 도구 반환과 `turn_aborted`를 대조한다. 중단 뒤 새 구간은 새 호출의 응답으로만 판정하며 앞선 본문을 합치지 않는다. 늦은 응답이 실제로 나타나지 않으면 “늦은 응답을 버리는 상황을 재현했다”고 기록하지 않는다. 관측할 수 없는 MCP 내부 경계나 정리는 미확인으로 남긴다.

## 실제 중단과 후속 읽기

사용자는 첫 `read_note` 표시와 반환값을 본 직후 중단했고 화면에 `Conversation interrupted`가 나왔다고 보고했다. 수집 기록 기록과 첫 판정 기록을 대조하면 도구 반환은 15:06:51.586 UTC, 요청 중단은 15:06:53.552 UTC였다. 첫 페이지가 돌아온 1.966초 뒤, 다음 파일 호출 전에 멈춘 상황이다. 전체 요청의 완료 기록은 없었다.

첫 페이지의 15,333바이트는 현재 사본과 일치했다. 1~340행 전체와 341행의 95바이트 중 앞 51바이트이며, `output_limit`과 이어 읽기 정보가 남았다. 전체 문서를 읽었다고 판정하지 않는다. 화면의 중단만으로 내부 MCP 취소 알림이나 작업자 종료를 확인한 것도 아니다.

후속 요청에는 1018~1035행만 새로 읽도록 지시했다. 사용자는 요청문을 덜 붙였다고 우려했지만, 실제 입력 기록에는 준비한 지시가 모두 있었고 로그에는 이미 완료된 실행이 있었다. 줄바꿈 차이를 확인한 뒤 재요청 없이 그 결과를 사용했다.

| 대조 항목 | 실제 결과 |
| --- | --- |
| 새 요청과 도구 호출 | 같은 대화의 새 turn/call ID, 파일명과 시작/끝 행을 명시. 옛 cursor를 사용하지 않음 |
| 도구가 반환한 원문 | 1018~1035행, 바이트 54,871~56,199의 1,328바이트가 독립 원문과 일치 |
| 사용자가 받은 답변 | 답변의 Markdown 인용도 같은 1,328바이트와 일치. `range_end`, 이어 읽기 없음, 오류 없음으로 안내 |
| 앞선 작업과의 분리 | 전체 읽기의 추가 호출이나 중단된 call ID의 뒤늦은 출력은 수집 구간에서 발견되지 않음 |
| 승인창 | 두 요청 모두 별도 보고가 없어 미확인. 로그의 `on-request` 정책을 승인창 없음의 증거로 쓰지 않음 |

후속 수집 기록과 원문 대조 기록은 **중단 후 독립 구간 읽기의 부분 통과**다. 실제 늦은 응답이 없었으므로 그것을 버리는 상황까지 재현했다고 판정하지 않는다. 최종 모델 입력 전체나 문서 의미 이해의 정확성도 별도 검증 대상이다.

사용자 요청은 예정한 두 회, 내부 모델 응답은 세 회였다. 사용량 기록의 총 164,141토큰에는 캐시 입력 121,600이 포함된다. 같은 대화 이력과 요청 중단을 포함한 관측이며 구독 차감량이나 직접 접근 대비 비용으로 해석하지 않는다. 첫 요청은 중단까지 6.814초, 후속 요청은 완료까지 14.978초였다.

첫 수집은 사용자 메시지가 하나라고 가정해 중단됐다. 실제 회차에는 호스트 환경 안내와 중단 통지도 사용자 역할로 기록돼 있었다. 수집 실패와 보정 기록에 원인을 남기고 실제 준비문과 일치하는 입력 하나를 선택해 기존 수집기에 전달했다. 모델이나 시험을 다시 실행하지 않았고 선행 검사도 반복하지 않았다.

## 기존 근거와 선택 이유

현재 후보의 `server.py`는 AnyIO 작업 스레드에서 파일 처리를 수행하고 `files.py`는 버퍼/파일 경계에서 취소를 확인한다. 앞선 SDK 검사는 32MiB 합성 입력과 관측용 실행기를 써서 작업자 종료와 다른 요청의 보존을 확인했다. 이 부분 근거를 실제 Codex 화면의 결과로 바꾸지 않는다.

[MCP 취소 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation)은 특정 요청을 대상으로 취소를 보내며, 완료와 취소가 경합할 수 있고 취소 후 늦은 응답을 무시하도록 권고한다. 반드시 오류 응답이 돌아오는 구조는 아니다. 현재 Codex의 `request_cancellation.rs`에는 대기 중 호출이 취소되면 해당 요청의 취소 알림을 보내는 경로가 있다. 정적 소스 확인은 실제 이번 요청의 취소 전달을 증명하지 않는다.

현재 설치본의 공식 소스와 관련 문서는 조사 기록 기록에 연결했다. Codex는 관측한 0.171.0이며 버전을 고정하지 않는다. 공식 소스는 읽기만 했고 제품이나 이번 근거에 복제하지 않았다. 기존 Apache-2.0 확인을 재사용한다.

별도 관측 실행기나 대량 합성 자료는 내부 경계를 진단하는 데 도움이 될 수 있지만, 정상 사용자 환경과 구별해야 한다. 우선 현재 실행 방식의 실제 사용 관측을 한 번 준비하고, 부족한 내부 경계는 기존 SDK 근거와 구분해 후속 판단한다. 모든 취소 문제를 이 두 요청만으로 닫는 계획은 아니다.

## 보호 범위와 다음 순서

기존 시험 프로젝트 원문, 기존 시험 사본, 후보 네 파일과 사용자 설정을 보존한다. 프로세스를 종료하거나 공용 Codex 서버를 재시작하지 않는다. 이전 실패와 재개 근거를 수정하지 않으며 백업은 2026-11-21 00:01:32 KST 생성 백업(식별자 `IzbhzoRq`)다.

준비 검사 기록에서 문서 4개와 내부 링크/제목 352개, 원문 86개, 직전 근거 19개와 백업의 다른 파일 3,047개, 후보 네 파일/설정 세 개와 제품 Git/index 보존을 확인했다. 후속 읽기의 18행/1,328바이트 기대값도 독립 원문에 일치했다. Obsidian lastOpenFiles는 사용자 화면 상태로 보존했다. 보고서 생성 뒤 이 검사 링크 한 개를 추가로 확인했다.

두 요청은 완료됐으며 다시 실행하지 않는다. 이번에 관측하지 못한 내부 취소와 늦은 응답은 기존 SDK 근거와 구분해 남긴다. 관련 설계와 진행표를 맞춘 뒤 실제 호스트의 잘림/미확인과 환경 변경에서 남은 확인 범위를 정리하고, 자유 탐색 품질/비용과 첫 MCP 제공 판단으로 돌아간다.

최종 문서/보존 검사 기록은 통과했다. Markdown 5개와 내부 링크/제목 360개, 원문 86개, 후보 네 파일과 설정 세 개, 직전 근거 19개, 백업의 다른 파일 3,048개와 제품 Git/index를 대조했다. 기존 제목을 보존했고 Obsidian의 최근 열기 목록만 사용자 화면 상태로 구분해 유지했다. 이 결과를 추가한 뒤 새 보고서 링크도 확인했으며 현재 근거의 체크섬은 `SHA256SUMS`에 둔다.
