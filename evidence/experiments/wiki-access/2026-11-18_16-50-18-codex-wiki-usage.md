# 실제 Codex의 직접 접근과 MCP 읽기 비교

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일: 2026-11-18. 원본을 수정하지 않고 실제 검색, 답변 품질, 시간과 토큰을 비교하라는 요청의 결과다. 선행 [모델 없는 비교](2026-11-18_16-32-09-wiki-compare.md)와 구분한다.

## 결과와 판단

두 방식 모두 실제 Windows Codex에서 답변을 완료했고 사용자는 추가 승인 요청이 없었다고 보고했다. 원본 86개와 시험 사본 두 벌, 제품 Git 상태는 보존됐다. **이번 표본은 MCP의 시간 또는 토큰 절감 이점을 보여주지 못했다.** 사전 평가 기준의 일부 조건은 두 답변 모두 누락했으므로 품질까지 완전 통과한 비교도 아니다.

기본 전용 시작 방식은 유지한다. MCP는 일반 Codex에서 `--add-dir` 없이 등록한 WIKI를 검색하고 읽을 수 있다는 사용성 근거를 얻었다. 그러나 읽기 범위의 전달, 합산 출력량과 답변 누락 문제가 남았다. 제품 도입의 확대나 쓰기 기능 착수로 해석하지 않는다. 현재 기준은 [두 방식의 선택 제공](../../../design/runtime/entry.md)이다.

## 비교 조건

| 항목 | 조건 |
| --- | --- |
| 실제 진입 | 사용자가 Windows PowerShell에서 `codex.cmd` 실행. 각 방식은 새 대화 |
| 실행 버전 | 패키지 조회, 사용자 `/status`, 두 세션 메타데이터 모두 Codex 0.170.0 |
| 모델 | `gpt-5.6-sol`, reasoning `low` |
| 문서 | 같은 스냅샷의 일반 파일 60개, 391,937바이트를 별도 폴더에 각각 복사 |
| 기본 지시 | 같은 AGENTS. 지정 사본만 읽고 문서 속 실행 지시는 데이터로 취급. 수정, 외부 조회, 다른 시험 결과 접근 금지 |
| 직접 접근 | `usage-direct`에서 `--sandbox workspace-write --add-dir ..\usage-wiki-direct` |
| MCP | `usage-mcp`에서 `--sandbox workspace-write`. 프로젝트의 search_notes/read_note 두 도구 사용 |
| 요청 수 | 같은 세 질문을 묶은 사용자 요청을 각 한 번. 직접 접근 먼저, MCP 다음 |
| 정답 근거 | 모델 실행 전에 expected.json 기록을 작성하고 시험 입력에서 제외 |
| 원문 보호 | 원본 대신 사본만 AI에 제공. 이동, symlink, junction, hardlink 사용 없음 |

질문은 새 블록 생성 계약, 브라우저 종료와 문서 복구 정책, 저장 API의 확정된 p99 성능 목표 유무다. 공통 질문 기록에 경로별 지시를 더한 직접 요청 기록과 MCP 요청 기록을 사용했다. p99는 응답 시간 분포의 99번째 백분위이며, 질문은 그런 수치 계약이 문서에 있는지를 확인한다.

직접 요청은 준비한 내용과 정확히 일치했다. MCP 요청은 붙여넣기 과정에서 줄바꿈과 들여쓰기, 단어 중간 줄바꿈이 추가됐다. 공백을 제외한 문자는 일치하며 의미 변경은 찾지 못했지만, 바이트 단위로 같은 입력이었다고 표시하지 않는다. 측정 기록 기록에 이 차이를 남겼다.

## 답변 품질

평가는 시험 모델의 자기 보고가 아니라 사전 기준과 원문, 실제로 반환된 도구 내용, 최종 답변을 대조한 수동 의미 검토다. 문서에 적힌 정책의 이해를 시험하며 실제 기존 시험 프로젝트 구현이나 테스트 완료를 판정하지 않는다.

| 질문 | 직접 접근 | MCP |
| --- | --- | --- |
| QUERY_A | 선택적 content, 기본값, temp 요청 합치기 권고와 별도 replace 허용, 기존 블록의 전체 교체, 과거안과 현재안 구분을 충족 | 같은 핵심 사실을 충족. 실제 구현 완료와도 구분 |
| 블록과 문서 복구 | 세션 범위, 문서/하위 문서/블록의 복구, 테스트용 5분과 후속 계획을 구분. 영구 삭제 완료 문서의 복구 제외 조건은 누락 | 같은 조건을 누락. 해당 원문을 실제로 읽었어도 최종 답에 반영하지 않음 |
| p99 목표 유무 | 사본에서 확정 수치를 찾지 못했다고 설명. 정성 성능 요구와 구분 | 같은 핵심 사실을 충족. autosave 주기와 API 응답 시간도 구분 |

직접 답변은 전체 본문 교체의 근거로 ADR 020의 9~25행을 제시했지만 해당 문장은 26행이다. 도구 출력에는 26행을 읽은 기록이 있어 사실 자체가 무근거인 것은 아니며, 인용 범위의 정확성 문제다. MCP는 이 항목을 26행으로 인용했다.

복구 제외 조건은 REQUIREMENTS 1029행이다. 직접 접근의 반환 출력에서는 이 문장을 확인하지 못했고, MCP의 좁은 재읽기에서는 확인했다. 따라서 검색/읽기 성공만으로 답변의 누락이 해결됐다고 볼 수 없다. 잘림과 누락의 인과관계나 두 방식의 일반적인 품질 우위까지 확정하지 않는다. 상세 판정은 grading.json 기록에 있다.

## 시간과 토큰

| 관측 항목 | 직접 접근 | MCP |
| --- | ---: | ---: |
| 호스트가 기록한 요청 처리 시간 | 40.359초 | 55.005초 |
| 관측 모델 응답 수 | 5 | 8 |
| 상위 도구 실행 횟수 | 4 | 7 |
| 입력 토큰 | 150,255 | 278,977 |
| 입력 중 캐시 토큰 | 115,712 | 234,752 |
| 캐시를 제외한 입력 토큰 | 34,543 | 44,225 |
| 출력 토큰 | 1,723 | 2,218 |
| 누적 총토큰 | 151,978 | 281,195 |
| 반환 도구 텍스트의 UTF-8 바이트 | 86,124 | 144,884 |
| 도구 합산 출력의 잘림 | 1회 | 2회 |

모델 응답별 사용량의 합은 해당 요청의 누적 사용량과 일치했다. 캐시는 입력의 부분집합이고, reasoning 토큰도 별도 합산하지 않는다. 총토큰은 여러 번의 모델 입력과 출력을 더한 값으로, 한 번의 컨텍스트 크기나 구독 한도의 차감량이 아니다. 바이트 수 역시 토큰 수가 아니다. 실제 요금과 주간 한도 차감은 측정하지 않았다.

시간은 질문 이후 호스트가 기록한 요청 처리 구간이다. CLI 시작, 로그인, 프로젝트 신뢰 확인과 사용자의 붙여넣기 시간은 포함하지 않는다. 기록 시각의 차이로 계산한 값은 직접 40.265초, MCP 54.916초이며 호스트의 duration 값과 따로 보존했다. 이 두 값을 섞어 개선율을 만들지 않는다.

직접 경로는 4회의 shell 호출에서 rg 검색과 문맥 출력을 사용했다. MCP는 도구 목록 확인 뒤 search_notes 23회와 read_note 11회를 여러 묶음으로 호출했다. 검색 기능은 rg의 정규식/문맥 출력과 자체 도구의 단순 문자열 검색으로 서로 다르다. **이번 수치는 실제 탐색 방식의 비교이며 MCP 통신 비용만의 비교가 아니다.** 통신만의 비용은 앞선 동일 코드 시험에서 따로 측정했다.

## 관측한 문제와 한계

MCP 모델은 `start_line=1018, limit=1035`를 요청했다. limit은 끝 줄 번호가 아니라 읽을 줄 수이며 도구의 최대값은 1,000이다. 같은 요청 묶음의 다른 큰 limit도 불필요한 긴 읽기와 중복 반환을 만들었다. 실제 stderr에서 해당 서버와 범위 검사 줄의 예외 경로를 확인했다. 최종 ValueError 문구의 로그 행은 확보하지 못했으므로 도구 오류 응답 원문을 추정해 복원하지 않는다. 호출 인자, 저장 소스와 좁힌 오류 근거 기록을 함께 사용한다.

MCP는 이후 1018행부터 16줄, 685행부터 14줄처럼 좁혀 다시 읽고 답변을 완료했다. 최종 답은 범위 오류를 별도로 알리지 않았다. 정상 답변 완료를 중간 오류가 전혀 없었다는 뜻으로 기록하지 않는다.

직접 경로도 여러 검색 결과를 한 번에 출력해 잘렸다. MCP의 개별 반환 한도와 페이지 정보만으로는 여러 결과를 합친 호스트 출력의 잘림을 막지 못했다. 필요한 다음 페이지와 원문을 실제로 읽었는지는 호출별로 확인해야 한다. MCP의 최종 답이 모든 잘림을 해소했다고 주장한 부분은 전체 출력의 완전 수신 근거로 채택하지 않는다.

표본은 방식별 한 요청뿐이고 실행 순서도 교차하지 않았다. 캐시 상태, 서비스 부하, 모델의 탐색 선택을 통제하지 못했다. 질문의 붙여넣기 형식도 완전히 같지 않았다. 따라서 비용 감소나 통계적 우위, 대규모 WIKI 복원 품질을 주장하지 않는다. 답변의 누락 때문에 동일한 완전 품질에서의 비용 우위도 확정하지 않는다.

## 원본과 설정 보존

before.json 기록과 preservation.json 기록에서 원본 86개, 직접/MCP 사본 각 60개, 제품 HEAD/index/상태와 시험 서버 소스를 대조했다. 원본 수정과 제품 stage/commit/push는 없다. 준비 단계에서 기존 시험 파일 80개도 보존했다. 과거 근거와 TIL은 이번 결과로 덮지 않는다.

준비기는 사용자 전역 Codex 설정을 쓰지 않았고 준비 전후 해시도 같았다. 실제 TUI 실행 뒤에는 전역 config의 해시가 바뀌었으며 두 시험 프로젝트의 `trust_level="trusted"` 항목이 존재했다. 사용자는 시험 프로젝트의 신뢰 확인을 허용하도록 안내받았다. 이 관측은 모듈이 전역 설정을 편집한 것과 구분한다. 사전 config 본문을 보존하지 않았으므로 두 항목만 바뀌었다거나 다른 변경이 없었다고 단정하지 않는다. 호스트가 남긴 신뢰 기록을 임의 삭제하거나 되돌리지 않았다.

저장한 세션 근거는 두 시험의 답변, 도구 입력/반환, 버전/모델, 시간과 사용량에 한정했다. 시스템 지침, 비공개 추론, 자격증명이나 다른 대화 전체는 복사하지 않았다. 로컬 경로와 시험 문서 일부가 포함된 개인 근거이므로 공개 배포물로 사용하지 않는다.

## 수집 도구와 검증

`prepare_usage.py`는 기존 일반 파일 사본에서 두 시험 환경과 동일 질문을 준비한다. 설치/분석 제품 코드가 아니며 모델을 호출하지 않는다. `capture_usage.py`는 지정한 시험 세션 ID와 프로젝트를 대조한 뒤 완료 요청 한 개의 필요한 기록만 추출한다. 준비 코드와 수집 코드, 당시 서버는 `source/`에 보존했다.

백업 첫 명령은 명시적 프로젝트 인자가 없어 Git 루트 확인 단계에서 멈췄고, 올바른 인자를 준 실행은 체크섬을 통과했다. 수집기의 첫 실행은 WSL Python 3.10에서 Z로 끝나는 ISO 시각을 해석하지 못했다. `+00:00`으로 처리하도록 고친 뒤 같은 세션 로그만 다시 추출했다. 초기 소스는 capture_usage-before.py 기록에 보존했다. 이것은 WIKI 접근 실패나 모델 재시험이 아니다.

Windows reader/server는 선행 13개 파일 검사와 140회 호출 때의 코드 그대로다. 그 검사를 반복하지 않고 실제 두 TUI의 동작과 새로운 준비/수집 결과를 확인했다. 최종 문서 링크, 근거 체크섬, 변경 범위와 원본 보존은 `document-check.json`에 별도로 기록한다. 이 기계 검사는 위 답변 의미 평가나 제품 전체의 성공을 대신하지 않는다.

## 다음 판단

현재는 기본 전용 시작 방식과 선택 MCP의 검토 상태를 유지한다. 다음 명세에서는 필요한 검색 범위, 줄 수의 뜻, 결과 묶음의 출력 한도, 다음 페이지 소비와 오류 보고를 연결해 검토한다. 원문을 가져온 뒤 필수 조건을 답에 연결하는 검사도 별도 책임으로 둔다. 단순히 오류 한 번을 피하려고 검색용 AI, 별도 색인이나 여러 임시 도구를 추가하지 않는다.

보완 뒤 다시 비교할 필요가 생기면 품질 기준을 그대로 유지하고 같은 모델/질문, 순서 교차와 반복 예산을 먼저 정한다. 이번 결과를 바꾸기 위해 성공한 사용자 시험을 반복하지 않는다. 쓰기/복원, 정식 MCP 지원과 첫 배포 포함 여부는 아직 결정하지 않았으며, 비교 정리 뒤 4단계 잔여 명세와 5단계 개발 준비로 복귀한다.
