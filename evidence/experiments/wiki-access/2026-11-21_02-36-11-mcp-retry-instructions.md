# MCP의 제한된 축소 재시도 지침

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일은 2026-11-20이다. 실제 응답이 잘렸을 때 같은 위치를 작은 크기로 다시 요청하는 B안을 수용한 뒤, 기존 후보의 지침과 오류 안내를 맞췄다. **Windows 코드/SDK 부분 검사는 마쳤으며, 실제 Codex의 잘림 판별과 횟수 준수는 아직 검증하지 않았다.**

## 반영한 요구와 범위

한 문서 전체/구간 읽기 또는 같은 검색 하나에서 자동 축소를 최대 두 번으로 제한하는 실행 규칙이다. 정상 이어 받기는 실패 횟수에 포함하지 않는다. 축소 성공 후에는 그 요청에서 작은 크기를 유지한다. 원래 범위를 줄이거나 사용자 설정을 바꾸는 방식이 아니다.

| 변경 | 역할 |
| --- | --- |
| server.py 기록 | 정상 페이지와 호스트 잘림 구별, 동일 입력 위치, 알려진 크기, 축소/종료와 미완료 안내를 기존 지침에 통합 |
| contract.py 기록 | 두 도구의 설명이 같은 서버 지침을 따르도록 연결. 입력/출력 형식은 보존 |
| reader.py 기록 | 너무 작은 페이지에서 무조건 늘리라는 세 오류 문구만 조정. 원문/검색 알고리즘과 오류 코드는 보존 |
| files.py 기록 | 변경 없음. 기존 Windows 파일 접근과 경로/권한 보호 유지 |

현재 Windows 시험 서버를 덮지 않고 이 근거 폴더에 분리한 후보로 작업했다. 새 조회 도구, 필드, DB, 모델 호출이나 재시도 실행 루프는 추가하지 않았다. 제품 저장소 생성이나 MCP 첫 배포 포함의 확정도 아니다.

## 확인한 범위

종합 판정 기록은 서로 다른 검사 3개의 현재 결과를 연결한다. 실패 포함 실행 횟수는 6회이며 성공한 검사를 다시 실행해 횟수를 늘리지 않았다.

| 검사 | 결과와 한계 |
| --- | --- |
| 같은 위치의 읽기 축소 | 72,422바이트 원문을 첫 기본 페이지 뒤 작은 페이지로 이어 받아 9개 유효 페이지에서 완전히 일치. 큰 응답/재실행 부분은 중복 합산하지 않음 |
| 같은 위치의 검색 축소 | 대소문자를 구분한 QUERY_A 검색의 일치 줄 71개를 4개 유효 페이지에서 위치/발췌와 대조. 누락/중복 없음. 검색 revision으로 실제 구간 읽기도 확인 |
| 두 SDK 규격 | 2025-11-25와 2026-07-28의 실제 STDIO에서 지침과 도구 설명 일치. 각 규격에서 오류 5개, 오류 뒤 정상 기본 읽기 확인 |

Windows Python 3.13.9와 기존 mcp/mcp-types 2.3.0, AnyIO 4.16.0, jsonschema 4.26.0을 관측했다. 설치하거나 버전을 고정하지 않았다. 실제 AI 요청은 0회다. 검사 입력의 절반 크기 요청은 지원 기능의 부분 검사이며 호스트 상한을 낮추거나 실제 잘림을 인위적으로 만든 실험이 아니다.

소스 구문 대조에서 지침, 설명과 세 오류 문구 외 실행 알고리즘을 보존했다. 이전 검사 중 변경 없는 파일/입력 보호의 근거는 재사용했다. 통신 원시 출력은 work 아래 각 SDK 규격의 stdin.jsonl, stdout.jsonl과 stderr.log에 있다. 이전 문서 사본 60개와 이번 복사본을 각 해시로 대조한다.

## 검사 실패와 보정

최초 Windows 실행은 샌드박스의 WSL interop 소켓 제한으로 Python 실행 전에 멈췄다. 허용된 같은 명령으로 실행했으며 후보 기능 실패로 세지 않았다.

초기 검사기는 revision을 단순 본문 해시로 오해해 읽기와 검색 두 검사에서 실패했다. 실제 값은 연결, 경로, 파일 식별과 본문을 함께 식별하므로 같은 원문의 revision 유지와 독립 본문 바이트 대조로 고쳤다. 검색은 반환 revision을 사용한 실제 구간 읽기도 대조한다. 이후 검색 기대값을 WindowsPath로 정렬한 가정도 보정했다. 반환 계약의 상대 경로 문자열 순서로 기대값을 정렬하며 실제 결과의 순서/누락/중복 검사는 유지했다.

실패 결과와 당시 검사기는 초기 시도 기록, revision 보정 뒤 시도 기록에 보존한다. 후보 코드는 실패 대응 중 바꾸지 않았다. 재검증 계획 기록에 SDK/원문 읽기의 PASS 재사용과 검색만 다시 검사한 이유를 남겼다. 최종 검색 결과 기록은 검색 1개 검사이며 전체 3개 결과는 종합 판정을 본다.

## 남은 한계

- 첫 요청에서 page_bytes를 생략한 채 결과가 잘려 적용 크기를 알 수 없으면 자동 축소하지 않고 미완료로 알린다. 이 정보의 자동 확보는 해결하지 않았다.
- 최대 두 번은 현재 메인 AI의 실행 규칙이다. 서버는 Codex가 모델에 보여줄 출력을 잘랐는지 직접 알지 못하며, 사용자 작업 전체의 확정된 식별자도 없다. 코드가 강제하는 총호출/토큰 상한으로 설명하지 않는다.
- 실제 AI의 판단, 정상 페이지 처리와 횟수 준수, 표시 없는 누락, 실제 토큰/시간 효과는 미검증이다. 작은 페이지가 정상 호출 수를 늘리는 비용도 남는다.
- 외부 WIKI 쓰기/복원과 설치부터의 제품 사용 검증은 이번 읽기/검색 검사에 포함되지 않는다.

## 다음 실제 사용 관측

사용자가 실제 읽기 1회와 검색 1회 기록을 승인했다. trial.json 기록은 준비 당시의 입력이고, 배치 코드 기록을 실행해 새 시험 위치에 후보/사본 64개를 배치했다. 배치 결과 기록과 보존 대조 기록은 실제 파일 일치, 기존 원문/설정/Git 보존을 확인했다. 아직 Codex의 모델 요청은 실행하지 않았으며 사용자의 Windows TUI 연결 관측을 기다린다.

1. Windows의 새 `lab/retry-20261120` 아래 후보 4개와 문서 사본 60개를 배치한다. 기존 연결/설정/사본과 원본은 보존한다. 로컬 시험 Git에는 remote와 커밋을 만들지 않는다.
2. 사용자의 일반 PowerShell과 현재 Codex 설치본/선택 모델로 새 시험 대화를 연다. 최초 프로젝트 신뢰 확인과 `/status`, `/mcp` 연결 상태를 확인한다. 호스트의 새 프로젝트 신뢰 등록은 모듈이 전역 설정을 수정하는 것과 구분한다.
3. 전체 읽기 요청 기록과 독립 검색 요청 기록을 각 한 번 수행한다. 요청문에 정답, 축소 수치나 재시도 절차를 추가하지 않는다. 배포 후보의 지침으로 동작하는지 확인한다.
4. 실제 도구 반환의 범위/원문, 모델 답변의 완료 판단, 정상 페이지/축소 호출과 사용량을 대조한다. 잘림이 없으면 축소 복구는 미관측으로 남기고 재현을 위해 호스트 한도를 낮추거나 입력을 부풀리지 않는다.

사용자 요청은 두 번이지만 내부 모델 응답/도구 호출은 여러 번일 수 있으며 총토큰을 미리 보장하지 않는다. 자동 재요청은 같은 읽기/검색 안의 흐름이고, 설정 변경/프로세스 종료나 무제한 추가 모델 실험을 포함하지 않는다. 이 결과 뒤 [수용 기준 — 「MCP 읽기 보완의 검증 입력」](../../../verification/acceptance.md)과 첫 MCP 제공 여부를 판단한다.
