# WIKI 읽기 후보와 Windows 부분 검증

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일은 2026-11-19다. “MCP를 거쳐도 요청한 원문과 범위가 빠지지 않아야 한다”는 요구를 [읽기 명세](../../../design/integration/mcp.md)에 맞춰 코드와 SDK 통신에서 확인했다. **파일 검사 21개와 SDK 검사 3개가 확인한 범위에서 통과했다. 실제 Codex 수신, 답변 품질/토큰과 제품 설치 검증은 아직이다.**

이 폴더는 4단계 후보 검증 근거다. 제품 저장소/배포물 생성이 아니며 옛 시험본, 기존 서버 등록과 원문을 바꾸지 않았다. 최종 검증 대응 기록, 실행과 소스 기록, 문서/보존 검사 기록, 의미 검토 기록을 함께 본다. 최초 FAIL은 삭제하지 않았다.

## 무엇을 바꿨는가

예를 들어 긴 문서를 읽다가 한 응답에 다 담지 못하면 본문 일부와 next를 돌려준다. next는 **같은 문서 버전의 바로 다음 위치를 다시 요청할 정보**다. 중간 응답이 유실되면 그 요청을 그대로 다시 실행할 수 있다. 파일이 바뀌거나 서버가 재시작되면 옛 next로 다른 내용을 붙이지 않고 재확인을 요구한다.

| 소스 | 책임 |
| --- | --- |
| contract.py 기록 | 두 도구의 입력/결과 형식, 설명, 16KiB 기본값과 보호 디렉토리 목록 |
| files.py 기록 | 프로젝트 연결, 상대 경로와 실제 Windows 핸들 대조, UTF-8 원문 스트리밍 |
| reader.py 기록 | 줄/바이트 범위, 리터럴 검색, 서명된 cursor와 재시도/변경 판정 |
| server.py 기록 | 설치된 공식 SDK의 STDIO 연결, worker 실행과 요청 취소, 오류 반환 |

설정은 새 파일을 늘리지 않고 프로젝트의 `.harness/local.json`에서 project_id, wiki와 선택 page_bytes를 읽는다. page_bytes 생략은 16,384바이트다. 초기 요청과 이어 요청을 섞지 않고 호출별 축소는 허용한다. 파일 크기, 파일 수와 전체 검색 바이트에 옛 시험 상한을 넣지 않았다. 일반적인 오류 응답을 작은 페이지 크기에 맞춰 잘라 버리는 방식도 쓰지 않는다.

파일/검색의 허용 집합은 같다. 일반 숨김 Markdown과 Git ignore 문서도 포함하고 `.agents`, `.codex`, `.git`, `.harness`, `.obsidian`은 제외 사실을 표시한다. 내부/외부 WIKI를 모두 지원하는 후보이며 기존 시험의 형제 폴더 제약은 제거했다. path나 cursor가 읽기 권한을 새로 부여하지 않으며 OS의 접근 권한과 경로 보호를 매번 적용한다.

## 실행 조건과 결과

Windows 로컬 경로에서 기존 시험 환경의 Python 3.13.9, mcp/mcp-types 2.3.0, AnyIO 4.16.0, jsonschema 4.26.0을 사용했다. 설치/업데이트하거나 사용자 버전을 고정하지 않았다. 현재 WSL 설계 세션에서 Windows Python을 호출한 코드/SDK 검사이며 PowerShell의 실제 Codex 진입을 재현한 결과는 아니다.

기존 사본 60개는 읽기만 했다. 합성 입력과 모든 실행 로그는 이 폴더의 work에 따로 만들었다. 사용자 Codex 전역/시험 등록 config, 기존 시험 프로젝트 원문 86개와 Git/index 보존은 문서 검사에서 대조한다. 실제 AI 요청, 인증/토큰/전역 설정 변경과 새 MCP 등록은 없다.

| 실행 | 결과 | 확인 범위 |
| --- | --- | --- |
| 파일 검사 기록 | 16개 PASS | 사본 60개 전체 원문, 입력/줄 범위, 긴 줄/UTF-8/BOM/CRLF, 숨김/제외, 리터럴 검색, 재시도/변경, junction, 내부/외부 WIKI |
| 추가 Windows 경계 기록 | 4개 PASS | 열린 파일의 접근 거부, 경로 검사 뒤 부모 junction 교체, 9MiB/18MiB 원문, 여러 검색 페이지의 비용 |
| cursor 보완 검사 기록 | 영향 항목 10개 PASS | 새 크기/위치 거부 1개와 영향받은 기존 9개. 고유 파일 검사 수는 21개이며 재실행을 새 사례로 세지 않음 |
| 최초 SDK 검사 기록 | 2개 PASS, 1개 FAIL | 이전 규격의 전체/구간 읽기와 검색/오류, 취소 PASS. 다른 규격의 검사기 연결 절차 FAIL |
| 규격 재검사 기록 | 실패한 1개 PASS | 검사기를 공식 규격으로 보정한 뒤 짧은 원문 전달 확인 |
| SDK의 cursor 영향 재검사 기록 | 영향받은 1개 PASS | 같은 기본값/서버의 전체 읽기/검색 페이지와 오류 대조. 취소/다른 규격 PASS는 재사용 |

정상 결과는 출력 schema와 대조하고, SDK의 텍스트 표현을 JSON으로 해제한 내용과 structuredContent가 같은지 확인했다. 실제 STDIO에서 받은 한 줄의 바이트를 보존했으며 SDK 수신 객체를 다시 직렬화한 크기를 wire로 부르지 않았다. 이전 규격에서는 약 5,000개 일치 줄의 페이지를 순서대로 대조했고 다른 규격에서는 짧은 한 문서를 확인했다. 두 규격의 시험 깊이가 같다는 뜻은 아니다.

실행 중 취소는 observe_server.py 기록가 시작/종료만 관측한다. 실제 Reader와 SDK 서버를 호출하고 임의 지연이나 대체 파일 처리 코드를 넣지 않았다. 32MiB 합성 입력을 읽기 시작한 뒤 취소했을 때 worker가 CancelledError로 멈추고 다른 읽기가 성공했다. 관측한 검사 경계는 25회였다. 모든 OS I/O가 즉시 취소된다는 보장은 아니며 실제 Codex 취소도 별도로 남는다.

검사기의 수신 대기 60초와 종료 대기 10초는 교착 감지/시험 프로세스 정리용이다. 후보 서버에는 실행 시간 제한을 넣지 않았고 해당 감지에 걸린 검사는 없었다. 실패하면 시간만 늘려 실제 사용 성공으로 바꾸지 않는다.

## 비용과 한계

| 표본 | 관측 | 해석 |
| --- | --- | --- |
| 실제 문서 사본 60개, 합계 391,937바이트 | 전체 읽기 68페이지, 원문 I/O 765,570바이트 | 변경 기준을 확인하려고 같은 파일을 다시 읽은 비용 포함 |
| 같은 사본 전체 읽기 | tracemalloc 계측 중 0.381초, Python 할당 최고 540,346바이트 | 한 번의 코드 검사이며 SDK/모델 시간, 프로세스 전체 메모리나 일반 성능 기준이 아님 |
| 합성 80개 파일, 800개 일치, 원문 5,600바이트 | 15페이지, I/O 84,000바이트, 계측 중 2.360초 | 각 페이지마다 범위 재검사가 필요. 작은 원문이어도 많은 결과의 위치 정보와 호출이 늘어남 |
| 합성 9MiB/18MiB 파일의 마지막 줄 읽기와 없는 문자열 검색 | 계측 중 약 0.068/0.109초, Python 할당 최고 약 87/81KB | 해당 입력의 본문을 전부 보관하지 않았다는 근거. 모든 규모/동시성의 상한이나 메모리 누수 부재를 증명하지 않음 |
| SDK의 정상/오류 응답 표본 | 논리 결과 최대 16,384바이트, 실제 STDIO 최대 38,168바이트 | 텍스트와 구조화 표현, 이스케이프와 전송 메타데이터 포함. 토큰과 동일하지 않음 |

검색 성능 계측의 최고 메모리에는 검사기가 모은 기대/결과 배열도 포함된다. 후보 자체는 한 페이지 결과만 보관하며 경로/식별 목록은 문서 수에 비례한다. 반복 조회 캐시를 새로 넣지 않았고 현재 비용으로 MCP의 토큰 절감이나 직접 접근 대비 우위를 주장하지 않는다. 실제 호스트가 받아들일 수 있는 크기와 호출 묶음의 총량은 여전히 별도 확인 대상이다.

## 실패와 보완

첫 Windows 실행은 샌드박스의 WSL interop 소켓 제한으로 시작 전 중단됐다. 실행 권한을 받은 같은 명령으로 검사를 수행했다. 이것을 후보의 시간 초과나 파일 처리 실패로 세지 않는다.

최초 SDK 검사에서는 새 프로토콜에 initialize를 보냈고 SDK가 이전 handshake 규격을 응답했다. [공식 Python SDK 문서](https://py.sdk.modelcontextprotocol.io/protocol-versions/)와 설치된 runner를 대조해 새 규격은 server/discover와 요청별 메타데이터를 사용해야 함을 확인했다. 기대값만 바꿔 통과시키지 않고 검사기의 실제 송신을 고쳤다. 초기 소스/실패 기록을 보존했으며 제품 후보는 공식 SDK에 규격 처리를 맡긴다.

최종 명세 대조에서는 cursor의 발행 가능한 크기/위치 검사가 빠진 것을 발견했다. 디코딩 전에 등록된 페이지 크기로 가능한 길이를 제한하고 서명 뒤 필드/위치를 대조했다. 임의의 별도 길이 상한은 아니다. 보완 전 소스 기록과 변경 영향 재검사 기록을 보존했다. HMAC 키는 프로세스 메모리에만 있으며 로그나 이 근거에 저장하지 않았다.

| 범위 | 이번 근거 | 남은 확인 |

| R-01~04 | 독립 원문, 1018~1035행, 입력 형식, 페이지/부분 줄, 빈 파일 | 실제 Codex의 동일 요청과 수신 잘림/재요청 |

| R-11/14 | 새 근거 없음 | 답변의 의미/누락, 실제 사용자 모델/버전/설정 변경과 호환성 |

다음은 같은 후보의 실제 Codex 연결 조건과 원문 수신 관측을 준비하는 단위다. 입력 문서/구간, 현재 모델, 실행 횟수와 비용, 잘림/오류 판정 방법을 구체화한 뒤 새 AI 요청을 진행한다. 정상 수신을 먼저 확인하고 자유 탐색의 품질/비용 비교로 이어간다. 첫 MCP 제공 판단, 쓰기/복원, 전체 제품 설치와 원래 4단계 잔여 명세는 그대로 남아 있다.

## 재현과 근거 사용

Windows에서 이 폴더를 작업 위치로 두고 준비된 Python으로 `-B source/test_reader.py`, `-B source/test_edges.py`, `-B source/test_sdk.py`를 실행한 명령과 해시는 metadata.json 기록에 있다. reader 검사는 옆의 사본/manifest 위치를 사용하는 이번 관측용 검사다. 배포 사용자의 설치 명령이나 필수 환경으로 복사하지 않는다. 실행하면 새 work 입력과 보고서가 만들어지므로 최초 결과를 보존하려면 별도 근거 복사본에서 실행한다.

외부 구현을 복사하지 않고 설치된 SDK/AnyIO/jsonschema API를 호출했다. 확인한 의존성의 MIT 메타데이터/허가문 해시와 [Windows 파일 핸들 API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), [AnyIO 취소 설명](https://anyio.readthedocs.io/en/stable/threads.html#reacting-to-cancellation-in-worker-threads)을 metadata에 연결한다. 이번 API 사용 확인은 최종 배포물의 전체 라이선스 감사 완료를 뜻하지 않는다.
