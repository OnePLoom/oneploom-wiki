# MCP 오류 후 사용의 실제 시험

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일: 2026-11-20. **없는 파일의 오류 전달과 변경된 문서의 이어 읽기 차단을 실제 두 요청에서 확인했다.** 변경 후 전체 재독은 실행되지 않았으며 이 결과와 구별한다. 새 사본만 변경했고 원본과 이전 시험 자료는 보존했다.

## 진행 범위

사용자는 [준비한 두 요청](2026-11-20_18-47-33-mcp-failure-plan.md)의 의미를 설명받고 “좋아. 이어서 진행하자”로 진행을 확인했다. 현재 사용자 모델을 유지하며 없는 파일과 원문 변경 후 이어 읽기를 시험한다. 원본 대신 새 사본만 사용하고 패키지 설치/업데이트는 하지 않는다.

준비 자료와 과거 수신 근거는 수정하지 않았다. 이 폴더에는 확인된 계획, 입력, 도구 사본과 이번 실행 결과를 분리해 남긴다. 현재 상태와 다음 순서의 기준은 [진행표](../../../development/roadmap.md)와 [오류 후 사용의 검증 순서](../../../design/integration/mcp.md)다.

## 배치 결과

- Windows Python으로 새 `<WORKSPACE_PATH>` 아래 project, wiki, source를 만들었다. 문서 사본 한 개와 검증된 후보 네 파일의 해시가 준비값과 일치했다.
- 배치 기록 기록은 Python 3.13.9, mcp/mcp-types 2.3.0, AnyIO 4.16.0, jsonschema 4.26.0을 관측했다. 이 값은 지원 버전 고정이나 새 설치를 뜻하지 않는다.
- 배치 대조 기록에서 문서, 코드, 연결/등록, 기본 설정과 없는 파일의 부재, remote 없는 독립 로컬 Git을 확인했다. 배치 전후 Codex 전역 설정 해시도 같았다.
- Native 명령의 콘솔 반환에는 한글 해석이 깨진 부분이 있었으므로 저장된 UTF-8 `prepared.json`을 직접 읽고 보존했다. 파일 내용은 정상이며 준비를 반복 실행하지 않았다. 이 출력 문제를 MCP 본문 수신 실패로 분류하지 않는다.

이 결과는 파일과 설정의 배치 확인이며 두 요청의 AI 행동을 통과시킨 결과가 아니다. 후속 사용자 화면 관측 기록에서 Codex 0.171.0, GPT-5.6-Sol low, 해당 시험 project, Workspace와 wiki_reader connected 2 tools를 확인했다. Session은 `<SESSION_ID>`다. 앞선 11/19의 0.170.0과 다른 현재 설치본이며 버전을 되돌리거나 모델을 바꾸지 않는다. 이 화면만으로 도구 선언/본문 수신과 오류 처리를 통과시키지 않는다.

## 다음 사용자 확인

아래는 이미 마친 최초 시작 절차다. 이 결과를 확인하려고 다시 실행하지 않는다. 기존 WSL 설계 세션은 유지했다.

```powershell
cd <WORKSPACE_PATH>
codex.cmd
```

입력 화면의 `/status`에서 버전, 모델/추론, Directory, Permissions, Session을 확인했고 `/mcp`에서 `wiki_reader` 연결을 확인했다. 계정 정보는 기록에 포함하지 않았다.

연결, 첫 요청과 사본 변경 뒤 같은 대화에서 둘째 요청 기록을 실행했다. 이번 두 요청의 확인은 끝났으므로 반복하지 않는다. 다음 실제 사용 시험은 [오류 후 사용의 검증 순서](../../../design/integration/mcp.md)에 따라 재연결과 취소를 구별해 준비한다. 변경 후 전체 재독, 재연결 또는 취소를 이번 차단 결과로 통과시키지 않는다.

## 첫 요청과 사본 변경

첫 요청 기록 기록에서 도구 발견 한 번과 두 파일 읽기만 확인했다. 독립 원문 대조 기록은 0~15,333바이트의 본문과 위치가 원문과 정확히 같고, 이어 읽기 정보가 반환됐으며 추가 읽기는 없음을 확인했다. `output_limit`은 정상 페이지의 분량 경계이고 문서 전체 완료가 아니다. 없는 파일은 `not_found` 오류와 `complete: false`가 실제 출력에 전달됐다. 상위 MCP 응답의 `isError` 필드는 이 출력에서 별도로 관측하지 못했다.

AI 답변은 미완료와 없는 파일을 구분했지만 “1~341행”이라는 범위 표현에는 보완 여지가 있다. 실제 수신은 340개 완전한 행과 341행 내용 94바이트 중 67바이트다. 341행 전체를 읽었다고 해석하면 안 되며 정확한 바이트 범위와 다음 위치는 보존됐다. 본문/오류 전달의 표본 PASS를 모든 답변 표현의 완전성으로 확대하지 않는다.

처음 수집은 준비 요청문과 실제 붙여넣기의 줄바꿈이 달라 중단됐다. 단어 중간 줄바꿈까지 포함한 실제 입력 기록을 보존하고 공백 외 문자 일치와 범위를 수동 대조한 뒤, 같은 수집 함수에 그 입력과 명시적 turn을 전달했다. 수집 시도 기록을 남겼으며 수집기를 느슨하게 바꾸거나 모델을 다시 호출하지 않았다. 첫 사용자 AI 요청 한 회에 내부 모델 응답 네 회가 있었고 사용량 기록은 캐시/반복 문맥을 포함한다. 둘째 결과와 함께 받은 사용자 관측 기록에서 두 요청 모두 추가 승인창이 없었음을 확인했다.

첫 결과 확인 뒤 Windows의 변경 도구 기록으로 새 사본의 첫 제목과 마지막 절만 바꿨다. 변경 기록 기록과 사후 대조 기록에서 계획한 72,577바이트의 사본과 예상 해시가 일치했다. 원본 문서 86개와 이전 요구사항 사본 두 개, 제품 Git, 후보 코드와 연결은 보존됐다. Codex/MCP 재시작이나 별도 모델 요청은 실행하지 않았다.

첫 결과 검사기는 변경 전 상태에서 실행했으므로 변경된 사본으로 같은 검사를 다시 돌리지 않는다. 첫 제목이나 끝 제목만 맞는 것으로 전체 읽기 완료를 판정하지 않는다.

## 둘째 요청과 판정

실제 호출 기록 기록과 대조 결과 기록에서 첫 요청이 돌려준 이어 읽기 정보가 그대로 사용됐음을 확인했다. 도구는 `changed_source` 오류와 `complete: false`를 반환했고 새 본문은 0바이트였다. 옛 위치를 새 문서에 그대로 적용해 서로 다른 버전을 섞는 동작은 이 표본에서 차단됐다. 상위 MCP 응답의 `isError` 필드는 별도로 출력되지 않아 확인 대상으로 남긴다.

AI는 미완료와 다시 읽어야 한다는 이유를 알리고 멈췄다. 첫 제목은 앞선 반환분의 값이라고 명시했고 마지막 절은 확인하지 못했다고 답했다. 따라서 **변경 감지와 안전한 중단은 확인했지만 변경 후 문서 전체 읽기는 미실행**이다. 자동 재독/작업 완료나 모든 오류의 처리가 성공한 것으로 확대하지 않는다. 앞선 “1~341행”의 부분 줄 표현 문제도 남긴다.

실제 둘째 입력 기록에는 준비한 본문 뒤에 결과와 승인창을 알려 달라는 안내도 함께 붙었다. 읽기 범위와 도구 제약은 같음을 확인하고 실제 입력과 명시적 turn으로 수집했다. 오류의 정답, 변경한 제목이나 새 본문은 요청에 넣지 않았다. 추가 승인창이 없었다는 판단은 모델의 자기 보고가 아니라 사용자 확인을 근거로 한다.

답변 검토 기록은 도구 관측, AI의 미완료 안내와 사용자 화면 관측을 구별한다. 검사기 기록은 원본 86개, 이전 요구사항 사본 두 개, 후보 코드와 연결, 제품 Git의 보존도 확인했다. 이 표본의 사용자 요청은 총 두 회이고 내부 모델 응답은 여섯 회다. 토큰 집계는 캐시를 포함한 관측이며 구독 차감량이나 직접 접근 대비 비용 우위를 뜻하지 않는다.

설정 대조 기록에서 전역 파일에는 이번 시험 프로젝트의 신뢰 절만 추가돼 있었고, 그 절을 제외한 바이트는 배치 전과 일치했다. 기존 설정의 수정이나 모듈의 전역 설정 쓰기로 해석하지 않으며 사용자 설정을 되돌리지 않는다. 앞선 다른 시험의 프로젝트 설정도 그대로였다. 첫 비교는 호스트가 사용한 TOML의 작은따옴표 키를 인식하지 못해 미분류로 남겼고, 초기 결과 기록을 보존한 뒤 같은 항목을 대조했다.

이번 기록 전 백업은 2026-11-20 19:51:43 KST 생성 백업(식별자 `Nk1JZV3b`)다. 첫 백업 시도는 vault에서 코드 Git 루트를 찾지 못해 파일 생성 전에 종료됐고, 코드 경로를 명시해 완료했다. 시도 기록 기록을 보존했으며 백업 스크립트와 시험 후보는 수정하지 않았다.

기록 집계의 첫 시도는 WSL 분석용 Python에 `tomllib`이 없어 저장 전에 중단됐다. 기록 시도 기록에 남기고 별도 의존성 설치 없이 알려진 신뢰 절과 나머지 바이트의 해시를 대조했다. Windows 제품/후보의 실패가 아니며 모델 요청이나 이미 통과한 본문 검사를 반복하지 않았다.

문서와 보존 검사 기록에서 관련 Markdown 4개의 링크/제목 363개와 기존 제목, 다른 백업 파일 2,974개, 준비/이전 근거 103개를 확인했다. 첫 보존 검사의 차이는 Obsidian의 `lastOpenFiles`뿐이었으며 나머지 설정 필드는 같았다. 사용자 화면 상태를 되돌리지 않고 초기 검사 기록을 보존한 뒤 나머지 보존 항목을 마쳤다. 유효한 문서 검사는 재사용했다.
