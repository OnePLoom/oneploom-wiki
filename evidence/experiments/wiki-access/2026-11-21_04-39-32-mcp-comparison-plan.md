# 직접 접근과 MCP의 후속 비교 준비

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일은 2026-11-20이다. 정상 원문 전달을 확인한 뒤, 필요한 근거를 스스로 찾아 답에 반영하는 품질과 실제 비용을 비교하기 위한 준비다. **Windows 배치와 새 AI 요청은 실행하지 않았다.**

## 목적과 범위

[직전 읽기/검색](2026-11-21_04-19-04-mcp-retry-run.md)은 지정한 문서 전체와 검색 결과의 정확한 수신을 확인했다. 이번 후보는 같은 질문에 직접 접근과 MCP가 필요한 자료를 찾아 답하는 사용 흐름을 비교한다. 자동 축소와 재시도 횟수의 실제 준수, 내부 취소/늦은 응답은 별도 미검증으로 유지하며 이 결과로 통과시키지 않는다.

실행 후보는 현재 사용자 Windows Codex의 새 대화 두 개에서 각 한 요청이다. 같은 모델/추론 수준, 사본/질문과 공통 지침을 사용한다. 최초 안내와 실제 도구 인터페이스만 경로별로 다르다. 먼저 MCP, 다음 직접 접근을 제안하며 정확한 배치와 조건은 trial.json 기록에 보존한다. 시작/신뢰 확인, 질문 처리 시간, 사람 개입은 따로 기록한다. 제품 설치기 전체의 성공을 검증하는 실행은 아니다.

## 질문과 판정

공통 질문 기록은 초기 content의 선택성, 브라우저 세션과 문서 복구의 경계, 확정된 성능 수치의 근거를 묻는다. 각각 과거안/채택안, 필수 예외, 근거 부재를 구분할 수 있는지 확인한다. 직접 요청 기록과 MCP 요청 기록의 공통 본문은 같다. 이전의 8줄 답변 상한은 두 방식 모두 제거했다. 이 변경과 호스트 버전 차이 때문에 과거 결과와의 차이를 MCP 코드 개선 효과 하나로 해석하지 않는다.

사전 판정 기준 기록은 이전 근거를 유지하고 원문을 먼저 대조한다. 60개 사본과 현재 프로젝트의 해당 원문은 해시/본문이 같다. 정답표, 이 계획과 과거 답변은 시험 프로젝트/WIKI에 복사하지 않는다. 기존 실패 사례의 회귀 비교이므로 별도의 새로운 문제에서 일반화 성능을 측정한 것처럼 제시하지 않는다.

각 사실의 충족/누락/상충, 인용 유효성, 실제 원문 수신을 먼저 본다. 예를 들어 영구 삭제가 끝난 문서의 복구 제외 조건은 원문을 받았는지와 최종 답에 반영했는지를 따로 판정한다. 답변 문장의 완전 일치를 요구하지 않으며 시험 모델의 자기 평가만으로 통과시키지 않는다. 품질이 부족한 결과도 시간과 사용량을 보존하되 절약 성공으로 표시하지 않는다.

## 실행 전 확인과 한계

두 사용자 요청 안에서도 여러 모델 응답과 정상 페이지/재시도가 발생할 수 있다. 코드/설정, 원본/사본 해시와 현재 사용자 설치본/모델을 확인한 뒤 실행한다. 인위적인 호스트 상한, 입력 부풀리기, 시험용 지연이나 추가 모델을 넣지 않는다. 실패 시 실제 실패를 기록하고 같은 요청을 자동으로 새 세션에서 다시 실행하지 않는다. 한 경로의 실패를 다른 경로의 원문으로 대신하지 않는다.

한 쌍은 기능과 비용의 예비 관측이다. 과거와 실행 순서를 바꿨다고 동일 조건의 순서 교차 반복이 되는 것은 아니며 캐시와 서비스 부하의 차이가 남는다. 반복/확인용 새 사례가 필요하면 첫 결과를 보존한 뒤 범위와 비용을 다시 정한다. 구독 잔량을 토큰이나 금액으로 환산하지 않는다. 사용량과 시간은 모든 시도를 포함하며 원문을 덜 읽거나 필요한 예외를 빠뜨린 것을 비용 개선으로 세지 않는다.

새 Windows 배치와 AI 두 요청은 아직 승인받지 않았다. 이번 준비를 실행 승인이나 첫 MCP 제공 결정으로 확대하지 않는다. 준비가 끝나면 입력과 남은 한계를 보여주고 사용자가 실행 범위를 선택하도록 한다.

## 설계 근거

[OpenAI 평가 안내](https://developers.openai.com/api/docs/guides/evaluation-best-practices)는 실제 작업에 맞는 사례, 사전 기준, 기록과 사람의 판단을 함께 사용하도록 한다. 여기서는 그 방법만 참고하며 별도 평가 서비스/API나 모델을 도입하지 않는다. [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)은 도구 발견/호출을 정의하지만 우리 요청별 재시도 예산을 자동으로 강제하지는 않는다. 구현과 호스트의 실제 수신을 따로 확인해야 한다는 판단은 현재 후보 코드와 관측에 근거한다.
