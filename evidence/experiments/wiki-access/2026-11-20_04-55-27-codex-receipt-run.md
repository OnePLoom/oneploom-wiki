# Windows Codex의 실제 읽기 수신

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일은 2026-11-19다. 사용자가 [준비한 세 요청](2026-11-20_04-22-37-codex-receipt.md)의 순차 실행을 승인했다. 구간 읽기, 전체 읽기 재시도와 검색의 로그 결과가 독립 원문에 일치했다. 입력 선언의 누락과 코드 내부에서만 본문을 읽은 문제를 보완했다. 최초 전체 읽기는 미확인으로 보존하며 추가 재시도 한 회를 포함해 사용자 AI 요청은 네 회다.

## 실제 환경과 보존

대상은 `<WORKSPACE_PATH>`다. Windows Python 3.13.9, 기존 MCP SDK 2.3.0으로 후보 네 파일과 문서 사본 60개를 배치했다. 사용자 PowerShell에서 Codex 0.170.0, GPT-5.6-Sol low, Workspace와 wiki_reader connected 2 tools를 확인했다. 버전/모델은 관측이며 배포 고정값이 아니다.

배치 결과 기록과 보존 검사 기록은 원문 86개, 기존 사본 60개, 사용자 전역 설정과 이전 시험 설정, 제품 Git/index 보존을 확인했다. 시험 저장소는 remote가 없다. 정답표를 모델에 주지 않았고 새 패키지 설치, 배포 저장소 생성이나 push도 없다. 배치 명령의 콘솔 한글 일부가 깨졌지만 UTF-8로 저장된 prepared.json은 정상이며 콘솔의 디코딩된 출력도 별도로 보존한다.

TUI 사용 뒤 최종 비교에서는 전역 Codex 설정의 해시가 달라져 첫 문서/보존 검사 기록가 FAIL이었다. 차이 확인 기록 결과 새 시험 프로젝트의 `trust_level = "trusted"` 절만 추가됐고, 메모리에서 그 절만 제외하면 시작 전 해시와 일치했다. 초기 Codex 프로젝트 신뢰 등록과 일치하는 변화이며 작성 프로세스 자체를 감사한 것은 아니다. 모듈의 배치/보정 코드는 이 전역 파일을 쓰지 않으며 사용자의 항목을 되돌리지 않았다. 배치 당시 보존 결과와 TUI 사용 뒤 관측을 구분하고 전역 파일 전체가 계속 동일했다고 주장하지 않는다.

## 구간 읽기 결과

실제 기록 기록의 read_note 호출은 `docs/REQUIREMENTS.md`의 시작 1018, 끝 1035를 전달했다. 본문 대조 기록에서 18행/1,328바이트, 시작/끝 바이트, 줄 위치와 range_end/next=null이 독립 사본과 일치했다. exec가 text 표현과 structuredContent를 둘 다 출력했으며 두 내용도 같았다. 두 표현의 출력은 서로 다른 두 읽기 성공으로 세지 않으며 비용에는 중복이 남는다.

사용자가 붙여넣은 요청에는 줄바꿈/들여쓰기 변화와 마지막 답변 형식 안내의 누락이 있었다. 최초 수집 실패 기록을 보존했다. 실제 입력의 도구/파일/끝 포함 줄 범위는 유지됐음을 직접 읽고 실제 요청문 기록으로 별도 수집했다. 다시 모델을 호출하거나 원래 요청문과 바이트가 같다고 처리하지 않았다. 최종 답변에는 원문까지 출력됐으므로 계획한 짧은 답변과 동일한 비용 조건도 아니다.

준비 기대값의 revision 필드에는 원문 SHA-256이 들어 있었으나 후보의 revision은 연결/경로/파일 식별과 내용 해시를 함께 묶은 값이다. 제품 오류로 오판하지 않고 현재 비교 입력 기록에서 content_sha256으로 명확히 했다. 과거 준비 파일은 덮지 않았다. 원문 내용은 독립 바이트와 SHA-256으로 대조하고, 같은 실제 연결의 revision 연속성은 별도로 확인한다. WSL의 파일 식별 값을 Windows 값과 같다고 가정하지 않는다.

이 결과는 기록에 나타난 구간 본문의 일치다. 최종 모델 요청 본문 전체를 관측했거나 다른 입력, 전체 문서, 검색까지 통과했다는 뜻은 아니다.

## 발견한 입력 형식 문제와 보완

실제 도구 선언 기록에서는 첫 read_note 요청의 start_line/end_line/revision/page_bytes, 첫 search_notes의 scope/page_bytes와 이어 요청의 page_bytes가 빠져 있었다. 이번 모델은 줄 범위를 명시해서 원문을 정확히 읽었지만, 선언과 실제 수용 입력의 차이는 그대로 둘 수 없다. 관측과 가설 기록에 이 상태를 FAIL로 남겼다.

기존 JSON Schema는 공통 properties를 바깥에 두고 oneOf 분기에서 필요한 제약만 좁혔다. [JSON Schema의 조합 설명](https://json-schema.org/understanding-json-schema/reference/combining)은 공통 조건의 분리와 분기 안의 표현을 허용한다. 기존 형식이 무조건 잘못된 표준이라는 뜻은 아니다. 현재 호스트에 표시된 선언은 공통 선택 필드를 보존하지 않았으며, 내부 어느 변환 단계가 원인인지는 직접 추적하지 않았다.

contract.py에서 같은 공통 정의로 **각 분기의 완전한 객체 형식**을 생성하도록 바꿨다. 최초/이어 요청 구분, 필수 값과 null, 추가 필드 거부, 검색어의 CR/LF 거부를 유지한다. 이 보정에서는 반환 기본값, 파일 읽기/검색 코드, 경로 보호와 SDK 서버 코드를 변경하지 않았다. 버전별 예외나 시험 전용 한도는 추가하지 않았다.

Windows 검사 기록은 기존/보정 schema의 입력 허용 여부 17,596건을 대조하고 영향받은 Reader 검사와 두 SDK 규격을 포함한 8개 검사를 통과했다. 상세 출력은 검사 로그 기록에 있다. 기존의 취소/경로 보호 등 영향받지 않은 결과는 재실행하지 않았다. 이어 실제 Codex를 재개한 호스트 선언 대조 기록에서도 누락됐던 선택 입력이 표시되는 것을 확인했다. SDK 검사와 호스트 관측은 별도 근거다.

반영 결과 기록에 따라 시험 source/contract.py 한 파일을 교체했다. 이전 파일은 원래 후보와 prior_contract.py에 보존했다. 같은 시험 대화를 종료/재개하여 새 도구 형식을 확인했다. 전체 읽기 요청문 기록은 현재 도구 목록/입력의 재확인만 추가했으며 읽을 문서와 기본 페이지는 그대로다.

## 전체 읽기의 본문 미전달과 재검증

첫 전체 읽기 기록 기록에서 모델이 작성한 exec 코드는 페이지를 가져온 뒤 길이, 범위와 완료 정보만 출력했다. 첫 코드 실행은 TextEncoder 부재로 실패했고, 다음 코드가 자체 바이트 계수로 재시도했다. 코드가 보고한 5개 페이지의 합은 72,422바이트였지만 실제 로그에 본문이 없으므로 판정 기록은 NOT_VERIFIED다. 서버가 본문을 잘랐다는 관측과 다르며 코드의 완료 주장으로 원문 수신을 대신하지 않는다. 코드의 200회 반복 한도는 모델이 작성했고 도달하지 않았으며 제품 정책이 아니다.

원문 읽기의 도구 지침을 server.py에 보강했다. 코드 실행을 거치더라도 본문과 진행 정보를 모델이 읽는 출력으로 전달하고, 응답 하나를 확인한 뒤 다음 응답을 요청하며, 같은 결과의 text 표현과 structuredContent를 중복 출력하지 않도록 했다. 자료를 읽는 코드의 작업과 AI의 원문 수신을 구분하기 위한 것이다. 사용자에게 최종 답변으로 본문 전체를 다시 보여 달라는 뜻이 아니다.

지침 검사와 반영 기록에서 Windows의 두 SDK 규격에 같은 지침이 전달됐고 지침 문자열 외 서버 실행 구문이 같음을 확인했다. 현재 시험 server.py만 반영한 뒤 사용자에게 추가 AI 요청 한 회의 이유를 설명하고 같은 전체 읽기 요청을 재실행했다. 한 페이지마다 모델 판단이 늘 수 있으므로 이를 비용 없는 보완으로 취급하지 않는다.

재시도 기록 기록에는 본문을 포함한 5개 응답이 각각 한 번 출력됐다. 원문 대조 기록은 0부터 72,422바이트까지의 연속 구간, 전체 1,191행, 같은 revision, 직전 next의 실제 재사용과 마지막 eof/next=null을 확인했다. 실제 도구 설명 기록에도 새 지침이 포함됐다. 같은 원문의 표본 관측이며 모든 모델이 항상 지침을 따른다는 보장은 아니다.

전체 읽기 두 요청과 검색의 붙여넣기는 계획문과 줄바꿈/들여쓰기가 달랐다. 실제 입력을 보존하고 모든 문단, 도구와 대상, 요청 범위가 유지됐는지 직접 대조했다. 수집기의 엄격한 비교를 느슨하게 바꾸지 않았고, 파일/검색어의 임의 공백 정규화도 하지 않았다.

## 검색 결과

실제 검색 기록은 docs 범위의 QUERY_A를 대소문자 구분으로 검색했다. 독립 대조 기록에서 세 페이지의 33개, 36개, 2개 결과가 기대한 71개 일치 줄과 9개 파일에 정확히 대응했다. 각 줄과 일치 문자열의 바이트 위치, 발췌 원문, next 사용과 마지막 complete를 확인했다. 중복 결과, 발췌 잘림과 제외 디렉토리는 없었다. 사용자도 같은 개수와 별도 승인창 없음으로 보고 기록했다.

## 사용량과 해석

실제 사용량 기록은 응답별 usage 합, 턴 합과 대화 누적의 차이를 함께 대조했다. 아래 입력 토큰에는 캐시 입력이 포함되며 추론 출력은 출력 토큰에 포함된다. 비용이나 주간 할당량 차감량으로 환산하지 않는다.

같은 대화에서 이력과 캐시를 이어 사용했고 도구 발견, 오류와 보완도 포함한다. 이 표는 순수 MCP 통신 비용이나 직접 파일 접근과 조건을 맞춘 비교가 아니다. 본문을 전달하지 않은 첫 전체 읽기가 더 적은 토큰으로 끝났다는 이유로 더 나은 읽기라고 판단할 수 없다. 현재 후보가 더 저렴하다는 결론도 내리지 않는다.

## 이어서 확인할 것

이번 세 기능 표본은 확인했으며 새 모델 요청을 더 실행하지 않는다. 다음은 기존 수용 입력과 관측을 대응해 남은 실제 호스트 실패 조건, 자유 탐색의 품질/비용 비교를 좁히는 단위다. 새 실행이 필요하면 대상, 반복과 비용을 구체화한다. 최종 모델 입력의 비관측 범위, 첫 MCP 제공 판단과 쓰기/복원은 별도다. 현재 시험 TUI는 사용자가 열어 둔 상태이며 임의 종료하지 않았다.
