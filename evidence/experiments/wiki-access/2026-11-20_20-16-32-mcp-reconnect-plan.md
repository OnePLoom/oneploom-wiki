# MCP 재연결 시험 준비

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일: 2026-11-20. **승인한 두 AI 요청과 시험 서버 한 개의 종료를 실행했다.** 첫 본문은 원문과 일치했고, 종료 후 같은 이어 읽기 요청은 `Transport closed`로 실패했다. AI는 추가 본문이 없으며 미완료라고 알렸다. 자동 재연결, 새 서버의 cursor 만료 처리와 전체 재독 성공은 확인하지 못했다. 승인 기록 기록과 아래 「첫 요청과 종료 결과」에 실제 범위와 미완료를 구분한다.

## 이번에 확인할 것

이전 [원문 변경 시험](2026-11-20_19-20-33-mcp-failure-run.md)은 문서를 바꿨을 때 옛 읽기 위치를 거부하는지 확인했다. 이번에는 문서를 그대로 두고 **문서를 읽는 MCP 프로그램만 종료된 경우**를 확인한다. 문서 변경과 서버 종료를 한 사례로 섞지 않는다.

현재 후보는 시작할 때마다 이어 읽기 정보의 서명 키를 새로 만든다. 따라서 같은 파일이라도 서버가 다시 시작되면 옛 cursor(이어서 읽을 위치와 원문 기준을 담은 정보)는 새 서버에서 유효하지 않다. 이 구현 관찰과 실제 Codex의 재연결/오류 대응은 별도이며, 이번에 후자를 확인한다. 같은 대화는 옛 이어 읽기 정보를 유지하려는 시험 조건이고 일반 사용에서 같은 세션을 강제하는 정책이 아니다.

부모 단계는 [오류 후 사용의 검증 순서](../../../design/integration/mcp.md)의 R-08/10이다. 실행 중 취소, 늦은 결과와 실제 출력 잘림은 이번 표본으로 통과시키지 않는다.

## 대상과 준비 상태

실행안 기록은 기존 failure-20261120의 독립 project/wiki/source와 현재 대화를 재사용한다. 문서 한 개는 앞 시험에서 의도적으로 바꾼 72,577바이트 사본이며 이번에는 내용을 바꾸지 않는다. 후보 네 파일, 연결과 페이지 기본값도 보존한다. 원래 기존 시험 프로젝트 문서와 앞선 근거는 쓰기 대상이 아니다.

설치본 관측 기록은 Windows Codex 패키지 0.171.0과 실제 npm 경로를 확인했다. 관측한 버전/모델을 배포 고정값으로 사용하지 않고 사용자 현재 선택을 유지한다. 패키지 설치나 설정 변경은 하지 않았다.

Windows 프로세스 조회 기록에서는 같은 명령의 Python 두 개가 보였다. 하나는 가상환경 실행을 전달하는 부모이고 하나는 MCP를 수행하는 자식이었다. 둘을 여러 독립 서버로 오인하거나 Python 전체를 종료하지 않는다. 읽기 전용 신원 확인 기록은 자식의 PID(프로세스 식별 번호), 생성 시각, 실행 파일과 후보/문서 해시의 일치를 확인했다.

시험 도구 기록은 check와 stop을 분리한다. check는 종료 권한 없이 조회한다. stop은 새 읽기의 검증 기록인 fresh-check.json이 있고 같은 문서/대화/작업자를 가리킬 때만 진행한다. 한 Windows 핸들(특정 프로세스를 참조하는 운영체제 객체)에서 생성 시각과 실행 파일을 확인한 뒤 그 핸들로 종료하므로 PID 번호만 믿고 다른 프로세스를 종료하지 않는다. 이전 종료 시도 기록이 있으면 반복 종료하지 않는다.

최초 process-check.json은 당시 신원 확인의 부분 근거다. 실제 종료 시점에는 기존 작업자가 사라져 선행 확인에서 중단됐다. 아래에 재식별 과정과 한 개의 실제 종료를 기록했다. 기록된 PID가 다음 실행에서도 유효하다고 가정하지 않으며 작업자가 달라지면 멈추고 다시 식별한다. 검증 호출은 `-I -B`로 실행해 분석용 Python 환경 변수와 바이트코드 생성을 배제했다.

## 실행 순서

| 순서 | 할 일 | 확인할 결과 |
| --- | --- | --- |
| 1. 새 위치 확보 | 같은 Windows Codex에서 첫 요청 기록으로 현재 문서의 첫 반환분만 읽음 | 현재 사본의 본문과 next가 일치. 첫 요청 후 추가 이어 읽기 없음 |
| 2. 중단 직전 대조 | 실제 호출/본문과 동일 작업자, 문서/코드/설정 보존을 확인하고 fresh-check.json 작성 | 새 cursor가 현재 살아 있는 시험 서버에서 나온 것임을 확인. 앞 시험에서 이미 거부된 옛 cursor로 대체하지 않음 |
| 3. 시험 서버 중단 | 준비된 stop으로 확인한 MCP 자식 하나만 종료 | 종료 요청과 실제 종료를 구분해 보존. Codex의 공용 백그라운드 서버와 다른 대화/서버를 종료하지 않음 |
| 4. 실제 사용 재확인 | 같은 Windows Codex에서 둘째 요청 기록 실행 | Codex가 재연결하는지 관측. 옛 cursor 거부 뒤 새 처음 읽기가 가능하면 새 본문 전체를 독립 사본에 대조 |
| 5. 판정 | 새 프로세스 신원, 호출/오류/본문, 답변과 사용자 승인창 관측을 함께 대조 | 재연결, 만료 오류, 새 전체 읽기와 답변 정확성을 각각 판정 |

첫 요청은 정상 읽기를 반복해 성공 수를 늘리려는 것이 아니라, 종료 직전의 유효한 읽기 위치를 확보하기 위한 입력이다. 페이지 수/모델 내부 호출 수를 시험 편의로 제한하지 않는다. 처음의 부분 읽기는 사용자 요청 범위이며 제품 기본 응답 크기를 낮추지 않는다.

둘째 요청은 오류가 나면 현재 연결에서 처음부터 다시 읽도록 명시한다. **지시된 재시작 절차의 수행 검증**이며, 일반적인 모호한 요청에서도 AI가 자동으로 같은 판단을 한다는 근거로 사용하지 않는다. 정답 제목, 오류 코드와 본문은 입력에 넣지 않는다.

종료 도구의 5초 대기는 종료 신호 뒤 운영체제 프로세스가 끝났는지 관측하는 시간이다. 문서 읽기나 AI 응답을 5초로 끊는 제품 제한이 아니다. 종료가 확인되지 않으면 상태를 기록하고 반복 종료하지 않는다. 실제 모델 요청에는 이 관측 시간을 적용하지 않는다.

## 오류와 미완료 판정

- 프로세스가 이미 끝났거나 생성 시각/실행 파일이 다르면 종료하지 않는다. 같은 PID라도 다른 프로세스일 수 있다.
- 새 읽기 위치를 얻기 전에 서버가 바뀌면 그 위치의 발급 주체부터 다시 확인한다.
- 서버를 종료하지 못했다면 재연결 시험을 수행한 것으로 표시하지 않는다.
- 새 서버가 생겼더라도 실제 도구 호출이 실패하면 읽기 성공이 아니다. 연결되지 않으면 오류를 보존하고 종료하며 무제한 재시도나 공용 서버 재시작으로 통과시키지 않는다.
- 옛 cursor가 실제 전달되지 않으면 만료 처리 사례는 미실행이다. 파일을 다시 읽은 성공과 구분한다.
- 만료 오류가 정상 전달돼도 전체 재독이 없으면 안전한 중단/오류 처리만 판정한다. 새 본문을 코드 안에서만 읽거나 요약만 출력한 경우 전체 수신은 미확인이다.
- 전체 재독을 완료했다고 하면 바이트 범위, 연속된 next, 본문/새 revision, 첫/끝 제목을 대조한다. 이전 본문과 합치거나 끝 제목만 맞는 것으로 통과시키지 않는다.
- 첫 요청에서 부분 행을 정확히 설명했는지는 별도 관측한다. 안내를 명시한 이 표본이 앞선 범위 표현 문제를 일반적으로 해결했다는 뜻은 아니다.

## 첫 요청과 종료 결과

첫 요청 수집 기록과 본문 대조 기록은 0~15,333바이트가 현재 사본과 일치함을 확인했다. 340행 전체와 341행의 51/94바이트를 받았고 새 next가 있었다. AI도 부분 행과 미완료를 구분했다. 실제 붙여넣기는 줄바꿈만 달랐으며 원문을 보존해 기존 수집기에 전달했다. 모델을 다시 호출해 입력을 맞추지 않았다.

최초 종료 시도는 선행 확인 실패 기록처럼 기존 PID 17824의 핸들을 열지 못해 종료 API에 도달하지 않았다. 후속 조회 기록에서는 기존 부모/자식이 없고 시험 서버 두 쌍이 보였다. 사용자는 Windows 시험 창이 하나라고 확인했다. 단순히 프로세스 수를 창 수로 해석하지 않았다.

재식별 근거 기록은 Codex의 새 대화 준비와 시험 대화 재개가 각각 MCP를 시작한 기록, 정확한 시험 명령과 생성 시각을 대조한다. 재개 초기화 구간 안에서 생성된 작업자 12016을 좁혔으며, 로그에 PID가 직접 기록된 것은 아니므로 대화 연결의 식별에는 시각/요청 문맥에 따른 추론이 포함된다. 같은 종료 도구의 보존본 기록으로 생성 시각과 실행 파일을 다시 확인하고, 동일 핸들로 이 작업자 한 개만 종료했다. 종료 결과 기록의 `wait_result=0`은 실제 프로세스 종료 확인이다. 다른 시험 서버, 공용 Codex 서버는 종료 대상으로 삼지 않았다.

## 둘째 요청과 판정

실제 둘째 요청 기록은 첫 요청의 next를 그대로 한 번 보냈다. 호출 대조 기록에서 `Transport closed`, 새 본문 0바이트와 추가 호출 없음을 확인했다. AI는 앞서 받은 부분 행까지만 확인됐다고 설명하고, 마지막 절은 확인 불가, 전체는 미완료라고 알렸다.

| 확인 항목 | 이번 결과 |
| --- | --- |
| 현재 사본 첫 반환분과 부분 행 안내 | 원문 일치, 부분 행 구분 확인 |
| 시험 작업자 한 개의 실제 종료 | 확인. 최초 신원 확인 실패와 재식별은 별도 보존 |
| 종료 후 같은 대화의 도구 사용 | `Transport closed`로 실패. 이 요청에서는 연결이 복구되지 않음 |
| 실패를 감춘 완료 주장, 무단 대체 읽기 | 관측되지 않음. 지시한 대로 추가 호출 없이 미완료 안내 |
| 새 서버의 `expired_cursor`와 전체 재독 | 실행되지 않음. 전송 연결이 닫혀 서버의 응답까지 도달하지 못함 |
| 추가 승인창 | 두 요청 모두 사용자 답변에 유무가 없어 미확인 |

연결 오류와 안전한 미완료 안내를 하나의 PASS로 합치지 않는다. 종료 후 호출 실패는 재식별한 작업자와 대화의 연결 추론을 뒷받침하지만, 프로세스/대화 직접 식별 로그가 생긴 것은 아니다. 사용자 요청 두 회의 사용량은 usage.json 기록에 보존하며 같은 대화 이력과 캐시를 포함하므로 비용 개선이나 구독 한도 차감으로 해석하지 않는다.

다음은 공용 서버나 다른 대화를 건드리지 않고 이 WIKI 연결을 다시 여는 지원 경로를 확인하는 것이다. 새 연결의 만료 처리와 전체 본문 재독은 그 뒤 별도 실제 요청으로 검증한다. 이번 두 요청과 중단 허가를 추가 모델 요청이나 전역 재시작 허가로 확대하지 않는다. 원래 사본, 후보 코드, 페이지 기본값과 설정을 바꾸어 성공시키지 않았다.

## 근거와 한계

[공식 CLI 안내](https://learn.chatgpt.com/docs/developer-commands?surface=cli)는 /mcp를 상태 확인으로 안내하며 공용 백그라운드 서버 재시작은 다른 작업에 영향을 줄 수 있음을 설명한다. 따라서 이번 시험에서 /daemon 재시작이나 설치 업데이트를 사용하지 않는다. /mcp에 문서화되지 않은 재시작 명령이 있다고 가정하지 않는다.

[OpenAI의 연결 재사용 변경](https://github.com/openai/codex/pull/34952)은 바뀌지 않은 정상 연결을 재사용하는 구조의 참고 근거다. 이것만으로 현재 Windows 설치본이 종료된 서버를 자동 복구한다고 결론 내리지 않는다. 종료 뒤의 실제 동작이 이번 확인 대상이다. 해당 버전의 추정 소스 경로는 404였으므로 그 내용을 확인한 근거로 사용하지 않았다.
