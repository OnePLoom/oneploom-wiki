# 실제 Codex 수신 시험 준비

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 작업일은 2026-11-19다. [앞선 읽기 후보](2026-11-20_03-42-30-wiki-reader.md)를 실제 Windows Codex에 연결하기 위한 입력과 수집 절차를 준비했다. **새 시험 폴더 배치, MCP 활성화와 모델 요청은 아직 실행하지 않았다.** 제품 설치기의 완성이나 MCP 제공 확정과 구별한다.

## 이번에 확인할 것

사용자 요구는 MCP를 거쳐도 요청한 원문과 검색 결과가 누락되지 않는 것이다. 앞선 검사는 파일에서 읽은 내용과 SDK 전송을 확인했다. 이번에는 Codex가 남긴 도구 출력에서 무엇을 관측할 수 있는지 확인하고 독립 원문과 대조한다.

예를 들어 전체 문서가 여러 응답으로 나뉘면 각 응답의 본문 위치를 원문에 맞춰 빈 구간을 찾는다. 마지막 페이지를 받았다는 표시나 AI의 “완료” 답변만으로 중간 본문까지 받았다고 판단하지 않는다. 기록에 원문이 없으면 원문 해시나 검색 발췌로 대신 통과시키지 않는다.

## 입력과 실행 순서

새 Windows 시험 대화 한 개에서 다음 요청을 각각 한 번씩 순서대로 보낸다. 각 결과를 확인한 뒤 다음 요청으로 넘어가며, 실패를 무시하고 나머지 요청을 자동 실행하지 않는다. 기본 페이지의 정상 이어 받기는 같은 요청에 포함한다. 별도 재실행이 필요하면 원인과 영향을 먼저 확인한다.

| 순서 | 요청문 | 독립 사본에서 만든 기대값 | 확인할 점 |
| --- | --- | --- | --- |
| 1 | 구간 읽기 기록 | REQUIREMENTS.md의 1018~1035행, 끝 포함 18행, 1,328바이트 | 범위 해석, 본문 일치, 오류 표시 |
| 2 | 전체 읽기 기록 | 같은 문서 72,422바이트, 1,191행 | 첫 바이트부터 EOF까지의 본문, 이어 받기, 빈 구간, 중복과 잘림 |
| 3 | 문자열 검색 기록 | docs 범위의 QUERY_A, 대소문자 구분, 일치 줄 71개와 파일 9개 | 검색 범위, 모든 일치 위치, 발췌와 완료 표시 |

정답 개수와 전체 원문 해시는 시험 AI에 주지 않는다. 기대값 기록은 후보 코드를 import하지 않는 별도 바이너리/LF 순회로 만들었다. 원문과 보호한 사본 60개는 변경하지 않는다. 새 시험 폴더에는 같은 60개를 바이트 그대로 복사한다. 검색은 한 줄에 여러 번 나와도 한 결과로 세며 정규식 검색과 비교하지 않는다.

최종 답변은 상태만 짧게 받는다. 답변에 원문을 다시 출력하는 비용을 추가하지 않으며, 실제 읽기는 도구 출력에서 확인한다. 이번 요청은 범위가 정해진 수신 검사다. 자유 탐색의 답변 품질 비교는 이 단계 뒤에 남는다.

## 환경과 비용

실행 계획 기록의 대상은 `<WORKSPACE_PATH>`이며 project, wiki, source를 나눈다. source에는 앞선 contract.py, files.py, reader.py, server.py 네 개를 해시가 같은 상태로 복사한다.

후보의 기본 16,384바이트 논리 결과와 보호 경로 정책을 그대로 사용한다. local.json에는 프로젝트 ID와 Windows WIKI 경로만 쓰고 page_bytes를 덮어쓰지 않는다. 등록 설정에 모델, sandbox, 승인, 출력 한도나 timeout을 새로 넣지 않는다. 반환이 실제로 잘리면 원래 후보가 제공하는 재요청 처리를 관측하며 시험만 작은 기본값으로 바꾸지 않는다.

현재 읽은 Windows npm 패키지는 Codex 0.170.0이다. 이는 관측이며 실행 버전을 고정하지 않는다. 실제 TUI의 `/status`에서 버전, 모델, 추론 수준과 프로젝트를 다시 확인한다. 모델은 사용자의 현재 선택을 유지하고 별도 모델 인자를 주지 않는다. 도중 환경이 바뀌면 어떤 요청에 적용됐는지 구분한다. Python은 이미 있는 시험 venv를 사용하며 의존성이 없으면 설치하지 않고 알린다.

[공식 Codex MCP 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)는 도구별 출력 토큰 설정과 호스트 timeout을 설명한다. 이 시험은 그 값을 바꾸지 않으며 문서의 기본값을 현재 세션의 유효값이라고 단정하지 않는다. 모델/호스트의 최종 한도나 비공개 전송 본문을 알기 위해 별도 AI 또는 App Server를 띄우지 않는다.

초기 요청은 총 세 번이다. 실제 도구 호출과 내부 추론 횟수, 이어 읽기나 재요청에 따른 토큰은 고정하지 않는다. 읽기 요청의 원문 합계는 73,750바이트이고 검색 결과 71개에는 별도 본문 발췌와 메타데이터가 붙는다. 이 바이트 수를 토큰 수로 환산하거나 무료라고 표시하지 않는다. 실행 후 실제 사용량과 캐시, 호출 수, 재시도와 사용자 개입을 기록한다. 세 요청 한 표본으로 비용 우위나 일반 신뢰성을 주장하지 않는다.

## 배치와 사용자 조작

prepare.py 기록은 인자 없이 실행하면 계획만 보여준다. `--apply`는 사용자가 구체안을 확인한 뒤 Windows Python으로 실행한다. 새 대상만 만들고 기존 폴더가 있으면 중단한다. 후보/사본 해시와 준비 도구를 확인한 다음 복사하며, 코드와 사본을 준비한 뒤 마지막에 프로젝트 MCP 설정을 놓는다. 실패한 새 폴더를 자동 삭제하거나 기존 시험을 덮지 않는다.

등록 초안 기록은 실제 프로젝트 밖의 준비 파일이다. 현재 Codex가 읽는 설정에 추가한 것이 아니다. 배치할 때 새 시험 프로젝트에만 복사하며 사용자 전역 설정을 편집하지 않는다. 절대 경로 등록은 이 한 시험의 연결 입력이며 최종 제품 설치와 재연결 전체를 검증하는 방식은 아니다. 공유 설정/로컬 경로 계약의 미검증을 지우지 않는다.

배치와 보존 확인 뒤 Windows PowerShell에서 새 시험 프로젝트로 이동하고 `codex.cmd`로 시작한다. 이번 환경에서 이미 수용한 진입 방식이며 다른 사용자 명령을 고정하지 않는다. 신뢰나 도구 승인이 나오면 해당 시험 경로인지 확인하고 실제 승인 횟수를 기록한다. `/mcp`에서 wiki_reader가 연결됐는지 확인한 뒤 첫 요청을 보낸다. 기존 WSL 설계 세션과 이전 시험 세션을 임의로 종료하지 않는다.

요청문은 준비 파일의 내용을 그대로 사용한다. 과거 붙여넣기에서 줄바꿈이 달라진 기록이 있어, 필요하면 별도 PowerShell의 `Get-Content -Raw -Encoding UTF8 -LiteralPath <요청문 파일> | Set-Clipboard`로 복사한다. 이 단계는 사용자가 실행하는 클립보드 조작이며 자동으로 AI 요청을 보내지 않는다. 구체 명령과 첫 요청은 배치 완료 뒤 제공한다.

## 기록과 판정

capture.py 기록은 사용자가 알려준 Session과 새 프로젝트 경로, 요청문이 일치하는 실행 한 개만 수집한다. 재시도 때문에 같은 요청이 여러 번 있으면 turn_id까지 지정해야 한다. 시스템 지침, 숨겨진 추론, 계정 정보와 다른 요청은 저장하지 않는다. 알려진 비밀값 형태가 발견되면 저장을 중단하지만 이 검사만으로 모든 비밀값 부재를 보증하지 않는다.

수집 결과는 `captured_not_graded`다. 새 로그의 실제 표현을 확인한 뒤 다음 항목을 대조한다. 수집기가 성공했다는 이유로 아래 검사를 통과시키지 않는다.

1. 도구 호출과 출력의 연결, 현재 모델/환경, 실제 사용 도구를 확인한다. exec가 여러 결과를 합치거나 일부만 출력했는지도 읽고, 서버 원문과 모델이 작성한 요약을 구별한다.
2. read_note 본문의 UTF-8 바이트를 독립 사본의 span과 비교한다. 모든 요청 구간이 채워졌는지, revision과 줄 위치, next와 종료 표시가 맞는지 확인한다. 같은 cursor의 재시도 중복과 서로 다른 내용의 충돌을 구분한다.
3. search_notes의 경로, 줄, revision, 원문 내 일치/발췌 위치를 기대값과 비교한다. 누락, 범위 밖 결과, 중복과 제외 경로, 마지막 complete를 확인한다. 발췌를 전체 문서 수신으로 세지 않는다.
4. 잘림 표시, 파싱할 수 없는 출력, 도구 오류와 원문 부재를 구별한다. 본문/next가 관측되지 않으면 미확인 또는 미완료로 남기며, 끝 위치나 모델의 주장으로 보충하지 않는다.
5. AI 최종 답변의 완료 주장과 관측 결과가 맞는지 확인한다. 명확한 실패가 있으면 해당 실패를 보완하고 영향받은 검사부터 재개한다.

과거 기록에서는 functions.exec의 출력 안에 구조화 응답을 출력하거나 여러 질의를 묶은 형태를 확인했다. 새 환경에서도 같은 형태라고 가정하지 않는다. Codex 로그에서 일치한 본문을 보더라도 그것이 **최종 모델 요청에 그대로 포함됐음을 직접 관측한 것**은 아니다. 그 경계는 미확인으로 남기며 실제 답변 검토와 분리한다. 로그 출력이 잘렸다는 사실만으로 서버가 누락했다고 단정하지도 않는다.

## 준비 검증과 남은 순서

수집 검사 기록은 WSL에서 실행한 오프라인 수집기 검사다. 다른 요청/추론 혼입, 잘못된 세션/프로젝트/요청, 반복 실행 선택, 미완료 구별과 사용량 보존을 검사했다. 합성 검사 5개가 통과했고, 11/18의 실제 보존 로그를 재수집한 도구 이벤트 14개는 기존 수집본과 같았다. 새 Windows Codex 사용 검증은 아니다.

최초 과거 로그 재사용 시 입력 불일치 기록가 있었다. 예전 결과에도 prompt_exact_match가 false였으며 붙여넣기 줄바꿈/들여쓰기가 계획 파일과 달랐다. 수집기의 엄격한 비교를 없애지 않고 실제 기록된 요청으로 별도 수집 검사를 진행했다. 과거 실험이나 질문 일치 상태를 성공으로 바꾸지 않았다. prepare.py의 문법과 미적용 미리보기만 확인했으며 Windows 배치는 아직 실행 전이다.

다음은 구체 입력과 현재 모델 사용, 초기 세 요청에 대한 확인을 받은 뒤 새 시험 배치와 보존 확인, TUI 연결, 구간 요청부터 진행하는 것이다. 실제 수신과 추가 실패를 확인한 뒤 자유 탐색의 품질/비용 비교로 이동한다. 첫 MCP 제공 판단, 쓰기/복원과 전체 제품 설치는 그 뒤의 기존 순서를 유지한다.
