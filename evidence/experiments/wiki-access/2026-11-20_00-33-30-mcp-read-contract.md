# MCP 읽기 계약의 입력 근거

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

이 기록은 사용자 지정 11/19 작업의 후속이다. 관측 시각은 폴더의 UTC 시각이며, 사용자 작업일/TIL 경계를 자동 변경하지 않는다. **보존된 사본의 정적 계수와 현재 Windows 설치본의 설정 파싱 확인**이다. 배포 후보를 실행하거나 MCP 원문 수신을 검증한 결과가 아니다.

## 사본의 분포

앞선 비교에서 보존한 사본 60개를 WSL Python으로 읽었다. 원문은 옮기거나 수정하지 않았다. 계수 코드 기록은 파일을 읽고 UTF-8 바이트/줄과 문자열 검색 분포를 corpus.json 기록에 기록한다. Windows SDK나 서버를 실행하지 않으며 Windows 성능 시험으로 해석하지 않는다.

| 항목 | 관측 |
| --- | ---: |
| 문서 수 / 합계 | 60개 / 391,937바이트 |
| 파일 크기 중앙값 / 95번째 백분위 | 3,098 / 18,193바이트 |
| 최대 파일 | 72,422바이트 |
| 줄 수 / 최대 줄 | 8,317개 / 355바이트 |
| 문자열 `블록` | 28개 파일, 541개 일치 줄, 일치 줄 본문 48,558바이트 |
| 문자열 `브라우저` | 10개 파일, 32개 일치 줄, 일치 줄 본문 3,496바이트 |
| 문자열 `p99` | 대소문자를 구분하는 이 문자열 조건에서는 0개 |

검색은 의미 검색이나 MCP 실행이 아니다. 0개 결과도 동일 의미의 요구사항/수치가 문서 어디에도 없다는 근거가 아니다. 여러 번 일치하는 한 줄은 한 결과로 계수했다.

| 비교할 본문 묶음 크기 | 본문만 한 묶음에 드는 파일 | 전체 본문의 산술 묶음 수 하한 |
| --- | ---: | ---: |
| 8KiB | 46 | 86 |
| 16KiB | 55 | 68 |
| 32KiB | 59 | 62 |
| 64KiB | 59 | 61 |

이는 나눗셈으로 계산한 분포이며 도구의 실행 제한으로 적용한 값이 아니다. 실제 결과는 메타데이터/이스케이프/SDK 표현 때문에 달라지고 실제 호출/토큰 수와 같지 않다. 이 자료를 근거로 **논리 결과 한 페이지 16KiB 후보**를 제안했으나 실제 수신과 비용 검증은 남는다. 최대 줄이 작으므로 긴 한 줄의 UTF-8/CRLF 경계 사례는 별도로 준비해야 한다. 이 한 프로젝트의 분포를 모든 사용자 규모의 대표값으로 취급하지 않는다.

## Windows 설치본에서 확인한 것

기존 시험 위치의 npm 패키지와 vendor 메타데이터는 0.170.0이다. 현재 사용자의 모든 PATH 후보를 재탐색한 결과나 배포 버전 고정이 아니다. 조회 기록 기록에 도움말, 일회성 config 인자와 결과를 보존했다.

1. 첫 도움말 실행은 sandbox의 WSL interop 오류로 Windows 진입 전에 실패했다. 허용된 같은 읽기 전용 실행으로 도움말을 확인했다.
2. debug prompt-input에는 프롬프트 입력 옵션이 있지만 도움말에서 과거 대화/도구 결과 수신을 지정하는 인자를 확인하지 못했다. 이 명령을 실제 대화 수신 대조 수단으로 확정하지 않았고 본 실행도 하지 않았다.
3. `mcp get`에 실행되지 않는 합성 서버 정의와 `output_token_limit="invalid-type-probe"`를 일회성 인자로 주자 해당 키에서 nonzero usize 타입 오류가 발생했다.
4. 같은 조회에서 값 1은 파싱됐고 종료 코드 0이었다. 응답은 서버 연결 정보만 보여 주며 도구별 설정값은 노출하지 않았다. **1은 파싱 경계 입력**이며 설정 파일에 저장하거나 모델/서버의 실제 출력 제한으로 적용한 값이 아니다.

확인한 것은 현재 설치본의 설정 키 파싱 지원이다. 현재 대화의 적용값, 모델 기본 출력 한도, 수신 잘림이나 16KiB 후보의 성공은 확인하지 않았다. 조회 중 모델, MCP 서버, TUI나 새 대화를 시작하지 않았고 전역 설정을 수정하지 않았다.

## 설계와 남은 확인

[MCP 읽기 명세](../../../design/integration/mcp.md)에 초기 요청과 cursor 이어 요청, 부분 줄의 바이트 범위, page_bytes 후보와 축소 재요청을 연결했다. cursor는 조회 진행 정보이며 SQLite/active에 새 작업을 만들지 않는다. 검색의 짧은 발췌와 전체 원문 읽기도 구별한다.

새 숫자를 시험 전용으로 덧붙이지 않고 후보 코드/설정으로 [R-01~14 — 「MCP 읽기 보완의 검증 입력」](../../../verification/acceptance.md)를 확인해야 한다. 구조화/텍스트 중복, 실제 호스트 수신, 긴 줄/많은 파일의 시간과 메모리, 오류/취소와 모델의 이어 요청을 검증한 뒤 첫 제공을 판단한다. 사본 분포만으로 별도 탐색 파일수/전체 바이트 제한을 정하지 않았다. 새 모델 요청의 입력/모델/반복/비용은 실행 전에 구체화한다.

## 출처와 보존

- [Codex MCP 공식 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli): 도구별 output_token_limit과 직렬화 여유 설명을 확인했다. 토큰 설정을 원문 UTF-8 바이트와 동일시하지 않는다. 현재 공개 설명과 설치본 파싱 관측을 구별한다.
- [MCP 페이지 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination): 불투명 cursor와 이어 요청의 개념을 참고했다. 표준의 대상은 list 연산이며 우리 read_note/search_notes에 자동 적용되는 기능은 아니다.
- [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools): 구조화 결과/텍스트와 오류 구분은 앞선 설계 근거를 유지한다. 이 기록에서 외부 구현을 복사하거나 새로운 패키지를 설치하지 않았다.
