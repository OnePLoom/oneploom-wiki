# MCP 검색과 읽기 묶음 후보

자료명은 관측에 사용한 근거를 식별한다. 개별 파일의 제공 범위는 [기록 기준](../../recording.md)을 따른다.

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

사용자 지정 작업일은 2026-11-21이다. 후보 작성은 11/21, 중단 후 Windows 검사는 실제 UTC 11/22에 실행했다. 원시 검사 시각을 작업일에 맞춰 바꾸지 않았다.

## 왜 바꿨는가

[이전 비교](2026-11-21_04-48-10-mcp-comparison-run.md)에서 반복된 검색/읽기 호출, 변형된 이어 검색 값과 답변의 필수 예외 누락을 관측했다. 사용자는 여러 파일 읽기까지 포함해 문제를 함께 보완하도록 선택했다. 기존 두 도구를 확장하고 원문/오류 보호를 유지한 후보를 구현한 뒤 같은 Windows 환경에서 실제 두 요청을 비교했다. 호출은 줄었지만 값 전달 오류와 캐시 제외 토큰 증가는 남았다.

## 바뀐 동작

- `search_notes`는 기존 query 또는 복수 queries를 받는다. 대소문자를 구분하는 리터럴 OR 검색이며, 같은 줄은 한 번만 반환한다. query_matches는 검색어별 첫 일치 위치와 입력 배열의 0부터 시작하는 query_index를 연결한다.
- `read_note`는 기존 path/줄 범위 또는 requests를 받는다. 겹친 같은 파일의 본문은 한 번만 보내고 request_indices와 span으로 원래 요청을 연결한다. 같은 내용의 다른 파일은 출처가 다르므로 합치지 않는다.
- 페이지 크기는 묶음의 전체 JSON에 적용한다. 처음 파일이 크더라도 다음 요청을 버리지 않으며, next로 원래 범위의 나머지를 이어 받는다. UTF-8, BOM, 개행과 부분 줄 위치를 보존한다.
- 없는 파일, 접근 거부, 잘못된 인코딩과 범위 밖 요청은 errors에 남긴다. 정상 본문은 results에 보존하지만 MCP 오류 표시인 isError를 유지한다. next가 없어도 errors가 있으면 complete=false, partial_error로 끝난다.
- 이어 요청 때 파일별 기준을 다시 확인하고 마지막 완료 전에 이미 읽은 파일도 재확인한다. 중간 변경이나 실패 상태 변경은 옛 결과와 합치지 않는다. 여러 파일을 같은 순간에 고정하는 기능은 아니다.
- 서버 설명에 정확한 next 객체 재사용과 직전 입력 보존을 연결했다. 호스트 호출 예시 기록은 긴 값을 다시 작성하지 않고 보관한 객체를 전송한다. 새 서버 도구, DB, 색인이나 별도 AI는 추가하지 않았다.

예를 들어 A 문서 1~20행과 10~30행, 없는 B 문서를 함께 요청하면 A의 10~20행 본문을 중복 전송하지 않는다. 어느 요청의 구간인지 표시하고 B의 not_found도 남긴다. A를 읽은 사실과 전체 요청의 미완료를 동시에 보존한다.

실패는 첫 결과 기록과 수정 이유 기록에 남겼다. 긴 검색어와 짧은 검색어가 같은 줄에 있으면 긴 일치를 발췌의 최소 크기로 골라 page_too_small을 잘못 반환했다. 모든 일치 위치는 보존하고 온전히 담을 수 있는 짧은 일치를 발췌 기준으로 삼아 수정했다. 관련 재검사는 통과했다.

합성 큰 파일과 작은 page_bytes는 코드 경계를 확인한 입력이다. 실제 Codex의 한도를 바꾸거나 출력 잘림을 재현한 것처럼 해석하지 않는다. SDK 관측기의 교착 감지 상한도 제품 시간 제한이 아니다. 위 코드/SDK 검사는 모델 호출 없이 수행했고 이후의 실제 AI 비교는 아래에 구분한다.

## 실제 비교 결과

사용자가 승인한 기존 MCP 한 요청과 개선 MCP 한 요청을 Windows PowerShell의 새 대화에서 각각 완료했다. 둘 다 Codex 0.171.0, GPT-5.6-Sol low, Workspace였고 추가 승인창이 없었다. 문서 사본은 각각 같은 60개다. 요청문 대조 기록에서 두 실제 입력은 서로 같고 준비본과는 붙여넣기 공백/줄바꿈만 다름을 확인했다. 두 요청을 다시 실행하거나 실패한 호출을 집계에서 빼지 않았다.

비교 집계 기록, 기존 사용량 기록, 개선 사용량 기록은 응답별 합계와 누적 기록의 일치를 확인한 값이다. 캐시 입력을 다시 더하지 않으며 reasoning 출력도 출력 토큰에 포함된다. 어느 합계도 Pro 구독 차감량이나 청구액이 아니다. 각 한 번의 알려진 회귀 사례이고 실행 순서, 캐시, 서비스 변동과 AI의 탐색 선택은 통제하지 못했다. 이전 직접 접근 수치는 별도 참고로 남긴다.

기존 답변 검토 기록과 개선 답변 검토 기록은 원문과 실제 수신 구간을 대조했다. 두 답변 모두 선택적 초기 content, 세션/문서 복구의 경계, 5분 테스트 기준과 영구 삭제 제외, 확정 p99 기준 부재를 반영했다. 기존본도 이번에는 필수 예외를 포함했으므로 과거 누락과 개선본만 비교해 품질 개선율을 만들지 않는다.

### 실패와 실제 사용의 차이

- 기존 수신 대조 기록은 읽기 8회와 검색 11회의 반환을 원문에 대조했다. 이어 검색 두 입력도 발행값과 같았다.
- 개선 수신 대조 기록은 정상 읽기/검색의 본문, 위치, 원래 요청 번호를 대조했다. 겹친 REQUIREMENTS 1028~1032행은 한 번 반환되고 두 요청 번호에 연결됐다. 실제 호스트 출력 잘림은 관측하지 않았다.
- 개선본은 반환된 next를 코드 저장값으로 재사용하지 않고 긴 cursor를 다시 입력했다. 검색값은 528자에서 527자로 달라져 본문 해석도 불가능했고, 묶음 읽기값은 같은 1,052자 안에서 REQUIREMENTS.md가 REQUIREMEMENTS.md로 바뀌었다. 두 경우 서명 부분은 같지만 내용이 달라 expired_cursor로 거절됐다. 시간 만료나 서버 재시작이 원인이라는 증거는 아니다.
- 묶음 읽기 첫 입력의 page_bytes=22000은 등록 상한 16384보다 커 invalid_arguments로 거부됐다. AI가 15000으로 고쳐 같은 논리 읽기를 다시 요청했다. 이는 실제 출력 잘림 후 축소 재시도나 호스트 한도 조회 성공이 아니다. 양쪽의 기본 설정은 같았고 서로 다른 크기는 AI가 선택했다.
- 개선본의 광역 검색 네 개와 첫 유효 묶음 읽기는 next가 남았다. 필요한 사실은 후속 범위 읽기로 확보했지만, 앞선 요청 전체를 완료했다고 판정하지 않는다. 최종 답은 cursor 실패를 알렸으나 시간 만료로 표현했고 page_bytes 오류는 빠뜨렸다.

**묶음 처리는 실제 사용됐지만 정확한 값 전달의 통합은 미완료다.** source/next-call.js는 호출 예시이며 실제 대화에서는 store/load를 사용하지 않았다. 지침과 모의 검사만으로 자동 연결이 된 것처럼 판단하지 않는다. 다음에는 원문/서명 검사를 유지하면서 긴 값의 재작성과 페이지 설정의 추정을 줄일 호출 계약을 먼저 구체화한다. 이번 측정 중 후보를 고치거나 추가 AI 요청을 하지 않았다.

보존 검사 기록은 원본 86개, 시험 코드/사본/설정 134개, 제품 Git과 닫힌 근거 42개를 확인했다. 전역 설정의 전체 TUI 전후 불변은 측정하지 않았으며 평가 코드에서 수정하지 않았다. 분석기에서 출력 형식과 손상 cursor를 잘못 가정했던 실패도 분석 이력 기록에 보존했다.

## 남은 한계

- Windows Codex가 부분 오류의 본문을 모델에 실제로 전달하는지와 store/load의 지원, 호출 간 보관, 취소/재개 뒤 수명은 아직 확인하지 않았다.
- 호출 예시의 receivedPrevious는 호출자가 직전 본문을 온전히 확인했다는 표시다. 저장 성공이나 이 값 자체가 실제 수신을 증명하지 않는다. 한 응답을 출력하고 확인한 뒤에만 다음 값을 사용하며, 잘림 때는 저장한 sent를 재사용한다.
- 호스트 잘림 판단과 최대 두 번 축소는 여전히 AI 실행 지침이다. 새 예시가 자동 복구 엔진이나 기계적 총호출 제한을 구현한 것은 아니다.
- 긴 cursor/입력 메타데이터가 전체 페이지에 들어가지 않으면 조용히 생략하지 않고 분할 필요를 알린다. 모든 크기의 요청을 한 번에 처리하거나 파일 재검사 비용이 없다고 보장하지 않는다.
- 값 검증 실패의 기존 expired_cursor 코드는 실제 시간 만료를 입증하지 않는다. 안내는 현재 연결에서 값을 확인할 수 없다고 하며, 서명 실패만으로 재시작과 입력 변형을 구별하지 않는다.
- 이번 후보는 읽기/검색이다. 세 질문의 필수 사실 반영과 위 사용량은 관측했지만 쓰기, 첫 배포 전체, 일반적인 답변 완전성과 비용 우위는 검증하지 않았다.

## 다음 실제 비교

실행안 기록은 **같은 현재 Windows Codex/모델에서 기존 MCP 1회와 개선 MCP 1회**를 새 대화로 비교하는 안이다. 둘 다 같은 문서 사본 60개와 같은 질문 기록을 사용한다. 세 질문을 포함한 사용자 요청 한 회씩이며 내부 모델 응답과 도구 호출은 여러 번 생길 수 있다.

새 위치는 `<WORKSPACE_PATH>`이다. 배치 코드 기록의 기본 실행은 해시/의존성/대상 부재를 확인하는 미리보기다. 미리보기 결과 기록은 사본 120개와 후보 코드 8개의 준비를 확인했다. 사용자가 두 요청 비교를 수용해 새 Windows 폴더에 배치를 마쳤다. 배치 대조 기록은 후보/문서/설정 134개를 확인했고 배치 전후 전역 설정 해시는 같았다. 이 절은 실행 전 준비 기록이며 승인한 두 요청의 결과는 위 「실제 비교 결과」에 연결한다. 기존 연결, 원문, 전역 설정을 교체하지 않으며 정답표는 시험 프로젝트 밖에 뒀다.

품질을 먼저 판정하고 모든 실패/재시도 비용도 포함했다. 설치본이나 모델이 바뀐 결과를 과거 단건에 곧바로 개선율로 붙이지 않기 위해 같은 환경에서 전후 후보를 함께 실행했다. 직접 접근은 기존의 별도 기준이다. 한 쌍은 알려진 회귀 사례이며 통계적 일반화나 별도 확인용 표본을 대신하지 않는다. 승인한 두 요청 기록은 모두 끝났고 현재 실행 대기는 없다. 추가 AI 실행은 새 입력/범위/비용을 구체화한 뒤 판단한다.
