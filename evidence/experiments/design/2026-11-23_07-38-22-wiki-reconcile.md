## 판단과 이어서 수행한 명세

공식 근거 대조 기록과 기존 요구를 확인한 결과 B안이 현재 제약에 가장 맞는다고 판단했다. 외부 관리 도구와 wheel은 공식 배포 자료, 기기 명령은 사용자 프로그램 영역, 편집 가능한 하네스는 프로젝트, 개인 WIKI 경로/상태는 로컬 제외 영역으로 구분한다. 모든 팀원의 최초 기기 준비가 필요하다는 비용은 유지된다.

명령만 준비하는 `oneploom.py command install`의 진입, 현재 등록 재사용, 프로젝트 없는 기록, 준비/적용/확인과 수용 입력을 연결했다. 최초 담당자의 프로젝트 install도 같은 등록 절차를 사용한다. 새 준비를 command repair나 connect에 숨겨 추가하지 않는다. 이는 명세이며 아직 실제 배포 명령이 아니다.

## 검증 범위와 남는 일

전체 문서의 링크/제목/형식을 검사하고 변경 전 사본, ADR 날짜, 역사 문서, 닫힌 근거, 제품 추적 원본/Git 상태를 대조한다. 주제별 의미 판단은 review.json에 별도로 기록하며 자동 링크 검사를 의미 검토의 대체로 사용하지 않는다. 편집 중 잘못된 종료 제목으로 멈춘 건은 edit-attempts.json에 보존하고 완료한 편집을 반복하지 않았다.

명확한 보정은 완료 대상으로 삼으며 새 정책을 추측해서 확정하지 않는다. 저장소/브랜치의 실제 생성, 공개 시점/범위와 배포 라이선스는 기존 5단계에서 선택할 항목이다. 기기 효과의 DDL/저장 구현, 실제 wheel/환경 등록, 지원할 두 Codex 설치 형태와 Windows 사용자 흐름은 구현 후 검증한다. 기존 SQL/도구 샘플의 PASS로 대체하지 않는다.

이번에 제품 코드, Git 저장소/커밋, 전역 Codex/PATH, Windows 시험 파일이나 실행 중 프로세스를 변경하지 않았으며 새 모델 실행도 없다. 외부 자료의 전수 최신성 검사나 실제 제품 무결함을 주장하지 않는다.
