# 문제 기록과 측정 근거

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

OnepLoom의 설계 판단에 사용한 예비 관측과 검증 근거를 연결한다. 현재 제품의 검증 상태와 과거 시험의 확인 범위를 구별한다.

## 기록 위치와 보존

- `issues.md`: 문제, 위험, 개선 후보의 짧은 대장. 원인과 영향이 큰 사례만 상세화한다.
- [cases/](cases/README.md): 문제, 분석, 대안 선택과 검증 결과를 연결하는 상세 트러블슈팅 기록. 개별 실행의 조건과 한계는 아래 관측 목록에서 확인한다.
- `experiments/<주제>/YYYY-MM-DD_HH-MM-SS-<관측명>.md`: 실험 조건, 결과와 한계를 설명하는 관측 문서. 파일명 시각은 KST이며 원시 실행 ID, 설계 작업일과 구분한다. 제공 자료의 범위는 [기록 기준](recording.md)을 따른다.
- 에이전트가 문제를 인지했을 때와 관련 검증 후 수동으로 기록한다. 모든 오류를 자동 포착하는 장치는 아직 없다.
- 개발 판단을 뒷받침하는 관측 기록을 유지한다. 제품의 로컬 복구 자료 보관/정리는 [별도 계약](../design/workflow/maintenance.md)을 따른다.
- 기존 대화에서 확인한 내용도 근거가 없으면 회고로 표시한다. 과거 소요 시간, 오류 횟수, 개선율을 추정해 채우지 않는다.

관측 시각과 설계 작업일의 구분은 [기록 시각과 작업일](recording.md#기록%20시각과%20작업일)을 따른다. 묶음 후보의 11/21 구현/부분 검사와 11/22 실제 AI 비교를 같은 날의 실행 결과로 합치지 않는다.

## 설계 근거와 구현 확인

2026-11-23 사용자 요청에 따라 설계부터 구현, 검증과 결과 설명까지 적용한다. 비교와 추천은 계속하되, 아직 확인하지 않은 전제를 증명된 사실처럼 사용하지 않는다.

| 근거 | 확인할 수 있는 것 | 확대하면 안 되는 주장 |
| --- | --- | --- |
| 공식 규격과 문서 | 명시된 조건에서 제공하는 계약과 제약 | 문서에 없는 동작, 모든 버전/환경의 호환성 |
| 확인한 공개 소스 | 해당 처리와 경계가 실제 코드로 존재함 | 우리 요구 전체 충족, 결함 없음, 우리 조합의 실행 성공 |
| 직접 실행한 부분 검사 | 기록한 입력, 환경과 판정 항목의 결과 | 다른 조건, 전체 제품이나 실제 사용자 흐름의 성공 |
| 배포 후보의 실제 사용 검증 | 시험한 지원 환경과 사용자 흐름의 결과 | 모든 규모/환경의 성공, 발견하지 못한 결함의 부재 |

- 핵심 판단에는 주장, 출처/버전 또는 조회 시점, 적용 조건, 확인 결과와 남은 한계를 연결한다. 외부 소스의 변경 가능한 브랜치를 읽었으면 고정 커밋을 확인한 것처럼 기록하지 않는다. 실제 의존성 채택과 배포 때는 사용할 버전 및 권리 조건을 확인한다.
- 선택안을 채택했다는 사실은 구현 성공이 아니다. 문서에 없는 조합이나 우리 제품의 경로, 권한, 중단 복구처럼 결과를 좌우하는 부분은 필요한 범위의 실현성 검사를 먼저 하고, 배포 후보에서는 [실제 사용 환경의 검증](README.md#%EC%8B%A4%EC%A0%9C%20%EC%82%AC%EC%9A%A9%20%ED%99%98%EA%B2%BD%EC%9D%98%20%EA%B2%80%EC%A6%9D)까지 연결한다.
- 실험 전 예상은 검증할 가설로 표시한다. 측정하지 않은 시간, 토큰, 오류율과 절감률을 채우지 않는다. 비교에서는 품질, 보존, 실패 처리 조건이 같았는지도 함께 확인한다.
- 근거가 부족하면 미확인 사항과 다음 확인 방법을 밝힌다. 설계에 영향을 주는 미확인을 숨긴 채 안전한 자동화나 구현 가능성을 확정하지 않는다. 확인 가능한 부분의 작업과 아직 판단할 수 없는 부분을 구분한다.
- 같은 제품의 선례가 반드시 있어야 한다는 뜻은 아니다. 확인된 구성 요소를 조합할 수 있지만, 그 조합의 작동은 별도로 입증해야 한다. 시험을 통과해도 검증 범위 밖의 완전한 무결함을 보장하지 않는다.

이 기준은 개발 WIKI의 근거 관리 규칙이다. 기술 판단과 관측 결과를 공유하되 계정 원시 로그나 실행 중 로컬 상태를 공개한다는 의미는 아니다.

## 문제를 발견했을 때

대장에는 ID, 문제와 영향, 근거 유형, 현재 상태, 다음 확인 또는 측정 항목을 남긴다. 사소한 관리 작업까지 억지로 기술 검토 사례로 만들지 않는다.

근거 유형은 다음을 구분한다.

- 관찰: 원시 실행 결과나 현재 파일로 확인했다.
- 회고: 이전 대화에서 발생했지만 당시 원시 자료가 보존되지 않았다.
- 정적 관찰: 코드, 문서의 구조로 확인했으나 실제 실패나 피해를 재현하지 않았다.
- 미검증 위험: 가능한 문제이며 발생 여부부터 확인해야 한다.

상세화할 사례에는 아래 항목을 추가한다.

1. 문제 정의: 기대 동작, 실제 증상, 영향받는 사용자, 작업, 발견 시점과 근거.
2. 재현 조건: 코드 revision, 미커밋 변경, 입력과 판정 기준, 명령, 환경, 도구 버전. 모델을 쓴 경우 모델 ID, 설정, provider도 기록.
3. 분석: 확인한 사실과 원인 가설, 비교한 대안, 채택, 기각 이유, 본인이 결정, 검증한 부분.
4. 변경과 결과: 전후 실행 ID, 표본 수, 분모, 실패 수, 남은 한계. 미측정은 미측정으로 유지.
5. 재발 방지: 회귀 사례, 기대 판정의 근거, 다음 확인과 공개 후보 여부.

11/20 [MCP 조회 비용 사례](cases/mcp-cost.md)를 상세 기록으로 시작했다. 개선 전과 개선 후는 같은 대상의 변경 전후로 구분하고 직접 접근 같은 다른 방식은 별도 비교 기준으로 표시한다. 11/21 후보 구현/코드 검사 뒤 11/22 실제 전후 비교를 마쳤고 입력 오류/비용 한계를 남겼다. 이후 [직접/긴 값/짧은 값의 실제 세 요청](experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)도 완료했다. 짧은 값 전달은 보존됐지만 입력 오류, 검색 미완료 보고와 답변 일부 누락이 남아 동등 품질의 절감으로 판정하지 않았다. 11/22 직접 접근 우선/MCP 후속을 채택했으며 [결정 기록 — 「11월 22일 첫 제공 범위」](../decisions/runtime/0022-wiki-entry.md)과 사례에 연결했다.

## 수치화 후보

아래는 측정 설계 후보이지 이미 확보한 성과나 확정 요구사항이 아니다.

| 질문 | 측정할 값 | 해석의 제한 |
| --- | --- | --- |
| 필요한 게이트를 누락하는가 | 누락 건수 / 사전 정답상 게이트가 필요한 사례 수 | 불필요한 활성화 건수도 반대 집합에서 함께 측정 |
| 실패를 성공으로 보고하는가 | 성공으로 오판한 건수 / 주입한 실패 사례 수 | 계획 산출 성공, 게이트 비활성, 실제 테스트 통과를 구분 |
| 재개 뒤 제약과 미완료 검증을 복구하는가 | 두 항목을 모두 복구한 횟수 / 실제 재개 시도 수 | 수동 문서 읽기나 hook 단위 테스트를 실제 compact 성공으로 대체하지 않음 |
| 검증 비용을 줄이는가 | 동일 품질 기준의 작업 성공률, 전체 시간, 불필요한 검증 횟수 | 필수 검증을 빼서 빨라진 결과는 개선으로 인정하지 않음 |
| 다른 프로젝트, 실행기로 옮길 수 있는가 | 설치 성공 수 / 대상 수, 코어 수정 파일 수, 설정 변경량, 설치, 검증 시간 | provider 교체, 실행기 교체, 프로젝트 이식을 별도 실험으로 구분 |
| 모델 비용이 줄어드는가 | 실제 사용량의 입력, 캐시, 출력 토큰, 요금 근거와 성공 작업당 비용 | 파일 수, 글자 수로 토큰 절감을 단정하지 않음. 로컬 추론 자원 비용도 무료로 간주하지 않음 |

## 실제 사용 환경의 검증

11/10 사용자 지시와 11/18 재확인에 따라 모듈의 모든 검증/실제 사용 관련 작업에 적용한다. 실행 전에 [실제 사용 환경과 검증 조건](../design/workflow/verification.md)을 대조하고 배포 후보의 코드, 유효 설정, 제한의 값/단위/출처, 실행 진입과 사용자 상호작용을 기록한다. 미정 값을 임의로 채운 내부 시험은 실제 사용 검증으로 인정하지 않는다.

- 실행 전에 지원 대상 사용자의 실제 경로와 시험 경로를 대조한다. OS, 파일시스템, 도구 버전, 터미널/CLI 진입, 권한/신뢰, WIKI 위치 중 결과에 영향을 주는 조건과 차이를 명시한다. 작성자의 개발 사본, 시험 전용 설정이 있어야만 성공하는 결과를 일반 설치 성공으로 보고하지 않는다.
- 단위, 부분 연결, 모의 시험은 유지하되 실제 설치, 사용의 검증과 구분한다. 일반 터미널 사용은 해당 진입으로, 모듈이 자식 CLI를 실행하는 기능은 그 실제 호출 경로로 확인한다. 에이전트 도구 안의 중첩 실행, app-server 직접 호출, 대체 provider, 수동 연결이 실제 사용을 대신하는지 확인 없이 동일시하지 않는다.
- 실제 적용 완료는 배포 후보와 안내 절차를 사용해 설치부터 해당 기능의 결과, 보존, 재개까지 확인한 근거로 판정한다. 아직 제품이나 환경이 준비되지 않았으면 부분 확인, 미검증으로 남긴다. 지원 조합과 표본을 밝히고 일부 검사 통과를 전체 수행률, 모든 사용자 환경의 호환성으로 환산하지 않는다.
- 실패와 제한은 발생 단계, 설정 주체, 재현 조건을 기록한다. 시험 관측기의 대기 제한, hook 제한, 모델/네트워크 실패, 예제 설정의 숫자를 구분한다. 환경을 바꿔 재실행했다면 실제 다시 확인한 범위만 표시하며 이전 검사 전체가 재검증됐다고 확대하지 않는다.

## 비교 실험 최소 조건

- 비교 전에 가설, 평가 입력, 기대 판정, 성공 기준을 정한다. 개발에 사용한 사례와 별도 확인용 사례를 구분한다.
- 구조 개선 효과를 볼 때 같은 비교 묶음의 모델, 설정, 입력, 환경과 실제 자원 조건을 맞춘다. 이는 배포 사용자의 버전이나 한도를 고정하는 정책이 아니다. 모델까지 바꾸면 그 효과를 분리하지 못했다고 명시한다. [환경 변경 기준 — 「사용자 환경의 변경과 호환성」](../design/workflow/verification.md)에 따라 변한 조건과 확인 범위를 따로 기록한다.
- 정상, 실패, 경계 사례와 게이트가 켜져야 할 때, 꺼져야 할 때를 함께 포함한다. 성공 사례만 고르지 않는다.
- 반복 횟수와 모든 시도의 결과를 보존한다. 환경 장애도 별도 분류해 남기고, 작은 표본의 성공률을 일반적 신뢰성으로 확대하지 않는다.
- 실행마다 초기 상태를 분리하고 캐시, 실행 순서, 이전 시도의 잔여 파일 영향을 기록한다. 변동성이 있는 비교에는 가능하면 순서를 교차한다.
- 모델의 완료 선언보다 테스트 결과와 최종 파일 상태를 확인한다. 판정기 자체의 오류, 누락도 점검하고 필요하면 사람이 판정을 대조한다.
- 검증 결과, 명령, 종료 코드, 입력 revision, 환경, 원시 출력, 집계 기준을 함께 보존한다. 수집하지 못한 항목은 비워 두고 이유를 쓴다.

이 기준은 작업별 평가, 개발 중 로그 보존을 권하는 [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)과, 반복 실행, 명확한 판정, 균형 잡힌 사례, 격리된 환경을 설명하는 [Anthropic 에이전트 평가 지침](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)을 이 작업에 맞게 좁힌 것이다. 자원 조건이 평가 결과를 바꿀 수 있다는 [인프라 변동 연구](https://www.anthropic.com/research/infrastructure-noise)도 비교 조건을 고정하는 근거로 참고했다. 특정 평가 서비스 도입을 결정한 것은 아니다.

[실행 경로와 인자 전달](experiments/runtime/2026-11-18_13-54-14-launch-arguments.md)은 ADR 0022의 전용 시작 명령을 구현하기 전 확인한 부분 근거다. 합성 인자 32회, 실제 Codex 도움말/버전 6회와 옵션 오류 2회, 모델 호출 0회다. `.cmd` 경유의 변수 확장을 관측하고 셸 없는 공식 npm 진입 후보를 비교했다. 기존 TUI/재개/권한 시험을 대체하지 않으며 제품 실행기, MCP와 토큰 효과는 아직이다. 상세는 E-024와 해당 원시 결과/검사에 연결했다.

## 2026-11-18 실제 터미널 시작 준비와 첫 실패

[시험 기록](experiments/runtime/2026-11-18_14-23-43-terminal-start.md)에 시작 파일, Windows 자동 검사 11개와 미리보기, 사용자 첫 시작 오류를 보존했다. 기본 권한 상속 상태에서 `--add-dir`가 거부되고 PowerShell로 돌아왔다. 명시적 workspace-write 선택 인자를 추가한 뒤 영향받은 기존 4개와 신규 2개 검사는 통과했다. 후속 [인증 화면 관측](experiments/runtime/2026-11-18_14-38-50-terminal-auth.md) 뒤 [관측 기록 (입력 화면 복귀)](experiments/runtime/2026-11-18_14-38-50-terminal-auth.md)를 사용자가 확인했다. 이어 [WIKI 읽기와 수정 표본](experiments/runtime/2026-11-18_14-49-24-terminal-io.md)을 실제 파일과 대조했다. 상태 한 줄만 바뀌고 나머지 바이트는 보존됐다. 같은 세션 재개 뒤 프로젝트/WIKI 권한, 직전 변경 설명과 파일 상태도 확인했다. 사용자는 재개 대화 선택 외 추가 요청이 없었다고 보고했다. 인자/모의 프로세스의 PASS를 실제 접근 성공으로 확대하지 않는다. 원인은 [E-025 — 「E-025 — 첫 터미널 시작에서 외부 WIKI 권한 거부」](issues.md)에 구분했다.

## 2026-11-18 로컬 MCP 읽기와 검색

[Windows MCP 시험](experiments/wiki-access/2026-11-18_15-21-34-mcp-read.md)은 파일 검사 9개, A/B의 SDK 연결 4회와 A 루트의 실제 Codex 검색/읽기를 구분한다. 최초 SDK 출력 형식과 Codex 상대 실행 경로 실패를 보존하고 보완했다. 실제 도구 기록, 사용자 보고의 추가 승인 없음과 문서 해시 보존을 확인했다. [후속 프로젝트/하위 경로 시험](experiments/wiki-access/2026-11-18_15-50-14-mcp-projects.md)에서 B 실제 사용과 A 재개를 확인했다. A/nested의 경로 실패는 루트 조회로 보정해 후보 명령의 SDK 연결 5곳, 경계 거부 2개와 실제 A/nested 읽기를 확인했다. 쓰기와 공정한 시간/토큰 비교는 남아 있다. MCP 정식 지원 완료나 첫 배포 포함 결정은 아니다.

[실제 문서 입력 사전 확인](experiments/wiki-access/2026-11-18_16-15-26-wiki-corpus.md)은 추적 Markdown 86개의 경로/크기/해시와 현재 시험 한도를 대조했다. REQUIREMENTS가 64 KiB를 넘는 점을 확인했으며 실제 내용 복사, 성능 측정이나 AI 실행은 하지 않았다. 다음 비교의 품질/시간/토큰과 보존 조건은 [읽기와 검색 비교 — 「실제 문서를 이용한 읽기와 검색 비교」](../verification/acceptance.md)가 소유한다.

[사본의 직접/MCP 비교](experiments/wiki-access/2026-11-18_16-32-09-wiki-compare.md)는 후속 실행이다. Windows 일반 파일 사본 60개를 준비하고 긴 문서/검색 결과를 나눠 받도록 보완했다. 파일 검사 13개와 동일 코드 호출 140개, 원문/검색 결과 전체 대조가 통과했다. 원본 86개, 제품 Git/index와 기존 A/B 시험을 보존했다. SDK 시작/호출 시간은 부분 측정이며 AI 요청은 없었다. 실제 Codex의 읽기는 아래 후속 표본에서 비교했고 쓰기/복구는 남아 있다.

[실제 Codex의 같은 질문 비교](experiments/wiki-access/2026-11-18_16-50-18-codex-wiki-usage.md)는 0.170.0 / GPT-5.6-Sol low의 새 대화 두 개에서 진행했다. 각 한 요청에서 직접 접근 40.359초/151,978토큰, MCP 55.005초/281,195토큰을 관측했다. 총량에는 캐시 입력과 여러 응답이 포함되며 요금/한도 차감이 아니다. 추가 승인은 두 경우 없었고 원본 86개, 사본 각 60개와 제품 Git은 보존됐다. 두 답변의 필수 조건 누락, MCP 범위 오류/합산 잘림, 직접 인용 범위 오류를 함께 기록했다. 표본별 탐색이 달라 순수 통신 효과나 일반 우위를 확정하지 않는다. 모듈의 전역 config 쓰기는 없었지만 사용자 TUI 시작 뒤 그 해시가 달라졌고 시험 프로젝트의 trusted 항목이 관측됐다. 사전 본문 미보존에 따른 변경 범위 한계도 실행 근거에 남겼다.

## 시작 전 설정과 세션 조회

[Windows 호스트 조회](experiments/wiki-access/2026-11-18_17-52-34-host-query.md)는 Codex 0.170.0의 합성 프로젝트 설정, 권한 후보와 세션 메타데이터를 확인한 부분 근거다. 모델 요청은 없었다. 권한 후보와 실제 적용의 차이, app-server의 --profile 제한, DB 전용 목록의 미색인 기록 누락을 확인했으며 제품 실행 성공으로 계산하지 않는다. [진입 명세 — 「호스트 조회와 실행 인계」](../design/runtime/entry.md)와 E-027에 후속 조건을 연결했다.

[실제 설치 환경의 읽기 점검](experiments/wiki-access/2026-11-18_19-21-31-mcp-environment.md)은 Windows 설치본, 선언된 관련 설정과 모델 캐시를 읽고 전후 설정 보존을 확인했다. 조회한 숫자는 당시 근거이며 배포 상수가 아니다. 유효한 TUI 설정/합산 한도의 자동 발견이나 실제 MCP 수신은 확인하지 않았고 모델 호출도 없었다.
