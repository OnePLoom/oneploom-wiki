# WIKI 조회의 반복 호출과 답변 누락

> 검토와 관측 기록. 검토 당시의 후보와 관측을 보존한다. 현재 채택 범위는 결정 목록에서 확인하며, 미실행 계획이나 예비 시험을 제품 검증 완료로 해석하지 않는다.

상태: **통합 후보와 후속 세 방식의 실제 비교를 완료했으나 제품 수용에는 이르지 못한 사례**. 사용자 지정 2026-11-20에 기록을 시작했고 11/22 작업에서 직접 접근, 긴 값과 짧은 값 MCP를 추가 비교했다. 짧은 값은 반환 보존과 별개로 미완료 보고/답변이 미충족이었다. 11/22 사용자가 첫 배포의 직접 접근 우선/MCP 후속을 채택했다. 최적화 완료나 제품 배포 성과는 아니다. 현재 문서는 공개용 완성본이 아니며 배포 모듈의 기능/필수 문서에 포함하지 않는다.

## 사례 요약

프로젝트의 외부 WIKI를 로컬 MCP(같은 PC에서 실행되는 AI용 도구 연결 방식)로 읽는 후보를 실제 Windows Codex에서 확인했다. 도구가 원문을 반환하는 것만으로 충분한지 보기 위해 같은 문서/질문의 직접 파일 접근과 비교했다.

한 사용자 요청 안에서 MCP는 내부 모델 응답 21회와 약 72.2만 누적 토큰, 직접 접근은 4회와 약 13.9만 토큰을 기록했다. MCP는 실제 받은 원문의 필수 복구 예외도 최종 답에서 빠뜨렸다. 비슷한 문맥 크기에서 많은 응답이 반복됐으며 검색 입력, 호출 지침과 결과 활용을 함께 개선할 필요가 드러났다.

사례의 핵심은 MCP를 사용했다는 사실보다 **원문 전달, 최종 답변의 완전성, 반복 호출 비용을 분리해 측정하고 품질을 보존하는 개선을 검증하는 과정**이다. 최초 MCP/직접 접근 비교는 문제 발견 근거로 보존한다. 후속에서는 같은 환경의 기존 MCP와 개선 MCP를 새 대화에서 각각 한 번 실행했다. 누적 토큰은 38.5% 줄었지만 캐시 제외 입력+출력은 5.0% 늘고 개선본에서 도구 오류 세 번이 발생했다. 이를 최적화 완료나 요금 절감 성과로 포장하지 않는다.

11/22 후속에서는 입력 상한 안내와 짧은 cursor(이어 위치를 나타내는 값)를 보완해 세 방식을 다시 비교했다. 짧은 값은 긴 값보다 적은 시간/토큰을 썼지만, 처리한 검색량과 답변 품질도 달랐다. 아래 「긴 값과 짧은 값의 후속 비교」에 수치를 보존하고 동등 품질의 개선으로 인정하지 않은 이유를 설명한다.

| 판단 대상 | 현재 판정 |
| --- | --- |
| 트러블슈팅 사례로 계속 기록할 가치 | 있음. 실제 요청/도구 기록과 원문 대조, 실패와 비용을 추적할 근거가 있음 |
| 현재 근거로 뒷받침할 수 있는 주장 | 명시한 환경의 단건 전후 수치, 원문 전달/답변 대조, 품질 미충족으로 절감 성과를 인정하지 않은 판단 |
| 아직 근거가 부족한 주장 | MCP 최적화 완료, 일반적인 토큰/요금 절감률, 대규모 실무의 신뢰성 또는 무누락 보장 |
| 제품의 기본 경로 | 전용 시작 명령과 직접 접근 유지. 11/22 실제 비교 후 사용자 확인으로 MCP 첫 제공은 후속 검토 |

## 배경과 사용자 영향

제품은 조건부 하네스이며 WIKI 연결은 필요한 지식과 근거에 접근하는 수단이다. 로컬 MCP는 프로젝트별 WIKI를 도구로 제공하는 선택 경로로 검토했다. 처음부터 MCP를 핵심 성과로 정하거나 직접 접근보다 유리하다고 가정하지 않았다. 연결의 현재 목적과 채택 범위는 [진입 명세 — 「두 방식의 선택 제공」](../../design/runtime/entry.md)가 소유한다.

사용자가 바라는 것은 개발 요청에 필요한 요구사항/결정/예외를 정확히 찾고 활용하는 것이다. 반복 탐색이 많으면 같은 문맥을 모델에 넣는 횟수와 대기 시간이 늘 수 있다. 실제로 받은 예외를 답에서 빠뜨리면 그 답을 근거로 한 구현도 잘못될 위험이 있다. 다만 이번 시험에서 제품 코드가 잘못 수정되거나 운영 장애가 발생한 것은 아니다. 문서가 많은 실무 규모의 비용 증가 역시 아직 측정하지 않았다.

원문 전체/지정 구간의 보존, 사용자 환경에 맞춘 실행, 원본 비변경과 구독 비용의 신중한 해석은 기존 요구다. 기술 검토용 수치를 만들기 위해 시험 한도를 줄이거나 비교 대상을 느리게 만들지 않는다.

캐시 입력은 이전 입력의 재사용이며 입력 합계에 이미 들어 있다. 누적 토큰은 고유 문서의 양도, 계정의 실제 요금/주간 차감량도 아니다. 캐시를 제외한 입력+출력의 약 7% 차이와 전체 합계 약 5.2배를 어느 쪽도 구독 비용으로 환산하지 않는다. [비용 해석 — 「실제 비교의 토큰 해석」](../../discussions/integration/ai-tools.md)을 따른다.

실패와 후속 처리도 결과에 포함한다. MCP는 이어 검색 입력의 변형으로 한 호출이 거부됐다. 직접 방식은 첫 시작의 권한 거부 뒤 Workspace를 명시했고, 질문 안의 첫 검색 잘림/한글 깨짐 뒤 UTF-8로 다시 읽었다. 질문 처리 시간은 모델 작업 구간이며 그 전의 시작 실패나 사람의 대기 시간을 포함한 전체 도입 시간은 아니다. 두 요청 모두 처리 중 추가 승인창은 없었다는 사용자 관측이 있다.

## 원인 분석

| 분류 | 확인한 내용 | 남은 해석/검증 |
| --- | --- | --- |
| 관측 | 첫 입력, 마지막 입력과 평균 입력은 비슷하지만 내부 응답 횟수는 21/4회 | 누적 입력 차이를 설명한다. 응답을 줄여도 같은 품질이 나온다는 인과 검증은 아님 |
| 관측 | MCP는 단일 문자열 검색을 여러 번 수행. 직접 방식은 OR 검색과 여러 구간 읽기를 묶음 | 질의 표현력/묶음 처리가 호출 차이에 기여했을 가능성. 각 변경의 효과는 별도 검증 필요 |
| 정적 관찰 | 후보 지침은 합산 출력의 잘림을 피하려 한 응답을 출력하고 실행을 끝내도록 안내 | 보호 의도가 있으나 모델 개입 증가의 후보 원인. 지침만 제거하면 과거 잘림이 재발할 수 있음 |
| 관측 | MCP의 확인한 읽기/정상 검색 반환은 원문과 일치했지만 받은 복구 예외가 답에서 누락 | 전송 성공과 의미상 완전성은 별개. 특정 도구나 모델 하나가 원인이라고 확정하지 않음 |
| 관측 | 반환 cursor 472자와 다음 입력 476자가 다르고, 같은 서명에 다른 내용이 붙어 거부됨 | 입력 변형은 확인. 오류명이 expired_cursor여도 시간 만료/서버 재시작으로 단정하지 않음 |
| 정적 관찰 | 이어 검색 때 변경 감지를 위해 범위의 내용을 다시 읽을 수 있음 | 자료 증가 시 디스크 I/O 비용 후보. 실제 병목 시간/최대 메모리는 미측정 |

이 표본에서는 실제 자동 페이지 축소가 관측되지 않았다. 따라서 축소 재시도가 큰 토큰 차이의 원인이었다고 쓰지 않는다. MCP 쪽도 코드 실행과 일부 검색 묶음을 이미 사용했으므로 “코드 실행을 도입하지 않아 생긴 문제”로 단순화하지 않는다. 도구 정의가 많으면 비용이 늘 수 있다는 일반론도 이번 차이의 주원인으로 입증되지 않았다.

검색 정보의 입력 변형은 [E-029 — 「E-029 — 이어 검색 정보가 호출 과정에서 달라짐」](../issues.md), 실제 수신/품질 경계는 [E-026 — 「E-026 — MCP 부분 검사와 실제 Codex 연결의 차이」](../issues.md), 반복 호출 비용은 [E-030 — 「E-030 — WIKI 조회에서 누적된 모델 호출 비용」](../issues.md)에 연결한다.

## 대안 비교와 선택 상태

아래는 기록 시작 시점의 검토 요약이다. 현재 기술 선택의 원본은 [호출 비용과 개선 순서](../../design/integration/mcp.md)이며, 사례에는 이후 실제 선택과 변경 이유를 근거와 함께 남긴다.

| 대안 | 장점 | 단점/채택 조건 | 현재 상태 |
| --- | --- | --- | --- |
| 페이지 크기만 확대 | 일부 이어 받기 감소 가능, 변경량이 작음 | 반복 검색/값 전달/답변 누락은 남고 합산 잘림 위험 증가 | 핵심 해법으로 비추천 |
| 기존 라우팅과 복수 검색/구간 묶음, 정확한 이어 받기 연결 | 의미 있는 검색 단위로 모델 개입을 줄일 가능성. 필수 원문 확인과 함께 설계 가능 | 합산 출력, 일부 실패, 중복/누락과 호스트의 값 보관 수명 검증 필요 | 우선 구체화할 추천 후보, 최종 계약/구현 전 |
| 검색 색인과 의미 검색/재정렬 | 큰 자료에서 후보 찾기와 반복 스캔 개선 가능 | 구축/갱신, 오래된 결과, 추가 의존성과 로컬 자원 비용. 검색 상위 결과가 전체 검토를 보장하지 않음 | 필요성 측정 후 검토 |
| 직접 접근 기본안을 유지하고 MCP 제공 보류 | 구현/검증 범위를 줄이고 이미 필요한 경로에 집중 | MCP 선택 연결의 이점을 제공하지 못함 | 개선의 실익/품질/일정이 맞지 않을 때 가능한 결론 |

**기록을 시작한 11/20에는 사례 구성과 추천 후보를 정리했으며 최종 기술안은 채택하지 않았다.** 11/21의 통합 개선 범위 선택은 아래 진행 이력에 구분한다. 원칙은 읽어야 할 정보를 생략하기보다 불필요한 탐색/입력 반복을 줄이는 것이다. 지침만 늘리기, 잘못된 값을 추정 보정하기, 원문/서명 검사를 빼기, 큰 결과를 무조건 한 번에 모으기는 해결 근거가 부족하다.

기술 검토를 위해 MCP를 억지로 유지하지 않는다. 동일한 필요를 직접 접근이 더 안정적이고 단순하게 충족한다는 결과가 나오면, MCP의 제공 범위를 줄이거나 미루는 결정도 이 사례의 결과로 남길 수 있다.

| 개선 전 비교 | 축소 재시도 지침을 포함한 당시 후보와 직접 접근을 같은 질문으로 비교 | 두 요청 완료. 문제 발견 근거로 보존 |
| 원인 분석 | 기존 로그를 재집계하고 호출/입력, 원문 수신과 답변 반영을 분리 | 완료, 새 AI 요청 없음 |
| 개선안 구체화와 결정 | 11/21 복수 검색/묶음 읽기/next 재사용, 합산 출력과 일부 실패를 통합한 범위 선택 | 사용자 범위 선택 완료, 별도 후보 구현/코드 검사 완료 |
| 후보 수정과 검증 | 11/21 코드 검사와 11/22 실제 비교의 실행 ID 연결 | Windows 코드/SDK 검사와 실제 두 요청 비교 완료. 값 전달과 비용 판단은 보완 필요 |
| 입력 안내 후속 보완 | 11/22 현재 연결의 페이지 최대/기본값 노출과 초과 입력의 실제 값 안내 | Windows 코드/SDK 9개 조건 최종 PASS. 후속 실제 짧은 값 요청에서도 상한 초과 입력 1회 관측 |
| 이어 읽기 값 단축 후보 | 11/22 요청 정보 1회 보관, 고정 길이 서명값, 보관 한도와 재시도 보호 | Windows 코드/SDK 63개 조건 최종 PASS. 실제 값 5개 정확히 전달, 미완료 보고와 답변 일부 누락은 남음 |
| 세 방식 후속 비교 | 11/22 직접 접근/긴 값/짧은 값 각 한 요청 | 세 요청 수집/검토 완료. 짧은 값의 비용 감소를 같은 작업량/품질의 개선으로 채택하지 않음 |

구현 뒤에는 바뀐 코드/지침과 이유, 원래 실패를 막는 검사, 유지한 보호 조건을 여기에 연결한다. 서로 독립된 변경 효과를 말하려면 해당 변경을 분리한 비교가 있어야 한다. 여러 변경을 한 번에 적용했다면 전체 변경 묶음의 효과로만 설명한다. 보기 좋은 원인/결과를 만들려고 과거 실패나 중간 시도를 지우지 않는다.

11/21 사용자는 시간 제약을 고려해 [통합 개선 범위 — 「첫 개선 후보와 선택 범위」](../../design/integration/mcp.md)를 선택했다. 기존 두 도구를 확장해 복수 검색, 여러 파일/구간 읽기와 정확한 next 전달, 합산 출력/부분 실패를 함께 다뤘다. [통합 후보](../experiments/wiki-access/2026-11-21_22-27-02-mcp-batch.md)의 Windows 코드/SDK 42개 조건과 최초 발췌 오류의 수정/재검사를 보존했다. 이어 11/22 실제 비교에서 묶음 기능은 사용됐지만 호스트 값 전달 예시는 사용되지 않았다. 내부 검사의 통과와 실제 자동 연결은 구별한다. 여러 변경을 함께 적용했고 AI의 탐색 선택도 달라 개별 변경 하나의 효과로 귀속하지 않는다.

## 검증 설계와 개선 전후 결과

주 비교는 **기존 MCP와 개선한 MCP**다. 직접 접근은 별도 기준으로 두어 MCP를 유지할 실익을 함께 판단한다. 새 비교 시 환경이 바뀌었다면 현재 사용자 환경에서 보존된 기존 후보와 개선 후보를 함께 비교하는 안을 먼저 정한다. 과거 설치본을 사용자에게 강제하거나 새 환경의 개선 결과를 과거 단건과 섞어 순수 개선율로 쓰지 않는다.

공통 평가 방법은 [비교 실험 최소 조건](../README.md), 실제 기능의 수용 입력은 [후속 비교의 질문과 판정](../../verification/acceptance.md)이 소유한다. 다음 표는 이 사례에서 그 기준을 어떻게 설명할지 정리한 것이며 별도 합격선을 만들지 않는다.

| 확인할 것 | 기록/판정 방법 |
| --- | --- |
| 비교 조건 | 같은 문서/질문/완료 범위와 사용자 설치본/모델/추론 설정, 후보 코드/설정 해시. 달라진 조건은 표에 명시 |
| 원문과 답변 품질 | 독립 원문 대조, 전체/구간/검색의 범위, 필수 사실/예외와 인용. MCP와 직접 결과가 같다는 사실만으로 정답 판정하지 않음 |
| 실제 사용 | Windows 사용자가 사용할 진입/권한/출력 조건. 큰 자료는 범위를 합의한 사본으로 검사하며 임시 한도나 지연으로 효과를 만들지 않음 |
| 호출과 시간 | 사용자 요청 수와 내부 모델 응답/도구 호출을 분리. 질문 처리 시간과 준비/사람 개입 시간을 구별 |
| 토큰과 자원 | 입력/캐시/출력, 오류와 재시도 비용을 보존. 색인이나 로컬 모델을 쓴다면 준비/메모리/실행 비용도 따로 확인 |
| 반복과 순서 | 회귀 사례와 개선에 사용하지 않은 확인용 사례를 구별. 횟수/예산/순서를 실행 전에 정하고 모든 시도 기록. 단건이면 단건으로 보고 |
| 통계와 한계 | 충분한 반복이 있을 때 중앙값과 변동 범위를 함께 표시. 작은 표본에 p99나 일반 신뢰성을 붙이지 않으며 캐시/서버 변동을 자동 통제했다고 가정하지 않음 |
| 실패 처리 | 필수 내용 누락을 숨긴 빠른 결과는 개선 성공이 아님. 실패 시도의 비용도 전체 결과에 남기며 성공 사례만 골라 성능을 보고하지 않음 |

### 실제 비교에서 남은 문제

묶음 검색과 읽기는 실제 사용됐고 겹친 본문은 원래 요청 번호와 함께 반환됐다. 그러나 AI는 next를 저장한 코드 객체로 보내지 않고 긴 문자열로 다시 작성했다. 검색 토큰은 한 글자가 줄었고, 읽기 토큰 안의 REQUIREMENTS.md는 REQUIREMEMENTS.md로 바뀌었다. 서버가 잘못된 서명을 거부한 것은 보호 성공이지만 자연스러운 이어 받기 성공은 아니다. 최종 답의 “만료”라는 표현도 실제 원인을 설명하지 못했다.

AI는 등록 상한 16384보다 큰 page_bytes=22000도 요청했다가 거부된 뒤 15000으로 수정했다. 실제 호스트 잘림은 관측하지 않았다. 일부 광역 검색과 첫 묶음은 미완료로 남았고, 최종 답에 필요한 사실은 다른 좁은 범위에서 확인했다. 마지막 답에는 이 크기 오류가 빠졌으므로 실패 보고까지 완전하다고 평가하지 않는다.

이 결과는 **묶음 처리의 호출 절감 가능성과 지침만으로는 값 전달을 보장할 수 없다는 한계**를 함께 보여 준다. [입력 안내 후속 후보](../experiments/wiki-access/2026-11-22_18-26-09-mcp-inputs.md)는 현재 설정의 크기를 명시하고 실행 시 다시 검사하도록 보완했다. 당시 Windows 코드/SDK 검사만으로 실제 모델의 추측 오류 감소를 주장하지 않았다. 후속 실제 결과는 아래 세 방식 비교에 구분한다. 초기 검사 경로/기대값 오류와 수정 이력도 보존했다. 기존 전후 토큰/시간 표를 이 후보의 성과로 바꾸지 않는다.

긴 값의 재작성 문제는 [이어 읽기 대안 비교 — 「이어 읽기 전달 방식의 선택」](../../design/integration/mcp.md)와 [관측 기록 (확장 조사)](../experiments/wiki-access/2026-11-22_18-26-09-mcp-inputs.md)로 구체화했다. 조사 뒤 이어서 진행 요청에 따라 [새 후보](../experiments/wiki-access/2026-11-22_19-16-43-mcp-cursor.md)에 요청 정보 1회 보관과 짧은 불변 cursor를 구현했다. 코드/SDK 63개 조건을 확인했으며 원문/응답 캐시는 추가하지 않았다. 코드의 정확한 값 전달과 서버 저장 여부는 함께 선택할 수 있는 별개 축이다. 기존 로그에서는 읽기 본문량도 달랐으므로 cursor를 줄이는 것만으로 전체 비용/시간이 해결된다고 가정하지 않는다. 수명/유실 코드 검사를 닫은 뒤 아래 실제 세 요청을 별도로 승인받아 완료했다. 기존 528~1052자 발급 사례와 새 고정 88자는 값의 형식 차이이며, 서로 다른 검사에서 얻은 길이를 실제 토큰 절감률로 바꾸지 않는다.

### 긴 값과 짧은 값의 후속 비교

[실행 근거](../experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)는 현재 Windows Codex 0.171.0 / GPT-5.6-Sol low에서 직접 → 긴 값 → 짧은 값 순서로 같은 문서 60개와 질문을 사용한 결과다. 각 방식의 새 대화에서 한 요청씩 수행했고 세 요청 모두 추가 승인창이 없었다. 긴 값 후보에도 복수 검색/묶음 읽기/입력 상한 안내가 들어 있으므로 앞의 최초 단일어 MCP와 혼동하지 않는다.

| 항목 | 직접 접근 | 긴 값 MCP | 짧은 값 MCP |
| --- | ---: | ---: | ---: |
| 내부 모델 응답 | 5회 | 18회 | 13회 |
| 캐시 포함 입력과 출력 합계 | 157,945 | 1,058,136 | 512,380 |
| 캐시 제외 입력과 출력 합계 | 32,121 | 82,904 | 52,092 |
| 질문 처리 시간 | 66.596초 | 168.568초 | 91.486초 |
| 사전 필수 사실 | 15개 충족 | 15개 충족 | 14개 충족, 1개 부분 충족 |
| 오류/완료 한계 | 첫 검색 잘림/읽기 실패 후 재조회, 인용 두 줄 미수신 | 이번 요청에서 MCP 오류 없음 | 상한 초과 1회, 첫 검색 90줄 미수신 상태를 보고하지 않음 |

짧은 값은 88자 값 5개를 정확히 재사용했다. 긴 값도 496~608자 값 10개를 정확히 재사용했으므로 이번 표본에서 값 단축에 따른 오류 감소를 입증한 것은 아니다. 짧은 값의 첫 검색은 일치 283줄 중 193줄만 받은 뒤 다른 검색/읽기로 넘어갔다. 나머지 90줄이 모두 답변의 필수 근거였다고 단정하지 않지만, 미완료 범위가 남았다는 사실은 최종 답에서 빠졌다. 상한 초과 오류는 알려졌다.

필수 사실의 부분 충족은 일반 문서 조회가 빨라야 한다는 정성 기준을 빠뜨린 것이다. 같은 기준의 자동 저장 빈도와 일관된 응답 시간은 포함했다. 해당 원문은 이미 반환됐으므로 서버 전송 누락이 아니다. 정상 수신한 본문/위치는 원문과 일치했고 없는 수치 목표를 만들거나 핵심 정책을 뒤집은 주장은 관측하지 않았다. [관측 기록 (의미 검토)](../experiments/wiki-access/2026-11-22_20-01-18-mcp-cursor-run.md)와 [E-031 — 「E-031 — 이어 검색이 남은 상태의 완료 보고」](../issues.md)을 연결한다.

관측 수치만 보면 짧은 값은 긴 값보다 캐시 포함 합계 51.6%, 캐시 제외 합계 37.2%, 시간 45.7% 감소했다. 그러나 검색 처리량/질의가 다르고 필수 답변도 일부 빠졌으므로 **같은 일을 완수한 비용 절감으로 인정하지 않는다.** 직접 접근보다 캐시 제외 합계는 62.2%, 시간은 37.4% 많았다. 한 방식당 한 요청이고 전역 설정 해시 변화의 상세 원인도 확인되지 않아 일반 우위/열위로 확대하지 않는다.

이 결과를 바탕으로 사용자가 첫 배포의 직접 접근 우선/MCP 후속을 채택했고 핵심 조건부 하네스 명세로 복귀했다. [선택 근거 — 「세 방식 비교와 첫 제공 판단」](../../design/integration/mcp.md)는 보존하며, MCP 전체가 쓸모없다는 결론이나 후보 삭제가 아니다. 기술 검토에는 추가 기술 도입 자체보다 품질과 비용을 함께 평가해 수용을 보류한 과정을 설명할 수 있다.

## 재발 방지와 남은 한계

현재의 실패 사례는 이후 변경의 회귀 입력으로 유지한다. 반환 문자열의 보존, 전체 요청의 실제 수신, 필수 예외 반영과 합산 잘림을 함께 확인하고, 소스 변경/연결 종료/취소의 기존 안전 조건을 비용 절감 때문에 제거하지 않는다. 서버 측 묶음 구현은 부분 검증됐지만 실제 호출의 값 보관/전달과 오류 보고는 보완이 남았다.

남은 범위에는 큰 자료의 비용, 실제 자동 축소, 처리 내부 취소/늦은 응답과 쓰기가 있다. 현재 한 요청의 읽기/검색 결과로 이들을 통과시키지 않는다. 최신 미검증 목록은 [MCP의 남은 검증 — 「남은 검증과 비교 조건」](../../design/integration/mcp.md)을 참조한다.

## 핵심 판단

11/20 같은 세 질문에서 기존 MCP의 내부 응답은 21회였고 필수 예외가 누락됐다. 후속 단건 비교에서 짧은 값 후보도 직접 접근보다 캐시 제외 합계 62.2%, 시간 37.4%가 더 들었다. 값 전달 성공만으로 동등 품질의 개선을 인정하지 않았으며 실제 환경/표본 조건과 함께 해석한다.

긴 이어 읽기 값의 재입력과 반복 호출이 발생했다. 복수 검색/묶음 읽기와 짧은 식별자 후보를 비교했으나 값 전달의 개선만으로 답변 누락과 실행 비용이 해결되지는 않았다. 첫 제공은 직접 접근을 우선하고 MCP는 후속으로 남겼다. 수치는 위 실제 비교표와 같은 관측이며 일반적인 요금 절감률이나 제품 전체 품질로 확대하지 않는다.

## 구성의 참고 근거

가장 많이 쓰이는 단일 기술 검토 양식이라는 통계는 확인하지 않았다. 아래 1차 자료의 설명 원리를 참고해 이 실험에 맞게 작성했다. 사고 예시를 우리 운영 장애처럼 사용하거나 템플릿 원문/코드를 복제하지 않았다.

- [Google SRE의 postmortem 예시](https://sre.google/sre-book/example-postmortem/): 요약, 영향, 원인, 해결, 후속 조치와 학습을 구분하는 구성. 이번에는 운영 장애가 아닌 개발/검증 문제에 맞췄다.
- [GitHub의 Move Fast and Fix Things](https://github.blog/engineering/move-fast/): 기존 경로와 후보를 비교하고 결과 불일치와 성능을 함께 확인하는 실제 기술 사례. 해당 운영 실험 규모나 성과 수치를 우리에게 적용하지 않는다.
- [Anthropic의 에이전트 평가 지침](https://www.anthropic.com/research/demystifying-evals-for-ai-agents): 명확한 사례/판정, 반복과 실제 환경, 실행 기록 확인의 중요성을 참고했다. 특정 평가 제품/모델이나 원문의 예시 표본 수를 채택하지 않았다.
